빠른 시작

시작하기

Spring Boot 앱에서 Contexa를 켜는 가장 짧은 길입니다. 의존성을 넣고, AI 보안을 켜고, 전용 DB와 AI 모델을 설정하고, 실행해서 켜졌는지 확인합니다. 단계마다 자세한 설명은 설치 가이드에 있습니다.

사전 요구 사항

시작하기 전에 다음이 설치되어 실행 중인지 확인하세요.

요구 사항 버전 비고
Java 17+ Contexa는 Java 17 툴체인으로 빌드됩니다.
Spring Boot 3.x 빌드 · 시험 판 3.5.4. 4.x에서는 기동을 거부합니다.
PostgreSQL pgvector vector 확장이 있는 Contexa 전용 DB(코드는 PostgreSQL 판을 검사하지 않음)
AI 모델 채팅 + 임베딩 이 페이지는 로컬 Ollama 기준입니다. OpenAI · Anthropic도 됩니다.

데이터베이스 설정

Contexa 전용 데이터베이스를 만들고 vector 확장을 켜세요. Contexa의 표는 앱이 처음 기동할 때 Contexa가 이 DB에 만듭니다.

SQL 
CREATE USER contexa WITH PASSWORD 'change-me';
CREATE DATABASE contexa OWNER contexa;
\c contexa
CREATE EXTENSION IF NOT EXISTS vector;

Ollama 모델

채팅과 임베딩에 쓸 모델을 받으세요. 이름은 3단계 설정의 model 값과 같아야 합니다.

Shell 
ollama pull qwen3:8b
ollama pull mxbai-embed-large

의존성 추가

Contexa 스타터 하나가 Contexa 모듈 다섯(common · core · identity · iam · autoconfigure)을 모두 가져옵니다. AI 공급자 스타터와 PgVector 스타터는 가져오지 않으므로 함께 넣습니다.

Gradle (Kotlin DSL) 
dependencies {
    implementation("ai.ctxa:spring-boot-starter-contexa:0.1.0")
    implementation(platform("org.springframework.ai:spring-ai-bom:1.1.8"))
    implementation("org.springframework.ai:spring-ai-starter-model-ollama")
    implementation("org.springframework.ai:spring-ai-starter-vector-store-pgvector")
}

}

공급자 고르기 — 채팅 공급자 스타터는 쓸 것만 넣습니다. OpenAI면 spring-ai-starter-model-openai, Anthropic이면 spring-ai-starter-model-anthropic입니다. Anthropic은 임베딩 모델이 없으므로 임베딩용으로 OpenAI나 Ollama를 함께 둡니다. Spring AI BOM 1.1.8은 Contexa가 빌드 · 시험한 판입니다.

AI 보안 활성화

메인 클래스에 @EnableAISecurity를 붙이면 Contexa가 켜집니다. 붙이지 않으면 스타터가 있어도 Contexa의 자동 설정은 모두 빠집니다. 속성 없이 쓰면 SANDBOX 모드이고 인증 소유권은 HOST_OWNED입니다. 이때 Contexa는 보안 체인을 만들지 않고, 로그인과 접근 규칙은 앱의 Spring Security가 그대로 맡습니다. 로그인을 Contexa에 맡기려면 @EnableAISecurity(mode = SecurityMode.FULL)을 씁니다(무엇이 달라지나, 어노테이션 참조).

Java 
@SpringBootApplication
@EnableAISecurity
public class MyApplication {

    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}

내부 동작 — @EnableAISecurity는 AiSecurityImportSelector를 통해 AiSecurityConfiguration을 가져옵니다. 앱에 PlatformConfig 빈이 없으면 이 구성이 기본 PlatformConfig를 만들고, 그 구성으로 보안 체인을 만드는 것은 Contexa가 로그인을 맡을 때(CONTEXA_OWNED)뿐입니다.

로그인을 앱이 맡을 때(기본) 앱이 할 일 — ① 자기 SecurityFilterChain을 둡니다(없으면 Spring Boot 기본 보안이 걸려 모든 요청에 로그인을 요구하고, Contexa가 ERROR 로그로 알림). ② 그 체인에서 관리 화면 /contexa/admin/**를 ADMIN 역할로 보호합니다. ③ @EnableMethodSecurity로 메서드 보안을 켭니다(관리 화면의 @PreAuthorize가 걸리도록). ④ 로그인한 사용자를 SecurityContext에 인증된 Authentication으로 넣습니다. Contexa는 이 방식에서 관리 화면 URL 규칙도 메서드 보안도 만들지 않습니다. 예시 코드는 설치 가이드의 기존 로그인과 연결하기에 있습니다.

3

설정

application.yml에 앱의 DB, Contexa 전용 DB(필수), AI 모델을 적습니다.

YAML 
spring:
  application:
    name: my-app                     # contexa- 로 시작하지 않게
  datasource:                        # 앱의 기본 DB
    url: jdbc:postgresql://localhost:5432/myapp
    username: myapp
    password: ${MYAPP_DB_PASSWORD}

contexa:
  datasource:                        # Contexa 전용 DB(필수)
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
  llm:
    selection:
      chat:
        mode: dynamic-priority       # 기본값, 이 표기 그대로
        priority: ollama
      embedding:
        mode: fixed                  # 기본값
        priority: ollama
    chat:
      ollama:
        base-url: http://127.0.0.1:11434
        model: qwen3:8b
        keep-alive: 30m
    embedding:
      ollama:
        dedicated-runtime-enabled: false
        model: mxbai-embed-large
        dimensions: 1024

Contexa 전용 DB는 필수 — contexa.datasource.url이 없으면 contexa.datasource.url must be configured for @EnableAISecurity로 기동이 멈춥니다. 앱 DB와 같은 주소도 기본으로 거부됩니다. 기존 앱에는 contexa.datasource.isolation.contexa-owned-application: true를 적지 마세요. 이 값이면 앱의 기본 DB 연결이 Contexa DB로 바뀔 수 있고 기능 진단이 엄격해집니다.

앱 이름 — spring.application.name이 contexa-로 시작하면 Contexa는 그 앱을 Contexa 소유 앱으로 보고 기능 진단을 FAIL_FAST로 합니다. 그러면 채팅 모델 · 벡터 저장소 같은 필수 부품이 빠졌을 때 기동이 멈춥니다. 다른 이름을 쓰세요.

Ollama 설정 — contexa.llm.chat.ollama.base-url을 적으면 Contexa가 그 Ollama 서버로 채팅 모델과 (같은 서버로) 임베딩 모델을 직접 만듭니다. 그래서 Spring AI의 spring.ai.ollama.*를 따로 적지 않아도 됩니다. model을 비우면 채팅은 qwen3:8b, 임베딩은 mxbai-embed-large입니다. keep-alive는 모델을 메모리에 둘 시간, dedicated-runtime-enabled: true는 임베딩만 다른 Ollama 서버(contexa.llm.embedding.ollama.base-url)에서 돌릴 때, dimensions는 임베딩 차원(기본 1024)입니다.

OpenAI · Anthropic — 공급자 키는 contexa.llm 아래가 아니라 Spring AI 설정에 둡니다: spring.ai.openai.api-key, spring.ai.anthropic.api-key. 그리고 contexa.llm.selection.chat.priority를 그 공급자로, 임베딩은 contexa.llm.selection.embedding.priority를 openai 또는 ollama로 둡니다(최소 설정).

모델 우선순위 — contexa.llm.selection.chat.priority는 쉼표로 구분한 공급자 목록(ollama, anthropic, openai)이고 기본값은 openai,anthropic,ollama입니다. Contexa는 목록 순서대로 공급자의 모델을 찾고, 쓸 수 없으면 다음 공급자로 넘어가며, 목록에 없더라도 있는 모델을 마지막에 씁니다. contexa.llm.selection.chat.mode는 dynamic-priority(기본, 목록 순서) · fixed(공급자 하나) · spring-primary(Spring @Primary 빈)이고, 값은 이 소문자-하이픈 표기 그대로 적어야 합니다. 임베딩은 벡터 차원이 고정되므로 fixed로 공급자 하나만 씁니다.

실행 및 확인

애플리케이션을 시작하고 Contexa가 켜졌는지 확인하세요.

Shell 
# Gradle
./gradlew bootRun

# Maven
mvn spring-boot:run

확인: 기동 로그

  • [IamSeedData] OSS schema provenance verified. — Contexa DB의 표가 준비됐습니다.
  • Skipping Contexa-owned authentication chain bootstrap in HOST_OWNED mode — 로그인을 앱이 맡는 방식으로 켜졌습니다.
  • ERROR 수준의 [ContexaCapability] ... — 채팅 모델 · 벡터 저장소 같은 부품이 빠졌습니다. 이대로면 판정이 나오지 않습니다(문제 해결).

확인: 자동 설정 리포트

--debug 플래그로 기동하면 어떤 Contexa 자동 설정이 적용됐는지 볼 수 있습니다.

Shell 
./gradlew bootRun --args='--debug'

양성 매치(positive matches)에서 CoreInfrastructureAutoConfiguration, CoreDataAutoConfiguration, CoreLLMAutoConfiguration 같은 io.contexa 자동 설정을 확인하세요. @EnableAISecurity가 없으면 이것들은 모두 빠집니다.

확인: Actuator 엔드포인트

spring-boot-starter-actuator를 넣으면 Health 엔드포인트와, Contexa 기능 진단 결과를 보여 주는 contexacapabilities 엔드포인트를 쓸 수 있습니다(웹으로 열려면 Spring Boot의 management.endpoints.web.exposure.include에 넣습니다).

Shell 
curl http://localhost:8080/actuator/health
curl http://localhost:8080/actuator/contexacapabilities

데이터베이스 필수 — Contexa 전용 DB에 연결할 수 없거나 그 DB에 Contexa 표가 일부만 있으면 Contexa는 기동하지 않습니다. 실행 전에 contexa.datasource.*가 맞고 DB와 vector 확장이 있는지 확인하세요.

메서드 수준 보안

첫 번째 메서드 보호하기

AI 판정으로 보호할 메서드에 @Protectable을 붙이세요. 호출 전에 정책과 그 사용자의 저장된 판정을 확인하고(BLOCK · CHALLENGE · ESCALATE면 실행하지 않음), 실행이 끝나면 분석을 맡깁니다. 기본은 응답이 나간 뒤 판정하고 그 판정은 다음 호출부터 적용되며, sync = true면 그 호출 안에서 판정합니다. 호출할 때 Spring Authentication이 있어야 하고, 없거나 익명이면 거부됩니다.

Java 
@Service
public class OrderService {

    @Protectable
    public Order getOrder(Long orderId) {
        return orderRepository.findById(orderId)
                .orElseThrow(() -> new OrderNotFoundException(orderId));
    }
}

자주 쓰는 @Protectable 속성

속성 타입 기본값 설명
ownerField String "" 행 단위 소유자 확인에 쓸 대상 객체의 필드(또는 getter) 이름. 그 값을 로그인 사용자 이름과 비교합니다(관리자는 건너뜀). 비우면 확인하지 않습니다.
sync boolean false true면 메서드가 반환되기 전에 그 호출 안에서 판정합니다(응답이 늦어짐). false면 분석 사건만 내고 판정은 응답 뒤에 비동기로 합니다.

속성은 모두 9개입니다(verificationRequired, category, sensitivity, actions, importance, privileged, exportSensitive 포함). 전체는 @Protectable 참조에 있습니다.

AI 판정

다음 단계 — 판정 다섯 가지

Contexa가 분석한 요청에는 판정(ZeroTrustAction)이 저장되고, 그 사용자의 다음 요청에 적용됩니다. 집행 모드가 ENFORCE(기본)일 때입니다.

판정 상태 코드 유효 시간 동작
ALLOW 200 15초 요청이 그대로 처리됩니다.
BLOCK 403 기한 없음 거부됩니다. 판정 권한은 ROLE_BLOCKED이고, 관리자가 풀거나 차단 해제 MFA를 거칠 때까지 유지됩니다.
CHALLENGE 401 1,800초 추가 인증(MFA)을 요구합니다. 판정 권한은 ROLE_MFA_REQUIRED.
ESCALATE 423 300초 검토 보류로 잠시 기다리게 합니다. 판정 권한은 ROLE_REVIEW_REQUIRED.
PENDING_ANALYSIS 통과(503) — 저장된 판정이 없는 상태입니다. 요청은 통과하고 분석이 시작됩니다(판정 권한 ROLE_PENDING_ANALYSIS). 에이전트 요청과 sync = true 메서드는 그 자리에서 판정하며, 판정을 받지 못하면 503으로 거부됩니다.

판정은 AI 모델이 내립니다 — 판정 엔진이 요청의 사실(로그인 정보, 행위 기준선, 과거 판정 기록 등)을 모아 AI 모델에 묻고, 정책 규칙을 따로 짜지 않아도 판정이 나옵니다. 기본은 응답이 나간 뒤 비동기로 판정합니다. 로그인을 앱이 맡는 기본 방식에서는 판정이 @Protectable 메서드에서 집행되고, URL 단계 집행은 Contexa가 로그인을 맡을 때 동작합니다. 자세한 것은 판정 엔진에 있습니다.
