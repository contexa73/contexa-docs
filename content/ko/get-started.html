빠른 시작

시작하기

CONTEXA는 Spring Boot 앱에 의존성으로 붙이는 보안 라이브러리입니다. 사용자가 보호한 메서드를 호출하면 AI 모델이 그 요청을 분석해 허용(ALLOW), 추가 인증(CHALLENGE), 검토 보류(ESCALATE), 차단(BLOCK) 중 하나로 판정합니다. CONTEXA는 이 판정을 저장해 두었다가 기본적으로 그 사용자의 다음 요청부터 적용합니다. 이 페이지는 CONTEXA를 앱에 켜는 가장 짧은 길입니다. 의존성을 넣고, 어노테이션 하나로 AI 보안을 켜고, 전용 DB와 AI 모델을 설정하고, 앱을 실행해 켜졌는지 확인한 뒤, 메서드 하나를 보호해 봅니다. 단계마다 자세한 설명은 설치 가이드에 있습니다.

가장 빠른 방법: CLI가 아래 과정을 모두 대신합니다. Spring Boot 3 프로젝트 폴더(빈 폴더면 예제 앱을 만들어 줍니다)에서:

curl -fsSL https://install.ctxa.ai | sh      # Windows: irm https://install.ctxa.ai/install.ps1 | iex
contexa init

CLI는 쓸 AI 모델을 묻고, 로컬 pgvector PostgreSQL과 그 모델을 준비하고, 프로젝트에 의존성 · @EnableAISecurity · 설정을 추가하고, 의존성이 풀리는지 확인한 다음, 앱을 실행할지 물어봅니다. 되돌리려면 contexa reset을 씁니다. 하는 일은 CLI로 설치에 있습니다. 아래 단계는 같은 일을 손으로 하는 방법입니다.

사전 요구 사항

시작하기 전에 다음이 설치되어 실행 중인지 확인합니다.

요구 사항 버전 비고
Java 17+ CONTEXA는 Java 17 툴체인으로 빌드됩니다.
Spring Boot 3.x CONTEXA를 빌드하고 시험한 판은 3.5.4입니다. 4.x에서는 기동을 거부합니다. 서블릿(Spring MVC) 웹 앱만 지원하므로, 리액티브(WebFlux) 설정, Spring AOT 처리, 네이티브 이미지도 기동을 거부합니다.
PostgreSQL pgvector CONTEXA가 자기 표와 벡터 저장소를 두는 전용 DB입니다. 앱의 DB와 따로 만들고, vector 확장이 필요합니다. 코드는 PostgreSQL 판을 검사하지 않습니다.
AI 모델 채팅 + 임베딩 채팅 모델은 판정을 만들고, 임베딩 모델은 뜻이 비슷한 과거 기록을 찾는 데 씁니다. 이 페이지는 로컬 Ollama 기준이고, OpenAI와 Anthropic도 쓸 수 있습니다.

CREATE EXTENSION IF NOT EXISTS vector;

AI 보안 활성화

메인 클래스에 @EnableAISecurity를 붙이면 CONTEXA가 켜집니다. 붙이지 않으면 스타터가 클래스패스에 있어도 CONTEXA의 자동 설정이 하나도 적용되지 않으므로 앱은 그대로입니다.

속성 없이 쓰면 기본 방식(SANDBOX)입니다. 로그인 기능이 이미 있는 앱에 CONTEXA를 덧붙이는 방식이어서, 로그인 · 세션 · 접근 규칙은 앱의 Spring Security가 그대로 맡습니다. 코드에서는 이를 로그인을 앱이 맡는다는 뜻의 HOST_OWNED라고 부릅니다. SANDBOX는 시험 환경이라는 뜻이 아니라 이 방식의 이름입니다. 이 방식에서 CONTEXA는 로그인 체인을 만들지 않습니다. 대신 앱의 Spring Security 필터 체인(Filter Chain)이 사용자를 정한 바로 뒤에서 CONTEXA의 필터가 돌며, 모든 경로에 저장된 판정을 적용합니다. 관리 화면 /contexa/admin/**은 CONTEXA가 자기 체인으로 직접 지킵니다.

로그인까지 CONTEXA에 맡기려면(CONTEXA_OWNED) @EnableAISecurity(mode = SecurityMode.FULL)을 씁니다. 이때는 CONTEXA의 체인이 로그인 · MFA · 세션을 처리하고, 앱의 일부 응답이 달라집니다(무엇이 달라지나, 어노테이션 참조). 이 페이지의 나머지는 기본 방식을 기준으로 합니다.

Java 
@SpringBootApplication
@EnableAISecurity
public class MyApplication {

    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}

기본 방식에서 앱이 할 일 — 로그인은 앱이 맡으므로, CONTEXA가 사용자를 알아보려면 앱이 두 가지를 해 두어야 합니다.

① 자기 SecurityFilterChain을 둡니다. 없으면 Spring Boot의 기본 보안이 걸려 모든 요청에 로그인을 요구합니다. CONTEXA는 이 상황을 WARN 로그로 알리고, 앱에 로그인할 수 있는 사용자(UserDetailsService, AuthenticationProvider, AuthenticationManager 빈)도 없으면 기동을 거부합니다.

② 로그인한 사용자를 그 체인의 필터에서 SecurityContext에 인증된 Authentication으로 넣습니다. CONTEXA의 필터는 이 값을 읽어 누구의 요청인지 알아냅니다. 이 값이 없으면 CONTEXA는 익명 요청으로 보고 판정을 적용하지 않습니다.

관리 화면 /contexa/admin/**는 CONTEXA의 자기 체인과 관리자 로그인이 지키므로 앱 체인이 막을 필요가 없습니다. 예시 코드는 설치 가이드의 기존 로그인과 연결하기에 있습니다.

내부 동작 — @EnableAISecurity는 AiSecurityImportSelector를 통해 설정 클래스 AiSecurityConfiguration을 가져옵니다. 앱에 PlatformConfig 빈이 없으면 기본 PlatformConfig를 만들지만, 이 설정으로 로그인 체인을 만드는 것은 CONTEXA가 로그인을 맡을 때(CONTEXA_OWNED)뿐입니다.

3

설정

application.yml에 세 가지를 적습니다. 앱이 이미 쓰는 DB(있으면 그대로 둡니다), CONTEXA 전용 DB(필수), AI 모델입니다.

YAML 
spring:
  application:
    name: my-app                     # contexa- 로 시작하지 않게
  datasource:                        # 앱의 기본 DB
    url: jdbc:postgresql://localhost:5432/myapp
    username: myapp
    password: ${MYAPP_DB_PASSWORD}

contexa:
  datasource:                        # Contexa 전용 DB(필수)
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
  llm:
    selection:
      chat:
        mode: dynamic-priority       # 기본값, 이 표기 그대로
        priority: ollama
      embedding:
        mode: fixed                  # 기본값
        priority: ollama
    chat:
      ollama:
        base-url: http://127.0.0.1:11434
        model: qwen3:8b
        keep-alive: 30m
    embedding:
      ollama:
        dedicated-runtime-enabled: false
        model: mxbai-embed-large
        dimensions: 1024

CONTEXA 전용 DB는 필수 — contexa.datasource.url을 적지 않으면 contexa.datasource.url must be configured for @EnableAISecurity 메시지와 함께 기동이 멈춥니다. 앱의 DB(spring.datasource.url)와 같은 주소를 적어도 기본으로 거부됩니다. 이미 DB가 있는 앱에는 contexa.datasource.isolation.contexa-owned-application: true를 적지 않습니다. 이 값은 CONTEXA DB를 앱의 DB로도 쓰겠다는 선언이라서, 앱의 기본 DB 연결이 CONTEXA DB로 바뀔 수 있고 기능 진단(필수 부품이 갖춰졌는지 기동 때 보는 검사)도 더 엄격해집니다.

앱 이름 — spring.application.name이 contexa-로 시작하면 CONTEXA는 그 앱을 CONTEXA 자체의 앱으로 보고 기능 진단을 FAIL_FAST로 합니다. 그러면 채팅 모델 · 벡터 저장소 같은 필수 부품이 빠졌을 때 기동이 멈춥니다. 일반 앱에서는 같은 문제를 ERROR 로그로만 알리고 기동은 계속합니다. contexa-로 시작하지 않는 이름을 씁니다.

Ollama 설정 — contexa.llm.chat.ollama.base-url을 적으면 CONTEXA가 그 Ollama 서버에 연결하는 채팅 모델을 직접 만들고, 같은 서버로 임베딩 모델도 만듭니다. 그래서 Spring AI의 spring.ai.ollama.*를 따로 적지 않아도 됩니다. model을 비우면 채팅은 qwen3:8b, 임베딩은 mxbai-embed-large를 씁니다. keep-alive는 채팅 모델을 메모리에 둘 시간입니다. dimensions는 임베딩 벡터의 차원이고 기본은 1024입니다. dedicated-runtime-enabled: true는 임베딩만 다른 Ollama 서버에서 돌릴 때 켜며, 그 서버 주소는 contexa.llm.embedding.ollama.base-url에 적습니다.

OpenAI · Anthropic — Ollama 대신 이 공급자를 쓰려면 두 가지를 바꿉니다. 첫째, API 키는 contexa.llm 아래가 아니라 Spring AI 설정에 적습니다: spring.ai.openai.api-key, spring.ai.anthropic.api-key. 둘째, 채팅은 contexa.llm.selection.chat.priority를 그 공급자로 바꾸고, 임베딩은 contexa.llm.selection.embedding.priority를 openai 또는 ollama로 둡니다(최소 설정).

모델 우선순위 — contexa.llm.selection.chat.priority는 쉼표로 구분한 공급자 목록(ollama, anthropic, openai)이고 기본값은 openai,anthropic,ollama입니다. CONTEXA는 목록 순서대로 공급자의 모델을 찾습니다. 어떤 공급자를 쓸 수 없으면 다음 공급자로 넘어가고, 목록의 공급자를 모두 쓸 수 없으면 목록에 없는 모델이라도 쓸 수 있는 것을 마지막에 씁니다. 고르는 방식은 contexa.llm.selection.chat.mode로 정합니다. dynamic-priority(기본)는 목록 순서, fixed는 공급자 하나, spring-primary는 Spring의 @Primary 빈을 씁니다. 값은 이 소문자-하이픈 표기 그대로 적어야 합니다. 임베딩은 벡터 차원이 고정되므로 fixed로 공급자 하나만 씁니다.

4

실행 및 확인

앱을 시작한 뒤 세 가지로 CONTEXA가 켜졌는지 확인합니다. 기동 로그, 자동 설정 리포트, Actuator 엔드포인트입니다.

Shell 
# Gradle
./gradlew bootRun

# Maven
mvn spring-boot:run

확인: 기동 로그

기동이 끝나면 로그에서 다음 줄을 찾습니다. 앞의 두 줄이 보이면 CONTEXA가 켜진 것입니다.

  • [IamSeedData] OSS schema provenance verified. — CONTEXA 전용 DB의 표가 준비되었다는 뜻입니다. 처음 기동이면 CONTEXA가 이 줄 직전에 표를 만듭니다.
  • Skipping Contexa-owned authentication chain bootstrap in HOST_OWNED mode — 로그인을 앱이 맡는 기본 방식으로 켜졌다는 뜻입니다. CONTEXA는 로그인 체인을 만들지 않고 건너뛰었습니다.
  • ERROR 수준의 [ContexaCapability] ... — 채팅 모델 · 벡터 저장소 같은 필수 부품이 빠졌다는 뜻입니다. 앱은 계속 기동하지만(앱 이름이 contexa-로 시작하면 기동이 멈춥니다), 이대로면 판정이 나오지 않습니다(문제 해결).

확인: 자동 설정 리포트

Spring Boot는 --debug 플래그로 기동하면 적용된 자동 설정의 리포트를 출력합니다. 이 리포트에서 어떤 CONTEXA 자동 설정이 적용되었는지 볼 수 있습니다.

Shell 
./gradlew bootRun --args='--debug'

리포트의 양성 매치(positive matches)에서 CoreInfrastructureAutoConfiguration, CoreDataAutoConfiguration, CoreLLMAutoConfiguration 같은 io.contexa 자동 설정을 찾습니다. @EnableAISecurity가 없으면 이것들은 모두 빠집니다.

확인: Actuator 엔드포인트

앱에 spring-boot-starter-actuator가 있으면 health 엔드포인트와, CONTEXA 기능 진단(필수 부품이 갖춰졌는지 보는 검사)의 결과를 보여 주는 contexacapabilities 엔드포인트를 쓸 수 있습니다. contexacapabilities는 웹으로 열려 있지 않으므로 Spring Boot의 management.endpoints.web.exposure.include에 넣어야 합니다.

Shell 
curl http://localhost:8080/actuator/health
curl http://localhost:8080/actuator/contexacapabilities

데이터베이스 필수 — CONTEXA 전용 DB를 쓸 수 없으면 CONTEXA는 켜지지 않습니다. 증상은 문제에 따라 다릅니다.

DB에 연결할 수 없거나(약 5초 동안 다시 시도합니다) DB 계정이 CONTEXA에 필요한 확장(vector 등)을 만들 수 없을 때: 기본 방식에서는 앱이 CONTEXA 없이 기동하고, 로그에 Contexa's database cannot be used로 시작하는 ERROR 한 줄이 남습니다. CONTEXA가 로그인을 맡는 방식에서는 앱이 기동하지 않습니다.

DB에 CONTEXA 표가 일부만 있을 때: Contexa schema is partially installed 오류로 기동이 멈춥니다. 빈 DB를 쓰거나 확인된 백업을 복원합니다.

실행 전에 contexa.datasource.*가 맞는지, DB와 vector 확장이 있는지 확인합니다.

메서드 수준 보안

첫 번째 메서드 보호하기

AI 판정으로 보호할 메서드에 @Protectable을 붙입니다. 보호한 메서드를 호출하면 CONTEXA는 그 사용자의 요청을 분석 대상으로 삼고, 이미 저장된 판정이 있으면 그 판정을 먼저 적용합니다.

Java 
@Service
public class OrderService {

    @Protectable
    public Order getOrder(Long orderId) {
        return orderRepository.findById(orderId)
                .orElseThrow(() -> new OrderNotFoundException(orderId));
    }
}

보호한 메서드를 호출하면 CONTEXA는 아래 순서로 검사합니다. 검사에 걸리면 메서드를 실행하지 않습니다.

  1. 로그인 확인. 호출할 때 로그인한 사용자의 Spring Authentication이 있어야 합니다. 없거나 익명이면 호출이 거부됩니다. 이 확인은 운영 모드가 관찰 모드(SHADOW)나 적용 모드(ENFORCE)일 때만 하고, 기본값은 ENFORCE입니다. 웹 요청도 사용자도 없는 스레드(예약 작업 등)의 호출은 판정할 사용자가 없으므로 그대로 실행하고, 실행했다는 기록만 남깁니다.
  2. 정책 확인. 그 메서드를 대상으로 한 정책을 평가합니다. 정책이 거부하면 메서드를 실행하지 않습니다. 대상 정책이 없으면 기본 결정인 허가(PERMIT)가 적용됩니다.
  3. 저장된 판정 확인. 그 사용자에게 차단(BLOCK), 추가 인증(CHALLENGE), 검토 보류(ESCALATE) 중 하나가 저장되어 있으면 호출을 거부합니다. 관찰 모드에서는 거부하지 않고 통과시키며 로그에 남깁니다.
  4. 실행과 분석 요청. 검사를 모두 통과하면 메서드가 실행되고, 끝난 뒤 CONTEXA가 분석 요청을 보냅니다. 응답은 판정을 기다리지 않습니다. 판정은 뒤에서 만들어져 그 사용자의 다음 호출부터 적용됩니다(sync = true는 아래 참고).

sync = true이면 정책 확인 뒤, 메서드를 실행하기 전에 그 호출 안에서 판정을 받습니다. 적용 모드에서는 판정이 ALLOW가 아니면 메서드를 실행하지 않고 거부하며, 응답은 그만큼 늦어집니다.

자주 쓰는 @Protectable 속성

속성 타입 기본값 설명
ownerField String "" 행 단위 소유자 확인에 쓸 필드(또는 getter) 이름입니다. 메서드 정책의 조건이 hasPermission(...)을 부를 때, 그 대상 객체에서 이 값을 읽어 로그인 사용자 이름과 비교합니다(ROLE_ADMIN 권한이 있으면 건너뜁니다). 비우면 소유자 확인을 하지 않습니다.
sync boolean false true면 메서드를 실행하기 전에 그 호출 안에서 판정합니다(응답이 늦어짐). false면 메서드가 끝난 뒤 분석 요청만 보내고, 판정은 뒤에서 비동기로 만들어 다음 호출부터 적용합니다.

속성은 모두 9개입니다. 위 표의 둘 말고도 verificationRequired, category, sensitivity, actions, importance, privileged, exportSensitive가 있습니다. 전체는 @Protectable 참조에 있습니다.

AI 판정

다음 단계 — 판정 다섯 가지

CONTEXA가 요청을 분석하면 판정(ZeroTrustAction)이 만들어져 사용자별로 저장되고, 그 사용자의 다음 요청부터 적용됩니다. 판정은 아래 다섯 가지입니다. 판정을 실제로 적용하는 것은 운영 모드가 적용 모드(ENFORCE, 기본값)일 때입니다.

판정 상태 코드 유효 시간 동작
ALLOW 200 15분 요청이 그대로 처리됩니다. 15분은 기본값이고 contexa.security.zerotrust.allow-validity로 바꿉니다.
BLOCK 403 기한 없음 요청을 거부합니다. 관리자가 풀 때까지, 또는 관리자가 MFA 해제를 허용한 경우 사용자가 차단 해제 MFA를 통과할 때까지 유지됩니다. CONTEXA가 로그인을 맡으면 사용자의 권한이 ROLE_BLOCKED 하나로 바뀝니다.
CHALLENGE 401 1,800초 추가 인증(MFA)을 요구합니다. API 요청은 401을 받고, 브라우저는 추가 인증 화면으로 이동합니다. CONTEXA가 로그인을 맡으면 사용자의 권한이 ROLE_MFA_REQUIRED 하나로 바뀝니다.
ESCALATE 423 300초 검토 보류입니다. 검토가 끝날 때까지 기다리라는 응답을 줍니다(API 요청은 423, 브라우저는 대기 화면). CONTEXA가 로그인을 맡으면 사용자의 권한이 ROLE_REVIEW_REQUIRED 하나로 바뀝니다.
PENDING_ANALYSIS 통과(503) — 아직 저장된 판정이 없는 상태입니다. 요청은 통과하고 분석이 시작됩니다. AI 에이전트 요청과 sync = true 메서드는 판정 없이 진행할 수 없으므로 그 자리에서 판정하며, 판정을 받지 못하면 503으로 거부됩니다. CONTEXA가 로그인을 맡으면 사용자의 원래 권한에 ROLE_PENDING_ANALYSIS가 더해집니다.

표의 ROLE_... 권한(판정 표시 권한)은 판정을 나타내는 표시입니다. CONTEXA가 로그인을 맡을 때만 사용자의 권한 목록에 들어가고, ALLOW는 원래 권한을 그대로 둡니다. 로그인을 앱이 맡는 기본 방식에서는 CONTEXA가 앱의 권한을 바꾸지 않습니다. 대신 CONTEXA의 필터와 @Protectable이 저장된 판정을 읽어 같은 응답을 냅니다.

운영 모드는 contexa.security.zerotrust.mode로 정합니다. 처음 도입할 때는 관찰 모드(SHADOW)로 두면 요청을 분석하고 판정을 기록하지만 요청은 막지 않습니다(관찰 모드로 안전하게 시작하기).

판정은 AI 모델이 만듭니다 — 판정 엔진이 요청의 사실(로그인 정보, 행위 기준선, 과거 판정 기록 등)을 모아 AI 모델에 묻습니다. 그래서 판정을 얻으려고 정책 규칙을 따로 쓸 필요가 없습니다. 분석은 보호한 메서드(@Protectable)를 호출할 때 일어납니다. @Protectable이 아닌 일반 URL 요청은 분석하지 않고, 저장된 판정을 적용받기만 합니다. 기본은 메서드가 끝난 뒤 비동기로 판정합니다. 저장된 판정은 로그인을 앱이 맡는 기본 방식에서도 모든 경로에 적용됩니다. 앱의 보안 체인이 사용자를 정한 바로 뒤에서 CONTEXA의 필터가 저장된 판정을 확인하고, @Protectable 메서드 앞에서 한 번 더 확인합니다. CONTEXA가 로그인을 맡을 때는 같은 필터가 CONTEXA의 체인 안에서 돕니다. 자세한 것은 판정 엔진에 있습니다.
