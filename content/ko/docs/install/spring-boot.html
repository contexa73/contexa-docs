기존 Spring Security 앱에 붙이기

이미 Spring Security로 로그인을 처리하는 앱에 CONTEXA를 붙여도 앱의 로그인 화면, 세션, 쿠키, URL 권한 규칙은 바뀌지 않습니다. 기본 방식에서는 앱이 로그인을 계속 담당하고, CONTEXA는 로그인한 사용자를 읽어 요청마다 판정을 적용합니다. 이 페이지는 무엇이 그대로이고 무엇이 달라지는지, 앱이 해야 할 일, 판정별로 사용자가 받는 응답을 설명합니다. CONTEXA가 로그인을 담당하는 방식은 후반부에서 설명합니다.

Spring Boot 판. CONTEXA는 Spring Boot 3.5.4로 빌드 · 시험됩니다. Spring Boot 4.x에서 @EnableAISecurity를 쓰면 ERROR 로그를 남기고 IllegalStateException으로 기동을 멈춥니다.

개요

기존 앱에 CONTEXA를 붙일 때 가장 먼저 정할 것은 로그인을 누가 맡는가입니다. 여기서 로그인은 로그인 화면, 세션, 쿠키, URL 권한 규칙을 가리킵니다. 선택지는 둘입니다.

  • 앱이 로그인을 맡는 방식(HOST_OWNED, 기본): 앱의 로그인 처리는 지금과 같습니다. CONTEXA는 앱이 로그인시킨 사용자를 읽고, 그 사용자의 요청에 판정을 적용합니다.
  • CONTEXA가 로그인을 맡는 방식(CONTEXA_OWNED): 로그인 화면, MFA, 세션, 보안 체인이 CONTEXA의 것으로 바뀝니다. 새로 만드는 앱이나 로그인을 CONTEXA로 옮기려는 앱에 맞습니다.

판정(Decision)은 CONTEXA의 AI가 한 사용자의 요청을 분석해 내리는 결론입니다. 허용(ALLOW), 추가 인증(CHALLENGE), 검토 보류(ESCALATE), 차단(BLOCK) 중 하나입니다. 어느 방식을 고르든 판정을 만들고 적용하는 일은 CONTEXA가 합니다.

아래 그림에는 CONTEXA의 세 구성 요소가 나옵니다. 요청 시점 필터는 요청이 들어올 때 그 사용자에게 저장된 판정을 읽어 적용하는 서블릿 필터입니다. 이 필터가 요청을 컨트롤러에 보내기 전에 저장된 판정을 적용하는 처리를 이 문서에서는 URL 단계라고 부릅니다. 인증 브리지는 앱의 로그인 결과를 요청마다 읽는 구성 요소입니다. 에이전트 관문은 AI 에이전트의 요청에서 호출 횟수 상한, 위임의 철회 · 만료, 좁혀진 허용 범위를 검사하고 필요하면 책임자 확인을 요청하는 구성 요소입니다(에이전트 통제). 그림은 두 방식에서 요청이 지나는 단계와 각 단계를 맡는 쪽을 보여 줍니다.

먼저 정할 것: 로그인을 누가 맡는가

인증 소유 방식(로그인을 누가 담당하는지)은 코드의 @EnableAISecurity나 설정으로 정합니다. 같은 선택을 어노테이션에서는 보안 모드(SANDBOX와 FULL)로, 설정에서는 인증 소유 방식(HOST_OWNED와 CONTEXA_OWNED)의 값으로 적습니다.

이렇게 쓰면인증 소유 방식함께 정해지는 것
@EnableAISecurity(속성 없음 = SANDBOX)HOST_OWNEDCONTEXA 소유 앱 설정(contexa.datasource.isolation.contexa-owned-application)은 false입니다. 이 설정은 CONTEXA의 DB를 앱의 기본 DB로도 쓸지 정하고, true이면 기능 진단도 더 엄격해집니다.
@EnableAISecurity(mode = SecurityMode.FULL)CONTEXA_OWNED앱에 자기 DB가 없고 이 설정을 따로 적지 않았으면 true입니다(아래).
설정 contexa.bridge.ownershipmode와 짝이 맞아야 함SANDBOX는 HOST_OWNED, FULL은 CONTEXA_OWNED와 짝입니다. 어긋나게 적으면 이유를 출력하고 기동을 멈춥니다. 적지 않으면 mode를 따릅니다. 모드를 코드 대신 설정으로 정하려면 contexa.ai.security.mode를 적습니다. 이 설정이 어노테이션보다 앞섭니다.
  • 이미 로그인이 있고 그대로 두려면 기본(HOST_OWNED)을 고릅니다. 판정을 만들고 모든 경로에 적용하는 일은 이 방식에서도 CONTEXA가 합니다. 앱이 할 일은 두 가지입니다(아래).
  • 로그인 · MFA · 세션까지 CONTEXA에 맡기려면 FULL을 고릅니다. 이 경우 보안 체인을 CONTEXA가 만들므로, 자기 SecurityFilterChain을 선언한 앱은 기동하지 않습니다(아래). 먼저 앱에서 달라지는 것을 확인합니다.
  • CLI를 쓰면 contexa init이 대신 고릅니다. 앱에 SecurityFilterChain이 있으면 HOST_OWNED, 없으면 CONTEXA_OWNED를 고르고, --ownership host|contexa로 직접 정할 수도 있습니다(CLI가 고르는 방법).

앱이 로그인을 맡을 때(기본)

이 방식에서 앱은 로그인을 지금처럼 처리합니다. CONTEXA는 앱 체인이 확인한 사용자를 읽고, 그 사용자에게 저장된 판정을 적용합니다. 이 소절은 그대로인 것, 달라지는 것, 앱이 할 일의 순서로 설명합니다.

그대로인 것

  • 로그인과 세션: CONTEXA는 앱의 SecurityFilterChain · UserDetailsService · 인증 제공자 · spring.security.* 설정과 세션 · 쿠키를 바꾸지 않습니다. 로그인 체인이나 AI 세션 저장소를 앱의 요청 경로에 붙이지도 않습니다.
  • URL 권한 규칙: 앱 체인이 먼저 사용자를 정하고 앱의 규칙을 적용합니다. CONTEXA의 필터는 그 뒤에 실행됩니다.
  • 앱 화면의 언어: 앱 화면은 앱이 정한 언어(Accept-Language, 앱의 LocaleResolver)를 유지합니다. 앱의 메시지 파일(messages.properties)이 있으면 앱의 문구를 먼저 보고, CONTEXA의 문구는 그 뒤에 둡니다. CONTEXA의 언어 해석기(기본 한국어)와 ?lang= 전환은 /contexa/ 아래 CONTEXA 화면에만 씁니다.
  • 앱의 DB: CONTEXA는 전용 DB(contexa.datasource.url)를 따로 씁니다. 앱의 DB 연결은 바꾸지 않습니다.

달라지는 것

  1. 모든 요청에 저장된 판정이 적용됩니다. 앱 체인 바로 뒤에서 CONTEXA의 서블릿 필터가 모든 경로(/*)의 요청을 확인합니다. 그 사용자에게 차단(BLOCK), 추가 인증(CHALLENGE), 검토 보류(ESCALATE) 판정이 저장되어 있으면 요청이 컨트롤러에 닿기 전에 CONTEXA가 응답합니다(판정과 응답).
  2. @Protectable 메서드(보호 메서드)가 분석 대상이 됩니다. 사용자가 @Protectable 메서드를 호출하면 CONTEXA가 그 요청을 분석하고, 메서드를 실행하기 전에 저장된 판정을 한 번 더 확인합니다. 관찰 모드(SHADOW)와 적용 모드(ENFORCE)에서는 로그인하지 않았거나 익명인 사용자의 호출을 거부합니다. 로그인 자체는 분석하지 않으므로, 사용자의 첫 판정은 그가 처음 호출하는 보호 메서드에서 나옵니다.
  3. 추가 인증 화면이 생깁니다. 판정이 추가 인증(CHALLENGE)이면 사용자는 CONTEXA의 추가 인증 화면 /contexa/step-up으로 이동합니다. 이 화면은 로그인을 대신하지 않습니다. 앱에 이미 로그인한 사용자에게 패스키나 메일 일회용 코드 같은 추가 인증만 요구합니다. 앱의 로그인 정보, 세션, 쿠키는 바뀌지 않습니다(HOST_OWNED의 추가 인증).
  4. /contexa/ 아래 경로를 CONTEXA가 씁니다. 추가 인증 화면과 판정 안내 화면(/contexa/step-up, /contexa/zero-trust/ 아래)은 로그인한 사용자에게만 답합니다. 이 경로에도 앱 체인의 URL 규칙이 먼저 적용되므로, 앱은 로그인한 사용자에게 이 경로를 허용해야 합니다. 앱의 규칙이 익명 요청을 허용하더라도 CONTEXA는 이 경로의 익명 요청에 401을 응답합니다. 앱 자신의 엔드포인트는 이 경로에 두지 않습니다.
  5. 관리 화면은 별도 로그인으로 보호됩니다. 관리 화면 /contexa/admin/**는 CONTEXA가 이 경로만을 위해 만든 체인이 맡습니다. 로그인은 앱 사용자와 별개인 CONTEXA 관리자 계정으로 /contexa/admin/login에서 합니다. 앱의 체인이 이 경로를 막을 필요는 없고, 관리 화면의 로그아웃은 앱의 세션을 끝내지 않습니다.
  6. 일부 요청은 판정을 기다립니다. 기본(비동기) 메서드는 응답이 나간 뒤에 분석하므로 응답이 느려지지 않습니다. sync = true 메서드는 호출 안에서 판정을 기다리며, 기본 최대 대기 시간은 40초입니다(contexa.security.zerotrust.agent.flight.wait).
  7. 기동에 전용 DB가 필요합니다. contexa.datasource.url이 없으면 기동이 멈춥니다. 전용 DB에 연결할 수 없거나, distributed 모드에서 Redis에 연결할 수 없으면 앱은 CONTEXA 없이 기동하고 ERROR 로그를 남깁니다(기동이 멈추거나 CONTEXA 없이 기동할 때).

운영 모드의 기본값은 적용 모드(ENFORCE)입니다. 이미 사용자가 있는 앱에 붙이면 판정이 처음부터 실제 요청에 적용되어 정상 사용자가 추가 인증이나 차단을 받을 수 있습니다. 먼저 관찰 모드(SHADOW)로 시작하는 방법은 운영 모드에 있습니다.

앱이 할 일: 로그인 정보를 CONTEXA에 알리기

CONTEXA는 요청마다 앱의 Spring Security가 정한 로그인 사용자를 읽습니다. 이 일을 하는 구성 요소가 인증 브리지입니다. 브리지는 읽기만 하고 앱의 로그인, 세션, 응답을 바꾸지 않습니다. 앱이 할 일은 두 가지입니다. 예시 코드는 설치 가이드의 기존 로그인과 연결하기에 있습니다.

  1. 자기 SecurityFilterChain을 둡니다. 앱에 체인이 없으면 Spring Boot 기본 보안이 적용되어 모든 요청에 로그인이 필요해지고, CONTEXA가 기동 로그에 WARN으로 알립니다. 앱 사용자도 없으면 기동이 거부됩니다.
  2. 로그인한 사용자를 앱 체인의 Spring Security 필터에서 SecurityContext에 인증된 Authentication으로 넣습니다. Spring Security의 폼 로그인, OAuth2 로그인, Bearer 토큰 필터를 쓰는 앱은 이미 이렇게 동작합니다. 세션에만 사용자 객체를 저장하는 자체 로그인은 앱 체인의 필터에서 SecurityContext를 채워야 합니다.

브리지는 이 사용자에 대해 세 가지를 읽습니다. 누구인지와 로그인 방식(인증), 어떤 권한이 있는지(인가), AI 에이전트가 대신 호출하는 경우 누가 무엇을 맡겼는지(위임)입니다. 이 정보가 판정의 근거 사실이 됩니다. 앱이 MFA 여부와 로그인 방식을 알리려면 Authentication의 details나 principal에 mfaVerified 같은 값을 두거나, OAuth2 토큰의 amr 클레임을 씁니다. 읽는 위치와 순서, 키 이름은 기존 로그인과 연결하기(인증 브리지)에 있습니다.

앱이 사용자를 MVC 인터셉터나 컨트롤러에서 늦게 정하면 요청 시점 필터는 사용자를 보지 못합니다. 그런 요청에는 판정이 @Protectable 메서드에서만 적용됩니다. 보호 메서드가 그런 요청을 처음 받으면 WARN 로그를 한 번 남깁니다. 앱의 폼 로그인이나 OAuth2 로그인이 성공하면 CONTEXA는 그 로그인 사실을 인증 브리지로 읽습니다. 이 로그인은 AI 분석에 보내지 않습니다.

판정과 응답

판정은 보통 응답이 나간 뒤에 만들어지고, 그 사용자의 다음 요청부터 적용됩니다. 판정이 아직 없는 첫 요청은 통과하고 분석이 시작됩니다. 아래는 운영 모드가 ENFORCE일 때 저장된 판정별로 사용자가 받는 응답입니다.

기본 설정에서는 검토 보류(ESCALATE) 응답이 나오지 않습니다. 2차 분석(1차 분석이 정하지 못한 요청을 한 번 더 판정하는 단계)이 검토 보류를 골라도, 설정 contexa.security.tiered.layer2.allow-escalate-final-action의 기본값(false)에서는 그 판정을 저장하지 않고 추가 인증(CHALLENGE)으로 바꿔 저장하기 때문입니다. 검토 보류를 그대로 저장하는 설정은 판정별 응답 · 권한 · 해제에 있습니다.

  • @Protectable 메서드(두 방식 모두): 차단, 추가 인증, 검토 보류 판정이면 메서드를 실행하지 않습니다. 컨트롤러에서 던져진 거부는 CONTEXA의 예외 처리기가 응답합니다. 브라우저의 화면 요청(Accept에 text/html)은 URL 단계와 같은 화면으로 이동시키고, 그 밖의 클라이언트에는 위 상태 코드와 JSON 본문으로 응답합니다.
  • URL 단계(두 방식 모두): 요청 시점 필터가 요청이 컨트롤러에 닿기 전에 저장된 판정을 처리합니다. 차단(사람이면 차단 해제 MFA를 먼저 시도), 검토 보류, 추가 인증이 여기서 처리됩니다. 판정이 허용이거나 없으면 응답을 감싸서 응답이 나가는 동안 모니터링하고, 그 사이에 차단 판정이 나오면 응답을 끊습니다. CONTEXA_OWNED에서는 CONTEXA 체인 안에서, HOST_OWNED에서는 앱 체인 바로 뒤에서 실행됩니다. 추가 인증은 각각 CONTEXA MFA와 추가 인증 화면으로 이어집니다. 자세한 내용은 요청 시점 적용에 있습니다.

운영 모드

운영 모드(contexa.security.zerotrust.mode)는 CONTEXA가 판정을 만들지, 만든 판정을 요청에 적용할지를 정합니다. 로그인을 누가 맡는지와는 별개로 정하며, 적지 않으면 ENFORCE로 동작합니다.

모드하는 일
끔(DISABLED)AI 분석을 하지 않습니다.
관찰 모드(SHADOW)AI가 판정하고, 판정 기록 · 감사 기록과 관찰 모드 전용 기억에 남깁니다. 요청에는 적용하지 않고, 허용 판정은 행위 기준선에 학습합니다. 로그인하지 않은 사용자의 @Protectable 호출은 이 모드에서도 거부합니다.
적용 모드(ENFORCE, 기본)AI가 판정하고, 판정을 저장해 다음 요청부터 적용합니다.

OBSERVE는 옛 설정을 위해 받아들이는 이름입니다. 설정에 적어도 DISABLED로 읽히고, 기동할 때 경고 로그를 남깁니다. 기존 앱에 처음 붙일 때는 아래처럼 SHADOW로 시작해 기록된 판정을 검토한 뒤 ENFORCE로 바꾸는 것이 안전합니다.

contexa:
  security:
    zerotrust:
      mode: SHADOW   # 처음에는 지켜보기만

관리 화면 /contexa/admin/system-settings에서 모드를 저장하면 재시작 없이 적용되고, 저장된 값이 YAML보다 우선합니다. SHADOW에서 무엇이 일어나는지, 언제 ENFORCE로 넘기는지는 관찰 모드로 안전하게 시작하기에 있습니다.

CONTEXA가 로그인을 맡을 때

이 방식(CONTEXA_OWNED)은 새로 만드는 앱에 맞습니다. 이미 로그인이 있는 앱은 아래의 변화를 확인한 뒤에 선택해야 합니다. 이 절은 앱에서 달라지는 것, 기본 체인의 모양, 기존 체인 · 빈과의 관계, DB 처리를 차례로 설명합니다.

FULL을 고르기 전에: 앱에서 달라지는 것

FULL에서는 CONTEXA 체인이 로그인을 맡고 모든 요청에 먼저 응답합니다. Spring Boot가 앱을 위해 만들던 보안 체인은 만들어지지 않습니다. 앱 코드는 바뀌지 않지만 일부 응답이 달라집니다. 먼저 앱의 클라이언트와 아래 목록을 대조합니다. 클라이언트가 이 응답 가운데 하나에 의존하면 기본(SANDBOX)을 씁니다. 기본에서는 앱이 로그인을 그대로 맡고, 판정과 모든 경로의 적용은 CONTEXA가 합니다.

  • URL 접근 정책이 없는 경로는 로그인이 필요합니다. URL 접근 정책은 URL 요청의 허용과 거부를 데이터베이스에 저장한 정책으로 정하는 CONTEXA의 기능입니다. 새 설치에서는 어떤 URL 접근 정책도 연결되지 않은 경로에 로그인한 사용자를 요구합니다. 그런 경로의 익명 요청은 둘 중 하나로 처리됩니다. JSON을 요구하는 요청(Accept에 application/json, X-Requested-With: XMLHttpRequest, 또는 /api/ 아래 경로)은 401을 받습니다. 그 밖의 요청은 CONTEXA 로그인 화면(/mfa/login)으로 이동합니다. /actuator/health도 여기에 포함되므로, 로그인 없이 호출하던 헬스 점검은 401이나 그 이동을 받습니다. 이 경로들의 처리 방식은 시스템 설정 화면의 "적용되는 URL 정책이 없을 때의 결정"에서 고릅니다(동적 인가).
  • 쓰기 요청에는 CSRF 토큰이 필요합니다. CONTEXA 체인은 Spring Security의 CSRF 보호를 사용합니다. 토큰이 없는 POST · PUT · PATCH · DELETE 요청은 컨트롤러에 닿기 전에 403을 받습니다. 앱이 401로 답하던 요청(틀린 비밀번호로 한 로그인, 읽을 수 없는 본문, 익명 쓰기)도 마찬가지입니다. 토큰을 보내면 CSRF 검사를 통과합니다. 토큰은 세션에 보관하며 XSRF-TOKEN 쿠키는 만들지 않습니다. CONTEXA 화면은 토큰을 _csrf · _csrf_header · _csrf_parameter meta 태그에 싣습니다. 토큰 없이 쓰던 단일 페이지 앱(SPA)이나 API 클라이언트는 토큰을 보내도록 바꿔야 합니다. 쿠키로 주고받으려면 global()에서 설정합니다(인증 DSL의 CSRF).
  • CONTEXA 로그인은 CONTEXA 계정만 읽습니다. CONTEXA 로그인(폼 · MFA 비밀번호 · REST · 일회용 코드 · 패스키)은 앱이 UserDetailsService를 몇 개 두었든 CONTEXA 자신의 사용자 저장소만 읽습니다(기존 빈과의 관계). 앱의 사용자는 CONTEXA 계정이 되기 전에는 로그인할 수 없습니다. CONTEXA의 인증 제공자가 유일한 AuthenticationProvider 빈이면 Spring Security가 전역 AuthenticationManager를 그것으로 만듭니다. 그러면 그 매니저로 로그인을 처리하는 앱 코드(예: POST /api/authenticate 같은 토큰 발급 엔드포인트)도 CONTEXA 계정으로 확인합니다.
  • HTTP Basic · Bearer 클라이언트는 로그인되지 않습니다. 기본 체인은 CONTEXA의 폼 · 패스키 · 일회용 코드로 로그인합니다. HTTP Basic과 Bearer 토큰 인증이 없으므로, Authorization: Basic …이나 앱이 받던 Bearer 토큰을 보내는 클라이언트는 로그인하지 않은 것으로 처리됩니다.
  • 로그인 사용자는 CONTEXA 타입입니다. CONTEXA로 비밀번호 로그인한 뒤의 principal은 io.contexa.contexacommon.security.UnifiedCustomUserDetails입니다. 이를 앱의 사용자 타입으로 캐스팅하는 코드는 ClassCastException을 내고, @AuthenticationPrincipal MyUser나 @AuthenticationPrincipal Jwt 같은 매개변수는 null을 받습니다.
  • Spring Boot가 만들어 주던 체인은 만들어지지 않습니다. Spring Boot는 앱에 SecurityFilterChain 빈이 없을 때만 자기 체인을 만드는데, CONTEXA 체인도 그런 빈입니다. 그래서 기본 체인(폼 로그인 · HTTP Basic), /actuator/health를 열어 두던 Actuator 관리 체인, 앱 설정에 따라 만들던 OAuth2 리소스 서버 · OAuth2 로그인 · SAML2 로그인 · Spring Authorization Server 체인이 없어집니다. 이 체인들의 엔드포인트(/.well-known/openid-configuration, /oauth2/jwks, SAML2 서비스 제공자 메타데이터와 어설션 소비 서비스 등)는 404 · 401 · 403으로 응답합니다. CONTEXA는 이 때문에 기동을 거부하지 않고, 기동 로그에도 알리지 않습니다.

FULL에서는 기동 로그에 다음 줄이 나올 수 있습니다.

기본 체인의 구성

PlatformConfig는 CONTEXA가 로그인을 맡을 때 로그인 방식을 적는 설정 빈입니다. 여기에는 흐름(인증 방법 하나와 로그인 상태 하나의 쌍)을 차례로 적고, CONTEXA는 흐름마다 SecurityFilterChain을 하나씩 만듭니다(인증 DSL). 앱이 PlatformConfig 빈을 두지 않으면 CONTEXA가 기본 구성을 만듭니다.

  • 요청: 정적 자원(/contexa/css/** 등)을 뺀 모든 요청을 동적 인가 정책(CustomDynamicAuthorizationManager)으로 평가합니다.
  • 로그인: 폼 로그인, 패스키, 일회용 토큰(OTT) MFA(요소 1개, 로그인 뒤 /)와 세션 상태 관리를 사용합니다.
  • SANDBOX에서는 만들지 않습니다. SANDBOX의 인증 소유 방식은 언제나 HOST_OWNED이며, CONTEXA는 기본 구성이든 앱의 PlatformConfig든 체인을 만들지 않습니다. CONTEXA의 체인은 /contexa/admin/**만 맡는 관리 화면 체인 하나뿐입니다(위).

어노테이션 속성과 모드별 구성의 정본은 @EnableAISecurity 참조에 있습니다.

앱의 기존 체인과의 관계

CONTEXA 체인은 가장 앞 순서(Ordered.HIGHEST_PRECEDENCE + 흐름의 order)로 등록됩니다. 기본 흐름은 경로 범위(urlPrefix)가 없으므로 모든 요청에 맞습니다. Spring Security는 요청에 맞는 첫 체인만 쓰므로, 앱이 선언한 체인은 한 번도 실행되지 않고 그 체인이 지키던 경로가 보호 없이 열립니다.

그래서 CONTEXA는 CONTEXA_OWNED에서 자기 SecurityFilterChain을 선언한 앱의 기동을 거부하고, 메시지에 그 체인을 적습니다. 앱 로그인을 지키려면 mode = FULL 없이 @EnableAISecurity를 쓰고, 그렇지 않으면 그 체인을 삭제합니다. MFA 흐름에 urlPrefix를 주면 그 흐름의 체인은 <urlPrefix>/** 요청에만 맞습니다(인증 DSL).

FULL이 더 하는 일

FULL은 앱에 자기 DB가 없을 때 CONTEXA 소유 앱 설정(contexa.datasource.isolation.contexa-owned-application)을 true로 둡니다. 앱에 자기 DB가 없다는 것은 spring.datasource.url이 없거나 contexa.datasource.url과 같은 DB를 가리킨다는 뜻입니다. 직접 적은 값은 언제나 그대로 쓰입니다. 이 설정이 true이면 다음과 같이 동작합니다.

  • 앱이 직접 DataSource 빈을 두지 않았다면 앱의 기본 DB 연결(dataSource)이 CONTEXA DB입니다. 앱이 따로 두지 않은 기본 JdbcTemplate · TransactionTemplate도 CONTEXA DB를 씁니다.
  • 기능 진단이 FAIL_FAST가 되어, 채팅 모델 · 벡터 저장소 같은 필수 부품이 없으면 기동이 멈춥니다(기능 진단).

spring.datasource.url이 앱 자신의 DB를 가리키면 FULL에서도 앱은 그 DB를 그대로 씁니다. 이 설정은 false로 남고 앱의 기본 연결은 바뀌지 않습니다. 그래도 직접 true로 적으면 CONTEXA DB가 앱의 DB 역할을 하고, 기동 로그에 [Contexa] contexa.datasource.isolation.contexa-owned-application=true: the application's spring.datasource is not used; Contexa's database serves the application.(WARN)가 나옵니다.

체인 직접 구성하기(CONTEXA_OWNED)

PlatformConfig 빈을 직접 두면 CONTEXA는 기본 구성 대신 그 구성으로 체인을 만듭니다. 이 빈은 CONTEXA_OWNED에서만 체인이 됩니다. HOST_OWNED에서는 앱의 Spring Security 설정이 그대로 쓰입니다.

예 A: REST API만

@Bean
public PlatformConfig platformConfig(IdentityDslRegistry<HttpSecurity> registry) throws Exception {
    return registry
        .global(http -> http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**").permitAll()
                .anyRequest().authenticated()))
        .rest(rest -> rest.order(10))
        .session(Customizer.withDefaults())
        .build();
}

예 B: 폼 로그인 + 동적 인가

@Bean
public PlatformConfig platformConfig(IdentityDslRegistry<HttpSecurity> registry,
                                     CustomDynamicAuthorizationManager customDynamicAuthorizationManager) throws Exception {
    return registry
        .global(http -> http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/css/**", "/js/**", "/images/**").permitAll()
                .anyRequest().access(customDynamicAuthorizationManager)))
        .form(form -> form.defaultSuccessUrl("/dashboard"))
        .session(Customizer.withDefaults())
        .build();
}

AI 신뢰 점수에 쓰이는 세션 보안 컨텍스트 저장소(AISessionSecurityContextRepository)는 CONTEXA가 모든 흐름에 자동으로 등록합니다. global()에 직접 넣지 않아도 됩니다.

예 C: Spring Security 설정에 직접 접근

DSL로 부족하면(사용자 정의 필터, AuthenticationEntryPoint 등) Spring Security의 설정 객체에 직접 접근합니다. 폼 로그인은 rawFormLogin, 흐름 전체의 HttpSecurity는 rawHttp()로 접근합니다. 직접 접근해도 CONTEXA의 구성(요청 시점 필터 등)은 흐름마다 그대로 붙습니다.

.form(form -> form
    .rawFormLogin(formLogin -> formLogin
        .authenticationDetailsSource(customDetailsSource)
        .successHandler(customSuccessHandler)))

참고: CONTEXA가 체인을 만드는 순서. CONTEXA는 앱이 직접 쓰는 것과 같은 Spring Security 메서드를 호출해 체인을 만듭니다. 순서는 다음과 같습니다.

  1. @EnableAISecurity가 CONTEXA 구성을 가져오고(AiSecurityImportSelector → AiSecurityConfiguration), 앱의 PlatformConfig가 없으면 기본 구성을 만듭니다.
  2. 흐름마다 HttpSecurity를 따로 만듭니다(FlowContextFactory).
  3. 인증 방식에 맞는 Spring Security 설정(formLogin · webAuthn · oneTimeTokenLogin)과 요청 시점 필터를 붙입니다(SecurityConfigurerOrchestrator).
  4. 각 체인을 빈으로 등록합니다(SecurityFilterChainRegistrar).

DSL 전체는 인증 DSL, 인증 흐름은 인증, MFA는 적응형 MFA에 있습니다.
