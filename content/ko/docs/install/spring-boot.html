기존 Spring Security 앱에 붙이기

이미 Spring Security를 쓰는 앱에 Contexa를 붙일 때, 로그인을 누가 맡게 할지 고르고 그에 따라 무엇이 바뀌고 무엇이 그대로인지 확인하는 페이지입니다. 판정이 어디서 집행되고 어떤 응답이 나가는지, Contexa가 로그인을 맡을 때 체인을 직접 짜는 법도 다룹니다.

Spring Boot 판. Contexa는 Spring Boot 3.5.4로 빌드 · 시험됩니다. Spring Boot 4.x에서 @EnableAISecurity를 쓰면 ERROR 로그를 남기고 IllegalStateException으로 기동을 멈춥니다.

한눈에 보기

Contexa를 붙이는 방식은 두 가지입니다. 앱이 로그인을 계속 맡거나(기본), Contexa에 로그인을 맡깁니다. 요청이 지나가는 길이 다릅니다.

먼저 고르기: 로그인을 누가 맡나

이렇게 쓰면인증 소유권함께 정해지는 것

앱이 로그인을 맡을 때(기본)

Contexa는 앱의 SecurityFilterChain · UserDetailsService · 인증 제공자 · spring.security.* 설정과 세션 · 쿠키를 바꾸지 않고, 로그인 체인이나 AI 세션 저장소를 앱의 요청 경로에 붙이지 않습니다. Contexa가 더하는 것은 앱 체인 뒤에서 돕니다. 요청 시점 필터, /contexa/step-up 아래의 추가 확인 화면, 관리 화면 /contexa/admin/**만 맡는 자기 체인입니다. 앱이 할 일은 아래 두 가지입니다. 예시 코드는 설치 가이드의 기존 로그인과 연결하기에 있습니다.

  1. 자기 SecurityFilterChain을 둡니다.
  2. 로그인한 사용자를 앱 체인의 Spring Security 필터에서 SecurityContext에 인증된 Authentication으로 넣습니다.

판정은 모든 경로에서 집행됩니다. Contexa가 자기 체인에 넣는 것과 같은 필터가 앱의 Spring Security 체인 바로 뒤에서 서블릿 필터로 돌기 때문에, 앱 체인이 먼저 사용자를 정하고 앱 규칙을 적용한 다음 저장된 BLOCK · CHALLENGE · ESCALATE에 CONTEXA_OWNED와 같은 응답을 냅니다(판정과 응답). @Protectable 메서드를 실행하기 전에도 저장된 판정을 한 번 더 확인합니다. CHALLENGE면 사용자를 Contexa의 확인 전용 추가 확인으로 보냅니다(HOST_OWNED의 추가 확인).

앱이 로그인한 사용자를 MVC 인터셉터나 컨트롤러에서 늦게 정하면 필터는 사용자를 보지 못합니다. 그런 요청은 @Protectable 메서드에서만 집행되고, 기동 뒤 처음 한 번 WARN 로그로 알려 줍니다. 사람이 앱의 폼 로그인이나 OAuth2 로그인으로 로그인하면 Contexa는 자기 로그인 때처럼 그 로그인을 분석에 보냅니다.

Contexa가 로그인을 맡을 때

FULL을 고르기 전에: 앱에서 달라지는 것

FULL에서는 Contexa 체인이 로그인을 맡고 모든 요청에 먼저 답하며, Spring Boot가 앱을 위해 만들던 보안 체인은 만들어지지 않습니다. 앱 코드는 바뀌지 않지만 일부 응답이 바뀝니다. 먼저 앱의 클라이언트와 아래 목록을 맞춰 보세요. 클라이언트가 이 응답 가운데 하나에 기대면 기본(SANDBOX)을 쓰세요. 앱이 로그인을 그대로 맡고, 판정과 모든 경로의 집행은 이때도 Contexa가 합니다.

  • URL 정책이 없는 경로는 로그인이 필요합니다. 새 설치는 어떤 URL 정책도 가리키지 않는 경로에 로그인한 사용자를 요구합니다. 그런 경로의 익명 요청은 JSON을 바라면(Accept에 application/json, X-Requested-With: XMLHttpRequest, 또는 /api/ 아래 경로) 401을 받고, 그 밖의 요청은 Contexa 로그인 화면(/mfa/login)으로 이동합니다. /actuator/health도 여기에 들므로, 로그인 없이 부르던 헬스 점검은 401이나 그 이동을 받습니다. 이 경로들에서 어떻게 할지는 시스템 설정 화면의 "적용되는 URL 정책이 없을 때의 결정"으로 고릅니다(동적 인가).
  • 쓰기 요청에는 CSRF 토큰이 필요합니다. Contexa 체인은 Spring Security의 CSRF 보호를 켜 둡니다. 토큰 없는 POST · PUT · PATCH · DELETE는 컨트롤러에 닿기 전에 403을 받고, 앱이 401로 답하던 요청(틀린 비밀번호 로그인, 읽지 못하는 본문, 익명 쓰기)도 마찬가지입니다. 토큰을 보내면 CSRF 검사는 통과합니다. 토큰은 세션에 두고 XSRF-TOKEN 쿠키는 만들지 않으며, Contexa 화면은 토큰을 _csrf · _csrf_header · _csrf_parameter meta 태그에 싣습니다. 토큰 없이 쓰던 단일 페이지 앱(SPA)이나 API 클라이언트는 토큰을 보내야 하고, 쿠키로 주고받으려면 global()에서 정합니다(인증 DSL의 CSRF).
  • Contexa 로그인은 Contexa 계정만 읽습니다. Contexa 로그인(폼 · MFA 비밀번호 · REST · 일회용 코드 · 패스키)은 앱이 UserDetailsService를 몇 개 두었든 Contexa 자신의 사용자 저장소만 읽습니다(기존 빈과의 관계). 앱의 사용자는 Contexa 계정이 되기 전에는 로그인하지 못합니다. Contexa의 인증 제공자가 유일한 AuthenticationProvider 빈이면 Spring Security가 전역 AuthenticationManager를 그것으로 만들므로, 그 매니저로 로그인을 처리하는 앱 코드(예: POST /api/authenticate 같은 토큰 발급 엔드포인트)도 Contexa 계정으로 확인합니다.
  • HTTP Basic · Bearer 클라이언트는 로그인되지 않습니다. 기본 체인은 Contexa의 폼 · 패스키 · 일회용 코드로 로그인합니다. HTTP Basic과 Bearer 토큰 인증이 없으므로, Authorization: Basic …이나 앱이 받던 Bearer 토큰을 보내는 클라이언트는 로그인하지 않은 것으로 다뤄집니다.
  • 로그인 사용자는 Contexa 타입입니다. Contexa로 비밀번호 로그인한 뒤의 principal은 io.contexa.contexacommon.security.UnifiedCustomUserDetails입니다. 이를 앱의 사용자 타입으로 캐스팅하는 코드는 ClassCastException을 내고, @AuthenticationPrincipal MyUser나 @AuthenticationPrincipal Jwt 같은 매개변수는 null을 받습니다.
  • Spring Boot가 만들어 주던 체인은 만들어지지 않습니다. Spring Boot는 앱에 SecurityFilterChain 빈이 없을 때만 자기 체인을 만들고, Contexa 체인도 그런 빈입니다. 그래서 기본 체인(폼 로그인 · HTTP Basic), /actuator/health를 열어 두던 Actuator 관리 체인, 그리고 앱 설정에 따라 만들던 OAuth2 리소스 서버 · OAuth2 로그인 · SAML2 로그인 · Spring Authorization Server 체인이 없어집니다. 그 엔드포인트(/.well-known/openid-configuration, /oauth2/jwks, SAML2 서비스 제공자 메타데이터와 어설션 소비 서비스 등)는 404 · 401 · 403으로 답합니다. Contexa는 이 때문에 기동을 거부하지 않고, 기동 로그에도 알리지 않습니다.

FULL에서는 기동 로그에 다음 줄이 나올 수 있습니다.

기본 체인 모양

앱이 PlatformConfig 빈을 두지 않으면 Contexa가 기본 구성을 만들고, 모양은 mode에 따라 다릅니다.

  • SANDBOX 모양: CSRF · CORS · 보안 헤더를 끄고, /contexa/admin/**만 ADMIN 역할로 보호합니다(/contexa/admin/login은 허용, 차단 해제 요청 등 본인용 경로 /contexa/admin/api/aiam/zero-trust/** · /contexa/admin/api/aiam/sse/zero-trust/**는 로그인만). 나머지 요청은 모두 허용하고, 폼 로그인 처리 주소는 기동할 때마다 임의로 정합니다.
  • FULL 모양: 정적 자원(/contexa/css/** 등) 말고는 모든 요청을 동적 인가 정책(CustomDynamicAuthorizationManager)으로 판단합니다.
  • 둘 다: 폼 로그인 + 패스키 + 일회용 토큰(OTT) MFA(요소 1개, 로그인 뒤 /)와 세션 상태 관리.

어노테이션 속성과 모드별 구성의 정본은 @EnableAISecurity 참조에 있습니다.

앱의 기존 체인과의 관계

Contexa 체인은 가장 앞 순서(Ordered.HIGHEST_PRECEDENCE + 흐름의 order)로 등록되고, 기본 흐름은 경로 범위(urlPrefix)가 없어 모든 요청에 맞습니다. Spring Security는 요청에 맞는 첫 체인만 쓰므로, 앱이 선언한 체인은 한 번도 돌지 않고 그 체인이 지키던 곳이 열립니다. 그래서 Contexa는 CONTEXA_OWNED에서 자기 SecurityFilterChain을 선언한 앱의 기동을 거부하고, 메시지에 그 체인을 적습니다. 앱 로그인을 지키려면 mode = FULL 없이 @EnableAISecurity를 쓰고, 아니면 그 체인을 지우세요. MFA 흐름에 urlPrefix를 주면 그 흐름의 체인은 <urlPrefix>/** 요청에만 맞습니다(인증 DSL).

기존 빈과의 관계

앱에 있던 것CONTEXA_OWNED에서
SecurityFilterChain둘 수 없습니다. Contexa owns the sign-in of this application, but the application declares its own security chain(s) [...]로 기동이 거부됩니다(앱의 기존 체인과의 관계). 그 체인을 지우거나, mode = FULL 없이 @EnableAISecurity를 써서 앱 로그인을 지킵니다.
UserDetailsService앱의 것은 그대로 둡니다. Contexa의 사용자 조회(Contexa DB)는 두 경우 모두 등록하며, 앱의 것이 있으면 기본 후보가 아니어서 앱 코드가 타입으로 UserDetailsService를 주입받을 때 그것이 오지 않습니다. Contexa 로그인(폼 · MFA 비밀번호 · REST · 일회용 코드 · 패스키 · 코드 발송)은 앱이 UserDetailsService를 몇 개 선언했든 Contexa의 조회만 읽습니다. 앱의 사용자는 Contexa 로그인으로 로그인되지 않고 없는 이름과 똑같이 거절되며(REST 로그인은 401), 읽지 않는 앱의 저장소는 시작할 때 WARN으로 나옵니다. 토큰의 사용자를 확인하는 경로(리소스 서버의 토큰 변환기, 사람의 토큰을 갱신할 때의 계정 확인)는 앱의 저장소가 하나뿐이거나 @Primary가 붙어 있으면 그것을, 아니면 Contexa의 것을 그대로 씁니다.
AuthenticationProviderContexa의 인증 제공자(CustomAuthenticationProvider)를 따로 등록합니다.
CSRF · CORS 설정앱 체인의 설정은 그대로이고, Contexa 체인의 것은 global()로 바꿉니다.
spring.security.*바꾸지 않습니다. Contexa는 contexa.*를 씁니다(Contexa가 넣는 기본값은 spring.ai.* · management.*뿐).

FULL이 더 하는 일

FULL은 앱에 자기 DB가 없을 때, 곧 spring.datasource.url이 없거나 contexa.datasource.url과 같은 DB를 가리킬 때 Contexa 소유 앱 표시(contexa.datasource.isolation.contexa-owned-application)를 true로 둡니다. 직접 적은 값은 언제나 그대로 쓰입니다. 표시가 true면:

  • 앱이 직접 DataSource 빈을 두지 않았다면 앱의 기본 DB 연결(dataSource)이 Contexa DB입니다. 앱이 따로 두지 않은 기본 JdbcTemplate · TransactionTemplate도 Contexa DB를 씁니다.
  • 기능 진단이 FAIL_FAST가 되어, 채팅 모델 · 벡터 저장소 같은 필수 부품이 빠지면 기동이 멈춥니다(기능 진단).

spring.datasource.url이 앱 자신의 DB를 가리키면 FULL에서도 앱은 그 DB를 그대로 씁니다. 표시는 false로 남고 앱의 기본 연결은 바뀌지 않습니다. 그래도 표시를 직접 true로 적으면 Contexa DB가 앱의 DB가 되고, 기동 로그에 [Contexa] contexa.datasource.isolation.contexa-owned-application=true: the application's spring.datasource is not used; Contexa's database serves the application.(WARN)가 나옵니다.

집행 모드

판정을 만들고 적용할지는 집행 모드(contexa.security.zerotrust.mode)가 정합니다. 로그인 소유 방식과는 따로 정합니다.

모드하는 일
ENFORCE(기본)AI가 판정하고, 판정을 저장해 다음 요청부터 적용합니다.
SHADOWAI가 판정하고 판정 기록 · 감사 기록에 남기지만, 저장 · 적용 · 학습하지 않습니다.
OBSERVE · DISABLEDAI 분석을 하지 않습니다(둘의 동작은 같음).
 
contexa:
  security:
    zerotrust:
      mode: SHADOW   # 처음에는 지켜보기만

관리 화면 /contexa/admin/system-settings에서 바꾸면 재시작 없이 적용되고, 한 번 저장하면 그 뒤로는 DB에 저장된 값이 YAML보다 우선합니다. SHADOW에서 무엇이 일어나는지, 언제 ENFORCE로 넘기는지는 집행 모드로 안전하게 시작하기에 있습니다.

판정과 응답

  • @Protectable 메서드(두 방식 모두): BLOCK · CHALLENGE · ESCALATE면 메서드를 실행하지 않고, 컨트롤러에서 던져진 거부는 Contexa 예외 처리기가 답합니다. 브라우저의 화면 요청(Accept에 text/html)은 URL 단계와 같은 화면으로 보내고, 그 밖의 클라이언트에는 위 상태 코드와 JSON 본문으로 답합니다.
  • URL 단계(두 방식 모두): 요청 시점 필터가 BLOCK(사람이면 차단 해제 MFA를 먼저 시도) · ESCALATE · CHALLENGE를 처리하고, 판정이 허용이거나 없으면 응답을 감싸 두었다가 차단 판정이 나오면 끊을 수 있게 합니다. CONTEXA_OWNED에서는 Contexa 체인 안에서, HOST_OWNED에서는 앱 체인 바로 뒤에서 돌고, CHALLENGE는 각각 Contexa MFA와 추가 확인으로 이어집니다. 자세한 것은 요청 시점 집행에 있습니다.

체인 직접 짜기(CONTEXA_OWNED)

PlatformConfig 빈을 직접 두면 기본 구성 대신 그 구성으로 Contexa 체인을 만듭니다. 이 빈은 CONTEXA_OWNED에서만 체인이 되고, HOST_OWNED에서는 앱의 Spring Security 설정이 그대로 쓰입니다.

예 A: REST API만

@Bean
public PlatformConfig platformConfig(IdentityDslRegistry<HttpSecurity> registry) throws Exception {
    return registry
        .global(http -> http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**").permitAll()
                .anyRequest().authenticated()))
        .rest(rest -> rest.order(10))
        .session(Customizer.withDefaults())
        .build();
}

예 B: 폼 로그인 + 동적 인가

@Bean
public PlatformConfig platformConfig(IdentityDslRegistry<HttpSecurity> registry,
                                     CustomDynamicAuthorizationManager customDynamicAuthorizationManager) throws Exception {
    return registry
        .global(http -> http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/css/**", "/js/**", "/images/**").permitAll()
                .anyRequest().access(customDynamicAuthorizationManager)))
        .form(form -> form.defaultSuccessUrl("/dashboard"))
        .session(Customizer.withDefaults())
        .build();
}

AI 신뢰 점수에 쓰이는 세션 보안 컨텍스트 저장소(AISessionSecurityContextRepository)는 Contexa가 모든 흐름에 자동으로 등록하므로 global()에 직접 넣지 않아도 됩니다.

예 C: Spring Security 설정에 직접 접근

DSL로 부족하면(사용자 정의 필터, AuthenticationEntryPoint 등) Spring Security의 설정 객체에 직접 접근합니다. 폼 로그인은 rawFormLogin, 흐름 전체의 HttpSecurity는 rawHttp()입니다. 직접 접근해도 Contexa의 구성(요청 시점 필터 등)은 흐름마다 그대로 붙습니다.

.form(form -> form
    .rawFormLogin(formLogin -> formLogin
        .authenticationDetailsSource(customDetailsSource)
        .successHandler(customSuccessHandler)))

참고: Contexa가 체인을 만드는 순서. @EnableAISecurity가 Contexa 구성을 가져오고(AiSecurityImportSelector → AiSecurityConfiguration), 앱의 PlatformConfig가 없으면 기본 구성을 만듭니다. 흐름마다 HttpSecurity를 따로 만들고(FlowContextFactory), 인증 방식에 맞는 Spring Security 설정(formLogin · webAuthn · oneTimeTokenLogin)과 요청 시점 필터를 붙인 뒤(SecurityConfigurerOrchestrator), 각 체인을 빈으로 등록합니다(SecurityFilterChainRegistrar). Contexa는 앱이 직접 쓰는 것과 같은 Spring Security 메서드를 부릅니다.

DSL 전체는 인증 DSL, 인증 흐름은 인증, MFA는 적응형 MFA에 있습니다.
