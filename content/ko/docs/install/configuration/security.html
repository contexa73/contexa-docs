운영 모드와 판정 조정

CONTEXA가 AI 판정을 만들고 요청에 적용하는 방식을 정하는 설정입니다. 대부분의 앱은 운영 모드(contexa.security.zerotrust.mode) 하나만 정하면 됩니다. 나머지 설정은 기본값으로 동작하며, 분석이 느리거나 처리량이 부족할 때처럼 문제가 나타날 때 해당 절에서 조정합니다. 판정이 만들어지고 적용되는 과정은 판정 엔진과 요청 시점 적용에 있습니다.

먼저 정할 것과 나중에 조정할 것

이 페이지의 설정에는 모두 기본값이 있으므로 반드시 적어야 하는 설정은 없습니다. 먼저 정할 것은 도입 단계에 맞는 운영 모드 하나입니다. 모드를 적지 않으면 적용 모드(ENFORCE)로 동작하므로, 처음 도입하는 앱은 관찰 모드(SHADOW)를 직접 지정합니다. 판정을 만들려면 채팅 모델과 벡터 저장소가 연결되어 있어야 합니다(준비물). 모델을 연결하는 설정은 AI 모델 연결에 있습니다.

나머지 설정은 운영 중에 아래와 같은 증상이 나타날 때 조정합니다. 표는 상황별로 볼 절을 안내합니다.

판정이 만들어지는 순서와 설정 절

판정 하나는 아래 순서로 만들어지고 적용됩니다. 요청 시점 적용은 요청이 들어올 때 CONTEXA의 필터가 그 사용자에게 저장된 판정을 확인해, 추가 인증 요구 · 차단 · 검토 보류 응답으로 바꾸는 단계입니다.

운영 모드 고르기

운영 모드(contexa.security.zerotrust.mode)는 CONTEXA가 AI 모델로 판정을 만들지, 만든 판정을 실제 요청에 적용할지를 정합니다. 판정(Decision)은 AI가 한 사용자의 요청을 분석해 내리는 결론으로, 허용(ALLOW) · 추가 인증(CHALLENGE) · 검토 보류(ESCALATE) · 차단(BLOCK) 중 하나입니다. 처음 도입할 때는 관찰 모드(SHADOW)로 시작해 판정을 확인한 뒤 적용 모드(ENFORCE)로 올립니다. 세 모드의 동작 차이와 올리는 절차는 관찰 모드로 안전하게 시작하기에 있으며, 이 절은 표로 요약합니다.

모드AI 분석판정 저장 · 적용학습쓰는 때
DISABLED(끔)하지 않음하지 않음하지 않음AI 판정을 쓰지 않을 때
OBSERVE(옛 이름)옛 설정을 위해 받아들이는 이름입니다. 코드가 DISABLED로 읽고, 시작할 때 경고 로그를 남깁니다.—
SHADOW(관찰)함판정 기록 · 감사 기록과 관찰 모드 전용 기억에 판정을 남깁니다. 요청을 막거나 응답을 바꾸지 않습니다허용 판정만도입 첫 단계에서 판정의 품질을 확인할 때
ENFORCE(적용, 기본)함판정을 저장하고 같은 사용자의 다음 요청부터 적용합니다실제로 적용된 허용 판정만운영 환경

정확히는 AI 분석은 enabled가 켜져 있고 모드가 SHADOW 또는 ENFORCE일 때 실행되고, 판정 저장과 적용은 enabled가 켜져 있고 모드가 ENFORCE일 때만 실행됩니다.

  • 관찰 모드 전용 기억은 관찰 모드가 만든 판정을 적용용 저장소와 따로 보관하는 곳입니다. 같은 사용자의 다음 요청에 AI를 다시 부르지 않으려고 쓰며, 어떤 요청도 막지 않습니다.
  • 관찰 모드에서도 요청 안에서 분석을 기다리는 경우가 있습니다. 즉시 판정 메서드(@Protectable(sync = true))와 판정 기록이 없는 AI 에이전트의 요청은 그 요청 안에서 분석 결과를 기다립니다. 결과가 허용이 아니어도 막지 않고 진행합니다.
  • 관찰 모드에서도 거부되는 호출이 있습니다. 로그인하지 않았거나 익명인 사용자가 @Protectable 메서드를 호출하면 SHADOW와 ENFORCE에서는 CONTEXA가 거부합니다. DISABLED에서는 거부하지 않으므로, 모드를 DISABLED에서 SHADOW로 바꾸면 이런 호출이 처음으로 거부될 수 있습니다(관찰 모드에서 실제로 일어나는 일).
  • contexa.security.zerotrust.enabled: false는 DISABLED보다 넓게 끕니다. AI 분석을 하지 않는 데 더해, 분석 사건을 받는 수신기와 로그인 맥락에 판정을 적용하는 단계도 멈춥니다.
  • 결과를 보는 곳, ENFORCE로 넘기기 전에 확인할 기준, 되돌리는 방법은 결과 확인 위치 · ENFORCE로 넘기기 · 되돌리기에 있습니다.
contexa:
  security:
    zerotrust:
      mode: SHADOW     # 지켜본 뒤 ENFORCE로
설정기본값뜻언제 바꾸나
contexa.security.zerotrust.enabledtrueAI 판정 기능 전체를 켭니다. false이면 AI 분석과 로그인 맥락에 대한 판정 적용이 멈춥니다(위 설명 참고)CONTEXA의 판정을 통째로 멈춰야 할 때(mode: DISABLED보다 넓게 꺼집니다)
contexa.security.zerotrust.modeENFORCE운영 모드입니다. 허용 값은 DISABLED · OBSERVE · SHADOW · ENFORCE이며, OBSERVE는 옛 이름이라 DISABLED와 같게 읽습니다. 관리 화면에 저장한 값이 있으면 그 값이 이깁니다도입 단계에 맞춰 바꿉니다(처음에는 SHADOW, 확인한 뒤 ENFORCE)
contexa.security.zerotrust.allow-validity15m허용(ALLOW) 판정이 유효한 시간입니다. 이 시간 안에는 같은 세션 · IP · 브라우저에서 들어오는 비동기 요청을 새로 분석하지 않고 그 허용을 씁니다. 셋 중 하나라도 바뀌면 바로 분석하고, 즉시 판정(sync) 메서드는 매번 판정합니다. 운영 환경에서는 10~20분을 권하며, 범위 밖의 값도 그대로 쓰되 시작할 때 한 번 알립니다. 0 이하의 값은 기본값으로 읽습니다허용을 더 짧게 또는 길게 유지해야 할 때(시험 환경에서는 짧게)

관리 화면에서 바꾸기

관리 화면의 시스템 설정(/contexa/admin/system-settings)에서도 운영 모드를 바꿀 수 있습니다. 저장하면 재시작 없이 바로 적용되므로, 운영 중에 모드를 바꿀 때는 이 방법을 씁니다. 저장한 값과 YAML 중 어느 쪽이 이기는지는 모드를 바꾸는 두 방법과 우선순위에 정리되어 있습니다.

  • 한 번 저장하면 그 뒤로는 저장한 값이 YAML을 이깁니다. CONTEXA는 기동할 때마다 저장한 값으로 contexa.security.zerotrust.mode를 덮어씁니다. 따라서 YAML만 바꿔서는 모드가 바뀌지 않으며, 관리 화면에서 바꿔야 합니다.
  • 저장한 적이 없으면 화면에는 지금 적용 중인 모드가 미리 채워져 있습니다. 이 상태로 다른 항목만 바꿔 저장하거나 모드 칸을 비워 저장해도 모드는 저장되지 않으며, YAML 값이 계속 적용됩니다. 지금과 다른 모드를 고르면 그때부터 저장한 값이 YAML을 이깁니다.
  • 이미 저장한 값이 있을 때 모드 칸을 비워 저장하면 SHADOW가 저장됩니다.
모드를 낮추면 이미 저장된 제한은 효력을 멈출 뿐 지워지지 않습니다. @Protectable 메서드는 운영 모드를 따릅니다. 관찰 모드에서는 저장된 제한을 기록만 하고, 끔에서는 확인하지 않습니다. 요청이 들어올 때 CONTEXA가 거는 필터 두 개(추가 인증 · 접근 제어)도 로그인을 앱이 맡는 방식(HOST_OWNED)과 CONTEXA가 맡는 방식(CONTEXA_OWNED) 모두에서 모드를 따라, enabled가 켜져 있고 모드가 ENFORCE일 때만 요청을 막습니다. 이미 저장된 차단(BLOCK) · 추가 인증(CHALLENGE) · 검토 보류(ESCALATE)는 남아 있다가 모드가 ENFORCE로 돌아오면 다시 적용되며, 관리자가 해제하거나 판정의 유효 시간이 지나야 없어집니다.

판정 시간 제한

AI 모델이 느리거나 응답하지 않을 때 판정을 얼마나 기다릴지 정하는 설정입니다. 기본값으로 분석이 시간 초과로 끝나는 일이 드물면 바꾸지 않습니다. 분석은 두 단계로 진행되며, 1차 분석이 정하지 못하면(ESCALATE) 2차 분석이 다시 판정합니다(판정 엔진). 시간 제한의 단위는 모두 밀리초입니다.

로컬 모델처럼 느린 모델을 쓸 때는 상황별 예처럼 1차 · 2차 분석의 제한, 모델 호출 하나의 제한, 분석 사건 전체의 예산을 함께 늘립니다. 한 값만 늘리면 그보다 짧은 다른 제한이 먼저 적용됩니다.

처리량과 대기열

CONTEXA는 분석 요청(판정 사건)을 먼저 대기열에 넣고, 작업자가 사건을 꺼내 AI 모델로 분석합니다. 이 절의 설정은 대기열의 크기와, 분석을 동시에 몇 개까지 실행할지를 정합니다. 동시 사용자가 많거나 대기열이 가득 차는 일이 반복될 때만 조정합니다.

AI 모델 분석에 쓰는 스레드 풀은 기본 크기 32개로 시작해 최대 64개까지 늘어납니다. 최대 크기에 이른 뒤에야 작업이 256개의 대기 자리에 쌓이고, 대기 자리도 모두 차면 새 작업을 거부합니다.

contexa.security.plane.agent.*는 AI 에이전트 설정이 아닙니다. CONTEXA 판정 엔진의 분석 작업자 설정입니다. AI 에이전트(사용자를 대신해 호출하는 AI)의 제한은 에이전트 제한에 있습니다.

최소 대응 규칙

최소 대응 규칙은 판정에 쓰는 사실이 아래 조건에 맞으면 모델이 낸 대응이 적어도 그 하한 이상이어야 한다고 정하는 규칙입니다. 위험한 상황에서 모델이 허용 같은 약한 대응을 내는 일을 막는 데 씁니다. 허용보다 추가 인증이, 추가 인증보다 검토 보류가 강한 대응입니다. 규칙의 모드는 OBSERVE와 ENFORCE 두 가지입니다.

  • OBSERVE(기본): 하한을 어긴 것을 기록만 합니다.
  • ENFORCE: 시스템 프롬프트에 하한을 적어 모델에 알리고, 모델의 답이 하한보다 약하면 한 번 고쳐 묻습니다. 그래도 약하면 검토 보류로 바꿉니다.

판정 프롬프트 조정

판정 프롬프트는 AI 모델에 보내는 지시문과 판정의 근거(요청 정보, 행위 기준선, 과거 판정 기록)를 담은 입력입니다. 이 절의 설정은 어떤 프롬프트 버전을 쓸지, 프롬프트에 무엇을 얼마나 넣을지, 답을 어떤 형식으로 받을지를 정합니다. 기본값으로 판정이 정상적으로 나오면 바꾸지 않습니다. 프롬프트의 내용은 판정 프롬프트에 있고, 분석 단계(1차 · 2차)마다 쓸 모델 · 출력 토큰 한도 · 공급자 옵션은 AI 모델 연결에 있습니다.

요청 시점 적용 조정

요청 시점 적용은 요청이 들어올 때 CONTEXA의 필터가 그 사용자에게 저장된 판정을 확인하고, 필요하면 추가 인증을 요구하거나 요청을 막는 단계입니다. 이 절의 설정은 MFA 시작 잠금, 세션 · 로그아웃 추적, 위협 점수 초기값처럼 그 동작의 세부를 정하며, 대부분 기본값을 그대로 씁니다.

요청 시점 필터는 두 소유 방식(로그인을 누가 맡는지) 모두에서 동작합니다. 로그인을 CONTEXA가 맡는 방식(CONTEXA_OWNED)에서는 CONTEXA가 만든 보안 체인 안에서, 기본 방식(HOST_OWNED)에서는 앱 보안 체인 바로 뒤의 서블릿 필터로 동작합니다. HOST_OWNED에서는 추가 인증(CHALLENGE)이 CONTEXA MFA 대신 CONTEXA의 추가 인증 화면(/contexa/step-up)으로 이어집니다. 따라서 아래 설정 가운데 CONTEXA MFA를 시작할 때의 잠금(challenge.*)과 CONTEXA 자체 로그인 맥락에 관한 설정은 CONTEXA_OWNED에서만 동작합니다. 저장된 판정은 @Protectable 메서드 앞에서도 적용합니다. 판정별 응답과 해제 방법은 요청 시점 적용에 있습니다. 두 소유 방식의 차이는 기존 Spring Security 앱에 붙이기에 있습니다.

contexa.security.zerotrust.session.tracking-enabledtrue로그인 맥락을 저장할 때 사용자의 세션을 함께 기록합니다. 기록해 두어야 강제 로그아웃이 그 사용자의 모든 세션에 적용됩니다세션 추적을 하지 않을 때
contexa.security.zerotrust.redis.update-interval-seconds30같은 세션의 추적 기록을 다시 쓰는 최소 간격(초)입니다. 이름과 달리 단독 모드에도 적용됩니다저장소 쓰기 횟수를 줄일 때
contexa.security.zerotrust.session-tracking.max-untimed-sessions-per-user64만료 시각을 알 수 없는 세션 식별자를 사용자당 몇 개까지 추적할지 정합니다. 넘으면 가장 오래 보이지 않은 것부터 추적 대상에서 제외하며, 제외된 세션은 다음 요청으로 다시 등록되기 전까지 강제 로그아웃이 닿지 않습니다. 0 이하이면 제한이 없습니다한 사용자가 세션을 아주 많이 쓸 때
contexa.security.zerotrust.analysis.max-age-ms3600000로그인 MFA 정책이 저장된 분석 결과를 신뢰하는 최대 경과 시간(ms)입니다. 이보다 오래된 분석은 추가 인증이 필요한 것으로 봅니다로그인 때 더 최근의 분석을 요구할 때

설정으로 바꿀 수 없는 고정값도 있습니다. 읽은 판정은 5초 동안 캐시합니다. 검토 보류(ESCALATE) 응답의 Retry-After는 30초입니다. 판정별 유효 시간은 추가 인증 1,800초, 검토 보류 300초이고, 차단은 해제될 때까지입니다(판정 엔진). 허용(ALLOW)의 유효 시간은 고정값이 아니라 기본 15분이며 contexa.security.zerotrust.allow-validity로 바꿉니다.

@Protectable 메서드(두 소유 방식 모두)

@Protectable이 붙은 메서드는 CONTEXA가 저장된 판정을 확인하고 분석을 시작하는 지점입니다. CONTEXA의 분석은 이 메서드의 호출에서 시작하며, 로그인 성공 자체는 분석하지 않습니다.

설정기본값뜻언제 바꾸나
contexa.security.zerotrust.protectable.rapid-reentry-window-ms5000같은 사용자 · 세션의 요청이 이 시간(ms) 안에 다시 들어올 때의 처리를 정합니다. 일반(비동기) 메서드는 새 분석 없이 실행하고, 즉시 판정(sync) 메서드는 분석이 진행 중이라는 뜻으로 503을 응답합니다. 관찰 모드에서는 즉시 판정 메서드도 실행합니다짧은 시간에 같은 호출이 몰리는 화면이 있을 때

판정 기록이 없는 AI 에이전트의 요청을 어떻게 처리할지(contexa.security.zerotrust.protectable.unrecorded-agent-request)는 에이전트 제한에 있습니다.

세션 식별자 이름

CONTEXA는 요청의 세션을 아래 순서로 알아봅니다. 이 식별자로 무효화된 세션을 걸러내고 세션을 추적합니다(CONTEXA_OWNED). 세션 쿠키나 헤더의 이름을 바꾸지 않았다면 이 절의 설정은 그대로 둡니다.

  1. JWT의 jti를 봅니다.
  2. 없으면 HTTP 세션을 봅니다.
  3. 둘 다 없으면 아래 이름으로 쿠키, 헤더, Bearer 토큰 순서로 찾습니다.
설정기본값뜻언제 바꾸나
contexa.security.session.cookie.nameSESSION세션 ID를 담은 쿠키의 이름입니다세션 쿠키의 이름을 바꿨을 때
contexa.security.session.header.nameX-Auth-Token세션 ID를 담은 헤더의 이름입니다(Bearer 로 시작하면 그 부분을 떼고 읽습니다)헤더로 세션 ID를 전달할 때
contexa.security.session.bearer.enabledtrueAuthorization: Bearer에서도 세션 ID를 찾습니다Bearer 토큰을 세션 ID로 쓰지 않을 때(false)
