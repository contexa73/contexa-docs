인증과 로그인

인증 설정은 로그인을 앱이 처리하는지 CONTEXA가 처리하는지에 따라 정할 내용이 달라집니다. 앱이 로그인을 처리하는 기본 모드(SANDBOX)에서는 CONTEXA가 앱의 로그인 결과를 읽기만 하므로, 정해야 하는 설정은 추가 인증 수단(패스키, 메일 일회용 코드)과 프록시 주소에 한정됩니다. CONTEXA가 로그인 · MFA · 토큰 발급을 직접 처리하는 모드(FULL)에서는 로그인 상태 유지 방식, 토큰 수명, 인가 서버, 로그인 · MFA 주소, MFA 제한 시간, MFA 상태 저장 위치를 정할 수 있습니다. 각 절은 첫 줄에 어느 경우에 해당하는지 표시합니다.

로그인을 누가 맡는지에 따라 달라지는 설정

적용 대상: 두 경우 모두. 이 절은 어느 경우에 해당하는지 고르는 기준을 설명합니다.

보안 모드(security mode)는 로그인, 곧 자격 증명 확인과 세션 · 토큰 관리를 앱이 처리하는지(SANDBOX) CONTEXA가 처리하는지(FULL)를 정하는 구분입니다. 두 모드 모두 CONTEXA의 전체 기능이 동작합니다. 이 구분에 따라 이 페이지에서 볼 설정이 정해집니다. 이 페이지에서 판정(Decision)은 CONTEXA가 사용자 요청에 내리는 결론으로, 허용(ALLOW) · 추가 인증(CHALLENGE) · 검토 보류(ESCALATE) · 차단(BLOCK) 중 하나입니다. 추가 인증(MFA, 다중 요소 인증)은 비밀번호 외에 패스키나 일회용 코드 같은 요소를 더 확인하는 인증입니다.

구분앱이 로그인을 맡을 때(SANDBOX, 기본)CONTEXA가 로그인을 맡을 때(FULL)
로그인 처리앱의 Spring Security가 로그인, 세션, 쿠키를 처리합니다. CONTEXA는 앱 사용자의 로그인용 보안 체인(Security Filter Chain)을 만들지 않고, CONTEXA 관리 콘솔(/contexa/admin)의 관리자 로그인 체인만 만듭니다. 앱에 보안 체인도 사용자도 없으면 CONTEXA를 넣기 전처럼 모든 요청을 통과시키는 격리 체인을 둡니다.CONTEXA가 로그인 · MFA · 토큰 발급을 처리하고, 이를 위한 보안 체인을 만듭니다.
판정이 추가 인증(CHALLENGE)일 때CONTEXA가 사용자를 확인 전용 추가 인증 화면(/contexa/step-up)으로 보냅니다. 이 화면은 로그인을 대신하지 않고, 요청한 사람이 앱에 로그인한 사용자가 맞는지만 확인합니다.CONTEXA의 MFA 흐름으로 보냅니다.
켜는 방법기본입니다. @EnableAISecurity를 붙이고 모드를 지정하지 않으면 이 방식입니다.@EnableAISecurity(mode = SecurityMode.FULL)로 켭니다. 설정 contexa.ai.security.mode: FULL로도 켤 수 있고, 이 설정이 어노테이션보다 우선합니다.
이 페이지에서 정하는 설정추가 인증 수단(패스키, 메일 일회용 코드, 앱 자체 재인증)과 앞단 프록시입니다. 앱이 로그인을 맡을 때 정하는 설정에서 시작합니다.로그인 상태, 토큰 수명, 인가 서버, 로그인 · MFA 주소, MFA 제한 시간, 저장 위치입니다. 로그인 상태부터 읽습니다.

인증 소유권(contexa.bridge.ownership)은 보안 모드와 다른 설정입니다. 앱이 직접 둔 구성요소(UserDetailsService · JwtDecoder 등)와 CONTEXA의 같은 종류가 만날 때 어느 쪽을 앱에 쓰는지 정합니다. HOST_OWNED는 앱 것을 쓰고, CONTEXA_OWNED는 앱에 없는 종류를 CONTEXA 것으로 채웁니다. 기능을 끄지 않으며 네 조합 모두 허용됩니다. 적지 않으면 모드를 따릅니다(SANDBOX → HOST_OWNED, FULL → CONTEXA_OWNED). 앱이 로그인을 맡을 때 앱의 로그인 정보를 CONTEXA에 알리는 방법은 인증 브리지에 있습니다.

하려는 일에 맞는 절은 아래 표에서 찾습니다. 적용 열은 그 설정이 어느 경우에 쓰이는지 나타냅니다.

앱이 로그인을 맡을 때 정하는 설정 (SANDBOX)

적용 대상: 앱이 로그인을 맡는 SANDBOX에서만.

이 방식에서는 로그인 방식, 토큰, 로그인 주소를 앱의 Spring Security 설정이 정합니다. 그래서 이 페이지의 로그인 상태, 토큰 수명, 인가 서버, 로그인 · MFA 주소 절은 쓰이지 않습니다. CONTEXA가 따로 정하는 것은 판정이 추가 인증(CHALLENGE)일 때 사용자가 거치는 확인 전용 추가 인증 화면(/contexa/step-up)입니다. 이 화면은 사용할 수 있는 방법(패스키, 메일 일회용 코드, 앱 자체 재인증) 가운데 하나로 사용자를 확인합니다. 화면의 동작은 앱이 로그인을 맡을 때의 추가 인증에 있습니다.

반드시 정해야 하는 설정은 없습니다. 운영 환경에서 추가 인증 수단을 제공하려면 아래 표에서 해당하는 행을 확인합니다. 조건을 채우지 못한 수단은 추가 인증 화면에서 제공되지 않습니다.

설정기본값뜻언제 정하나
contexa.auth.urls.factors.passkey.*rp-id는 localhost패스키의 신뢰 당사자(도메인 · 출처)입니다. 값은 패스키 신뢰 당사자에 있습니다.운영 환경에서 패스키를 추가 인증 수단으로 제공할 때
contexa.bridge.step-up.share-application-passkeysfalse앱이 이미 가진 패스키 저장소를 추가 인증에 그대로 쓸지 정합니다. 켜도 앱에 PublicKeyCredentialUserEntityRepository와 UserCredentialRepository 빈이 각각 하나일 때만 적용되고, 아니면 CONTEXA의 저장소를 씁니다. 끄면 패스키를 CONTEXA의 표에 보관하고, 사용자는 CONTEXA 화면에서 패스키를 등록합니다.앱의 기존 패스키 사용자가 추가 인증에서도 같은 패스키를 쓰게 할 때
spring.mail.*와 앱의 JavaMailSender 빈없음메일 일회용 코드를 보내는 발송기입니다. 앱에 JavaMailSender 빈이 하나 있으면(여럿 가운데 @Primary인 것 포함) 그 발송기를 쓰고, 없거나 여럿이면 spring.mail.*로 CONTEXA 전용 발송기를 만듭니다. 이때 spring.mail.host가 없으면 발송기를 만들지 못해 메일 코드는 제공되지 않습니다. 사용자의 이메일은 실제 주소여야 하며, contexa.bridge.sync.synthetic-email-domain(기본 shadow.contexa.local)에 속한 주소는 실제 주소로 보지 않습니다.메일 일회용 코드를 추가 인증 수단으로 제공할 때
contexa.auth.ott.email-max-concurrent-sends · email-send-wait-seconds · email-smtp-timeout-seconds64 · 5 · 0메일 발송 제한입니다. 값의 뜻은 MFA 제한 시간과 재시도의 표에 있습니다.메일 서버 응답이 느릴 때
contexa.auth.mfa.max-retry-attempts5일회용 코드를 틀리게 입력할 수 있는 횟수입니다. CONTEXA MFA와 같은 값을 쓰고, 세션 환경(브라우저와 접속 주소의 조합)마다 따로 셉니다.입력 허용 횟수를 바꿀 때
contexa.bridge.step-up.reauthentication-url없음앱이 자체 MFA나 신원 공급자로 사용자를 다시 인증하는 주소입니다. 적으면 추가 인증 화면에 그 주소로 가는 링크가 나옵니다. 비어 있으면 앱의 재인증은 추가 인증 수단으로 쓰이지 않습니다. 자세한 조건은 인증 브리지의 설정에 있습니다.앱이 사용자를 직접 다시 인증할 수 있을 때
contexa.infrastructure.modestandalonedistributed이면 추가 인증이 발급한 패스키 옵션과 일회용 코드의 사용 기록을 Redis에 저장해 모든 인스턴스가 공유합니다. 자세한 내용은 저장 위치와 처음 켜기와 배포에 있습니다.인스턴스를 둘 이상 운영할 때
앞단 프록시없음로드밸런서나 API 게이트웨이 뒤에서 운영할 때 클라이언트 IP를 정하는 설정입니다. 앞단 프록시와 클라이언트 IP를 봅니다.앱 앞에 프록시가 있을 때

로그인 상태: 세션 또는 OAuth2 토큰

적용 대상: CONTEXA가 로그인을 맡는 FULL에서만.

로그인한 사용자를 HTTP 세션으로 유지할지(SESSION) OAuth2 액세스 토큰으로 유지할지(OAUTH2)를 정합니다. 흐름(로그인 방식 하나의 구성)마다 DSL에서 .session() 또는 .oauth2()로 정할 수 있고, 그 값이 설정보다 우선합니다. contexa.auth.state-type은 흐름이 정하지 않았을 때 쓰입니다. 로그아웃 처리 같은 일부 공통 처리는 흐름과 관계없이 이 값을 읽습니다. 기본 FULL 체인은 흐름마다 .session()을 지정합니다. OAuth2 상태 흐름은 로그인 상태를 OAuth2 토큰으로 유지하는 흐름입니다. DSL은 인증 DSL에 있습니다.

설정기본값뜻
contexa.auth.state-typeOAUTH2흐름에 지정이 없을 때의 상태 방식(OAUTH2 · SESSION)
contexa.auth.oauth2-server-modeCOMBINEDOAuth2 상태 흐름에서 CONTEXA가 맡는 서버 역할(아래 표). CONTEXA가 토큰을 발급할지를 실제로 정하는 설정입니다
contexa.auth.token-transport-typeHEADER토큰을 주고받는 방법(아래 표)
contexa.auth.token-persistencememoryCONTEXA가 만드는 MFA 화면의 스크립트가 토큰을 보관하는 곳: memory(새로 고침하면 사라짐) · localStorage · sessionStorage
contexa.auth.oauth2-csrffalseOAuth2 체인의 CSRF 보호입니다. COOKIE 전송에서는 이 값과 관계없이 항상 켜집니다
contexa.auth.cookie-securetrue토큰 쿠키에 Secure 속성을 붙입니다. Redis MFA 세션 쿠키는 이 값이 true이고 HTTPS 요청일 때만 Secure가 붙습니다
contexa.auth.cookie-same-siteLax토큰 쿠키의 SameSite(Strict · Lax · None). None은 cookie-secure: true일 때만 됩니다(아니면 기동이 멈춤)

OAuth2 서버 역할

contexa.auth.oauth2-server-mode가 정하는, CONTEXA가 OAuth2 상태 흐름에서 맡는 역할입니다.

값하는 일
RESOURCE_SERVER요청의 액세스 토큰을 검사만 합니다. CONTEXA는 토큰을 발급하지 않으므로 토큰 상태의 로그인 흐름이 있으면 기동이 멈춥니다.
AUTHORIZATION_SERVERCONTEXA가 토큰을 발급합니다(인가 서버 끝점과 로그아웃).
COMBINED(기본)둘 다 합니다.

토큰 전송 방식

contexa.auth.token-transport-type이 정하는, 액세스 토큰과 갱신 토큰을 요청과 응답에 실어 보내는 방법입니다.

값액세스 토큰갱신 토큰
COOKIE쿠키 accessToken쿠키 refreshToken
HEADER(기본)Authorization: Bearer … 헤더X-Refresh-Token 헤더
HEADER_COOKIEAuthorization: Bearer … 헤더쿠키 refreshToken
  • 서버가 HTML 페이지를 렌더링하는 앱은 COOKIE를 씁니다. 헤더 방식에 token-persistence: memory를 함께 쓰면 브라우저가 페이지를 이동할 때 요청에 토큰이 실리지 않으므로, 로그인한 뒤에도 서버가 렌더링한 페이지는 인증되지 않습니다. 이 조합이면 기동 때 ERROR 로그가 한 번 남습니다. 헤더 방식은 SPA에 맞습니다.
  • COOKIE에서는 CSRF 보호가 항상 켜집니다. 브라우저가 쿠키를 모든 요청에 실어 보내기 때문입니다. COOKIE와 oauth2-csrf: false를 함께 적으면 기동이 멈춥니다.

토큰 수명과 동시 로그인

적용 대상: CONTEXA가 로그인을 맡는 FULL에서만.

OAuth2 상태 흐름에서 CONTEXA가 발급하는 토큰의 수명과, 한 사용자가 동시에 유지할 수 있는 로그인 수입니다.

설정기본값뜻
contexa.auth.access-token-validity3600000액세스 토큰 수명(ms, 1시간). 0 이하면 기동이 멈춥니다
contexa.auth.refresh-token-validity604800000갱신 토큰 수명(ms, 7일). 0 이하면 기동이 멈춥니다
contexa.auth.enable-refresh-tokentruefalse면 갱신 토큰을 만들지 않습니다
contexa.auth.allow-multiple-loginsfalsefalse면 새로 로그인할 때 같은 사용자의 이전 로그인(유효한 갱신 토큰)을 모두 무효로 합니다
contexa.auth.max-concurrent-logins3allow-multiple-logins: true일 때 동시 로그인 상한. 넘으면 가장 오래된 로그인부터 무효로 합니다
  • 두 수명은 CONTEXA 인가 서버의 내부 클라이언트 토큰 설정과 토큰 쿠키에 함께 쓰입니다. 이미 DB에 저장된 내부 클라이언트도 기동할 때 이 수명으로 맞춥니다.
  • 갱신할 때마다 새 갱신 토큰을 발급하고 이전 것을 다시 쓰지 않습니다.

CONTEXA가 토큰을 발급할 때(인가 서버)

적용 대상: CONTEXA가 로그인을 맡는 FULL에서만.

FULL이면 소유권과 관계없이 CONTEXA 인가 서버가 구성됩니다. 실제로 토큰을 발급하는 것은 서버 역할에 AUTHORIZATION_SERVER가 들어 있고(COMBINED 포함), OAuth2 상태를 쓰는 흐름이 있을 때입니다. 끝점(endpoint)의 경로는 고정되어 있습니다: /oauth2/authorize · /oauth2/token · /oauth2/jwks · /oauth2/revoke · /oauth2/introspect · /connect/register · /userinfo.

# 기존 설정에 더하는 부분
contexa:
  auth:
    oauth2:
      client-secret: ${CONTEXA_OAUTH2_CLIENT_SECRET}
      issuer-uri: https://auth.example.com
      jwk-key-store-path: file:/etc/contexa/keys/jwk-keystore.p12
      jwk-key-store-password: ${CONTEXA_JWK_STORE_PASSWORD}
      jwk-key-alias: contexa

패스키 신뢰 당사자(RP)

적용 대상: 두 경우 모두(SANDBOX, FULL).

패스키(WebAuthn 자격 증명)는 브라우저가 사이트 도메인에 묶어 생성합니다. 신뢰 당사자(relying party, RP)는 그 도메인을 대표하는 서버 쪽 신원입니다. 한 번에 로그인의 패스키, MFA의 패스키, 앱이 로그인을 맡는 SANDBOX의 추가 인증 패스키가 모두 아래 값을 씁니다. 운영 환경에서는 rp-id를 사이트 도메인으로, allowed-origins를 실제 https 주소로 바꿉니다.

패스키는 webauthn4j 라이브러리와 Jackson CBOR 코덱이 클래스패스에 있어야 동작합니다. 앱이 이 라이브러리를 제외하면 패스키는 꺼지고 다른 수단만 제공됩니다.

설정기본값뜻
contexa.auth.urls.factors.passkey.rp-idlocalhost신뢰 당사자 ID입니다(보통 사이트 도메인).
contexa.auth.urls.factors.passkey.rp-namecontexa-identity사용자에게 보이는 이름
contexa.auth.urls.factors.passkey.allowed-origins없음패스키를 받을 출처(쉼표로만 구분, 공백 없이). 비우면 http://localhost:{server.port}(포트가 없으면 8080)

MFA 제한 시간과 재시도

적용 대상: 항목마다 다릅니다. contexa.auth.mfa.max-retry-attempts와 메일 발송 제한 세 가지(contexa.auth.ott.email-max-concurrent-sends, contexa.auth.ott.email-send-wait-seconds, contexa.auth.ott.email-smtp-timeout-seconds)는 두 경우 모두에 쓰이고, 나머지는 CONTEXA가 로그인을 맡는 FULL에서 주 흐름의 MFA와 일회용 코드 로그인에 쓰입니다.

메일을 보내는 발송기는 두 모드 모두(소유권과 무관) 같은 규칙을 따릅니다. 앱에 JavaMailSender 빈이 하나 있으면(여럿 가운데 @Primary인 것 포함) 그 발송기를 쓰고, 없거나 여럿이면 CONTEXA가 spring.mail.*로 자체 발송기를 만듭니다. 이 발송기는 빈으로 등록하지 않으므로 앱이 주입받는 발송기와 Spring Boot의 메일 자동설정은 그대로입니다.

설정기본값뜻
contexa.auth.mfa.session-timeout-ms600000MFA 세션이 만들어지거나 마지막 MFA 단계를 지난 뒤 유지되는 시간(ms, 10분)
contexa.auth.mfa.challenge-timeout-ms300000요소 확인을 시작한 뒤 이 시간이 지나면 확인 요청에 403(MFA session expired)으로 답합니다(ms, 5분)
contexa.auth.mfa.max-retry-attempts5요소마다 실패를 허용하는 횟수. 넘으면 그 요소의 확인 요청에 403으로 답하고 MFA 상태를 재시도 초과로 넘깁니다. 1보다 작으면 기동이 멈춥니다

차단된 사용자가 차단을 풀려고 거치는 MFA의 횟수는 이 설정이 아니라 운영 모드와 판정 조정에 있습니다. MFA 화면과 요소는 MFA에 있습니다.

MFA 세션과 상태 머신을 저장하는 곳

적용 대상: 두 경우 모두. MFA 세션과 MFA 상태 머신은 CONTEXA의 MFA 흐름(FULL의 주 흐름, 관리 콘솔 로그인)이 쓰고, 마지막 행의 추가 인증 상태는 앱이 로그인을 맡는 SANDBOX의 추가 인증이 씁니다. CONTEXA 로그인의 메일 일회용 코드도 두 모드 모두 발송 제한 기록을 같은 저장소에 둡니다.

저장 위치를 고르는 MFA 전용 설정은 없습니다. contexa.infrastructure.mode(처음 켜기와 배포)가 정합니다. MFA 상태 머신은 사용자 한 명의 MFA가 지금 어느 단계(요소 선택, 요소 확인, 완료, 재시도 초과 등)인지를 기록합니다.

앞단 프록시와 클라이언트 IP

적용 대상: 두 경우 모두(SANDBOX, FULL).

앱 앞에 로드밸런서나 API 게이트웨이가 있으면 앱이 보는 접속 주소는 프록시의 주소입니다. 실제 클라이언트 IP는 X-Forwarded-For 헤더에 담겨 오지만, 이 헤더는 누구나 보낼 수 있습니다. 그래서 CONTEXA는 기본값에서 이 헤더를 믿지 않고 접속한 주소를 씁니다. 믿을 프록시의 주소 목록을 정하면, 그 프록시에서 온 요청에 한해 헤더의 IP를 씁니다.

같은 용도의 설정이 쓰임새별로 두 벌 있고, 서로 별개이므로 각각 정합니다. 두 설정의 프록시 검사(trusted-proxy-validation-enabled)를 끄면 헤더를 위조해 클라이언트 IP를 속일 수 있으므로 기본값(true)으로 둡니다.

설정기본값쓰이는 곳자세한 설명
contexa.bridge.network.trusted-proxies없음인증 브리지가 읽는 요청 정보의 클라이언트 IP를 정할 때인증 브리지의 설정
contexa.security.tiered.security.trusted-proxies없음판정 사건 · 세션 지문 · IP 접근 제한의 클라이언트 IP를 정할 때클라이언트 IP와 믿을 프록시

자동 구성 끄기

적용 대상: 두 경우 모두(항목마다 다름). contexa.identity.handler.enabled가 끄는 처리기는 두 모드 모두 만들어집니다.

다섯 설정은 모두 기본으로 켜져 있습니다. 끄면 해당 자동 구성(Auto-configuration)의 빈이 만들어지지 않습니다. 같은 일을 하는 빈을 앱이 직접 등록할 때만 끕니다.

설정기본값끄는 것
contexa.identity.statemachine.enabledtrueMFA 상태 머신(MFA 흐름에 필요)
contexa.identity.mfa.enabledtrueMFA 정책 평가기 · 정책 제공자, MFA 화면 생성
contexa.identity.security-core.enabledtrue인증 보안 핵심(보안 체인을 만드는 부트스트랩 포함)
contexa.identity.service.enabledtrue주소 제공자, OTT 메일 서비스, MFA 설정 API. 앱이 로그인을 맡는 SANDBOX의 메일 일회용 코드도 이 메일 서비스를 씁니다
contexa.identity.handler.enabledtrueOTT 발급 성공 처리기, 세션 로그인 성공 · 실패 처리기(두 모드 모두 만들어짐. OTT 발급 성공 처리기는 FULL에서 앱에 같은 종류가 없을 때만 타입으로 등록되고, 그 밖에는 CONTEXA 흐름만 이름으로 씀)
