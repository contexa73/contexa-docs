Contexa가 로그인을 맡을 때

Contexa가 로그인 · MFA · 토큰 발급을 직접 맡을 때(CONTEXA_OWNED) 쓰는 설정입니다. 로그인 상태를 세션과 토큰 중 무엇으로 유지할지, 토큰 수명, Contexa 인가 서버, 로그인 · MFA 주소, MFA 제한 시간, MFA 상태를 저장하는 곳을 정할 수 있습니다.

이 설정이 쓰일 때

Contexa가 로그인을 맡는 것은 인증 소유권이 CONTEXA_OWNED일 때입니다. @EnableAISecurity(mode = SecurityMode.FULL)이면 이것이 기본이고, contexa.bridge.ownership으로 직접 정할 수도 있습니다. 기본인 HOST_OWNED에서는 앱의 Spring Security가 로그인을 처리하고 Contexa는 보안 체인을 만들지 않으므로 이 페이지의 설정은 쓰이지 않습니다. 그때 앱의 로그인 정보를 Contexa에 알리는 방법은 인증 브리지에 있습니다.

하려는 일설정절
로그인 상태를 세션 또는 토큰으로 유지contexa.auth.state-type, contexa.auth.token-transport-type로그인 상태
토큰 수명 · 동시 로그인 정하기contexa.auth.access-token-validity 등토큰 수명
Contexa가 토큰을 발급하게 하기contexa.auth.oauth2.*인가 서버
로그인 · MFA 주소 바꾸기contexa.auth.urls.*주소
MFA 제한 시간 · 재시도 횟수contexa.auth.mfa.*MFA
MFA 상태를 저장하는 곳contexa.infrastructure.mode, contexa.identity.statemachine.*저장 위치

로그인 상태: 세션 또는 OAuth2 토큰

로그인한 사용자를 HTTP 세션으로 기억할지(SESSION), OAuth2 액세스 토큰으로 기억할지(OAUTH2)를 정합니다. 흐름마다 DSL에서 .session() · .oauth2()로 정할 수 있고, 그 값이 먼저입니다. contexa.auth.state-type은 흐름이 정하지 않았을 때 쓰이며, 로그아웃 처리 같은 몇몇 공통 처리는 흐름과 상관없이 이 값을 읽습니다. 기본 FULL 체인은 흐름에 .session()을 지정합니다. DSL은 인증 DSL에 있습니다.

설정기본값뜻
contexa.auth.state-typeOAUTH2흐름에 지정이 없을 때의 상태 방식(OAUTH2 · SESSION)
contexa.auth.oauth2-server-modeCOMBINEDOAuth2 상태 흐름에서 Contexa가 맡는 서버 역할(아래 표). 토큰을 발급할지 정하는 실제 스위치입니다
contexa.auth.token-transport-typeHEADER토큰을 주고받는 방법(아래 표)
contexa.auth.token-persistencememoryContexa가 그리는 MFA 화면의 스크립트가 토큰을 둘 곳: memory(새로 고침하면 사라짐) · localStorage · sessionStorage
contexa.auth.oauth2-csrffalseOAuth2 체인의 CSRF 보호. COOKIE 전송에서는 이 값과 상관없이 늘 켜집니다
contexa.auth.cookie-securetrue토큰 쿠키에 Secure 표시. Redis MFA 세션 쿠키는 이 값이 true이고 HTTPS 요청일 때만 Secure가 붙습니다
contexa.auth.cookie-same-siteLax토큰 쿠키의 SameSite(Strict · Lax · None). None은 cookie-secure: true일 때만 됩니다(아니면 기동이 멈춤)

OAuth2 서버 역할

값하는 일
RESOURCE_SERVER요청의 액세스 토큰을 검사만 합니다. Contexa는 토큰을 발급하지 않습니다.
AUTHORIZATION_SERVERContexa가 토큰을 발급합니다(인가 서버 끝점과 로그아웃).
COMBINED(기본)둘 다 합니다.

토큰 전송 방식

값액세스 토큰갱신 토큰
COOKIE쿠키 accessToken쿠키 refreshToken
HEADER(기본)Authorization: Bearer … 헤더X-Refresh-Token 헤더
HEADER_COOKIEAuthorization: Bearer … 헤더쿠키 refreshToken
  • 서버가 그리는 페이지를 쓰는 앱은 COOKIE로 둡니다. 헤더 방식에 token-persistence: memory를 함께 쓰면 브라우저가 페이지를 옮길 때 토큰이 실리지 않아, 로그인한 뒤에도 서버 페이지가 인증되지 않습니다. 이 조합이면 기동 때 ERROR 로그가 한 번 남습니다. 헤더 방식은 SPA에 맞습니다.
  • COOKIE에서는 CSRF 보호가 늘 켜집니다. 브라우저가 쿠키를 모든 요청에 실어 보내기 때문입니다. COOKIE와 oauth2-csrf: false를 함께 적으면 기동이 멈춥니다.

토큰 수명과 동시 로그인

OAuth2 상태 흐름에서 Contexa가 발급하는 토큰의 수명과, 한 사용자가 동시에 유지할 수 있는 로그인 수입니다.

설정기본값뜻
contexa.auth.access-token-validity3600000액세스 토큰 수명(ms, 1시간)
contexa.auth.refresh-token-validity604800000갱신 토큰 수명(ms, 7일)
contexa.auth.enable-refresh-tokentruefalse면 갱신 토큰을 만들지 않습니다
contexa.auth.allow-multiple-loginsfalsefalse면 새로 로그인할 때 같은 사용자의 이전 로그인(유효한 갱신 토큰)을 모두 무효로 합니다
contexa.auth.max-concurrent-logins3allow-multiple-logins: true일 때 동시 로그인 상한. 넘으면 가장 오래된 로그인부터 무효로 합니다
  • 두 수명은 Contexa 인가 서버의 내부 클라이언트 토큰 설정과 토큰 쿠키에 함께 쓰입니다. 이미 DB에 저장된 내부 클라이언트도 기동할 때 이 수명으로 맞춥니다.
  • 갱신할 때마다 새 갱신 토큰을 발급하고 이전 것을 다시 쓰지 않습니다.

Contexa가 토큰을 발급할 때(인가 서버)

CONTEXA_OWNED이면 Contexa 인가 서버가 구성됩니다. 실제로 토큰을 발급하는 것은 서버 역할에 AUTHORIZATION_SERVER가 들어 있고(COMBINED 포함), OAuth2 상태를 쓰는 흐름이 있을 때입니다. 끝점은 정해져 있습니다: /oauth2/authorize · /oauth2/token · /oauth2/jwks · /oauth2/revoke · /oauth2/introspect · /connect/register · /userinfo.

# 기존 설정에 더하는 부분
contexa:
  auth:
    oauth2:
      client-secret: ${CONTEXA_OAUTH2_CLIENT_SECRET}
      issuer-uri: https://auth.example.com
      jwk-key-store-path: file:/etc/contexa/keys/jwk-keystore.p12
      jwk-key-store-password: ${CONTEXA_JWK_STORE_PASSWORD}
      jwk-key-alias: contexa
설정기본값뜻
contexa.auth.oauth2.client-iddefault-clientContexa 내부 클라이언트 ID. 처음 기동할 때 이 ID로 클라이언트를 DB에 저장합니다
contexa.auth.oauth2.client-secret없음내부 클라이언트 비밀. 토큰을 발급할 때 필수이고(없으면 기동이 멈춤), 재시작해도 같은 값이어야 합니다. 예전 기본 비밀값은 거부합니다
contexa.auth.oauth2.issuer-urihttp://localhost:9000발급하는 토큰의 발급자(iss), 리소스 서버가 기대하는 발급자, Contexa가 스스로 토큰을 받는 주소의 앞부분. 운영에서는 실제 주소로 바꿉니다
contexa.auth.oauth2.token-endpoint/oauth2/tokenContexa가 스스로 토큰을 받을 때 issuer-uri 뒤에 붙이는 경로
contexa.auth.oauth2.scoperead내부 클라이언트의 범위(쉼표 · 공백으로 여러 개). 비면 read
contexa.auth.oauth2.redirect-urihttp://localhost:8080내부 클라이언트를 처음 저장할 때 등록하는 redirect URI
contexa.auth.oauth2.authorized-uri없음함께 등록하는 redirect URI
contexa.auth.oauth2.jwk-key-store-path없음토큰 서명 키를 담은 PKCS12 저장소. 일반 경로는 클래스패스에서 찾고, 파일은 file: 접두사를 붙입니다. 비우면 기동할 때마다 임시 RSA 키를 만들어(ERROR 로그) 재시작하면 이전 토큰을 검증하지 못합니다
contexa.auth.oauth2.jwk-key-store-password없음키 저장소 비밀번호
contexa.auth.oauth2.jwk-key-alias없음저장소 안 키의 별칭. 토큰의 키 ID로도 쓰입니다
contexa.auth.oauth2.jwk-key-password없음키 비밀번호. 비우면 저장소 비밀번호를 씁니다
contexa.auth.internal.refresh-uri/api/refresh브라우저가 액세스 토큰을 새로 받는 주소. 인가 서버를 같은 앱에 둘 때(AUTHORIZATION_SERVER · COMBINED) 등록됩니다
저장된 내부 클라이언트와 비밀이 다르면 기동이 멈춥니다. 내부 클라이언트는 처음 기동할 때 DB에 한 번 저장되고, 그 뒤에는 토큰 수명만 맞춥니다. 저장된 클라이언트가 지금의 client-secret을 받지 않으면 Contexa는 저장된 값을 몰래 바꾸지 않고 기동을 멈춥니다. 저장된 클라이언트의 비밀을 바꾸거나, 그 클라이언트를 지워 다시 등록되게 하십시오. 서명 키 저장소를 /etc/… 같은 일반 경로로 적으면 클래스패스에서 찾다가 KeyStore not found로 기동이 멈추니, 파일이면 file:을 붙이십시오.

리소스 서버의 토큰 검사와 서비스 클라이언트

설정기본값뜻
contexa.auth.oauth2.issuer-validation-enabledtrue발급자(iss)가 Contexa 인가 서버의 발급자(없으면 issuer-uri)인 토큰만 받습니다. 아니면 401
contexa.auth.oauth2.audiences[]적으면 aud에 이 가운데 하나가 있는 토큰만 받습니다(아니면 401). 비면 검사하지 않습니다. Contexa 인가 서버는 토큰을 받은 클라이언트 ID를 aud에 넣습니다
contexa.auth.oauth2.service-client-ids[]자기 이름으로 받은 토큰(client credentials)을 사용자 계정 없이 인증할 클라이언트. 토큰의 범위가 권한이 됩니다. 내부 클라이언트는 이렇게 인증하지 않습니다
contexa.auth.oauth2.token-exchange-enabledfalseRFC 8693 토큰 교환 허용. 꺼져 있으면 모든 클라이언트의 교환 요청을 거부합니다. 에이전트가 사람 대신 토큰을 받을 때 씁니다(위임)
contexa.auth.oauth2.delegation-claim-enabledtrue교환으로 에이전트가 받는 토큰에 그 사람의 위임 ID(delegation_id)를 넣습니다

로그인 · MFA 주소

Contexa가 만드는 로그인 · MFA 화면과 처리 주소입니다. 흐름의 DSL에 주소를 적으면 그 값이 먼저이고, 적지 않은 주소만 이 설정을 씁니다. 이름이 있는 MFA 흐름이 여럿이면 흐름마다 주소 앞에 접두사가 붙을 수 있습니다. 로그아웃 처리 주소는 /logout(흐름 접두사 포함)으로 정해져 있습니다.

패스키 신뢰 당사자(RP)

패스키는 브라우저가 사이트 도메인에 묶어 만듭니다. 한 번에 로그인과 MFA의 패스키가 모두 아래 값을 씁니다. 운영에서는 rp-id를 사이트 도메인으로, allowed-origins를 실제 https 주소로 바꾸십시오.

설정기본값뜻
contexa.auth.urls.factors.passkey.rp-idlocalhost신뢰 당사자 ID(보통 사이트 도메인)
contexa.auth.urls.factors.passkey.rp-namecontexa-identity사용자에게 보이는 이름
contexa.auth.urls.factors.passkey.allowed-origins없음패스키를 받을 출처(쉼표로만 구분, 공백 없이). 비우면 http://localhost:{server.port}(포트가 없으면 8080)

MFA 제한 시간과 재시도

설정기본값뜻
contexa.auth.mfa.session-timeout-ms600000MFA 세션이 만들어지거나 마지막 MFA 단계를 지난 뒤 유지되는 시간(ms, 10분)
contexa.auth.mfa.challenge-timeout-ms300000요소 확인을 시작한 뒤 이 시간이 지나면 확인 요청에 403(MFA session expired)으로 답합니다(ms, 5분)
contexa.auth.mfa.max-retry-attempts5요소마다 실패를 허용하는 횟수. 넘으면 그 요소의 확인 요청에 403으로 답하고 MFA 상태를 재시도 초과로 넘깁니다
contexa.auth.mfa.minimum-delay-ms500로그인 · 요소 확인 응답이 이보다 빨리 나가지 않도록 기다리는 시간(ms)
contexa.auth.mfa.otp-token-validity-seconds300OTT 메일에 적는 유효 시간(분으로 바꿔 적음). 실제 코드 유효 시간은 Spring Security 기본값 5분이고 이 설정으로 바뀌지 않습니다
contexa.auth.mfa.metrics-enabledtruefalse면 MFA 상태 변화 리스너(MfaStateChangeListener)를 만들지 않습니다

차단된 사용자가 차단을 풀려고 거치는 MFA의 횟수는 이 설정이 아니라 집행 모드와 판정 조정에 있습니다. MFA 화면과 요소는 MFA에 있습니다.
