AI 모델 연결

CONTEXA는 AI 모델로 보호 대상 요청마다 판정(Decision)을 만듭니다. CONTEXA는 모델 공급자에 직접 접속하지 않고, 앱에 추가한 Spring AI 스타터가 만든 모델을 사용합니다. 따라서 모델을 연결하려면 공급자의 Spring AI 스타터와 API 키를 앱에 추가합니다. 반드시 정해야 하는 것은 채팅 모델 공급자(판정을 만드는 모델), 임베딩 모델 공급자(비슷한 과거 판정 기록을 찾는 모델), CONTEXA 전용 DB와 벡터 저장소입니다. 나머지 설정은 기본값으로 동작합니다. 이 페이지는 모델을 연결하고 고르는 방법과 모델 서버의 동시 호출 한도를 설명합니다.

이 페이지에서 정하는 것

CONTEXA는 모델 공급자에 직접 접속하지 않습니다. 앱에 있는 Spring AI의 채팅 모델 빈과 임베딩 모델 빈을 모아 이름을 붙이고, 기동할 때 기본 채팅 모델 하나와 임베딩 모델 하나를 고릅니다. 판정을 만들 때는 1차 · 2차 분석에 지정한 모델을 쓰고, 지정이 없으면 기본 채팅 모델을 씁니다. 이 페이지는 설정을 중심으로 설명하고, 모델이 정해지는 동작의 자세한 내용은 모델 공급자 참조(요청마다 모델이 정해지는 순서)에 있습니다.

이 페이지에서 쓰는 용어는 다음과 같습니다.

  • 공급자(provider): 모델을 제공하는 쪽입니다. 이 페이지는 openai · anthropic · ollama를 다룹니다.
  • 모델 빈: Spring AI가 앱 안에 만든 채팅 모델 또는 임베딩 모델 객체입니다.
  • 모델 목록과 바인딩: CONTEXA가 앱의 모든 채팅 모델 · 임베딩 모델 빈에 이름을 붙여 올려 두는 목록입니다. 목록의 항목 하나를 바인딩(binding)이라고 하며, 자세한 내용은 모델에 이름 붙이기에 있습니다.
  • AI 파이프라인과 AI Lab: AI 파이프라인은 Lab이나 컨트롤러가 호출하면 요청을 여러 단계로 나누어 처리하는 구성입니다(파이프라인과 RAG). Lab은 도메인 데이터를 모으고 파이프라인을 부르는 작업 단위입니다.
  • 채팅 모델: 요청의 사실을 읽고 판정을 답하는 AI 모델입니다. 판정은 허용(ALLOW) · 추가 인증(CHALLENGE) · 검토 보류(ESCALATE) · 차단(BLOCK) 중 하나입니다.
  • 임베딩 모델: 문서를 숫자 배열(벡터)로 바꾸는 AI 모델입니다. 비슷한 과거 판정 기록을 찾는 검색에 씁니다.
  • 1차 분석 · 2차 분석(분석 단계): 판정을 만드는 두 단계입니다. 1차 분석이 요청을 판정하고, 검토 보류(ESCALATE, 이 사실만으로는 정할 수 없다는 답)를 받은 요청만 2차 분석이 다시 판정합니다. 설정 키에서는 두 단계를 layer1 · layer2라고도 부릅니다.
채팅 모델이 없어도 대부분의 앱은 기동합니다. 채팅 모델이 하나도 없으면 CONTEXA는 기동하지만 판정을 만들지 못하고, 보호 대상 요청은 분석 대기(PENDING_ANALYSIS) 상태로 남습니다. 기동이 끝날 때 CONTEXA는 필요한 빈이 만들어졌는지 검사하는 기능 진단을 실행하고, 만들어지지 않은 모델 빈을 기동 로그([ContexaCapability] llm-runtime · embedding-runtime)로 알립니다. 예외는 CONTEXA 소유 앱입니다. contexa.datasource.isolation.contexa-owned-application이 true이거나 spring.application.name이 contexa-로 시작하는 앱이 CONTEXA 소유 앱이며, 여기서는 기능 진단이 기본으로 FAIL_FAST가 되어 필수 모델 빈이 만들어지지 않으면 기동을 멈춥니다(기능 진단). 로그를 읽는 방법은 기동 로그의 진단 메시지와 대응에 있습니다.

먼저 정할 것과 기본값으로 두는 것

반드시 정해야 하는 것은 세 가지입니다. 나머지는 기본값으로 동작하고, 해당하는 상황에서만 바꿉니다.

구분정할 것설명
필수채팅 모델 공급자공급자의 Spring AI 스타터와 API 키를 앱에 추가합니다. 채팅 모델이 없으면 앱은 시작하지만 판정이 만들어지지 않습니다(공급자 연결하기).
필수임베딩 모델 공급자임베딩 공급자는 contexa.llm.selection.embedding.priority(기본 openai)가 정하고, openai 또는 ollama입니다. Ollama를 쓰려면 ollama로 바꿉니다. Anthropic은 채팅 모델 키만 있으므로, Anthropic을 쓰면 OpenAI나 Ollama의 임베딩 모델을 함께 연결합니다(임베딩 모델과 벡터 차원).
필수전용 DB와 벡터 저장소CONTEXA 전용 DB 주소(contexa.datasource.url), 벡터 저장소 의존성, DB의 vector 확장이 필요합니다(설치 가이드, 벡터 저장소).
상황에 따라 바꿈기본 채팅 모델공급자를 둘 이상 연결했고 쓸 공급자를 정해야 할 때 바꿉니다(기본 채팅 모델 고르기).
상황에 따라 바꿈1차 · 2차 분석 모델두 단계에 서로 다른 모델을 쓰려고 할 때 바꿉니다(1차 · 2차 분석 모델, 모델에 이름 붙이기).
상황에 따라 바꿈자체 호스팅 서버Ollama를 쓰거나, 모델 서버의 동시 처리 수가 기본값(자체 호스팅 2, 원격 16)과 다를 때 바꿉니다(로컬 Ollama 쓰기, 모델 서버가 한 번에 받는 호출 수).
상황에 따라 바꿈벡터 차원과 스키마모르는 임베딩 모델을 쓰거나, 차원이 2000을 넘거나, 벡터 표(DB 테이블)를 마이그레이션으로 관리할 때 바꿉니다(차원이 정해지는 순서, 벡터 저장소).
거의 바꾸지 않음저장 재시도, 문맥 검색 기본값, 공급자별 호출 옵션, 모델별 처리 표, 어드바이저 · 스트리밍기본값으로 둡니다(저장 실패 재시도, 과거 기록 · 문맥 검색, 공급자별 판정 호출 옵션, 모델별 처리 표, 어드바이저와 스트리밍).

공급자 연결하기

공급자는 앱의 Spring AI 설정으로 연결합니다. CONTEXA 스타터에는 모델 공급자가 들어 있지 않고, CONTEXA에는 contexa.llm.openai.* 같은 공급자 키도 없습니다. CONTEXA는 Spring AI 1.1.8로 빌드됩니다. 연결은 다음 순서로 합니다.

  1. 쓸 공급자의 Spring AI 스타터를 앱 의존성에 더합니다(아래 표).
  2. API 키와 모델 이름을 Spring AI 설정(spring.ai.*)에 적습니다.
  3. CONTEXA 전용 DB 주소(contexa.datasource.url)를 적습니다. 모델과 상관없이 늘 필요합니다.
  4. 앱을 기동하고 로그를 확인합니다. 기능 진단 ERROR([ContexaCapability])가 없는지, INFO 로그에 Embedding vector dimension verified가 남았는지 봅니다(읽는 방법은 진단 메시지와 대응).
공급자앱에 더할 의존성CONTEXA가 모델 이름으로 읽는 키
OpenAIorg.springframework.ai:spring-ai-starter-model-openai채팅 spring.ai.openai.chat.options.model, 임베딩 spring.ai.openai.embedding.options.model
Anthropicorg.springframework.ai:spring-ai-starter-model-anthropic채팅 spring.ai.anthropic.chat.options.model
Ollamaorg.springframework.ai:spring-ai-starter-model-ollama, 또는 CONTEXA 전용 연결채팅 spring.ai.ollama.chat.options.model, 임베딩 spring.ai.ollama.embedding.options.model

OpenAI 하나로 시작하는 설정 예입니다. OpenAI는 채팅 모델과 임베딩 모델을 모두 제공하므로 이 설정 하나로 두 모델이 연결됩니다. 임베딩 모델 이름을 적지 않으면 Spring AI의 기본 임베딩 모델이 쓰입니다(임베딩 모델과 벡터 차원). contexa.datasource.url은 모델과 상관없이 늘 필요한 CONTEXA 전용 DB 주소입니다.

spring:
  ai:
    openai:
      api-key: ${OPENAI_API_KEY}
      chat:
        options:
          model: gpt-4o-mini

contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
  • 공급자를 여러 개 넣으면 모두 목록에 오르고, 기본 채팅 모델은 다음 절의 규칙으로 하나만 고릅니다.
  • Spring AI 모델 자동 구성 고르기. Spring AI는 스타터마다 채팅 모델 자동 구성을 켭니다. contexa.llm.selection.chat.priority에 공급자를 하나만 적으면(openai · anthropic · ollama) CONTEXA는 spring.ai.model.chat의 기본값을 그 공급자로 넣고, 다른 공급자의 Spring AI 채팅 자동 구성은 켜지지 않습니다. 임베딩도 contexa.llm.selection.embedding.priority의 첫 공급자로 spring.ai.model.embedding의 기본값을 넣습니다. 앱이 spring.ai.model.*를 직접 적으면 그 값이 우선합니다. CONTEXA는 이미지 · 음성 · 검열 모델의 자동 구성을 끄지 않으므로, 끄려면 앱이 해당 키에 none을 적습니다.
  • 판정 호출의 온도(temperature)와 seed는 Spring AI 설정이 정하지 않습니다. temperature는 답의 무작위성을 정하는 값이고, seed는 같은 입력에 같은 답을 내도록 하는 난수 시작값입니다. 판정 호출은 contexa.security.tiered.determinism.temperature(기본 0.0) · seed(기본 1)를 호출마다 넣습니다. 운영 모드와 판정 조정에서 바꿉니다.
  • contexa.llm.enabled: false면 CONTEXA의 LLM 자동 구성 전체가 꺼집니다.

기본 채팅 모델 고르기

CONTEXA는 기동할 때 채팅 모델 하나를 기본 채팅 모델(빈 이름 primaryChatModel)로 정합니다. 분석 단계 모델을 지정하지 않은 판정과 CONTEXA의 AI 파이프라인 호출이 이 모델을 씁니다. 고르는 방법은 contexa.llm.selection.chat.mode로 정합니다. 공급자를 하나만 연결했다면 기본값(dynamic-priority)을 그대로 둡니다. 공급자가 둘 이상이면 아래 세 가지 방법 중 하나를 고릅니다.

값고르는 방법기동이 멈추는 경우
dynamic-priority(기본)priority 목록의 공급자 순서대로, 그 공급자의 모델 빈을 만들 수 있는 첫 모델을 고릅니다. 목록의 공급자 모델을 하나도 쓸 수 없으면 목록에 없는 공급자의 모델도 차례로 시도합니다(고르는 순서).모델 빈이 있는데 하나도 만들 수 없을 때
fixedpriority에 적은 공급자 하나의 모델만 씁니다. 다른 공급자로 넘어가지 않습니다.priority에 공급자를 둘 이상 적었거나, 그 공급자의 모델이 없을 때
spring-primaryprimary로 표시된 모델 하나(바인딩의 primary: true 또는 @Primary 빈). 모델이 하나뿐이면 그것을 씁니다.primary가 둘 이상이거나, 모델이 여럿인데 primary가 없을 때

같은 공급자의 모델이 여럿이면 primary로 표시된 모델이 먼저이고, 그다음은 이름 순서입니다.

dynamic-priority가 모델을 고르는 순서

기본값인 dynamic-priority는 아래 순서로 기본 채팅 모델을 정합니다.

  1. priority 값을 쉼표로 나누어 소문자로 바꾸고, 겹치는 공급자는 하나로 합칩니다. 기본값은 openai,anthropic,ollama입니다.
  2. 목록의 첫 공급자부터, 그 공급자로 분류된 모델 빈을 차례로 만들어 봅니다. 순서는 primary로 표시된 빈이 먼저이고, 그다음은 이름(바인딩 키 또는 빈 이름) 순서입니다. 처음 만들어지는 모델이 기본 채팅 모델이 됩니다.
  3. 만들 수 없는 빈은 WARN 로그 LLM runtime provider '<공급자>' binding '<빈>' is not ready: ...를 남기고 건너뜁니다. 같은 공급자의 다음 빈, 그다음 공급자 순서로 계속합니다. 로그 끝의 원인(API 키 누락, 주소 오류 등)이 건너뛴 이유입니다.
  4. 목록의 공급자에서 하나도 얻지 못하면, 목록에 없는 공급자를 포함한 모든 모델 빈을 같은 방식(primary 먼저, 그다음 공급자 이름, 바인딩 키 순서)으로 시도합니다. 이때의 WARN 로그는 LLM runtime binding '<빈>' is not ready: ...입니다.
  5. 모든 빈을 만들 수 없으면, 처음 실패한 오류로 기동이 멈춥니다.
mode 값은 소문자와 하이픈으로 적습니다. dynamic-priority · fixed · spring-primary로 적습니다. CONTEXA는 이 값을 조건으로 써서 기본 채팅 모델 빈을 만듭니다. DYNAMIC_PRIORITY처럼 밑줄을 쓴 이름은 어느 조건에도 맞지 않아, 오류 없이 기본 채팅 모델이 만들어지지 않습니다. 모델 빈은 있는데 기능 진단의 Missing beans에 UnifiedLLMOrchestrator(CONTEXA의 모든 모델 호출이 거치는 오케스트레이터, LLM 호출하기)가 나오면 mode 값의 철자를 먼저 확인합니다.
  • 고르는 일은 기동할 때 한 번입니다. 운영 중 공급자 호출이 실패해도 다른 모델로 바꿔 부르지 않습니다. 연결 끊김 · 429 · 503 같은 일시 오류는 같은 모델로 최대 4번 다시 시도합니다. 다시 시도할 때마다 WARN 로그(Retry #번호 - RequestId: ...)가 남고, 모두 실패하면 ERROR 로그(failed after 4 retries)가 남습니다. 끝내 답을 받지 못한 판정이 어떻게 되는지는 판정 엔진에 있습니다.
  • 예전 설정 contexa.llm.chat-model-priority는 priority를 빈 값으로 적었을 때만 쓰입니다.

    selection:
      chat:
        mode: fixed
        priority: anthropic

1차 · 2차 분석 모델

판정은 대부분 1차 분석에서 끝나고, 1차가 검토 보류(ESCALATE)로 답한 요청만 2차 분석으로 갑니다(판정 엔진). 두 분석 단계는 서로 다른 모델을 쓸 수 있습니다. 예를 들어 1차는 빠르고 비용이 낮은 모델, 2차는 더 신중한 모델로 둡니다. 지정하지 않으면 두 분석 단계 모두 기본 채팅 모델을 씁니다.

# 기본 채팅 모델이 OpenAI일 때(기존 설정에 더하는 부분)
contexa:
  security:
    tiered:
      llm:
        layer1:
          model: gpt-4o-mini
        layer2:
          model: gpt-4o
          backup:
            model: gpt-4o-mini

분석 단계 모델 이름은 다음 순서로 실제 모델이 됩니다.

  1. 같은 이름의 모델을 찾습니다. 적은 이름이 목록의 어떤 모델의 이름(빈 이름 · 바인딩 키 · 모델 이름 · 별칭)과 같으면 그 모델을 씁니다.
  2. 같은 이름이 없으면 기본 채팅 모델을 복사합니다. 모델 이름만 바꾼 복사본을 씁니다. 이 복사는 OpenAI 채팅 모델(mutate())과 Anthropic 채팅 모델(CONTEXA가 같은 클라이언트와 기본 옵션으로 다시 만듦)에서 됩니다. Ollama 채팅 모델은 복사할 수 없습니다. 그런 모델을 분석 단계마다 바꾸려면 바인딩으로 이름을 붙입니다(Ollama는 아래 방법).
  3. 둘 다 안 되면 그 분석 단계의 모델은 쓸 수 없습니다. 기동은 계속되고 ERROR 로그 한 줄이 남습니다(아래).

쓸 수 없는 분석 단계 모델마다 기동할 때 ERROR 로그 한 줄이 남습니다. 형식은 다음과 같습니다.

[TieredLayerModel] contexa.security.tiered.llm.layer2.model '<적어 둔 이름>' cannot be used, so layer 2 runs on '<대신 쓰는 모델>': no chat runtime binding has this model id and the primary chat model cannot be copied with it. Bind a chat model with contexa.llm.bindings.chat to run it.
  • 대신 쓰는 모델은 그 분석 단계의 백업 모델이고, 백업 모델도 쓸 수 없으면 기본 채팅 모델의 모델 이름입니다. 채팅 모델이 하나도 없으면 no chat model이 나옵니다.
  • 이 로그가 나오면 적어 둔 이름을 바인딩의 별칭이나 모델 이름으로 붙입니다.
  • 이 검사는 운영 모드가 관찰 모드(SHADOW) 또는 적용 모드(ENFORCE)일 때만 합니다. 끔(DISABLED)에서는 두 분석 단계가 실행되지 않으므로 로그도 남지 않습니다.
  • 백업 모델은 분석 단계 모델을 적었을 때만 쓰이고, 기동 때 검사하지 않습니다. 호출할 때 백업도 만들 수 없으면 기본 채팅 모델을 씁니다.
설정기본값뜻
contexa.security.tiered.llm.layer1.model없음1차 분석 모델. 비우면 기본 채팅 모델
contexa.security.tiered.llm.layer2.model없음2차 분석 모델. 비우면 기본 채팅 모델
contexa.security.tiered.llm.layer1.backup.model없음1차 분석 모델을 쓸 수 없을 때 대신 쓸 모델
contexa.security.tiered.llm.layer2.backup.model없음2차 분석 모델을 쓸 수 없을 때 대신 쓸 모델
contexa.security.tiered.llm.tiered.layer1.timeout-ms없음1차 분석 스트리밍 호출의 제한 시간(ms). 비우면 30000, 120000을 넘으면 120000
contexa.security.tiered.llm.tiered.layer2.timeout-ms없음2차 분석 스트리밍 호출의 제한 시간(ms). 비우면 60000, 120000을 넘으면 120000

마지막 두 설정은 스트리밍 호출(답을 조각으로 나눠 받는 호출)에만 쓰이고 판정 시간에는 영향이 없습니다. 1차 · 2차 분석의 제한 시간, 모델 호출 하나의 제한 시간은 운영 모드와 판정 조정에서 정합니다.

모델에 이름 붙이기(bindings)

CONTEXA는 앱에 있는 모든 채팅 모델 · 임베딩 모델 빈을 스스로 목록에 올립니다. 목록의 항목(바인딩)은 빈 이름, 공급자, 모델 이름, 별칭, primary 표시로 이루어집니다. 설정하지 않아도 빈 이름, 공급자(빈 클래스 · 이름에서 추정), 모델 이름(공급자의 spring.ai.…options.model, 없으면 빈 이름)으로 찾을 수 있습니다. contexa.llm.bindings는 이 항목을 고치거나 별칭(분석 단계 모델 설정에 적을 수 있는 추가 이름)을 더할 때 씁니다. 모델 빈이 하나뿐이거나 이름을 바꿀 필요가 없으면 설정하지 않습니다.

설정기본값뜻
contexa.llm.bindings.chat.<이름>.bean-name없음붙일 모델 빈 이름. 비우면 <이름>이 빈 이름과 같을 때 그 빈에 붙습니다
contexa.llm.bindings.chat.<이름>.provider없음공급자. 비우면 빈 클래스 · 이름에서 추정합니다(ollama · anthropic · openai · gemini · mistral · bedrock · huggingface, 그 밖은 spring)
contexa.llm.bindings.chat.<이름>.model-id없음모델 이름. 비우면 위 공급자 표의 키, 그것도 없으면 빈 이름
contexa.llm.bindings.chat.<이름>.aliases[]더 붙일 이름. 분석 단계 모델 설정에 이 이름을 적을 수 있습니다
contexa.llm.bindings.chat.<이름>.enabledtruefalse면 이 설정을 쓰지 않습니다. 빈은 자기 이름으로 목록에 그대로 남습니다
contexa.llm.bindings.chat.<이름>.primaryfalse같은 공급자 안에서 먼저 고르고, spring-primary 모드의 기준이 됩니다

임베딩 모델은 같은 필드를 contexa.llm.bindings.embedding.<이름>.…에 적습니다. 임베딩의 모델 이름을 키에서 추정하는 공급자는 OpenAI · Ollama뿐입니다.

  • 이름이 겹치면 기동이 멈춥니다. 빈 이름 · 바인딩 키 · 별칭이 서로 다른 두 모델에 겹치면 안 됩니다. 이때 로그는 Duplicate chat runtime selector '<이름>' is mapped by multiple bindings: ...입니다(임베딩은 embedding). 이름을 서로 다르게 적습니다.
  • 모델 이름만 겹치는 경우. 같은 공급자 모델 빈이 둘이고 둘 다 모델 이름을 같은 키에서 얻으면 모델 이름이 같아집니다. 이것만으로는 기동이 멈추지 않습니다. 다만 그 모델 이름으로 분석 단계 모델을 지정하면 어느 빈인지 정할 수 없어 오류가 납니다(... is the model of several of the application's beans ...). 이때는 model-id를 서로 다르게 적고, 빈 이름이나 바인딩 키로 지정합니다.
  • 별칭은 고르는 데 쓰는 이름입니다. OpenAI · Anthropic 모델은 별칭으로 골라도 그 빈에 설정된 모델로 호출합니다. 호출 모델이 별칭이 되는 것은 Ollama뿐입니다(아래).
  • bean-name이 가리키는 빈이 없으면 WARN 로그(Configured LLM binding '<키>' references missing bean '<빈>')만 남기고 그 설정을 건너뜁니다.

예: 기본 채팅 모델은 OpenAI 그대로 두고, 2차 분석만 Anthropic 모델로 돌립니다. anthropicChatModel은 Spring AI Anthropic 스타터가 만드는 빈 이름입니다.

# 기존 설정에 더하는 부분
spring:
  ai:
    anthropic:
      api-key: ${ANTHROPIC_API_KEY}

contexa:
  llm:
    bindings:
      chat:
        anthropicChatModel:
          aliases: [expert]
  security:
    tiered:
      llm:
        layer2:
          model: expert

로컬 Ollama 쓰기

Ollama는 직접 운영하는 서버에서 모델을 실행하는 자체 호스팅(self-hosted) 공급자입니다. CONTEXA에 연결하는 방법은 두 가지이고, 하나만 고릅니다.

CONTEXA 전용 연결은 contexa.llm.chat.ollama.base-url을 적으면 켜집니다(앱에 Ollama 라이브러리가 있을 때). 채팅과 임베딩이 같은 Ollama 서버를 쓰고, 모델을 적지 않으면 채팅은 qwen3:8b, 임베딩은 mxbai-embed-large를 씁니다. 아래 예는 채팅과 임베딩 공급자를 모두 ollama로 지정합니다(두 priority). Ollama 하나로 시작하는 설정 예입니다.

contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
  llm:
    chat:
      ollama:
        base-url: http://localhost:11434
        model: qwen3:8b
        keep-alive: 30m
    selection:
      chat:
        priority: ollama
      embedding:
        priority: ollama
설정기본값뜻
contexa.llm.chat.ollama.base-url없음Ollama 서버 주소. 적으면 CONTEXA가 Ollama 연결과 위 두 빈을 만듭니다
contexa.llm.chat.ollama.model없음채팅 모델. 비우면 qwen3:8b
contexa.llm.chat.ollama.keep-alive없음호출 뒤 모델을 메모리에 남겨 둘 시간(Ollama keep_alive, 예 30m). 비우면 Ollama 기본
contexa.llm.embedding.ollama.model없음임베딩 모델. 비우면 mxbai-embed-large
contexa.llm.embedding.ollama.dedicated-runtime-enabledfalsetrue면 임베딩만 다른 Ollama 서버로 보냅니다(빈 contexaDedicatedOllamaEmbeddingModel)
contexa.llm.embedding.ollama.base-url없음임베딩 전용 서버 주소. 전용 서버를 켰는데 비우면 기동이 멈춥니다
contexa.llm.model-capabilities.ollama.disable-thinking-patterns없음사고(thinking)를 끌 Ollama 모델 이름 패턴(정규식, 쉼표로 구분). 이름이 맞는 모델은 호출할 때 thinking을 끕니다

채팅 서버 주소와 전용 임베딩 서버를 함께 쓰면 임베딩 모델 빈이 둘(공유 · 전용) 생깁니다. 이름 순서로 전용 빈이 먼저 골라집니다.

Ollama 서버 하나에서 분석 단계마다 다른 모델 쓰기

Ollama 채팅 모델은 복사할 수 없으므로, 분석 단계 모델 이름을 Ollama 채팅 빈의 별칭으로 붙입니다. Ollama 호출은 고른 이름을 그대로 모델로 보내므로 같은 서버의 다른 모델이 쓰입니다. 그 모델은 Ollama 서버에 미리 내려받아 두어야 합니다.

# 위 Ollama 예에 더하는 부분
contexa:
  llm:
    bindings:
      chat:
        contexaOllamaChatModel:
          aliases: [qwen3:8b, qwen3:14b]
  security:
    tiered:
      llm:
        layer1:
          model: qwen3:8b
        layer2:
          model: qwen3:14b

모델 서버가 한 번에 받는 호출 수

모델 서버는 한 번에 처리할 수 있는 요청 수가 정해져 있습니다. CONTEXA는 이 한도를 넘지 않도록 모델 서버로 보내는 모든 호출을 서버별 동시 호출 제한 장치(게이트, gate)에 통과시킵니다. 서버는 공급자와 주소의 조합입니다. 두 분석 단계의 판정, AI 파이프라인, 벡터 저장소의 임베딩이 모두 이 제한을 받습니다. 한도를 넘는 호출은 서버에 쌓이지 않고 게이트에서 대기합니다.

  • 자체 호스팅 서버(Ollama, 또는 이 컴퓨터나 사설망의 주소)는 한 번에 2개, 한 번에 한 모델만 받습니다. 서버가 모델을 한 번에 하나만 메모리에 올린다고 가정하기 때문입니다. 다른 모델 호출(판정 중의 임베딩 같은)은 진행 중인 호출이 끝나면 들어갑니다. 원격 공급자는 한 번에 16개를 받습니다.
  • 임베딩 호출은 대기 중인 판정 호출보다 먼저 게이트를 통과합니다. 게이트를 통과해 실행 중인 호출은 다른 호출 때문에 중단되지 않습니다.
  • 모델 호출과 벡터 저장 · 검색의 제한 시간은 호출이 게이트를 통과한 때부터 셉니다. 게이트에서 대기하는 시간은 이벤트 처리 제한 시간(contexa.security.plane.agent.event-timeout-ms) 안으로 제한됩니다. 그 안에 차례가 오지 않은 호출은 MODEL_SERVER_BUSY로 끝납니다. 서버 장애가 아니라 정의된 결과로 기록됩니다. 자주 나타나면 서버가 실제로 더 많은 요청을 병렬로 처리할 수 있는지 확인하고, 그렇다면 아래 표의 동시 호출 수를 그 값에 맞춥니다.
  • 분당 한도(429), 과부하(529), 잠시 쓸 수 없음(503) 응답을 받으면 그 서버로 가는 호출을 2초 멈추고, 같은 응답이 이어지면 4 · 8 · 12초로 늘립니다. 호출은 차례가 오면 다시 보냅니다.
설정기본값뜻

contexa:

    gate:
      servers:
        gpu:
          base-url: http://gpu-box:11434
          max-concurrent: 4
          one-model-at-a-time: false

임베딩 모델과 벡터 차원

임베딩 모델은 과거 판정 기록 같은 문서를 벡터(숫자 배열)로 바꿔 저장하고 검색할 때 씁니다. 벡터의 길이를 차원(dimension)이라고 하며 모델마다 정해져 있습니다. 저장된 벡터의 차원이 모델과 같아야 하므로 임베딩은 공급자 하나로 고정합니다. 임베딩 공급자는 openai 또는 ollama입니다. 임베딩 모델은 다음 순서로 정해집니다(fixed, 기본).

  1. contexa.llm.selection.embedding.priority를 읽습니다. 기본값은 openai입니다. 공급자가 정확히 하나가 아니면 기동이 멈춥니다.
  2. 그 공급자의 임베딩 모델 빈 가운데 처음 만들어지는 것을 씁니다. primary로 표시된 빈이 먼저이고, 그다음은 이름 순서입니다.
  3. 그 공급자의 임베딩 모델이 없으면 다른 임베딩 모델 빈 가운데 처음 만들어지는 것을 씁니다.
설정기본값뜻

contexa.llm.embedding.ollama.dimensions1024Ollama 임베딩 차원. 직접 적었을 때만 쓰입니다(아래 순서 3)

차원이 정해지는 순서

CONTEXA는 아래 순서로 벡터 차원을 정하고, 위쪽에 값이 있으면 그 값을 씁니다.

  1. contexa.vectorstore.pgvector.dimensions를 직접 적었으면 그 값
  2. contexa.llm.embedding.dimensions를 적었으면 그 값
  3. 공급자의 차원 키: OpenAI는 spring.ai.openai.embedding.options.dimensions, Ollama는 contexa.llm.embedding.ollama.dimensions(또는 spring.ai.ollama.embedding.options.dimensions)
  4. CONTEXA가 아는 모델이면 그 모델의 값: OpenAI text-embedding-ada-002 · text-embedding-3-small은 1536, text-embedding-3-large는 3072, Ollama mxbai-embed-large · bge-m3는 1024
  5. 모르는 모델인데 위 값이 하나도 없으면 기동이 멈춥니다. 그 모델의 차원을 contexa.llm.embedding.dimensions와 contexa.vectorstore.pgvector.dimensions에 함께 적습니다.

OpenAI의 임베딩 모델과 차원은 다음과 같습니다.

  • CONTEXA는 spring.ai.openai.embedding.options.model과 dimensions에 기본값을 넣지 않고 앱의 임베딩 모델을 따릅니다.
  • 모델을 적지 않은 OpenAI는 Spring AI 기본값 text-embedding-ada-002(1536차원)이고, dimensions를 적으면 그 값입니다.
  • contexa init의 OpenAI 설치는 설정 파일에 text-embedding-3-small(1536)을 적습니다.
  • contexa.llm.selection.embedding.priority나 spring.ai.model.embedding으로 공급자를 지정하지 않으면, 앱에 OpenAI 임베딩 모델 클래스가 있을 때만 OpenAI로 평가합니다.

차원과 관련해 기동이 달라지는 경우는 세 가지입니다.

  • 새 DB: 벡터 열은 사용 중인 모델의 차원으로 만들어집니다.
  • 2000차원을 넘을 때: pgvector HNSW 색인은 2000차원까지이므로 기동이 거부됩니다(initialize-schema가 true이고 색인이 HNSW일 때). 로그는 The vector store cannot create its index: an HNSW index holds at most 2000 dimensions ...로 시작해 할 일을 알려 줍니다. 더 작은 출력을 지정하거나(예: text-embedding-3-large에 spring.ai.openai.embedding.options.dimensions=1536), 표를 직접 만들고 contexa.vectorstore.pgvector.initialize-schema=false를 적습니다.
  • 이전 버전의 OpenAI 설치: 표가 1024차원이라 기동이 거부됩니다. 이때 차원 불일치 로그의 끝에 A store made by an earlier Contexa keeps its vectors with ...가 붙습니다. 아래 두 줄을 넣으면 다시 임베딩하지 않고 그대로 유지됩니다.
spring.ai.openai.embedding.options.model=text-embedding-3-small
spring.ai.openai.embedding.options.dimensions=1024
차원을 바꾸면 이미 저장된 벡터와 맞지 않습니다. 기동할 때 CONTEXA는 쓰는 임베딩 모델의 차원, 설정된 벡터 저장소 차원, 이미 있는 벡터 표(기본 ctxa_vector_store)의 차원을 비교하고 하나라도 다르면 기동을 멈춥니다. 차원을 바꾸려면 표를 새로 만들거나 문서를 다시 임베딩합니다. 맞으면 기동 로그에 INFO로 Embedding vector dimension verified: provider=…, model=…, dimension=…이 남습니다. 실제 로그는 끝에 source=…(차원을 정한 근거)가 더 붙습니다.

벡터 저장소(pgvector)

벡터 저장소는 임베딩 벡터와 문서를 저장하고, 비슷한 문서를 유사도로 검색하는 저장소입니다. CONTEXA는 PostgreSQL의 pgvector 확장으로 이를 구현합니다. 벡터는 CONTEXA가 만드는 벡터 저장소 빈(contexaVectorStore)에 저장되며, 이 빈은 CONTEXA 전용 DB(contexaJdbcTemplate)를 사용합니다. 벡터가 저장되는 DB 테이블을 이 문서에서는 벡터 표라고 부릅니다. CONTEXA는 앱의 VectorStore 빈을 쓰지 않고, 앱 DB에는 아무것도 만들지 않습니다. 필요한 의존성은 설치 준비에 있습니다.

설정은 contexa.vectorstore.pgvector.*로 적습니다. CONTEXA 저장소는 이 키만 읽습니다. spring.ai.vectorstore.pgvector.*는 앱 자신의 Spring AI 저장소를 위한 키이므로 CONTEXA 저장소에는 적용되지 않습니다.

설정기본값뜻
contexa.vectorstore.pgvector.dimensions임베딩 모델의 차원벡터 차원(128~3072). 적지 않으면 위 순서로 정해집니다
contexa.vectorstore.pgvector.initialize-schematrue첫 기동 때 CONTEXA 전용 DB에 vector 확장 · 표 · 색인을 만들지. 마이그레이션으로 스키마를 관리하면 false
contexa.vectorstore.pgvector.schema-namepublic벡터 표를 둘 스키마
contexa.vectorstore.pgvector.table-namectxa_vector_store벡터 표 이름. 기동할 때 이미 있는 표의 차원을 이 표에서 읽어 비교합니다
contexa.vectorstore.pgvector.index-typeHNSW색인 종류(HNSW · IVFFLAT). Spring AI 저장소가 표를 만들 때 씁니다
contexa.vectorstore.pgvector.distance-typeCOSINE_DISTANCE거리 계산(COSINE_DISTANCE · EUCLIDEAN_DISTANCE · NEGATIVE_INNER_PRODUCT)

contexa.vectorstore.pgvector.search-timeout-ms15000검색 하나를 기다리는 시간(ms)

첫 기동 때 표 만들기. CONTEXA는 contexa.vectorstore.pgvector.initialize-schema의 기본값을 true로 넣습니다(Spring AI 자체 기본은 false). 그래서 첫 기동 때 CONTEXA 전용 DB에 vector 확장, ctxa_vector_store 표, HNSW 색인, 사용자별 검색용 메타데이터 색인을 만듭니다. 확장을 만들 권한이 없으면 문제 해결의 방법으로 먼저 만듭니다. 스키마를 마이그레이션으로 관리하는 DB에서는 이 설정을 끄고 표와 두 색인을 직접 만듭니다.

# 기존 설정에 더하는 부분
contexa:
  vectorstore:
    pgvector:
      initialize-schema: false

과거 기록 · 문맥 검색(RAG)

RAG(Retrieval-Augmented Generation)는 모델에 질문을 보내기 전에 관련 문서를 검색해 함께 보내는 방식입니다. CONTEXA는 비슷한 과거 판정 기록을 이렇게 검색합니다. contexa.rag.*는 AI 파이프라인과 AI Lab 서비스(행동 분석 · 정책 생성)가 벡터 저장소를 검색할 때의 기본값, 과거 판정 기록을 얼마나 보관할지를 정합니다. 판정 엔진의 1차 · 2차 분석이 과거 기록을 몇 건, 어떤 유사도로 찾는지는 운영 모드와 판정 조정에서 정합니다. 기본값으로 동작하며, 기록 보관 기간(retention-days)이 조직의 보존 정책에 맞는지 확인합니다.
