처음 켜기와 배포(단독 · 분산)

이 페이지는 CONTEXA를 앱에 붙여 기동하고 운영 환경에 배포할 때 정하는 인프라 설정을 설명합니다. 이 페이지에서 반드시 정해야 하는 설정은 CONTEXA 전용 데이터베이스(DB) 하나입니다. 앱을 기동하려면 어노테이션 · 의존성과 AI 모델 연결도 필요하며, 아래 개요의 1~3단계에 정리했습니다. 배포 환경에 따라 정하는 것은 인프라 모드(단독 또는 분산)이며, 인스턴스를 여러 개 운영하거나 재시작 뒤에도 학습 상태를 유지해야 하면 분산 모드(Redis, 선택으로 Kafka)를 씁니다. 캐시, 예약 작업 잠금, 기능 켜고 끄기는 기본값으로 시작할 수 있습니다.

개요

CONTEXA를 켜고 배포하는 순서는 아래와 같습니다. 1~3단계를 마치면 앱이 기동합니다. 4단계부터는 필요할 때 진행합니다.

이 페이지에서 쓰는 용어는 세 가지입니다. 판정(Decision)은 CONTEXA가 사용자의 요청을 분석해 내리는 결론으로, 허용(ALLOW) · 추가 인증(CHALLENGE) · 검토 보류(ESCALATE) · 차단(BLOCK) 중 하나입니다. 행위 기준선은 사용자별 정상 행동 패턴을 쌓은 기록이고, CONTEXA는 이후 판정에서 이 기록을 참고합니다. 인스턴스는 같은 앱을 실행하는 JVM 프로세스 하나입니다.

이 페이지의 설정은 필요한 정도에 따라 네 묶음으로 나뉩니다.

  • 이 페이지에서 반드시 정할 것. CONTEXA 전용 DB의 주소와 계정입니다(전용 DB). 주소가 없으면 기동이 멈춥니다.
  • 배포 환경에 따라 정할 것. 인프라 모드입니다(단독과 분산 고르기). 기본값 standalone은 상태를 JVM 메모리에 두므로 개발과 인스턴스 한 개 운영에 맞습니다. 인스턴스가 둘 이상이면 distributed를 쓰고 Redis(필수)와 Kafka(선택)를 연결합니다.
  • 쓰지 않는 기능만 끌 것. 기능별 설정(기능 켜고 끄기), 관리 화면 웹소켓, 추적(OpenTelemetry)입니다. 쓰는 기능은 끄지 않습니다.
  • 기본값을 유지할 것. DB 연결 풀, 캐시 유지 시간, 예약 작업 잠금입니다. 관측된 문제가 있을 때만 바꿉니다.

켜기

앱이 선언하는 CONTEXA 의존성은 ai.ctxa:spring-boot-starter-contexa 하나입니다. 이 스타터가 함께 가져오는 것과 앱이 직접 넣어야 하는 것은 아래와 같습니다.

구분내용
스타터가 함께 가져옴CONTEXA 모듈 다섯(common · core · identity · iam · autoconfigure), OAuth2 리소스 서버 · 클라이언트 · 인가 서버, Spring AI 1.1.8 BOM
앱이 직접 넣음Spring Security(spring-boot-starter-security), 채팅 모델 스타터(OpenAI · Anthropic · Ollama 가운데 하나 이상), pgvector 벡터 저장소 스타터(spring-ai-starter-vector-store-pgvector). 분산 모드라면 Redis · Redisson · Kafka(분산 모드)
Spring Boot3.x. CONTEXA는 3.5.4로 빌드되고, 4.x에서는 기동 때 거부합니다.

메인 클래스에 @EnableAISecurity를 붙여야 CONTEXA가 켜집니다. 붙이지 않으면 CONTEXA 자동설정(auto-configuration)이 하나도 적용되지 않으므로 앱은 CONTEXA의 영향을 받지 않습니다. 붙인 상태에서 contexa.enabled: false를 적으면 CONTEXA 설정이 하나도 등록되지 않으므로 CONTEXA가 꺼집니다.

@SpringBootApplication
@EnableAISecurity                       // 기본 mode = SecurityMode.SANDBOX
public class MyApplication { }

어노테이션의 mode는 로그인을 누가 맡는지의 기본값을 정합니다. 기본값 SANDBOX는 앱이 로그인을 그대로 맡는 방식(HOST_OWNED)입니다. FULL은 CONTEXA가 로그인을 맡는 방식(CONTEXA_OWNED)입니다. 앱이 spring.datasource.url을 적지 않았다면 FULL은 CONTEXA 전용 DB가 앱의 DB까지 맡는 설정도 함께 켭니다(아래 CONTEXA가 앱의 DB까지 맡기). 두 방식의 차이는 Spring Boot 앱에 붙이기에 있습니다. 로그인한 사용자 객체를 찾는 위치와 이름을 알려 주는 어노테이션 속성(authObjectLocation · authObjectAttribute · authObjectType)은 기존 로그인 연결에 있습니다.

CONTEXA 전용 DB(필수)

CONTEXA는 정책, 판정 기록, 감사 기록, 봉인 증거 같은 자기 데이터를 앱의 DB와 분리한 PostgreSQL에 저장합니다. 봉인 증거는 판정 근거를 증거 묶음으로 봉인해 저장한 감사 증적입니다. contexa.datasource.url이 비어 있으면 기동이 IllegalStateException("contexa.datasource.url must be configured for @EnableAISecurity")으로 멈춥니다.

DB 계정은 PostgreSQL 확장 vector를 만들 수 있어야 합니다. 벡터 표 자동 생성(contexa.vectorstore.pgvector.initialize-schema, 기본 true)을 끄지 않으면 hstore와 uuid-ossp도 필요합니다. 대부분의 서버에서는 DB 관리자만 확장을 만들 수 있으므로, 관리자가 배포 전에 CREATE EXTENSION을 실행해야 합니다.

기동할 때 CONTEXA는 전용 DB에 연결해 이 권한까지 확인합니다. DB가 응답하지 않으면 1초 간격으로 5초 동안 다시 시도합니다. 응답은 하는데 권한이 모자라면 다시 시도하지 않고 바로 실패로 처리합니다. 실패했을 때의 결과는 로그인을 누가 맡는지에 따라 다릅니다.

  • 앱이 로그인을 맡는 기본 방식(HOST_OWNED)에서는 앱이 CONTEXA 없이 기동하고 ERROR 로그(Contexa's database cannot be used)를 남깁니다. 원인을 고친 뒤 앱을 다시 시작해야 CONTEXA가 켜집니다.
  • CONTEXA가 로그인을 맡는 방식(CONTEXA_OWNED)에서는 CONTEXA 없이 로그인할 수 없으므로 기동이 실패합니다.

첫 기동에 CONTEXA는 이 DB에 자기 표와 기본 데이터를 만듭니다(contexa.iam.seed.enabled, 기본 true). 표가 일부만 있는 DB는 기동을 거부합니다. 견본 계정은 설정이 없어도 켜져 있습니다. 사용자 계정이 하나도 없는 DB에서는 견본 계정 다섯 개(공용 비밀번호)가 함께 들어갑니다. 아래 둘 중 하나에 해당하면 들어가지 않습니다. 사용자 계정이 이미 있는 DB에는 contexa.iam.seed.accounts.enabled: true로 명시해도 들어가지 않습니다.

  • 관리자 비밀번호를 contexa.iam.seed.admin.password로 정했습니다.
  • contexa.iam.seed.accounts.enabled: false로 두었습니다.

운영 환경에서는 견본 계정이 공용 비밀번호로 만들어지지 않도록 관리자 비밀번호를 설정하거나 contexa.iam.seed.accounts.enabled: false로 꺼야 합니다. 견본 계정을 만들었다면 기동 로그에 WARN이 남습니다. 자세한 내용은 인가 정책에 있습니다.

앱 DB와 같은 주소를 쓰려면

기본은 앱 DB와 분리한 CONTEXA 전용 DB입니다. contexa.datasource.url이 spring.datasource.url과 문자열로 같으면 아래 두 조건을 모두 채워야 기동합니다. 하나라도 어긋나면 기동이 멈춥니다. 두 주소가 문자열로 다르면 같은 DB를 가리켜도 이 검사는 하지 않습니다.

  • allow-shared-application-datasource와 shared-application-datasource-risk-accepted가 모두 true입니다.
  • 활성 프로필에 prod · production이 없습니다. 운영 프로필에서는 위 두 설정과 관계없이 함께 쓸 수 없습니다.

CONTEXA가 앱의 DB까지 맡기

contexa-owned-application: true(또는 앱에 자기 DB 주소가 없는 @EnableAISecurity(mode = SecurityMode.FULL))는 앱 전체를 CONTEXA가 맡는 경우를 위한 값입니다. 켜면 다음이 바뀝니다.

  • 앱이 DataSource 빈을 따로 만들지 않았으면 CONTEXA DB가 앱의 기본 DataSource가 됩니다. 기본 JdbcTemplate · TransactionTemplate도 CONTEXA DB를 씁니다.
  • 앱 DB와 주소가 같아도 위의 공유 검사를 하지 않습니다.
  • 기능 진단의 기본 동작이 "필수 부품이 없으면 기동을 멈춤"(FAIL_FAST)이 됩니다.
  • 앱이 spring.datasource.url을 따로 적은 채 true를 명시하면 앱의 spring.datasource는 쓰이지 않습니다. 기동 로그에 WARN이 한 줄 남습니다.
자기 DB가 있는 기존 앱에는 켜지 않아야 합니다. 앱이 자기 DB 주소를 적었더라도 true를 명시하면 앱의 spring.datasource.* 대신 CONTEXA DB가 앱의 기본 DB가 됩니다.

벡터 저장소가 쓰는 DB

과거 판정 기록을 담는 벡터 저장소는 항상 CONTEXA 전용 DB에 만들어집니다. CONTEXA는 전용 DB의 연결(contexaDataSource)로 contexaJdbcTemplate을 만들고, 이를 사용해 VectorStore 빈(contexaVectorStore)을 직접 만듭니다. Spring AI의 pgvector 자동설정이 쓰는 앱의 기본 JdbcTemplate은 쓰지 않습니다. 그래서:

  • contexa-owned-application: true여도 false여도 벡터 표는 CONTEXA DB에 생깁니다. 앱의 기본 JdbcTemplate이 CONTEXA DB가 되는 경우에도 같습니다.
  • CONTEXA는 앱 DB에 벡터 표를 만들지 않습니다.
  • 앱이 pgvector 스타터로 자기 VectorStore를 쓰면 그 저장소는 앱의 것입니다. CONTEXA의 판정 기록은 그곳으로 가지 않습니다.

pgvector 표 이름 · 차원 · 표 자동 생성은 AI 모델 연결에 있습니다.

기능 진단

기능 진단(capability)은 기능을 켜는 설정이 아닙니다. 기동이 끝날 때 판정에 필요한 부품(채팅 모델 · 임베딩 모델 · 벡터 저장소 · 학습 · 판정 엔진 · 브리지)이 모두 만들어졌는지 검사합니다. 없는 부품은 [ContexaCapability] …로 시작하는 ERROR 로그로 알리거나 기동을 멈춥니다. 동작은 아래 모드가 정합니다.

contexa.capability.mode하는 일
AUTO(기본)CONTEXA가 앱을 맡은 경우(contexa-owned-application: true, 또는 spring.application.name이 contexa-로 시작)는 FAIL_FAST처럼, 그 밖의 앱은 WARN처럼 동작합니다.
WARN없는 필수 부품을 ERROR 로그로만 알립니다. 기동은 계속됩니다.
FAIL_FAST필수 부품이 없으면 기동을 멈춥니다.
STRICT필수가 아닌 부품의 문제까지 알리고, 필수 부품이 없으면 기동을 멈춥니다.
OFF검사하지 않습니다.
설정기본값뜻언제 바꾸나
contexa.capability.modeAUTO위 표운영 환경에서 없는 부품을 기동 단계에서 막으려면 FAIL_FAST
contexa.capability.required.<기능>없음기능 하나의 필수 여부를 덮어씁니다. 기능 이름은 llm-runtime · embedding-runtime · rag-vector · security-learning · autonomous-decision · bridge입니다. 이 버전에 없는 이름(예: 없어진 pqa-engine)은 아무것도 정하지 않습니다. 기동 때 경고 한 줄을 남기고 그대로 기동합니다쓰지 않는 기능의 경고를 끄거나, 반드시 필요한 기능을 필수로 올릴 때
contexa.capability.expose-diagnostics-endpointtrueActuator가 있으면 진단 결과 엔드포인트(contexacapabilities)를 만듭니다엔드포인트를 두지 않으려면 false

Actuator가 있으면 GET /actuator/contexacapabilities로 같은 결과를 볼 수 있습니다. 웹으로 노출할지는 Spring Boot의 management.endpoints.web.exposure.include가 정합니다.

contexa.security.async.enabledtrue비동기 작업에 요청 당시의 로그인 정보를 넘기는 부품. 단독 모드에서는 메모리에, 분산 모드에서는 Redis에 둡니다
contexa.prompt.governance.enabledtrue프롬프트 버전 화면 · 시험 판정 · 레지스트리 · 출시 관문 · 되돌리기(프롬프트 버전 관리), 프롬프트 품질 화면 · 측정 · 품질 관문(프롬프트 품질 보증)
contexa.enterprise.enabled(기본 false)는 오픈소스판(OSS)에서 켜지 않아야 합니다. 이 값은 엔터프라이즈 모듈이 있을 때를 위한 것입니다. OSS에서 true로 두면 엔터프라이즈 기능이 켜지지 않습니다. 그 결과 OSS의 봉인 증거 부품(봉인, 증거 감사, 재현)도 만들어지지 않고 프롬프트 버전을 측정할 수 없습니다.

  • 메모리에 있던 허용(ALLOW) · 추가 인증(CHALLENGE) · 검토 보류(ESCALATE) 판정이 사라지고, 다음 요청을 다시 분석합니다.
  • 차단(BLOCK)은 CONTEXA DB의 차단 사용자 기록(ctxa_blocked_user)에 유효하게 남아 있는 것만 재시작 때 다시 저장되어 유지됩니다. 기록에 없는 차단은 서버와 함께 사라집니다.

단독 모드 메모리 상한

단독 모드는 판정과 학습 상태를 JVM 힙에 두므로 상한이 있습니다. 상한을 넘으면 오래된 것부터 정리합니다.

설정기본값뜻언제 바꾸나

분산 모드로 옮기기

분산 모드(contexa.infrastructure.mode: distributed)는 판정과 학습 상태를 Redis에 두고, 분석할 사건을 Kafka로 나눠 보냅니다. 전환에 필요한 것은 라이브러리, 연결 설정, 앱 이름입니다. 라이브러리는 CONTEXA 스타터가 가져오지 않으므로 앱이 직접 넣습니다.

필요한 라이브러리와 없을 때의 결과

spring-boot-starter-data-redisRedis 연결과 템플릿. 판정 · 행위 기준선 · 판정 맥락 · 분산 잠금 · 캐시를 Redis에 둡니다기동이 거부됩니다

dependencies {

    implementation 'org.redisson:redisson:3.48.0'                              // Contexa가 빌드에 쓴 판
    implementation 'org.springframework.statemachine:spring-statemachine-data-redis'  // 판은 스타터가 정함
    implementation 'org.springframework.kafka:spring-kafka'
}
contexa:

    mode: distributed
  datasource:
    url: jdbc:postgresql://db.internal:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}

spring:

      host: redis.internal
      port: 6379
  kafka:

Redisson을 넣으면 JCache 제공자가 함께 들어옵니다. 앱의 캐시가 JCache(javax.cache)를 거치면 앱이 기동하지 못할 수 있습니다. 이때는 spring.cache.type=caffeine처럼 앱의 캐시를 직접 지정합니다. 앱이 쓰는 JCache 제공자가 따로 있으면 spring.cache.jcache.provider로 그 제공자를 지정합니다. CONTEXA는 앱의 캐시 설정을 대신 바꾸지 않고, 실패했을 때 원인과 고칠 방법을 기동 로그에 출력합니다.

Redis 연결

  • 앱의 Redis 연결을 그대로 씁니다. spring-boot-starter-data-redis가 spring.data.redis.host · port를 비롯한 spring.data.redis.*로 만드는 연결에 CONTEXA의 Redis 템플릿이 붙습니다. 주소, 사용자 이름, 비밀번호, DB 번호, TLS, Sentinel, 풀, 시간 제한 설정이 모두 그대로 적용됩니다.
  • 요청 처리 중의 접근은 시간을 제한합니다. 앱의 요청이 Redis를 읽을 때(Lettuce를 쓰는 단일 서버 또는 Sentinel)는 같은 연결 설정으로 만든 CONTEXA 전용 클라이언트가 응답을 약 1초만 기다립니다. 앱 자신의 Redis 클라이언트 설정은 바꾸지 않습니다.
  • 앱에 Redis 연결이 없을 때만 CONTEXA가 직접 만듭니다. 앱에 RedisConnectionFactory 빈이 없으면 CONTEXA가 spring.data.redis.host · port · username · password · database로 단일 서버 연결을 만듭니다. 앱이 연결 설정을 만들었다면 이 연결은 만들어지지 않습니다. 이때만 contexa.security.zerotrust.redis.timeout(기본 5000)을 밀리초로 연결 · 명령 · 풀 대기 시간 제한에 씁니다.
  • Redisson은 CONTEXA 전용 클라이언트를 따로 만듭니다. 앱이 RedissonClient 빈을 선언했는지와 관계없이 CONTEXA는 자기 클라이언트(contexaRedissonClient)를 만들어 씁니다. 앱이 RedissonClient를 직접 선언해도 CONTEXA는 그것을 쓰지 않으므로 비밀번호가 있는 Redis를 위해 따로 선언할 필요가 없습니다. 이 클라이언트는 spring.data.redis.*의 사용자 이름 · 비밀번호 · DB 번호 · TLS · 단일 서버 · Sentinel 설정을 읽습니다. 이 클라이언트는 처음 쓸 때 연결하므로, 클라이언트를 만드는 일 자체는 기동할 때 Redis가 내려가 있어도 기동을 막지 않습니다. 기동할 때 Redis 응답을 확인하는 별도의 점검은 다음 항목에 있습니다. 대기 시간은 spring.data.redis.timeout과 1초 가운데 짧은 쪽이고 다시 시도하지 않습니다.
  • 단일 서버와 Sentinel만 지원합니다. Redis Cluster는 이 릴리스에서 지원하지 않습니다. Cluster를 쓰면 기동 로그에 ERROR가 한 줄 남고(Redis Cluster is not supported in this release) 기동은 계속됩니다. 판정은 여러 키에 걸친 스크립트로 저장하므로 Cluster가 일부 판정의 저장을 거부할 수 있고, 저장되지 않은 판정은 적용되지 않습니다.
  • 기동할 때 Redis가 응답하는지 확인합니다. 단일 서버 Redis에 5초 동안 1초 간격으로 접속을 시도합니다. 그래도 응답이 없으면 앱이 로그인을 맡는 기본 방식(HOST_OWNED)에서는 앱이 CONTEXA 없이 기동하고 ERROR 로그(Contexa's Redis cannot be reached)를 남깁니다. Redis를 복구한 뒤 앱을 다시 시작해야 CONTEXA가 켜집니다. Sentinel을 쓰면 이 확인을 하지 않습니다.

Kafka 연결과 토픽

  • 연결 설정은 Spring의 spring.kafka.*를 씁니다. CONTEXA는 이 설정으로 자기 전용 생산자와 소비자, 템플릿(contexaKafkaTemplate)을 따로 만들며 앱의 Kafka 빈은 바꾸지 않습니다. 그래서 앱이 KafkaTemplate 빈을 선언할 필요는 없습니다. 사건을 보내는 생산자는 모든 복제본의 확인을 받고(acks=all) 전송을 최대 몇 초만 기다립니다.
  • 토픽 이름. 분석할 사건은 토픽 ctxa.<앱 이름>.security.events.<범주>.<유형>(예: ctxa.order-service.security.events.authorization.method)으로 보내고, 처리하지 못한 사건은 DLQ 토픽으로 보냅니다. 앱 이름은 spring.application.name을 소문자로 바꾼 것이고 a-z · 0-9 · - 이외의 문자는 _와 바이트의 16진수로 적습니다. 이름이 없으면 접두사는 ctxa.뿐입니다(ctxa.security.events.authorization.method).
  • 토픽 생성. 시작할 때 CONTEXA는 쓰는 토픽만 만듭니다. 사건 토픽 3개(authentication.mfa · authentication.success · authorization.method)와 DLQ 토픽입니다. 사건 토픽은 파티션 3개에 보존 기간 7일이고 복제본 수는 브로커 기본값을 따릅니다. DLQ 토픽은 파티션 1개, 복제본 1개, 보존 기간 30일입니다. 이전 버전이 만든 토픽은 지우지 않습니다.
  • 토픽을 만들지 못할 때. spring.kafka.admin.auto-create: false이거나 브로커가 응답하지 않아 토픽을 만들거나 확인하지 못하면, 기동 로그에 ERROR가 한 줄 남고([ContexaKafkaTopics] Kafka topics Contexa needs are missing) 기동은 계속됩니다. 토픽이 생길 때까지 그 사건은 발행되지 않아 분석에 닿지 않습니다. 이 경우 토픽을 미리 만들어야 합니다.
  • 처리 실패. 사건 처리에 실패하면 1초 간격으로 3번 다시 시도하고, 그 사건은 DLQ 토픽으로도 보냅니다. 사건에는 보낸 앱의 이름이 실려 있으므로 CONTEXA는 다른 앱의 사건을 분석하지 않고 건너뜁니다.

Redis와 Kafka를 다른 앱과 나눠 쓸 때

CONTEXA는 spring.application.name으로 자기 데이터를 구분합니다. 이름이 있으면 Redis 키는 ctxa:<이름>:으로 시작하고, Kafka 토픽은 위의 ctxa.<앱 이름>. 규칙을 따르며, Kafka 리스너 그룹에는 이름이 붙습니다. 같은 앱의 인스턴스는 같은 이름을 쓰므로 상태를 함께 봅니다.

이름이 없으면 접두사 없는 키와 공용 리스너 그룹을 씁니다. 같은 Redis와 Kafka를 쓰는 다른 애플리케이션과 차단 정보와 사건을 서로 보게 됩니다. 기동 로그에 이 사실을 알리는 INFO가 한 줄 남습니다. Redis나 Kafka를 다른 애플리케이션과 나눠 쓴다면 spring.application.name을 반드시 정해야 합니다. 전용 Redis와 Kafka를 쓴다면 바꿀 것이 없습니다.

security.plane.kafka.group-idsecurity-plane-consumer사건을 받는 Kafka 리스너 그룹의 바탕 이름. 이름이 있는 앱은 security-plane-consumer.<식별자> 그룹에 들어갑니다. 식별자는 spring.application.name을 소문자로 바꾸고 a-z · 0-9 · . · _ · - 이외의 문자는 ~와 바이트의 16진수로 적은 것입니다. 48자를 넘으면 잘라 끝에 다이제스트를 붙입니다. 이름이 없으면 이 값 그대로입니다. 이 키는 contexa로 시작하지 않습니다같은 Kafka를 다른 CONTEXA 묶음과 나눠 쓸 때
Kafka 리스너 그룹은 security.plane.kafka.group-id를 읽습니다. 이 키는 옛 이름 그대로 읽히는 예외입니다. 별칭이 아니라 리스너가 그 이름을 직접 읽으므로 기동 로그에 알림은 없습니다. 값은 리스너 그룹의 바탕 이름으로 쓰이고, 앱 이름이 있으면 뒤에 .과 그 식별자(위 표 참고)가 붙습니다. contexa.security.plane.kafka.group-id는 읽는 곳이 없어 효과가 없습니다.

분석 대기열 · 스레드 수 · 시간 제한 같은 판정 엔진 처리량은 운영 모드와 판정 조정에 있습니다.

Redis나 DB가 응답하지 않을 때

CONTEXA는 저장소 장애 때문에 앱을 멈추지 않습니다. 운영 중 Redis나 CONTEXA DB가 응답하지 않으면 다음과 같이 동작합니다.

  1. 처음 장애를 만난 요청 하나가 약 1초를 기다립니다. 그 뒤에는 요청이 저장소를 기다리지 않고 진행합니다.
  2. CONTEXA가 ERROR 로그를 한 줄 남기고([Contexa] Redis does not answer 또는 [Contexa] Contexa's database does not answer), 장애가 이어지는 동안 응답이 없던 시간을 1분마다 ERROR로 다시 남깁니다.
  3. 보호 메서드(@Protectable) 호출은 판정 없이 진행될 수 있습니다. 판정 없이 진행된 호출 수를 1분마다 ERROR 로그로 알리고, DB가 돌아오면 감사 기록에 남깁니다. 다만 정책을 읽지 못한 민감한 자원의 호출은 추가 인증이 필요한 거부로 처리합니다.
  4. 저장소가 다시 응답하면 CONTEXA가 1초 간격으로 확인해 자동으로 복귀합니다. 앱을 다시 시작할 필요가 없습니다.

저장소 장애 동안은 판정 통제가 약해지므로, 위 ERROR 로그를 알림 대상에 넣어야 합니다. 분산 모드에서는 Redis를 Sentinel로 구성해 가용성을 확보하는 편이 안전합니다.

캐시

CONTEXA 캐시는 정책 판정이 사용자 정보(users 도메인)와 정책(policies 도메인)을 조회할 때 씁니다. 단독 모드는 늘 이 JVM 안의 로컬 캐시입니다. 아래 Redis · 무효화 설정은 분산 모드에서만 뜻이 있습니다.

설정기본값뜻언제 바꾸나
contexa.cache.typeREDISLOCAL · REDIS · HYBRID. 단독 모드에서는 무엇을 적어도 LOCAL입니다. 분산 모드에서 HYBRID이면 항목을 지울 때 다른 인스턴스에 알립니다분산 모드에서 인스턴스마다 바뀐 정책을 바로 보게 하려면 HYBRID
contexa.cache.local.max-size1000로컬 캐시 최대 항목 수사용자 · 정책이 많을 때
contexa.cache.local.default-ttl-seconds60도메인이 없는 항목의 로컬 유지 시간(초)드물게
contexa.cache.redis.default-ttl-seconds60도메인이 없는 항목의 Redis 유지 시간(초)드물게
contexa.cache.redis.key-prefixcontexa:cache:Redis 키의 앞부분. 앱 이름이 있으면 그 앞에 ctxa:<앱 이름>:이 붙습니다같은 Redis를 다른 앱과 나눠 쓸 때
contexa.cache.pubsub.enabledtrueHYBRID일 때 무효화 알림을 보냅니다알림을 끄려면
contexa.cache.pubsub.channelcontexa:cache:invalidation무효화 알림 채널(앱 이름이 있으면 앞에 ctxa:<앱 이름>:이 붙습니다)채널 이름 규칙이 있을 때
contexa.cache.domains.users.local-ttl-seconds3600사용자 정보의 로컬 유지 시간(초). Redis 쪽은 redis-ttl-seconds(기본값 같음)사용자 권한 변경을 더 빨리 반영하려면 줄입니다
contexa.cache.domains.policies.local-ttl-seconds30정책의 로컬 유지 시간(초). Redis 쪽 redis-ttl-seconds도 30이라 두 모드에서 같은 시간 뒤에 바뀐 정책이 보입니다정책을 자주 바꾸지 않으면 늘려도 됩니다

contexa.cache.domains.roles · permissions · groups · soar의 값도 있지만, 지금 OSS에서 그 도메인으로 CONTEXA 캐시를 부르는 코드는 없습니다(@Cacheable("roles") 같은 Spring 캐시는 별개입니다).

여러 인스턴스의 예약 작업

보관 기간이 지난 기록 삭제 같은 예약 작업은 인스턴스가 여러 개여도 한 번만 실행되어야 합니다. 이를 위해 CONTEXA는 CONTEXA DB의 ctxa_shedlock 표로 잠금을 겁니다(ShedLock). 인스턴스 한 개만 운영해도 해가 없습니다. ShedLock은 CONTEXA가 함께 가져오고, CONTEXA DB가 있으면 켜집니다.

설정기본값뜻언제 바꾸나
contexa.scheduler.lock.enabledtrue예약 작업 잠금을 켭니다. 잠금의 최대 유지 시간은 5분으로 고정입니다DB 이전 작업 중 잠시 끌 때
contexa.scheduler.lock.use-database-timetrue잠금 시각에 DB 시계를 씁니다(false이면 JVM 시계)DB와 JVM 시간대가 다른 시험 환경

추적(OpenTelemetry)

CONTEXA는 추적(span)을 OTLP gRPC로 내보내는 OpenTelemetry SDK를 만들어 JVM 전역으로 등록할 수 있습니다. 지표(metrics) 내보내기는 없습니다. 기본은 꺼져 있습니다. 앱에 이미 OpenTelemetry 에이전트나 SDK가 있으면 CONTEXA가 그것과 겹치지 않도록 기본을 끈 것입니다. 켜려면 두 가지가 필요합니다.

  1. 앱이 io.opentelemetry:opentelemetry-sdk와 io.opentelemetry:opentelemetry-exporter-otlp를 의존성에 추가합니다. 스타터는 이 둘을 가져오지 않으며, 클래스가 없으면 이 설정은 적용되지 않습니다.
  2. contexa.opentelemetry.enabled: true로 켜고 수집기 주소를 적습니다. 주소를 적지 않으면 localhost:4317로 보내려 하므로 그 주소에 수집기가 있어야 합니다.

전역 OpenTelemetry는 JVM당 한 번만 등록할 수 있습니다. 이미 등록되어 있으면 CONTEXA는 ERROR 로그를 한 줄 남기고 전역 인스턴스를 바꾸지 않은 채 자기 빈만 씁니다.

설정기본값뜻언제 바꾸나
contexa.opentelemetry.enabledfalsetrue이면 추적을 OTLP gRPC 수집기로 내보냅니다. false이면 아무것도 내보내지 않는 빈 SDK입니다수집기를 운영하고 CONTEXA 추적이 필요할 때 true
contexa.opentelemetry.service-namecontexa-core추적에 붙는 서비스 이름앱 이름으로 구분할 때
contexa.opentelemetry.exporter-endpointhttp://localhost:4317OTLP gRPC 수집기 주소(HTTP 4318은 맞지 않습니다)수집기 주소
contexa.opentelemetry.sampling-probability1.0추적을 남길 비율(0~1)요청이 많아 줄일 때
