처음 켜기와 배포(단독 · 분산)

앱에 Contexa를 붙여 기동시키는 데 필요한 설정(전용 DB · 기능 진단 · 기능 켜고 끄기)과, 한 대짜리 단독 모드에서 여러 대가 상태를 나누는 분산 모드(Redis · Kafka)로 옮기는 설정을 다룹니다. 캐시 · 예약 작업 잠금 · 추적도 여기에 있습니다.

한눈에 보기

Contexa를 켜는 일은 아래 순서입니다. 1~3단계가 끝나면 기동하고, 4단계부터는 필요할 때 합니다.

켜기

의존성은 ai.ctxa:spring-boot-starter-contexa 하나입니다. 이 스타터가 무엇을 가져오고 무엇을 앱에 맡기는지는 아래와 같습니다.

구분내용
스타터가 함께 가져옴Contexa 모듈 다섯(common · core · identity · iam · autoconfigure), Spring Security, OAuth2 리소스 서버 · 클라이언트 · 인가 서버, Spring AI 1.1.8 BOM
앱이 직접 넣음채팅 모델 스타터(OpenAI · Anthropic · Ollama 가운데 하나 이상), pgvector 벡터 저장소 스타터(spring-ai-starter-vector-store-pgvector). 분산 모드라면 Redis · Redisson · Kafka(분산 모드)
Spring Boot3.x. Contexa는 3.5.4로 빌드되고, 4.x에서는 기동 때 거부합니다.

메인 클래스에 @EnableAISecurity를 붙여야 Contexa가 켜집니다. 붙이지 않으면 Contexa 자동설정이 모두 빠져 앱에 관여하지 않습니다. 붙인 상태에서 contexa.enabled: false로 두면 어노테이션도 아무것도 가져오지 않아 다시 모두 꺼집니다.

@SpringBootApplication
@EnableAISecurity                       // 기본 mode = SecurityMode.SANDBOX
public class MyApplication { }

어노테이션의 mode는 로그인을 누가 맡는지의 기본값을 정합니다. 기본 SANDBOX는 앱이 로그인을 맡고(HOST_OWNED), FULL은 Contexa가 맡습니다(CONTEXA_OWNED). FULL은 아래 Contexa가 앱의 DB까지 맡기도 함께 켭니다. 두 방식의 차이는 Spring Boot 앱에 붙이기, 로그인 객체를 찾는 힌트 속성은 기존 로그인 연결에 있습니다.

Contexa 전용 DB(필수)

Contexa는 정책 · 판정 기록 · 증거 같은 자기 데이터를 앱의 DB와 나눈 PostgreSQL에 둡니다. contexa.datasource.url이 비어 있으면 기동이 IllegalStateException("contexa.datasource.url must be configured for @EnableAISecurity")으로 멈춥니다.

첫 기동에 Contexa는 이 DB에 자기 표와 기본 데이터를 만듭니다(contexa.iam.seed.enabled, 기본 true). 표가 일부만 있으면 기동이 멈춥니다. 견본 계정은 contexa.iam.seed.accounts.enabled: true일 때만 넣습니다(인가 정책).

앱 DB와 같은 주소를 쓰려면

기본은 따로 둔 DB입니다. contexa.datasource.url이 spring.datasource.url과 같으면 아래 두 조건을 모두 채워야 기동합니다. 하나라도 빠지면 기동이 멈춥니다.

  • allow-shared-application-datasource와 shared-application-datasource-risk-accepted가 모두 true
  • 활성 프로필에 prod · production이 없음(운영 프로필에서는 함께 쓸 수 없음)

Contexa가 앱의 DB까지 맡기

contexa-owned-application: true(또는 @EnableAISecurity(mode = SecurityMode.FULL))는 앱 전체를 Contexa가 맡는 경우를 위한 값입니다. 켜면 다음이 바뀝니다.

  • 앱이 DataSource 빈을 따로 만들지 않았으면 앱의 기본 DataSource가 Contexa DB가 됩니다. 기본 JdbcTemplate · TransactionTemplate도 Contexa DB를 씁니다.
  • 앱 DB와 주소가 같아도 위의 공유 검사를 하지 않습니다.
  • 기능 진단의 기본 동작이 "빠진 필수 부품이 있으면 기동을 멈춤"(FAIL_FAST)이 됩니다.
자기 DB가 있는 기존 앱에는 켜지 마세요. 앱의 spring.datasource.* 대신 Contexa DB가 앱의 기본 DB가 될 수 있습니다.

벡터 저장소가 쓰는 DB

과거 판정 기록을 담는 벡터 저장소는 Spring AI의 pgvector 자동설정이 만듭니다. 이 자동설정은 앱의 기본 JdbcTemplate을 씁니다. Contexa 전용 DB의 contexaJdbcTemplate은 기본 후보가 아니어서 여기에 쓰이지 않습니다. 그래서:

  • contexa-owned-application: true이면 기본 JdbcTemplate이 Contexa DB라 벡터 표도 Contexa DB에 생깁니다.
  • 그렇지 않으면 벡터 표는 앱의 기본 DB에 생깁니다. 그 DB가 pgvector를 쓸 수 있어야 합니다.
  • 앱 DB는 그대로 두고 벡터 표만 Contexa DB에 두려면, contexaDataSource로 만든 VectorStore 빈을 직접 선언하세요. 같은 종류의 빈이 있으면 Spring AI 자동설정이 물러납니다.

pgvector 표 이름 · 차원 · 표 자동 생성은 AI 모델 연결에 있습니다.

기능 진단

기능 진단(capability)은 기능을 켜는 스위치가 아닙니다. 기동이 끝날 때 판정에 필요한 부품(채팅 모델 · 임베딩 모델 · 벡터 저장소 · 학습 · 판정 엔진 · 브리지)이 모두 만들어졌는지 검사하고, 빠진 것을 [ContexaCapability] …로 시작하는 ERROR 로그로 알리거나 기동을 멈춥니다.

contexa.capability.mode하는 일
AUTO(기본)Contexa가 앱을 맡은 경우(contexa-owned-application: true, 또는 spring.application.name이 contexa-로 시작)는 FAIL_FAST, 그 밖의 앱은 WARN처럼 동작합니다.
WARN빠진 필수 부품을 ERROR 로그로만 알립니다. 기동은 계속됩니다.
FAIL_FAST필수 부품이 빠지면 기동을 멈춥니다.
STRICT필수가 아닌 부품의 문제까지 알리고, 필수 부품이 빠지면 기동을 멈춥니다.
OFF검사하지 않습니다.
설정기본값뜻언제 바꾸나
contexa.capability.modeAUTO위 표운영에서 빠진 부품을 기동 단계에서 막으려면 FAIL_FAST
contexa.capability.required.<기능>없음기능 하나의 필수 여부를 덮어씀. 기능 이름: llm-runtime · embedding-runtime · rag-vector · security-learning · autonomous-decision · bridge쓰지 않는 기능의 경고를 끄거나, 꼭 필요한 기능을 필수로 올릴 때
contexa.capability.expose-diagnostics-endpointtrueActuator가 있으면 진단 결과 엔드포인트(contexacapabilities)를 만듦엔드포인트를 두지 않으려면 false

Actuator가 있으면 GET /actuator/contexacapabilities로 같은 결과를 봅니다. 웹으로 노출할지는 Spring Boot의 management.endpoints.web.exposure.include가 정합니다.

인프라 모드(contexa.infrastructure.mode)는 판정 · 학습 상태를 어디에 둘지 정합니다. 어느 모드든 전용 DB는 필요합니다.

판정 · 기준선 등 저장소 빈(ZeroTrustActionRepository, BaselineDataStore, SecurityContextDataStore 등)을 앱이 직접 선언하면 단독 모드에서도 메모리 대신 그 구현이 쓰입니다. 기준선 저장소와 맥락 저장소(SecurityContextDataStore)를 모두 앱이 주면 단독 모드 WARN도 나오지 않습니다.

분산 모드로 옮기기

Redis · Redisson · Kafka는 Contexa 스타터가 가져오지 않으므로 앱이 넣습니다.

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-redis'   // Lettuce
    implementation 'org.redisson:redisson:3.48.0'                              // Contexa가 빌드에 쓴 판
    implementation 'org.springframework.kafka:spring-kafka'
}
contexa:
  infrastructure:
    mode: distributed
  datasource:
    url: jdbc:postgresql://db.internal:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
  security:
    zerotrust:
      redis:
        timeout: 5000          # 밀리초

spring:
  data:
    redis:
      host: redis.internal
      port: 6379
  kafka:
    bootstrap-servers: kafka.internal:9092
  • Redis 연결은 Contexa가 만듭니다. 분산 모드에서는 Contexa가 spring.data.redis.host · port · password로 단일 서버 Redis 연결을 직접 만들고, 이 연결이 앱 전체의 기본 Redis 연결이 됩니다. 연결 · 명령 · 풀 대기 시간 제한에는 contexa.security.zerotrust.redis.timeout을 밀리초로 씁니다.
  • Redisson. 앱이 RedissonClient 빈을 두지 않으면 Contexa가 spring.data.redis.host · port로 단일 서버 클라이언트를 만듭니다. 이 클라이언트는 비밀번호와 DB 번호를 쓰지 않습니다(DB 0). 비밀번호가 있는 Redis라면 RedissonClient 빈을 직접 선언하세요.
  • Kafka 연결은 Spring의 spring.kafka.*를 씁니다. 분석할 사건은 토픽 security.events.<범주>.<유형>(예: security.events.authorization.method)으로 보내고, 처리하지 못한 사건은 DLQ 토픽으로 보냅니다. 처리 실패는 1초 간격으로 3번 다시 시도합니다.

security.plane.kafka.group-idsecurity-plane-consumer사건을 받는 Kafka 리스너의 그룹. 이름이 contexa로 시작하지 않습니다같은 Kafka를 다른 Contexa 묶음과 나눠 쓸 때
security.plane.kafka.group-id를 적으면 기동 로그에 ERROR가 한 번 남습니다. Contexa가 security.plane.을 옛 접두사로 보고 별칭을 만들 때 남기는 로그입니다. 값은 리스너 그룹에 그대로 쓰입니다. contexa.security.plane.kafka.group-id는 읽는 곳이 없어 효과가 없습니다.

분석 대기열 · 스레드 수 · 시간 제한 같은 판정 엔진 처리량은 집행 모드와 판정 조정에 있습니다.

캐시

Contexa 캐시는 정책 판정이 사용자 정보(users 도메인)와 정책(policies 도메인)을 조회할 때 씁니다. 단독 모드는 늘 이 JVM 안의 로컬 캐시이고, 아래 Redis · 무효화 설정은 분산 모드에서만 뜻이 있습니다.

설정기본값뜻언제 바꾸나
contexa.cache.typeREDISLOCAL · REDIS · HYBRID. 단독 모드에서는 무엇을 적어도 LOCAL. 분산 모드에서 HYBRID면 지울 때 다른 노드에 알림분산 모드에서 노드마다 바뀐 정책을 바로 보게 하려면 HYBRID
contexa.cache.local.max-size1000로컬 캐시 최대 항목 수사용자 · 정책이 많을 때
contexa.cache.local.default-ttl-seconds60도메인이 없는 항목의 로컬 유지 시간(초)드물게
contexa.cache.redis.default-ttl-seconds60도메인이 없는 항목의 Redis 유지 시간(초)드물게
contexa.cache.redis.key-prefixcontexa:cache:Redis 키 앞부분같은 Redis를 다른 앱과 나눠 쓸 때
contexa.cache.pubsub.enabledtrueHYBRID일 때 무효화 알림을 보냄알림을 끄려면
contexa.cache.pubsub.channelcontexa:cache:invalidation무효화 알림 채널채널 이름 규칙이 있을 때
contexa.cache.domains.users.local-ttl-seconds3600사용자 정보의 로컬 유지 시간(초). Redis 쪽은 redis-ttl-seconds(기본 같음)사용자 권한 변경을 더 빨리 보려면 줄임
contexa.cache.domains.policies.local-ttl-seconds30정책의 로컬 유지 시간(초). Redis 쪽 redis-ttl-seconds도 30이라 두 모드에서 같은 시간에 바뀐 정책이 보임정책을 자주 바꾸지 않으면 늘려도 됨

contexa.cache.domains.roles · permissions · groups · soar의 값도 있지만, 지금 OSS에서 그 도메인으로 Contexa 캐시를 부르는 코드는 없습니다(@Cacheable("roles") 같은 Spring 캐시는 별개입니다).

여러 인스턴스의 예약 작업

보관 기간이 지난 기록 삭제 같은 예약 작업이 여러 인스턴스에서 한 번만 돌도록, Contexa는 Contexa DB의 shedlock 표로 잠금을 겁니다(ShedLock). 한 대만 돌려도 해가 없습니다. ShedLock은 Contexa가 함께 가져오고, Contexa DB가 있으면 켜집니다.

설정기본값뜻언제 바꾸나
contexa.scheduler.lock.enabledtrue예약 작업 잠금 켜기. 잠금의 최대 유지 시간은 5분으로 고정DB 이전 작업 중 잠시 끌 때
contexa.scheduler.lock.use-database-timetrue잠금 시각에 DB 시계를 씀(false면 JVM 시계)DB와 JVM 시간대가 다른 시험 환경

추적(OpenTelemetry)

Contexa는 추적(span)을 OTLP gRPC로 내보내는 OpenTelemetry SDK를 만들어 전역으로 등록합니다. 지표(metrics) 내보내기는 없습니다. 기본으로 켜져 있어 수집기가 없어도 localhost:4317로 보내려 합니다. 수집기를 두지 않는다면 끄세요.

설정기본값뜻언제 바꾸나
contexa.opentelemetry.enabledtruefalse면 아무것도 내보내지 않는 빈 SDK수집기가 없을 때
contexa.opentelemetry.service-namecontexa-core추적에 붙는 서비스 이름앱 이름으로 구분할 때
contexa.opentelemetry.exporter-endpointhttp://localhost:4317OTLP gRPC 수집기 주소(HTTP 4318은 맞지 않음)수집기 주소
contexa.opentelemetry.sampling-probability1.0추적을 남길 비율(0~1)요청이 많아 줄일 때
