인가 정책

인가는 로그인한 사용자가 어떤 URL과 메서드를 쓸 수 있는지 정책으로 정하는 일입니다. 이 페이지의 설정은 관리 콘솔에 들어갈 계정, 첫 기동 때 DB에 넣는 데이터, 정책이 여럿 맞거나 하나도 맞지 않을 때의 결정, 관리 콘솔의 자원 스캔을 정합니다. 정책 자체는 관리 콘솔에서 만듭니다. 기본값이 개발과 시험에 맞춰져 있어 배포 환경에서 바꿔야 하는 설정은 첫 절에 모았습니다.

배포 환경에서 확인할 설정

이 페이지의 설정은 대부분 기본값으로 동작합니다. 아래 네 설정은 기본값이 개발과 시험을 기준으로 정해져 있습니다. 배포 환경(운영 환경)에 올리기 전에 값을 확인합니다. 첫 번째 설정은 반드시 꺼야 합니다.

예시 계정은 배포 환경에서 반드시 꺼야 합니다. 예시 계정은 다섯 개이고 비밀번호가 하나로 같습니다. 이 비밀번호는 코드와 함께 공개되어 있습니다. 그중 admin은 관리자 역할(ROLE_ADMIN)을 가지므로, 비밀번호를 아는 사람은 관리 콘솔에서 정책 · 계정 · 시스템 설정을 바꿀 수 있습니다. contexa.iam.seed.accounts.enabled를 설정하지 않으면 CONTEXA는 사용자 계정이 하나도 없는 DB로 처음 기동할 때 이 계정을 만듭니다. 비어 있는 배포용 DB도 여기에 해당합니다. 배포 환경 설정에 contexa.iam.seed.accounts.enabled: false를 명시합니다.
설정배포 환경에서의 값기본 동작그대로 두면
contexa.iam.seed.accounts.enabledfalse(필수)설정하지 않으면 예시 계정을 만듭니다. 첫 관리자 비밀번호(contexa.iam.seed.admin.password)가 설정되어 있거나 사용자 계정이 이미 있는 DB에서는 만들지 않습니다.공개된 비밀번호로 관리 콘솔에 로그인할 수 있는 관리자 계정이 생깁니다(첫 기동).
contexa.policy.no-matching-url-policy-decision과 시스템 설정 화면의 "적용되는 URL 정책이 없을 때의 결정"AUTHENTICATED(기본) 또는 DENY. PERMIT은 쓰지 않습니다.AUTHENTICATED: 로그인한 사용자만 통과합니다.PERMIT이면 정책이 없는 URL을 로그인하지 않은 사용자도 쓸 수 있습니다. 이전 버전에서 만든 설치는 시스템 설정에 PERMIT이 저장되어 있을 수 있으므로 화면에서 확인합니다(정책 결정).
contexa.policy.missing-method-policy-decision정책이 없는 메서드를 막으려면 DENYPERMIT@Protectable 메서드에 정책이 하나도 없으면 모든 호출이 허용됩니다.
contexa.iam.websocket.enabled쓰지 않으면 falsetrue모든 출처의 연결을 받는 STOMP 끝점 /ws-soar가 열립니다(실시간 끝점).

시스템 설정 화면에 저장된 값은 설정 파일보다 우선합니다. 두 번째와 세 번째 설정은 설정 파일뿐 아니라 화면에 저장된 값도 확인합니다.

이 페이지로 정하는 것

정책은 URL이나 메서드를 허용(ALLOW)하거나 거부(DENY)하는 규칙입니다. 정책 본문은 application.yml이 아니라 CONTEXA 전용 DB에 저장되고, 관리 콘솔에서 만들고 고칩니다(정책). 이 페이지의 설정은 정책 본문이 아니라 정책을 둘러싼 동작을 정합니다.

설정은 두 곳에서 정합니다. 하나는 설정 파일(YAML)이고, 다른 하나는 관리 콘솔의 시스템 설정 화면입니다. 정책 결정 세 가지는 양쪽에 있고, 저장된 시스템 설정이 설정 파일보다 우선합니다.

관리 콘솔 접근

관리 콘솔(/contexa/admin/**)은 정책 · 계정 · 시스템 설정을 관리하는 화면입니다. CONTEXA가 이 주소를 직접 보호하므로 앱이 막을 필요가 없습니다. 콘솔에 들어가려면 앱 사용자 계정이 아니라 CONTEXA 관리자 계정이 있어야 합니다.

  • 켜고 끄기: 관리 콘솔을 켜고 끄는 전용 설정은 이 페이지에 없습니다. 콘솔은 CONTEXA와 함께 동작하고, 들어갈 수 있는 사람은 관리자 역할(ROLE_ADMIN)을 가진 계정으로 제한합니다. CONTEXA 전체를 끄는 방법은 관찰 모드로 안전하게 시작하기의 되돌리기에 있습니다.
  • 누가 지키나: 네 조합 모두 CONTEXA가 지킵니다. FULL + CONTEXA_OWNED가 아닌 세 조합에서는 콘솔 전용 보안 체인이 /contexa/admin/login에서 CONTEXA 관리자를 로그인시킵니다(비밀번호 다음에 패스키 또는 메일 코드, 2단계 필수). FULL + CONTEXA_OWNED에서는 CONTEXA 주 보안 체인이 관리자와 앱 사용자를 함께 로그인시키고, /contexa/admin/login은 주 흐름의 MFA 로그인 화면(기본 /mfa/login)으로 이동합니다. 콘솔 컨트롤러의 메서드 보안(@PreAuthorize)은 네 조합 모두 적용됩니다. 보안 모드와 인증 소유권의 설명은 기존 Spring Security 앱에 붙이기에 있습니다.
  • 첫 관리자: contexa.iam.seed.admin.*로 만듭니다(아래, 예시는 관리 콘솔). 이후 관리자는 관리 콘솔에서 만들고 관리자 역할을 배정합니다.
  • 기본 보호 정책: 첫 기동 때 정책 두 개가 들어갑니다. ALLOW_CONTEXA_ADMIN_LOGIN은 로그인 화면 /contexa/admin/login을 누구에게나 열고, ALLOW_CONTEXA_ADMIN_ADMINISTRATORS는 나머지 /contexa/admin/**를 관리자 역할로 제한합니다. 두 정책은 삭제하거나 비활성화할 수 없습니다. 허용 범위를 넓히는 수정도 거부됩니다.
  • 마지막 관리자 보호: 활성 관리자가 한 명 남으면 그 계정을 삭제하거나 비활성화하거나 관리자 역할을 뺄 수 없습니다. 관리자가 모두 잠긴 경우에는 DB에 없는 사용자 이름과 메일로 contexa.iam.seed.admin.*를 설정하고 재시작합니다. 시작할 때 새 관리자가 만들어집니다.
  • 변경 기록: 시스템 설정 화면에서 정책 결정이나 스캐너 패키지 같은 항목을 바꾸면 이전 값과 새 값이 감사 기록에 남습니다. 운영 모드를 바꾸면 입력한 사유와 함께 별도 기록이 남습니다.

첫 기동: 스키마와 기본 데이터

CONTEXA는 앱을 처음 기동할 때 전용 DB에 스키마와 기본 데이터를 넣습니다. 이 작업을 시드(seed)라고 부릅니다. 시드는 @EnableAISecurity로 CONTEXA가 켜져 있고 CONTEXA 전용 DB(contexa.datasource.url)가 있을 때 실행됩니다.

  1. CONTEXA가 전용 DB의 스키마 상태를 검사합니다.
  2. 스키마가 없으면 설치합니다(db/schema.sql). 이미 모두 있으면 빠진 표 · 인덱스 · 열을 채우는 정비만 합니다. 일부만 있으면 아무것도 바꾸지 않고 기동을 멈춥니다. 이때는 검증된 백업을 복원하거나 새 DB를 씁니다.
  3. 기본 데이터를 넣습니다. 역할 · 그룹 · 정책 · 조건 템플릿 · 관리 메뉴 · 시스템 설정입니다.
  4. 조건을 충족하면 예시 계정을 넣습니다(아래 표).
  5. 모든 빈을 만든 뒤, contexa.iam.seed.admin.password가 있으면 첫 관리자를 만듭니다.

기본 데이터 대부분은 이미 있는 행을 건너뛰므로 재시작해도 안전합니다. 예외는 관리 콘솔을 지키는 기본 정책입니다. 이 정책들의 이름 · 효과 · 우선순위 · 활성 여부는 시작할 때마다 기본값으로 다시 맞춥니다.

설정기본값뜻언제 바꾸나
contexa.iam.seed.enabledtrue기동 때 스키마, 기본 데이터, 첫 관리자 만들기를 실행합니다. 끄면 세 가지 모두 실행되지 않습니다.스키마를 직접 관리하는 DB에서만 끕니다.
contexa.iam.seed.accounts.enabled설정하지 않음(켜짐으로 동작)예시 계정 다섯과 그 그룹 배정(db/data-accounts.sql)을 넣을지 정합니다. 설정하지 않으면 contexa.iam.seed.admin.password가 없을 때만 넣습니다. true는 비밀번호 설정과 상관없이 넣고, false는 넣지 않습니다. 어느 경우든 사용자 계정이 이미 있는 DB에는 넣지 않습니다.배포 환경에서는 false로 명시합니다. 로컬에서 빠르게 시작할 때만 켭니다.
contexa.iam.seed.admin.password(없음)값이 있으면 기동 때 관리자 한 명을 만듭니다. 이 관리자는 ROLE_ADMIN을 가진 시스템관리자 그룹에 속합니다. 로그인은 FULL + CONTEXA_OWNED가 아니면 /contexa/admin/login의 콘솔 전용 로그인(늘 2단계: 비밀번호 다음에 패스키 또는 메일 코드)이고, FULL + CONTEXA_OWNED에서는 주 흐름의 로그인(기본은 2단계)입니다. 사용자 이름이나 메일이 같은 사용자가 이미 있으면 만들지 않고 아무것도 바꾸지 않습니다. 그래서 관리 콘솔에서 바꾼 비밀번호가 유지됩니다. contexa init은 이 값을 프로젝트 밖 ~/.contexa/credentials.properties에 둡니다.첫 관리자를 만들 때 설정합니다. 계정이 만들어진 뒤에는 이 설정을 지워도 계정이 남습니다.
contexa.iam.seed.admin.usernameadmin그 관리자의 사용자 이름입니다.기본 이름을 바꿀 때
contexa.iam.seed.admin.emailadmin@localhost그 관리자의 메일입니다. 두 번째 로그인 단계의 일회용 코드가 이 주소로 갑니다(네 조합 모두).코드를 메일로 받으려면 받을 수 있는 주소로 바꿉니다.
예시 계정은 배포 환경에서 켜지 않아야 합니다.
  • 예시 계정은 admin · manager · developer · user · finance 다섯 개입니다. 비밀번호가 하나로 같고 코드와 함께 공개되어 있습니다.
  • admin만 관리자 역할을 가집니다. 나머지는 개발 · 인프라 · 재무 역할 그룹에 속합니다.
  • 예시 계정을 만들면 기동 로그에 WARN 한 줄(Sample accounts were added ...)이 남습니다. 계정이 이미 있는 DB에서는 만들지 않고 그 사실을 INFO로 남깁니다.
  • 설정을 false로 바꿔도 이미 만들어진 예시 계정은 지워지지 않습니다. 다른 관리자를 먼저 만든 뒤 콘솔에서 예시 계정을 삭제하거나 비활성화합니다. 마지막 관리자는 삭제할 수 없습니다.
  • contexa.iam.seed.accounts.enabled를 true로 두고 contexa.iam.seed.admin.password도 설정하면, 예시 계정 admin이 먼저 들어가 있어 설정한 관리자는 만들어지지 않습니다.

정책이 여럿 맞을 때와 하나도 없을 때

요청 하나에 맞는 정책이 여럿일 수 있고, 하나도 없을 수 있습니다. 아래 설정 세 개가 이때의 정책 결정(허용 또는 거부)을 정합니다.

설정기본값뜻언제 바꾸나
contexa.policy.combining-algorithmFIRST_APPLICABLE요청에 맞는 정책이 여럿일 때 하나의 결정으로 묶는 방법입니다(결합 알고리즘).거부 정책이 우선해야 하면 DENY_OVERRIDES로 바꿉니다.
contexa.policy.no-matching-url-policy-decisionAUTHENTICATED맞는 URL 정책이 하나도 없을 때의 결정입니다. 값은 표 아래에 있습니다. 시스템 설정 화면의 이름은 "적용되는 URL 정책이 없을 때의 결정"입니다.모든 주소에 정책을 두는 운영이면 DENY. 배포 환경에서 PERMIT은 쓰지 않습니다.
contexa.policy.missing-method-policy-decisionPERMIT@Protectable 메서드에 정책이 하나도 없을 때의 결정입니다(PERMIT · DENY). 시스템 설정 화면의 이름은 "적용되는 메서드 정책이 없을 때의 결정"입니다.정책이 없는 메서드를 막으려면 DENY로 바꿉니다.

contexa.policy.no-matching-url-policy-decision의 값은 세 가지입니다.

  • AUTHENTICATED: 로그인한 사용자는 통과합니다. 로그인하지 않은 요청은 로그인으로 돌려보냅니다. CONTEXA 자신의 로그인 화면은 열려 있습니다.
  • PERMIT: 누구나 통과합니다.
  • DENY: 아무도 통과하지 못합니다. 정책이 이름을 붙이지 않은 CONTEXA 로그인 화면도 거부하므로, 로그인 화면을 허용하는 정책을 먼저 만듭니다.

맞는 정책이 있어도 모두 조건을 충족하지 못한 거부 정책이면, 정책이 없는 경우와 같이 위 결정을 씁니다. 이 경우에만 DENY_UNLESS_PERMIT가 거부합니다. 맞는 정책이 전혀 없으면 어떤 결합 알고리즘이든 위 결정을 씁니다. 앱 체인이 맡는 요청(앱이 로그인을 맡는 SANDBOX의 앱 요청, FULL에서 앱이 securityMatcher로 좁힌 체인의 경로)은 앱 체인이 정하므로, 이 결정은 앱이 CONTEXA의 정책 매니저(.access(customDynamicAuthorizationManager))에 넘긴 요청에만 적용됩니다.

저장된 시스템 설정이 YAML을 이깁니다. 정책 결정 설정이 어떤 순서로 적용되는지 정리하면 다음과 같습니다.
  1. 기본 시드는 시스템 설정 행 하나를 넣습니다. 이 행은 결합 알고리즘 FIRST_APPLICABLE, 정책 없는 메서드 PERMIT, 정책 없는 URL은 값 없음입니다.
  2. 이 행이 있으면 CONTEXA는 모든 빈을 만든 뒤 요청을 받기 전에 결합 알고리즘과 메서드 결정을 행의 값으로 덮어씁니다. 시드를 켠 설치에서는 YAML의 contexa.policy.combining-algorithm과 contexa.policy.missing-method-policy-decision이 쓰이지 않습니다. 이 두 YAML 값은 시스템 설정 행이 없을 때만 쓰입니다.
  3. 정책 없는 URL의 결정은 운영자가 저장한 뒤에야 행의 값으로 덮입니다. 그 전에는 YAML의 contexa.policy.no-matching-url-policy-decision이 적용됩니다. YAML에도 없으면 AUTHENTICATED입니다.
  4. 시스템 설정 화면은 URL 결정이 저장되기 전까지 지금 적용 중인 값을 선택된 것으로 보여 줍니다.
  5. 화면에서 저장하면 이 인스턴스에 바로 적용됩니다. contexa.infrastructure.mode: distributed이면 다른 인스턴스에도 다시 읽으라는 신호를 보냅니다(처음 켜기와 배포).
  6. 이전 버전에서 만든 설치는 행에 URL 결정으로 PERMIT을 갖고 있습니다. 업그레이드는 저장된 결정을 바꾸지 않으므로, 운영자가 다른 값을 고를 때까지 정책 없는 URL이 모두에게 열려 있습니다. CONTEXA가 로그인을 맡는 FULL에서는 시작할 때 이를 알리는 줄이 한 번 나옵니다.

결합 알고리즘

결합 알고리즘은 맞는 정책이 여럿일 때 정책 하나하나의 결과를 하나의 결정으로 합치는 규칙입니다. 정책 하나의 결과는 효과에 따라 정해집니다. 허용(ALLOW) 정책은 조건이 맞으면 허용으로, 맞지 않으면 거부로 계산합니다. 거부(DENY) 정책은 조건이 맞으면 거부로 계산하고, 맞지 않으면 계산에서 뺍니다.

값맞는 정책이 여럿일 때시스템 설정 화면의 이름
FIRST_APPLICABLE(기본)우선순위 순서로 처음 적용되는 정책이 정합니다.먼저 매칭된 정책 적용
DENY_OVERRIDES하나라도 거부면 거부합니다. 허용과 거부가 겹치면 거부가 이깁니다.거부 우선
PERMIT_OVERRIDES하나라도 허용이면 허용합니다.허용 우선
DENY_UNLESS_PERMIT명시적인 허용이 없으면 거부합니다.명시적 허용 없으면 거부

어디에 적용되나

  • URL 정책: 모든 요청을 CONTEXA의 동적 인가(CustomDynamicAuthorizationManager)로 판정하는 체인에서 쓰입니다. 기본으로는 @EnableAISecurity(mode = SecurityMode.FULL)의 기본 체인입니다. 그 밖의 요청(앱 체인이 맡거나 어느 체인도 맡지 않는 요청)에는 두 모드 모두 앱의 보안 체인과 서블릿 필터가 모두 끝난 뒤에 도는 URL 정책 필터가 그 요청에 맞는 정책을 적용하고, 정책이 정하지 않으면 앱 체인의 결정을 그대로 둡니다.
  • 메서드 정책: @Protectable 메서드를 호출할 때 쓰입니다. 보안 모드와 인증 소유권에 상관없이 적용됩니다(@Protectable).

관리 콘솔의 자원 스캔

자원은 정책을 걸 수 있는 대상입니다. 관리 콘솔은 앱의 컨트롤러 주소를 찾아 자원으로 등록합니다(자원 스캐너). 찾는 범위는 설정 파일이 아니라 시스템 설정 화면에서 정합니다.

  1. 스캐너는 시스템 설정 화면의 "컨트롤러 기본 패키지"에 적힌 패키지(기본 io.contexa.contexaiam.)를 찾습니다.
  2. 여기에 앱 자신의 패키지(Spring Boot가 아는 패키지)를 항상 더해서 찾습니다.
  3. 앱 패키지 밖의 주소를 등록하려면 "컨트롤러 기본 패키지"에 그 패키지를 더합니다. 한 줄에 하나씩 적거나 쉼표로 구분합니다.
설정기본값뜻언제 바꾸나
contexa.iam.admin.rest-docs-path/docs/index.html스캐너가 URL 자원마다 만드는 API 문서 링크(<경로>#<컨트롤러>_<메서드>)의 앞부분입니다. 관리 화면의 자원 정보와 AI 자원 이름 짓기에 쓰입니다. CONTEXA는 이 문서 페이지를 제공하지 않습니다.앱의 API 문서 주소로 바꿉니다.
contexa.iam.admin.condition-templates.enabledfalse조건 템플릿은 정책 조건에 다시 쓰는 표현식 틀입니다. true이면 관리 콘솔에서 자원을 새로 고칠 때(정책 센터 · 자원 관리 화면) 조건 템플릿을 자동으로 만듭니다. 기동 때 만드는 것은 아닙니다. 조건 템플릿을 직접 만드는 기능은 이 값과 상관없습니다.자원에서 조건 템플릿을 자동으로 만들고 싶을 때

실시간 끝점

IAM은 실시간 메시지용 STOMP 끝점을 등록할 수 있습니다. STOMP는 WebSocket 위에서 메시지를 주고받는 규약입니다. 이 끝점은 모든 출처의 연결을 받습니다. CONTEXA 안에는 이 끝점으로 메시지를 보내는 코드가 없으므로, 쓰지 않으면 false로 끕니다.

설정기본값뜻언제 바꾸나
contexa.iam.websocket.enabledtrueIAM이 STOMP 끝점 /ws-soar(SockJS, 브로커 /topic · /queue, 앱 접두사 /app)를 등록합니다. 서블릿 웹 앱이고, 앱에 Spring 메시지 브로커 빈의 이름(clientInboundChannel 등 21개)을 가진 빈이 하나도 없을 때만 등록합니다. 앱이 자기 STOMP 설정을 두면 이 이름의 빈이 생깁니다. 하나라도 있으면 WARN을 남기고 등록하지 않습니다.끝점을 쓰지 않으면 false로 끕니다. 앱의 STOMP 설정과 이름이 겹쳐 WARN이 나올 때도 false로 끄면 WARN이 사라집니다.
