받고 돌리기

git clone https://github.com/contexa73/contexa-examples.git
cd contexa-examples
./gradlew :contexa-example-quickstart:bootRun
  • Java 21. 예제 빌드는 Java 21 툴체인을 씁니다. Spring Boot는 3.5.11입니다.
  • Contexa 의존성. 루트 build.gradle이 모든 예제에 ai.ctxa:spring-boot-starter-contexa:0.1.0-SNAPSHOT을 넣고, Maven Local과 Central Portal 스냅숏 저장소에서 받습니다.
  • PostgreSQL과 vector 확장. 예제의 Contexa 전용 DB 기본 주소는 jdbc:postgresql://localhost:5432/contexa(protectable은 contexa_oss), 사용자는 contexa입니다. 다른 DB를 쓰려면 환경 변수 CONTEXA_DB_URL · CONTEXA_DB_USERNAME · CONTEXA_DB_PASSWORD로 바꿉니다. 이 변수를 읽는 예제는 quickstart · protectable · identity-mfa-multi · identity-oauth2 · legacy-system입니다.
  • AI 모델. 예제 설정은 Ollama 모델 qwen2.5:7b(채팅)와 mxbai-embed-large(임베딩)를 씁니다(ollama pull로 받기). 모델을 연결하는 지금 설정은 AI 모델 연결을 기준으로 하세요.

돌리기 전에 고칠 것

예제가 마지막으로 바뀐 뒤 Contexa 동작이 바뀐 곳이 세 군데 있습니다. 예제마다 해당하는 것을 예제별 안내에 적었습니다.

1. Contexa가 로그인을 맡게 하기(소유 방식)

quickstart · protectable · identity-* 예제는 인증 DSL(PlatformConfig)로 Contexa의 로그인 흐름을 만듭니다. 그런데 @EnableAISecurity의 기본값은 앱이 로그인을 맡는 방식(HOST_OWNED)이고, 이때 Contexa는 PlatformConfig의 로그인 체인을 만들지 않습니다. 그대로 돌리면 예제의 로그인 화면 · MFA · OAuth2가 나오지 않으니, 예제의 application.yml에 다음을 더합니다.

contexa:
  bridge:
    ownership: CONTEXA_OWNED

메인 클래스를 @EnableAISecurity(mode = SecurityMode.FULL)로 바꿔도 같습니다. 두 방식의 차이는 기존 Spring Security 앱에 붙이기에 있습니다.

2. Contexa 전용 DB 설정 더하기

identity-dsl · identity-mfa의 설정에는 Contexa 전용 DB(contexa.datasource.*)가 없습니다. contexa.datasource.url이 비어 있으면 기동이 IllegalStateException으로 멈추므로 더합니다. 앱 DB와 같은 DB를 쓰려면 isolation.contexa-owned-application: true도 넣습니다(DB 설정).

contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}

3. 옛 설정 이름 바꾸기

  • spring.auth.* · security.zerotrust.*는 옛 접두사입니다. 지금은 contexa.auth.* · contexa.security.zerotrust.*로 자동으로 옮겨지지만, 기동 로그에 ERROR가 남고 별칭은 0.3.0에서 없어집니다(옛 접두사).
  • contexa.hcad.*(없어진 기능), spring.zero-trust.*, spring.ai.chat.model.priority는 읽는 곳이 없어 효과가 없습니다. 지워도 됩니다.

예제별 안내

quickstart(8081): 가장 작은 구성

  • 보여 주는 것: 메인 클래스의 @EnableAISecurity와, 인증 DSL로 만든 폼 로그인(/login → /test/quickstart)입니다. /api/hello에만 @Protectable이 붙어 있어 판정 대상이 됩니다.
  • 해 볼 것: 로그인한 뒤 시험 화면 /test/quickstart에서 /api/hello를 불러 봅니다.
  • 돌리기 전에: 소유 방식을 더합니다. 설정이 분산 모드(contexa.infrastructure.mode: DISTRIBUTED)라 Redis · Kafka가 있어야 하므로, 없으면 standalone으로 바꿉니다(단독 · 분산). 집행 모드는 SHADOW입니다(집행 모드).

protectable(8082): @Protectable 네 가지 쓰임

API보호 방식동작
GET /api/orders@Protectable응답은 바로 하고 판정은 뒤에서 합니다(비동기)
GET /api/orders/customer/{customerId}@Protectable(ownerField = "customerId")정책 조건이 hasPermission(...)을 쓸 때, 대상의 customerId 값을 로그인 사용자 이름과 비교합니다. 그런 정책이 없으면 효과가 없습니다
POST /api/orders@Protectable(sync = true)판정이 나올 때까지 기다린 뒤 실행합니다
DELETE /api/orders/{orderId}?customerId=@Protectable(ownerField = "customerId", sync = true)판정을 기다리고, 소유자 비교도 위와 같이 합니다
  • 해 볼 것: 로그인한 뒤 시험 화면 /test/protectable에서 네 API를 불러 봅니다. 시작할 때 data.sql이 주문 한 건을 넣습니다.
  • 돌리기 전에: 소유 방식을 더합니다. 설정에 contexa.llm.enabled: false가 있어 판정용 AI 모델이 꺼져 있으니, AI 판정을 보려면 이 줄을 지우고 모델을 연결합니다.
  • 함께 읽기: sync · ownerField · 응답

identity-dsl(8083): 인증 DSL

  • 보여 주는 것: PlatformConfig 하나에 폼 로그인(/login → /)과 REST(JSON) 로그인(POST /api/login → /api/profile)을 함께 둡니다.
  • 돌리기 전에: 소유 방식과 전용 DB를 더합니다. 설정이 spring.jpa.hibernate.ddl-auto: validate라 표가 미리 있어야 하므로, 같은 폴더의 initdb/01-ddl.sql · 02-dml.sql(사용자 · 역할 · 그룹 기본값)을 먼저 실행합니다. AI 모델 설정은 OpenAI · Anthropic 키 자리만 있으니 AI 모델 연결에 맞춰 채웁니다.
  • 함께 읽기: 인증 DSL · 인증

identity-mfa(8087): MFA와 직접 만든 화면

  • 보여 주는 것: 1차는 직접 만든 로그인 화면(/customLogin)의 폼 로그인, 2차는 일회용 토큰(OTT)과 패스키입니다. mfaPage(...)로 2차 인증 화면 주소를 직접 정합니다: 토큰 요청 /custom/mfa/ott/request-code-ui, 토큰 입력 /custom/mfa/challenge/ott, 패스키 /custom/challenge/passkey. 화면은 Thymeleaf 템플릿과 contexa-mfa-sdk.js로 만듭니다.
  • 돌리기 전에: 소유 방식과 전용 DB를 더합니다(설정에는 앱용 H2만 있음).
  • 함께 읽기: 직접 만든 MFA 화면 · SDK

identity-mfa-multi(8088): MFA 흐름 두 개

  • 보여 주는 것: 이름이 다른 MFA 흐름 두 개를 둡니다. admin 흐름은 urlPrefix("/admin")에 패스키(순서 60), user 흐름은 urlPrefix("/user")에 일회용 토큰(순서 70)입니다. 로그인 화면 주소 앞에 각 접두사가 붙어 첫 화면 /에서 /admin/mfa/login · /user/mfa/login으로 들어가고, 성공하면 /admin/dashboard · /user/dashboard로 갑니다.
  • 돌리기 전에: 이 폴더는 루트 settings.gradle에 들어 있지 않아 ./gradlew :contexa-example-identity-mfa-multi:bootRun이 되지 않습니다. settings.gradle에 include 'contexa-example-identity-mfa-multi'를 더한 뒤 돌립니다. 소유 방식도 더합니다. 이 예제의 Contexa 설정(contexa.datasource.* · contexa.llm.*)은 지금 이름으로 되어 있습니다.
  • 함께 읽기: MFA 흐름 여러 개

identity-oauth2(8089): OAuth2 무상태 인증

  • 보여 주는 것: .form().oauth2()로 폼 로그인 뒤 JWT를 받고, 그다음 API는 Bearer 토큰으로 부릅니다. 시험 화면 /test/token과 시험 API POST /api/token-test/refresh · GET /api/token-test/validate · GET /api/token-test/userinfo가 있습니다.
  • 돌리기 전에: Contexa 인가 서버는 Contexa가 로그인을 맡을 때만 만들어지므로 소유 방식이 꼭 필요합니다. 설정의 spring.auth.*(상태 방식 OAUTH2, 토큰 전달 HEADER, 클라이언트 contexa-example)는 contexa.auth.*로 옮깁니다.
  • 함께 읽기: OAuth2 상태 · 로그인한 사용자에게 토큰 발급

legacy-system(9090): 레거시 로그인에 붙이기

  • 보여 주는 것: Spring Security 없이 자체 필터(LegacyAuthFilter)로 로그인하는 앱에 @EnableAISecurity(mode = SecurityMode.SANDBOX)로 붙입니다. 로그인 방법은 폼(/legacy/login), X-Auth-Token 헤더, remember-me 쿠키이고, 권한은 @LegacyRole 인터셉터가 봅니다. 로그인에 성공하면 필터가 ContexaAuthBridge.handoff(...)로 사용자 · 역할 · 부서 · 로그인 방식을 Contexa에 넘기고, 세션 속성 legacyUser에도 사용자 객체를 둡니다.
  • 보호된 API: GET /api/customers(@Protectable, 비동기)와 GET /api/customers/export(@Protectable(sync = true))입니다.
  • 예제 사용자: admin/admin123(ADMIN · MANAGER), kim_manager/manager123, park_dev/dev123, lee_analyst/analyst123.
  • 시나리오 프로필: application-scenario-*.yml 10개는 DB 구성별 기동을 시험합니다(전용 H2, 공유 DB의 PoC 허용 · 운영 거부, 전용 DB 없음, 브리지 끔, context path와 프록시 등, 포트 19081~19091). fake-chat 프로필은 늘 허용(PERMIT)을 돌려주는 시험용 모델과 빈 벡터 저장소를 씁니다.
  • 돌리기 전에: 이 앱에는 Spring Security 체인이 없고, 로그인한 사용자를 SecurityContext에 넣지도 않습니다. 앱이 로그인을 맡을 때 Contexa는 체인을 만들지 않으므로 그대로 돌리면 두 가지가 생깁니다.
    • Spring Boot 기본 보안이 모든 요청에 로그인을 요구하고, 기동 로그에 ERROR가 남습니다.
    • @Protectable API는 SecurityContext에 인증된 사용자가 없어 거부됩니다. 직접 넘기기(handoff)는 그 요청의 증거만 남기고 SecurityContext를 채우지 않습니다.
    기존 접근 규칙을 그대로 두는 체인과, 레거시 세션의 사용자를 SecurityContext에 넣는 필터를 더합니다(아래, import 생략). 설정의 security.zerotrust.* · spring.auth.*는 옛 이름입니다.
@Bean
SecurityFilterChain legacyChain(HttpSecurity http) throws Exception {
    return http
            .authorizeHttpRequests(auth -> auth.anyRequest().permitAll())
            .addFilterBefore(new LegacySessionAuthenticationFilter(), AnonymousAuthenticationFilter.class)
            .build();
}

// 레거시 로그인이 세션에 둔 사용자를 요청마다 SecurityContext에 넣습니다
class LegacySessionAuthenticationFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        HttpSession session = request.getSession(false);
        if (session != null
                && session.getAttribute(LegacyAuthFilter.SESSION_USER_KEY) instanceof LegacyUserSession user) {
            List<SimpleGrantedAuthority> roles = user.getRoles().stream()
                    .map(role -> new SimpleGrantedAuthority("ROLE_" + role))
                    .toList();
            SecurityContextHolder.getContext().setAuthentication(
                    UsernamePasswordAuthenticationToken.authenticated(user.getUserId(), null, roles));
        }
        chain.doFilter(request, response);
    }
}
