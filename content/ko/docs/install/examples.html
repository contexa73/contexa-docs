contexa-examples

예제

CONTEXA를 Spring Boot 앱에 붙이는 대표 상황 일곱 가지를 실행할 수 있는 예제로 제공합니다. 예제는 GitHub의 예제 저장소 contexa73/contexa-examples에 있습니다. 이 페이지는 상황에 맞는 예제를 고르는 방법, 예제를 받아 실행하는 방법, 예제마다 앱에 붙이는 것과 실행했을 때 확인할 수 있는 것을 설명합니다. 예제는 받은 그대로 기동하고 동작합니다.

예제 고르기

CONTEXA는 보호할 메서드를 호출하는 요청을 AI로 분석해 판정(Decision)을 내립니다. 판정은 허용(ALLOW), 추가 인증(CHALLENGE), 검토 보류(ESCALATE), 차단(BLOCK) 중 하나입니다. 분석 대상은 모든 요청이 아니라 @Protectable이 붙은 메서드를 호출하는 요청입니다.

예제는 각각 독립된 Spring Boot 앱이고 포트가 서로 다릅니다. CONTEXA를 처음 쓴다면 아래 순서로 봅니다.

이미 로그인 기능이 있는 시스템에 CONTEXA를 붙이려면 quickstart, protectable, legacy-system 순서로 봅니다. 새 시스템에서 로그인까지 CONTEXA에 맡기려면 quickstart와 protectable에 이어 identity-* 예제를 봅니다.

예제포트로그인을 맡는 쪽이런 상황에서 고릅니다
contexa-example-quickstart8081CONTEXACONTEXA를 처음 켭니다. @EnableAISecurity와 폼 로그인으로 가장 작은 구성을 만들고, 첫 @Protectable이 판정을 받는 것을 확인합니다
contexa-example-protectable8082CONTEXA메서드마다 @Protectable 설정을 정합니다. 네 가지 쓰임(비동기 · 소유자 확인 · sync · 둘 다) 중 맞는 것을 고릅니다
contexa-example-identity-dsl8083CONTEXA한 앱에서 폼 로그인과 REST(JSON) 로그인을 함께 제공합니다. 인증 DSL로 두 로그인 흐름을 설정합니다
contexa-example-identity-mfa8087CONTEXA첫 번째 인증 뒤에 일회용 토큰이나 패스키로 두 번째 인증(MFA, 다중 요소 인증)을 요구하고, 로그인 · MFA 화면을 직접 만듭니다

contexa-example-legacy-system9090앱Spring Security 없이 자체 로그인을 쓰는 레거시 앱에 로그인 코드를 바꾸지 않고 CONTEXA를 붙입니다

로그인을 맡는 쪽 열은 로그인 화면, 세션, 로그인용 필터 체인(Filter Chain)을 누가 만들고 관리하는지를 뜻합니다. 판정과 적용은 어느 쪽이든 CONTEXA가 합니다. 이 선택은 메인 클래스의 @EnableAISecurity에서 mode로 정합니다.

  • FULL: CONTEXA가 로그인과 필터 체인을 만듭니다. CONTEXA가 로그인을 맡는 예제 여섯 개는 메인 클래스에 @EnableAISecurity(mode = SecurityMode.FULL)을 붙입니다.
  • SANDBOX: 앱이 자기 로그인을 그대로 맡고, CONTEXA는 누가 로그인했는지 읽기만 합니다. legacy-system은 SecurityMode.SANDBOX를 씁니다.

두 방식에서 무엇이 같고 무엇이 달라지는지는 기존 Spring Security 앱에 붙이기에 있습니다.

받아서 실행하기

예제는 로컬 PC에서 실행합니다. 실행하기 전에 Java 21, CONTEXA 전용 PostgreSQL, 로컬 AI 모델 서버(Ollama)를 준비합니다. 준비를 마치면 저장소를 받아 예제 하나를 실행합니다.

준비물

  • Java 21. 예제 빌드는 Java 21 툴체인을 씁니다. Spring Boot는 3.5.11, Spring AI는 1.1.8입니다. CONTEXA를 쓰는 앱의 최소 Java 버전은 17입니다(준비물).
  • CONTEXA 의존성. 루트 build.gradle이 모든 예제에 ai.ctxa:spring-boot-starter-contexa:0.1.0을 넣습니다. 빌드는 로컬 Maven 저장소를 먼저, 그다음 Maven Central을 찾습니다. 빌드가 의존성을 찾지 못하면 CONTEXA 저장소에서 ./gradlew publishToMavenLocal을 실행해 로컬 Maven 저장소에 게시합니다.
  • PostgreSQL과 vector 확장. 벡터 확장(pgvector)은 PostgreSQL에 벡터 검색을 더하는 확장입니다. CONTEXA는 이 DB에 사용자 · 정책, 판정 기록, 감사 기록, 시스템 설정을 저장하고, 비슷한 과거 판정 기록을 찾는 벡터 저장소도 만듭니다. 예제는 모두 CONTEXA 데이터를 전용 DB에 둡니다. 기본 주소는 jdbc:postgresql://localhost:5432/contexa이고, 사용자와 비밀번호는 contexa입니다. 다른 DB를 쓰려면 CONTEXA_DB_URL · CONTEXA_DB_USERNAME · CONTEXA_DB_PASSWORD로 바꿉니다. 처음 기동할 때 CONTEXA가 그 DB에 표와 기본 데이터를 만듭니다. 여러 예제를 실행하면 예제마다 DB를 따로 둡니다.
  • AI 모델. 예제는 로컬 Ollama(http://localhost:11434, 또는 OLLAMA_BASE_URL로 지정한 주소)에서 모델 두 개를 씁니다. qwen3:8b는 판정을 만들고, mxbai-embed-large는 텍스트를 벡터로 바꿔 과거 판정 기록을 찾는 데 씁니다. 실행하기 전에 ollama pull로 두 모델을 내려받습니다. CONTEXA는 Ollama 서버 하나에 호출을 한 번에 두 개씩 보내고, 진행 중인 호출이 끝난 뒤에 모델을 바꿉니다(모델 서버가 한 번에 받는 호출 수). 로컬 모델은 호스팅 모델보다 느리므로, 예제는 2차 분석에 120초를 줍니다(contexa.security.tiered.layer2.timeout-ms, 기본 30초). 2차 분석은 1차 분석이 검토 보류(ESCALATE)로 넘긴 요청을 한 번 더 판정하는 단계입니다.

예제 기본값에 맞는 사용자와 DB는 아래 SQL로 만듭니다. 이 SQL은 사용자 contexa와 DB contexa를 만들고 vector 확장을 켭니다.

CREATE USER contexa WITH PASSWORD 'contexa';
CREATE DATABASE contexa OWNER contexa;
\c contexa
CREATE EXTENSION IF NOT EXISTS vector;

저장소를 받고 실행하기

git clone https://github.com/contexa73/contexa-examples.git
cd contexa-examples
./gradlew :contexa-example-quickstart:bootRun

기동이 끝나면 quickstart가 포트 8081에서 요청을 받습니다. 처음 기동할 때 CONTEXA가 전용 DB에 표와 기본 데이터를 만듭니다. 기동 로그에 [ContexaCapability]로 시작하는 ERROR 줄이 나오면 판정에 필요한 부품이 누락된 것입니다. 이때는 켜졌는지 확인하기에서 원인을 찾습니다.

로컬 실행에만 쓰는 값

예제가 받은 그대로 기동하도록, 예제의 application.yml에는 배포 환경에 가져가면 안 되는 값이 들어 있습니다. 이 값은 로컬 시험용입니다. 배포 환경에서는 아래 표처럼 바꿉니다.

값예제에 든 것로컬 실행 밖에서는
견본 계정admin · manager · developer · user · finance, 비밀번호 1111(contexa.iam.seed.accounts.enabled: true)contexa.iam.seed.accounts.enabled: false를 적어 견본 계정이 만들어지지 않게 합니다. 이 설정을 적지 않으면 CONTEXA가 사용자 계정이 없는 DB에 견본 계정을 만듭니다. 관리자 비밀번호(contexa.iam.seed.admin.password)를 정한 경우에는 만들지 않습니다
증거 서명 키고정된 예제 키CONTEXA_EVIDENCE_KEY(Base64, 32바이트 이상)를 넣습니다. 이 키는 CONTEXA가 판정 기록과 증거에 서명하는 데 쓰입니다(contexa.security.evidence.signing.keys). 키가 없으면 임시 키로 서명하고, 그 서명은 재시작한 뒤 검증할 수 없습니다
토큰 서명 키리소스의 example-jwk.p12CONTEXA_JWK_KEY_STORE · CONTEXA_JWK_KEY_STORE_PASSWORD를 넣습니다. 이 키 저장소(PKCS12)는 OAuth2 토큰에 서명합니다(contexa.auth.oauth2.jwk-key-store-path). 키 저장소가 없으면 CONTEXA는 시작할 때마다 새 임시 키로 서명하므로, 재시작하면 발급한 토큰이 모두 무효가 됩니다
OAuth2 클라이언트 비밀값(identity-oauth2)example-local-client-secretCONTEXA_OAUTH2_CLIENT_SECRET을 넣습니다. 이 값은 contexa.auth.oauth2.client-secret에 해당하고, 토큰을 발급하는 구성에서는 반드시 있어야 합니다

예제별 안내

예제마다 이런 상황에서 쓰는지, 앱에 무엇을 붙이는지, 실행하면 무엇이 보이는지를 같은 순서로 설명합니다. 따로 적지 않으면 admin / 1111로 로그인합니다.

quickstart(8081): 가장 작은 구성

  • 이런 상황에서 씁니다: CONTEXA를 처음 켜고, 메서드 하나가 판정을 받는 과정을 가장 작은 구성으로 확인할 때입니다.
  • 붙이는 것:
    • 메인 클래스의 @EnableAISecurity. 이 어노테이션이 CONTEXA를 켭니다.
    • 인증 DSL로 만든 폼 로그인(/login → /test/quickstart). 로그인은 CONTEXA가 맡습니다.
    • /api/hello에만 붙인 @Protectable. 이 API만 판정 대상이 됩니다.
    • 운영 모드 SHADOW(관찰 모드). CONTEXA가 판정하고 기록하지만 요청을 막지 않습니다(운영 모드). 모드를 적지 않으면 판정을 요청에 적용하는 적용 모드(ENFORCE)로 동작합니다.
  • 실행하는 순서:
    1. /login에서 로그인합니다. 로그인하면 시험 화면 /test/quickstart가 열립니다.
    2. 시험 화면에서 /api/hello를 부릅니다.
    3. 잠시 뒤 관리 화면의 판정 기록에서 판정을 확인합니다(결과 보는 곳).
  • 실행하면 보이는 것:
    • /api/hello의 응답이 정상으로 돌아옵니다. 운영 모드가 SHADOW이므로 판정이 차단이어도 요청을 막지 않습니다.
    • 판정은 응답이 나간 뒤에 만들어지므로 판정 기록은 응답보다 늦게 나타납니다. 판정은 CONTEXA DB에 이유와 함께 남습니다.
    • 로그인하지 않고 호출하면 SHADOW에서도 거부됩니다.

protectable(8082): @Protectable 네 가지 쓰임

  • 이런 상황에서 씁니다: 보호할 메서드마다 판정 방식을 정할 때입니다. 기본은 응답을 보낸 뒤에 판정하는 비동기 방식입니다. 삭제처럼 되돌릴 수 없는 작업에는 판정을 기다린 뒤 실행하는 sync 방식을 씁니다. 데이터 소유자만 호출하게 하려면 소유자 확인(ownerField)을 더합니다.
  • 붙이는 것: 메서드의 @Protectable 속성입니다. 아래 표는 이 예제의 API 네 개와 속성 조합입니다.
API보호 방식동작
GET /api/orders@Protectable응답은 바로 보내고 판정은 그 뒤에 합니다(비동기)
GET /api/orders/customer/{customerId}@Protectable(ownerField = "customerId")정책 조건이 hasPermission(...)을 쓸 때, 대상의 customerId 값을 로그인 사용자 이름과 비교합니다. 그런 정책이 없으면 효과가 없습니다
POST /api/orders@Protectable(sync = true)판정이 나올 때까지 기다린 뒤 실행합니다
DELETE /api/orders/{orderId}?customerId=@Protectable(ownerField = "customerId", sync = true)판정을 기다리고, 소유자 비교도 위와 같이 합니다
  • 실행하는 순서:
    1. 로그인한 뒤 시험 화면 /test/protectable을 엽니다.
    2. 시험 화면에서 네 API를 차례로 부릅니다. 앱이 시작할 때 data.sql이 견본 주문을 넣으므로 따로 데이터를 만들 필요가 없습니다.
  • 실행하면 보이는 것:
    • 비동기 API(GET /api/orders)는 응답이 바로 옵니다. sync = true인 두 API는 판정이 끝난 뒤에 응답하므로 더 늦게 옵니다. 판정이 기본 40초(contexa.security.zerotrust.agent.flight.wait) 안에 끝나지 않으면, 적용 모드에서는 호출을 통과시키지 않습니다.
    • 운영 모드가 ENFORCE일 때 허용이 아닌 판정은 메서드를 실행하지 않습니다. API 호출은 상태 코드로 거부 응답을 받습니다: 차단은 403, 추가 인증은 401, 검토 보류는 423입니다.
    • 소유자 비교는 정책 조건이 hasPermission(...)을 쓸 때만 동작합니다. ROLE_ADMIN 권한이 있는 계정은 이 비교를 건너뜁니다. 비교 결과를 보려면 관리자가 아닌 계정으로 로그인합니다.
    • 이 예제는 CONTEXA가 로그인을 맡으므로, 앱에 별도 DataSource가 없으면 CONTEXA DB가 앱의 기본 DB가 됩니다. 그래서 앱의 표도 CONTEXA DB에 함께 있습니다.
  • 함께 읽기: sync · ownerField · 응답

identity-dsl(8083): 인증 DSL

  • 이런 상황에서 씁니다: 한 앱이 브라우저용 폼 로그인과 API용 REST(JSON) 로그인을 함께 제공해야 할 때입니다.
  • 붙이는 것: PlatformConfig 하나에 로그인 흐름 두 개를 적습니다. 흐름은 로그인 방법과 로그인 상태를 짝지은 설정입니다.
    • REST(JSON) 로그인 흐름(POST /api/login → /api/profile)은 /api/**만 받고(rawHttp(http -> http.securityMatcher("/api/**"))) 먼저 놓입니다(order(50)).
    • 폼 로그인 흐름(/login → /)은 나머지 요청을 모두 받습니다.
    • 이렇게 나누는 이유는 요청이 순서가 낮은 흐름부터 비교되고, 처음 맞는 흐름 하나가 처리하기 때문입니다. 두 흐름이 모두 모든 요청을 받으면 뒤 흐름에는 요청이 닿지 않습니다(인증 DSL).
  • 실행하는 순서:
    1. 폼 로그인은 /login의 폼에서 로그인합니다.
    2. REST 로그인은 POST /api/login에 {"username":"admin","password":"1111"}을 보냅니다. 그다음 같은 세션으로 GET /api/profile을 부릅니다.
  • 실행하면 보이는 것: 한 앱에서 두 로그인 방식이 각각 동작합니다. 폼 로그인 뒤에는 /로 이동하고, REST 로그인 뒤에는 /api/profile을 부를 수 있습니다.
  • 함께 읽기: 인증 DSL · 인증

identity-mfa(8087): MFA와 직접 만든 화면

  • 이런 상황에서 씁니다: 비밀번호 로그인 뒤에 두 번째 인증을 요구하고, 로그인 화면과 두 번째 인증 화면을 앱의 디자인으로 직접 만들 때입니다. 일회용 토큰(OTT)은 사용자에게 메일로 보내는 일회용 코드이고, 패스키는 WebAuthn 기반 인증 수단입니다.
  • 붙이는 것:
    • 첫 번째 인증은 직접 만든 로그인 화면(/customLogin)의 폼 로그인입니다.
    • 두 번째 인증은 일회용 토큰(OTT)과 패스키입니다.
    • mfaPage(...)로 두 번째 인증 화면 주소를 직접 정합니다: 토큰 요청 /custom/mfa/ott/request-code-ui, 토큰 입력 /custom/mfa/challenge/ott, 패스키 /custom/challenge/passkey.
    • 화면은 Thymeleaf 템플릿과 contexa-mfa-sdk.js로 만듭니다.
  • 실행하는 순서:
    1. /customLogin에서 로그인합니다. 화면이 비밀번호를 /mfa/login으로 보냅니다.
    2. 이어서 일회용 코드 화면이 열립니다. 코드를 입력합니다.
  • 실행하면 보이는 것: 직접 만든 로그인 화면이 열리고, 비밀번호 단계 뒤에 일회용 코드 화면이 이어집니다. 두 번째 인증 화면의 주소는 mfaPage(...)로 정한 주소입니다. 코드는 메일로 보냅니다. 메일 서버(spring.mail.*)가 설정되어 있지 않거나 개발 프로필(local · dev · development · test)이 켜져 있으면 앱 콘솔에도 [OTT] Sign-in code for ... 줄로 출력됩니다(일회용 코드 받기).
  • 함께 읽기: 직접 만든 MFA 화면 · SDK

identity-mfa-multi(8088): MFA 흐름 두 개

  • 이런 상황에서 씁니다: 사용자 집단마다 다른 MFA를 적용해야 할 때입니다. 이 예제는 관리자에게 패스키와 일회용 토큰을, 일반 사용자에게 일회용 토큰을 요구합니다.
  • 붙이는 것: 이름이 다른 MFA 흐름 두 개입니다. urlPrefix는 그 흐름의 모든 MFA 주소 앞에 붙고, 흐름은 그 접두사 아래 요청만 받습니다.
    • admin 흐름은 urlPrefix("/admin")에 패스키와 일회용 토큰(순서 60)을 씁니다.
    • user 흐름은 urlPrefix("/user")에 일회용 토큰(순서 70)을 씁니다.
    • 패스키는 MFA를 마친 뒤에만 등록할 수 있습니다. 그래서 패스키가 없는 관리자는 먼저 이메일로 받은 일회용 코드로 인증합니다.
  • 실행하는 순서:
    1. 첫 화면 /을 엽니다. 각 접두사가 로그인 화면 주소 앞에 붙어 /admin/mfa/login · /user/mfa/login으로 들어갑니다.
    2. /user/mfa/login에서 user / 1111로 로그인합니다.
    3. 일회용 코드 화면에서 코드를 입력합니다. 코드를 받는 방법은 identity-mfa와 같습니다.
  • 실행하면 보이는 것: 흐름마다 로그인 화면 주소가 다르고, 성공한 뒤 이동하는 화면도 /admin/dashboard · /user/dashboard로 다릅니다.
  • 함께 읽기: MFA 흐름 여러 개

identity-oauth2(8089): OAuth2 무상태 인증

  • 이런 상황에서 씁니다: 서버에 로그인 세션을 두지 않고, 로그인 뒤에 받은 토큰으로 API를 호출하는 구조가 필요할 때입니다. 무상태 인증은 서버가 세션을 저장하지 않고 요청마다 토큰으로 사용자를 인증하는 방식입니다.
  • 붙이는 것:
    • .form().oauth2()로 폼 로그인에 토큰 발급을 더합니다. 로그인에 성공하면 응답에 JWT(JSON Web Token) 접근 토큰이 실리고, 그다음 API는 Bearer 토큰으로 부릅니다.
    • 토큰은 브라우저 localStorage에 둡니다(contexa.auth.token-persistence: localstorage).
    • 토큰 서명 키와 클라이언트 비밀값은 예제 값을 씁니다(로컬 실행에만 쓰는 값).
  • 실행하는 순서:
    1. /login에서 로그인합니다. 로그인하면 시험 화면 /test/token으로 이동합니다.
    2. 시험 화면(/test/token)이 저장된 토큰으로 POST /api/token-test/refresh · GET /api/token-test/validate · GET /api/token-test/userinfo를 부릅니다.
  • 실행하면 보이는 것: 세 API는 세션이 아니라 토큰으로 호출됩니다. 토큰 서명을 검증하는 공개 키는 /oauth2/jwks에 공개되고, 토큰 없이도 이 주소를 부를 수 있습니다.
  • 보안 참고: localStorage에 둔 토큰은 XSS(크로스 사이트 스크립팅) 공격으로 읽힐 수 있습니다. MFA 화면용 SDK는 localStorage 보관을 선택 사항으로 두고 CSP(콘텐츠 보안 정책)와 함께 쓰도록 안내합니다. 이 예제의 설정은 시험용입니다.
  • 함께 읽기: OAuth2 상태 · 로그인한 사용자에게 토큰 발급

legacy-system(9090): 레거시 로그인에 붙이기

  • 이런 상황에서 씁니다: 자체 필터로 로그인하는 기존 앱에, 로그인 코드를 바꾸지 않고 CONTEXA의 판정을 붙일 때입니다. 이 예제의 앱은 Spring Security 없이 자체 로그인을 씁니다. 로그인은 앱이 계속 맡고(SANDBOX), CONTEXA는 로그인한 사용자를 읽어 판정합니다. 예제의 레거시 로그인은 폼(/legacy/login), X-Auth-Token 헤더, remember-me 쿠키를 받고, 권한은 @LegacyRole 인터셉터가 검사합니다.
  • 붙이는 것:
    1. 메인 클래스에 @EnableAISecurity(mode = SecurityMode.SANDBOX)를 붙입니다.
    2. Spring Security 의존성을 추가하고, 기존 접근 규칙을 그대로 두는 체인(LegacySecurityConfig)을 선언합니다.
    3. 레거시 세션의 사용자를 SecurityContext에 넣는 필터(LegacySessionAuthenticationFilter)를 그 체인에 둡니다.
    4. 로그인에 성공하면 기존 로그인 필터(LegacyAuthFilter)가 ContexaAuthBridge.handoff(...)로 사용자 · 역할 · 부서 · 로그인 방식을 CONTEXA에 넘기고, 세션 속성 legacyUser에도 사용자 객체를 둡니다.
    5. 보호할 API에 @Protectable을 붙입니다.
  • 앱의 보안 체인이 필요한 이유: 앱이 로그인을 맡으면(인증 소유권 HOST_OWNED) CONTEXA는 로그인 체인을 만들지 않고 SecurityContext도 채우지 않습니다. 그런데 @Protectable은 SecurityContext에 인증된 사용자가 있어야 합니다. 없으면 SHADOW와 ENFORCE에서 호출이 거부됩니다. ContexaAuthBridge.handoff(...)는 로그인 정보를 CONTEXA에 알리는 호출이고 SecurityContext를 채우지는 않습니다. 그래서 위 2번과 3번이 따로 필요하고, 코드는 아래와 같습니다.
@Bean
SecurityFilterChain legacyChain(HttpSecurity http) throws Exception {
    return http.csrf(csrf -> csrf.disable())
            .authorizeHttpRequests(auth -> auth.anyRequest().permitAll())
            .addFilterBefore(new LegacySessionAuthenticationFilter(), AnonymousAuthenticationFilter.class)
            .build();
}

// 레거시 로그인이 세션에 둔 사용자를 요청마다 SecurityContext에 넣는다
class LegacySessionAuthenticationFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        HttpSession session = request.getSession(false);
        if (session != null
                && session.getAttribute(LegacyAuthFilter.SESSION_USER_KEY) instanceof LegacyUserSession user) {
            List<SimpleGrantedAuthority> roles = user.getRoles().stream()
                    .map(role -> new SimpleGrantedAuthority("ROLE_" + role))
                    .toList();
            SecurityContextHolder.getContext().setAuthentication(
                    UsernamePasswordAuthenticationToken.authenticated(user.getUserId(), null, roles));
        }
        chain.doFilter(request, response);
    }
}

체인은 모든 URL을 허용하고(permitAll()) 접근 규칙을 기존 앱에 맡깁니다. 필터는 요청마다 세션의 LegacyUserSession을 읽어, 역할 앞에 ROLE_을 붙인 권한으로 사용자를 SecurityContext에 넣습니다. 이 체인에도 Spring Security 기본 설정이 적용되므로, 기존 동작과 다른 부분은 앱에 맞게 조정합니다(기존 로그인과 연결하기).

  • 실행하는 순서:
    1. 레거시 로그인 방법 중 하나로 로그인합니다: 폼(/legacy/login), X-Auth-Token 헤더, remember-me 쿠키.
    2. 보호된 API를 부릅니다: GET /api/customers(@Protectable, 비동기)와 GET /api/customers/export(@Protectable(sync = true)).
  • 예제 사용자: admin/admin123(ADMIN · MANAGER), kim_manager/manager123, park_dev/dev123, lee_analyst/analyst123.
  • 실행하면 보이는 것:
    • 로그인은 CONTEXA 화면이 아니라 앱의 기존 필터와 로그인 방법이 처리합니다.
    • 두 API 호출이 판정 대상이 되어 CONTEXA DB의 판정 기록에 남습니다. 운영 모드가 SHADOW나 ENFORCE이면, 로그인하지 않고 /api/customers를 부르는 호출은 거부됩니다.
    • 앱 데이터는 앱의 DB(메모리 H2)에, CONTEXA 데이터는 CONTEXA 전용 DB에 따로 저장됩니다.
    • CONTEXA 관리 화면은 앱 계정이 아니라 앱 사용자와 별개인 CONTEXA 관리자 계정으로 로그인합니다(관리 화면에서 보기).
  • 시나리오 프로필: application-scenario-*.yml 10개는 DB 구성별 기동을 시험하는 설정 파일입니다(전용 H2, 공유 DB의 PoC 허용 · 운영 거부, 전용 DB 없음, 브리지 끔, context path와 프록시 등, 포트 19081~19091). fake-chat 프로필은 늘 허용(PERMIT)을 돌려주는 시험용 모델과 빈 벡터 저장소를 씁니다. 실제 AI 모델을 쓰지 않는 시험용 프로필입니다.
