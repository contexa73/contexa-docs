contexa-examples

예제

GitHub의 예제 저장소 contexa73/contexa-examples에 있는 예제 7개를 받고 돌리는 방법, 예제마다 보여 주는 것과 해 볼 것을 안내합니다. 예제는 받은 그대로 기동하고 돌아갑니다.

한눈에 보기

예제는 각각 따로 도는 Spring Boot 앱입니다. 처음이라면 아래 순서로 보면 쉽습니다.

예제포트로그인을 맡는 쪽보여 주는 것
contexa-example-quickstart8081Contexa@EnableAISecurity와 폼 로그인, 첫 @Protectable
contexa-example-protectable8082Contexa@Protectable 네 가지 쓰임(비동기 · 소유자 확인 · sync · 둘 다)
contexa-example-identity-dsl8083Contexa인증 DSL로 폼 로그인과 REST(JSON) 로그인 함께 두기
contexa-example-identity-mfa8087ContexaMFA(일회용 토큰 · 패스키)와 직접 만든 로그인 · MFA 화면

Contexa가 로그인을 맡는 예제 여섯 개는 메인 클래스에 @EnableAISecurity(mode = SecurityMode.FULL)을 붙이고, legacy-system은 SecurityMode.SANDBOX로 자기 로그인을 그대로 둡니다. 두 소유 방식의 차이는 기존 Spring Security 앱에 붙이기에 있습니다.

받고 돌리기

git clone https://github.com/contexa73/contexa-examples.git
cd contexa-examples
./gradlew :contexa-example-quickstart:bootRun
  • Java 21. 예제 빌드는 Java 21 툴체인을 씁니다. Spring Boot는 3.5.11, Spring AI는 1.1.8입니다.
  • Contexa 의존성. 루트 build.gradle이 모든 예제에 ai.ctxa:spring-boot-starter-contexa:0.1.0을 넣고, 로컬 Maven 저장소를 먼저, 그다음 Maven Central을 찾습니다. 빌드가 찾지 못하면 Contexa 저장소에서 ./gradlew publishToMavenLocal로 올려 둡니다.
  • PostgreSQL과 vector 확장. 예제는 모두 Contexa 데이터를 전용 DB에 둡니다. 기본 주소는 jdbc:postgresql://localhost:5432/contexa, 사용자 · 비밀번호는 contexa입니다. 다른 DB를 쓰려면 CONTEXA_DB_URL · CONTEXA_DB_USERNAME · CONTEXA_DB_PASSWORD로 바꿉니다. 처음 기동할 때 Contexa가 그 DB에 표와 기본 데이터를 만들므로, 여러 예제를 돌리면 예제마다 DB를 따로 둡니다.
  • AI 모델. 예제는 로컬 Ollama(http://localhost:11434, 또는 OLLAMA_BASE_URL)의 qwen3:8b(판정)와 mxbai-embed-large(과거 판정 기록)를 씁니다. ollama pull로 받아 둡니다. Contexa는 Ollama 서버 하나에 호출을 한 번에 두 개씩 보내고, 진행 중인 호출이 끝난 뒤에 모델을 바꿉니다(모델 서버가 한 번에 받는 호출 수). 로컬 모델은 호스팅 모델보다 느리므로, 예제는 2차 분석에 120초를 줍니다(contexa.security.tiered.layer2.timeout-ms, 기본 30초).
CREATE USER contexa WITH PASSWORD 'contexa';
CREATE DATABASE contexa OWNER contexa;
\c contexa
CREATE EXTENSION IF NOT EXISTS vector;

예제가 받은 그대로 기동하도록, 예제의 application.yml에는 배포에 절대 가져가면 안 되는 값이 들어 있습니다.

견본 계정admin · manager · developer · user · finance, 비밀번호 1111(contexa.iam.seed.accounts.enabled: true)이 설정을 켜지 않습니다

예제별 안내

따로 적지 않으면 admin / 1111로 로그인합니다.

quickstart(8081): 가장 작은 구성

  • 보여 주는 것: 메인 클래스의 @EnableAISecurity와, 인증 DSL로 만든 폼 로그인(/login → /test/quickstart)입니다. /api/hello에만 @Protectable이 붙어 있어 판정 대상이 됩니다. 집행 모드는 SHADOW라 판정하고 기록만 하며 막지 않습니다(집행 모드).
  • 해 볼 것: 로그인한 뒤 시험 화면 /test/quickstart에서 /api/hello를 불러 봅니다. 판정은 Contexa DB에 기록됩니다.

protectable(8082): @Protectable 네 가지 쓰임

API보호 방식동작
GET /api/orders@Protectable응답은 바로 하고 판정은 뒤에서 합니다(비동기)
GET /api/orders/customer/{customerId}@Protectable(ownerField = "customerId")정책 조건이 hasPermission(...)을 쓸 때, 대상의 customerId 값을 로그인 사용자 이름과 비교합니다. 그런 정책이 없으면 효과가 없습니다
POST /api/orders@Protectable(sync = true)판정이 나올 때까지 기다린 뒤 실행합니다
DELETE /api/orders/{orderId}?customerId=@Protectable(ownerField = "customerId", sync = true)판정을 기다리고, 소유자 비교도 위와 같이 합니다
  • 해 볼 것: 로그인한 뒤 시험 화면 /test/protectable에서 네 API를 불러 봅니다. 시작할 때 data.sql이 견본 주문을 넣습니다. Contexa가 앱을 맡으므로 앱의 표도 Contexa DB에 함께 있습니다.
  • 함께 읽기: sync · ownerField · 응답

identity-dsl(8083): 인증 DSL

  • 보여 주는 것: PlatformConfig 하나에 REST(JSON) 로그인(POST /api/login → /api/profile)과 폼 로그인(/login → /)을 함께 둡니다. REST 흐름은 /api/**만 받고(rawHttp(http -> http.securityMatcher("/api/**"))) 먼저 놓이며(order(50)), 폼 흐름이 나머지 요청을 모두 받습니다. 두 흐름이 모두 모든 요청을 받으면 뒤 흐름에는 요청이 닿지 않습니다(인증 DSL).
  • 해 볼 것: /login의 폼으로, 또는 POST /api/login에 {"username":"admin","password":"1111"}을 보내고 같은 세션으로 GET /api/profile을 불러 봅니다.
  • 함께 읽기: 인증 DSL · 인증

identity-mfa(8087): MFA와 직접 만든 화면

  • 보여 주는 것: 1차는 직접 만든 로그인 화면(/customLogin)의 폼 로그인, 2차는 일회용 토큰(OTT)과 패스키입니다. mfaPage(...)로 2차 인증 화면 주소를 직접 정합니다: 토큰 요청 /custom/mfa/ott/request-code-ui, 토큰 입력 /custom/mfa/challenge/ott, 패스키 /custom/challenge/passkey. 화면은 Thymeleaf 템플릿과 contexa-mfa-sdk.js로 만듭니다.
  • 해 볼 것: /customLogin에서 로그인합니다. 화면이 비밀번호를 /mfa/login으로 보내고, 이어서 일회용 코드 화면이 열립니다.
  • 함께 읽기: 직접 만든 MFA 화면 · SDK

identity-mfa-multi(8088): MFA 흐름 두 개

  • 보여 주는 것: 이름이 다른 MFA 흐름 두 개를 둡니다. admin 흐름은 urlPrefix("/admin")에 패스키와 일회용 토큰(순서 60)입니다. 패스키는 MFA를 마친 뒤에만 등록할 수 있어, 패스키가 없는 관리자는 먼저 이메일로 확인합니다. user 흐름은 urlPrefix("/user")에 일회용 토큰(순서 70)입니다. 로그인 화면 주소 앞에 각 접두사가 붙어 첫 화면 /에서 /admin/mfa/login · /user/mfa/login으로 들어가고, 성공하면 /admin/dashboard · /user/dashboard로 갑니다.
  • 해 볼 것: /user/mfa/login에서 user / 1111로 로그인하면 일회용 코드 화면이 이어집니다.
  • 함께 읽기: MFA 흐름 여러 개

identity-oauth2(8089): OAuth2 무상태 인증

  • 보여 주는 것: .form().oauth2()로 폼 로그인 뒤 JWT를 받고, 그다음 API는 Bearer 토큰으로 부릅니다. 토큰은 브라우저 localStorage에 두고(contexa.auth.token-persistence: localstorage), 시험 화면 /test/token이 그 토큰으로 POST /api/token-test/refresh · GET /api/token-test/validate · GET /api/token-test/userinfo를 부릅니다. 서명 키는 /oauth2/jwks에 공개됩니다.
  • 해 볼 것: /login에서 로그인하면 /test/token으로 갑니다.
  • 함께 읽기: OAuth2 상태 · 로그인한 사용자에게 토큰 발급

legacy-system(9090): 레거시 로그인에 붙이기

  • 보여 주는 것: 자체 필터(LegacyAuthFilter)로 로그인하는 앱에 @EnableAISecurity(mode = SecurityMode.SANDBOX)로 붙입니다. 로그인은 앱이 맡습니다. 로그인 방법은 폼(/legacy/login), X-Auth-Token 헤더, remember-me 쿠키이고, 권한은 @LegacyRole 인터셉터가 봅니다. 로그인에 성공하면 필터가 ContexaAuthBridge.handoff(...)로 사용자 · 역할 · 부서 · 로그인 방식을 Contexa에 넘기고, 세션 속성 legacyUser에도 사용자 객체를 둡니다. 앱 데이터는 앱의 DB(메모리 H2)에, Contexa 데이터는 Contexa 전용 DB에 둡니다.
  • 보호된 API: GET /api/customers(@Protectable, 비동기)와 GET /api/customers/export(@Protectable(sync = true))입니다.
  • 예제 사용자: admin/admin123(ADMIN · MANAGER), kim_manager/manager123, park_dev/dev123, lee_analyst/analyst123.
  • 앱의 보안 체인: 앱이 로그인을 맡으면 Contexa는 체인을 만들지 않고, @Protectable은 SecurityContext에 인증된 사용자가 있어야 합니다. 그래서 예제는 기존 접근 규칙을 그대로 두는 체인(LegacySecurityConfig)과, 레거시 세션의 사용자를 SecurityContext에 넣는 필터(LegacySessionAuthenticationFilter)를 둡니다.
@Bean
SecurityFilterChain legacyChain(HttpSecurity http) throws Exception {
    return http.csrf(csrf -> csrf.disable())
            .authorizeHttpRequests(auth -> auth.anyRequest().permitAll())
            .addFilterBefore(new LegacySessionAuthenticationFilter(), AnonymousAuthenticationFilter.class)
            .build();
}

// 레거시 로그인이 세션에 둔 사용자를 요청마다 SecurityContext에 넣는다
class LegacySessionAuthenticationFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        HttpSession session = request.getSession(false);
        if (session != null
                && session.getAttribute(LegacyAuthFilter.SESSION_USER_KEY) instanceof LegacyUserSession user) {
            List<SimpleGrantedAuthority> roles = user.getRoles().stream()
                    .map(role -> new SimpleGrantedAuthority("ROLE_" + role))
                    .toList();
            SecurityContextHolder.getContext().setAuthentication(
                    UsernamePasswordAuthenticationToken.authenticated(user.getUserId(), null, roles));
        }
        chain.doFilter(request, response);
    }
}
