spring-boot-starter-contexa

설치 개요

Contexa를 내 Spring Boot 앱에서 켜는 데 무엇이 필요하고, 어떤 길로 설치할지 정하는 페이지입니다. 준비물, 로그인을 누가 맡을지, 의존성 좌표, 상태를 어디에 둘지(인프라 모드)를 한 번에 봅니다.

한눈에 보기

Contexa는 의존성을 넣는 것만으로는 켜지지 않습니다. 메인 클래스에 @EnableAISecurity를 붙여야 켜지고, 켜지면 Contexa 전용 DB가 있어야 기동하며, AI 모델과 벡터 저장소가 있어야 판정이 나옵니다.

켜짐과 꺼짐은 이렇게 정해집니다. @EnableAISecurity는 기동할 때 켜짐 표지(속성 소스 contexaAiSecurityAnnotation)를 설정에 넣고, Contexa는 이 표지가 있을 때만 자기 자동 설정을 씁니다. 그래서 어노테이션이 없으면 Contexa의 자동 설정은 모두 빠집니다. 반대로 contexa.enabled: false이면 어노테이션이 있어도 아무것도 켜지 않습니다.

설치 길 고르기

두 길 모두 결과는 같습니다. 앱의 빌드 파일에 의존성이 들어가고, 메인 클래스에 @EnableAISecurity가 붙고, application.yml에 Contexa 설정이 들어갑니다.

로그인을 누가 맡나

@EnableAISecurity의 mode가 로그인을 누가 맡을지의 기본값을 정합니다. 이 값은 인증 소유권(contexa.bridge.ownership)으로 이어지고, 설정에 소유권을 직접 적으면 그 값이 이깁니다.

보안 모드인증 소유권로그인 · 보안 체인이럴 때
SANDBOX(기본)HOST_OWNED로그인 · 세션 · 쿠키 · URL 권한 규칙은 앱의 Spring Security가 그대로 맡고, Contexa는 누가 로그인했는지 읽기만 합니다. 판정과 모든 경로의 집행은 Contexa가 합니다. Contexa 필터가 앱 체인 바로 뒤에서 돌고, CHALLENGE는 Contexa의 추가 확인(/contexa/step-up)으로 가며, 에이전트 관문이 동작하고, 관리 화면(/contexa/admin/**)은 Contexa가 자기 관리자 로그인으로 지킵니다.이미 로그인이 있는 기존 시스템
FULLCONTEXA_OWNEDContexa가 로그인(폼 · 패스키 · 일회용 토큰 MFA)과 보안 체인을 만듭니다. 요청 시점 집행 필터와 에이전트 관문은 HOST_OWNED와 똑같이 동작하고, CHALLENGE는 Contexa MFA로 갑니다.로그인을 Contexa에 맡길 신규 시스템

CLI를 쓰면 직접 고르지 않아도 됩니다. contexa init은 앱에 SecurityFilterChain이 있으면 HOST_OWNED, 없으면 CONTEXA_OWNED를 고르고, 무엇을 바꾸기 전에 고른 방식을 보여 줍니다. 다르게 하려면 --ownership host|contexa를 줍니다(CLI가 고르는 방법).

두 방식에서 무엇이 동작하는지 전체 표는 기존 Spring Security 앱에 붙이기에 있습니다.

채팅 모델과 벡터 저장소가 없으면 판정이 나오지 않습니다. 판정 전략이 만들어지지 않아, 보호된 요청은 모두 분석 대기(PENDING_ANALYSIS)로 남습니다. 로그인을 앱이 맡는 기본 설정에서는 기동은 되므로 놓치기 쉽습니다. 기동 로그의 기능 진단 줄([ContexaCapability])을 확인하세요(켜졌는지 확인하기).

의존성 좌표

안정 판은 Maven Central에 ai.ctxa 그룹으로 게시됩니다. 진입점은 스타터 하나이고, mavenCentral() 말고 다른 저장소는 필요 없습니다.

implementation("ai.ctxa:spring-boot-starter-contexa:0.1.1")
<dependency>
    <groupId>ai.ctxa</groupId>
    <artifactId>spring-boot-starter-contexa</artifactId>
    <version>0.1.1</version>
</dependency>

스타터가 가져오는 것과 가져오지 않는 것

무엇스타터에 들어 있나메모
Contexa 모듈 다섯(common · core · identity · iam · autoconfigure)예실제로 무엇이 켜지는지는 켜짐 조건과 설정이 정합니다.
OAuth2 리소스 서버 · 클라이언트, Spring Authorization Server예인가 서버는 1.5.1로 고정
Spring Security(spring-boot-starter-security)아니오Spring Boot는 이것이 클래스패스에 있으면 앱을 보호하므로, 스타터만 넣어도 앱이 바뀌지 않도록 일부러 뺐습니다(빌드가 검사). @EnableAISecurity를 쓰려면 앱이 넣습니다.
Spring AI · resilience4j · Spring Statemachine BOM예(판 관리만)Spring AI BOM은 1.1.8
Spring AI 공급자 스타터(OpenAI · Anthropic · Ollama)아니오어느 공급자를 쓸지는 앱이 고릅니다.
PgVector 스타터(spring-ai-starter-vector-store-pgvector)아니오의존성만 넣은 앱에서 그 자동 설정이 돌지 않도록 일부러 뺐습니다. 앱이 넣습니다.
Redis(spring-boot-starter-data-redis) · Redisson · Kafka(spring-kafka)아니오distributed로 쓸 때 앱이 넣습니다.

의존성만 넣었을 때

  • @EnableAISecurity가 없으면 Contexa의 자동 설정이 모두 빠지므로, Contexa의 필터 · 인증 제공자 · 표가 생기지 않습니다.
  • 스타터는 Spring Security를 가져오지 않으므로, 스타터만 넣어서는 Spring Security를 쓰지 않던 앱에 Spring Boot의 기본 보안 체인이 생기지 않습니다.
  • Contexa의 표는 Contexa가 켜진 앱이 기동할 때 Contexa DB에 만들고 검증합니다. CLI는 표를 만들지 않습니다.

인프라 모드

contexa.infrastructure.mode가 판정 · 학습 상태를 어디에 둘지 정합니다. 값은 standalone(기본)과 distributed이고 대소문자는 가리지 않습니다.

무엇standalone(기본)distributed
사용자 판정 저장소메모리Redis
행위 기준선 · 맥락 기록 등 학습 상태메모리(재시작하면 사라짐)Redis
보안 사건 전달메모리Kafka
차단 신호 전파메모리Redisson
MFA 세션HTTP 세션Redis
앱이 넣을 의존성없음spring-boot-starter-data-redis, Redisson, spring-kafka(Redis · Kafka 연결 설정 포함)
기동 로그"학습 상태가 메모리에 있어 재시작하면 사라진다"는 WARN 한 줄없음

standalone에서는 Contexa의 Redis · Kafka 자동 설정을 쓰지 않습니다. Spring Boot의 Redis 자동 설정도 거르지만, 앱이 자기 연결 설정(예: spring.data.redis.host)을 적었거나 앱의 클래스가 Spring Data Redis · Redisson을 쓰면 그대로 둡니다. Spring Boot의 Kafka 자동 설정은 Contexa가 없을 때와 똑같이 둡니다. 여러 인스턴스로 운영하거나 재시작 뒤에도 학습을 이어 가려면 distributed를 쓰세요(분산 배포로 넘어가기).
