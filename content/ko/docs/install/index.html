spring-boot-starter-contexa

설치 개요

CONTEXA를 Spring Boot 앱에 설치하려면 네 가지가 필요합니다. 스타터 의존성, 메인 클래스의 @EnableAISecurity 어노테이션, CONTEXA 전용 데이터베이스(DB), AI 모델입니다. 설치할 때 정할 것은 두 가지입니다. CLI로 설치할지 직접 설치할지, 그리고 로그인을 계속 앱이 담당할지 CONTEXA에 맡길지입니다.

필요한 것과 켜는 순서

스타터 의존성만 추가하면 앱은 바뀌지 않고 CONTEXA도 켜지지 않습니다. 메인 클래스에 @EnableAISecurity를 붙이면 CONTEXA가 켜집니다. 켜진 CONTEXA는 전용 DB가 없으면 기동하지 않습니다. AI 모델과 벡터 저장소(비슷한 과거 판정 기록을 찾는 저장소)가 없으면 앱은 기동하지만 판정이 나오지 않습니다.

@EnableAISecurity를 붙이면 CONTEXA가 Spring Security로 요청을 보호하기 시작하므로, 앱이 org.springframework.boot:spring-boot-starter-security 의존성을 직접 선언해야 합니다. 스타터는 이 의존성을 일부러 포함하지 않습니다. Spring Boot는 Spring Security가 있으면 모든 요청에 로그인을 요구하므로, 스타터가 포함하면 의존성만 추가해도 앱이 바뀌기 때문입니다(스타터가 가져오는 것과 가져오지 않는 것).

CONTEXA가 켜지지 않는 경우. 메인 클래스에 @EnableAISecurity가 없으면 스타터가 있어도 CONTEXA의 기능이 하나도 적용되지 않습니다. 어노테이션이 있어도 설정에 contexa.enabled: false를 적으면 아무것도 켜지지 않습니다.

설치 방법 고르기

두 방법은 끝났을 때의 상태가 같습니다. 앱의 빌드 파일에 의존성이 들어가고, 메인 클래스에 @EnableAISecurity가 붙고, 설정 파일에 CONTEXA 설정이 들어갑니다. DB와 AI 모델이 아직 없으면 둘을 로컬에 대신 준비해 주는 CLI가 빠릅니다. DB와 모델을 이미 정했거나 클라우드의 관리형 DB를 쓴다면 직접 설치합니다.

로그인을 누가 담당할지 정하기

CONTEXA는 어느 쪽을 고르든 위험을 판정하고 모든 요청에 적용합니다. 고르는 것은 로그인(로그인 화면, 세션, 쿠키, URL 권한 규칙)을 앱이 계속 담당할지, CONTEXA에 맡길지입니다. 기본값은 앱이 계속 담당하는 방식이며, 이미 로그인 기능이 있는 앱은 이 방식을 씁니다. 이 선택은 @EnableAISecurity의 mode로 정하는 보안 모드(SANDBOX 또는 FULL)이며, 두 모드 모두 CONTEXA의 전체 기능이 동작합니다. 설정 contexa.bridge.ownership의 인증 소유권(HOST_OWNED 또는 CONTEXA_OWNED)은 이와 다른 설정입니다. 인증 소유권은 앱이 직접 둔 구성요소(UserDetailsService · JwtDecoder 등)와 CONTEXA의 같은 종류가 만날 때 어느 쪽을 앱에 쓰는지 정합니다. HOST_OWNED는 앱 것을 쓰고, CONTEXA_OWNED는 앱에 없는 종류를 CONTEXA 것으로 채웁니다. 기능을 끄지 않으며 네 조합 모두 허용됩니다. 적지 않으면 모드를 따릅니다(SANDBOX → HOST_OWNED, FULL → CONTEXA_OWNED).

설정 contexa.ai.security.mode를 적으면 어노테이션의 mode보다 그 값이 우선합니다. contexa.bridge.ownership은 보통 적지 않고, 적으면 모드와 상관없이 그 값을 씁니다. 실제로 정해진 값은 기동 때 남는 INFO 줄 [Contexa] mode=… ownership=… data=… enforcement=…에서 확인합니다.

보안 모드인증 소유권(적지 않을 때)로그인과 Spring Security 필터 체인이럴 때
SANDBOX(기본)HOST_OWNED로그인, 세션, 쿠키, URL 권한 규칙은 앱의 Spring Security가 지금처럼 처리합니다. CONTEXA는 로그인한 사용자를 읽기만 하고, 판정과 모든 경로에 대한 적용은 CONTEXA가 합니다. CONTEXA의 필터는 앱의 필터 체인과 다른 서블릿 필터가 모두 끝난 뒤에 실행됩니다. 판정이 추가 인증(CHALLENGE)이면 사용자는 CONTEXA의 추가 인증 화면(/contexa/step-up)으로 이동합니다. AI 에이전트 요청을 검사하는 에이전트 관문도 동작합니다. 관리 화면(/contexa/admin/**)은 앱 사용자와 별개인 CONTEXA 관리자 로그인(비밀번호 다음에 패스키 또는 메일 코드)으로 보호합니다.이미 로그인 기능이 있는 기존 시스템
FULLCONTEXA_OWNEDCONTEXA가 로그인(폼 로그인, 패스키, 일회용 토큰 MFA)과 필터 체인을 만듭니다. 요청마다 판정을 적용하는 필터와 에이전트 관문은 SANDBOX와 동일하게 동작합니다. 추가 인증(CHALLENGE)이 나오면 사용자는 CONTEXA의 MFA 흐름으로 이동합니다.로그인을 CONTEXA에 맡길 신규 시스템

CLI를 쓰면 직접 고르지 않아도 됩니다. contexa init은 앱이 SecurityFilterChain을 이미 선언했으면 SANDBOX를, 선언하지 않았으면 FULL을 고릅니다. 파일을 바꾸기 전에 고른 방식을 먼저 보여 줍니다. CLI는 contexa.bridge.ownership을 적지 않으므로 인증 소유권은 모드를 따릅니다. 다르게 하려면 --ownership host|contexa 옵션을 줍니다(CLI가 고르는 방법).

두 모드에서 무엇이 같고 무엇이 달라지는지는 기존 Spring Security 앱에 붙이기의 표에 있습니다.

채팅 모델이나 벡터 저장소가 없으면 판정이 나오지 않습니다. CONTEXA가 판정을 만들지 못하고, 보호된 요청은 모두 분석 대기(PENDING_ANALYSIS) 상태로 남습니다. 앱은 오류 없이 기동하므로 놓치기 쉽습니다. 기동 로그에서 [ContexaCapability]로 시작하는 기능 진단 줄을 찾으면 빠진 것이 나옵니다(켜졌는지 확인하기). 일부러 판정 없이 쓰려면 운영 모드를 끔(contexa.security.zerotrust.mode=DISABLED)으로 둡니다.

기동이 멈추거나 CONTEXA 없이 기동할 때

준비물이 빠졌을 때 CONTEXA는 세 가지 중 하나로 반응합니다. 어느 쪽인지는 콘솔 출력이나 기동 로그에 나옵니다.

  • 기동이 거부됩니다. Spring Boot 4.x, Spring Security 없음, WebFlux나 AOT 처리, 비어 있는 contexa.datasource.url(또는 앱 DB와 같은 주소), Redis 라이브러리 없이 쓴 distributed 모드, FULL에서 모든 요청을 받는 앱의 보안 체인이 해당합니다. 콘솔에 원인(Description)과 고칠 방법(Action)이 함께 출력됩니다.
  • 앱은 기동하고 CONTEXA만 꺼집니다. 앱이 로그인을 맡는 SANDBOX에서 CONTEXA의 DB나 Redis에 문제가 있으면 CONTEXA가 5초 동안 다시 시도한 뒤 포기합니다. 문제는 다음 중 하나입니다.
    • CONTEXA의 DB에 접속할 수 없습니다.
    • DB 계정이 필요한 확장(예: vector)을 만들 수 없습니다.
    • distributed 모드의 Redis에 접속할 수 없습니다.
    이때 앱은 CONTEXA를 넣기 전과 같게 동작하고, 로그에 ERROR 줄(Contexa's database cannot be used 또는 Contexa's Redis cannot be reached)이 남습니다. 문제를 고친 뒤 앱을 다시 시작합니다. CONTEXA가 로그인을 맡는 FULL에서는 CONTEXA 없이 로그인할 수 없으므로, DB 문제가 있으면 기동이 실패합니다.
  • 기동은 되지만 판정이 나오지 않습니다. 채팅 모델이나 벡터 저장소가 없을 때입니다. 위 경고의 기능 진단 줄로 확인합니다.

의존성 좌표

릴리스된 판은 Maven Central의 ai.ctxa 그룹에 올라 있습니다. 앱이 선언하는 CONTEXA 의존성은 스타터 하나입니다. 앞에서 설명한 대로 spring-boot-starter-security를 함께 선언합니다. 저장소는 mavenCentral()만 있으면 됩니다. AI 공급자 스타터와 PgVector 스타터는 아래 선언에 들어 있지 않으므로 따로 추가합니다(다음 표 참고).

implementation("ai.ctxa:spring-boot-starter-contexa:0.1.1")
implementation("org.springframework.boot:spring-boot-starter-security")
<dependency>
    <groupId>ai.ctxa</groupId>
    <artifactId>spring-boot-starter-contexa</artifactId>
    <version>0.1.1</version>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>

스타터가 가져오는 것과 가져오지 않는 것

스타터를 추가하면 아래 표에서 "예"인 것만 앱에 들어옵니다. "아니오"인 것은 앱이 필요에 따라 직접 추가합니다.

무엇스타터에 들어 있나메모
CONTEXA 모듈 다섯(common · core · identity · iam · autoconfigure)예모듈이 클래스패스에 들어와도 실제로 켜지는 기능은 켜짐 조건과 설정이 정합니다.
OAuth2 리소스 서버 · 클라이언트, Spring Authorization Server예Spring Authorization Server는 1.5.1 판으로 고정됩니다.
Spring Security(spring-boot-starter-security)아니오일부러 뺐습니다. Spring Boot는 이것이 클래스패스에 있으면 앱을 보호하기 시작하므로, 스타터에 넣으면 스타터만 추가해도 앱이 바뀝니다(빌드가 이를 검사합니다). @EnableAISecurity로 CONTEXA를 켤 때 앱이 직접 선언합니다. contexa init은 자동으로 추가합니다.
Spring AI · Spring Statemachine BOM예(판 관리만)판을 맞추는 목록(BOM)만 들어옵니다. Spring AI BOM은 1.1.8, Spring Statemachine BOM은 4.0.0입니다.
Spring AI 공급자 스타터(OpenAI · Anthropic · Ollama)아니오어느 AI 공급자를 쓸지는 앱이 고르고 직접 추가합니다.
PgVector 스타터(spring-ai-starter-vector-store-pgvector)아니오일부러 뺐습니다. 이 스타터의 자동 설정은 CONTEXA를 켜지 않은 앱에서도 돌기 때문에, 의존성만 넣은 앱이 바뀌지 않도록 앱이 직접 추가하게 했습니다.
Redis(spring-boot-starter-data-redis) · Redisson · Kafka(spring-kafka)아니오distributed 모드로 쓸 때 앱이 추가합니다(필요한 목록은 인프라 모드 표에 있습니다).

의존성만 넣었을 때

  • 메인 클래스에 @EnableAISecurity가 없으면 CONTEXA의 자동 설정이 하나도 적용되지 않습니다. CONTEXA의 필터, 인증 제공자, DB 표가 만들어지지 않습니다.
  • 스타터는 Spring Security를 가져오지 않습니다. 그래서 Spring Security를 쓰지 않던 앱은 그대로이고, 보안 체인이 생기지 않으며, 로그인을 요구받는 요청도 없습니다.
  • CONTEXA의 DB 표는 CONTEXA가 켜진 앱이 기동할 때 전용 DB에 만들고 검사합니다. 빈 DB에는 표를 새로 만들고, 표가 일부만 있는 DB는 기동을 거부합니다. CLI는 표를 만들지 않으므로 설치할 때 표를 따로 준비하지 않습니다.

인프라 모드: 상태를 어디에 저장하나

contexa.infrastructure.mode는 CONTEXA가 상태를 어디에 저장할지 정합니다. 상태는 사용자별 현재 판정과, CONTEXA가 쌓은 학습 내용입니다. 값은 standalone(기본)과 distributed이고 대소문자는 가리지 않습니다. standalone은 앱 프로세스의 메모리에 저장하므로 Redis나 Kafka가 필요 없지만, 재시작하면 상태가 사라집니다. 개발과 서버 한 대 운영에 맞습니다. distributed는 Redis와 Kafka를 써서 여러 인스턴스가 같은 상태를 보고, 재시작한 뒤에도 학습을 이어 갑니다.

무엇standalone(기본)distributed
사용자별 현재 판정(사용자 판정 저장소)메모리Redis
학습 상태: 행위 기준선(사용자별 행동 패턴 기록), 맥락 기록 등메모리(재시작하면 사라짐)Redis
보안 사건 전달(분석할 이벤트)메모리(같은 프로세스 안에서 바로 넘김)Kafka
차단 신호 전파(차단(BLOCK) 판정이 나면 응답을 보내는 중인 요청을 끊는 신호)메모리Redisson
MFA 세션(추가 인증 진행 상태)HTTP 세션Redis
앱이 넣을 의존성없음spring-boot-starter-data-redis, org.redisson:redisson, spring-statemachine-data-redis(이 셋이 없으면 기동이 거부됩니다). Kafka로 사건을 전달하려면 spring-kafka도 넣습니다. Redis · Kafka 연결 설정도 함께 적습니다.
기동 로그WARN 두 줄: 학습 상태가 메모리에 있어 재시작하면 사라진다는 줄, 진행 중인 판정이 메모리에 있어 재시작하면 사라진다는 줄(판정을 분석하는 운영 모드인 SHADOW · ENFORCE일 때만)없음

standalone에서는 CONTEXA가 Redis와 Kafka를 연결하지 않습니다. 빼는 것은 CONTEXA 자신의 Redis · Kafka 자동 설정뿐이고, Spring Boot · Redisson · Spring Kafka의 Redis · Kafka 자동 설정은 빼지 않습니다. 그래서 앱의 Redis · Kafka 연결은 CONTEXA가 없을 때와 같습니다. 여러 인스턴스로 운영하거나 재시작한 뒤에도 학습을 이어 가려면 distributed를 씁니다(분산 배포로 넘어가기).

모듈 구성

앱이 선언하는 것은 스타터 하나이고, 모듈을 따로 고를 필요는 없습니다. 실제로 켜지는 기능은 앞에서 본 켜짐 조건과 설정이 정합니다.
