spring-boot-starter-contexa

설치 가이드

내 Spring Boot 앱에 Contexa를 켜고, 첫 판정이 도는지 확인하기까지의 순서입니다. CLI로 한 번에 설치하거나, 의존성 · 전용 DB · 설정을 하나씩 직접 넣을 수 있습니다.

한눈에 보기

설치가 끝나면 앱 안의 Contexa는 세 곳과 연결됩니다. 각 연결을 무엇으로 정하는지가 이 페이지의 대부분입니다.

순서: CLI로 설치 또는 직접 설치 → 기존 로그인과 연결(로그인을 앱이 맡을 때) → 켜졌는지 확인.

CLI로 설치

Contexa CLI는 Spring Boot 3 앱에 Contexa를 붙이고 실행까지 해 줍니다. 로컬 DB와 AI 모델을 준비하고, 프로젝트를 바꾸고, 의존성을 받을 수 있는지 확인한 뒤, 앱을 바로 실행해 확인할 수 있게 합니다. 미리 빌드된 실행 파일은 Linux x64, macOS Apple Silicon(arm64), Windows x64용이 있습니다.

CLI 설치

# Linux · macOS
curl -fsSL https://install.ctxa.ai | sh
# Windows PowerShell
irm https://install.ctxa.ai/install.ps1 | iex

설치 스크립트는 서명된 릴리스와 실행 파일의 SHA-256을 확인한 뒤에야 파일을 바꾸고, 끝나면 다음 단계를 알려 줍니다. 지금 터미널이 새 명령을 아직 모르면 바로 쓸 수 있게 하는 한 줄도 알려 주며, 새 터미널은 따로 할 일이 없습니다.

contexa init이 하는 일

cd your-spring-project
contexa init

프로젝트가 아직 없나요? 빈 폴더에서 contexa init을 실행하면 Contexa와 샘플 로그인 계정이 들어간 작은 Spring Boot 3.5 앱을 만들어 줍니다(start.spring.io는 이제 Contexa가 아직 지원하지 않는 Spring Boot 4 프로젝트만 만듭니다).

  1. 바꾸기 전 점검: Spring Boot 3.5.x(3.4 이하나 4.x면 아무것도 바꾸지 않고 멈춤), Java 17 이상, @SpringBootApplication 클래스, 로컬 서비스를 위한 Docker 또는 Ollama를 확인합니다. 빠진 것이 있으면 해결 방법과 함께 알려 줍니다.
  2. 질문 하나: AI 모델 공급자를 고릅니다. Ollama(내 PC에서 실행, API 키 불필요, 기본값), OpenAI, Anthropic 중 하나입니다. 그다음 로그인을 누가 맡을지(아래)를 포함해 바꿀 내용을 모두 보여 주고 진행할지 묻습니다.
  3. 내 프로젝트들이 함께 쓰는 로컬 서비스: Docker로 pgvector PostgreSQL을 띄웁니다(컨테이너 contexa-local-postgres, 55432 같은 빈 포트, 127.0.0.1에만 바인딩). 프로젝트마다 전용 데이터베이스를 만듭니다. Ollama는 이미 실행 중인 것을 쓰고, 없으면 Docker로 띄우며, 모델 qwen3:8b와 mxbai-embed-large는 한 번만 내려받습니다. Contexa의 일회용 코드를 받는 로컬 메일함(Mailpit)도 두 소유 방식 모두 띄웁니다. Contexa가 로그인을 맡으면 로그인 2단계 코드를, 앱이 로그인을 맡으면 CHALLENGE 뒤 추가 확인 코드를 받습니다. CLI가 spring.mail.*을 이 메일함으로 맞춥니다. 기본 포트에서 이미 쓰고 있는 PostgreSQL이나 Ollama는 건드리지 않습니다.
  4. 빌드 파일: starter, spring-boot-starter-security, Spring AI BOM(1.1.8), 모델 스타터, PgVector 스타터를 추가합니다(Maven, Gradle Groovy, Kotlin DSL, 다중 모듈 빌드 모두). 이미 있는 의존성은 그대로 둡니다.
  5. 메인 클래스: 앱이 SecurityFilterChain을 선언하고 있으면(또는 --ownership host를 주면) 속성 없는 @EnableAISecurity를 붙입니다(로그인은 앱이 계속 담당하므로 기존 로그인 연결의 두 가지를 해 주세요. Spring Boot 기본 계정으로 로그인하던 앱이면 그 계정 user를 유지하고 비밀번호를 한 번 만들어 프로젝트 밖에 보관합니다. 기본 계정 참고). 그렇지 않으면(또는 --ownership contexa를 주면) @EnableAISecurity(mode = SecurityMode.FULL)을 붙여 Contexa가 로그인을 제공합니다.
  6. 설정: Contexa 설정을 src/main/resources/config/application.yml에 씁니다. Spring Boot가 이 위치를 스스로 읽으므로 앱의 application.yml과 application.properties는 그대로이고, 앱이 이미 설정한 키는 쓰지 않습니다. 내용은 전용 데이터베이스(contexa.datasource.*, 각 값은 CONTEXA_DB_URL, CONTEXA_DB_USERNAME, CONTEXA_DB_PASSWORD로 덮어씀), 앱에 자체 데이터베이스가 없을 때만 true로 쓰는 contexa.datasource.isolation.contexa-owned-application, SHADOW 집행 모드, 모델 선택(contexa.llm.*), OpenAI 임베딩을 쓸 때는 임베딩 모델 text-embedding-3-small(spring.ai.openai.embedding.options.model, 1536차원)입니다. 앱이 그 폴더에 자기 설정 파일을 이미 두고 있으면 설정은 application-contexa.yml에 쓰고, 그 파일에 spring.config.import 한 줄을 넣습니다.
  7. 의존성 확인: 프로젝트의 Gradle 또는 Maven 래퍼로 의존성을 해석해 봅니다. 받을 수 없으면 프로젝트 변경을 모두 되돌리고 이유를 보여 줍니다.
  8. 실행 확인: 앱을 바로 실행해 볼지 묻고, 뜨면 주소를, 멈추면 이유를 알려 줍니다.

두 소유 방식 모두(예제 앱이거나 설정에 contexa.iam.seed.admin.*이 이미 있으면 제외) contexa init이 관리 콘솔 계정 admin의 비밀번호를 만들어 프로젝트 밖 ~/.contexa/credentials.properties에 보관하고 마지막에 보여 줍니다. 계정은 앱이 처음 시작할 때 Contexa가 만듭니다(첫 기동). 로그인을 앱이 맡으면 완료 화면은 이 순서로 안내합니다. 앱이 원래 쓰는 방식(또는 Spring Boot 기본 사용자)으로 로그인하고, 관리 콘솔 /contexa/admin을 연 뒤, 앱 계정이 아닌 Contexa 관리자 admin으로 로그인합니다.

OpenAI와 Anthropic API 키는 OPENAI_API_KEY, ANTHROPIC_API_KEY에서 읽거나, 물어본 뒤 프로젝트 밖 ~/.contexa/credentials.properties에 보관합니다. contexa init은 다시 실행해도 안전합니다. 이미 갖춰진 것은 그대로 두고 빠진 것만 채웁니다.

init 옵션뜻
--provider ollama|openai|anthropic묻지 않고 AI 모델 공급자를 정함(기본 ollama)
--ownership host|contexa로그인을 누가 맡을지: host(앱이 계속 담당) 또는 contexa(Contexa가 제공). 주지 않으면 앱의 SecurityFilterChain 유무로 정함(아래)
--yes묻지 않고 기본값으로 진행(스크립트·CI용)
--dir <path>프로젝트 폴더(기본: 현재 폴더)
--db-url <jdbc-url>로컬 DB 대신 이미 있는 pgvector PostgreSQL 사용. 비밀번호는 CONTEXA_DB_PASSWORD에서 읽음
--db-username <name>--db-url의 사용자(기본 contexa)
--lang en|koCLI 언어(모든 명령에 적용, CONTEXA_LANG도 가능)

배포하기 전에

  • 로컬 데이터베이스와 그 비밀번호 contexa는 내 PC용입니다. 실제 데이터베이스는 CONTEXA_DB_URL, CONTEXA_DB_USERNAME, CONTEXA_DB_PASSWORD로 지정하세요.
  • 샘플 계정은 빈 폴더에서 만든 예제 앱에만 있습니다(contexa.iam.seed.accounts.enabled=true). 배포에서는 절대 켜지 마세요. 관리 콘솔 비밀번호는 내 PC의 ~/.contexa/credentials.properties에만 있으므로 배포 서버에서는 그 계정이 만들어지지 않습니다.
  • Contexa는 SHADOW로 시작합니다. 판단을 기록만 하고 차단하지 않습니다. 판단을 검토한 뒤 ENFORCE로 바꾸세요(모드 바꾸기).

contexa init이 고르는 소유 방식

contexa init은 무엇을 바꾸기 전에 보안 소유 방식 블록을 보여 줍니다. 고른 방식, 판단 근거(앱의 SecurityFilterChain 유무 또는 직접 준 --ownership), 누가 무엇을 맡는지, 다른 방식으로 바꾸는 명령이 들어 있습니다.

무엇기존 시스템(SANDBOX · HOST_OWNED)신규 시스템(FULL · CONTEXA_OWNED)
이럴 때 고름앱에 SecurityFilterChain이 있거나 --ownership host앱에 체인이 없거나 --ownership contexa
로그인 · 세션 · 쿠키 · URL 권한앱이 지금처럼 담당(Contexa는 누가 로그인했는지 읽기만 함)Contexa(로그인 화면 · 패스키 · 일회용 코드)
위험 판정과 모든 경로의 집행(차단 화면 · 추가 확인 · 에이전트 관문)ContexaContexa, 똑같음
CHALLENGE가 나오면Contexa의 추가 확인 /contexa/step-up(패스키 또는 메일 일회용 코드). 앱의 로그인과 세션은 그대로Contexa MFA
관리 콘솔 /contexa/admin앱 사용자와 별개인 Contexa 관리자 계정으로 Contexa가 보호Contexa 관리자 계정

자동 판정이 맞지 않으면 --ownership host|contexa로 정합니다. 예를 들어 앱이 Spring Security 없이 자체 로그인(필터 · 인터셉터 · 세션)을 쓰는 경우입니다. 다음 두 경우에는 블록에 경고가 함께 나옵니다.

  • 체인이 있는 앱에 --ownership contexa: 로그인을 Contexa가 맡으므로, 자기 SecurityFilterChain을 선언한 앱은 기동하지 않습니다. 기동이 거부되고 그 체인이 메시지에 나옵니다. 그 체인을 지우거나, --ownership host로 앱 로그인을 지키세요.
  • 체인이 없는 앱에 --ownership host: Spring Boot 기본 보안이 모든 요청에 로그인을 요구합니다. 지금 접근 규칙을 지키려면 체인을 하나 선언하세요(예: anyRequest().permitAll()). 관리 콘솔은 Contexa가 따로 보호합니다.

로컬 메일함(Mailpit)은 두 방식 모두 준비하므로, 메일 서버가 없어도 일회용 코드를 받을 수 있습니다.

처음 로그인

사용자 계정이 하나도 없는 DB로 처음 기동하면 기본 계정 다섯 개(admin · manager · developer · user · finance, 비밀번호 모두 1111)가 들어가고, 기동 로그에 Sample accounts were added ...(WARN)가 남습니다. /contexa/admin/login에서 admin / 1111로 로그인한 뒤, 콘솔 머리의 "비밀번호 변경"에서 바로 바꾸세요. contexa.iam.seed.admin.password로 관리자 비밀번호를 정했거나 contexa.iam.seed.accounts.enabled=false이면 기본 계정을 넣지 않습니다. 계정이 이미 있는 DB에서는 아무것도 넣지 않고, 그 사실을 기동 로그(INFO)에 남깁니다.

일회용 코드 받기: 개발과 운영

admin 같은 계정은 비밀번호 다음에 일회용 코드를 넣어야 로그인이 끝납니다.

  • 개발 · 테스트: local · dev · development · test 프로필로 띄우거나 메일 서버를 설정하지 않으면, 코드가 기동 로그(콘솔)에도 [OTT] Sign-in code for admin <admin@localhost>: ...로 찍힙니다. 그 코드를 넣으면 로그인이 끝나고, 메일 서버가 없거나 응답하지 않아도 로그인은 계속됩니다. CLI가 준비한 로컬 메일함(Mailpit)을 쓰면 같은 코드를 메일로도 받습니다. SMTP는 127.0.0.1:51025(로그인 없음)이고, 받은 메일은 http://127.0.0.1:58025에서 봅니다.
  • 운영: 개발 프로필 없이 띄우고 spring.mail.*에 실제 메일 서버를 넣습니다. 코드는 메일로만 갑니다. 기동이 끝나면 Contexa가 메일 서버에 한 번 접속해 보고, 되면 [Contexa] One-time sign-in codes are mailed through 호스트:포트(INFO), 안 되면 원인과 넣어야 할 설정을 WARN으로 남깁니다.
# 개발: 로컬 메일함(Mailpit)
spring:
  mail:
    host: localhost
    port: 51025
    properties:
      mail:
        smtp:
          auth: false

# 운영: 실제 메일 서버(예: 587 + STARTTLS)
spring:
  mail:
    host: smtp.example.com
    port: 587
    username: ${SPRING_MAIL_USERNAME}
    password: ${SPRING_MAIL_PASSWORD}
    properties:
      mail:
        smtp:
          auth: true
          starttls:
            enable: true

코드를 로그에도 찍을지는 contexa.auth.ott.code-to-console로 정합니다. 정하지 않으면 위 규칙을 따르고, 운영에서 확실히 끄려면 false로 둡니다.

준비물

  • Java 17 이상, Spring Boot 3.5.x(빌드 · 시험 판 3.5.4, 3.4 이하는 앱이 기동하지 않고 4.x는 기동 거부)
  • PostgreSQL과 vector 확장(pgvector). 예: Docker 이미지 pgvector/pgvector:pg16
  • 채팅 모델과 임베딩 모델: OpenAI, 또는 Anthropic(채팅)+OpenAI · Ollama(임베딩), 또는 Ollama

무엇이 왜 필요한지는 설치 개요의 준비물에 있습니다.

직접 설치

아래 다섯 단계를 차례로 합니다. 예시는 로컬 Ollama 기준이고, OpenAI · Anthropic은 3단계에 따로 있습니다.

1단계 · 의존성 넣기

스타터와 함께 Spring Security, 채팅 공급자 스타터 하나 이상, PgVector 스타터를 넣습니다. 스타터는 이들을 가져오지 않습니다. 스타터만으로는 앱이 아무것도 바뀌지 않고, 4단계의 @EnableAISecurity가 보안을 적용하는 결정입니다.

dependencies {
    implementation 'ai.ctxa:spring-boot-starter-contexa:0.1.1'
    implementation 'org.springframework.boot:spring-boot-starter-security'
    implementation platform('org.springframework.ai:spring-ai-bom:1.1.8')
    implementation 'org.springframework.ai:spring-ai-starter-model-ollama'          // 또는 -openai, -anthropic
    implementation 'org.springframework.ai:spring-ai-starter-vector-store-pgvector'
}
<dependencyManagement>

2단계 · 전용 DB 만들기

Contexa는 자기 표를 앱의 DB가 아닌 전용 DB에 둡니다. 계정과 데이터베이스를 만들고 vector 확장을 켭니다.

CREATE USER contexa WITH PASSWORD 'change-me';
CREATE DATABASE contexa OWNER contexa;
\c contexa
CREATE EXTENSION IF NOT EXISTS vector;
  • 표는 첫 기동 때 Contexa가 만듭니다. 앱이 기동할 때 Contexa가 표를 만들고 검증합니다. 그 스키마는 vector 확장 만들기로 시작하므로, 계정에 확장을 만들 권한이 없으면 위처럼 미리 만들어 두세요.
  • 깨끗한 DB를 쓰세요. Contexa 표가 일부만 있는 DB면 아무것도 바꾸지 않고 기동이 멈춥니다.
  • 앱 DB와 같은 주소는 기본으로 막힙니다. 같은 주소를 쓰려면 contexa.datasource.isolation.allow-shared-application-datasource=true와 contexa.datasource.isolation.shared-application-datasource-risk-accepted=true를 둘 다 켜야 하고, prod · production 프로필에서는 켜도 거부됩니다.
  • 벡터 표의 위치: 벡터 표(ctxa_vector_store)는 Contexa가 Contexa 전용 DB(contexaJdbcTemplate)에 직접 만듭니다. Spring AI의 PgVector 스타터는 그 클래스를 가져오는 의존성일 뿐이고, 앱의 기본 DB 연결과 앱의 VectorStore 빈은 쓰이지 않습니다. 그러니 vector 확장은 Contexa 전용 DB에 있으면 됩니다. Contexa는 첫 기동 때 그 확장과 표를 만들도록 기본값(contexa.vectorstore.pgvector.initialize-schema=true)을 둡니다.
  • 앱에 자기 DB 연결이 없다면: 스타터가 JPA를 함께 가져오므로 Spring Boot가 앱의 기본 DB 연결을 만들려고 합니다. Contexa가 로그인을 맡는 FULL이면 Contexa DB가 앱의 기본 DB 연결이 되므로 따로 둘 것이 없습니다. 로그인을 앱이 맡는다면 앱용 DB 주소(spring.datasource.url)를 따로 적으세요.

4단계 · @EnableAISecurity 붙이기

@EnableAISecurity                      // 기본 SANDBOX: 로그인은 앱이 그대로 맡음
@SpringBootApplication
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}

로그인을 Contexa에 맡기려면 @EnableAISecurity(mode = SecurityMode.FULL)을 씁니다. 무엇이 달라지는지는 기존 Spring Security 앱에 붙이기에, 어노테이션 속성 전체는 @EnableAISecurity 참조에 있습니다. 로그인을 앱이 맡는 기본 방식이면 다음 기존 로그인과 연결하기를 꼭 하세요.

5단계 · 보호할 메서드에 @Protectable

@Protectable
@GetMapping("/api/customers")
public List<Customer> getCustomers() { ... }
  • @Protectable(sync = true)이면 그 호출 안에서 판정하고 결과를 바로 적용합니다(응답이 늦어집니다).
  • 판정이 없는 에이전트 요청은 비동기 메서드라도 그 자리에서 판정합니다(에이전트 보안).
  • 속성 전체와 정책 연결은 @Protectable 참조에, 판정이 만들어지는 과정은 판정 엔진에 있습니다.

기존 로그인과 연결하기(로그인을 앱이 맡을 때)

기본(SANDBOX, 인증 소유권 HOST_OWNED)에서 Contexa는 로그인 체인을 만들지 않습니다. 로그인 · 세션 · 쿠키 · 접근 규칙은 앱의 Spring Security가 그대로 맡고, Contexa는 앱의 로그인 결과를 읽기만 합니다(인증 브리지). 그래도 판정은 앱 체인 바로 뒤에서 도는 필터로 모든 경로에서 집행하고, 관리 화면 /contexa/admin/**는 자기 체인과 Contexa 관리자 로그인으로 직접 지킵니다. 그래서 앱이 할 일은 아래 두 가지입니다.

  1. 자기 SecurityFilterChain을 둡니다. 없으면 Spring Boot 기본 보안이 걸려 모든 요청에 로그인을 요구하고, Contexa가 기동 때 WARN 로그로 알립니다. 앱 사용자도 없으면 기동이 거부됩니다.
  2. 로그인한 사용자를 그 체인의 필터에서 SecurityContext에 인증된 Authentication으로 넣습니다. @Protectable 메서드는 이것이 없거나 익명이면 SHADOW · ENFORCE 모드(기본은 ENFORCE)에서 거부합니다. DISABLED · OBSERVE에서는 거부하지 않고, 메서드 정책이 보안 컨텍스트에 담긴 것을 보고 판단합니다. 세션에만 저장된 레거시 사용자 객체는 인증 증거가 되지 않습니다. 사용자를 MVC 인터셉터나 컨트롤러에서 늦게 넣으면 Contexa 필터가 보지 못하므로, 그런 요청은 @Protectable 메서드에서만 집행되고 WARN 로그가 한 번 나옵니다.
@Configuration
public class HostSecurityConfig {

    @Bean
    public SecurityFilterChain hostSecurityFilterChain(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth -> auth
                // 앱 페이지 보호는 기존 규칙과 필터가 계속 맡음
                .anyRequest().permitAll());
        return http.build();
    }
}

이 체인에도 Spring Security 기본 설정(CSRF 보호, 보안 응답 헤더 등)이 적용되므로, 기존 동작과 다른 부분은 앱에 맞게 조정하세요. Contexa의 기동 진단 로그는 체인이 없을 때 anyRequest().permitAll()을 예로 듭니다. 관리 화면은 Contexa 자기 체인이 지키고 Contexa의 사용자용 화면(판정 화면 · 추가 확인 · 에이전트 확인)은 로그인한 사용자에게만 답하므로, Contexa 경로에 대해서는 이렇게 해도 안전합니다. 메서드 보안(@EnableMethodSecurity)은 선택입니다. 켜면 관리 화면 컨트롤러의 @PreAuthorize 검사가 한 겹 더해집니다.

레거시 세션 객체가 있을 때

@EnableAISecurity의 authObjectLocation · authObjectAttribute · authObjectType은 브리지가 사용자 객체를 어디서 먼저 찾을지와 그 속성 이름 · 타입만 알려 줍니다. 로그인을 연결해 주지는 않으므로, 위 2번(인증된 Authentication)은 여전히 필요합니다.

@EnableAISecurity(
    authObjectLocation = AuthObjectLocation.SESSION,   // AUTO(기본) · SESSION · REQUEST_ATTRIBUTE · HEADER
    authObjectAttribute = "loginUser"                  // 레거시 세션 속성 이름
)
@SpringBootApplication
public class LegacyApplication { }

AUTO와 SESSION은 세션 → 요청 속성 → 헤더, REQUEST_ATTRIBUTE는 요청 속성 먼저, HEADER는 헤더 먼저 찾습니다. 세션 · 요청 속성 · 헤더에서 읽은 값은 권한 · 위임 증거로 쓰입니다. 속성의 정본은 @EnableAISecurity 참조에, 세션 객체를 인증 도장의 근거로 삼는 방법 등은 기존 로그인과 연결하기(인증 브리지)에 있습니다.

기능 진단

Contexa는 기동이 끝날 때 판정에 필요한 부품(채팅 모델 llm-runtime, 임베딩 모델 embedding-runtime, 벡터 저장소 rag-vector, 학습 security-learning, 판정 엔진 autonomous-decision, 브리지 bridge)이 다 만들어졌는지 검사합니다. 검사 강도는 contexa.capability.mode가 정합니다.

값동작
AUTO(기본)Contexa 소유 앱이면 FAIL_FAST, 아니면 WARN. Contexa 소유 앱 = contexa.datasource.isolation.contexa-owned-application=true이거나 spring.application.name이 contexa-로 시작하는 앱
WARN빠진 필수 부품을 ERROR 로그로만 알리고 기동은 계속합니다. 앱이 고칠 수 있는 항목(채팅 · 임베딩 모델, 벡터 저장소, 판정 전략)만 보여 줍니다.
FAIL_FAST필수 부품이 빠지면 Contexa required capability check failed.로 기동을 멈춥니다.
STRICT선택 부품까지 모두 로그로 알리고, 필수 부품이 빠지면 멈춥니다.
OFF검사하지 않습니다.

Spring Boot Actuator가 있으면 같은 결과를 엔드포인트 contexacapabilities(GET /actuator/contexacapabilities)로 봅니다. 웹으로 열려면 Spring Boot의 management.endpoints.web.exposure.include에 넣습니다. 엔드포인트를 끄려면 contexa.capability.expose-diagnostics-endpoint: false.

  • 판정 모니터는 지금 로그인한 사용자의 권한에 ROLE_ADMIN이 있어야 열립니다. 로그인을 앱이 맡으면 관리 화면은 앱 사용자와 별개인 Contexa 관리자 계정(Contexa DB에서 ADMIN 역할을 가진 사용자)을 /contexa/admin/login에서 로그인시키고, 앱 사용자는 들어올 수 없습니다. 첫 관리자는 처음 기동할 때 contexa.iam.seed.admin.username · contexa.iam.seed.admin.password · contexa.iam.seed.admin.email 설정으로 Contexa가 만듭니다(비밀번호가 없으면 만들지 않음. contexa init이 비밀번호를 대신 정해 주고, 직접 설정하는 예시는 관리 화면). 콘솔의 로그아웃은 콘솔 로그인만 끝내고 앱 로그인은 유지합니다.
  • 샘플 계정(admin 등 다섯 개, 공용 비밀번호)은 contexa.iam.seed.accounts.enabled: true일 때만 Contexa DB에 들어갑니다(기본 false). 로컬 시험용이니 배포 환경에서는 켜지 마세요. HOST_OWNED에서는 콘솔 전용 폼 /contexa/admin/login에서 로그인합니다. CONTEXA_OWNED(FULL)에서는 이 주소가 Contexa 로그인 화면 /mfa/login으로 이동하고, 비밀번호 뒤에 2단계(메일 코드 또는 패스키)가 필수이므로 메일 서버가 필요합니다.

분산 배포로 넘어가기

여러 인스턴스를 띄우거나 재시작 뒤에도 학습 상태를 이어 가려면 인프라 모드를 distributed로 바꾸고, 앱에 Redis · Redisson · Kafka 의존성과 연결 설정을 넣습니다(Contexa 모듈은 이것들을 가져오지 않습니다).

implementation 'org.springframework.boot:spring-boot-starter-data-redis'
implementation 'org.redisson:redisson'          // 판은 앱이 정함
implementation 'org.springframework.kafka:spring-kafka'
contexa:
  infrastructure:
    mode: distributed
spring:
  data:
    redis:
      host: localhost
      port: 6379
  kafka:
    bootstrap-servers: localhost:9092

판정 저장소 · 학습 상태는 Redis에, 보안 사건은 Kafka에, 차단 신호는 Redisson으로 전파됩니다. 무엇이 바뀌는지는 인프라 모드에 있습니다.
