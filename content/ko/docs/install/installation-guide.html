spring-boot-starter-contexa

설치 가이드

내 Spring Boot 앱에 Contexa를 켜고, 첫 판정이 도는지 확인하기까지의 순서입니다. CLI로 한 번에 설치하거나, 의존성 · 전용 DB · 설정을 하나씩 직접 넣을 수 있습니다.

한눈에 보기

설치가 끝나면 앱 안의 Contexa는 세 곳과 연결됩니다. 각 연결을 무엇으로 정하는지가 이 페이지의 대부분입니다.

순서: CLI로 설치 또는 직접 설치 → 기존 로그인과 연결(로그인을 앱이 맡을 때) → 켜졌는지 확인.

CLI로 설치

Contexa CLI는 앱 프로젝트에 의존성 · 어노테이션 · 설정을 넣어 주는 도구입니다. 미리 빌드된 실행 파일은 Linux x64, macOS Apple Silicon(arm64), Windows x64용이 있습니다.

CLI 설치

# Linux · macOS · Git Bash · WSL
curl -fsSL https://install.ctxa.ai | sh
# Windows PowerShell
irm https://install.ctxa.ai/install.ps1 | iex

설치 스크립트는 실행 파일 옆에 게시된 SHA-256 값으로 내려받은 파일을 검증합니다. 스크립트 대신 contexa-cli 릴리스 페이지에서 실행 파일(예: Windows용 contexa-win-x64.exe)을 직접 받아 PATH에 두어도 됩니다.

contexa init이 하는 일

cd your-spring-project
contexa init --check   # 환경 점검만 하고 끝냄(Java 17 이상, Docker)
contexa init
  1. 질문: 빠른 시작(기본)과 고급 설정 중에 고릅니다. 빠른 시작은 공급자 OpenAI · Anthropic, 집행 모드 SHADOW, 인프라 없음이고, Ollama를 쓸지 한 번 더 묻습니다. 고급 설정은 보안 모드 · 집행 모드 · 공급자 · 분산 인프라를 하나씩 묻습니다.
  2. 빌드 파일: 스타터, Spring AI BOM과 고른 공급자 스타터, PgVector 스타터를 넣습니다. 고르지 않은 공급자 스타터는 지웁니다.
  3. 메인 클래스: @SpringBootApplication이 붙은 클래스에 속성 없는 @EnableAISecurity를 붙입니다(로그인을 앱이 맡는 기본 방식).
  4. application.yml: Contexa 전용 DB(contexa.datasource.*, 기본 주소 jdbc:postgresql://localhost:5432/contexa, 환경 변수 CONTEXA_DB_URL · CONTEXA_DB_USERNAME · CONTEXA_DB_PASSWORD로 바꿈), 집행 모드, 모델 선택(contexa.llm.selection.*), 고른 공급자의 spring.ai.*(키는 환경 변수 OPENAI_API_KEY · ANTHROPIC_API_KEY)를 씁니다.
  5. 백업: 바꾸기 전의 원본을 프로젝트의 contexa/bak/ 아래에 남깁니다.
  6. 인프라(선택): --distributed나 --simulate를 주면 Docker Compose 파일을 프로젝트 밖(운영체제별 Contexa 폴더)에 만들고 PostgreSQL(pgvector) · Redis · Zookeeper · Kafka와 선택한 경우 Ollama를 띄웁니다. 이미지는 pgvector/pgvector:pg16 · redis:7.2-alpine · confluentinc/cp-zookeeper:7.4.0 · confluentinc/cp-kafka:7.4.0 · ollama/ollama:latest, 포트는 5432 · 6379 · 2181 · 9092 · 11434이고 127.0.0.1에만 엽니다(환경 변수 CONTEXA_*_PORT · COMPOSE_BIND_HOST로 바꿈). Ollama를 띄웠으면 채팅 모델(기본 qwen2.5:7b, 환경 변수 OLLAMA_CHAT_MODEL)과 임베딩 모델(mxbai-embed-large, OLLAMA_EMBEDDING_MODEL)을 받습니다. 옵션이 없으면 인프라는 건드리지 않으므로 PostgreSQL은 직접 준비합니다(전용 DB 만들기).
init 옵션뜻
--yes묻지 않고 기본값(빠른 시작)으로 진행. Java · Docker 점검도 건너뜀
--force이미 설치된 프로젝트도 다시 설정
--dir <path>프로젝트 폴더(기본: 현재 폴더)
--include-ollama공급자에 Ollama를 넣음(기본 꺼짐)
--distributed분산 인프라(PostgreSQL · Redis · Zookeeper · Kafka)를 만들고, contexa.infrastructure.mode를 분산으로, Redis · Redisson · Kafka 의존성을 넣음
--no-dockerCompose 파일만 만들고 컨테이너는 띄우지 않음
--simulate연습용 격리 환경. 분산 인프라와 Ollama를 켜고 컨테이너 이름을 ctxa-sim-으로, 포트를 +20000(예: 5432 → 25432)으로 옮김. 집행 모드는 ENFORCE로 씀
--merge / --standalone, --standalone-dir앱의 빌드 파일 · 설정에 직접 넣을지(기본), 따로 만든 폴더(기본 <프로젝트>/contexa)에 둘지
--infra-dir <path>Compose 파일을 둘 폴더
--check환경 점검만 하고 끝냄(실패하면 종료 코드 1)
--lang en|koCLI 화면 언어(모든 명령에 씀)

CLI가 쓴 설정에서 꼭 확인할 것.

  • 기존 앱이면 contexa.datasource.isolation.contexa-owned-application: true 줄을 지우세요. CLI는 이 값을 늘 씁니다. 이 값이면 앱의 기본 DB 연결이 Contexa DB로 바뀔 수 있고(앱이 직접 DataSource 빈을 두지 않았을 때), 기능 진단이 엄격해져 모델 · 벡터 저장소가 빠지면 기동이 멈춥니다(기능 진단).
  • DB 비밀번호는 환경 변수로 바꾸세요. CLI가 쓰는 기본 비밀번호는 로컬 시험용입니다. contexa scan이 기본 비밀번호를 경고합니다.
  • 로그인을 앱이 맡으면 앱 쪽 할 일이 남습니다. CLI가 붙이는 @EnableAISecurity는 기본 방식이므로 기존 로그인과 연결하기의 네 가지를 하세요. 고급 설정에서 SANDBOX를 고르면 끝에 예시 코드가 출력되는데, 그 예시에는 @EnableAISecurity에 없는 속성이 들어 있으니 이 페이지의 예시를 쓰세요.

contexa reset-c(코드) · -i(프로젝트 인프라) · -s(시뮬레이션) · -a(전부). 코드 되돌리기는 contexa/bak/의 원본으로 파일을 덮어쓰고, Contexa 설정(contexa: · spring.ai)과 Java 파일의 @EnableAISecurity를 지웁니다. init 뒤에 직접 고친 내용도 사라집니다. 인프라 되돌리기는 컨테이너와 볼륨을 지웁니다.
contexa simulate up|down|reset|ps|logs--simulate로 만든 ctxa-sim 환경을 켜고 끄고, 볼륨까지 지우고 다시 켜고(reset), 상태 · 로그를 봅니다.
contexa ollama pull채팅 · 임베딩 모델을 받습니다(--chat-model · --embed-model, 환경 변수가 옵션보다 우선).

준비물

  • Java 17 이상, Spring Boot 3.x(빌드 · 시험 판 3.5.4, 4.x는 기동 거부)
  • PostgreSQL과 vector 확장(pgvector). 예: Docker 이미지 pgvector/pgvector:pg16
  • 채팅 모델과 임베딩 모델: OpenAI, 또는 Anthropic(채팅)+OpenAI · Ollama(임베딩), 또는 Ollama

무엇이 왜 필요한지는 설치 개요의 준비물에 있습니다.

직접 설치

아래 다섯 단계를 차례로 합니다. 예시는 로컬 Ollama 기준이고, OpenAI · Anthropic은 3단계에 따로 있습니다.

1단계 · 의존성 넣기

스타터와 함께 채팅 공급자 스타터 하나 이상과 PgVector 스타터를 넣습니다. 스타터는 이 둘을 가져오지 않습니다.

dependencies {
    implementation 'ai.ctxa:spring-boot-starter-contexa:0.1.0'
    implementation platform('org.springframework.ai:spring-ai-bom:1.1.8')
    implementation 'org.springframework.ai:spring-ai-starter-model-ollama'          // 또는 -openai, -anthropic
    implementation 'org.springframework.ai:spring-ai-starter-vector-store-pgvector'
}
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.ai</groupId>
      <artifactId>spring-ai-bom</artifactId>
      <version>1.1.8</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<dependencies>
  <dependency>
    <groupId>ai.ctxa</groupId>
    <artifactId>spring-boot-starter-contexa</artifactId>
    <version>0.1.0</version>
  </dependency>
  <dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-model-ollama</artifactId>
  </dependency>
  <dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-vector-store-pgvector</artifactId>
  </dependency>
</dependencies>

Spring AI BOM 판 1.1.8은 Contexa가 빌드 · 시험한 판이고, 스타터가 내보내는 BOM과 같습니다.

2단계 · 전용 DB 만들기

Contexa는 자기 표를 앱의 DB가 아닌 전용 DB에 둡니다. 계정과 데이터베이스를 만들고 vector 확장을 켭니다.

CREATE USER contexa WITH PASSWORD 'change-me';
CREATE DATABASE contexa OWNER contexa;
\c contexa
CREATE EXTENSION IF NOT EXISTS vector;
  • 표는 첫 기동 때 Contexa가 만듭니다. 앱이 기동할 때 Contexa가 표를 만들고 검증합니다. 그 스키마는 vector 확장 만들기로 시작하므로, 계정에 확장을 만들 권한이 없으면 위처럼 미리 만들어 두세요.
  • 깨끗한 DB를 쓰세요. Contexa 표가 일부만 있는 DB면 아무것도 바꾸지 않고 기동이 멈춥니다.
  • 앱 DB와 같은 주소는 기본으로 막힙니다. 같은 주소를 쓰려면 contexa.datasource.isolation.allow-shared-application-datasource=true와 contexa.datasource.isolation.shared-application-datasource-risk-accepted=true를 둘 다 켜야 하고, prod · production 프로필에서는 켜도 거부됩니다.
  • 벡터 표의 위치: 벡터 표(vector_store)는 Spring AI의 PgVector 스타터가 만들고, 앱의 기본 DB 연결을 씁니다. Contexa의 DB 연결(contexaJdbcTemplate)은 기본 후보가 아니기 때문입니다. 그러니 앱의 기본 DB에도 vector 확장이 있어야 합니다. Contexa는 첫 기동 때 그 확장과 표를 만들도록 기본값(spring.ai.vectorstore.pgvector.initialize-schema=true)을 둡니다.
  • 앱에 자기 DB 연결이 없다면: 스타터가 JPA를 함께 가져오므로 Spring Boot가 앱의 기본 DB 연결을 만들려고 합니다. Contexa가 로그인을 맡는 FULL이면 Contexa DB가 앱의 기본 DB 연결이 되므로 따로 둘 것이 없습니다. 로그인을 앱이 맡는다면 앱용 DB 주소(spring.datasource.url)를 따로 적으세요.

3단계 · 최소 application.yml

spring:
  datasource:                        # 앱의 기본 DB(이미 있으면 그대로 둠)
    url: jdbc:postgresql://localhost:5432/myapp
    username: myapp
    password: ${MYAPP_DB_PASSWORD}

contexa:
  datasource:                        # Contexa 전용 DB(필수)
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
  llm:
    selection:
      chat:
        priority: ollama
      embedding:
        priority: ollama
    chat:
      ollama:
        base-url: http://localhost:11434
        model: qwen3:8b
        keep-alive: 30m
    embedding:
      ollama:
        model: mxbai-embed-large

Ollama에서 두 모델을 미리 받아 둡니다: ollama pull qwen3:8b, ollama pull mxbai-embed-large. 받는 모델 이름은 설정의 model 값과 같아야 합니다.

설정기본값뜻언제 바꾸나
contexa.datasource.url없음Contexa 전용 DB 주소. 비어 있으면 기동이 멈춥니다.늘 적습니다.
contexa.datasource.username · .password · .driver-class-name없음그 DB의 계정 · 비밀번호 · 드라이버계정에 맞게
contexa.datasource.isolation.contexa-owned-applicationfalsetrue면 Contexa가 소유한 앱으로 봅니다: 앱의 기본 DB 연결도 Contexa DB가 되고, 기능 진단이 엄격해집니다. @EnableAISecurity(mode = SecurityMode.FULL)이면 따로 적지 않았을 때 true가 들어갑니다.기존 앱에는 적지 않습니다.
contexa.llm.selection.chat.priorityopenai,anthropic,ollama채팅 모델을 찾는 공급자 순서. 목록의 공급자가 없으면 있는 채팅 모델을 씁니다. 공급자를 하나만 적으면 Spring AI의 spring.ai.model.chat 기본값도 그 공급자로 둡니다.쓸 공급자를 정할 때
contexa.llm.selection.chat.modedynamic-priority위 순서대로 고르기. spring-primary면 Spring의 @Primary 모델. 값은 이 소문자-하이픈 표기 그대로 씁니다.보통 적지 않습니다.
contexa.llm.selection.embedding.priorityopenai임베딩 공급자. 벡터 차원이 고정되므로 하나만(openai 또는 ollama). 그 공급자가 없으면 있는 임베딩 모델을 씁니다.Ollama 임베딩이면 ollama
contexa.llm.chat.ollama.base-url없음적으면 Contexa가 이 Ollama 서버로 채팅 모델과 (같은 서버로) 임베딩 모델을 직접 만듭니다.Ollama를 쓸 때
contexa.llm.chat.ollama.model없음채팅 모델 이름. 비우면 qwen3:8b다른 모델을 쓸 때
contexa.llm.chat.ollama.keep-alive없음모델을 메모리에 둘 시간(Ollama에 그대로 전달, 예: 30m)응답 속도와 메모리를 맞출 때
contexa.llm.embedding.ollama.model없음임베딩 모델 이름. 비우면 mxbai-embed-large다른 모델을 쓸 때
contexa.llm.embedding.ollama.dedicated-runtime-enabledfalsetrue면 임베딩만 다른 Ollama 서버(contexa.llm.embedding.ollama.base-url, 필수)에서 돌립니다.임베딩 서버를 나눌 때
contexa.vectorstore.pgvector.dimensions1024벡터 차원. 임베딩 모델의 차원과 같아야 합니다. 표 만들기(initialize-schema)는 Contexa 기본값으로 이미 켜져 있어 적을 필요가 없습니다.차원이 다른 임베딩 모델을 쓸 때

OpenAI를 쓸 때는 1단계에서 spring-ai-starter-model-openai를 넣고, 키는 Spring AI 설정에 둡니다(contexa.llm 아래에 공급자 키 설정은 없습니다). Contexa는 OpenAI 임베딩 모델의 기본값을 text-embedding-3-small · 1024차원으로 둡니다.

spring:
  ai:
    openai:
      api-key: ${OPENAI_API_KEY}
contexa:
  llm:
    selection:
      chat:
        priority: openai
      embedding:
        priority: openai

Anthropic을 쓸 때는 spring-ai-starter-model-anthropic과 spring.ai.anthropic.api-key를 두고 contexa.llm.selection.chat.priority: anthropic으로 합니다. Anthropic은 임베딩 모델이 없으므로 임베딩은 OpenAI나 Ollama 공급자를 함께 둡니다(contexa.llm.selection.embedding.priority는 openai 또는 ollama).

모델 연결의 모든 설정은 설정 길잡이에 있습니다.

4단계 · @EnableAISecurity 붙이기

@EnableAISecurity                      // 기본 SANDBOX: 로그인은 앱이 그대로 맡음
@SpringBootApplication
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}

로그인을 Contexa에 맡기려면 @EnableAISecurity(mode = SecurityMode.FULL)을 씁니다. 무엇이 달라지는지는 기존 Spring Security 앱에 붙이기에, 어노테이션 속성 전체는 @EnableAISecurity 참조에 있습니다. 로그인을 앱이 맡는 기본 방식이면 다음 기존 로그인과 연결하기를 꼭 하세요.

5단계 · 보호할 메서드에 @Protectable

@Protectable
@GetMapping("/api/customers")
public List<Customer> getCustomers() { ... }
  • @Protectable(sync = true)이면 그 호출 안에서 판정하고 결과를 바로 적용합니다(응답이 늦어집니다).
  • 판정이 없는 에이전트 요청은 비동기 메서드라도 그 자리에서 판정합니다(에이전트 보안).
  • 속성 전체와 정책 연결은 @Protectable 참조에, 판정이 만들어지는 과정은 판정 엔진에 있습니다.

기존 로그인과 연결하기(로그인을 앱이 맡을 때)

기본(SANDBOX, 인증 소유권 HOST_OWNED)에서 Contexa는 보안 체인을 만들지 않습니다. 로그인 · 세션 · 접근 규칙은 앱의 Spring Security가 그대로 맡고, Contexa는 앱의 로그인 결과를 읽기만 합니다(인증 브리지). 그래서 앱이 아래 네 가지를 해야 합니다.

  1. 자기 SecurityFilterChain을 둡니다. 없으면 Spring Boot 기본 보안이 걸려 모든 요청에 로그인을 요구하고, Contexa가 기동 때 ERROR 로그로 알립니다.
  2. 관리 화면 /contexa/admin/**를 ADMIN 역할로 보호합니다. Contexa의 관리 화면 URL 규칙은 Contexa가 만드는 체인 안에만 있고, 이 방식에서는 그 체인이 없습니다.
  3. 메서드 보안(@EnableMethodSecurity)을 켭니다. 관리 화면 컨트롤러 · 서비스의 @PreAuthorize("hasRole('ADMIN')")는 메서드 보안이 켜져야 걸리는데, Contexa는 CONTEXA_OWNED에서만 켭니다.
  4. 로그인한 사용자를 SecurityContext에 인증된 Authentication으로 넣습니다. @Protectable 메서드는 이것이 없거나 익명이면 거부합니다. 세션에만 저장된 레거시 사용자 객체는 인증 증거가 되지 않습니다.
@Configuration
@EnableMethodSecurity
public class HostSecurityConfig {

    @Bean
    public SecurityFilterChain hostSecurityFilterChain(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth -> auth
                // Contexa가 자기 체인에 두는 규칙과 같게: 차단 해제 요청 등 본인용 경로는 로그인만
                .requestMatchers("/contexa/admin/api/aiam/zero-trust/**",
                                 "/contexa/admin/api/aiam/sse/zero-trust/**").authenticated()
                .requestMatchers("/contexa/admin/**").hasRole("ADMIN")
                // 그 밖의 페이지 보호는 기존 레거시 필터가 계속 맡음
                .anyRequest().permitAll());
        return http.build();
    }
}

이 체인에도 Spring Security 기본 설정(CSRF 보호, 보안 응답 헤더 등)이 적용되므로, 기존 동작과 다른 부분은 앱에 맞게 조정하세요. Contexa의 기동 진단 로그는 체인이 없을 때 anyRequest().permitAll()을 예로 들지만, 그것만으로 끝내면 관리 화면이 보호되지 않습니다.

레거시 세션 객체가 있을 때

@EnableAISecurity의 authObjectLocation · authObjectAttribute · authObjectType은 브리지가 사용자 객체를 어디서 먼저 찾을지와 그 속성 이름 · 타입만 알려 줍니다. 로그인을 연결해 주지는 않으므로, 위 4번(인증된 Authentication)은 여전히 필요합니다.

@EnableAISecurity(
    authObjectLocation = AuthObjectLocation.SESSION,   // AUTO(기본) · SESSION · REQUEST_ATTRIBUTE · HEADER
    authObjectAttribute = "loginUser"                  // 레거시 세션 속성 이름
)
@SpringBootApplication
public class LegacyApplication { }

AUTO와 SESSION은 세션 → 요청 속성 → 헤더, REQUEST_ATTRIBUTE는 요청 속성 먼저, HEADER는 헤더 먼저 찾습니다. 세션 · 요청 속성 · 헤더에서 읽은 값은 권한 · 위임 증거로 쓰입니다. 속성의 정본은 @EnableAISecurity 참조에, 세션 객체를 인증 도장의 근거로 삼는 방법 등은 기존 로그인과 연결하기(인증 브리지)에 있습니다.

기능 진단

Contexa는 기동이 끝날 때 판정에 필요한 부품(채팅 모델 llm-runtime, 임베딩 모델 embedding-runtime, 벡터 저장소 rag-vector, 학습 security-learning, 판정 엔진 autonomous-decision, 브리지 bridge)이 다 만들어졌는지 검사합니다. 검사 강도는 contexa.capability.mode가 정합니다.

값동작
AUTO(기본)Contexa 소유 앱이면 FAIL_FAST, 아니면 WARN. Contexa 소유 앱 = contexa.datasource.isolation.contexa-owned-application=true이거나 spring.application.name이 contexa-로 시작하는 앱
WARN빠진 필수 부품을 ERROR 로그로만 알리고 기동은 계속합니다. 앱이 고칠 수 있는 항목(채팅 · 임베딩 모델, 벡터 저장소, 판정 전략)만 보여 줍니다.
FAIL_FAST필수 부품이 빠지면 Contexa required capability check failed.로 기동을 멈춥니다.
STRICT선택 부품까지 모두 로그로 알리고, 필수 부품이 빠지면 멈춥니다.
OFF검사하지 않습니다.

Spring Boot Actuator가 있으면 같은 결과를 엔드포인트 contexacapabilities(GET /actuator/contexacapabilities)로 봅니다. 웹으로 열려면 Spring Boot의 management.endpoints.web.exposure.include에 넣습니다. 엔드포인트를 끄려면 contexa.capability.expose-diagnostics-endpoint: false.

분산 배포로 넘어가기

여러 인스턴스를 띄우거나 재시작 뒤에도 학습 상태를 이어 가려면 인프라 모드를 distributed로 바꾸고, 앱에 Redis · Redisson · Kafka 의존성과 연결 설정을 넣습니다(Contexa 모듈은 이것들을 가져오지 않습니다).

implementation 'org.springframework.boot:spring-boot-starter-data-redis'
implementation 'org.redisson:redisson'          // 판은 앱이 정함
implementation 'org.springframework.kafka:spring-kafka'
contexa:
  infrastructure:
    mode: distributed
spring:
  data:
    redis:
      host: localhost
      port: 6379
  kafka:
    bootstrap-servers: localhost:9092

판정 저장소 · 학습 상태는 Redis에, 보안 사건은 Kafka에, 차단 신호는 Redisson으로 전파됩니다. 무엇이 바뀌는지는 인프라 모드에 있습니다.
