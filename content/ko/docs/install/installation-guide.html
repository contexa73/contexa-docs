spring-boot-starter-contexa

설치 가이드

Spring Boot 앱에 CONTEXA를 설치하고, 첫 판정이 만들어지는 것을 확인하기까지의 절차입니다. 설치 방법은 두 가지입니다. CLI로 설치하면 CLI가 로컬 DB, AI 모델, 프로젝트 설정을 준비합니다. 직접 설치하면 개발자가 의존성, 전용 DB, 설정을 하나씩 추가합니다. 어느 방법이든 마지막에 같은 확인 절차를 따릅니다.

설치 후의 구성과 진행 순서

이 페이지를 끝까지 따르면 앱이 CONTEXA와 함께 기동하고, 보호한 메서드를 호출할 때 첫 판정이 만들어져 관리 화면에 기록됩니다. 판정(Decision)은 AI가 한 사용자의 요청을 분석해 내리는 결론이며, 허용(ALLOW) · 추가 인증(CHALLENGE) · 검토 보류(ESCALATE) · 차단(BLOCK) 중 하나입니다.

설치가 끝나면 앱 안의 CONTEXA는 세 곳과 연결됩니다. 이 페이지에서 정하는 설정은 대부분 이 세 연결에 관한 것입니다.

설치는 다음 순서로 진행합니다.

  1. 준비물 확인: Java, Spring Boot, PostgreSQL(pgvector), AI 모델을 확인합니다(준비물).
  2. 설치: CLI로 설치하거나 직접 설치합니다.
  3. 기존 로그인과 연결: 앱이 로그인을 맡는 기본 SANDBOX에서만 필요합니다(기존 로그인과 연결).
  4. 확인: 기동 로그, 기능 진단, 첫 판정을 차례로 확인합니다(켜졌는지 확인).

설치 방법 선택. 두 방법은 끝났을 때의 상태가 같습니다. 개발 환경에 DB와 AI 모델이 아직 없으면 CLI로 설치합니다. 관리형 DB를 쓰거나 모든 설정을 직접 정해야 하면 직접 설치합니다. 비교는 설치 개요에 있습니다.

로그인을 누가 맡는지에 따라 달라지는 부분이 있습니다. 로그인은 로그인 화면, 세션, 쿠키, URL 접근 규칙을 말합니다. 기본 방식은 앱이 로그인을 계속 맡는 방식입니다. 보안 모드 SANDBOX(어노테이션 mode의 기본값)이며, 이미 로그인 기능이 있는 앱에 맞습니다. CONTEXA에 로그인을 맡기는 방식은 보안 모드 FULL이며, 새로 만드는 시스템에 맞습니다. 설정 contexa.bridge.ownership의 인증 소유권은 이와 다른 설정이고, 적지 않으면 모드를 따릅니다(SANDBOX → HOST_OWNED, FULL → CONTEXA_OWNED). 두 방식의 차이는 기존 Spring Security 앱에 붙이기에 있습니다.

준비물

설치하기 전에 다음 항목을 확인합니다. 각 항목이 필요한 이유는 설치 개요의 준비물에 있습니다.

  • Java와 Spring Boot: Java 17 이상, Spring Boot 3.5.x(빌드 · 시험 판 3.5.4, 3.4 이하는 앱이 기동하지 않고 4.x는 기동 거부). Java 판은 java -version으로, Spring Boot 판은 빌드 파일에서 확인합니다.
  • PostgreSQL: vector 확장(pgvector)이 있는 PostgreSQL입니다. CONTEXA 전용 DB로 씁니다. 예: Docker 이미지 pgvector/pgvector:pg16
  • AI 모델: 판정을 만드는 채팅 모델과 벡터를 만드는 임베딩 모델입니다. OpenAI, 또는 Anthropic(채팅)+OpenAI · Ollama(임베딩), 또는 Ollama 중 하나로 구성합니다.
  • Docker(CLI로 설치할 때만): CLI가 로컬 PostgreSQL과 Ollama를 실행할 때 씁니다. contexa init --db-url로 기존 pgvector PostgreSQL을 지정하면 PostgreSQL용 Docker는 필요하지 않습니다.

CLI로 설치

CONTEXA CLI는 Spring Boot 3 프로젝트에 CONTEXA를 설치하는 명령줄 도구입니다. 한 번의 실행으로 로컬 DB와 AI 모델을 준비하고, 프로젝트를 CONTEXA에 맞게 바꾸고, 의존성을 받을 수 있는지 확인한 뒤, 앱을 실행할지 묻습니다. 미리 빌드된 실행 파일은 Linux x64, macOS Apple Silicon(arm64), Windows x64용이 있습니다.

CLI 설치

운영체제에 맞는 명령을 터미널에서 실행합니다.

# Linux · macOS
curl -fsSL https://install.ctxa.ai | sh
# Windows PowerShell
irm https://install.ctxa.ai/install.ps1 | iex

설치 스크립트는 서명된 릴리스와 실행 파일의 SHA-256 해시를 먼저 검증하고, 검증이 끝난 뒤에 파일을 설치합니다. 설치가 끝나면 다음에 할 일을 출력합니다. 현재 터미널이 새 명령을 아직 인식하지 못하면, 바로 쓸 수 있게 하는 명령 한 줄도 함께 출력합니다. 새 터미널에서는 추가 작업이 필요하지 않습니다.

결과 확인. 설치 스크립트가 오류 없이 끝나고 다음 단계를 출력하면 정상입니다. 터미널에서 contexa 명령을 실행할 수 있어야 다음 절차로 넘어갈 수 있습니다.

결과가 다를 때. contexa 명령을 찾지 못하면 문제 해결의 해당 항목을 봅니다.

contexa init이 하는 일

프로젝트 폴더에서 contexa init을 실행합니다.

cd your-spring-project
contexa init

프로젝트가 아직 없으면 빈 폴더에서 contexa init을 실행합니다. 그러면 CONTEXA와 샘플 로그인 계정이 들어간 작은 Spring Boot 3.5 앱을 만듭니다(start.spring.io는 이제 CONTEXA가 아직 지원하지 않는 Spring Boot 4 프로젝트만 만듭니다).

contexa init은 다음 순서로 진행합니다.

  1. 바꾸기 전 점검: Spring Boot 3.5.x인지(3.4 이하나 4.x면 아무것도 바꾸지 않고 멈춥니다), Java 17 이상인지, @SpringBootApplication 클래스가 있는지, 로컬 서비스에 필요한 Docker 또는 Ollama가 있는지 확인합니다. 빠진 것이 있으면 해결 방법과 함께 출력합니다.
  2. 질문과 변경 내용 확인: AI 모델 공급자를 하나 고릅니다. Ollama(로컬 PC에서 실행, API 키 불필요, 기본값), OpenAI, Anthropic 중 하나입니다. 이어서 로그인을 누가 맡을지(아래)를 포함해 바꿀 내용을 모두 보여 주고, 진행할지 묻습니다.
  3. 로컬 서비스 준비: 로컬 PC의 여러 프로젝트가 함께 쓰는 서비스입니다.
    • PostgreSQL(pgvector): Docker 컨테이너 contexa-local-postgres를 55432 같은 빈 포트에서 실행하고 127.0.0.1에서만 연결을 받습니다. 프로젝트마다 전용 데이터베이스를 만듭니다.
    • Ollama: 이미 실행 중인 Ollama를 쓰고, 없으면 Docker로 실행합니다. 모델 qwen3:8b와 mxbai-embed-large는 한 번만 내려받습니다.
    • 로컬 메일함(Mailpit): CONTEXA가 보내는 일회용 코드를 받는 개발용 메일함입니다. 로그인을 누가 맡든 준비합니다. CONTEXA가 로그인을 맡는 FULL에서는 로그인 2단계 코드를, 앱이 로그인을 맡는 SANDBOX에서는 추가 인증(CHALLENGE) 뒤의 코드를 받고, 관리 화면 로그인의 2단계 코드는 두 모드 모두 이 메일함으로 옵니다. CLI가 spring.mail.*을 이 메일함으로 설정합니다.
    • 기본 포트에서 이미 사용 중인 PostgreSQL이나 Ollama는 변경하지 않습니다.
  4. 빌드 파일: starter, spring-boot-starter-security, Spring AI BOM(1.1.8), 모델 스타터, PgVector 스타터를 추가합니다. Maven, Gradle Groovy, Kotlin DSL, 다중 모듈 빌드를 모두 지원합니다. 이미 있는 의존성은 그대로 둡니다.
  5. 메인 클래스: 보안 모드에 따라 붙이는 어노테이션이 다릅니다(아래 참고).
    • 옵션을 주지 않으면 속성 없는 @EnableAISecurity를 붙입니다(기본 SANDBOX). 로그인은 앱이 계속 맡으므로 로그인한 사용자를 CONTEXA에 알립니다(기존 로그인 연결). Spring Security로 로그인하는 앱은 할 일이 거의 없고, 메일이 토큰에 없으면 메일 공급자 빈 하나를 둡니다. Spring Security를 쓰지 않는 앱은 리졸버 빈 하나를 둡니다. 앱의 SecurityFilterChain이 Spring Boot 기본 계정으로 로그인하던 경우에는 그 계정 user를 유지하고, 비밀번호를 한 번 만들어 프로젝트 밖에 보관합니다(기본 계정 참고).
    • --mode full을 주면 @EnableAISecurity(mode = SecurityMode.FULL)을 붙입니다. 그러면 CONTEXA가 로그인을 제공합니다. CLI가 빈 폴더에 만드는 예제 앱은 자체 로그인이 없으므로 옵션 없이도 FULL을 받습니다.
    • 앱에 이미 있는 @EnableAISecurity는 그 모드 그대로 둡니다.
  6. 설정: CONTEXA 설정을 src/main/resources/config/application.yml에 씁니다. Spring Boot가 이 위치를 자동으로 읽으므로 앱의 application.yml과 application.properties는 바뀌지 않고, 앱이 이미 설정한 키는 쓰지 않습니다. 쓰는 내용은 다음과 같습니다.
    • 전용 데이터베이스(contexa.datasource.*). 각 값은 CONTEXA_DB_URL, CONTEXA_DB_USERNAME, CONTEXA_DB_PASSWORD로 덮어쓸 수 있습니다.
    • contexa.datasource.isolation.contexa-owned-application: 앱에 자체 데이터베이스가 없을 때만 true로 씁니다.
    • SHADOW 운영 모드: 판정을 기록하고 요청은 막지 않는 관찰 모드입니다.
    • 모델 선택(contexa.llm.*)
    • OpenAI 임베딩을 쓸 때는 임베딩 모델 text-embedding-3-small(spring.ai.openai.embedding.options.model, 1536차원)
    앱이 그 폴더에 자기 설정 파일을 이미 두고 있으면 설정은 application-contexa.yml에 쓰고, 그 파일에 spring.config.import 한 줄을 넣습니다.
  7. 의존성 확인: 프로젝트의 Gradle 또는 Maven 래퍼로 의존성을 해석해 봅니다. 받을 수 없으면 프로젝트 변경을 모두 되돌리고 이유를 보여 줍니다.
  8. 실행 확인: 앱을 바로 실행할지 묻습니다. 앱이 뜨면 주소를, 멈추면 이유를 출력합니다.

결과 확인. 마지막 단계에서 앱 주소가 출력되면 설치가 끝난 것입니다. 빌드 파일, 메인 클래스, config/application.yml이 위 내용대로 바뀌었는지 확인한 뒤 켜졌는지 확인으로 넘어갑니다.

결과가 다를 때. 점검이나 의존성 확인에서 멈추면 출력된 원인과 해결 방법을 따릅니다. CLI 오류별 해결은 문제 해결의 CLI 설치 · 초기화 오류에 있습니다. 원인을 고친 뒤 contexa init을 다시 실행합니다. 이미 갖춰진 것은 그대로 두고 빠진 것만 채우므로 다시 실행해도 안전합니다. 변경을 취소하려면 contexa reset을 실행합니다(그 밖의 CLI 명령).

contexa init은 로그인을 누가 맡든 관리 화면 계정 admin의 비밀번호를 만들어, 프로젝트 밖의 ~/.contexa/credentials.properties에 보관하고 마지막 화면에 보여 줍니다. 예제 앱이거나 설정에 contexa.iam.seed.admin.*가 이미 있으면 만들지 않습니다. 계정은 앱이 처음 시작할 때 CONTEXA가 만듭니다(첫 기동). 앱이 로그인을 맡는 SANDBOX이면 완료 화면이 다음 순서로 안내합니다.

  1. 앱이 원래 쓰는 방식(또는 Spring Boot 기본 사용자)으로 로그인합니다.
  2. 관리 콘솔 /contexa/admin을 엽니다.
  3. 앱 계정이 아닌 CONTEXA 관리자 admin으로 로그인합니다.

OpenAI와 Anthropic API 키는 OPENAI_API_KEY, ANTHROPIC_API_KEY에서 읽거나, CLI가 물어본 뒤 프로젝트 밖의 ~/.contexa/credentials.properties에 보관합니다.

자주 쓰는 init 옵션은 다음과 같습니다.

init 옵션뜻
--provider ollama|openai|anthropic묻지 않고 AI 모델 공급자를 정함(기본 ollama)

배포하기 전에

  • 로컬 데이터베이스와 그 비밀번호 contexa는 로컬 PC용입니다. 운영 환경에서는 실제 데이터베이스를 CONTEXA_DB_URL, CONTEXA_DB_USERNAME, CONTEXA_DB_PASSWORD로 지정합니다.
  • 샘플 계정은 로컬 시험용입니다. contexa.iam.seed.accounts.enabled를 정하지 않으면 계정이 없는 DB에 기본으로 만들어지므로, 배포 환경에서는 false로 끄거나 관리자 비밀번호(contexa.iam.seed.admin.password)를 정해야 합니다. 관리 콘솔 비밀번호는 로컬 PC의 ~/.contexa/credentials.properties에만 있으므로 배포 서버에서는 그 계정이 만들어지지 않습니다.
  • CONTEXA는 SHADOW로 시작합니다. 판정을 기록만 하고 차단하지 않습니다. 판정을 검토한 뒤 ENFORCE로 바꿉니다(모드 바꾸기).

contexa init이 고르는 보안 모드

보안 모드는 CONTEXA의 보안 설정이 앱에 무엇을 하는지를 정합니다. 로그인 화면 · 세션 · 쿠키 · 보안 설정은 SANDBOX에서는 앱의 것으로 남고, FULL에서는 CONTEXA가 맡습니다. 두 모드 모두 CONTEXA의 기능을 모두 씁니다. contexa init은 무엇을 바꾸기 전에 보안 모드 블록을 보여 줍니다. 이 블록에는 고른 모드, 선택 근거(기본값, 직접 준 --mode, 예제 앱, 앱에 이미 있는 @EnableAISecurity), 누가 무엇을 맡는지, 다른 모드로 바꾸는 명령이 들어 있습니다.

CLI는 인증 소유권(contexa.bridge.ownership)을 적지 않습니다. 적지 않으면 소유권은 모드를 따르고(SANDBOX는 HOST_OWNED, FULL은 CONTEXA_OWNED), 앱과 CONTEXA가 같은 종류의 구성 요소(UserDetailsService, JwtDecoder 등)를 함께 가져올 때 어느 쪽을 쓸지만 정하며 기능을 끄지 않습니다. --ownership host|contexa는 --mode sandbox|full의 옛 이름으로 계속 받습니다.

다음 세 경우에는 블록에 경고가 함께 나옵니다.

  • 체인이 있는 앱에 --mode full: FULL에서는 CONTEXA의 주 체인이 모든 요청을 받으므로, 앱 체인도 모든 요청을 받으면 기동이 거부되고 그 체인이 메시지에 나옵니다. 앱 체인을 http.securityMatcher(...)로 맡을 경로만 좁히면 그 경로는 앱 체인이 먼저 맡고 함께 기동합니다. 앱 체인을 주 보안으로 두려면 기본 SANDBOX로 앱 로그인을 유지합니다.
  • 앱에 이미 있는 @EnableAISecurity와 다른 --mode: CLI는 있는 어노테이션을 바꾸지 않습니다. 모드를 바꾸려면 앱 클래스에서 그 mode를 직접 고칩니다.
  • 체인이 없는 앱에 기본 SANDBOX: 앱에 사용자(UserDetailsService 등)가 있으면 Spring Boot 기본 보안이 모든 요청에 로그인을 요구합니다. 앱에 사용자도 없으면 CONTEXA가 모든 요청을 허용하는 격리 체인을 두어 지금의 접근이 그대로 유지됩니다. 사용자가 있는 앱에서 지금의 접근 규칙을 유지하려면 체인을 하나 선언합니다(예: anyRequest().permitAll()). 관리 콘솔은 CONTEXA가 따로 보호합니다. Spring Security를 쓰지 않는 앱은 체인을 선언하지 않고, 로그인한 사용자를 리졸버로 알립니다(기존 로그인과 연결하기).

로컬 메일함(Mailpit)은 두 방식 모두 준비하므로, 메일 서버가 없어도 일회용 코드를 받을 수 있습니다.

직접 설치

아래 다섯 단계를 차례로 수행합니다. 단계마다 하는 일, 확인할 결과, 결과가 다를 때 볼 곳을 적었습니다. 예시는 로컬 Ollama 기준이고, OpenAI · Anthropic은 3단계에 따로 있습니다.

1단계 · 의존성 넣기

빌드 파일에 다음 네 가지를 추가합니다.

  1. CONTEXA 스타터(ai.ctxa:spring-boot-starter-contexa). CONTEXA 모듈 다섯 개를 가져옵니다.
  2. Spring Security(spring-boot-starter-security)
  3. Spring AI 공급자 스타터 하나 이상. 채팅 모델을 연결합니다.
  4. PgVector 스타터와 Spring AI BOM

결과가 다를 때. ai.ctxa 의존성을 찾지 못하면 저장소에 mavenCentral()이 있는지 확인합니다(문제 해결).

2단계 · 전용 DB 만들기

CONTEXA는 자기 표를 앱의 DB가 아니라 전용 DB에 둡니다. 전용 DB에는 사용자 · 역할 · 정책, 판정 기록, 감사 기록, 시스템 설정이 들어가고, 벡터 저장소도 여기에 만들어집니다. PostgreSQL 관리자 계정으로 계정과 데이터베이스를 만들고 vector 확장을 켭니다.

CREATE USER contexa WITH PASSWORD 'change-me';
CREATE DATABASE contexa OWNER contexa;
\c contexa
CREATE EXTENSION IF NOT EXISTS vector;

전용 DB에 대해 다음 사항을 알아야 합니다.

  • 표는 첫 기동 때 CONTEXA가 만듭니다. 앱이 기동할 때 CONTEXA가 표를 만들고 검증하므로 표를 직접 만들 필요가 없습니다. 그 스키마는 vector 확장 만들기로 시작하므로, 계정에 확장을 만들 권한이 없으면 위 SQL처럼 미리 만듭니다.
  • 깨끗한 DB를 씁니다. CONTEXA 표가 일부만 있는 DB면 아무것도 바꾸지 않고 기동이 멈춥니다.
  • 앱 DB와 같은 주소는 기본으로 막힙니다. 같은 주소를 쓰려면 contexa.datasource.isolation.allow-shared-application-datasource=true와 contexa.datasource.isolation.shared-application-datasource-risk-accepted=true를 둘 다 켜야 합니다. prod · production 프로필에서는 켜도 거부됩니다.
  • 벡터 표의 위치: 벡터 표(ctxa_vector_store)는 CONTEXA가 CONTEXA 전용 DB(contexaJdbcTemplate)에 직접 만듭니다. Spring AI의 PgVector 스타터는 그 클래스를 가져오는 의존성일 뿐이고, 앱의 기본 DB 연결과 앱의 VectorStore 빈은 쓰이지 않습니다. 그러므로 vector 확장은 CONTEXA 전용 DB에 있으면 됩니다. CONTEXA는 첫 기동 때 그 확장과 표를 만들도록 기본값(contexa.vectorstore.pgvector.initialize-schema=true)을 둡니다.
  • 앱에 자기 DB 연결이 없다면: 스타터가 JPA를 함께 가져오므로 Spring Boot가 앱의 기본 DB 연결을 만들려고 합니다. CONTEXA가 로그인을 맡는 FULL이면 CONTEXA DB가 앱의 기본 DB 연결이 되므로 따로 할 일이 없습니다. 앱이 로그인을 맡는 SANDBOX에서는 앱용 DB 주소(spring.datasource.url)를 따로 적거나, CONTEXA DB를 앱 DB로도 쓰도록 contexa.datasource.isolation.contexa-owned-application: true를 적습니다.

결과 확인. SQL의 마지막 명령이 오류 없이 끝나면 준비가 끝난 것입니다. 이 시점에는 CONTEXA 표가 없어도 정상입니다. 표는 4단계 뒤에 앱을 처음 실행할 때 만들어집니다.

결과가 다를 때. 확장 만들기가 실패하면 PostgreSQL에 pgvector가 설치되어 있지 않거나 계정에 확장을 만들 권한이 없는 것입니다(문제 해결).

3단계 · 최소 application.yml

앱의 application.yml에 CONTEXA 전용 DB와 AI 모델을 적습니다. 반드시 적어야 하는 것은 전용 DB 주소(contexa.datasource.url)입니다. AI 모델은 쓰는 공급자에 맞게 정합니다. 아래 예시는 로컬 Ollama 기준입니다.

spring:
  datasource:                        # 앱의 기본 DB(이미 있으면 그대로 둠)
    url: jdbc:postgresql://localhost:5432/myapp
    username: myapp
    password: ${MYAPP_DB_PASSWORD}

contexa:
  datasource:                        # Contexa 전용 DB(필수)
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
  llm:
    selection:
      chat:
        priority: ollama
      embedding:
        priority: ollama
    chat:
      ollama:
        base-url: http://localhost:11434
        model: qwen3:8b
        keep-alive: 30m
    embedding:
      ollama:
        model: mxbai-embed-large

Ollama를 쓰면 두 모델을 먼저 내려받습니다: ollama pull qwen3:8b, ollama pull mxbai-embed-large. 내려받는 모델 이름은 설정의 model 값과 같아야 합니다.

설정 값의 뜻은 다음과 같습니다.

설정기본값뜻언제 바꾸나
contexa.datasource.url없음CONTEXA 전용 DB의 주소입니다. 비어 있으면 기동이 멈춥니다.늘 적습니다.

OpenAI를 쓸 때는 1단계에서 spring-ai-starter-model-openai를 넣고, API 키는 Spring AI 설정에 적습니다(contexa.llm 아래에 공급자 키 설정은 없습니다). CONTEXA는 OpenAI 임베딩 모델을 정하지 않고 앱의 모델을 따릅니다. 모델을 적지 않으면 Spring AI 기본값 text-embedding-ada-002(1536차원)를 씁니다. 다른 모델은 spring.ai.openai.embedding.options.model에 적으며, 벡터 차원은 그 모델을 따릅니다.

spring:
  ai:
    openai:
      api-key: ${OPENAI_API_KEY}
contexa:
  llm:
    selection:
      chat:
        priority: openai
      embedding:
        priority: openai

Anthropic을 쓸 때는 spring-ai-starter-model-anthropic을 넣고 spring.ai.anthropic.api-key를 적은 뒤 contexa.llm.selection.chat.priority: anthropic으로 정합니다. Anthropic은 임베딩 모델이 없으므로 임베딩은 OpenAI나 Ollama 공급자를 함께 둡니다(contexa.llm.selection.embedding.priority는 openai 또는 ollama).

모델 연결의 모든 설정은 설정 길잡이에 있습니다.

처음 설치할 때는 관찰 모드로 시작하는 것을 권장합니다. 운영 모드(contexa.security.zerotrust.mode)를 적지 않으면 적용 모드(ENFORCE)로 동작하므로 AI 판정이 실제 요청에 적용됩니다. 관찰 모드(SHADOW)는 판정을 만들고 기록하지만 요청은 막지 않습니다. CLI로 설치하면 SHADOW로 시작합니다. 직접 설치에서 같은 방식으로 시작하려면 다음 설정을 추가합니다. 결과를 검토한 뒤 적용 모드로 전환하는 방법은 관찰 모드로 안전하게 시작하기에 있습니다.

contexa:
  security:
    zerotrust:
      mode: SHADOW

결과 확인. 이 단계의 설정은 4단계 뒤에 앱을 실행할 때 처음 읽힙니다. Ollama를 쓰면 지금 ollama list로 설정한 두 모델이 내려받아져 있는지 확인합니다.

결과가 다를 때. 앱을 실행했을 때 contexa.datasource.url must be configured for @EnableAISecurity가 나오면 전용 DB 주소가 없는 것입니다(문제 해결). 모델이나 벡터 저장소 오류는 모델 · 벡터 저장소 오류를 봅니다.

4단계 · @EnableAISecurity 붙이기

메인 클래스에 @EnableAISecurity를 붙이면 CONTEXA가 켜집니다. 붙이지 않으면 스타터가 클래스패스에 있어도 CONTEXA의 자동 설정이 하나도 적용되지 않습니다.

@EnableAISecurity                      // 기본 SANDBOX: 로그인은 앱이 그대로 맡음
@SpringBootApplication
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}

로그인을 CONTEXA에 맡기려면 @EnableAISecurity(mode = SecurityMode.FULL)을 씁니다. 무엇이 달라지는지는 기존 Spring Security 앱에 붙이기에, 어노테이션 속성 전체는 @EnableAISecurity 참조에 있습니다. 앱이 로그인을 맡는 기본 SANDBOX이면 다음 절 기존 로그인과 연결하기를 반드시 해야 합니다.

결과 확인. 앱을 실행합니다(./gradlew bootRun 또는 mvn spring-boot:run). 기동 로그에 [IamSeedData] OSS schema provenance verified.가 나오면 CONTEXA가 전용 DB에 연결되어 표가 준비된 것입니다. 첫 기동이면 이 줄 앞에서 CONTEXA가 표를 만듭니다.

결과가 다를 때. 기동이 거부되면 콘솔에 원인(Description)과 고칠 방법(Action)이 함께 출력됩니다. 자주 나는 오류는 처음 기동할 때 자주 나는 오류에 모았습니다.

5단계 · 보호할 메서드에 @Protectable

@Protectable은 AI 판정으로 보호할 메서드를 표시하는 어노테이션입니다. 로그인한 사용자가 이 메서드를 호출하면 CONTEXA가 그 요청을 분석합니다. 어노테이션이 없는 메서드와 URL은 분석하지 않고, 이미 저장된 판정만 적용받습니다.

@Protectable
@GetMapping("/api/customers")
public List<Customer> getCustomers() { ... }
  • @Protectable(sync = true)이면 그 호출 안에서 판정하고 결과를 바로 적용합니다. 응답이 그만큼 늦어집니다.
  • 판정이 없는 에이전트 요청은 비동기 메서드라도 그 자리에서 판정합니다(에이전트 보안).
  • 속성 전체와 정책 연결은 @Protectable 참조에, 판정이 만들어지는 과정은 판정 엔진에 있습니다.

결과 확인. 앱을 다시 실행하고 로그인한 사용자로 이 메서드를 호출하면, 잠시 뒤 관리 화면의 판정 기록에 판정이 나타납니다. 확인 절차는 첫 판정 확인하기에 있습니다.

결과가 다를 때. 판정이 나타나지 않는 원인은 첫 판정 확인하기의 끝에 정리했습니다.

기존 로그인과 연결하기(앱이 로그인을 맡는 SANDBOX)

이 절은 앱이 로그인을 맡는 기본 SANDBOX에서만 필요합니다(인증 소유권과 무관). CONTEXA가 로그인을 맡는 FULL에서는 건너뜁니다. FULL에서는 앱이 모든 요청을 받는 SecurityFilterChain을 선언하면 기동이 거부되고, http.securityMatcher(...)로 좁힌 체인은 CONTEXA 주 체인 앞에서 자기 경로를 맡습니다.

기본 방식에서 CONTEXA는 앱 사용자의 로그인 체인을 만들지 않습니다. 로그인 · 세션 · 쿠키 · 접근 규칙은 앱이 그대로 맡고, CONTEXA는 요청마다 누가 로그인했는지 읽기만 합니다(인증 브리지). 앱이 CONTEXA에 알리는 값은 사용자 하나(ContexaSubject)입니다. 아이디와 메일은 필수이고, 표시 이름 · 권한 · 로그인 방식 같은 나머지는 선택입니다. 메일은 추가 인증(CHALLENGE) 때 일회용 코드를 보내는 주소입니다. 판정은 앱의 필터가 모두 끝난 뒤 실행되는 CONTEXA 필터가 모든 경로에 적용합니다. 관리 화면 /contexa/admin/**는 CONTEXA 자신의 체인과 CONTEXA 관리자 로그인으로 직접 보호합니다. 앱이 할 일은 앱이 로그인하는 방식에 따라 아래 둘 중 하나입니다.

  1. Spring Security로 로그인하는 앱: 자기 SecurityFilterChain에서 지금처럼 로그인합니다(폼 로그인, OAuth2 로그인, Bearer 토큰 등). CONTEXA는 SecurityContext의 인증된 Authentication을 그대로 읽습니다. 아이디는 getName()이고, 메일은 토큰이나 OAuth2 로그인의 email 클레임에서 읽습니다. 폼 로그인의 UserDetails처럼 메일이 없으면 메일 공급자 빈 하나를 둡니다(아래). principal이 UserDetails · 문자열 · OAuth2 사용자 같은 표준 종류가 아니라 앱 고유 객체이면, CONTEXA는 그 필드를 추측하지 않으므로 ContexaSubjectMapper 빈으로 바꿔 줍니다. 체인이 없는데 앱 사용자(UserDetailsService 등)가 있으면 Spring Boot 기본 보안이 걸려 모든 요청이 로그인을 요구하고, CONTEXA가 기동 때 WARN 로그로 알립니다(문제 해결).
  2. Spring Security를 쓰지 않는 앱: 자체 세션 · 토큰 · 필터 · 인터셉터로 로그인하는 앱입니다. 보안 체인은 선언하지 않습니다. 앱에 체인도 사용자도 없으면 CONTEXA가 필터가 하나도 없는 격리 체인을 두어 모든 요청을 그대로 통과시키므로, 지금의 접근과 응답이 유지됩니다(문제 해결). 로그인한 사용자는 ContexaSubjectResolver 빈 하나로 알립니다(아래 예시). 요청마다 도는 자체 인증 필터가 이미 있으면, 그 필터에서 요청 속성 ContexaSubject.REQUEST_ATTRIBUTE에 넣어도 됩니다. Spring Security 의존성은 @EnableAISecurity가 쓰므로 이 앱에도 필요합니다(1단계).

어느 쪽이든 CONTEXA가 사용자를 알아보지 못한 요청이 @Protectable 메서드를 부르면 호출을 거부합니다. 단, 거부하는 것은 SHADOW · ENFORCE 모드(기본은 ENFORCE)일 때뿐이고, DISABLED · OBSERVE에서는 거부하지 않고 메서드 정책이 보안 컨텍스트에 담긴 것을 보고 평가합니다. 사용자를 MVC 인터셉터나 컨트롤러에서 늦게 정하면 CONTEXA 필터가 볼 수 없습니다. 그런 요청에는 @Protectable 메서드에서만 판정이 적용되고, WARN 로그가 한 번 나옵니다. 인터셉터에서 로그인을 확인하는 앱은 그 인터셉터가 읽는 값(세션 속성 등)을 리졸버가 읽게 합니다.

Spring Security로 로그인하는 앱에서 메일이 토큰에 없을 때의 메일 공급자는 다음과 같습니다. 앱이 이미 가진 사용자 조회로 아이디의 메일을 돌려줍니다. 리졸버나 요청 속성으로 알린 사용자에게 메일이 없을 때도 이 빈이 쓰입니다.

@Bean
BridgeUserEmailProvider contexaEmailProvider(EmployeeRepository employees) {
    return userId -> employees.findEmailByLoginId(userId);
}

Spring Security 앱에 사용자는 있는데 체인이 없을 때, 지금의 접근 규칙을 유지하는 가장 단순한 체인은 다음과 같습니다. 앱 페이지의 보호는 기존 규칙과 필터가 계속 맡습니다.

@Configuration
public class HostSecurityConfig {

    @Bean
    public SecurityFilterChain hostSecurityFilterChain(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth -> auth
                // 앱 페이지 보호는 기존 규칙과 필터가 계속 맡음
                .anyRequest().permitAll());
        return http.build();
    }
}

이 체인에도 Spring Security 기본 설정(CSRF 보호, 보안 응답 헤더 등)이 적용되므로, 기존 동작과 다른 부분은 앱에 맞게 조정합니다. 체인이 없을 때 CONTEXA의 기동 진단 로그는 anyRequest().permitAll()을 예로 듭니다. CONTEXA 경로에서는 이 설정도 안전합니다. 관리 화면은 CONTEXA 자기 체인이 지키고, CONTEXA의 사용자용 화면(판정 화면 · 추가 인증 · 에이전트 확인)은 로그인한 사용자에게만 응답하기 때문입니다. 관리 화면 컨트롤러의 @PreAuthorize 검사는 앱이 메서드 보안(@EnableMethodSecurity)을 켜지 않아도 적용됩니다.

Spring Security를 쓰지 않는 앱의 리졸버는 다음과 같습니다. 앱이 이미 가진 로그인 상태(여기서는 앱 자신의 토큰 검증)에서 사용자를 꺼내 돌려주고, 로그인하지 않은 요청에는 빈 값을 돌려줍니다.

@Component
class OwnTokenResolver implements ContexaSubjectResolver {

    private final LegacyTokenVerifier verifier;   // 앱이 이미 쓰는 토큰 검증 코드

    OwnTokenResolver(LegacyTokenVerifier verifier) {
        this.verifier = verifier;
    }

    @Override
    public Optional<ContexaSubject> resolve(ContexaRequestView request) {
        return request.header("Authorization")
                .filter(value -> value.startsWith("Bearer "))
                .flatMap(value -> verifier.verify(value.substring("Bearer ".length())))
                .map(claims -> ContexaSubject.of(claims.userId(), claims.email())
                        .displayName(claims.name())
                        .sessionKey(String.valueOf(claims.loginSeq()))
                        .build());
    }
}
  • CONTEXA는 앱의 필터가 모두 끝난 뒤 요청마다 한 번 리졸버를 부르고, 같은 요청의 포워드 · 인클루드 · 비동기 · 오류 처리에서는 그 결과를 다시 씁니다.
  • 리졸버가 받는 요청 보기(ContexaRequestView)는 읽기 전용입니다. 헤더 · 쿠키 · 요청 속성 · 세션 속성(세션을 만들지 않음) · 컨테이너가 로그인시킨 사용자(remoteUser()) · 경로를 읽을 수 있고, 본문과 파라미터는 읽지 않습니다.
  • sessionKey는 세션이 없는 앱에서 로그인 하나를 가리키는 값입니다. 토큰을 갱신해도 바뀌지 않는 값을 씁니다.
  • 리졸버가 예외를 던지면 CONTEXA가 잡고, 그 요청은 CONTEXA 신원 없이 앱 그대로 진행합니다. 기준(contexa.bridge.resolver.slow-threshold, 기본 100ms)보다 오래 걸린 호출은 로그로 알립니다. 정적 자원처럼 리졸버를 부를 필요가 없는 경로는 contexa.bridge.resolver.exclude-paths(서블릿 경로의 Ant 패턴)로 뺄 수 있습니다. 리졸버 빈이 둘 이상이면 기동하지 않습니다.
  • 앞단 게이트웨이가 넣는 사용자 헤더는, 게이트웨이를 검증하는 앱 자신의 코드를 거친 값만 돌려줍니다. CONTEXA는 헤더를 직접 믿지 않습니다.

요청마다 도는 자체 인증 필터가 이미 있으면, 리졸버 대신 그 필터에서 한 줄로 넣어도 됩니다. 앱의 필터는 모두 CONTEXA 필터보다 앞에서 실행되므로 CONTEXA에 맞춰 필터 순서를 바꿀 필요는 없습니다. 인증 필터를 고칠 수 없어 이 한 줄을 넣는 필터를 따로 두면, 그 필터는 인증 필터 뒤에 둡니다.

request.setAttribute(ContexaSubject.REQUEST_ATTRIBUTE, ContexaSubject.of(userId, email).build());

결과 확인. 로그인한 사용자로 @Protectable 메서드를 한 번 부른 뒤 관리 콘솔의 Zero Trust → 사용자 연동 상태(/contexa/admin/zero-trust/bridge)를 엽니다. 확인 결과에 "성립"이 늘고 확인 경로에 앱의 방식(Spring Security 로그인 · 리졸버 · 요청 속성)이 나오면 연결된 것입니다. 기동 로그에는 아래 두 WARN이 없어야 합니다. 두 줄은 켜졌는지 확인의 로그 표에 있습니다.

  • [Contexa] SANDBOX mode: the application declares users of its own and no SecurityFilterChain ...: Spring Security로 로그인하는 앱이 체인을 선언하지 않았습니다(1번).
  • [Contexa] SANDBOX mode: the application sets the signed-in user after Spring Security's filters ...: 사용자를 MVC 인터셉터나 컨트롤러에서 늦게 정하고 있습니다.

결과가 다를 때. "규칙 위반"이나 "실패"가 늘거나 메일 주소 문제가 기록되면, 같은 화면의 "발생한 문제"에 원인과 권장 조치가 나옵니다. 같은 내용이 ERROR 로그 [Contexa] Bridge: ...로 문제마다 1분에 한 번 남습니다. 모든 요청이 로그인을 요구하면 문제 해결의 해당 항목을, 폼 저장이 403으로 거부되면 CSRF 항목을 봅니다.

세션에 사용자 객체를 두는 앱

Spring Security 없이, 로그인한 사용자 객체를 세션에 직접 저장하는 앱의 리졸버입니다. 리졸버가 세션 속성을 읽어 ContexaSubject로 돌려줍니다. CONTEXA는 앱의 객체를 추측해 읽지 않으므로, 어느 필드가 아이디이고 메일인지는 앱이 정합니다.

@Component
class SessionLoginResolver implements ContexaSubjectResolver {

    @Override
    public Optional<ContexaSubject> resolve(ContexaRequestView request) {
        return request.sessionAttribute("loginUser", LoginUser.class)   // 앱이 로그인 때 세션에 둔 객체
                .map(user -> ContexaSubject.of(user.getLoginId(), user.getEmail())
                        .displayName(user.getName())
                        .authorities(user.getRoles())
                        .authentication(ContexaAuthentication.of("PASSWORD").authenticatedAt(user.getLoginAt()))
                        .build());
    }
}
  • 아이디는 앱의 로그인 아이디처럼 같은 사람을 늘 같은 값으로 가리키는 것을 씁니다. 판정 · 차단 · 사용자 사본이 이 값에 묶입니다.
  • 세션은 읽기만 하고 만들지 않습니다. 로그아웃해서 세션 속성이 사라지면 리졸버가 빈 값을 돌려주므로, CONTEXA의 신원도 앱보다 오래 남지 않습니다. CONTEXA는 앱 세션에 아무것도 쓰지 않습니다.
  • 인터셉터에서 로그인을 확인하는 앱도 같습니다. 인터셉터가 읽는 세션 값을 리졸버가 읽습니다.
  • 로그인 순간을 바로 알리려면, 로그인 성공 자리에서 세션 ID를 바꾼 뒤 ContexaBridge.signedIn(request, subject)를 부릅니다(선택). CONTEXA가 그 자리에서 사용자 사본을 만들고(최대 1초 기다림) 로그인 사실을 기록하므로, 다음 요청부터 그 사용자를 아는 상태로 판정합니다. 로그인 실패와 로그아웃은 ContexaBridge.signInFailed · signedOut으로, 퇴사 · 삭제는 ContexaUsers.delete로 알립니다. 모두 선택이고, 예외를 던지지 않고 결과로 답합니다.

사용자를 읽는 출처의 순서(contexa.bridge.identity-sources), 메일을 읽는 출처(contexa.bridge.email-sources) 같은 세부는 인증 브리지의 설정에 있습니다.

켜졌는지 확인하기

앱을 실행한 뒤 세 가지를 순서대로 확인합니다.

  1. 기동 로그: CONTEXA가 켜졌는지 봅니다.
  2. 기능 진단: 판정에 필요한 부품이 모두 만들어졌는지 봅니다(기능 진단).
  3. 첫 판정: 보호한 메서드를 호출하고, 판정이 관리 화면에 기록되는지 봅니다(첫 판정 확인하기).

앞의 두 확인이 끝나기 전에는 세 번째에서 판정이 나오지 않을 수 있습니다. 앱을 실행하고(./gradlew bootRun) 기동 로그에서 아래 줄을 찾습니다. 정상이면 INFO 줄이 보입니다. WARN이나 ERROR 줄은 해당 행의 안내를 따릅니다.

기능 진단

기능 진단은 CONTEXA가 기동을 마칠 때 판정에 필요한 부품이 모두 만들어졌는지 검사하는 기능입니다. 검사하는 부품은 채팅 모델 llm-runtime, 임베딩 모델 embedding-runtime, 벡터 저장소 rag-vector, 학습 security-learning, 판정 엔진 autonomous-decision, 브리지 bridge입니다. 검사 강도는 contexa.capability.mode가 정합니다.

값동작
AUTO(기본)CONTEXA 소유 앱이면 FAIL_FAST, 아니면 WARN입니다. CONTEXA 소유 앱은 contexa.datasource.isolation.contexa-owned-application=true이거나 spring.application.name이 contexa-로 시작하는 앱입니다.
WARN빠진 필수 부품을 ERROR 로그로만 알리고 기동은 계속합니다. 앱이 고칠 수 있는 항목(채팅 · 임베딩 모델, 벡터 저장소, 판정 전략)만 보여 줍니다.
FAIL_FAST필수 부품이 빠지면 Contexa required capability check failed.로 기동을 멈춥니다.
STRICT선택 부품까지 모두 로그로 알리고, 필수 부품이 빠지면 멈춥니다.
OFF검사하지 않습니다.

Spring Boot Actuator가 있으면 같은 결과를 엔드포인트 contexacapabilities(GET /actuator/contexacapabilities)로 볼 수 있습니다. 웹으로 열려면 Spring Boot의 management.endpoints.web.exposure.include에 넣습니다. 엔드포인트를 끄려면 contexa.capability.expose-diagnostics-endpoint: false를 적습니다.

curl http://localhost:8080/actuator/contexacapabilities

결과 확인. 응답의 mode는 적용 중인 검사 방식이고, capabilities는 부품별 결과입니다. 문제가 없으면 필수 부품의 status가 ACTIVE입니다. DEGRADED · INACTIVE_UNEXPECTED · FAILED는 문제가 있는 상태이며, 그 부품에는 이유(reason)와 빠진 빈(missingBeans)이 함께 나옵니다.

결과가 다를 때. 채팅 모델이나 벡터 저장소가 빠지면 판정이 만들어지지 않고 요청이 분석 대기(PENDING_ANALYSIS)로 남습니다. 원인별 해결은 문제 해결에 있습니다.

처음 로그인

관리 화면에는 CONTEXA 관리자 계정으로 로그인합니다. 이 계정은 앱의 사용자 계정과 별개이며 CONTEXA 전용 DB에 있습니다. 계정은 설치 방법에 따라 다음과 같이 준비됩니다.

  • CLI로 설치한 경우: CLI가 admin의 비밀번호를 만들어 ~/.contexa/credentials.properties에 보관하고 마지막 화면에 보여 줍니다. 그 비밀번호로 로그인합니다. 예제 앱은 아래 샘플 계정을 씁니다.
  • 직접 설치한 경우: 사용자 계정이 하나도 없는 DB로 처음 기동하면 CONTEXA가 샘플 계정 다섯 개(admin · manager · developer · user · finance, 비밀번호 모두 1111)를 넣습니다. 기동 로그에는 Sample accounts were added ...(WARN)가 남습니다. /contexa/admin/login에서 admin / 1111로 로그인한 뒤, 콘솔 머리의 "비밀번호 변경"에서 바로 바꿉니다.

샘플 계정을 넣을지는 설정이 정합니다. contexa.iam.seed.admin.password로 관리자 비밀번호를 정했거나 contexa.iam.seed.accounts.enabled=false이면 샘플 계정을 넣지 않습니다. 계정이 이미 있는 DB에서는 아무것도 넣지 않고, 그 사실을 기동 로그(INFO)에 남깁니다. 운영 환경에서는 공용 비밀번호를 가진 계정이 만들어지지 않도록, 둘 중 하나를 반드시 적습니다.

일회용 코드 받기: 개발과 운영

일회용 코드는 CONTEXA가 사용자의 메일로 보내는 로그인용 코드입니다. 다음 두 경우에 입력합니다.

  • CONTEXA가 로그인을 맡는 FULL에서: 비밀번호 다음의 2단계에서 입력합니다. 패스키로도 확인할 수 있습니다.
  • 앱이 로그인을 맡는 SANDBOX에서: 판정이 추가 인증(CHALLENGE)일 때 CONTEXA의 추가 인증 화면에서 입력합니다. 관리 화면 로그인(/contexa/admin/login)에서도 비밀번호 다음의 2단계에서 입력하며, 패스키로도 확인할 수 있습니다.

코드를 받는 방법은 개발과 운영이 다릅니다.

  • 개발 · 테스트: local · dev · development · test 프로필로 실행하거나 메일 서버를 설정하지 않으면, 코드가 기동 로그(콘솔)에도 [OTT] Sign-in code for admin <admin@localhost>: ...로 출력됩니다. 그 코드를 입력하면 로그인이 끝납니다. 메일 서버가 없거나 응답하지 않아도 로그인은 계속됩니다. CLI가 준비한 로컬 메일함(Mailpit)을 쓰면 같은 코드를 메일로도 받습니다. SMTP는 127.0.0.1:51025(로그인 없음)이고, 받은 메일은 http://127.0.0.1:58025에서 봅니다.
  • 운영: 개발 프로필 없이 실행하고 spring.mail.*에 실제 메일 서버를 넣습니다. 코드는 메일로만 전달됩니다. 기동이 끝나면 CONTEXA가 메일 서버에 한 번 접속해 보고, 접속되면 [Contexa] One-time sign-in codes are mailed through 호스트:포트(INFO)를, 접속되지 않으면 원인과 넣어야 할 설정을 WARN으로 남깁니다.
# 개발: 로컬 메일함(Mailpit)
spring:
  mail:
    host: localhost
    port: 51025
    properties:
      mail:
        smtp:
          auth: false

# 운영: 실제 메일 서버(예: 587 + STARTTLS)
spring:
  mail:
    host: smtp.example.com
    port: 587
    username: ${SPRING_MAIL_USERNAME}
    password: ${SPRING_MAIL_PASSWORD}
    properties:
      mail:
        smtp:
          auth: true
          starttls:
            enable: true

코드를 로그에도 출력할지는 contexa.auth.ott.code-to-console로 정합니다. 정하지 않으면 위 규칙을 따르고, 운영에서 확실히 끄려면 false로 둡니다.

관리 화면(관리 콘솔)은 CONTEXA의 운영 화면입니다. 위에서 정리한 CONTEXA 관리자 계정으로 로그인하고, 아래 화면에서 설치 결과를 확인합니다.

  • 샘플 계정(admin 등 다섯 개, 공용 비밀번호)은 로컬 시험용이므로 운영 환경에서는 넣지 않아야 합니다. 설정 contexa.iam.seed.accounts.enabled: true를 적으면 관리자 비밀번호를 정했어도 사용자 계정이 없는 DB에는 샘플 계정이 들어가고, false를 적으면 들어가지 않습니다. FULL + CONTEXA_OWNED가 아닌 세 조합에서는 콘솔 전용 폼 /contexa/admin/login에서 로그인하고, FULL + CONTEXA_OWNED에서는 이 주소가 CONTEXA 로그인 화면 /mfa/login으로 이동합니다. 어느 쪽이든 비밀번호 뒤에 2단계(메일 코드 또는 패스키)가 필수이므로 메일 서버가 필요합니다.

첫 판정 확인하기

보호한 메서드를 호출하고, 그 호출의 판정이 관리 화면에 기록되는지 확인합니다. 기본 설정에서 분석은 메서드가 끝난 뒤에 진행되므로, 호출한 직후가 아니라 AI 모델이 응답한 뒤에 판정이 보입니다.

  1. 앱에 일반 사용자 계정으로 로그인합니다. 로그인하지 않은 호출은 관찰 모드와 적용 모드에서 거부되므로, 로그인한 상태에서 호출해야 합니다. CLI가 만든 예제 앱은 샘플 계정으로 로그인합니다.
  2. 5단계에서 @Protectable을 붙인 메서드를 호출합니다. 예를 들어 로그인한 브라우저에서 /api/customers를 엽니다.
  3. 관리 화면 /contexa/admin에 CONTEXA 관리자 admin으로 로그인합니다.
  4. 제로 트러스트 → 판정 기록(/contexa/admin/zero-trust/decisions)을 엽니다. 방금 호출한 사용자의 판정이 한 줄 나타나고, 판정 결과와 그 이유가 함께 보입니다. 판정은 허용(ALLOW) · 추가 인증(CHALLENGE) · 검토 보류(ESCALATE) · 차단(BLOCK) 중 하나입니다. 보이지 않으면 잠시 뒤 화면을 새로 고칩니다.

적용 모드(기본값)에서는 이 판정이 같은 사용자의 다음 요청부터 적용됩니다. 첫 판정이 추가 인증, 검토 보류, 차단이면 그 사용자의 다음 요청이 제한됩니다. 처음 확인하는 환경에서는 관찰 모드(SHADOW)로 두는 것이 안전합니다. 관찰 모드는 판정을 기록하고 아무도 막지 않습니다(관찰 모드로 안전하게 시작하기).

판정 기록에 아무것도 나타나지 않으면 다음을 순서대로 확인합니다.

  • 로그인 여부: 로그인하지 않은 호출은 거부되고 분석되지 않습니다.
  • 운영 모드: 끔(DISABLED)이면 분석하지 않습니다. 관리 화면에 저장한 모드가 있으면 설정 파일보다 우선하므로, contexa.security.zerotrust.mode와 /contexa/admin/system-settings를 함께 확인합니다.
  • 필수 부품: 채팅 모델이나 벡터 저장소가 없으면 판정이 만들어지지 않습니다. 기동 로그의 [ContexaCapability] ERROR와 위 기능 진단을 봅니다.
  • AI 모델 연결: Ollama가 실행 중이 아니거나, 모델을 내려받지 않았거나, API 키가 틀리면 분석이 실패합니다. 제로 트러스트 → 운영 상태(/contexa/admin/zero-trust/operations)에서 종류별 실패를 봅니다.
  • 호출한 위치: 웹 요청도 사용자도 없는 스레드(예약 작업 등)에서 호출하면 판정할 사용자가 없으므로, 메서드를 그대로 실행하고 실행 기록만 남깁니다.
  • 관리자 권한: 관리 화면은 ROLE_ADMIN 권한이 있는 CONTEXA 관리자 계정만 열 수 있습니다.

그 밖의 원인은 문제 해결의 판정이 계속 나오지 않음에 있습니다.

분산 배포로 넘어가기

이 절은 여러 인스턴스로 운영하거나 재시작 뒤에도 학습 상태를 이어 가려는 운영 환경에서 수행합니다. 한 대로 개발하거나 시험할 때는 기본값(standalone)을 그대로 씁니다. 인프라 모드를 distributed로 바꾸고, 앱에 Redis · Redisson · Kafka 의존성과 연결 설정을 추가합니다. CONTEXA 모듈은 이 의존성을 가져오지 않습니다.

implementation 'org.springframework.boot:spring-boot-starter-data-redis'
implementation 'org.redisson:redisson'          // 판은 앱이 정함
implementation 'org.springframework.statemachine:spring-statemachine-data-redis'  // 판은 스타터가 정함
implementation 'org.springframework.kafka:spring-kafka'
contexa:
  infrastructure:
    mode: distributed
spring:
  data:
    redis:
      host: localhost
      port: 6379
  kafka:
    bootstrap-servers: localhost:9092

판정 저장소와 학습 상태는 Redis에, 보안 사건은 Kafka에, 차단 신호는 Redisson으로 전파됩니다. 무엇이 바뀌는지는 인프라 모드에 있습니다.

결과 확인. 기동 로그에서 [Contexa] contexa.infrastructure.mode is standalone: ... 경고가 사라집니다.

결과가 다를 때. spring-boot-starter-data-redis, org.redisson:redisson, spring-statemachine-data-redis 중 하나라도 없으면 기동이 거부됩니다. 앱이 로그인을 맡는 SANDBOX에서 Redis에 접속할 수 없으면 5초 동안 다시 시도한 뒤 앱이 CONTEXA 없이 기동하고, Contexa's Redis cannot be reached ERROR가 남습니다. 연결 설정을 고친 뒤 앱을 다시 시작합니다.
