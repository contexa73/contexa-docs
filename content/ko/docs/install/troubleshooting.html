spring-boot-starter-contexa

문제 해결

CLI 설치 중 오류가 나거나, 앱이 기동하지 않거나, CONTEXA가 켜지지 않거나, 로그인이 이상하거나, 판정이 나오지 않을 때 이 페이지에서 증상에 맞는 항목을 찾습니다. 각 항목은 원인, 먼저 확인할 것(로그 줄, 설정, 화면), 해결 순서로 구성되고, 로그 메시지와 오류 문구는 제품이 출력하는 원문 그대로 적습니다. 어느 증상인지 모르겠으면 기동 로그의 [Contexa] mode= 줄과 ERROR 줄, contexa doctor 결과부터 확인합니다.

먼저 확인할 것

CONTEXA는 JDK, 전용 데이터베이스, AI 모델이 모두 맞물려야 동작합니다. 전용 데이터베이스(전용 DB)는 CONTEXA가 자기 표를 만드는 별도 데이터베이스이며 contexa.datasource.url로 지정합니다. 증상을 찾기 전에 아래 세 곳을 순서대로 확인합니다.

  1. 기동 로그의 [Contexa] mode= 줄: CONTEXA가 켜질 때 INFO 등급으로 한 번 남는 줄이며, 예를 들어 [Contexa] mode=SANDBOX ownership=HOST_OWNED data=application enforcement=ENFORCE처럼 나옵니다. mode는 보안 모드, ownership은 인증 소유권(앱이 직접 둔 구성요소와 CONTEXA의 같은 종류가 만날 때 어느 쪽을 앱에 쓰는지), data는 앱의 데이터를 어느 DB에 두는지(contexa이면 전용 DB가 앱의 DB를 겸합니다), enforcement는 운영 모드입니다. 이 줄이 없으면 CONTEXA가 켜지지 않은 것이므로 앱은 기동했는데 CONTEXA가 동작하지 않음을 봅니다.
  2. 앱 기동 로그의 ERROR 줄: CONTEXA가 남기는 줄과 그 뜻은 켜졌는지 확인에 있습니다. 특히 ERROR 등급의 [ContexaCapability] 줄과 the application starts without Contexa가 들어 있는 줄을 확인합니다. [Contexa]로 시작하는 줄은 CONTEXA의 기동 점검 결과이며 WARN 등급도 있습니다.
  3. CLI 점검: contexa doctor는 Spring Boot·Java 버전, starter와 @EnableAISecurity, CONTEXA 설정이 읽히는지, CONTEXA 데이터베이스가 응답하는지, Ollama와 모델, API 키를 점검하고 문제마다 해결 방법을 함께 보여 줍니다.
contexa doctor

이 페이지는 보안 모드에 따라 증상이 달라지는 경우를 구분합니다. 기본 SANDBOX(@EnableAISecurity)에서는 앱이 자기 로그인을 유지하고, FULL(@EnableAISecurity(mode = SecurityMode.FULL))에서는 CONTEXA가 로그인을 제공합니다. 인증 소유권(HOST_OWNED · CONTEXA_OWNED)은 보안 모드와 서로 다른 설정이며, 앱이 직접 둔 구성요소(UserDetailsService · JwtDecoder 등)와 CONTEXA의 같은 종류가 만날 때 어느 쪽을 앱에 쓰는지 정합니다. 적지 않으면 모드를 따릅니다(SANDBOX → HOST_OWNED, FULL → CONTEXA_OWNED).

판정(Decision)은 CONTEXA의 AI가 한 사용자의 요청을 분석해 내리는 결론입니다. 판정은 허용(ALLOW), 추가 인증(CHALLENGE), 검토 보류(ESCALATE), 차단(BLOCK) 중 하나입니다. 운영 모드는 판정을 만들지, 만든 판정을 실제 요청에 적용할지를 정하며 끔(DISABLED), 관찰 모드(SHADOW), 적용 모드(ENFORCE) 세 가지입니다.

증상에서 소절을 찾는 순서는 다음과 같습니다.

  • CLI 설치 · 초기화 증상: contexa 명령, Docker, Ollama, starter 다운로드, 되돌리기.
  • 앱이 기동하지 않거나 CONTEXA가 켜지지 않을 때: 기동이 멈추는 오류, CONTEXA 없이 앱만 뜨는 경우, 설정이 적용되지 않는 경우.
  • 로그인이 이상할 때: 기본 계정, 관리 콘솔 계정, 모든 요청이 로그인을 요구하는 경우, 폼 저장의 403.
  • 판정이 나오지 않거나 모델 · 벡터 저장소가 문제일 때: 기능 진단 로그, 채팅 모델, vector 확장, 판정이 계속 나오지 않는 경우, 봉인 불일치.
  • 의존성을 찾지 못할 때.

CLI 설치 · 초기화 증상

contexa init의 모든 오류는 할 일을 함께 알려 주며, 프로젝트는 아무것도 바뀌지 않거나 모든 변경이 되돌려집니다. 원인을 고친 뒤 contexa init을 다시 실행합니다.

contexa 명령을 찾지 못함

터미널이 contexa를 실행 파일로 찾지 못하는 증상입니다. 설치 스크립트가 마지막에 알려 준 export PATH=... 줄이 현재 터미널에 적용되지 않은 것이 원인입니다.

해결: 아래 순서로 실행합니다.

  1. 설치 스크립트가 알려 준 export PATH=... 줄을 실행하거나 새 터미널을 엽니다. Windows는 설치 전에 열려 있던 터미널을 다시 엽니다.
  2. contexa --version을 실행해 버전이 나오는지 확인합니다.

Spring Boot 4 또는 3.4 이하 (SPRING_BOOT_UNSUPPORTED, SPRING_BOOT_TOO_OLD)

contexa init이 위 오류 코드로 멈추는 증상입니다. 프로젝트의 Spring Boot 버전이 CONTEXA가 지원하는 범위 밖입니다.

원인: CONTEXA 0.1.x에는 Spring Boot 3.5.x가 필요합니다. start.spring.io에서 만든 프로젝트는 이제 Spring Boot 4이고, 3.4 이하에서는 CONTEXA의 작업 실행기가 Spring Boot의 taskExecutor와 이름이 겹쳐 앱이 기동하지 않습니다.

해결: 빌드 파일의 Spring Boot 버전을 3.5.x로 바꾸거나, 빈 폴더에서 contexa init을 실행해 CONTEXA가 붙은 Spring Boot 3.5 예제 앱을 받습니다. 앱이 이미 Spring Boot 4에서 기동을 시도한 경우의 메시지는 Spring Boot 4.x에 있습니다.

Docker가 없거나 실행 중이 아님 (DOCKER_MISSING, DOCKER_STOPPED)

원인: contexa init은 로컬 PostgreSQL(실행 중인 Ollama가 없으면 Ollama도)을 Docker로 실행합니다. Docker가 설치되어 있지 않거나 실행 중이 아니면 위 오류 코드로 멈춥니다.

해결: 운영체제별로 Docker를 실행합니다.

  1. Windows와 macOS는 Docker Desktop을 실행해 준비될 때까지 기다리고, Linux는 sudo systemctl start docker를 실행합니다.
  2. 대화형 init은 다시 확인할지 물어봅니다.
  3. Docker를 쓰지 않으려면 이미 있는 pgvector PostgreSQL을 씁니다. 질문에서 고르거나 contexa init --db-url jdbc:postgresql://host:5432/db를 실행하고, 비밀번호는 CONTEXA_DB_PASSWORD에 둡니다.

포트가 이미 쓰이고 있음

포트 충돌은 조치할 것이 없는 증상입니다. 로컬 서비스는 사용 중이지 않은 포트를 골라 시작합니다. PostgreSQL은 55432부터, Ollama는 11434 또는 51434부터, 로컬 메일함은 51025와 58025부터입니다. 기본 포트에서 이미 실행 중인 서비스는 변경하지 않으며, 11434에서 이미 실행 중인 Ollama는 그대로 사용합니다.

Ollama가 없거나 모델이 없음 (OLLAMA_MISSING)

원인: AI 모델을 실행할 Ollama가 설치되어 있지 않거나, 필요한 모델을 내려받지 않았습니다.

해결: 둘 중 하나를 고릅니다.

  • ollama.com/download에서 Ollama를 설치하거나(또는 CONTEXA가 실행할 수 있게 Docker를 켜거나) --provider openai로 OpenAI를 고릅니다.
  • contexa init은 없는 모델(qwen3:8b, mxbai-embed-large)만 내려받으며, 받다가 멈추면 다시 실행할 때 이어서 받습니다.
  • 작은 PC에서 더 가벼운 채팅 모델을 쓰려면 contexa init 전에 CONTEXA_OLLAMA_CHAT_MODEL(예: qwen2.5:3b)을 설정합니다. 그 모델을 내려받고 설정에도 씁니다.

CONTEXA starter를 받지 못함 (STARTER_UNAVAILABLE)

원인: 프로젝트 빌드가 저장소 설정으로 ai.ctxa:spring-boot-starter-contexa를 해석하지 못했습니다. contexa init은 모든 변경을 되돌렸습니다.

해결: 빌드가 Maven Central(또는 이를 미러링하는 사내 저장소)에 닿는지 네트워크·프록시를 확인하고 contexa init을 다시 실행합니다(아래).

contexa reset이 되돌리는 범위

reset은 contexa init이 바꾼 파일만 정확히 복원합니다. 프로젝트의 contexa/ 폴더(git이 무시함)에 있는 설치 기록과 백업을 사용합니다. 되돌리는 범위는 세 가지입니다.

  • 파일: init이 만든 파일은 지우고 바꾼 파일은 되돌립니다. init 이후 직접 바꾼 내용은 지키며, CONTEXA의 변경과 겹치는 곳은 파일을 그대로 두고 목록으로 알려 줍니다.
  • 로컬 서비스: 다른 프로젝트를 위해 남겨 둡니다. 쓰는 프로젝트가 더 없으면 데이터와 함께 지울지 묻고, contexa reset --services는 묻지 않고 지웁니다.
  • 데이터: 프로젝트의 CONTEXA 데이터는 로컬 서비스를 지울 때까지 그 데이터베이스에 남습니다.

CLI 0.1.x로 한 설치도 같은 방식으로 되돌립니다. 그때의 Docker 스택은 소유가 확인되면 지우고, 확인되지 않으면 그대로 둡니다.

앱이 기동하지 않거나 CONTEXA가 켜지지 않을 때

@EnableAISecurity를 붙인 앱의 기동 결과는 세 가지입니다. 어느 쪽인지 알면 찾을 소절이 정해집니다.

  • 기동이 멈춥니다. 설정이 CONTEXA가 지원하는 구성과 맞지 않을 때입니다. 대부분 Spring Boot의 "APPLICATION FAILED TO START" 안내에 Description(무엇이 문제인가)과 Action(무엇을 바꾸는가)이 나옵니다. 아래 소절의 오류가 여기에 속합니다.
  • 앱은 뜨지만 CONTEXA가 켜지지 않습니다. 로그인을 앱이 맡는 기본 SANDBOX에서 전용 DB나 Redis에 연결할 수 없을 때입니다. 앱이 CONTEXA 없이 뜨고 ERROR 로그를 남깁니다(아래).
  • 앱도 CONTEXA도 뜨지만 경고가 남습니다. 정상 경고이거나 설정을 고쳐야 한다는 신호입니다(standalone 경고, 옛 설정 이름).

앱은 기동했는데 CONTEXA가 동작하지 않음

앱이 정상으로 기동했지만 기동 로그에 [Contexa] mode= 줄이 없고, 보호된 메서드에 판정이 생기지 않으며, 관리 화면이 열리지 않는 증상입니다.

원인: 로그인을 앱이 맡는 기본 SANDBOX는 CONTEXA에 문제가 있어도 앱의 기동을 막지 않습니다. 앱은 CONTEXA가 없을 때와 같게 기동하고, CONTEXA는 아무것도 켜지 않습니다. 이때 원인을 알리는 ERROR 로그를 한 줄 남깁니다. CONTEXA가 로그인을 맡는 FULL은 CONTEXA 없이 아무도 로그인할 수 없으므로 같은 원인에서 앱이 기동하지 않습니다.

먼저 확인할 것: 기동 로그에서 아래 줄을 찾습니다.

ERROR 로그 줄(앞부분)원인해결
Contexa's database cannot be used (...): the application starts without Contexa, and nothing of it is active.전용 DB에 연결되지 않습니다. CONTEXA는 약 5초 동안 1초 간격으로 연결을 다시 시도한 뒤 포기합니다. 연결은 되지만 DB 계정이 vector 확장을 만들 수 없는 경우에도 같은 줄이 나오며, 괄호 안에 CREATE EXTENSION을 실행하라는 안내가 붙습니다.DB가 실행 중인지, contexa.datasource.url · 계정 · 비밀번호가 맞는지 확인합니다. 확장 문제이면 DB 관리자가 그 DB에서 CREATE EXTENSION을 한 번 실행합니다(vector 확장). 고친 뒤 앱을 다시 시작합니다.
Contexa's Redis cannot be reached (...): the application starts without Contexa, and nothing of it is active.contexa.infrastructure.mode가 distributed인데 Redis 서버에 연결되지 않습니다. 이 점검은 서버가 하나일 때만 하며, 클러스터나 센티널 구성은 Redis 클라이언트에 맡깁니다.Redis가 실행 중인지, spring.data.redis.* 주소가 맞는지 확인하고 Redis가 돌아온 뒤 앱을 다시 시작합니다.
contexa.autonomous.enabled=... switches off the decision engine, which all of Contexa reads: the application starts without Contexacontexa.autonomous.enabled가 true가 아닙니다. 판정 엔진은 CONTEXA 전체가 읽으므로 이 값이 꺼지면 CONTEXA 전체가 꺼집니다.이 설정을 지웁니다. 판정만 끄려면 contexa.security.zerotrust.mode: DISABLED를 씁니다.
(로그 줄 없음)contexa.enabled가 false입니다. CONTEXA를 켜지 않기로 한 설정이므로 아무 줄도 남기지 않습니다.CONTEXA를 쓰려면 이 설정을 지웁니다(기본값은 켜짐).

CONTEXA가 켜지지 않은 상태에서는 앱이 직접 만든 Spring Security 필터 체인이 없으면 Spring Boot의 기본 보안이 적용됩니다. 앱의 로그인과 페이지는 CONTEXA를 끈 앱과 같게 동작합니다.

contexa.datasource.url must be configured for @EnableAISecurity

앱이 @EnableAISecurity를 켰는데 CONTEXA 전용 DB 주소가 없어 기동이 멈추는 증상입니다.

메시지: Spring Boot의 기동 실패 안내에 Description으로 contexa.datasource.url must be configured for @EnableAISecurity.가, Action으로 Use a dedicated Contexa database by default; sharing the application database requires explicit POC approval.가 나옵니다. 0.1.1은 두 문장을 이어 예외 한 줄로 냅니다. 전체 메시지: java.lang.IllegalStateException: contexa.datasource.url must be configured for @EnableAISecurity. Use a dedicated Contexa database by default; sharing the application database requires explicit POC approval.

원인: @EnableAISecurity를 켜면 CONTEXA 전용 DB 주소가 반드시 있어야 합니다. 주소를 비워 두면 CONTEXA는 연결을 시도하기 전에 이 메시지로 기동을 멈춥니다. 로그인을 앱이 맡는 방식에서도 같습니다.

먼저 확인할 것: 설정 파일(프로필별 파일 포함)에 contexa.datasource.url이 정확한 이름으로 있고 값이 비어 있지 않은지 봅니다.

해결: 전용 DB를 만들고(전용 DB 만들기) 주소를 적습니다. 기존 앱이라면 contexa.datasource.isolation.contexa-owned-application: true는 적지 않아야 합니다(최소 설정).

contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}

contexa.datasource must not share ...

CONTEXA 전용 DB가 앱의 DB와 같아서 기동이 멈추는 증상입니다.

메시지: Description으로 contexa.datasource must not share spring.datasource unless it is an approved POC: contexa.datasource.url and spring.datasource.url name the same database., 운영 프로필이면 contexa.datasource must not share the application datasource in production profiles: ...가 나오고, Action에 필요한 두 설정이 적힙니다. 0.1.1의 메시지는 contexa.datasource must not share spring.datasource unless contexa.datasource.isolation.allow-shared-application-datasource=true and contexa.datasource.isolation.shared-application-datasource-risk-accepted=true are both set for an approved POC, 또는 contexa.datasource must not share the application datasource in production profiles입니다.

원인: contexa.datasource.url이 앱의 spring.datasource.url과 같습니다. 두 값을 앞뒤 공백을 지우고 비교해 완전히 같을 때만 이 검사에 걸립니다.

해결: 전용 DB를 따로 둡니다. 시험용으로 같은 DB를 반드시 써야 하면 위 두 설정을 모두 true로 하되, prod · production 프로필에서는 그래도 거부됩니다. CONTEXA 소유 앱(contexa-owned-application: true)은 이 검사를 하지 않습니다.

앱의 기본 DB 연결이 없음

앱이 DB 연결 오류로 기동하지 못하는 증상입니다. CONTEXA 전용 DB가 아니라 앱 자신의 기본 DB 연결에 대한 오류입니다.

메시지(Spring Boot): Failed to configure a DataSource: 'url' attribute is not specified and no embedded datasource could be configured.

원인: 스타터가 JPA를 함께 가져오므로 앱에 DB 주소가 없으면 Spring Boot가 기본 DB 연결을 만들지 못합니다. 0.1.1은 CONTEXA를 켠 앱에 DB 주소가 없으면 DB가 필요 없는 앱에서도 이 오류가 났습니다. 0.2.0부터는 앱이 DB 설정을 전혀 적지 않았고 내장 DB도 없으면 Spring Boot의 DB 자동 설정을 빼고 기동하므로, 이 오류는 앱이 DB 관련 설정은 적었는데 주소가 없을 때 남습니다. 대표적인 경우는 spring.jpa.* · spring.flyway.* · spring.liquibase.* · spring.sql.init.*만 있고 spring.datasource.url이 없는 설정입니다.

먼저 확인할 것: 설정 파일에 위와 같은 DB 관련 설정이 남아 있는지, 앱이 DB를 실제로 쓰는지 봅니다.

해결: 앱이 DB를 쓰면 앱용 DB 주소(spring.datasource.url)를 적습니다. 쓰지 않으면 DB 관련 설정을 지웁니다. CONTEXA에 로그인을 맡기는 @EnableAISecurity(mode = SecurityMode.FULL)이고 앱이 자기 DB 주소를 두지 않으면 CONTEXA DB가 앱의 기본 연결이 되므로 이 오류가 나지 않습니다.

Contexa schema is partially installed ...

CONTEXA DB에 CONTEXA 표가 일부만 있어 기동이 멈추는 증상입니다.

메시지: Contexa schema is partially installed without a complete ownership contract. No schema changes were applied. Restore a verified OSS backup or use a clean database.

원인: CONTEXA DB에 CONTEXA 표가 일부만 있습니다. CONTEXA는 이런 DB를 고치지 않고 기동을 멈춥니다. 첫 설치 뒤에도 표가 다 갖춰지지 않으면 Contexa schema is partially installed after canonical schema execution.으로 멈추고, 이 메시지는 DB를 다시 만들거나 META-INF/contexa/db/schema.sql을 직접 실행한 뒤 기동하라고 안내합니다.

먼저 확인할 것: 이 DB를 다른 용도로 쓰거나 이전 설치가 중간에 실패한 적이 있는지 봅니다.

해결: 깨끗한 DB를 쓰거나 검증된 백업으로 되돌립니다. DB 계정이 vector 확장을 만들 수 있는지도 확인합니다.

Spring Boot 4.x

앱의 Spring Boot 버전이 4.x여서 기동이 멈추는 증상입니다. CONTEXA는 Spring Boot 3.x용으로 만들어졌습니다.

메시지: Description으로 Contexa runs on Spring Boot 3.x, and this application runs on Spring Boot 4.x.y.가, Action으로 Run this application on Spring Boot 3.x, or remove @EnableAISecurity.가 나옵니다(4.x.y 자리에는 실제 버전이 들어갑니다). 0.1.1의 메시지는 Contexa does not support Spring Boot 4.x. Current version: ...(ERROR 로그), Spring Boot 4.x is not supported by Contexa. Current version: ...(IllegalStateException)입니다.

해결: Spring Boot 3.5.x를 씁니다. CONTEXA는 3.5.4로 빌드 · 시험됩니다.

@EnableAISecurity applies security through Spring Security

앱에 Spring Security가 없어서 기동이 멈추는 증상입니다.

메시지: @EnableAISecurity applies security through Spring Security, and it is not on the class path.

원인: @EnableAISecurity는 보안을 적용하겠다는 선언이고 실제 적용은 Spring Security가 합니다. 스타터는 Spring Security를 가져오지 않으므로 앱이 직접 선언해야 합니다.

해결: 앱에 org.springframework.boot:spring-boot-starter-security를 추가합니다(의존성 넣기). contexa init은 자동으로 추가합니다.

SANDBOX keeps the application's sign-in, and this application has none

앱이 로그인을 맡는 기본 SANDBOX인데 앱에 로그인 구성이 없어서 기동이 멈추는 증상입니다.

메시지: SANDBOX keeps the application's sign-in, and this application has none: no SecurityFilterChain and no users of its own, so every request would ask for a sign-in that nobody can complete.

원인: 기본 SANDBOX에서는 앱이 로그인을 맡는데, 앱에 SecurityFilterChain도 사용자도 없고 Spring Boot의 기본 보안 체인만 남았습니다. 이대로면 모든 요청이 아무도 통과할 수 없는 로그인을 요구하므로 CONTEXA가 기동을 거부합니다. 앱에 체인도 사용자도 없으면 CONTEXA가 Spring Boot 기본 체인 대신 모든 요청을 허용하는 격리 체인(contexaSandboxIsolationChain)을 두어 CONTEXA를 넣기 전의 접근을 유지하므로, 이 거부는 보통 나지 않습니다(안전 장치).

해결: 둘 중 하나를 고릅니다. 앱의 SecurityFilterChain이나 사용자를 선언하거나(기존 로그인과 연결하기), @EnableAISecurity(mode = SecurityMode.FULL)로 CONTEXA가 로그인을 제공하게 합니다. 앱이 자기 SecurityFilterChain을 선언했으면 이 오류가 나지 않습니다. 체인이 없어도 앱에 로그인할 사용자가 있으면 이 오류 대신 모든 요청이 로그인을 요구함의 경고만 남습니다. Spring Security를 쓰지 않고 자체 로그인을 쓰는 앱은 체인이나 사용자를 선언하지 않습니다. 이런 앱에는 격리 체인이 놓이므로, 로그인한 사용자는 ContexaSubjectResolver 빈 하나로 알립니다(기존 로그인과 연결하기).

그 밖에 기동이 거부되는 경우

아래 오류도 기동 실패 안내의 Description 줄에 나오며, 같은 안내의 Action 줄에 해결 방법이 적혀 있습니다.

Description 줄(앞부분)원인해결
With mode FULL Contexa's main chain takes every request, and the application declares its own security chain(s) [...] for every request as well.FULL에서 앱이 모든 요청을 받는 자기 SecurityFilterChain을 선언했습니다. Spring Security는 모든 요청을 받는 체인 뒤의 체인을 실행하지 않으므로 CONTEXA 주 체인과 앱 체인 중 하나는 실행되지 않습니다. 그래서 CONTEXA가 기동을 거부합니다.앱 체인을 http.securityMatcher(...)로 지키는 경로에 좁히면 CONTEXA 주 체인 앞에서 함께 동작합니다. 앱 체인을 앱의 주 보안으로 유지하려면 mode = FULL 없이 @EnableAISecurity(SANDBOX)를 씁니다.
contexa.infrastructure.mode is distributed, and the Redis client is not on the class path: [...]distributed 모드는 Redis에 상태를 두는데 필요한 라이브러리(spring-boot-starter-data-redis, org.redisson:redisson, spring-statemachine-data-redis)가 앱에 없습니다. 메시지의 대괄호에 없는 것이 나열됩니다.나열된 라이브러리를 앱에 추가하거나 contexa.infrastructure.mode=standalone으로 되돌립니다(분산 배포). org.redisson:redisson은 JCache 제공자를 함께 가져오므로, 캐시를 JCache로 쓰는 앱은 spring.cache.type=caffeine처럼 캐시를 직접 정하거나 spring.cache.jcache.provider로 제공자를 지정해야 합니다.

WebFlux 앱은 지원하지 않습니다.
Contexa does not support Spring AOT processing or native images, and this build runs AOT processing on an application with @EnableAISecurity: ...빌드가 Spring AOT 처리를 실행합니다. CONTEXA의 빈은 AOT가 코드로 쓸 수 없습니다.AOT 처리와 네이티브 이미지 없이 빌드하거나 @EnableAISecurity를 뺍니다.

contexa.infrastructure.mode is standalone 경고

기동 로그에 WARN 등급으로 이 경고가 한두 줄 나오는 증상입니다. 설정 오류가 아니라 기본 인프라 모드(standalone)의 정상 경고입니다.

원인: standalone에서는 CONTEXA가 상태를 앱의 메모리에 둡니다. 경고는 두 가지입니다.

  • 학습 상태(행위 기준선 등)가 메모리에 있어 재시작하면 사용자별 학습이 처음부터 다시 시작됩니다.
  • 적용 중인 판정이 메모리에 있어 재시작하면 추가 인증(CHALLENGE), 검토 보류(ESCALATE), 허용(ALLOW) 판정이 끝나고 다음 요청을 다시 분석합니다. 차단(BLOCK)은 CONTEXA가 차단 사용자 기록(ctxa_blocked_user)에서 기동할 때 다시 적용하므로 그 기록에 남은 차단은 유지되고, 기록되지 않은 차단은 재시작과 함께 끝납니다.

끔(DISABLED)에서는 학습도 판정 저장도 없으므로 이 경고가 나오지 않습니다.

해결: 개발 중에는 그대로 두어도 됩니다. 운영에서 학습과 판정을 유지하려면 distributed로 바꿉니다.

옛 설정 이름이 적용되지 않을 때

증상: security.zerotrust.* · spring.auth.* · spring.ai.security.*처럼 contexa.* 아래가 아닌 옛 이름으로 적은 설정이 적용되지 않고, 로그에도 아무 알림이 없습니다.

원인: 옛 이름의 별칭은 없어졌습니다. 그 이름은 앱 자신의 설정으로 보고 CONTEXA가 읽거나 옮기지 않으므로 값이 조용히 무시됩니다(예외: Kafka 리스너 그룹의 security.plane.kafka.group-id). 벡터 저장소 설정(spring.ai.vectorstore.pgvector.*)도 CONTEXA 저장소에는 닿지 않으니 contexa.vectorstore.pgvector.*로 씁니다.

먼저 확인할 것: 설정 파일에서 contexa.로 시작하지 않는 CONTEXA 관련 키가 있는지 봅니다.

해결: 새 접두어로 바꿉니다. 옮겨 간 이름 전체는 설정 길잡이에 있습니다.

스타터만 넣었는데 CONTEXA 표가 없음

의존성을 추가했는데 CONTEXA DB에 CONTEXA 표가 생기지 않는 증상입니다.

원인: @EnableAISecurity가 없는 상태(의존성만)에서는 정상입니다. 스타터만으로는 CONTEXA 필터 · 인증 제공자 · 표를 만들지 않습니다. 표는 CONTEXA가 켜진 앱이 기동할 때 CONTEXA DB에 만들고 검증합니다.

먼저 확인할 것: @EnableAISecurity를 붙였다면 기동 로그에 [Contexa] mode= 줄이 있는지 봅니다. 줄이 없으면 CONTEXA가 켜지지 않은 것이므로 앱은 기동했는데 CONTEXA가 동작하지 않음을 따릅니다.

해결: 켠 뒤에도 표가 없으면 contexa.iam.seed.enabled가 false가 아닌지, contexa.datasource.*가 CONTEXA DB를 가리키는지 확인합니다.

로그인이 이상할 때

로그인 증상은 로그인을 누가 맡는지에 따라 원인이 다릅니다. 앱이 로그인을 맡는 SANDBOX에서는 앱의 로그인이 그대로이고, CONTEXA는 관리 콘솔에만 별도 관리자 계정을 둡니다. CONTEXA가 로그인을 맡는 FULL에서는 CONTEXA의 로그인 화면을 쓰고, 앱 사용자는 인증 소유권에 따라 CONTEXA 계정(CONTEXA_OWNED, 기본) 또는 앱의 UserDetailsService(HOST_OWNED)로 확인합니다.

Spring Boot 기본 계정으로 로그인되지 않음

Spring Security를 쓰는 앱에서 Spring Boot는 기본 계정 user를 만들고, 기동할 때마다 새 비밀번호를 생성해 로그에 Using generated security password 줄로 남깁니다. 이 계정으로 로그인하던 앱에서 로그인이 되지 않는 증상입니다.

먼저 확인할 것: 기동 로그에서 Using generated security password 줄을 찾습니다. 줄이 있으면 계정은 만들어진 것이므로 그 줄의 비밀번호로 로그인합니다. 비밀번호는 기동할 때마다 바뀝니다. 줄이 없으면 아래 원인 중 하나입니다.

원인:

  • 0.1.1: CONTEXA starter가 OAuth2 클래스를 가져옵니다. Spring Boot는 OAuth2 클래스가 클래스패스에 있으면 앱이 자기 로그인을 쓴다고 보고 기본 계정을 만들지 않으므로, 그 계정으로 로그인하던 앱은 CONTEXA를 넣은 뒤 계정이 없어집니다. 또 이 판은 CONTEXA의 위임 비밀번호 인코더가 앱의 비밀번호 인코더로 잡혀 {noop} 같은 접두어가 없는 비밀번호를 검사하지 못하므로 계정 이름만 정해서는 로그인되지 않습니다.
  • 0.2.0부터: CONTEXA가 로그인을 맡지 않는 앱에서는 starter가 계정 이름 user를 Spring Boot에 대신 알려 기본 계정과 로그 줄이 그대로 유지됩니다. CONTEXA의 비밀번호 인코더는 앱의 인증과 분리되어 있어 영향을 주지 않습니다. 계정이 없다면 다음 중 하나입니다. CONTEXA가 로그인을 맡는 방식이거나, 앱에 spring.security.oauth2.* 또는 spring.security.saml2.* 설정이나 SAML 클래스가 있어 Spring Boot가 이 계정을 원래 만들지 않는 앱이거나, 앱이 spring.security.user.name을 다른 이름으로 정했습니다.

해결: spring.security.user.name: user와 spring.security.user.password: "{noop}비밀번호"를 설정합니다. 비밀번호 앞의 {noop}은 암호화하지 않은 비밀번호라는 Spring Security의 표기이므로 개발 환경에서만 씁니다.

앱이 로그인을 맡고 자기 계정·OAuth2·spring.security.user.*가 없으면 contexa init이 대신 해 줍니다. contexa init은 비밀번호를 한 번 만들어 프로젝트 밖 ~/.contexa/credentials.properties에 보관하고 마지막에 보여 줍니다. CONTEXA가 로그인을 맡는 FULL + CONTEXA_OWNED(소유권을 적지 않은 FULL)에서는 기본 계정이 아니라 CONTEXA 계정으로 로그인합니다(관리 콘솔 계정과 비밀번호).

관리 콘솔 계정과 비밀번호

관리 콘솔(/contexa/admin/login)에 로그인할 수 없거나 계정과 비밀번호를 모르는 증상입니다. 콘솔 계정은 앱의 사용자와 별개이므로 앱 계정으로는 들어갈 수 없습니다.

원인: 콘솔 계정은 다음 방식으로 만들어집니다.

  1. 두 모드 모두(소유권과 무관) contexa init이 계정 admin의 비밀번호를 만들어 ~/.contexa/credentials.properties에 보관하고 마지막에 보여 줍니다.
  2. 앱이 시작할 때 CONTEXA가 contexa.iam.seed.admin.password로 이 계정을 만듭니다.
  3. 빈 폴더에서 만든 예제 앱은 대신 견본 계정(admin / 1111)을 씁니다.
  4. 앱이 로그인을 맡는 SANDBOX에서도 콘솔 계정은 이 admin입니다. FULL + CONTEXA_OWNED가 아닌 세 조합에서 콘솔은 /contexa/admin/login에서 CONTEXA 관리자를 비밀번호 다음에 패스키 또는 메일 코드로 로그인시키고, 앱 사용자는 들어올 수 없습니다.
  5. CLI 없이 설치했다면 contexa.iam.seed.admin.*을 직접 설정합니다(예시).

먼저 확인할 것: 비밀번호는 contexa init의 마지막 화면이나 그 파일의 contexa.iam.seed.admin.password 줄에서 확인합니다. 계정이 없으면 기동 로그에서 아래 줄을 찾습니다.

  • [IamSeedData] Administrator 'admin' created(INFO): 계정이 만들어졌습니다.
  • [IamSeedData] A user named ... exists; the administrator from ... is not created(INFO): 같은 이름이나 같은 이메일의 사용자가 이미 있어 만들지 않았습니다. 기존 계정은 바꾸지 않습니다.
  • [IamSeedData] Administrator ... created ..., but the administrators group ... is missing(WARN): 계정은 만들어졌지만 관리자 그룹이 없습니다. 관리 화면에서 그룹을 지정합니다.
  • 아무 줄도 없음: contexa.iam.seed.admin.password가 비어 있어 계정을 만들지 않았거나, CONTEXA가 켜지지 않았거나, contexa.iam.seed.enabled가 false입니다.

해결: 이미 있는 계정은 다시 만들지 않으므로 관리 콘솔에서 바꾼 비밀번호가 유지됩니다. 계정이 없으면 같은 PC의 같은 사용자로 앱을 시작했는지 확인합니다. contexa init이 비밀번호를 사용자의 홈 폴더 파일에 보관하기 때문입니다. CONTEXA가 로그인을 맡을 때 두 번째 단계의 일회용 코드는 contexa init이 알려 준 로컬 메일함으로 옵니다.

모든 요청이 로그인을 요구함 · SANDBOX mode: the application declares users of its own and no SecurityFilterChain

CONTEXA를 넣은 뒤 로그인 없이 열려야 할 페이지까지 모두 로그인을 요구하는 증상입니다.

원인: 앱이 spring-boot-starter-security를 넣었는데 자기 SecurityFilterChain이 없으면 Spring Boot 기본 보안이 걸려 모든 요청이 인증을 요구합니다. 스타터는 Spring Security를 가져오지 않으므로 스타터만 넣어서는 걸리지 않습니다.

@EnableAISecurity를 켠 기본 SANDBOX에서는 CONTEXA가 앱의 체인을 만들지 않습니다. 앱에 로그인할 사용자(UserDetailsService · AuthenticationProvider · AuthenticationManager)가 있으면 Spring Boot 기본 보안이 앱의 보안으로 남고, CONTEXA는 이 상태를 알리는 WARN 로그 [Contexa] SANDBOX mode: the application declares users of its own and no SecurityFilterChain, so Spring Boot's default security is active and every request requires authentication. ...를 기동 때 남깁니다. 앱에 사용자도 없으면 CONTEXA가 Spring Boot 기본 체인 대신 모든 요청을 허용하는 격리 체인을 두므로 이 증상은 나지 않습니다(위).

먼저 확인할 것: 기동 로그에서 위 WARN 줄을 찾습니다. 줄이 있으면 앱이 자기 SecurityFilterChain을 선언하지 않은 것입니다.

해결: 앱의 SecurityFilterChain을 선언합니다(기존 로그인과 연결하기). 로그에 예로 나오는 anyRequest().permitAll()은 CONTEXA 경로에 대해서는 안전합니다. 관리 화면 /contexa/admin/**는 CONTEXA 자기 체인과 관리자 로그인이 지키므로 앱 체인이 막을 필요가 없습니다. 앱 자신의 페이지는 지금처럼 보호합니다. 로그인을 CONTEXA에 맡기려면 @EnableAISecurity(mode = SecurityMode.FULL)을 씁니다(CLI라면 contexa init --mode full).

Spring Security를 켠 뒤 폼 저장이 403으로 거부됨

Spring Security를 넣은 뒤 Thymeleaf 폼의 저장 요청이 403으로 응답하는 증상입니다.

원인: Spring Security를 켜면 CSRF 보호가 켜집니다. Thymeleaf 폼에 th:action이 없으면 CSRF 토큰이 들어가지 않아 저장이 403이 됩니다. CONTEXA가 아니라 Spring Security의 표준 동작입니다.

해결: 폼에 th:action을 쓰거나 요청에 _csrf를 함께 보냅니다.

판정이 나오지 않거나 모델 · 벡터 저장소가 문제일 때

[ContexaCapability] ... · Contexa required capability check failed.

기동 로그에 ERROR 등급의 [ContexaCapability] 줄이 나오거나, 앱이 Contexa required capability check failed.로 기동하지 못하는 증상입니다.

로그 형식: [ContexaCapability] <기능> status=<상태> required=<true|false> 뒤에 Reason · Missing beans · Recommended actions가 이어집니다.

원인: 기동이 끝날 때 CONTEXA는 판정에 필요한 부품이 만들어졌는지 검사합니다. 부품이 빠졌습니다. 검사 결과가 어떻게 나타나는지는 앱 유형이 정합니다.

  • CONTEXA 소유 앱이 아닌 앱(WARN)은 ERROR 로그만 남기고 기동합니다. 이 로그는 필수(required=true)로 판정된 부품에만 남고, STRICT 모드에서는 필수가 아닌 부품도 남습니다.
  • CONTEXA 소유 앱(FAIL_FAST)은 Contexa required capability check failed.로 멈춥니다. 소유 앱은 contexa-owned-application: true인 앱, spring.application.name이 contexa-로 시작하는 앱이며, FULL에서는 앱이 자기 DB 주소를 따로 두지 않으면 contexa-owned-application이 자동으로 true가 됩니다.

먼저 확인할 것: 로그의 <기능> 이름과 뒤따르는 Reason · Missing beans · Recommended actions를 읽고 아래 표에서 같은 기능을 찾습니다.

No Spring AI ChatModel is configured for CONTEXA

CONTEXA가 쓸 채팅 모델을 찾지 못해 기동이 멈추는 증상입니다.

메시지(앞부분): No Spring AI ChatModel is configured for CONTEXA. Add at least one Spring AI chat provider starter to your application dependencies ... then configure the matching provider under spring.ai.*

원인: 채팅 모델 빈은 있지만 CONTEXA가 쓸 채팅 클라이언트 · 모델 선택을 만들지 못했습니다. 메시지는 의존성이 이미 있다면 그 공급자의 키나 주소가 실제로 설정됐는지 확인하라고 안내합니다. 공급자 스타터가 전혀 없으면 이 메시지 대신 위 llm-runtime 기능 진단 결과가 나옵니다.

먼저 확인할 것: 앱에 Spring AI 채팅 공급자 스타터가 있는지, 그 공급자의 키나 주소가 설정되어 있는지 봅니다.

해결: 공급자 키는 contexa.llm 아래가 아니라 Spring AI 설정에 둡니다: spring.ai.openai.api-key, spring.ai.anthropic.api-key, Ollama는 spring.ai.ollama.* 또는 contexa.llm.chat.ollama.base-url. 공급자 순서는 contexa.llm.selection.chat.priority로 정합니다(최소 설정).

vector 확장이 없음(PostgreSQL)

CONTEXA DB에 pgvector의 vector 확장이 없거나 DB 계정이 만들 수 없어, 벡터 저장소가 만들어지지 않거나 CONTEXA가 켜지지 않는 증상입니다.

원인: CONTEXA의 벡터 표는 앱의 기본 DB가 아니라 CONTEXA DB에 만들어지며, 이 DB에 vector 확장이 필요합니다. 벡터 저장소가 표를 만들 때(contexa.vectorstore.pgvector.initialize-schema, 기본 true) hstore와 uuid-ossp 확장도 필요합니다. CONTEXA는 기동 초기에 이 확장을 만들어 보고 취소하는 방식으로 계정 권한을 점검하며, 권한이 없으면 CONTEXA 없이 앱이 뜨거나(로그인을 앱이 맡는 방식) 기동이 멈춥니다.

먼저 확인할 것: 기동 로그의 Contexa's database cannot be used (...) 줄 괄호 안에 CREATE EXTENSION 안내가 있는지 봅니다.

해결: pgvector가 든 이미지(예: pgvector/pgvector:pg16)를 쓰거나, 기존 DB라면 권한 있는 계정으로 CONTEXA DB에서 한 번 실행합니다.

CREATE EXTENSION IF NOT EXISTS vector;

판정이 계속 나오지 않음

앱은 정상으로 기동하고 로그인도 되지만, 보호된 메서드를 호출해도 판정이 생기지 않거나 요청이 분석 대기로 남는 증상입니다. 아래 항목을 위에서부터 확인합니다.

  1. 운영 모드: 기동 로그의 [Contexa] mode= 줄에서 enforcement 값을 봅니다. DISABLED · OBSERVE이면 @Protectable 호출을 분석하지 않습니다. 관리 화면에 저장한 모드가 있으면 YAML보다 우선하므로 /contexa/admin/system-settings에서 확인합니다(기동 로그 System runtime settings applied to AI decision mode: ...). 모드의 뜻은 관찰 모드로 안전하게 시작하기에 있습니다.
  2. 부품: 채팅 모델 · 벡터 저장소가 없으면 분석 대기로 남습니다(위).
  3. 보호 대상: 분석되는 것은 @Protectable 메서드 호출입니다. 로그인은 분석하지 않고, 로그인한 사용자가 처음 호출하는 보호 메서드가 그 사용자의 첫 판정이 됩니다. SHADOW와 ENFORCE 모드(기본은 ENFORCE)에서는 로그인하지 않은(익명) 호출을 분석 전에 거부하고, DISABLED와 OBSERVE에서는 거부하지 않고 앱이 만든 그대로 진행합니다.
  4. 판정은 다음 요청부터: 기본 비동기 메서드는 응답 뒤에 판정하므로 그 판정은 다음 호출에 적용됩니다.
  5. 동기 호출이 오래 걸림: sync = true로 호출을 동기로 분석하면 요청은 판정을 최대 40초(contexa.security.zerotrust.agent.flight.wait) 기다립니다. 그 시간을 넘으면 요청이 거부되고 분석은 계속됩니다. 사용하는 모델이 이보다 느리면 이 값을 늘립니다.

생성된 판정은 관리 화면 제로 트러스트 → 판정 기록에서 확인합니다(결과 확인 위치).

업그레이드 뒤 옛 판정 기록의 봉인 불일치

업그레이드 뒤 보안 이벤트 기록과 대시보드의 "봉인이 깨진 판정 기록"에 판정 기록이 MISMATCH로 나타나는 증상입니다. 판정 기록의 봉인은 기록이 저장된 뒤 바뀌지 않았음을 확인하는 무결성 봉인입니다.

원인: 업그레이드 전에 저장된 기록이 MISMATCH이면, 예전 판이 저장할 때 기록 시각을 다시 써서 생긴 불일치입니다. 새 판에서 저장한 기록은 봉인한 그대로 확인됩니다.

해결: 옛 기록은 다시 봉인하지 않으므로(변조 증거의 뜻을 지키기 위해) 감사 기록 보관 기간이 지나 지워질 때까지 불일치로 남습니다. 업그레이드 뒤 새로 생긴 기록이 MISMATCH이면 실제로 바뀐 기록이니 살펴봐야 합니다(판정 기록).

ai.ctxa 의존성을 찾지 못할 때

Gradle이나 Maven이 ai.ctxa:spring-boot-starter-contexa를 해석하지 못하는 증상입니다. 정식 {{contexa.version}}은 mavenCentral()만 있으면 됩니다. Spring milestone · snapshot이나 Sonatype snapshot 저장소를 일반 앱 빌드에 넣지 않아야 합니다. 좌표가 ai.ctxa:spring-boot-starter-contexa:{{contexa.version}}인지 확인하고, 게시 직후라면 Maven Central 동기화가 끝난 뒤 다시 시도합니다.
