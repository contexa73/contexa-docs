spring-boot-starter-contexa

문제 해결

Contexa를 설치하고 처음 기동할 때 만나는 오류를 메시지로 찾아 고치는 페이지입니다. CLI 설치 · 초기화 오류, 앱 기동 오류, 모델 · 벡터 저장소 오류, 의존성 오류 순서입니다.

먼저 볼 것

Contexa는 JDK, 전용 DB, AI 모델, (선택) Docker가 함께 맞아야 동작합니다. 문제가 생기면 먼저 두 곳을 봅니다.

  • 앱의 기동 로그: Contexa가 남기는 줄과 그 뜻은 켜졌는지 확인하기에 있습니다. 특히 ERROR 수준의 [ContexaCapability] 줄과 [Contexa] 줄을 찾으세요.
  • 연결 거부: PostgreSQL · Ollama에 연결되지 않으면 docker ps로 컨테이너가 떠 있는지와 포트(PostgreSQL 5432, Ollama 11434)를 확인하고, docker logs contexa-ollama로 Ollama 로그를 봅니다.
  • CLI 점검: contexa init --check는 프로젝트를 바꾸지 않고 Java 17 이상과 Docker만 점검하고 끝냅니다. contexa doctor는 여기에 PostgreSQL 포트와 Ollama 모델까지 점검합니다.
contexa doctor

CLI 설치 · 초기화 오류

contexa 명령을 찾지 못함

해결: 새 터미널을 열고 설치 스크립트가 끝에 알려 준 폴더가 PATH에 있는지 확인한 뒤 contexa --version으로 확인합니다. 스크립트 대신 릴리스 페이지에서 운영체제에 맞는 실행 파일을 받아 PATH에 두어도 됩니다.

Docker가 없거나 꺼져 있음

메시지: x Docker CLI is not installed. · x Docker daemon is not running. · Docker is installed but the daemon is not running.

언제: contexa init의 사전 점검(--yes가 아닐 때)과, 인프라를 만들 때(--distributed · --simulate)입니다. 인프라를 만들지 않는 기본 init에서는 점검 결과를 경고로만 보여 주고 진행합니다.

해결: Windows · macOS는 Docker Desktop을 실행하고 준비될 때까지 기다립니다. Linux는 sudo systemctl start docker. Docker 없이 진행하려면 인프라 옵션 없이 init하고 PostgreSQL을 직접 준비합니다(전용 DB 만들기). --no-docker는 Compose 파일만 만들고 컨테이너를 띄우지 않습니다.

포트가 이미 쓰이는 중

메시지: Port 5432 (PostgreSQL) is already in use on 127.0.0.1. 이어서 Local service PostgreSQL is already running on host. Contexa will skip starting this docker container and reuse the host service.

원인: 인프라를 만들 때 CLI가 PostgreSQL 5432, (Ollama를 고르면) 11434, (분산이면) Redis 6379 · Zookeeper 2181 · Kafka 9092 포트를 점검합니다. 쓰이는 포트의 서비스는 컨테이너를 만들지 않고 이미 있는 것을 다시 씁니다. 같은 이름의 컨테이너가 이미 있어도 새로 만들지 않고 다시 씁니다(Existing infrastructure detected (...); reusing it.). 그 컨테이너의 설정이 달라졌다면 docker rm -f <컨테이너 이름>으로 지우고 contexa init을 다시 실행합니다.

해결: 포트를 쓰는 서비스가 쓰려던 PostgreSQL · Ollama인지 확인하고, 그 접속 정보를 contexa.datasource.* 등 설정과 맞춥니다. 기존 서비스와 따로 연습하려면 격리 환경을 씁니다. 컨테이너 이름이 ctxa-sim-으로, 포트가 +20000(5432 → 25432, 11434 → 31434 등)으로 바뀝니다.

contexa init --simulate

Ollama 모델이 없음

메시지(contexa doctor): Ollama Model 'qwen2.5:7b' is missing.

해결: 모델을 받습니다. 임베딩 모델도 함께 받습니다.

docker exec -it contexa-ollama ollama pull qwen2.5:7b
docker exec -it contexa-ollama ollama pull mxbai-embed-large
  • 받을 모델은 앱이 쓰는 모델과 같아야 합니다. 앱이 쓰는 채팅 모델은 contexa.llm.chat.ollama.model이고(비우면 qwen3:8b), CLI가 쓴 설정에서는 환경 변수 CONTEXA_CHAT_OLLAMA_MODEL로 바뀝니다(기본 qwen2.5:7b). CLI가 받고 점검하는 모델은 다른 환경 변수 OLLAMA_CHAT_MODEL(기본 qwen2.5:7b)입니다.
  • 메모리가 작은 기계에서 가벼운 모델(예: qwen2.5:3b)을 쓰려면 두 값을 같은 모델로 맞춥니다. contexa ollama pull --chat-model qwen2.5:3b로 받을 수도 있습니다(환경 변수가 있으면 환경 변수가 우선).

contexa reset이 되돌리는 것

reset은 설치 기록을 따로 두지 않고, init이 바꾸기 전에 남긴 백업(contexa/bak/)과 정해진 규칙으로 되돌립니다.

  • 코드(-c): 백업의 원본으로 파일을 덮어씁니다. init 뒤에 직접 고친 내용도 사라집니다. 백업이 없는 빌드 파일 · 설정은 Contexa 관련 줄(contexa: 전체, spring.ai 전체 등)을 지우고, 모든 Java 파일에서 @EnableAISecurity와 그 import를 지웁니다(직접 붙인 것도). <프로젝트>/contexa 폴더를 지웁니다.
  • 인프라(-i): 프로젝트의 Compose 스택을 내리고 컨테이너 · 볼륨을 지웁니다.
  • 시뮬레이션(-s): ctxa-sim 스택과 볼륨을 지우고 코드도 되돌립니다. -a는 모두입니다.

되돌리기 전에 직접 고친 파일은 따로 보관하세요.

앱 기동 오류

contexa.datasource.url must be configured for @EnableAISecurity

전체 메시지: java.lang.IllegalStateException: contexa.datasource.url must be configured for @EnableAISecurity. Use a dedicated Contexa database by default; sharing the application database requires explicit POC approval.

원인: @EnableAISecurity를 켜면 Contexa 전용 DB 주소가 꼭 있어야 합니다.

해결: 전용 DB를 만들고(전용 DB 만들기) 주소를 적습니다. 기존 앱이라면 contexa.datasource.isolation.contexa-owned-application: true는 적지 마세요(최소 설정).

contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}

contexa.datasource must not share ...

메시지: contexa.datasource must not share spring.datasource unless contexa.datasource.isolation.allow-shared-application-datasource=true and contexa.datasource.isolation.shared-application-datasource-risk-accepted=true are both set for an approved POC, 또는 contexa.datasource must not share the application datasource in production profiles

원인: contexa.datasource.url이 앱의 spring.datasource.url과 같습니다.

해결: 전용 DB를 따로 둡니다. 시험용으로 같은 DB를 꼭 써야 하면 위 두 설정을 모두 true로 하되, prod · production 프로필에서는 그래도 거부됩니다. Contexa 소유 앱(contexa-owned-application: true)은 이 검사를 하지 않습니다.

앱의 기본 DB 연결이 없음

메시지(Spring Boot): Failed to configure a DataSource: 'url' attribute is not specified and no embedded datasource could be configured.

원인: 스타터가 JPA를 함께 가져오고, Contexa가 켜져 있으면 Spring Boot의 DB 자동 설정을 거르지 않습니다. 앱에 자기 DB 주소(spring.datasource.url)도 내장 DB도 없으면 Spring Boot가 앱의 기본 DB 연결을 만들지 못합니다.

해결: 앱용 DB 주소를 적습니다. Contexa에 로그인을 맡기는 @EnableAISecurity(mode = SecurityMode.FULL)이면 Contexa DB가 앱의 기본 연결이 되므로 이 오류가 나지 않습니다.

Contexa schema is partially installed ...

메시지: Contexa schema is partially installed without a complete ownership contract. No schema changes were applied. Restore a verified OSS backup or use a clean database.

원인: Contexa DB에 Contexa 표가 일부만 있습니다. Contexa는 이런 DB를 고치지 않고 기동을 멈춥니다. 첫 설치 뒤에도 표가 다 갖춰지지 않으면 Contexa schema is partially installed after canonical schema execution.으로 멈춥니다.

해결: 깨끗한 DB를 쓰거나 검증된 백업으로 되돌립니다. DB 계정이 vector 확장을 만들 수 있는지도 확인합니다.

Spring Boot 4.x

메시지: Contexa does not support Spring Boot 4.x. Current version: ...(ERROR 로그), Spring Boot 4.x is not supported by Contexa. Current version: ...(IllegalStateException)

해결: Spring Boot 3.x를 씁니다. Contexa는 3.5.4로 빌드 · 시험됩니다.

모든 요청이 로그인을 요구함 · HOST_OWNED mode: no SecurityFilterChain is declared

원인: 스타터가 Spring Security를 가져오므로, 자기 SecurityFilterChain이 없는 앱에는 Spring Boot 기본 보안이 걸립니다. 스타터만 넣어도(@EnableAISecurity 없이) 그렇습니다. @EnableAISecurity를 켠 기본 방식(HOST_OWNED)이면 Contexa가 기동 때 [Contexa] HOST_OWNED mode: no SecurityFilterChain is declared by the application ... ERROR 로그를 남깁니다.

해결: 앱의 SecurityFilterChain을 선언합니다. 로그에 예로 나오는 anyRequest().permitAll()만으로 끝내지 말고 관리 화면 /contexa/admin/**도 보호하세요(기존 로그인과 연결하기). 로그인을 Contexa에 맡기려면 contexa.bridge.ownership: CONTEXA_OWNED 또는 mode = SecurityMode.FULL을 씁니다.

옛 설정 이름을 알리는 ERROR 로그

메시지: Contexa legacy property prefix '<옛 접두어>*' detected. Migrate to '<새 접두어>*'. Aliases will be removed in v0.3.0.

원인: contexa.* 아래가 아닌 옛 설정 이름을 썼습니다. 지금은 새 이름으로 옮겨 읽어 주지만, 기동할 때마다 접두어마다 한 번 ERROR 로그를 남기고 v0.3.0에서 없앨 예정입니다. 새 이름에 이미 값이 있으면 새 이름의 값이 쓰입니다. 벡터 저장소 설정(spring.ai.vectorstore.pgvector.*)도 이 목록에 있어 contexa.vectorstore.pgvector.*로 쓰는 것이 맞습니다.

해결: 로그가 알려 주는 새 접두어로 바꿉니다. 옮겨 간 이름 전체는 설정 길잡이에 있습니다.

contexa.infrastructure.mode is standalone 경고

기본 인프라 모드(standalone)에서는 학습 상태가 메모리에 있어 재시작하면 사라진다는 정상 경고(WARN)입니다. 개발 중에는 그대로 두어도 됩니다. 운영에서 학습을 유지하려면 distributed로 바꿉니다.

스타터만 넣었는데 Contexa 표가 없음

@EnableAISecurity가 없는 상태(의존성만)에서는 정상입니다. 스타터만으로는 Contexa 필터 · 인증 제공자 · 표를 만들지 않습니다. 표는 Contexa가 켜진 앱이 기동할 때 Contexa DB에 만들고 검증합니다. 켠 뒤에도 표가 없으면 contexa.iam.seed.enabled가 false가 아닌지, contexa.datasource.*가 Contexa DB를 가리키는지 확인합니다.

모델 · 벡터 저장소 오류

[ContexaCapability] ... · Contexa required capability check failed.

로그 형식: [ContexaCapability] <기능> status=<상태> required=<true|false> 뒤에 Reason · Missing beans · Recommended actions가 이어집니다.

원인: 기동이 끝날 때 판정에 필요한 부품이 빠졌습니다. 로그인을 앱이 맡는 앱(WARN)은 ERROR 로그만 남기고 기동하고, Contexa 소유 앱(FAIL_FAST: contexa-owned-application: true, FULL, 또는 spring.application.name이 contexa-로 시작)은 Contexa required capability check failed.로 멈춥니다.

기능빠진 것해결
llm-runtime채팅 모델(ChatModel)Spring AI 채팅 공급자 스타터를 넣고 키 · 주소를 설정합니다(spring.ai.*, Ollama는 contexa.llm.chat.ollama.base-url도 가능).
embedding-runtime임베딩 모델(EmbeddingModel)OpenAI 또는 Ollama 임베딩을 설정합니다.
rag-vector벡터 저장소(VectorStore)org.springframework.ai:spring-ai-starter-vector-store-pgvector를 넣고, DB 연결과 vector 확장을 확인합니다.
security-learning판정 뒤 학습 부품로그가 Resolve rag-vector first라고 하면 rag-vector를 먼저 해결합니다(벡터 저장소가 있어야 만들어짐).
autonomous-decision판정 전략 또는 판정 기록 저장소채팅 모델과 벡터 저장소를 둡니다. 없으면 판정 전략이 만들어지지 않아 보호된 요청이 모두 분석 대기로 남습니다. 판정 엔진 없이 쓰려면 contexa.autonomous.enabled: false.

검사 강도는 contexa.capability.mode로 바꿉니다(기능 진단).

No Spring AI ChatModel is configured for CONTEXA

메시지(앞부분): No Spring AI ChatModel is configured for CONTEXA. Add at least one Spring AI chat provider starter to your application dependencies ... then configure the matching provider under spring.ai.*

원인: 채팅 모델 빈은 있지만 Contexa가 쓸 채팅 클라이언트 · 모델 선택을 만들지 못했습니다. 메시지는 의존성이 이미 있다면 그 공급자의 키나 주소가 실제로 설정됐는지 확인하라고 안내합니다. 공급자 스타터가 아예 없으면 이 메시지 대신 위 llm-runtime 기능 진단 결과가 나옵니다.

해결: 공급자 키는 contexa.llm 아래가 아니라 Spring AI 설정에 둡니다: spring.ai.openai.api-key, spring.ai.anthropic.api-key, Ollama는 spring.ai.ollama.* 또는 contexa.llm.chat.ollama.base-url. 공급자 순서는 contexa.llm.selection.chat.priority로 정합니다(최소 설정).

vector 확장이 없음(PostgreSQL)

해결: pgvector가 든 이미지(예: pgvector/pgvector:pg16)를 쓰거나, 기존 DB라면 권한 있는 계정으로 한 번 실행합니다. Contexa DB와, 벡터 표가 생기는 앱의 기본 DB 둘 다 필요합니다.

CREATE EXTENSION IF NOT EXISTS vector;

판정이 계속 나오지 않음

  • 집행 모드: DISABLED · OBSERVE이면 @Protectable 호출을 분석하지 않습니다. 관리 화면에 저장한 모드가 있으면 YAML보다 우선하므로 /contexa/admin/system-settings에서 확인합니다(기동 로그 System runtime settings applied to AI decision mode: ...).
  • 부품: 채팅 모델 · 벡터 저장소가 없으면 분석 대기로 남습니다(위).
  • 보호 대상: 분석되는 것은 @Protectable 메서드 호출입니다. 로그인하지 않은(익명) 호출은 분석 전에 거부됩니다.
  • 판정은 다음 요청부터: 기본 비동기 메서드는 응답 뒤에 판정하므로 그 판정은 다음 호출에 적용됩니다.

ai.ctxa 의존성을 찾지 못함

정식 0.1.0은 mavenCentral()만 있으면 됩니다. Spring milestone · snapshot이나 Sonatype snapshot 저장소를 일반 앱 빌드에 넣지 마세요. 좌표가 ai.ctxa:spring-boot-starter-contexa:0.1.0인지 확인하고, 게시 직후라면 Maven Central 동기화가 끝난 뒤 다시 시도합니다.
