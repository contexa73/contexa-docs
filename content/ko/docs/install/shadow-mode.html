관찰 모드로 안전하게 시작하기

CONTEXA는 기본값인 적용 모드에서 AI 판정을 실제 요청에 적용하므로, 잘못된 판정이 정상 사용자를 막을 수 있습니다. 도입 초기에는 관찰 모드(SHADOW)로 시작하는 것을 권장합니다. 관찰 모드는 판정을 만들어 기록하지만 그 판정으로 요청을 막지는 않습니다. 기록된 판정을 검토해 오탐(정상 사용자에게 내려진 차단이나 추가 인증)이 허용 범위인지 확인한 뒤, 적용 모드(ENFORCE)로 전환합니다.

세 가지 운영 모드

운영 모드(contexa.security.zerotrust.mode)는 두 가지를 정합니다. AI가 판정(Decision)을 만들지, 만든 판정을 실제 요청에 적용할지입니다. 판정은 AI가 한 사용자의 요청을 분석해 내리는 결론으로, 허용(ALLOW) · 추가 인증(CHALLENGE) · 검토 보류(ESCALATE) · 차단(BLOCK) 중 하나입니다. 모드를 적지 않으면 ENFORCE로 동작합니다.

처음 도입할 때는 이 순서로 운영합니다.

  1. 관찰: SHADOW로 켭니다. AI가 판정을 만들고 기록하지만 사용자의 요청은 아무것도 막히지 않습니다.
  2. 확인: 기록된 판정을 관리 화면에서 봅니다(결과 확인 위치). 정상 사용자에게 차단이나 추가 인증이 나왔을 판정이 얼마나 되는지 봅니다.
  3. 적용: 결과가 받아들일 만하면 ENFORCE로 바꿉니다. 그때부터 판정이 실제 요청에 적용됩니다.

기본값이 ENFORCE이므로 관찰부터 시작하려면 SHADOW를 직접 지정해야 합니다. 지정하는 방법은 다음 절에 있습니다.

세 모드가 하는 일은 아래 표와 같습니다.

모드설명AI 분석판정 기록 · 감사 기록적용(판정 저장 · 차단)학습
끔(DISABLED)AI 판정 기능을 끕니다.하지 않음(@Protectable 호출과 판정 API 모두)그 호출로는 남기지 않음하지 않음하지 않음
관찰 모드(SHADOW)판정을 만들고 기록하지만 아무도 막지 않습니다.함남김하지 않음. 판정은 관찰 모드 전용 기억에만 남음함: ALLOW 판정만
적용 모드(ENFORCE, 기본값)판정을 저장해 다음 요청부터 실제로 적용합니다.함남김함: 판정을 저장해 다음 요청부터 적용함: 실제로 적용된 ALLOW만

OBSERVE는 옛 설정을 위해 받아들이는 이름입니다. 설정에 적어도 DISABLED로 읽히고, 시작할 때 경고 로그를 남깁니다. 관리 화면에서는 고를 수 없습니다.

표에서 쓴 말은 이렇습니다.

  • 판정 기록 · 감사 기록: CONTEXA DB에 남는 두 기록입니다. 판정 기록(ctxa_ai_security_decision_observation)은 판정 하나하나와 그 이유이고, 감사 기록(ctxa_audit_log)은 보안 사건의 이력입니다. 로그 파일이 아니라 DB 표이므로 관리 화면에서 볼 수 있습니다.
  • 적용: 판정을 저장소에 저장해 두고 같은 사용자의 다음 요청에 쓰는 일입니다. BLOCK이면 진행 중인 응답을 끊는 신호와 차단 사용자 기록도 함께 남깁니다.
  • 관찰 모드 전용 기억: 관찰 모드가 만든 판정을 적용용 저장소와 따로 보관하는 곳입니다. 같은 사용자의 다음 요청에 AI를 또 부르지 않으려고 쓰고, 어떤 요청을 막는 데도 쓰이지 않습니다.
  • 학습: ALLOW 판정을 받은 요청의 사용 패턴(접속 시간대 · 네트워크 · 브라우저 등)을 사용자별 행위 기준선에 쌓는 일입니다. AI는 이후 판정에서 이 기준선을 참고합니다. 이미 더 엄격한 판정이 남아 있는 사용자의 ALLOW는 어느 모드에서도 학습하지 않습니다.

분석을 받는 것은 모든 요청이 아니라 @Protectable이 붙은 메서드를 호출하는 요청입니다(AI 에이전트의 요청 포함). 판정 API(AuthZEN)는 다른 시스템이 "이 사용자가 이 일을 해도 되는지"를 CONTEXA에 묻는 API이고 기본으로 꺼져 있습니다(contexa.security.zerotrust.authzen.enabled). 켰다면 이 API로 들어오는 평가 요청도 분석합니다. 로그인은 어떤 모드에서도 분석하지 않습니다. 로그인한 사용자가 처음 호출하는 보호 메서드가 그 사용자의 첫 판정이 됩니다.

저장된 판정이 적용되는 곳은 두 군데입니다. 하나는 요청이 들어올 때 CONTEXA가 거는 필터(이 문서에서는 요청 시점 필터)이고, 다른 하나는 @Protectable 메서드를 실행하기 직전의 확인입니다. 이 둘은 로그인을 앱이 맡는 경우(HOST_OWNED)와 CONTEXA가 맡는 경우(CONTEXA_OWNED) 모두에서 쓰입니다. 이 문서의 "두 소유 방식 모두"는 이 두 경우를 가리킵니다(기존 Spring Security 앱에 붙이기).

모드를 바꾸는 두 방법과 우선순위

모드는 관리 화면에서 저장하거나 application.yml에 적어서 정합니다. 둘 다 있으면 관리 화면에 저장한 값이 이깁니다. 운영 중에 모드를 바꾸려면 재시작이 필요 없는 관리 화면을 씁니다.

방법언제 적용되나우선순위
관리 화면 /contexa/admin/system-settings에서 저장바로(재시작 없음). 저장한 값은 CONTEXA DB(ctxa_system_settings)에 남고, 앱이 기동을 마칠 때마다 다시 적용됩니다. 여러 인스턴스를 contexa.infrastructure.mode: distributed로 운영하면 다른 인스턴스도 저장 신호를 받아 같은 값을 다시 적용합니다.1(가장 높음)
application.yml의 contexa.security.zerotrust.mode기동할 때 읽으므로 바꾸면 재시작해야 합니다.2: 관리 화면에 저장한 값이 없을 때만
아무것도 적지 않음—3: ENFORCE
 
contexa:
  security:
    zerotrust:
      mode: SHADOW   # DISABLED · OBSERVE · SHADOW · ENFORCE
  • 관리 화면의 선택지: 모드 선택 목록에는 "비활성", "점검 모드", "적용 모드" 세 가지만 있고(영어 화면은 "Disabled", "Shadow", "Enforce") 각각 DISABLED, SHADOW, ENFORCE입니다. OBSERVE는 선택지에 없습니다. 모드를 바꿀 때 "모드를 바꾸는 사유"를 적으면 감사 기록에 남고 적용 전환 화면의 "모드 이력"에 보입니다.
  • 미리 채워진 값: 관리 화면에 저장된 모드가 없으면 화면은 지금 적용 중인 모드를 미리 채워 보여 줍니다. 그 상태로 다른 항목만 바꿔 저장하면 모드는 저장되지 않으므로 YAML 값이 계속 이깁니다. 지금 적용 중인 모드와 다른 모드를 고르면 그때부터 DB 값이 YAML을 이깁니다. YAML과 같은 모드를 일부러 골라도 저장되지 않아 YAML이 계속 정합니다. 이미 저장된 값이 있는데 모드 칸을 비워 저장하면 SHADOW로 저장됩니다.
  • CLI의 contexa mode --shadow · --enforce는 YAML만 바꿉니다. 관리 화면에 저장한 값이 있으면 효과가 없습니다.
  • 모드를 바꾸는 순간의 분석: 각 분석 요청에는 만들어질 때의 모드가 붙어 있습니다. SHADOW일 때 만들어진 분석은 결과가 나올 무렵 모드가 ENFORCE로 바뀌었어도 적용하지 않습니다. 반대로 ENFORCE에서 만들어진 분석도 결과가 나오기 전에 모드를 SHADOW로 바꾸면 적용하지 않습니다.

SHADOW에서 실제로 일어나는 일

관찰 모드는 판정을 만들고 기록하지만 판정으로 사용자를 막지 않습니다. 동작을 세 묶음으로 정리합니다.

분석하고 기억하는 것

  • 분석 대상: 모든 요청이 아니라 @Protectable 메서드를 호출하는 요청이 분석됩니다(AI 에이전트의 요청 포함). 로그인은 분석하지 않고, 로그인 뒤 처음 호출하는 보호 메서드가 그 사용자의 첫 판정이 됩니다.
  • 남는 것: 판정 기록 표(ctxa_ai_security_decision_observation)와 감사 기록(ctxa_audit_log)에 판정이 남습니다. 로그에만 남는 것이 아닙니다.
  • 기억하고 학습하는 것: 판정은 관찰 모드 전용 기억에 남습니다. 같은 사용자의 다음 요청은 이 기억으로 답하므로 AI를 다시 부르지 않고, 그래서 관찰 기간의 AI 호출 수와 비용이 ENFORCE와 같은 수준입니다. ALLOW 판정은 ENFORCE와 동일하게 행위 기준선에 학습됩니다.
  • 지연: 기본(비동기) 메서드는 응답이 나간 뒤에 분석하므로 응답이 느려지지 않습니다. sync = true 메서드와, 아직 판정이 없는 AI 에이전트의 요청은 그 요청 안에서 판정을 기다리므로 그만큼 느려집니다.

하지 않는 것

  • 하지 않는 일: 판정을 적용용 저장소에 저장하기, 진행 중인 응답을 끊는 차단 신호 보내기, 차단 사용자 기록 남기기, 사용자의 위험도가 바뀌었음을 앱의 수신처에 알리는 위험 신호 보내기, AI 에이전트의 허용 범위 좁히기.
  • @Protectable 메서드: 이미 저장된 BLOCK · CHALLENGE · ESCALATE가 있어도 막지 않고 로그만 남긴 채 메서드를 실행합니다. sync = true는 메서드를 실행하기 전에 그 요청 안에서 판정을 기다리는 설정인데, 관찰 모드에서는 판정이 BLOCK이어도, 분석이 실패해도 메서드를 실행합니다.
  • 요청 시점 필터(두 소유 방식 모두): 아무것도 막지 않습니다. ENFORCE 기간에 저장된 BLOCK · CHALLENGE · ESCALATE와 관리자가 건 차단이 남아 있어도 SHADOW인 동안은 적용하지 않습니다. ENFORCE로 돌아오면 아직 만료되지 않은 것이 다시 적용됩니다.
  • 판정 API(AuthZEN): SHADOW에서는 분석하지만 응답의 decision은 항상 true입니다. DISABLED와 OBSERVE에서는 분석 없이 true로 답합니다.
  • 에이전트 관문(두 소유 방식 모두): AI 에이전트의 요청이 끝난 위임, 좁혀진 범위, 호출 상한에 걸리는지 확인하는 곳입니다. 적용이 꺼져 있으면(ENFORCE가 아닌 모드) 걸린 사실을 기록하고 요청을 통과시킵니다(에이전트 통제의 SHADOW).
  • 위임자 권한 재평가: AI 에이전트가 사용자를 대신해 호출할 때는 그 사용자(위임자)도 같은 호출을 할 수 있었는지 다시 평가합니다. 적용이 꺼져 있으면(ENFORCE가 아닌 모드, 또는 enabled: false) 결과를 기록만 하고 호출은 막지 않습니다.

관찰 모드에서도 막는 것

  • 로그인하지 않은 호출: 로그인하지 않았거나 익명인 사용자가 @Protectable 메서드를 호출하면 SHADOW와 ENFORCE에서는 CONTEXA가 거부합니다. DISABLED와 OBSERVE(그리고 enabled: false)에서는 CONTEXA가 거부하지 않고, 앱이 만든 보안 컨텍스트 그대로 호출이 진행됩니다. 이때도 메서드 정책은 보안 컨텍스트에 담긴 것(방문자 또는 아무도 아님)을 보고 평가합니다. 그래서 DISABLED에서 SHADOW로 바꾸면 이런 호출이 처음으로 거부될 수 있습니다.
  • 접근 정책(XACML)의 거부: 접근 정책이 거부한 호출은 모든 모드에서 거부됩니다.

결과 확인 위치

관찰 모드를 켠 뒤에는 관리 화면의 아래 위치에서 결과를 봅니다. 제로 트러스트 아래 화면은 개요, 적용 전환, 판정 기록 순서로 보면 따라가기 쉽고, 모두 ROLE_ADMIN 권한이 필요합니다.

어디무엇을 보나
제로 트러스트 → 개요 /contexa/admin/zero-trust보호 범위, 기간별 판정 수와 멈춘 요청 수(일별), 콘솔의 경고를 봅니다. 관찰 모드에서 멈춘 요청은 실제로 멈춘 수가 아니라 적용 모드였다면 멈췄을 요청 수입니다.
제로 트러스트 → 적용 전환 /contexa/admin/zero-trust/adoptionENFORCE로 넘어가도 되는지 평가합니다. 관찰 모드를 켠 뒤 쌓인 SHADOW 판정으로 평가하고, 지금이 관찰 모드가 아니면 최근 90일의 SHADOW 판정으로 평가합니다. 모드를 바꿀 때마다 적은 사유와 함께 "모드 이력"도 보여 줍니다.
제로 트러스트 → 판정 기록 /contexa/admin/zero-trust/decisions판정 하나하나와 그 이유를 봅니다. 관찰 모드에서는 아무도 막히지 않으므로, 관찰 모드에서 BLOCK이 나온 판정(재시도가 아닌 첫 분석)은 "검토 대기" 탭(?view=review)에 "차단했을 판정"(SHADOW_BLOCK)으로 올라와 관리자의 평가를 기다립니다. 이 탭에는 매일 무작위로 뽑은 "일일 표본"과, AI의 답이 판정 규칙을 어긴 "규칙 위반" 판정도 함께 올라오고, 관리자가 판정이 타당한지 평가합니다.
제로 트러스트 → 운영 상태 /contexa/admin/zero-trust/operations판정이 만들어지는 경로, 종류별 실패, AI 모델의 답 없이 정한 판정, "단계별 지연"(판정 단계마다 걸린 시간)을 봅니다.
보안 이벤트 기록 /contexa/admin/security-monitor감사 기록(ctxa_audit_log)을 바탕으로 한 보안 사건 목록
CONTEXA DB판정 기록 ctxa_ai_security_decision_observation, 감사 기록 ctxa_audit_log

적용 전환 화면의 결론은 셋 중 하나입니다.

  • RECOMMENDED: "권장 기준을 모두 충족했습니다. ENFORCE 전환을 검토해도 됩니다."
  • CONDITIONS_UNMET: "조건 {개수}개가 미달입니다. 적용을 미루십시오."
  • DATA_INSUFFICIENT: "아직 판단할 데이터가 부족합니다. 관찰 기간이나 판정 수가 권장 기준에 못 미칩니다."

관리 화면은 두 소유 방식 모두 CONTEXA가 보호합니다. 로그인을 앱이 맡으면 관리 화면에는 앱 계정이 아닌 CONTEXA 관리자 계정으로 로그인합니다(설치 가이드).

ENFORCE로 전환하기

먼저 적용 전환 화면의 결론이 RECOMMENDED인지 봅니다. CONDITIONS_UNMET이면 "기준별 현재값" 표가 미달인 기준을 보여 주고, DATA_INSUFFICIENT이면 관찰 기간이나 판정 수가 모자랍니다. 화면이 평가하는 기준과 기본 권장 값은 다음과 같습니다.

이 값들은 제품이 보장하는 값이 아니라 출발점으로 둔 권장 값입니다. 시스템 설정(Zero Trust 콘솔)이나 contexa.security.zerotrust.console.adoption.*로 바꿀 수 있습니다. 아래 항목은 팀이 직접 확인합니다.

  • SHADOW가 차단했을 판정(검토 대기열의 "차단했을 판정")을 검토했는지 확인합니다. ENFORCE에서는 그 사용자가 실제로 막힙니다.
  • 판정 종류 분포(ALLOW · BLOCK · CHALLENGE · ESCALATE)에서 정상 요청에 BLOCK · CHALLENGE가 나온 비율(오탐률)이 팀이 정한 기준(예: 1% 미만)보다 낮은지 확인합니다. 기준은 코드가 정하지 않습니다.
  • 판정 지연이 처리량에 영향을 주지 않는지 확인합니다(제로 트러스트 → 운영 상태의 "단계별 지연", 적용 전환 기준 "사용자 대기 p95(동기)").
  • BLOCK · ESCALATE가 나올 때 알림을 받을 수 있는지 확인합니다.
  • 판정 저장소가 운영에 맞는지 확인합니다. standalone(기본)은 메모리, distributed는 Redis입니다(인프라 모드).
contexa:
  security:
    zerotrust:
      mode: ENFORCE

관리 화면에 모드를 저장한 적이 있으면 YAML 대신 관리 화면에서 바꿉니다. 바꾸면 이렇게 달라집니다.

  • 이전에 ENFORCE로 운영한 적이 있으면, 그때 저장된 BLOCK · CHALLENGE · ESCALATE와 관리자 차단 가운데 만료되지 않은 것이 다시 적용됩니다.
  • 관찰 모드 전용 기억의 판정은 이어지지 않습니다. 각 사용자는 ENFORCE에서 새로 판정을 받습니다.
  • 관찰 기간에 쌓인 행위 기준선은 그대로 쓰입니다.

바뀐 뒤 저장된 판정은 이렇게 적용됩니다.

되돌리기

적용 모드에서 문제가 생기면 모드를 SHADOW로 되돌립니다. 그때부터 새 판정은 적용되지 않습니다. 방법은 네 가지이고, 아래로 갈수록 끄는 범위가 넓습니다.

방법결과
관리 화면에서 SHADOW 저장바로 적용됩니다(재시작 없음). 새 판정은 적용되지 않습니다. 판정 기록과 감사 기록은 계속 남고, ALLOW 판정은 계속 학습됩니다.
YAML contexa.security.zerotrust.mode: SHADOW재시작 뒤 적용됩니다. 관리 화면에 저장한 값이 없을 때만 효과가 있습니다.
contexa.security.zerotrust.enabled: falseAI 분석을 하지 않습니다(mode: DISABLED와 같습니다). 거기에 더해 CONTEXA가 로그인을 맡을 때 로그인 정보를 꺼내며 하는 권한 바꾸기와 세션 추적도 멈춥니다. mode: DISABLED는 이 둘을 멈추지 않습니다.
contexa.enabled: falseCONTEXA 전체를 켜지 않습니다. 앱이 직접 만든 Spring Security 필터 체인이 없으면 Spring Boot의 기본 보안이 적용됩니다.

이미 저장된 판정은 남지만, 되돌린 동안에는 적용되지 않습니다. 두 소유 방식 모두 요청 시점 필터와 @Protectable 메서드 앞의 확인은 운영 모드와 contexa.security.zerotrust.enabled를 따릅니다. 그래서 SHADOW로 바꾸거나 contexa.security.zerotrust.enabled: false로 AI 판정을 끄면 이 둘은 저장된 판정으로 아무것도 막지 않습니다(@Protectable 메서드 앞의 확인은 기록만 합니다).

바꾸기 전에 저장된 BLOCK · CHALLENGE · ESCALATE는 관리자 차단까지 포함해 그대로 남아 있다가, ENFORCE로 돌아오면 유효 시간이 지나거나 관리자가 풀기 전까지 다시 적용됩니다. 한 단계만 모드를 따르지 않습니다. CONTEXA가 로그인을 맡을 때 로그인 정보를 꺼내며 저장된 판정에 따라 권한을 줄이는 단계는 enabled: false일 때만 멈춥니다.

행위 기준선은 모드를 바꿔도 지워지지 않습니다. 다만 standalone에서는 기준선이 메모리에 있으므로 앱을 재시작하면 사라집니다. 관리 화면에서 모드를 바꾸면 재시작이 필요 없으므로 기준선을 잃지 않습니다.

참고: 판정 뒤 처리 단계

분석 요청 하나(판정 사건)는 아래 처리기를 번호 순서대로 지납니다. 관찰 모드에서 다르게 동작하는 곳은 적용 단계(55)뿐입니다. 적용 단계는 contexa.security.zerotrust.enabled가 true이고 모드가 ENFORCE일 때만 판정을 저장하고 적용합니다(isEnforcementEnabled()).

순서하는 일SHADOW에서
50판정 만들기(ProcessingExecutionHandler): AI 분석을 실행해 판정을 만듭니다.같음
55적용(SecurityDecisionEnforcementHandler): 판정 기록을 씁니다. ENFORCE면 판정 저장(writeFinalAction)도 하고, BLOCK이면 차단 표시(setBlockedFlag) · 차단 신호(registerBlockAndAwait) · 차단 사용자 기록(recordBlock)을 하며, 적용된 ALLOW를 학습합니다.판정 기록을 쓰고, 판정을 관찰 모드 전용 기억에 남기고, ALLOW를 학습합니다. 판정 저장 · 차단 표시 · 차단 신호 · 차단 사용자 기록은 건너뜁니다.
56증거 봉인(SealedEvidenceCaptureHandler): 판정의 근거(AI에게 보낸 입력 등)를 증거 묶음으로 봉인해 저장합니다. 어떤 판정을 저장할지는 표본 추출 규칙이 정합니다.같음
60감사 기록(AuditingHandler): 감사 기록을 씁니다.같음(남김)
65CONTEXA SaaS 전달(SaasForwardingHandler, 켰을 때만): ALLOW와 분석 대기를 뺀 판정을 CONTEXA SaaS로 보낼 수 있게 모읍니다.같음

각 단계는 판정 엔진에 자세히 있습니다.
