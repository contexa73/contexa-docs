사람 승인 연결하기(ApprovalService 구현)

대응 도구를 실행하기 전에 사람의 승인을 받는 흐름을 직접 붙일 때 보는 페이지입니다. 구현할 때 채워야 할 메서드, OSS가 이 서비스를 부르는 곳, 승인 데이터 형식, 알림 연결, 저장 표를 설명합니다.

OSS에는 ApprovalService 구현이 없습니다. 승인 요청을 만들고, 승인자에게 알리고, 승인을 기다렸다 대응을 이어 가는 구현은 직접 만들거나 엔터프라이즈 SOAR 모듈이 필요합니다. 인터페이스의 기본 메서드 여러 개는 UnsupportedOperationException을 던집니다.

지금 OSS에서 동작하는 사람 승인: 차단 해제

OSS에서 실제로 동작하는 사람 승인은 SOAR가 아니라 관리자의 차단 해제입니다. 관리자가 관리 콘솔에서 차단된 사용자를 풀면 Contexa가 그 결정을 기록하고 배웁니다.

  • 차단당한 요청의 사실로 그 사용자의 행위 기준선을 학습합니다.
  • 관리자 재정의를 감사 기록에 남깁니다.
  • Contexa SaaS 연결에서 판정 피드백 · 위협 결과 채널을 켰으면 그 결과를 보냅니다(Contexa SaaS 연결, 기본 꺼짐).

차단 · 차단 해제 흐름은 요청 시점 집행과 관리 콘솔에 있습니다.

OSS가 이 서비스를 부르는 곳

빈은 선택 주입(@Autowired(required = false))이라, 앱이 ApprovalService 빈 하나를 두면 2차 분석이 받습니다. 구현한 서비스는 이 호출보다는 직접 만든 SOAR 흐름(SOAR 확장점)에서 쓰게 됩니다.

구현 체크리스트

추상 메서드 다섯 개는 반드시 구현합니다. 기본 메서드는 예외를 던지는 것이 많으니, 쓰려는 것은 재정의합니다.

승인 데이터

ApprovalRequest

io.contexa.contexacore.domain의 직렬화 가능한 값 객체입니다. 주요 필드:

필드뜻
requestId요청 ID. create(...)로 만들면 APR-<현재 밀리초>(예: APR-1709942400000)
sessionId · incidentId · organizationId세션 · 사건 · 조직
toolName · actionType · parameters · reason · potentialImpact무엇을 왜 하려는지
approvalType · status승인 유형 · 상태(아래 표)
requestedAt · requestedBy · approvedAt · approvedBy · rejectionReason요청 · 처리 기록
requiredRoles승인할 수 있는 역할
requiredApprovers필요한 승인자 수. 이 값을 읽는 OSS 코드는 없습니다
approvalTimeout승인 제한 시간(분). getTimeoutMinutes() · 빌더 timeoutMinutes(...)와 같은 값
metadata그 밖의 값(빌더의 toolDescription · riskAssessment가 여기에 들어감)

상태를 바꾸는 메서드는 지금 상태를 확인하지 않고 값만 바꿉니다.

  • approve(approver): APPROVED, 처리자 · 처리 시각 기록. reject(approver, reason): REJECTED와 거절 사유.
  • expire() · cancel(): EXPIRED · CANCELLED. 대기 중이 아니어도 바꿉니다.
  • addApproval(approver, name, role, comments): 이름 · 역할 · 의견을 저장하지 않고 첫 호출에 바로 APPROVED가 됩니다. 여러 승인자의 승인을 세지 않으므로, 다중 승인은 구현에서 직접 셉니다.
  • isAutoApprovable(): 승인 유형이 AUTO이면 참.
// 정적 생성: requestId = "APR-<밀리초>", status = PENDING, requestedAt = 지금
ApprovalRequest request = ApprovalRequest.create(
        "session-123", "session_termination", Map.of("userId", "alice"), "Repeated unblock MFA failures");

// 빌더: build()가 requestedAt을 지금으로 두고 requiredRoles를 빈 집합으로 둡니다.
// status는 빌더에서 정하지 않으면 비어 있으므로 직접 정합니다.
ApprovalRequest built = ApprovalRequest.builder()
        .requestId("APR-" + System.currentTimeMillis())
        .sessionId("session-123")
        .toolName("session_termination")
        .toolParameters(Map.of("userId", "alice"))
        .approvalType(ApprovalRequest.ApprovalType.MANUAL)
        .status(ApprovalRequest.ApprovalStatus.PENDING)
        .requestReason("Repeated unblock MFA failures")
        .timeoutMinutes(30)
        .build();

승인 유형 ApprovalType과 상태 ApprovalStatus

열거형값(코드의 설명)
ApprovalRequest.ApprovalTypeAUTO(Auto Approval) · MANUAL(Manual Approval Required) · SINGLE(Single Approval) · MULTI(Multi Approval Required) · UNANIMOUS(Unanimous) · EMERGENCY(Emergency Approval)
ApprovalRequest.ApprovalStatusPENDING(대기) · APPROVED(승인) · REJECTED(거절) · EXPIRED(만료) · CANCELLED(취소)

유형마다 다르게 처리하는 코드(다중 · 만장일치 집계, 긴급 절차)는 OSS에 없습니다. 유형은 구현이 처리 방법을 고르는 표지로 씁니다. @SoarTool의 승인 요구 수준이 어떤 유형으로 바뀌는지는 @SoarTool과 도구 승인 등급에 있습니다.

ApprovalRequestDetails

requestApproval(SoarContext, ApprovalRequestDetails)에 넘기는 직렬화 가능한 레코드(io.contexa.contexacore.soar.approval)입니다. 필드: actionName · actionType · riskLevel · description · arguments(문자열) · parameters(맵).

ApprovalRequestDetails details = new ApprovalRequestDetails(
        "session_termination",            // actionName
        "CONTAINMENT",                    // actionType
        "HIGH",                           // riskLevel
        "Terminate every session of alice",
        "userId=alice",                   // arguments
        Map.of("userId", "alice"));       // parameters

String approvalId = approvalService.requestApproval(soarContext, details);   // 앱이 구현한 빈

알림 받기: SoarApprovalNotifier

io.contexa.contexacore.autonomous.notification의 인터페이스로, 메서드는 receiveApprovalNotification(String message)와 sendApprovalReminder(String approvalId) 둘입니다. OSS 구현은 없습니다.

  • 분산 모드(contexa.infrastructure.mode=distributed)에서 Redis 구성이 켜지고(Redisson 라이브러리와 Redis 연결이 있을 때) 이 빈이 있으면, Redis 채널 soar:approval:requests의 메시지가 receiveApprovalNotification으로 전달됩니다.
  • 이 채널에 메시지를 보내는 OSS 코드는 없습니다. 보내는 쪽(승인 요청을 만들 때 발행)과 메일 · 메신저 알림은 구현자의 몫입니다.
  • sendApprovalReminder를 부르는 OSS 코드도 없습니다.

저장

OSS 스키마는 승인용 표 6개(soar_approval_policies, soar_approval_requests, soar_approval_steps, soar_approval_assignments, soar_approval_votes, approval_notifications)를 만들고, 엔티티(ApprovalPolicyEntity · SoarApprovalRequest · SoarApprovalStep · SoarApprovalAssignment · SoarApprovalVote · ApprovalNotification)와 저장소도 들어 있습니다. 하지만 이 표에 쓰거나 읽는 OSS 코드는 없습니다(빈으로 등록되는 저장소는 ApprovalPolicyRepository 하나이고, 그것도 쓰는 곳이 없음). 승인 기록을 DB에 두려면 구현에서 저장소를 직접 연결합니다.

최소 구현 예

승인 요청을 메모리에 두는 가장 작은 구현입니다. 실제로는 저장(DB)과 승인자 알림을 더합니다.

import io.contexa.contexacore.domain.ApprovalRequest;
import io.contexa.contexacore.domain.SoarContext;
import io.contexa.contexacore.soar.approval.ApprovalRequestDetails;
import io.contexa.contexacore.soar.approval.ApprovalService;
import org.springframework.stereotype.Service;

import java.util.Map;
import java.util.Set;
import java.util.UUID;
import java.util.concurrent.ConcurrentHashMap;
import java.util.stream.Collectors;

@Service
public class InMemoryApprovalService implements ApprovalService {

    private final Map<String, ApprovalRequest> requests = new ConcurrentHashMap<>();

    @Override
    public String requestApproval(SoarContext soarContext, ApprovalRequestDetails details) {
        String approvalId = "APR-" + UUID.randomUUID();
        ApprovalRequest request = ApprovalRequest.builder()
                .requestId(approvalId)
                .sessionId(soarContext.getSessionId())
                .toolName(details.actionName())
                .actionDescription(details.description())
                .toolParameters(details.parameters() != null ? details.parameters() : Map.of())
                .status(ApprovalRequest.ApprovalStatus.PENDING)
                .build();
        requests.put(approvalId, request);
        // 승인자에게 알리는 코드(메일 · 메신저)를 여기에 둡니다.
        return approvalId;
    }

    @Override
    public ApprovalRequest.ApprovalStatus getApprovalStatus(String approvalId) {
        ApprovalRequest request = requests.get(approvalId);
        return request != null ? request.getStatus() : null;
    }

    @Override
    public void handleApprovalResponse(String approvalId, boolean isApproved, String comment, String reviewer) {
        ApprovalRequest request = requests.get(approvalId);
        if (request == null || request.getStatus() != ApprovalRequest.ApprovalStatus.PENDING) {
            return;   // ApprovalRequest는 상태를 검사하지 않으므로 여기서 막습니다.
        }
        if (isApproved) {
            request.approve(reviewer);
        } else {
            request.reject(reviewer, comment);
        }
    }

    @Override
    public Set<String> getPendingApprovalIds() {
        return requests.values().stream()
                .filter(r -> r.getStatus() == ApprovalRequest.ApprovalStatus.PENDING)
                .map(ApprovalRequest::getRequestId)
                .collect(Collectors.toSet());
    }

    @Override
    public int getPendingCount() {
        return getPendingApprovalIds().size();
    }

    @Override
    public ApprovalRequest getApprovalRequest(String approvalId) {
        return requests.get(approvalId);
    }
}
