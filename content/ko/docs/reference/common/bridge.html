기존 로그인과 연결하기(인증 브리지)

앱이 이미 가진 로그인 정보를 CONTEXA가 요청마다 받아 판정의 사실로 쓰게 하는 방법입니다. 앱이 CONTEXA에 넘기는 값은 요청의 사용자 ContexaSubject 하나이고, 아이디와 메일이 필수, 나머지는 선택입니다. Spring Security를 쓰는 앱과 쓰지 않는 앱이 각각 무엇을 하는지, CONTEXA가 어떤 순서로 읽는지, MFA를 어떻게 알려 주는지, 선택 API(ContexaBridge · ContexaUsers), 확인 결과와 확장점을 설명합니다.

이 페이지의 용어. ContexaSubject는 앱이 CONTEXA에 알리는 요청의 사용자입니다. 아이디와 메일이 필수이고, 표시 이름 · 조직 · 테넌트 · 권한 · 로그인 방식 · 세션 키 · 위임은 선택입니다. 신원은 CONTEXA가 요청마다 사용자를 확인한 결과로, 그 사용자 · 출처(어디서 읽었나) · 확인 결과를 담습니다. 리졸버(ContexaSubjectResolver)는 Spring Security를 쓰지 않는 앱이 자기 로그인 상태에서 요청의 사용자를 꺼내 주는 빈입니다. 신뢰 프록시는 X-Forwarded-For 헤더에 담긴 클라이언트 IP를 믿어도 되는 서버(로드 밸런서, API 게이트웨이 등)입니다. 사용자 사본은 앱에서 로그인한 사용자를 CONTEXA DB의 사용자 표에 남기는 행입니다. 보안 모드(SANDBOX · FULL)와 인증 소유권(HOST_OWNED · CONTEXA_OWNED)은 공통 계약에 있습니다.

개요

CONTEXA를 기본 모드(@EnableAISecurity, 앱이 로그인을 맡는 SANDBOX)로 켜면 로그인은 앱이 원래 하던 방식(Spring Security, 또는 앱 자체 세션 · 토큰) 그대로 맡습니다. CONTEXA는 요청마다 인증 브리지(BridgeResolutionFilter)로 그 요청의 사용자를 ContexaSubject로 받아 신원을 만들고, 로그인 방식 · MFA 여부 · 권한 · 위임을 판정 프롬프트의 사실로 싣습니다.

앱이 해 두어야 할 일

앱이 CONTEXA에 넘기는 값은 요청의 사용자 ContexaSubject 하나입니다(넘기는 값). 넘기는 방법은 앱이 로그인에 Spring Security를 쓰는지에 따라 다릅니다.

  1. 로그인한 사용자를 알려 줍니다. Spring Security를 쓰는 앱은 따로 할 일이 없습니다(Spring Security를 쓰는 앱). 쓰지 않는 앱은 리졸버나 요청 속성으로 넘깁니다(리졸버, 요청 속성). 사용자를 확인하지 못한 요청(신원 없음)에서 부른 보호 메서드(@Protectable)는 SHADOW · ENFORCE(기본은 ENFORCE)에서 거부되며 DISABLED(옛 이름 OBSERVE 포함)에서는 거부되지 않습니다.
  2. 메일을 알려 줍니다. 추가 인증 코드가 이 주소로 갑니다. 메일이 없어도 신원은 성립하지만, 그 사용자에게는 메일로 추가 인증 코드를 보낼 수 없습니다.
  3. MFA와 로그인 방식을 알려 줍니다(선택). OAuth2 · OIDC 토큰이라면 표준 클레임(amr · acr · auth_time)으로 충분합니다. 폼 로그인처럼 표준 클레임이 없으면 Authentication의 details에 ContexaAuthentication을 두거나 요청 속성 ctxa.context.authenticationType · ctxa.context.mfaVerified를 넣습니다. 리졸버 · 요청 속성으로 넘기는 앱은 ContexaSubject에 ContexaAuthentication을 담습니다(MFA 알려 주기).
  4. 권한과 위임은 선택입니다. Spring Security를 쓰는 앱은 Authentication의 권한과 접근 토큰의 위임 클레임을 그대로 읽습니다. 리졸버 · 요청 속성으로 넘기는 앱은 ContexaSubject의 authorities · delegation에 담습니다. CONTEXA는 권한의 뜻을 해석하지 않고 판정에 참고 사실로 보입니다.
  5. Spring Security 체인. 앱 사용자(UserDetailsService 등)는 있는데 앱의 체인이 없으면 Spring Boot 기본 보안(모든 요청 인증)이 걸리고, CONTEXA가 시작할 때 경고 로그로 알려 줍니다. 앱에 체인도 사용자도 없으면 CONTEXA가 Spring Boot 기본 보안 대신 모든 요청을 들이는 격리 체인을 두어, CONTEXA를 넣기 전의 접근이 그대로 유지됩니다.
로그인에 Spring Security를 쓰지 않는 앱. @EnableAISecurity는 Spring Security 라이브러리를 요구하므로 의존성(spring-boot-starter-security)은 앱이 직접 넣습니다. 그 밖에 체인을 선언하거나 SecurityContext를 채울 필요는 없습니다. 기존 로그인이 확인한 사용자를 리졸버로 알려 주거나, 기존 인증 필터에서 요청 속성에 넣습니다. SANDBOX에서 앱에 체인도 사용자도 없으면 CONTEXA가 필터 없는 격리 체인을 두므로 기존 접근 규칙이 그대로입니다. 다만 Spring Security의 표준 방화벽(StrictHttpFirewall)은 체인과 상관없이 모든 요청에 적용되어, 예를 들어 경로에 ;jsessionid=나 //가 든 요청은 400으로 거부됩니다. 바꾸려면 Spring 표준 방법(HttpFirewall 빈)을 씁니다.

브리지가 하지 않는 일

  • SANDBOX에서는 앱의 인증 · 인가 · 세션에 관여하지 않습니다. 세션에 저장하지 않고, 헤더를 쓰지 않습니다.
  • 앱 고유 객체(세션의 사용자 객체, 표준 형식이 아닌 principal)의 필드를 추측해 사용자를 정하지 않습니다. 사용자는 앱이 넘긴 ContexaSubject와 Spring Security의 표준 형식에서만 읽습니다.
  • 브리지 필터는 두 모드 모두 앱의 보안 체인과 서블릿 필터가 모두 끝난 뒤에 실행되는 서블릿 필터로 등록됩니다. CONTEXA 서블릿 필터 등록 contexaFilterSlot은 서블릿 표준의 "다른 모든 필터 매핑 뒤"로 매핑되어 앱의 필터가 앱이 준 순서와 상관없이 모두 먼저 돌고, 브리지는 그 안에서 첫째입니다(CONTEXA 적용 필터보다 앞). 그래서 CONTEXA 적용 필터 · 컨트롤러 · @Protectable 메서드에서는 신원을 읽을 수 있지만, 앱 체인 안의 URL 인가 단계에서는 아직 신원이 없습니다. FULL에서는 CONTEXA 체인 안에도 들어갑니다(세션 흐름은 SecurityContextHolderFilter 다음, 토큰 흐름은 BearerTokenAuthenticationFilter 다음). 한 요청에서는 한 번만 돕니다.
  • 예외: 사용자 사본은 SANDBOX에서도 CONTEXA DB에 사용자 행을 씁니다.

어디서 어떤 순서로 읽나

CONTEXA는 contexa.bridge.identity-sources의 출처를 차례로 시도하고, 처음으로 사용자를 정한 출처가 그 요청의 신원이 됩니다. 사용자가 없는 출처는 건너뜁니다.

순서(기본)출처읽는 것기록되는 출처 이름
1spring-security앱의 Spring Security가 로그인시킨 사용자(SecurityContext의 인증된 Authentication). CONTEXA 자신의 계정(관리 콘솔의 관리자 등)이면 그 계정으로, 다음으로 앱의 ContexaSubjectMapper, 그다음 표준 형식으로 읽습니다.SPRING_SECURITY(CONTEXA 계정은 CONTEXA_ACCOUNT)
2resolver앱의 ContexaSubjectResolver 빈. 요청당 한 번만 부르고, 앞 출처가 사용자를 정했으면 부르지 않습니다.RESOLVER
3request-attribute앱이 요청 속성 ctxa.subject(ContexaSubject.REQUEST_ATTRIBUTE)에 넣은 ContexaSubject. 앞 출처가 사용자를 정했어도 읽어서, 두 출처가 서로 다른 사용자를 알리면 문제(SOURCES_DISAGREE)로 알립니다. 이때는 앞 출처의 사용자를 씁니다.REQUEST_ATTRIBUTE

신원에는 출처와 확인 결과가 함께 기록되어 판정 이벤트와 관리 콘솔의 사용자 연동 상태 화면에 남습니다. 순서는 contexa.bridge.identity-sources로 바꾸며, 모르는 이름을 적거나 하나도 남기지 않으면 시작이 거부됩니다. 리졸버 · 요청 속성으로 넘긴 사용자는 SANDBOX에서 CONTEXA만의 신원으로 요청 안에만 두고 SecurityContext에 넣지 않습니다. FULL에서는 CONTEXA 주 체인이 로그인시킨 사용자를 읽습니다.

권한은 Spring Security를 쓰는 앱이면 Authentication의 권한(getAuthorities())에서, 리졸버 · 요청 속성이면 ContexaSubject의 authorities에서 읽습니다. 위임은 접근 토큰의 클레임(act 등, contexa.bridge.delegation.token.*)에서 먼저 읽고, 승인된 에이전트의 자기 계정이면 그 계정에서 찾습니다(에이전트 보안). 리졸버 · 요청 속성으로 넘기는 앱은 ContexaSubject의 delegation(ContexaDelegation)에 담습니다.

넘기는 값: ContexaSubject

레거시 앱이 CONTEXA에 알리는 사용자입니다(패키지 io.contexa.contexacommon.security.bridge.subject). 만들 때 예외를 던지지 않고, 규칙을 어긴 값은 getProblems()에 문제로 담깁니다. 값의 앞뒤 공백은 지우고, 아이디의 대소문자는 준 그대로 둡니다.

ContexaSubject subject = ContexaSubject.of(userId, email)
        .displayName(name)
        .authentication(ContexaAuthentication.of("PASSWORD+OTP").mfa(true).authenticatedAt(loginAt))
        .build();
필드필수규칙어기면
userId필수비어 있지 않고 255자 이하, 제어 문자 없음그 요청은 CONTEXA 신원 없이 앱 그대로 진행합니다(INVALID).
email필수주소 형식(@ 하나, 공백 · 제어 문자 없음), 255자 이하신원은 성립하고 메일 결손(EMAIL_MISSING · EMAIL_MALFORMED · EMAIL_TOO_LONG)만 표시됩니다. 메일로 추가 인증 코드를 보낼 수 없습니다.
displayName선택100자 이하, 제어 문자 없음그 값만 빠지고, 신원은 그대로 성립합니다. 문제로 기록됩니다.
organizationId · tenantId선택각 255자 이하, 제어 문자 없음. 다중 조직 · 테넌트에서 사용자를 구분
authorities선택최대 256개, 각 255자 이하. CONTEXA는 뜻을 해석하지 않습니다
authentication선택ContexaAuthentication: 로그인 방식(method, 64자 이하) · MFA 여부(mfa) · 인증 시각(authenticatedAt) · 보증 수준(assurance, 64자 이하)
sessionKey선택255자 이하. 로그인 하나를 가리키고 토큰을 갱신해도 바뀌지 않는 값(세션이 없는 앱)
delegation선택ContexaDelegation: 에이전트 ID(없으면 위임이 빠짐) · 목적 · 허용 작업 · 허용 자원(각 최대 64개) · 승인 필요 · 만료 시각

아이디는 판정 · 차단 · 사용자 사본의 키가 되므로 한 사람에게 늘 같은 값(예: 로그인 아이디)을 씁니다. 판정 · 사용자 사본 · 추가 인증은 아이디를 같은 규칙으로 비교합니다(유니코드 NFKC 정규화와 대소문자 무시, contexa.security.zerotrust.normalize-user-keys=false로 끔).

Spring Security를 쓰는 앱

로그인은 지금처럼 앱의 Spring Security가 맡고, CONTEXA는 SecurityContext의 인증된 Authentication을 읽습니다. 아이디는 늘 Authentication.getName()이고, 메일은 contexa.bridge.email-sources 순서(기본: 클레임 email, 다음 메일 공급자 빈)로 찾습니다.

로그인 형태아이디메일
폼 · Basic · 자동 로그인 등(principal이 UserDetails나 문자열)getName()BridgeUserEmailProvider 빈
리소스 서버의 JWT · 불투명 토큰getName()(JWT는 기본 sub)토큰의 email 클레임, 없으면 메일 공급자
OAuth2 · OIDC 로그인getName()사용자 속성의 email, 없으면 메일 공급자

폼 로그인의 UserDetails처럼 로그인 정보에 메일이 없으면 메일 공급자 빈 하나를 둡니다. 메일이 없는 사용자의 요청에서 불리므로 빠르게 답해야 합니다. 리졸버 · 요청 속성으로 넘긴 사용자에게 메일이 없을 때도 같은 빈에 묻습니다.

@Bean
BridgeUserEmailProvider contexaEmailProvider(EmployeeRepository employees) {
    return userId -> employees.findEmailByLoginId(userId);
}

principal이 Spring Security의 표준 형식(UserDetails · Principal · 문자열 · OAuth2 토큰 · 로그인 등)이 아닌 앱 고유 객체라면 CONTEXA는 그 필드를 읽지 않고, 그 요청은 신원 없이 진행합니다(UNSUPPORTED_PRINCIPAL). 이 문제는 [Contexa] Bridge: the signed-in Spring Security principal is of none of the kinds Spring Security names a user by ...(ERROR) 로그로 1분에 한 번까지 남습니다(확인 결과). 이때 ContexaSubjectMapper 빈으로 직접 바꿔 줍니다. 빈 값을 돌려주면 CONTEXA가 표준 형식으로 읽습니다.

@Bean
ContexaSubjectMapper contexaSubjectMapper() {
    return authentication -> authentication.getPrincipal() instanceof MyLoginUser user
            ? Optional.of(ContexaSubject.of(user.getEmpNo(), user.getMail()).build())
            : Optional.empty();
}
  • 매퍼 빈이 둘 이상이면 시작이 거부됩니다. 매퍼가 예외를 던지면 CONTEXA가 잡고, 그 요청은 신원 없이 진행합니다(FAILED).
  • SANDBOX에서 인터셉터나 컨트롤러가 브리지 필터보다 늦게 로그인시키면, @Protectable 메서드가 불릴 때 다시 읽어 판정합니다(리졸버는 다시 부르지 않습니다).

Spring Security를 쓰지 않는 앱: 리졸버

앱이 ContexaSubjectResolver를 빈 하나로 구현합니다. 구현은 앱의 로그인 상태(세션 객체, 자체 토큰 검증, 서블릿 컨테이너의 사용자)에서 요청의 사용자를 꺼내 돌려줍니다.

@Component
class SessionLoginResolver implements ContexaSubjectResolver {

    @Override
    public Optional<ContexaSubject> resolve(ContexaRequestView request) {
        return request.sessionAttribute("loginVO", LoginVO.class)
                .map(vo -> ContexaSubject.of(vo.getLoginId(), vo.getEmail())
                        .displayName(vo.getName())
                        .build());
    }
}
  • 부르는 때: 앱의 서블릿 필터가 모두 끝난 뒤 요청마다 한 번 부르고, 같은 요청의 포워드 · 인클루드 · 비동기 · 오류 디스패치에서는 처음 답을 다시 씁니다.
  • 요청 보기 ContexaRequestView는 읽기 전용입니다. method() · path() · header(name) · headers(name) · cookie(name) · attribute(name[, type]) · sessionAttribute(name[, type]) · sessionId() · remoteUser() · userPrincipal()를 씁니다. 세션은 만들지 않고, 본문과 파라미터는 읽을 수 없습니다(멀티파트나 스트림을 직접 읽는 앱을 보호하기 위해서입니다).
  • 빈 답: 로그인하지 않은 요청입니다. 앱이 로그아웃하면 빈 값을 돌려주면 됩니다. CONTEXA는 앱의 세션에 아무것도 쓰지 않으므로 신원이 앱의 로그인보다 오래 남지 않습니다.
  • 예외와 지연: 리졸버가 예외를 던지면 CONTEXA가 잡고, 그 요청은 신원 없이 앱 그대로 진행합니다(FAILED). 걸린 시간을 재어 contexa.bridge.resolver.slow-threshold(기본 100ms)를 넘으면 알리며(RESOLVER_SLOW), 호출을 끊지는 않습니다.
  • 다른 로그인 방식: 서블릿 컨테이너 인증을 쓰는 앱은 request.remoteUser()를 씁니다. 게이트웨이 헤더를 쓰는 앱은 게이트웨이를 검증하는 자기 코드를 거친 값만 돌려줍니다. CONTEXA는 헤더를 직접 믿지 않습니다.
  • 정적 자원처럼 리졸버를 부를 필요가 없는 경로는 contexa.bridge.resolver.exclude-paths(서블릿 경로의 Ant 패턴)로 뺍니다. 리졸버 빈이 둘 이상이면 시작이 거부됩니다.

자기 필터에서 요청 속성으로 넘기기

요청마다 인증 필터를 이미 도는 앱은 그 필터에서 요청 속성에 넣어도 됩니다. CONTEXA는 앱의 서블릿 필터가 모두 끝난 뒤 읽으므로 CONTEXA와의 순서는 신경 쓰지 않아도 됩니다. 넣는 코드는 앱이 사용자를 확인한 뒤에 돌아야 합니다.

request.setAttribute(ContexaSubject.REQUEST_ATTRIBUTE,
        ContexaSubject.of(user.getLoginId(), user.getEmail()).build());
  • 값은 ContexaSubject여야 합니다. 다른 타입이면 읽지 않고 문제(NOT_A_SUBJECT)로 알리며, 그 요청은 신원 없이 진행합니다(INVALID).
  • 클라이언트는 요청 속성을 넣을 수 없으므로, 이 값은 앱의 코드만 정합니다.
  • 리졸버와 함께 쓰면 기본 순서상 리졸버가 먼저이고, 둘이 다른 사용자를 알리면 SOURCES_DISAGREE로 알립니다(읽는 순서).

MFA와 로그인 방식 알려 주기

로그인 방식 · MFA 여부 · 인증 시각 · 보증 수준은 모두 선택이며, 알려 준 것만 판정에 사실로 실립니다. Spring Security를 쓰는 앱은 아래 순서로 읽습니다.

  1. Authentication의 details에 ContexaAuthentication이 있으면 그것을 씁니다. 폼 로그인처럼 표준 클레임이 없을 때 앱이 직접 적는 방법입니다.
  2. 없으면 토큰의 표준 클레임에서 읽습니다. amr(RFC 8176)에서 로그인 방식과 MFA 여부를 계산하고(출처는 DERIVED_FROM_AMR로 표시), auth_time은 인증 시각, acr은 보증 수준입니다.
  3. 둘 다 없으면 요청 속성을 읽습니다. 앱의 필터가 ctxa.context.authenticationType(로그인 방식)과 ctxa.context.mfaVerified(true · false)에 넣은 값입니다.

판정 프롬프트에 싣는 로그인 사실은 Authentication의 details와 principal에서 정해진 키 이름으로 찾습니다. 앱이 MFA 완료나 로그인 방식을 다른 이름으로 두면 그 이름을 키 이름 설정에 더합니다.

amr 값로그인 방식
pwdPASSWORD
otp, sms, telONE_TIME_CODE
pop, hwk, swkPASSKEY
face, fpt, iris, retina, vbmBIOMETRIC
  • MFA 완료 규칙: amr에 mfa가 있거나, 서로 다른 방식이 2개 이상이면 완료입니다. 예: ["pwd","otp"] → MFA 완료, 방식 PASSWORD+ONE_TIME_CODE. ["otp","sms"] → 같은 방식 하나라 MFA 아님.
  • 인증 시각은 ContexaAuthentication의 authenticatedAt이나 토큰의 auth_time에서 읽습니다. 토큰 발급 시각(iat)은 다시 발급될 때 바뀌므로 일부러 쓰지 않습니다. Spring Security 로그인에서 읽은 인증 시각이 이 서버의 지금 시각보다 60초 넘게 뒤(미래)면 판정 입력에서 뺍니다.
  • 보증 수준은 ContexaAuthentication의 assurance나 토큰의 acr에서 읽고, amr로 계산하지 않습니다.
  • 리졸버 · 요청 속성으로 넘기는 앱은 ContexaSubject의 authentication에 ContexaAuthentication을 담습니다. amr을 해석하지 않으므로 MFA 여부는 mfa(true)로 직접 적고, 서로 다른 인증 수단을 둘 이상 확인했을 때만 true로 적습니다.

선택 API: 로그인 · 로그아웃 · 퇴사 알리기

모두 선택입니다. CONTEXA는 이 호출 없이도 동작하고, 호출하면 Spring Security를 쓰지 않는 앱에서 앱만 아는 순간(로그인 성공 · 실패 · 로그아웃)이 판정에 더해집니다. Spring Security로 로그인하는 앱은 부를 것이 없습니다. CONTEXA가 Spring Security의 로그인 · 로그아웃 이벤트를 듣습니다.

ContexaBridge.signedIn(request, ContexaSubject.of(user.getLoginId(), user.getEmail()).build());
ContexaBridge.signInFailed(request, loginId);
ContexaBridge.signedOut(request, user.getLoginId());
ContexaUsers.delete(user.getLoginId());
API부르는 곳CONTEXA가 하는 일
ContexaBridge.signedIn(request, subject)로그인이 성공한 자리. 앱이 세션 ID를 바꾼 뒤그 사용자를 요청의 신원으로 두고, 사용자 사본을 기다려(최대 1초) 로그인 시각과 함께 만들거나 고칩니다. 로그인 사실을 판정에 한 번 보냅니다.
ContexaBridge.signInFailed(request, userId)로그인이 실패한 자리그 사용자의 로그인 실패로 셉니다(판정의 실패 횟수).
ContexaBridge.signedOut(request, userId)로그아웃한 자리그 요청 세션의 추적을 끝내고, 로그인 때 기억한 것을 놓습니다. 차단 · 추가 인증 · 검토 제한은 남습니다.
ContexaUsers.delete(userId)퇴사 · 삭제(요청 밖에서도)사용자 사본과 그 사용자의 판정 상태를 모두 지웁니다. 같은 아이디가 다시 오면 새 사용자로 봅니다. 관리 콘솔에서 지울 수도 있습니다.
  • 모든 호출은 예외를 던지지 않고 결과 ContexaBridgeResult의 outcome으로 알립니다. 결과에 상관없이 앱의 요청은 그대로 진행합니다.
  • DONE: 한 일. NOT_APPLICABLE: FULL처럼 CONTEXA가 직접 로그인 · 로그아웃시키는 모드라 할 일이 없음(ContexaBridge의 세 호출). NOT_INITIALIZED: CONTEXA가 시작 전이거나 이 앱에서 켜지지 않음. INVALID: 요청이나 사용자가 없거나 아이디 규칙 위반. FAILED: CONTEXA가 하지 못함.
  • 결과의 reason은 앱의 로그에 남기기 위한 이유이고, 아이디와 메일은 들어가지 않습니다.

확인 결과와 사용자 연동 상태 화면

CONTEXA는 요청의 사용자를 확인할 때마다 네 결과 가운데 하나를 남깁니다. 어떤 결과든 앱의 요청은 실패하지 않습니다.

결과뜻그 요청
RESOLVED신원 성립. 메일이 없으면 메일 결손이 함께 표시됩니다CONTEXA가 그 사용자로 판정합니다.
ABSENT로그인하지 않은 요청CONTEXA 신원 없이 앱 그대로 진행합니다. 이 요청에서 부른 @Protectable 메서드는 앱이 해 두어야 할 일의 규칙대로 거부됩니다.
INVALID앱이 넘긴 사용자가 표준을 어김(아이디 규칙 위반, CONTEXA가 읽지 않는 principal, 요청 속성의 값이 ContexaSubject가 아님)
FAILED앱의 리졸버나 매퍼에서 예외

CONTEXA는 결과 · 출처 · 문제(SubjectProblem)를 종류별로 세고, 같은 문제는 1분에 한 번 오류 로그로 남깁니다(아이디와 메일은 쓰지 않음). 관리 콘솔의 사이드바 제로 트러스트 → 사용자 연동 상태(/contexa/admin/zero-trust/bridge)에서 확인 결과, 확인 경로(출처), 발생한 문제와 권장 조치, 합치지 못한 사용자를 봅니다. 숫자는 그 서버(노드)가 시작한 뒤부터 센 값입니다.

사용자 사본: 로그인한 사용자를 CONTEXA DB에 남기기

브리지는 앱에서 로그인한 사용자를 CONTEXA DB의 사용자 표에 사본 행으로 남깁니다. 관리 콘솔 · 정책에서 그 사용자를 다루기 위해서입니다. 동작은 다음과 같습니다.

  • 키와 비밀번호: 행의 키는 brg_ + SHA-256(SUBJECT | 조직(없으면 GLOBAL) | 사용자 ID)입니다. 사용자 ID는 판정과 같은 규칙(NFKC 정규화와 대소문자 무시)으로 맞춘 값입니다. 신원의 출처(Spring Security · 리졸버 · 요청 속성)는 키에 들어가지 않습니다. 비밀번호는 무작위 값이어서 이 행으로는 직접 로그인할 수 없습니다.
  • 다시 쓰는 때: 사본이 저장하는 값(아이디와 로그인 출처, 표시 이름, 로그인 방식, 권한, 메일 · 조직 · 부서 등)이 바뀔 때만 씁니다. 요청의 IP, 갱신된 토큰, 요청의 인가 결과로는 쓰지 않고, 마지막 로그인 시각 · IP는 로그인 때와 사본을 만들 때만 씁니다. 같은 사용자가 같은 값으로 오면 contexa.bridge.sync.min-refresh-interval-seconds(기본 60초) 동안 CONTEXA DB를 읽지 않고 기억한 결과로 답합니다. 0 이하면 기억하지 않습니다. CONTEXA 자신의 계정(FULL + CONTEXA_OWNED에서 주 체인이 로그인시키는 계정, 콘솔 요청의 관리자)은 사본을 만들지 않습니다.
  • 이메일: 리졸버 · 요청 속성으로 넘긴 사용자는 ContexaSubject의 메일, Spring Security를 쓰는 앱은 인증 객체에서 찾은 email(키 이름)을 쓰고, 없으면 메일 공급자 빈에 묻습니다. 앱이 메일을 주지 않으면 사본에 이미 있는 실제 주소를 두고, 없으면 비워 둡니다. 주소를 만들어 붙이지 않습니다. 추가 인증 코드가 이 주소로 가므로 다음 규칙을 둡니다. 앱이 처음 보여 주는 실제 주소는 바로 저장합니다. 그 뒤 앱이 다른 주소를 보여 주면 바로 바꾸지 않고 대기 주소로 둡니다. 사용자가 기록된 주소와 대기 주소를 차례로 증명하거나 관리자가 주소를 입력해야 바뀝니다. 세션을 가진 사람은 누구나 앱의 프로필을 바꿀 수 있으므로, 남의 주소로 코드가 가는 일을 막기 위해서입니다. 여러 사본이 같은 메일을 가져도 저장은 실패하지 않지만, 다른 사용자와 같은 메일인 사본에는 추가 인증 코드를 보내지 않습니다(메일이 고유해야 하는 것은 CONTEXA 계정끼리뿐입니다).
  • 긴 값: 앱에서 온 값이 열 길이보다 길면(긴 조직 경로 형태의 부서, 내선이 붙은 전화번호, 긴 프로필 이미지 주소) 열 길이로 잘라 담으므로, 값 하나가 길다고 사본 저장이 실패하지 않습니다. 255자를 넘는 이메일은 없는 것으로 봅니다(메일 결손). 255자를 넘는 사용자 ID는 아이디 규칙을 어기므로 사본 행을 만들지 않습니다(오류 로그 한 번).
  • 관리자가 끈 사본: 동기화가 다시 켜지 않습니다.
  • 끄기: contexa.bridge.sync.enabled=false.

Spring Security 로그인에서 사실을 찾는 키 이름

Spring Security를 쓰는 앱의 principal과 details에서 로그인 방식 · MFA · 인증 시각 · 권한 같은 사실을 찾을 때 보는 키 이름입니다. Authentication의 details를 먼저, 다음에 principal을 보고, 객체에 claims · attributes 맵이 있으면(JWT 클레임, OAuth2 사용자 속성) 그 맵에서도 찾습니다. 값 하나를 찾는 키는 목록의 앞쪽 이름부터 처음 나온 값을 쓰고, 여러 값을 모으는 키(amr · 역할 · 권한 · 범위)는 details와 principal에서 모두 모읍니다. 앱이 같은 사실을 다른 이름으로 두면 그 이름을 목록에 더합니다.
