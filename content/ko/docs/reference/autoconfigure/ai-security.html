Contexa 켜기와 보안 모드 고르기

@EnableAISecurity로 Contexa를 켜고, 로그인을 앱이 계속 맡을지(SANDBOX) Contexa에 맡길지(FULL) 고르고, 제대로 켜졌는지 확인하는 방법을 설명합니다.

한눈에 보기

보안 모드는 "로그인을 누가 맡나"를 정합니다. 판정을 실제로 집행할지는 따로 정하는 집행 모드의 몫입니다.

준비

  1. 스타터 하나: ai.ctxa:spring-boot-starter-contexa. OAuth2 리소스 서버 · 클라이언트 · 인가 서버 라이브러리를 함께 가져오지만, Spring Security 스타터(spring-boot-starter-security)는 가져오지 않습니다(앱이 넣음). AI 모델 공급자 스타터도 가져오지 않습니다.
  2. Contexa 전용 DB: contexa.datasource.url은 필수입니다. 비어 있으면 기동이 IllegalStateException으로 멈춥니다. 앱 DB와 같은 주소는 기본으로 거부됩니다.
  3. 판정 엔진용 AI: Spring AI 채팅 모델 · 임베딩 모델 공급자와 벡터 저장소(PgVector)를 앱이 넣습니다. 빠지면 기동 진단이 알려 줍니다(AI 모델 연결).
  4. Spring Boot 3.x: 빌드 기준은 3.5.4입니다. 4.x에서는 기동하지 않습니다.
contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: contexa

켜기

@SpringBootApplication
@EnableAISecurity                      // mode = SecurityMode.SANDBOX (기본)
public class LegacyApplication {
    public static void main(String[] args) {
        SpringApplication.run(LegacyApplication.class, args);
    }
}

이름이 비슷한 모드 셋

세 모드는 서로 다른 것을 정합니다. 보안 모드와 집행 모드는 코드에서 둘 다 SecurityMode라는 이름이라 특히 헷갈리기 쉽습니다(패키지 구분).

모드무엇을 정하나정하는 곳값기본
보안 모드Contexa 기본 인증 구성의 모양, 인증 소유권 · Contexa 소유 앱 표시의 기본값@EnableAISecurity(mode = ...)SANDBOX · FULLSANDBOX
인증 소유권로그인 체인을 Contexa가 만드나(CONTEXA_OWNED), 앱이 맡나(HOST_OWNED)contexa.bridge.ownershipHOST_OWNED · CONTEXA_OWNED보안 모드를 따름(SANDBOX → HOST_OWNED, FULL → CONTEXA_OWNED)
집행 모드판정을 만들지, 저장 · 적용할지contexa.security.zerotrust.mode, 관리 화면 시스템 설정DISABLED · OBSERVE · SHADOW · ENFORCEENFORCE

집행 모드에서 DISABLED · OBSERVE는 분석하지 않고, SHADOW는 판정을 만들되 저장 · 적용하지 않으며, ENFORCE는 저장해 다음 요청부터 적용합니다. 처음 도입할 때의 순서는 집행 모드로 안전하게 시작하기에 있습니다.

SANDBOX(앱이 로그인을 맡음)를 고르면

앱이 할 일

  1. 자기 SecurityFilterChain을 선언합니다. 이 모드에서 Contexa는 인증 체인도, 자리표시용 체인도 만들지 않습니다. 앱 체인이 없으면 Spring Boot 기본 보안(모든 요청에 인증 필요)이 걸리고, Contexa가 기동 때 WARN 로그로 알립니다(앱에 로그인할 사용자도 없으면 기동을 거부합니다). Spring Security를 쓰지 않던 앱은 기존 규칙을 그대로 두는 체인(예: anyRequest().permitAll())을 선언합니다.
  2. 로그인한 사용자를 SecurityContext에 인증된 Authentication으로 넣습니다. 인증 브리지는 그런 Authentication이 있을 때만 판정 사실을 만들고, @Protectable은 없으면 호출을 거부합니다. 자체 로그인을 쓰는 앱은 앱 체인에 넣은 필터에서 넣어 줍니다(기존 로그인과 연결하기).
  3. 관리 화면에 대해서는 할 일이 없습니다. Contexa가 /contexa/admin/**를 자기 체인과 Contexa 관리자 로그인으로 지킵니다(관리 화면). 메서드 보안은 선택입니다. 이 모드에서 Contexa는 @EnableMethodSecurity를 등록하지 않고, 앱이 켜면 관리 컨트롤러의 @PreAuthorize 검사가 더해집니다.

Contexa가 하는 일 · 하지 않는 일

기능HOST_OWNED에서
앱의 로그인 페이지 · 세션 · 접근 규칙바꾸지 않습니다.
인증 브리지(로그인 정보를 판정 사실로)동작. 요청마다 인증된 Authentication을 읽습니다. 브리지 필터는 앱 체인 바로 뒤(체인 순서 + 1)의 서블릿 필터로 등록됩니다.
@Protectable 메서드의 분석 · 집행동작. 저장된 차단 · 추가 인증 · 검토 보류는 이 메서드에서도 거부됩니다.
요청 시점 필터(URL 단계 집행)동작. 같은 필터가 앱 체인 바로 뒤의 서블릿 필터로 모든 경로에서 돌며, CONTEXA_OWNED와 같은 응답을 냅니다(요청 시점 집행).
에이전트 관문(호출 상한 · 책임자 확인 등)동작(소유 방식에 따라 되는 일)
메서드 보안 @EnableMethodSecurity와 #ai 식 처리기등록하지 않음. 메서드 보안은 앱이 켭니다. #ai 식 처리기는 어느 소유 방식에서도 앱의 메서드 보안에 등록되지 않습니다.
관리 화면 URL 보호/contexa/admin/**를 맡는 Contexa 자기 콘솔 체인이 /contexa/admin/login의 Contexa 관리자 로그인으로 지킵니다. 앱 체인이 보호할 필요 없습니다.
CHALLENGE 뒤 추가 확인(/contexa/step-up)동작. Contexa의 확인 전용 추가 확인(패스키, 메일 일회용 코드, 앱 자체 재인증)이며, 앱의 로그인 · 세션 · 쿠키는 그대로입니다(HOST_OWNED의 추가 확인).
앱 로그인 순간의 분석상호작용 로그인(폼 로그인 · OAuth2 로그인)에서 동작합니다. Contexa가 Spring Security의 로그인 이벤트를 듣고 그 로그인을 분석에 보냅니다. 요청마다 인증하는 경우(Basic · 토큰)는 첫 보호 메서드에서 분석합니다.
Contexa OAuth2 인가 서버, 인증 성공 · 실패 처리기켜지지 않음
직접 넘기기(ContexaAuthBridge.handoff(...))그 요청의 판정 사실만 남기고 SecurityContext를 채우지 않습니다. 같은 요청에 같은 사용자의 Authentication이 있으면 직접 넘긴 결과를 유지합니다.
사용자 거울예외적으로 Contexa DB의 사용자 표에 거울 행을 씁니다(사용자 거울).

contexa.bridge.populate-security-context는 CONTEXA_OWNED에서만 뜻이 있습니다.

FULL(Contexa가 로그인을 맡음)을 고르면

앱이 PlatformConfig 빈을 두지 않으면 Contexa가 아래 기본 구성으로 보안 체인을 만듭니다.

  • 접근 규칙: /contexa/css/** · /contexa/js/** · /images/** · /favicon.ico는 허용, 그 밖의 모든 요청은 동적 인가 관리자(CustomDynamicAuthorizationManager, 관리 화면의 정책)가 판단합니다(동적 인가).
  • 로그인: 폼 로그인(성공 뒤 /)을 1차로 하고 패스키 · 일회용 토큰(OTT)을 2차 요소로 쓰는 MFA 흐름(필요한 요소 수 1), 세션 상태.
  • 판정 집행: 판정은 요청이 끝난 뒤 만들어지고, 집행 모드가 ENFORCE일 때 저장됩니다. 체인 안의 요청 시점 필터가 저장된 판정을 다음 요청에 적용합니다(요청 시점 집행).
  • 함께 켜지는 것: Contexa 자신의 클래스에만 거는 @PreAuthorize 처리(Contexa 식 처리기, 앱 전체의 @EnableMethodSecurity는 켜지 않음), Contexa OAuth2 인가 서버, 인증 성공 · 실패 처리기. 에이전트 관문은 여기서는 Contexa 체인 안에서 돕니다.
FULL은 앱 기본 DataSource를 바꿀 수 있습니다. 앱에 자기 DB가 없으면(spring.datasource.url이 없거나 contexa.datasource.url과 같은 DB를 가리키면) 이 모드는 contexa.datasource.isolation.contexa-owned-application=true를 넣고, 앱 자신의 DB를 가리키면 표시는 false로 남아 앱의 연결이 그대로입니다. 직접 적은 값은 언제나 그대로 쓰입니다. 표시가 true이고 앱이 DataSource 빈을 직접 만들지 않았다면 앱 기본 dataSource · JdbcTemplate · TransactionTemplate이 Contexa DB를 가리키고, 기동 진단의 기본(AUTO)이 필수 기능이 빠지면 기동을 멈추는 FAIL_FAST가 됩니다. 기존 앱에 붙일 때는 SANDBOX를 쓰십시오.

기본 구성 대신 내 인증 구성을 쓰려면 PlatformConfig 빈을 직접 선언합니다(Identity DSL). 이 구성은 CONTEXA_OWNED일 때만 체인이 됩니다.

SANDBOX 모양 체인은 없음

SANDBOX의 소유권은 언제나 HOST_OWNED입니다. 여기에 contexa.bridge.ownership=CONTEXA_OWNED를 적으면 기동이 멈춥니다. 이때 Contexa는 기본이든 앱의 것이든 PlatformConfig로 체인을 만들지 않습니다. Contexa의 체인은 /contexa/admin/**만 맡는 관리 화면 체인 하나이고, Contexa 관리자 로그인과 ADMIN 역할을 씁니다(소유 방식에 따라 동작하는 것).

레거시 인증 객체 힌트

앱이 Spring Security 밖에서 세션이나 요청 속성에 사용자 객체를 두는 경우에 씁니다. 인증 도장은 먼저 SecurityContext의 Authentication에서 만들고, 그다음 세션 · 요청 속성 · 헤더 세 통로를 차례로 시도합니다. 아래 세 속성은 이 세 통로에만 영향을 줍니다(읽는 순서).

속성기본값바꾸는 것
authObjectLocationAUTO세 통로의 시도 순서만 바꿉니다. 다른 통로를 끄지 않습니다.
AUTO · SESSION: 세션 → 요청 속성 → 헤더
REQUEST_ATTRIBUTE: 요청 속성 → 세션 → 헤더
HEADER: 헤더 → 세션 → 요청 속성
authObjectAttribute""사용자 객체가 든 속성 이름. 위치가 SESSION이면 세션 속성, REQUEST_ATTRIBUTE면 요청 속성 이름으로 쓰입니다. AUTO · HEADER에서는 쓰이지 않습니다.
authObjectTypeObject.class(지정 안 함)사용자 객체의 클래스. 후보 객체 가운데 클래스 이름이 같은 것에 점수를 더 줍니다(다른 객체를 거르지는 않음). 세션 · 요청 속성 통로 모두에 적용됩니다.
 
@SpringBootApplication
@EnableAISecurity(
        authObjectLocation = AuthObjectLocation.SESSION,
        authObjectAttribute = "loginUser",
        authObjectType = LoginUser.class)     // LoginUser: 앱이 세션에 두는 사용자 클래스
public class LegacyApplication { }

헤더 통로는 X-Contexa-* 헤더를 읽으며 기본으로 꺼져 있습니다(contexa.bridge.authentication.headers.enabled=false). 켜도 신뢰 프록시에서 온 요청이고 헤더의 사용자가 앱이 인증한 사용자와 같을 때만 받습니다(게이트웨이 헤더로 넘기기). 세션 · 요청 속성 · 헤더는 권한(인가 도장) · 위임 정보를 읽는 곳이기도 하며, 위 세 속성은 그쪽 읽기에는 영향을 주지 않습니다.

켜졌는지 확인하기

  • 기동 로그
    • HOST_OWNED에서 Skipping Contexa-owned authentication chain bootstrap in HOST_OWNED mode(INFO): Contexa가 로그인 체인을 만들지 않았다는 뜻입니다.
    • [Contexa] HOST_OWNED mode: no SecurityFilterChain is declared by the application ...(WARN): 앱 체인이 없어 Spring Boot 기본 보안이 걸렸습니다. 앱 체인을 선언하십시오. 로그가 권하는 anyRequest().permitAll()은 관리 화면을 Contexa 자기 체인이 지키므로 Contexa 경로에 대해서는 안전합니다.
    • [Contexa] HOST_OWNED: the application sets the signed-in user after Spring Security's filters ...(WARN, 한 번): MVC 인터셉터나 컨트롤러에서 사용자를 정하는 요청은 @Protectable 메서드에서만 집행됩니다.
    • Contexa owns the sign-in of this application, but the application declares its own security chain(s) [...] ...(기동 거부): 앱 로그인을 지키려면 SANDBOX를 쓰고, 아니면 그 체인을 지우십시오.
    • [Contexa] CONTEXA_OWNED: the application declares the user store(s) [...], which Contexa's sign-in does not read: ...(WARN): Contexa 로그인은 앱의 사용자 저장소를 몇 개를 두었든 읽지 않습니다. 시드 관리자를 포함한 Contexa 계정은 Contexa 자신의 사용자 저장소에서 로그인하고, 앱의 사용자는 Contexa 로그인으로 로그인되지 않습니다.
    • [Contexa] A one-time-code factor is offered but no mail sender is configured (spring.mail.*) ...(WARN): 코드를 보낼 수 없습니다. 메일을 설정하거나, 사용자는 패스키로만 확인합니다.
    • [ContexaCapability] ...(ERROR): 기동 진단이 빠진 빈을 찾았습니다(기동 진단).
  • 관리 화면 시스템 설정(/contexa/admin/system-settings, ADMIN 역할): 지금의 집행 모드를 보고 바꿀 수 있습니다. 여기서 저장한 값은 재시작 없이 적용되고 YAML 값보다 우선합니다.
  • Actuator가 있으면 엔드포인트 contexacapabilities로 기동 진단 결과를 볼 수 있습니다.

앞의 네 키는 어노테이션 속성으로 정하세요. 어노테이션은 이 키들을 가장 높은 우선순위의 속성 소스로 넣지만, 앱 설정(YAML 등)에 같은 키를 적었다면 그 값을 그대로 넣습니다. 어노테이션 속성은 적지 않았을 때의 기본값입니다. 그래서 contexa.ai.security.mode: FULL을 적으면 어노테이션이 SANDBOX여도 FULL로 동작합니다. 또 contexa.ai.security.mode를 YAML에 적는 것만으로는 어노테이션 없이 Contexa가 켜지지 않습니다. 켜짐 표지는 어노테이션이 넣는 속성 소스이기 때문입니다. 이 키들은 설정 메타데이터에도 없습니다.
