CONTEXA 켜기와 보안 모드 고르기

@EnableAISecurity로 CONTEXA를 켜고, 로그인을 앱이 계속 맡을지(SANDBOX) CONTEXA에 맡길지(FULL) 고르고, 제대로 켜졌는지 확인하는 방법을 설명합니다.

이 페이지의 용어. 보안 모드(SANDBOX · FULL)는 @EnableAISecurity의 속성으로, CONTEXA의 보안 설정이 앱에 무엇을 하는지 정합니다. SANDBOX(기본)는 앱과 격리하고 로그인은 앱이 맡으며, FULL은 CONTEXA가 앱의 주 보안 구성(로그인 · 인가 · 보안 설정)을 만듭니다. 두 모드 모두 CONTEXA의 전체 기능이 동작합니다. 인증 소유권(HOST_OWNED · CONTEXA_OWNED)은 앱이 직접 둔 구성요소(UserDetailsService · JwtDecoder 등)와 CONTEXA의 같은 종류가 만날 때 어느 쪽을 앱에 쓰는지 정하는, 보안 모드와 다른 설정입니다. 기능을 끄지 않으며 네 조합 모두 허용됩니다. 운영 모드(DISABLED · SHADOW · ENFORCE)는 판정을 분석하고 적용할지를 정합니다. 속성 소스는 Spring 설정(Environment)이 가진 설정 묶음 하나이고, 켜짐 표지는 어노테이션이 넣는 속성 소스 contexaAiSecurityAnnotation입니다. PlatformConfig는 CONTEXA의 인증 구성(로그인 흐름의 정의)을 담는 객체입니다.

개요

보안 모드는 "로그인을 누가 맡나"를 정합니다. 판정을 실제로 적용할지는 따로 정하는 운영 모드가 정합니다.

준비

CONTEXA를 켜려면 아래가 필요합니다. 충족하지 못하면 대개 기동이 거부되고, 이유와 해야 할 일을 담은 오류 메시지가 나옵니다(스택 트레이스 없이).

필요한 것충족하지 못하면
스타터 하나: ai.ctxa:spring-boot-starter-contexa. OAuth2 리소스 서버 · 클라이언트 · 인가 서버 라이브러리를 함께 가져옵니다. Spring Security와 AI 모델 공급자 스타터는 가져오지 않습니다.—
Spring Boot 3.x(빌드 기준 3.5.4)4.x에서는 기동을 거부합니다.
서블릿 웹 스택: 서블릿 API(spring-boot-starter-web)가 있고, spring.main.web-application-type이 reactive가 아니며, 앱에 WebFlux 라우트(RouterFunction 빈)가 없어야 합니다.기동을 거부합니다.
Spring Security 라이브러리: 클래스패스에 Spring Security 설정 라이브러리(HttpSecurity 클래스)가 있어야 합니다. 스타터는 이것을 가져오지 않으므로 앱이 org.springframework.boot:spring-boot-starter-security를 직접 선언합니다. Spring Security로 로그인하지 않는 앱도 이 의존성은 필요하지만 보안 체인은 선언하지 않아도 됩니다(앱이 할 일).@EnableAISecurity가 기동을 거부합니다.
AOT 처리 · 네이티브 이미지가 아님AOT 처리 중이면 기동을 거부합니다.
CONTEXA 전용 DB: contexa.datasource.url은 필수입니다. 앱 DB와 같은 주소는 기본으로 거부됩니다. 운영 프로파일(prod · production)에서는 예외 없이 거부하고, 그 밖에서는 시험용 허용 설정(contexa.datasource.isolation.allow-shared-application-datasource와 shared-application-datasource-risk-accepted를 둘 다 true)이 있을 때만 허용합니다.비어 있거나 거부 조건에 걸리면 기동이 IllegalStateException 계열 오류로 멈춥니다.
DB가 응답함: 주소가 있다면 DB가 응답해야 합니다. PostgreSQL이면 계정이 확장 vector를 만들 수 있어야 하고, 벡터 저장소의 표 만들기(contexa.vectorstore.pgvector.initialize-schema)를 끄지 않았다면 hstore · uuid-ossp도 만들 수 있어야 합니다.1초 간격으로 5초 동안 다시 시도합니다. 그래도 안 되면 앱이 로그인을 맡는 SANDBOX에서는 ERROR 로그를 남기고 CONTEXA 없이 앱만 기동합니다(고친 뒤 앱을 다시 시작). CONTEXA가 로그인을 맡는 FULL에서는 기동에 실패합니다.
분산 모드의 Redis: contexa.infrastructure.mode=distributed이면 Redis 클라이언트 라이브러리(spring-boot-starter-data-redis, org.redisson:redisson, spring-statemachine-data-redis)가 있고 Redis 서버에 닿아야 합니다.라이브러리가 없으면 기동을 거부합니다. 단일 Redis 서버에 닿지 못하면 위 DB와 같이 처리합니다(클러스터 · 센티넬 구성은 확인하지 않음).
판정 엔진용 AI: Spring AI 채팅 모델 · 임베딩 모델 공급자와 벡터 저장소(PgVector)를 앱이 넣습니다.빠지면 기동 진단이 알려 줍니다(AI 모델 연결).

    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa

이름이 비슷한 모드 셋

세 모드는 서로 다른 것을 정합니다. 이름이 비슷해 헷갈리기 쉽습니다. 보안 모드의 열거형은 SecurityMode이고, 운영 모드의 열거형은 SecurityZeroTrustProperties.EnforcementMode입니다(공통 계약).

모드무엇을 정하나정하는 곳값기본
보안 모드CONTEXA의 보안 설정이 앱에 무엇을 하는지(SANDBOX는 앱과 격리, FULL은 CONTEXA가 앱의 주 보안 구성)와 CONTEXA 기본 인증 구성의 모양, 인증 소유권 · CONTEXA 소유 앱 표시의 기본값@EnableAISecurity(mode = ...)SANDBOX · FULLSANDBOX
인증 소유권앱이 직접 둔 구성요소(UserDetailsService · JwtDecoder 등)와 CONTEXA의 같은 종류가 만날 때 어느 쪽을 앱에 쓰나(HOST_OWNED는 앱 것, CONTEXA_OWNED는 앱에 없는 종류를 CONTEXA 것으로 채움). 기능을 끄지 않음contexa.bridge.ownershipHOST_OWNED · CONTEXA_OWNED보안 모드를 따름(SANDBOX → HOST_OWNED, FULL → CONTEXA_OWNED)
운영 모드판정을 만들지, 저장 · 적용할지contexa.security.zerotrust.mode, 관리 화면 시스템 설정DISABLED · SHADOW · ENFORCE(OBSERVE는 DISABLED로 읽는 옛 이름)ENFORCE

운영 모드에서 DISABLED는 요청을 분석하지 않습니다. 옛 이름 OBSERVE로 적어도 DISABLED로 읽히고 기동할 때 경고가 한 번 남습니다. SHADOW는 판정을 만들어 관찰 모드 전용 기억에만 남기고 적용하지 않으며, ENFORCE는 저장해 다음 요청부터 적용합니다. 처음 도입할 때의 순서는 관찰 모드로 안전하게 시작하기에 있습니다.

SANDBOX(앱이 로그인을 맡음)를 고르면

앱이 할 일

  1. 보안 체인은 앱이 쓰던 그대로 둡니다. 이 모드에서 CONTEXA는 인증 체인도, 자리표시용 체인도 만들지 않습니다. Spring Security로 로그인하는 앱은 자기 SecurityFilterChain을 그대로 씁니다. 앱에 사용자는 있는데 체인이 없으면 Spring Boot 기본 보안(모든 요청에 인증 필요)이 걸리고, CONTEXA가 기동 때 WARN 로그로 알립니다. Spring Security를 쓰지 않던 앱은 spring-boot-starter-security 의존성만 넣고 체인은 선언하지 않습니다. 앱에 체인도 사용자도 없으면 CONTEXA가 Spring Boot 기본 체인 대신 필터가 하나도 없는 격리 체인(contexaSandboxIsolationChain, 맨 뒤 순서)을 두어 CONTEXA를 넣기 전처럼 모든 요청을 통과시킵니다. 이 체인은 CSRF · CORS · 보안 헤더 · 세션 관리 · 로그아웃을 처리하지 않고, 앱이 체인 앞에서 SecurityContext에 둔 사용자도 그대로 둡니다.
  2. 로그인한 사용자를 CONTEXA에 알립니다. Spring Security로 로그인하는 앱은 할 일이 없습니다. 인증 브리지가 앱의 필터가 끝난 뒤 SecurityContext의 인증된 Authentication을 읽습니다. Spring Security 없이 자체 세션 · 토큰으로 로그인하는 앱은 ContexaSubjectResolver 빈 하나를 두거나, 자기 서블릿 필터에서 요청 속성 ContexaSubject.REQUEST_ATTRIBUTE(ctxa.subject)에 ContexaSubject를 넣습니다. 사용자 아이디와 메일을 넘기고 나머지(표시 이름 · 조직 · 권한 · 로그인 방식 · 위임)는 선택입니다. 메일이 없으면 신원은 성립하지만 메일로 추가 인증 코드를 보낼 수 없습니다. CONTEXA는 이 사용자를 판정에만 쓰고 SecurityContext에 넣지 않습니다. 신원을 알 수 없는 요청이 @Protectable 메서드를 부르면 호출을 거부합니다(기존 로그인과 연결하기).
  3. 관리 화면에 대해서는 할 일이 없습니다. CONTEXA가 /contexa/admin/**를 자기 체인과 CONTEXA 관리자 로그인으로 지킵니다(관리 화면). 메서드 보안은 선택입니다. CONTEXA는 앱에 @EnableMethodSecurity를 등록하지 않고, 관리 컨트롤러의 @PreAuthorize는 CONTEXA 자신의 클래스에만 거는 처리로 늘 검사합니다(앱이 메서드 보안을 켜면 앱의 메서드 보안이 그 검사를 맡음).

CONTEXA가 하는 일 · 하지 않는 일

기능SANDBOX에서
앱의 로그인 페이지 · 세션 · 접근 규칙바꾸지 않습니다.
인증 브리지(로그인 정보를 판정 사실로)동작. 요청마다 contexa.bridge.identity-sources 순서(기본: 앱 Spring Security의 인증된 Authentication → ContexaSubjectResolver 빈 → 요청 속성 ctxa.subject)로 읽어, 처음 성립한 신원을 씁니다. 브리지 필터는 앱의 보안 체인과 서블릿 필터가 모두 끝난 뒤의 CONTEXA 서블릿 필터 자리(contexaFilterSlot)에서 판정 필터보다 먼저 돕니다.
@Protectable 메서드의 분석 · 적용동작. 저장된 차단 · 추가 인증 · 검토 보류는 이 메서드에서도 거부됩니다.
요청 시점 필터(URL 단계 적용)동작. 같은 필터가 앱의 보안 체인과 서블릿 필터가 모두 끝난 뒤의 서블릿 필터로 모든 경로에서 돌며, FULL과 같은 응답을 냅니다(요청 시점 적용).
에이전트 관문(호출 상한 · 책임자 확인 등)동작(보안 모드에 따라 되는 일)
메서드 보안 @EnableMethodSecurity와 #ai 식 처리기등록하지 않음. 메서드 보안은 앱이 켭니다. #ai 식 처리기는 두 모드 모두(소유권과 무관) 앱의 메서드 보안에 등록되지 않습니다.
관리 화면 URL 보호/contexa/admin/**를 맡는 CONTEXA 자기 콘솔 체인이 /contexa/admin/login의 CONTEXA 관리자 로그인(비밀번호 다음 패스키 또는 메일 코드)으로 지킵니다. 앱 체인이 보호할 필요 없습니다.
CHALLENGE 뒤 추가 인증(/contexa/step-up)동작. CONTEXA의 확인 전용 추가 인증(패스키, 메일 일회용 코드, 앱 자체 재인증)이며, 앱의 로그인 · 세션 · 쿠키는 그대로입니다(SANDBOX의 추가 인증).
앱 로그인 순간의 분석상호작용 로그인(폼 로그인 · OAuth2 로그인)에서 동작합니다. CONTEXA가 Spring Security의 로그인 이벤트를 듣고 그 로그인을 분석에 보냅니다. 요청마다 인증하는 경우(Basic · 토큰)는 첫 보호 메서드에서 분석합니다.
CONTEXA OAuth2 인가 서버(토큰 발급)켜지지 않음(FULL에서만). CONTEXA는 토큰을 발급하지 않고, 에이전트 요청은 앱 자신의 토큰 클레임으로 판단합니다. 인증 성공 · 실패 처리기는 두 모드 모두 등록됩니다.
로그인 순간 알리기(ContexaBridge.signedIn(request, subject))선택입니다. Spring Security 없이 로그인하는 앱이 로그인 성공 자리(세션 ID를 바꾼 뒤)에서 부르면, CONTEXA가 그 사용자를 그 요청의 신원으로 삼고 사용자 사본을 그 자리에서 만들거나 고친 뒤(최대 1초 기다림) 그 로그인을 분석에 한 번 보냅니다. SecurityContext는 채우지 않습니다. 로그인 실패는 ContexaBridge.signInFailed, 로그아웃은 ContexaBridge.signedOut으로 알립니다. 호출은 예외를 던지지 않고 결과(ContexaBridgeResult)로 알립니다. Spring Security로 로그인하는 앱은 부를 필요가 없습니다(CONTEXA가 Spring Security의 이벤트를 듣습니다).
사용자 사본예외적으로 CONTEXA DB의 사용자 표에 사본 행을 씁니다(사용자 사본).

SANDBOX에서 CONTEXA는 앱의 SecurityContext와 권한을 바꾸지 않습니다. 인증 브리지가 정한 신원은 CONTEXA의 요청 속성에만 두고, 판정과 URL 정책이 그 신원을 씁니다. 앱이 사용자를 넘기는 방법 전체(리졸버 · 요청 속성 · 메일 공급자 · 설정)는 인증 브리지에 있습니다.

FULL(CONTEXA가 로그인을 맡음)을 고르면

앱이 PlatformConfig 빈을 두지 않으면 CONTEXA가 아래 기본 구성으로 보안 체인을 만듭니다. 관리 콘솔(/contexa/admin)은 FULL + CONTEXA_OWNED에서 이 주 흐름이 관리자도 로그인시키고(/contexa/admin/login은 주 흐름의 MFA 로그인 화면으로 이동), FULL + HOST_OWNED에서는 관리 흐름 체인이 CONTEXA 관리자를 따로 로그인시킵니다.

  • 접근 규칙: /contexa/css/** · /contexa/js/** · /contexa/img/** · /images/** · /favicon.ico와 비밀번호 변경 화면 /contexa/password-change는 허용, 그 밖의 모든 요청은 동적 인가 관리자(CustomDynamicAuthorizationManager, 관리 화면의 정책)가 평가합니다(동적 인가).
  • 로그인: 폼 로그인(성공 뒤 /)을 1차로 하고 패스키 · 일회용 토큰(OTT)을 2차 요소로 쓰는 MFA 흐름(필요한 요소 수 1), 세션 상태.
  • 판정 적용: 판정은 요청이 끝난 뒤 만들어지고, 운영 모드가 ENFORCE일 때 저장됩니다. 체인 안의 요청 시점 필터가 저장된 판정을 다음 요청에 적용합니다(요청 시점 적용).
  • 함께 켜지는 것: CONTEXA OAuth2 인가 서버 · 리소스 서버 · 토큰 클라이언트. CONTEXA 자신의 클래스에만 거는 @PreAuthorize 처리(CONTEXA 식 처리기, 앱 전체의 @EnableMethodSecurity는 켜지 않음)와 인증 성공 · 실패 처리기는 두 모드 모두 있습니다. 에이전트 관문은 여기서는 CONTEXA 체인 안에서 실행됩니다.
FULL은 앱 기본 DataSource를 바꿀 수 있습니다. 앱에 자기 DB가 없으면(spring.datasource.url이 없거나 contexa.datasource.url과 같은 DB를 가리키면) 이 모드는 contexa.datasource.isolation.contexa-owned-application=true를 넣고, 앱 자신의 DB를 가리키면 표시는 false로 남아 앱의 연결이 그대로입니다. 직접 적은 값은 언제나 그대로 쓰입니다. 표시가 true이고 앱이 DataSource 빈을 직접 만들지 않았다면 앱 기본 dataSource · JdbcTemplate · TransactionTemplate이 CONTEXA DB를 가리키고, 기동 진단의 기본(AUTO)이 필수 기능이 빠지면 기동을 멈추는 FAIL_FAST가 됩니다. 기존 앱에 붙일 때는 SANDBOX를 씁니다.

기본 구성 대신 내 인증 구성을 쓰려면 PlatformConfig 빈을 직접 선언합니다(Identity DSL). FULL에서는 이 구성의 흐름이 소유권과 상관없이 체인이 되고, FULL + CONTEXA_OWNED가 아니면 관리 흐름 contexa-admin이 더해집니다.

SANDBOX 모양 체인은 없음

SANDBOX의 소유권은 적지 않으면 HOST_OWNED이고, contexa.bridge.ownership=CONTEXA_OWNED를 적어도 기동은 멈추지 않습니다(네 조합 모두 허용). 이때 CONTEXA는 기본이든 앱의 것이든 PlatformConfig로 체인을 만들지 않습니다. CONTEXA의 체인은 /contexa/admin/**만 맡는 관리 화면 체인 하나이고(앱에 보안 체인도 사용자도 없을 때만 모든 요청을 들이는 격리 체인 contexaSandboxIsolationChain이 더해짐), 관리 화면 체인은 CONTEXA 관리자 로그인과 ADMIN 역할을 씁니다(두 보안 모드 비교).

켜졌는지 확인하기

  • 기동 로그
    • [Contexa] mode=SANDBOX ownership=HOST_OWNED data=application enforcement=ENFORCE(INFO, 기동이 끝날 때 한 줄): 이 앱이 CONTEXA를 어떤 방식으로 쓰는지 알려 줍니다. 보안 모드, 인증 소유권, 데이터(CONTEXA DB가 앱 DB를 겸하면 contexa), 운영 모드 순서입니다.
    • [Contexa] On the class path with Contexa, unless the application declares them itself: ...(INFO): CONTEXA와 함께 클래스패스에 들어온 것(Reactor Netty, Thymeleaf, Prometheus, Bean Validation, Spring MVC)이 Spring Boot의 설정에 무엇을 하는지 알려 줍니다. Thymeleaf는 CONTEXA 화면이 자기 템플릿 엔진으로 쓰고, Spring Boot는 앱이 Thymeleaf를 직접 쓸 때만 Thymeleaf를 설정합니다. contexa.startup.class-path-report=false로 끕니다.
    • [Contexa] This application runs on the servlet stack, which Contexa brings, and these WebFlux beans of it never run there: ...(WARN): WebFlux용으로 만든 필터나 보안 체인은 서블릿 스택에서 실행되지 않습니다. WebFlux 앱은 지원하지 않습니다.
    • [Contexa] SANDBOX mode: the application declares users of its own and no SecurityFilterChain, so Spring Boot's default security is active and every request requires authentication. ...(WARN): SANDBOX에서 앱에 사용자는 있는데 체인이 없어 Spring Boot 기본 보안이 걸렸습니다. 앱 체인을 선언합니다. 로그가 권하는 anyRequest().permitAll()은 관리 화면을 CONTEXA 자기 체인이 지키므로 CONTEXA 경로에 대해서는 안전합니다.
    • [Contexa] SANDBOX mode: the application sets the signed-in user after Spring Security's filters ...(WARN, 한 번): MVC 인터셉터나 컨트롤러에서 사용자를 정하는 요청은 @Protectable 메서드에서만 적용됩니다.
    • With mode FULL Contexa's main chain takes every request, and the application declares its own security chain(s) [...] for every request as well. ...(기동 거부, FULL): 앱 체인을 http.securityMatcher(...)로 그 체인이 지키는 경로에 좁히면 CONTEXA 주 체인 앞에서 그 경로를 맡고 함께 기동합니다. 앱 체인을 계속 앱의 주 보안으로 두려면 SANDBOX를 씁니다.
    • [Contexa] FULL mode with CONTEXA_OWNED: the application declares the user store(s) [...], which Contexa's sign-in does not read: ...(WARN, FULL + CONTEXA_OWNED): CONTEXA 로그인은 앱의 사용자 저장소를 몇 개를 두었든 읽지 않습니다. 시드 관리자를 포함한 CONTEXA 계정은 CONTEXA 자신의 사용자 저장소에서 로그인하고, 앱의 사용자는 CONTEXA 로그인으로 로그인되지 않습니다.
    • [Contexa] A one-time-code factor is offered but no mail sender is configured (spring.mail.*) ...(WARN): 코드를 보낼 수 없습니다. 메일을 설정하거나, 사용자는 패스키로만 확인합니다.
    • [ContexaCapability] ...(ERROR): 기동 진단이 빠진 빈을 찾았습니다(기동 진단).
  • 관리 화면 시스템 설정(/contexa/admin/system-settings, ADMIN 역할): 지금의 운영 모드를 보고 바꿀 수 있습니다. 여기서 저장한 값은 재시작 없이 적용되고 YAML 값보다 우선합니다.
  • Actuator가 있으면 엔드포인트 contexacapabilities로 기동 진단 결과를 볼 수 있습니다.

참고: 어노테이션이 넣는 설정 키

설정 키어노테이션 속성넣는 때뜻
contexa.ai.security.modemode늘기본 인증 구성의 모양. 앱 설정에 같은 키를 적었으면 그 값이 어노테이션 속성보다 우선합니다
contexa.bridge.ownershipmode앱이 이 키를 적지 않았을 때SANDBOX → HOST_OWNED, FULL → CONTEXA_OWNED
contexa.datasource.isolation.contexa-owned-applicationmode앱이 이 키를 적지 않았을 때FULL이고 앱이 자기 DB를 따로 정하지 않았으면(spring.datasource.url이 없거나 contexa.datasource.url과 같으면) true, 그 밖에는 false(위 주의)
첫 키 contexa.ai.security.mode는 어노테이션 속성 mode로 정합니다. 어노테이션은 이 키를 가장 높은 우선순위의 속성 소스로 넣지만, 앱 설정(YAML 등)에 같은 키를 적었다면 그 값을 그대로 넣습니다. 어노테이션 속성은 적지 않았을 때의 기본값입니다. 그래서 contexa.ai.security.mode: FULL을 적으면 어노테이션이 SANDBOX여도 FULL로 동작합니다. 또 contexa.ai.security.mode를 YAML에 적는 것만으로는 어노테이션 없이 CONTEXA가 켜지지 않습니다. 켜짐 표지는 어노테이션이 넣는 속성 소스이기 때문입니다. 이 키는 설정 메타데이터에도 없습니다.
