판정 엔진: 판정은 어떻게 만들어지나

판정 엔진은 AI 모델로 요청마다 판정(허용, 추가 인증, 검토 보류, 차단 중 하나)을 만들고, 저장하고, 같은 사용자의 다음 요청에 적용합니다. 이 페이지에서 어떤 요청이 분석 대상인지, 모델이 받는 사실과 두 단계 판정 방식, CONTEXA가 모델의 답을 바꾸는 경우, 판정의 유지 기간과 학습 대상을 확인할 수 있습니다.

개요

CONTEXA는 보호 메서드(@Protectable)를 호출한 요청을 AI 모델에게 보내 판정(Decision)을 받습니다. 모델이 요청을 어떻게 다룰지 고른 값을 대응(action)이라고 부르며, 대응은 허용(ALLOW), 추가 인증(CHALLENGE), 검토 보류(ESCALATE), 차단(BLOCK) 중 하나입니다. 판정은 이 대응과 근거를 담아 사용자별로 저장하는 결과입니다.

기본 방식에서는 요청이 판정을 기다리지 않습니다. 메서드가 실행되고 응답이 나간 뒤에 CONTEXA가 뒤에서 판정을 만들어 저장하고, 같은 사용자의 다음 요청부터 그 판정을 적용합니다. 예를 들어 모델이 차단을 고르면 그 사용자의 다음 요청이 차단 응답을 받습니다. 호출 안에서 바로 판정이 필요한 메서드만 @Protectable(sync=true)로 표시합니다. 이 메서드는 판정을 받은 뒤에 실행합니다.

대응은 AI 모델이 고릅니다. 정상적인 경우 CONTEXA 엔진은 모델에게 보낼 사실을 모을 뿐 대응을 정하지 않습니다. 모델이 받는 사실은 다음과 같습니다.

  • 이번 요청: 사용자, 자원, 시각, IP, 단말, 메서드 실행 결과
  • 세션 흐름: 같은 세션에서 앞서 한 요청
  • 행위 기준선과 다른 점: 행위 기준선은 사용자마다 학습해 둔 일하는 시간 · 단말 · 네트워크 · 접근 대상입니다. 학습 방법은 무엇을 배우나에 있습니다.
  • 업무 컨텍스트: 결재 · 티켓 · 담당 같은 업무 기록이 그 차이를 설명하는지
  • 과거 판정 기록: 이 사용자의 과거 판정과, 이번 요청과 비슷한 과거 요청

모델을 부르지 못했거나 모델의 답이 형식에 맞지 않을 때는 CONTEXA가 대응을 대신 정합니다. 이 경우는 모델의 답이 바뀌는 경우에 모았습니다. 저장된 판정이 없거나 유효 시간이 지난 상태는 분석 대기(PENDING_ANALYSIS)라고 부릅니다. 이 상태의 요청은 통과하고, 분석 대상이 됩니다.

어떤 요청이 분석되나

모든 요청이 AI 모델에게 가지는 않습니다. 아래 표에서 "분석합니다"라고 된 경우만 모델을 불러 새 판정을 만들고, 나머지는 모델을 부르지 않습니다.

경우어떻게 되나
보호 메서드 호출(기본)메서드를 실행하고 응답이 나간 뒤에 분석합니다. 메서드는 판정을 기다리지 않습니다.
즉시 판정 메서드(@Protectable(sync=true))호출 안에서 먼저 판정합니다.
  • 대기열을 거치지 않고 같은 엔진을 바로 실행하며, 호출한 스레드는 판정이 나올 때까지 기다립니다.
  • 허용이면 메서드를 실행하고, 허용이 아니면 거부합니다(적용 모드).
  • 저장된 허용이 있어도 매번 판정합니다. 차단 · 추가 인증 · 검토 보류가 이미 걸려 있을 때만 분석 없이 거부합니다.
  • 판정을 기다리는 시간은 최대 40초(contexa.security.zerotrust.agent.flight.wait)입니다. 그 안에 판정이 나오지 않으면 이번 호출만 추가 인증으로 거부합니다(AI 에이전트의 호출은 잠시 뒤 다시 시도하라는 응답으로 거부).
  • 분석은 호출과 별개로 이어져 다음 요청에 쓰입니다.
AI 에이전트의 요청이고 저장된 판정이 없음메서드에 sync=true가 없어도 호출 안에서 먼저 판정하고 그 판정을 적용합니다(적용 모드). 판정 없이 에이전트를 통과시키지 않는 기본 동작입니다. contexa.security.zerotrust.protectable.unrecorded-agent-request=PROCEED로 바꾸면 사람의 요청처럼 통과시킨 뒤에 분석합니다.
운영 모드가 끔(DISABLED, 옛 이름 OBSERVE 포함)이거나 contexa.security.zerotrust.enabled=false분석하지 않습니다. AI 모델을 부르지 않습니다.
이 사용자에게 차단 · 추가 인증 · 검토 보류가 걸려 있음적용 모드에서는 메서드를 실행하기 전에 거부하고 분석하지 않습니다. 관찰 모드(SHADOW)에서는 막지 않고 기록만 남깁니다.
저장된 판정이 아직 유효함(분석 대기가 아님)새로 분석하지 않고 세션 이력(그 세션이 한 일의 기록으로, 이후 판정이 읽습니다)에 "분석하지 않은 요청"으로만 남깁니다. 허용 판정은 판정을 받은 세션 · IP · 브라우저에서만 유효합니다. 다른 세션 · IP · 브라우저에서 온 요청에는 유효한 판정이 없으므로 새로 분석합니다.
같은 사용자가 같은 맥락(세션 · IP · 브라우저의 조합)에서 같은 보호 메서드를 5초 안에 다시 호출통과시키되 분석하지 않습니다(contexa.security.zerotrust.protectable.rapid-reentry-window-ms, 기본 5000). 즉시 판정 메서드는 앞선 호출의 판정이 진행 중이라는 이유로 거부합니다(적용 모드).
인가 정책(XACML · URL)이 거부분석하지 않고 세션 이력에만 기록합니다.
분석 대기열에 들어갈 수 없음: 사람의 요청인데 같은 세션 · 맥락의 분석이 이미 대기 중이거나 그 사용자의 분석이 이미 8건 대기 중임, 또는 대기열 전체가 가득 참이번 요청은 대기열에 들어가지 않고 세션 이력에만 기록합니다. 대기 중인 분석이 판정을 내지 못하면 그 세션의 다음 요청이 다시 분석됩니다.
같은 사건이 두 번 처리되려 함(여러 서버, 대기열에 다시 들어감)분석을 시작하기 전에 사건마다 처리 권한(claim)을 한 번만 확보합니다(테넌트 · 사용자 · 맥락 · 사건 · 자원 · 메서드로 만든 식별자). 이미 처리됐거나 다른 곳에서 처리 중인 사건은 건너뜁니다.
한 에이전트가 같은 요청을 한꺼번에 보냄판정 통합을 켜면 같은 질문은 한 번만 분석합니다(기본 꺼짐).

판정이 만들어지는 순서: 1차 분석과 2차 분석

분석 대상이 된 요청의 판정은 최대 두 단계로 만들어집니다. 1차 분석이 모델에게 사실을 보내 대응을 받습니다. 그 대응이 검토 보류(ESCALATE, 이 사실만으로는 정할 수 없다는 답)가 아니면 그대로 최종 판정이 됩니다. 검토 보류를 받은 요청만 2차 분석으로 가고, 2차 분석이 같은 요청을 한 번 더 판정합니다. 대부분의 요청은 1차 분석에서 끝납니다.

1차 분석은 분석을 시작하자마자 과거 판정 기록 검색을 뒤에서 시작합니다. 세션 흐름과 행위 기준선을 정리하는 동안 검색이 진행되고, 프롬프트에 기록이 필요한 시점에 최대 0.6초(contexa.security.tiered.layer1.timeout.interactive-rag-wait-ms) 기다립니다. 그때까지 검색이 끝나지 않으면 과거 판정 기록 없이 판정합니다.

찾은 기록은 프롬프트의 PAST RECORDS 구역에 실립니다. 모델은 이 구역으로 이번 요청을 그 사용자의 이전 요청과 견줍니다. 기록은 두 방법으로 함께 찾습니다.

찾는 법1차 분석2차 분석
정확 조회이 사용자가 같은 종류의 행동에서 허용받은 기록을 조건으로 조회합니다. 임베딩(의미 비교용 벡터 계산)은 쓰지 않습니다. 이번 요청과 같은 대상의 기록을 먼저, 그 안에서는 최신 기록을 먼저 싣습니다. 프롬프트에는 PastRecord 줄로 나옵니다.1차가 찾은 기록을 그대로 쓰고, 없을 때만 다시 조회합니다.
유사도 검색뜻이 비슷한 기록을 최대 12건(contexa.security.tiered.layer1.vector-search-limit), 관련도 0.5 이상(layer1.rag.similarity-threshold)만 찾아 SimilarCase 줄로 싣습니다. 프롬프트 버전에 "유사 사례 읽는 법" 부분이 있을 때만 실행합니다. 이 부분을 지운 버전은 정확 조회만 씁니다.1차가 찾은 기록을 그대로 쓰고, 없을 때만 다시 찾습니다(최대 5건 layer2.rag-top-k, 관련도 0.5 이상).
과부하 보호. 모델이 많은 요청에 "정할 수 없다(ESCALATE)"고 답하면 2차 분석 호출이 한꺼번에 몰립니다. 이를 막기 위해 CONTEXA는 조직(조직이 없으면 사용자)과 요청 경로별로 1차 분석 결과를 셉니다. 11건 이상이 쌓였고 그중 절반을 넘게 ESCALATE이면 2차 분석을 부르지 않고 추가 인증으로 끝냅니다. 100건을 채우면 처음부터 다시 세고, 하루 동안 기록이 없어도 처음부터 다시 셉니다. 비율과 건수는 코드에 정해져 있습니다.

분석 단계마다 다른 모델 쓰기

1차와 2차에 서로 다른 모델을 쓸 수 있습니다. 예를 들어 1차는 빠르고 비용이 낮은 모델, 2차는 더 신중한 모델로 둡니다. 설정하지 않으면 두 분석 단계 모두 기본 채팅 모델을 씁니다.

contexa:
  security:
    tiered:
      llm:
        layer1:
          model: gpt-4o-mini   # 비우면 기본 채팅 모델
        layer2:
          model: gpt-4o        # 비우면 기본 채팅 모델

위 예는 기본 채팅 모델이 OpenAI일 때 그대로 동작합니다(같은 공급자 안에서 이름만 바꿈).

  • 모델을 고르는 순서: 그 분석 단계의 모델 → (있으면) 그 분석 단계의 백업 모델(layerN.backup.model) → 기본 채팅 모델.
  • 모델 이름에 맞는 연결 설정(contexa.llm.bindings.chat)이 없으면 기본 채팅 모델을 복사해 이름만 바꿔 씁니다. 이 복사는 OpenAI(mutate())와 Anthropic(CONTEXA가 같은 클라이언트와 기본 옵션으로 다시 만듦) 채팅 모델에서 됩니다. Ollama처럼 복사할 수 없는 모델은 연결 설정을 따로 두어야 합니다.
  • 분석 단계 모델을 만들 수 없어도 애플리케이션은 시작합니다. 시작할 때 ERROR 로그 한 줄이 그 분석 단계 · 적어 둔 모델 · 대신 쓰는 모델(백업 모델, 없으면 기본 채팅 모델)을 알리므로 시작 로그를 확인합니다. 같은 공급자 안의 틀린 모델 이름은 시작할 때 알 수 없고 그 분석 단계의 첫 호출에서 실패합니다.

판정 뒤에 하는 일: 다섯 단계

판정을 만드는 일부터 저장하고 기록하는 일까지는 번호가 붙은 다섯 처리 단계(핸들러)가 번호 순서로 처리합니다. 처리 단계는 1차 · 2차 분석과 다른 구분입니다. 첫 처리 단계(50)가 위에서 설명한 1차 · 2차 분석을 실행하고, 나머지는 만들어진 판정을 적용하고, 증거로 보관하고, 기록하고, 전달합니다.

순서단계하는 일언제 실행되나
50판정 만들기 (ProcessingExecutionHandler)1차 · 2차 분석으로 판정을 만듭니다.항상. 채팅 모델과 벡터 저장소 중 하나라도 없으면 판정을 만들지 못해 사용자는 분석 대기로 남습니다.
55적용 (SecurityDecisionEnforcementHandler)먼저 판정과 이유를 판정 관찰 기록(DB 표 ctxa_ai_security_decision_observation)에 씁니다. 적용 모드이면 그다음에 판정을 사용자 판정 저장소에 저장합니다. 차단이면 사람의 경우 차단 사용자 기록을 남기고, 진행 중인 응답을 끊는 신호를 보냅니다.판정 결과가 있을 때
56증거 봉인 (SealedEvidenceCaptureHandler)모델에 보낸 그대로의 프롬프트와 판정을 해시로 봉인해 보관합니다. 나중에 판정이 어떤 프롬프트로 내려졌는지 확인하고, 그 기록이 바뀌지 않았음을 보이는 증거입니다. 판정 자체는 바꾸지 않습니다. 기본 규칙은 이렇습니다. 서버가 시작한 뒤와 판정이 쓰는 프롬프트 버전이 바뀐 뒤의 처음 1,000건은 모두 봉인합니다. 그 밖에는 요청을 멈춘 판정과 위험 신호가 있는 허용 판정을 하루 2,000건까지 봉인하고, 나머지는 1%만 봉인합니다. 봉인한 증거는 90일 보관합니다. 봉인 증거AI 모델이 판정한 경우(contexa.pqa.oss.sealed-evidence.capture-enabled, 기본 켜짐)
60감사 (AuditingHandler)감사 기록(ctxa_audit_log)에 판정을 남깁니다. 관찰 모드에서도 남깁니다.판정 결과가 있을 때
65SaaS 전달 (SaasForwardingHandler)허용과 분석 대기가 아닌 판정(추가 인증 · 검토 보류 · 차단)을 CONTEXA SaaS로 보낼 상자(outbox)에 담습니다. CONTEXA SaaS 연결contexa.saas.enabled=true일 때만(기본 꺼짐)

판정이 저장되고 적용되는 방법

적용 모드(ENFORCE)에서는 판정을 사용자 판정 저장소에 저장합니다. 저장소는 단독 모드(standalone)에서는 서버 메모리이고, 분산 모드(distributed)에서는 Redis입니다. 사용자의 다음 요청은 이 저장소에서 판정을 읽어 적용합니다. 판정마다 유효 시간이 있습니다. 유효 시간이 지나면 판정이 저장소에서 사라지고, 사용자는 분석 대기로 돌아갑니다.

판정유효 시간어디에 적용되나
허용(ALLOW)15분(contexa.security.zerotrust.allow-validity로 바꿈)판정이 만들어진 같은 세션 · IP · 브라우저에서만. 다른 곳에서 온 요청은 새로 분석합니다.
추가 인증(CHALLENGE)1,800초(30분). 모델이 정하지 않고 CONTEXA가 대신 정한 추가 인증은 60초그 사용자의 모든 세션
검토 보류(ESCALATE)300초(5분). 기본 설정에서는 최종 판정으로 저장되지 않습니다(아래 참고)그 사용자의 모든 세션
차단(BLOCK)기한 없음(관리자가 승인해 풀 때까지. 차단 해제 MFA를 통과해도 차단은 풀리지 않습니다)그 사용자의 모든 세션
분석 대기(PENDING_ANALYSIS)저장된 판정이 없는 상태요청은 통과하고 분석이 시작됩니다
  • 더 엄격한 판정은 약한 판정에 덮이지 않습니다. 엄격한 순서는 차단 > 검토 보류 > 추가 인증입니다. 더 엄격한 판정이 걸려 있으면 약한 새 판정은 저장하지 않습니다.
  • 검토 보류는 기본 설정에서 저장되지 않습니다. 2차 분석이 검토 보류를 고르면 contexa.security.tiered.layer2.escalate-fallback-action(기본 CHALLENGE)으로 바꿔 저장합니다. 검토 보류를 그대로 저장하려면 contexa.security.tiered.layer2.allow-escalate-final-action=true를 씁니다.
  • 관찰 모드(SHADOW)는 판정을 만들고 적용하지 않습니다. 관찰 모드에서는 다음과 같이 동작합니다.
    • 모델은 적용 모드와 같은 방식으로 판정하고 판정 관찰 기록에도 남깁니다.
    • 판정은 사용자 판정 저장소에 쓰지 않고 별도의 키 아래 관찰 모드 전용 기억에 둡니다. 이 기억은 같은 사용자의 다음 요청을 다시 분석할지 정하는 데에만 씁니다.
    • 요청을 막거나 권한을 바꾸는 필터와 메서드 검사는 이 기억을 읽지 않습니다.
    • 차단 신호를 보내지 않고, 차단 사용자 기록을 남기지 않습니다.
    • AI 에이전트의 이후 요청을 읽기만 허용하는 범위 축소를 하지 않고, 위험 수준 변경 신호(위험 신호)도 보내지 않습니다.
    • 이 기억 속의 허용 판정은 학습에 쓰입니다.
  • 분석 사건에는 만들어질 때의 운영 모드가 기록됩니다(decisionBoundaryMode). 관찰 모드에서 만들어진 사건은, 판정이 나올 무렵 운영 모드가 ENFORCE로 바뀌었어도 적용하지 않습니다.
  • 판정 관찰 기록을 DB에 쓰지 못하면 판정을 적용하지 않습니다. 판정은 보관만 하고 사용자는 분석 대기로 남습니다. 같은 맥락(세션 · IP · 브라우저의 조합)의 새 분석은 30초 멈춥니다(contexa.security.zerotrust.analysis.audit-failure-cooldown-ms). 같은 사건을 다시 처리할 때는 분석 없이 보관한 판정을 씁니다.

저장된 판정이 다음 요청에서 권한을 어떻게 바꾸는지는 요청 시점 적용에서 설명합니다.

모델의 답이 바뀌는 경우

모델이 고른 대응은 아래 경우가 아니면 그대로 최종 판정이 됩니다. 모델을 부르지 못했거나 모델의 답을 쓸 수 없을 때는 CONTEXA가 안전한 쪽(추가 인증이나 검토 보류)으로 대응을 정합니다.

경우최종 판정
모델의 답을 받지 못함(공급자 장애, 호출 시간 초과, 출력 · 컨텍스트 한도 초과)1차 분석에서 일어나면 같은 요청을 2차 분석으로 넘깁니다(아래 "1차 분석 자체가 실패" 행). 2차 분석에서도 모델의 답을 받지 못하면 추가 인증으로 끝납니다. 이 추가 인증은 모델이 정한 판정이 아니므로 60초만 유지되고, 그동안 CONTEXA가 모델에게 최대 3번(10초 간격) 다시 묻습니다. 모델이 판정하면 그 판정이 이 추가 인증을 대신합니다.
대응 값이 없거나 알 수 없는 값추가 인증. 단 DENY 계열은 차단, REVIEW는 검토 보류로 읽습니다.
답의 형식이 출력 계약(모델이 답할 형식의 규약)에 맞지 않고, CONTEXA가 한 번 고쳐 물었는데도 그대로임검토 보류(1차라면 2차로 넘어감). 준비된 부분 "판정 규칙"(CONTEXA가 준비해 두었지만 제품 기본 버전에는 넣지 않은 부분)을 넣은 프롬프트 버전에서는 여전히 어긴 경계가 정한 대응(차단이나 허용)이 됩니다.
1차 분석 자체가 실패(결과 없음, 1차 제한 시간 초과)검토 보류로 바꿔 2차 분석으로 넘깁니다.
2차 분석이 검토 보류(ESCALATE)를 고름2차 분석 뒤에는 넘길 곳도, 검토하는 사람도 없으므로 contexa.security.tiered.layer2.escalate-fallback-action(기본 CHALLENGE)으로 바꿉니다.
2차 분석이 기술적으로 실패(예외, 30초 초과)같은 escalate-fallback-action으로 끝납니다. 실패하기 전에 모델이 이미 추가 인증이나 차단을 정했다면 그 판정을 유지합니다. allow-escalate-final-action=true이면 검토 보류가 최종 판정으로 저장됩니다(5분).
과부하 보호 조건(위 상자)추가 인증
최소 대응 규칙(모델의 대응이 너무 약하지 않도록 두는 하한)을 이 규칙 자체의 모드(contexa.security.zerotrust.minimum-action.mode=ENFORCE)로 켰고 답이 하한보다 약함CONTEXA가 한 번 고쳐 묻고, 그래도 약하면 검토 보류. 기본값 OBSERVE는 기록만 합니다(최소 대응 규칙의 모드이며, 운영 모드의 옛 이름 OBSERVE와 다릅니다). 최소 대응 규칙의 예: 설명되지 않는 단말 · 네트워크 차이가 있는 민감한 자원의 내보내기 요청은 추가 인증 이상이어야 합니다.

무엇을 배우나

판정 엔진은 판정 결과로 두 가지를 배웁니다. 하나는 사람마다의 행위 기준선(일하는 시간 · 단말 · 네트워크 · 대상 등)이고, 다른 하나는 과거 판정 기록입니다. 둘 다 다음 분석에서 모델이 받는 사실이 됩니다. 허용 판정이 쌓일수록 "이 사용자에게는 이것이 정상"이라는 기준이 더 정확해지고, 그 기준을 벗어난 요청을 구별하기 쉬워집니다.

  • 실제로 유지되는 허용 판정은 행위 기준선에 반영합니다. 적용 모드에서는 저장된 허용 판정이고, 관찰 모드에서는 기억해 둔 허용 판정입니다. 더 엄격한 판정이 걸려 있어 저장되지 않은 허용과 삭제된 계정의 늦게 도착한 결과는 배우지 않습니다. 허용이 아닌 판정으로 막힌 요청은 이 경로가 아니라 아래 "막혔다가 인증을 통과한 요청"의 경로로만 배웁니다. 학습은 지수 이동 평균(계수 0.1)이고, 사람의 요청이면 조직 기준선도 함께 갱신합니다.
  • 기준선이 "확립"되는 조건: 개인 기준선은 학습한 요청이 20건 이상이고, 서로 다른 날이 5일 이상이며, 최근 10번의 학습에서 처음 보는 값이 20% 이하일 때 확립됩니다. 조직 기준선은 3명 이상의 요청에서 배워야 확립됩니다. IP 대역처럼 값을 여러 개 기억하는 항목은 자리가 차면 가장 덜 쓰인 값을 밀어냅니다(오래된 값은 반감기 14일로 덜 셉니다).
  • 설명되지 않는 새 값은 바로 배우지 않고 학습을 보류합니다. 적용 모드에서 민감 등급 이상의 자원에 대한 요청에 시간 · 요일 · 네트워크 · 단말 가운데 기준선과 다르고 업무 기록으로도 설명되지 않는 값이 있으면, 그 요청에서 배우는 일을 보류합니다. 요청 자체는 허용된 채로 처리되고, 검토 보류(ESCALATE)와는 다릅니다. 같은 값이 2일 이상에 걸쳐 2번 이상 보이거나, 그 값이 든 요청에서 사용자가 추가 인증을 통과하면 그때 배웁니다. 한 번 나타난 값이 곧바로 보통의 행동으로 굳어지지 않게 하는 장치입니다. 에이전트는 자원 등급과 상관없이 처음 보는 값의 학습을 보류합니다. 관찰 모드에서는 이 보류 없이 바로 배웁니다.
  • 막혔다가 인증을 통과한 요청도 배웁니다. 적용 모드에서 추가 인증 · 검토 보류 · 차단으로 막힌 요청은 보관했다가, 사용자가 MFA를 통과하거나 관리자가 차단을 풀면 가중치 0.5로 배웁니다(허용된 요청의 가중치는 1입니다).
  • 과거 판정 기록은 판정이 저장될 때(관찰 모드에서는 기억될 때) 허용 · 추가 인증 · 검토 보류 · 차단을 가리지 않고 벡터 저장소에 함께 남깁니다. 90일(contexa.rag.etl.behavior.retention-days)이 지난 기록은 매일 03:45에 지웁니다. 0 이하로 두면 지우지 않습니다.
  • 행위 기준선은 마지막 학습 뒤 30일(contexa.security.zerotrust.baseline.retention) 동안 새 학습이 없으면 지웁니다.

운영할 때 알아 둘 것

  • 판정 결과 보기: 판정은 판정 관찰 기록 표(ctxa_ai_security_decision_observation)와 감사 기록에 남고, Zero Trust 콘솔의 판정 기록(/contexa/admin/zero-trust/decisions)과 관리 콘솔의 보안 이벤트 기록(/contexa/admin/security-monitor)에서 봅니다.
  • 판정이 나오지 않고 계속 분석 대기라면 먼저 확인합니다: 운영 모드가 OBSERVE · DISABLED가 아닌지, 채팅 모델과 벡터 저장소 빈이 있는지, 판정 관찰 기록 DB에 쓸 수 있는지.
  • 사건 대기열(분석을 기다리는 사건이 모이는 곳)은 10,000건까지입니다(contexa.security.plane.monitor.queue-size).
  • 사건 하나의 예산은 180초입니다. 분석 스레드 풀(기본 코어 32 · 최대 64 · 대기 256)에서 60초 넘게 기다리거나 예산을 넘기면 그 시도는 판정 없이 끝나고, 사건이 최대 3번 대기열에 다시 들어갑니다.
  • 분산 모드(contexa.infrastructure.mode=distributed)에서는 사건을 Kafka 토픽 ctxa.<앱 이름>.security.events.<범주>.<유형>(예: ctxa.order-service.security.events.authorization.method. 앱 이름은 spring.application.name이고, 이름이 없으면 접두사는 ctxa.뿐입니다)으로 보내고, 처리하지 못한 사건은 DLQ 토픽(ctxa.<앱 이름>.security-events-dlq, 또는 contexa.security.kafka.topic.dlq로 지정한 이름)으로 보냅니다.
  • contexa.security.tiered.layer2.enable-soar는 현재 OSS에서 효과가 없습니다. 차단 판정에 붙일 플레이북을 채우는 코드가 없어 SOAR가 실행되지 않습니다(SOAR).
