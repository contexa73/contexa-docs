Contexa는 어떻게 동작하나

Contexa가 요청마다 무엇을 묻고, 그 답(판정)을 언제 만들어 언제 적용하는지 한 화면에 설명합니다. 켜는 방법과 처음 고를 세 가지, 소유 방식에 따라 실제로 동작하는 것, 모듈 구성을 함께 다룹니다.

Contexa가 하는 일

로그인과 권한 검사를 통과한 요청이라도 계정을 훔친 사람이나 자기 권한을 다른 목적에 쓰는 사람의 요청일 수 있습니다. Contexa는 보호할 요청마다 "이 계정의 주인이 지금 자기 일을 하고 있나"를 AI 모델에게 묻고, 그 답을 판정으로 저장해 같은 사용자의 요청에 적용합니다.

판정은 요청을 붙잡아 두고 만들지 않습니다. 요청이 처리되고 응답이 나간 뒤 뒤에서 만들어지고, 같은 사용자의 다음 요청부터 적용됩니다. 그 요청 안에서 바로 판정이 필요한 메서드(@Protectable(sync=true))와, 판정 기록이 없는 에이전트 요청만 그 자리에서 판정합니다.

AI 에이전트의 요청도 사람의 요청과 구분해 따로 판정합니다(에이전트를 보안 주체로).

켜기

스타터 의존성(spring-boot-starter-contexa)만 넣으면 Contexa는 꺼져 있고 앱은 그대로 동작합니다. 메인 클래스에 @EnableAISecurity를 붙여야 켜집니다. 이 어노테이션은 AiSecurityImportSelector를 거쳐 AiSecurityConfiguration을 불러오고, 나머지 모듈별 자동 설정이 그 뒤를 잇습니다. 어노테이션이 있어도 contexa.enabled=false면 아무것도 불러오지 않습니다.

import io.contexa.contexacommon.annotation.EnableAISecurity;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
@EnableAISecurity   // mode를 비우면 SANDBOX: 로그인은 앱이 맡음(HOST_OWNED)
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}

그리고 Contexa 전용 데이터베이스를 꼭 적어야 합니다. 비어 있으면 애플리케이션이 시작하지 않습니다.

contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa   # 앱 DB와 다른 Contexa 전용 DB
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
  • 앱 DB와 같은 주소를 쓰면 시작하지 않습니다. 시험(POC)에서만 contexa.datasource.isolation.allow-shared-application-datasource와 contexa.datasource.isolation.shared-application-datasource-risk-accepted를 둘 다 true로 두면 같이 쓸 수 있고, 운영 프로필(prod · production)에서는 그래도 거부합니다.
  • 판정을 만들려면 AI 채팅 모델과 벡터 저장소가 있어야 합니다. Spring AI의 ChatModel과 VectorStore(PgVector, 이를 위한 임베딩 모델) 빈이 없으면 1차 · 2차 분석이 만들어지지 않아 보호된 요청이 계속 분석 대기에 머뭅니다.
  • 판정은 Contexa DB에 기록된 뒤에만 적용됩니다. 판정마다 관찰 기록(ctxa_ai_security_decision_observation 표)을 먼저 남기고, 이 기록을 쓰지 못하면 판정을 적용하지 않습니다.
  • 시작할 때 필요한 빈이 모두 있는지 진단합니다(contexa.capability.mode: AUTO · OFF · WARN · FAIL_FAST · STRICT). 기본 AUTO는 빠진 것이 있을 때 보통 앱이면 로그만 남기고, Contexa 전용 앱(FULL 모드 등)이면 시작을 멈춥니다(FAIL_FAST).

의존성부터 첫 판정 확인까지의 순서는 시작하기에 있습니다.

요청 하나가 지나가는 두 줄기

Contexa는 두 줄기로 일합니다. 요청 시점 줄기는 사용자가 기다리는 동안 이미 저장된 판정을 읽어 적용하고, 비동기 판정 줄기는 응답이 나간 뒤 판정을 새로 만들어 저장합니다. 두 줄기는 판정 저장소에서만 만납니다.

  • 분석 사건은 보호 메서드에서 나옵니다. 기본 설정에서 분석 사건을 내는 곳은 @Protectable 메서드 호출과 MFA 로그인 성공입니다. 보호 메서드가 아닌 일반 URL 요청은 분석하지 않고, 인가 정책이 거부한 요청은 분석 없이 세션 사실로만 남깁니다.
  • 요청 시점 단계는 AI 모델을 부르지 않습니다. 저장소의 판정만 읽습니다. 그래서 새 판정은 대개 다음 요청부터 적용됩니다.
  • 판정이 저장되기 전에는 분석 대기입니다. 요청은 통과하고, 진행 중인 응답은 차단 신호가 오면 끊을 수 있게 감싸집니다(두 소유 방식 모두, 허용일 때도 같습니다).

요청 하나를 처음부터 끝까지 따라가는 설명은 요청 하나의 일생에 있습니다.

소유 방식에 따라 동작하는 것

기본값(@EnableAISecurity만 붙임)은 HOST_OWNED입니다. 이때 Contexa는 로그인 체인을 만들지 않지만 집행은 모든 경로에서 합니다. 같은 요청 시점 필터가 앱의 Spring Security 체인 바로 뒤에서 서블릿 필터로 돌며 CONTEXA_OWNED와 같은 응답을 내고, @Protectable 메서드에서도 한 번 더 집행합니다.

기능CONTEXA_OWNEDHOST_OWNED(기본)
보안 필터 체인(로그인 · MFA 화면 · 필터)Contexa가 만듦만들지 않음(아래 관리 콘솔용 체인만 만듦). 앱의 SecurityFilterChain이 로그인 · 세션 · 쿠키 · 권한을 맡음. 앱이 체인을 선언하지 않았으면 Spring Boot 기본 보안이 모든 요청에 인증을 요구하고, Contexa가 시작할 때 WARN 로그로 알림. 앱 사용자도 없으면 시작이 거부됨
요청 시점 필터(추가 인증 · 차단 · 검토 보류 응답)Contexa 체인 안에서 동작앱 체인 바로 뒤의 서블릿 필터(브리지 · 추가 인증 · 차단 · 검토 보류)로 모든 경로에서 동작
판정에 맞춘 권한 바꾸기(ROLE_BLOCKED 등)세션 · JWT 체인에서 동작없음
@Protectable 메서드의 저장된 판정 집행동작동작(Spring Security 필터 뒤에서 사용자를 정하는 앱도 여기서 집행됨)
앱의 @PreAuthorize에서 쓰는 #ai 식앱에는 등록되지 않음(Contexa 식 처리기는 Contexa 자신의 클래스의 @PreAuthorize에만 쓰임)등록되지 않음
관리 콘솔 /contexa/admin/** 보호Contexa 체인과 메서드 보안이 보호/contexa/admin/**만 맡는 Contexa 자기 체인이 보호하고, /contexa/admin/login에서 Contexa 관리자로 로그인. 앱이 보호할 필요 없음. 메서드 보안(@EnableMethodSecurity)은 선택하는 추가 검사
에이전트 관문(호출 상한 · 끝난 위임 · 책임자 확인 · 좁혀진 범위)동작동작(자세히)

추가 인증(CHALLENGE)에 답하는 방법Contexa MFA 흐름Contexa의 확인 전용 추가 확인 /contexa/step-up(패스키, 메일 일회용 코드, 앱 자체 재인증). 앱의 로그인과 세션은 그대로(자세히)

소유 방식을 고르는 방법과 기존 Spring Security 앱에 붙이는 순서는 기존 Spring Security 앱에 붙이기에 있습니다.

판정 다섯 가지와 유효 시간

판정은 사용자마다 저장되고, 판정마다 유효 시간이 정해져 있습니다. "새 분석이 바꿀 때까지" 남지 않습니다.

판정유효 시간어디에 걸리나풀리는 방법
허용(ALLOW)15분(contexa.security.zerotrust.allow-validity로 바꿈)판정이 만들어진 같은 세션 · IP · 브라우저에서만시간이 지나면 분석 대기로 돌아감
추가 인증(CHALLENGE)1,800초(30분)그 사용자의 모든 세션이 판정이 시작한 MFA를 통과하면 허용, 또는 시간 만료
검토 보류(ESCALATE)300초(5분)그 사용자의 모든 세션관리자 승인. 풀리지 않고 시간이 지나면 다음 요청에서 차단으로 올라감(CONTEXA_OWNED)
차단(BLOCK)기한 없음그 사용자의 모든 세션관리자 승인(사용자는 차단 해제 MFA를 거쳐 해제를 요청)
분석 대기(PENDING_ANALYSIS)—저장된 판정이 없는 상태분석이 끝나 판정이 저장되면 바뀜
  • 더 엄격한 판정이 이깁니다. 차단 > 검토 보류 > 추가 인증 순서로, 더 엄격한 판정이 걸려 있으면 약한 새 판정은 저장하지 않습니다.
  • 판정별로 사용자가 받는 응답(HTTP 상태 · 이동하는 화면)은 요청 하나의 일생과 요청 시점 집행에 있습니다.

판정이 만들어지는 길

  • 대응(허용 · 추가 인증 · 차단 · 검토 보류)은 AI 모델이 고릅니다. 엔진은 사실을 모아 보낼 뿐입니다. 모델의 답을 받지 못하면(공급자 장애 · 시간 초과) 추가 인증으로 끝나고 2차 분석으로 넘기지 않습니다.
  • 섀도 모드에서는 저장하지 않습니다. 관찰 기록과 감사 기록만 남깁니다.
  • 무엇을 배우는지, 모델의 답이 바뀌는 경우는 판정 엔진에 있습니다.

판정을 확인하는 기록

판정이 왜 나왔는지 나중에 확인할 수 있도록 Contexa는 세 가지를 남깁니다. 어느 것도 판정을 바꾸지 않습니다.
