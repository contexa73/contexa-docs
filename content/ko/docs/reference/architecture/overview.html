CONTEXA는 어떻게 동작하나

요청이 들어와서 판정이 나고 그 판정이 적용되기까지 CONTEXA 안에서 무슨 일이 일어나는지 한 페이지에 설명합니다. 판정이 무엇인지, 켜는 방법, 처음 고를 세 가지 설정, 보안 모드에 따라 달라지는 동작, 모듈 구성을 차례로 다룹니다.

CONTEXA가 하는 일

로그인과 권한 검사를 통과한 요청이라도 계정을 탈취한 사람이나 자기 권한을 다른 목적에 쓰는 사람의 요청일 수 있습니다. CONTEXA는 이런 요청을 가려내는 보안 계층입니다. 개발자가 보호 대상으로 표시한 메서드(@Protectable)가 호출되면 CONTEXA는 "이 계정의 주인이 지금 자기 일을 하고 있나"를 AI 모델에게 묻습니다. 모델의 답은 판정이라는 이름으로 사용자별로 저장되고, 그 사용자의 이후 요청에 적용됩니다.

예를 들어 한 계정이 보호 메서드를 처음 호출하는 경우를 봅니다. 이 사용자에게 저장된 판정은 아직 없습니다. 이 계정은 지금까지 하루 몇 건씩만 고객 정보를 조회했는데, 이번에는 고객 정보 1,000건을 한꺼번에 내려받습니다. 요청은 다음 순서로 처리됩니다.

  1. 요청이 들어오면 CONTEXA의 필터가 이 사용자에게 저장된 판정을 읽습니다. 차단(BLOCK) · 추가 인증(CHALLENGE) · 검토 보류(ESCALATE)가 걸려 있으면 요청은 여기서 멈춥니다. 허용(ALLOW)이거나 저장된 판정이 아직 없으면 통과합니다.
  2. 통과한 요청은 앱 로직과 보호 메서드에서 그대로 처리되고 응답이 나갑니다. 이 사이에 CONTEXA가 AI 모델의 답을 기다리지 않으므로 응답이 느려지지 않습니다.
  3. 보호 메서드가 끝나면 CONTEXA는 이 요청의 사실(누가, 어느 세션과 IP에서, 무엇을 했는지)을 담은 기록을 냅니다. 이 기록을 분석 사건이라고 부릅니다.
  4. 요청 처리와는 별개로, 뒤에서 AI 모델이 분석 사건을 보고 판정을 만들어 저장합니다. 이 예에서는 모델이 추가 인증이나 차단을 고를 수 있습니다.
  5. 같은 사용자의 다음 요청에서 1번의 필터가 이 판정을 읽고 적용합니다. 새 판정은 이렇게 보통 다음 요청부터 효과가 납니다.

이 사용자에게 유효한 판정이 이미 있으면 3번과 4번에서 새로 분석하지 않습니다. 예를 들어 허용(ALLOW)은 같은 세션 · IP · 브라우저의 요청에서 15분 동안 그대로 쓰입니다.

요청 안에서 바로 판정이 필요한 메서드(@Protectable(sync=true))와, 저장된 판정이 없는 AI 에이전트 요청만 그 자리에서 판정하고 결과를 기다립니다(요청 하나가 지나가는 두 길). AI 에이전트(사람을 대신해 앱을 호출하는 프로그램)의 요청은 사람의 요청과 구분해 따로 판정합니다(에이전트를 보안 주체로). 판정은 다섯 가지입니다.

켜기

스타터 의존성(spring-boot-starter-contexa)만 추가하면 CONTEXA는 꺼진 채로 있고 앱은 이전과 동일하게 동작합니다. 메인 클래스에 @EnableAISecurity를 붙이면 켜집니다. 내부에서는 이 어노테이션이 AiSecurityImportSelector를 거쳐 AiSecurityConfiguration을 불러오고, 이어서 모듈별 자동 설정이 동작합니다. 어노테이션이 있어도 contexa.enabled=false이면 아무것도 불러오지 않습니다. mode를 쓰지 않으면 SANDBOX로 켜지고, 이때 로그인은 계속 앱이 맡습니다(인증 소유권은 적지 않으면 HOST_OWNED, 처음 고르는 세 가지 참고).

import io.contexa.contexacommon.annotation.EnableAISecurity;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
@EnableAISecurity   // mode를 비우면 SANDBOX: 로그인은 앱이 맡음(소유권 기본값 HOST_OWNED)
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}

켤 때는 CONTEXA 전용 데이터베이스(PostgreSQL)도 반드시 적어야 합니다. 주소(contexa.datasource.url)가 비어 있으면 애플리케이션이 시작하지 않습니다.

contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa   # 앱 DB와 다른 Contexa 전용 DB
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
  • 앱의 DB와 같은 주소를 쓰면 시작하지 않습니다. CONTEXA는 앱과 분리된 자기 전용 DB를 쓰는 것이 원칙이어서, contexa.datasource.url이 앱의 spring.datasource.url과 같으면 거부합니다. 시험(POC)에서만 contexa.datasource.isolation.allow-shared-application-datasource와 contexa.datasource.isolation.shared-application-datasource-risk-accepted를 둘 다 true로 두면 같이 쓸 수 있습니다. 운영 프로필(prod · production)에서는 그래도 거부합니다.
  • CONTEXA DB에 연결할 수 없을 때. 앱이 로그인을 맡는 기본 SANDBOX에서는, 시작할 때 5초를 기다려도 DB가 응답하지 않으면 앱이 CONTEXA 없이 시작하고 ERROR 로그를 남깁니다. DB에 연결은 되지만 계정에 PostgreSQL 확장(vector 등)을 만들 권한이 없을 때, 분산 인프라 모드(distributed)에서 Redis가 응답하지 않을 때도 같습니다. 원인을 고친 뒤 앱을 다시 시작해야 CONTEXA가 켜집니다. CONTEXA가 로그인을 맡는 FULL은 DB 없이는 아무도 로그인할 수 없으므로 앱이 시작하지 않습니다.
  • 판정을 만들려면 AI 채팅 모델과 벡터 저장소가 있어야 합니다. Spring AI의 ChatModel과 VectorStore(PgVector, 이를 위한 임베딩 모델) 빈이 없으면 1차 · 2차 분석이 만들어지지 않아 보호된 요청이 계속 분석 대기에 머뭅니다. 1차 · 2차 분석은 판정이 만들어지는 길에서 설명합니다.
  • 판정은 CONTEXA DB에 기록된 뒤에만 적용됩니다. CONTEXA는 판정마다 관찰 기록(ctxa_ai_security_decision_observation 표)을 먼저 남깁니다. 이 기록은 판정의 감사 기록이면서, 같은 사건을 다시 처리할 때 모델을 다시 부르지 않고 판정을 되살리는 기준입니다. 기록을 쓰지 못하면 판정을 적용하지 않습니다.
  • 시작할 때 필요한 빈이 모두 있는지 점검합니다(contexa.capability.mode: AUTO · OFF · WARN · FAIL_FAST · STRICT). 기본값 AUTO는 빠진 것이 있을 때 일반 앱이면 로그만 남기고, CONTEXA 전용 앱이면 시작을 멈춥니다(FAIL_FAST). CONTEXA 전용 앱은 앱의 데이터도 CONTEXA DB에 두는 FULL 모드 앱이거나, 앱 이름(spring.application.name)이 contexa-로 시작하는 앱입니다.

의존성부터 첫 판정 확인까지의 순서는 시작하기에 있습니다.

요청 하나가 지나가는 두 길

CONTEXA는 일을 두 길로 나눕니다. 요청 시점에는 사용자가 응답을 기다리는 동안 이미 저장된 판정을 읽어서 적용합니다. 비동기 판정은 요청 처리와 별개로 뒤에서 새 판정을 만들어 저장합니다. 두 길은 판정 저장소에서만 만납니다. 요청 시점이 읽는 판정은, 비동기 판정이 이전 요청에서 써 둔 것입니다.

  • 분석 사건은 보호 메서드에서 나옵니다. 기본 설정에서 AI 모델 분석으로 이어지는 사건은 @Protectable 메서드 호출이 냅니다. 로그인 성공은 분석하지 않습니다. 로그인한 사용자가 보호 메서드를 처음 부를 때, 모델이 그 자원을 함께 보고 판정합니다. 보호 메서드가 아닌 일반 URL 요청도 분석하지 않고, 인가 정책이 거부한 요청은 분석 없이 세션 기록에만 남깁니다.
  • 요청 시점에는 보통 AI 모델을 부르지 않습니다. 저장소의 판정만 읽습니다. 그래서 새 판정은 대개 다음 요청부터 적용됩니다. 요청 안에서 판정하고 결과를 기다리는 경우는 @Protectable(sync=true) 메서드와, 기본 설정에서 저장된 판정이 없는 AI 에이전트 요청입니다. 사람이 새 세션 · IP · 브라우저에서 앱이 민감하다고 표시한 자원을 처음 부르면, 요청을 붙잡지 않고 몇 초 뒤에 다시 보내라는 응답(429, Retry-After)을 돌려준 뒤 뒤에서 판정을 만듭니다.
  • 판정이 저장되기 전에는 분석 대기(PENDING_ANALYSIS)입니다. 요청은 통과합니다. 응답은 감싸서 내보냅니다. 응답이 나가는 도중 이 사용자에게 차단 신호가 오면 그 응답을 끊기 위해서입니다. 이 동작은 두 모드 모두 같고, 허용일 때도 같습니다.

요청 하나를 처음부터 끝까지 따라가는 설명은 요청 하나의 일생에 있습니다.

보안 모드에 따라 동작하는 것

보안 모드는 CONTEXA의 보안 설정이 앱에 무엇을 하는지 정합니다. 기본값(@EnableAISecurity만 붙임)은 앱과 격리하는 SANDBOX입니다. 앱의 로그인 · 인가 · 보안 설정(CSRF · CORS · 헤더)은 CONTEXA 때문에 바뀌지 않고, CONTEXA는 앱 사용자의 로그인 체인을 만들지 않지만 판정은 모든 경로에서 적용합니다. 같은 요청 시점 필터가 앱의 Spring Security 체인과 다른 서블릿 필터가 모두 끝난 뒤에 서블릿 필터로 돌며 FULL과 같은 응답을 내고, @Protectable 메서드 앞에서도 한 번 더 적용합니다. CONTEXA가 앱의 주 보안 구성(로그인 · 인가 · 보안 설정)을 만드는 FULL에서는 같은 필터가 CONTEXA가 만든 체인 안에서 돕니다. 두 모드 모두 CONTEXA의 전체 기능이 동작합니다. 인증 소유권(contexa.bridge.ownership)은 보안 모드와 다른 설정입니다. 앱이 직접 둔 구성요소(UserDetailsService · JwtDecoder 등)와 CONTEXA의 같은 종류가 만날 때 어느 쪽을 앱에 쓰는지 정하고(HOST_OWNED는 앱 것, CONTEXA_OWNED는 앱에 없는 종류를 CONTEXA 것으로 채움), 기능을 끄지 않으며, 네 조합 모두 허용됩니다. 적지 않으면 모드를 따릅니다(SANDBOX → HOST_OWNED, FULL → CONTEXA_OWNED). 소유권이 바꾸는 주된 것은 FULL의 주 체인이 앱 사용자를 어느 저장소로 로그인시키는지(HOST_OWNED는 앱의 UserDetailsService, CONTEXA_OWNED는 CONTEXA 계정)와, 관리자가 앱 사용자와 따로 로그인하는지(FULL + CONTEXA_OWNED만 한 체인에서 함께 로그인)입니다.

기능FULLSANDBOX(기본)
보안 필터 체인(로그인 · MFA 화면 · 필터)CONTEXA가 만듭니다(모든 요청을 받는 주 체인, 맨 끝 순서). 앱이 http.securityMatcher(...)로 좁힌 자기 체인은 그 앞에서 자기 경로를 맡고, 모든 요청을 받는 앱 체인이 있으면 시작을 거부합니다만들지 않습니다(아래 관리 콘솔용 체인만 따로 만듭니다). 앱의 SecurityFilterChain이 로그인 · 세션 · 쿠키 · 권한을 맡습니다. 앱이 사용자(UserDetailsService 등)는 두고 체인을 선언하지 않으면 Spring Boot 기본 보안이 모든 요청에 인증을 요구하고, CONTEXA는 시작할 때 WARN 로그로 알립니다. 앱에 체인도 사용자도 없으면 CONTEXA가 Spring Boot 기본 보안 대신 모든 요청을 들이는 격리 체인(contexaSandboxIsolationChain)을 두어, CONTEXA를 넣기 전의 접근이 그대로 유지됩니다
요청 시점 필터(추가 인증 · 차단 · 검토 보류 응답)CONTEXA 체인 안에서 동작합니다앱의 보안 체인과 서블릿 필터가 모두 끝난 뒤의 서블릿 필터(인증 브리지 · 추가 인증 · 차단 · 검토 보류)로 모든 경로에서 동작합니다
판정에 맞춘 권한 바꾸기(ROLE_BLOCKED 등)세션 · JWT 체인에서 동작합니다. 차단 · 추가 인증 · 검토 보류가 걸린 사용자는 권한이 판정 표시 권한 하나로 바뀌어, URL 정책과 @PreAuthorize 검사에서도 제한이 걸립니다하지 않습니다. 앱의 권한은 그대로이고, 제한은 요청 시점 필터가 응답으로 적용합니다

판정 다섯 가지와 유효 시간

판정은 사용자마다 저장되고, 판정마다 유효 시간이 정해져 있습니다. 새 분석이 바꿀 때까지 계속 남는 것이 아니라, 유효 시간이 끝나면 판정이 사라지고 그 사용자는 다시 분석 대기가 됩니다(차단은 기한이 없습니다).

판정유효 시간어디에 걸리나풀리는 방법
허용(ALLOW)15분(contexa.security.zerotrust.allow-validity로 바꿉니다. 운영에서는 10~20분을 권장하고, 벗어나면 WARN 로그를 남깁니다)판정이 만들어진 같은 세션 · IP · 브라우저(User-Agent)의 요청에만 적용됩니다. 셋 중 하나라도 달라지면 새로 분석합니다유효 시간이 지나면 분석 대기로 돌아갑니다
추가 인증(CHALLENGE)1,800초(30분)그 사용자의 모든 세션사용자가 추가 인증(MFA)을 통과하면 통과한 그 세션만 허용으로 바뀝니다. 다른 세션은 유효 시간이 끝날 때까지 계속 추가 인증을 요구받습니다. 유효 시간이 끝나도 풀립니다
검토 보류(ESCALATE)300초(5분)그 사용자의 모든 세션관리자가 승인하면 풀립니다. MFA로는 풀리지 않습니다. 풀리지 않은 채 유효 시간(300초)과 처음 대기 응답부터 5분이 모두 지나면, 그다음 요청에서 차단으로 올라갑니다. 기본 설정에서는 이 판정이 저장되지 않습니다(표 아래 설명)
차단(BLOCK)기한 없음그 사용자의 모든 세션관리자가 승인해야 풀립니다. 관리자가 허용한 경우 사용자는 해제용 MFA를 거쳐 해제를 요청할 수 있습니다
분석 대기(PENDING_ANALYSIS)—저장된 판정이 없는 상태분석이 끝나 판정이 저장되면 바뀝니다
  • 더 엄격한 판정이 이깁니다. 차단 > 검토 보류 > 추가 인증 순서로, 이미 더 엄격한 판정이 걸려 있으면 약한 새 판정은 저장하지 않습니다.
  • 허용이 걸려 있어도 즉시 판정 메서드는 매번 판정합니다. 허용은 같은 세션 · IP · 브라우저의 비동기 요청에서만 새 분석을 건너뜁니다. @Protectable(sync=true) 메서드는 허용이 걸려 있어도 호출마다 새로 판정합니다.
  • 기본 설정에서는 검토 보류가 저장되지 않습니다. 2차 분석도 정하지 못하고 검토 보류를 고르면, CONTEXA는 이를 contexa.security.tiered.layer2.escalate-fallback-action의 대응(기본 CHALLENGE)으로 바꿔 저장합니다. 관리자의 검토를 기다리는 검토 보류를 그대로 저장하려면 contexa.security.tiered.layer2.allow-escalate-final-action을 true로 합니다.
  • 판정별로 사용자가 받는 응답(HTTP 상태 · 이동하는 화면)은 요청 하나의 일생과 요청 시점 적용에 있습니다.

판정이 만들어지는 길

판정을 만들려고 AI 모델에게 묻는 일은 요청 처리와 별개로 뒤에서 일어납니다. 먼저 1차 분석이 판정하고, 1차가 정하지 못한 요청만 2차 분석이 다시 판정합니다. 모델이 판정을 내면 CONTEXA가 이를 저장하고 기록합니다.

  • 대응(허용 · 추가 인증 · 차단 · 검토 보류)은 AI 모델이 고릅니다. CONTEXA의 엔진은 사실을 모아 보낼 뿐 대응을 정하지 않습니다.
  • 모델의 답을 받지 못하면(공급자 장애 · 시간 초과) 1차 분석은 같은 요청을 2차 분석으로 넘깁니다. 2차 분석도 답을 받지 못하면 추가 인증으로 끝납니다. 이 추가 인증은 모델이 정한 것이 아니어서 60초만 유지되고, 그동안 CONTEXA는 모델에게 최대 3번(10초 간격) 다시 묻습니다. 모델이 나중에 허용을 고르면 이 추가 인증은 풀립니다. 같은 조직(없으면 같은 사용자)의 같은 경로에서 최근 1차 분석의 검토 보류가 절반을 넘으면(11건 이상 쌓인 뒤) 과부하 보호로 2차 분석 없이 바로 추가 인증으로 끝냅니다.
  • 관찰 모드에서는 판정을 적용하지 않습니다. 요청을 막지 않고 권한도 바꾸지 않습니다. 판정은 실제 판정 저장소에 쓰지 않고 관찰 모드용 메모리에만 기억해 같은 사용자의 다음 요청을 다시 분석하지 않게 하며, 관찰 기록과 감사 기록을 남깁니다.
  • 학습 내용과 모델의 답이 바뀌는 경우는 판정 엔진에 있습니다.

판정을 확인하는 기록

판정이 왜 나왔는지 나중에 확인할 수 있도록 CONTEXA는 세 가지를 남깁니다. 어느 것도 판정을 바꾸지 않습니다.

인프라 모드는 CONTEXA가 상태(저장된 판정, 분석 사건, 학습한 기준)를 어디에 두는지 정합니다. 두 모드 모두 CONTEXA 전용 DB(PostgreSQL)는 필요합니다.

상태단독(standalone, 기본)분산(distributed)

값은 contexa.infrastructure.mode에 standalone 또는 distributed로 적습니다. 연결 설정은 처음 켜기와 배포에 있습니다.

  • standalone에서 서버를 재시작하면 저장된 허용 · 추가 인증 · 검토 보류 판정이 사라지고, 사용자의 다음 요청을 다시 분석합니다. 차단은 contexa-iam이 ctxa_blocked_user 표에 남긴 기록에서 시작할 때 다시 올라오므로 유지되고, 그 기록이 없는 차단은 사라집니다. 서버가 여러 대이면 서버마다 판정을 따로 가집니다. 그래서 standalone은 개발용입니다.
  • distributed에는 Redis 클라이언트 라이브러리가 필요합니다. 앱에 spring-boot-starter-data-redis, org.redisson:redisson, spring-statemachine-data-redis가 없으면 앱이 시작하지 않습니다.
