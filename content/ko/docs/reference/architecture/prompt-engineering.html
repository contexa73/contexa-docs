보안 판단 프롬프트 파이프라인

Contexa의 프롬프트는 단순 문자열 조립이 아니라, 고객 시스템의 인증/인가/위임 증거를 수집하고, CanonicalSecurityContext로 표준화한 뒤, 신뢰도와 누락 지식을 함께 포함하여 LLM이 보안 판단을 내릴 수 있도록 구성됩니다. 요청 하나가 프롬프트가 되기까지는 수집 → 가공 → 정제 → 표준화 → 조립 → 검사 여섯 단계를 거칩니다. 조립 단계는 두 프롬프트 번들 가운데 하나로 그립니다. 빌드 기본인 v19 섹션 프롬프트, 또는 사실 ID 와 출력 계약 v3 을 쓰는 v20 사전 프롬프트입니다. 이 문서는 그 흐름을 처음부터 끝까지 한 줄로 이어 보여 드립니다.

여섯 단계 파이프라인

프롬프트는 즉석에서 만들어지지 않습니다. 여섯 단계를 거치며 요청 주변의 모든 사실을 수집·정리·검증한 뒤에야 LLM 에 전달됩니다. 각 단계는 독립된 패키지로 구현되어 있고, 이전 단계의 출력이 다음 단계의 입력이 됩니다.

1
수집
common/security
증거 도장 세 가지 추출
2
가공
autonomous/context
세션·업무·역할 프로필 확장
3
정제
context/hardener
주입 방어 · 형식 강제
4
표준화
CanonicalSecurityContext
22 필드 + 7 프로필 단일 레코드
5
조립
tiered/prompt
v19 섹션 또는 v20 사전 블록
6
검사
pipeline/processor
응답 검사, 최소 대응 규칙
설계 원칙. 빠진 사실 하나가 다음 단계를 막지 않습니다. v19 레이아웃은 증거가 없는 섹션을 빼고, v20 레이아웃은 모르는 사실마다 UNKNOWN 블록에 이름을 적으며, 시스템 글에서 모르는 사실은 일치도 불일치도 아니라고 밝힙니다.

Stage 1 · 수집

요청이 Spring Security 필터 체인(Filter Chain)에 들어오면 AuthBridge 구현체가 헤더·세션·속성 등 다양한 출처에서 주체를 추출합니다. 추출된 정보는 세 종류의 증거 도장(Stamp) 으로 포장됩니다. 이 세 도장이 이후 모든 단계의 원천 입력입니다.

Stage 2 · 가공

수집된 증거만으로는 LLM 이 이 사람이 평소와 다르게 행동하는지 판단할 수 없습니다. 2 단계는 세 종류의 구성요소가 원시 증거를 관찰 가능한 패턴으로 확장합니다.

수집기 (Collector)
  • SessionNarrativeCollector — 세션 내 행동 시퀀스
  • ProtectableWorkProfileCollector — @Protectable 어노테이션 리소스의 평소 업무 프로필
  • RoleScopeCollector — 역할 범위 스냅샷
보강기 (Enricher)
  • AuthenticationContextProvider — 인증 강도
  • DelegationContextProvider — 위임 범위 확장
  • PeerCohortContextProvider — 동료 그룹 이상치
  • FrictionContextProvider — 마찰·승인 이력
  • OrganizationContextProvider — 조직 계층
  • ReasoningMemoryContextProvider — 과거 강화 사례
추론기 (Inference)
  • ObjectiveDriftEvaluator — Agent 목표 이탈
  • ObservedScopeInferenceService — 관찰 범위
  • ContextCoverageEvaluator — 완성도 평가
Agent 전용 추론. 사람과 달리 Agent 는 허용된 목표 안에서만 움직여야 합니다. ObjectiveDriftEvaluator 는 현재 요청의 리소스·액션이 DelegationStamp 의 allowedOperations·allowedResources 범위를 벗어나는지 실시간으로 판정합니다.

Stage 3 · 정제

프롬프트 주입(Prompt Injection) · 필드 스푸핑 · 신호 위조는 LLM 기반 보안 시스템이 가장 경계해야 할 위협입니다. CanonicalSecurityContextHardener 는 모든 필드를 LLM 에 넘기기 전에 필드별 정규화 절차를 거칩니다.

입력 검증
  1. Null 필드 기본값 치환
  2. 문자열 트림 · 길이 제한
  3. 열거형 값 정규화
  4. 시간 · 좌표 범위 검증
  5. 언어 · 국가 코드 ISO 정규화
  6. 페이로드 디코딩 후 출력 가능 문자 80% 이상 필터
프로필 강화
  1. 세션 이야기 버스트 플래그 유지
  2. 업무 프로필 음수 값 제거
  3. 역할 범위 중복 제거 · 순서 보존
  4. 마찰 프로필 승인 이력 순서 고정
  5. 추론 메모리 가드레일 정제
  6. 신뢰 프로필 결정 상태 정규화

Stage 4 · 표준화

3 단계를 거친 모든 정보는 CanonicalSecurityContext 라는 단일 표준 컨텍스트 모델로 집약됩니다. 현재 구현은 Lombok 기반의 클래스이며, hardener가 필드 정규화와 기본값 보정을 수행한 뒤 프롬프트 조립 단계에 전달합니다. 22 개 필드와 7 개 프로필이 정해진 자리에 담기므로, 이후 프롬프트 조립 단계는 어떤 필드가 어디 있는지 예측 가능합니다.

CanonicalSecurityContext Java 클래스 구조

플랫폼 내부적으로 22개 기본 보안 필드와 7가지 행동 프로필을 단일 레코드로 담아 정규화하는 CanonicalSecurityContext의 실제 구조는 다음과 같습니다:

@Data
@Builder
@NoArgsConstructor
@AllArgsConstructor
public class CanonicalSecurityContext {
    private Actor actor;                             // 주체 신원 (userId, tenantId, roleSet 등)
    private Session session;                         // 세션/인증 상태 (sessionId, clientIp, mfaVerified 등)
    private Device device;                           // 기기 핑거프린트 (os, browser 등)
    private Intent intent;                           // 행위 의도 분석 (botUserAgent, impossibleTravel 등)
    private Location location;                       // 지리/네트워크 위치 (country, city, ipBand, asn 등)
    private Resource resource;                       // 대상 리소스 정보 (resourceId, sensitivity, actionFamily 등)
    private Authorization authorization;             // 기존 인가 결과 (effectiveRoles, policyId 등)
    private Delegation delegation;                   // 대리 위임 증거 (delegated, agentId, allowedOperations 등)
    private ExecutionSubject executionSubject;
    private ExecutionEnvelope executionEnvelope;
    private Bridge bridge;                           // 브릿지 탐지/커버리지 정보
    private ObservedScope observedScope;             // 자율적으로 관찰된 범위 스냅샷
    
    // 7종 자율 행동/보안 프로필
    private SessionNarrativeProfile sessionNarrativeProfile;  // 세션 내 행동 시퀀스
    private WorkProfile workProfile;                          // 평소 개인 업무 프로필
    private RoleScopeProfile roleScopeProfile;                // 역할 범위 프로필
    private PeerCohortProfile peerCohortProfile;              // 동료 그룹(Cohort) 프로필
    private FrictionProfile frictionProfile;                  // 마찰 및 승인 이력 프로필
    private ReasoningMemoryProfile reasoningMemoryProfile;    // RAG/과거 사례 분석 메모리 프로필
    
    private ContextCoverageReport coverage;          // 정보 완성도 분석 보고서
    @Builder.Default
    private Map<String, Object> attributes = new LinkedHashMap<>();
    @Builder.Default
    private List<ContextTrustProfile> contextTrustProfiles = new ArrayList<>();
    @Builder.Default
    private Instant collectedAt = Instant.now();

    // 내부 정적 도메인 모델 클래스 예시
    @Data public static class Actor {
        private String userId;
        private String organizationId;
        private String tenantId;
        private String principalType;
        private List<String> roleSet;
        private List<String> authoritySet;
    }

    @Data public static class Session {
        private String sessionId;
        private String clientIp;
        private String userAgent;
        private String authenticationType;
        private Boolean mfaVerified;
        private Integer concurrentSessions;
    }

    @Data public static class Delegation {
        private Boolean delegated;
        private String agentId;
        private String objectiveId;
        private List<String> allowedOperations;
        private List<String> allowedResources;
        private Boolean objectiveDrift;              // 대리 위임 목표 이탈 여부
    }
}

정보 완성도 네 단계

채워진 필드 수와 프로필 유무를 종합해 ContextCoverageEvaluator 가 완성도 등급을 매깁니다. 등급이 낮으면 LLM 에게 업무 패턴 기반 결론을 내리지 말라는 경고 문구가 자동 삽입됩니다.

BUSINESS_AWARE
신원 · 세션 · 범위 · 리소스 · 관찰 패턴 모두 확보
SCOPE_AWARE
신원 · 범위만. 관찰 프로필 부재
IDENTITY_AWARE
신원만. 범위 · 프로필 부재
ENVIRONMENT_ONLY
IP · 시간 등 환경만 확보

Stage 5 · 조립

표준화된 컨텍스트는 이제 프롬프트가 됩니다. SecurityDecisionPromptSections 가 시스템 글과 사용자 글을 만들고, 요청에 고른 프롬프트 번들이 사용자 글을 어떤 모양으로 그릴지 정합니다. 한 빌드는 프롬프트 키 cortex.security-decision 의 번들 두 개를 실행합니다. 이름 붙은 섹션을 그리는 v19 번들이 빌드 기본이고, 프롬프트 사전의 블록을 그리는 v20 번들이 함께 들어 있습니다. 같은 이벤트의 뒤 프롬프트(Layer2 프롬프트나 2차 분석)는 첫 프롬프트를 그린 번들로 그립니다.

v19 번들 · 빌드 기본

선택기가 다른 번들을 고르지 않으면 실행됩니다. 디스크립터의 릴리스 상태는 PRODUCTION 입니다.

  1. 레이아웃 V19_SECTIONS
  2. 시스템 섹션 2 개 + 사용자 섹션 16 개
  3. 계약 CORTEX_PROMPT_CONTRACT_V2
  4. 응답 검사는 v19 라벨을 읽음
v20 번들 · 사전 블록

초안(DRAFT)으로 함께 배포되며, 선택기가 고를 때만 실행됩니다.

  1. 레이아웃 V20_BLOCKS (v20-dictionary-blocks)
  2. 자체 시스템 글 + 사용자 블록 최대 7 개, Layer2 2차 분석에는 SECOND PASS
  3. 계약 CORTEX_PROMPT_CONTRACT_V3 (출력 계약 v3)
  4. 응답 검사는 프롬프트를 그린 사실을 읽음
번들 선택. contexa.security.tiered.prompt-bundle.active 에 실행할 번들 버전을 적습니다. 비워 두면 빌드 기본 번들이 실행됩니다. contexa.security.tiered.prompt-bundle.selector=registry 로 두면 프롬프트 릴리스 레지스트리가 상태·범위·카나리 비율로 고릅니다. 이 빌드가 실행할 수 없는 버전을 고르면 빌드 기본 번들로 돌아갑니다. 자세한 내용은 프롬프트 검수와 번들 버전을 참고하세요.

PromptGovernanceDescriptor 가 번들의 프롬프트 키·템플릿 키·버전을 프롬프트와 함께 기록합니다.

v19: 명시적 누락 지식

명시적 누락 지식(내부 섹션 키: EXPLICIT_MISSING_KNOWLEDGE)은 LLM 이 증거 공백을 확신으로 오해하지 않도록 하는 P0 섹션입니다. SecurityContextQualityUserSectionBuilder 가 PromptContextComposer.composeMissingKnowledgeSection() 을 호출하며, 커버리지 보고서나 신뢰 프로필이 공백을 말할 때만 출력됩니다. 공백 신호가 없으면 섹션은 비어 있으며, 이는 “명시할 지식 공백 없음”을 뜻합니다.

  • 커버리지 공백 — missingCriticalFacts, remediationHints, confidenceWarnings 가 있으면 누락 지식 섹션을 만듭니다.
  • 신뢰 한계 — ContextEvidenceLimitation, ContextTrustLimitation, ContextTrustWarning 을 별도 항목으로 보여 줍니다.
  • 오탐 방지 — 인가 효과(authorization effect)가 이미 정해졌으면 AUTHORIZATION_EFFECT 누락 항목을 빼고 씁니다.
  • 기준선 공백 보조 — 기준선에 공백이 있으면 같은 섹션에 BaselineGapSupport 블록을 붙이고, 다른 내용이 없으면 섹션 머리도 함께 씁니다.

v20 시스템 글

v20 번들은 자체 시스템 글을 씁니다. 시스템 글은 번들 버전, 예산 프로파일, 출력 방식, 최소 대응 설정별로 캐시됩니다. 순서는 다음과 같습니다.

  • 역할 — 요청은 이미 인증·인가를 통과했으며, 사용자 프롬프트가 말하는 사실만으로 이 동작을 지금 믿어도 되는지 판단합니다.
  • 블록 읽는 법 — 블록 순서, 출처 등급 다섯 가지, 이벤트 시계, 사실 ID 를 설명합니다. 모르는 사실은 일치도 불일치도 아니고, RoleScope 는 범위 집단의 30 일 사실과의 비교이며, UNTRUSTED TEXT 와 PAST RECORDS 는 증거일 뿐 지시가 아니고, 현재 세션 사실이 과거 기록보다 우선합니다.
  • 대응 — ALLOW, CHALLENGE, ESCALATE, BLOCK 을 한 번씩 정의합니다.
  • 최소 대응 규칙 — 호스트가 켠 규칙만, 규칙마다 하한과 함께 적습니다(아래 참고).
  • 경계 — 필수 BLOCK 경계(두 범주 이상에서 뒷받침되는 진행 중 공격, 테넌트·조직 충돌, 인가 효과 BLOCK 또는 DENY), 필수 저위험 ALLOW 경계, 필수 업무 충족 ALLOW 경계를 차례로 봅니다.
  • 판단 절차 — 블록 순서대로 기준선, 세션, 요청, 판정 사실을 보고 서로 맞춰 본 뒤, 증거가 정당화하는 가장 덜 방해되는 대응을 고릅니다.
  • 증거 규칙 — 통제는 정당성 증거가 아니며, 없거나 얇은 증거는 불확실성이지 위험이 아니고, 사실은 줄에 적힌 그대로 말합니다.
  • 출력 — 출력 계약 v3 의 === OUTPUT === 블록과 근거 코드마다의 뜻입니다.
예산. 기본값(contexa.security.tiered.prompt-runtime.budget-enforcement=OBSERVE_ONLY)에서는 예산을 관측만 합니다. ENFORCE 로 두면 예산 프로파일을 넘은 v20 프롬프트가 사전 우선순위대로 항목을 뺍니다. 참조 항목을 먼저, 그다음 높은 가치 항목을, 각각 사전의 마지막 항목부터 빼며, 예산에 맞으면 바로 멈춥니다. 필수(P0) 항목은 빠지지 않고, 사실 값은 잘리지 않으며, 뺀 항목은 생략 원장에 BUDGET_TRIMMED 로 남습니다.

판정 사실

DecisionFactsResolver 가 요청의 DECISION FACTS 를 계산합니다. 차원별로 평소 행동과 어떻게 다른지, 요청 시점에 회사 규정이 충족되는지, 승인·담당·티켓·당번·출장 기록, 세션 안 반복, 범위 집단 비교, 데이터 충돌, 집단 비교가 들어갑니다. 엔진이 확정하지 못한 사실은 줄을 쓰지 않고 모름으로 이름만 남깁니다. 엔진은 사실을 말할 뿐 판정하지 않습니다. 같은 DecisionFacts 가 프롬프트가 붙인 ID 와 함께 표준 컨텍스트에 남으므로, 프롬프트·봉인 기록·응답 검사·프롬프트 검수기가 한 계산을 읽습니다.

차원근거 코드차이를 설명할 수 있는 것
time, dayDEVIATION_TIME, DEVIATION_DAY그 작업을 덮는 유효한 승인이나 티켓
networkDEVIATION_NETWORK등록된 출장
device, login methodDEVIATION_DEVICE, DEVIATION_LOGIN_METHOD없음
target, action, class, size, rateDEVIATION_TARGET, DEVIATION_ACTION, DEVIATION_RESOURCE_CLASS, DEVIATION_SIZE, DEVIATION_RATE그 작업을 덮는 유효한 승인이나 티켓

최소 대응 규칙은 어떤 기록으로도 설명되지 않는 차이만 셉니다. 확립되지 않은 기준선과의 차이나 비교하지 않은 차원은 "설명되지 않음"이 아니라 모름입니다.

최소 대응 규칙

MinimumActionRules 는 판정 사실을 읽고 요청이 요구하는 가장 약한 대응을 정합니다. 대응의 순서는 ALLOW < CHALLENGE < ESCALATE < BLOCK 입니다. 규칙은 하한일 뿐 더 강한 대응을 고를 이유가 아니며, 코드가 대응을 직접 고르지는 않습니다.

규칙조건하한설정 (contexa.security.zerotrust.minimum-action)
MIN_P1_IDENTITY_DEVIATIONResourceClass 가 최소 등급 이상이고, 시각·요일·네트워크·기기 가운데 최소 개수 이상이 설명 없이 평소와 다름(기기는 하나로 셈)CHALLENGE.identity.enabled (true), .identity.min-deviations (2), .identity.min-resource-class (SENSITIVE)
MIN_P2_NEW_DEVICE_OR_NETWORK_EXPORT행동이 EXPORT 이고, ResourceClass 가 SENSITIVE 또는 CRITICAL 이며, 기기나 네트워크가 설명 없이 평소와 다름CHALLENGE.new-device-export.enabled (true)
MIN_P3_POLICY_NOT_SATISFIEDPolicySatisfied 가 no: 회사 규정이 요구하는 것을 덮는 유효한 기록이 없음.policy-satisfaction.action (ESCALATE).policy-satisfaction.enabled (true). 대응은 CHALLENGE 또는 ESCALATE 만 되며, 다른 값이면 기동이 멈춥니다
  • 프롬프트에서 — v20 시스템 글은 켜진 규칙만 하한과 함께 적습니다. 켜진 규칙이 없으면 규칙 문단이 빠집니다.
  • OBSERVE(기본) — .mode=OBSERVE 는 요청이 걸린 규칙과 판정이 그보다 약했는지를 이벤트 메타데이터(minimumActionFindings)에 기록만 하고, 판정은 그대로 둡니다.
  • ENFORCE — .mode=ENFORCE 이면 응답 검사가 걸린 규칙보다 약한 답을 위반(MINIMUM_ACTION_VIOLATION)으로 보고 교정 재시도로 보냅니다.
  • Layer2 — 풀리지 않은 Layer2 ESCALATE 는, 대체 대응이 걸린 규칙의 하한보다 약하면 대체 대응으로 바꾸지 않습니다.

LLM 이 응답을 돌려주면 끝이 아닙니다. 응답 검사가 답을 판정으로 만들기 전에 읽습니다. v20 프롬프트라면 근거 문장의 주장(예: LoginMethod 는 MFA 미확인인데 확인됐다고 쓴 경우), 필수 경계, 근거 코드 하나하나를 프롬프트를 그린 사실과 대조하고, ENFORCE 모드에서는 최소 대응 규칙도 적용합니다. v19 프롬프트는 라벨로 검사합니다.

  • Layer2 ESCALATE — contexa.security.tiered.layer2.allow-escalate-final-action 이 true 가 아니면, 풀리지 않은 ESCALATE 는 contexa.security.tiered.layer2.escalate-fallback-action(기본 CHALLENGE)으로 바뀌고 판정에 LAYER2_ESCALATE_TERMINALIZED 가 남습니다.

최종 결정 레코드

모든 단계를 통과한 뒤 만들어지는 SecurityDecision 은 단순히 ALLOW · BLOCK 한 값이 아닙니다. LLM 이 제안한 대응, 최종 집행 대응, 둘이 다른 이유가 함께 남습니다.

SecurityDecision 발췌

Layer2 판정의 발췌입니다. 모델은 모르는 사실을 인용해 ESCALATE 를 제안했고, 계층 전략이 풀리지 않은 ESCALATE 를 설정된 대체 대응 CHALLENGE 로 바꿨습니다.

사람과 Agent 의 프롬프트 차이

같은 파이프라인을 통과해도 주체 유형에 따라 프롬프트의 무게 중심이 달라집니다. 사람은 평소 행동 기준과의 편차가 핵심이고, Agent 는 허용된 목표 범위의 이탈이 핵심입니다.

프롬프트 검수

프롬프트 검수기는 판정 경로와 떨어져 봉인된 프롬프트를 읽고, 각 줄을 그 줄을 그린 봉인 사실과 대조합니다. 봉인 무결성, 번들 대조, 사전 계약, 판정 사실 일치, 사실 정확성, 모름 표기, 과거 기록 표기, 원천 진실성, 같은 사실, 근거 일치를 봅니다. 사람이 검토할 문제를 가리킬 뿐 프롬프트·판정·규칙은 바꾸지 않습니다. 번들 버전은 릴리스 게이트를 거쳐 레지스트리 상태를 옮겨 가며, 섀도 실행·카나리·롤백을 지원합니다.

더 보기. 검사 목록, 레지스트리 상태, 릴리스 게이트와 설정은 프롬프트 검수와 번들 버전에서 설명합니다.
