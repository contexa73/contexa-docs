요청 하나의 일생

요청 하나가 들어와 저장된 판정을 적용받고, 실행된 뒤 분석되어, 그 판정이 다음 요청에 적용되기까지를 차례로 따라갑니다. 판정마다 사용자가 받는 응답, 차단이 퍼지고 풀리는 길, 앱 코드에서 판정을 읽는 방법도 함께 다룹니다.

한눈에 보기

요청 시점에는 이미 저장된 판정만 적용합니다. 이 요청에 대한 새 판정은 응답이 나간 뒤 만들어지고, 같은 사용자의 다음 요청부터 적용됩니다. 두 일을 잇는 것은 사용자별 판정 저장소 하나입니다.

예. 사용자가 보호 메서드로 보고서를 내보냅니다. 응답은 바로 나가고 뒤에서 분석이 시작됩니다. AI 모델이 차단을 고르면 판정이 저장되고, 그 사용자의 다음 요청은 차단 응답을 받습니다. 모델이 허용을 고르면 그 허용은 같은 세션 · IP · 브라우저에서 15초 동안만 쓰이고, 그 뒤 요청은 다시 분석 대기가 되어 분석됩니다.

소유 방식의 전체 비교는 Contexa는 어떻게 동작하나에 있습니다.

요청 시점 ①: 판정 읽기와 권한 바꾸기

이 단계는 CONTEXA_OWNED에서만 있습니다. Contexa 체인이 보안 컨텍스트를 읽는 순간 저장된 판정을 적용해, 앱의 hasRole() 같은 권한 검사가 판정을 따르게 합니다.

  • 어디서: 세션 체인은 보안 컨텍스트 저장소(AISessionSecurityContextRepository)가 컨텍스트를 처음 읽을 때, 토큰 체인은 JWT 검증 바로 뒤의 필터(AIOAuth2ZeroTrustFilter)가 적용합니다.
  • 누구의 판정: 사용자 ID로 읽습니다. 사람 대신 일하는 에이전트는 자기 키(<사용자>::agent::<에이전트>)로 읽고, 위임자가 차단이면 함께 차단으로 봅니다.
  • 허용은 맥락에 묶입니다: 허용은 판정이 만들어진 세션 · IP · 브라우저(맥락 해시)에서만 허용으로 읽히고, 다른 맥락에서는 분석 대기로 읽힙니다.
  • 5초 캐시: 같은 사용자 · 맥락의 판정은 5초 동안 서버 메모리에 두고 다시 씁니다. 그래서 새 차단 직후 권한 바꾸기는 최대 5초 늦을 수 있지만, 두 필터는 캐시 없이 저장소를 직접 읽으므로 차단 응답은 늦지 않습니다.
  • 무효화된 세션 · 토큰: 무효화 목록에 있는 세션은 끝내고 로그인하지 않은 요청으로 처리합니다. JWT는 401로 거부합니다.
  • contexa.security.zerotrust.enabled=false면 이 단계(판정 적용 · 권한 바꾸기 · 세션 추적)를 하지 않습니다.
  • 구현 순서: AISessionSecurityContextRepository의 loadDeferredContext → AbstractZeroTrustSecurityService의 applyZeroTrustToContext → adjustAuthoritiesByAction. 세션 추적과 무효화 기록은 단독 모드에서 메모리(InMemoryZeroTrustSecurityService), 분산 모드에서 Redis(RedisZeroTrustSecurityService)에 둡니다.
판정바뀐 권한
허용원래 권한

차단ROLE_BLOCKED 하나만

권한 집합이 실제로 바뀔 때만 로그인 객체를 바꿉니다. 세션 체인은 판정과 점수를 담은 ZeroTrustAuthenticationToken으로, 토큰 체인은 권한만 바꾼 새 JwtAuthenticationToken으로 바꿉니다. 불투명(opaque) 토큰은 권한을 바꾸지 않고 두 필터의 판정 읽기만 남습니다.

요청 시점 ②: 판정별로 사용자가 받는 것

CONTEXA_OWNED에서는 필터 두 개(추가 인증을 다루는 챌린지 필터, 차단 · 검토 보류를 다루는 접근 제어 필터)가 권한이 아니라 저장소의 판정을 직접 읽어 응답합니다. 브라우저 요청은 안내 화면으로 이동하고, API · AJAX 요청은 JSON 오류를 받습니다.

판정브라우저API풀리는 방법
허용그대로 진행—
추가 인증/contexa/zero-trust/challenge-required?mfaUrl=…로 이동401 MFA_CHALLENGE_REQUIRED(본문 mfaUrl). MFA 시작은 사용자마다 잠금(기본 임대 30초)을 잡아 한 번만 하고, 다른 요청이 시작하는 중이면 503 MFA_BUSY_RETRY + Retry-After: 3. 앱에 MFA 흐름이 없으면 401 ZERO_TRUST_CHALLENGE이 판정이 시작한 MFA를 통과하면 허용으로 바뀜(로그인 때의 MFA는 풀지 않음). 또는 1,800초 만료
차단/contexa/zero-trust/blocked로 이동403 ACCOUNT_BLOCKED. 차단 해제 MFA를 시작한 뒤에는 401 BLOCK_MFA_REQUIRED관리자 승인(차단의 전파와 해제)
검토 보류/contexa/zero-trust/analysis-pending?returnUrl=…로 이동423 SECURITY_REVIEW_IN_PROGRESS + Retry-After: 30관리자 승인. MFA로는 풀리지 않음. 분석 판정(300초)과 첫 대기 응답부터 5분이 모두 지나면 그다음 요청에서 차단으로 올라감
분석 대기통과. 응답은 감싸져, 응답 도중 차단 신호가 오면 끊김판정이 저장되면 바뀜
  • 차단 응답은 세션을 끝내지 않습니다. 진행 중인 응답을 끊고, 이후 요청을 차단 응답으로 막습니다.
  • 판정 때문에 멈춘 요청은 분석하지 않고 세션 사실로만 남깁니다.
  • 필터의 위치, 제외 경로, 응답 본문 전체는 요청 시점 집행에 있습니다.

메서드 단계: @Protectable

보호 메서드 앞의 가로채기(AuthorizationManagerMethodInterceptor)는 두 소유 방식 모두에서 돕니다. Spring의 메서드 보안(@PreAuthorize 등)보다 먼저 실행됩니다.

  • 섀도 모드에서는 6단계의 저장된 판정과 즉시 판정을 기록만 하고 거부하지 않습니다.
  • 앱이 자원 인증 관문(ProtectableResourceCertificationGate) 빈을 두면, @Protectable(verificationRequired)(기본 true)인 메서드 가운데 인증되지 않은 자원을 423으로 거부합니다. OSS에는 이 빈의 구현이 없습니다.
  • 판정 기록이 없는 에이전트 요청을 그 자리에서 판정할지는 contexa.security.zerotrust.protectable.unrecorded-agent-request(기본 DECIDE_IN_PLACE, PROCEED면 사람처럼 통과)로 정합니다.

거부는 아래 응답으로 바뀝니다. 본문은 status · code(ZERO_TRUST_<판정>) · message · action · resourceId · riskScore · analysisTimeout · timestamp입니다.

HTTP 상태언제
403차단
401추가 인증. 그 자리에서 추가 인증 MFA를 시작하고 본문에 mfaUrl을 넣음. 에이전트의 추가 인증은 CONTEXA_OWNED에서 책임자 확인 요청으로 답함(책임자 확인)

판정이 만들어지는 과정

분석 사건이 나간 뒤의 일입니다. 요청 스레드는 기다리지 않습니다.

  • 거르기: 이 사용자(에이전트는 자기 키) · 맥락의 판정이 분석 대기가 아니면 새로 분석하지 않고 "분석하지 않은 요청"으로만 기록합니다. contexa.security.zerotrust.enabled=false면 사건을 받아도 아무것도 하지 않습니다.
  • 전달: 단독 모드는 같은 서버 안에서, 분산 모드는 Kafka로 사건을 넘깁니다.
  • 줄 세우기: 크기 10,000의 대기열에 넣고 8건씩 꺼내, 사용자 · 세션마다 한 줄로 세워 한 번에 하나씩 처리합니다. 사건 하나의 분석 예산은 180초이고, 일시적으로 실패하면 최대 3번 다시 줄을 섭니다.
  • 판정: 1차 분석이 판정하고, 1차가 ESCALATE를 고른 경우만 2차 분석이 다시 판정합니다. 한 사건의 1차 · 2차 프롬프트는 같은 프롬프트 묶음으로 그립니다.
  • 처리 단계: 판정 만들기(50) → 집행(55) → 증거 봉인(56) → 감사(60) → SaaS 전달(65, 켰을 때만) 순서로 돕니다.

어떤 요청이 분석되는지, 모델의 답이 바뀌는 경우, 층마다 다른 모델 쓰기는 판정 엔진에 있습니다.

차단의 전파와 해제

차단이 퍼지는 길

신호를 놓친 서버도 0.5초마다 저장소를 확인합니다. Contexa 자신의 거부 응답은 끊지 않습니다.

차단을 푸는 길

  • 차단 기록의 상태는 BLOCKED · UNBLOCK_REQUESTED · RESOLVED · TIMEOUT_RESPONDED · MFA_FAILED 다섯 가지입니다.
  • 차단 해제 MFA는 시도 한도(contexa.security.zerotrust.max-block-mfa-attempts, 기본 2)를 넘으면 더 시작할 수 없습니다. 실패 횟수는 24시간 동안 셉니다.
  • 위임 에이전트의 차단은 MFA로 풀 수 없고 403 AGENT_BLOCKED를 받습니다.
  • 검토 보류가 풀리지 않고 차단으로 올라갈 때도 같은 차단 저장 · 깃발 · 차단 기록(사람) 또는 에이전트 정지가 일어납니다.

에이전트 요청은 어떻게 다른가

항목에이전트 요청에서동작하는 소유 방식
판정 키위임 에이전트는 <사용자>::agent::<에이전트>에 따로 저장. 위임자가 차단이면 함께 차단으로 봄둘 다

자세한 내용은 에이전트를 보안 주체로와 정지 · 확인 · 제한에 있습니다.

집행 모드와 운영

집행 모드AI 분석판정 저장 · 적용관찰 · 감사 기록학습
DISABLED · OBSERVE안 함없음없음없음
SHADOW함안 함. 보호 메서드의 저장된 판정도 기록만남김안 함
ENFORCE(기본)함저장하고 다음 요청부터 적용남김실제로 적용된 허용만
  • 요청 시점 필터는 집행 모드를 보지 않습니다. 집행 모드를 SHADOW로 바꾸거나 contexa.security.zerotrust.enabled=false로 꺼도, 이미 저장된 차단(기한 없음) · 추가 인증 · 검토 보류는 필터가 계속 집행합니다(CONTEXA_OWNED).
  • 사건은 낼 때의 모드를 가지고 다닙니다. SHADOW일 때 낸 사건의 판정은 그사이 ENFORCE로 바꿔도 저장 · 적용하지 않습니다.
  • 판정 결과는 관찰 기록과 감사 기록에 남습니다. 관찰 기록 표는 ai_security_decision_observation이고, 관리 콘솔 "실시간 현황"(/contexa/admin/security-monitor)에서 판정 기록을 봅니다.

앱 코드에서 판정 읽기

  • 요청 속성 contexa.zeroTrustAction: 판정을 적용한 요청에 그 판정이 남습니다(CONTEXA_OWNED).
  • 로그인 객체 ZeroTrustAuthenticationToken: getAction() · getTrustScore() · getThreatScore(). 세션 체인에서 권한이 바뀌었을 때만 이 객체가 되고, 토큰 체인에서는 JwtAuthenticationToken이 남습니다.
  • 정책 식 #ai: Contexa 정책(XACML) 식에서 씁니다. 앱의 @PreAuthorize에서 쓰려면 CONTEXA_OWNED여야 합니다.
  • 판정 값의 분류: ZeroTrustAction의 isBlocking()은 차단 · 검토 보류, isAccessRestricted()는 차단 · 추가 인증 · 검토 보류일 때 참입니다.
식참이 되는 때
#ai.isAllowed()현재 판정이 허용
#ai.isBlocked()현재 판정이 차단
#ai.needsChallenge()현재 판정이 추가 인증
#ai.needsEscalation()현재 판정이 검토 보류
#ai.isPendingAnalysis()현재 판정이 분석 대기
#ai.hasAction('ALLOW')현재 판정이 적은 것과 같음
#ai.hasActionIn('ALLOW', 'PENDING_ANALYSIS')현재 판정이 적은 것 가운데 하나
평소 상태는 대개 분석 대기입니다. 허용은 15초 동안 같은 맥락에서만 쓰이므로 #ai.isAllowed()만 요구하면 대부분의 요청이 거부됩니다. 제한 판정만 거르려면 아래처럼 허용과 분석 대기를 함께 받습니다. 
// CONTEXA_OWNED(@EnableAISecurity(mode = SecurityMode.FULL) 또는 contexa.bridge.ownership=CONTEXA_OWNED)에서만 #ai가 등록됩니다.
import org.springframework.security.access.prepost.PreAuthorize;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class ReportController {

    @GetMapping("/reports")
    @PreAuthorize("#ai.hasActionIn('ALLOW', 'PENDING_ANALYSIS') and hasRole('ADMIN')")
    public String reports() {
        return "ok";
    }
}

에이전트용 식(isAgent() 등)은 정지 · 확인 · 제한, 정책 식 전체는 AI 보안 표현식에 있습니다.

학습과 실시간 알림

  • 학습: 실제로 적용된 허용 판정만 행위 기준선에 배웁니다. 섀도 모드의 판정은 배우지 않습니다. 학습 서비스(SecurityLearningService)가 기준선 학습(BaselineLearningService, 지수 이동 평균)으로 넘기고, 자주 쓰는 IP 대역은 덜 쓰인 것부터 밀어내며 일정 개수만 남깁니다. 자세한 조건은 판정 엔진의 "무엇을 배우나"에 있습니다.
  • 실시간 알림(SSE): GET /contexa/admin/api/aiam/sse/zero-trust/subscribe를 구독하면 로그인한 사용자 자신의 판정 · 분석 진행 · 오류 알림을 받습니다(ZeroTrustSsePublisher). 관리자에게 모든 판정을 보내는 통로가 아닙니다.
  • 안내 화면: /contexa/zero-trust/blocked · /contexa/zero-trust/challenge-required · /contexa/zero-trust/analysis-pending는 판정을 받은 사용자가 보는 화면입니다.
