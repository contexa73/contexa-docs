요청 하나의 처리 과정

이 페이지는 요청 하나가 들어와서 판정이 나고 적용되기까지의 경로를 따라갑니다. CONTEXA는 요청을 처리하는 경로와 요청을 분석하는 경로를 나눕니다. 요청 시점에는 이미 저장된 판정만 적용하고, 새 판정은 응답이 나간 뒤에 만들어 다음 요청에 적용합니다. 판정별로 사용자가 받는 응답, 차단이 전파되고 해제되는 방식, 앱 코드에서 판정을 읽는 방법도 설명합니다.

개요: 요청 경로와 분석 경로

CONTEXA는 요청을 처리하는 일과 요청을 분석하는 일을 서로 다른 길에서 합니다. 요청 경로는 요청이 들어와 응답이 나갈 때까지입니다. 이 길에서는 이미 저장된 판정만 적용합니다. 분석 경로는 응답이 나간 뒤에 AI 모델이 그 요청을 분석해 새 판정을 만들고 저장하는 길입니다. 새 판정은 같은 사용자의 다음 요청부터 적용됩니다.

판정은 한 사용자의 요청을 어떻게 다룰지 정한 결과입니다. 허용(ALLOW), 추가 인증(CHALLENGE, 한 번 더 인증을 요구), 검토 보류(ESCALATE, 관리자가 검토할 때까지 요청을 멈춤), 차단(BLOCK) 가운데 하나입니다. 저장된 판정이 없거나 유효 시간이 지난 상태는 분석 대기(PENDING_ANALYSIS)라고 부릅니다. 이때 요청은 통과하고 분석이 시작됩니다.

두 길을 잇는 것은 사용자별 판정 저장소 하나입니다. 분석 경로가 판정을 저장소에 쓰면, 요청 경로가 같은 사용자의 다음 요청에서 그 판정을 읽습니다. 저장소는 단독 모드(standalone, 기본)에서는 서버 메모리이고, 분산 모드(distributed)에서는 Redis입니다. 모드는 contexa.infrastructure.mode로 정합니다.

예. 사용자가 보호 메서드로 보고서를 내보냅니다. 응답은 분석을 기다리지 않고 바로 나가고, 분석은 뒤에서 시작됩니다. AI 모델이 차단을 고르면 판정이 저장되고, 그 사용자의 다음 요청은 차단 응답을 받습니다. 모델이 허용을 고르면 그 허용은 같은 세션 · IP · 브라우저에서 15분 동안만 쓰입니다(contexa.security.zerotrust.allow-validity). 15분이 지난 뒤의 요청은 다시 분석 대기가 되어 분석됩니다. 그 요청 안에서 바로 판정이 필요한 메서드만 예외이며, 아래 메서드 단계에서 설명합니다.

3단계(적용)가 이루어지는 방식은 로그인 · 세션 · 쿠키를 누가 맡느냐에 따라 달라집니다. 앱이 맡으면 HOST_OWNED, CONTEXA가 맡으면 CONTEXA_OWNED입니다. 이 설정을 소유 방식이라고 부르며 contexa.bridge.ownership으로 정합니다.

어느 소유 방식이든 저장된 판정을 필터와 보호 메서드가 적용한다는 점은 같고, 달라지는 것은 권한을 바꾸는지와 추가 인증을 어디로 보내는지입니다. 소유 방식의 전체 비교는 CONTEXA는 어떻게 동작하나에 있습니다.

요청 시점 ①: 저장된 판정을 권한에 반영하기 (CONTEXA_OWNED)

CONTEXA가 로그인을 맡을 때(CONTEXA_OWNED)만 있는 단계입니다. CONTEXA가 만든 체인이 요청에서 보안 컨텍스트(Spring Security의 로그인 정보)를 읽는 순간, 저장된 판정을 읽어 사용자의 권한을 판정에 맞게 바꿉니다. 그러면 앱의 hasRole() 같은 권한 검사가 따로 코드를 쓰지 않아도 판정을 따릅니다. 예를 들어 차단된 사용자는 원래 권한 대신 ROLE_BLOCKED만 가지므로 hasRole('ADMIN') 검사를 통과하지 못합니다.

  • 어디서: 세션으로 로그인하는 체인(세션 체인)에서는 보안 컨텍스트 저장소(AISessionSecurityContextRepository)가 컨텍스트를 처음 읽을 때 적용합니다. JWT로 인증하는 체인(토큰 체인)에서는 JWT 검증 바로 뒤의 필터(AIOAuth2ZeroTrustFilter)가 적용합니다.
  • 누구의 판정을 읽나: 사용자 ID로 저장된 판정을 읽습니다. 사용자를 대신해 일하는 AI 에이전트는 자기 키(<사용자>::agent::<에이전트>)로 저장된 판정을 읽습니다. 에이전트에게 일을 맡긴 사용자(위임자)가 차단이면 에이전트도 차단으로 봅니다.
  • 허용은 만들어진 환경에 묶입니다: 허용은 판정이 만들어질 때의 세션 · IP · 브라우저로 만든 값(맥락 해시)과 같은 요청에서만 허용으로 읽습니다. 하나라도 다르면 분석 대기로 읽습니다. 차단 · 추가 인증 · 검토 보류는 이렇게 묶이지 않고 그 사용자의 모든 세션에 걸립니다.
  • 5초 캐시: 허용으로 읽은 결과는 같은 사용자 · 맥락에서 5초 동안 서버 메모리에 두고 다시 씁니다. 차단 같은 제한 판정은 캐시하지 않습니다. 그래서 새 차단이 저장된 직후에도 권한 바꾸기는 최대 5초 늦을 수 있습니다. 다음 소절의 필터 두 개는 캐시 없이 저장소를 직접 읽으므로 차단 응답은 늦지 않습니다.
  • 무효화된 세션 · 토큰: 무효화 목록에 있는 세션은 끝내고, 요청은 로그인하지 않은 것으로 처리합니다. 무효화된 JWT는 401로 거부합니다.
  • contexa.security.zerotrust.enabled=false이면 이 단계(판정 적용 · 권한 바꾸기 · 세션 추적)를 하지 않습니다. 세션 추적은 강제 로그아웃이 사용자의 모든 세션에 닿도록 세션 ID를 사용자별로 기록하는 일입니다.
  • 코드에서 따라가기: AISessionSecurityContextRepository의 loadDeferredContext → AbstractZeroTrustSecurityService의 applyZeroTrustToContext → adjustAuthoritiesByAction 순서로 실행됩니다. 세션 추적과 무효화 기록은 단독 모드에서는 메모리(InMemoryZeroTrustSecurityService)에, 분산 모드에서는 Redis(RedisZeroTrustSecurityService)에 둡니다.

권한이 실제로 달라질 때만 로그인 객체를 바꿉니다. 세션 체인에서는 판정과 점수를 담은 ZeroTrustAuthenticationToken으로 바꾸고, 토큰 체인에서는 권한만 바꾼 새 JwtAuthenticationToken으로 바꿉니다. 불투명(opaque) 토큰은 권한을 바꾸지 않으므로, 이 경우에는 아래 필터 두 개가 판정을 읽어 적용하는 것만 남습니다.

요청 시점 ②: 판정별로 사용자가 받는 것

저장된 판정이 추가 인증 · 차단 · 검토 보류이면 CONTEXA는 요청을 앱에 넘기지 않고 직접 응답합니다. 이 일은 필터 두 개가 맡습니다. 챌린지 필터는 추가 인증을 다루고, 접근 제어 필터는 차단과 검토 보류를 다룹니다. 두 필터는 사용자의 권한이 아니라 판정 저장소의 판정을 직접 읽습니다. 그래서 두 소유 방식 모두 같은 응답을 냅니다. HOST_OWNED에서는 두 필터가 앱 체인 바로 뒤에서 돌고, 추가 인증은 CONTEXA의 추가 인증 화면으로 보냅니다(HOST_OWNED의 추가 인증). 브라우저 요청은 안내 화면으로 이동하고, API · AJAX 요청은 JSON 오류를 받습니다.

판정브라우저API풀리는 방법
허용요청이 그대로 진행됩니다. 응답은 감싸서 감시하다가, 응답이 나가는 도중 이 사용자에게 차단 신호가 오면 끊습니다—
추가 인증/contexa/zero-trust/challenge-required?mfaUrl=…로 이동합니다401 MFA_CHALLENGE_REQUIRED를 받고, 본문의 mfaUrl에 추가 인증 주소가 들어 있습니다. CONTEXA는 MFA를 사용자마다 한 번만 시작하려고 잠금(기본 30초 동안 유지)을 잡습니다. 다른 요청이 시작하는 중이면 503 MFA_BUSY_RETRY와 Retry-After: 3을 받습니다. 앱에 MFA 흐름이 없으면 401 ZERO_TRUST_CHALLENGE를 받습니다. HOST_OWNED에서는 CONTEXA가 MFA를 시작하지 않고, mfaUrl이 /contexa/step-up입니다이 판정이 내려진 뒤에 통과한 MFA로 풀립니다. 판정이 내려지기 전에 로그인하며 거친 MFA로는 풀리지 않습니다. MFA를 통과한 세션만 허용으로 바뀌고, 같은 사용자의 다른 세션은 각자 통과할 때까지 추가 인증이 남습니다. HOST_OWNED에서는 추가 인증 화면을 통과하거나, 판정 뒤에 앱이 사용자를 자체 재인증하면 풀립니다. 아무것도 하지 않으면 1,800초 뒤에 만료됩니다
차단/contexa/zero-trust/blocked로 이동합니다403 ACCOUNT_BLOCKED를 받습니다. 사용자가 차단 해제 MFA를 시작한 뒤에는 401 BLOCK_MFA_REQUIRED를 받습니다관리자가 승인해야 풀립니다(차단의 전파와 해제)
검토 보류/contexa/zero-trust/analysis-pending?returnUrl=…로 이동합니다423 SECURITY_REVIEW_IN_PROGRESS와 Retry-After: 30을 받습니다관리자가 승인해야 풀리고, MFA로는 풀리지 않습니다. 분석 판정(300초)과 첫 대기 응답부터 5분이 모두 지나면 그다음 요청에서 차단으로 올라갑니다
분석 대기요청이 통과합니다. 응답은 감싸서 감시하다가, 응답이 나가는 도중 차단 신호가 오면 끊습니다판정이 저장되면 바뀝니다
  • 차단 응답은 로그인 세션을 끝내지 않습니다. CONTEXA는 진행 중인 응답을 끊고, 이후 요청마다 차단 응답을 돌려줍니다.
  • 판정 때문에 멈춘 요청은 AI 모델이 분석하지 않고, 그 세션에서 일어난 사실로만 기록합니다.
  • 필터의 위치, 제외 경로, 응답 본문 전체는 요청 시점 적용에 있습니다.

메서드 단계: 보호 메서드(@Protectable)

필터가 HTTP 요청마다 저장된 판정을 적용한다면, 보호 메서드 앞의 가로채기(AuthorizationManagerMethodInterceptor)는 메서드를 호출할 때마다 한 번 더 적용합니다. 보호 메서드는 분석 사건을 내는 곳이기도 합니다. 이 가로채기는 두 소유 방식 모두에서 돌며, Spring의 메서드 보안(@PreAuthorize 등)보다 먼저 실행됩니다.

보호 메서드는 두 가지로 나뉩니다. 일반 메서드는 판정을 기다리지 않고 실행한 뒤 분석합니다. 즉시 판정 메서드(@Protectable(sync=true))는 그 호출 안에서 바로 판정을 받고, 결과가 허용일 때만 실행합니다.

  • 관찰 모드(SHADOW)에서는 6단계의 저장된 판정과 즉시 판정을 기록만 하고 거부하지 않습니다.
  • 앱이 자원 인증 관문(ProtectableResourceCertificationGate) 빈을 등록하면, @Protectable(verificationRequired)(기본 true)인 메서드가 인증되지 않은 자원을 다룰 때 423으로 거부합니다. OSS에는 이 빈의 구현이 없습니다.
  • 저장된 판정이 없는 AI 에이전트 요청을 그 자리에서 판정할지는 contexa.security.zerotrust.protectable.unrecorded-agent-request로 정합니다. 기본은 DECIDE_IN_PLACE이고, PROCEED이면 사람처럼 통과시킵니다.

메서드 단계에서 거부하면 아래 HTTP 응답을 돌려줍니다. 본문에는 status · code(ZERO_TRUST_<판정>) · message · action · resourceId · riskScore · analysisTimeout · timestamp가 들어 있습니다. 차단 · 시작된 추가 인증 · 검토 보류일 때 브라우저의 화면 요청(Accept에 text/html)은 JSON 대신 요청 시점 ②와 같은 안내 화면으로 이동합니다.

403차단입니다.
401추가 인증입니다. 그 자리에서 추가 인증 MFA를 시작하고 본문에 mfaUrl을 넣습니다(HOST_OWNED에서는 추가 인증 주소 /contexa/step-up). AI 에이전트의 추가 인증은 사람의 MFA 대신 책임자 확인 요청으로 답합니다(책임자 확인).

분석 경로: 판정이 만들어지는 과정

분석 사건이 나간 뒤의 일입니다. 요청을 처리하던 스레드는 이 과정을 기다리지 않습니다. 분석은 응답과 따로 뒤에서 진행되고, 결과는 다음 요청에서 쓰입니다.

  • 거르기: 이 사용자(AI 에이전트는 자기 키)와 맥락의 판정이 분석 대기가 아니면 새로 분석하지 않습니다. 그 요청은 "분석하지 않은 요청"으로만 기록합니다. contexa.security.zerotrust.enabled=false이면 사건을 받아도 아무것도 하지 않습니다.
  • 전달: 단독 모드에서는 같은 서버 안에서 사건을 넘기고, 분산 모드에서는 Kafka로 넘깁니다.
  • 줄 세우기: 사건을 크기 10,000의 대기열에 넣고 8건씩 꺼냅니다. 꺼낸 사건은 사용자 · 세션마다 한 줄로 세워 한 번에 하나씩 처리합니다. 사건 하나를 분석하는 데 주는 시간은 180초입니다. 일시적으로 실패하면 최대 3번 다시 줄을 섭니다.
  • 판정: 1차 분석이 먼저 판정합니다. 1차가 검토 보류(ESCALATE)를 고르면 2차 분석이 다시 판정합니다. 한 사건의 1차 · 2차 분석은 같은 프롬프트 버전을 씁니다.
  • 처리 단계: 판정이 나오면 판정 만들기(50) → 적용(55) → 증거 봉인(56) → 감사(60) → SaaS 전달(65, 켰을 때만) 순서로 돕니다. 괄호의 숫자는 실행 순서입니다. 적용 단계는 판정을 저장하고, 차단이면 진행 중인 응답을 끊는 신호를 보냅니다. 증거 봉인은 모델에 보낸 그대로의 프롬프트와 판정을 봉인해 두고, 감사는 감사 기록에 판정을 남깁니다.

어떤 요청이 분석되는지, 모델의 답이 바뀌는 경우, 분석 단계마다 다른 모델 쓰기는 판정 엔진에 있습니다.

차단의 전파와 해제

차단은 가장 강한 판정입니다. 차단이 저장되면 진행 중인 응답과 다음 요청이 어떻게 막히는지, 그리고 차단이 어떻게 풀리는지를 설명합니다.

차단이 퍼지는 길

신호를 놓친 서버도 0.5초마다 저장소를 확인합니다. CONTEXA 자신의 거부 응답은 끊지 않습니다.

차단을 푸는 길

  • 차단 기록의 상태는 BLOCKED · UNBLOCK_REQUESTED · RESOLVED · TIMEOUT_RESPONDED · MFA_FAILED 다섯 가지입니다.
  • 차단 해제 MFA는 시도 한도(contexa.security.zerotrust.max-block-mfa-attempts, 기본 2)를 넘으면 더 시작할 수 없습니다. 실패 횟수는 24시간 동안 셉니다.
  • 앱이 로그인을 맡을 때(HOST_OWNED)는 CONTEXA의 MFA 흐름을 시작하지 않습니다. 해제 MFA는 확인 전용 추가 인증 화면(/contexa/step-up?purpose=block)에서 거칩니다(HOST_OWNED의 추가 인증).
  • 위임받아 일하는 AI 에이전트의 차단은 MFA로 풀 수 없고, 그 요청은 403 AGENT_BLOCKED를 받습니다.
  • 검토 보류가 풀리지 않고 차단으로 올라갈 때도 같은 일이 일어납니다. 차단을 저장하고, 차단 깃발을 세우고, 사람이면 차단 기록을 남기고, 에이전트면 에이전트를 정지시킵니다.

에이전트 요청은 어떻게 다른가

AI 에이전트가 사용자를 대신해 보내는 요청은 사람의 요청과 판정을 따로 저장하고, 사람용 MFA 대신 책임자 확인으로 답합니다. 아래 표는 사람의 요청과 달라지는 점입니다.

항목에이전트 요청에서동작하는 소유 방식
판정 키(판정을 저장하는 이름)위임받은 에이전트의 판정은 <사용자>::agent::<에이전트>에 따로 저장합니다. 위임한 사용자가 차단이면 에이전트도 차단으로 봅니다둘 다
저장된 판정이 없을 때통과시키지 않고 그 자리에서 판정합니다(기본)둘 다(@Protectable)
차단 응답403 AGENT_BLOCKED를 받고, MFA로 풀 수 없습니다둘 다(필터)
에이전트 관문(에이전트 요청에만 거는 검사)호출 상한 · 끝난 위임 · 책임자 확인 · 좁혀진 범위를 검사합니다둘 다

자세한 내용은 에이전트를 보안 주체로와 정지 · 확인 · 제한에 있습니다.

운영 모드와 운영

운영 모드는 CONTEXA가 요청을 분석하는지, 판정을 저장하고 적용하는지를 정합니다. 처음 도입할 때는 판정을 요청에 적용하지 않고 기록하는 관찰 모드(SHADOW)로 시작할 수 있습니다.

운영 모드AI 분석판정 저장 · 적용관찰 · 감사 기록학습
끔(DISABLED, 옛 이름 OBSERVE 포함)안 함없음없음없음
관찰 모드(SHADOW)함적용하지 않음. 판정은 관찰 모드 전용 기억에만 남습니다. 보호 메서드의 저장된 판정도 기록만 합니다남김허용 판정만
적용 모드(ENFORCE, 기본)함저장하고 다음 요청부터 적용합니다남김실제로 적용된 허용만
  • 요청 시점 필터는 운영 모드를 따릅니다. 운영 모드를 SHADOW로 바꾸거나 contexa.security.zerotrust.enabled=false로 끄면, 두 소유 방식 모두 아무것도 막지 않습니다. 이미 저장된 차단(기한 없음) · 추가 인증 · 검토 보류는 저장소에 남아 있다가 ENFORCE로 돌아오면 다시 적용됩니다.
  • 분석 사건은 낼 때의 운영 모드를 가지고 다닙니다. SHADOW일 때 낸 사건의 판정은 그사이 ENFORCE로 바꿔도 저장 · 적용하지 않습니다.
  • 판정 결과는 관찰 기록과 감사 기록에 남습니다. 관찰 기록 표는 ctxa_ai_security_decision_observation입니다. 관리 콘솔 "보안 이벤트 기록"(/contexa/admin/security-monitor)과 Zero Trust 콘솔의 판정 기록(/contexa/admin/zero-trust/decisions)에서 판정 기록을 봅니다.

앱 코드에서 판정 읽기

앱 코드에서 현재 사용자의 판정을 알아야 할 때 쓰는 방법입니다.

  • 요청 속성 contexa.zeroTrustAction: 판정을 적용한 요청에는 그 판정이 이 이름으로 남습니다(CONTEXA_OWNED).
  • 로그인 객체 ZeroTrustAuthenticationToken: getAction() · getTrustScore() · getThreatScore()를 씁니다. 세션 체인에서 권한이 바뀌었을 때만 이 객체가 되고, 토큰 체인에서는 JwtAuthenticationToken이 그대로 남습니다.
  • 정책 식 #ai: CONTEXA 정책(XACML) 식에서 씁니다. 앱의 @PreAuthorize에서는 쓸 수 없습니다.
  • 판정 값의 분류: ZeroTrustAction의 isBlocking()은 차단 · 검토 보류일 때 참이고, isAccessRestricted()는 차단 · 추가 인증 · 검토 보류일 때 참입니다.
식참이 되는 때
#ai.isAllowed()현재 판정이 허용
#ai.isBlocked()현재 판정이 차단
#ai.needsChallenge()현재 판정이 추가 인증
#ai.needsEscalation()현재 판정이 검토 보류
#ai.isPendingAnalysis()현재 판정이 분석 대기
#ai.hasAction('ALLOW')현재 판정이 적은 것과 같음
#ai.hasActionIn('ALLOW', 'PENDING_ANALYSIS')현재 판정이 적은 것 가운데 하나
저장된 판정이 없으면 분석 대기입니다. 허용은 판정이 만들어진 세션 · IP · 브라우저에서 15분 동안만 쓰입니다. 그래서 사용자의 첫 요청, 15분이 지난 뒤의 요청, 다른 환경에서 온 요청은 모두 분석 대기로 읽힙니다. #ai.isAllowed()만 요구하면 이런 요청이 거부됩니다. 차단 · 추가 인증 · 검토 보류만 걸러 내려면 아래처럼 허용과 분석 대기를 함께 받습니다. 
// #ai는 앱의 @PreAuthorize에서 쓸 수 없습니다. @Protectable 메서드에 거는 Contexa 메서드 정책의 조건으로 씁니다.
// 정책 조건(정책 센터에서 입력): #ai.hasActionIn('ALLOW', 'PENDING_ANALYSIS') and hasRole('ADMIN')
import io.contexa.contexacommon.annotation.Protectable;
import org.springframework.stereotype.Service;

@Service
public class ReportService {

    @Protectable
    public String reports() {
        return "ok";
    }
}

에이전트용 식(isAgent() 등)은 정지 · 확인 · 제한, 정책 식 전체는 AI 보안 표현식에 있습니다.

학습과 실시간 알림

판정이 학습에 쓰이는 방식과, 사용자가 자신의 판정을 실시간으로 받는 방법입니다.

  • 학습: 행위 기준선(사용자별로 학습한 일하는 시간 · 단말 · 네트워크 같은 행동 패턴)은 허용 판정에서만 배웁니다. 적용 모드에서는 실제로 적용된 허용 판정을, 관찰 모드에서는 관찰 모드 전용 기억에 남은 허용 판정을 배웁니다. 학습 서비스(SecurityLearningService)가 기준선 학습(BaselineLearningService, 지수 이동 평균)으로 넘깁니다. 자주 쓰는 IP 대역은 일정 개수만 남기고, 넘치면 덜 쓰인 것부터 밀어냅니다. 자세한 조건은 판정 엔진의 "무엇을 배우나"에 있습니다.
  • 실시간 알림(SSE): GET /contexa/admin/api/aiam/sse/zero-trust/subscribe를 구독하면 로그인한 사용자 자신의 판정 · 분석 진행 · 오류 알림을 받습니다(ZeroTrustSsePublisher). 관리자에게 모든 판정을 보내는 통로가 아닙니다.
  • 안내 화면: /contexa/zero-trust/blocked · /contexa/zero-trust/challenge-required · /contexa/zero-trust/analysis-pending는 판정을 받은 사용자가 보는 화면입니다.
