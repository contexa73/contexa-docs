프롬프트 거버넌스와 검수

판정 프롬프트 묶음을 안전하게 바꾸고, 바꾼 결과를 확인하는 방법을 설명합니다. 묶음이 무엇으로 식별되는지, 요청마다 어느 묶음이 도는지, 새 묶음을 섀도 · 카나리 · 활성으로 내보내고 되돌리는 법, 봉인된 프롬프트를 검수하고 다른 묶음으로 재생하는 법을 다룹니다.

한눈에 보기

판정 프롬프트는 버전이 붙은 묶음으로 돕니다(묶음 세 개의 내용 차이는 판정 프롬프트와 묶음). 묶음을 바꾸는 원칙은 먼저 관찰하고, 확인한 뒤 집행으로 올리는 것입니다. 새 묶음은 표본 요청에서 판정과 떨어져 돌려 보고(섀도), 일부 범위에만 적용한 뒤(카나리), 기본으로 올립니다(활성). 봉인된 판정을 다른 묶음으로 다시 물어 볼 수도 있습니다(재생).

묶음이란 무엇인가

묶음은 거버넌스 기술자(프롬프트 키 · 템플릿 키 · 버전 · 출력 계약 버전 · 릴리스 상태 · 롤백 버전 등)와 그 코드가 그리는 사용자 글의 모양을 묶은 것입니다. 프롬프트 버전이 곧 묶음 버전이고, 클래스패스의 매니페스트 prompt-bundles/manifests/<프롬프트 키>/<버전>.json을 가리킵니다.

  • 실행할 수 있는 묶음은 세 개입니다. 판정 프롬프트(cortex.security-decision)의 매니페스트는 71개(v19 계열 22 · v20 29 · v21 20)지만, 이 빌드가 돌리는 것은 2026.10.24-v19.21 · 2026.10.24-v20.26 · 2026.10.30-v21.19뿐이고 나머지는 지난 묶음의 기록입니다. IAM 모듈의 프롬프트 세 종(ConditionTemplate · PolicyGeneration · PolicyGenerationStreaming)의 매니페스트도 같은 목록에 실립니다.
  • 요소 11개가 묶음을 이룹니다. 상태가 PRESENT면 내용을, ABSENT · UNVERSIONED · INCLUDED면 고정 표지를 해시해 상태 자체도 식별의 일부가 되고, 묶음 해시가 모든 요소를 덮습니다.
  • 읽을 때 검증합니다. 묶음 해시가 요소와 맞지 않거나, 같은 이름에 해시가 다른 매니페스트가 둘이면 바로 실패합니다.
  • 매니페스트 칸: 요소, 골든 입력, 부모 버전, 변경 요약, 문제 ID, 작성자, 고정일, 어휘 버전과 호환 어휘 버전, 롤백 대상, 선언한 모델 프로파일, 평가 시나리오 묶음.

요청마다 묶음이 정해지는 법

요청마다 도는 묶음은 선택기 하나가 고르고, 선택기는 contexa.security.tiered.prompt-bundle.selector로 정합니다. 사건의 첫 프롬프트가 묶음을 사건에 적어 두고, 같은 사건의 2차 분석 프롬프트는 같은 묶음을 씁니다. 프롬프트 실행 정보에 어떤 출처로 골랐는지가 남습니다.

선택 출처언제
BUILD_DEFAULT아무것도 고르지 않았거나, 선택기가 실패했거나, 고른 버전을 이 빌드가 돌리지 않을 때(버전마다 오류 로그 한 번)
CONFIGURATION선택기 CONFIGURATION(기본): contexa.security.tiered.prompt-bundle.active의 버전을 모든 요청에
REGISTRY선택기 registry: 요청 범위의 최신 ACTIVE 릴리스, 범위에 없으면 PLATFORM_GLOBAL의 것
CANARY선택기 registry: 카나리 비율 · 대상 안에 드는 요청에 범위의 CANARY 릴리스
SHADOW범위의 SHADOW 릴리스. 판정과 떨어진 표본 복사본에서만(섀도 실행)
REPLAY봉인된 판정을 고른 묶음으로 다시 물을 때(재생)

레지스트리 선택기는 범위의 릴리스를 최대 60초 캐시하고 5초마다 무효화를 확인합니다. 상태 전환과 롤백이 무효화를 알립니다. 레지스트리를 읽지 못하는 동안에는 빌드 기본 묶음이 돕니다.

새 묶음을 내보내는 순서

상태 여섯 가지

레지스트리의 상태 어휘는 하나(PromptBundleState)입니다. 예전에 저장된 이름도 같은 뜻으로 읽고, 전환 API도 두 이름을 모두 받습니다. 실제로 집행되는 상태는 ACTIVE와 CANARY뿐입니다.

상태뜻예전 이름

SHADOW표본 요청에서 돌리고 기록만EVAL_ONLY · SHADOW_READY · REPLAY_READY
CANARY범위 안에서 집행ACTIVE_FOR_SCOPE · CANARY_READY
ACTIVE기본으로 집행PRODUCTION · PROMOTED · RELEASED · CURRENT · RUNTIME_APPROVED · PRODUCTION_APPROVED
DEPRECATED더는 고를 수 없음. 롤백 대상이자 기록ROLLED_BACK · WITHDRAWN · KILL_SWITCH_ACTIVE
RETIRED빌드에서 빠짐. 기록만—

목표막는 사유
SHADOWCHANGE_LEDGER_MISSING(변경 기록 없음)
CANARYEVALUATION_NOT_FOR_BUNDLE_HASH, CHANGE_LEDGER_MISSING, MODEL_COMPATIBILITY_MISSING, BUDGET_PROFILE_MISSING, ROLLBACK_TARGET_MISSING
ACTIVECANARY의 사유에 더해 PROMPT_INJECTION_GATE_FAILED, NON_FUNCTIONAL_GATE_FAILED(지연 · 비용), EMPIRICAL_EVAL_MISSING, TEVV_GATE_NOT_READY, TOKEN_COUNTING_POLICY_MISSING, CACHE_POLICY_MISSING, COMPACTION_POLICY_MISSING
DEPRECATEDNO_OTHER_ACTIVE_RELEASE(같은 범위 · 키 · 템플릿에 다른 ACTIVE가 없음)
  • EVALUATION_NOT_FOR_BUNDLE_HASH는 기록된 평가가 이 묶음의 해시로 한 것이 아니라는 뜻입니다. 묶음의 증거는 그 묶음으로 한 평가뿐입니다.
  • TEVV_GATE_NOT_READY: 평가가 매니페스트의 평가 시나리오 묶음(evaluationScenarioFamilies, 없으면 PROMPT_INJECTION · TOOL_MISUSE · MEMORY_POISONING)을 덮어야 합니다. v20.26 · v21.19는 PROMPT_INJECTION · MEMORY_POISONING을 선언합니다.
  • 막힌 전환은 아무것도 바꾸지 않고 사유와 함께 기록됩니다. 적용된 전환은 레지스트리 상태와 승인 · 롤백 기록을 바꾸고 런타임 캐시에 무효화를 알립니다.
  • ACTIVE로 옮기면 같은 범위 · 키 · 템플릿의 다른 ACTIVE가 DEPRECATED가 되어, 활성 릴리스는 하나만 남습니다.

Content-Type: application/json

{
  "registryScope": "PLATFORM_GLOBAL",
  "promptKey": "cortex.security-decision",
  "promptVersion": "2026.10.30-v21.19",
  "targetReleaseStatus": "SHADOW",
  "rationale": "Open the shadow run of the candidate bundle"
}

응답은 전환 영수증입니다. 적용되면 200, 막히면 사유와 함께 422, 어느 어휘에도 없는 상태 이름이면 400입니다. registryScope를 비우면 PLATFORM_GLOBAL입니다.

기동할 때 등록

애플리케이션이 시작할 때 빌드의 묶음 세 개를 PLATFORM_GLOBAL 범위에 등록합니다. 새 행은 기술자 상태로 시작합니다: v19.21은 ACTIVE(단, 이 빌드가 돌리는 다른 묶음의 ACTIVE가 이미 있으면 AVAILABLE), v20.26 · v21.19는 AVAILABLE입니다. 이미 있는 행은 운영 칸(상태 등)을 바꾸지 않습니다. 이 빌드가 더는 돌리지 않는 묶음의 ACTIVE 행은 새 빌드 기본값을 막지 않습니다.

섀도 실행과 카나리

  • 섀도 실행은 후보 묶음을 실제 요청에 돌려 보되 아무것도 정하지 않습니다. 판정 묶음을 어느 선택기가 고르든 레지스트리의 SHADOW 릴리스를 읽으므로, 설정 선택기를 쓰는 앱도 후보를 시험할 수 있습니다.
  • 사건 ID 해시가 contexa.security.tiered.prompt-bundle.shadow.sample-percent(0~100, 기본 0 = 실행 안 함)보다 작은 요청이 표본입니다. 섀도 실행기는 이 설정을 적었을 때만 만들어집니다.
  • UTC 하루에 shadow.daily-call-cap(기본 100)번까지, 한 번에 모델 호출 하나입니다. 판정 전에 사건을 복사해 두고 판정 뒤 별도 스레드에서 분석해 SHADOW 단계로 봉인합니다. 집행 · 학습되지 않습니다. 이 빌드가 돌리지 않는 버전의 SHADOW 릴리스는 건너뜁니다.
  • 카나리는 registry 선택기에서만 돕니다. 레지스트리 행의 canary_percent(0~100, 없으면 범위 전체)를 요청자(사용자, 없으면 세션, 없으면 사건)의 해시에 적용하고, canary_tenants · canary_resource_families로 테넌트 · 자원 계열을 좁힙니다. 나머지 요청은 최신 ACTIVE를 씁니다.
  • OSS에는 카나리 비율 · 대상을 저장하는 API · 화면이 없습니다. 이 세 열은 DB의 레지스트리 표에 직접 넣어야 합니다.

되돌리기와 긴급 중지

롤백은 범위에서 돌고 있는 묶음을 그 매니페스트가 선언한 롤백 대상으로 바로 바꿉니다. 원래 묶음은 DEPRECATED, 대상은 ACTIVE가 되고(같은 범위의 다른 ACTIVE도 DEPRECATED), 런타임 캐시에 알린 뒤 확인한 조건과 함께 실행을 기록합니다. 거부된 롤백은 사유와 함께 기록되고 아무것도 바꾸지 않습니다.

거부 사유조건
SOURCE_NOT_EXECUTING원래 버전이 범위에서 ACTIVE나 CANARY가 아님
TARGET_NOT_IN_BUILD대상 매니페스트가 이 빌드에 없음
TARGET_NOT_DECLARED원래 매니페스트의 rollbackTargets에 대상이 없음
VOCABULARY_INCOMPATIBLE대상 매니페스트가 지금 어휘 버전을 읽지 못함
TARGET_NOT_REGISTERED대상이 범위에 레지스트리 행이 없음
POLICY_SET_MISSING대상의 정책 세트가 없음(정책 세트 조회기가 없으면 NOT_APPLICABLE로 기록)
 
POST /contexa/admin/api/prompt-quality/releases/rollback
Content-Type: application/json

{
  "registryScope": "PLATFORM_GLOBAL",
  "promptKey": "cortex.security-decision",
  "fromVersion": "2026.10.24-v20.26",
  "toVersion": "2026.10.24-v19.21",
  "reason": "Decision quality dropped after the release",
  "emergency": false
}

결과에는 실행 키(RBX-…), 상태, 확인한 조건이 담깁니다. 상태는 EXECUTED이거나 HTTP 422와 함께 REFUSED입니다. 긴급 중지("emergency": true)도 같은 방식으로 실행되고 AWAITING_APPROVAL로 끝나며, 다른 관리자가 POST /contexa/admin/api/prompt-quality/releases/rollback/{executionKey}/approve로 승인합니다. 실행한 관리자는 승인할 수 없습니다.

롤백 대상이 실제로 돌 수 있는지 확인하세요. TARGET_NOT_IN_BUILD는 매니페스트 71개를 기준으로 보므로, 이 빌드가 돌리지 않는 버전도 롤백 대상으로 통과합니다. 그런 버전이 ACTIVE가 되면 요청에는 빌드 기본 묶음(v19.21)이 돕니다. 예를 들어 v21.19 매니페스트의 롤백 대상은 2026.10.29-v21.18 · 2026.10.27-v21.17이고, 둘 다 이 빌드가 돌리지 않는 버전입니다.

봉인된 프롬프트 검수

검수기(PromptInspector)는 봉인 증거에서 모델이 받은 사용자 글을 읽고, 검사마다 일치 · 불일치 · 확인 불가를 셉니다. 사람이 검토할 문제를 가리킬 뿐 프롬프트 · 판정 · 규칙은 바꾸지 않고, 판정 스레드에서 돌지 않습니다. OSS 검사는 늘 10종입니다.

검사대상대조하는 것
SEAL_INTEGRITY모든 묶음묶음 해시가 봉인 칸을 모두 덮는지, 시스템 · 사용자 글이 수집되어 해시와 맞는지, 그린 프롬프트와의 차이가 기록되었는지, 요청 · 상관 ID가 있는지. 서명된 증거 묶음(판 3)은 서명까지
BUNDLE_TRACE모든 묶음봉인된 기술자가 레지스트리 릴리스를 가리키고, 계약 버전 · 해시 · 승인이 그 릴리스의 것인지. 레지스트리가 없으면 모두 확인 불가
DICTIONARY_CONTRACT사전 프롬프트줄바꿈, 사전 순서의 블록 머리, 블록에 속한 항목만 순서대로, 값 형식 · 결측 문구, 번호 줄 상한, 사실 ID 순서
DECISION_FACT_MATCH사전 프롬프트봉인된 판정 사실마다 줄이 있고 값이 같고 같은 사실 ID가 붙었는지
FACT_ACCURACY사전 프롬프트그린 사실을 봉인된 표준 맥락과 칸 단위로 대조(다시 그리지 않음). 원천이 봉인되지 않은 줄은 확인 불가
UNKNOWN_DECLARED사전 프롬프트확정하지 못한 사실이 종류와 함께 UNKNOWN에 있고 다른 곳에 값으로 그려지지 않았는지, 결측 표기대로 그렸는지
PAST_RECORD_NOTATION사전 프롬프트PAST RECORDS 상태 줄의 개수, 기록 줄마다 12칸, 같은 대상 먼저 · 최신 먼저 순서
SOURCE_TRUTH사전 프롬프트사실을 출처 기록과 대조. 원천 검증기(PromptFactSourceVerifier)가 요청 시각 기준으로 기록을 다시 읽음. 기본 검증기는 Contexa의 업무 기록과 위임(당직 · 배정 · 승인 · 위임의 에이전트 · 사람 · 목적 · 작성자)을 읽고, 앱이 이 빈을 선언하면 대신 씀
SAME_FACT사전 프롬프트한 사실을 두 줄이 말할 때 값이 하나인지
REASON_MATCH사전 프롬프트봉인된 판정의 근거 코드가 프롬프트 줄 ID를 인용하고, 그 줄이 코드가 인용할 수 있는 줄이며, 조건이 봉인된 맥락에서 성립하는지
  • 사전 프롬프트는 v20 묶음(v20-dictionary-blocks)과 v21 묶음(v21-dictionary-blocks)입니다. v21 묶음에는 각 검사의 v21판이 돕니다. 다른 빌드의 사전 · 렌더로 그린 묶음은 사전 검사에서 확인 불가로 셉니다.
  • 판정: PASS(모두 일치), FAIL(불일치 하나 이상), INCOMPLETE(불일치 없이 확인 불가가 있음), NOT_APPLICABLE(사전 프롬프트가 아니어서 모든 묶음용 검사만 돔, v19), ERROR(검수할 수 없음). 발견은 MISMATCH · UNVERIFIABLE이고, 확인 불가는 통과로 세지 않습니다.
  • 버전: 결과마다 검수기 버전(prompt-inspector/N)과 사전 버전(v20@ 또는 v21@과 사전 다이제스트 앞부분)을 남깁니다. 검수기 버전이 바뀌면 다시 검수합니다.
  • 실행: 30초마다 아직 검수하지 않은 가장 오래된 묶음을 50개씩, 모든 서버를 통틀어 잠금 하나로 검수합니다. 묶음 ID 해시로 contexa.prompt-inspection.sample-percent(기본 100)만큼 고릅니다.
  • 검수 결과가 바꾸는 것은 하나입니다. 마지막 검수가 PASS 또는 NOT_APPLICABLE이고 공식 검증에 쓰이지 않은 증거 묶음은 30일 뒤 지워집니다.
  • 검수기는 contexa.enterprise.enabled가 true가 아니고 contexa.prompt-inspection.enabled가 true(기본)일 때만 만들어집니다.

봉인 표본과 보관

검수의 입력은 봉인 증거입니다. AI 모델이 판정한 경우만 봉인하고, 시작 직후와 묶음이 바뀐 직후의 판정 1,000건은 모두, 그 뒤에는 1%를 봉인해 90일 보관합니다(서버마다 셈). 무엇을 봉인하는지, 서명 키, 보관과 설정은 봉인 증거와 공식 검증에 있습니다.

봉인 판정 재생

재생은 봉인된 판정의 입력으로 프롬프트를 고른 묶음으로 다시 그려, AI 모델에 한 번 다시 물어 봅니다. 새 묶음을 섀도 · 카나리로 올리기 전에 같은 사건에서 판정이 어떻게 달라지는지 볼 때 씁니다. 결과는 적용 · 학습 · 봉인하지 않고, 모델을 실제로 부르므로 비용이 들며 감사 기록(SEALED_DECISION_REPLAYED)이 남습니다.

  • 이 빌드가 돌리는 묶음만 고를 수 있습니다: 2026.10.24-v19.21 · 2026.10.24-v20.26 · 2026.10.30-v21.19. 다른 버전은 400으로 거부합니다. 목록은 GET /contexa/admin/api/sealed-decisions/replay-bundles입니다.
  • 답이 ESCALATE면 고른 2차 분석 모델(최대 3개)마다 다시 묻습니다. 기준선을 넣지 않으면 지금 저장된 사람 · 조직 기준선을 쓰고, 답에 baselines(GIVEN 또는 CURRENT)로 밝힙니다.
POST /contexa/admin/api/sealed-decisions/7f3c2a/replay
Content-Type: application/json

{"bundleVersion": "2026.10.30-v21.19", "secondPassModels": ["gpt-4o"]}

경로의 7f3c2a는 봉인된 판정의 요청(상관) ID입니다. 시간 한도 · 오류 응답 같은 세부와 화면에서 재생하는 법은 봉인 증거와 공식 검증의 재생에 있습니다.
