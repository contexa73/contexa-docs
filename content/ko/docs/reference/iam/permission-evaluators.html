권한 평가기: hasPermission

메서드 정책 조건의 hasPermission(...)이 무엇을 보고 참 · 거짓을 내는지 설명합니다. 권한을 만들어 역할에 붙이는 법, 내장 도메인 5개, 동작 이름의 동의어, 새 도메인 평가기를 만드는 법을 다룹니다.

hasPermission이 실제로 보는 것

hasPermission(...)은 Spring Security의 객체 권한 식입니다. Contexa의 CompositePermissionEvaluator(Spring PermissionEvaluator)가 도메인별 평가기 하나를 골라 맡깁니다. 내장 평가기는 대상 객체나 ID를 보지 않고, 로그인 사용자가 가진 권한 이름에 도메인 단어와 동작 단어가 함께 들어 있는지만 봅니다.

  1. 사용자의 권한 가운데 Contexa 권한 레코드에서 온 PermissionAuthority만 봅니다. 역할(ROLE_...) 같은 다른 권한은 보지 않습니다.
  2. 그 권한의 대상 유형이 METHOD여야 합니다.
  3. 권한 이름(대문자)에 도메인 단어(예: USER)와 동작의 동의어 가운데 하나(아래)가 부분 문자열로 들어 있으면 참입니다.
  4. 대상 객체 · ID는 판정에 쓰지 않습니다. 객체 단위 확인은 @Protectable(ownerField)의 소유자 확인뿐입니다(소유자 확인과 함께).
사용자가 가진 권한식결과
METHOD_USERSERVICE_GETUSER(대상 유형 METHOD)hasPermission(#id, 'USER', 'READ')참: USER와 GET(READ의 동의어)이 들어 있음
METHOD_REPORTSERVICE_EXPORTREPORT(METHOD)같음거짓: USER가 없음
USER_READ(대상 유형 URL)같음거짓: 대상 유형이 METHOD가 아님
HOST_OWNED에서는 보통 거짓이 됩니다. PermissionAuthority는 Contexa가 로그인을 맡을 때(CONTEXA_OWNED) Contexa 사용자 저장소가 로그인 정보에 담습니다. 앱이 로그인을 맡는 기본 HOST_OWNED에서는 앱의 로그인 정보에 이 권한이 없어 내장 평가기가 거짓을 냅니다. 앱의 권한으로 판단하려면 사용자 정의 평가기에서 판단 규칙을 바꿉니다.

준비: 권한 만들고 역할에 붙이기

  1. 관리 화면 IAM > 권한 관리(/contexa/admin/permissions)에서 권한을 만듭니다. 칸은 이름 · 설명 · 대상 유형(URL · METHOD) · 동작 유형(READ · WRITE · EXECUTE · DELETE · ALL)입니다.
  2. 평가기는 동작 유형 칸이 아니라 이름을 봅니다. 이름에 도메인과 동작 단어를 넣고(관례 도메인_동작, 예: USER_READ), 대상 유형은 METHOD로 합니다.
  3. 정책 센터에서 자원으로 만든 권한은 이름이 자동으로 정해집니다. METHOD 자원은 METHOD_{클래스}_{메서드}, URL 자원은 URL_{주소}(영문 · 숫자 밖의 글자는 _)이고 모두 대문자입니다. 자동 이름도 부분 문자열 규칙으로 맞을 수 있습니다. 예: METHOD_ORDERSERVICE_UPDATEORDER는 ORDER와 UPDATE에 맞습니다.
  4. IAM > 역할 관리(/contexa/admin/roles)에서 역할에 권한을 붙이고, 사용자나 그룹에 역할을 줍니다. 로그인하면 역할의 권한이 PermissionAuthority로 담깁니다. 그 값은 권한 이름의 대문자입니다.

쓰는 곳

쓰는 곳됨?
@Protectable 메서드 정책의 조건됨(두 인증 소유 방식 모두)
@PreAuthorize 등 Spring 메서드 보안앱의 메서드 보안에는 Contexa가 이 평가기를 쓰는 처리기를 등록하지 않음(CONTEXA_OWNED에서 Contexa 자신의 클래스의 @PreAuthorize에만 쓰임)
URL 정책의 조건안 됨. 적재할 때 지워집니다. hasPermission만 있던 ALLOW 정책은 늘 거부, DENY 정책은 늘 적용됩니다

역할 전체를 보는 검사는 hasRole(...)이고, 메서드마다 데이터베이스 정책으로 보호하는 것은 @Protectable입니다. hasPermission은 그 정책 조건 안에서 권한 이름을 따질 때 씁니다. 조건의 #이름은 메서드 매개변수 이름입니다. #targetId는 그 이름의 매개변수가 있을 때만 값이 있습니다. 메서드 정책은 조건을 and로 묶으므로 다른 조건과 함께 써도 됩니다.

내장 도메인과 예

도메인인자 3개의 대상 타입인자 2개의 권한 접두사저장소 빈(소유자 확인용)
USER'USER'USER_userRepository
ROLE'ROLE'ROLE_roleRepository
ROLE_HIERARCHY'ROLE_HIERARCHY'ROLE_HIERARCHY_roleHierarchyRepository
GROUP'GROUP'GROUP_groupRepository
PERMISSION'PERMISSION'PERMISSION_permissionRepository

대상 타입은 대소문자를 가리지 않습니다. 내장 평가기 다섯 개는 도메인 · 저장소 빈 이름만 다르고 판단 규칙은 같습니다.

hasPermission(#id, 'USER', 'READ')
hasPermission(#id, 'ROLE', 'EDIT')
hasPermission(#groupId, 'GROUP', 'DELETE')
hasPermission(null, 'USER_READ')
hasPermission(#userId, 'USER', 'UPDATE') and T(java.time.LocalTime).now().getHour() < 18
  • ORDER · DOCUMENT · REPORT · PAYMENT 같은 도메인은 평가기가 없습니다. 쓰려면 평가기를 만들어야 하고, 없으면 인자 3개 식은 예외로 끝납니다.
  • 시간 조건은 T(java.time.LocalTime) 등으로 씁니다. #time 같은 변수는 없습니다.

동작 이름과 동의어

동작같은 뜻으로 보는 단어
읽기GET · FIND · READ · FETCH · VIEW · RETRIEVE · LIST · SEARCH
만들기CREATE · SAVE · ADD · INSERT · REGISTER · POST
바꾸기UPDATE · EDIT · MODIFY · CHANGE · PATCH · PUT
지우기DELETE · REMOVE · DESTROY · DROP · ERASE · PURGE · CLEAR · TRUNCATE
  • 식에 쓴 동작이 어느 묶음에 있으면 그 묶음의 단어 가운데 하나가 권한 이름에 있으면 됩니다. 묶음에 없는 동작(예: EXPORT)은 그 단어 하나로만 찾습니다.
  • 인자 2개에서는 권한 문자열의 도메인 접두사를 떼고 남은 부분이 동작입니다. hasPermission(#user, 'USER_FETCH')는 FETCH → 읽기 묶음이므로, 이름에 USER와 GET · READ 등이 든 METHOD 권한이 있으면 참입니다.

평가기를 고르는 규칙

  • 평가기는 앱 시작 때 모아서 도메인 이름이 긴 것부터 봅니다. 그래서 ROLE_HIERARCHY_READ는 ROLE 평가기가 아니라 ROLE_HIERARCHY 평가기로 갑니다. 길이가 같은 USER와 ROLE은 접두사가 겹치지 않아 순서와 상관이 없습니다.
  • 로그인하지 않았으면 늘 거짓입니다.
  • DomainPermissionEvaluator는 평가기의 인터페이스이고, 위의 판단 규칙은 기본 클래스 AbstractDomainPermissionEvaluator에 있습니다.

소유자 확인과 함께

메서드 정책에서 hasPermission이 참이고 그 메서드에 @Protectable(ownerField = "...")가 있으면, 이어서 대상의 소유자를 확인합니다. 인자 2개는 넘긴 객체에서, 인자 3개는 고른 평가기가 저장소 빈의 findById로 읽은 엔티티에서 그 필드를 읽어 로그인 사용자 이름과 비교합니다. 규칙은 @Protectable > 소유자 확인에 있습니다.

사용자 정의 도메인 평가기

새 도메인(예: DOCUMENT)을 쓰려면 AbstractDomainPermissionEvaluator를 상속한 빈을 등록합니다. DomainPermissionEvaluator 인터페이스만 구현하면, 평가기를 모으는 쪽이 기본 클래스로 형변환하므로 앱이 시작할 때 ClassCastException으로 실패합니다.

import io.contexa.contexaiam.security.xacml.pdp.evaluation.method.AbstractDomainPermissionEvaluator;
import org.springframework.context.ApplicationContext;
import org.springframework.stereotype.Component;

@Component
public class DocumentPermissionEvaluator extends AbstractDomainPermissionEvaluator {

    private final ApplicationContext applicationContext;

    public DocumentPermissionEvaluator(ApplicationContext applicationContext) {
        this.applicationContext = applicationContext;
    }

    @Override
    protected String domain() {
        return "DOCUMENT";
    }

    @Override
    protected String repositoryBeanName() {
        return "documentRepository";
    }

    @Override
    protected ApplicationContext getApplicationContext() {
        return applicationContext;
    }
}
  • domain()은 대문자로 씁니다. 권한 문자열은 대문자로 바꿔 비교하지만 도메인 이름은 바꾸지 않습니다.
  • repositoryBeanName()은 인자 3개 소유자 확인 때 findById로 엔티티를 읽을 저장소 빈 이름입니다(Spring Data 저장소면 됨). 빈이 없으면 소유자 확인이 거부됩니다.
  • 빈으로 등록하면 자동 구성이 모든 평가기를 모아 길이순으로 정렬하므로 다른 설정은 필요 없습니다. CompositePermissionEvaluator 빈을 직접 두면 자동 구성의 것은 물러납니다.
  • 판단 규칙을 바꾸려면 checkPermission(Authentication, Object)(protected)을 재정의합니다. 예를 들어 HOST_OWNED에서 앱 자신의 권한으로 판단할 때입니다.
  • 이제 hasPermission(#docId, 'DOCUMENT', 'READ'), hasPermission(#document, 'DOCUMENT_UPDATE')를 쓸 수 있습니다.
