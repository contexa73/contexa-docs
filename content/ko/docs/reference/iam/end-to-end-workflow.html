동적 인가 전체 흐름

코드에 박아 둔 requestMatchers 규칙을 데이터베이스 정책으로 옮겨, 코드를 바꾸지 않고 URL과 메서드의 접근을 바꾸는 과정을 처음부터 끝까지 따라 합니다. 준비, 시나리오 네 가지, 정책이 없을 때의 결정, 확인과 되돌리기, 요청 한 건의 처리 순서를 다룹니다.

무엇을 얻나

보통의 Spring Security 앱은 접근 규칙을 Java 설정에 씁니다. 엔드포인트가 늘거나 역할이 바뀔 때마다 코드를 고치고, 빌드하고, 배포해야 합니다.

http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/api/admin/**").hasRole("ADMIN")
    .requestMatchers("/api/users/**").hasAuthority("READ_USERS")
    .requestMatchers("/api/reports/**").hasAnyRole("ADMIN", "ANALYST")
    .requestMatchers("/api/orders/**").hasAuthority("MANAGE_ORDERS")
    // ... 규칙이 수십 줄 더
    .anyRequest().authenticated()
);

Contexa에서는 공개 경로만 코드에 남기고, 나머지는 동적 인가 매니저 하나에 맡깁니다. 규칙은 관리 콘솔에서 정책으로 고치고 Contexa DB에 저장하며, 저장하는 즉시 다시 읽혀 다시 컴파일하지 않고 적용됩니다.

http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/css/**", "/js/**").permitAll()
    .anyRequest().access(customDynamicAuthorizationManager)
);

전체 흐름 한 장

준비하기

URL 정책은 요청이 CustomDynamicAuthorizationManager를 지날 때만 평가됩니다. 누가 이 매니저를 체인에 연결하는지는 구성에 따라 다릅니다. @Protectable 메서드 정책은 어느 구성에서나 메서드를 부를 때 평가됩니다.

구성URL 정책메서드 정책
HOST_OWNED(기본)앱의 체인이 .access(customDynamicAuthorizationManager)를 부를 때만 평가평가
@EnableAISecurity(mode = SecurityMode.FULL)Contexa 체인이 정적 파일을 뺀 모든 요청을 보냄평가
SANDBOX 모드에 CONTEXA_OWNED를 직접 준 경우평가되지 않음(이 체인은 /contexa/admin/**만 ADMIN으로 막고 나머지는 허용)평가

기본 HOST_OWNED에서는 앱의 보안 설정에 매니저를 연결합니다. 정적 matcher는 정적 파일 · 공개 API처럼 정말 공개여야 하는 곳에만 남깁니다.

import io.contexa.contexaiam.security.xacml.pep.CustomDynamicAuthorizationManager;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class AppSecurityConfig {

    @Bean
    SecurityFilterChain securityFilterChain(HttpSecurity http,
            CustomDynamicAuthorizationManager customDynamicAuthorizationManager) throws Exception {
        http.authorizeHttpRequests(auth -> auth
                        .requestMatchers("/css/**", "/js/**", "/images/**").permitAll()
                        .requestMatchers("/api/public/**").permitAll()
                        .anyRequest().access(customDynamicAuthorizationManager))
                .formLogin(Customizer.withDefaults());
        return http.build();
    }
}
정책이 없는 URL은 기본으로 열립니다. .anyRequest().authenticated()를 매니저로 바꾸면, 맞는 정책이 없는 URL은 "정책이 없을 때의 결정"(기본 PERMIT)에 따라 로그인 없이도 허용됩니다. 정책을 다 만들기 전에 정책이 없을 때의 결정을 먼저 정하세요.
  • 이 체인에서는 관리 콘솔도 시드 정책이 막습니다: /contexa/admin/**는 ALLOW_CONTEXA_ADMIN_ADMINISTRATORS(hasRole('ADMIN'))가 정합니다(관리 콘솔 보호).
  • 앱 패키지를 스캔 대상으로 바꿉니다: 관리 콘솔 "IAM → 시스템 설정 → 컨트롤러 기본 패키지"(스캔할 패키지 정하기). 기본값 io.contexa.contexaiam.으로는 앱의 엔드포인트가 하나도 등록되지 않습니다.

시나리오 1: URL 보호

1. 컨트롤러를 평소처럼 씁니다. 보안 애노테이션은 필요 없습니다.

@RestController
@RequestMapping("/api/v1/invoices")
public class InvoiceController {

    private final InvoiceService invoiceService;

    public InvoiceController(InvoiceService invoiceService) {
        this.invoiceService = invoiceService;
    }

    @GetMapping
    public List<InvoiceDto> listInvoices() {
        return invoiceService.findAll();
    }

    @PostMapping
    public InvoiceDto createInvoice(@RequestBody CreateInvoiceRequest req) {
        return invoiceService.create(req);
    }

    @DeleteMapping("/{id}")
    public void deleteInvoice(@PathVariable Long id) {
        invoiceService.delete(id);
    }
}

2. 정책 센터에서 "리소스 불러오기"를 누릅니다. 패키지가 스캔 대상이면 리소스 두 개가 등록됩니다. 식별자가 URL 패턴만이라 같은 경로의 GET과 POST는 하나로 합쳐집니다.

식별자HTTP 메서드유형
/api/v1/invoicesGET 또는 POST(먼저 찾은 쪽 하나)URL
/api/v1/invoices/{id}DELETEURL

리소스로 만든 정책은 그 리소스의 HTTP 메서드 하나에만 맞습니다. /api/v1/invoices의 두 메서드를 모두 다루려면 "리소스 권한 설정하기"로 HTTP 메서드 ANY 대상을 넣거나 수동 모드에서 대상을 더하세요.

3. 리소스를 검토하고 권한을 만듭니다. AI가 붙인 이름과 설명(예: "List Invoices")을 봅니다. AI 모델이 없으면 핸들러 메서드 이름이 그대로 남습니다. 보호할 리소스에서 "권한 생성 & 정책 생성"을 누르면 자동 권한(URL_…)이 생깁니다. 공개해야 할 경로는 제외가 아니라 앱 체인의 permitAll이나 정책으로 엽니다(제외는 목록에서 숨기기만 함).

4. 간편 모드로 정책을 만듭니다. 역할 ROLE_ADMIN · ROLE_FINANCE, CRUD 권한 READ, 효과 ALLOW를 고르고 "정책 생성"을 누르면 아래 조건이 저장됩니다. 자동 권한은 대상을 정할 뿐 조건에는 들어가지 않습니다.

(hasAuthority('ROLE_ADMIN') or hasAuthority('ROLE_FINANCE')) and (hasAuthority('READ'))

"송장 읽기" 같은 업무 권한을 조건에 쓰려면 "IAM → 권한 관리"에서 그 이름의 권한을 만들고 역할에 연결한 뒤, 간편 모드의 권한 선택에서 고르세요.

5. 더 좁은 규칙은 수동 모드로 씁니다. 예를 들어 송장 삭제를 "근무일 9~18시, 내부망, AI 판정이 ALLOW 또는 CHALLENGE인 관리자"에게만 허용하려면, 조건 하나에 and로 이어 씁니다. URL 정책은 조건 여러 개를 OR로 묶기 때문에, 셋으로 나눠 넣으면 하나만 맞아도 허용됩니다.

이름      INVOICE_DELETE_RESTRICTED
효과      ALLOW        우선순위 50
대상      URL /api/v1/invoices/{id}   HTTP 메서드 DELETE
조건      hasAuthority('ROLE_ADMIN')
          and T(java.time.LocalDate).now().getDayOfWeek().getValue() <= 5
          and T(java.time.LocalTime).now().isAfter(T(java.time.LocalTime).of(9,0))
          and T(java.time.LocalTime).now().isBefore(T(java.time.LocalTime).of(18,0))
          and hasIpAddress('10.0.0.0/8')
          and #ai.hasActionIn('ALLOW','CHALLENGE')

수동 모드는 입력한 조건을 그대로 SpEL로 저장합니다(정책 서비스 DefaultPolicyService). 간편 · AI 모드는 비즈니스 규칙 변환(BusinessPolicyServiceImpl)을 거쳐 조건을 만듭니다.

6. 요청이 들어오면 DELETE /api/v1/invoices/42는 이렇게 처리됩니다. 체인이 CustomDynamicAuthorizationManager에 맡기고, 매니저가 우선순위 순서의 URL 정책 가운데 경로와 메서드가 맞는 정책(위 정책)을 찾아 조건 식을 평가합니다. 기본 결합 방식 FIRST_APPLICABLE에서는 그 첫 결과(허용 또는 거부)로 끝나고, 결과는 허용이든 거부든 감사 기록에 남습니다. 코드 변경도 재배포도 없습니다.

시나리오 2: 메서드 보호

서비스 메서드에 @Protectable을 붙이면 메서드 단위로 보호합니다. ownerField는 반환 객체 · 대상 객체에서 소유자를 나타내는 필드 이름입니다.

@Service
public class DocumentService {

    private final DocumentRepository documentRepository;

    public DocumentService(DocumentRepository documentRepository) {
        this.documentRepository = documentRepository;
    }

    @Protectable(ownerField = "createdBy")
    public Document getDocument(Long documentId) {
        return documentRepository.findById(documentId)
                .orElseThrow(() -> new NotFoundException("Document not found"));
    }

    @Protectable(ownerField = "createdBy")
    public void updateDocument(Long documentId, UpdateDocumentRequest req) {
        Document doc = documentRepository.findById(documentId)
                .orElseThrow(() -> new NotFoundException("Document not found"));
        doc.setTitle(req.getTitle());
        doc.setContent(req.getContent());
        documentRepository.save(doc);
    }
}

"리소스 불러오기"를 누르면 메서드 리소스 두 개가 URL 리소스와 같은 목록에 등록되고, 검토 · 권한 생성 · 정책 연결 · 제외 흐름도 같습니다. 클래스가 스캔 패키지 안에 있어야 하고, 메서드에 직접 붙인 @Protectable만 목록에 올라옵니다.

식별자소유 클래스유형
com.example.docs.DocumentService.getDocument(Long)DocumentServiceMETHOD
com.example.docs.DocumentService.updateDocument(Long,UpdateDocumentRequest)DocumentServiceMETHOD

메서드 정책은 정책 안의 모든 조건을 AND로 묶고, 규칙마다 효과를 달 수는 없습니다. 그래서 "소유자 또는 관리자"는 조건 하나에 or로 쓰고, "BLOCK 판정이면 막기"는 다른 조건으로 더합니다.

정책    DOCUMENT_UPDATE_OWNER     효과 ALLOW   우선순위 100
대상    METHOD com.example.docs.DocumentService.updateDocument(Long,UpdateDocumentRequest)
조건 1  !#ai.isBlocked()
조건 2  hasAuthority('ROLE_ADMIN') or hasPermission(#documentId, 'DOCUMENT', 'UPDATE')
  • 두 조건이 AND로 묶여 "BLOCK이 아니고, 관리자이거나 소유자"일 때만 허용됩니다. 같은 메서드에 DENY 정책을 따로 두면 효과가 반대인 정책끼리 대상이 같아 충돌(CRITICAL)로 저장되지 않습니다(효과 · 우선순위 · 결합).
  • updateDocument를 부르면 Contexa의 메서드 가로채기(AOP)가 실행 전에 정책을 평가합니다. hasPermission(...)은 DOCUMENT 유형을 처리하는 도메인 권한 평가기가 허락해야 하고(권한 평가기), 그다음 문서의 createdBy 값과 로그인 이름(authentication.getName())을 비교합니다. ROLE_ADMIN은 소유자 비교를 건너뜁니다.
  • 메서드에 실행할 정책이 없으면 "메서드 정책이 없을 때의 결정"(기본 PERMIT)을 따릅니다.

시나리오 3: AI 초안과 승인

AI 모드는 새 위협 언어를 만드는 것이 아니라, 지금 있는 역할 · 권한 · 조건 템플릿 · SpEL을 조합한 정책 초안을 만듭니다. 초안을 만들 때 모델이 받는 것은 다음과 같습니다.

  • 쓸 수 있는 역할과 권한(권한이 보호하는 리소스 포함)
  • 저장된 조건 템플릿
  • 기존 정책 요약(충돌 · 중복을 피하도록)과 역할 계층
  • 벡터 저장소에서 찾은 비슷한 정책

모델은 조건 추천 목록이 아니라 정책 초안(이름 · 효과 · 역할 · 권한 · CRUD · 조건 템플릿 · #ai 조건 · 사용자 SpEL), ID → 이름 표, 이유를 돌려줍니다. 저장하면 출처 AI_GENERATED, 승인 대기(PENDING)가 됩니다.

승인 상태평가되나언제
PENDING아니요AI가 쓴 정책을 저장했을 때
APPROVED예(활성일 때)관리자가 승인했을 때
REJECTED아니요관리자가 거부했을 때(비활성)
NOT_REQUIRED예(활성일 때)사람이 쓴 정책

초안(DRAFT) 같은 별도 상태는 없습니다. 승인 절차와 검증 항목은 AI 초안 승인에 있습니다. 승인된 정책의 #ai 조건은 그 사용자에게 저장된 AI 판정으로 평가됩니다.

#ai.isAllowed()                          AI 판정이 ALLOW
#ai.needsChallenge()                     추가 인증이 필요(CHALLENGE)
#ai.hasActionIn('ALLOW', 'CHALLENGE')    둘 중 하나
hasRole('ADMIN') and !#ai.isBlocked()    역할 검사와 함께

시나리오 4: 정적 규칙에서 동적 정책으로

아래처럼 규칙이 많은 설정을 Contexa 정책으로 옮기는 순서입니다.

@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(auth -> auth
        .requestMatchers("/css/**", "/js/**", "/images/**").permitAll()
        .requestMatchers("/api/public/**").permitAll()
        .requestMatchers("/api/admin/users/**").hasRole("ADMIN")
        .requestMatchers("/api/admin/audit/**").hasAuthority("VIEW_AUDIT")
        .requestMatchers("/api/reports/financial/**").hasAnyRole("ADMIN", "FINANCE")
        .requestMatchers(HttpMethod.DELETE, "/api/**").hasRole("ADMIN")
        // ... 규칙이 더
        .anyRequest().authenticated()
    );
    return http.build();
}
  1. 스타터와 @EnableAISecurity: 리소스 스캐너는 자동으로 구성되지만, 앱 시작 때 돌지는 않습니다.
  2. 스캔 패키지를 정하고 "리소스 불러오기": 찾은 리소스의 이름을 확인하고, 보호할 리소스는 권한으로 정의합니다. 이 목록이 앱 전체의 보호 대상 목록이 됩니다.
  3. 규칙마다 정책을 만듭니다: 아래 표처럼 옮깁니다. 옮긴 뒤에는 시간 · IP · AI 판정처럼 정적 설정으로는 어려운 조건을 바로 더할 수 있습니다.
  4. 체인을 바꿉니다: 공개 경로만 남기고 .anyRequest().access(customDynamicAuthorizationManager)로 바꿉니다(준비하기의 설정).
  5. 정책이 없을 때의 결정을 정합니다: 지금까지 .anyRequest().authenticated()가 막던 나머지 URL을 어떻게 할지 정합니다(다음 절).
정적 규칙만드는 정책저장되는 조건
.hasRole("ADMIN")간편 모드, 역할 ROLE_ADMIN(hasAuthority('ROLE_ADMIN'))
.hasAuthority("VIEW_AUDIT")"IAM → 권한 관리"에서 만든 권한 VIEW_AUDIT을 간편 모드에서 고름(hasAuthority('VIEW_AUDIT'))
.hasAnyRole("ADMIN", "FINANCE")간편 모드, 역할 ROLE_ADMIN · ROLE_FINANCE(hasAuthority('ROLE_ADMIN') or hasAuthority('ROLE_FINANCE'))
.requestMatchers(HttpMethod.DELETE, "/api/**").hasRole("ADMIN")수동 모드, 대상 URL /api/** · HTTP 메서드 DELETEhasRole('ADMIN')

정책이 없을 때의 결정과 결합 방식

요청에 맞는 URL 정책이 없으면, 매니저는 "정책이 없을 때의 결정"을 씁니다. 기본값은 PERMIT(허용)입니다. 맞은 정책이 모두 DENY 정책이고 조건이 거짓(해당 없음)일 때도 같습니다(DENY_UNLESS_PERMIT은 이때 거부). 매니저의 마지막 줄은 이 결정을 넘겨 결합합니다.

return combiningEvaluator.evaluate(matchedDecisions, currentAlgorithm, currentNoPolicyDecision);

정책이 없는 URL을 막는 방법은 설정입니다.

  • 막기로 바꾸기: 관리 콘솔 "IAM → 시스템 설정 → 적용되는 URL 정책이 없을 때의 결정"을 DENY로 저장합니다. 설정 이름은 contexa.policy.no-matching-url-policy-decision이지만, 기본 시드가 만든 시스템 설정 값이 기동 때 YAML을 덮어쓰므로 화면에서 바꿉니다(결정 방식 설정). 맞는 정책이 하나도 없으면 결합 방식과 관계없이 이 결정을 씁니다.
  • 넓은 정책으로는 만들 수 없습니다: /** 같은 넓은 경로에 정책을 두면 효과가 반대인 다른 정책과 대상이 겹쳐 충돌(HIGH)로 저장이 거부되거나, 나중에 만드는 반대 효과 정책이 거부됩니다(충돌 검사).

효과의 뜻: ALLOW 정책은 조건이 참이면 허용, 거짓이면 거부입니다. DENY 정책은 조건이 참이면 거부, 거짓이면 해당 없음(다음 정책으로)입니다. 결합 방식 네 가지는 효과 · 우선순위 · 결합에 있습니다.

확인하는 법

  • 시뮬레이터: 정책 센터 "시뮬레이터" 탭에서 사용자와 요청을 넣어 결과를 봅니다. 저장 전의 후보 정책으로 전후를 비교할 수 있습니다(#ai는 참으로, hasIpAddress는 거짓으로 봄).
  • 접근 매트릭스: 역할 × 리소스 표로 누가 어디에 닿는지 봅니다.
  • 실시간 현황: URL 정책 판정은 허용(AUTHORIZATION_GRANTED)과 거부(AUTHORIZATION_DENIED) 모두 감사 기록에 남습니다. 결정 값 필터 DECISION_ALLOW · DECISION_DENY로 거를 수 있습니다(실시간 현황).
  • 로그인한 사용자의 요청이 URL 정책에서 거부되면, Contexa는 그 사실을 그 사용자의 세션과 사용자 범위의 사실로도 남깁니다(AuthorizationDenialRecorder가 있을 때).
