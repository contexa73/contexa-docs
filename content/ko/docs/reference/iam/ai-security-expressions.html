AI 보안 표현식: 판정 · 에이전트 조건

정책 조건에서 Contexa가 저장한 최신 Zero Trust 판정(#ai.isAllowed() 등)과 에이전트 · 위임 사실(isDelegatedAgent() 등)을 읽는 식입니다. 어디서 쓸 수 있는지는 인증 소유 방식에 따라 다릅니다.

@PreAuthorize에서 #ai를 쓰려면 CONTEXA_OWNED여야 합니다. Contexa가 Spring 메서드 보안을 켜고 #ai가 들어 있는 표현식 처리기를 앱 전체에 등록하는 것은 contexa.bridge.ownership이 CONTEXA_OWNED일 때(@EnableAISecurity(mode = SecurityMode.FULL)의 기본)뿐입니다. 기본 HOST_OWNED에서는 Contexa 정책의 조건, 곧 @Protectable 메서드 정책과 앱 체인에 연결한 URL 정책에서 씁니다.

어디서 쓸 수 있나

쓰는 곳CONTEXA_OWNEDHOST_OWNED(기본)
@Protectable 메서드 정책의 조건됨됨
URL 정책의 조건됨(Contexa 체인이 URL 정책을 연결)앱 체인에 URL 정책을 연결했을 때 됨. 다만 이 단계에서는 위임 도장이 아직 없어 에이전트 식은 사람 요청처럼 답하고, #ai는 위임 에이전트가 아니라 사람의 판정을 읽음(URL 접근 정책 켜기)
@PreAuthorize · @PostAuthorize 등 Spring 메서드 보안됨(앱이 MethodSecurityExpressionHandler 빈을 따로 두지 않았을 때)안 됨. 앱의 메서드 보안이 쓰는 처리기에는 #ai가 없음
agentRequestConfirmed()책임자가 확인한 요청에서 참같음: 책임자가 확인한 요청에서 참(에이전트 관문이 앱 체인 뒤에서 돎)
agentCallsInLastMinuteAtMost(n)관문이 센 호출 수로 비교같음

소유 방식은 @EnableAISecurity의 mode가 정하고(FULL이면 CONTEXA_OWNED, 기본 SANDBOX면 HOST_OWNED), contexa.bridge.ownership을 적으면 그 값이 우선합니다. 에이전트 관문은 정지 · 확인 · 제한에 있습니다.

판정은 언제 만들어지고 언제 읽히나

#ai 식은 그 자리에서 AI 분석을 하지 않습니다. 앞선 요청을 응답 뒤에 분석해 저장해 둔 그 사용자의 최신 판정을 읽습니다.

  • 판정 키: 사용자 ID입니다. 사람 대신 일하는 위임 에이전트는 자기 키(<사용자>::agent::<에이전트>)의 판정을 읽고, 위임자가 BLOCK이면 에이전트도 BLOCK으로 읽습니다(판정은 에이전트 자신의 키에).
  • 판정이 없을 때: 아직 분석되지 않았거나, 유효 시간이 지났거나, 로그인 정보가 없으면 PENDING_ANALYSIS로 읽힙니다.
  • ALLOW는 맥락에 묶입니다: ALLOW는 그 판정이 내려진 세션 · 클라이언트 IP · User-Agent(맥락 지문)에서만 ALLOW로 읽히고, 다른 맥락에서는 분석 대기로 읽힙니다. BLOCK · CHALLENGE · ESCALATE는 사용자의 모든 요청에 적용됩니다.
  • sync 메서드에서도 메서드 정책의 조건은 그 호출의 판정보다 먼저 평가되므로, 그때까지 저장된 판정을 읽습니다(호출 하나의 처리 순서).
  • 숫자 위험 점수는 식으로 노출하지 않습니다. 판정 5종만 읽습니다.

판정 5종

판정뜻유효 시간참이 되는 식
ALLOW허용15초isAllowed()
CHALLENGE추가 인증(MFA) 필요30분needsChallenge()
ESCALATE검토 보류(분석 미완료)5분. 풀리지 않으면 계속 ESCALATE로 읽힘needsEscalation()
BLOCK차단해제할 때까지isBlocked()
PENDING_ANALYSIS판정 없음(분석 대기)-isPendingAnalysis()
  • 풀리지 않은 ESCALATE를 요청 시점 필터(두 소유 방식 모두)는 BLOCK으로 올립니다(요청 시점 집행).
  • CHALLENGE의 추가 인증은 MFA입니다. CONTEXA_OWNED에서는 Contexa MFA, HOST_OWNED에서는 Contexa의 확인 전용 추가 확인(패스키, 메일 일회용 코드, 앱 자체 재인증)입니다. CAPTCHA 같은 다른 확인은 없습니다.
  • 판정 이름을 글자로 받는 식(hasAction 등)은 대소문자를 가리지 않고 A · B · C · E 약자도 받습니다. 모르는 글자는 ESCALATE로 해석하므로 오타에 주의하세요.

에이전트 식

모델 판정과 별도로, URL · 메서드 정책에서 위임을 결정적으로 따질 수 있습니다. 이 식들은 위임 기록이 아니라 요청의 위임 도장(토큰 · 세션 등에서 인증 브리지가 만든 것)을 읽습니다.

식뜻
isAgent() / isDelegatedAgent() / isAutonomousAgent()에이전트 요청인지 / 위임 에이전트인지 / 단독 에이전트인지
agentId / isAgentIn('a', 'b')요청한 에이전트 ID / 그 가운데 하나인지
delegatorId위임자(위임 에이전트일 때)
delegationChainDepth / delegationChainDepthAtMost(n)위임 사슬 깊이(사람 · 단독 에이전트 0, 직접 위임 1) / n 이하인지
delegationAllowsOperation('READ')위임이 그 작업을 허용하는지(대소문자 무시)
delegationAllowsResource('/api/reports/1')위임이 그 대상을 허용하는지(목록 항목이 *로 끝나면 앞부분이 같은 모든 대상)
delegationRequiresApproval()위임이 위임자 승인을 요구하는지
agentRequestConfirmed()책임자가 바로 이 요청을 확인했는지(에이전트 요청일 때만 true). 확인 표지는 두 소유 방식 모두에서 도는 에이전트 관문이 붙임
agentCallsInLastMinuteAtMost(n)이 위임의 최근 1분 호출이 이 요청을 포함해 n 이하인지. 사람이거나 센 것이 없으면 true
 
isDelegatedAgent() and delegationAllowsOperation('READ') and delegationChainDepthAtMost(1)
!delegationRequiresApproval() or agentRequestConfirmed()
  • 사람의 요청에는 위임 도장이 없어 에이전트 식은 거짓입니다. 다만 delegationChainDepthAtMost(n)(n이 0 이상)과 agentCallsInLastMinuteAtMost(n)은 사람에게 참입니다.
  • 둘째 줄은 승인을 요구하는 위임이면 책임자가 확인한 그 요청만 통과시키는 확인 필수 정책입니다. ALLOW 정책으로 다른 허용 정책보다 앞 순서(작은 우선순위)에 둡니다. 같은 대상에 효과가 반대인 정책은 충돌로 저장이 막힙니다. 흐름은 책임자 확인에 있습니다.
  • 같은 설명이 위임과 업무 목표 계약, 정지 · 확인 · 제한에도 있습니다.

판정을 어디서 읽나

식이 있는 곳읽는 순서
URL 정책평가할 때마다 판정 저장소를 바로 읽음
메서드 정책① Contexa 체인이 로그인을 읽을 때 요청에 남긴 판정(CONTEXA_OWNED, 위임 에이전트는 건너뜀) → ② 5초 로컬 캐시(최대 10,000개, 키는 판정 키 + 맥락 지문) → ③ 판정 저장소
  • 메서드 정책의 식은 로컬 캐시 때문에 판정이 바뀐 뒤 최대 5초 동안 이전 판정을 읽을 수 있습니다. 판정 없음은 캐시하지 않습니다.
  • 판정 저장소는 단독 모드(contexa.infrastructure.mode: standalone, 기본)면 메모리, 분산 모드(distributed)면 Redis입니다. 메모리 저장소가 기억하는 사용자 수는 contexa.security.zerotrust.standalone.max-decision-users(0이면 힙 크기에서 정함)이고, 넘치면 오래전에 판정한 사용자부터 지우되 제한 상태인 사용자는 지우지 않습니다.

권한 · 소유권과 함께

  • hasPermission(...)은 메서드 정책의 조건(그리고 CONTEXA_OWNED의 @PreAuthorize)에서만 씁니다. URL 정책에서는 지워집니다.
  • 내장 도메인은 USER · ROLE · ROLE_HIERARCHY · GROUP · PERMISSION입니다. ORDER · DOCUMENT 같은 다른 도메인은 사용자 정의 평가기가 있어야 하고, 없으면 인자 3개 hasPermission은 예외로 끝납니다(권한 평가기).
  • hasIpAddress · httpMethod는 URL 정책에서만, ownerField 소유자 확인은 메서드 정책에서만 됩니다(소유자 확인).
hasPermission(#userId, 'USER', 'READ') and #ai.isAllowed()
hasPermission(#groupId, 'GROUP', 'UPDATE') and !#ai.isBlocked()
// CONTEXA_OWNED에서만: Spring 메서드 보안 식에서 #ai 사용
@PreAuthorize("!#ai.isBlocked() and hasRole('ADMIN')")
public void rotateSigningKeys() {
    ...
}

관리 화면에서

  • 정책 센터(/contexa/admin/policy-center)의 정책 생성 탭에서 조건에 식을 직접 씁니다(정책 관리).
  • 비즈니스 규칙 경로(POST /contexa/admin/api/policies/build-from-business-rule)에서 AI 판정 사용(aiActionEnabled)과 허용할 판정(allowedActions)을 고르면, 판정이 하나면 #ai.isAllowed() 같은 식을, 여럿이면 #ai.hasActionIn(...)을 만들고 역할 · 권한 · 직접 쓴 SpEL과 함께 한 조건 안에 and로 묶습니다. 이름 붙은 AI 조건 템플릿은 없습니다.
  • AI가 만든 정책은 PENDING으로 들어와 승인해야 실행됩니다. 손으로 만든 정책은 NOT_REQUIRED로 바로 실행됩니다.
  • 기록만 하는 운영(SHADOW)은 정책마다 정하는 것이 아니라 전역 집행 모드(contexa.security.zerotrust.mode, 또는 시스템 설정의 AI 판정 모드)입니다.
  • 결과는 정책 목록의 승인 상태, 시뮬레이터, 감사 기록으로 확인합니다.

안전장치

데이터베이스에 저장된 조건은 저장 · 적재 때 검사하고 샌드박스에서 평가합니다. T(...)는 LocalTime · LocalDate · LocalDateTime · DayOfWeek만, new · @bean · 리플렉션은 쓸 수 없습니다. 판정 식과 에이전트 식은 그대로 됩니다. 자세한 규칙은 인가 개요 > 안전장치에 있습니다.
