정책 관리

관리 콘솔의 정책 센터에서 URL과 메서드의 접근 정책을 만들고, AI가 쓴 초안을 승인하고, 저장한 정책이 요청을 어떻게 판정하는지 확인하는 방법을 설명합니다. 정책은 Contexa DB에 저장되며, 저장하는 즉시 다시 읽혀 다음 요청부터 적용됩니다.

한눈에 보기

정책 한 건은 네 가지로 이루어집니다. 어디에(대상), 어떤 조건이면(조건), 허용할지 막을지(효과), 어느 정책을 먼저 볼지(우선순위)입니다. 예를 들어 "/api/v1/invoices/**에 대해, ROLE_FINANCE 권한이 있으면, 허용한다, 우선순위 100"이 정책 한 건입니다.

URL 정책은 요청이 동적 인가 매니저를 지날 때만 평가됩니다. @EnableAISecurity(mode = SecurityMode.FULL)이면 Contexa가 만든 보안 체인이 모든 요청을 CustomDynamicAuthorizationManager로 보냅니다. 기본 HOST_OWNED에서는 Contexa가 보안 체인을 만들지 않으므로, 앱의 체인에서 .anyRequest().access(customDynamicAuthorizationManager)처럼 직접 연결해야 URL 정책이 평가됩니다(준비하기). @Protectable 메서드 정책은 두 방식 모두에서 그 메서드를 부를 때 평가됩니다.

URL 대상은 Spring 경로 패턴(/api/**, /api/v1/invoices/{id})으로 요청과 맞춥니다. HTTP 메서드가 없거나 ANY · ALL이면 모든 메서드에 맞습니다. 화면에서 ALL을 고르면 메서드 없음으로 저장됩니다. 경로 변수는 조건에서 #id처럼 쓸 수 있습니다.

메서드 대상의 식별자는 패키지.클래스.메서드(단순 파라미터 타입) 모양입니다(예: com.example.docs.DocumentService.getDocument(Long)). 리소스 스캐너가 만드는 식별자와 같습니다.

조건이 묶이는 방식

한 정책에 조건이 여러 개 있으면 Contexa는 이를 식 하나로 묶어 평가합니다. 묶는 방법이 URL 정책과 메서드 정책에서 다릅니다.

조건 1: hasAuthority('ROLE_ADMIN')
조건 2: #ai.isAllowed()

URL 정책    → (hasAuthority('ROLE_ADMIN')) or (#ai.isAllowed())
메서드 정책 → (hasAuthority('ROLE_ADMIN')) and (#ai.isAllowed())
수동 모드 화면의 안내와 실제 동작이 다릅니다. 수동 모드 화면은 "각 규칙은 OR로 결합, 규칙 안의 조건은 AND로 결합"이라고 안내하지만, 실제로는 규칙과 관계없이 URL 정책의 조건은 모두 OR, 메서드 정책의 조건은 모두 AND로 묶입니다. URL 정책에서 여러 조건을 모두 만족해야 한다면 조건 하나에 and로 이어 쓰세요.

효과 · 우선순위 · 결합

요청과 대상이 맞는 정책을 우선순위가 작은 것부터 평가합니다. 메서드 정책은 그 메서드에 걸린 대상의 targetOrder가 먼저이고, 그다음 우선순위, 그다음 정책 ID 순입니다. 효과는 조건 결과를 다음처럼 바꿉니다.

효과조건이 참이면조건이 거짓이면
ALLOW허용거부
DENY거부해당 없음(이 정책은 결과를 내지 않음)

기본 결합 방식 FIRST_APPLICABLE은 "해당 없음"이 아닌 첫 결과로 정합니다. 그래서 먼저 평가되는 ALLOW 정책은 조건이 거짓이어도 거부로 결론을 냅니다. 맞는 정책이 없거나 모두 "해당 없음"이면 "정책이 없을 때의 결정"(기본값은 URL이 AUTHENTICATED, 메서드가 PERMIT)을 씁니다. 바꾸는 방법은 결정 방식 설정에 있습니다.

예: BLOCK 판정을 받은 사용자는 막고 나머지는 역할로 정하려면 조건 하나에 함께 씁니다: hasAuthority('ROLE_FINANCE') and !#ai.isBlocked(). 같은 대상에 DENY 정책과 ALLOW 정책을 따로 두는 방법은 아래 충돌 검사에 걸려 저장되지 않습니다.

효과가 반대인 정책은 대상이 겹치면 저장되지 않습니다. 저장할 때 Contexa는 활성 정책 가운데 효과가 반대이고 대상이 겹치는 정책을 찾습니다. URL 대상의 경로와 HTTP 메서드가 같으면 CRITICAL, 한 패턴이 다른 패턴을 포함하거나 둘 다 와일드카드이면서 앞의 두 마디 이상이 같으면 HIGH이고, 둘 다 저장을 막습니다. 경로가 같고 한쪽만 HTTP 메서드가 ANY이면 MEDIUM이라 저장됩니다. HTTP 메서드가 서로 다르면(GET과 DELETE) 겹치지 않습니다. 메서드 대상은 식별자가 같으면 CRITICAL입니다. 그래서 /** 같은 넓은 DENY 정책으로 "기본 거부"를 만들 수 없습니다. 기본 거부는 결정 방식 설정의 "정책이 없을 때의 결정"으로 정하세요.

정책 만드는 세 가지 방법

관리 콘솔의 "정책 → 정책 센터"(/contexa/admin/policy-center)에서 "정책 생성" 탭을 엽니다. 이 탭에 리소스 목록과 세 가지 작성 모드가 함께 있습니다. 리소스 목록은 리소스 스캐너가 채웁니다.

모드이럴 때들어가는 길만들어지는 정책
간편 모드리소스에 역할 · 권한을 붙일 때리소스의 "권한 생성 & 정책 생성" → "간편 모드", 또는 "리소스 권한 설정하기"(대상 직접 입력)우선순위 100, 출처 MANUAL, 바로 적용
수동 모드대상 · 규칙 · 조건을 직접 쓸 때"수동 모드" 카드입력한 그대로, 출처 MANUAL, 바로 적용
AI 모드원하는 정책을 글로 설명하고 초안을 받을 때"AI 모드" 카드, 또는 리소스의 "AI 정책 마법사"(리소스 하나만)출처 AI_GENERATED, 승인한 뒤 적용

간편 모드

역할 둘과 CRUD 권한 READ를 고르면 아래 조건이 만들어집니다.

(hasAuthority('ROLE_ADMIN') or hasAuthority('ROLE_FINANCE')) and (hasAuthority('READ'))
  • 역할끼리, CRUD 권한끼리, 직접 만든 권한끼리 or로 묶고, 묶음끼리는 and로 잇습니다.
  • 리소스를 정의할 때 자동으로 생긴 권한(URL_… · METHOD_…)은 정책의 대상을 정하는 데만 쓰이고 조건에는 들어가지 않습니다.
  • 대상은 고른 리소스의 경로와 그 리소스의 HTTP 메서드 하나입니다. "리소스 권한 설정하기"로 대상을 직접 넣으면 출처 MANUAL 대상이 되고, HTTP 메서드를 고를 수 있습니다(주지 않으면 ANY).
  • 고를 수 있는 주체는 역할뿐이고 그룹은 고르지 않습니다. 간편 모드는 권한을 새로 만들거나 역할에 권한을 붙이지 않습니다. 사용자 · 그룹에 역할과 CRUD 권한을 주는 일은 권한 센터에서 합니다.
  • 고른 역할의 자동 정책(AUTO_POLICY_FOR_<역할 이름>, 역할 변경 자동 동기화)이 이미 있으면 정책은 만들고 경고를 함께 돌려줍니다.
  • 만들기 전에 POST /contexa/admin/policy-center/api/validate-quick으로 검사 결과를 미리 볼 수 있습니다.

수동 모드

  1. 기본 정보: 정책 이름(고유) · 설명 · 효과 · 우선순위(작을수록 먼저)
  2. 적용 대상: 유형(URL · METHOD), 식별자(예: /api/v1/invoices/** 또는 메서드 식별자), HTTP 메서드. 대상은 여러 개 넣을 수 있습니다.
  3. 규칙: 규칙 설명
  4. 조건: SpEL 식과 단계("사전 인가" · "사후 인가")
  5. 정책 저장: POST /contexa/admin/policy-center/create-policy로 저장하고 정책 목록 탭으로 갑니다.

수동 모드에는 조건 템플릿 선택이나 추천 단계가 없습니다. 조건은 직접 씁니다(조건 쓰기). 저장하기 전에 POST /contexa/admin/policy-center/api/validate로 식 검사 · 충돌을 미리 볼 수 있습니다.

AI 모드

  1. 원하는 정책을 글로 씁니다(예: "재무팀은 송장 목록을 읽을 수 있다"). 리소스에서 "AI 정책 마법사"로 들어오면 그 리소스가 입력 앞에 채워집니다.
  2. Contexa가 쓸 수 있는 역할 · 권한 · 조건 템플릿 목록, 기존 정책 요약, 역할 계층, 벡터 저장소에서 찾은 비슷한 정책 5건을 함께 모델에 보냅니다.
  3. 모델이 초안을 돌려줍니다. 정책 이름 · 효과 · 역할 ID · 권한 ID · CRUD 권한 · 조건 템플릿과 값 · #ai 판정 조건 · 사용자 SpEL, ID를 이름으로 바꾼 표, 이유입니다. 화면은 POST /contexa/admin/api/ai/policies/generate/stream(SSE)으로 받고, 한 번에 받는 POST /contexa/admin/api/ai/policies/generate도 있습니다.
  4. 화면이 초안을 실제로 있는 항목과 맞춰 보고 카드로 보여 줍니다. 고친 뒤 저장하면 POST /contexa/admin/api/policies/build-from-business-rule로 출처 AI_GENERATED 정책이 만들어집니다.
  5. 정책은 승인 대기(PENDING)로 저장되어, 승인하기 전에는 평가되지 않습니다(AI 초안 승인).
AI 모드는 정책 초안을 만드는 기능입니다. 조건을 따로 추천하거나 한 번에 적용하는 기능은 없습니다. AI 모델 연결이 필요합니다(AI 모델 연결).

여러 리소스에 한꺼번에

리소스 목록에서 여러 리소스를 골라 간편 모드로 들어가면, 리소스마다 권한을 만들고(define-batch) 정책을 한꺼번에 만듭니다(POST /contexa/admin/policy-center/api/batch-create).

  • 역할을 하나 이상 골라야 합니다. CRUD 권한이 없는 리소스는 건너뜁니다.
  • 리소스마다 조건 (역할 or …) and (CRUD 권한 or …), 우선순위 100, 이름 <효과>_<역할들>_<CRUD>_<경로>(200자까지)로 만듭니다.
  • 리소스마다 저장 전 검사를 하고, 막히면 그 리소스만 건너뜁니다. 결과는 리소스별로 CREATED · SKIPPED · ERROR입니다.
  • AI 정책 마법사는 리소스 하나만 받습니다.

코드에서 만들기(비즈니스 규칙 API)

화면 없이 HTTP로 정책을 만들 수 있습니다. 간편 모드와 AI 모드도 같은 변환을 씁니다.

POST /contexa/admin/api/policies/build-from-business-rule
Content-Type: application/json

{
  "policyName": "INVOICE_READ_FOR_FINANCE",
  "description": "재무팀 송장 조회",
  "effect": "ALLOW",
  "roleIds": [4],
  "permissionIds": [15],
  "crudPermissions": ["READ"],
  "aiActionEnabled": true,
  "allowedActions": ["ALLOW"]
}

permissionIds의 권한이 리소스에 연결돼 있으면 그 리소스가 대상이 됩니다. 역할 · 권한 · spelId 가운데 하나는 있어야 합니다. 성공하면 만든 정책을, 실패하면 본문 없는 400을 돌려줍니다.

입력만들어지는 조건
roleIdshasAuthority('ROLE_…')를 or로
crudPermissionshasAuthority('READ') 등을 or로
permissionIds직접 만든 권한만 hasAuthority('권한 이름')을 or로. 자동 생성 권한과 CRUD 권한은 뺍니다
aiActionEnabled + allowedActions 하나ALLOW → #ai.isAllowed(), BLOCK → #ai.isBlocked(), CHALLENGE → #ai.needsChallenge(), ESCALATE → #ai.needsEscalation(), 그 밖은 #ai.hasAction('X')
allowedActions 여럿#ai.hasActionIn('ALLOW','CHALLENGE')
customConditionSpel(식) 그대로
conditions(템플릿 ID → 값 목록)조건 템플릿의 %s 자리에 값을 따옴표로 넣은 식
spelId저장된 표현식 권한 하나만. 역할 · 권한 입력은 쓰지 않습니다

위 조건들은 모두 and로 이어 조건 하나가 됩니다. 우선순위는 100으로 고정입니다. source가 AI_GENERATED · AI_EVOLVED이면 승인 대기, 아니면 승인이 필요 없습니다. sourceType: "MANUAL"과 manualTargetType · manualTargetIdentifier · manualHttpMethod · manualTargetOrder로 대상을 직접 줄 수 있습니다.

조건 쓰기

조건은 Spring Security 식(SpEL)입니다. #ai로 시작하는 식은 그 사용자에게 저장된 AI 판정을 읽습니다(AI 보안 식).

하려는 일조건쓸 수 있는 곳
근무 시간(9시~18시)에만T(java.time.LocalTime).now().isAfter(T(java.time.LocalTime).of(9,0)) and T(java.time.LocalTime).now().isBefore(T(java.time.LocalTime).of(18,0))URL · 메서드
내부망에서만hasIpAddress('10.0.0.0/8')URL
특정 역할만hasAuthority('ROLE_MANAGER')URL · 메서드
remember-me가 아닌 완전한 로그인isFullyAuthenticated()URL · 메서드
AI 판정이 ALLOW이고 추가 인증 대기가 아님#ai.isAllowed() and !#ai.needsChallenge()URL · 메서드
AI 허용 + 객체 권한(소유자)#ai.isAllowed() and hasPermission(#id, 'USER', 'READ')메서드. URL 정책에서는 hasPermission(...)이 지워져 #ai.isAllowed()만 남습니다
관리자는 늘, 나머지는 AI 허용 + 객체 권한hasAnyAuthority('ROLE_ADMIN') or (#ai.isAllowed() and hasPermission(#id, 'DOCUMENT', 'UPDATE'))메서드. URL 정책이면 hasAnyAuthority('ROLE_ADMIN') or (#ai.isAllowed())로 바뀝니다

메서드 정책의 hasPermission(대상 ID, '대상 유형', '동작')은 그 대상 유형을 처리하는 도메인 권한 평가기가 있어야 합니다(권한 평가기). @Protectable(ownerField = "createdBy")가 붙은 메서드면 평가기가 허락한 뒤 객체의 createdBy 값과 로그인 이름을 한 번 더 비교합니다. ROLE_ADMIN은 이 소유자 비교를 건너뜁니다.

식 안전 규칙

조건은 DB에 저장되는 식입니다. Contexa는 저장할 때와 읽을 때 두 번 검사하고, 평가는 제한된 환경(샌드박스)에서 합니다.

  • 쓸 수 없는 것: T(...) 타입 참조(java.time의 LocalTime · LocalDate · LocalDateTime · DayOfWeek만 허용), 생성자 호출(new), 빈 참조(@이름), 대입, 리플렉션 · 클래스 로딩 · 프로세스 실행에 쓰이는 메서드(getClass · forName · exec · getRuntime 등)와 속성(class · classLoader 등). 식은 값을 읽기만 하고 바꿀 수 없습니다.
  • 저장할 때: 화면 · API · 버전 롤백 등 모든 저장 경로에서 검사하고, 걸리면 저장하지 않습니다. 조건 엔티티를 DB에 쓰기 직전에도 한 번 더 검사합니다.
  • 읽을 때: 이미 저장된 식이 걸리면 그 정책을 버리지 않고 거부로 바꿉니다. URL 정책은 그 대상 경로를 모두 거부하고, 메서드 정책은 효과에 맞춰 거부가 나오게 합니다. 정책을 버리면 "정책이 없을 때의 결정"(기본 허용)으로 열릴 수 있기 때문입니다. 오류 로그에 정책 ID와 이유가 남습니다.

조건 템플릿

조건 템플릿은 %s 자리에 값을 넣어 다시 쓰는 SpEL 조각입니다. AI 모드의 초안이 템플릿 ID와 값을 골라 조건을 만들 때 씁니다. 정책 센터의 조건 목록(GET /contexa/admin/policy-center/api/conditions)은 이름 · 설명 키워드로만 거릅니다.

분류정해지는 기준승인 필요
UNIVERSAL복잡도 점수 3 이하아니요
CONTEXT_DEPENDENT복잡도 점수 4~6아니요
CUSTOM_COMPLEX복잡도 점수 7 이상예

복잡도 점수는 템플릿을 저장할 때 식 안의 # · 괄호 · and · or · 비교 연산자, hasPermission · hasRole 등을 세어 1~10으로 정합니다. permitAll · denyAll이 들어 있거나, 역할 · 권한 검사 없이 isAuthenticated()만 있으면 점수와 관계없이 승인 필요로 표시합니다.

템플릿은 AI 모델이 만듭니다. 공통 템플릿과, 파라미터가 있는 메서드 리소스마다의 템플릿을 10개씩 나눠 만들며, 메서드 리소스가 하나도 없으면 만들지 않습니다. 리소스를 불러올 때 함께 만들려면 contexa.iam.admin.condition-templates.enabled: true로 켭니다(기본 false). 아래 API로 직접 부를 수도 있습니다.

API(/contexa/admin/api/conditions 아래)하는 일
GET /classified분류별 템플릿 목록
GET /compatible/{resourceId}그 리소스에 맞는 템플릿과 호환 결과

저장하면 일어나는 일

조건 hasAuthority('ROLE_ADMIN') and isAuthenticated()의 읽기 쉬운 설명은 ((Has authority(ROLE_ADMIN) and Authenticated user))입니다. 규칙마다 괄호로 묶고 규칙끼리는 or로 잇습니다.

  • 다른 인스턴스 알림은 contexa.infrastructure.mode: distributed이고 Redisson이 있을 때 Redis 토픽으로 보냅니다. 단독 모드에서는 그 인스턴스만 다시 읽습니다.
  • 삭제하면 그 정책의 대상을 다른 정책이 쓰지 않는 리소스를 "정책 미 설정"으로 되돌리고, 자동 생성 권한을 지우고, 버전 기록을 지운 뒤 재로드합니다. 감사 기록(POLICY_DELETED)은 삭제 전에 남깁니다.
  • 정책 상세 화면에서 수정하면 고치기 전 내용이 버전(UPDATED)으로 먼저 기록되고, 같은 검사를 거쳐 저장됩니다.
  • 정책 서비스는 저장할 때 조건에 hasAuthority('…')로 쓴 권한이 있으면 그 권한 ID를 담은 정책 변경 이벤트(PolicyChangedEvent)를 내고, 삭제할 때는 권한 ID 없이 냅니다.

AI 초안 승인

AI가 쓴 정책은 사람이 승인해야 평가됩니다. 사람이 쓴 정책(MANUAL · IMPORTED)은 승인 없이(NOT_REQUIRED) 바로 평가됩니다.

  1. 정책 센터의 "정책 목록" 탭(/contexa/admin/policy-center?tab=list)에서 승인 상태로 거릅니다. 키워드 · 활성 여부로도 거를 수 있습니다.
  2. 정책을 열어(/contexa/admin/policies/{id}) 대상 · 조건 · AI 이유를 봅니다. 시뮬레이터와 영향 분석으로 결과를 미리 확인합니다(적용 확인).
  3. 목록에서 "승인"을 누르면 AI 검증 창이 열립니다(GET /contexa/admin/policy-center/api/{policyId}/ai-validation). 실패 항목이 없어야 승인됩니다.
  4. 승인 POST /contexa/admin/policies/{id}/approve, 거부 POST /contexa/admin/policies/{id}/reject. 승인 · 거부한 사람과 시각이 기록되고 재로드됩니다. 목록의 거부 버튼은 승인 대기 정책에만 보입니다.

충돌CRITICAL 충돌그 밖의 충돌

버전과 되돌리기

역할 변경 자동 동기화

역할에 권한을 붙이거나 바꾸면 Contexa가 그 역할의 자동 정책을 만들거나 고칩니다.

역할을 지우면 그 역할의 자동 정책도 지웁니다. 정책 서비스에 권한 하나마다 자동 정책을 만드는 메서드(synchronizePolicyForPermission)도 있지만, 지금 이 메서드를 부르는 곳은 없습니다.

결정 방식 설정

정책이 여러 개 맞을 때 하나로 합치는 방식과, 맞는 정책이 없을 때의 결정을 정합니다.

설정기본값뜻언제 바꾸나
contexa.policy.combining-algorithmFIRST_APPLICABLE결합 방식(아래 표)우선순위 대신 "거부가 하나라도 있으면 거부" 같은 규칙으로 합치고 싶을 때
contexa.policy.no-matching-url-policy-decisionAUTHENTICATED맞는 URL 정책이 없거나, 맞은 정책이 모두 해당 없음일 때(DENY_UNLESS_PERMIT는 뒤의 경우 거부). AUTHENTICATED이면 정책 없는 URL은 로그인한 사용자만 통과하고(Contexa 자신의 로그인은 열려 있음), PERMIT이면 모두에게 열려 있습니다정책을 다 만든 뒤 나머지 URL을 기본으로 막을 때(DENY)
contexa.policy.missing-method-policy-decisionPERMIT실행할 메서드 정책이 없거나, 모두 해당 없음일 때(DENY_UNLESS_PERMIT는 뒤의 경우 거부)정책 없는 @Protectable 메서드를 막을 때(DENY)
결합 방식결과
FIRST_APPLICABLE"해당 없음"이 아닌 첫 결과
DENY_OVERRIDES거부가 하나라도 있으면 거부, 아니면 허용이 있으면 허용
PERMIT_OVERRIDES허용이 하나라도 있으면 허용, 아니면 거부가 있으면 거부
DENY_UNLESS_PERMIT맞은 정책 가운데 허용이 있어야 허용, 없으면 거부(모두 해당 없음이어도 거부). 맞는 정책이 하나도 없으면 "정책이 없을 때의 결정"
YAML 값은 기동할 때 시스템 설정 값으로 덮어씌워집니다. 기본 시드가 system_settings 행을 만들고(결합 방식 FIRST_APPLICABLE, 메서드 PERMIT, URL은 값 없음), Contexa는 기동할 때와 시스템 설정을 저장할 때마다 그 행의 값을 적용합니다. URL의 결정은 운영자가 저장한 뒤에야 적용되고, 그 전에는 YAML 값이 그대로 유효합니다(없으면 AUTHENTICATED). 이전 버전이 만든 행은 URL에 PERMIT을 갖고 있고 그대로 유지됩니다. 그래서 위 세 값은 관리 콘솔의 "IAM → 시스템 설정"에서 바꾸세요. 저장하면 이 인스턴스에 바로 적용되고, URL 정책을 다시 읽고, 분산 모드면 다른 인스턴스에도 알립니다. YAML 값은 system_settings 행이 없을 때만 쓰입니다(예: contexa.iam.seed.enabled: false이고 아무도 시스템 설정을 저장하지 않았을 때). 
contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
  iam:
    seed:
      enabled: false          # system_settings 행을 만들지 않을 때만 아래 값이 쓰입니다
  policy:
    combining-algorithm: DENY_OVERRIDES
    no-matching-url-policy-decision: DENY
    missing-method-policy-decision: PERMIT
