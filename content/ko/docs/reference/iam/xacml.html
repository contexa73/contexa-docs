contexa-iam 인가

인가 개요

Contexa는 접근 규칙을 코드 대신 데이터베이스의 정책으로 두고, URL 요청과 @Protectable 메서드 호출에 적용합니다. 이 페이지에서 두 적용 지점이 언제 켜지는지, 정책 하나가 허용 · 거부를 어떻게 정하는지, 바꾼 정책이 어떻게 반영되는지 한 번에 봅니다.

한눈에 보기

Spring Security의 @PreAuthorize("hasRole('ADMIN')") 같은 규칙은 코드 안에 있어서, 바꾸려면 다시 빌드하고 배포해야 합니다. Contexa는 규칙을 정책으로 데이터베이스에 저장합니다. 관리 화면의 정책 센터(Policy Center)나 정책 서비스로 정책을 바꾸면 다시 배포하지 않아도 곧바로 적용됩니다.

다만 정책을 요청에 거는 일은 코드 · 구성입니다. URL 정책은 보안 필터 체인에 연결되어 있어야 하고, 메서드 정책은 그 메서드에 @Protectable이 붙어 있어야 합니다(언제 켜지나).

정책 조건은 XML 정책 언어가 아니라 Spring의 SpEL 식입니다. 조건에서 역할 · 권한뿐 아니라 Contexa가 저장한 AI 판정(#ai.isAllowed())과 에이전트의 위임 사실도 읽을 수 있습니다(조건에 쓸 수 있는 것).

언제 켜지나: 인증 소유 방식별

로그인을 Contexa가 맡는지(CONTEXA_OWNED), 앱이 맡는지(HOST_OWNED, 기본)에 따라 정책이 걸리는 곳이 다릅니다. @EnableAISecurity(mode = SecurityMode.FULL)이면 CONTEXA_OWNED, 기본 SANDBOX이면 HOST_OWNED가 기본값이고, contexa.bridge.ownership을 적으면 그 값이 우선합니다.

실행되는 정책

출처와 상관없이 활성이고 승인 상태가 APPROVED 또는 NOT_REQUIRED인 정책만 실행됩니다.

  • 손으로 만든 정책(MANUAL, 출처를 비우면 이것)과 가져온 정책(IMPORTED)은 저장할 때 NOT_REQUIRED라 바로 실행됩니다. 역할의 권한이 바뀔 때 만들어지는 정책 AUTO_POLICY_FOR_{역할}(우선순위 500)도 같은 길로 저장됩니다.
  • AI가 만든 정책(AI_GENERATED · AI_EVOLVED)은 PENDING으로 들어와 관리자가 승인해야 실행됩니다. 거절(REJECTED)하면 비활성이 됩니다.

결정 규칙

정책마다 조건을 평가하고, 효과를 적용해 그 정책의 결과를 만듭니다. DENY 정책의 조건 식은 뒤집지 않습니다. 조건이 참이면 거부, 거짓이면 "적용 안 됨"입니다.

효과조건이 참조건이 거짓
ALLOW허용거부
DENY거부적용 안 됨(결합에서 빠짐)

조건이 없는 정책은 늘 적용됩니다. ALLOW면 늘 허용, DENY면 늘 거부입니다. 여러 정책의 결과는 결합 알고리즘으로 하나로 합칩니다. URL 정책과 메서드 정책이 같은 설정을 씁니다.

결합 알고리즘결과
FIRST_APPLICABLE(기본)우선순위 순서로 처음 적용되는 정책의 결과
DENY_OVERRIDES적용된 정책 중 하나라도 거부면 거부, 아니면 허용
PERMIT_OVERRIDES적용된 정책 중 하나라도 허용이면 허용, 아니면 거부
DENY_UNLESS_PERMIT허용한 정책이 있으면 허용, 없으면 거부

맞는 정책이 없을 때

요청에 맞는 정책이 하나도 없으면 알고리즘과 상관없이 기본 결정을 씁니다. 맞는 정책은 있지만 모두 "적용 안 됨"(조건이 거짓인 DENY 정책뿐)이면 DENY_UNLESS_PERMIT은 거부하고, 나머지 알고리즘은 기본 결정을 씁니다.

설정기본값뜻
contexa.policy.no-matching-url-policy-decisionPERMITURL 요청의 기본 결정. DENY면 정책이 없는 URL을 막음
contexa.policy.missing-method-policy-decisionPERMIT@Protectable 메서드의 기본 결정
contexa.policy.combining-algorithmFIRST_APPLICABLE결합 알고리즘
기본은 "정책이 없으면 허용"입니다. 정책이 없는 URL과 메서드는 열려 있습니다. 운영에서 기본 거부로 바꾸려면 관리 화면 IAM > 시스템 설정(/contexa/admin/system-settings)에서 두 기본 결정을 DENY로 저장하세요. 기본 시드가 만드는 시스템 설정 행이 있으면, 기동할 때 그 행의 값(결합 알고리즘 · 두 기본 결정)이 YAML의 contexa.policy.*를 덮어씁니다. 시드 행의 처음 값은 FIRST_APPLICABLE · PERMIT · PERMIT입니다.

조건에 쓸 수 있는 것

무엇예어디서
Spring 표준 식hasRole('ADMIN'), hasAuthority('REPORT_READ'), hasAnyAuthority('A','B'), isAuthenticated(), permitAll, denyAllURL · 메서드
요청 정보hasIpAddress('10.0.0.0/8'), httpMethod == 'GET', 주소 패턴의 경로 변수(/api/users/{id}의 #id)URL만
메서드 정보매개변수 이름(#reportId), hasPermission(...), #ownerField메서드만(권한 평가기)
시간T(java.time.LocalTime).now().getHour() < 18URL · 메서드
AI 판정#ai.isAllowed(), #ai.needsChallenge(), #ai.hasActionIn('ALLOW','ESCALATE')URL · 메서드(AI 보안 표현식)
에이전트 · 위임isDelegatedAgent(), delegationAllowsOperation('READ'), agentRequestConfirmed()URL · 메서드(에이전트 식)
  • #ai 식은 요청마다 새로 분석하지 않고, 그 사용자(위임 에이전트는 에이전트 자신)에게 저장된 최신 판정을 읽습니다. 숫자 위험 점수는 식에 나오지 않습니다.
  • 조건은 평가 컨텍스트의 사용자 · 자원 속성을 직접 읽지 못합니다. 평가 컨텍스트(AuthorizationContext)에는 주체 · 자원 · 행동 · 환경과 속성 userRoles · userGroups만 담기고, 식에는 드러나지 않습니다. 데이터베이스 속성 조회 빈(DatabaseAttributePIP)은 등록되지만 평가 흐름에서 부르지 않아 결정에 영향이 없습니다.

안전장치

  • 식 검사: 조건은 저장할 때와 적재할 때 검사합니다. 파싱되지 않거나 금지된 구문이 있으면 저장을 거부합니다. 이미 저장된 정책이 적재할 때 걸리면 그 정책은 늘 거부로 바뀝니다(URL 정책은 대상을 거부로 매핑, 메서드 정책은 효과에 맞춰 거부가 되는 상수). 정책을 빼 버리면 기본 결정(허용)으로 열릴 수 있기 때문입니다.
  • 샌드박스: 저장된 조건은 제한된 환경에서 평가합니다. T(...)는 java.time의 LocalTime · LocalDate · LocalDateTime · DayOfWeek만, new와 @bean 참조는 쓸 수 없고, 리플렉션 · 클래스 로딩 · 프로세스 · 스레드 쪽 메서드와 속성은 거부하며, 속성에 값을 쓸 수 없습니다. hasRole · hasPermission · #ai.* 같은 식은 그대로 됩니다.
  • 위임자 재평가: 정책이 허용한 위임 에이전트 요청은 위임자 자격으로 한 번 더 평가해, 위임자가 할 수 없으면 Contexa 판정 전에 거부합니다(위임자 권한으로 한 번 더 평가).

정책을 바꾸고 반영 확인하기

  1. 바꾸기: 관리 화면 정책 > 정책 센터(Policy Center, /contexa/admin/policy-center)에서 자원을 고르고 권한과 정책을 만들거나, 서버 코드에서 PolicyService로 저장합니다(정책 관리). 보호할 엔드포인트와 메서드는 리소스 스캐너가 찾아 정책 센터에 보여 줍니다.
  2. 반영: 정책을 저장 · 수정 · 삭제 · 승인 · 거절하면 정책 캐시를 비우고 URL 매핑을 다시 만듭니다. 분산 모드(contexa.infrastructure.mode: distributed)에서 Redisson이 있으면 다른 인스턴스에도 다시 적재하라는 신호를 보냅니다. 시스템 설정에서 결합 알고리즘 · 기본 결정을 저장해도 바로 적용되고 같은 신호가 나갑니다.
  3. 미리 보기: 정책 센터의 시뮬레이터는 실제 적용과 같은 정책 선택 · 순서 · 주소 매칭 규칙을 씁니다.
  4. 확인: URL 인가 결과는 허용(AUTHORIZATION_GRANTED)과 거부(AUTHORIZATION_DENIED) 모두 감사 기록에 남습니다. 로그인한 사용자의 거부는 그 세션의 사실로도 기록되어 다음 판정의 맥락이 됩니다. 관리 화면 대시보드는 /contexa/admin/dashboard입니다(관리 콘솔).

관리 화면에서 하는 일은 크게 셋입니다. 정책 센터의 리소스 탭에서 보호 대상을 검토 · 정의하고, 정책 생성 탭에서 대상 · 조건 · 효과를 정해 정책을 만들고, 보안 > 실시간 현황과 감사 기록으로 결과를 봅니다. 처음부터 끝까지의 따라하기는 전체 흐름에 있습니다.

부록: 구성 요소 지도(XACML 용어)

Contexa 인가는 XACML의 다섯 역할로 나뉘어 있습니다. 코드를 읽거나 확장할 때 참고하세요.

XACML 역할하는 일Contexa 구현
PEP(적용 지점)요청 · 호출을 멈추고 결정을 받아 집행URL: CustomDynamicAuthorizationManager(Spring AuthorizationManager, 앱 시작 · 다시 적재 때 URL 정책으로 매처 목록을 만듦). 메서드: AuthorizationManagerMethodInterceptor + ProtectableMethodAuthorizationManager
PDP(결정 지점)조건 식을 평가하고 결과를 합침PolicyExpressionConverter(URL 조건을 SpEL로 정리), ExpressionAuthorizationManagerResolver(isAuthenticated() · 권한 이름 하나는 Spring 기본 매니저로, 나머지는 Contexa 식 처리기로 평가할 매니저를 만듦), CustomWebSecurityExpressionHandler · CustomMethodSecurityExpressionHandler(식의 루트는 AbstractAISecurityExpressionRoot를 확장한 CustomWebSecurityExpressionRoot · CustomMethodSecurityExpressionRoot), PolicyCombiningEvaluator
PAP(관리 지점)정책 저장 · 승인 · 버전 · 분석PolicyService(만들기 · 수정 · 삭제 · 승인 · 거절 · 버전 · 되돌리기 · 충돌 · 영향 · 시뮬레이션), PolicySynchronizationService(역할 권한 변경 때 정책 자동 생성 · 갱신, 비동기), PolicyBuilderService(템플릿 · 시각 모델 · 충돌), BusinessPolicyService(비즈니스 규칙 → 정책), PolicyEnrichmentService(정책 설명 보강)

PolicyTranslator는 판정에 쓰이지 않고, 조건 식을 사람이 읽는 설명과 권한 목록으로 바꿉니다. and · or · not과 비교(같음 · 다름 · 크다 · 크거나 같다 · 작다 · 작거나 같다)를 풀어 쓰고, permitAll · denyAll은 "All access permitted / denied"로 씁니다. 함수 호출은 기본 번역기 다섯 개(인증 · 권한 · 역할 · IP 주소 · 기본)가 설명합니다.
