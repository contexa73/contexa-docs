@Protectable: 메서드 보호

메서드에 @Protectable을 붙이면 CONTEXA가 그 메서드를 실행하기 직전에 호출을 검사합니다. 이 메서드에 연결한 접근 정책이 호출을 허용하는지, 그리고 이 사용자에게 이미 내려진 판정(허용, 추가 인증, 검토 보류, 차단)이 호출을 막는지를 봅니다. 호출이 끝나면 그 호출을 AI 분석(AI가 호출의 위험도를 평가해 판정을 내리는 일)에 보내 다음 판정에 반영합니다. 이 페이지는 붙이는 법, 정책 연결, 호출 하나의 처리 순서, sync 고르기, 거부 응답, 소유자 확인, 속성 9개를 다룹니다.

개요

import io.contexa.contexacommon.annotation.Protectable;
import org.springframework.stereotype.Service;

@Service
public class ReportService {

    // 저장된 판정을 적용하고, 실행 뒤 분석해 다음 호출부터 반영
    @Protectable(category = "REPORT", actions = "READ")
    public Report findReport(Long reportId) {
        ...
    }

    // 되돌릴 수 없는 반출: 이 호출 안에서 판정을 받고 나서 실행
    @Protectable(category = "REPORT", actions = "EXPORT", sensitivity = "CONFIDENTIAL",
            exportSensitive = true, sync = true)
    public ReportFile exportReport(Long reportId) {
        ...
    }
}

예제의 두 메서드는 다르게 처리됩니다. 기본 운영 모드(ENFORCE)에서 findReport를 부르면 CONTEXA가 다음 순서로 처리합니다.

  1. 이 메서드에 연결된 접근 정책을 평가합니다. 정책이 거부하면 메서드를 실행하지 않습니다.
  2. 이 사용자에게 저장된 판정을 확인합니다. 차단, 추가 인증, 검토 보류 판정이 걸려 있으면 메서드를 실행하지 않고 호출을 거부합니다.
  3. 두 검사를 모두 통과하면 메서드를 실행합니다. 사용자의 판정이 아직 없어도 사람의 호출은 실행합니다(AI 에이전트의 호출은 예외입니다. 아래 처리 순서의 ⑥을 봅니다).
  4. 실행이 끝나면 호출 내용을 분석에 보냅니다. 분석 결과는 이 사용자의 다음 호출부터 적용됩니다.

저장된 판정은 AI 분석이 이 사용자에게 마지막으로 내려 저장해 둔 판정입니다.

exportReport는 sync = true를 씁니다. 이 메서드는 실행하기 전에 그 자리에서 분석을 마치고, 결과가 허용(ALLOW)일 때만 실행합니다. 한 번 실행하면 되돌릴 수 없는 반출을 첫 호출부터 막기 위해서입니다. 대신 호출마다 분석이 끝날 때까지 기다립니다.

어노테이션은 contexa-common에 있고, 호출을 가로채 검사하는 일은 contexa-iam의 메서드 인터셉터가 합니다. 다른 보호 방법과 견주면 다음과 같습니다.

방법무엇을 막나규칙이 있는 곳AI 판정
@Protectable메서드 호출데이터베이스의 METHOD 정책과, 사용자에게 저장된 판정저장된 판정을 호출마다 적용합니다(운영 모드에 따름). sync면 그 호출 안에서 새로 판정합니다
@PreAuthorize메서드 호출코드에 적은 식(고정)식에서 #ai를 쓸 수 없습니다(어디서 쓸 수 있나)
URL 정책URL 요청데이터베이스의 URL 정책조건에서 #ai로 저장된 판정을 읽습니다

쓰기 전에

  • CONTEXA가 켜져 있어야 합니다(@EnableAISecurity). 로그인을 CONTEXA가 맡는 방식(CONTEXA_OWNED)과 앱이 맡는 방식(HOST_OWNED, 기본) 모두에서 동작합니다. HOST_OWNED에서는 앱이 로그인 결과를 Spring의 SecurityContext에 넣어 두어야 합니다.
  • 기본 모드에서는 로그인한 호출만 지나갑니다. SHADOW와 ENFORCE 모드(기본은 ENFORCE)에서 로그인 정보가 없거나 익명인 호출은 거부합니다. 이때 던지는 예외는 AccessDeniedException이고, 그 원인(cause)은 AuthenticationCredentialsNotFoundException입니다. 앱의 Spring Security 설정은 이 예외를 로그인하지 않은 요청과 같게 처리합니다(로그인 화면으로 보내거나 401로 답합니다). DISABLED와 OBSERVE 모드(그리고 contexa.security.zerotrust.enabled: false)에서는 CONTEXA가 거부하지 않습니다. 호출은 앱이 만든 그대로 진행되고, 메서드 정책은 보안 컨텍스트에 담긴 사용자(방문자이거나 없음)를 기준으로 평가합니다. 사용자도 요청도 없는 스레드의 호출(@Scheduled, 보안 컨텍스트를 넘기지 않는 @Async)은 판정할 대상이 없어서 모든 모드에서 그대로 실행됩니다.
  • Spring 프록시를 지날 때만 가로챕니다. 다른 빈이 부른 호출은 검사하고, 같은 클래스 안에서 this로 부른 호출은 검사하지 않습니다(Spring AOP의 동작입니다).
  • 저장된 판정은 두 곳에서 적용됩니다. 하나는 요청이 들어올 때 거치는 CONTEXA 필터이고, 다른 하나는 @Protectable 메서드입니다. HOST_OWNED에서는 필터가 앱의 보안 필터 체인 바로 뒤에서 돌므로, 차단, 추가 인증, 검토 보류 판정이 걸린 사용자의 요청은 대부분 메서드에 닿기 전에 필터에서 막힙니다. 앱이 로그인한 사용자를 늦게(MVC 인터셉터나 컨트롤러에서) 정하면 필터는 그 사용자를 보지 못합니다. 그런 요청을 막는 곳은 @Protectable 메서드뿐입니다(소유 방식에 따라 되는 일). CONTEXA는 이런 요청을 처음 발견하면 경고 로그를 한 번 남깁니다.

Zero Trust 운영 모드(contexa.security.zerotrust.mode)는 CONTEXA가 판정을 어디까지 적용할지 정합니다. 접근 정책 평가는 모드와 상관없이 늘 합니다.

운영 모드메서드 정책저장된 판정 적용분석
DISABLED(끔) · OBSERVE(끔과 같음). enabled: false도 같음평가적용하지 않음하지 않음. 같은 요청 안 반복 호출 확인도, 분석에 보내는 일도 없음
SHADOW(관찰 모드)평가기록만 하고 거부하지 않음함(sync는 그 호출 안에서). 결과는 호출에 영향을 주지 않고 판정으로 저장하지 않음
ENFORCE(적용 모드, 기본)평가적용(거부)함

위임자 재평가(처리 순서의 ④)는 ENFORCE에서만 거부하고, 그 밖의 모드에서는 기록만 합니다.

붙이는 곳

  • 메서드나 클래스에 붙입니다(io.contexa.contexacommon.annotation.Protectable, 실행 중에도 읽히는 어노테이션). 클래스에 붙이면 그 빈의 메서드 호출이 모두 검사 대상이 됩니다. CONTEXA는 호출된 메서드, 프록시 뒤 실제 클래스의 그 메서드, 실제 클래스, 메서드를 선언한 클래스 순서로 어노테이션을 찾고 처음 찾은 것을 씁니다.
  • 다만 ownerField는 메서드에 직접 붙인 어노테이션에서만 읽습니다. 클래스에 붙인 어노테이션의 ownerField는 쓰이지 않습니다.
  • 정책 대상 식별자는 패키지.클래스.메서드(매개변수 단순 형식)입니다. 예를 들면 com.example.report.ReportService.exportReport(Long)입니다. 매개변수가 둘 이상이면 쉼표로 잇고 공백은 두지 않습니다. METHOD 정책의 대상에 이 문자열을 씁니다.
  • 거부 응답의 resourceId는 클래스 단순 이름.메서드입니다(예: ReportService.exportReport).
  • 인터셉터는 Spring 메서드 보안의 맨 앞(AuthorizationInterceptorsOrder.FIRST + 1)에서 돌므로 @PreAuthorize보다 먼저 실행됩니다.
  • 클래스 프록시로 만든 빈의 final 메서드는 보호되지 않습니다. Spring이 final 메서드를 가로채지 못하기 때문입니다. 앱이 시작될 때 CONTEXA가 이런 메서드를 경고 로그로 알려 줍니다.

정책 연결

접근 정책은 관리자가 메서드마다 따로 연결합니다. 이 메서드를 대상으로 한 정책이 하나도 없으면(켜져 있고 승인된 정책이 없는 경우도 같습니다) 기본 결정 contexa.policy.missing-method-policy-decision(기본 PERMIT)에 따라 정책 단계를 통과하고, 다음 단계인 저장된 판정 확인으로 넘어갑니다. 정책 없는 보호 메서드를 막으려면 이 값을 DENY로 바꿉니다(맞는 정책이 없을 때).

정책 센터에서 연결하기

  1. 자원 찾기: 리소스 스캐너가 @Protectable이 붙은 메서드를 METHOD 자원으로 모읍니다. 클래스에 붙인 경우에는 그 클래스에 선언된 public 비정적 메서드를 모두 모읍니다. 대상은 스캔 패키지 안의 빈이고 컨트롤러는 뺍니다. 스캔 패키지는 앱 자신의 패키지(Spring Boot 자동 구성이 아는 패키지)와 관리 화면 IAM > 시스템 설정에 적은 패키지(기본 io.contexa.contexaiam.)를 합친 것입니다. 앱의 패키지를 따로 적지 않아도 앱의 메서드가 보입니다. 스캔은 시작할 때 저절로 돌지 않고, 정책 센터에서 "리소스 불러오기"를 누를 때 돕니다(리소스 스캐너).
  2. 권한 만들기: 정책 센터(/contexa/admin/policy-center)의 리소스 탭에서 자원에 이름과 설명을 주고 "권한 생성 & 정책 생성"을 누릅니다. 권한 이름은 METHOD_{클래스}_{메서드}(대문자) 꼴로 자동으로 정해지고(예: METHOD_REPORTSERVICE_EXPORTREPORT), 동작 유형은 EXECUTE입니다.
  3. 정책 만들기: 정책 생성 탭에서 METHOD 대상 정책을 만듭니다. 간편 모드는 역할, 권한, 효과, 대상을 고르고, 수동 모드는 대상과 조건을 직접 쓰며, AI 모드도 있습니다. 저장하면 바로 반영됩니다.

조건 직접 쓰기

수동 모드에서는 정책의 조건을 표현식으로 직접 씁니다. 예는 다음과 같습니다.

hasRole('ADMIN') and #ai.isAllowed()
hasRole('ANALYST') and !#ai.isBlocked() and T(java.time.LocalTime).now().getHour() < 18
isDelegatedAgent() and delegationAllowsOperation('EXPORT') and #ai.isAllowed()
  • 메서드 정책의 조건은 쓴 그대로 SpEL(Spring 표현식 언어)로 평가합니다. 권한 이름만 쓰는 축약(ROLE_ADMIN)은 URL 정책에서만 됩니다.
  • 한 정책에 조건이 여러 개면 and로 묶으므로 모두 참이어야 합니다. 정책이 여럿이면 대상 순서, 우선순위, 정책 ID 순으로 평가하고, URL 정책과 같은 결합 알고리즘으로 결과를 합칩니다(결정 규칙).
  • 조건에서 쓸 수 있는 변수는 메서드 매개변수 이름(#reportId), 저장된 판정을 읽는 #ai, ownerField를 지정했을 때의 #ownerField입니다. CONTEXA는 이 메서드에 적용할 정책 목록(정책 계획)을 #methodPolicyPlan 변수에 담아 평가합니다.
  • 세 번째 줄 같은 에이전트 식은 두 소유 방식 모두에서 위임 도장(에이전트가 누구의 위임으로 어떤 작업과 자원을 맡았는지 담은 값)을 봅니다(에이전트 식).

호출 하나의 처리 순서

메서드를 부르면 CONTEXA는 아래 순서로 호출을 검사합니다. 어느 단계에서든 걸리면 거기서 호출을 거부하고 메서드를 실행하지 않습니다.

  • ③ 정책 평가: 이 메서드에 연결된 정책을 모두 평가해 하나의 결과로 합칩니다. 평가에 쓰는 정책 목록이 정책 계획(#methodPolicyPlan, 정책마다 조건과 효과)입니다. 정책이 하나도 없으면 기본 결정을 씁니다. 데이터베이스에 저장된 조건은 리플렉션 같은 위험한 기능을 쓸 수 없는 샌드박스에서 평가합니다(안전장치). 정책이 거부한 호출은 분석에 보내지 않습니다. 대신 SHADOW · ENFORCE에서는 그 세션과 사용자의 권한 범위에 "거부된 일"로 기록해 두고, 다음 판정이 이 기록을 봅니다.
  • ④ 위임자 재평가: 사람의 위임을 받은 AI 에이전트가 호출하면, 같은 정책을 위임한 사람의 자격으로 한 번 더 평가합니다. 위임한 사람이 할 수 없는 호출이거나 위임한 사람을 알 수 없으면 거부합니다. 에이전트가 위임자보다 많은 일을 하지 못하게 하는 장치입니다(위임자 권한으로 한 번 더 평가).
  • ⑤ 인증 게이트: OSS에는 게이트 구현이 없어서 기본 설치에서는 이 단계를 건너뜁니다. ProtectableResourceCertificationGate 빈을 등록하면, 프롬프트 품질 인증을 받지 않은 자원의 호출을 ENFORCE에서 검토 보류(423)로 거부합니다(확장점).
  • ⑥ sync = false 메서드: 저장된 차단, 추가 인증, 검토 보류가 있으면 실행하기 전에 거부합니다. 사람의 호출은 판정이 없어도 실행하고 뒤에서 분석합니다. 판정 기록이 없는 AI 에이전트 호출은 그 자리에서 판정합니다(protectable.unrecorded-agent-request: DECIDE_IN_PLACE, 판정 없는 요청과 ALLOW 재사용). 사람의 호출도 세션, 접속 주소, 브라우저가 마지막 판정 때와 달라졌고 민감 자원을 부르면 막힐 수 있습니다(아래 거부 응답의 429).
  • 실행 중 예외: 메서드가 실행하다 던진 예외는 보안 거부가 아니라 업무 오류로 봅니다. 분석에는 실행 실패(METHOD_FAILED)로 기록하고, 예외는 호출한 쪽에 그대로 전달됩니다.

sync 고르기

기준은 하나입니다. 한 번 실행하면 되돌릴 수 없는 일(송금, 대량 반출, 권한 변경, 삭제)에는 sync = true를 쓰고, 나머지는 기본값 sync = false로 둡니다.

sync = false(기본)sync = true
언제 판정하나호출이 끝난 뒤에 분석합니다. 판정은 다음 호출부터 적용됩니다이 호출 안에서 분석하고, 그 결과로 실행 여부를 정합니다
실행 전에 막는 것저장된 차단 · 추가 인증 · 검토 보류. 판정이 없는 AI 에이전트 호출은 그 자리에서 판정해 막을 수 있습니다저장된 제한이 있으면 그 제한으로 막고, 없으면 그 자리의 분석 결과가 허용이 아닐 때 막습니다
지연거의 없습니다(판정이 없는 AI 에이전트 호출만 분석이 끝날 때까지 기다립니다)호출마다 분석이 끝날 때까지 기다립니다. 저장된 허용이 있어도 다시 분석합니다
맞는 곳대부분의 조회와 일반 업무되돌릴 수 없는 일: 송금, 대량 반출, 권한 변경, 삭제

sync = true는 부작용이 생기기 전에 호출을 막습니다. 어노테이션 설명은 3초 안에 응답할 수 있는 자원에만 쓰라고 권합니다. 분석이 제한 시간(기본 40초, contexa.security.zerotrust.agent.flight.wait) 안에 끝나지 않으면 ENFORCE에서는 호출을 통과시키지 않습니다. 사람의 호출은 추가 인증을 요구하고(401), AI 에이전트의 호출은 429로 거부합니다. sync = false에서는 사용자의 첫 호출이 판정 없이 실행될 수 있고, 위험은 그다음 호출부터 막힙니다.

소유자 확인(ownerField)

ownerField는 "이 데이터의 주인만 호출할 수 있다"를 확인할 때 씁니다. 예를 들어 프로필 수정 메서드가 로그인한 사용자 본인의 프로필만 고치게 할 수 있습니다. 이 확인은 정책 조건이 hasPermission(...)을 부를 때만 동작합니다. 메서드를 실행하기 전, 정책을 평가하는 도중에 hasPermission의 대상 객체(또는 ID로 읽어 온 엔티티)에서 ownerField로 지정한 필드 값을 읽어 로그인 사용자 이름(Authentication.getName())과 비교합니다. 메서드의 반환값은 보지 않습니다.

@Protectable(ownerField = "username")
public void updateProfile(UserProfile profile) {
    ...
}
// 이 메서드의 METHOD 정책 조건
// hasPermission(#profile, 'USER_UPDATE')
  1. hasPermission 자체가 먼저 참이어야 합니다(권한 평가기). 거짓이면 소유자 확인까지 가지 않고 거부합니다.
  2. 인자가 2개인 호출(hasPermission(#profile, 'USER_UPDATE'))은 그 객체의 필드를 봅니다. 인자가 3개인 호출(hasPermission(#id, 'USER', 'UPDATE'))은 그 도메인 평가기의 저장소 빈에서 findById로 읽은 엔티티의 필드를 봅니다.
  3. 필드는 클래스 계층을 거슬러 올라가며 찾고, 없으면 getter(getUsername())를 부릅니다. 값은 문자열로 바꿔 비교합니다.
  4. ROLE_ADMIN 권한이 있으면 소유자 확인을 건너뜁니다.
  5. 필드, 값, 엔티티를 찾지 못하면 거부합니다. 점으로 이어 쓰는 중첩 경로(owner.id)는 지원하지 않습니다. 대상이 null이면 소유자 확인을 하지 않습니다.
  6. 조건에서는 필드 이름을 #ownerField로 읽을 수 있습니다.
HOST_OWNED에서는 먼저 권한 평가기를 확인합니다. 내장 도메인 평가기가 보는 권한(PermissionAuthority)은 CONTEXA가 로그인을 맡을 때 CONTEXA 사용자 저장소에서 담깁니다. 앱이 로그인을 맡으면 앱의 로그인 정보에는 보통 이 권한이 없습니다. 그러면 hasPermission이 거짓이 되고 소유자 확인도 통과하지 못합니다(hasPermission이 보는 것).

속성 9개

ownerField · verificationRequired · sync는 호출을 검사하는 방식을 바꿉니다. 나머지 여섯 개는 이 메서드가 어떤 자원인지를 CONTEXA에 알려 주는 속성입니다. AI 분석이 이 값을 읽어 판정하고, importance는 요청이 몰릴 때의 처리도 바꿉니다.

속성기본값하는 일
ownerField""소유자 확인에 쓸 필드 또는 getter 이름입니다. 비워 두면 소유자 확인을 하지 않습니다(위)
verificationRequiredtrue프롬프트 품질 인증 게이트(처리 순서의 ⑤)를 적용할지 정합니다. OSS에는 게이트 구현이 없으므로 ProtectableResourceCertificationGate 빈을 등록했을 때만 효과가 있습니다. false로 하면 이 메서드는 게이트를 건너뜁니다. 인증 기능이나 헬스 체크처럼 예외적인 자원에 씁니다
syncfalse이 호출 안에서 판정을 받을지 정합니다. true면 분석이 끝나 허용이 나온 뒤에야 메서드를 실행합니다(sync 고르기)
category""이 메서드가 속한 업무 범주입니다(예: REPORT). AI 분석은 이 값을 사용자의 역할이 다루는 업무 범주, 그리고 AI 에이전트에게 위임된 범위와 견줍니다. CONFIDENTIAL 같은 민감도 단어만 쓰면 범주로 보지 않습니다
sensitivity""자원의 민감도입니다(PUBLIC · INTERNAL · CONFIDENTIAL · RESTRICTED 등). 앱이 요청에 따로 밝힌 민감도가 있으면 그 값이 우선합니다. CONFIDENTIAL과 RESTRICTED 같은 높은 민감도는 민감한 자원으로 다룹니다(아래 importance)
actions{}메서드가 하는 일입니다(READ · EXPORT 등). 값은 READ, WRITE, EXPORT, DELETE, ADMIN, EXECUTE 가운데 하나를 가리켜야 합니다. 하나만 쓰면, 앱이 요청에 다른 값을 밝히지 않는 한 그 요청의 작업 종류가 됩니다. 이 여섯 가지에 들지 않는 값은 시작할 때 경고 로그를 남기고, 작업 종류는 요청의 HTTP 메서드로 정해집니다
importanceUNSPECIFIED이 메서드가 민감한 자원인지 앱이 직접 밝힙니다. 세 값의 차이는 표 아래에 있습니다
privilegedfalse이 메서드가 특권 메서드임을 밝힙니다. true일 때만 의미가 있고 false는 "밝히지 않음"입니다. AI 분석에 넘기는 자원 정보에 특권 표시가 붙습니다
exportSensitivefalse이 메서드가 민감한 데이터를 내보냄을 밝힙니다. true일 때만 의미가 있습니다. 자원 정보에 민감 데이터 반출 표시가 붙습니다. privileged나 이 속성이 true인데 sensitivity를 밝히지 않았으면 민감도를 높음(HIGH)으로 넘깁니다
  • SENSITIVE: 민감한 자원으로 다룹니다. 요청이 이 값을 낮출 수 없습니다. AI 에이전트 요청에서는 자원마다 따로 판정하고(이 자원에서 받은 허용을 다른 자원에 재사용하지 않습니다), 판정 통합을 켠 경우에는 실행 직전에 제한이 새로 걸렸는지 한 번 더 확인합니다. 사람의 호출은 환경이 바뀐 직후 새 환경의 판정이 나오기 전에는 통과하지 못합니다.
  • NON_SENSITIVE: 민감하지 않은 자원으로 밝힙니다. 판정 통합(판정 통합, 기본 꺼짐)을 켜면 AI 에이전트의 읽기 요청 몇 건(기본 3건)이 첫 판정이 나오기 전에 먼저 통과할 수 있습니다. 요청이 더 높은 민감도를 밝히면 SENSITIVE로 올라갑니다.
  • UNSPECIFIED(기본): 밝히지 않습니다. sensitivity에 CONFIDENTIAL이나 RESTRICTED 같은 단어가 있으면 민감한 자원으로 다루고, 없으면 민감한지 모르는 자원으로 다룹니다. 어느 쪽이든 판정 통합이 먼저 통과시키는 후보에는 들지 않습니다.
  • 속성은 이 9개뿐입니다. 옛 문서에 있던 resourceId · resourceUrl · httpMethod · criticality 속성은 코드에 없습니다.
  • 앱이 시작되면 CONTEXA가 모든 빈의 @Protectable 메서드를 자원 정보 등록부(메서드별 자원 정보를 모아 두는 곳)에 올립니다. 자원 ID는 클래스 전체 이름#메서드입니다. 같은 이름으로 오버로드한 메서드는 자원 ID가 같아서 먼저 찾은 메서드의 값이 쓰입니다. category · sensitivity · actions · privileged · exportSensitive · importance는 판정 엔진이 쓰는 자원 정보가 됩니다. 같은 자원 ID로 ResourceContextDescriptor 빈을 두면 어노테이션 값 대신 그 빈의 값이 쓰입니다.

같은 요청 안의 재진입

한 HTTP 요청을 처리하는 동안 같은 보호 메서드가 다시 호출되면(예: 한 요청이 같은 메서드를 두 번 부름) CONTEXA는 분석을 한 번만 합니다. 같은 사용자가 몇 초 안에 반복해서 호출하는 것을 막는 기능은 아닙니다. 확인 키에 서버가 요청마다 새로 만드는 요청 ID가 들어가므로, 서로 다른 요청끼리는 막지 않습니다.

  • 확인 키: 테넌트, 요청 ID, HTTP 메서드, 주소, 클래스 전체 이름.메서드, 운영 모드, 그리고 사용자와 맥락 지문(세션, 클라이언트 IP, User-Agent)입니다.
  • 걸렸을 때: sync = false 메서드는 분석 없이 실행합니다(분석 사건은 보내지 않고 억제 기록만 남깁니다). sync = true 메서드는 ENFORCE에서 503(PENDING_ANALYSIS)으로 거부하고, 다른 모드에서는 실행합니다.
  • 창: contexa.security.zerotrust.protectable.rapid-reentry-window-ms(기본 5000)가 첫 호출 뒤 확인을 유지하는 시간입니다. 0 이하면 끕니다. 로그인, 요청, 맥락 지문이 없으면 확인하지 않습니다.
  • 저장소: 단독 모드는 메모리(창이 끝나면 사라지는 키), 분산 모드는 Redis(SET NX, 키 security:protectable:rapid-reentry: + MD5)를 씁니다. Redis에 오류가 나면 호출을 통과시킵니다. ProtectableRapidReentryRepository 빈으로 바꿀 수 있습니다.

분석 사건과 지표

  • sync = false 메서드는 실행이 끝나면(정상이든 예외든) 분석 사건을 보냅니다. 분석 사건은 이 호출 한 건의 기록입니다. 사건에는 실행 결과(METHOD_COMPLETED · METHOD_FAILED)가 담기고, 분석이 이를 읽어 다음 호출부터 적용할 판정을 만듭니다(판정 엔진).
  • 사건을 보내지 않는 경우: 분석하지 않는 모드(DISABLED · OBSERVE), 같은 요청 안 재진입, 정책 거부(대신 거부 기록을 남깁니다), Zero Trust 거부, sync로 이미 판정한 호출, 판정 통합이 먼저 통과시킨 요청 중 첫 요청을 뺀 나머지입니다. 사건 발행기 빈이 없어도 보내지 않습니다.
  • 지표: 자동 구성은 인터셉터에 지표 수집기(AuthorizationMetrics)를 넣지 않습니다. 직접 넣으면 사건을 보내는 데 걸린 시간과 결정 수를 셉니다.
