@Protectable: 메서드 보호

메서드에 @Protectable을 붙이면 Contexa가 호출 직전에 그 메서드의 정책을 평가하고 저장된 Zero Trust 판정을 적용하며, 호출이 끝나면 다음 판정을 위한 분석 사건을 보냅니다. 이 페이지는 붙이는 법, 정책 연결, 호출 하나의 처리 순서, sync 고르기, 소유자 확인, 속성 9개를 다룹니다.

한눈에 보기

import io.contexa.contexacommon.annotation.Protectable;
import org.springframework.stereotype.Service;

@Service
public class ReportService {

    // 저장된 판정을 적용하고, 실행 뒤 분석해 다음 호출부터 반영
    @Protectable(category = "REPORT", actions = "READ")
    public Report findReport(Long reportId) {
        ...
    }

    // 되돌릴 수 없는 반출: 이 호출 안에서 판정을 받고 나서 실행
    @Protectable(category = "REPORT", actions = "EXPORT", sensitivity = "CONFIDENTIAL",
            exportSensitive = true, sync = true)
    public ReportFile exportReport(Long reportId) {
        ...
    }
}

어노테이션은 contexa-common에 있고, 처리는 contexa-iam의 메서드 인터셉터가 합니다. 다른 보호 방법과의 차이는 아래와 같습니다.

방법무엇을 막나규칙이 있는 곳AI 판정
@Protectable메서드 호출데이터베이스의 METHOD 정책 + 저장된 Zero Trust 판정늘 적용(집행 모드에 따라), sync면 그 호출 안에서 판정
@PreAuthorize메서드 호출코드(정적)CONTEXA_OWNED일 때만 식에서 #ai를 쓸 수 있음(어디서 쓸 수 있나)
URL 정책URL 요청데이터베이스의 URL 정책조건에 #ai

쓰기 전에

  • Contexa가 켜져 있어야 합니다(@EnableAISecurity). 두 인증 소유 방식 모두에서 동작합니다. 앱이 로그인을 맡는 HOST_OWNED(기본)에서는 앱이 로그인 결과를 Spring SecurityContext에 넣어 두어야 합니다.
  • 로그인한 호출만 지나갑니다. 로그인 정보가 없거나 익명이면 AuthenticationCredentialsNotFoundException으로 거부합니다.
  • Spring 프록시를 지날 때만 가로챕니다. 다른 빈에서 부른 호출이 대상이고, 같은 클래스 안에서 this로 부른 호출은 가로채지 않습니다(Spring AOP 동작).
  • 저장된 판정은 두 소유 방식 모두 여기와 요청 시점 필터에서 적용됩니다. HOST_OWNED에서는 요청 시점 필터가 앱 보안 체인 바로 뒤에서 돌므로, 대부분의 요청은 메서드에 닿기 전에 저장된 BLOCK · CHALLENGE · ESCALATE를 만납니다. 앱이 로그인한 사용자를 늦게(MVC 인터셉터나 컨트롤러에서) 정하면 필터가 사용자를 보지 못하므로, 그런 요청을 막는 곳은 @Protectable 메서드입니다(소유 방식에 따라 되는 일).

Zero Trust 집행 모드(contexa.security.zerotrust.mode)에 따라 하는 일이 다릅니다. 정책 평가는 모드와 상관없이 늘 합니다.

집행 모드메서드 정책저장된 판정 적용분석
DISABLED · OBSERVE(또는 enabled: false)평가안 함안 함. 재진입 확인 · 분석 사건도 없음
SHADOW평가기록만함(sync는 그 호출 안에서). 판정은 저장하지 않음
ENFORCE(기본)평가함함

위임자 재평가는 ENFORCE에서만 거부하고, 그 밖의 모드에서는 기록만 합니다.

붙이는 곳

  • 메서드나 클래스에 붙입니다(io.contexa.contexacommon.annotation.Protectable, 실행 중에도 읽히는 어노테이션). 찾는 순서는 호출된 메서드 → 실제 클래스의 그 메서드 → 실제 클래스 → 메서드를 선언한 클래스입니다. 클래스에 붙이면 그 빈의 메서드 호출이 모두 대상이 됩니다.
  • 다만 ownerField는 메서드에 붙인 어노테이션에서만 읽고, 리소스 스캐너도 메서드에 붙은 것만 자원으로 등록합니다.
  • 정책 대상 식별자는 패키지.클래스.메서드(매개변수 단순 형식)입니다. 예: com.example.report.ReportService.exportReport(Long). METHOD 정책의 대상에 이 문자열을 씁니다.
  • 거부 응답의 resourceId는 클래스 단순 이름.메서드(예: ReportService.exportReport)입니다.
  • 인터셉터 순서는 Spring 메서드 보안의 맨 앞(AuthorizationInterceptorsOrder.FIRST + 1)이라 @PreAuthorize보다 먼저 돕니다.

정책 연결

그 메서드를 대상으로 한 실행 가능한 정책이 없으면 기본 결정 contexa.policy.missing-method-policy-decision(기본 PERMIT)에 따라 정책 단계를 지나고, 다음 단계(판정 확인)는 그대로 합니다. 정책 없는 보호 메서드를 막으려면 이 값을 DENY로 바꿉니다(맞는 정책이 없을 때).

정책 센터에서 연결하기

  1. 자원 찾기: 리소스 스캐너가 스캔 패키지 아래 빈(컨트롤러 제외)의 public 메서드에 붙은 @Protectable을 METHOD 자원으로 등록합니다. 스캔 패키지 기본값은 io.contexa.contexaiam.이므로, 관리 화면 IAM > 시스템 설정에서 앱 패키지를 넣어야 앱의 메서드가 보입니다. 스캔은 시작할 때 저절로 돌지 않고, 정책 센터에서 "리소스 불러오기"를 누를 때 돕니다(리소스 스캐너).
  2. 권한 만들기: 정책 센터(/contexa/admin/policy-center) 리소스 탭에서 자원에 이름 · 설명을 주고 "권한 생성 & 정책 생성"을 누릅니다. 권한 이름은 METHOD_{클래스}_{메서드}(대문자, 예: METHOD_REPORTSERVICE_EXPORTREPORT)로 자동으로 정해지고, 동작 유형은 EXECUTE입니다.
  3. 정책 만들기: 정책 생성 탭의 간편 모드(역할 · 권한 · 효과 · 대상), 수동 모드(대상 · 조건 직접), AI 모드로 METHOD 대상 정책을 만듭니다. 저장하면 바로 반영됩니다.

조건 직접 쓰기

hasRole('ADMIN') and #ai.isAllowed()
hasRole('ANALYST') and !#ai.isBlocked() and T(java.time.LocalTime).now().getHour() < 18
isDelegatedAgent() and delegationAllowsOperation('EXPORT') and #ai.isAllowed()
  • 메서드 정책의 조건은 쓴 그대로 SpEL로 평가합니다. 권한 이름만 쓰는 축약(ROLE_ADMIN)은 URL 정책에서만 됩니다.
  • 한 정책의 조건 여러 개는 and로 묶입니다. 정책 사이 순서는 대상 순서 → 우선순위 → 정책 ID이고, 결과는 URL 정책과 같은 결합 알고리즘으로 합칩니다(결정 규칙).
  • 조건에서 쓸 수 있는 변수: 메서드 매개변수 이름(#reportId), #ai, ownerField를 줬으면 #ownerField. Contexa는 이 메서드의 정책 계획을 #methodPolicyPlan 변수에 넣어 평가합니다.
  • 에이전트 식(셋째 줄)은 두 소유 방식 모두에서 위임 도장을 봅니다(에이전트 식).

호출 하나의 처리 순서

  • ③ 정책 평가: 정책 계획(#methodPolicyPlan, 정책마다 조건 · 효과)을 평가하고 결합합니다. 정책이 하나도 없으면 기본 결정입니다. 저장된 조건은 샌드박스에서 평가합니다(안전장치). 정책 거부는 분석하지 않지만, SHADOW · ENFORCE에서는 그 세션과 사용자의 권한 범위에 "거부된 일"로 기록되어 다음 판정이 봅니다.
  • ④ 위임자 재평가: 위임 에이전트의 호출은 같은 정책을 위임자 자격으로 다시 평가해, 위임자가 할 수 없거나 알 수 없는 사람이면 거부합니다(위임자 권한으로 한 번 더 평가).
  • ⑤ 인증 게이트: OSS에는 게이트 구현이 없습니다. ProtectableResourceCertificationGate 빈을 두면, 인증되지 않은 자원 호출을 ENFORCE에서 검토 보류(423)로 거부합니다(확장점).
  • ⑥ 비동기 메서드: 저장된 BLOCK · CHALLENGE · ESCALATE가 있으면 실행 전에 거부합니다. 사람의 호출은 판정이 없어도 실행하고 뒤에서 분석하지만, 판정 기록이 없는 에이전트 호출은 그 자리에서 판정합니다(protectable.unrecorded-agent-request: DECIDE_IN_PLACE, 판정 없는 요청과 ALLOW 재사용).
  • 실행 중 예외는 거부가 아니라 실행 실패로 기록합니다(사건의 실행 결과 METHOD_FAILED).

sync 고르기

지연거의 없음(판정 없는 에이전트 호출은 분석 시간만큼)호출마다 분석 시간만큼. 저장된 ALLOW가 있어도 다시 분석
맞는 곳대부분의 조회 · 일반 업무되돌릴 수 없는 일: 송금, 대량 반출, 권한 변경, 삭제

sync = true는 부작용이 생기기 전에 막습니다. 어노테이션 설명은 3초 안에 응답할 수 있는 자원에만 쓰라고 권합니다. sync = false에서는 첫 호출이 판정 없이 실행될 수 있고, 위험은 그다음 호출부터 막힙니다.

소유자 확인(ownerField)

ownerField는 정책 조건이 hasPermission(...)을 부를 때만 동작합니다. 메서드를 실행하기 전, 정책을 평가하는 도중에 hasPermission의 대상 객체(또는 ID로 읽어 온 엔티티)에서 그 필드를 읽어 로그인 사용자 이름(Authentication.getName())과 비교합니다. 반환값을 보지 않습니다.

@Protectable(ownerField = "username")
public void updateProfile(UserProfile profile) {
    ...
}
// 이 메서드의 METHOD 정책 조건
// hasPermission(#profile, 'USER_UPDATE')
  1. hasPermission 자체가 먼저 참이어야 합니다(권한 평가기). 거짓이면 소유자 확인까지 가지 않습니다.
  2. 인자 2개(hasPermission(#profile, 'USER_UPDATE'))는 그 객체의 필드를, 인자 3개(hasPermission(#id, 'USER', 'UPDATE'))는 그 도메인 평가기의 저장소 빈에서 findById로 읽은 엔티티의 필드를 봅니다.
  3. 필드는 클래스 계층을 거슬러 찾고, 없으면 getter(getUsername())를 부릅니다. 값은 문자열로 바꿔 비교합니다.
  4. ROLE_ADMIN 권한이 있으면 소유자 확인을 건너뜁니다.
  5. 필드 · 값 · 엔티티가 없으면 거부합니다. 점 표기 중첩(owner.id)은 안 됩니다. 대상이 null이면 소유자 확인을 하지 않습니다.
  6. 조건에서 필드 이름은 #ownerField로 읽을 수 있습니다.
HOST_OWNED에서는 먼저 권한 평가기를 확인하세요. 내장 도메인 평가기가 보는 권한(PermissionAuthority)은 Contexa가 로그인을 맡을 때 Contexa 사용자 저장소에서 담깁니다. 앱의 로그인 정보에는 보통 이 권한이 없어 hasPermission이 거짓이 되고, 소유자 확인도 통과하지 못합니다(hasPermission이 보는 것).

같은 요청 안의 재진입

한 HTTP 요청을 처리하는 동안 같은 보호 메서드에 다시 들어오면(예: 한 요청이 같은 메서드를 두 번 부름) 분석을 한 번만 합니다. 같은 사용자가 몇 초 안에 반복 호출하는 것을 막는 기능은 아닙니다. 판단 키에 서버가 요청마다 새로 만드는 요청 ID가 들어가므로, 서로 다른 요청끼리는 막지 않습니다.

  • 키: 테넌트 · 요청 ID · HTTP 메서드 · 주소 · 클래스 전체 이름.메서드 · 집행 모드, 그리고 사용자와 맥락 지문(세션 · 클라이언트 IP · User-Agent).
  • 걸리면: 비동기 메서드는 분석 없이 실행하고(사건 없음, 억제 기록만 남김), sync 메서드는 ENFORCE에서 503(PENDING_ANALYSIS)으로 거부합니다. 다른 모드에서는 실행합니다.
  • 창: contexa.security.zerotrust.protectable.rapid-reentry-window-ms(기본 5000). 0 이하면 끕니다. 로그인 · 요청 · 맥락 지문이 없으면 확인하지 않습니다.
  • 저장소: 단독 모드는 메모리(창이 끝나면 사라지는 키), 분산 모드는 Redis(SET NX, 키 security:protectable:rapid-reentry: + MD5). Redis 오류면 통과시킵니다. ProtectableRapidReentryRepository 빈으로 바꿀 수 있습니다.

분석 사건과 지표

  • 비동기 메서드는 실행이 끝나면(정상이든 예외든) 인가 사건을 발행합니다. 사건에는 실행 결과(METHOD_COMPLETED · METHOD_FAILED)가 담기고, 비동기 판정이 이를 분석해 다음 호출부터 적용합니다(판정 엔진).
  • 발행하지 않는 경우: 분석하지 않는 모드(DISABLED · OBSERVE), 같은 요청 안 재진입, 정책 거부(대신 거부 기록), Zero Trust 거부, sync로 이미 판정한 호출, 판정 통합에서 먼저 통과시킨 요청 중 첫 요청을 뺀 나머지. 사건 발행기 빈이 없어도 발행하지 않습니다.
  • 지표: 자동 구성은 인터셉터에 지표 수집기(AuthorizationMetrics)를 넣지 않습니다. 직접 넣으면 사건 발행에 걸린 시간과 결정 수를 셉니다.
