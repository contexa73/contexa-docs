URL 접근 정책(동적 URL 인가)

URL 요청의 허용 · 거부를 데이터베이스에 저장한 정책으로 정합니다. 이 페이지는 URL 정책을 요청에 연결하는 방법, 첫 정책을 만드는 방법, 요청 하나가 결정되는 순서, 조건 쓰는 법, 바꾼 정책이 반영되는 방식을 다룹니다.

무엇을 하나

Spring Security의 정적 매처(requestMatchers(...).hasRole(...))는 코드에 고정됩니다. CustomDynamicAuthorizationManager는 Spring의 AuthorizationManager로서, 앱이 시작될 때 데이터베이스의 URL 정책을 읽어 주소 매처 목록을 만들고 요청마다 그 목록으로 결정합니다. 관리 화면 정책 센터(Policy Center)에서 정책을 바꾸면 다시 배포하지 않아도 목록이 다시 만들어집니다. AI가 만든 정책은 사람이 승인한 뒤에야 목록에 들어갑니다.

켜기: 요청에 연결하기

URL 정책은 매니저가 보안 필터 체인의 인가 단계에 연결되어 있을 때만 요청에 걸립니다. contexa-iam이 있으면 매니저 빈은 늘 만들어지지만, 연결은 인증 소유 방식에 따라 다릅니다.

구성URL 정책 연결
@EnableAISecurity(mode = SecurityMode.FULL)(CONTEXA_OWNED)Contexa 체인이 /contexa/css/** · /contexa/js/** · /images/** · /favicon.ico만 허용하고 나머지 모든 요청을 anyRequest().access(customDynamicAuthorizationManager)로 연결합니다. 바꾸려면 PlatformConfig 빈을 직접 정의합니다(인증 DSL)
기본 @EnableAISecurity(HOST_OWNED)Contexa가 체인을 만들지 않습니다. 앱 체인에 아래처럼 직접 연결합니다
SANDBOX + contexa.bridge.ownership: CONTEXA_OWNED연결하지 않습니다. Contexa 체인은 관리 영역만 ADMIN으로 막고 나머지는 허용합니다
 
import io.contexa.contexaiam.security.xacml.pep.CustomDynamicAuthorizationManager;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class AppSecurityConfig {

    @Bean
    SecurityFilterChain appChain(HttpSecurity http,
                                 CustomDynamicAuthorizationManager contexaUrlPolicies) throws Exception {
        http.authorizeHttpRequests(auth -> auth
                        .requestMatchers("/css/**", "/js/**", "/images/**", "/favicon.ico").permitAll()
                        .anyRequest().access(contexaUrlPolicies))
                .formLogin(Customizer.withDefaults());
        return http.build();
    }
}
HOST_OWNED에서 URL 정책이 보지 못하는 것. 인증 브리지 필터는 앱 보안 체인 바로 뒤(체인 순서 + 1)의 서블릿 필터라서 앱의 보안 체인이 끝난 뒤에 돕니다. 그래서 앱 체인에 연결한 URL 정책은 위임 도장을 보지 못합니다. 에이전트 식은 사람 요청처럼 답하고, 위임자 재평가도 일어나지 않습니다. 에이전트 조건은 @Protectable 메서드 정책에 두세요.

정적 규칙과 함께 쓰기

  • Spring Security는 매처를 위에서부터 보고 처음 맞는 규칙을 씁니다. 정적 requestMatchers는 anyRequest() 앞에 둡니다.
  • 정적 매처에 걸린 요청은 URL 정책 매니저를 부르지 않습니다. permitAll()로 연 주소를 노리는 데이터베이스 정책은 조용히 무시되므로, 같은 주소를 정적 규칙과 정책에 함께 두지 마세요.
  • 정적으로 허용된 요청은 URL 정책을 지나지 않으므로 인가 감사 기록에도 남지 않습니다.

.anyRequest().access(customDynamicAuthorizationManager)		대부분의 앱. FULL 기본 체인과 같은 모양정적 자원은 정책 조회가 없어 빠름

첫 URL 정책 만들기

  1. 관리 화면 정책 > 정책 센터(/contexa/admin/policy-center)를 엽니다.
  2. 리소스 탭에서 URL 자원을 고르고 "권한 생성 & 정책 생성"(Create Permission & Policy)을 누르거나, 정책 생성 탭에서 간편 · 수동 · AI 모드로 만듭니다. 자원이 보이지 않으면 리소스 스캐너의 스캔 패키지를 확인하세요.
  3. 이름, 효과(ALLOW · DENY), 우선순위(숫자가 작을수록 먼저), URL 패턴(/api/reports/**), HTTP 메서드(GET 등, 모든 메서드는 ANY), 조건(hasRole('MANAGER'))을 정합니다.
  4. 저장하면 바로 매핑이 다시 만들어집니다. 다시 시작할 필요가 없습니다. 손으로 만든 정책은 출처 MANUAL, 승인 상태 NOT_REQUIRED라 곧바로 실행됩니다.
  5. 정책 목록 · 시뮬레이터 · 영향 분석으로 확인합니다. 작성 · 검사 · 영향 · 시뮬레이션은 모두 정책 센터에 있습니다(정책 관리).

칸뜻

priority숫자가 작을수록 먼저. 같으면 저장소에서 읽은 순서

주소 패턴은 Spring PathPattern 문법입니다. /api/reports/**처럼 **는 패턴 끝에만 쓰고, /api/users/{id}처럼 경로 변수를 쓰면 조건에서 #id로 읽을 수 있습니다.

서버 코드에서 만들 때는 PolicyService를 씁니다. 저장하면 화면에서 만든 것과 똑같이 바로 반영됩니다.

import io.contexa.contexaiam.domain.dto.ConditionDto;
import io.contexa.contexaiam.domain.dto.PolicyDto;
import io.contexa.contexaiam.domain.dto.RuleDto;
import io.contexa.contexaiam.domain.dto.TargetDto;
import io.contexa.contexaiam.domain.entity.policy.Policy;
import io.contexa.contexaiam.domain.entity.policy.PolicyCondition;
import io.contexa.contexaiam.security.xacml.pap.service.PolicyService;
import java.util.List;
import org.springframework.stereotype.Service;

@Service
public class ReportPolicySetup {

    private final PolicyService policyService;

    public ReportPolicySetup(PolicyService policyService) {
        this.policyService = policyService;
    }

    public void createReportPolicy() {
        PolicyDto policy = PolicyDto.builder()
                .name("REPORTS_FOR_MANAGERS")
                .description("Managers read reports while the AI decision allows them")
                .effect(Policy.Effect.ALLOW)
                .priority(100)
                .targets(List.of(TargetDto.builder()
                        .targetType("URL")
                        .targetIdentifier("/api/reports/**")
                        .httpMethod("GET")
                        .build()))
                .rules(List.of(RuleDto.builder()
                        .description("manager and AI allow")
                        .conditions(List.of(ConditionDto.builder()
                                .expression("hasRole('MANAGER') and #ai.isAllowed()")
                                .authorizationPhase(PolicyCondition.AuthorizationPhase.PRE_AUTHORIZE)
                                .build()))
                        .build()))
                .build();
        policyService.createPolicy(policy);
    }
}
"그리고"는 한 조건 안에 씁니다. URL 정책은 조건 여러 개를 or로 묶습니다. hasRole('MANAGER')와 #ai.isAllowed()를 조건 두 개로 나눠 넣으면 (hasRole('MANAGER')) or (#ai.isAllowed())가 되어 둘 중 하나만 맞아도 허용됩니다.

요청 하나가 결정되는 순서

  • 맞는 ALLOW 정책의 조건이 거짓이어도 거부입니다. 명시적인 DENY 정책만 막는 것이 아닙니다. 효과 · 결합 규칙 전체는 인가 개요 > 결정 규칙에 있습니다.
  • 정책이 없는 주소는 기본으로 허용됩니다. 기본 거부로 바꾸려면 contexa.policy.no-matching-url-policy-decision을 DENY로 하거나 시스템 설정 화면에서 저장합니다(설정). /** 같은 전체 DENY 정책으로 대신하기는 어렵습니다. 같은 주소이거나 패턴으로 겹치는 주소에 효과가 반대인 활성 정책이 있으면 정책 저장이 충돌로 거부되기 때문입니다(HTTP 메서드가 서로 다르면 겹치지 않은 것으로 봅니다).
  • 적재 때 검사에 걸린 정책은 그 대상들을 늘 거부합니다. 오류 로그에 정책 ID와 이유가 남습니다.
  • 감사 기록(AUTHORIZATION_GRANTED · AUTHORIZATION_DENIED)에는 출처 IAM, 사용자, 클라이언트 IP, 세션 ID, User-Agent, 요청 주소, HTTP 메서드, 결정(ALLOW · DENY), 결과(GRANTED · DENIED)가 담깁니다.
  • URL 정책 결정은 Zero Trust 집행 모드와 상관없이 늘 적용됩니다. 집행 모드가 바꾸는 것은 위임자 재평가의 거부 여부뿐입니다(아래).

조건 쓰기

저장된 조건이 식이 되는 규칙

URL 정책은 적재할 때 저장된 조건들을 식 하나로 정리합니다(PolicyExpressionConverter). 메서드 정책은 이 정리를 하지 않고 조건을 그대로 and로 묶습니다.

저장된 조건만들어지는 식
없음permitAll. 효과가 ALLOW면 늘 허용, DENY면 늘 거부
하나그대로. permitAll · denyAll · isAuthenticated()도 그대로
권한 이름만(ROLE_ADMIN)hasAuthority('ROLE_ADMIN')
여럿이고 모두 권한 이름hasAnyAuthority('ROLE_ADMIN','ROLE_AUDITOR')
여럿이고 섞임(조건1) or (조건2)
식 안의 대문자 권한 이름그 이름만 감쌈: ROLE_ADMIN or hasRole('AUDITOR') → hasAuthority('ROLE_ADMIN') or hasRole('AUDITOR')
hasPermission(...)이 든 조건그 부분을 지움(객체 권한은 URL에서 판단할 수 없음). 지운 뒤 비면 ALLOW는 늘 거부(denyAll), DENY는 늘 적용(permitAll)

조건 예

hasRole('MANAGER') and #ai.isAllowed()
ROLE_ADMIN or hasRole('AUDITOR')
hasIpAddress('10.0.0.0/8') and T(java.time.LocalTime).now().getHour() < 18
httpMethod == 'GET' and !#ai.isBlocked()
isDelegatedAgent() and delegationAllowsOperation('READ')
  • 쓸 수 있는 식 전체는 인가 개요 > 조건에 쓸 수 있는 것에 있습니다. #ai 판정 식과 에이전트 식의 뜻은 AI 보안 표현식에 있습니다.
  • 식은 #ai. 없이도 부를 수 있습니다(isAllowed() = #ai.isAllowed()). 에이전트 식은 보통 접두사 없이 씁니다.
  • 마지막 줄 같은 에이전트 조건은 URL 단계에서 위임 도장이 보이는 CONTEXA_OWNED에서만 의미가 있습니다(켜기).

사람을 대신하는 에이전트

위임 에이전트는 위임자가 할 수 있는 일보다 더 할 수 없습니다. URL 정책이 허용한 위임 에이전트 요청은 위임자 자격으로 정책을 한 번 더 평가하고, 위임자가 할 수 없거나 알 수 없는 사람이면 Contexa 판정 전에 거부합니다. 결과는 판정 사건에 delegatorAuthority로 남습니다.

결과뜻요청
CARRIED요청이 위임자 본인으로 인증됨(토큰 교환으로 받은 위임자 토큰). 요청 자체의 평가가 위임자의 평가그대로
PERMITTED위임자도 할 수 있음그대로
DENIED위임자는 할 수 없음거부
UNKNOWN위임자를 알 수 없음(계정 없음 · 비활성 · 잠김 · 읽기 실패)거부
UNAVAILABLE위임자 정보를 읽을 곳이 없어 확인하지 않음그대로
  • 위임자 권한은 앱의 UserDetailsService에서 읽습니다. 비활성 · 잠긴 계정은 아무것도 위임하지 못합니다. 다른 곳(디렉터리 등)에서 읽으려면 DelegatorAuthoritySource 빈을 둡니다.
  • 집행 모드가 ENFORCE가 아니면(SHADOW · OBSERVE · DISABLED) 거부하지 않고 기록만 합니다.
  • 사람의 요청과 단독 에이전트의 요청은 재평가하지 않습니다.
  • URL 정책의 재평가는 Contexa 체인(CONTEXA_OWNED)에서 일어납니다. 메서드 정책의 재평가는 두 소유 방식 모두에서 일어납니다(에이전트 보안).

바꾸고 반영 확인하기

  • 앱 시작: 애플리케이션 컨텍스트가 준비되면(ContextRefreshedEvent) 매핑 목록을 처음 만듭니다.
  • 정책 저장: 정책 센터 저장, PolicyService의 만들기 · 수정 · 삭제 · 승인 · 거절 · 되돌리기, 비즈니스 규칙 경로는 모두 정책 캐시(URL · 메서드)를 비우고 매핑 목록을 다시 만듭니다. 따로 부를 공개 REST API는 없습니다.
  • 시스템 설정 저장: 결합 알고리즘과 기본 결정을 바꾸면 이 인스턴스에 바로 적용하고 목록을 다시 만듭니다.
  • 여러 인스턴스: 분산 모드(contexa.infrastructure.mode: distributed)에서 Redisson이 있으면 PolicyReloadBroadcaster가 Redis 토픽 contexa:policy:reload-signal로 다른 인스턴스에 알리고, 받은 인스턴스는 저장된 시스템 설정을 다시 읽은 뒤 목록을 다시 만듭니다. 단독 모드는 그 인스턴스만 바뀝니다.
  • 미리 보기: 정책 센터 시뮬레이터는 실제 적용과 같은 정책 선택 · 순서 · 주소 매칭 규칙을 씁니다.

이전 인가 개요 다음 @Protectable: 메서드 보호
