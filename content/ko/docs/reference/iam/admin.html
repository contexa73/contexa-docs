관리 콘솔

관리 콘솔(/contexa/admin/**)에서 정책 · 권한 · 사용자 · 보안 판정 · 에이전트 · 프롬프트 품질을 다룹니다. 이 페이지는 콘솔을 어떻게 보호하고 들어가는지, 메뉴마다 무엇을 하는지, 처음에 무엇부터 하는지를 설명합니다.

기본 HOST_OWNED에서는 Contexa가 관리 콘솔을 보호하지 않습니다. 이 모드에서 Contexa는 보안 체인을 만들지 않으므로 /contexa/admin/**에 URL 규칙이 없고, 메서드 보안(@EnableMethodSecurity)도 켜지 않으므로 컨트롤러에 붙은 @PreAuthorize("hasRole('ADMIN')")도 걸리지 않습니다. 앱의 보안 체인에서 /contexa/admin/**를 관리자만 쓰도록 막고, 앱에서 메서드 보안을 켜세요(HOST_OWNED에서 보호하기). 앱 체인이 모든 요청을 permitAll로 두면 관리 화면과 API가 그대로 열립니다.

들어가기와 보호

콘솔이 누구에게 열리는지는 인증 소유권(contexa.bridge.ownership)과 보안 모드에 따라 다릅니다.

구성/contexa/admin/** URL 보호컨트롤러의 @PreAuthorize로그인
@EnableAISecurity(mode = SecurityMode.FULL)(CONTEXA_OWNED)Contexa 체인이 모든 요청을 동적 인가 매니저로 보내고, 시드 정책이 막습니다: /contexa/admin/login 공개(우선순위 10), 차단 해제 요청 · 분석 대기 경로는 로그인한 사용자(20), 나머지 /contexa/admin/**는 hasRole('ADMIN')(100)걸림(Contexa가 메서드 보안을 켬)Contexa 로그인 /contexa/admin/login
SANDBOX 모드에 contexa.bridge.ownership: CONTEXA_OWNED를 직접 준 경우Contexa 체인의 URL 규칙: 로그인 화면 공개, 차단 해제 요청 · 분석 대기 경로는 로그인한 사용자, 나머지 /contexa/admin/**는 ADMIN, 그 밖의 요청은 모두 허용걸림Contexa 로그인
HOST_OWNED(기본, SANDBOX)없음. 앱 체인이 막아야 합니다앱이 메서드 보안을 켤 때만 걸림앱의 로그인. Contexa는 로그인 처리를 만들지 않고 앱의 인증을 그대로 씁니다

차단 해제 요청 · 분석 대기 경로는 /contexa/admin/api/aiam/zero-trust/**와 /contexa/admin/api/aiam/sse/zero-trust/**입니다. 차단된 사용자가 스스로 해제를 요청하는 데 쓰므로 관리자가 아니어도 로그인만 되어 있으면 엽니다. 관리 컨트롤러는 @PreAuthorize("hasRole('ADMIN')")를 달고 있어 메서드 보안이 켜지면 ROLE_ADMIN 권한이 필요합니다.

HOST_OWNED에서 보호하기

앱의 보안 설정에서 Contexa가 CONTEXA_OWNED일 때 쓰는 규칙과 같은 모양으로 막고, 메서드 보안을 켭니다.

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.method.configuration.EnableMethodSecurity;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
@EnableMethodSecurity
public class AppSecurityConfig {

    @Bean
    SecurityFilterChain appSecurityFilterChain(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth -> auth
                        .requestMatchers("/contexa/admin/api/aiam/zero-trust/**",
                                "/contexa/admin/api/aiam/sse/zero-trust/**").authenticated()
                        .requestMatchers("/contexa/admin/**").hasRole("ADMIN")
                        .anyRequest().authenticated())
                .formLogin(Customizer.withDefaults());
        return http.build();
    }
}

앱 체인의 나머지 요청을 .anyRequest().access(customDynamicAuthorizationManager)로 Contexa 정책에 맡기면, 시드 정책이 /contexa/admin/**를 위 표의 FULL과 같은 모양으로 막습니다(시드가 켜져 있고 그 정책을 지우지 않았을 때). 연결 방법은 동적 인가 전체 흐름에 있습니다.

IP 관리의 규칙도 보조로 쓸 수 있습니다. HOST_OWNED에서는 /contexa/* 경로에만, CONTEXA_OWNED에서는 모든 경로에 적용됩니다(IP와 세션). 이것은 인증을 대신하지 않습니다.

메뉴

  • 메뉴는 Contexa DB의 admin_menu 표에 있습니다. 기동할 때 시드 파일 db/data-menu.sql이 기본 메뉴를 넣거나 고치고, 같은 data_page 값의 중복 행은 하나로 합칩니다. 화면은 AdminMenuService가 이 표에서 만든 menuTree로 그립니다. 템플릿에 따로 박아 둔 메뉴는 없습니다.
  • 메뉴 종류 CORE는 늘 보입니다. ENTERPRISE는 contexa.enterprise.enabled: true일 때, SAAS는 그것과 contexa.saas.enabled: true가 모두 켜졌을 때만 보입니다.
  • 메뉴에 역할(admin_menu_role)을 걸면 그 역할이 있는 사람에게만 보이고, 걸지 않으면 모두에게 보입니다. 메뉴는 "메뉴 관리" 화면이나 시드 파일로 더합니다.

권한 센터

경로 /contexa/admin/access-center. 사용자 → 그룹 → 역할 → 권한의 연결을 탭 네 개(사용자 · 그룹 · 역할 · 현황)에서 다룹니다. 사용자 상세에는 소속 그룹, 직접 받은 역할, 그룹에서 물려받은 역할, 실제로 갖는 권한이 함께 보입니다. 현황 탭은 사용자 · 그룹 · 역할 · 권한 수와 사용자 → 그룹 → 역할 → 권한 연결 구조 그림을 보여 줍니다.

역할에 이름이 READ · WRITE · UPDATE · DELETE인 권한이 연결돼 있으면 CRUD 권한으로 봅니다. 사용자나 그룹에 역할을 줄 때 그 가운데 일부만 고를 수 있고, READ는 늘 들어갑니다. 고른 값은 사용자 · 역할별(UserRolePermission), 그룹 · 역할별(GroupRolePermission)로 저장됩니다.

사용자 · 그룹 · 역할 · 권한 · 역할 계층

사용자(/contexa/admin/users), 그룹(/contexa/admin/groups), 역할(/contexa/admin/roles), 권한(/contexa/admin/permissions)을 만들고 고치고 지웁니다. 사용자는 그룹 소속과 직접 받은 역할로 권한을 얻습니다.

역할 계층(/contexa/admin/role-hierarchies)은 상위 역할이 하위 역할의 권한을 물려받게 합니다. 기본 시드의 계층은 ROLE_ADMIN > ROLE_DEVELOPER > ROLE_INFRA > ROLE_USER입니다. 활성 계층은 기동할 때와 바꿀 때마다 Spring Security RoleHierarchy에 적용되고, URL · 메서드 정책의 식 평가에도 쓰입니다.

IP와 세션

  • IP 관리(/contexa/admin/ip-management): ALLOW · DENY 규칙을 IPv4 · IPv6 · CIDR로 만들고, 만료 시각 · 켜고 끄기 · CSV 내보내기를 씁니다. DENY에 걸린 IP는 403입니다. 켜진 ALLOW 규칙이 하나라도 있으면 허용 목록 방식이 되어, 목록에 없는 IP도 403입니다. 이 필터는 HOST_OWNED에서 /contexa/* 경로에만, CONTEXA_OWNED에서 모든 경로에 걸리고, 정적 파일은 건너뜁니다.
  • 세션 관리(/contexa/admin/session-management): 활성 세션을 검색하고(세션 ID · 사용자 · IP · User Agent · 로그인 시각 · 마지막 활동), 세션 하나(POST /{sessionId}/invalidate)나 사용자의 모든 세션(POST /user/{userId}/invalidate-all)을 끊습니다. CSV 내보내기가 있습니다.

AI 정책 생성

메서드 · 경로하는 일
POST /contexa/admin/api/ai/policies/generate/stream자연어 요구로 정책 초안을 SSE 스트리밍으로 만듦
POST /contexa/admin/api/ai/policies/generate같은 일을 한 번에 돌려줌
POST /contexa/admin/api/policies/build-from-business-rule확인한 초안을 정책으로 저장
  1. 관리자가 요구를 글로 씁니다(예: "개발자는 근무 시간에 /api/**에 접근할 수 있다").
  2. AdvancedPolicyGenerationLab이 쓸 수 있는 역할 · 권한 · 조건 템플릿과 기존 정책 · 역할 계층을 요청에 더하고, PolicyGenerationContextRetriever가 벡터 저장소에서 비슷한 정책을 찾습니다.
  3. AI가 PolicyResponse(정책 초안, 역할 · 권한 · 조건의 ID → 이름 표, 이유)를 돌려줍니다.
  4. 화면이 쓸 수 있는 항목과 맞춰 보고 미리 보여 줍니다.
  5. 저장하면 BusinessPolicyService가 정책 · 대상 · 규칙 · 조건을 만들고 다시 읽습니다. 출처가 AI_GENERATED라서 승인 대기로 저장되고, 승인하기 전에는 평가되지 않습니다(AI 초안 승인).
