관리 콘솔

관리 콘솔(/contexa/admin/**)에서 정책 · 권한 · 사용자 · 보안 판정 · 에이전트 · 프롬프트 품질을 다룹니다. 이 페이지는 콘솔을 어떻게 보호하고 들어가는지, 메뉴마다 무엇을 하는지, 처음에 무엇부터 하는지를 설명합니다.

관리 콘솔은 두 소유 방식 모두 Contexa가 보호하고, 들어가려면 Contexa 관리자 계정이 있어야 합니다. 기본 HOST_OWNED에서는 /contexa/admin/**만 맡는 Contexa 자기 체인이 /contexa/admin/login에서 Contexa 관리자를 로그인시킵니다. 앱 사용자는 들어올 수 없고, 앱 체인이 모든 요청을 permitAll로 두더라도 앱이 이 경로를 따로 막을 필요는 없습니다(HOST_OWNED에서 보호하기).

들어가기와 보호

콘솔이 누구에게 열리는지는 인증 소유권(contexa.bridge.ownership)과 보안 모드에 따라 다릅니다.

구성/contexa/admin/** URL 보호컨트롤러의 @PreAuthorize로그인
@EnableAISecurity(mode = SecurityMode.FULL)(CONTEXA_OWNED)Contexa 체인이 모든 요청을 동적 인가 매니저로 보내고, 시드 정책이 막습니다: /contexa/admin/login 공개(우선순위 10), 차단 해제 요청 · 분석 대기 경로는 로그인한 사용자(20), 나머지 /contexa/admin/**는 hasRole('ADMIN')(100)걸림(Contexa 자신의 클래스에 거는 @PreAuthorize 처리가 관리 컨트롤러에 적용됨)/contexa/admin/login은 Contexa 로그인 화면 /mfa/login으로 이동합니다. 비밀번호 뒤에 2단계(메일 코드 또는 패스키)가 필수이므로 메일 서버가 필요합니다
SANDBOX 모드에 contexa.bridge.ownership: CONTEXA_OWNED를 직접 준 경우Contexa 체인의 URL 규칙: 로그인 화면 공개, 차단 해제 요청 · 분석 대기 경로는 로그인한 사용자, 나머지 /contexa/admin/**는 ADMIN, 그 밖의 요청은 모두 허용걸림Contexa 로그인
HOST_OWNED(기본, SANDBOX)/contexa/admin/**만 맡는 Contexa 콘솔 체인: /contexa/admin/login은 공개, 나머지 경로는 콘솔에 로그인한 관리자(hasRole('ADMIN')). 익명의 /contexa/admin/api/** 호출은 401, 화면은 콘솔 로그인으로앱이 메서드 보안을 켤 때만 걸림(선택하는 추가 검사)Contexa 관리자 로그인 /contexa/admin/login, Contexa 사용자 저장소 사용. 앱의 로그인과 사용자는 콘솔에 쓰이지 않습니다

차단 해제 요청 · 분석 대기 경로는 /contexa/admin/api/aiam/zero-trust/**와 /contexa/admin/api/aiam/sse/zero-trust/**입니다. Contexa 체인(표의 위 두 줄)에서는 차단된 사용자가 스스로 해제를 요청하는 데 쓰므로 관리자가 아니어도 로그인만 되어 있으면 엽니다. 관리 컨트롤러는 @PreAuthorize("hasRole('ADMIN')")를 달고 있어 메서드 보안이 켜지면 ROLE_ADMIN 권한이 필요합니다.

HOST_OWNED에서 보호하기

앱의 보안 설정에 더할 것은 없습니다. Contexa가 /contexa/admin과 /contexa/admin/**만 맡는 자기 체인(contexaAdminConsoleSecurityFilterChain, 순서 Ordered.HIGHEST_PRECEDENCE + 10)을 등록합니다. 이 체인은 Spring Boot 보안 자동 구성 뒤에 등록되므로, 자기 체인이 없는 앱에는 Spring Boot 기본 체인이 그대로 생깁니다. 관리자는 Contexa 사용자 저장소(Contexa DB에서 ADMIN 역할을 가진 사용자)로 /contexa/admin/login에서 로그인하고, 로그인 양식도 같은 주소로 보냅니다. 콘솔 로그인 정보 · CSRF 토큰 · 저장된 요청은 앱과 다른 세션 키에 두므로, 한 브라우저에서 관리자와 앱 사용자가 서로 덮어쓰지 않습니다.

콘솔에 들어가려면 Contexa 관리자 계정이 있어야 하고, 앱 사용자 계정으로는 들어갈 수 없습니다. 첫 관리자는 아래 설정으로 처음 기동할 때 Contexa가 만듭니다. 비밀번호 설정이 없으면 만들지 않고, 같은 사용자 이름이나 이메일을 가진 사용자가 이미 있으면 그 사용자를 바꾸지 않습니다(첫 기동).

contexa:
  iam:
    seed:
      admin:
        username: admin                       # 기본값 admin
        email: admin@example.com              # 기본값 admin@localhost
        password: ${CONTEXA_ADMIN_PASSWORD}   # 예: CONTEXA_ADMIN_PASSWORD=Change-Me-2026

Change-Me-2026은 예시 값일 뿐입니다. 실제 비밀번호는 환경 변수(또는 비밀 저장소)로 넣고, 커밋하는 파일에는 적지 마세요.

콘솔 머리글의 로그아웃 버튼은 /contexa/admin/logout으로 보냅니다. 콘솔 로그인만 끝내고 세션은 그대로 두므로, 같은 브라우저의 앱 로그인은 유지됩니다.

콘솔 로그인은 CONTEXA_OWNED와 똑같이 관리자 계정에 집계됩니다. 실패 횟수 · 잠금 · 주소 제한이 비밀번호 정책을 따릅니다. 앱 자체의 로그인은 Contexa 계정에 집계되지 않습니다.

/contexa/admin/api/aiam/ 아래의 두 경로 묶음은 관리자가 아니라 앱의 로그인한 사용자 몫입니다. 차단된 사용자의 해제 요청(zero-trust/initiate-block-mfa, zero-trust/unblock-request)과 분석 대기 화면의 갱신(sse/zero-trust/**)입니다. 콘솔 체인은 이 경로를 맡지 않고, 다른 사용자용 화면처럼 로그인한 사용자에게만 답합니다.

메서드 보안은 선택입니다. 앱이 켜면(@EnableMethodSecurity) 콘솔 컨트롤러의 @PreAuthorize("hasRole('ADMIN')") 검사가 한 겹 더해집니다. 콘솔 체인이 /contexa/admin/**를 맡으므로, 앱 체인과 거기에 연결한 URL 정책은 이 경로를 보지 않습니다.

IP 관리의 규칙도 보조로 쓸 수 있습니다. HOST_OWNED에서는 /contexa/* 경로에만, CONTEXA_OWNED에서는 모든 경로에 적용됩니다(IP와 세션). 이것은 인증을 대신하지 않습니다.

메뉴

  • 메뉴는 Contexa DB의 ctxa_admin_menu 표에 있습니다. 기동할 때 시드 파일 db/data-menu.sql이 기본 메뉴를 넣거나 고치고, 같은 data_page 값의 중복 행은 하나로 합칩니다. 화면은 AdminMenuService가 이 표에서 만든 menuTree로 그립니다. 템플릿에 따로 박아 둔 메뉴는 없습니다.
  • 메뉴 종류 CORE는 늘 보입니다. ENTERPRISE는 contexa.enterprise.enabled: true일 때, SAAS는 그것과 contexa.saas.enabled: true가 모두 켜졌을 때만 보입니다.
  • 메뉴에 역할(ctxa_admin_menu_role)을 걸면 그 역할이 있는 사람에게만 보이고, 걸지 않으면 모두에게 보입니다. 메뉴는 "메뉴 관리" 화면이나 시드 파일로 더합니다.

  • 기간: 칩 "24시간" · "7일"(기본) · "30일" · "90일"이고, 주소에 ?period=day · week · month · quarter로 남습니다. "기간은 판정·이벤트·변경 수에 적용됩니다. 사용자·정책·에이전트·차단 수는 지금 상태입니다." 시간별 집계에서 오는 숫자는 기간이 시작하는 시간칸의 정시부터 셉니다.

JSON API와 시간별 집계

GET /contexa/admin/api/dashboard?period=day|week|month|quarter(기본 week)는 대시보드 전체를 JSON 문서 하나로 답합니다: period, zeroTrust(기간의 콘솔 개요, 검토를 기다리는 판정 수, SHADOW이면 적용 전환 판정), operations, policy, iam, security, blocked, agents, system, attention, changes, denials. 관리자만 받습니다. 메서드 보안과 따로 부를 때마다 ROLE_ADMIN을 확인하고, 다른 사용자는 403입니다. 네 값이 아닌 기간은 400입니다. 처리할 일과 영역 상태는 화면이 이 숫자들로 정합니다.

숫자 둘은 부를 때마다 기록에서 세기에 무거워, 주기 작업이 시간칸마다 세어 둡니다. Zero Trust 콘솔이 자기 시간별 집계를 두는 방식과 같습니다.

표세는 것보존
ctxa_dashboard_denial_hourly로그인한 사용자의 요청 가운데 URL 인가에서 거부된 것(AUTHORIZATION_DENIED), 리소스별 · 사용자별판정 원본과 같은 기간(contexa.security.zerotrust.console.decision-retention-days, 기본 90). 행에 사용자 이름이 있기 때문입니다
ctxa_dashboard_seal_hourly판정 기록의 봉인 확인 결과(VERIFIED · MISMATCH · UNVERIFIABLE). 가장 오래전에 확인한 시간칸부터 회마다 2,000건까지 다시 확인해, 나중에 바뀐 기록도 찾습니다집계와 같은 기간(contexa.security.zerotrust.console.aggregate-retention-days, 기본 730)

contexa.security.zerotrust.console.aggregation-interval-ms(기본 60000)마다 지금 시간칸과 바로 앞 시간칸을 다시 세고, 늦게 쓰인 감사 기록이 속한 시간칸도 다시 셉니다. 기동 뒤 첫 회는 최근 48시간을 다시 세고, 그 뒤의 회는 최근 90일 가운데 행이 없는 시간칸을 48시간씩 채웁니다. 보존 정리는 contexa.security.zerotrust.console.retention-cron(기본 0 17 3 * * *)에 돕니다. 두 보존 값은 시스템 설정에도 저장할 수 있습니다(시스템 설정).

권한 센터

경로 /contexa/admin/access-center. 사용자 → 그룹 → 역할 → 권한의 연결을 탭 네 개(사용자 · 그룹 · 역할 · 현황)에서 다룹니다. 사용자 상세에는 소속 그룹, 직접 받은 역할, 그룹에서 물려받은 역할, 실제로 갖는 권한이 함께 보입니다. 현황 탭은 사용자 · 그룹 · 역할 · 권한 수와 사용자 → 그룹 → 역할 → 권한 연결 구조 그림을 보여 줍니다.

역할에 이름이 READ · WRITE · UPDATE · DELETE인 권한이 연결돼 있으면 CRUD 권한으로 봅니다. 사용자나 그룹에 역할을 줄 때 그 가운데 일부만 고를 수 있고, READ는 늘 들어갑니다. 고른 값은 사용자 · 역할별(UserRolePermission), 그룹 · 역할별(GroupRolePermission)로 저장됩니다.

사용자 · 그룹 · 역할 · 권한 · 역할 계층

사용자(/contexa/admin/users), 그룹(/contexa/admin/groups), 역할(/contexa/admin/roles), 권한(/contexa/admin/permissions)을 만들고 고치고 지웁니다. 사용자는 그룹 소속과 직접 받은 역할로 권한을 얻습니다.

역할 계층(/contexa/admin/role-hierarchies)은 상위 역할이 하위 역할의 권한을 물려받게 합니다. 기본 시드의 계층은 ROLE_ADMIN > ROLE_DEVELOPER > ROLE_INFRA > ROLE_USER입니다. 활성 계층은 기동할 때와 바꿀 때마다 Spring Security RoleHierarchy에 적용되고, URL · 메서드 정책의 식 평가에도 쓰입니다.

보안 이벤트 기록

경로 /contexa/admin/security-monitor(보안 → 보안 이벤트 기록). "감사 기록에 남은 인증·인가·판정 사건을 시간순으로 봅니다. 판정 행은 판정 상세로 이어집니다." 감사 기록(ctxa_audit_log)을 데이터베이스에서 20건씩 나눠 읽습니다. 기간은 1시간 · 6시간 · 24시간(기본) · 3일이고(?hours=, 대시보드 링크처럼 다른 시간 수도 받습니다), 분류 · 사용자 이름 키워드 · 주체 종류(HUMAN_USER · DELEGATED_AGENT · AUTONOMOUS_AGENT)로 거릅니다. 링크는 시간 수 대신 시작 시각을 줄 수 있습니다(?from=, 2026-11-18T03:00:00Z 같은 ISO 시각). 카드 · 분류 · 필터 링크, 쪽 넘김, CSV는 이 시작 시각을 이어 가고, 기간 칩을 누르면 빠집니다. 읽을 수 없거나 앞으로의 시각이면 무시하고 최근 시간 수만큼 읽습니다.

  • 분류가 SECURITY_DECISION인 행의 "판정 상세 보기 ›"는 Zero Trust 콘솔의 그 판정을 엽니다(/contexa/admin/zero-trust/decisions/request/{requestId}). 판정이 있으면 판정 상세, 그 요청의 판정이 따로 없으면 그 요청으로 찾은 판정 기록입니다.

차단된 사용자와 에이전트 정지

경로 /contexa/admin/blacklist. AI 판정으로 차단된 사용자를 상태별로 봅니다.

상태뜻
BLOCKED차단됨
UNBLOCK_REQUESTED사용자가 해제를 요청함
RESOLVED관리자가 처리함
TIMEOUT_RESPONDED차단 뒤 24시간 안에 해제 요청이 없어 자동 대응으로 넘어감

상세 화면(/{id})에서 처리 동작과 이유를 적어 해결하면(POST /{id}/resolve) RESOLVED가 되고, 그 결정은 관리자 재정의로 판정 엔진에 전해집니다. 기록 삭제는 POST /{id}/delete, 같은 일을 하는 JSON API는 /contexa/admin/api/blacklist입니다.

정지된 에이전트와 위임은 같은 메뉴의 에이전트 정지 탭(/contexa/admin/blacklist/agents)에서 보고 해제하며, 킬 스위치도 여기 있습니다. 사람 차단 목록과는 따로입니다(정지 · 확인 · 제한의 콘솔 화면).

IP와 세션

  • IP 관리(/contexa/admin/ip-management): ALLOW · DENY 규칙을 IPv4 · IPv6 · CIDR로 만들고, 만료 시각 · 켜고 끄기 · CSV 내보내기를 씁니다. DENY에 걸린 IP는 403입니다. 켜진 ALLOW 규칙이 하나라도 있으면 허용 목록 방식이 되어, 목록에 없는 IP도 403입니다. 이 필터는 HOST_OWNED에서 /contexa/* 경로에만, CONTEXA_OWNED에서 모든 경로에 걸리고, 정적 파일은 건너뜁니다. 목록 위의 허용 · 차단 · 전체 수는 지금 걸려 있는 규칙만 셉니다. 켜져 있고 만료되지 않은 규칙이며, 필터가 적용하는 규칙과 같습니다.
  • 세션 관리(/contexa/admin/session-management): 활성 세션을 검색하고(세션 ID · 사용자 · IP · User Agent · 로그인 시각 · 마지막 활동), 세션 하나(POST /{sessionId}/invalidate)나 사용자의 모든 세션(POST /user/{userId}/invalidate-all)을 끊습니다. CSV 내보내기가 있습니다.

시스템 설정

경로 /contexa/admin/system-settings. 값은 Contexa DB의 ctxa_system_settings 행에 저장되고, 저장하면 이 인스턴스에 바로 적용되며 URL 정책을 다시 읽고, 분산 모드면 다른 인스턴스에도 알립니다. 저장된 값은 YAML 설정보다 우선합니다.

메서드 · 경로하는 일
POST /contexa/admin/api/ai/policies/generate/stream자연어 요구로 정책 초안을 SSE 스트리밍으로 만듦
POST /contexa/admin/api/ai/policies/generate같은 일을 한 번에 돌려줌. 똑같은 요청이 이미 돌고 있으면 409
POST /contexa/admin/api/policies/build-from-business-rule확인한 초안을 정책으로 저장
  1. 관리자가 요구를 글로 씁니다(예: "개발자는 근무 시간에 /api/**에 접근할 수 있다").
  2. AdvancedPolicyGenerationLab이 쓸 수 있는 역할 · 권한 · 조건 템플릿과 기존 정책 · 역할 계층을 요청에 더하고, PolicyGenerationContextRetriever가 벡터 저장소에서 비슷한 정책을 찾습니다.
  3. AI가 PolicyResponse(정책 초안, 역할 · 권한 · 조건의 ID → 이름 표, 이유)를 돌려줍니다.
  4. 화면이 쓸 수 있는 항목과 맞춰 보고 미리 보여 줍니다.
  5. 저장하면 BusinessPolicyService가 정책 · 대상 · 규칙 · 조건을 만들고 다시 읽습니다. 출처가 AI_GENERATED라서 승인 대기로 저장되고, 승인하기 전에는 평가되지 않습니다(AI 초안 승인).
