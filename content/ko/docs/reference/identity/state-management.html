세션과 토큰

로그인한 뒤 그 상태를 서버 세션에 둘지(.session()), 토큰(JWT)으로 주고받을지(.oauth2()) 고르는 방법입니다. 켜는 데 꼭 필요한 설정과 확인 방법, 사람은 세션 · 에이전트는 토큰으로 나누는 방법, 토큰 검사와 위임 토큰을 설명합니다.

Contexa가 로그인을 맡을 때(CONTEXA_OWNED)의 기능입니다. 기본값 HOST_OWNED에서는 앱의 Spring Security가 세션 · 토큰을 맡고, Contexa 인가 서버와 리소스 서버 구성은 만들어지지 않습니다. 앱의 기존 로그인을 그대로 쓰려면 기존 로그인과 연결하기를 보세요.

세션과 토큰 중 고르기

흐름마다 인증 방법 다음에 상태를 하나 고릅니다(인증 방법과 상태 고르기). 흐름마다 다르게 고를 수 있습니다.

registry
        .form(form -> form.defaultSuccessUrl("/home"))
        .session(Customizer.withDefaults())       // 사람: 세션
        .rest(rest -> rest.order(50))
        .oauth2(Customizer.withDefaults())        // API 클라이언트: 토큰
        .build();
항목.session().oauth2()
로그인 저장서블릿 컨테이너의 HTTP 세션. 여러 서버가 세션을 나누려면 앱이 Spring Session 등을 직접 구성합니다저장하지 않고 요청마다 토큰을 검증합니다(STATELESS). 인가 정보 · 갱신 토큰은 Contexa DB에 둡니다
맞는 곳서버가 그리는 화면SPA · 모바일 앱 · API · 에이전트
세션 고정 방지로그인할 때 세션 ID를 바꿈해당 없음

Contexa의 Redis(분산 모드)는 판정 저장소 · MFA 세션 · 세션 추적에 쓰이며, 앱의 HTTP 세션을 Redis에 두지는 않습니다.

세션 상태

.session(Customizer.withDefaults())로 켭니다.

  • 로그인할 때 세션 ID를 바꿉니다(changeSessionId). 세션에 로그인이 남는 모든 로그인이 그렇습니다: 폼, REST, 일회용 코드, 패스키, 그리고 MFA(요소 확인을 모두 마쳤을 때, 또는 요소가 필요 없어 1차 로그인에서 끝날 때). 로그인하면 CSRF 토큰도 바뀌므로, REST로 로그인하고 화면을 그대로 쓰는 페이지는 다음 요청 전에 토큰을 다시 읽습니다.
  • 로그아웃 주소는 /logout입니다. 접두사가 있는 MFA 흐름은 <접두사>/logout입니다. 이 주소는 고정입니다. global이나 흐름 옵션 logout(...)에 쓴 logoutUrl(...)은 쓰이지 않습니다. 요청 시점 접근 제어와 MFA 진행 중 접근 제어가 제한된 세션을 바로 이 주소로는 통과시키기 때문입니다.
  • 로그아웃하면 세션을 무효화하고 로그인을 지운 뒤, Contexa 로그아웃 처리기(compositeLogoutHandler)가 Contexa 쪽 정리와 토큰 쿠키 지우기를 합니다.
  • 로그아웃 뒤 이동: 접두사가 있는 MFA 흐름은 <접두사>/mfa/login, 그 밖의 세션 흐름은 /contexa/admin/login입니다. 이 주소들은 기본값입니다. global이나 흐름 옵션 logout(...)에 logoutSuccessUrl(...) 또는 logoutSuccessHandler(...)를 쓰면 그것이 쓰입니다.

.session(...)에 넘기는 구성자에는 바꿀 옵션이 없습니다. 동시 세션 수 같은 세션 설정은 흐름 옵션 sessionManagement(...)로 합니다.

registry
        .form(form -> form.sessionManagement(session -> session.maximumSessions(1)))
        .session(Customizer.withDefaults())
        .build();

이 제한은 어떤 방법으로 로그인했든 세션에 로그인이 남는 모든 로그인에 적용됩니다. maxSessionsPreventsLogin(true)면 제한을 넘는 로그인은 로그인 실패로 거부되고(REST 로그인과 MFA 1차 로그인은 401, 폼 로그인은 실패 주소로 이동), 비밀번호 오류 횟수로 세지 않습니다.

확인하기

  • 로그인 전후로 세션 쿠키 값이 바뀝니다.
  • POST /logout 뒤에는 세션이 끝나고 위의 로그아웃 뒤 주소로 이동합니다.

토큰 상태(OAuth2)

.oauth2(Customizer.withDefaults())로 켭니다. Contexa가 Spring Authorization Server와 Spring 리소스 서버를 그 체인에 구성합니다.

꼭 필요한 설정

  • 조건: CONTEXA_OWNED, Contexa DB(contexaJdbcTemplate · contexaTransactionTemplate 빈), 클래스패스의 Spring Authorization Server.
  • contexa.auth.oauth2.client-secret: 토큰 흐름이 하나라도 있고 서버 모드가 인가 서버를 포함하면(기본 COMBINED) 꼭 있어야 합니다. 비어 있으면 시작이 실패합니다. 예전 기본값(173f8245-…)은 거부되고, DB에 이미 저장된 클라이언트의 비밀값이 이 값과 맞지 않아도 시작이 실패합니다. 재시작 뒤에도 같은 값을 쓰세요.
  • 서명 키스토어: contexa.auth.oauth2.jwk-key-store-path를 두지 않으면 시작할 때마다 바뀌는 임시 RSA 키로 서명하므로, 재시작하면 기존 토큰이 모두 무효가 됩니다(시작 때 오류 로그). 경로는 클래스패스에서 찾고, 파일이면 file:을 붙입니다. 키스토어 형식은 PKCS12이고, 파일이 없으면 시작이 실패합니다.
contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: contexa
  bridge:
    ownership: CONTEXA_OWNED
  auth:
    oauth2:
      client-secret: replace-with-a-long-random-secret
      jwk-key-store-path: file:/etc/contexa/jwk.p12
      jwk-key-store-password: change-me
      jwk-key-alias: contexa
      jwk-key-password: change-me

자동으로 붙는 것

  • 리소스 서버: JWT 검증, Contexa 토큰 변환기, 401 · 403 처리기, 상태 없음(STATELESS).
  • 인가 서버: OAuth2AuthorizationService, RegisteredClientRepository, 토큰 엔드포인트, OIDC, 로그인한 사용자에게 토큰을 주는 그랜트(아래).
  • 서버 모드 contexa.auth.oauth2-server-mode: RESOURCE_SERVER(검증만) · AUTHORIZATION_SERVER(발급만) · COMBINED(둘 다, 기본).
  • 앱이 OAuth2TokenGenerator 빈이나 BearerTokenResolver 빈을 하나 두면 Contexa는 그 빈을 그대로 씁니다.
  • 로그아웃(권한 서버를 포함하는 모드): POST /logout. API 요청에는 200과 status LOGGED_OUT으로 답하고, 브라우저가 직접 낸 요청은 로그인 화면으로 이동시킵니다(MFA 흐름은 그 흐름의 로그인 화면, 그 밖에는 contexa.auth.urls.primary.form-login-page). 토큰 상태에서는 global이나 logout(...)에 쓴 logoutSuccessUrl(...) · logoutSuccessHandler(...)가 쓰이지 않습니다. 응답을 바꾸려면 contexaOauth2LogoutSuccessHandler라는 이름의 LogoutSuccessHandler 빈을 정의합니다.

토큰 전달 방식

contexa.auth.token-transport-type접근 토큰갱신 토큰맞는 곳
HEADER(기본)응답 본문 → 요청의 Authorization 헤더응답 본문SPA · 모바일 · API
COOKIE쿠키 accessToken쿠키 refreshToken서버가 그리는 화면. CSRF가 늘 켜지고, 쿠키 토큰을 읽고 갱신하는 필터가 붙습니다
HEADER_COOKIE응답 본문 → 헤더쿠키 refreshToken갱신 토큰을 스크립트에서 감추고 싶을 때
서버가 그리는 화면에는 COOKIE 전송을 쓰세요. HEADER · HEADER_COOKIE 전송에 토큰 보관이 메모리(contexa.auth.token-persistence: memory, 기본)이면, 브라우저가 화면을 이동할 때 접근 토큰이 실리지 않아 로그인 뒤 화면이 로그인 안 된 상태로 보입니다. Contexa는 시작할 때 이 조합을 오류 로그로 알립니다.

로그인 뒤 토큰 발급

폼 · REST · MFA 로그인을 마친 사용자에게 토큰을 주는 그랜트 urn:ietf:params:oauth:grant-type:authenticated-user가 있습니다. 로그인이 성공하면 Contexa가 같은 앱 안에서 내부 클라이언트로 이 그랜트를 요청해 토큰을 받고, 성공 응답에 싣습니다. contexaTransactionTemplate 빈이 있을 때 구성됩니다.

확인하기

POST /api/login
Content-Type: application/json

{"username": "alice", "password": "s3cret"}

응답의 accessToken을 Authorization: Bearer …로 실어 보호된 API를 부르면 응답하고, 빼면 401이 옵니다. 갱신은 POST /api/refresh(contexa.auth.internal.refresh-uri)입니다.

사람은 세션, 에이전트는 토큰(요청 범위)

한 앱에서 사람은 세션 흐름으로 쓰고, 에이전트와 API 클라이언트는 토큰으로 부르게 할 수 있습니다. 기본으로 토큰 흐름의 체인은 그 흐름이 맡는 요청을 모두 받습니다(모든 요청, 또는 urlPrefix 아래). 요청 범위를 TOKEN_REQUESTS로 두면 토큰에 속한 요청만 받고 나머지는 다음 흐름으로 넘깁니다.

TOKEN_REQUESTS 흐름이 받는 요청:

  • 체인이 읽는 방식 그대로 접근 토큰을 실은 요청: Authorization: Bearer 헤더, COOKIE 전송이면 접근 토큰 쿠키(앱이 BearerTokenResolver 빈을 두었으면 그 빈). 형식이 잘못된 토큰도 여기로 와서 401로 거부됩니다.
  • Authorization 헤더를 보내겠다고 알리는 CORS 사전 요청.
  • 그 체인의 인가 서버 엔드포인트(토큰, JWK 세트, 검사, 폐기, 메타데이터, OIDC)와 갱신 주소.
  • 그 흐름의 인증 주소(로그인 처리 주소, 일회용 코드 · 패스키 엔드포인트, MFA 흐름의 화면과 엔드포인트)와 urlPrefix.
  • tokenScopeRequests(...)로 더한 요청. 예: 클라이언트가 토큰을 받기 전에 읽는 메타데이터 경로.
registry
        .rest(rest -> rest
                .loginProcessingUrl("/api/agent/login")
                .order(50))
        .oauth2(oauth2 -> oauth2.requestScope(OAuth2RequestScope.TOKEN_REQUESTS))
        .form(form -> form.defaultSuccessUrl("/home"))
        .session(Customizer.withDefaults())
        .build();
  • 순서가 같은 흐름은 적은 순서를 따릅니다. 모든 요청을 받는 흐름 뒤의 흐름은 요청을 받지 못하며, Contexa가 시작할 때 오류 로그로 알립니다.
  • urlPrefix가 없으면 MFA 흐름들의 주소가 모두 같으므로, 토큰 범위 MFA 흐름에는 자기 접두사를 주세요.
  • 요청 범위가 체인의 요청 매처를 정하므로 rawHttp로 매처를 따로 정하지 말고, 경로는 tokenScopeRequests(...)로 더하세요.
  • 토큰 범위 흐름에서 로그아웃할 때는 접근 토큰을 실어 보내세요. 토큰 없는 로그아웃은 세션 흐름으로 갑니다.

토큰 검사와 판정

Contexa 리소스 서버는 Contexa가 요청을 읽기 전에 Spring 검증기로 모든 접근 토큰을 검사합니다: 서명, 유효 기간, 발급자(contexa.auth.oauth2.issuer-validation-enabled, 기본 켜짐), 그리고 contexa.auth.oauth2.audiences를 정했으면 대상(aud). Contexa 인가 서버는 토큰을 받은 클라이언트의 ID를 대상으로 적으므로, 이 앱이 받아 줄 클라이언트를 적으세요. 검사에 실패한 토큰은 401로 거부되고, 그 요청에는 Contexa 필터도 판정도 돌지 않습니다.

Contexa 판정은 권한을 더하지 않습니다. ALLOW는 토큰이 준 권한을 그대로 두고, CHALLENGE · BLOCK · ESCALATE는 원래 권한을 지우고 판정 표시 권한 하나만 남깁니다(권한이 바뀌는 방식). 작업을 범위에 묶으려면 hasAuthority("SCOPE_reports.write") 같은 Spring 규칙을 쓰세요. 그 범위가 없는 토큰은 판정과 상관없이 거부됩니다.

앱이 자기 리소스 서버로 토큰을 검증한다면 그 디코더에 같은 검사를 거세요.

@Bean
JwtDecoder jwtDecoder() {
    NimbusJwtDecoder decoder = NimbusJwtDecoder.withIssuerLocation("https://idp.example.com").build();
    decoder.setJwtValidator(JwtValidators.createDefaultWithValidators(
            new JwtIssuerValidator("https://idp.example.com"),
            new JwtAudienceValidator("https://api.example.com")));
    return decoder;
}

위임 토큰(토큰 교환)

사람을 대신해 일하는 에이전트는 둘을 모두 밝힌 토큰을 받습니다. 사람은 sub, 에이전트는 행위자(act, RFC 8693)입니다. contexa.auth.oauth2.token-exchange-enabled: true로 이 그랜트를 켭니다. 기본은 꺼져 있고, 꺼져 있는 동안 토큰 엔드포인트는 모든 클라이언트의 교환 요청을 unsupported_grant_type으로 거부합니다.

에이전트의 클라이언트를 Spring의 RegisteredClientRepository 빈에 client_credentials와 urn:ietf:params:oauth:grant-type:token-exchange 그랜트, 에이전트가 받을 수 있는 범위로 등록하고, 그 클라이언트 ID로 에이전트를 등록하세요(에이전트 등록). 그러면 에이전트가 자기 토큰을 행위자 토큰으로 내고 사람의 토큰을 교환합니다.

POST /oauth2/token
Authorization: Basic (에이전트 클라이언트 자격 증명)
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&subject_token=(사람의 접근 토큰)
&subject_token_type=urn:ietf:params:oauth:token-type:access_token
&actor_token=(에이전트 자신의 접근 토큰)
&actor_token_type=urn:ietf:params:oauth:token-type:access_token
&scope=reports.read
  • 두 토큰 모두 이 인가 서버가 발급했고 아직 유효해야 합니다. 사람의 토큰에 may_act가 있으면 거기 적힌 행위자만 교환할 수 있습니다.
  • 범위는 요청한 범위이며 에이전트 클라이언트에 등록된 범위 안이어야 합니다.
  • 발급된 토큰은 sub = 사람, act.sub = 에이전트 클라이언트, client_id = 에이전트 클라이언트입니다. 리소스 서버는 이 요청을 사람으로 인증하고(사람의 권한과 토큰 범위), 판정은 그 사람을 대신하는 등록 에이전트를 기록합니다.
  • Contexa가 발급하는 토큰은 Spring Authorization Server의 토큰 생성기로 만들어지며, 이 생성기가 Contexa 클레임(client_id, 로그인 사실, 역할)보다 먼저 토큰 교환의 act와 DPoP · mTLS 클라이언트의 cnf 결속을 넣습니다. 그래서 DPoP 증명을 보낸 토큰 요청은 보낸 쪽에 묶인 토큰(token_type DPoP)을 받습니다. OAuth2TokenGenerator 빈을 직접 두면 그 빈을 그대로 쓰므로 이 클레임은 그 빈이 넣어야 합니다.

contexa.auth.oauth2.client-secret없음토큰 흐름이 있으면 꼭 적어야 함. 재시작 뒤에도 같은 값
contexa.auth.oauth2.jwk-key-store-path없음토큰 서명 키스토어. 운영과 여러 서버에서는 꼭 지정
contexa.auth.token-transport-typeHEADER토큰 전달 방식. 서버가 그리는 화면은 COOKIE
contexa.auth.oauth2-server-modeCOMBINED이 앱이 토큰을 발급만 · 검증만 할 때
