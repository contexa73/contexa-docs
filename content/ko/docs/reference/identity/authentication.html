로그인 방법

Contexa가 로그인을 맡을 때 쓰는 단일 로그인 방법 네 가지(폼 · REST · 일회용 코드 · 패스키)를 켜고, 주소를 바꾸고, 결과를 확인하는 방법을 설명합니다. 로그인 성공 · 실패를 누가 처리하는지와 로그인 정보를 어디에 저장하는지도 다룹니다.

Contexa가 로그인을 맡을 때(CONTEXA_OWNED)의 기능입니다. 기본값 HOST_OWNED에서는 앱의 Spring Security가 로그인을 맡고 이 페이지의 흐름은 만들어지지 않습니다. 앱의 기존 로그인을 그대로 쓰려면 기존 로그인과 연결하기를 보세요. 흐름을 적는 방법과 공통 옵션은 인증 DSL에 있습니다.

어떤 방법을 언제 쓰나

방법쓰는 곳기본 order로그인 처리 기본 주소
폼 .form()서버가 그리는 로그인 화면100POST /login
REST .rest()SPA · 모바일 앱 · API 클라이언트(JSON)200POST /api/login
일회용 코드 .ott()메일로 받은 코드로 로그인300발급 POST /ott/generate, 로그인 POST /login/ott
패스키 .passkey()비밀번호 없는 로그인(WebAuthn)400POST /login/webauthn

각 방법은 자기 체인 하나가 되고, order가 낮은 체인이 먼저 요청을 비교합니다. order · rawHttp · disableCsrf 같은 공통 옵션은 흐름 옵션에 있습니다.

단일 로그인과 MFA 안의 요소

같은 방법을 MFA 흐름 안에서 2차 요소로 쓰면 주소 · 구현 · 진행 관리가 달라집니다. MFA는 적응형 MFA를 보세요. 패스키를 예로 들면:

항목단일 패스키MFA 안의 패스키
DSL.passkey(...).mfa(mfa -> mfa.passkey(...))
로그인 처리 주소/login/webauthn/login/mfa-webauthn
구현PasskeyAuthenticationAdapter, Spring 내장 필터MfaPasskeyAuthenticationAdapter, Spring 필터 + Contexa 처리기
진행 관리로그인 저장소(SecurityContextRepository)MFA 상태 기계와 MFA 세션

폼 로그인

registry
        .form(form -> form.defaultSuccessUrl("/home"))
        .session(Customizer.withDefaults())
        .build();

loginPage를 주지 않으면 Spring 기본 로그인 화면이 GET /login에 생기고, 그 화면이 POST /login으로 보냅니다.

옵션기본값언제 바꾸나
loginPage(String)없음(Spring 기본 화면 /login)앱이 만든 로그인 화면을 쓸 때. 처리 주소는 바뀌지 않습니다
loginProcessingUrl(String)/login화면이 다른 주소로 보낼 때, 체인 범위가 /login을 포함하지 않을 때
usernameParameter(String) · passwordParameter(String)username · password화면의 입력 이름이 다를 때
defaultSuccessUrl(String), defaultSuccessUrl(String, boolean)없음로그인 뒤 이동할 주소. true면 원래 가려던 주소 대신 늘 이 주소로
failureUrl(String)없음(Spring 기본 /login?error)실패 뒤 이동할 주소
permitAll()꺼짐로그인 화면 · 처리 주소를 인증 없이 열어야 할 때
rawFormLogin(...)없음Spring FormLoginConfigurer를 직접 만질 때. 여러 번 부르면 마지막 것만 남습니다
로그인 화면만 바꾸면 처리 주소는 그대로 /login입니다. Spring Security에서는 loginPage가 처리 주소도 정하지만, Contexa 폼 흐름은 처리 주소를 contexa.auth.urls.single.form-login-processing(기본 /login)으로 먼저 정합니다. 체인 범위를 좁혔다면 loginProcessingUrl도 함께 바꾸세요. 
registry
        .form(form -> form
                .loginPage("/admin/login")
                .loginProcessingUrl("/admin/login")
                .permitAll()
                .rawHttp(http -> http.securityMatcher("/admin/**"))
                .rawFormLogin(login -> login.usernameParameter("email")))
        .session(Customizer.withDefaults())
        .build();

여기서 /admin/login 화면은 앱이 만들어야 합니다. 응답을 직접 만들려면 successHandler(...) · failureHandler(...)를 줍니다(성공 · 실패 처리).

확인하기

  • 보호된 주소를 열면 로그인 화면으로 이동합니다.
  • 로그인에 성공하면 defaultSuccessUrl(또는 원래 가려던 주소)로, 실패하면 /login?error로 갑니다.

REST 로그인

JSON 본문으로 로그인합니다. 토큰 상태와 함께 쓰는 경우가 많지만 세션 상태도 됩니다.

registry
        .rest(rest -> rest.defaultSuccessUrl("/app"))
        .oauth2(Customizer.withDefaults())
        .build();
POST /api/login
Content-Type: application/json

{"username": "alice", "password": "s3cret"}
상태성공 응답(200, JSON)
.oauth2(), HEADER 전송(기본)accessToken, tokenType(Bearer), expiresIn, refreshToken, refreshExpiresIn, tokenTransportMethod, authenticated, redirectUrl, message, username
.session()authenticated, redirectUrl, message, username, stateType(SESSION) + 세션 쿠키
  • 로그인 처리 주소는 POST만 받습니다. 같은 주소의 GET /api/login에는 기본 로그인 화면이 나옵니다.
  • 실패하면 401 JSON을 돌려주며, 실패 응답은 최소 contexa.auth.mfa.minimum-delay-ms(기본 500ms)가 지난 뒤 나갑니다. 비밀번호 추측의 속도를 늦추기 위해서입니다.
  • .oauth2()가 이미 상태 없음(STATELESS)으로 구성하므로 rawHttp로 따로 지정할 필요가 없습니다. .oauth2()를 쓰면 contexa.auth.oauth2.client-secret이 꼭 있어야 합니다(토큰 상태에 꼭 필요한 설정).
옵션기본값언제 바꾸나
loginProcessingUrl(String)/api/loginAPI 경로 규칙이 다를 때
defaultSuccessUrl(...) · failureUrl(String)없음응답의 redirectUrl · 실패 뒤 이동 주소
securityContextRepository(...)없음REST 흐름은 이 옵션을 지정했을 때만 로그인 저장소를 바꿉니다

확인하기

GET /api/orders
Authorization: Bearer <accessToken>

받은 accessToken을 실으면 보호된 API가 응답하고, 빼면 401이 옵니다.

일회용 코드(OTT)

사용자 이름을 받아 일회용 코드를 메일로 보내고, 그 코드로 로그인합니다.

registry
        .ott(Customizer.withDefaults())
        .session(Customizer.withDefaults())
        .build();
  • 발송 서비스: 기본 OneTimeTokenService 빈은 EmailOneTimeTokenService입니다. 코드를 Contexa DB의 ctxa_one_time_tokens 표에 두고 Spring 메일(spring.mail.*)로 보냅니다.
  • 받는 주소: 사용자 표(ctxa_users)의 메일 주소입니다. 주소가 없으면 사용자 이름을 주소로 씁니다. 요청의 email이 등록된 주소와 다르면 거부합니다.
  • 메일을 보내지 못하면: contexa.auth.ott.fail-on-email-error(기본 true)이면 발급이 실패합니다. false면 코드는 만들고 경고 로그만 남깁니다.
  • 유효 시간: 코드는 만든 뒤 5분 동안 유효합니다(Spring 기본값). contexa.auth.mfa.otp-token-validity-seconds(기본 300)는 메일 안내 문구의 분 수에만 쓰입니다.
옵션기본값언제 바꾸나
tokenGeneratingUrl(String)/ott/generate코드 발급 주소를 바꿀 때
defaultSubmitPageUrl(String)/login/ott/verify코드 입력 화면 주소를 바꿀 때
showDefaultSubmitPage(boolean)true코드 입력 화면을 앱이 직접 만들 때 false
loginProcessingUrl(String)/login/ott코드 확인 주소를 바꿀 때
tokenGenerationSuccessHandler(...)oneTimeTokenCreationSuccessHandler 빈코드를 만든 뒤 응답을 바꿀 때. 기본 처리기는 contexa.auth.urls.factors.ott.code-sent(기본 /mfa/ott/code-sent) 주소로 이동시킵니다
tokenService(...)OneTimeTokenService 빈아래 주의를 보세요

요청 파라미터 이름은 username · token으로 정해져 있습니다.

발송 서비스를 바꾸려면 옵션이 아니라 빈으로 등록하세요. DSL의 tokenService(...)는 코드 발급에만 쓰이고, 코드 확인은 OneTimeTokenService 빈으로 합니다. 옵션으로 다른 서비스를 주면 확인이 실패합니다. 빈을 등록하면 발급과 확인 모두 그 빈을 씁니다. 
@Bean
public OneTimeTokenService oneTimeTokenService() {
    // 예: 시험용 메모리 저장. 이 서비스는 메일을 보내지 않으므로 코드 전달은 앱이 맡습니다.
    return new InMemoryOneTimeTokenService();
}

패스키

WebAuthn 패스키로 비밀번호 없이 로그인합니다. 패스키는 브라우저가 서비스 이름(rpId)과 접속한 출처(origin)를 확인하므로, 이 두 값을 운영 주소에 맞춰야 합니다.

registry
        .passkey(Customizer.withDefaults())
        .session(Customizer.withDefaults())
        .build();
contexa:
  auth:
    urls:
      factors:
        passkey:
          rp-id: example.com
          rp-name: Example
          allowed-origins: https://app.example.com
옵션기본값언제 바꾸나
rpId(String)localhost운영 도메인으로. 설정 contexa.auth.urls.factors.passkey.rp-id가 기본값의 출처
rpName(String)contexa-identity사용자에게 보이는 서비스 이름
allowedOrigins(...)http://localhost: + server.port(없으면 8080)브라우저가 접속하는 출처. 설정 allowed-origins(쉼표로 여러 개)가 있으면 그 값
assertionOptionsEndpoint(String) · loginProcessingUrl(String)/webauthn/authenticate/options · /login/webauthn단일 패스키 흐름에서는 반영되지 않고 Spring 기본 주소를 씁니다
  • 패스키 흐름에서는 successHandler · failureHandler 옵션이 쓰이지 않습니다(성공 · 실패 처리).
  • rpId가 비어 있으면 시작할 때 검사기가 오류 로그를 남기지만 시작은 막지 않습니다.
  • Contexa DB가 있으면(contexaJdbcTemplate 빈) 패스키 정보를 저장하는 Spring JDBC 저장소(JdbcUserCredentialRepository, JdbcPublicKeyCredentialUserEntityRepository)가 자동 등록됩니다.

패스키 등록

로그인한 사용자가 패스키를 등록합니다. 등록 화면 GET /webauthn/register는 Contexa 화면으로 바뀌어 있습니다.

주소하는 일
POST /webauthn/register/options등록 옵션 만들기
POST /webauthn/register패스키 등록(200)
POST /webauthn/authenticate/options로그인 옵션 만들기
POST /login/webauthn패스키 로그인
DELETE /webauthn/register/{id}등록한 패스키 지우기(204)

성공 · 실패 처리

successHandler · failureHandler를 주지 않으면 Contexa가 흐름 종류와 상태에 맞는 처리기를 고릅니다. 여기서 단일은 MFA가 아닌 흐름, MFA 1차는 MFA의 첫 로그인, MFA 2차 요소는 그 뒤의 일회용 코드 · 패스키입니다.

흐름상태성공실패
단일 폼 · 일회용 코드세션Spring 기본(defaultSuccessUrl로 이동)Spring 기본(failureUrl로 이동)
단일 REST세션SessionSingleAuthSuccessHandlerSessionSingleAuthFailureHandler
단일 패스키세션Spring 기본 JSON 응답(로그인 기록 포함)Spring 기본
단일 모든 방법토큰OAuth2SingleAuthSuccessHandler(토큰 발급)OAuth2SingleAuthFailureHandler
MFA 1차모두PrimaryAuthenticationSuccessHandlerUnifiedAuthenticationFailureHandler
MFA 2차 요소모두MfaFactorProcessingSuccessHandlerUnifiedAuthenticationFailureHandler
  • Contexa 처리기는 요청이 Accept · Content-Type에 JSON을 담았거나 경로에 /api/가 있으면 JSON으로, 아니면 이동(redirect)으로 답합니다.
  • 폼 · REST 흐름에 successHandler를 주면 자동 처리기 대신 그 처리기가 바로 붙습니다. 토큰 상태라도 Contexa가 토큰을 발급하지 않으므로 응답은 그 처리기가 책임집니다.
  • 일회용 코드 흐름은 자동 처리기가 있으면 그것이 우선입니다. 토큰 상태에서는 준 처리기가 토큰 발급 뒤에 먼저 불리고, 그 처리기가 응답을 쓰지 않으면 Contexa가 씁니다.
  • MFA의 결과 처리는 MFA 결과 처리를 보세요.

로그인 정보 저장

상태저장소뜻
세션AISessionSecurityContextRepository(@EnableAISecurity에서 늘 있음). 없으면 옵션으로 준 저장소, 그것도 없으면 HttpSessionSecurityContextRepositoryHTTP 세션에 저장합니다. Contexa 저장소는 꺼낼 때 판정을 적용합니다
토큰RequestAttributeSecurityContextRepository. 폼 흐름은 옵션으로 준 저장소가 있으면 그것그 요청 안에서만 둡니다. 다음 요청은 토큰으로 다시 인증합니다

MFA 1차 로그인도 같습니다. 세션 상태면 세션에, 토큰 상태면 요청 안에만 두고, MFA 도중에는 1차 로그인 증명을 MFA 세션에서 다시 꺼냅니다.
