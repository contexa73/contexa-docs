로그인 방법

CONTEXA가 로그인을 맡을 때 쓰는 단일 인증 방법 네 가지(폼 · REST · 일회용 코드 · 패스키)의 설정, 처리 주소, 동작 확인 방법을 설명합니다. 로그인 성공 · 실패 응답을 만드는 처리기와 로그인 정보를 보관하는 위치도 다룹니다.

이 페이지는 CONTEXA가 로그인을 맡는 FULL(주 흐름)에 적용됩니다. 기본 보안 모드 SANDBOX에서는 앱이 로그인을 맡으며(소유권과 무관), 이 페이지의 인증 흐름(CONTEXA 주 흐름)은 만들어지지 않습니다. 앱의 기존 로그인을 그대로 쓰려면 기존 로그인과 연결하기를 봅니다. 로그인을 CONTEXA에 맡기는 방법은 아래 시작하기 전에에 있습니다.
이 페이지의 용어. 인증은 요청한 사람이 누구인지 확인하는 일이고, 자격 증명은 그 사람임을 증명하는 값(비밀번호, 일회용 코드, 패스키)입니다. 인증 흐름(flow)은 인증 방법 하나와 인증 상태 하나를 묶은 설정 단위입니다. 흐름 하나마다 보안 필터 체인(요청을 검사하는 Spring Security 필터 묶음) 하나가 만들어지고, order 값이 작은 체인이 요청을 먼저 받습니다. 단일 인증은 자격 증명 하나로 끝나는 로그인이고, 다단계 인증(MFA)은 비밀번호 다음에 두 번째 인증 요소(일회용 코드나 패스키)를 더 확인하는 로그인입니다. 인증 상태는 로그인한 사용자 정보를 보관하는 방식입니다. 세션 상태(.session())는 서버의 HTTP 세션에 두고, 토큰 상태(.oauth2())는 클라이언트가 요청마다 보내는 접근 토큰에 둡니다. 보안 컨텍스트(SecurityContext)는 로그인한 사용자 정보를 담은 객체이고, 처리기(handler)는 로그인 성공 · 실패 때 응답을 만드는 코드입니다. 설정 문법은 인증 DSL, 인증 상태는 상태 관리에 있습니다.

시작하기 전에: 세 가지 준비

CONTEXA가 로그인을 처리하려면 아래 세 가지가 모두 갖춰져야 합니다.

1. 로그인을 CONTEXA에 맡긴다고 선언합니다

@SpringBootApplication
@EnableAISecurity(mode = SecurityMode.FULL)
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}
  • mode = SecurityMode.FULL이면 CONTEXA의 주 흐름이 앱 사용자를 로그인시킵니다. 모드를 적지 않으면 기본값 SANDBOX이고, 이때는 앱이 로그인을 맡습니다. 인증 소유권(contexa.bridge.ownership)은 보안 모드와 다른 설정이며, 적지 않으면 모드를 따릅니다(SANDBOX → HOST_OWNED, FULL → CONTEXA_OWNED). 네 조합 모두 허용됩니다. FULL에서 주 흐름은 CONTEXA_OWNED면 CONTEXA 계정으로, HOST_OWNED면 앱이 둔 UserDetailsService로(없으면 CONTEXA 계정으로) 사용자를 확인합니다.
  • 설정 contexa.ai.security.mode: FULL로도 정할 수 있습니다. 설정 값은 코드에 적은 값보다 우선합니다.

2. 인증 흐름을 빈 하나에 적습니다

로그인 방법은 PlatformConfig 빈 하나에 적습니다. 빈 메서드는 IdentityDslRegistry<HttpSecurity>를 받아 인증 방법(.form() 등), 인증 상태(.session() 또는 .oauth2()), build() 순서로 적습니다. 이 페이지에 나오는 짧은 예제(registry ...)는 모두 이 메서드의 본문입니다.

@Configuration
public class LoginFlowsConfig {

    @Bean
    public PlatformConfig platformDslConfig(IdentityDslRegistry<HttpSecurity> registry) throws Exception {
        return registry
                .form(form -> form.defaultSuccessUrl("/home"))
                .session(Customizer.withDefaults())
                .build();
    }
}

설정 클래스에는 @Configuration을 반드시 붙입니다. 빈을 두지 않았을 때 쓰이는 기본 구성과 모든 흐름에 공통인 옵션은 인증 DSL에 있습니다.

3. 로그인할 계정은 CONTEXA 계정 저장소에 있습니다

  • 모든 단일 로그인과 MFA의 1차 로그인은 CONTEXA DB의 사용자 표 ctxa_users에서 계정을 찾습니다(빈 contexaUnifiedUserDetailsService). 권한은 그 계정에 직접 준 역할과 소속 그룹의 역할로 계산합니다.
  • 앱이 자기 UserDetailsService 빈을 두어도 CONTEXA의 로그인에는 쓰이지 않습니다. 앱에만 있는 사용자는 없는 이름과 같이 로그인이 거부됩니다.
  • 잠긴 계정, 비활성 계정, 계정 유효 기간이 지난 계정은 비밀번호 · 일회용 코드 · 패스키 어느 방법으로도 로그인할 수 없습니다. 브리지가 앱의 로그인에서 옮겨 온 외부 계정(externalAuthOnly)도 CONTEXA 로그인에는 쓸 수 없습니다(기존 로그인과 연결하기).
  • 첫 계정: contexa.iam.seed.admin.password를 정하면 시작할 때 관리자 계정 하나(기본 이름 admin)를 만듭니다. 정하지 않으면 사용자 계정이 하나도 없는 DB에 예시 계정 다섯 개를 만듭니다. 예시 계정은 같은 비밀번호를 함께 쓰므로, 운영 환경에서는 contexa.iam.seed.accounts.enabled: false로 만들지 않게 합니다(첫 기동과 기본 데이터).

로그인 요청 한 건이 처리되는 순서

폼 로그인을 세션 상태로 쓰는 경우, 사용자가 로그인 화면에서 제출한 요청은 다음 순서로 처리됩니다.

  1. 요청 도착: 브라우저가 POST /login으로 username · password를 보냅니다.
  2. 체인 선택: 흐름마다 만든 보안 필터 체인 가운데 이 주소를 받는 체인이 요청을 처리합니다. 여러 체인이 받을 수 있으면 order 값이 작은 체인이 먼저입니다.
  3. 계정 조회: CONTEXA 계정 저장소에서 같은 이름의 계정을 찾습니다. 계정이 없으면 로그인은 실패합니다.
  4. 자격 증명 확인: 먼저 계정 상태(잠김 · 비활성 · 계정 유효 기간)를 검사하고, 통과한 계정만 보낸 비밀번호를 저장된 비밀번호와 비교합니다. 비밀번호가 맞으면 마지막으로 비밀번호 유효 기간을 확인합니다.
  5. 성공 처리: 로그인 정보를 담은 보안 컨텍스트를 HTTP 세션에 저장하고, 세션 ID를 새 값으로 바꿉니다(세션 고정 공격 방지). 그다음 원래 가려던 주소나 defaultSuccessUrl로 이동시킵니다.
  6. 다음 요청: 브라우저가 세션 쿠키를 보내면 CONTEXA 저장소가 세션에서 보안 컨텍스트를 꺼내고, 그 사용자에게 저장된 Zero Trust 판정을 적용합니다(로그인 정보 저장).

실패하면 Spring 기본 처리기가 /login?error로 이동시킵니다. 다른 로그인 방법이나 토큰 상태에서 달라지는 점은 아래 각 절과 성공 · 실패 처리에 있습니다.

어떤 방법을 언제 쓰나

처음 고를 때는 클라이언트 종류로 정합니다. 서버가 화면을 그리는 웹 애플리케이션은 폼과 세션 상태, SPA · 모바일 앱 · API 클라이언트는 REST와 토큰 상태가 기본 조합입니다. 비밀번호 없이 로그인하게 하려면 일회용 코드(운영에는 메일 서버가 필요)나 패스키(HTTPS 도메인이 필요, 개발 중에는 localhost)를 더합니다.

방법쓰는 곳기본 order로그인 처리 기본 주소
폼 .form()서버가 그리는 로그인 화면100POST /login
REST .rest()SPA · 모바일 앱 · API 클라이언트(JSON)200POST /api/login
일회용 코드 .ott()메일로 받은 코드로 로그인300발급 POST /ott/generate, 로그인 POST /login/ott
패스키 .passkey()비밀번호 없는 로그인(WebAuthn)400POST /login/webauthn

각 방법은 자기 체인 하나가 됩니다. order · rawHttp · disableCsrf 같은 공통 옵션은 흐름 옵션에 있습니다.

단일 로그인과 MFA 안의 요소

같은 방법을 MFA 흐름 안에서 2차 요소로 쓰면 주소 · 구현 · 진행 관리가 달라집니다. MFA는 적응형 MFA를 참고합니다. 패스키를 예로 들면 다음과 같습니다.

항목단일 패스키MFA 안의 패스키
DSL.passkey(...).mfa(mfa -> mfa.passkey(...))
로그인 처리 주소/login/webauthn/login/mfa-webauthn
구현PasskeyAuthenticationAdapter, Spring 내장 필터MfaPasskeyAuthenticationAdapter, Spring 필터 + CONTEXA 처리기
진행 관리로그인 저장소(SecurityContextRepository)MFA 상태 기계와 MFA 세션

폼 로그인

registry
        .form(form -> form.defaultSuccessUrl("/home"))
        .session(Customizer.withDefaults())
        .build();

loginPage를 주지 않으면 Spring 기본 로그인 화면이 GET /login에 생기고, 그 화면이 POST /login으로 보냅니다.

옵션기본값언제 바꾸나
loginPage(String)없음(Spring 기본 화면 /login)앱이 만든 로그인 화면을 쓸 때. 처리 주소는 바뀌지 않습니다
loginProcessingUrl(String)/login화면이 다른 주소로 보낼 때, 체인 범위가 /login을 포함하지 않을 때
usernameParameter(String) · passwordParameter(String)username · password화면의 입력 이름이 다를 때
defaultSuccessUrl(String), defaultSuccessUrl(String, boolean)없음로그인 뒤 이동할 주소. true면 원래 가려던 주소 대신 늘 이 주소로
failureUrl(String)없음(Spring 기본 /login?error)실패 뒤 이동할 주소
permitAll()꺼짐로그인 화면 · 처리 주소를 인증 없이 열어야 할 때
rawFormLogin(...)없음Spring FormLoginConfigurer를 직접 만질 때. 여러 번 부르면 마지막 것만 남습니다. MFA의 1차 로그인에 쓰면 애플리케이션이 시작하지 않습니다
로그인 화면만 바꾸면 처리 주소는 그대로 /login입니다. Spring Security에서는 loginPage가 처리 주소도 정하지만, CONTEXA 폼 흐름은 처리 주소를 contexa.auth.urls.single.form-login-processing(기본 /login)으로 먼저 정합니다. 체인 범위를 좁혔다면 loginProcessingUrl도 함께 바꿉니다. 
registry
        .form(form -> form
                .loginPage("/admin/login")
                .loginProcessingUrl("/admin/login")
                .permitAll()
                .rawHttp(http -> http.securityMatcher("/admin/**"))
                .rawFormLogin(login -> login.usernameParameter("email")))
        .session(Customizer.withDefaults())
        .build();

여기서 /admin/login 화면은 앱이 만들어야 합니다. 응답을 직접 만들려면 successHandler(...) · failureHandler(...)를 줍니다(성공 · 실패 처리).

확인하기

  • 보호된 주소를 열면 로그인 화면으로 이동합니다.
  • 로그인에 성공하면 defaultSuccessUrl(또는 원래 가려던 주소)로, 실패하면 /login?error로 갑니다.

REST 로그인

JSON 본문으로 로그인합니다. 주로 토큰 상태와 함께 쓰며, 세션 상태와도 함께 쓸 수 있습니다.

registry
        .rest(rest -> rest.defaultSuccessUrl("/app"))
        .oauth2(Customizer.withDefaults())
        .build();
POST /api/login
Content-Type: application/json

{"username": "alice", "password": "s3cret"}
상태성공 응답(200, JSON)
.oauth2(), HEADER 전송(기본)accessToken, tokenType(Bearer), expiresIn, refreshToken, refreshExpiresIn, tokenTransportMethod, authenticated, redirectUrl, message, username
.session()authenticated, redirectUrl, message, username, stateType(SESSION) + 세션 쿠키
  • 로그인 처리 주소는 POST만 받습니다. 같은 주소의 GET /api/login에는 기본 로그인 화면이 나옵니다. loginProcessingUrl로 주소를 바꾸면 화면도 그 주소에 있습니다.
  • .session()에서는 브라우저가 로그인으로 보내지기 전에 요청했던 페이지가 있으면 redirectUrl이 그 페이지입니다(경로와 쿼리). defaultSuccessUrl(url, true)면 언제나 url입니다.
  • 로그인에 실패하면 401 상태와 JSON 본문으로 응답합니다. 실패 응답은 요청을 받고 최소 contexa.auth.mfa.minimum-delay-ms(기본 500ms)가 지나야 나갑니다. 비밀번호를 연속으로 바꿔 넣는 무차별 대입 공격의 속도를 늦추기 위해서입니다.
  • .oauth2()가 세션을 만들지 않는 구성(STATELESS)을 이미 적용하므로 rawHttp로 따로 지정할 필요가 없습니다. .oauth2()를 쓰면 contexa.auth.oauth2.client-secret이 반드시 있어야 합니다(토큰 상태에 반드시 필요한 설정).
옵션기본값언제 바꾸나
loginProcessingUrl(String)/api/loginAPI 경로 규칙이 다를 때
defaultSuccessUrl(...) · failureUrl(String)없음응답의 redirectUrl · 실패 뒤 이동 주소
securityContextRepository(...)없음REST 흐름은 이 옵션을 지정했을 때만 로그인 저장소를 바꿉니다

확인하기

GET /api/orders
Authorization: Bearer <accessToken>

받은 accessToken을 실으면 보호된 API가 응답하고, 빼면 401이 옵니다.

일회용 코드(OTT)

사용자 이름을 받아 일회용 코드를 메일로 보내고, 그 코드로 로그인합니다.

registry
        .ott(Customizer.withDefaults())
        .session(Customizer.withDefaults())
        .build();
  • 발송 서비스: 기본 OneTimeTokenService 빈은 EmailOneTimeTokenService입니다. 코드를 CONTEXA DB의 ctxa_one_time_tokens 표에 두고 Spring 메일(spring.mail.*)로 보냅니다.
  • 받는 주소: 사용자 표(ctxa_users)의 메일 주소입니다. 주소가 없으면 사용자 이름을 주소로 씁니다. 요청의 email이 등록된 주소와 다르면 거부합니다.
  • 메일을 보내지 않는 경우: 계정이 없거나, 잠기거나 비활성이거나 만료된 계정이면 코드를 만들지도 메일을 보내지도 않습니다. 이때 응답은 정상 발급과 같아 보이므로, 코드를 요청해서 계정이 있는지 알아낼 수 없습니다. 코드 로그인은 비밀번호를 쓰지 않으므로, 비밀번호가 만료된 계정도 코드로 로그인할 수 있습니다.
  • 재발송 간격: 같은 주소로는 contexa.auth.mfa.email-resend-interval-seconds(기본 120초)에 메일 한 통만 보냅니다. 그 안에 다시 요청하면 새 코드를 만들지 않고 먼저 받은 코드가 그대로 유효합니다. 메일 주소는 대소문자와 공백이 달라도 같은 주소로 봅니다.
  • 메일을 보내지 못하면: contexa.auth.ott.fail-on-email-error(기본 true)이면 발급이 실패합니다. false면 코드는 만들고 경고 로그만 남깁니다.
  • 발송 제한: 한 번에 보내는 메일은 contexa.auth.ott.email-max-concurrent-sends(기본 64)통까지입니다. 요청은 여유가 생길 때까지 contexa.auth.ott.email-send-wait-seconds(기본 5)초 기다리고, 그래도 자리가 없으면 메일을 보내지 못한 때와 같이 실패합니다. contexa.auth.ott.email-smtp-timeout-seconds(기본 0, 정하지 않음)는 SMTP 연결 · 읽기 · 쓰기의 제한 시간입니다. 값을 주면 spring.mail.properties.mail.smtp.*timeout이 정하지 않은 항목에 한해 앱의 메일 발송기에 써넣으므로, 그 발송기로 보내는 앱의 다른 메일에도 적용됩니다.
  • 유효 시간: 단일 일회용 코드 로그인의 코드는 만든 뒤 5분 동안 유효합니다(Spring 기본값). MFA 안의 일회용 코드는 6자리이며 contexa.auth.mfa.otp-token-validity-seconds(기본 300초) 동안 유효합니다. 메일 안내 문구의 분 수는 두 경우 모두 이 설정에서 옵니다.
  • 개발 · 시험 때의 코드 확인: 개발 프로파일(local · dev · development · test)이 켜져 있거나 메일 서버가 설정되지 않았으면, 코드를 메일과 함께 로그(WARN)에도 남깁니다. 메일 서버 없이도 로그인을 끝낼 수 있게 하기 위해서이며, 이때는 메일을 보내지 못해도 로그인이 실패하지 않습니다. 운영 환경에서는 메일로만 보냅니다. contexa.auth.ott.code-to-console로 직접 정할 수 있습니다(true · false).

발송 서비스를 바꾸려면 옵션이 아니라 빈으로 등록합니다. DSL의 tokenService(...)는 코드 발급에만 쓰이고, 코드 확인은 OneTimeTokenService 빈으로 합니다. 옵션으로 다른 서비스를 주면 확인이 실패합니다. 빈을 등록하면 발급과 확인 모두 그 빈을 씁니다. 
@Bean
public OneTimeTokenService oneTimeTokenService() {
    // 예: 시험용 메모리 저장. 이 서비스는 메일을 보내지 않으므로 코드 전달은 앱이 맡습니다.
    return new InMemoryOneTimeTokenService();
}

패스키

WebAuthn 패스키로 비밀번호 없이 로그인합니다. 패스키는 서비스의 도메인(신뢰 당사자 ID, rpId)에 묶여 만들어지고, 브라우저는 로그인할 때 이 도메인과 접속한 출처(origin, 프로토콜 · 호스트 · 포트)를 확인합니다. 그래서 두 값을 운영 주소에 맞춰야 합니다.

registry
        .passkey(Customizer.withDefaults())
        .session(Customizer.withDefaults())
        .build();
contexa:
  auth:
    urls:
      factors:
        passkey:
          rp-id: example.com
          rp-name: Example
          allowed-origins: https://app.example.com
옵션기본값언제 바꾸나
rpId(String)localhost운영 도메인으로 바꿉니다. 기본값은 설정 contexa.auth.urls.factors.passkey.rp-id에서 옵니다
rpName(String)contexa-identity사용자에게 보이는 서비스 이름
allowedOrigins(...)http://localhost: + server.port(없으면 8080)브라우저가 접속하는 출처. 설정 allowed-origins(쉼표로 여러 개)가 있으면 그 값
assertionOptionsEndpoint(String) · loginProcessingUrl(String)/webauthn/authenticate/options · /login/webauthn단일 패스키 흐름에서는 반영되지 않고 Spring 기본 주소를 씁니다
  • 세션 상태의 패스키 흐름에서는 successHandler · failureHandler 옵션이 쓰이지 않습니다. 토큰 상태와 MFA의 패스키 요소에서는 다른 방법과 같이 호출됩니다(성공 · 실패 처리).
  • 패스키 로그인은 그 패스키가 속한 CONTEXA 계정의 로그인이며, 비밀번호 로그인과 같은 계정입니다. 이를 위해 계정을 따로 만들지 않습니다.
  • rpId가 비어 있으면 시작할 때 설정 검사기가 오류 로그를 남깁니다. 시작은 막지 않습니다.
  • CONTEXA DB가 있으면(contexaJdbcTemplate 빈) 패스키 정보를 저장하는 Spring JDBC 저장소(JdbcUserCredentialRepository, JdbcPublicKeyCredentialUserEntityRepository)가 자동 등록됩니다.

패스키 등록

로그인한 사용자가 패스키를 등록합니다. 등록 화면 GET /webauthn/register는 CONTEXA 화면으로 바뀌어 있습니다.

성공 · 실패 처리

successHandler · failureHandler를 주지 않으면 CONTEXA가 흐름 종류와 상태에 맞는 처리기를 고릅니다. 표에서 단일은 MFA가 아닌 흐름, MFA 1차는 MFA의 첫 로그인, MFA 2차 요소는 그 뒤의 일회용 코드 · 패스키입니다.

흐름상태성공실패
단일 폼 · 일회용 코드세션Spring 기본(defaultSuccessUrl로 이동)Spring 기본(failureUrl로 이동)
단일 REST세션SessionSingleAuthSuccessHandlerSessionSingleAuthFailureHandler
단일 패스키세션Spring 기본 JSON 응답(로그인 기록 포함)Spring 기본
단일 모든 방법토큰OAuth2SingleAuthSuccessHandler(토큰 발급)OAuth2SingleAuthFailureHandler
MFA 1차모두PrimaryAuthenticationSuccessHandlerUnifiedAuthenticationFailureHandler
MFA 2차 요소모두MfaFactorProcessingSuccessHandlerUnifiedAuthenticationFailureHandler
  • CONTEXA 처리기는 요청이 Accept · Content-Type에 JSON을 담았거나 경로에 /api/가 있으면 JSON으로, 아니면 이동(redirect)으로 답합니다.
  • 토큰 상태에서도 단일 흐름의 화면 로그인은 세션 상태처럼 로그인으로 보내지기 전에 요청했던 페이지로 갑니다(defaultSuccessUrl(url, true)면 언제나 url). 실패한 화면 로그인은 흐름의 failureUrl, 없으면 세션 상태처럼 그 흐름의 로그인 화면에 ?error를 붙인 주소(/login?error)로 갑니다.
  • 비밀번호는 맞지만 유효 기간이 지났을 때, REST 흐름 · 토큰 상태의 폼 흐름 · MFA 1차 로그인은 비밀번호 변경 화면으로 안내합니다. 브라우저는 /contexa/password-change?expired=true로 이동시키고, 스크립트 요청에는 401 CREDENTIALS_EXPIRED와 그 화면 주소 nextStepUrl로 응답합니다. 계정 이름은 세션에 담아 변경 화면에 넘깁니다. 세션 상태의 폼 흐름은 일반 로그인 실패로 응답합니다. 일회용 코드 · 패스키 로그인은 비밀번호를 쓰지 않습니다(일회용 코드).
  • 폼 · REST 흐름에 successHandler를 주면 자동 처리기 대신 그 처리기가 바로 붙습니다. 토큰 상태라도 CONTEXA가 토큰을 발급하지 않으므로 응답은 그 처리기가 책임집니다.
  • 일회용 코드 흐름은 자동 처리기가 있으면 그것이 우선입니다. 토큰 상태에서는 준 처리기가 토큰 발급 뒤에 먼저 호출되고, 그 처리기가 응답을 쓰지 않으면 CONTEXA가 씁니다.
  • MFA 흐름에서는 1차 로그인이나 요소에 준 successHandler가 로그인이 그 단계에서 끝날 때 호출됩니다. 정책이 요소를 요구하지 않으면 1차 로그인의 것이, 요소를 요구했으면 로그인을 끝낸 요소의 것이 호출됩니다. failureHandler는 자기 단계의 실패에 호출됩니다. 각 처리기는 자기 흐름의 자기 단계에서만 호출되며, 처리기가 응답을 쓰지 않았으면 CONTEXA가 이어서 씁니다.
  • MFA의 결과 처리는 MFA 결과 처리를 참고합니다.
