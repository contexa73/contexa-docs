contexa-identity

인증 DSL

Contexa가 로그인을 맡을 때, 로그인 방법(폼 · REST · 일회용 코드 · 패스키 · MFA)과 로그인 상태(세션 · 토큰)를 메서드 하나에 적으면 Contexa가 흐름마다 Spring Security 체인을 만들어 줍니다. 켜는 조건, 첫 체인 만들기, 여러 체인 나누기, 모든 체인 공통 설정과 체인 하나만 바꾸는 설정, 기존 Spring Security 설정에서 옮기는 방법을 설명합니다.

Contexa가 로그인을 맡을 때(CONTEXA_OWNED)의 기능입니다. 기본값 HOST_OWNED에서는 앱의 Spring Security가 로그인을 맡고, 여기에 적은 흐름으로 체인이 만들어지지 않습니다. 앱의 기존 로그인을 그대로 쓰려면 기존 로그인과 연결하기를 보세요.

한눈에 보기

PlatformConfig 빈 하나에 흐름을 차례로 적습니다. 흐름 하나는 인증 방법 하나와 로그인 상태 하나의 쌍입니다. 시작할 때 Contexa가 흐름마다 SecurityFilterChain 빈을 하나씩 등록하고, 요청이 오면 순서(order)가 낮은 체인부터 비교해 처음 맞는 체인 하나가 그 요청을 처리합니다.

켜는 조건: 로그인을 누가 맡나

Contexa에는 로그인을 누가 맡는지 정하는 인증 소유권(contexa.bridge.ownership)이 있습니다. DSL로 적은 흐름은 CONTEXA_OWNED일 때만 체인이 됩니다.

켜는 방법

방법결과
contexa.bridge.ownership: CONTEXA_OWNED로그인만 Contexa에 맡깁니다. 이 값을 적으면 어노테이션의 모드보다 우선합니다.
@EnableAISecurity(mode = SecurityMode.FULL)소유권을 적지 않았으면 CONTEXA_OWNED가 됩니다. Contexa가 앱 전체를 맡는 모드라서, 앱에 DataSource 빈이 없으면 Contexa DB를 앱의 기본 DataSource로 씁니다(contexa.datasource.isolation.contexa-owned-application).
 
contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: contexa
  bridge:
    ownership: CONTEXA_OWNED

인증 DSL은 spring-boot-starter-contexa에 들어 있습니다. 스타터가 identity · iam · core · autoconfigure · common 모듈과 Spring Authorization Server를 함께 가져오므로 따로 넣을 의존성은 없습니다.

DSL · 체인 · 요청 시점 필터 자동 구성을 모두 끄려면 contexa.identity.security-core.enabled: false를 둡니다.

PlatformConfig를 정의하지 않으면

앱이 PlatformConfig 빈을 두지 않으면 @EnableAISecurity가 아래 기본 구성을 씁니다. 자기 빈을 두면 기본 구성은 쓰이지 않습니다.

모드모든 체인 공통흐름
FULL정적 경로(/contexa/css/**, /contexa/js/**, /images/**, /favicon.ico)는 허용, 나머지 요청은 Contexa 동적 인가(CustomDynamicAuthorizationManager)MFA 흐름 하나: 1차 폼 로그인 + 패스키 + 일회용 코드, 필요한 요소 1개, order 100, 세션 상태
SANDBOX(기본 모드)체인을 만들지 않음: SANDBOX의 소유권은 언제나 HOST_OWNED이고, 거기서는 PlatformConfig가 체인이 되지 않음없음(SANDBOX 모양 체인은 없음)

첫 체인 만들기

폼 로그인 하나를 세션 상태로 쓰는 가장 작은 구성입니다. 설정 클래스에는 @Configuration을 꼭 붙이세요. Spring Security 6의 @EnableWebSecurity에는 @Configuration이 들어 있지 않아서, 그것만 붙이면 PlatformConfig 빈이 등록되지 않습니다.

@Configuration
public class LoginFlowsConfig {

    @Bean
    public PlatformConfig platformDslConfig(IdentityDslRegistry<HttpSecurity> registry) throws Exception {
        return registry
                .global(http -> http.authorizeHttpRequests(auth -> auth
                        .requestMatchers("/css/**", "/js/**").permitAll()
                        .anyRequest().authenticated()))
                .form(form -> form.defaultSuccessUrl("/home"))
                .session(Customizer.withDefaults())
                .build();
    }
}

이 구성으로 생기는 것:

  • 체인 빈 contexaform_flowSecurityFilterChain1 하나. 이 흐름은 범위를 정하지 않았으므로 모든 요청을 받습니다.
  • 로그인 화면은 Spring 기본 화면 GET /login, 로그인 처리는 POST /login(contexa.auth.urls.single.form-login-processing)입니다.
  • 로그인하면 세션 ID가 바뀌고(세션 고정 방지), /logout으로 로그아웃합니다.
  • CSRF는 Spring 기본대로 켜져 있습니다.

확인하기

  • 보호된 주소를 브라우저로 열면 /login으로 이동하고, 로그인하면 /home으로 갑니다.
  • 시작 로그에 Skipping Contexa-owned authentication chain bootstrap in HOST_OWNED mode가 보이면 소유권이 HOST_OWNED라서 체인을 만들지 않은 것입니다.
  • 어떤 흐름이 요청을 하나도 받지 못하면 시작 로그에 Flow '…' is never reached 오류가 남습니다(여러 체인 나누기).

인증 방법과 상태 고르기

인증 방법 메서드 다음에는 상태 메서드를 부르도록 되어 있습니다. 상태 메서드는 바로 앞에 적은 인증 방법에 붙습니다.

인증 방법쓰는 곳기본 order흐름 이름
.form(...)서버가 그리는 로그인 화면(폼 로그인)100form_flow
.rest(...)SPA · 모바일 · API의 JSON 로그인(REST 로그인)200rest_flow
.ott(...)메일로 받은 일회용 코드(일회용 코드)300ott_flow
.passkey(...)패스키(패스키)400passkey_flow
.mfa(...)1차 로그인 + 2차 요소(적응형 MFA)200mfa
상태하는 일
.session(...)로그인을 HTTP 세션에 저장, 로그인할 때 세션 ID를 바꿈, 로그아웃을 구성(세션 상태)
.oauth2(...)토큰(JWT)을 발급 · 검증. 기본으로 리소스 서버와 인가 서버를 함께 구성하고, contexa.auth.oauth2.client-secret이 꼭 있어야 합니다(토큰 상태)
  • 같은 방법을 여러 번 쓰면 흐름 이름이 form_flow, form_flow_2, form_flow_3처럼 붙습니다.
  • 같은 .form()이라도 흐름마다 다른 상태를 고를 수 있습니다. 인증 방법 다섯 가지와 상태 두 가지를 자유롭게 짝지을 수 있습니다.
  • .session(...) · .oauth2(...)에 넘긴 람다는 그 상태의 구성자에 적용됩니다. 토큰 상태에서는 요청 범위(requestScope, tokenScopeRequests)를 여기서 정합니다.
  • 상태를 정하지 않은 흐름은 성공 · 실패 처리기만 contexa.auth.state-type(기본 OAUTH2)을 따르고, 세션 · 토큰 구성은 붙지 않습니다. 흐름마다 상태를 꼭 정하세요.

여러 체인 나누기

체인은 order가 낮은 것부터 비교됩니다. 범위를 정하지 않은 체인은 모든 요청을 받으므로, 그 뒤에 놓인 체인은 요청을 받지 못합니다. 이때 Contexa는 시작 로그에 두 흐름을 밝혀 Flow '…' is never reached 오류를 남깁니다. order가 같으면 적은 순서대로 비교합니다.

범위 정하는 방법쓰는 흐름효과
rawHttp(http -> http.securityMatcher("/admin/**"))폼 · REST · 일회용 코드 · 패스키그 주소 아래 요청만 받음
.mfa(mfa -> mfa.urlPrefix("/admin"))MFA모든 MFA 주소에 접두사가 붙고 체인 범위가 /admin/**가 됨(여러 MFA 흐름)
.oauth2(oauth2 -> oauth2.requestScope(OAuth2RequestScope.TOKEN_REQUESTS))토큰 상태토큰을 실은 요청과 그 흐름의 인증 주소만 받고, 나머지는 다음 흐름으로 넘김(요청 범위)
폼 흐름의 범위를 좁힐 때는 로그인 처리 주소도 함께 바꾸세요. 폼 흐름의 로그인 처리 주소는 loginPage가 아니라 contexa.auth.urls.single.form-login-processing(기본 /login)입니다. 범위가 /admin/**인 체인에 loginPage("/admin/login")만 주면 로그인 POST(/login)가 다른 체인으로 갑니다. 같은 처리 주소를 두 흐름이 써도 시작은 막히지 않으므로 주의하세요. 
registry
        .global(http -> http.authorizeHttpRequests(auth -> auth.anyRequest().authenticated()))
        // 관리자: /admin 아래만, 직접 만든 로그인 화면
        .form(form -> form.order(10)
                .loginPage("/admin/login")
                .loginProcessingUrl("/admin/login")
                .defaultSuccessUrl("/admin")
                .permitAll()
                .rawHttp(http -> http.securityMatcher("/admin/**")))
        .session(Customizer.withDefaults())
        // API 클라이언트: 토큰을 실은 요청만
        .rest(rest -> rest.order(50))
        .oauth2(oauth2 -> oauth2.requestScope(OAuth2RequestScope.TOKEN_REQUESTS))
        // 그 밖의 사용자: 나머지 모든 요청
        .form(form -> form.order(100).defaultSuccessUrl("/home"))
        .session(Customizer.withDefaults())
        .build();

체인의 실제 순서 값은 Ordered.HIGHEST_PRECEDENCE + 흐름의 order라서, 앱이 따로 등록한 SecurityFilterChain 빈보다 앞에 섭니다.

모든 체인에 같은 설정(global)

global(http -> ...) 람다는 모든 흐름의 HttpSecurity에 가장 먼저 적용됩니다. 흐름별 설정은 그다음에 적용되므로 같은 항목이면 흐름 설정이 이깁니다. 예를 들어 흐름 옵션의 disableCsrf()는 그 체인의 CSRF만 끕니다. global 람다가 예외를 던지면 그 흐름에 경고 로그만 남기고 계속 진행합니다.

CSRF

흐름CSRF
세션 상태Spring 기본대로 켜져 있습니다.
토큰 상태, HEADER · HEADER_COOKIE 전송인가 서버를 포함하는 서버 모드(기본 COMBINED)에서는 contexa.auth.oauth2-csrf(기본 false)를 따르므로 기본으로 꺼집니다.
토큰 상태, COOKIE 전송늘 켜집니다. 브라우저가 쿠키를 자동으로 보내기 때문입니다. contexa.auth.oauth2-csrf: false를 적으면 시작이 실패합니다.
흐름 옵션 disableCsrf()그 체인만 끕니다.

쿠키로 CSRF 토큰을 주고받으려면 Spring 설정을 global에 둡니다.

registry
        .global(http -> http.csrf(csrf -> csrf
                .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())))
        // ... 흐름들

로그인 저장소

@EnableAISecurity를 쓰면 Contexa가 모든 흐름에 세션 로그인 저장소(AISessionSecurityContextRepository)를 global 다음 차례에 넣습니다. 그래서 global에서 securityContext(sc -> sc.securityContextRepository(...))를 지정해도 이 저장소로 바뀝니다. 직접 연결할 필요는 없습니다.

이 저장소는 Spring의 HttpSessionSecurityContextRepository를 확장합니다. 로그인 정보를 꺼낼 때 무효화된 세션이면 세션을 끝내고 빈 로그인을 돌려주고, 아니면 저장된 판정에 맞게 권한을 바꿉니다(권한이 바뀌는 방식). 저장할 때는 강제 로그아웃에 쓰는 세션 추적을 기록합니다.

CORS와 직접 만든 필터

CORS 설정이나 앱의 필터도 global(모든 체인) 또는 흐름 옵션 rawHttp(체인 하나)에 Spring 방식 그대로 적습니다. 앱의 필터는 같은 람다 안에서 http.addFilterBefore(...)로 넣습니다.

registry
        .global(http -> http.cors(cors -> cors.configurationSource(request -> {
            CorsConfiguration config = new CorsConfiguration();
            config.setAllowedOrigins(List.of("https://app.example.com"));
            config.setAllowedMethods(List.of("GET", "POST"));
            config.setAllowCredentials(true);
            return config;
        })))
        // ... 흐름들

체인 하나만 바꾸기(흐름 옵션)

인증 방법 메서드의 람다에서 쓰는 옵션입니다. 방법별 옵션(로그인 화면, 파라미터 이름 등)은 로그인 방법에 있습니다.

옵션쓸 수 있는 방법언제 쓰나
order(int)폼 · REST · 일회용 코드 · 패스키체인을 비교하는 순서를 바꿀 때. MFA는 .mfa(mfa -> mfa.order(...))
loginProcessingUrl(String)폼 · REST · 일회용 코드 · 패스키로그인 POST 주소를 바꿀 때. 단일 패스키 흐름에는 반영되지 않습니다
defaultSuccessUrl(...) · failureUrl(String)폼 · REST로그인 성공 · 실패 뒤 이동할 주소
successHandler(...) · failureHandler(...)폼 · REST · 일회용 코드응답을 직접 만들 때(성공 · 실패 처리). 패스키 흐름에서는 쓰이지 않습니다
securityContextRepository(...)모든 방법로그인 저장 위치를 바꿀 때. 세션 상태에서는 Contexa 세션 저장소가 우선합니다
disableCsrf()모든 방법그 체인만 CSRF를 끌 때
cors(...) · headers(...) · sessionManagement(...) · logout(...)모든 방법그 체인의 Spring 설정을 바꿀 때
authorizeStaticPermitAll(...)모든 방법정적 경로를 인증 없이 열 때
rawHttp(...)모든 방법위에 없는 Spring 설정, 체인 범위(securityMatcher). 여러 번 부르면 차례로 모두 적용됩니다
asep(...)모든 방법현재 버전에서는 효과가 없습니다(ASEP)
  • 옵션은 global 다음에 적용됩니다. rawHttp 람다는 SafeHttpCustomizer라서 검사 예외를 던질 수 있습니다.
  • .mfa()에는 이 옵션들이 없습니다. MFA 흐름의 범위는 urlPrefix로 정하고, rawHttp는 1차 로그인 · 2차 요소의 옵션 안에서 씁니다.
  • global은 옵션 없이 HttpSecurity 람다를 바로 받습니다.
registry
        .form(form -> form
                .rawHttp(http -> http.securityMatcher("/portal/**"))
                .rawHttp(http -> http.headers(headers -> headers.frameOptions(frame -> frame.sameOrigin()))))
        .session(Customizer.withDefaults())
        .build();

완전한 예제

API 클라이언트는 토큰, 관리자는 /admin 아래 MFA, 그 밖의 사용자는 폼 로그인을 쓰는 구성입니다.

@Configuration
public class LoginFlowsConfig {

    @Bean
    public PlatformConfig platformDslConfig(IdentityDslRegistry<HttpSecurity> registry) throws Exception {
        return registry
                .global(http -> http.authorizeHttpRequests(auth -> auth
                        .requestMatchers("/css/**", "/js/**", "/favicon.ico").permitAll()
                        .anyRequest().authenticated()))
                // 1. API 클라이언트 · 에이전트: 토큰을 실은 요청만
                .rest(rest -> rest.order(50))
                .oauth2(oauth2 -> oauth2.requestScope(OAuth2RequestScope.TOKEN_REQUESTS))
                // 2. 관리자: /admin 아래 MFA
                .mfa(mfa -> mfa.urlPrefix("/admin").order(80)
                        .primaryAuthentication(primary -> primary.formLogin(form -> form.defaultSuccessUrl("/admin")))
                        .passkey(Customizer.withDefaults())
                        .ott(Customizer.withDefaults()))
                .session(Customizer.withDefaults())
                // 3. 그 밖의 사용자: 폼 로그인
                .form(form -> form.order(100).defaultSuccessUrl("/home"))
                .session(Customizer.withDefaults())
                .build();
    }
}
contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: contexa
  bridge:
    ownership: CONTEXA_OWNED
  auth:
    oauth2:
      client-secret: replace-with-a-long-random-secret   # .oauth2() 흐름이 있으면 필수

spring:
  mail:
    host: smtp.example.com   # MFA의 일회용 코드를 메일로 보냄
    port: 587
  • 토큰 서명 키스토어를 지정하지 않으면 시작할 때마다 바뀌는 임시 키를 씁니다. 운영 설정은 토큰 상태에 꼭 필요한 설정을 보세요.
  • 메일 발송 설정이 없으면 일회용 코드 발급이 실패합니다(일회용 코드).

동작 원리

검사기는 로그인 처리 주소 중복, MFA 흐름 구조, 패스키 옵션(rpId), MFA 패스키 등록 경로, 인증 방법 구현 존재, 흐름 이름 중복을 봅니다. 검사 결과는 시작을 막지 않고, 일부 검사기만 오류 로그를 남깁니다(로그인 처리 주소 중복은 로그도 남기지 않습니다).

구성자 순서

순서 값은 구성자를 적용하는 차례이지 필터의 위치가 아닙니다. 필터 위치는 필터가 도는 곳에 있습니다.

순서 값구성자가 하는 일
HIGHEST_PRECEDENCE + 100global 람다 적용
HIGHEST_PRECEDENCE + 105Contexa 세션 로그인 저장소 연결

확장점: 모든 체인에 구성 더하기

SecurityConfigurer를 구현한 빈을 두면 Contexa가 모든 흐름의 체인에 적용합니다. getOrder()로 위 표의 어느 차례에 들어갈지 정합니다(기본 500).

@Bean
public SecurityConfigurer chainNameHeaderConfigurer() {
    return new SecurityConfigurer() {
        @Override
        public void init(PlatformContext ctx, PlatformConfig config) {
        }

        @Override
        public void configure(FlowContext fc) throws Exception {
            String flowName = fc.flow().getTypeName();
            fc.http().headers(headers -> headers.addHeaderWriter(
                    new StaticHeadersWriter("X-Login-Flow", flowName)));
        }
    };
}

기존 Spring Security 설정에서 옮기기

  1. 소유권을 CONTEXA_OWNED로 둡니다(켜는 방법).
  2. SecurityFilterChain 빈을 PlatformConfig 하나로 옮깁니다. 체인 하나가 흐름 하나입니다. securityMatcher는 rawHttp로, @Order는 order로 옮깁니다.
  3. URL 규칙을 Contexa 동적 인가로 바꾸려면 global에서 anyRequest().access(customDynamicAuthorizationManager)를 씁니다(기본 FULL 구성과 같습니다). 그러면 URL 결정은 관리 콘솔의 정책이 맡습니다. 리소스 스캐너는 엔드포인트를 리소스로 등록할 뿐 hasRole 규칙을 읽어 정책을 만들지 않으므로, 같은 규칙의 정책을 먼저 만들어 두세요(리소스 스캐너, 정책).
  4. 정책이 하나도 맞지 않는 URL은 기본으로 로그인한 사용자에게만 열립니다(contexa.policy.no-matching-url-policy-decision, 기본 AUTHENTICATED. PERMIT이면 모두에게 열립니다).
  5. 집행 모드는 URL 정책과 상관이 없습니다. contexa.security.zerotrust.mode(기본 ENFORCE)를 SHADOW로 두면 AI 판정을 저장 · 적용하지 않을 뿐, URL 정책 결정은 그대로 집행됩니다. 정책은 시험 환경에서 확인하세요(집행 모드).
// 옮기기 전
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain appChain(HttpSecurity http) throws Exception {
        return http
                .authorizeHttpRequests(auth -> auth
                        .requestMatchers("/admin/**").hasRole("ADMIN")
                        .anyRequest().authenticated())
                .formLogin(Customizer.withDefaults())
                .build();
    }
}
// 옮긴 뒤: /admin/** 규칙은 관리 콘솔의 정책으로 만들어 둡니다
@Configuration
public class SecurityConfig {

    @Bean
    public PlatformConfig platformDslConfig(IdentityDslRegistry<HttpSecurity> registry,
                                            CustomDynamicAuthorizationManager customDynamicAuthorizationManager) throws Exception {
        return registry
                .global(http -> http.authorizeHttpRequests(auth -> auth
                        .requestMatchers("/css/**", "/js/**").permitAll()
                        .anyRequest().access(customDynamicAuthorizationManager)))
                .form(Customizer.withDefaults())
                .session(Customizer.withDefaults())
                .build();
    }
}
