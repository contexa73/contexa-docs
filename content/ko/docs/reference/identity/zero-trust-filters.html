요청 시점 집행

저장된 판정(허용 · 추가 인증 · 차단 · 검토 보류 · 분석 대기)이 사용자의 다음 요청에 어떻게 적용되는지 설명합니다. 판정마다 사용자가 받는 응답, 바뀌는 권한, 푸는 방법, 필터가 보안 체인 안 어디서 도는지, 에이전트 요청은 어떻게 다른지를 이 페이지에서 한 번에 봅니다.

이 필터들은 두 소유 방식 모두에서 같은 응답으로 동작합니다. Contexa가 로그인을 맡을 때(CONTEXA_OWNED)는 서블릿 등록을 끈 채 Contexa가 만든 보안 체인에 들어갑니다. 기본값 HOST_OWNED에서는 Contexa가 체인을 만들지 않고, 같은 필터가 앱의 Spring Security 체인 바로 뒤에서 서블릿 필터로 돕니다(HOST_OWNED에서). 그래서 앱 체인이 먼저 사용자를 정하고 앱 규칙을 적용한 뒤, 모든 경로에서 집행합니다. 이때 CHALLENGE는 Contexa MFA 대신 Contexa의 추가 확인으로 갑니다(HOST_OWNED의 추가 확인). 저장된 BLOCK · CHALLENGE · ESCALATE는 @Protectable 메서드 앞에서도 거부합니다(보호 메서드). 앱의 기존 로그인을 쓰는 방법은 기존 로그인과 연결하기에 있습니다.

한눈에 보기

판정은 응답이 나간 뒤 비동기로 만들어져 판정 저장소에 쓰이고(판정 엔진), 그 사용자의 다음 요청에서 적용됩니다. 로그인하지 않은 요청은 이 필터들이 그냥 통과시킵니다.

MFA 시작은 사용자마다 잠금(mfa:challenge:init:<사용자>)으로 한 번만 하며, 잠금 대기 · 임대 시간 · 재시도 안내 초는 설정으로 바꿉니다(설정). HOST_OWNED에서는 위 표의 앞 네 줄이 생기지 않습니다. Contexa MFA를 시작하지 않고, 사람에게는 아래 추가 확인으로 답합니다.

HOST_OWNED의 추가 확인

앱이 로그인을 맡을 때 Contexa는 자기 MFA 흐름을 시작하지 않고, 앱의 로그인 · 세션 · 쿠키도 바꾸지 않습니다. CHALLENGE면 사용자를 챌린지 안내 화면을 거쳐 확인 전용 추가 확인 /contexa/step-up으로 보냅니다. 추가 확인 화면은 앱 체인을 거쳐 들어오므로 사용자는 앱이 로그인시킨 그 사람이고, 화면의 POST 요청에는 앱의 CSRF 보호가 그대로 걸립니다. 통과하면 Contexa MFA를 마친 것과 같은 방식으로 기록되어 CHALLENGE가 ALLOW가 됩니다.

요인이럴 때 보여 줌
패스키이 사용자의 패스키가 Contexa에 등록되어 있을 때. 첫 패스키는 같은 화면에서 등록할 수 있지만, 판정 제한(CHALLENGE · BLOCK · ESCALATE)이 걸려 있지 않을 때만 됩니다. 신뢰 당사자 설정 contexa.auth.urls.factors.passkey.*을 씁니다
메일 일회용 코드Contexa에 있는 이 사용자 사본에 실제 이메일 주소가 있고(contexa.bridge.sync.synthetic-email-domain의 주소가 아님) 메일이 설정되어 있을 때(spring.mail.*)
앱 자체 재인증앱이 자기 MFA나 신원 공급자로 사용자를 다시 인증한 경우. 인증 도장에 CHALLENGE보다 늦은 인증 시각의 MFA 완료가 보이면, 챌린지 필터가 그 요청에서 스스로 CHALLENGE를 풉니다. contexa.bridge.step-up.reauthentication-url을 설정하면 화면에 그 주소로 가는 링크가 나옵니다
  • 사용자는 브리지가 관리하는 앱 사용자 사본만 씁니다. 그래서 앱 사용자가 이름이 같은 Contexa 계정과 섞이지 않습니다.
  • 관리자가 MFA로 해제하도록 허용한 BLOCK도 같은 화면(?purpose=block)으로 갑니다(차단 해제).
  • 에이전트 요청은 요인에 답하지 않고, 책임자 확인으로 갑니다(에이전트 요청).
  • 화면이 내준 값(패스키 옵션)은 세션이 아니라 사용자의 판정 키 아래에 둡니다. 메모리에, contexa.infrastructure.mode: distributed면 Redis에 둡니다.
  • 확인 코드는 사용자마다 30초에 한 통만 메일로 보냅니다. 그 안에 다시 요청하면 보내지 않고(응답이 기다리라고 알려 줍니다), 그래서 추가 확인 중인 세션이 사용자의 편지함을 채울 수 없습니다. 코드는 한 번만 쓸 수 있어, 다시 쓰거나 여러 요청이 동시에 쓰면 첫 요청만 통과합니다.
  • Contexa 화면의 스크립트 · 스타일 · 이미지(/contexa/js/, /contexa/css/, /contexa/img/)는 판정이 막지 않습니다. 그래서 차단 화면이 뜨고 해제 요청을 보낼 수 있습니다.
  • /contexa/step-up 아래 화면, /contexa/zero-trust/ 아래 판정 화면, 에이전트 위임 · 확인 화면은 로그인한 사용자에게만 답합니다. 앱 규칙이 무엇을 허용하든 익명 요청은 401 AUTHENTICATION_REQUIRED를 받습니다.

PENDING_ANALYSIS: 응답 지켜보기

판정이 허용이거나 아직 없으면 요청을 통과시키되, 응답을 감싸서 지켜봅니다. 응답이 나가는 동안 이 사용자에게 BLOCK 신호가 오면 응답을 끊습니다. 아직 아무것도 보내지 않았으면 쓰던 내용을 버리고 403과 표식 __CONTEXA_RESPONSE_BLOCKED__:BLOCK을 보내고, 이미 보내기 시작했으면 표식을 쓰고 끊습니다. 자바스크립트 SDK는 이 표식을 보면 차단 화면으로 이동합니다(로그인 뒤 추가 인증).

권한이 바뀌는 방식

  • 세션 흐름: Contexa 세션 로그인 저장소(AISessionSecurityContextRepository)가 요청에서 로그인 정보를 처음 꺼낼 때 판정을 적용합니다. 권한이 바뀌면 로그인 객체를 판정이 담긴 ZeroTrustAuthenticationToken(신뢰 점수 · 위협 점수 · 판정)으로 바꿉니다. 무효화된 세션이면 세션을 끝내고 로그인 안 된 요청으로 진행합니다.
  • 토큰 흐름: 토큰 검증(BearerTokenAuthenticationFilter) 바로 뒤의 AIOAuth2ZeroTrustFilter가 JWT 요청에 판정을 적용하고, 바뀐 권한으로 새 JwtAuthenticationToken을 넣습니다. 무효화된 토큰이면 401입니다.
  • 권한 바꾸기에 쓰는 판정은 5초 동안 캐시합니다. 두 필터는 캐시 없이 저장소를 직접 읽으므로, 새 BLOCK의 응답 차단은 늦지 않습니다.
  • 판정은 권한을 더하지 않습니다. ALLOW는 원래 권한, CHALLENGE · BLOCK · ESCALATE는 판정 표시 권한 하나만 남깁니다. 그래서 URL 정책과 @PreAuthorize 같은 권한 검사에서도 제한이 걸립니다.
  • HOST_OWNED에서는 권한을 바꾸지 않습니다. Contexa는 앱의 SecurityContext를 건드리지 않고, 두 필터가 저장된 판정을 보고 바로 답합니다.

필터가 도는 곳

CONTEXA_OWNED에서는 필터 세 개(MFA 진행 중 접근 제어, 접근 제어, 챌린지)의 서블릿 등록을 FilterRegistrationBean으로 꺼 두고, Contexa 구성자가 흐름마다 체인 안에 넣습니다. 위치는 고정 번호가 아니라 Spring 필터를 기준으로 한 상대 위치입니다. 구성자의 순서 값 44 · 45 · 50은 구성자를 적용하는 차례이지 필터의 위치가 아닙니다.

체인필터위치

토큰 체인인증 브리지 → AIOAuth2ZeroTrustFilterBearerTokenAuthenticationFilter 바로 뒤

HOST_OWNED에서

Contexa가 체인을 만들지 않으므로, 필터를 Spring Security 필터 체인의 순서(spring.security.filter.order, 기본 -100) 뒤에 오는 서블릿 필터로 등록합니다. 앱 체인이 먼저 돌고, MFA 진행 중 접근 제어와 권한 바꾸기는 쓰지 않습니다.

순서필터하는 일
체인 + 1인증 브리지(BridgeResolutionFilter)앱 체인이 정한 로그인을 읽어 도장을 만듦
체인 + 2챌린지(ZeroTrustChallengeFilter)CHALLENGE를 추가 확인으로 보냄, 에이전트 관문
체인 + 3접근 제어(ZeroTrustAccessControlFilter)BLOCK · ESCALATE, PENDING_ANALYSIS 응답 지켜보기
체인 + 4사용자 경로 보호(HostOwnedUserPathGuard)Contexa의 사용자용 화면은 로그인한 사용자에게만 답함

필터는 앱이 Spring Security 필터에서 사용자를 정해야 그 사용자를 봅니다. 사용자를 더 늦게(MVC 인터셉터나 컨트롤러에서) 정하면 그런 요청은 @Protectable 메서드에서만 집행되고, Contexa가 [Contexa] HOST_OWNED: the application sets the signed-in user after Spring Security's filters ...(WARN)를 한 번 남깁니다.

두 필터는 집행 모드를 따릅니다. 새 판정을 저장하고 적용하는 일은 contexa.security.zerotrust.enabled가 켜져 있고 contexa.security.zerotrust.mode가 ENFORCE일 때만 하고, 접근 제어 · 챌린지 필터도 두 소유 방식 모두에서 그때만 요청을 막습니다. SHADOW · OBSERVE · DISABLED이거나 enabled: false면 아무것도 막지 않습니다. 앞서 저장된 BLOCK · CHALLENGE · ESCALATE는 남아 있다가, 만료되거나 해제되지 않았다면 모드가 ENFORCE로 돌아올 때 다시 적용됩니다. 그동안 에이전트 관문은 기록만 하고 에이전트를 통과시킵니다. enabled: false면 로그인 정보를 꺼낼 때의 권한 바꾸기와 세션 추적도 멈춥니다.

MFA 진행 중 접근 제어

1차 로그인만 마치고 MFA를 끝내지 않은 세션은 MFA를 진행하거나 빠져나가는 데 필요한 요청만 통과합니다: 로그인 · 로그아웃, 모든 MFA 흐름의 화면과 요소 주소, MFA 설정 API, Contexa 정적 파일, Zero Trust 안내 화면, 오류 경로. 그 밖의 요청은 브라우저면 진행 중인 MFA 화면(MFA 세션이 없으면 로그인 화면)으로 이동하고, API면 401 MFA_REQUIRED를 받습니다. 1차 로그인만으로 패스키를 등록해 2차 요소를 건너뛰지 못하도록 패스키 등록 요청도 막습니다(API는 401 PASSKEY_REGISTRATION_REQUIRES_MFA).

차단 해제

BLOCK은 관리자가 승인해야 풀립니다. 사용자는 차단 화면에서 본인 확인(MFA)을 하고 해제를 요청할 수 있습니다.

  • 시도 한도: 해제 MFA 시작 API와 접근 제어 필터는 contexa.security.zerotrust.max-block-mfa-attempts(기본 2)를 봅니다. 다만 해제 MFA 실패를 세는 처리기는 이 설정 대신 상수 2를 씁니다. 실패한 MFA 세션 하나가 한 번이며, 두 번이면 대기 표식을 지우고 이후 차단 응답만 줍니다. 실패할 때마다 403 BLOCK_MFA_FAILED와 차단 화면 주소를 돌려주고, 실패 횟수는 24시간 유지됩니다.
  • 세션은 그대로입니다. 차단할 때 필터는 응답만 쓰고, 세션을 무효화하거나 로그아웃시키지 않습니다.
  • HOST_OWNED에서는 해제 MFA를 Contexa 추가 확인에서 합니다. 관리자가 MFA로 해제하도록 허용한 BLOCK이면 접근 제어 필터가 브라우저는 /contexa/step-up?purpose=block으로 보내고, API에는 401 BLOCK_MFA_REQUIRED와 mfaUrl로 답합니다. 통과하면 위 해제 MFA와 같은 확인 표시가 남습니다. BLOCK을 푸는 것은 여전히 관리자 승인입니다.
  • 에이전트의 BLOCK은 403 AGENT_BLOCKED이고 MFA로 풀지 않습니다. 해제는 정지와 해제를 보세요.

검토 보류가 차단이 되는 때

ESCALATE로 처음 막힐 때 재시도 표식(5분)을 한 번 둡니다. 판정의 유효 시간(300초)과 재시도 표식이 모두 지난 뒤 들어온 다음 요청에서, 접근 제어 필터가 BLOCK을 저장하고 차단 표시를 남긴 뒤 차단으로 답합니다. 사람이면 차단 기록을 남기고, 에이전트면 그 에이전트를 정지합니다. MFA 성공은 ESCALATE를 풀지 않습니다.

에이전트 요청

인증 브리지가 요청에 에이전트를 밝힌 위임 도장을 붙였으면 에이전트 요청입니다. 에이전트는 사람의 MFA에 답할 수 없으므로, 챌린지 필터가 사람의 MFA 대신 에이전트 관문으로 보냅니다. 관문은 호출 상한 → 끝난 위임 → CHALLENGE의 책임자 확인 → 좁혀진 범위를 차례로 검사합니다. 자세한 응답과 처리는 정지 · 확인 · 제한에 있습니다.

  • 관문이 없으면(에이전트 확인 서비스 빈이 없을 때) CHALLENGE에 403 AGENT_CONFIRMATION_REQUIRED로 답합니다.
  • 사람 대신 일하는 에이전트의 판정은 <사용자>::agent::<에이전트> 키로 읽고, 위임한 사람의 BLOCK도 함께 받습니다.
  • 에이전트의 BLOCK은 403 AGENT_BLOCKED입니다.
  • 관문은 두 소유 방식 모두에서 돕니다. HOST_OWNED에서는 챌린지 필터가 인증 브리지 다음에 돌므로(HOST_OWNED에서) 관문이 위임 도장을 봅니다. 다만 앱 체인 안의 URL 인가 단계는 브리지보다 먼저 돌므로, 그때는 위임 도장이 아직 없습니다.
