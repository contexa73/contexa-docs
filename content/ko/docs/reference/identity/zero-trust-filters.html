요청 시점 적용

CONTEXA가 만든 판정은 그 사용자의 다음 요청에서 실제로 적용됩니다. 이 페이지는 판정별(허용 · 추가 인증 · 검토 보류 · 차단 · 분석 대기)로 사용자가 보는 화면, 브라우저와 API 클라이언트가 받는 응답의 차이, 권한이 바뀌고 해제되는 방식을 설명합니다. 로그인을 앱이 담당할 때와 CONTEXA가 담당할 때의 차이, 필터가 실행되는 위치, AI 에이전트 요청의 처리, 설정도 안내합니다.

로그인을 누가 맡든 사용자가 받는 응답은 같습니다. 앱의 Spring Security가 로그인을 맡는 방식이 기본값 HOST_OWNED이고, CONTEXA가 로그인을 맡는 방식이 CONTEXA_OWNED입니다. 두 방식에서 같은 필터가 같은 응답을 냅니다. 다른 점은 두 가지입니다. 첫째는 필터가 도는 자리입니다. CONTEXA_OWNED에서는 필터가 CONTEXA가 만든 보안 체인 안에 들어갑니다. HOST_OWNED에서는 CONTEXA가 체인을 만들지 않고, 필터가 앱의 Spring Security 체인이 끝난 바로 뒤에서 서블릿 필터로 돕니다(앱이 로그인을 맡을 때의 필터 위치). 앱 체인이 먼저 사용자를 정하고 앱의 규칙을 적용하므로, 필터는 앱의 모든 경로에 판정을 적용합니다(건너뛰는 주소는 필터가 건너뛰는 주소). 둘째는 추가 인증(CHALLENGE)을 처리하는 곳입니다. HOST_OWNED에서는 CONTEXA의 MFA 대신 CONTEXA의 추가 인증 화면으로 보냅니다. 이 화면은 로그인을 대신하지 않고 사용자를 한 번 더 확인하기만 합니다(앱이 로그인을 맡을 때의 추가 인증). 어느 방식이든 저장된 차단 · 추가 인증 · 검토 보류 판정은 @Protectable 메서드 앞에서도 요청을 거부합니다(보호 메서드). 앱의 기존 로그인을 그대로 쓰는 방법은 기존 로그인과 연결하기에 있습니다.

개요

판정은 보통 응답이 나간 뒤에 만들어져 판정 저장소에 쓰이고(판정 엔진), 그 사용자의 다음 요청부터 적용됩니다. 요청을 붙잡아 두고 판정을 기다리지는 않습니다. 로그인하지 않은 요청은 이 필터들이 그대로 통과시킵니다.

판정마다 얼마나 오래 유지되는지, 어느 요청에 적용되는지는 아래 표와 같습니다.

판정저장 유효 시간어디에 걸리나
ALLOW15분(contexa.security.zerotrust.allow-validity로 바꿈)판정이 난 세션 · IP · 브라우저(컨텍스트 해시)에서 온 요청에만 적용됩니다. 셋 중 하나라도 다르면 PENDING_ANALYSIS로 읽힙니다
CHALLENGE1800초. 분석이 실패해 임시로 건 CHALLENGE는 60초그 사용자의 모든 세션
ESCALATE300초그 사용자의 모든 세션
BLOCK풀릴 때까지그 사용자의 모든 세션
PENDING_ANALYSIS기한 없음저장된 판정이 없거나 유효 시간이 지나면 이 값으로 읽힙니다

컨텍스트 해시는 세션 ID · 클라이언트 IP · User-Agent를 합쳐 만든 값입니다. 허용은 이 환경에서만 통하므로, 환경이 바뀐 요청은 새로 분석합니다. 차단 · 추가 인증 · 검토 보류는 환경과 상관없이 사용자 전체에 걸립니다. 이 제한이 걸려 있는 동안에는 새로 나온 더 느슨한 판정이 제한을 덮어쓰지 못합니다.

판정별 응답 · 권한 · 해제

제한이 걸린 요청에는 요청한 쪽이 브라우저인지 API 클라이언트인지에 따라 다른 응답이 갑니다. 브라우저 요청은 안내 화면으로 이동합니다. API · AJAX 요청은 JSON 오류를 받습니다.

요청에 Accept: application/json 헤더나 X-Requested-With: XMLHttpRequest 헤더가 있거나 경로가 /api/로 시작하면 API · AJAX 요청으로 봅니다. JSON 오류 본문에는 항상 timestamp · status · error · message · path가 들어 있고, 아래 표에 적은 필드가 더해집니다.

판정브라우저API · AJAX권한푸는 방법
ALLOW그대로 진행그대로 진행원래 권한 그대로—
CHALLENGE/contexa/zero-trust/challenge-required?mfaUrl=… 안내 화면으로 이동합니다. 화면에 추가 인증이 필요하다는 안내와 인증을 진행하는 버튼이 나옵니다(HOST_OWNED에서는 mfaUrl이 /contexa/step-up)401 MFA_CHALLENGE_REQUIRED. 본문에 mfaUrl(인증 화면 주소), challengeNoticeUrl(안내 화면 주소), sessionId(MFA 세션), currentState(MFA 단계), currentFactor(진행 중인 요소, 정해졌을 때만)가 들어갑니다. HOST_OWNED에서는 MFA 흐름을 시작하지 않으므로 mfaUrl과 challengeNoticeUrl만 들어갑니다원래 권한이 모두 빠지고 ROLE_MFA_REQUIRED 하나만 남습니다추가 인증을 통과한 세션만 ALLOW로 바뀝니다. 통과하는 방법은 두 가지입니다. 하나는 이 CHALLENGE가 시작한 MFA를 통과하는 것입니다(HOST_OWNED에서는 추가 인증을 통과하는 것입니다). 다른 하나는 CHALLENGE가 걸린 뒤 요소를 하나 이상 거쳐 끝난 새 로그인입니다. 이 로그인이 여는 세션의 CHALLENGE가 풀립니다. 정책이 요소 없이 통과시킨 로그인은 풀지 않습니다. 그 사용자의 다른 세션은 각자 통과할 때까지 CHALLENGE가 남습니다. 비밀번호를 탈취한 쪽의 세션이 원래 사용자의 인증으로 함께 풀리지 않게 하려는 것입니다. 아무도 통과하지 않으면 1800초가 지나 저절로 풀립니다
BLOCK/contexa/zero-trust/blocked 차단 화면으로 이동합니다403 ACCOUNT_BLOCKED. 본문에 관리자 검토가 필요하다는 뜻의 adminReviewRequired(true)와 차단 화면 주소 redirectUrl이 들어갑니다원래 권한이 모두 빠지고 ROLE_BLOCKED 하나만 남습니다관리자 승인(차단 해제)
ESCALATE/contexa/zero-trust/analysis-pending?returnUrl=… 분석 대기 화면으로 이동합니다. returnUrl은 사용자가 원래 가려던 주소입니다. 화면은 보안 분석이 진행 중이라고 알리고, 결과가 허용이면 원래 주소로 돌아가며 차단이면 차단 화면으로 이동합니다423 SECURITY_REVIEW_IN_PROGRESS와 헤더 Retry-After: 30. 본문에 retryAfterSeconds(30초 뒤 다시 시도)와 redirectUrl이 들어갑니다원래 권한이 모두 빠지고 ROLE_REVIEW_REQUIRED 하나만 남습니다관리자의 승인. MFA를 통과해도 풀리지 않습니다. 오래 풀리지 않으면 BLOCK이 됩니다(검토 보류가 차단이 되는 때)
PENDING_ANALYSIS통과통과원래 권한에 표시용 ROLE_PENDING_ANALYSIS가 더해집니다분석 결과가 저장되면 다음 요청부터 그 판정이 적용됩니다

검토 보류(ESCALATE) 응답은 기본 설정에서는 나오지 않습니다. 기본값 contexa.security.tiered.layer2.allow-escalate-final-action: false에서는 2차 분석이 검토 보류를 골라도 그 판정을 저장하지 않고 contexa.security.tiered.layer2.escalate-fallback-action(기본 CHALLENGE)으로 바꿔 저장하기 때문입니다.

이 설정을 true로 켠 설치에서만 검토 보류 판정이 저장되어 위 표의 동작이 일어납니다(설정).

추가 인증(CHALLENGE)의 다른 응답

CONTEXA_OWNED에서 CHALLENGE는 보통 CONTEXA의 MFA 화면으로 이어지지만, 아래 상황에서는 응답이 다릅니다.

상황응답
이 CHALLENGE로 시작한 MFA가 이미 진행 중MFA를 새로 시작하지 않고 그 MFA 화면으로 이어갑니다
같은 사용자의 MFA 시작 요청이 동시에 겹침503 MFA_BUSY_RETRY와 Retry-After: 3. 잠시 뒤 다시 요청하면 됩니다
앱에 MFA 흐름이 하나도 없음사용자가 답할 요소가 없습니다. 브라우저는 /contexa/zero-trust/challenge-required?stepUp=none으로 이동합니다. 이 화면은 이 앱에서는 확인할 수 없다고 알리고 로그아웃 버튼을 보여 줍니다. API는 401 ZERO_TRUST_CHALLENGE를 받습니다. 새로 로그인해도 판정이 끝날 때(1800초)나 바뀔 때까지 같은 응답을 받습니다. 이 구성은 기동 시 경고를 남깁니다
MFA 시작에 실패500 MFA_INIT_FAILED
AI 에이전트 요청사람의 MFA 대신 책임자 확인으로 갑니다(에이전트 요청)

MFA를 시작할 때는 사용자마다 잠금(mfa:challenge:init:<사용자>)을 걸어 한 번에 한 요청만 시작하게 합니다. 잠금을 기다리는 시간, 잠금 임대 시간, 503의 재시도 안내 초는 설정으로 바꿉니다(설정). HOST_OWNED에서는 위 표의 앞 네 줄이 일어나지 않습니다. CONTEXA의 MFA를 시작하지 않고, 사람에게는 아래 추가 인증 화면으로 답하기 때문입니다.

앱이 로그인을 맡을 때의 추가 인증 (HOST_OWNED)

HOST_OWNED는 로그인, 세션, 쿠키를 앱이 맡는 방식입니다. 이 방식에서 판정이 CHALLENGE(추가 인증 요구)이면 CONTEXA는 지금 요청하는 사람이 앱에 로그인한 그 사용자가 맞는지 한 번 더 확인합니다. CONTEXA가 로그인을 대신하지는 않습니다. 확인만 하고, 앱의 로그인 정보, 세션, 쿠키는 바꾸지 않습니다.

  1. 사용자의 요청에 CHALLENGE 판정이 내려집니다.
  2. 브라우저는 "추가 인증이 필요합니다"라는 안내 화면을 거쳐 /contexa/step-up으로 이동합니다. API 클라이언트는 401 응답을 받고, 응답 본문의 mfaUrl에 이 주소가 들어 있습니다.
  3. 사용자는 화면에 나온 확인 방법 중 하나로 본인을 확인합니다. 방법은 아래 표에 있습니다.
  4. 확인에 성공하면 CHALLENGE가 풀리고 요청이 허용(ALLOW)됩니다. CONTEXA 자체 MFA를 마쳤을 때와 같은 방식으로 기록됩니다.

이 화면은 앱의 Spring Security 필터 체인 안에서 열립니다. 그래서 화면에 들어온 사람은 앱이 이미 로그인시킨 사용자이고, 화면에서 보내는 POST 요청에는 앱의 CSRF 보호가 그대로 적용됩니다.

확인 방법화면에 나오는 조건
패스키이 사용자의 패스키가 CONTEXA에 등록되어 있을 때입니다. 패스키 신뢰 당사자(relying party) 설정은 contexa.auth.urls.factors.passkey.*를 씁니다. 패스키가 아직 없는 사용자는 같은 화면에서 첫 패스키를 등록할 수 있습니다(아래 "첫 패스키 등록" 참고).
메일 일회용 코드CONTEXA에 저장된 이 사용자의 사본에 실제 이메일 주소가 있고(contexa.bridge.sync.synthetic-email-domain에 속한 주소는 실제 주소가 아닙니다) 메일 설정(spring.mail.*)이 되어 있을 때입니다.
앱 자체 재인증앱이 자기 MFA나 신원 공급자로 사용자를 다시 인증할 때입니다. 아래 "앱 자체 재인증" 참고.

첫 패스키 등록. 패스키는 CHALLENGE를 풀 수 있는 수단이므로 아무 때나 등록할 수 없습니다. 등록하려면 다음 두 조건이 맞아야 합니다.

  • 이 사용자에게 CHALLENGE, BLOCK, ESCALATE 판정이 걸려 있지 않아야 합니다.
  • 이 세션이 일회용 코드나 앱의 MFA 로그인(5분 이내, 재인증 주소를 설정한 앱만)으로 사용자를 먼저 확인한 상태여야 합니다.

방금 일회용 코드로 CHALLENGE를 푼 사용자에게는 바로 패스키 등록이 안내됩니다.

메일 일회용 코드. 메일로 보낸 코드에는 세 가지 제한이 있습니다.

  • 발송 간격: 코드는 사용자마다 30초에 한 통만 보냅니다. 그 안에 다시 요청하면 메일을 보내지 않고 "잠시 기다리라"고 답합니다. 그래서 CHALLENGE가 걸린 세션이 사용자의 편지함을 채울 수 없습니다.
  • 한 번만 사용: 같은 코드를 다시 쓰거나 여러 요청이 동시에 쓰면 첫 요청만 통과합니다.
  • 틀린 입력 횟수: 코드를 틀리게 입력할 수 있는 횟수는 contexa.auth.mfa.max-retry-attempts(CONTEXA MFA와 같은 값)이고, 세션 환경(브라우저와 접속 주소)마다 따로 셉니다. 한도에 이르면 그 환경에서 요청한 코드가 모두 폐기되어 새 코드를 받아야 합니다. 쿠키를 탈취한 사람이 틀린 코드를 입력해도 원래 사용자는 자기 코드를 계속 쓸 수 있습니다.

앱 자체 재인증. CHALLENGE 이후에 앱이 사용자를 자기 MFA나 신원 공급자로 다시 인증했고 그 사실이 인증 도장(인증 브리지가 앱의 로그인 결과를 담아 두는 값)에 남아 있으면, 챌린지 필터가 그 요청에서 CHALLENGE를 스스로 풉니다. 조건은 MFA 완료가 기록되어 있고 인증 시각이 CHALLENGE보다 늦다는 것입니다.

contexa.bridge.step-up.reauthentication-url에 앱의 재인증 주소를 적으면 화면에 그 주소로 가는 링크가 나옵니다. 이 주소를 적지 않으면 앱의 재인증은 확인 방법으로 쓰이지 않습니다.

  • 확인 대상: 인증 브리지가 관리하는 앱 사용자의 사본만 확인합니다. 그래서 앱 사용자가 이름이 같은 CONTEXA 자체 계정과 섞이지 않습니다.
  • 차단 해제: 차단된 사용자가 차단 화면에서 해제용 MFA를 시작하면 같은 화면(?purpose=block)으로 옵니다. MFA를 통과해도 BLOCK이 풀리지는 않고, 관리자가 해제 요청을 승인해야 풀립니다(차단 해제).
  • 에이전트 요청: 에이전트의 요청은 이 화면에서 확인하지 않고, 책임자가 확인합니다(에이전트 요청).
  • 패스키 옵션 저장: 화면이 발급한 패스키 옵션은 세션이 아니라 사용자의 판정 키 아래에 저장합니다. 기본은 메모리이고, contexa.infrastructure.mode: distributed이면 Redis에 저장합니다.
  • 화면 자원: CONTEXA 화면의 스크립트, 스타일, 이미지(/contexa/js/, /contexa/css/, /contexa/img/)는 판정이 막지 않습니다. 차단된 사용자도 차단 화면을 열고 해제 요청을 보낼 수 있어야 하기 때문입니다.
  • 로그인한 사용자 전용: /contexa/step-up 아래 화면, /contexa/zero-trust/ 아래 판정 화면, 에이전트 위임과 확인 화면은 로그인한 사용자에게만 답합니다. 앱의 접근 규칙이 무엇을 허용하든 익명 요청은 401 AUTHENTICATION_REQUIRED를 받습니다.

응답 감시 (PENDING_ANALYSIS)

CONTEXA는 판정이 나올 때까지 요청을 붙잡아 두지 않습니다. 차단이나 검토 보류가 걸려 있지 않은 요청(허용, 분석 대기)은 먼저 통과시킵니다.

대신 응답을 감싸서 응답이 나가는 동안 감시합니다. 허용은 그 뒤에 이어질 응답까지 보장하지 않기 때문입니다. 허용 직후에 시작한 긴 스트림 응답도 도중에 차단이 나오면 멈춰야 합니다. 응답이 나가는 동안 이 사용자에게 BLOCK 신호가 오면 CONTEXA가 응답을 끊습니다.

  • 아직 아무것도 보내지 않았으면: 쓰던 내용을 버리고 403과 표식 __CONTEXA_RESPONSE_BLOCKED__:BLOCK을 보냅니다.
  • 이미 보내기 시작했으면: 상태 코드를 바꿀 수 없으므로 표식을 쓰고 응답을 끊습니다.

자바스크립트 SDK는 이 표식을 보면 사용자를 차단 화면으로 보냅니다(로그인 뒤 추가 인증). 감싼 응답에는 SDK가 읽는 X-Contexa-Monitored: true 헤더와 차단 화면 주소를 담은 X-Contexa-Blocked-Redirect 헤더가 붙습니다. 이 헤더는 contexa.security.zerotrust.monitoring-headers: false로 끌 수 있습니다.

권한이 바뀌는 방식

CONTEXA는 판정에 맞춰 로그인한 사용자의 Spring Security 권한(GrantedAuthority)을 바꿉니다. 그래서 URL 정책이나 @PreAuthorize 같은 권한 검사에서도 제한이 걸립니다. 판정은 권한을 새로 주지 않고 줄이기만 합니다.

  • ALLOW는 원래 권한을 그대로 둡니다.
  • CHALLENGE · BLOCK · ESCALATE는 원래 권한을 모두 빼고 판정 표시 권한 하나만 남깁니다.
  • PENDING_ANALYSIS는 원래 권한에 표시 권한을 더합니다.

권한을 바꾸는 자리는 로그인 방식마다 다릅니다.

  • 세션 로그인: CONTEXA의 세션 로그인 저장소(AISessionSecurityContextRepository)가 요청에서 로그인 정보를 처음 꺼낼 때 판정을 적용합니다. 권한이 달라지면 로그인 객체를 판정이 담긴 ZeroTrustAuthenticationToken(신뢰 점수 · 위협 점수 · 판정)으로 바꿉니다. 무효화된 세션이면 세션을 끝내고, 그 요청은 로그인하지 않은 요청처럼 진행합니다.
  • 토큰 로그인: 토큰 검증(BearerTokenAuthenticationFilter) 바로 뒤의 AIOAuth2ZeroTrustFilter가 JWT 요청에 판정을 적용하고, 바뀐 권한으로 새 JwtAuthenticationToken을 넣습니다. 무효화된 토큰이면 401을 돌려줍니다.
  • 캐시: 권한을 바꿀 때 읽는 판정은 허용일 때만 5초 동안 캐시합니다. 제한 판정은 풀리거나 바뀔 수 있으므로 캐시하지 않습니다. 챌린지 필터와 접근 제어 필터는 캐시 없이 저장소를 직접 읽으므로, 새 BLOCK이 응답을 막는 데는 지연이 없습니다.
  • HOST_OWNED에서는 권한을 바꾸지 않습니다. CONTEXA는 앱의 SecurityContext를 건드리지 않고, 두 필터가 저장된 판정을 읽어 바로 응답합니다.

필터가 도는 곳

요청 시점 적용에는 필터 세 개가 쓰입니다. 챌린지 필터는 추가 인증을, 접근 제어 필터는 차단과 검토 보류를 처리합니다. MFA 진행 중 접근 제어 필터는 MFA를 끝내지 않은 세션을 제한합니다. 이 필터들이 도는 자리는 로그인을 누가 맡는지에 따라 다릅니다.

CONTEXA_OWNED에서는 세 필터(MFA 진행 중 접근 제어, 접근 제어, 챌린지)의 서블릿 등록을 FilterRegistrationBean으로 꺼 둡니다. 대신 CONTEXA 구성자(configurer)가 인증 흐름마다 보안 체인 안에 필터를 넣습니다.

필터의 위치는 고정 번호가 아니라 Spring 필터를 기준으로 한 상대 위치입니다. 구성자의 순서 값 44 · 45 · 50은 구성자를 적용하는 차례이지 필터의 위치가 아닙니다.

아래 표에 쓰는 용어는 다음과 같습니다.

  • 세션 체인: 세션 쿠키로 로그인 상태를 유지하는 체인입니다.
  • 토큰 체인: 베어러 토큰(JWT)으로 인증하는 체인입니다.
  • 인증 브리지: 앱의 로그인 결과를 읽어 인증 도장으로 남기는 필터입니다.
체인필터위치
모든 체인MFA 진행 중 접근 제어(MfaPendingAccessControlFilter)LogoutFilter 바로 뒤
세션 체인인증 브리지 + 판정 적용(세션 로그인 저장소)SecurityContextHolderFilter 바로 뒤
토큰 체인인증 브리지 → AIOAuth2ZeroTrustFilterBearerTokenAuthenticationFilter 바로 뒤
세션 · MFA 흐름챌린지(ZeroTrustChallengeFilter)MFA 화면 생성 필터(DefaultMfaPageGeneratingFilter) 바로 뒤
세션 · MFA 아닌 흐름챌린지AuthorizationFilter 바로 앞(접근 제어 다음)
토큰 체인챌린지BasicAuthenticationFilter 바로 앞
모든 체인접근 제어(ZeroTrustAccessControlFilter)AuthorizationFilter 바로 앞

앱이 로그인을 맡을 때의 필터 위치 (HOST_OWNED)

HOST_OWNED에서는 CONTEXA가 보안 체인을 만들지 않습니다. 대신 필터를 서블릿 필터로 등록하고, 순서를 Spring Security 필터 체인의 순서(spring.security.filter.order, 기본 -100) 바로 뒤로 잡습니다. 그래서 앱 체인이 먼저 돌아 사용자를 정하고 앱의 규칙을 적용한 다음에 CONTEXA 필터가 돕니다. 이 경우 MFA 진행 중 접근 제어와 권한 바꾸기는 쓰이지 않습니다.

순서필터하는 일
체인 + 1인증 브리지(BridgeResolutionFilter)앱 체인이 정한 로그인 사용자를 읽어 인증 도장을 만듭니다
체인 + 2챌린지(ZeroTrustChallengeFilter)CHALLENGE를 CONTEXA 추가 인증으로 보냅니다. 에이전트 요청은 에이전트 관문으로 보냅니다
체인 + 3접근 제어(ZeroTrustAccessControlFilter)BLOCK과 ESCALATE를 막고, PENDING_ANALYSIS 응답을 지켜봅니다
체인 + 4사용자 경로 보호(HostOwnedUserPathGuard)CONTEXA의 사용자용 화면은 로그인한 사용자에게만 응답합니다

필터는 앱이 Spring Security 필터 안에서 사용자를 정해야 그 사용자를 볼 수 있습니다. 앱이 사용자를 더 늦게(MVC 인터셉터나 컨트롤러에서) 정하면 필터는 그 요청의 사용자를 알지 못합니다. 그런 요청에는 @Protectable 메서드에서만 판정이 적용되고, CONTEXA가 [Contexa] HOST_OWNED: the application sets the signed-in user after Spring Security's filters ...(WARN) 로그를 한 번 남깁니다.

두 필터는 운영 모드가 적용 모드(ENFORCE)일 때만 요청을 막습니다. 새 판정을 저장하고 적용하는 일은 contexa.security.zerotrust.enabled가 켜져 있고 contexa.security.zerotrust.mode가 ENFORCE일 때만 합니다. 접근 제어 필터와 챌린지 필터도 두 로그인 방식 모두에서 이때만 요청을 막습니다. 모드가 SHADOW(관찰 모드) · DISABLED(끔, 옛 이름 OBSERVE 포함)이거나 enabled: false이면 필터는 아무것도 막지 않습니다. 앞서 저장된 BLOCK · CHALLENGE · ESCALATE는 지워지지 않고 남아 있다가, 만료되거나 해제되지 않았다면 모드가 ENFORCE로 돌아올 때 다시 적용됩니다. 그동안 에이전트 관문은 끝난 위임과 좁혀진 범위를 기록만 하고 에이전트 요청을 통과시킵니다. enabled: false이면 로그인 정보를 꺼낼 때의 권한 바꾸기와 세션 추적도 멈춥니다.

MFA 진행 중 접근 제어

사용자가 1차 로그인만 마치고 MFA를 끝내지 않았으면, 그 세션은 MFA를 진행하거나 빠져나가는 데 필요한 요청만 통과합니다. 통과하는 요청은 다음과 같습니다.

  • 로그인 · 로그아웃
  • 모든 MFA 흐름의 화면과 요소 주소
  • MFA 설정 API
  • CONTEXA 정적 파일
  • Zero Trust 안내 화면
  • 오류 경로

그 밖의 요청은 막습니다. 브라우저는 진행 중인 MFA 화면으로 이동합니다. MFA 세션이 없으면 로그인 화면으로 이동합니다. API는 401 MFA_REQUIRED를 받습니다.

1차 로그인만으로 패스키를 등록해 2차 요소를 건너뛰지 못하도록 패스키 등록 요청도 막습니다. 이때 API는 401 PASSKEY_REGISTRATION_REQUIRES_MFA를 받습니다.

차단 해제

BLOCK은 관리자가 승인해야 풀립니다. 차단된 사용자는 차단 화면에서 추가 인증(MFA)을 거친 뒤 해제를 요청할 수 있습니다. MFA를 통과해도 BLOCK이 풀리지는 않습니다. 관리자가 요청을 검토해 승인해야 풀립니다.

  • 시도 한도: 해제 MFA를 시작하는 API와 접근 제어 필터는 contexa.security.zerotrust.max-block-mfa-attempts(기본 2)를 봅니다. 그러나 해제 MFA의 실패를 세는 처리기는 이 설정 대신 상수 2를 씁니다.
  • 실패 처리: 실패한 MFA 세션 하나가 한 번으로 세어지고, 두 번 실패하면 대기 표식이 지워져 이후에는 차단 응답만 받습니다. 실패할 때마다 403 BLOCK_MFA_FAILED와 차단 화면 주소를 돌려주고, 실패 횟수는 24시간 유지됩니다.
  • 세션은 그대로입니다. 차단할 때 필터는 응답만 쓰고, 세션을 무효화하거나 로그아웃시키지 않습니다.
  • HOST_OWNED에서는 해제 MFA를 CONTEXA 추가 인증 화면에서 합니다. 사용자가 해제 MFA를 시작해 둔 BLOCK이면 접근 제어 필터가 브라우저를 /contexa/step-up?purpose=block으로 보내고, API에는 401 BLOCK_MFA_REQUIRED와 mfaUrl로 답합니다. 통과하면 위 해제 MFA와 같은 확인 표식이 남습니다. BLOCK을 푸는 것은 여전히 관리자 승인입니다.
  • 에이전트의 BLOCK은 403 AGENT_BLOCKED이고 MFA로 풀지 않습니다. 해제는 정지와 해제를 참고합니다.

검토 보류가 차단이 되는 때

검토 보류(ESCALATE)는 관리자가 검토해 승인할 때까지 요청을 막는 판정입니다. 검토가 오래 끝나지 않으면 접근 제어 필터가 이 판정을 BLOCK으로 올립니다. 순서는 다음과 같습니다.

  1. 접근 제어 필터가 ESCALATE로 처음 요청을 막을 때 재시도 표식(5분)을 한 번 남깁니다.
  2. 판정의 유효 시간(300초)과 재시도 표식이 모두 지납니다.
  3. 그 뒤에 처음 들어온 다음 요청에서 필터가 BLOCK을 저장하고 차단 표시를 남긴 뒤 차단으로 응답합니다.

사람의 요청이면 차단 기록을 남기고, 에이전트의 요청이면 그 에이전트를 정지합니다. MFA를 통과해도 ESCALATE는 풀리지 않습니다. 앞에서 설명했듯이 기본 설정에서는 ESCALATE가 저장되지 않으므로 이 승격도 일어나지 않습니다.

필터가 건너뛰는 주소

아래 주소로 오는 요청에는 필터가 판정을 적용하지 않습니다. 필터가 이 주소까지 막으면 차단되거나 추가 인증이 걸린 사용자가 안내 화면과 인증 화면을 열 수 없기 때문입니다.

필터건너뛰는 주소(이 경로로 시작)
접근 제어/logout, /contexa/zero-trust, /contexa/step-up, /contexa/api/aiam/zero-trust, /contexa/api/aiam/sse/zero-trust, /contexa/admin/api/aiam/zero-trust, /contexa/admin/api/aiam/sse/zero-trust, /.well-known/(아래 설명 참고). CONTEXA_OWNED에서 해제 MFA를 기다리는 사용자에게는 MFA 주소도 통과시킵니다
챌린지/logout, /contexa/admin/api/mfa/, /contexa/zero-trust, /contexa/step-up, /contexa/api/agent-confirmations, /.well-known/(아래 설명 참고). CONTEXA_OWNED에서는 모든 MFA 흐름에 등록된 주소(기본 주소는 /mfa/challenge/, /api/mfa/, /webauthn/, /login/webauthn 아래에 있습니다)도 건너뜁니다

/.well-known/ 아래에서는 CONTEXA가 공개하거나 브라우저가 로그인에 읽는 문서만 건너뜁니다. 그 문서는 authzen-configuration, oauth-authorization-server, oauth-protected-resource, openid-configuration, webauthn입니다. 그 폴더의 나머지는 앱의 주소이므로 판정이 적용됩니다.

두 필터는 CONTEXA 화면의 스크립트 · 스타일 · 이미지(/contexa/js/, /contexa/css/, /contexa/img/)도 건너뜁니다. HOST_OWNED에서는 앱의 로그인과 MFA 주소가 CONTEXA의 주소가 아니므로 건너뛰지 않고, 다른 앱 주소처럼 판정이 적용됩니다.

에이전트 요청

AI 에이전트의 요청은 사람의 MFA에 답할 수 없습니다. 그래서 에이전트 요청에 CHALLENGE가 걸리면 챌린지 필터가 MFA 대신 에이전트 관문으로 보냅니다. 인증 브리지가 요청에 에이전트를 밝힌 위임 도장을 붙였으면 에이전트 요청입니다.

관문은 그 에이전트를 책임지는 사람(에이전트에게 위임한 사람, 위임 없이 일하는 에이전트는 후원자)에게 요청을 확인해 달라고 요청하고, 승인될 때까지 요청을 멈춥니다. 에이전트는 403 AGENT_CONFIRMATION_REQUIRED를 받고, 책임자가 승인하면 같은 요청을 다시 보냅니다. 자세한 응답과 처리는 정지 · 확인 · 제한에 있습니다.

관문은 요청을 다음 순서로 검사합니다.

  1. 호출 상한: 에이전트가 정해진 호출 수를 넘으면 요청을 거절하고 기다릴 시간을 알립니다.
  2. 끝난 위임: 위임이 철회되었으면 거절합니다. 위임 기간이 끝났거나 시작하지 않았으면 책임자 확인을 요구합니다.
  3. CHALLENGE의 책임자 확인: 판정이 CHALLENGE이면 책임자가 이 요청을 승인할 때까지 멈춥니다.
  4. 좁혀진 범위: 판정으로 에이전트의 범위가 좁혀졌으면, 책임자가 그 요청을 확인하지 않은 한 범위 밖 요청을 거절합니다.
  • 관문이 만들어지지 않았으면(에이전트 확인 서비스 빈이 없을 때) CHALLENGE에 403 AGENT_CONFIRMATION_REQUIRED로 답합니다. 이때는 책임자 확인을 요청하는 절차가 없습니다.
  • 사람 대신 일하는 에이전트의 판정은 <사용자>::agent::<에이전트> 키로 따로 읽습니다. 위임한 사람의 BLOCK도 함께 받으므로, 위임자가 차단되면 그 에이전트도 멈춥니다.
  • 에이전트 자신의 BLOCK은 403 AGENT_BLOCKED로 답합니다. 위임한 사람의 계정은 차단되지 않고 그 에이전트만 정지됩니다.
  • 관문은 두 로그인 방식 모두에서 돕니다. HOST_OWNED에서는 챌린지 필터가 인증 브리지 다음에 돌므로(앱이 로그인을 맡을 때의 필터 위치) 관문이 위임 도장을 볼 수 있습니다. 다만 앱 체인 안의 URL 인가 단계는 브리지보다 먼저 돌므로, 그 단계에서는 위임 도장이 아직 없습니다.

구성 요소하는 일
ZeroTrustActionRepository판정 저장소. getCurrentAction(사용자, 컨텍스트 해시)로 판정을 읽습니다. 메모리 또는 Redis에 저장합니다(contexa.infrastructure.mode)
AISessionSecurityContextRepository세션 로그인 정보를 꺼낼 때 판정을 적용하고 무효화된 세션을 처리합니다. 로그인 정보를 저장할 때는 세션을 추적합니다
AIOAuth2ZeroTrustFilterJWT 요청에 판정을 적용합니다
ZeroTrustChallengeFilter · ChallengeMfaInitializerCHALLENGE이면 MFA를 시작하거나 진행 중인 MFA로 이어 줍니다(HOST_OWNED에서는 CONTEXA 추가 인증으로 보냅니다)
ZeroTrustAccessControlFilterBLOCK과 ESCALATE를 막고, PENDING_ANALYSIS 응답을 감시하고, ESCALATE를 BLOCK으로 올립니다

HostOwnedUserPathGuardHOST_OWNED에서 CONTEXA의 사용자용 화면에 로그인한 사용자만 들입니다
MfaSessionRepositoryMFA 세션을 저장합니다
MfaFlowUrlRegistry · AuthUrlProviderMFA 주소를 관리합니다(건너뛸 주소와 MFA 화면 주소를 계산)

앱이 같은 타입의 빈(bean)을 직접 등록하면 필터와 구성자 빈 대신 그 빈이 쓰입니다(@ConditionalOnMissingBean). 이 필터들을 만드는 자동 구성 전체는 contexa.identity.security-core.enabled: false로 끕니다.

설정

설정기본값뜻 · 언제 바꾸나
contexa.security.zerotrust.enabledtrue끄면 필터가 요청을 막지 않고, 로그인 정보를 꺼낼 때의 권한 바꾸기와 세션 추적도 멈춥니다
contexa.security.zerotrust.modeENFORCE운영 모드. ENFORCE일 때만 필터가 요청을 막습니다. SHADOW는 판정만 하고 요청에는 적용하지 않습니다
contexa.security.zerotrust.allow-validity15mALLOW 하나가 같은 세션 · IP · 브라우저의 요청에 통하는 시간. 운영 권장 범위는 10분에서 20분입니다
contexa.security.zerotrust.monitoring-headerstrue응답에 X-Contexa-Monitored · X-Contexa-Blocked-Redirect 헤더를 붙일지. 응답에 CONTEXA 흔적을 남기고 싶지 않을 때 끕니다
contexa.security.tiered.layer2.allow-escalate-final-actionfalsetrue로 켜야 ESCALATE가 최종 판정으로 저장되어 이 페이지의 검토 보류 동작이 일어납니다
contexa.security.zerotrust.max-block-mfa-attempts2차단 해제 MFA 시도 한도(시작 API · 접근 제어 필터). 실패를 세는 처리기는 상수 2를 씀
contexa.security.zerotrust.challenge.lock-wait-time0챌린지 MFA 시작 잠금을 기다리는 시간(0이면 바로 503)
contexa.security.zerotrust.challenge.lock-lease-time30s그 잠금의 임대 시간
contexa.security.zerotrust.challenge.busy-retry-after-seconds3잠금을 못 잡았을 때 503의 Retry-After
contexa.bridge.step-up.reauthentication-url없음HOST_OWNED에서 추가 인증이 앱 자체 재인증을 위해 사용자를 보내는 주소(기존 로그인과 연결하기)
contexa.identity.security-core.enabledtrue끄면 이 필터들의 자동 구성이 꺼집니다
