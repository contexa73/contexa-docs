적응형 MFA

1차 로그인(폼 · REST) 뒤에 2차 요소(메일 일회용 코드 · 패스키)를 요구하는 MFA 흐름을 켜는 방법입니다. MFA가 필요한지를 무엇이 정하는지, 화면과 주소, 응답 형식, 로그인 뒤 추가 인증, 자바스크립트 SDK, 설정을 설명합니다.

Contexa가 로그인을 맡을 때(CONTEXA_OWNED)의 기능입니다. 기본값 HOST_OWNED에서는 앱의 Spring Security가 로그인을 맡고 Contexa MFA 흐름은 만들어지지 않습니다. 앱의 기존 로그인 · MFA를 쓰면서 그 결과를 Contexa에 알리려면 기존 로그인과 연결하기를 보세요. @EnableAISecurity(mode = SecurityMode.FULL)이고 PlatformConfig를 정의하지 않으면 MFA 흐름 하나(폼 + 패스키 + 일회용 코드)가 기본으로 켜집니다.

한눈에 보기

1차 로그인이 성공하면 MFA 정책이 이 사용자에게 MFA가 필요한지 정합니다. 필요하면 Contexa가 첫 2차 요소의 화면을 바로 열고, 사용자는 "다른 방법"으로 남은 요소를 고를 수도 있습니다. 필요한 개수만큼 요소를 마치면 로그인이 끝납니다.

2차 요소는 메일 일회용 코드(.ott())와 패스키(.passkey()) 두 가지입니다. 인증 앱 코드(TOTP)와 문자 메시지(SMS) 요소는 없습니다.

가장 간단한 MFA

registry
        .mfa(mfa -> mfa
                .primaryAuthentication(primary -> primary.formLogin(Customizer.withDefaults()))
                .passkey(Customizer.withDefaults())
                .ott(Customizer.withDefaults()))
        .session(Customizer.withDefaults())
        .build();
  • Contexa가 로그인 화면 GET /mfa/login과 요소 화면을 만들어 줍니다. 1차 로그인 처리는 POST /mfa/login입니다.
  • 흐름 이름은 mfa, 기본 order는 200, 체인 빈은 mfaSecurityFilterChain1처럼 붙습니다.
  • 1차 로그인은 formLogin과 restLogin 가운데 하나입니다(.primaryAuthentication(...) 필수).
  • 2차 요소가 하나도 없으면 시작이 실패합니다. .mfa() 안에서 .form() · .rest()를 부르면 UnsupportedOperationException이 납니다. 같은 요소를 두 번 적으면 뒤의 것이 앞의 것을 바꿉니다.
일회용 코드 요소에는 메일 발송 설정이 필요합니다. 코드는 Spring 메일(spring.mail.*)로 보내며, 발송기가 없으면 contexa.auth.ott.fail-on-email-error(기본 true)에 따라 코드 발급이 실패합니다(일회용 코드).

확인하기

  • 보호된 주소를 열면 /mfa/login 화면으로 갑니다.
  • 1차 로그인 뒤 MFA가 필요하면 첫 요소 화면(예: /mfa/challenge/passkey)이 열립니다. 처음 로그인하는 사용자는 저장된 판정이 없으므로 MFA를 거칩니다.

2차 요소와 필요한 개수

1차 로그인은 0번, 2차 요소는 적은 순서대로 1번, 2번, …이 됩니다. requiredFactors(n)로 마쳐야 하는 요소 개수를 정합니다.

requiredFactors동작
정하지 않음등록한 요소를 모두 마쳐야 합니다
1아무 요소 하나. 첫 요소가 자동으로 열리고 "다른 방법" 링크로 남은 요소를 고를 수 있습니다(마친 요소는 목록에서 빠짐)
NN개를 마쳐야 합니다. 하나를 마치면 다음 요소가 자동으로 이어집니다
요소 수보다 큼끝까지 완료할 수 없습니다. 시작할 때 검사하지 않으므로 주의하세요
 
registry
        .mfa(mfa -> mfa
                .primaryAuthentication(primary -> primary.formLogin(Customizer.withDefaults()))
                .passkey(Customizer.withDefaults())
                .ott(Customizer.withDefaults())
                .requiredFactors(1))   // 패스키를 먼저 열고, 패스키가 없는 기기는 일회용 코드로
        .session(Customizer.withDefaults())
        .build();

화면 주소 바꾸기

mfaPage(...)로 화면 주소를 바꾸면 Contexa는 그 주소의 화면을 만들지 않고 요청을 앱으로 넘깁니다. 그 화면은 앱이 만들어야 합니다.

메서드바꾸는 화면
selectFactorPage(String)요소 선택 화면
ottPages(String requestUrl, String verifyUrl)일회용 코드 요청 · 입력 화면을 함께
ottRequestPage(String)일회용 코드 요청 화면
ottVerifyPage(String)일회용 코드 입력 화면
passkeyChallengePages(String)패스키 화면
configurePageUrl(String)MFA 설정 화면
failurePageUrl(String)MFA 실패 화면
 
registry
        .mfa(mfa -> mfa
                .primaryAuthentication(primary -> primary.formLogin(Customizer.withDefaults()))
                .ott(Customizer.withDefaults())
                .mfaPage(page -> page
                        .selectFactorPage("/mfa/select")
                        .ottPages("/mfa/ott/request", "/mfa/ott/verify")
                        .failurePageUrl("/mfa/failed")))
        .session(Customizer.withDefaults())
        .build();

직접 만든 1차 로그인 화면

  • formLogin(form -> form.loginPage("/login"))처럼 loginPage를 주면 Contexa는 로그인 화면을 만들지 않습니다. 앱이 그 화면을 만들고, 화면은 POST /mfa/login으로 보내야 합니다.
  • Contexa가 만든 화면을 쓰면서 주소만 바꾸려면 defaultLoginUrl("/signin")을 씁니다. 화면 주소와 처리 주소가 함께 바뀝니다.

MFA가 필요한지 정하는 정책

1차 로그인이 성공하면 MFA 정책 공급자가 판정합니다. 기본 공급자는 AI 적응형 공급자(AIAdaptiveMfaPolicyProvider)이고, 등록된 평가기 가운데 우선순위가 가장 높고 이 사용자를 맡는 평가기 하나가 결정합니다.

평가기우선순위맡는 사용자결정
AgentAccountMfaPolicyEvaluator1000승인된 에이전트의 계정사람용 요소로 보내지 않고 Contexa 판정만 따릅니다
ZeroTrustPolicyEvaluator100그 밖의 모든 사용자저장된 판정 ALLOW → MFA 생략. CHALLENGE → MFA. BLOCK → 차단. ESCALATE → 검토 보류(차단). 판정 없음(PENDING_ANALYSIS) → 마지막 확인 판정이 ALLOW면 생략, 아니면 MFA. 판정 기록이 없거나 오래되면(contexa.security.zerotrust.analysis.max-age-ms, 1시간) MFA
DefaultMfaPolicyEvaluator-100앞의 평가기가 예외를 던졌을 때의 대비용MFA 흐름이면 MFA를 요구합니다. 내장 평가기는 평가 중 오류를 스스로 "MFA 필요"로 바꾸므로 보통은 쓰이지 않습니다

정책의 결정은 네 가지입니다: NO_MFA_REQUIRED(필요 없음), CHALLENGED(필요), BLOCKED(차단), ESCALATED(검토 보류, 접근 차단). 차단과 검토 보류는 1차 로그인에 403 AUTHENTICATION_BLOCKED로 답합니다.

AI 적응형 공급자는 평가기의 결정에 AI 분석 결과(차단 표시, 결정 종류, 위험 점수)를 더해 조정합니다. AI 기능(AICoreOperations)이 없으면 이 조정 없이 평가기의 결정을 그대로 씁니다. 승인된 에이전트 계정의 결정은 조정하지 않습니다.

정책 바꾸기

  • 평가기 더하기: MfaPolicyEvaluator 빈을 두면 내장 평가기와 함께 우선순위 순으로 고려됩니다. supports(...)로 맡을 사용자를 좁히세요. 모든 사용자를 맡는 평가기를 100보다 높게 두면 Zero Trust 판정에 따른 결정을 대신하게 됩니다.
  • 흐름 하나만: .mfa(mfa -> mfa.policyProvider(myProvider))로 그 흐름의 공급자를 바꿉니다.
  • 공급자 전체: 빈 이름을 aiAdaptiveMfaPolicyProvider로 한 MfaPolicyProvider 빈을 두면 기본 공급자를 대신합니다. 다른 이름으로 같은 타입 빈을 더하면 @Primary인 기본 공급자가 그대로 쓰입니다. 공급자는 evaluateInitialMfaRequirement, evaluateNextFactor, isFactorAvailableForUser, getRequiredFactorCount 네 메서드를 구현합니다.
@Bean
public MfaPolicyEvaluator adminFlowAlwaysMfa() {
    return new MfaPolicyEvaluator() {
        @Override
        public boolean supports(FactorContext context) {
            return context != null && "mfa_admin".equals(context.getFlowTypeName());
        }

        @Override
        public MfaDecision evaluatePolicy(FactorContext context) {
            return MfaDecision.challenged("The admin flow always asks for a second factor");
        }

        @Override
        public int getPriority() {
            return 500;
        }
    };
}

평가기 안에서는 FactorContext의 속성으로 요청 정보를 읽습니다. 예: 1차 로그인 요청의 IP는 context.getAttribute(FactorContextAttributes.DeviceAndSession.CLIENT_IP).

로그인 뒤 추가 인증

로그인한 사용자의 다음 요청에 저장된 판정이 CHALLENGE이면, 요청 시점 챌린지 필터가 MFA를 다시 시작합니다(단계 상승). 브라우저는 /contexa/zero-trust/challenge-required?mfaUrl=… 안내 화면으로, API는 401 MFA_CHALLENGE_REQUIRED(본문 mfaUrl · challengeNoticeUrl)를 받습니다. 이 MFA가 성공하면 판정이 ALLOW로 바뀝니다. 자세한 응답은 요청 시점 집행에 있습니다.

자바스크립트 SDK를 올린 화면에서는 SDK가 fetch 응답을 보고 아래처럼 처리합니다.

응답SDK 동작
401 MFA_CHALLENGE_REQUIRED · BLOCK_MFA_REQUIREDchallengeNoticeUrl(없으면 mfaUrl)로 이동
그 밖의 401(접근 토큰 만료)토큰을 한 번 갱신하고 같은 요청을 다시 보냄
403 ACCOUNT_BLOCKED · BLOCK_MFA_FAILEDredirectUrl(차단 화면)로 이동
423 SECURITY_REVIEW_IN_PROGRESSredirectUrl(분석 대기 화면)로 이동
403 + 응답 끊김 표식차단 화면으로 이동

MFA를 마친 뒤 원래 요청을 자동으로 다시 보내지는 않습니다. 다시 보내는 것은 만료된 토큰을 갱신한 경우뿐입니다.

여러 MFA 흐름

MFA 흐름마다 자기 체인 · 요소 · 주소를 가질 수 있습니다. urlPrefix("/admin")를 주면 그 흐름의 모든 MFA 주소 앞에 접두사가 붙고, 체인 범위가 /admin/**가 됩니다(securityMatcher 자동). 접두사에는 영문 · 숫자 · / · _ · -만 쓸 수 있습니다.

기본 주소urlPrefix("/admin")
/mfa/login/admin/mfa/login
/mfa/select-factor/admin/mfa/select-factor
/login/mfa-ott/admin/login/mfa-ott
/login/mfa-webauthn/admin/login/mfa-webauthn
/mfa/cancel/admin/mfa/cancel
  • 흐름 이름: name("admin")을 주면 mfa_admin, 주지 않으면 mfa, mfa_2, mfa_3 순으로 붙습니다.
  • 접두사 없는 MFA 흐름은 모든 요청을 받으므로 맨 뒤에 둡니다. 그 뒤의 흐름은 도달하지 못하며 시작 로그에 오류가 남습니다.
  • .mfa()에는 rawHttp가 없습니다. 범위는 urlPrefix로 정합니다.
registry
        .mfa(mfa -> mfa.name("admin").urlPrefix("/admin").order(50)
                .primaryAuthentication(primary -> primary.formLogin(Customizer.withDefaults()))
                .passkey(Customizer.withDefaults())
                .requiredFactors(1))
        .session(Customizer.withDefaults())
        .mfa(mfa -> mfa
                .primaryAuthentication(primary -> primary.formLogin(Customizer.withDefaults()))
                .ott(Customizer.withDefaults()))
        .session(Customizer.withDefaults())
        .build();

단일 로그인과 함께 쓰기

MFA 흐름과 단일 로그인 흐름을 함께 둘 수 있습니다. 순서(order)와 범위로 요청을 나누고, 흐름마다 상태를 따로 고릅니다.

registry
        .mfa(mfa -> mfa.urlPrefix("/admin").order(50)
                .primaryAuthentication(primary -> primary.formLogin(Customizer.withDefaults()))
                .passkey(Customizer.withDefaults()))
        .session(Customizer.withDefaults())
        .rest(rest -> rest.order(100))
        .oauth2(Customizer.withDefaults())
        .build();

.mfa() 옵션

자바스크립트 SDK

/js/contexa-mfa-sdk.js를 올리면 window.ContexaMFA(버전 2.2.0)가 생깁니다. Contexa가 만든 MFA 화면은 이 SDK를 씁니다. 직접 만든 화면이나 SPA에서는 new ContexaMFA.Client(options)로 씁니다.

<script src="/js/contexa-mfa-sdk.js"></script>
<script>
  const mfa = new ContexaMFA.Client({ tokenPersistence: 'sessionStorage' });

  async function signIn(username, password) {
    // 1차 로그인은 apiClient로 보냅니다. 응답에 따라 selectFactor · verifyOtt · verifyPasskey를 이어서 부릅니다.
    const result = await mfa.apiClient.loginForm(username, password);
    console.log(result);
  }
</script>

autoInittrue저장된 MFA 진행 상태와 토큰을 되살림

진행 상태

MFA 진행은 상태 기계(MfaState)가 관리합니다. 끝나는 상태는 다음과 같습니다.

상태뜻
MFA_SUCCESSFULMFA 성공
MFA_NOT_REQUIREDMFA 필요 없음
MFA_FAILED_TERMINAL최종 실패
MFA_CANCELLED사용자가 취소
MFA_SESSION_EXPIREDMFA 세션 만료
MFA_SESSION_INVALIDATEDMFA 세션 무효화
MFA_RETRY_LIMIT_EXCEEDED시도 한도(contexa.auth.mfa.max-retry-attempts) 초과
MFA_SYSTEM_ERROR시스템 오류
상태 변경 이벤트는 발행되지 않습니다. 상태 기계 이벤트 클래스(MfaStateMachineEvents)는 코드에 있지만 현재 버전에서는 아무 곳에서도 발행하지 않으므로 @EventListener로 받을 수 없습니다.

결과 처리 바꾸기

  • .mfa()의 mfaSuccessHandler · mfaFailureHandler는 값을 받기만 하고 쓰이지 않습니다.
  • MFA 응답을 만드는 처리기(PrimaryAuthenticationSuccessHandler, MfaFactorProcessingSuccessHandler, UnifiedAuthenticationFailureHandler)는 상속할 수 없는(final) 클래스입니다.
  • 그래서 MFA 결과는 위 응답 형식의 JSON · 이동을 받아 화면이나 SDK에서 처리합니다. 단일 로그인 흐름의 처리기는 성공 · 실패 처리를 보세요.

설정

설정기본값뜻 · 언제 바꾸나

  • MFA 세션 저장 위치는 contexa.infrastructure.mode가 정합니다. standalone(기본)은 HTTP 세션, distributed(Redis 있음)는 Redis이며, Redis 키 접두사 mfa:session:v2:와 쿠키 이름 MFA_SID는 고정입니다. contexa.auth.mfa 아래의 저장소 선택 · Redis 설정은 읽히지 않습니다.

설정 전체는 Contexa가 로그인을 맡을 때의 설정에 있습니다.
