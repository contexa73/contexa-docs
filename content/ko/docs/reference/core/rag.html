RAG: 문서 저장과 검색

Contexa의 벡터 저장소(pgvector)에 문서를 저장하고, 뜻이 비슷한 문서를 찾아 AI 모델에 함께 보내는(RAG) 방법을 설명합니다. 준비할 것, 저장 · 검색 · 실패 처리, 도메인 전용 서비스 만들기, 그리고 판정 엔진의 과거 판정 기록이 같은 저장소를 어떻게 쓰는지 알 수 있습니다.

한눈에 보기

문서를 저장하면 임베딩 모델이 본문을 숫자 목록(벡터)으로 바꿔 pgvector 표에 넣습니다. 검색할 때는 질의 글도 벡터로 바꿔 가장 가까운 문서를 찾습니다.

  • 범용 서비스(UnifiedVectorService): 아무 문서나 저장 · 검색 · 삭제합니다. 검색 캐시, 바쁨 재시도, 실패한 저장의 재시도가 들어 있습니다. 판정 엔진의 과거 판정 기록도 이 서비스를 씁니다.
  • 도메인 전용 서비스(Lab): AbstractVectorLabService를 상속해 한 종류의 문서에 맞춘 서비스입니다. 메타데이터 보강 · 검증 · 지표를 더합니다. 예: BehaviorVectorService(core), PolicyGenerationVectorService(iam).
  • 둘 다 같은 계약 VectorOperations를 구현합니다.

준비

  • 벡터 저장소: Spring AI pgvector 스타터(spring-ai-starter-vector-store-pgvector)를 넣고 임베딩 모델이 있으면 Contexa가 Contexa 전용 DB에 자기 벡터 저장소 빈(contexaVectorStore)을 직접 만듭니다. 앱의 VectorStore 빈은 쓰지 않습니다. 이 빈이 없으면 범용 · 행동 기록 서비스가 만들어지지 않고, 파이프라인의 문맥 검색은 빈 결과를 돌려줍니다.
  • 임베딩 모델: Spring AI 임베딩 모델 하나(공급자 하나로 고정). 고르는 방법은 임베딩 모델 고르기에 있습니다. Contexa는 앱의 모델을 따릅니다. 모델을 적지 않은 OpenAI는 Spring AI 기본값 text-embedding-ada-002입니다.
  • 표: Contexa는 기본으로 contexa.vectorstore.pgvector.initialize-schema를 켜 둡니다. 첫 시작 때 Contexa 전용 DB에 vector 확장 · 표(public.ctxa_vector_store) · HNSW 색인과, 사용자별 검색에 쓰는 메타데이터 색인이 만들어집니다.
  • 스키마를 마이그레이션으로 관리한다면 initialize-schema를 끄고 표 · 벡터 색인 · 메타데이터 색인을 직접 만듭니다. 끄면 시작할 때 아무것도 만들거나 바꾸지 않습니다.
  • Contexa 저장소는 contexa.vectorstore.pgvector.*에 적은 키를 읽습니다. spring.ai.vectorstore.pgvector.*는 앱 자신의 Spring AI 저장소를 위한 키라 Contexa 저장소에는 쓰이지 않습니다(차원만 예외로 아래 순서에서 읽힙니다). 색인 종류 contexa.vectorstore.pgvector.index-type(기본 HNSW)와 거리 contexa.vectorstore.pgvector.distance-type(기본 COSINE_DISTANCE)는 Contexa가 직접 쓰지 않고, 이 저장소를 만들 때 Spring AI 저장소 빌더에 넘깁니다.
  • contexa.rag.enabled=false면 RAG 자동 구성이 꺼집니다.
# 운영 DB의 스키마를 마이그레이션으로 관리할 때
contexa:
  vectorstore:
    pgvector:
      initialize-schema: false   # Contexa 벡터 저장소가 읽음(기본 true)

차원 맞추기

pgvector 표의 차원은 임베딩 모델이 내놓는 벡터 길이와 같아야 합니다. Contexa는 아래 순서로 차원을 정하고, 정한 값을 기본 설정으로 넣습니다. 새 DB의 벡터 열도 이 크기로 만들어집니다.

  1. contexa.vectorstore.pgvector.dimensions(또는 spring.ai.vectorstore.pgvector.dimensions)
  2. contexa.llm.embedding.dimensions
  3. 공급자 설정: OpenAI는 spring.ai.openai.embedding.options.dimensions, Ollama는 contexa.llm.embedding.ollama.dimensions · spring.ai.ollama.embedding.options.dimensions
  4. Contexa가 아는 모델의 값: text-embedding-ada-002 · text-embedding-3-small은 1536, text-embedding-3-large는 3072, mxbai-embed-large · bge-m3는 1024
  5. 그 밖의 모델은 위 1~3 가운데 하나를 적어야 합니다(없으면 시작하지 않음).
# 더 작은 출력으로 쓰기(OpenAI): text-embedding-3-large는 그대로면 3072 차원
spring:
  ai:
    openai:
      embedding:
        options:
          model: text-embedding-3-large
          dimensions: 1536

시작할 때 차원을 검사하고, 아래 경우에는 시작을 멈춥니다.

  • 모르는 임베딩 모델인데 차원을 적지 않음(Unknown embedding model dimension)
  • pgvector 차원 설정이 임베딩 모델의 차원과 다름(Embedding dimension mismatch)
  • 이미 있는 표의 embedding 열 차원이 설정과 다름. 표를 다시 만들거나 문서를 다시 임베딩해야 합니다. 이전 버전의 OpenAI 설치(1024 표)는 두 줄을 넣으면 다시 임베딩하지 않고 그대로 유지됩니다.
  • Contexa가 표를 만드는데 차원이 2000을 넘음. pgvector HNSW 색인은 2000차원까지입니다. 더 작은 출력을 지정하거나, 표를 직접 만들고 contexa.vectorstore.pgvector.initialize-schema=false를 적습니다.

통과하면 INFO Embedding vector dimension verified: provider=…, model=…, dimension=…, source=…가 남습니다.

문서 저장하기

// UnifiedVectorService 를 주입받았다고 봅니다
Document policyDoc = new Document(
        "관리자 작업에는 MFA가 필요합니다",
        Map.of("documentType", "policy", "category", "auth"));

unifiedVectorService.storeDocument(policyDoc);
  • 메타데이터 채우기: id(문서 id), timestamp(없으면 지금), documentType(없으면 standard), version(없으면 1.0)을 넣습니다. 임베딩 모델을 알면 embeddingModel(공급자/모델)도 넣고, 이 값은 임베딩할 글에서는 뺍니다.
  • 같은 사건은 덮어쓰기: 메타데이터에 eventId와 documentType이 둘 다 있으면 id를 그 둘로 정합니다(UnifiedVectorService.documentId()). 같은 사건을 다시 저장하면 새 줄을 더하지 않고 덮어씁니다.
  • 여러 개: storeDocuments(list)는 contexa.vectorstore.pgvector.batch-size(기본 100)씩 나눠 넣습니다.
  • 나중에 저장: storeLater(document)는 지금 저장하지 않고 재시도 대기열에 맡깁니다(재시도를 끄면 바로 저장).
  • 본문이 비었으면 VectorStoreException입니다. 저장 제한 시간은 contexa.vectorstore.pgvector.store-timeout-ms(기본 15000ms)입니다.
  • documentType에 behavior · behavior_analysis · suspicious · threat · ambiguous를 쓰면 판정 기록과 함께 보관 기간이 지나 지워집니다(아래). 앱 문서는 다른 이름을 쓰세요.

검색하기

// 같음(==) 조건으로 거르기
List<Document> docs = unifiedVectorService.searchSimilar(
        "multi-factor authentication requirements",
        Map.of("category", "auth"));

// 건수 · 관련도 · 필터 식을 직접 정하기
List<Document> top5 = unifiedVectorService.searchSimilar(SearchRequest.builder()
        .query("MFA 정책")
        .topK(5)
        .similarityThreshold(0.7)
        .filterExpression("category == 'auth' && version == '1.0'")
        .build());
  • 기본값: 질의만 주면 상위 contexa.vectorstore.pgvector.top-k(100)건, 관련도 contexa.vectorstore.pgvector.similarity-threshold(0.5) 이상입니다. 검색 제한 시간은 contexa.vectorstore.pgvector.search-timeout-ms(15000ms), HNSW 검색 폭은 contexa.vectorstore.pgvector.hnsw.ef-search(100)입니다.
  • 검색 캐시: 같은 검색 결과를 contexa.security.tiered.vector-cache.expire-minutes(5분) 동안, 최대 max-size(10000)건 기억합니다. 문서를 쓰면 영향을 받는 검색(쓴 사용자 · 그 조직 · 범위 없는 검색)을 지웁니다(invalidate-on-write). contexa.security.tiered.vector-cache.enabled=false로 끕니다.

범용 서비스의 필터 키는 영문자 · 숫자 · _ · . · -만 쓸 수 있습니다(그 밖은 IllegalArgumentException). 여러 조건은 모두 맞아야 합니다(AND).

실패에 대비하기

  • 바쁨 재시도: 저장소가 "바쁨"(maximum pending requests exceeded, server busy, please try again, HTTP 503, Spring AI 일시 오류)으로 답하면 250ms부터 두 배씩(최대 2초) 기다리며 모두 5번까지 시도합니다. 횟수는 JVM 시스템 속성 contexa.vector.busy-retry-attempts로 바꿉니다.
  • 실패한 저장의 재시도(기본 켜짐): 저장이 실패한 문서는 호출한 쪽에 오류를 돌려주면서 대기열에 들어가고, 뒤에서 다시 저장됩니다. contexa.vectorstore.retry.*로 정합니다: 대기열 2000건(차면 가장 오래된 문서를 버림), 문서마다 최대 20번 · 처음 실패부터 1시간까지, 첫 대기 10초에서 두 배씩 최대 5분, 한 번에 20건(실패가 이어지면 반으로 줄이고 성공하면 다시 늘림). contexa.vectorstore.retry.enabled=false면 실패를 돌려주기만 합니다.
  • 재시작에도 남기려면: 대기열은 기본으로 메모리에 있어 재시작하면 사라집니다. 남겨야 하면 FailedDocumentSink 빈(예: 아웃박스 표)을 직접 둡니다.
  • 삭제와 계정 정리: deleteDocuments(ids)는 대기열에서 기다리는 같은 문서도 지웁니다. 계정을 지울 때는 그 사용자의 대기 문서를 버립니다(discardPendingStores(userId)).
  • 늦게 저장된 문서를 알고 싶으면 addRetriedStoreListener(listener)를 등록합니다.

도메인 전용 서비스(Lab) 만들기

한 종류의 문서만 다루는 서비스가 필요하면 AbstractVectorLabService를 상속합니다. 메서드 네 개를 채우면 저장할 때 메타데이터 보강 · 검증이, 검색할 때 서비스 전용 필터가 붙습니다.

public class FaqVectorService extends AbstractVectorLabService {

    public FaqVectorService(VectorStore vectorStore, ContexaRagProperties ragProperties) {
        super(vectorStore, null, ragProperties);   // 지표(VectorStoreMetrics)가 없으면 null
    }

    @Override
    protected String getLabName() { return "Faq"; }

    @Override
    protected String getDocumentType() { return "faq"; }

    @Override
    protected Document enrichLabSpecificMetadata(Document document) {
        Map<String, Object> metadata = new HashMap<>(document.getMetadata());
        metadata.put("language", "ko");
        return new Document(document.getText(), metadata);
    }

    @Override
    protected void validateLabSpecificDocument(Document document) {
        if (!document.getMetadata().containsKey("category")) {
            throw new IllegalArgumentException("category is required");
        }
    }
}
  • 저장할 때: id(없으면 무작위) · timestamp · documentType(없으면 getDocumentType()) · labName · processingTimestamp를 넣고, 검증(contexa.rag.lab.validation-enabled) → 보강(contexa.rag.lab.enrichment-enabled) 순서로 부른 뒤 값이 null인 메타데이터를 뺍니다. 여러 개는 contexa.rag.lab.batch-size씩 넣습니다.
  • 검색할 때: getLabSpecificFilters()가 돌려준 필터가 더해집니다. 필터에 topK를 넣으면 건수로 쓰고, 없으면 contexa.rag.lab.top-k입니다. 관련도는 contexa.rag.lab.similarity-threshold입니다.
  • Lab 서비스는 VectorStore를 바로 씁니다. 검색 캐시 · 바쁨 재시도 · 저장 재시도는 없습니다.
  • 저장 · 삭제 메서드는 Contexa 트랜잭션 관리자(contexaTransactionManager)의 트랜잭션 안에서 돕니다(Spring 빈으로 둘 때).
  • VectorStoreMetrics 빈을 두면 저장 · 검색 · 삭제의 건수 · 시간 · 오류를 서비스 이름별로 기록합니다. OSS에는 이 빈의 구현이 없습니다.
  • 저장 · 검색 뒤에 할 일이 있으면 postProcessDocument(document, operationType)를 재정의합니다.
# Lab 서비스 공통 설정(아래는 기본값)
contexa:
  rag:
    lab:
      batch-size: 50
      top-k: 100
      similarity-threshold: 0.75
      validation-enabled: true
      enrichment-enabled: true

행동 기록 서비스(BehaviorVectorService)

사용자 행동을 문서로 저장하고 비슷한 행동을 찾는 Lab 서비스입니다(이름 BehavioralAnalysis, 문서 종류 behavior). VectorStore 빈이 있으면 만들어집니다. OSS 코드에는 이 서비스의 메서드를 부르는 곳이 없습니다. 판정 엔진의 과거 판정 기록은 이 서비스가 아니라 범용 서비스로 저장 · 검색합니다(아래).

메서드하는 일
storeBehavior(context)사용자 · IP(remoteIp) · 세션(없으면 무작위 ID) · 브라우저 · OS · 새 단말 · 새 위치를 메타데이터로, User: …, IP: …, Path: …, Activity: … 글을 본문으로 저장. 경로는 문맥 메타데이터 requestPath
storeThreatPattern(context, response)문서 종류 threat로 위협 패턴 저장. 실패해도 예외 없이 로그만
storeAnalysisResult(context, response)문서 종류 behavior_analysis로 분석 결과 저장(analysisId)
findSimilarBehaviors(userId, ip, path, topK)그 사용자 · 이 서비스의 문서 가운데 비슷한 행동. 실패하면 빈 목록
 
BehavioralAnalysisContext context = new BehavioralAnalysisContext("user-123", "session-abc");
context.setRemoteIp("192.168.1.100");
context.setUserAgent("Mozilla/5.0");
context.setCurrentActivity("GET /api/reports");
context.addMetadata("requestPath", "/api/reports");

behaviorVectorService.storeBehavior(context);

List<Document> similar = behaviorVectorService
        .findSimilarBehaviors("user-123", "192.168.1.100", "/api/reports", 5);
  • 검증: 메타데이터에 userId · sessionId · ipAddress 가운데 하나가 있고, 본문이 10자 이상이어야 합니다.
  • 보강: 저장하는 시각의 hour · dayOfWeek · isWeekend와, remoteIp의 마지막 점 앞부분인 networkSegment를 더합니다.
  • 이 서비스가 쓰는 behavior · threat · behavior_analysis 문서도 판정 기록과 함께 보관 기간이 지나면 지워집니다.

판정 엔진의 과거 판정 기록

보안 판정 엔진은 저장소를 따로 두지 않고, 같은 범용 서비스(UnifiedVectorService)와 같은 pgvector 표를 씁니다. 판정 엔진 쪽의 자세한 내용은 판정 엔진: 무엇을 배우나에 있습니다.

  • 저장: 집행이 그 대응을 실제로 적용했을 때만 판정 문서를 저장합니다(섀도 모드에서는 저장하지 않음). 문서 종류는 판정에 따라 ALLOW → behavior, BLOCK → threat, CHALLENGE → suspicious, ESCALATE · 분석 대기 → ambiguous입니다. id는 사건 ID와 문서 종류로 정해지고, 저장이 실패하면 위 재시도 대기열을 탑니다.
  • 읽기: v20 · v21 프롬프트 묶음은 임베딩 없이 pgvector 표의 메타데이터를 직접 조회합니다(정확 조회, PgVectorPastRecordQuery). v19 묶음은 같은 서비스의 유사도 검색(searchSimilar)을 사용자 조건과 함께 씁니다. 사용자 ID가 없는 사건은 과거 기록을 찾지 않습니다.
  • 보관: contexa.rag.etl.behavior.retention-days(90일)보다 오래된 behavior · behavior_analysis · suspicious · threat · ambiguous 문서를 매일 03:45(contexa.rag.etl.behavior.retention-cleanup-cron)에 지웁니다. 0 이하면 지우지 않습니다. 지운 뒤에는 검색 캐시를 비웁니다.
  • 같은 표를 쓰므로: 앱 문서와 판정 기록이 한 표에 함께 있습니다. 앱 문서의 documentType은 위 다섯 이름과 겹치지 않게 두세요.

파이프라인과 RAG 어드바이저

  • 파이프라인의 문맥 검색 단계(CONTEXT_RETRIEVAL): 기본 검색기(AuthorizedContextRetriever)가 범용 서비스로 찾습니다. 질의는 요청 매개변수 naturalLanguageQuery, 없으면 도메인 문맥의 글입니다. 상위 contexa.rag.defaults.top-k(10)건, 관련도 contexa.rag.defaults.similarity-threshold(0.7) 이상을 찾고, 그 가운데 요청의 사용자 · 조직 · 테넌트 · 검색 목적에 맞는 문서만 프롬프트에 넣습니다(PromptContextAuthorizationService). 파이프라인은 AI 파이프라인에 있습니다.
  • RAG 검색 어드바이저 빈: VectorStore와 ChatClient.Builder 빈이 있으면 Spring AI RetrievalAugmentationAdvisor 빈이 만들어집니다. riskAssessmentRagAdvisor(risk_assessment 문서 중 riskScore 0.5 이상, contexa.rag.risk.top-k 50건 · similarity-threshold 0.8), policyGenerationRagAdvisor(policy_evolution 문서, 20건 · 0.7). 둘 다 질의를 먼저 채팅 모델로 다듬습니다.
  • behaviorAnalysisRagAdvisor는 contexa.rag.behavior.shared-advisor-enabled=true일 때만 만들어집니다(기본 꺼짐). 모든 사용자의 최근 contexa.rag.behavior.lookback-days(30)일 behavior 문서를 찾으므로, 사용자별로 찾으려면 사용자 조건을 넣은 어드바이저를 직접 만드세요.
  • OSS 코드에는 이 어드바이저 빈을 쓰는 곳이 없고, 레지스트리에도 자동으로 들어가지 않습니다. 쓰려면 호출에 ExecutionContext.addAdvisor(…)로 넣습니다(어드바이저).
  • contexa.rag.vocabulary-reindex-on-start(기본 true): 시작한 뒤 뒤에서, 옛 분류 어휘로 저장된 과거 기록 문서를 지금 어휘로 옮깁니다.

확인하기

  • 시작 로그: INFO Embedding vector dimension verified: …가 보이면 차원 검사를 통과한 것입니다.
  • 저장 실패: unifiedVectorService.storeFailureStats()가 StoreFailureStats(failed · pending · retried · dropped · deferred)를 돌려줍니다. Micrometer가 있으면 같은 값이 지표 contexa.vector.store.*(failed · pending · retried · dropped · deferred)로 나갑니다.
  • 검색 캐시: VectorStoreCacheLayer.getStatistics()(적중 · 실패 수, record-stats가 켜졌을 때).
  • 바쁨 재시도: WARN [UnifiedVectorService] Retrying … after busy failure (attempt=…, backoff=…ms, …).
