어드바이저: LLM 호출 앞뒤에 끼어들기

어드바이저는 Contexa가 AI 모델을 부를 때마다 요청 앞뒤에서 실행되는 부품입니다. 기본으로 들어 있는 보안 문맥 어드바이저가 하는 일, 내 어드바이저를 만들어 등록하는 방법, 실행 순서와 오류 처리, 켜고 끄는 방법을 설명합니다.

한눈에 보기

어드바이저는 Spring AI의 CallAdvisor · StreamAdvisor입니다. 모델에 가기 전 요청을 살피거나 바꾸고, 돌아온 응답을 살핍니다. Contexa의 어드바이저는 기본 클래스 BaseAdvisor를 상속해 도메인(묶음 이름) · 이름 · 순서를 가지고, 레지스트리(AdvisorRegistry)가 켜진 것을 순서대로 모아 둡니다. 오케스트레이터는 모델을 부를 때마다 이 목록을 붙입니다(LLM 호출하기).

  • 자동 등록: BaseAdvisor를 상속한 Spring 빈은 레지스트리가 만들어질 때 한 번 등록됩니다.
  • 자동으로 붙지 않는 것: BaseAdvisor가 아닌 Spring AI Advisor 빈(예: RAG 검색 어드바이저)은 레지스트리에 들어가지 않습니다. 붙이려면 advisorRegistry.register(…)로 등록하거나 호출마다 ExecutionContext.addAdvisor(…)로 넣습니다.
  • OSS가 기본으로 주는 레지스트리 어드바이저는 SECURITY 도메인의 보안 문맥 어드바이저 하나입니다.

기본 어드바이저: 보안 문맥(SecurityContextAdvisor)

모든 LLM 호출의 요청 문맥에 "누구의 호출인지"를 넣고, 응답이 오면 감사 로그를 남깁니다. 이름은 SECURITY.security-context, 순서는 contexa.advisor.security.order(기본 50)입니다.

  1. 오케스트레이터가 ExecutionContext의 userId · sessionId를 event.userId · event.sessionId로 넘깁니다(execute() 계열이고 어드바이저가 켜진 호출만).
  2. event.userId가 있으면 비동기 보안 문맥 제공자(AsyncSecurityContextProvider)에서 그 사용자의 인증 정보를 찾습니다. 제공자는 generalRedisTemplate 빈이 있으면(분산 모드) Redis, 없으면 메모리입니다.
  3. 아래 키를 요청 문맥에 넣습니다.
키값
user.id찾은 인증 정보의 사용자, 없으면 event.userId, 그것도 없으면 anonymous
session.id찾은 인증 정보의 세션, 없으면 event.sessionId, 그것도 없으면 async-<UUID>
authenticated인증 정보를 찾았거나 event.userId가 있으면 true
authorities찾은 인증 정보의 권한(글). 인증 정보를 찾았을 때만
principal.type찾은 인증 정보의 주체 종류(없으면 AsyncPrincipal). 인증 정보를 찾았을 때만
async.context늘 true
timestamp요청 시각(밀리초)

응답이 오면 INFO 로그 LLM audit - userId: …, sessionId: …, authenticated: …, executionTimeMs: …, hasResponse: …를 남깁니다.

인증 요구는 "사용자 ID가 넘어왔는지"만 봅니다. contexa.advisor.security.require-authentication=true(기본 false)면 사용자 ID도 인증 정보도 없는 호출을 차단 오류로 막아 모델을 부르지 않습니다. 실제 로그인을 확인하는 것은 아닙니다. 또 stream()은 사용자 ID를 넘기지 않고 스트림에서는 차단 오류도 건너뛰므로 막지 못하고, advisorEnabled(false)인 호출은 이 어드바이저를 거치지 않습니다.

내 어드바이저 만들기

BaseAdvisor를 상속하고 beforeCall · afterCall 두 메서드를 채운 뒤 Spring 빈으로 둡니다. 아래는 너무 긴 프롬프트를 막는 예입니다.

@Component
public class PromptSizeAdvisor extends BaseAdvisor {

    private static final int MAX_CHARS = 20_000;

    public PromptSizeAdvisor() {
        super("APP", "prompt-size", 60);   // 도메인, 이름, 순서(50보다 크면 보안 문맥 어드바이저 다음)
    }

    @Override
    protected ChatClientRequest beforeCall(ChatClientRequest request) {
        String text = request.prompt().getContents();
        if (text != null && text.length() > MAX_CHARS) {
            throw AdvisorException.blocking(getDomain(), getName(),
                    "Prompt too long for user " + request.context().get("user.id"));
        }
        return request;
    }

    @Override
    protected ChatClientResponse afterCall(ChatClientResponse response, ChatClientRequest request) {
        return response;
    }
}
  • 순서: 보안 문맥 어드바이저가 넣은 user.id를 읽으려면 순서를 50보다 크게 둡니다. 더 작으면 그 값이 아직 없습니다(이때는 event.userId를 읽으세요).
  • 이름: 전체 이름은 도메인.이름(예: APP.prompt-size)입니다. 도메인이나 이름이 비면 등록할 때 IllegalArgumentException이 납니다.
  • 스트림: beforeStream은 기본으로 beforeCall을 부르고, afterStream은 기본으로 아무것도 하지 않습니다(스트림 응답 조각마다 불림). 스트림에서 다르게 하려면 재정의합니다.
  • 문맥 키: beforeCall 뒤에 advisor.domain · advisor.name · advisor.timestamp가 요청 문맥에 들어갑니다(enrichContext).
  • 설정값으로 켜고 끄려면 isEnabled()를 재정의합니다. 이것은 레지스트리 목록에 들어갈지만 정하고, 붙은 뒤 실제로 동작할지는 setEnabled(…)로 바꾸는 값이 정합니다.

실행 순서와 오류 처리

레지스트리는 getOrder()가 작은 것부터 늘어놓습니다. 요청은 이 순서로, 응답은 거꾸로 지나갑니다. 오류가 나면 언제 났는지와 호출 방식에 따라 다르게 처리됩니다.

경우동기 호출(execute() 계열)스트림(stream())
모델 호출 전(beforeCall)에 차단 오류(AdvisorException.blocking(…))모델을 부르지 않고 그 오류로 끝납니다. 요청 문맥에 advisor.error · advisor.error.message · advisor.error.domain · advisor.blocked.by를 남깁니다.이 어드바이저만 건너뛰고 모델을 부릅니다(막지 못함).
모델 호출 전에 비차단 오류(AdvisorException.nonBlocking(…))이 어드바이저만 건너뛰고 계속합니다.같음
모델 호출 전에 그 밖의 예외요청 문맥 <도메인.이름>.error에 메시지를 남기고 계속합니다.건너뛰고 계속합니다.
모델 호출 뒤(afterCall)나 안쪽에서 난 오류종류와 상관없이 오류로 끝납니다(차단 오류면 위 문맥 키도 남김).스트림이 오류로 끝납니다.

켜고 끄기

범위방법결과
어드바이저 하나setEnabled(false) · setEnabled(true)꺼지면 아무것도 하지 않고 다음으로 넘깁니다
도메인 하나advisorRegistry.disableDomain("SECURITY") · enableDomain(…)그 도메인의 어드바이저를 모두 끄거나 켭니다
전부disableAll() · enableAll()등록된 BaseAdvisor를 모두 끄거나 켭니다
호출 하나ExecutionContext.builder().advisorEnabled(false)전역 어드바이저가 빠집니다. ThinkingGenerationAdvisor와 그 호출의 어드바이저는 남습니다
보안 문맥 어드바이저contexa.advisor.security.enabled=false레지스트리 목록에서 빠집니다

레지스트리를 바꾸면 오케스트레이터의 다음 호출부터 반영됩니다(호출마다 켜진 목록을 비교해 바뀌었으면 ChatClient를 다시 만듭니다). 다만 primaryChatClient 빈은 시작할 때의 목록으로 만들어져 바뀌지 않습니다.

// 점검 중에는 SECURITY 도메인 어드바이저를 모두 끔
advisorRegistry.disableDomain("SECURITY");

// 점검이 끝나면 다시 켬
advisorRegistry.enableDomain("SECURITY");

// 등록 상태 보기
AdvisorRegistry.RegistryStats stats = advisorRegistry.getStats();
// stats.totalAdvisors, stats.totalDomains, stats.advisorsPerDomain

contexa.advisor.enabled(기본 true)는 끄지 마세요. 끄면 레지스트리 빈이 없어지는데, 오케스트레이터는 이 빈이 있어야 만들어집니다.

확인하기

  • 지금 붙는 목록: advisorRegistry.getEnabled()(순서대로). 어드바이저 하나는 advisorRegistry.get("SECURITY.security-context"), 도메인은 getDomains(), 개수는 getStats().
  • 로그: 보안 문맥 어드바이저의 INFO LLM audit - …, 어드바이저 오류의 ERROR [<이름>] Advisor error after …ms: ….
  • 요청 문맥: 뒤에 도는 어드바이저와 afterCall에서 user.id · advisor.* 키를 읽을 수 있습니다.

설정

설정기본값뜻언제 바꾸나
contexa.advisor.enabledtrue어드바이저 레지스트리 자동 구성바꾸지 않습니다(오케스트레이터가 필요로 함)
contexa.advisor.security.enabledtrue보안 문맥 어드바이저를 붙일지사용자 문맥 · 감사 로그가 필요 없을 때

contexa.advisor.security.require-authenticationfalse사용자 ID가 없는 호출을 막을지(위 주의 참고)모든 동기 LLM 호출에 사용자 ID를 붙이게 할 때
읽는 곳이 없는 설정. contexa.advisor.chain-profile(기본 STANDARD), contexa.advisor.soar.approval.enabled · order · timeout, contexa.llm.advisor-enabled는 받기만 하고 쓰는 코드가 없어 바꿔도 아무 일도 일어나지 않습니다. OSS에는 SOAR 승인 어드바이저가 없습니다(SOAR는 SOAR 확장점 참고).
