LLM 호출하기

Contexa 안에서 AI 모델(LLM)을 부르는 호출은 모두 한 곳(오케스트레이터)을 지납니다. 앱 코드에서 모델을 직접 부르는 방법, 요청이 어느 모델로 가는지, 제한 시간 · 재시도 · 공급자별 옵션이 어떻게 붙는지, 호출 결과를 어떻게 확인하는지 설명합니다.

한눈에 보기

오케스트레이터(UnifiedLLMOrchestrator)는 Contexa의 LLM 호출 창구입니다. 파이프라인의 LLM 실행 단계(LLM_EXECUTION), 보안 판정 엔진, 앱 코드가 모두 이 객체로 모델을 부릅니다. 호출 하나는 아래 순서로 처리됩니다.

하려는 일쓰는 것
입력 · 출력 형식이 정해진 AI 기능 만들기Strategy · Lab · 파이프라인(AI 기능 만들기). 파이프라인의 LLM 실행 단계가 오케스트레이터를 대신 부릅니다.
글 하나 생성 · 채팅ExecutionContext와 execute()
답을 자바 객체로 받기executeEntity()
답을 조각조각 받기stream()(스트리밍)
모델이 앱의 도구를 부르게 하기callTools() · callToolCallbacks()(도구 호출)
모델 · temperature를 정해서 부르기ExecutionContext.builder()의 preferredModel · temperature 등

준비

  • 채팅 모델이 하나 이상 있어야 합니다. Spring AI 공급자 스타터(예: spring-ai-starter-model-openai)를 넣고 spring.ai.<공급자>.*(API 키 · 주소)를 설정하면 Spring AI가 채팅 모델(ChatModel) 빈을 만듭니다. Contexa 전용 Ollama 연결(contexa.llm.chat.ollama.base-url)도 채팅 모델로 칩니다. 연결 방법은 모델 연결과 선택에 있습니다.
  • 채팅 모델이 없으면 오케스트레이터 빈이 만들어지지 않습니다. 모델 고르기가 아무 모델도 찾지 못하면 호출은 No LLM model configured. … 오류로 끝납니다.
  • 주입: LLMOperations(이 페이지의 execute() · stream() · executeEntity()), 또는 프롬프트만 받는 LLMClient · ToolCapableLLMClient로 받습니다. 빈 이름 llmClient · toolCapableLLMClient도 같은 오케스트레이터입니다.
  • 오케스트레이터는 어드바이저 레지스트리(AdvisorRegistry) 빈이 있어야 만들어집니다. contexa.advisor.enabled(기본 true)는 끄지 마세요. 어드바이저를 빼려면 켜고 끄기의 다른 방법을 씁니다.
  • contexa.llm.enabled=false면 LLM 자동 구성 전체(오케스트레이터 · 모델 고르기 · 기본 채팅 모델)가 꺼집니다.

첫 호출

호출 내용은 ExecutionContext에 담습니다. 프롬프트만 있으면 되고, 나머지는 필요할 때만 넣습니다.

@Service
public class SummaryService {

    private final LLMOperations llm;

    public SummaryService(LLMOperations llm) {
        this.llm = llm;
    }

    public Mono<String> summarize(String text, String userId) {
        ExecutionContext context = ExecutionContext.builder()
                .prompt(new Prompt("다음 글을 세 줄로 요약해 주세요.\n\n" + text))
                .requestId(UUID.randomUUID().toString())
                .userId(userId)          // 어드바이저가 받는 사용자 ID
                .temperature(0.2)
                .build();
        return llm.execute(context);     // 답 글
    }
}

답을 자바 객체로 받으려면 executeEntity()에 형식을 줍니다.

record Summary(String title, List<String> points) {}

Mono<Summary> summary = llm.executeEntity(context, Summary.class);
  • 짧게 만들기: ExecutionContext.from(prompt)(프롬프트만), ExecutionContext.forTier(2, prompt)(층 지정). 둘 다 어드바이저를 켠 채 만듭니다.
  • 나중에 더하기: addMetadata(key, value), addAdvisor(advisor), addToolCallback(callback)(도구 실행도 켭니다).
  • 빈 답이 오면 LLM response is null or empty 오류가 납니다. Claude처럼 생각(thinking) 블록을 답 앞에 돌려주는 모델은 생각을 건너뛰고 답만 읽습니다.

요청이 어느 모델로 가나

모델은 호출마다 아래 순서로 정해집니다. 앞에서 정해지면 뒤는 보지 않습니다. 기록되는 값과 자세한 규칙은 모델 연결과 선택에 있습니다.

  1. 명시한 모델: preferredModel, 없으면 메타데이터 requestedModelId → preferredModel → modelId. 그 모델을 만들 수 없으면 다음 단계로 내려갑니다.
  2. 층 모델: analysisLevel(QUICK → 1, NORMAL → 2, DEEP → 3) → securityTaskType(아래 표) → tier 순서로 층을 정합니다. 1 이하는 1층, 2 이상은 2층이고, 그 층의 모델(contexa.security.tiered.llm.layer1.model · layer2.model)을 씁니다. 층 모델이 비어 있으면 이 단계를 건너뜁니다.
  3. 백업 모델: 층 모델을 만들 수 없을 때 그 층의 backup.model
  4. 기본 채팅 모델: 위에서 정하지 못하면 늘 이것(primaryChatModel)

ExecutionContext.getEffectiveTier()는 같은 순서(analysisLevel → securityTaskType → tier)로 정한 층 번호를 돌려줍니다(3도 그대로, 없으면 null).

보안 판정 엔진의 1차 · 2차 분석도 같은 층 모델을 씁니다. 판정에 쓸 층별 모델은 판정 엔진: 층마다 다른 모델 쓰기를 보세요.

작업 종류(securityTaskType)층
THREAT_FILTERING · QUICK_DETECTION1
CONTEXTUAL_ANALYSIS · BEHAVIOR_ANALYSIS · CORRELATION2
EXPERT_INVESTIGATION · INCIDENT_RESPONSE · FORENSIC_ANALYSIS · SOAR_AUTOMATION · APPROVAL_WORKFLOW3(2층 모델로 감)
코드에 있지만 쓰이지 않는 값. AnalysisLevel의 기본 제한 시간(AnalysisLevel.getDefaultTimeoutMs(), 50 · 300 · 5000ms)과 기본 모델 이름(AnalysisLevel.getDefaultModelName()), 층별 temperature(TieredLLMProperties.getTemperatureForTier(), 0.3 · 0.7)는 어떤 호출에도 적용되지 않습니다. temperature가 필요하면 ExecutionContext에 직접 넣으세요.

도구 호출

모델이 답하는 동안 앱의 도구(메서드)를 부르게 할 수 있습니다. Spring AI의 두 방식을 그대로 받습니다. 아래 예는 ToolCapableLLMClient를 toolClient로 주입받았다고 봅니다.

public class IpTools {

    @Tool(description = "Block an IP address")
    public String blockIp(String ip) {
        // 앱의 차단 로직
        return "blocked " + ip;
    }
}

Prompt prompt = new Prompt("Block suspicious IP 192.168.1.100");

// 방식 1: @Tool 메서드를 가진 객체를 넘김
Mono<String> answer = toolClient.callTools(prompt, List.of(new IpTools()));
// 방식 2: ToolCallback 배열을 넘김
ToolCallback[] callbacks = ToolCallbacks.from(new IpTools());
Mono<String> answer = toolClient.callToolCallbacks(prompt, callbacks);
  • 두 메서드 모두 execute()와 같은 길(모델 고르기 · 제한 시간 · 재시도)을 지납니다. 도구 호출 내역까지 받으려면 callToolsResponse() · callToolCallbacksResponse()를 씁니다(ChatResponse를 돌려줌).
  • ExecutionContext로 할 때는 addToolCallback(...)(도구 실행도 켬)이나 toolProviders와 toolExecutionEnabled(true)를 씁니다. 둘 다 있으면 toolCallbacks를 씁니다.
  • 스트리밍: streamTools()는 모델이 답하는 동안 도구를 부릅니다. streamToolCallbacks()는 다르게 동작합니다. 모델이 도구를 고르지 않고, Contexa가 먼저 도구마다 한 번씩 실행한 뒤(입력은 프롬프트에서 도구 이름 뒤에 나오는 첫 JSON, 없으면 프롬프트 전체) 그 결과를 Tool Results: 아래에 붙인 프롬프트로 스트리밍합니다. 도구가 실패하면 [도구 이름] Error: … 줄이 붙습니다.

어드바이저와 함께 쓰기

어드바이저는 모델 호출 앞뒤에서 요청과 응답을 살피는 부품입니다. 자세한 내용은 어드바이저에 있고, 여기서는 오케스트레이터가 붙이는 방식만 정리합니다.

  • 전역 어드바이저: 레지스트리(AdvisorRegistry)에서 켜진 것을 순서대로 붙입니다. 레지스트리가 바뀌면 다음 호출부터 반영됩니다.
  • ThinkingGenerationAdvisor는 늘 붙습니다. 공급자가 답 앞에 돌려준 생각 블록을 건너뛰고 답을 읽게 합니다.
  • 이 호출의 어드바이저: addAdvisor(...)로 넣은 것은 execute() · executeEntity() · 도구 호출에만 붙습니다.
  • advisorEnabled(false): 전역 어드바이저만 빠집니다. ThinkingGenerationAdvisor와 이 호출의 어드바이저는 그대로 붙고, event.userId · event.sessionId는 넘기지 않습니다. 비워 두면(null) 켜진 것으로 봅니다.
  • stream(): 전역 어드바이저만 붙습니다. 이 호출의 어드바이저와 사용자 ID는 넘어가지 않습니다.

제한 시간 · 재시도 · 실패

항목execute() · executeEntity() · 도구 호출stream()
제한 시간contexa.security.plane.llm-timeout.provider-call-timeout-ms(기본 60000ms). 메타데이터 callTimeoutMs가 더 작으면 그 값. 둘 다 없으면(0) 제한 없음timeoutMs(넣었을 때)와 층 제한 시간 contexa.security.tiered.llm.tiered.layer1.timeout-ms · layer2.timeout-ms(기본 30000 · 60000ms, 최대 120000ms)
일시 오류 재시도최대 4번없음
거절된 필드 빼고 다시 보내기한 번없음
공급자 호출 속도 조절켰을 때없음
어드바이저전역 + 이 호출의 것전역만
  • 제한 시간을 넘기면 LLM provider call exceeded timeout … 오류가 나고, 메타데이터 providerCallFailureCategory가 PROVIDER_CALL_TIMEOUT이 됩니다.
  • stream()에서 층을 정했다면(analysisLevel · securityTaskType · tier) 그 층의 제한 시간이 걸립니다. 1층은 시간이 지나면 시간 초과 오류를 TIMEOUT이라는 글로 바꾸고, 2층은 시간 초과 오류 그대로입니다. DEEP처럼 3층이 되는 값을 주면 층 제한 시간을 찾지 못해 Invalid tier value: 3 오류로 끝납니다. 층을 정하지 않으면 층 제한 시간은 없습니다.

다시 보내는 경우

  • 일시 오류 재시도(execute() 계열): 2초부터 간격을 늘려(최대 12초) 최대 4번 다시 보냅니다. 대상은 Spring AI가 일시 오류로 분류한 오류, 입출력 오류(IOException), HTTP 408 · 409 · 429, 502 · 503 · 504 · 연결 끊김 · 연결 거부, "rate limit" · "try again in" 같은 속도 제한 문구입니다. 그 밖의 4xx(요청 자체를 거절)는 다시 보내지 않습니다.
  • 서버 관문이 있을 때(contexa.llm.gate.enabled, 기본 켜짐): 429 · 503 · 529처럼 서버가 과부하라고 답하면 기다리지 않고 바로 다시 보내되, 그 서버의 관문이 잠시 닫혀 있어 관문 앞에서 줄을 서서 기다립니다. 관문은 서버마다 동시에 받는 호출 수를 제한합니다(자체 호스팅 2 · 원격 16, AI 모델 연결).
  • 끄기: 메타데이터 disableRetries=true. 다시 보낸 횟수는 providerRetryCount에 남습니다.
  • 거절된 필드: 공급자가 요청에 실린 생각(thinking) · 샘플링 필드 때문에 4xx(408 · 409 · 429 제외)로 거절하면, 그 필드를 빼고 남은 제한 시간 안에 한 번 더 보냅니다. 그 모델의 다음 요청에서도 그 필드를 뺍니다.
  • 보안 판정 엔진은 판정 호출의 실패를 따로 처리합니다(모델의 답이 바뀌는 경우).

공급자별로 맞춰 보내는 옵션

공급자마다 받는 옵션 이름과 규칙이 다릅니다. Contexa는 고른 모델의 공급자를 보고 옵션을 맞춰 보냅니다. 어느 모델이 어느 규칙에 드는지는 공급자별 기능 설정으로 바꿀 수 있습니다.

공급자Contexa가 하는 일
OpenAIgpt-5 · o 계열(기본 목록)은 maxTokens를 max_completion_tokens로 보내고, 기본 샘플링만 받는 모델이면 temperature · topP를 뺍니다. 이 모델들에는 seed와 메타데이터 openAiReasoningEffort · openAiVerbosity도 실립니다. 메타데이터 promptCacheKey가 있으면 프롬프트 캐시 키로 보냅니다.
Anthropic모델의 기본 옵션(프롬프트 캐시 설정 포함)을 복사해 요청 값을 얹습니다. 기본 샘플링만 받는 Claude 모델이면 temperature · topP · topK를 뺍니다.
OllamaOllamaChatOptions에 모델 이름 · temperature · topP · seed · numPredict(= maxTokens)를 넣습니다. 생각 끄기 목록에 든 모델이거나 메타데이터 disableOllamaThinking=true면 생각(thinking)을 끕니다.
그 밖Spring AI 공통 ChatOptions(모델 이름 · temperature · topP · maxTokens)

actualPromptTokens · actualCompletionTokens · actualTotalTokens토큰 수(공급자가 알려 줄 때)
cachedPromptTokens · promptCacheHit프롬프트 캐시에서 읽은 토큰(공급자가 알려 줄 때)
providerCallFailureCategory실패 종류(예: PROVIDER_CALL_TIMEOUT, PROVIDER_CALL_FAILED)
determinismNotApplied요청했지만 옵션에 실리지 않은 temperature · seed

호출마다 INFO 로그 한 줄이 남고, 재시도는 WARN LLM Retry #1 - RequestId: …로 남습니다.

[UnifiedLLMOrchestrator.timing] requestId=3f2a… modelClass=org.springframework.ai.openai.OpenAiChatModel modelSelectionMs=0 chatClientBuildMs=1 promptSpecPrepareMs=2 providerThrottleWaitMs=0 providerCallMs=842 responseMetadataMs=0

앱에 ObservationRegistry 빈이 하나 있으면 오케스트레이터가 만드는 ChatClient가 그것으로 Spring AI의 채팅 클라이언트 · 어드바이저 관찰 기록을 남깁니다.

API 레퍼런스

LLMOperations — ExecutionContext를 받는 메서드
메서드돌려주는 것하는 일
execute(ExecutionContext)Mono<String>답 글. 제한 시간 · 재시도 · 메타데이터 기록 포함
stream(ExecutionContext)Flux<String>답을 조각으로. 도구 실행이 켜져 있으면 도구 스트리밍으로 갑니다
executeEntity(ExecutionContext, Class<T>)Mono<T>답을 그 형식의 객체로. 판정 엔진의 응답 형식(SecurityDecisionResponseLite)은 글로 받아 판정 엔진의 해석기로 읽고, 형식이 어긋나면 한 번 더 묻습니다

ToolCapableLLMClient — LLMClient + 도구 호출
메서드돌려주는 것하는 일
