커스텀 AI 기능 만들기

상품 추천 기능 하나를 처음부터 끝까지 만들며 입력 · 출력 타입, 프롬프트 템플릿, Lab, Strategy, (선택) 검색기, 컨트롤러를 차례로 만듭니다. 결과 객체로 받는 표준 호출과 화면에 실시간으로 보내는 스트리밍 호출이 모두 동작하는 코드입니다.

여기의 Strategy는 앱 기능을 고르는 부품입니다. 보안 판정의 1차 · 2차 분석 전략과는 관계가 없습니다. 판정은 판정 엔진이 따로 만듭니다.

무엇을 만드나

  • POST /api/recommend: 상품 · 분류 · 사용자 취향을 받아 추천 목록, 신뢰도, 이유를 담은 결과 객체(JSON)를 돌려줍니다.
  • POST /api/recommend/stream: 같은 입력으로 모델이 분석하는 글을 문장 단위 SSE 이벤트로 보내고, 마지막에 같은 모양의 JSON 결과를 보냅니다.

예제는 상품 추천이지만 요약 · 분류 · 코드 리뷰 같은 어떤 AI 기능에도 같은 순서가 그대로 적용됩니다.

준비

  • 애플리케이션 클래스에 @EnableAISecurity, 설정에 contexa.datasource.url, Spring AI 채팅 모델 하나가 있어야 합니다. 이유와 없을 때의 모습은 AI 엔진 개요에 있습니다.
  • 모델 연결(공급자 · 키 · 모델 이름)은 AI 모델 연결 설정을 따릅니다. 이 페이지에서는 다루지 않습니다.
  • 5단계(RAG)를 쓰려면 벡터 저장소(VectorStore 빈, 예: PGVector)가 있어야 합니다.

1단계: 입력과 출력 타입

입력: 문맥

DomainContext를 확장해 입력 데이터를 담습니다. 구현할 메서드는 도메인 이름을 돌려주는 getDomainType() 하나입니다.

@Getter
public class ProductContext extends DomainContext {

    private final String productId;
    private final String category;
    private final List<String> userPreferences;

    public ProductContext(String productId, String category, List<String> userPreferences) {
        this.productId = productId;
        this.category = category;
        this.userPreferences = userPreferences;
    }

    @Override
    public String getDomainType() {
        return "PRODUCT_RECOMMENDATION";
    }
}

DomainContext에는 이미 contextId(자동 생성 UUID), createdAt, userId · sessionId · organizationId(setter 있음), metadata 맵이 있습니다. 값을 더 붙이려면 addMetadata(key, value), 타입을 정해 꺼내려면 getMetadata(key, Class)를 씁니다. 사용자 · 세션을 채워 두면 같은 입력을 보낸 다른 사용자끼리 잠금 충돌이 나지 않고(확인하기), 기본 검색기가 그 사용자에게 허락된 문서만 고릅니다.

출력: 응답 타입

AIResponse를 확장해 모델이 채울 결과를 정의합니다. 파이프라인은 이 클래스의 JSON 스키마를 프롬프트에 넣고, 모델 답을 이 클래스로 바꿉니다.

@Getter @Setter
@NoArgsConstructor
public class ProductRecommendationResponse extends AIResponse {

    private List<Recommendation> recommendations;
    private double confidence;
    private String reasoning;

    @Getter @Setter
    @NoArgsConstructor
    public static class Recommendation {
        private String productName;
        private String reason;
        private double score;
    }
}
인자 없는 생성자와 setter가 꼭 있어야 합니다. 모델 답을 이 클래스로 바꿀 때와, 실패해서 대체 응답을 만들 때 둘 다 인자 없는 생성자를 씁니다. 또 AIResponse.withMetadata()와 AIRequest.withParameter()에는 null 값을 넣을 수 없습니다(동시성 맵이라 예외가 납니다).

이름표 두 개

요청은 이름표 두 개를 가집니다. 템플릿 타입(TemplateType)은 어느 프롬프트 템플릿을 쓸지, 진단 타입(DiagnosisType)은 어느 Strategy가 맡을지 정합니다. 둘 다 이름 하나를 감싼 단순한 클래스이고, 이름 글자가 같아야 짝이 맞습니다.

// 프롬프트 템플릿을 고르는 이름: 템플릿의 getSupportedType()과 같은 글자
new TemplateType("PRODUCT_RECOMMENDATION")

// Strategy를 고르는 이름: Strategy의 getSupportedType()과 같은 글자
new DiagnosisType("PRODUCT_RECOMMENDATION")

2단계: 프롬프트 템플릿

프롬프트 템플릿은 모델이 보는 글을 만듭니다. 시스템 프롬프트(역할 · 규칙 · 결과 형식)와 사용자 프롬프트(이번 질문과 데이터)입니다. 템플릿은 Spring 빈이어야 하고, 요청의 템플릿 타입 이름과 같은 템플릿이 없으면 Template matching failed로 실패합니다. 표준과 스트리밍을 모두 쓰면 템플릿이 둘 필요합니다.

표준 템플릿

AbstractStandardPromptTemplate<응답 타입>을 확장합니다. 응답 타입에서 만든 JSON 형식 지시가 시스템 프롬프트 끝의 <output_format> 블록에, 전처리 단계가 만든 시스템 메타데이터가 <context> 블록에 자동으로 붙습니다.

@Component
public class ProductPromptTemplate
        extends AbstractStandardPromptTemplate<ProductRecommendationResponse> {

    public ProductPromptTemplate() {
        super(ProductRecommendationResponse.class);
    }

    @Override
    public TemplateType getSupportedType() {
        return new TemplateType("PRODUCT_RECOMMENDATION");
    }

    @Override
    protected String generateDomainSystemPrompt(
            AIRequest<? extends DomainContext> request, String systemMetadata) {
        return """
            You are a product recommendation assistant.
            Analyze the user's preferences and the product category
            and recommend 3-5 products ranked by relevance.
            Give each recommendation a reason and a score from 0.0 to 1.0.
            """;
    }

    @Override
    public String generateUserPrompt(
            AIRequest<? extends DomainContext> request, String contextInfo) {
        ProductContext ctx = (ProductContext) request.getContext();
        StringBuilder prompt = new StringBuilder();
        prompt.append("[Query]\n");
        prompt.append("Product ID: ").append(ctx.getProductId()).append("\n");
        prompt.append("Category: ").append(ctx.getCategory()).append("\n");
        prompt.append("User preferences: ")
              .append(String.join(", ", ctx.getUserPreferences())).append("\n");

        // Lab이 보탠 값은 템플릿이 직접 읽어야 프롬프트에 들어갑니다(3단계)
        String details = request.getParameter("productDetails", String.class);
        if (details != null) {
            prompt.append("\n[Product details]\n").append(details).append("\n");
        }
        // 검색 단계가 찾은 문서(없으면 빈 문자열)
        if (contextInfo != null && !contextInfo.isEmpty()) {
            prompt.append("\n[Context]\n").append(contextInfo);
        }
        return prompt.toString();
    }
}

형식 지시나 메타데이터를 빼고 싶으면 shouldIncludeFormatInstructions(request) · shouldIncludeSystemMetadata(request)를 false로 재정의합니다. 사용자 프롬프트 끝에 형식 지시를 붙이려면 appendFormatInstructions(prompt)를 씁니다.

스트리밍 템플릿

AbstractStreamingPromptTemplate을 확장하고, 결과 JSON의 예(getJsonSchemaExample())를 줍니다. 응답 타입에서 스키마를 만들고 싶으면 대신 getOutputConverter()가 BeanOutputConverter를 돌려주게 하면 됩니다(그러면 예시는 쓰지 않습니다).

@Component
public class ProductStreamingPromptTemplate extends AbstractStreamingPromptTemplate {

    @Override
    public TemplateType getSupportedType() {
        return new TemplateType("PRODUCT_RECOMMENDATION_STREAMING");
    }

    @Override
    protected String generateDomainSystemPrompt(
            AIRequest<? extends DomainContext> request, String systemMetadata) {
        return """
            You are a product recommendation assistant.
            First explain your analysis of the user's preferences,
            then give structured recommendations.
            """;
    }

    @Override
    protected String getJsonSchemaExample() {
        return """
            {
              "recommendations": [
                { "productName": "Example Product", "reason": "Matches ...", "score": 0.95 }
              ],
              "confidence": 0.88,
              "reasoning": "Based on the user's preferences ..."
            }
            """;
    }

    @Override
    public String generateUserPrompt(
            AIRequest<? extends DomainContext> request, String contextInfo) {
        ProductContext ctx = (ProductContext) request.getContext();
        return "Recommend products for category '" + ctx.getCategory()
                + "' based on preferences: " + String.join(", ", ctx.getUserPreferences())
                + buildUserPromptExecutionInstructions();
    }
}
스트리밍 템플릿이 모델에게 시키는 것. Contexa가 시스템 프롬프트에 규칙을 덧붙입니다: 분석 과정을 한국어로만 차례로 설명하고, 다 끝나면 ===JSON_START===와 ===JSON_END=== 사이에 JSON 하나만 쓰라는 것입니다. buildUserPromptExecutionInstructions()는 같은 지시를 사용자 프롬프트 끝에 한 번 더 붙입니다. 표지 처리는 Contexa가 하며, 브라우저는 표지 없는 문장과 최종 JSON을 받습니다(실제로 오는 이벤트). 시스템 프롬프트를 만드는 generateSystemPrompt()는 재정의할 수 없습니다.

공통 도우미

두 템플릿의 공통 부모가 주는 도우미입니다.

  • extractNaturalQuery(request): 요청의 자연어 질문을 꺼냅니다. setNaturalLanguageQuery()로 넣은 값 → 파라미터 naturalLanguageQuery → 기본 문구 순서입니다.
  • extractContextInfo(request, contextInfo): 파라미터 iamDataContext가 있으면 검색 결과 앞에 붙여 돌려줍니다.
  • isContextType(request, 문맥 클래스): 요청의 문맥이 그 타입인지 봅니다.

3단계: Lab

Lab은 도메인 데이터를 모으고 파이프라인을 부르는 작업 단위입니다. AbstractAILab<Lab 요청, 응답 타입>을 확장한 Spring 빈으로 만듭니다. Strategy가 Lab을 클래스로 찾아 쓰기 때문입니다.

@Component
public class ProductRecommendationLab
        extends AbstractAILab<AIRequest<ProductContext>, ProductRecommendationResponse> {

    private final PipelineOrchestrator orchestrator;

    public ProductRecommendationLab(PipelineOrchestrator orchestrator) {
        super("ProductRecommendation");
        this.orchestrator = orchestrator;
    }

    @Override
    public boolean supportsStreaming() {
        return true;   // 없으면 processStream()이 바로 오류를 냅니다
    }

    @Override
    protected ProductRecommendationResponse doProcess(AIRequest<ProductContext> request) {
        return doProcessAsync(request).block();
    }

    @Override
    protected Mono<ProductRecommendationResponse> doProcessAsync(AIRequest<ProductContext> request) {
        // 표준 6단계
        return orchestrator.execute(request,
                PipelineConfiguration.createPipelineConfig(),
                ProductRecommendationResponse.class);
    }

    @Override
    protected Flux<String> doProcessStream(AIRequest<ProductContext> request) {
        // 스트리밍 4단계
        return orchestrator.executeStream(request,
                PipelineConfiguration.createStreamPipelineConfig());
    }
}

Lab이 받는 요청 형식은 자유입니다. 이 예처럼 AIRequest를 그대로 받으면 컨트롤러가 정한 템플릿 타입 · 파라미터 · 사용자 정보가 바뀌지 않고 파이프라인까지 갑니다(Contexa IAM의 정책 생성도 이 방식입니다). Lab 전용 요청 객체(DTO)를 따로 만들어도 되지만, 그러면 Lab 안에서 AIRequest를 다시 만들고 파라미터도 옮겨 넣어야 합니다.

데이터 보태기

데이터베이스나 외부 API에서 가져온 값을 요청 파라미터로 보탤 수 있습니다. 파라미터는 프롬프트에 저절로 들어가지 않습니다. 2단계 템플릿처럼 request.getParameter(이름, 타입)으로 읽어 넣어야 합니다.

// productCatalog는 앱의 빈입니다(예시). doProcessAsync를 이렇게 바꿉니다.
@Override
protected Mono<ProductRecommendationResponse> doProcessAsync(AIRequest<ProductContext> request) {
    String details = productCatalog.describe(request.getContext().getProductId());
    if (details != null) {                       // null은 넣을 수 없습니다
        request.withParameter("productDetails", details);
    }
    return orchestrator.execute(request,
            PipelineConfiguration.createPipelineConfig(),
            ProductRecommendationResponse.class);
}

Lab이 불리는 순서

진입 메서드순서
process() · processAsync()validateRequest()(기본: null 거부) → preProcess() → doProcess() · doProcessAsync()(기본: doProcess()를 감쌈) → postProcess(). 오류는 LabProcessingException으로 감싸집니다.
processStream()supportsStreaming()이 false면 즉시 오류 → validateRequest() → preProcess() → doProcessStream(). postProcess()는 불리지 않습니다.

4단계: Strategy

Strategy는 진단 타입 이름으로 골라져 입력을 검사하고, Lab을 찾아, Lab 요청으로 바꿔 넘깁니다. AbstractAIStrategy<문맥, 응답 타입>을 확장하고 메서드 일곱 개를 구현합니다: getSupportedType(), getPriority(), getLabType(), validateRequest(), convertLabRequest(), processLabExecution(), processLabExecutionAsync(). 스트리밍을 쓰려면 supportsStreaming()과 processLabExecutionStream()도 재정의합니다.

@Component
public class ProductRecommendationStrategy
        extends AbstractAIStrategy<ProductContext, ProductRecommendationResponse> {

    public ProductRecommendationStrategy(AILabFactory labFactory) {
        super(labFactory);
    }

    @Override
    public DiagnosisType getSupportedType() {
        return new DiagnosisType("PRODUCT_RECOMMENDATION");
    }

    @Override
    public int getPriority() {
        return 100;   // 같은 진단 타입이 둘이면 작은 값이 이깁니다
    }

    @Override
    public boolean supportsStreaming() {
        return true;
    }

    @Override
    protected Class<?> getLabType() {
        return ProductRecommendationLab.class;
    }

    @Override
    protected void validateRequest(AIRequest<ProductContext> request) throws DiagnosisException {
        if (request.getContext().getCategory() == null) {
            throw new DiagnosisException(getSupportedType().name(),
                    "INVALID_REQUEST", "Product category is required");
        }
    }

    @Override
    protected Object convertLabRequest(AIRequest<ProductContext> request) {
        return request;   // AIRequest를 그대로 Lab에 넘깁니다
    }

    @Override
    protected ProductRecommendationResponse processLabExecution(
            Object lab, Object labRequest, AIRequest<ProductContext> request) {
        return ((ProductRecommendationLab) lab).process(request);
    }

    @Override
    protected Mono<ProductRecommendationResponse> processLabExecutionAsync(
            Object lab, Object labRequest, AIRequest<ProductContext> originRequest) {
        return ((ProductRecommendationLab) lab).processAsync(originRequest);
    }

    @Override
    protected Flux<String> processLabExecutionStream(
            Object lab, Object labRequest, AIRequest<ProductContext> request) {
        return ((ProductRecommendationLab) lab).processStream(request);
    }
}

실행 순서와 오류 코드

  1. (스트리밍만) supportsStreaming()이 false면 바로 STREAMING_NOT_SUPPORTED.
  2. validateRequest()로 입력을 검사합니다.
  3. getLabType()의 클래스로 Lab 빈을 찾습니다(AILabFactory).
  4. convertLabRequest()로 Lab 요청을 만듭니다.
  5. 진입 메서드에 맞는 processLabExecution*()을 부릅니다.
오류 코드언제
STRATEGY_NOT_FOUND요청의 진단 타입을 맡은 Strategy 빈이 없음
STREAMING_NOT_SUPPORTED스트리밍을 불렀는데 Strategy의 supportsStreaming()이 false
INVALID_LAB_TYPEgetLabType()이 Lab이 아닌 클래스를 돌려줌
LAB_NOT_FOUND그 클래스의 Lab 빈이 없음
EXECUTION_ERROR · ASYNC_EXECUTION_ERROR · STREAM_EXECUTION_ERROR동기 · 비동기 · 스트리밍 실행 중 다른 예외

Strategy 경로에서 이 오류들은 호출자에게 그대로 가지 않습니다. 표준 호출은 원인과 상관없이 AIOperationException("Pipeline returned unexpected response type")으로, 스트리밍은 AI_OPERATION_ERROR 이벤트로 바뀌고, 원인은 서버 로그에 남습니다(확인하기).

5단계(선택): RAG 붙이기

검색 단계는 문맥 타입에 등록된 검색기를 부르고, 없으면 기본 검색기를 씁니다. 기본 검색기는 요청 파라미터 naturalLanguageQuery로 벡터 저장소를 찾고(contexa.rag.defaults.top-k · similarity-threshold), 사용자 · 조직 · 테넌트 · 목적에 맞는 문서만 남깁니다. 많은 기능은 컨트롤러에서 이 파라미터만 넣어 주면 충분합니다. 파라미터가 없으면 질문 대신 문맥의 toString()(클래스 이름 · ID · 도메인 이름)으로 찾으므로 결과가 쓸모없습니다.

도메인에 맞게 검색을 바꾸려면 ContextRetriever를 확장합니다. 빈으로 만드는 것만으로는 불리지 않습니다. 등록부(ContextRetrieverRegistry)에 문맥 타입과 함께 직접 등록해야 합니다.

@Component
public class ProductContextRetriever extends ContextRetriever {

    private final ContextRetrieverRegistry registry;

    public ProductContextRetriever(VectorStore vectorStore,
                                   ContexaRagProperties ragProperties,
                                   ContextRetrieverRegistry registry) {
        super(vectorStore, ragProperties);
        this.registry = registry;
    }

    // 등록해야 검색 단계가 ProductContext 요청에 이 검색기를 씁니다
    @EventListener
    public void onApplicationEvent(ContextRefreshedEvent event) {
        registry.registerRetriever(ProductContext.class, this);
    }

    @Override
    public ContextRetrievalResult retrieveContext(AIRequest<? extends DomainContext> request) {
        if (!(request.getContext() instanceof ProductContext ctx)) {
            return super.retrieveContext(request);
        }
        String query = ctx.getCategory() + " " + String.join(" ", ctx.getUserPreferences());
        SearchRequest search = SearchRequest.builder()
                .query(query)
                .topK(ragProperties.getDefaults().getTopK())
                .similarityThreshold(ragProperties.getDefaults().getSimilarityThreshold())
                .build();
        List<Document> docs = vectorOperations.searchSimilar(search);
        String contextInfo = docs.stream()
                .map(doc -> "- " + doc.getText())
                .collect(Collectors.joining("\n"));
        return new ContextRetrievalResult(contextInfo, docs,
                Map.of("retrieverType", "product", "documentsFound", docs.size()));
    }
}

돌려준 contextInfo는 프롬프트 단계에서 템플릿의 generateUserPrompt(request, contextInfo)로 그대로 전달됩니다. 문자열 하나만 넘기는 vectorOperations.searchSimilar(query)는 5건 · 임계값 없이 찾으므로, 설정값을 쓰려면 위처럼 SearchRequest를 넘깁니다.

내 검색기는 권한 거르기를 하지 않습니다. 등록한 문맥 타입의 요청은 기본 검색기의 사용자 · 조직 · 테넌트 · 목적 거르기와 프롬프트 주입 검사를 거치지 않습니다. 사용자마다 볼 수 있는 문서가 다르면 검색 조건에 직접 넣으세요. 또 이 검색기는 VectorStore 빈이 없으면 만들어지지 않아 애플리케이션이 시작하지 않습니다. 자세한 검색 규칙은 RAG와 벡터 저장소에 있습니다.

6단계: 컨트롤러로 열기

컨트롤러는 AIRequest를 만들어 StandardStreamingService에 넘깁니다. AI 처리 진입점은 빈이 선언된 타입 그대로 AICoreOperations<문맥>으로 주입받습니다(Contexa IAM도 같습니다).

public record RecommendInput(String productId, String category, List<String> preferences) {
}

@RestController
@RequestMapping("/api/recommend")
@RequiredArgsConstructor
public class ProductRecommendationController {

    private final AICoreOperations<ProductContext> aiProcessor;
    private final StandardStreamingService streamingService;

    @PostMapping
    public Mono<ProductRecommendationResponse> recommend(
            @RequestBody RecommendInput body, Principal principal) {
        AIRequest<ProductContext> request = buildRequest(body, principal, "PRODUCT_RECOMMENDATION");
        return streamingService.process(request, aiProcessor, ProductRecommendationResponse.class);
    }

    @PostMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<String>> recommendStream(
            @RequestBody RecommendInput body, Principal principal) {
        if (body.category() == null) {
            return streamingService.errorStream("VALIDATION_ERROR", "category is required");
        }
        AIRequest<ProductContext> request =
                buildRequest(body, principal, "PRODUCT_RECOMMENDATION_STREAMING");
        return streamingService.stream(request, aiProcessor);
    }

    private AIRequest<ProductContext> buildRequest(
            RecommendInput body, Principal principal, String templateName) {
        ProductContext context = new ProductContext(
                body.productId(), body.category(), body.preferences());
        if (principal != null) {
            context.setUserId(principal.getName());
        }
        AIRequest<ProductContext> request = new AIRequest<>(
                context,
                new TemplateType(templateName),
                new DiagnosisType("PRODUCT_RECOMMENDATION"));
        // 기본 검색기가 찾을 질문
        request.withParameter("naturalLanguageQuery",
                body.category() + " " + String.join(" ", body.preferences()));
        return request;
    }
}
@SpringBootApplication
@EnableAISecurity   // io.contexa.contexacommon.annotation.EnableAISecurity
public class MyAiApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyAiApplication.class, args);
    }
}
  • Strategy 경로(위 예): AICoreOperations가 진단 타입으로 Strategy를 찾고, 같은 요청이 동시에 돌지 않게 잠그며, 시작 감사 로그를 남깁니다.
  • 직접 Lab 경로: Lab 빈을 주입해 processAsync(request) · processStream(request)를 부릅니다. Strategy · 잠금 · 감사를 건너뜁니다. processStream()은 SSE로 묶이지 않은 조각 흐름(Flux<String>)이라, 화면용 SSE가 필요하면 Strategy 경로나 직접 파이프라인 경로를 쓰세요.

모델과 생성 옵션 고르기

모델과 생성 옵션은 요청 파라미터로 정합니다. 주지 않으면 기본 채팅 모델과 그 모델의 기본 옵션을 씁니다.

request.withParameter("preferredModel", "gpt-4o-mini")   // 모델 연결 설정에 있는 모델 이름
       .withParameter("temperature", 0.2)
       .withParameter("maxTokens", 1200);
파라미터뜻
preferredModel쓸 모델 이름(requestedModelId · runtimeModelId도 같은 뜻). 찾지 못하면 경고 로그를 남기고 기본 채팅 모델로 갑니다.
temperature · topP · seed생성 옵션(숫자 또는 숫자 문자열)
maxTokens답의 최대 토큰 수
disableRetriestrue면 일시 오류에도 다시 보내지 않습니다(기본은 백오프로 최대 4번)
  • 이 파라미터들은 표준 호출에만 적용됩니다. 스트리밍은 항상 기본 채팅 모델과 기본 옵션을 씁니다.
  • 모델 이름이 실제 모델이 되는 규칙(같은 이름의 연결, 이름만 바꾼 복사)과 모델을 고르는 순서는 모델 공급자에 있습니다. 연결 설정은 AI 모델 연결 설정을 보세요.
  • 1차 · 2차 분석 모델 설정(contexa.security.tiered.llm.layer1.model 등)은 판정 엔진용이라 이 요청에는 쓰이지 않습니다(요청마다 모델이 정해지는 순서).
  • 결과 해석 · 실패 처리 · 검색에 쓰는 다른 파라미터는 파이프라인의 요청 파라미터에 모아 두었습니다.
