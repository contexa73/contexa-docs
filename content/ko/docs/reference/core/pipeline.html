파이프라인과 RAG

Lab이나 컨트롤러가 부르는 파이프라인이 요청을 어떤 단계로 처리하는지 설명합니다. 구성을 고르고, RAG 검색을 붙이고, 결과를 손보고, 단계를 바꾸고, 실패를 다루는 방법을 알 수 있습니다.

보안 판정과는 다른 쓰임입니다. 판정 엔진도 안쪽에서 같은 오케스트레이터와 단계를 지나가지만, 자기 구성과 규칙으로 판정을 만듭니다. 이 페이지는 앱 기능이 부르는 범용 사용만 다룹니다. 판정은 판정 엔진을 보세요.

파이프라인이 하는 일

파이프라인 오케스트레이터(PipelineOrchestrator)는 요청과 구성(PipelineConfiguration)을 받아, 그 구성을 처리할 실행기를 고르고 단계를 차례로 실행합니다. 실행기는 둘입니다: 결과 객체를 돌려주는 표준 실행기(UniversalPipelineExecutor)와 글 조각을 흘려보내는 스트리밍 실행기(StreamingUniversalPipelineExecutor).

보통은 Lab 안에서 부릅니다(Lab 만들기). Strategy · Lab 없이 프롬프트 하나로 끝나는 기능이면 컨트롤러가 바로 부를 수도 있습니다. 이때는 문맥 · 응답 타입 · 템플릿만 있으면 됩니다.

// 직접 파이프라인: 기본 표준 구성(6단계)으로 실행
Mono<SummaryResponse> result = pipelineOrchestrator.execute(request, SummaryResponse.class);

// 화면용 SSE가 필요하면 StandardStreamingService에 오케스트레이터를 넘깁니다(기본 스트리밍 구성)
Flux<ServerSentEvent<String>> events = streamingService.stream(request, pipelineOrchestrator);

팩토리 메서드와 아래 빌더 코드는 같은 구성을 만듭니다.

// 표준: 1~6단계
PipelineConfiguration standard = PipelineConfiguration.builder()
    .addStep(PipelineConfiguration.PipelineStep.CONTEXT_RETRIEVAL)
    .addStep(PipelineConfiguration.PipelineStep.PREPROCESSING)
    .addStep(PipelineConfiguration.PipelineStep.PROMPT_GENERATION)
    .addStep(PipelineConfiguration.PipelineStep.LLM_EXECUTION)
    .addStep(PipelineConfiguration.PipelineStep.RESPONSE_PARSING)
    .addStep(PipelineConfiguration.PipelineStep.POSTPROCESSING)
    .build();

// 스트리밍: 1~4단계
PipelineConfiguration streaming = PipelineConfiguration.builder()
    .addStep(PipelineConfiguration.PipelineStep.CONTEXT_RETRIEVAL)
    .addStep(PipelineConfiguration.PipelineStep.PREPROCESSING)
    .addStep(PipelineConfiguration.PipelineStep.PROMPT_GENERATION)
    .addStep(PipelineConfiguration.PipelineStep.LLM_EXECUTION)
    .enableStreaming(true)
    .build();
  • 구성의 단계 목록은 켜고 끄는 목록입니다. 실행 순서는 넣은 순서가 아니라 단계마다 정해진 번호(1~6)입니다.
  • 검색 · 전처리를 빼면 그 결과가 빈 글로 대신 들어가 문제없이 돕니다.
  • 표준에서 응답 해석이나 후처리를 빼면 결과가 응답 타입이 되지 않아 실패로 처리되고 실패 정책대로 대체 응답이 나갑니다.
  • 스트리밍에서 모델 호출을 빼면 글이 하나도 나오지 않고 끝납니다.
  • timeoutSeconds(…)와 addParameter(…)는 효과가 없습니다. 값을 담기만 하고 읽는 코드가 없습니다. 단계가 읽는 값은 구성의 파라미터가 아니라 요청 파라미터(AIRequest.withParameter)입니다(요청 파라미터).

단계별 동작

1. 검색(CONTEXT_RETRIEVAL)

검색기 등록부(ContextRetrieverRegistry)가 요청 문맥의 클래스(또는 그 부모 클래스)에 등록된 검색기를 찾고, 없으면 기본 검색기를 씁니다. 검색기는 질문으로 벡터 저장소를 찾아 문서들을 한 줄씩 이어 붙인 글(contextInfo)과 문서 목록 · 메타데이터를 돌려줍니다. 찾은 문서가 없으면 빈 글로 다음 단계가 그대로 돕니다. 걸린 시간은 메타데이터 contextRetrievalMs에 남습니다. 검색기 쪽 내용은 아래 RAG 붙이기에 있습니다.

2. 전처리(PREPROCESSING)

시스템 메타데이터 글을 하나 만들어 남깁니다. 기본 구현은 빈 글을 남기므로 아무 일도 하지 않습니다(걸린 시간만 preprocessingMs에 남음). 이 글은 템플릿의 generateDomainSystemPrompt(request, systemMetadata)로 전달되고, 표준 템플릿은 비어 있지 않으면 시스템 프롬프트에 <context> 블록으로 붙입니다. 값을 넣고 싶으면 전처리 단계를 바꿉니다.

3. 프롬프트 만들기(PROMPT_GENERATION)

  1. 요청의 템플릿 타입 이름으로 템플릿 빈을 찾습니다. 없으면 Template matching failed로 실패합니다.
  2. 템플릿의 generateSystemPrompt(request, systemMetadata)와 generateUserPrompt(request, contextInfo)를 부릅니다. 표준 템플릿은 JSON 형식 지시를, 스트리밍 템플릿은 스트리밍 규칙과 JSON 예를 시스템 프롬프트에 붙입니다.
  3. 프롬프트 정리기(LLMViewComposer, 기본 SafePromptNormalizationLLMViewComposer)가 줄바꿈을 정리하고, 글자까지 똑같은 절이 되풀이되면 하나만 남깁니다. 자르거나 요약하지 않습니다.
  4. 시스템 메시지와 사용자 메시지로 된 Spring AI Prompt를 남깁니다. 템플릿이 응답 타입을 알려 주면(표준 템플릿) 그 타입도 다음 단계에 넘깁니다.

4. 모델 호출(LLM_EXECUTION)

  • 보내는 곳: UnifiedLLMOrchestrator가 Spring AI 채팅 모델로 보내고, 등록된 어드바이저(BaseAdvisor 빈)를 적용합니다(LLM 오케스트레이터 · 어드바이저).
  • 모델: 요청 파라미터 preferredModel이 있으면 그 모델, 없거나 찾지 못하면 기본 채팅 모델입니다. 범용 요청에는 분석 계층이 없어 1차 · 2차 분석 모델 설정을 쓰지 않습니다. 이름이 실제 모델이 되는 규칙은 모델 공급자에 있습니다.
  • 답 받는 방식: 표준 실행은 응답 타입을 알므로 구조화 출력(모델에 스키마를 주고 객체로 받기)을 먼저 하고, 실패하면 원문 글로 다시 받습니다(요청 파라미터 structuredOutputPolicy=RAW_FORBIDDEN이면 다시 받지 않고 실패).
  • 시간 제한과 재시도: 호출 한 번은 contexa.security.plane.llm-timeout.provider-call-timeout-ms(기본 60000ms) 안에 끝나야 합니다. 일시 오류(408 · 409 · 429, 5xx, 연결 끊김 등)는 백오프로 최대 4번(2초부터, 간격 최대 12초) 다시 보냅니다(재시도).
  • 스트리밍: 스트리밍 단계(StreamingLLMExecutionStep)가 모델 글을 조각마다 흘려보냅니다. 요청 파라미터(모델 · 온도 등)를 쓰지 않고, 다시 보내지 않으며, 호출 자체의 시간 제한도 없습니다(스트리밍 시간 제한). 어드바이저는 붙지만, 어드바이저가 모델 호출 전에 차단 오류를 내도 막지 못하고 그 어드바이저만 건너뜁니다(어드바이저 오류 처리).

5. 응답 해석(RESPONSE_PARSING)

  • 4단계가 구조화 출력으로 이미 객체를 받았으면 그대로 넘깁니다.
  • 글로 받았으면 JSON을 꺼냅니다: ```json 코드 블록과 앞뒤 글을 걷어 내고, 닫는 괄호 앞의 남는 쉼표를 지우고, 잘린 JSON은 마지막 온전한 항목까지 살립니다.
  • 꺼낸 JSON을 목표 타입으로 바꿉니다. 목표 타입은 템플릿의 응답 타입 → 실행 때 넘긴 응답 타입 → 요청 파라미터 responseType → outputConverter → Map 순서로 정해집니다.
  • 목표 타입으로 바꾸지 못하면 Map으로 남기고(후처리의 응답 처리기가 바꿀 기회), Map도 안 되면 JSON 글을 그대로 남깁니다. 요청 파라미터 structuredOutputPolicy=RAW_FORBIDDEN이면 이런 대체 없이 실패합니다.

6. 후처리(POSTPROCESSING)

  • 해석 결과가 이미 응답 타입이면 그대로 씁니다.
  • 아니면 응답 처리기를 결과 손보기의 규칙대로 부릅니다.
  • 해석 결과가 비어 있으면 FALLBACK 표시만 든 응답을 만듭니다(응답 타입이 아니므로 결국 실패로 처리됨).
  • 결과가 AIResponse면 실행 기록을 메타데이터로 붙입니다: 실제로 쓴 모델 selectedModelId, 기본 모델로 대신했는지 modelSelectionFallbackUsed, 호출 시간 llmExecutionLatencyMs, 재시도 수 providerRetryCount, 템플릿 · 프롬프트 정보 등.
  • 마지막으로 실행기는 이 결과가 요청한 응답 타입일 때만 돌려주고, 아니면 실패로 처리합니다.

RAG 붙이기

RAG(검색 증강 생성)는 관련 문서를 찾아 프롬프트에 넣어 답을 낫게 하는 방법입니다. 검색 단계가 이 일을 하며, 따로 켤 필요가 없습니다.

  • 기본 검색기(AuthorizedContextRetriever)는 요청 파라미터 naturalLanguageQuery로 contexa.rag.defaults.top-k개를 similarity-threshold 이상으로 찾고, 요청한 사용자 · 조직 · 테넌트 · 검색 목적에 맞는 문서만 남기며, 프롬프트 주입이 의심되는 문서를 걸러 냅니다. 남은 문서는 줄마다 [auth=…] 꼬리표가 붙습니다.
  • 벡터 저장소가 없으면 기본 검색기가 늘 빈 결과를 돌려주고 나머지 단계는 그대로 돕니다.
  • Spring AI RAG 어드바이저(RetrievalAugmentationAdvisor) 빈은 모델 호출에 자동으로 붙지 않습니다. 모델 호출에 붙는 어드바이저는 BaseAdvisor 빈뿐이고, 범용 파이프라인의 RAG는 이 검색 단계가 합니다.
  • 내 검색기는 ContextRetriever를 확장한 빈을 만들고, 등록부의 registerRetriever(문맥 클래스, 검색기)로 직접 등록해야 불립니다. 등록한 문맥 타입은 기본 검색기의 권한 거르기를 거치지 않습니다. 전체 예는 커스텀 AI 기능 만들기 5단계에 있습니다.

검색하려면 먼저 문서가 벡터 저장소에 있어야 합니다. Spring AI VectorStore로 넣습니다.

Document doc = new Document(
        "Product A is a lightweight laptop ideal for travel",
        Map.of("category", "electronics", "productId", "PROD-001"));
vectorStore.add(List.of(doc));

메타데이터에 허용 목적이 적히지 않은 문서는 어느 목적의 검색에도 나옵니다. 사용자 · 조직 범위, 문서 종류, 보관 같은 자세한 규칙은 RAG와 벡터 저장소에 있습니다.

결과 손보기: 응답 처리기

응답 처리기(DomainResponseProcessor)는 후처리 단계에서 해석 결과를 응답 타입으로 바꾸는 마지막 기회입니다. 빈으로 만들면 자동으로 모이며, 이렇게 불립니다.

  • 해석 결과가 이미 응답 타입이면 불리지 않습니다. 구조화 출력이나 응답 해석이 성공하면 처리기를 거치지 않습니다.
  • 처리기들을 getOrder() 오름차순(기본 0)으로 보고, supports(템플릿 키) 또는 supportsType(결과 클래스)가 true인 첫 처리기 하나의 wrapResponse()만 부릅니다. 템플릿 키는 요청의 템플릿 타입 이름입니다.
  • 처리기가 예외를 던지면 로그만 남기고 다음 처리기를 봅니다. 요청 파라미터 strictResponsePostprocessing=true면 그 자리에서 실패하고, 맞는 처리기가 없거나 결과가 응답 타입이 아닐 때도 실패합니다.
@Component
@RequiredArgsConstructor
public class ProductResponseProcessor implements DomainResponseProcessor {

    private final ObjectMapper objectMapper;   // Spring Boot가 만든 것

    @Override
    public boolean supports(String templateKey) {
        return "PRODUCT_RECOMMENDATION".equals(templateKey);
    }

    @Override
    public boolean supportsType(Class<?> responseType) {
        return false;   // 템플릿 키로만 고릅니다
    }

    @Override
    public Object wrapResponse(Object parsedData, PipelineExecutionContext context) {
        // 해석 결과가 Map으로 남았을 때 응답 타입으로 바꿉니다
        if (!(parsedData instanceof Map)) {
            return parsedData;
        }
        ProductRecommendationResponse response =
                objectMapper.convertValue(parsedData, ProductRecommendationResponse.class);
        response.withMetadata("pipelineExecutionMs", context.getExecutionTime());
        return response;
    }
}

supportsType()을 넓게 열면(예: 모든 Map) 다른 기능의 결과까지 이 처리기가 가져가므로, 템플릿 키로 좁히는 편이 안전합니다. 파이프라인 문맥의 getMetadata(이름, 타입)으로 selectedModelId 같은 실행 기록을 읽을 수 있습니다.

단계 바꾸기와 실행기 더하기

PipelineStep을 구현한 빈을 새로 만들어도 파이프라인에 끼워지지 않습니다. 실행기는 생성될 때 받은 내장 단계(표준 6개, 스트리밍 4개)만 돌립니다. 대신 아래 방법으로 바꿉니다.

바꾸고 싶은 것방법
시스템 메타데이터 넣기PreprocessingStep을 상속한 빈을 만들고 buildSystemMetadata(request)를 재정의합니다(아래 예). 내장 전처리 빈 대신 쓰입니다.
프롬프트 정리 방식LLMViewComposer 빈을 직접 둡니다.
검색 · 프롬프트 · 응답 해석 · 후처리 단계 전체ContextRetrievalStep · PromptGenerationStep · ResponseParsingStep · PostprocessingStep 빈을 직접 두면 내장 빈 대신 쓰입니다. 단, 응답 해석 · 후처리에는 판정용 처리도 들어 있으므로 상속해서 일부만 바꾸세요.
실행 방식 자체PipelineExecutor 빈을 더합니다. 오케스트레이터는 getPriority()가 작은 실행기부터 보며 supportsConfiguration(구성)이 true이고 스트리밍 여부가 맞는 첫 실행기를 씁니다.
 
@Component
public class CatalogPreprocessingStep extends PreprocessingStep {

    @Override
    protected <T extends DomainContext> String buildSystemMetadata(AIRequest<T> request) {
        return "catalogVersion=2026-11, locale=ko-KR";
    }
}
이 빈들은 애플리케이션 전체에서 하나입니다. 판정 엔진의 요청도 같은 오케스트레이터와 단계를 지나가므로, 바꾼 단계와 더한 실행기는 판정 요청에서도 불립니다. 실행기는 supportsConfiguration()으로 맡을 구성을 좁히세요. 판정 프롬프트는 전처리의 시스템 메타데이터를 넣지 않습니다.

실패와 확인

표준 실행(execute)이 실패했을 때의 모습은 요청 파라미터 pipelineFailurePolicy가 정합니다(대소문자 무관, 모르는 값은 기본값).

pipelineFailurePolicy실패하면
SYNTHETIC_FALLBACK_RESPONSE(기본)오류 대신 응답 타입의 빈 객체를 돌려줍니다. errorMessage는 Pipeline execution failed: 원인, 메타데이터에 errorType(예외 클래스 이름)과 timestamp. 응답 타입에 인자 없는 생성자(또는 (String, ExecutionStatus) 생성자)가 없으면 이것마저 실패합니다.
PROPAGATE_ERROR오류를 그대로 호출자에게 보냅니다. Strategy 경로에서는 AIOperationException("Pipeline returned unexpected response type")으로 바뀌어 도착합니다.
  • 스트리밍 실행(executeStream)이 실패하면 오류 대신 ERROR: 원인 글 조각 하나를 내고 끝납니다. SSE에서 어떻게 보이는지는 스트리밍 문제 해결에 있습니다.
  • 단계 로그: [PIPELINE] STEP 3 completed: PROMPT_GENERATION (4ms) - Request: …, 실패하면 STEP 3 failed: …(스트리밍은 [STREAMING-PIPELINE]).
  • 단계 시간: 파이프라인 문맥 메타데이터 pipelineStep.<단계 이름>.ms(응답 처리기에서 읽을 수 있음).
  • 결과의 메타데이터: selectedModelId · modelSelectionFallbackUsed · llmExecutionLatencyMs · providerRetryCount 등(후처리).

요청 파라미터

파이프라인 단계가 읽는 요청 파라미터입니다. AIRequest.withParameter(이름, 값)으로 넣습니다(null 값 불가).

파라미터읽는 곳뜻
naturalLanguageQuery검색(기본 검색기), 템플릿 도우미검색 질문. 없으면 문맥의 toString()으로 찾습니다
retrievalPurpose검색(기본 검색기)검색 목적(기본 general_context). 허용 목적이 적힌 문서는 이 목적과 같을 때만 나옵니다
allowedDocumentTypes검색(기본 검색기)남길 문서 종류 목록. 없으면 모든 종류
userId · organizationId · tenantId검색(기본 검색기)권한 거르기 기준. 없으면 문맥의 값
iamDataContext템플릿 도우미 extractContextInfo()검색 결과 앞에 붙일 글
preferredModel(또는 requestedModelId · runtimeModelId)모델 호출(표준)쓸 모델 이름
temperature · topP · seed · maxTokens모델 호출(표준)생성 옵션
disableRetries모델 호출(표준)true면 일시 오류에도 다시 보내지 않음
structuredOutputMode모델 호출(표준)구조화 출력 방식(NATIVE_STRUCTURED · VALIDATED_CONVERTER · RAW_FORBIDDEN · LEGACY_RAW). 없으면 모델 · 공급자에 맞춰 자동
structuredOutputPolicy모델 호출 · 응답 해석ALLOW_RAW_FALLBACK(기본) 또는 RAW_FORBIDDEN(글로 대신 받기 · Map 대체 없이 실패)
responseType · outputConverter응답 해석목표 타입(템플릿 · 실행의 응답 타입이 없을 때)
strictResponsePostprocessing후처리true면 응답 처리기가 응답 타입을 만들지 못할 때 바로 실패
pipelineFailurePolicy오케스트레이터(표준)실패 정책(실패와 확인)

설정

설정기본값뜻언제 바꾸나
contexa.std.enabledtrue파이프라인 부품(오케스트레이터 · 실행기 · 단계 · Strategy 등록부) 전체AI 엔진 부품이 필요 없을 때만 끕니다(판정 엔진도 이 부품을 씁니다)

모델 연결(공급자 · 키 · 모델 이름)은 AI 모델 연결 설정, 스트리밍 설정은 스트리밍에 있습니다.

SOAR 단계(OSS에는 구현 없음)

구성의 단계 목록에는 SOAR_TOOL_EXECUTION도 있지만 단계를 하나 더 끼우는 것이 아닙니다. 요청 문맥이 SoarContext이고 pipelineSoarToolExecutionStep이라는 이름의 빈이 있을 때, 모델 호출 단계를 그 빈으로 바꿔 돌리는 자리입니다. OSS 모듈에는 이 빈이 없으므로 앱 기능에는 쓰지 않습니다. SoarContext 요청은 스트리밍 실행기에서도 스트리밍 없이 처리됩니다. SOAR 확장은 SOAR를 보세요.
