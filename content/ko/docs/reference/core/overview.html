AI 엔진: 내 기능에서 LLM 부르기

Contexa의 범용 AI 엔진으로 앱 기능에서 AI 모델(LLM)을 불러, 타입이 정해진 결과 객체를 받거나 화면에 글을 실시간으로 흘려보낼 수 있습니다. 이 페이지에서 무엇을 만들고, 어떤 길로 부르고, 켜려면 무엇이 필요하고, 어디서 조정하는지 한눈에 봅니다.

보안 판정 엔진과는 다릅니다. 이 묶음(AI 엔진)은 앱이 직접 부르는 범용 AI 파이프라인입니다. 요청을 보고 허용 · 추가 인증 · 차단을 정하는 보안 판정(1차 · 2차 분석)은 판정 엔진이 따로 하며, 앱이 이 페이지의 API로 부르지 않습니다.

이 엔진으로 할 수 있는 일

내 프롬프트와 내 데이터로 AI 모델에 묻고, 답을 두 가지 방식 가운데 하나로 받습니다. 보안과 상관없는 기능(상품 추천, 문서 요약, 분류 등)에도 그대로 쓸 수 있습니다.

Contexa도 이 엔진을 씁니다. IAM 관리 화면의 정책 생성, 리소스 이름 추천, 조건 템플릿 생성이 이 엔진 위에서 돕니다(Contexa가 이 엔진을 쓰는 곳).

켜기 전에 필요한 것

AI 엔진은 따로 켜는 스위치가 없고, Contexa 플랫폼이 켜질 때 함께 만들어집니다. 아래가 모두 갖춰져야 엔진의 빈(AICoreOperations · PipelineOrchestrator · StandardStreamingService)이 생깁니다.

필요한 것왜없으면
@EnableAISecurityContexa 플랫폼을 켜는 표지입니다. 붙이면 Contexa 보안 기능(보안 모드 기본 SANDBOX)도 함께 켜집니다. spring-boot-starter-security가 필요합니다.Contexa 자동 설정이 모두 빠져 엔진 빈이 하나도 없습니다.
contexa.datasource.urlContexa 전용 DB 주소입니다.애플리케이션이 시작하지 않습니다.
Spring AI 채팅 모델(ChatModel 빈)LLM 호출을 맡는 UnifiedLLMOrchestrator가 이 모델로 만들어집니다. 연결 방법은 AI 모델 연결 설정에 있습니다.파이프라인 실행기가 만들어지지 않아 엔진을 부를 수 없습니다.
영역 스위치 세 개(모두 기본 켜짐)contexa.std.enabled(파이프라인 부품), contexa.rag.enabled(벡터 저장소 서비스 · RAG 부품과 AICoreOperations), contexa.streaming.enabled(StandardStreamingService)끈 영역의 빈이 없습니다. 특히 contexa.rag.enabled=false면 AICoreOperations도 사라집니다.
(선택) 벡터 저장소(VectorStore)RAG 검색(관련 문서를 찾아 프롬프트에 넣기)에 씁니다.기본 검색기가 빈 결과를 돌려주고, 나머지는 그대로 동작합니다.

설치와 처음 켜기는 설치 준비에 있습니다.

부르는 길 세 가지

엔진을 부르는 길은 세 가지입니다. 어느 길이든 마지막에는 같은 파이프라인이 AI 모델을 부릅니다.

길무엇을 부르나내가 만드는 것언제 쓰나
Strategy 경로(권장)AICoreOperations를 직접, 또는 StandardStreamingService에 넘겨서문맥 · 응답 타입 · 템플릿 · Lab · Strategy입력 검사, 같은 요청 동시 실행 막기, 진단 타입별 나누기가 필요할 때
직접 파이프라인PipelineOrchestrator를 직접, 또는 StandardStreamingService에 넘겨서문맥 · 응답 타입 · 템플릿프롬프트 하나로 끝나는 단순한 호출. 잠금 · 감사 로그가 없습니다
직접 LabLab 빈의 processAsync() · processStream()문맥 · 응답 타입 · 템플릿 · LabStrategy 없이 Lab만 쓸 때. 진단 타입 나누기 · 잠금 · 감사 로그를 건너뜁니다. 스트림은 SSE로 묶이지 않은 조각 흐름입니다

내가 만드는 것

모두 Spring 빈이나 일반 클래스로 만들고, Contexa가 이름표로 찾아 씁니다. 처음부터 끝까지 만드는 예는 커스텀 AI 기능 만들기에 있습니다.

부품하는 일필요한 때
문맥(DomainContext 하위 클래스)모델에 넘길 입력 데이터입니다. getDomainType() 하나만 구현합니다.항상 (1단계)
응답 타입(AIResponse 하위 클래스)모델 답을 담을 결과 클래스입니다.항상 (1단계)
프롬프트 템플릿(PromptTemplate 빈)시스템 프롬프트와 사용자 프롬프트를 만듭니다. 템플릿 타입(TemplateType) 이름으로 골라집니다.항상. 표준 · 스트리밍을 모두 쓰면 둘 (2단계)
Lab(AbstractAILab 빈)도메인 데이터를 모으고 파이프라인을 부르는 작업 단위입니다.Strategy · 직접 Lab 경로 (3단계)
Strategy(AbstractAIStrategy 빈)진단 타입(DiagnosisType) 이름으로 골라져 입력을 검사하고 Lab에 넘깁니다.Strategy 경로 (4단계)
검색기(ContextRetriever 하위 클래스)내 도메인에 맞게 관련 문서를 찾습니다. 빈으로 만든 뒤 등록부에 직접 등록해야 불립니다.선택 (5단계)
응답 처리기(DomainResponseProcessor 빈)해석 결과가 응답 타입이 아닐 때 바꿔 줍니다.선택 (결과 손보기)

결과 받는 방식 고르기

컨트롤러에서 StandardStreamingService의 메서드 하나로 방식을 고릅니다. request는 AIRequest, aiProcessor는 주입받은 AICoreOperations입니다.

// 표준: 결과 객체 하나를 받습니다
Mono<ProductRecommendationResponse> result =
        streamingService.process(request, aiProcessor, ProductRecommendationResponse.class);

// 스트리밍: 화면에 흘려보낼 SSE 이벤트를 받습니다
Flux<ServerSentEvent<String>> events = streamingService.stream(request, aiProcessor);
표준스트리밍
받는 것응답 타입 객체 하나(Spring이 JSON으로 바꿔 보냄)문장 이벤트 여러 개 → 결과 생성 알림 → 최종 JSON → [DONE]
파이프라인 단계6단계앞의 4단계(모델 호출까지)
모델 · 온도 지정요청 파라미터로 할 수 있음할 수 없음(기본 채팅 모델)
시간 제한모델 호출 한 번에 60초, 일시 오류는 백오프로 최대 4번 다시 보냄다음 이벤트가 5분 안에 오지 않으면 끝냄(코드에 고정)
실패하면기본은 errorMessage가 채워진 빈 응답 객체ERROR:로 시작하는 이벤트

스트리밍 이벤트의 실제 모습과 클라이언트 코드는 스트리밍에 있습니다.

조정하는 곳: 설정과 요청 파라미터

AI 엔진의 동작은 대부분 application.yml이 아니라 요청마다 정합니다. AIRequest.withParameter(이름, 값)으로 넣는 값을 파이프라인 단계가 읽습니다.

바꾸고 싶은 것어디서자세히
어느 모델 · 온도 · 최대 토큰으로 부를지요청 파라미터 preferredModel · temperature · topP · seed · maxTokens(표준만). 주지 않으면 기본 채팅 모델모델과 생성 옵션
실패를 오류로 받을지요청 파라미터 pipelineFailurePolicy실패와 확인
검색 문서 수 · 유사도 하한contexa.rag.defaults.top-k(10) · contexa.rag.defaults.similarity-threshold(0.7)파이프라인 설정
모델 호출 한 번의 시간 제한contexa.security.plane.llm-timeout.provider-call-timeout-ms(60000)파이프라인 설정
모델 연결(공급자 OpenAI · Anthropic · Ollama, 키, 모델 이름)spring.ai.*와 Contexa 모델 연결 설정AI 모델 연결 설정 · 모델 공급자
  • 1차 · 2차 분석 모델 설정은 여기에 적용되지 않습니다. contexa.security.tiered.llm.layer1.model · contexa.security.tiered.llm.layer2.model은 판정 엔진이 씁니다. 범용 요청에는 분석 계층이 없어 기본 채팅 모델을 씁니다(모델이 정해지는 순서).
  • 파이프라인 전체 시간 제한 설정은 없습니다. PipelineConfiguration의 timeoutSeconds는 값을 담기만 하고 읽는 코드가 없습니다.
  • 스트리밍 시간 제한은 코드에 정해진 5분이라 설정으로 바꿀 수 없습니다.

잘 되는지 확인하기

  • 단계 로그: 표준 실행은 단계마다 [PIPELINE] STEP 4 completed: LLM_EXECUTION (1830ms) - Request: … 같은 로그를 남깁니다(스트리밍은 [STREAMING-PIPELINE]).
  • 실제로 쓴 모델: 표준 결과 객체의 메타데이터 selectedModelId에 들어 있습니다. 요청한 모델을 찾지 못해 기본 모델로 갔으면 modelSelectionFallbackUsed가 true입니다.
  • 실패: 기본은 오류 대신 errorMessage가 Pipeline execution failed: …로 시작하는 응답 객체가 옵니다. 결과를 쓰기 전에 getErrorMessage()를 확인하세요.
  • 잠금 충돌: Strategy 경로에서 똑같은 요청(같은 응답 타입 · 템플릿 · 진단 타입 · 사용자 · 세션 · 조직 · 파라미터)이 이미 돌고 있으면 StrategicOperationConflictException(AIOperationException의 하위, 메시지 Strategic operation conflict)으로 거절됩니다.
  • 감사 로그: Strategy 경로는 시작할 때 로거 IAM_AUDIT에 AUDIT_START 한 줄을 남깁니다. 완료 · 실패는 따로 남기지 않습니다.

기본 검색기는 권한을 거릅니다

검색기를 따로 등록하지 않으면 기본 검색기(AuthorizedContextRetriever)가 쓰입니다. 이 검색기는 벡터 저장소에서 찾은 문서 가운데 요청한 사용자 · 조직 · 테넌트 · 검색 목적에 맞는 것만 남기고, 프롬프트 주입이 의심되는 문서를 걸러 낸 뒤, 줄마다 [auth=…] 꼬리표를 붙여 프롬프트에 넣습니다. 내 검색기를 등록하면 그 문맥 타입에서는 이 거르기를 거치지 않습니다. 자세한 규칙은 RAG와 벡터 저장소에 있습니다.
