Examples

How to get and run the 7 examples in the GitHub repository contexa73/contexa-examples, what each one shows, and the settings to change before running them with today's Contexa.

At a glance

Each example is a Spring Boot application that runs on its own. If you are new, this order is the easiest.

The README still names examples that are no longer in the repository (shadow-enforce, identity-rest, identity-ott, identity-asep, iam-*, ai-* and others). The examples that exist are the 7 above, and the build (settings.gradle) includes 6 of them, all but identity-mfa-multi. The repository last changed on 2026-06-15, so Contexa behavior changed since then is not reflected in the examples (Change before running).

Getting and running them

git clone https://github.com/contexa73/contexa-examples.git
cd contexa-examples
./gradlew :contexa-example-quickstart:bootRun
  • Java 21. The example build uses a Java 21 toolchain. Spring Boot is 3.5.11.
  • The Contexa dependency. The root build.gradle adds ai.ctxa:spring-boot-starter-contexa:0.1.0-SNAPSHOT to every example and fetches it from Maven Local and the Central Portal snapshot repository.
  • PostgreSQL with the vector extension. The examples' default dedicated Contexa database is jdbc:postgresql://localhost:5432/contexa (contexa_oss for protectable) with the user contexa. To use another database, set the environment variables CONTEXA_DB_URL, CONTEXA_DB_USERNAME and CONTEXA_DB_PASSWORD. The examples that read them are quickstart, protectable, identity-mfa-multi, identity-oauth2 and legacy-system.
  • AI models. The example settings use the Ollama models qwen2.5:7b (chat) and mxbai-embed-large (embedding); get them with ollama pull. For today's model settings follow Connecting AI Models.

Change before running

Contexa behavior changed in three places since the examples were last changed. Each example lists the ones that apply to it.

1. Let Contexa own sign-in (ownership)

The quickstart, protectable and identity-* examples build Contexa's sign-in flows with the authentication DSL (PlatformConfig). But the default of @EnableAISecurity is the application owns sign-in (HOST_OWNED), and then Contexa does not build the sign-in chains of PlatformConfig. Run as they are, the examples show no login page, MFA or OAuth2, so add this to the example's application.yml:

contexa:
  bridge:
    ownership: CONTEXA_OWNED

Changing the main class to @EnableAISecurity(mode = SecurityMode.FULL) does the same. The two ownership modes are compared in Add to an Existing Spring Security Application.

2. Add the dedicated Contexa database

The settings of identity-dsl and identity-mfa have no dedicated Contexa database (contexa.datasource.*). With an empty contexa.datasource.url start-up stops with IllegalStateException, so add it. To use the same database as the application, also set isolation.contexa-owned-application: true (Database settings).

contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}

3. Rename old settings

  • spring.auth.* and security.zerotrust.* are old prefixes. They are moved to contexa.auth.* and contexa.security.zerotrust.* automatically today, but the start-up log shows an ERROR and the aliases go away in 0.3.0 (Old prefixes).
  • contexa.hcad.* (a removed feature), spring.zero-trust.* and spring.ai.chat.model.priority are read by nothing and have no effect. You can delete them.

Each example

quickstart (8081): the smallest setup

  • What it shows: @EnableAISecurity on the main class and a form login built with the authentication DSL (/login → /test/quickstart). Only /api/hello carries @Protectable, so only it is decided on.
  • Try: sign in, then call /api/hello from the test page /test/quickstart.
  • Before running: add ownership. The settings use distributed mode (contexa.infrastructure.mode: DISTRIBUTED), which needs Redis and Kafka; without them change it to standalone (Standalone and distributed). The enforcement mode is SHADOW (Enforcement modes).

protectable (8082): four ways to use @Protectable

APIProtectionBehavior
GET /api/orders@ProtectableAnswers at once and decides in the background (asynchronous)
GET /api/orders/customer/{customerId}@Protectable(ownerField = "customerId")When a policy condition uses hasPermission(...), compares the target's customerId with the signed-in user's name. Without such a policy it has no effect
POST /api/orders@Protectable(sync = true)Waits for the decision, then runs
DELETE /api/orders/{orderId}?customerId=@Protectable(ownerField = "customerId", sync = true)Waits for the decision and compares the owner as above
  • Try: sign in, then call the four APIs from the test page /test/protectable. data.sql inserts one order at start-up.
  • Before running: add ownership. The settings contain contexa.llm.enabled: false, which turns the decision model off; to see AI decisions, delete that line and connect a model.
  • Read with: sync, ownerField, responses

identity-dsl (8083): the authentication DSL

  • What it shows: one PlatformConfig with form login (/login → /) and REST (JSON) login (POST /api/login → /api/profile) together.
  • Before running: add ownership and the dedicated database. The settings use spring.jpa.hibernate.ddl-auto: validate, so the tables must exist first: run initdb/01-ddl.sql and 02-dml.sql (default users, roles and groups) from the same folder. The AI settings only hold placeholders for OpenAI and Anthropic keys; fill them as in Connecting AI Models.
  • Read with: Authentication DSL, Authentication

identity-mfa (8087): MFA with custom pages

  • What it shows: the first factor is form login on a custom login page (/customLogin), the second a one-time token (OTT) or a passkey. mfaPage(...) sets the second-factor page addresses: token request /custom/mfa/ott/request-code-ui, token entry /custom/mfa/challenge/ott, passkey /custom/challenge/passkey. The pages are Thymeleaf templates using contexa-mfa-sdk.js.
  • Before running: add ownership and the dedicated database (the settings only have H2 for the application).
  • Read with: Custom MFA pages, SDK

identity-mfa-multi (8088): two MFA flows

  • What it shows: two named MFA flows. The admin flow uses urlPrefix("/admin") with a passkey (order 60), the user flow urlPrefix("/user") with a one-time token (order 70). Each prefix goes in front of the login page address, so the home page / leads to /admin/mfa/login and /user/mfa/login, and success goes to /admin/dashboard or /user/dashboard.
  • Before running: this folder is not in the root settings.gradle, so ./gradlew :contexa-example-identity-mfa-multi:bootRun does not work. Add include 'contexa-example-identity-mfa-multi' to settings.gradle first, and add ownership. This example's Contexa settings (contexa.datasource.*, contexa.llm.*) already use today's names.
  • Read with: Several MFA flows

identity-oauth2 (8089): OAuth2 stateless authentication

  • What it shows: with .form().oauth2() the user gets a JWT after form login and calls the next APIs with a Bearer token. There is a test page /test/token and the test APIs POST /api/token-test/refresh, GET /api/token-test/validate and GET /api/token-test/userinfo.
  • Before running: Contexa's authorization server is built only when Contexa owns sign-in, so ownership is required. Move the spring.auth.* settings (state type OAUTH2, token transport HEADER, client contexa-example) to contexa.auth.*.
  • Read with: OAuth2 state, Issuing tokens to a signed-in user

legacy-system (9090): adding Contexa to a legacy login

  • What it shows: an application that signs users in with its own filter (LegacyAuthFilter) and no Spring Security, with Contexa added through @EnableAISecurity(mode = SecurityMode.SANDBOX). Sign-in works by form (/legacy/login), an X-Auth-Token header or a remember-me cookie, and a @LegacyRole interceptor checks roles. After a successful sign-in the filter hands the user, roles, department and login method to Contexa with ContexaAuthBridge.handoff(...) and keeps the user object in the session attribute legacyUser.
  • Protected APIs: GET /api/customers (@Protectable, asynchronous) and GET /api/customers/export (@Protectable(sync = true)).
  • Example users: admin/admin123 (ADMIN, MANAGER), kim_manager/manager123, park_dev/dev123, lee_analyst/analyst123.
  • Scenario profiles: 10 application-scenario-*.yml files test start-up with different database setups (dedicated H2, a shared database allowed for a PoC or refused in production, no dedicated database, bridge off, a context path behind a proxy and more, ports 19081 to 19091). The fake-chat profile uses a test model that always answers allow (PERMIT) and an empty vector store.
  • Before running: this application has no Spring Security chain and does not put the signed-in user into the SecurityContext. When the application owns sign-in, Contexa builds no chain, so running it as it is leads to two things:
    • Spring Boot's default security requires sign-in for every request, and the start-up log shows an ERROR.
    • The @Protectable APIs are refused because the SecurityContext holds no authenticated user. A handoff only records evidence for that request and does not fill the SecurityContext.
    Add a chain that keeps the existing access rules and a filter that puts the legacy session's user into the SecurityContext (below, imports left out). The security.zerotrust.* and spring.auth.* settings are old names.
@Bean
SecurityFilterChain legacyChain(HttpSecurity http) throws Exception {
    return http
            .authorizeHttpRequests(auth -> auth.anyRequest().permitAll())
            .addFilterBefore(new LegacySessionAuthenticationFilter(), AnonymousAuthenticationFilter.class)
            .build();
}

// Puts the user the legacy login left in the session into the SecurityContext on every request
class LegacySessionAuthenticationFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        HttpSession session = request.getSession(false);
        if (session != null
                && session.getAttribute(LegacyAuthFilter.SESSION_USER_KEY) instanceof LegacyUserSession user) {
            List<SimpleGrantedAuthority> roles = user.getRoles().stream()
                    .map(role -> new SimpleGrantedAuthority("ROLE_" + role))
                    .toList();
            SecurityContextHolder.getContext().setAuthentication(
                    UsernamePasswordAuthenticationToken.authenticated(user.getUserId(), null, roles));
        }
        chain.doFilter(request, response);
    }
}
