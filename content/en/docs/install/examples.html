contexa-examples

Examples

Seven runnable examples cover the typical situations in which you add CONTEXA to a Spring Boot application. They are in the GitHub examples repository contexa73/contexa-examples, and each is an independent Spring Boot application. Choose the example that fits your situation and run it on your local PC to see how CONTEXA behaves. To run one you need Java 21, a dedicated PostgreSQL database for CONTEXA, and a local AI model server (Ollama).

Choosing an example

CONTEXA analyzes the requests that call a protected method with AI and produces a decision. A decision is one of ALLOW, CHALLENGE (step-up authentication required), ESCALATE (held for review) or BLOCK. Not every request is analyzed: only a request that calls a method marked with @Protectable is. The examples show this setup in different situations.

Each example is a separate Spring Boot application with its own port. If you are new to CONTEXA, read them in this order.

To add CONTEXA to a system that already has sign-in, read quickstart, protectable and legacy-system. To leave sign-in to CONTEXA in a new system, read quickstart and protectable, then the identity-* examples.

The Who owns sign-in column says who builds and manages the login pages, the sessions and the filter chain used for sign-in. CONTEXA makes and applies the decisions in either case. You choose with the mode of @EnableAISecurity on the main class.

  • FULL: CONTEXA builds the sign-in and the filter chain. The six examples in which CONTEXA owns sign-in put @EnableAISecurity(mode = SecurityMode.FULL) on the main class.
  • SANDBOX: the application keeps its own sign-in, and CONTEXA only reads who signed in. legacy-system uses SecurityMode.SANDBOX.

What stays the same and what differs between the two is described in Add to an Existing Spring Security Application.

Download and run the examples

You run the examples on your own machine. Before you start, prepare Java 21, a dedicated PostgreSQL database for CONTEXA, and a local AI model server (Ollama). Then download the repository and run one example.

Prerequisites

  • Java 21. The example build uses a Java 21 toolchain. Spring Boot is 3.5.11, Spring AI 1.1.8. An application that uses CONTEXA needs Java 17 at minimum (Prerequisites).
  • The CONTEXA dependency. The root build.gradle adds ai.ctxa:spring-boot-starter-contexa:0.1.0 to every example. The build looks for it in the local Maven repository first, then in Maven Central. If the build cannot find it, run ./gradlew publishToMavenLocal in the CONTEXA repository to publish it to the local Maven repository.
  • PostgreSQL with the vector extension. The vector extension (pgvector) adds vector search to PostgreSQL. CONTEXA stores users and policies, decision records, audit records and system settings in this database, and it creates the vector store that finds similar past decision records there. Every example keeps CONTEXA's data in a dedicated database. The default address is jdbc:postgresql://localhost:5432/contexa, and the user and password are both contexa. To use another database, set CONTEXA_DB_URL, CONTEXA_DB_USERNAME and CONTEXA_DB_PASSWORD. On the first start CONTEXA creates its tables and default data in that database. If you run several examples, give each its own database.
  • AI models. The examples use two models on a local Ollama (http://localhost:11434, or the address in OLLAMA_BASE_URL). qwen3:8b produces the decisions. mxbai-embed-large turns text into vectors so that past decision records can be found. Download both with ollama pull before you run an example.
  • Values tuned for a local model. A local model answers slower than a hosted one, so the examples raise the time limit of the Layer 2 analysis to 120 seconds (contexa.security.tiered.layer2.timeout-ms, 30 seconds by default). Analysis runs in two stages. The Layer 2 analysis decides again only the requests for which the Layer 1 analysis answered ESCALATE, which here means that it could not decide from the facts alone; this ESCALATE is the first stage's answer, not the final decision. CONTEXA also sends one Ollama server two calls at a time and switches its model only when the running calls are done (How many calls a model server takes).

This SQL creates the user and the database that match the example defaults. It creates the user contexa and the database contexa, and it enables the vector extension.

CREATE USER contexa WITH PASSWORD 'contexa';
CREATE DATABASE contexa OWNER contexa;
\c contexa
CREATE EXTENSION IF NOT EXISTS vector;

Download and run

git clone https://github.com/contexa73/contexa-examples.git
cd contexa-examples
./gradlew :contexa-example-quickstart:bootRun

When the start finishes, quickstart accepts requests on port 8081. On the first start CONTEXA creates its tables and default data in the dedicated database. If the startup log shows an ERROR line that begins with [ContexaCapability], a component that decisions need is missing. Look up the cause in Check that it is on.

Each example

Every example is described in the same order: when you use it, what you add to the application, and what you see when you run it. Sign in with admin / 1111 unless noted.

quickstart (8081): the smallest setup

  • When to use it: You turn CONTEXA on for the first time and want to see one method receive a decision in the smallest possible setup.
  • What you add:
    • @EnableAISecurity on the main class. This annotation turns CONTEXA on.
    • A form login built with the authentication DSL (/login → /test/quickstart). CONTEXA owns sign-in.
    • @Protectable on /api/hello only. Only this API is decided on.
    • The operating mode SHADOW (observation mode). CONTEXA decides and records, and it does not block (Operating modes). Without a mode, CONTEXA applies decisions to requests in enforce mode (ENFORCE).
  • What you do:
    1. Sign in at /login. After sign-in the test page /test/quickstart opens.
    2. On the test page, call /api/hello.
    3. After a short time, open the decision records in the admin console to see the decision (Where to look at the results).
  • What you see:
    • The response of /api/hello comes back normally. The operating mode is SHADOW, so the request is not blocked even when the decision is BLOCK.
    • The decision is made after the response is sent, so the decision record appears later than the response. The decision is kept in the CONTEXA database together with its reason.
    • A call without sign-in is refused even in SHADOW.

protectable (8082): four ways to use @Protectable

  • When to use it: You choose the decision mode for each protected method. The default is asynchronous: the decision is made after the response is sent. For work that cannot be undone, such as a deletion, use the sync mode, which waits for the decision before the method runs. To let only the owner of the data call a method, add the owner check (ownerField) to a method whose policy condition uses hasPermission(...). Without such a policy, ownerField has no effect.
  • What you add: The attributes of @Protectable on each method. The table lists the four APIs of this example and the attribute combination of each.
APIProtectionBehavior
GET /api/orders@ProtectableAnswers at once and decides afterwards (asynchronous)
GET /api/orders/customer/{customerId}@Protectable(ownerField = "customerId")When a policy condition uses hasPermission(...), compares the target's customerId with the signed-in user's name. Without such a policy it has no effect
POST /api/orders@Protectable(sync = true)Waits for the decision, then runs
DELETE /api/orders/{orderId}?customerId=@Protectable(ownerField = "customerId", sync = true)Waits for the decision and compares the owner as above
  • What you do:
    1. Sign in and open the test page /test/protectable.
    2. On the test page, call the four APIs one after another. data.sql inserts sample orders when the application starts, so you do not have to create data.
  • What you see:
    • The asynchronous API (GET /api/orders) answers at once. The two APIs with sync = true answer after the decision is made, so they are slower. If the decision takes longer than 40 seconds by default (contexa.security.zerotrust.agent.flight.wait), enforce mode does not let the call through.
    • When the operating mode is ENFORCE, a decision other than ALLOW stops the method. An API call receives a refusal with a status code: 403 for BLOCK, 401 for CHALLENGE and 423 for ESCALATE.
    • The owner comparison works only when a policy condition uses hasPermission(...). An account with the ROLE_ADMIN authority skips the comparison. To see the comparison take effect, sign in with an account that is not an administrator.
    • CONTEXA owns sign-in in this example, so when the application has no DataSource of its own, the CONTEXA database becomes the application's default database. The application's tables are therefore in the CONTEXA database too.
  • Read with: sync, ownerField, responses

identity-dsl (8083): the authentication DSL

  • When to use it: One application must offer a form login for browsers and a REST (JSON) login for API clients together.
  • What you add: One PlatformConfig that declares two login flows. A flow pairs a login method (form, REST and so on) with how the login is kept afterwards (a session or a token).
    • The REST (JSON) login flow (POST /api/login → /api/profile) takes only /api/** (rawHttp(http -> http.securityMatcher("/api/**"))) and is ordered first (order(50)).
    • The form login flow (/login → /) takes every other request.
    • The split is needed because requests are compared with the flows in ascending order and the first matching flow handles the request. Two flows that both take every request would leave the second one unreachable (Authentication DSL).
  • What you do:
    1. For form login, sign in with the form at /login.
    2. For REST login, send POST /api/login with {"username":"admin","password":"1111"}. Then call GET /api/profile with the same session.
  • What you see: Both login methods work side by side in one application. After form login you go to /, and after REST login you can call /api/profile.
  • Read with: Authentication DSL, Authentication

identity-mfa (8087): MFA with custom pages

  • When to use it: You require a second authentication after the password, and you build the login page and the second-factor pages in your application's own design. A one-time token (OTT) is a one-time code sent to the user by mail, and a passkey is a WebAuthn-based credential.
  • What you add:
    • The first authentication is a form login on a custom login page (/customLogin).
    • The second authentication is a one-time token (OTT) or a passkey.
    • mfaPage(...) sets the second-factor page addresses: token request /custom/mfa/ott/request-code-ui, token entry /custom/mfa/challenge/ott, passkey /custom/challenge/passkey.
    • The pages are Thymeleaf templates using contexa-mfa-sdk.js.
  • What you do:
    1. Sign in at /customLogin. The page posts the password to /mfa/login.
    2. The one-time code page opens next. Enter the code.
  • What you see: Your own login page opens, and the one-time code page follows the password step. The addresses of the second-factor pages are the ones set with mfaPage(...). CONTEXA mails the code. When no mail server (spring.mail.*) is configured, or when a development profile (local, dev, development, test) is active, it also writes the code to the application console in a line that starts with [OTT] Sign-in code for ... (Receiving the one-time code).
  • Read with: Custom MFA pages, SDK

identity-mfa-multi (8088): two MFA flows

  • When to use it: Different groups of users need different MFA. This example requires a passkey or a one-time token from administrators and a one-time token from regular users.
  • What you add: Two named MFA flows. The urlPrefix goes in front of every MFA address of its flow, and the flow takes only requests under that prefix.
    • The admin flow uses urlPrefix("/admin") with a passkey and a one-time token (order 60).
    • The user flow uses urlPrefix("/user") with a one-time token (order 70).
    • A passkey can be registered only after MFA completes. An administrator without a passkey therefore authenticates first with a one-time code received by email.
  • What you do:
    1. Open the home page /. Each prefix goes in front of the login page address, so it leads to /admin/mfa/login and /user/mfa/login.
    2. Sign in at /user/mfa/login as user / 1111.
    3. Enter the code on the one-time code page. You receive the code in the same way as in identity-mfa.
  • What you see: Each flow has its own login page address, and the page after success differs too: /admin/dashboard or /user/dashboard.
  • Read with: Several MFA flows

identity-oauth2 (8089): OAuth2 stateless authentication

  • When to use it: The server keeps no sign-in session, and clients call the API with a token they receive after signing in. Stateless authentication means that the server stores no session and authenticates each request by its token.
  • What you add:
    • .form().oauth2() adds token issuance to the form login. After a successful sign-in the response carries a JWT (JSON Web Token) access token, and the next APIs are called with a Bearer token.
    • The tokens are kept in the browser's localStorage (contexa.auth.token-persistence: localstorage).
    • The token signing key and the client secret use example values (Values for a local run only).
  • What you do:
    1. Sign in at /login. After sign-in you land on the test page /test/token.
    2. The test page (/test/token) reads the stored tokens and calls POST /api/token-test/refresh, GET /api/token-test/validate and GET /api/token-test/userinfo.
  • What you see: The three APIs are called with a token, not with a session. The public key that verifies the token signature is published at /oauth2/jwks, and you can call that address without a token.
  • Security note: A token kept in localStorage can be read through an XSS (cross-site scripting) attack. The SDK for the MFA pages treats localStorage as an opt-in and advises using it together with a CSP (Content Security Policy). The setting in this example is for testing.
  • Read with: OAuth2 state, Issuing tokens to a signed-in user

legacy-system (9090): adding CONTEXA to a legacy login

  • When to use it: An existing application signs users in with its own filter, and you add CONTEXA decisions without changing the login code. The application in this example has its own login and no Spring Security. The application keeps owning sign-in (SANDBOX), and CONTEXA reads the signed-in user and makes the decisions. The legacy login accepts a form (/legacy/login), an X-Auth-Token header or a remember-me cookie, and a @LegacyRole interceptor checks roles.
  • What you add:
    1. Put @EnableAISecurity(mode = SecurityMode.SANDBOX) on the main class.
    2. Add the Spring Security dependency and declare a chain that keeps the existing access rules (LegacySecurityConfig).
    3. Put a filter in that chain that places the legacy session's user into the SecurityContext (LegacySessionAuthenticationFilter).
    4. After a successful sign-in, the existing login filter (LegacyAuthFilter) hands the user, roles, department and login method to CONTEXA with ContexaAuthBridge.handoff(...) and keeps the user object in the session attribute legacyUser.
    5. Put @Protectable on the APIs you protect.
  • Why the application needs its own chain: When the application owns sign-in (authentication ownership HOST_OWNED), CONTEXA builds no sign-in chain and does not fill the SecurityContext. @Protectable needs an authenticated user in the SecurityContext. Without one, the call is refused in SHADOW and ENFORCE. ContexaAuthBridge.handoff(...) tells CONTEXA about the sign-in but does not fill the SecurityContext. Steps 2 and 3 above are therefore still needed, and this is their code:
@Bean
SecurityFilterChain legacyChain(HttpSecurity http) throws Exception {
    return http.csrf(csrf -> csrf.disable())
            .authorizeHttpRequests(auth -> auth.anyRequest().permitAll())
            .addFilterBefore(new LegacySessionAuthenticationFilter(), AnonymousAuthenticationFilter.class)
            .build();
}

// Puts the user the legacy login left in the session into the SecurityContext on every request
class LegacySessionAuthenticationFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        HttpSession session = request.getSession(false);
        if (session != null
                && session.getAttribute(LegacyAuthFilter.SESSION_USER_KEY) instanceof LegacyUserSession user) {
            List<SimpleGrantedAuthority> roles = user.getRoles().stream()
                    .map(role -> new SimpleGrantedAuthority("ROLE_" + role))
                    .toList();
            SecurityContextHolder.getContext().setAuthentication(
                    UsernamePasswordAuthenticationToken.authenticated(user.getUserId(), null, roles));
        }
        chain.doFilter(request, response);
    }
}

In this code the chain lets every URL through (permitAll()) and leaves the access rules to the existing application. On every request the filter reads the LegacyUserSession from the session and puts the user into the SecurityContext with the roles prefixed by ROLE_. Spring Security's defaults also apply to this chain, so adjust whatever differs from the application's earlier behavior (Connecting your existing sign-in).

  • What you do:
    1. Sign in with one of the legacy methods: the form (/legacy/login), the X-Auth-Token header or the remember-me cookie.
    2. Call the protected APIs: GET /api/customers (@Protectable, asynchronous) and GET /api/customers/export (@Protectable(sync = true)).
  • Example users: admin/admin123 (ADMIN, MANAGER), kim_manager/manager123, park_dev/dev123, lee_analyst/analyst123.
  • What you see:
    • The application's existing filter and login methods handle sign-in, not a CONTEXA page.
    • The two API calls are decided on and recorded in the CONTEXA database. When the operating mode is SHADOW or ENFORCE, a call to /api/customers without sign-in is refused.
    • The application's data stays in its own (in-memory H2) database. CONTEXA's data goes to the dedicated CONTEXA database.
    • The CONTEXA admin console takes a CONTEXA administrator account, separate from the application's users, not an application account (Looking at the admin console).
  • Scenario profiles: 10 application-scenario-*.yml files test start-up with different database setups (dedicated H2, a shared database allowed for a PoC or refused in production, no dedicated database, bridge off, a context path behind a proxy and more, ports 19081 to 19091). The fake-chat profile uses a test model that always answers allow (PERMIT) and an empty vector store. It is a test profile that uses no real AI model.
  • Read with: What the application must do, Direct handoff, Finding the user in the session
