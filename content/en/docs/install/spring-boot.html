Add to an Existing Spring Security Application

Adding CONTEXA to an application that already signs users in with Spring Security does not change your login pages, sessions, cookies or URL permission rules. In the default mode your application keeps handling sign-in, and CONTEXA reads who signed in and applies a decision to each request. This page explains what stays the same and what changes, what your application must do, and what users receive for each decision. The mode in which CONTEXA handles sign-in is described in the second half.

Spring Boot version. CONTEXA is built and tested with Spring Boot 3.5.4. With @EnableAISecurity on Spring Boot 4.x it logs an ERROR and stops the startup with an IllegalStateException.

Overview

When you add CONTEXA to an existing application, the first choice is who handles sign-in. Here, sign-in means the login page, the session, the cookies and the URL access rules. There are two options.

  • Your application keeps its sign-in (SANDBOX, default): Your sign-in works as it does today. CONTEXA reads the user your application has signed in and applies decisions to that user's requests.
  • CONTEXA provides the sign-in (FULL): The login page, MFA, sessions and the security chain become CONTEXA's. This fits a new application, or one that moves its sign-in to CONTEXA.

A decision is the conclusion CONTEXA's AI reaches about one user's request: ALLOW, step-up authentication (CHALLENGE), held for review (ESCALATE) or BLOCK. With either option, CONTEXA makes and applies the decisions.

The figure names two CONTEXA components. The request-time filters are servlet filters that read the decision stored for a user when a request comes in and apply it. The authentication bridge is the component that reads your application's sign-in result on every request. The figure shows the steps a request passes under each option and who is responsible for each step.

Decide first: who handles sign-in

Who handles sign-in is set by the security mode (SANDBOX or FULL), which you write with @EnableAISecurity in code or with a setting. The security mode says what CONTEXA's security configuration does to your application. SANDBOX (the default) keeps CONTEXA apart from it: your application's sign-in, authorization and security settings (CSRF, CORS, headers) stay as they are, and CONTEXA applies its decisions from servlet filters behind your application's chain. FULL makes CONTEXA your application's main security configuration (sign-in, authorization, security settings). All of CONTEXA's features work in either mode. The security mode and the authentication ownership (HOST_OWNED or CONTEXA_OWNED) are two separate settings. The authentication ownership settles which of two components of the same kind serves your application when your application brings its own (its UserDetailsService, JwtDecoder and the like) and CONTEXA has one too: HOST_OWNED keeps your application's, CONTEXA_OWNED lets CONTEXA's serve where your application has none. It turns no feature off, and all four combinations are allowed. Left unset, it follows the mode (SANDBOX → HOST_OWNED, FULL → CONTEXA_OWNED).

When your application keeps its sign-in (default SANDBOX)

Under this option your application signs users in as it does today. CONTEXA reads the user your chain has verified and applies the stored decisions to that user. This section covers what stays the same, what changes, and what your application must do.

What stays the same

  • Sign-in and sessions: CONTEXA does not change your SecurityFilterChain, UserDetailsService, authentication providers, spring.security.* settings, sessions or cookies. It does not add a sign-in chain or an AI session repository to your request path.
  • URL access rules: Your chain sets who the user is and applies your rules first. CONTEXA's filters run after your security chain and your other servlet filters have all run, so you do not need to change the order of your own filters for CONTEXA.
  • The language of your pages: Your pages keep the language your application resolves (Accept-Language, your LocaleResolver). If you have a message bundle (messages.properties), your texts come first and CONTEXA's texts stand behind them. CONTEXA's language resolver (Korean by default) and its ?lang= switch serve only the screens under /contexa/.
  • Your database: CONTEXA uses its own database (contexa.datasource.url). It does not change your application's database connection.

What changes

  1. Stored decisions apply to every request. After your security chain and all of your servlet filters, CONTEXA's servlet filters check requests on every path (/*). When the user has a stored BLOCK, CHALLENGE or ESCALATE, CONTEXA answers the request before it reaches your controller (Decisions and answers).
  2. Methods marked @Protectable (protected methods) are analyzed. When a user calls a @Protectable method, CONTEXA analyzes the request and checks the stored decision again before the method runs. In shadow mode (SHADOW) and enforcement mode (ENFORCE), CONTEXA refuses a call whose user it cannot know (no user signed in to your Spring Security, or only an anonymous one, and no user named through a resolver or the request attribute either). CONTEXA does not analyze the sign-in itself, so a user's first decision comes from the first protected method that user calls.
  3. A step-up page appears. When the decision is CHALLENGE, the user goes to CONTEXA's step-up page /contexa/step-up. The page only verifies the user and does not replace your sign-in. Your sign-in, session and cookies stay as they are (The step-up under SANDBOX).
  4. CONTEXA owns the paths under /contexa/. The step-up page and the decision pages (/contexa/step-up and everything under /contexa/zero-trust/) answer only signed-in users. Your chain's URL rules apply to these paths first, so your application must allow signed-in users on them. Even if your rules allow an anonymous request, CONTEXA answers an anonymous request on these paths with 401. Keep your own endpoints out of these paths.
  5. The admin console has a separate sign-in. A chain that CONTEXA builds only for this purpose takes the admin console /contexa/admin/**. Administrators sign in at /contexa/admin/login with a CONTEXA administrator account, which is separate from your application's users, and give a passkey or a mailed code as a second step after the password. Your chain does not need to protect these paths, and signing out of the console does not end your application's session.
  6. Some requests wait for a decision. A default (asynchronous) method is analyzed after the response, so the response is not slowed. A sync = true method waits for the decision inside the call, for at most 40 seconds by default (contexa.security.zerotrust.agent.flight.wait).
  7. The start needs the dedicated database. The start stops when contexa.datasource.url is missing. When CONTEXA's database cannot be reached, or Redis cannot be reached in distributed mode, your application starts without CONTEXA and logs an ERROR (When the start stops or runs without CONTEXA).

The default operating mode is enforcement mode (ENFORCE). If you add CONTEXA to an application that already has users, decisions apply to real requests from the start, and normal users can be asked for step-up authentication or blocked. Operating mode shows how to start in shadow mode (SHADOW) first.

What your application does: tell CONTEXA about your sign-in

On every request CONTEXA reads the signed-in user that your Spring Security has established. The component that does this is the authentication bridge. It only reads; it does not change your sign-in, session or response. Your application has two tasks. The example code is in Connect your existing sign-in in the installation guide.

  1. Declare your own SecurityFilterChain. Without one and with users of your own, Spring Boot's default security applies and every request needs a sign-in, and CONTEXA logs a WARN at start. With no users of your own either, CONTEXA puts an isolation chain that lets every request through in place of Spring Boot's default chain, so access stays as it was before CONTEXA came.
  2. Put the signed-in user into the SecurityContext as an authenticated Authentication, in a Spring Security filter of your chain. An application that uses Spring Security's form login, OAuth2 login or Bearer token filter already does this. An application that signs users in with a session or a token of its own, without Spring Security, declares no chain and names the signed-in user with a ContexaSubjectResolver bean (Connect your existing sign-in in the installation guide).

The bridge reads three things about the user: who the user is and how the user signed in (authentication), which authorities the user has (authorization), and, when an AI agent calls on the user's behalf, who delegated what (delegation). These facts become the evidence of the decision. The user id is Authentication.getName(), and the mail address is read from the email claim of the token or the OAuth2 login. When there is none, as with the UserDetails of a form login, add a mail address provider (a BridgeUserEmailProvider bean). The authorities are those of the Authentication, and the delegation is read from the delegation claims of the token (contexa.bridge.delegation.token.*). The sign-in method, whether MFA was used and the time of authentication are read from the standard token claims amr, acr and auth_time. Without standard claims, as with a form login, put a ContexaAuthentication in the details of the Authentication (for example ContexaAuthentication.of("PASSWORD+OTP").mfa(true)), or use the request attributes ctxa.context.authenticationType and ctxa.context.mfaVerified. CONTEXA does not guess at the fields of a principal object, so when the principal is an object of your application's own, map it with a ContexaSubjectMapper bean. The details are in Connect your existing sign-in (authentication bridge).

If your application sets the signed-in user later, in an MVC interceptor or a controller, the request-time filters see no user. For such requests the decision is applied only at @Protectable methods. The first time a protected method receives such a request, CONTEXA logs a WARN once. When a person signs in through your form login or OAuth2 login, CONTEXA reads that sign-in through the authentication bridge. It does not send the sign-in to AI analysis.

Decisions and answers

A decision is usually made after the response and applies from that user's next request. The first request, which has no decision yet, goes through and starts the analysis. The figure shows what the user receives for each stored decision when the operating mode is ENFORCE.

With the default settings no ESCALATE answer occurs. When the second analysis stage, the more thorough one, chooses ESCALATE, CONTEXA does not store it and stores a CHALLENGE instead. The setting that stores ESCALATE as it is is described in Answers, authorities and release by decision.

  • @Protectable methods (either mode): On BLOCK, CHALLENGE or ESCALATE the method does not run. A refusal thrown from a controller is answered by CONTEXA's exception handler. A browser page request (Accept with text/html) goes to the same screen as at the URL. Other clients get the status codes above with a JSON body.
  • At the URL (either mode): The request-time filters handle BLOCK (for a person, block-release MFA is offered first), ESCALATE and CHALLENGE. When the decision is ALLOW or there is none, they wrap the response and monitor it, and cut it if a block decision arrives while the response is going out. Under FULL they run in the CONTEXA chain and a CHALLENGE leads to CONTEXA's MFA. Under SANDBOX they run after your security chain and all of your servlet filters, and a CHALLENGE leads to the step-up page. Details are in Request-time enforcement.

Operating mode

The operating mode (contexa.security.zerotrust.mode) sets whether CONTEXA makes decisions and whether it applies them to requests. You set it separately from who handles sign-in. Without a setting, CONTEXA runs in ENFORCE.

ModeWhat it does
Off (DISABLED)No AI analysis.
Shadow mode (SHADOW)The AI makes decisions and they go to the decision and audit records and to shadow mode's own memory. Decisions are not applied to requests, and ALLOW decisions are learned into the behavioral baseline. A @Protectable call from a user who is not signed in is refused in this mode too.
Enforcement mode (ENFORCE, default)The AI makes decisions, and each decision is stored and applied from the user's next request.

OBSERVE is an old name that is still accepted. When you set it, the mode is read as DISABLED and CONTEXA logs a warning at start. When you add CONTEXA to an existing application for the first time, start with SHADOW as below, review the recorded decisions, and then switch to ENFORCE.

contexa:
  security:
    zerotrust:
      mode: SHADOW   # only watch at first

A mode saved in the admin console at /contexa/admin/system-settings applies without restart, and the saved value wins over YAML. What happens in SHADOW and when to move to ENFORCE is in Start Safely in Shadow Mode.

When CONTEXA provides the sign-in (FULL)

This mode (FULL) fits a new application. An application that already has sign-in should check the changes below before choosing it. This section covers what changes for your application, the shape of the default chain, the relation to your existing chain and beans, and how the database is handled.

Before you choose FULL: what changes for your application

Under FULL CONTEXA's main chain signs users in and answers every request that no chain ahead of it (such as a chain of yours narrowed with http.securityMatcher(...)) takes, and the security chains Spring Boot would build for your application are not built. Your code is not changed, but some answers are. Compare your clients with the list below. If a client depends on one of these answers, keep the default (SANDBOX). With the default your application keeps its sign-in, and CONTEXA still makes decisions and applies them on every path.

  • A path without a URL policy needs a sign-in. A new installation asks for a signed-in user on every path that no URL policy names. An anonymous request on such a path is handled in one of two ways. A request that asks for JSON (Accept with application/json, X-Requested-With: XMLHttpRequest, or a path under /api/) gets 401. Any other request is sent to CONTEXA's sign-in page (/mfa/login). This includes /actuator/health, so a health check that calls it without signing in gets 401 or that redirect. "Decision when no URL policy applies" on the system settings screen chooses what happens on these paths (Dynamic authorization).
  • A write needs a CSRF token. The CONTEXA chain uses Spring Security's CSRF protection. A POST, PUT, PATCH or DELETE request without the token gets 403 before your controller runs. This also applies where your application answered 401 (a sign-in with a wrong password, a body it could not read, an anonymous write). With the token, the CSRF check passes. CONTEXA keeps the token in the session and sets no XSRF-TOKEN cookie. CONTEXA's pages carry the token in the _csrf, _csrf_header and _csrf_parameter meta tags. A single-page application (SPA) or API client that wrote without the token must now send it. To exchange the token in a cookie instead, configure it in global() (CSRF in the Identity DSL).
  • CONTEXA's sign-in reads CONTEXA's accounts only (FULL + CONTEXA_OWNED, the default). CONTEXA's sign-in (form, MFA password, REST, one-time code, passkey) reads only CONTEXA's own user store, however many UserDetailsService beans your application declares (Relation to existing beans). Your users cannot sign in until they are CONTEXA accounts. When CONTEXA's provider is the only AuthenticationProvider bean, Spring Security builds the global AuthenticationManager from it. Code of yours that signs users in through that manager (for example a token endpoint such as POST /api/authenticate) then checks CONTEXA's accounts as well. Under FULL with contexa.bridge.ownership: HOST_OWNED, the main chain signs your users in with your application's UserDetailsService.
  • HTTP Basic and Bearer clients are not signed in. The default chain signs users in with CONTEXA's form, passkey and one-time code. It has no HTTP Basic and no Bearer token authentication, so a client that sends Authorization: Basic …, or a Bearer token your application accepted, is treated as not signed in.
  • The signed-in user is CONTEXA's type. After a password sign-in through CONTEXA the principal is io.contexa.contexacommon.security.UnifiedCustomUserDetails. Code that casts it to your own user type throws ClassCastException, and a parameter such as @AuthenticationPrincipal MyUser or @AuthenticationPrincipal Jwt receives null.
  • Chains that Spring Boot would build for you are not built. Spring Boot builds its chains only when the application has no SecurityFilterChain bean, and CONTEXA's chain is such a bean. So these chains do not exist: the default chain (form login and HTTP Basic), Actuator's management chain (which leaves /actuator/health open), and the chains Spring Boot builds from your settings for an OAuth2 resource server, OAuth2 login, SAML2 login and Spring Authorization Server. The endpoints of these chains, such as /.well-known/openid-configuration, /oauth2/jwks, the SAML2 service provider metadata and its assertion consumer service, then answer 404, 401 or 403. CONTEXA does not refuse the start for this, and the startup log does not mention it.

The default chain shape

When your application declares no PlatformConfig bean, CONTEXA builds a default configuration.

  • Requests: Every request except static resources (/contexa/css/** and so on) is evaluated by the dynamic authorization policies (CustomDynamicAuthorizationManager).
  • Sign-in: The chain uses form login, passkey and one-time token (OTT) MFA (one factor, then /), with session state management.
  • Not built under SANDBOX. The ownership under SANDBOX is always HOST_OWNED, and CONTEXA builds no chain from a PlatformConfig, whether it is the default or yours. CONTEXA's only chain is the console chain for /contexa/admin/** (above).

The reference for the annotation attributes and the configuration of each mode is the @EnableAISecurity reference.

Relation to your existing chain

A chain of a CONTEXA flow with a path scope (urlPrefix) is registered early (Ordered.HIGHEST_PRECEDENCE + the flow's order), and one that matches every request is registered last (Ordered.LOWEST_PRECEDENCE). The default flow has no path scope, so it matches every request and stands last. Spring Security uses only the first chain that matches a request, and runs no chain after one that takes every request.

So a chain of yours narrowed with http.securityMatcher(...) to the paths it protects takes those paths ahead of CONTEXA's main chain, and both run. When your chain takes every request as well, one of the two would never run, so under FULL CONTEXA refuses to start such an application, and the message names the chain. To keep your chain as your application's main security, use @EnableAISecurity without mode = FULL; otherwise narrow that chain or remove it. When you give the MFA flow a urlPrefix, that flow's chain matches only <urlPrefix>/** requests (Identity DSL).

What FULL does on top

FULL sets the CONTEXA-owned application flag (contexa.datasource.isolation.contexa-owned-application) to true when your application has no database of its own. That means spring.datasource.url is not set, or names the same database as contexa.datasource.url. A value you set yourself always stands. With the flag true:

  • Unless your application declares a DataSource bean itself, your application's default database connection (dataSource) is the CONTEXA database. The default JdbcTemplate and TransactionTemplate, when your application declares none, use the CONTEXA database too.
  • The capability check becomes FAIL_FAST, so the startup stops when a required part such as the chat model or the vector store is missing (Capability check).

When spring.datasource.url names a database of your own, your application keeps it under FULL. The flag stays false and your default connection is not replaced. If you set the flag to true yourself anyway, the CONTEXA database serves your application, and the startup log says [Contexa] contexa.datasource.isolation.contexa-owned-application=true: the application's spring.datasource is not used; Contexa's database serves the application. (WARN).

Build the chain yourself (FULL)

When you declare a PlatformConfig bean, CONTEXA builds its chain from it instead of from the default configuration. Under FULL the bean's flows become chains whatever the ownership, and outside FULL + CONTEXA_OWNED the flow of CONTEXA's administrators, contexa-admin, is added.

Example A: REST API only

@Bean
public PlatformConfig platformConfig(IdentityDslRegistry<HttpSecurity> registry) throws Exception {
    return registry
        .global(http -> http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**").permitAll()
                .anyRequest().authenticated()))
        .rest(rest -> rest.order(10))
        .session(Customizer.withDefaults())
        .build();
}

Example B: form login + dynamic authorization

@Bean
public PlatformConfig platformConfig(IdentityDslRegistry<HttpSecurity> registry,
                                     CustomDynamicAuthorizationManager customDynamicAuthorizationManager) throws Exception {
    return registry
        .global(http -> http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/css/**", "/js/**", "/images/**").permitAll()
                .anyRequest().access(customDynamicAuthorizationManager)))
        .form(form -> form.defaultSuccessUrl("/dashboard"))
        .session(Customizer.withDefaults())
        .build();
}

CONTEXA registers the session security context repository used for AI trust scores (AISessionSecurityContextRepository) on every flow automatically. You do not put it in global() yourself.

Example C: direct access to the Spring Security configuration

When the DSL is not enough (custom filters, an AuthenticationEntryPoint and so on), you can reach Spring Security's configuration objects directly. Use rawFormLogin for form login and rawHttp() for the flow's whole HttpSecurity. CONTEXA's configuration (request-time filters and so on) is still applied to each flow.

.form(form -> form
    .rawFormLogin(formLogin -> formLogin
        .authenticationDetailsSource(customDetailsSource)
        .successHandler(customSuccessHandler)))

For reference: how CONTEXA builds the chains. CONTEXA calls the same Spring Security methods you would call yourself. The order is as follows.

  1. @EnableAISecurity imports the CONTEXA configuration (AiSecurityImportSelector → AiSecurityConfiguration), which builds the default configuration when your application has no PlatformConfig.
  2. CONTEXA creates an HttpSecurity per flow (FlowContextFactory).
  3. It applies the Spring Security configuration for each authentication method (formLogin, webAuthn, oneTimeTokenLogin) and the request-time filters (SecurityConfigurerOrchestrator).
  4. It registers each chain as a bean (SecurityFilterChainRegistrar).

The whole DSL is in Identity DSL, authentication flows in Authentication, MFA in Adaptive MFA.
