Add to an Existing Spring Security Application

When you add Contexa to an application that already uses Spring Security, choose who owns sign-in and check what changes and what stays as a result. This page also covers where decisions are enforced, which answers go out, and how to build the chain yourself when Contexa owns sign-in.

Spring Boot version. Contexa is built and tested with Spring Boot 3.5.4. With @EnableAISecurity on Spring Boot 4.x it logs an ERROR and stops the startup with an IllegalStateException.

At a glance

There are two ways to add Contexa: your application keeps owning sign-in (default), or you leave sign-in to Contexa. Requests take different paths.

When your application owns sign-in (default)

Contexa does not change your SecurityFilterChain, UserDetailsService, authentication providers or spring.security.* settings, and it does not put its own security chain, request-time filters or AI session repository on your request path. Instead your application must do the four things below. The example code is in Connect your existing sign-in in the installation guide.

  1. Declare your own SecurityFilterChain.
  2. Protect /contexa/admin/** with the ADMIN role in your chain.
  3. Turn on method security with @EnableMethodSecurity.
  4. Put the signed-in user into the SecurityContext as an authenticated Authentication.

Decisions are enforced at @Protectable methods. Before running a method Contexa checks the user's stored decision and does not run it on BLOCK, CHALLENGE or ESCALATE; a refusal thrown from a controller is answered by Contexa's exception handler with the status code of the decision (Decisions and answers). The URL-level filters live only in the Contexa chain, so they do not work in this way.

When Contexa owns sign-in

The default chain shape

When your application declares no PlatformConfig bean, Contexa builds a default one, shaped by mode.

  • SANDBOX shape: CSRF, CORS and security headers off; only /contexa/admin/** is protected with the ADMIN role (/contexa/admin/login allowed; self-service paths such as asking to release a block, /contexa/admin/api/aiam/zero-trust/** and /contexa/admin/api/aiam/sse/zero-trust/**, need sign-in only). Every other request is allowed, and the form login processing address is chosen at random at each start.
  • FULL shape: every request except static resources (/contexa/css/** and so on) goes through the dynamic authorization policies (CustomDynamicAuthorizationManager).
  • Both: form login + passkey + one-time token (OTT) MFA (one factor, then /) and session state management.

The reference for the annotation attributes and the configuration of each mode is the @EnableAISecurity reference.

Relation to your existing chain

The Contexa chain is registered first in order (Ordered.HIGHEST_PRECEDENCE + the flow's order), and the default flow has no path scope (urlPrefix), so it matches every request. Spring Security uses only the first chain that matches a request, so a chain your application declared separately receives no requests. When you give the MFA flow a urlPrefix, that flow's chain matches only <urlPrefix>/** requests (Identity DSL).

What FULL does on top

FULL sets the Contexa-owned application flag (contexa.datasource.isolation.contexa-owned-application) to true. Then:

  • Unless your application declares a DataSource bean itself, your application's default database connection (dataSource) becomes the Contexa database. The default JdbcTemplate and TransactionTemplate use the Contexa database too.
  • The capability check becomes FAIL_FAST, so the startup stops when a required part such as the chat model or the vector store is missing (Capability check).

To leave sign-in to Contexa without these two, keep mode at its default and set only contexa.bridge.ownership: CONTEXA_OWNED (the chain then has the SANDBOX shape).

Enforcement mode

Whether decisions are made and applied is set by the enforcement mode (contexa.security.zerotrust.mode), separately from who owns sign-in.

ModeWhat it does
ENFORCE (default)The AI decides, and the decision is stored and applied from the next request.
SHADOWThe AI decides and the decision goes to the decision and audit records, but it is not stored, applied or learned from.
OBSERVE, DISABLEDNo AI analysis (the two behave the same).
 
contexa:
  security:
    zerotrust:
      mode: SHADOW   # only watch at first

A change made in the admin console at /contexa/admin/system-settings applies without restart, and once saved, the value stored in the database wins over YAML. What happens in SHADOW and when to move to ENFORCE is in Start safely with enforcement modes.

Decisions and answers

  • @Protectable methods (both ways): on BLOCK, CHALLENGE or ESCALATE the method does not run; a refusal thrown from a controller is answered by Contexa's exception handler with the status codes above.
  • At the URL (CONTEXA_OWNED only): request-time filters handle BLOCK (for a person, block-release MFA is offered first), ESCALATE and CHALLENGE; when there is no decision they wrap the response so it can be cut if a block decision arrives during analysis. Details are in Request-time enforcement.

Build the chain yourself (CONTEXA_OWNED)

When you declare a PlatformConfig bean, Contexa builds its chain from it instead of the default. The bean becomes a chain only under CONTEXA_OWNED; under HOST_OWNED your Spring Security configuration is used as is.

Example A: REST API only

@Bean
public PlatformConfig platformConfig(IdentityDslRegistry<HttpSecurity> registry) throws Exception {
    return registry
        .global(http -> http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**").permitAll()
                .anyRequest().authenticated()))
        .rest(rest -> rest.order(10))
        .session(Customizer.withDefaults())
        .build();
}

Example B: form login + dynamic authorization

@Bean
public PlatformConfig platformConfig(IdentityDslRegistry<HttpSecurity> registry,
                                     CustomDynamicAuthorizationManager customDynamicAuthorizationManager) throws Exception {
    return registry
        .global(http -> http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/css/**", "/js/**", "/images/**").permitAll()
                .anyRequest().access(customDynamicAuthorizationManager)))
        .form(form -> form.defaultSuccessUrl("/dashboard"))
        .session(Customizer.withDefaults())
        .build();
}

Contexa registers the session security context repository used for AI trust scores (AISessionSecurityContextRepository) on every flow automatically, so you do not put it in global() yourself.

Example C: direct access to the Spring Security configuration

When the DSL is not enough (custom filters, an AuthenticationEntryPoint and so on), reach Spring Security's configuration objects directly: rawFormLogin for form login, rawHttp() for the flow's whole HttpSecurity. Contexa's configuration (request-time filters and so on) is still applied to each flow.

.form(form -> form
    .rawFormLogin(formLogin -> formLogin
        .authenticationDetailsSource(customDetailsSource)
        .successHandler(customSuccessHandler)))

For reference: how Contexa builds the chains. @EnableAISecurity imports the Contexa configuration (AiSecurityImportSelector → AiSecurityConfiguration), which builds the default configuration when your application has no PlatformConfig. Contexa creates an HttpSecurity per flow (FlowContextFactory), applies the Spring Security configuration for each authentication method (formLogin, webAuthn, oneTimeTokenLogin) and the request-time filters (SecurityConfigurerOrchestrator), then registers each chain as a bean (SecurityFilterChainRegistrar). Contexa calls the same Spring Security methods you would call yourself.

The whole DSL is in Identity DSL, authentication flows in Authentication, MFA in Adaptive MFA.
