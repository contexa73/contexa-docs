contexa-autoconfigure Configuration

Configuration Guide

Most CONTEXA settings work with their defaults. To start, you must settle four things (turning CONTEXA on, the dedicated database, the AI models and vector store, and your application's sign-in), and a few more before you move to production. Choose what you want to do on this page (turn it on for the first time, change the model, deploy several instances and so on) to find the settings you need and the page that explains them. For a setting name you saw in older documents or examples, the section “Moved keys · removed keys” near the end of this page gives today's name.

Settings you must set and settings whose defaults are enough

Most CONTEXA settings work with their defaults. To start, you must have the four items below. If one is missing, CONTEXA does not turn on, the start stops, or no decisions are made. A decision is the conclusion the AI model reaches about a user's request: ALLOW, step-up authentication (CHALLENGE), held for review (ESCALATE) or BLOCK. Step-up authentication is a decision that asks for MFA.

When responses are slow

By default CONTEXA analyzes a request after the response has left, so the analysis time is not added to the response time of that request. A response is slow when the request has to wait for a decision. Check in this order.

  1. Check whether the slow request is a @Protectable(sync = true) method. sync = true waits for the decision inside the request, before the method runs. The default is false, so use sync = true only for a method that needs the decision at once (@Protectable).
  2. Check whether the request comes from a new session, a new IP address or a new browser. A person's request whose session, address or browser changed since the user's last decision waits for the decision of that request, even for a default (asynchronous) method. The wait does not exceed contexa.security.zerotrust.agent.flight.wait (default 40s) (Decision merging). For requests from the same session, address and browser, an ALLOW decision is reused without a new analysis for contexa.security.zerotrust.allow-validity (default 15m) (Choosing the operating mode).
  3. Check whether the analysis itself takes long. If the model is slow, set a faster model for Layer 1 (contexa.security.tiered.llm.layer1.model, Layer 1 and Layer 2 models). The time limit of the whole Layer 1 analysis is contexa.security.tiered.layer1.timeout.llm-ms (default 90000 ms) (Decision time limits).
  4. Check how long a decision made inside the request waits for the search of past decision records. The default is contexa.security.tiered.layer1.timeout.interactive-rag-wait-ms (600 ms) (Decision time limits).
  5. A self-hosted model server such as Ollama takes only a limited number of calls at once. The default is 2 (contexa.llm.gate.self-hosted-max-concurrent). Set it to the number of requests the server can process at once (How many calls a model server takes).

All settings pages

Settings are spread over the five settings pages below and the settings sections of the feature pages.

Where settings apply

CONTEXA works in two stages. First, when a request comes in, it applies the decision already stored (request time). Second, after the response has left, it analyzes that request and makes the decision for the same user's next request (asynchronous decision). The two stages are linked through the decision store. Each box in the figure names the settings page that controls that point.

Minimal configuration example

The smallest setup that adds CONTEXA to a Spring Boot application that already has sign-in and runs decisions. It uses one OpenAI model and one PostgreSQL database that can use the pgvector extension. For other models (Anthropic · Ollama), see Connecting AI Models.

dependencies {
    implementation 'ai.ctxa:spring-boot-starter-contexa:{{contexa.version}}'
    implementation 'org.springframework.boot:spring-boot-starter-security'
    implementation platform('org.springframework.ai:spring-ai-bom:1.1.8')
    implementation 'org.springframework.ai:spring-ai-starter-model-openai'
    implementation 'org.springframework.ai:spring-ai-starter-vector-store-pgvector'
}
import io.contexa.contexacommon.annotation.EnableAISecurity;

@SpringBootApplication
@EnableAISecurity
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}
contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
    isolation:
      contexa-owned-application: true   # only when the application has no database of its own; see the box below

spring:
  ai:
    openai:
      api-key: ${OPENAI_API_KEY}

Starting with this configuration works as follows.

  • On the first start CONTEXA creates its own tables and default data in the dedicated database (contexa.iam.seed.enabled, default true). At the same time it creates the pgvector extension and the vector table (the default CONTEXA adds, contexa.vectorstore.pgvector.initialize-schema=true).
  • Decisions use the OpenAI chat model. No embedding model is named, so embeddings use Spring AI's default, OpenAI text-embedding-ada-002 (1536 dimensions). CONTEXA follows your application's embedding model and does not set one.
  • The operating mode is ENFORCE: decisions are stored and applied from the next request. The infrastructure mode is standalone: decision and learning state stay in memory.
  • The application keeps its sign-in (the default SANDBOX). CONTEXA analyzes calls to methods marked @Protectable. It applies a stored decision in two places: a filter that runs after the application's security chain and all of its servlet filters applies it on every path, and a check applies it once more before a @Protectable method runs. You choose what to protect with @Protectable.
Set contexa-owned-application: true only when the application has no database of its own. This value makes the application's default DataSource · JdbcTemplate the CONTEXA database too. Spring AI's pgvector auto-configuration builds the vector store on the application's default JdbcTemplate. So in a new application this line puts the vector table in the CONTEXA database. An application with its own database leaves this line out. The vector store then uses the application's default database, which must be able to use pgvector. To keep the vector store in the CONTEXA database, declare your own VectorStore bean built on contexaDataSource. Spring AI's auto-configuration then does not apply. Details are in Dedicated database.
This setup needs a SecurityFilterChain or users of the application's own. With neither, CONTEXA puts an isolation chain in place that lets every request through, so access stays as it was before CONTEXA. To leave sign-in to CONTEXA, use @EnableAISecurity(mode = SecurityMode.FULL). With users but no chain, Spring Boot's default security turns on, every request requires authentication, and one WARN line appears in the start-up log. For using CONTEXA with an application's existing security settings, see Adding CONTEXA to a Spring Boot application.
