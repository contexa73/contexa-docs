spring-boot-starter-contexa

Installation Guide

The steps to turn Contexa on in your Spring Boot application and check that the first decision runs. You can install in one go with the CLI, or add the dependencies, the dedicated database and the settings by hand.

At a glance

After installation, Contexa inside your application is connected to three places. Most of this page is about what sets each connection.

Order: install with the CLI or install by hand → connect your existing sign-in (when your application owns sign-in) → check that it is on.

Install with the CLI

The Contexa CLI puts the dependencies, the annotation and the settings into your application project. Prebuilt binaries exist for Linux x64, macOS Apple Silicon (arm64) and Windows x64.

Install the CLI

# Linux, macOS, Git Bash, WSL
curl -fsSL https://install.ctxa.ai | sh
# Windows PowerShell
irm https://install.ctxa.ai/install.ps1 | iex

The installer verifies the download against the SHA-256 digest published next to the binary. Instead of the script you can download the binary (for example contexa-win-x64.exe for Windows) from the contexa-cli releases page and put it on your PATH.

What contexa init does

cd your-spring-project
contexa init --check   # only checks the environment and exits (Java 17+, Docker)
contexa init
  1. Questions: choose Quick Start (default) or Advanced Setup. Quick Start uses OpenAI and Anthropic as providers, the SHADOW enforcement mode and no infrastructure, and asks once more whether to use Ollama. Advanced Setup asks for the security mode, enforcement mode, providers and distributed infrastructure one by one.
  2. Build file: adds the starter, the Spring AI BOM with the chosen provider starters, and the PgVector starter. Provider starters you did not choose are removed.
  3. Main class: puts @EnableAISecurity without attributes on the class annotated with @SpringBootApplication (the default way, where your application owns sign-in).
  4. application.yml: writes the dedicated Contexa database (contexa.datasource.*, default address jdbc:postgresql://localhost:5432/contexa, overridable with the environment variables CONTEXA_DB_URL, CONTEXA_DB_USERNAME, CONTEXA_DB_PASSWORD), the enforcement mode, the model selection (contexa.llm.selection.*) and the chosen providers' spring.ai.* (keys from the environment variables OPENAI_API_KEY, ANTHROPIC_API_KEY).
  5. Backup: keeps the original files under contexa/bak/ in the project before changing them.
  6. Infrastructure (optional): with --distributed or --simulate it writes a Docker Compose file outside the project (in an OS-specific Contexa folder) and starts PostgreSQL (pgvector), Redis, Zookeeper, Kafka and, when chosen, Ollama. The images are pgvector/pgvector:pg16, redis:7.2-alpine, confluentinc/cp-zookeeper:7.4.0, confluentinc/cp-kafka:7.4.0 and ollama/ollama:latest; the ports are 5432, 6379, 2181, 9092 and 11434, opened on 127.0.0.1 only (changed with the environment variables CONTEXA_*_PORT and COMPOSE_BIND_HOST). When Ollama was started it pulls the chat model (default qwen2.5:7b, environment variable OLLAMA_CHAT_MODEL) and the embedding model (mxbai-embed-large, OLLAMA_EMBEDDING_MODEL). Without these options it does not touch infrastructure, so you prepare PostgreSQL yourself (Create the dedicated database).

Check these in the settings the CLI wrote.

  • For an existing application, remove the line contexa.datasource.isolation.contexa-owned-application: true. The CLI always writes it. With this value your application's default database connection can become the Contexa database (when your application declares no DataSource bean of its own), and the capability check becomes strict, so the startup stops when a model or the vector store is missing (Capability check).
  • Move the database password to an environment variable. The default password the CLI writes is for local trials. contexa scan warns about it.
  • When your application owns sign-in, it still has work to do. The @EnableAISecurity the CLI adds uses the default way, so do the four things in Connect your existing sign-in. When you choose SANDBOX in Advanced Setup, the CLI prints example code at the end; that example has an attribute @EnableAISecurity does not have, so use the examples on this page.

Prerequisites

  • Java 17 or later, Spring Boot 3.x (built and tested with 3.5.4; 4.x is refused at startup)
  • PostgreSQL with the vector extension (pgvector). For example the Docker image pgvector/pgvector:pg16
  • A chat model and an embedding model: OpenAI, or Anthropic (chat) with OpenAI or Ollama (embeddings), or Ollama

Why each one is needed is in the prerequisites of the installation overview.

Install by hand

Do the five steps below in order. The examples use a local Ollama; OpenAI and Anthropic are covered in step 3.

Step 1 · Add the dependencies

Add at least one chat provider starter and the PgVector starter next to the starter. The starter does not bring either of them.

dependencies {
    implementation 'ai.ctxa:spring-boot-starter-contexa:0.1.0'
    implementation platform('org.springframework.ai:spring-ai-bom:1.1.8')
    implementation 'org.springframework.ai:spring-ai-starter-model-ollama'          // or -openai, -anthropic
    implementation 'org.springframework.ai:spring-ai-starter-vector-store-pgvector'
}
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.ai</groupId>
      <artifactId>spring-ai-bom</artifactId>
      <version>1.1.8</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<dependencies>
  <dependency>
    <groupId>ai.ctxa</groupId>
    <artifactId>spring-boot-starter-contexa</artifactId>
    <version>0.1.0</version>
  </dependency>
  <dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-model-ollama</artifactId>
  </dependency>
  <dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-vector-store-pgvector</artifactId>
  </dependency>
</dependencies>

Spring AI BOM 1.1.8 is the version Contexa is built and tested with, the same BOM the starter exports.

Step 2 · Create the dedicated database

Contexa keeps its tables in a dedicated database, not in your application's database. Create the account and the database and turn on the vector extension.

CREATE USER contexa WITH PASSWORD 'change-me';
CREATE DATABASE contexa OWNER contexa;
\c contexa
CREATE EXTENSION IF NOT EXISTS vector;
  • Contexa creates its tables on the first start. When your application starts, Contexa creates and verifies its tables. Its schema begins by creating the vector extension, so if the account cannot create extensions, create it beforehand as above.
  • Use a clean database. On a database where only some Contexa tables exist, the startup stops without changing anything.
  • Using the same address as your application database is blocked by default. To use the same address you must set both contexa.datasource.isolation.allow-shared-application-datasource=true and contexa.datasource.isolation.shared-application-datasource-risk-accepted=true, and it is refused anyway under the prod or production profile.
  • Where the vector table lives: the vector table (vector_store) is created by Spring AI's PgVector starter, which uses your application's default database connection, because Contexa's connection (contexaJdbcTemplate) is not a default candidate. So your application's default database needs the vector extension too. Contexa sets a default (spring.ai.vectorstore.pgvector.initialize-schema=true) so that the first start creates that extension and the table.
  • If your application has no database connection of its own: the starter brings JPA, so Spring Boot tries to create your application's default database connection. With FULL, where Contexa owns sign-in, the Contexa database becomes your application's default connection and nothing else is needed. When your application owns sign-in, set a separate address for your application (spring.datasource.url).

Step 3 · Minimal application.yml

spring:
  datasource:                        # your application's default database (keep it if you have one)
    url: jdbc:postgresql://localhost:5432/myapp
    username: myapp
    password: ${MYAPP_DB_PASSWORD}

contexa:
  datasource:                        # dedicated Contexa database (required)
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
  llm:
    selection:
      chat:
        priority: ollama
      embedding:
        priority: ollama
    chat:
      ollama:
        base-url: http://localhost:11434
        model: qwen3:8b
        keep-alive: 30m
    embedding:
      ollama:
        model: mxbai-embed-large

Pull both models in Ollama beforehand: ollama pull qwen3:8b, ollama pull mxbai-embed-large. The names you pull must match the model values in the settings.

spring:
  ai:
    openai:
      api-key: ${OPENAI_API_KEY}
contexa:
  llm:
    selection:
      chat:
        priority: openai
      embedding:
        priority: openai

For Anthropic, add spring-ai-starter-model-anthropic with spring.ai.anthropic.api-key and set contexa.llm.selection.chat.priority: anthropic. Anthropic has no embedding model, so add an OpenAI or Ollama provider for embeddings (contexa.llm.selection.embedding.priority is openai or ollama).

Every model connection setting is in the configuration guide.

Step 4 · Add @EnableAISecurity

@EnableAISecurity                      // default SANDBOX: your application keeps owning sign-in
@SpringBootApplication
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}

To leave sign-in to Contexa use @EnableAISecurity(mode = SecurityMode.FULL). What changes is in Add to an existing Spring Security application, and all annotation attributes are in the @EnableAISecurity reference. With the default way, where your application owns sign-in, be sure to do Connect your existing sign-in next.

Step 5 · Put @Protectable on the methods to protect

@Protectable
@GetMapping("/api/customers")
public List<Customer> getCustomers() { ... }
  • With @Protectable(sync = true) the decision is made inside that call and applied right away (the response takes longer).
  • An agent request with no decision on record is decided in place even on an asynchronous method (Agent security).
  • All attributes and the policy link are in the @Protectable reference; how a decision is made is in Decision engine.

Connect your existing sign-in (when your application owns sign-in)

By default (SANDBOX, authentication ownership HOST_OWNED) Contexa builds no security chain. Sign-in, sessions and access rules stay with your application's Spring Security, and Contexa only reads the result of your sign-in (the authentication bridge). So your application must do these four things.

  1. Declare your own SecurityFilterChain. Without it Spring Boot's default security applies and every request asks for sign-in; Contexa reports this with an ERROR log at startup.
  2. Protect the admin console /contexa/admin/** with the ADMIN role. Contexa's URL rule for the admin console lives only in the chain Contexa builds, and in this way there is no such chain.
  3. Turn on method security (@EnableMethodSecurity). The @PreAuthorize("hasRole('ADMIN')") on the admin controllers and services applies only with method security on, and Contexa turns it on only under CONTEXA_OWNED.
  4. Put the signed-in user into the SecurityContext as an authenticated Authentication. @Protectable methods refuse calls without it or with an anonymous one. A legacy user object kept only in the session is not proof of authentication.
@Configuration
@EnableMethodSecurity
public class HostSecurityConfig {

    @Bean
    public SecurityFilterChain hostSecurityFilterChain(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth -> auth
                // the same as the rule Contexa puts in its own chain: self-service paths such as asking to release a block need sign-in only
                .requestMatchers("/contexa/admin/api/aiam/zero-trust/**",
                                 "/contexa/admin/api/aiam/sse/zero-trust/**").authenticated()
                .requestMatchers("/contexa/admin/**").hasRole("ADMIN")
                // other pages stay protected by your existing legacy filters
                .anyRequest().permitAll());
        return http.build();
    }
}

Spring Security's defaults (CSRF protection, security response headers and so on) apply to this chain too, so adjust whatever differs from your existing behavior. Contexa's startup diagnostic names anyRequest().permitAll() as an example when no chain exists, but stopping there leaves the admin console unprotected.

When you have a legacy session object

The authObjectLocation, authObjectAttribute and authObjectType attributes of @EnableAISecurity only tell the bridge where to look first for the user object, and its attribute name and type. They do not connect sign-in, so item 4 above (an authenticated Authentication) is still needed.

@EnableAISecurity(
    authObjectLocation = AuthObjectLocation.SESSION,   // AUTO (default), SESSION, REQUEST_ATTRIBUTE, HEADER
    authObjectAttribute = "loginUser"                  // legacy session attribute name
)
@SpringBootApplication
public class LegacyApplication { }

AUTO and SESSION look in the session, then request attributes, then headers; REQUEST_ATTRIBUTE looks in request attributes first; HEADER looks in headers first. Values read from the session, request attributes or headers are used as authorization and delegation evidence. The reference for these attributes is the @EnableAISecurity reference; using the session object as the basis of the authentication stamp and more is in Connect your existing sign-in (authentication bridge).

Capability check

When the startup finishes, Contexa checks that the parts decisions need were created: the chat model llm-runtime, the embedding model embedding-runtime, the vector store rag-vector, learning security-learning, the decision engine autonomous-decision and the bridge bridge. contexa.capability.mode sets how strict the check is.

ValueBehavior
AUTO (default)FAIL_FAST for an application owned by Contexa, otherwise WARN. Owned by Contexa = contexa.datasource.isolation.contexa-owned-application=true, or spring.application.name starting with contexa-
WARNReports missing required parts with ERROR logs only and keeps starting. Shows only what your application can fix (chat and embedding models, vector store, decision strategy).
FAIL_FASTStops the startup with Contexa required capability check failed. when a required part is missing.
STRICTLogs every missing part, optional ones too, and stops when a required part is missing.
OFFNo check.

With Spring Boot Actuator on the classpath the same result is available from the endpoint contexacapabilities (GET /actuator/contexacapabilities). To open it over the web, add it to Spring Boot's management.endpoints.web.exposure.include. To turn the endpoint off, set contexa.capability.expose-diagnostics-endpoint: false.

Moving to a distributed deployment

To run several instances, or to keep learned state across restarts, set the infrastructure mode to distributed and add the Redis, Redisson and Kafka dependencies and connection settings to your application (the Contexa modules do not bring them).

implementation 'org.springframework.boot:spring-boot-starter-data-redis'
implementation 'org.redisson:redisson'          // your application picks the version
implementation 'org.springframework.kafka:spring-kafka'
contexa:
  infrastructure:
    mode: distributed
spring:
  data:
    redis:
      host: localhost
      port: 6379
  kafka:
    bootstrap-servers: localhost:9092

The decision store and learned state go to Redis, security events to Kafka, and block signals spread through Redisson. What changes is in Infrastructure mode.
