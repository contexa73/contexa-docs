spring-boot-starter-contexa

Installation Guide

The steps to turn Contexa on in your Spring Boot application and check that the first decision runs. You can install in one go with the CLI, or add the dependencies, the dedicated database and the settings by hand.

At a glance

After installation, Contexa inside your application is connected to three places. Most of this page is about what sets each connection.

Order: install with the CLI or install by hand → connect your existing sign-in (when your application owns sign-in) → check that it is on.

Install with the CLI

The Contexa CLI adds Contexa to a Spring Boot 3 application and gets it running: it prepares a local database and AI model, changes the project, checks that the dependencies download, and offers to start the application. Prebuilt binaries exist for Linux x64, macOS Apple Silicon (arm64) and Windows x64.

Install the CLI

# Linux, macOS
curl -fsSL https://install.ctxa.ai | sh
# Windows PowerShell
irm https://install.ctxa.ai/install.ps1 | iex

The installer checks the signed release and the binary's SHA-256 before it replaces anything, and prints the next step. When the current terminal cannot see the new command yet, it also prints the one line that makes it available; new terminals find it on their own.

What contexa init does

cd your-spring-project
contexa init

No project yet? Run contexa init in an empty folder: it creates a small Spring Boot 3.5 application with Contexa and sample sign-in accounts (start.spring.io only creates Spring Boot 4 projects, which Contexa does not support yet).

  1. Checks before any change: Spring Boot 3.5.x (on 3.4 and older, and on 4.x, it stops and changes nothing), Java 17 or later, the @SpringBootApplication class, and Docker or Ollama for the local services. Anything missing is explained with the fix.
  2. One question: the AI model provider, Ollama (runs on your computer, no API key; the default), OpenAI or Anthropic. The CLI then shows everything it will change, including who will own sign-in (below), and asks to go ahead.
  3. Local services, shared by your projects: PostgreSQL with pgvector in Docker (container contexa-local-postgres, on a free port such as 55432, bound to 127.0.0.1) with a database of its own for each project; the Ollama already running on your computer, or one started in Docker, with the models qwen3:8b and mxbai-embed-large downloaded once; and a local mail inbox (Mailpit) that receives Contexa's one-time codes, in both ownerships: the second sign-in step when Contexa provides the sign-in, the step-up after a CHALLENGE when your application keeps it. The CLI points spring.mail.* at it. Your existing PostgreSQL or Ollama on the default ports is left alone.
  4. Build file: adds the starter, the Spring AI BOM (1.1.8), the model starter and the PgVector starter (Maven, Gradle Groovy or Kotlin DSL, also in multi-module builds). Dependencies already in the file are kept.
  5. Main class: when your application declares a SecurityFilterChain (or you give --ownership host), adds @EnableAISecurity without attributes (your application keeps sign-in; do the two things in Connect your existing sign-in; when it signs in with Spring Boot's default user, that user user is kept with a password made once and kept outside the project, see Default user). Otherwise (or with --ownership contexa) it adds @EnableAISecurity(mode = SecurityMode.FULL), so Contexa provides the sign-in.
  6. Settings: writes the Contexa settings to src/main/resources/config/application.yml. Spring Boot reads that location by itself, so your own application.yml and application.properties stay unchanged, and keys you already set are not written. It contains the dedicated database (contexa.datasource.*, each value overridable with CONTEXA_DB_URL, CONTEXA_DB_USERNAME, CONTEXA_DB_PASSWORD), contexa.datasource.isolation.contexa-owned-application set to true only when your application has no database of its own, the SHADOW enforcement mode and the model selection (contexa.llm.*). When the application already keeps its own file in that folder, the settings go to application-contexa.yml and that file gets one spring.config.import line.
  7. Dependency check: resolves the dependencies with the project's own Gradle or Maven wrapper. If they cannot be downloaded, every project change is rolled back and the reason is shown.
  8. Start and confirm: offers to start the application and reports the address once it is up, or the reason when it stops.

In both ownerships (unless the application is the example application or your settings already set contexa.iam.seed.admin.*), contexa init makes a password for the admin-console account admin, keeps it in ~/.contexa/credentials.properties outside the project and shows it at the end. Contexa creates the account when the application first starts (First start). When your application keeps sign-in, the last screen says: sign in to your application the way it always does (or with Spring Boot's default user), open the admin console /contexa/admin, and sign in there with Contexa's administrator admin, not with an account of your application.

API keys for OpenAI and Anthropic come from OPENAI_API_KEY and ANTHROPIC_API_KEY, or are asked for and kept in ~/.contexa/credentials.properties, outside the project. Running contexa init again is safe: it checks what is in place and adds only what is missing.

Before a deployment

  • The local database and its password contexa are for your computer. Set CONTEXA_DB_URL, CONTEXA_DB_USERNAME and CONTEXA_DB_PASSWORD for a real database.
  • The sample accounts exist only in the sample application created in an empty folder (contexa.iam.seed.accounts.enabled=true). Never turn that on for a deployment. The admin-console password lives only in ~/.contexa/credentials.properties on your computer, so a deployment does not get that account.
  • Contexa starts in SHADOW: it records decisions but blocks nothing. Switch to ENFORCE after reviewing them (Changing the mode).

Which ownership contexa init chooses

Before it changes anything, contexa init shows a Security ownership block: the ownership it chose, why (whether your application declares a SecurityFilterChain, or your --ownership), who does what, and the command for the other choice.

WhatExisting system (SANDBOX, HOST_OWNED)New system (FULL, CONTEXA_OWNED)
Chosen whenYour application declares a SecurityFilterChain, or --ownership hostIt declares none, or --ownership contexa
Sign-in, sessions, cookies, URL rulesYour application, as now (Contexa only reads who signed in)Contexa (sign-in page, passkey, one-time code)
Risk decisions and their enforcement on every path (block screen, step-up, agent request gate)ContexaContexa, the same
A CHALLENGEContexa's step-up /contexa/step-up (a passkey, or a one-time code by mail); your sign-in and session stay as they areContexa's MFA
Admin console /contexa/adminProtected by Contexa with its own administrator account, apart from your usersContexa's administrator account

Use --ownership host|contexa when the detection does not fit, for example for an application that signs users in on its own without Spring Security (a filter, an interceptor, a session). Two choices come with a warning in the block:

  • --ownership contexa for an application that declares its own chain: Contexa's chain takes every request first, so your chain and its sign-in are no longer used.
  • --ownership host for an application that declares no chain: Spring Boot's default security asks every request to sign in. To keep your access as it is, declare a chain, for example with anyRequest().permitAll(); the admin console stays protected by Contexa.

The local mail inbox (Mailpit) is prepared for both, so the one-time codes arrive without a mail server of your own.

First sign-in

A first start on a database without user accounts adds five sample accounts (admin, manager, developer, user and finance, all with the password 1111) and logs Sample accounts were added ... (WARN). Sign in at /contexa/admin/login as admin / 1111, then change the password at once with "Change password" in the console header. With contexa.iam.seed.admin.password set, or contexa.iam.seed.accounts.enabled=false, the sample accounts are not added. A database that has accounts gets nothing, and the start log says so (INFO).

One-time codes in development and in production

Accounts such as admin finish their sign-in with a one-time code after the password.

  • Development and tests: with a local, dev, development or test profile, or without a mail server, the code is written to the start log (the console) as well: [OTT] Sign-in code for admin <admin@localhost>: .... Enter it and the sign-in finishes, even when no mail server answers. With the local mail inbox (Mailpit) the CLI prepares, the same code arrives by mail too: SMTP 127.0.0.1:51025 without a sign-in, the mails at http://127.0.0.1:58025.
  • Production: start without a development profile and set spring.mail.* to your mail server. Codes go by mail only. Once the application is ready, Contexa connects to the mail server once and logs [Contexa] One-time sign-in codes are mailed through host:port (INFO), or the reason and what to set (WARN).
# Development: the local mail inbox (Mailpit)
spring:
  mail:
    host: localhost
    port: 51025
    properties:
      mail:
        smtp:
          auth: false

# Production: your mail server (for example 587 with STARTTLS)
spring:
  mail:
    host: smtp.example.com
    port: 587
    username: ${SPRING_MAIL_USERNAME}
    password: ${SPRING_MAIL_PASSWORD}
    properties:
      mail:
        smtp:
          auth: true
          starttls:
            enable: true

contexa.auth.ott.code-to-console decides whether codes go to the log as well. Unset, the rule above applies; set it to false to be sure a production start mails them only.

Prerequisites

  • Java 17 or later, Spring Boot 3.5.x (built and tested with 3.5.4; on 3.4 and older the application does not start, 4.x is refused at startup)
  • PostgreSQL with the vector extension (pgvector). For example the Docker image pgvector/pgvector:pg16
  • A chat model and an embedding model: OpenAI, or Anthropic (chat) with OpenAI or Ollama (embeddings), or Ollama

Why each one is needed is in the prerequisites of the installation overview.

Install by hand

Do the five steps below in order. The examples use a local Ollama; OpenAI and Anthropic are covered in step 3.

Step 1 · Add the dependencies

Add the Spring Security starter, at least one chat provider starter and the PgVector starter next to the starter. The starter brings none of them.

dependencies {
    implementation 'ai.ctxa:spring-boot-starter-contexa:0.1.1'
    implementation 'org.springframework.boot:spring-boot-starter-security'
    implementation platform('org.springframework.ai:spring-ai-bom:1.1.8')
    implementation 'org.springframework.ai:spring-ai-starter-model-ollama'          // or -openai, -anthropic
    implementation 'org.springframework.ai:spring-ai-starter-vector-store-pgvector'
}
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.ai</groupId>
      <artifactId>spring-ai-bom</artifactId>
      <version>1.1.8</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<dependencies>
  <dependency>
    <groupId>ai.ctxa</groupId>
    <artifactId>spring-boot-starter-contexa</artifactId>
    <version>0.1.1</version>
  </dependency>
  <dependency>

Spring AI BOM 1.1.8 is the version Contexa is built and tested with, the same BOM the starter exports.

Step 2 · Create the dedicated database

Contexa keeps its tables in a dedicated database, not in your application's database. Create the account and the database and turn on the vector extension.

CREATE USER contexa WITH PASSWORD 'change-me';
CREATE DATABASE contexa OWNER contexa;
\c contexa
CREATE EXTENSION IF NOT EXISTS vector;
  • Contexa creates its tables on the first start. When your application starts, Contexa creates and verifies its tables. Its schema begins by creating the vector extension, so if the account cannot create extensions, create it beforehand as above.
  • Use a clean database. On a database where only some Contexa tables exist, the startup stops without changing anything.
  • Using the same address as your application database is blocked by default. To use the same address you must set both contexa.datasource.isolation.allow-shared-application-datasource=true and contexa.datasource.isolation.shared-application-datasource-risk-accepted=true, and it is refused anyway under the prod or production profile.
  • Where the vector table lives: Contexa creates the vector table (ctxa_vector_store) itself, in the dedicated Contexa database (contexaJdbcTemplate). Spring AI's PgVector starter is only the dependency that brings the classes; your application's default database connection and your application's VectorStore bean are not used. So the vector extension is needed in the dedicated Contexa database. Contexa sets a default (contexa.vectorstore.pgvector.initialize-schema=true) so that the first start creates that extension and the table.
  • If your application has no database connection of its own: the starter brings JPA, so Spring Boot tries to create your application's default database connection. With FULL, where Contexa owns sign-in, the Contexa database becomes your application's default connection and nothing else is needed. When your application owns sign-in, set a separate address for your application (spring.datasource.url).

Step 3 · Minimal application.yml

spring:
  datasource:                        # your application's default database (keep it if you have one)
    url: jdbc:postgresql://localhost:5432/myapp
    username: myapp
    password: ${MYAPP_DB_PASSWORD}

contexa:
  datasource:                        # dedicated Contexa database (required)
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
  llm:
    selection:
      chat:
        priority: ollama
      embedding:
        priority: ollama
    chat:
      ollama:
        base-url: http://localhost:11434
        model: qwen3:8b
        keep-alive: 30m
    embedding:
      ollama:
        model: mxbai-embed-large

Pull both models in Ollama beforehand: ollama pull qwen3:8b, ollama pull mxbai-embed-large. The names you pull must match the model values in the settings.

Step 4 · Add @EnableAISecurity

@EnableAISecurity                      // default SANDBOX: your application keeps owning sign-in
@SpringBootApplication
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}

To leave sign-in to Contexa use @EnableAISecurity(mode = SecurityMode.FULL). What changes is in Add to an existing Spring Security application, and all annotation attributes are in the @EnableAISecurity reference. With the default way, where your application owns sign-in, be sure to do Connect your existing sign-in next.

Step 5 · Put @Protectable on the methods to protect

@Protectable
@GetMapping("/api/customers")
public List<Customer> getCustomers() { ... }
  • With @Protectable(sync = true) the decision is made inside that call and applied right away (the response takes longer).
  • An agent request with no decision on record is decided in place even on an asynchronous method (Agent security).
  • All attributes and the policy link are in the @Protectable reference; how a decision is made is in Decision engine.

Connect your existing sign-in (when your application owns sign-in)

By default (SANDBOX, authentication ownership HOST_OWNED) Contexa builds no sign-in chain. Sign-in, sessions, cookies and access rules stay with your application's Spring Security, and Contexa only reads the result of your sign-in (the authentication bridge). Contexa still enforces its decisions on every path, with filters that run right after your chain, and protects its admin console /contexa/admin/** itself with a chain of its own and Contexa's administrator sign-in. So your application must do these two things.

  1. Declare your own SecurityFilterChain. Without it Spring Boot's default security applies and every request asks for sign-in; Contexa reports this with a WARN log at startup.
  2. Put the signed-in user into the SecurityContext as an authenticated Authentication, in a filter of that chain. @Protectable methods refuse calls without it or with an anonymous one. A legacy user object kept only in the session is not proof of authentication. When the user is set later (in an MVC interceptor or a controller), Contexa's filters do not see it, so decisions are enforced for those requests only at @Protectable methods, and a WARN says so once.
@Configuration
public class HostSecurityConfig {

    @Bean
    public SecurityFilterChain hostSecurityFilterChain(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth -> auth
                // your pages stay protected by your existing rules and filters
                .anyRequest().permitAll());
        return http.build();
    }
}

Spring Security's defaults (CSRF protection, security response headers and so on) apply to this chain too, so adjust whatever differs from your existing behavior. Contexa's startup diagnostic names anyRequest().permitAll() as an example when no chain exists; that is safe for Contexa's paths, because the admin console is protected by Contexa's own chain and Contexa's user pages (decision screens, step-up, agent confirmations) answer only a signed-in user. Method security (@EnableMethodSecurity) is optional: when you turn it on, the @PreAuthorize on the admin console's controllers adds one more check.

When you have a legacy session object

The authObjectLocation, authObjectAttribute and authObjectType attributes of @EnableAISecurity only tell the bridge where to look first for the user object, and its attribute name and type. They do not connect sign-in, so item 2 above (an authenticated Authentication) is still needed.

@EnableAISecurity(
    authObjectLocation = AuthObjectLocation.SESSION,   // AUTO (default), SESSION, REQUEST_ATTRIBUTE, HEADER
    authObjectAttribute = "loginUser"                  // legacy session attribute name
)
@SpringBootApplication
public class LegacyApplication { }

AUTO and SESSION look in the session, then request attributes, then headers; REQUEST_ATTRIBUTE looks in request attributes first; HEADER looks in headers first. Values read from the session, request attributes or headers are used as authorization and delegation evidence. The reference for these attributes is the @EnableAISecurity reference; using the session object as the basis of the authentication stamp and more is in Connect your existing sign-in (authentication bridge).

Capability check

When the startup finishes, Contexa checks that the parts decisions need were created: the chat model llm-runtime, the embedding model embedding-runtime, the vector store rag-vector, learning security-learning, the decision engine autonomous-decision and the bridge bridge. contexa.capability.mode sets how strict the check is.

ValueBehavior
AUTO (default)FAIL_FAST for an application owned by Contexa, otherwise WARN. Owned by Contexa = contexa.datasource.isolation.contexa-owned-application=true, or spring.application.name starting with contexa-
WARNReports missing required parts with ERROR logs only and keeps starting. Shows only what your application can fix (chat and embedding models, vector store, decision strategy).
FAIL_FASTStops the startup with Contexa required capability check failed. when a required part is missing.
STRICTLogs every missing part, optional ones too, and stops when a required part is missing.
OFFNo check.

With Spring Boot Actuator on the classpath the same result is available from the endpoint contexacapabilities (GET /actuator/contexacapabilities). To open it over the web, add it to Spring Boot's management.endpoints.web.exposure.include. To turn the endpoint off, set contexa.capability.expose-diagnostics-endpoint: false.

Moving to a distributed deployment

To run several instances, or to keep learned state across restarts, set the infrastructure mode to distributed and add the Redis, Redisson and Kafka dependencies and connection settings to your application (the Contexa modules do not bring them).

implementation 'org.springframework.boot:spring-boot-starter-data-redis'
implementation 'org.redisson:redisson'          // your application picks the version
implementation 'org.springframework.kafka:spring-kafka'
contexa:
  infrastructure:
    mode: distributed
spring:
  data:
    redis:
      host: localhost
      port: 6379
  kafka:
    bootstrap-servers: localhost:9092

The decision store and learned state go to Redis, security events to Kafka, and block signals spread through Redisson. What changes is in Infrastructure mode.
