Installation Guide

The procedure for installing CONTEXA in a Spring Boot application and confirming that the first decision is made. There are two ways to install. With the CLI, the CLI prepares a local database, an AI model and the project settings. By hand, you add the dependencies, the dedicated database and the settings yourself. Both ways end with the same checks.

The setup after installation and the order of steps

When you finish this page, your application starts with CONTEXA, and a call to a protected method produces a first decision that appears in the admin console. A decision is the conclusion the AI reaches about one user's request: ALLOW, CHALLENGE (additional authentication), ESCALATE (held for review) or BLOCK.

After installation, CONTEXA inside your application is connected to three places. Most settings on this page decide one of these connections.

Install in this order.

  1. Check the prerequisites: Java, Spring Boot, PostgreSQL with pgvector, and an AI model (Prerequisites).
  2. Install: install with the CLI or install by hand.
  3. Connect your existing sign-in: needed only in the default way, where your application owns sign-in (connect your existing sign-in).
  4. Check: the startup log, the capability check and the first decision, in that order (check that it is on).

Choosing a way to install. Both ways end in the same state. Use the CLI when your development environment has no database and AI model yet. Install by hand when you use a managed database or must set every value yourself. The two are compared in the installation overview.

Who owns sign-in changes part of the procedure. Sign-in means the sign-in page, sessions, cookies and URL access rules. In the default way, your application keeps owning sign-in. The annotation calls this SANDBOX and the settings call it HOST_OWNED; it suits an application that already has sign-in. In the other way CONTEXA owns sign-in: the annotation is FULL and the settings name is CONTEXA_OWNED; it suits a new system. The differences are in Add to an existing Spring Security application.

Prerequisites

Check the following before you install. Why each item is needed is explained in the prerequisites of the installation overview.

  • Java and Spring Boot: Java 17 or later and Spring Boot 3.5.x (built and tested with 3.5.4; on 3.4 and older the application does not start, and 4.x is refused at startup). Check Java with java -version and Spring Boot in your build file.
  • PostgreSQL: PostgreSQL with the vector extension (pgvector), used as the dedicated CONTEXA database. For example the Docker image pgvector/pgvector:pg16
  • AI models: a chat model, which produces decisions, and an embedding model, which produces vectors. Use OpenAI, or Anthropic (chat) with OpenAI or Ollama (embeddings), or Ollama.
  • Docker (only when you install with the CLI): the CLI uses it to run a local PostgreSQL and Ollama. With contexa init --db-url, which points to an existing PostgreSQL with pgvector, the CLI does not need Docker for PostgreSQL.

Install with the CLI

The CONTEXA CLI is a command-line tool that installs CONTEXA in a Spring Boot 3 project. In one run it prepares a local database and AI model, changes the project for CONTEXA, checks that the dependencies download, and offers to start the application. Prebuilt binaries exist for Linux x64, macOS Apple Silicon (arm64) and Windows x64.

Install the CLI

Run the command for your operating system in a terminal.

# Linux, macOS
curl -fsSL https://install.ctxa.ai | sh
# Windows PowerShell
irm https://install.ctxa.ai/install.ps1 | iex

The installer first verifies the signed release and the binary's SHA-256 hash, and installs the file only after that check passes. When it finishes, it prints the next step. When the current terminal does not recognize the new command yet, it also prints the one line that makes it available. New terminals need no extra action.

Expected result. The installer ends without an error and prints the next step. You can then run the contexa command in a terminal, which the next procedures need.

If the result differs. When the contexa command is not found, see the matching entry in Troubleshooting.

What contexa init does

Run contexa init in the project folder.

cd your-spring-project
contexa init

With no project yet, run contexa init in an empty folder. It creates a small Spring Boot 3.5 application with CONTEXA and sample sign-in accounts (start.spring.io only creates Spring Boot 4 projects, which CONTEXA does not support yet).

contexa init works in this order.

  1. Checks before any change: it checks Spring Boot 3.5.x (on 3.4 and older, and on 4.x, it stops and changes nothing), Java 17 or later, the @SpringBootApplication class, and Docker or Ollama for the local services. For anything missing it prints the fix.
  2. One question and a confirmation: you choose the AI model provider: Ollama (runs on your computer, no API key; the default), OpenAI or Anthropic. The CLI then shows everything it will change, including who will own sign-in (below), and asks whether to go ahead.
  3. Local services: these are shared by the projects on your computer.
    • PostgreSQL with pgvector: runs the Docker container contexa-local-postgres on a free port such as 55432, accepting connections only on 127.0.0.1, with a database of its own for each project.
    • Ollama: uses the Ollama already running on your computer, or starts one in Docker. The models qwen3:8b and mxbai-embed-large are downloaded once.
    • Local mail inbox (Mailpit): a development inbox that receives CONTEXA's one-time codes. It is prepared whoever owns sign-in. When CONTEXA owns sign-in, the codes are for the second sign-in step; when your application owns it, they are for the step-up after a CHALLENGE (additional authentication). The CLI points spring.mail.* at the inbox.
    • An existing PostgreSQL or Ollama on the default ports is left alone.
  4. Build file: it adds the starter, spring-boot-starter-security, the Spring AI BOM (1.1.8), the model starter and the PgVector starter. Maven, Gradle Groovy, Kotlin DSL and multi-module builds are supported. Dependencies already in the file are kept.
  5. Main class: the annotation depends on who owns sign-in.
    • When your application declares a SecurityFilterChain (or you give --ownership host), the CLI adds @EnableAISecurity without attributes. Your application keeps sign-in, so do the two things in Connect your existing sign-in. When the application signs in with Spring Boot's default user, that user user is kept, with a password made once and kept outside the project (see Default user).
    • Otherwise (or with --ownership contexa) the CLI adds @EnableAISecurity(mode = SecurityMode.FULL), so CONTEXA provides the sign-in.
  6. Settings: it writes the CONTEXA settings to src/main/resources/config/application.yml. Spring Boot reads that location by itself, so your own application.yml and application.properties stay unchanged, and keys you already set are not written. It writes:
    • the dedicated database (contexa.datasource.*), each value overridable with CONTEXA_DB_URL, CONTEXA_DB_USERNAME and CONTEXA_DB_PASSWORD
    • contexa.datasource.isolation.contexa-owned-application, set to true only when your application has no database of its own
    • the SHADOW operating mode, which records decisions and blocks nothing
    • the model selection (contexa.llm.*)
    • with OpenAI embeddings, the embedding model text-embedding-3-small (spring.ai.openai.embedding.options.model, 1536 dimensions)
    When the application already keeps its own file in that folder, the settings go to application-contexa.yml and that file gets one spring.config.import line.
  7. Dependency check: it resolves the dependencies with the project's own Gradle or Maven wrapper. If they cannot be downloaded, every project change is rolled back and the reason is shown.
  8. Start and confirm: it asks whether to start the application. It prints the address once the application is up, or the reason when it stops.

Expected result. When the last step prints the application address, the installation is done. Confirm that the build file, the main class and config/application.yml changed as described, then continue with Check that it is on.

If the result differs. When the run stops at the checks or at the dependency check, follow the reason and the fix it prints. Errors of the CLI are listed with their fixes in CLI installation and initialization errors in Troubleshooting. After you fix the cause, run contexa init again. It checks what is in place and adds only what is missing, so running it again is safe. To cancel the changes, run contexa reset (Other CLI commands).

Whoever owns sign-in, contexa init makes a password for the admin-console account admin, keeps it in ~/.contexa/credentials.properties outside the project and shows it on the last screen. It does not do this when the application is the example application or your settings already set contexa.iam.seed.admin.*. CONTEXA creates the account when the application first starts (First start). When your application keeps sign-in, the last screen gives these steps.

  1. Sign in to your application the way it always does (or with Spring Boot's default user).
  2. Open the admin console /contexa/admin.
  3. Sign in there with CONTEXA's administrator admin, not with an account of your application.

API keys for OpenAI and Anthropic come from OPENAI_API_KEY and ANTHROPIC_API_KEY, or the CLI asks for them and keeps them in ~/.contexa/credentials.properties, outside the project.

These are the init options you use most.

Before a deployment

  • The local database and its password contexa are for your development computer. In production, set CONTEXA_DB_URL, CONTEXA_DB_USERNAME and CONTEXA_DB_PASSWORD for a real database.
  • The sample accounts are for local trials. When contexa.iam.seed.accounts.enabled is not set, they are created by default in a database without accounts, so in a deployment turn them off with false or set an administrator password (contexa.iam.seed.admin.password). The admin-console password lives only in ~/.contexa/credentials.properties on your computer, so a deployment does not get that account.
  • CONTEXA starts in SHADOW: it records decisions but blocks nothing. Switch to ENFORCE after reviewing them (Changing the mode).

Which ownership contexa init chooses

Ownership means who owns sign-in (the sign-in page, sessions, cookies and URL access rules). Before it changes anything, contexa init shows a Security ownership block. The block names the ownership it chose, why (whether your application declares a SecurityFilterChain, or your --ownership), who does what, and the command for the other choice.

WhatExisting system (SANDBOX, HOST_OWNED)New system (FULL, CONTEXA_OWNED)
Chosen whenYour application declares a SecurityFilterChain, or --ownership hostIt declares none, or --ownership contexa
Sign-in, sessions, cookies, URL rulesYour application, as now (CONTEXA only reads who signed in)CONTEXA (sign-in page, passkey, one-time code)
Risk decisions and their enforcement on every path (block screen, step-up, agent request gate)CONTEXACONTEXA, the same
A CHALLENGECONTEXA's step-up /contexa/step-up (a passkey, or a one-time code by mail); your sign-in and session stay as they areCONTEXA's MFA
Admin console /contexa/adminProtected by CONTEXA with its own administrator account, apart from your usersCONTEXA's administrator account

Use --ownership host|contexa when the automatic choice does not fit, for example for an application that signs users in on its own without Spring Security (a filter, an interceptor, a session). Two choices come with a warning in the block:

  • --ownership contexa for an application that declares its own chain: CONTEXA owns the sign-in, and an application that declares a SecurityFilterChain of its own does not start then: the start is refused and names the chain. Remove those chains, or keep your sign-in with --ownership host.
  • --ownership host for an application that declares no chain: Spring Boot's default security asks every request to sign in. To keep your access rules as they are, declare a chain, for example with anyRequest().permitAll(); the admin console stays protected by CONTEXA.

The local mail inbox (Mailpit) is prepared for both, so the one-time codes arrive without a mail server of your own.

Use these to check the state after the installation or to cancel its changes.

Install by hand

Do the five steps below in order. Each step states what to do, the result to expect and where to look when the result differs. The examples use a local Ollama; OpenAI and Anthropic are covered in step 3.

Step 1 · Add the dependencies

Add these four things to your build file.

  1. The CONTEXA starter (ai.ctxa:spring-boot-starter-contexa), which brings the five CONTEXA modules.
  2. Spring Security (spring-boot-starter-security)
  3. At least one Spring AI provider starter, which connects the chat model.
  4. The PgVector starter and the Spring AI BOM

The starter does not bring items 2 to 4, so your application declares them. The starter alone changes nothing in your application; @EnableAISecurity in step 4 is the decision to apply security. The examples below are Gradle (Groovy) and Maven; Gradle (Kotlin DSL) is in the quick start.

dependencies {
    implementation 'ai.ctxa:spring-boot-starter-contexa:0.1.1'
    implementation 'org.springframework.boot:spring-boot-starter-security'
    implementation platform('org.springframework.ai:spring-ai-bom:1.1.8')
    implementation 'org.springframework.ai:spring-ai-starter-model-ollama'          // or -openai, -anthropic
    implementation 'org.springframework.ai:spring-ai-starter-vector-store-pgvector'
}
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.ai</groupId>
      <artifactId>spring-ai-bom</artifactId>
      <version>1.1.8</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<dependencies>
  <dependency>
    <groupId>ai.ctxa</groupId>
    <artifactId>spring-boot-starter-contexa</artifactId>
    <version>0.1.1</version>
  </dependency>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
  </dependency>
  <dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-model-ollama</artifactId>
  </dependency>
  <dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-vector-store-pgvector</artifactId>
  </dependency>
</dependencies>

Spring AI BOM 1.1.8 is the version CONTEXA is built and tested with, the same BOM the starter exports.

Expected result. Check that the dependencies resolve with ./gradlew dependencies for Gradle or mvn dependency:tree for Maven. There is no error, and spring-boot-starter-contexa appears in the list. This step alone does not change how your application behaves.

If the result differs. When the ai.ctxa dependency is not found, check that your repositories include mavenCentral() (Troubleshooting).

Step 2 · Create the dedicated database

CONTEXA keeps its tables in a dedicated database, not in your application's database. The dedicated database holds users, roles, policies, decision records, audit records and system settings, and the vector store is created there as well. With a PostgreSQL administrator account, create the account and the database and turn on the vector extension.

CREATE USER contexa WITH PASSWORD 'change-me';
CREATE DATABASE contexa OWNER contexa;
\c contexa
CREATE EXTENSION IF NOT EXISTS vector;

Know these points about the dedicated database.

  • CONTEXA creates its tables on the first start. When your application starts, CONTEXA creates and verifies its tables, so you do not create them. Its schema begins by creating the vector extension, so if the account cannot create extensions, create the extension beforehand as in the SQL above.
  • Use a clean database. On a database where only some CONTEXA tables exist, the startup stops without changing anything.
  • Using the same address as your application database is blocked by default. To use the same address you must set both contexa.datasource.isolation.allow-shared-application-datasource=true and contexa.datasource.isolation.shared-application-datasource-risk-accepted=true. It is refused anyway under the prod or production profile.
  • Where the vector table lives: CONTEXA creates the vector table (ctxa_vector_store) itself, in the dedicated CONTEXA database (contexaJdbcTemplate). Spring AI's PgVector starter is only the dependency that brings the classes; your application's default database connection and your application's VectorStore bean are not used. So the vector extension is needed in the dedicated CONTEXA database. CONTEXA sets a default (contexa.vectorstore.pgvector.initialize-schema=true) so that the first start creates that extension and the table.
  • If your application has no database connection of its own: the starter brings JPA, so Spring Boot tries to create your application's default database connection. With FULL, where CONTEXA owns sign-in, the CONTEXA database becomes your application's default connection and nothing else is needed. When your application owns sign-in, set a separate address for your application (spring.datasource.url).

Expected result. The last SQL command ends without an error. CONTEXA tables do not exist yet at this point, and that is normal. They are created when you first start the application after step 4.

If the result differs. When creating the extension fails, PostgreSQL has no pgvector installed or the account may not create extensions (Troubleshooting).

Step 3 · Minimal application.yml

In your application's application.yml, set the dedicated CONTEXA database and the AI models. The one value you must set is the dedicated database address (contexa.datasource.url). Choose the AI models for the provider you use. The example below uses a local Ollama.

spring:
  datasource:                        # your application's default database (keep it if you have one)
    url: jdbc:postgresql://localhost:5432/myapp
    username: myapp
    password: ${MYAPP_DB_PASSWORD}

contexa:
  datasource:                        # dedicated Contexa database (required)
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
  llm:
    selection:
      chat:
        priority: ollama
      embedding:
        priority: ollama
    chat:
      ollama:
        base-url: http://localhost:11434
        model: qwen3:8b
        keep-alive: 30m
    embedding:
      ollama:
        model: mxbai-embed-large

With Ollama, download both models first: ollama pull qwen3:8b, ollama pull mxbai-embed-large. The names you pull must match the model values in the settings.

For OpenAI, add spring-ai-starter-model-openai in step 1 and put the API key in the Spring AI settings (there are no provider key settings under contexa.llm). CONTEXA does not set the OpenAI embedding model; it follows your application's. With no model named, Spring AI uses text-embedding-ada-002 (1536 dimensions). To use another one, set spring.ai.openai.embedding.options.model; the vector dimension follows it.

spring:
  ai:
    openai:
      api-key: ${OPENAI_API_KEY}
contexa:
  llm:
    selection:
      chat:
        priority: openai
      embedding:
        priority: openai

For Anthropic, add spring-ai-starter-model-anthropic, set spring.ai.anthropic.api-key, and set contexa.llm.selection.chat.priority: anthropic. Anthropic has no embedding model, so add an OpenAI or Ollama provider for embeddings (contexa.llm.selection.embedding.priority is openai or ollama).

Every model connection setting is in the configuration guide.

Start a first installation in the observation mode. When you do not set the operating mode (contexa.security.zerotrust.mode), CONTEXA runs in the enforcement mode (ENFORCE), and AI decisions apply to real requests. The observation mode (SHADOW) makes and records decisions but blocks no request. The CLI starts in SHADOW. To start the same way after a manual installation, add the setting below. How to move to the enforcement mode after you review the results is in Start Safely in Shadow Mode.

contexa:
  security:
    zerotrust:
      mode: SHADOW

Expected result. CONTEXA reads these settings for the first time when you start the application after step 4. With Ollama, run ollama list now to confirm that both models are downloaded.

If the result differs. When the start prints contexa.datasource.url must be configured for @EnableAISecurity, the dedicated database address is missing (Troubleshooting). For model and vector store errors, see Model and vector store errors.

Step 4 · Add @EnableAISecurity

Add @EnableAISecurity to the main class and CONTEXA turns on. Without it, none of CONTEXA's auto-configuration applies, even when the starter is on the classpath.

@EnableAISecurity                      // default SANDBOX: your application keeps owning sign-in
@SpringBootApplication
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}

To leave sign-in to CONTEXA use @EnableAISecurity(mode = SecurityMode.FULL). What changes is in Add to an existing Spring Security application, and all annotation attributes are in the @EnableAISecurity reference. With the default way, where your application owns sign-in, you must do the next section, Connect your existing sign-in.

Expected result. Start the application (./gradlew bootRun or mvn spring-boot:run). When the startup log shows [IamSeedData] OSS schema provenance verified., CONTEXA is connected to the dedicated database and its tables are ready. On a first start, CONTEXA creates the tables just before this line.

If the result differs. When the start is refused, the console prints the cause (Description) and the fix (Action) together. The errors seen most often are in Common errors on the first start.

Step 5 · Put @Protectable on the methods to protect

@Protectable is the annotation that marks a method to be protected with AI decisions. When a signed-in user calls the method, CONTEXA analyzes that request. Methods and URLs without the annotation are not analyzed; they only receive the decision already stored for the user.

@Protectable
@GetMapping("/api/customers")
public List<Customer> getCustomers() { ... }
  • With @Protectable(sync = true) the decision is made inside that call and applied right away. The response takes longer by that time.
  • An agent request with no decision on record is decided in place even on an asynchronous method (Agent security).
  • All attributes and the policy link are in the @Protectable reference; how a decision is made is in Decision engine.

Expected result. Start the application again and call this method as a signed-in user. After a short time, a decision appears in the decision records of the admin console. The procedure is in Check the first decision.

If the result differs. The reasons a decision does not appear are listed at the end of Check the first decision.

Connect your existing sign-in (when your application owns sign-in)

You need this section only in the default way (SANDBOX, authentication ownership HOST_OWNED), where your application owns sign-in. Skip it with FULL, where CONTEXA owns sign-in. With FULL, an application that declares its own SecurityFilterChain is refused at startup.

By default CONTEXA builds no sign-in chain. Sign-in, sessions, cookies and access rules stay with your application's Spring Security, and CONTEXA only reads the result of your sign-in (the authentication bridge). CONTEXA's filters, which run right after your chain, apply its decisions on every path. CONTEXA protects its admin console /contexa/admin/** itself, with a chain of its own and CONTEXA's administrator sign-in. So your application must do these two things.

  1. Declare your own SecurityFilterChain. Without it Spring Boot's default security applies and every request asks for sign-in; CONTEXA reports this with a WARN log at startup. With no users of your own either, the start is refused.
  2. Put the signed-in user into the SecurityContext as an authenticated Authentication, in a filter of that chain. CONTEXA reads this value to learn whose request it is. @Protectable methods refuse calls without it or with an anonymous one in the SHADOW and ENFORCE modes (ENFORCE is the default); under DISABLED and OBSERVE they do not refuse, and the method policies decide on what the security context holds. A legacy user object kept only in the session is not proof of authentication. When the user is set later (in an MVC interceptor or a controller), CONTEXA's filters do not see it, so decisions are applied for those requests only at @Protectable methods, and a WARN says so once.

The simplest chain is below. Your existing rules and filters keep protecting your pages.

@Configuration
public class HostSecurityConfig {

    @Bean
    public SecurityFilterChain hostSecurityFilterChain(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth -> auth
                // your pages stay protected by your existing rules and filters
                .anyRequest().permitAll());
        return http.build();
    }
}

Spring Security's defaults (CSRF protection, security response headers and so on) apply to this chain too, so adjust whatever differs from your existing behavior. CONTEXA's startup diagnostic names anyRequest().permitAll() as an example when no chain exists. That is safe for CONTEXA's paths, because the admin console is protected by CONTEXA's own chain and CONTEXA's user pages (decision screens, step-up, agent confirmations) answer only a signed-in user. Method security (@EnableMethodSecurity) is optional: when you turn it on, the @PreAuthorize on the admin console's controllers adds one more check.

Expected result. When you start the application, the startup log shows neither of these two WARN lines. Both are in the log table of Check that it is on.

  • [Contexa] HOST_OWNED mode: no SecurityFilterChain is declared ...: item 1 was not done.
  • [Contexa] HOST_OWNED: the application sets the signed-in user after Spring Security's filters ...: item 2 was not done in a filter of the chain.

If the result differs. When every request asks for sign-in, see the matching entry in Troubleshooting. When saving a form is refused with 403, see the CSRF entry.

When you have a legacy session object

Use this when your application stores the signed-in user object in the session itself. The authObjectLocation, authObjectAttribute and authObjectType attributes of @EnableAISecurity only tell the bridge where to look first for the user object, and its attribute name and type. They do not connect sign-in, so item 2 above (an authenticated Authentication) is still needed.

@EnableAISecurity(
    authObjectLocation = AuthObjectLocation.SESSION,   // AUTO (default), SESSION, REQUEST_ATTRIBUTE, HEADER
    authObjectAttribute = "loginUser"                  // legacy session attribute name
)
@SpringBootApplication
public class LegacyApplication { }

AUTO and SESSION look in the session, then request attributes, then headers; REQUEST_ATTRIBUTE looks in request attributes first; HEADER looks in headers first. Values read from the session, request attributes or headers are used as authorization and delegation evidence. The reference for these attributes is the @EnableAISecurity reference; how to pass your session object's authentication information to CONTEXA, and more, is in Connect your existing sign-in (authentication bridge).

Check that it is on

Start the application and check three things in order.

  1. The startup log: shows whether CONTEXA is on.
  2. The capability check: shows whether every part that decisions need was created (Capability check).
  3. The first decision: call a protected method and see whether a decision is recorded in the admin console (Check the first decision).

Until the first two checks pass, the third may show no decision. Start the application (./gradlew bootRun) and look for these lines in the startup log. When all is well, the INFO lines appear. For a WARN or ERROR line, follow the guidance in its row.

Capability check

The capability check is the check CONTEXA runs when the startup finishes, to see that every part decisions need was created. The parts are the chat model llm-runtime, the embedding model embedding-runtime, the vector store rag-vector, learning security-learning, the decision engine autonomous-decision and the bridge bridge. contexa.capability.mode sets how strict the check is.

ValueBehavior
AUTO (default)FAIL_FAST for an application owned by CONTEXA, otherwise WARN. An application owned by CONTEXA has contexa.datasource.isolation.contexa-owned-application=true, or a spring.application.name that starts with contexa-.
WARNReports missing required parts with ERROR logs only and keeps starting. Shows only what your application can fix (chat and embedding models, vector store, decision strategy).
FAIL_FASTStops the startup with Contexa required capability check failed. when a required part is missing.
STRICTLogs every missing part, optional ones too, and stops when a required part is missing.
OFFNo check.

With Spring Boot Actuator on the classpath the same result is available from the endpoint contexacapabilities (GET /actuator/contexacapabilities). To open it over the web, add it to Spring Boot's management.endpoints.web.exposure.include. To turn the endpoint off, set contexa.capability.expose-diagnostics-endpoint: false.

curl http://localhost:8080/actuator/contexacapabilities

Expected result. In the response, mode is the check mode in force and capabilities holds the result for each part. When nothing is wrong, the status of each required part is ACTIVE. DEGRADED, INACTIVE_UNEXPECTED and FAILED mean a problem, and that part also shows its reason (reason) and its missing beans (missingBeans).

If the result differs. With no chat model or no vector store, no decision is made and requests stay in analysis pending (PENDING_ANALYSIS). The fix for each cause is in Troubleshooting.

First sign-in

You sign in to the admin console with a CONTEXA administrator account. It is separate from your application's user accounts and lives in the dedicated CONTEXA database. How the account is prepared depends on how you installed.

  • Installed with the CLI: the CLI makes a password for admin, keeps it in ~/.contexa/credentials.properties and shows it on the last screen. Sign in with that password. The example application uses the sample accounts below.
  • Installed by hand: a first start on a database without user accounts makes CONTEXA add five sample accounts (admin, manager, developer, user and finance, all with the password 1111) and log Sample accounts were added ... (WARN). Sign in at /contexa/admin/login as admin / 1111, then change the password at once with "Change password" in the console header.

Settings decide whether the sample accounts are added. With contexa.iam.seed.admin.password set, or contexa.iam.seed.accounts.enabled=false, the sample accounts are not added. A database that has accounts gets nothing, and the start log says so (INFO). In production, set one of the two so that no account with a shared password is created.

One-time codes in development and in production

A one-time code is a sign-in code that CONTEXA sends to the user's mail. The user enters it in two cases.

  • When CONTEXA owns sign-in (FULL): at the second step after the password. A passkey also works.
  • When your application owns sign-in (HOST_OWNED): at CONTEXA's step-up screen when the decision is CHALLENGE (additional authentication). The admin-console sign-in (/contexa/admin/login) of an application that owns sign-in asks for the password only.

How you receive the code differs between development and production.

  • Development and tests: with a local, dev, development or test profile, or without a mail server, the code is written to the start log (the console) as well: [OTT] Sign-in code for admin <admin@localhost>: .... Enter it and the sign-in finishes, even when no mail server answers. With the local mail inbox (Mailpit) the CLI prepares, the same code arrives by mail too: SMTP 127.0.0.1:51025 without a sign-in, the mails at http://127.0.0.1:58025.
  • Production: start without a development profile and set spring.mail.* to your mail server. Codes go by mail only. Once the application is ready, CONTEXA connects to the mail server once. When the connection works it logs [Contexa] One-time sign-in codes are mailed through host:port (INFO); when it fails it logs the reason and what to set (WARN).
# Development: the local mail inbox (Mailpit)
spring:
  mail:
    host: localhost
    port: 51025
    properties:
      mail:
        smtp:
          auth: false

# Production: your mail server (for example 587 with STARTTLS)
spring:
  mail:
    host: smtp.example.com
    port: 587
    username: ${SPRING_MAIL_USERNAME}
    password: ${SPRING_MAIL_PASSWORD}
    properties:
      mail:
        smtp:
          auth: true
          starttls:
            enable: true

contexa.auth.ott.code-to-console decides whether codes go to the log as well. Unset, the rule above applies; set it to false to be sure a production start mails them only.

Look in the admin console

The admin console is CONTEXA's operations screen. Sign in with the CONTEXA administrator account described above, and check the installation on these screens.

ScreenPathWhat you see
Zero Trust → Overview/contexa/admin/zero-trustProtection coverage and the period's decisions, which build up after @Protectable calls
Zero Trust → Decisions/contexa/admin/zero-trust/decisionsEach decision and its reason
Zero Trust → Adoption/contexa/admin/zero-trust/adoptionWhether moving to ENFORCE is advisable (Where to look at the results)
System settings/contexa/admin/system-settingsThe operating mode and more (applied without restart when saved)
  • The Zero Trust console opens only when the signed-in user's authorities include ROLE_ADMIN. When your application owns sign-in, the admin console signs in CONTEXA's own administrator accounts (users in the CONTEXA database with the ADMIN role) at /contexa/admin/login, apart from your users; your application's users cannot enter it. CONTEXA creates the first administrator at the first start from contexa.iam.seed.admin.username, contexa.iam.seed.admin.password and contexa.iam.seed.admin.email (none without the password; contexa init sets the password for you, by hand see the example in Admin Console). The console's sign-out ends only the console sign-in; your application's sign-in stays.
  • The sample accounts (five, including admin, with a shared password) are for local trials, so a production environment must not get them. With contexa.iam.seed.accounts.enabled: true, CONTEXA adds them to a database without user accounts even when an administrator password is set; with false it does not add them. Under HOST_OWNED they sign in at the console's own form /contexa/admin/login. Under CONTEXA_OWNED (FULL) that address leads to the CONTEXA sign-in page /mfa/login, where a second step after the password (a code by mail or a passkey) is required, so a mail server is needed.

Check the first decision

Call a protected method and confirm that the decision for that call is recorded in the admin console. By default the analysis runs after the method finishes, so the decision appears after the AI model answers, not at the moment of the call.

  1. Sign in to your application with an ordinary user account. In the SHADOW and ENFORCE modes a call without a sign-in is refused, so the user must be signed in. The example application the CLI creates uses a sample account.
  2. Call the method that got @Protectable in step 5. For example, open /api/customers in the signed-in browser.
  3. Sign in to the admin console /contexa/admin as the CONTEXA administrator admin.
  4. Open Zero Trust → Decisions (/contexa/admin/zero-trust/decisions). A row for the user who just made the call appears, with the decision and its reason. The decision is ALLOW, CHALLENGE (additional authentication), ESCALATE (held for review) or BLOCK. When you do not see it, reload the screen after a moment.

In the enforcement mode (the default), the decision applies from that user's next request. When the first decision is CHALLENGE, ESCALATE or BLOCK, the user's next request is restricted. For a first check, keeping the observation mode (SHADOW) is safer: it records decisions and blocks no one (Start Safely in Shadow Mode).

When no decision appears in the decision records, check these in order.

  • Sign-in: a call without a sign-in is refused and not analyzed.
  • Operating mode: with DISABLED nothing is analyzed. A mode saved in the admin console takes precedence over the settings file, so check both contexa.security.zerotrust.mode and /contexa/admin/system-settings.
  • Required parts: without a chat model or a vector store no decision is made. See the [ContexaCapability] ERROR in the startup log and the capability check above.
  • AI model connection: the analysis fails when Ollama is not running, a model was not downloaded, or an API key is wrong. See the failures by kind in Zero Trust → Operations (/contexa/admin/zero-trust/operations).
  • Where the call came from: a call on a thread that holds neither a web request nor a user (a scheduled job, for example) has no user to decide for. The method runs and the run is recorded.
  • Administrator authority: only a CONTEXA administrator account with ROLE_ADMIN can open the admin console.

More causes are in Decisions keep not appearing in Troubleshooting.

Moving to a distributed deployment

Do this in a production environment that runs several instances, or that must keep learned state across restarts. For development or a single server, keep the default (standalone). Set the infrastructure mode to distributed and add the Redis, Redisson and Kafka dependencies and connection settings to your application. The CONTEXA modules do not bring them.

implementation 'org.springframework.boot:spring-boot-starter-data-redis'
implementation 'org.redisson:redisson'          // your application picks the version
implementation 'org.springframework.statemachine:spring-statemachine-data-redis'  // the starter sets the version
implementation 'org.springframework.kafka:spring-kafka'
contexa:
  infrastructure:
    mode: distributed
spring:
  data:
    redis:
      host: localhost
      port: 6379
  kafka:
    bootstrap-servers: localhost:9092

The decision store and learned state go to Redis, security events to Kafka, and block signals spread through Redisson. What changes is in Infrastructure mode.

Expected result. The [Contexa] contexa.infrastructure.mode is standalone: ... warning disappears from the startup log.

If the result differs. When one of spring-boot-starter-data-redis, org.redisson:redisson and spring-statemachine-data-redis is missing, the start is refused. When your application owns sign-in and Redis cannot be reached, CONTEXA retries for 5 seconds, then the application starts without CONTEXA and logs the ERROR Contexa's Redis cannot be reached. Fix the connection settings and restart the application.
