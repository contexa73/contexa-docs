Installation Overview

CONTEXA needs four things in your Spring Boot application: the starter dependency, the @EnableAISecurity annotation on the main class, a dedicated CONTEXA database, and an AI model. Two choices remain at installation: whether to install with the CLI or by hand, and whether your application keeps handling sign-in or leaves it to CONTEXA.

What you need, and the order to turn it on

Adding the starter dependency alone changes nothing in your application and does not turn CONTEXA on. CONTEXA turns on when you add @EnableAISecurity to the main class. A running CONTEXA does not start without its dedicated database. Without an AI model and a vector store (the store used to find similar past decision records) the application starts but no decision is made.

Once the annotation is present, CONTEXA protects requests through Spring Security, so your application must declare the org.springframework.boot:spring-boot-starter-security dependency itself. The starter leaves it out on purpose. Spring Boot asks every request to sign in once Spring Security is present, so if the starter included it, adding the starter alone would change your application (What the starter brings and what it does not).

When CONTEXA does not turn on. Without @EnableAISecurity on the main class, none of CONTEXA's features applies, even with the starter present. With the annotation present, setting contexa.enabled: false keeps everything off.

Choose an installation method

Both ways end in the same state: the dependencies are in your build file, @EnableAISecurity is on the main class, and the CONTEXA settings are in a configuration file. If you have no database or AI model yet, the CLI is faster, because it prepares both locally. Install by hand when you have already chosen your database and model, or when you use a managed cloud database.

Decide who handles sign-in

CONTEXA makes the decisions and applies them to every request in either case. What you choose is whether your application keeps handling sign-in (the login pages, sessions, cookies and URL permission rules) or leaves it to CONTEXA. The default is that your application keeps it, and an application that already has sign-in uses this. The same choice appears under two names. In the mode of @EnableAISecurity it is the security mode (SANDBOX or FULL); in the setting contexa.bridge.ownership it is the authentication ownership (HOST_OWNED or CONTEXA_OWNED).

If you set contexa.ai.security.mode, that value is used instead of the annotation's mode. A contexa.bridge.ownership you set must match the mode. CONTEXA_OWNED with SANDBOX, or HOST_OWNED with FULL, makes the startup refuse, and the message says what to change.

Without a chat model or a vector store no decision is made. CONTEXA cannot make decisions, so every protected request stays in "analysis pending" (PENDING_ANALYSIS). The application still starts without an error, which makes this easy to miss. Look in the startup log for the capability lines that begin with [ContexaCapability]; they name what is missing (Check that it is on). If running without decisions is intended, set the operating mode to off (contexa.security.zerotrust.mode=DISABLED).

When the startup stops or CONTEXA stays off

When something on this list is missing, CONTEXA reacts in one of three ways. The console output or the startup log tells you which.

  • The startup is refused. This happens with Spring Boot 4.x, without Spring Security, with WebFlux or AOT processing, with an empty contexa.datasource.url (or the same address as your application's database), with the distributed mode and no Redis libraries, and with a mode and an ownership setting that contradict each other. The console prints the cause (Description) and what to change (Action) together.
  • The application starts and only CONTEXA stays off. This happens when your application owns sign-in (HOST_OWNED) and CONTEXA's database or Redis has a problem: CONTEXA retries for 5 seconds and then gives up. The problem is one of these:
    • CONTEXA's database cannot be reached.
    • Its account cannot create an extension CONTEXA needs (such as vector).
    • The Redis of the distributed mode cannot be reached.
    The application then behaves as it did before you added CONTEXA, and the log gets an ERROR line (Contexa's database cannot be used or Contexa's Redis cannot be reached). Fix the problem and restart the application. When CONTEXA owns sign-in (CONTEXA_OWNED), nobody could sign in without it, so a database problem makes the startup fail instead.
  • The application starts but no decision is made. A chat model or a vector store is missing. Check the capability lines described in the warning above.

Dependency coordinates

Released versions are published to Maven Central under the ai.ctxa group. The only CONTEXA dependency your application declares is the single starter, together with spring-boot-starter-security as explained above. No repository other than mavenCentral() is needed. The AI provider starter and the PgVector starter are not in the declarations below; add them separately (see the table that follows).

implementation("ai.ctxa:spring-boot-starter-contexa:0.1.1")
implementation("org.springframework.boot:spring-boot-starter-security")
<dependency>
    <groupId>ai.ctxa</groupId>
    <artifactId>spring-boot-starter-contexa</artifactId>
    <version>0.1.1</version>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>

With the dependency only

  • Without @EnableAISecurity on the main class, none of CONTEXA's auto-configurations applies. No CONTEXA filter, authentication provider or database table is created.
  • The starter does not bring Spring Security. An application that did not use Spring Security stays as it was: no security chain appears and no request asks for sign-in.
  • CONTEXA creates and checks its database tables in the dedicated database when an application with CONTEXA turned on starts. An empty database gets the tables; a database that holds only some of them is refused. The CLI does not create tables, so you prepare none during installation.

Infrastructure mode: where state is kept

contexa.infrastructure.mode decides where CONTEXA keeps its state: each user's current decision and what CONTEXA has learned. The values are standalone (default) and distributed, in any letter case. standalone keeps state in the memory of the application process, so it needs no Redis or Kafka, but the state is lost on restart. It fits development and a single server. distributed uses Redis and Kafka, so several instances see the same state and learning continues after a restart.

In standalone CONTEXA does not connect to Redis or Kafka. If your application uses Redis itself, it keeps its own Redis connection: it wrote its own connection settings (for example spring.data.redis.host), or one of its classes uses Spring Data Redis or Redisson. Otherwise Spring Boot's Redis auto-configurations are left out. Spring Boot's Kafka auto-configurations stay exactly as your application has them without CONTEXA. To run several instances or to keep learning across restarts, use distributed (Moving to a distributed deployment).

Modules

Your application declares only the starter; you do not pick modules. What actually turns on follows the activation conditions described above and your settings.
