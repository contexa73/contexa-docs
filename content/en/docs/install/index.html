Installation Overview

What you need to turn Contexa on in your Spring Boot application, and which way to install it. This page covers the prerequisites, who owns sign-in, the dependency coordinates, and where state is kept (the infrastructure mode).

At a glance

Adding the dependency does not turn Contexa on. It turns on when you put @EnableAISecurity on the main class; once on, it needs a dedicated Contexa database to start, and an AI model and a vector store to produce decisions.

How on and off are decided. At startup @EnableAISecurity puts an activation marker (contexa.ai.security.mode) into the configuration, and Contexa uses its auto-configuration only when that marker is present. Without the annotation every Contexa auto-configuration is left out. Conversely, with contexa.enabled: false nothing is turned on even with the annotation.

Choose how to install

Both ways end in the same place: the dependencies are in your build file, @EnableAISecurity is on the main class, and the Contexa settings are in application.yml.

Who owns sign-in

The mode of @EnableAISecurity sets the default for who owns sign-in. It becomes the authentication ownership (contexa.bridge.ownership); when you set the ownership in the configuration yourself, your value wins.

Security modeAuthentication ownershipSign-in and security chainWhen
SANDBOX (default)HOST_OWNEDYour application's Spring Security keeps sign-in, sessions, cookies and URL rules; Contexa only reads who signed in. Contexa still decides and enforces on every path: its filters run right after your chain, a CHALLENGE goes to Contexa's step-up (/contexa/step-up), the agent request gate works, and Contexa protects its admin console (/contexa/admin/**) with its own administrator sign-in.An existing system that already has sign-in
FULLCONTEXA_OWNEDContexa builds sign-in (form, passkey, one-time-token MFA) and the security chain. The request-time enforcement filters and the agent request gate work as under HOST_OWNED; a CHALLENGE goes to Contexa's MFA.A new system that leaves sign-in to Contexa

With the CLI you do not have to choose by hand: contexa init picks HOST_OWNED when your application declares a SecurityFilterChain and CONTEXA_OWNED when it declares none, shows the choice before it changes anything, and takes --ownership host|contexa to choose otherwise (How the CLI chooses).

The full table of what works under each ownership is in Add to an existing Spring Security application.

Dependency coordinates

Stable versions are published to Maven Central under the ai.ctxa group. The entry point is the single starter, and no repository other than mavenCentral() is needed.

implementation("ai.ctxa:spring-boot-starter-contexa:0.1.1")
<dependency>
    <groupId>ai.ctxa</groupId>
    <artifactId>spring-boot-starter-contexa</artifactId>
    <version>0.1.1</version>
</dependency>

With the dependency only

  • Without @EnableAISecurity every Contexa auto-configuration is left out, so no Contexa filter, authentication provider or table is created.
  • The starter does bring Spring Security, so an application that did not use Spring Security gets Spring Boot's default security chain (every request asks for sign-in).
  • The Contexa tables are created and verified in the Contexa database when an application with Contexa turned on starts. The CLI does not create tables.

Infrastructure mode

contexa.infrastructure.mode decides where decision and learning state is kept. The values are standalone (default) and distributed, in any letter case.

Whatstandalone (default)distributed
Per-user decision storeMemoryRedis
Learning state such as behavioral baselines and context recordsMemory (lost on restart)Redis
Security event deliveryMemoryKafka
Block signal propagationMemoryRedisson
MFA sessionHTTP sessionRedis
Dependencies your application addsNonespring-boot-starter-data-redis, Redisson, spring-kafka (with the Redis and Kafka connection settings)
Startup logOne WARN line saying the learned state is kept in memory and lost on restartNone

In standalone the Contexa Redis and Kafka auto-configurations are not used. Spring Boot's Redis and Kafka auto-configurations are left out too, unless your application wrote its own connection settings (for example spring.data.redis.host or spring.kafka.bootstrap-servers). Use distributed to run several instances or to keep learning across restarts (Moving to a distributed deployment).
