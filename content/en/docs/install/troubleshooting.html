Troubleshooting

Find the errors you meet when installing Contexa and starting it for the first time by their message, and fix them. The order is CLI install and init errors, application startup errors, model and vector store errors, and dependency errors.

Look here first

Contexa works when the JDK, the dedicated database, the AI models and (optionally) Docker all fit together. When something goes wrong, look at two places first.

  • The application's startup log: the lines Contexa writes and what they mean are in Check that it is on. Look especially for the ERROR-level [ContexaCapability] and [Contexa] lines.
  • Connection refused: when PostgreSQL or Ollama cannot be reached, check with docker ps that the containers are up and check the ports (PostgreSQL 5432, Ollama 11434), and read the Ollama log with docker logs contexa-ollama.
  • The CLI checks: contexa init --check checks only Java 17+ and Docker without changing the project, then exits. contexa doctor also checks the PostgreSQL port and the Ollama model.
contexa doctor

CLI install and init errors

The contexa command is not found

Fix: open a new terminal, check that the folder the installer named at the end is on your PATH, then run contexa --version. Instead of the script you can download the binary for your OS from the releases page and put it on your PATH.

Docker is missing or not running

Messages: x Docker CLI is not installed., x Docker daemon is not running., Docker is installed but the daemon is not running.

When: in the pre-check of contexa init (without --yes) and when creating infrastructure (--distributed, --simulate). The default init, which creates no infrastructure, only shows the pre-check result as a warning and goes on.

Fix: on Windows and macOS start Docker Desktop and wait until it is ready; on Linux run sudo systemctl start docker. To go on without Docker, run init without the infrastructure options and prepare PostgreSQL yourself (Create the dedicated database). --no-docker writes the Compose file without starting containers.

A port is already in use

Message: Port 5432 (PostgreSQL) is already in use on 127.0.0.1. followed by Local service PostgreSQL is already running on host. Contexa will skip starting this docker container and reuse the host service.

Cause: when creating infrastructure, the CLI checks PostgreSQL 5432, (with Ollama) 11434, and (distributed) Redis 6379, Zookeeper 2181 and Kafka 9092. For a port in use it does not create the container and reuses the existing service. When a container with the same name already exists, it is reused instead of created again (Existing infrastructure detected (...); reusing it.). If that container's configuration has drifted, remove it with docker rm -f <container name> and run contexa init again.

Fix: check that the service on the port is the PostgreSQL or Ollama you meant to use, and match its connection details in contexa.datasource.* and the other settings. To practice apart from existing services, use the isolated environment: container names become ctxa-sim- and ports move by +20000 (5432 → 25432, 11434 → 31434 and so on).

contexa init --simulate

An Ollama model is missing

Message (contexa doctor): Ollama Model 'qwen2.5:7b' is missing.

Fix: pull the model, and the embedding model with it.

docker exec -it contexa-ollama ollama pull qwen2.5:7b
docker exec -it contexa-ollama ollama pull mxbai-embed-large
  • The model you pull must be the model the application uses. The application's chat model is contexa.llm.chat.ollama.model (empty means qwen3:8b); in the settings the CLI writes, it is overridden by the environment variable CONTEXA_CHAT_OLLAMA_MODEL (default qwen2.5:7b). The model the CLI pulls and checks is another environment variable, OLLAMA_CHAT_MODEL (default qwen2.5:7b).
  • To use a lighter model on a small machine (for example qwen2.5:3b), set both to the same model. You can also pull it with contexa ollama pull --chat-model qwen2.5:3b (the environment variable wins when set).

What contexa reset reverts

reset keeps no install record; it reverts with the backups init made before changing files (contexa/bak/) and with fixed rules.

  • Code (-c): overwrites files with the originals from the backup, so changes you made after init are lost too. For build files and settings without a backup it removes the Contexa lines (all of contexa:, all of spring.ai and more), and removes @EnableAISecurity and its import from every Java file (even ones you added yourself). It deletes the <project>/contexa folder.
  • Infrastructure (-i): takes the project's Compose stack down and removes its containers and volumes.
  • Simulation (-s): removes the ctxa-sim stack and its volumes and reverts the code too. -a does everything.

Keep a copy of files you changed yourself before resetting.

Application startup errors

contexa.datasource.url must be configured for @EnableAISecurity

Full message: java.lang.IllegalStateException: contexa.datasource.url must be configured for @EnableAISecurity. Use a dedicated Contexa database by default; sharing the application database requires explicit POC approval.

Cause: once @EnableAISecurity is on, a dedicated Contexa database address is required.

Fix: create the dedicated database (Create the dedicated database) and set its address. In an existing application do not set contexa.datasource.isolation.contexa-owned-application: true (Minimal settings).

contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}

contexa.datasource must not share ...

Message: contexa.datasource must not share spring.datasource unless contexa.datasource.isolation.allow-shared-application-datasource=true and contexa.datasource.isolation.shared-application-datasource-risk-accepted=true are both set for an approved POC, or contexa.datasource must not share the application datasource in production profiles

Cause: contexa.datasource.url equals your application's spring.datasource.url.

Fix: keep a separate dedicated database. If you must use the same database for a trial, set both settings above to true; it is still refused under the prod and production profiles. An application owned by Contexa (contexa-owned-application: true) skips this check.

Your application has no default database connection

Message (Spring Boot): Failed to configure a DataSource: 'url' attribute is not specified and no embedded datasource could be configured.

Cause: the starter brings JPA, and while Contexa is on it does not filter out Spring Boot's database auto-configuration. When your application has neither its own database address (spring.datasource.url) nor an embedded database, Spring Boot cannot create your application's default connection.

Fix: set a database address for your application. With @EnableAISecurity(mode = SecurityMode.FULL), where Contexa owns sign-in, the Contexa database becomes your application's default connection and this error does not occur.

Contexa schema is partially installed ...

Message: Contexa schema is partially installed without a complete ownership contract. No schema changes were applied. Restore a verified OSS backup or use a clean database.

Cause: only some Contexa tables exist in the Contexa database. Contexa does not repair such a database and stops the startup. If the tables are still incomplete after the first installation, it stops with Contexa schema is partially installed after canonical schema execution.

Fix: use a clean database or restore a verified backup. Also check that the database account can create the vector extension.

Spring Boot 4.x

Messages: Contexa does not support Spring Boot 4.x. Current version: ... (ERROR log), Spring Boot 4.x is not supported by Contexa. Current version: ... (IllegalStateException)

Fix: use Spring Boot 3.x. Contexa is built and tested with 3.5.4.

Every request asks for sign-in · HOST_OWNED mode: no SecurityFilterChain is declared

Cause: the starter brings Spring Security, so an application without its own SecurityFilterChain gets Spring Boot's default security. This happens with the starter alone too (without @EnableAISecurity). In the default way with @EnableAISecurity on (HOST_OWNED), Contexa logs [Contexa] HOST_OWNED mode: no SecurityFilterChain is declared by the application ... as an ERROR at startup.

Fix: declare your application's SecurityFilterChain. Do not stop at the anyRequest().permitAll() the log names as an example; protect the admin console /contexa/admin/** too (Connect your existing sign-in). To leave sign-in to Contexa, use contexa.bridge.ownership: CONTEXA_OWNED or mode = SecurityMode.FULL.

ERROR logs about old setting names

Message: Contexa legacy property prefix '<old prefix>*' detected. Migrate to '<new prefix>*'. Aliases will be removed in v0.3.0.

Cause: you used an old setting name outside contexa.*. It is still read under the new name for now, but an ERROR is logged once per prefix at every startup, and the aliases are to be removed in v0.3.0. If the new name already has a value, the new name's value is used. The vector store settings (spring.ai.vectorstore.pgvector.*) are on this list too; write them as contexa.vectorstore.pgvector.*.

Fix: change to the new prefix the log names. All moved names are in the configuration guide.

The contexa.infrastructure.mode is standalone warning

An expected warning (WARN) that in the default infrastructure mode (standalone) learned state lives in memory and is lost on restart. You can leave it during development. To keep learning in operation, switch to distributed.

The starter is added but there are no Contexa tables

Expected without @EnableAISecurity (the dependency only). The starter alone creates no Contexa filter, authentication provider or table. The tables are created and verified in the Contexa database when an application with Contexa turned on starts. If they are still missing after turning it on, check that contexa.iam.seed.enabled is not false and that contexa.datasource.* points at the Contexa database.

Model and vector store errors

[ContexaCapability] ... · Contexa required capability check failed.

Log format: [ContexaCapability] <capability> status=<status> required=<true|false> followed by Reason, Missing beans and Recommended actions.

Cause: when the startup finished, a part that decisions need was missing. An application that owns sign-in (WARN) logs ERRORs and keeps starting; an application owned by Contexa (FAIL_FAST: contexa-owned-application: true, FULL, or spring.application.name starting with contexa-) stops with Contexa required capability check failed.

CapabilityWhat is missingFix
llm-runtimeChat model (ChatModel)Add a Spring AI chat provider starter and set its key or address (spring.ai.*; for Ollama, contexa.llm.chat.ollama.base-url also works).
embedding-runtimeEmbedding model (EmbeddingModel)Set up OpenAI or Ollama embeddings.
rag-vectorVector store (VectorStore)Add org.springframework.ai:spring-ai-starter-vector-store-pgvector and check the database connection and the vector extension.
security-learningLearning parts after decisionsWhen the log says Resolve rag-vector first, fix rag-vector first (they need the vector store).
autonomous-decisionThe decision strategy or the decision record storeProvide a chat model and a vector store. Without them no decision strategy is created and every protected request stays pending analysis. To run without the decision engine, set contexa.autonomous.enabled: false.

Change how strict the check is with contexa.capability.mode (Capability check).

No Spring AI ChatModel is configured for CONTEXA

Message (start): No Spring AI ChatModel is configured for CONTEXA. Add at least one Spring AI chat provider starter to your application dependencies ... then configure the matching provider under spring.ai.*

Cause: a chat model bean exists, but Contexa could not build the chat client and model selection it uses. The message advises that, if the dependency is already present, you check that the provider's key or address is actually set. With no provider starter at all you get the llm-runtime capability result above instead of this message.

Fix: put provider keys in the Spring AI settings, not under contexa.llm: spring.ai.openai.api-key, spring.ai.anthropic.api-key, and for Ollama spring.ai.ollama.* or contexa.llm.chat.ollama.base-url. Set the provider order with contexa.llm.selection.chat.priority (Minimal settings).

The vector extension is missing (PostgreSQL)

Fix: use an image with pgvector (for example pgvector/pgvector:pg16), or on an existing database run this once with an account that has the privilege. Both the Contexa database and your application's default database, where the vector table is created, need it.

CREATE EXTENSION IF NOT EXISTS vector;

No decisions come out

  • Enforcement mode: with DISABLED or OBSERVE, @Protectable calls are not analyzed. A mode saved in the admin console wins over YAML, so check /contexa/admin/system-settings (startup log System runtime settings applied to AI decision mode: ...).
  • Parts: without a chat model and a vector store, requests stay pending analysis (above).
  • What is protected: what gets analyzed is @Protectable method calls. Calls without sign-in (anonymous) are refused before analysis.
  • Decisions apply from the next request: the default asynchronous methods are decided after the response, so the decision applies to the next call.

The ai.ctxa dependency is not found

The official 0.1.0 needs only mavenCentral(). Do not add Spring milestone or snapshot repositories, or the Sonatype snapshot repository, to a regular application build. Check that the coordinates are ai.ctxa:spring-boot-starter-contexa:0.1.0; right after a release, try again once the Maven Central sync has finished.
