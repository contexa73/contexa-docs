Troubleshooting

Find the errors you meet when installing Contexa and starting it for the first time by their message, and fix them. The order is CLI install and init errors, application startup errors, model and vector store errors, and dependency errors.

Look here first

Contexa works when the JDK, the dedicated database and the AI models all fit together. When something goes wrong, look at two places first.

  • The CLI check: contexa doctor checks the Spring Boot and Java versions, the starter and @EnableAISecurity, that the Contexa settings are loaded, that the Contexa database answers, Ollama and its models, and the API key, and prints the fix next to each problem.
  • The application's startup log: the lines Contexa writes and what they mean are in Check that it is on. Look especially for the ERROR-level [ContexaCapability] and [Contexa] lines.
contexa doctor

CLI install and init errors

Every contexa init error says what to do, and nothing in the project is changed (or every change is rolled back). After fixing the cause, run contexa init again.

The contexa command is not found

Fix: run the export PATH=... line the installer printed at the end, or open a new terminal (on Windows, reopen terminals that were open before the installation), then run contexa --version.

Spring Boot 4 or 3.4 and older (SPRING_BOOT_UNSUPPORTED, SPRING_BOOT_TOO_OLD)

Cause: Contexa 0.1.x needs Spring Boot 3.5.x. Projects created on start.spring.io now use Spring Boot 4, and on 3.4 and older Contexa's task executor clashes with the one Spring Boot names taskExecutor, so the application does not start.

Fix: change the Spring Boot version in the build file to 3.5.x, or run contexa init in an empty folder to get a ready Spring Boot 3.5 sample application with Contexa.

Docker is missing or not running (DOCKER_MISSING, DOCKER_STOPPED)

When: contexa init runs the local PostgreSQL (and, without a running Ollama, Ollama) in Docker.

Fix: on Windows and macOS start Docker Desktop and wait until it is ready; on Linux run sudo systemctl start docker. Interactive init offers to check again. To use a PostgreSQL with pgvector you already have instead, choose it in the question or run contexa init --db-url jdbc:postgresql://host:5432/db with the password in CONTEXA_DB_PASSWORD.

A port is already in use

Nothing to do: the local services take free ports (PostgreSQL from 55432, Ollama 11434 or from 51434, the mail inbox from 51025 and 58025) and leave services already on the default ports alone. An Ollama already running on 11434 is used as it is.

Ollama is not available or a model is missing (OLLAMA_MISSING)

Fix: install Ollama from ollama.com/download (or start Docker so Contexa can start one), or choose OpenAI with --provider openai. contexa init downloads only the models that are missing (qwen3:8b and mxbai-embed-large); when a download stops, running it again continues.

  • A lighter chat model for a small machine: set CONTEXA_OLLAMA_CHAT_MODEL (for example qwen2.5:3b) before contexa init; it downloads that model and writes it into the settings.

The Contexa starter cannot be downloaded (STARTER_UNAVAILABLE)

Cause: the project's build could not resolve ai.ctxa:spring-boot-starter-contexa through its repositories. contexa init rolled every change back.

Fix: check that the build reaches Maven Central (network, proxy, or a company repository that mirrors it), then run contexa init again (below).

Spring Boot's default user no longer signs in

Cause: Spring Boot creates its default user user (and logs Using generated security password) only while no OAuth2 classes are on the classpath. The Contexa starter brings them, so an application that signed in with that user has no user after Contexa is added. Contexa also registers a delegating password encoder, which cannot check a password without a prefix such as {noop}, so naming the user alone is not enough.

Fix: set spring.security.user.name: user and spring.security.user.password: "{noop}your-password". When the application keeps its own sign-in and has no users, OAuth2 or spring.security.user.* of its own, contexa init does this for you: it makes the password once, keeps it in ~/.contexa/credentials.properties outside the project and shows it at the end.

The admin-console account and its password

Cause: In both ownerships, contexa init makes a password for the account admin, keeps it in ~/.contexa/credentials.properties and shows it at the end; Contexa creates the account from contexa.iam.seed.admin.password when the application starts. The example application created in an empty folder uses the sample accounts (admin / 1111) instead. When your application keeps its sign-in (HOST_OWNED), this admin is still the account for the console: the console signs in Contexa's administrator at /contexa/admin/login, and your application's users cannot enter it. Without the CLI, set contexa.iam.seed.admin.* yourself (example).

Fix: read the password on the last screen of contexa init or in the line contexa.iam.seed.admin.password of that file. A password changed in the admin console stays, because an existing account is never created again. If there is no account, start the application as the same user on the same computer and look for [IamSeedData] Administrator 'admin' created in its log. When Contexa provides the sign-in, the one-time code of the second step arrives in the local inbox contexa init named.

What contexa reset reverts

reset restores exactly the files contexa init changed, using the installation record and the backups in the project's contexa/ folder (ignored by git).

  • Files: files init created are removed and changed files are put back. Changes you made after init are kept; where they overlap with Contexa's changes the file is left as it is and listed.
  • Local services: they stay for your other projects. When no project uses them any more, reset offers to remove them with their data; contexa reset --services does that without asking.
  • Data: the project's Contexa data stays in its database until the local services are removed.

Installations made by CLI 0.1.x are reverted the same way; their old Docker stack is removed when its ownership can be verified, and left alone otherwise.

Application startup errors

contexa.datasource.url must be configured for @EnableAISecurity

Full message: java.lang.IllegalStateException: contexa.datasource.url must be configured for @EnableAISecurity. Use a dedicated Contexa database by default; sharing the application database requires explicit POC approval.

Cause: once @EnableAISecurity is on, a dedicated Contexa database address is required.

Fix: create the dedicated database (Create the dedicated database) and set its address. In an existing application do not set contexa.datasource.isolation.contexa-owned-application: true (Minimal settings).

contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}

contexa.datasource must not share ...

Message: contexa.datasource must not share spring.datasource unless contexa.datasource.isolation.allow-shared-application-datasource=true and contexa.datasource.isolation.shared-application-datasource-risk-accepted=true are both set for an approved POC, or contexa.datasource must not share the application datasource in production profiles

Cause: contexa.datasource.url equals your application's spring.datasource.url.

Fix: keep a separate dedicated database. If you must use the same database for a trial, set both settings above to true; it is still refused under the prod and production profiles. An application owned by Contexa (contexa-owned-application: true) skips this check.

Your application has no default database connection

Message (Spring Boot): Failed to configure a DataSource: 'url' attribute is not specified and no embedded datasource could be configured.

Cause: the starter brings JPA, and while Contexa is on it does not filter out Spring Boot's database auto-configuration. When your application has neither its own database address (spring.datasource.url) nor an embedded database, Spring Boot cannot create your application's default connection.

Fix: set a database address for your application. With @EnableAISecurity(mode = SecurityMode.FULL), where Contexa owns sign-in, the Contexa database becomes your application's default connection and this error does not occur.

Contexa schema is partially installed ...

Message: Contexa schema is partially installed without a complete ownership contract. No schema changes were applied. Restore a verified OSS backup or use a clean database.

Cause: only some Contexa tables exist in the Contexa database. Contexa does not repair such a database and stops the startup. If the tables are still incomplete after the first installation, it stops with Contexa schema is partially installed after canonical schema execution.

Fix: use a clean database or restore a verified backup. Also check that the database account can create the vector extension.

Spring Boot 4.x

Messages: Contexa does not support Spring Boot 4.x. Current version: ... (ERROR log), Spring Boot 4.x is not supported by Contexa. Current version: ... (IllegalStateException)

Fix: use Spring Boot 3.5.x. Contexa is built and tested with 3.5.4.

Every request asks for sign-in · HOST_OWNED mode: no SecurityFilterChain is declared

Cause: your application added spring-boot-starter-security but declares no SecurityFilterChain of its own, so Spring Boot's default security applies. The starter does not bring Spring Security, so the starter alone does not cause it. In the default way with @EnableAISecurity on (HOST_OWNED), Contexa logs [Contexa] HOST_OWNED mode: no SecurityFilterChain is declared by the application ... as a WARN at startup, and refuses to start when the application has no user to sign in either (UserDetailsService, AuthenticationProvider or AuthenticationManager), because nobody could sign in.

Fix: declare your application's SecurityFilterChain (Connect your existing sign-in). The anyRequest().permitAll() the log names as an example is safe for Contexa's paths: the admin console /contexa/admin/** is protected by Contexa's own chain and administrator sign-in, so your chain does not need to protect it. Keep your own pages protected as before. To leave sign-in to Contexa, use contexa.bridge.ownership: CONTEXA_OWNED or mode = SecurityMode.FULL (with the CLI, contexa init --ownership contexa).

Old setting names have no effect

Symptom: a setting written under an old name outside contexa.*, such as security.zerotrust.*, spring.auth.* or spring.ai.security.*, has no effect, and nothing is logged about it.

Cause: the aliases of the old names are gone. Contexa treats those names as your application's own settings and neither reads nor moves them, so the value is silently ignored (the exception is security.plane.kafka.group-id of the Kafka listener group). The vector store settings (spring.ai.vectorstore.pgvector.*) do not reach Contexa's store either; write them as contexa.vectorstore.pgvector.*.

Fix: change to the new prefix. All moved names are in the configuration guide.

The contexa.infrastructure.mode is standalone warning

An expected warning (WARN) that in the default infrastructure mode (standalone) learned state lives in memory and is lost on restart. You can leave it during development. To keep learning in operation, switch to distributed.

The starter is added but there are no Contexa tables

Expected without @EnableAISecurity (the dependency only). The starter alone creates no Contexa filter, authentication provider or table. The tables are created and verified in the Contexa database when an application with Contexa turned on starts. If they are still missing after turning it on, check that contexa.iam.seed.enabled is not false and that contexa.datasource.* points at the Contexa database.

Model and vector store errors

[ContexaCapability] ... · Contexa required capability check failed.

Log format: [ContexaCapability] <capability> status=<status> required=<true|false> followed by Reason, Missing beans and Recommended actions.

Cause: when the startup finished, a part that decisions need was missing. An application that owns sign-in (WARN) logs ERRORs and keeps starting; an application owned by Contexa (FAIL_FAST: contexa-owned-application: true, FULL, or spring.application.name starting with contexa-) stops with Contexa required capability check failed.

CapabilityWhat is missingFix
llm-runtimeChat model (ChatModel)Add a Spring AI chat provider starter and set its key or address (spring.ai.*; for Ollama, contexa.llm.chat.ollama.base-url also works).
embedding-runtimeEmbedding model (EmbeddingModel)Set up OpenAI or Ollama embeddings.
rag-vectorVector store (VectorStore)Add org.springframework.ai:spring-ai-starter-vector-store-pgvector and check the database connection and the vector extension.
security-learningLearning parts after decisionsWhen the log says Resolve rag-vector first, fix rag-vector first (they need the vector store).
autonomous-decisionThe decision strategy or the decision record storeProvide a chat model and a vector store. Without them no decision strategy is created and every protected request stays pending analysis. To run without decisions, set contexa.security.zerotrust.mode: DISABLED (contexa.autonomous.enabled: false turns off all of Contexa, not only the decisions).

Change how strict the check is with contexa.capability.mode (Capability check).

No Spring AI ChatModel is configured for CONTEXA

Message (start): No Spring AI ChatModel is configured for CONTEXA. Add at least one Spring AI chat provider starter to your application dependencies ... then configure the matching provider under spring.ai.*

Cause: a chat model bean exists, but Contexa could not build the chat client and model selection it uses. The message advises that, if the dependency is already present, you check that the provider's key or address is actually set. With no provider starter at all you get the llm-runtime capability result above instead of this message.

Fix: put provider keys in the Spring AI settings, not under contexa.llm: spring.ai.openai.api-key, spring.ai.anthropic.api-key, and for Ollama spring.ai.ollama.* or contexa.llm.chat.ollama.base-url. Set the provider order with contexa.llm.selection.chat.priority (Minimal settings).

The vector extension is missing (PostgreSQL)

Fix: use an image with pgvector (for example pgvector/pgvector:pg16), or on an existing database run this once with an account that has the privilege. Both the Contexa database and your application's default database, where the vector table is created, need it.

CREATE EXTENSION IF NOT EXISTS vector;

No decisions come out

  • Enforcement mode: with DISABLED or OBSERVE, @Protectable calls are not analyzed. A mode saved in the admin console wins over YAML, so check /contexa/admin/system-settings (startup log System runtime settings applied to AI decision mode: ...).
  • Parts: without a chat model and a vector store, requests stay pending analysis (above).
  • What is protected: what gets analyzed is @Protectable method calls. Calls without sign-in (anonymous) are refused before analysis.
  • Decisions apply from the next request: the default asynchronous methods are decided after the response, so the decision applies to the next call.

The ai.ctxa dependency is not found

The official 0.1.1 needs only mavenCentral(). Do not add Spring milestone or snapshot repositories, or the Sonatype snapshot repository, to a regular application build. Check that the coordinates are ai.ctxa:spring-boot-starter-contexa:0.1.1; right after a release, try again once the Maven Central sync has finished.
