Troubleshooting

Use this page when the CLI install fails, the application does not start, CONTEXA does not turn on, sign-in behaves oddly, or no decisions come out: find the entry that matches your symptom. Each entry gives the cause, what to check first (a log line, a setting, a screen) and the fix, and log messages and error text are quoted exactly as the product writes them. If you are not sure which symptom you have, start with the [Contexa] mode= line and the ERROR lines in the startup log, and the output of contexa doctor.

Look here first

CONTEXA works when the JDK, the dedicated database and the AI models all fit together. The dedicated database (dedicated DB) is the separate database where CONTEXA creates its own tables; you set it with contexa.datasource.url. Before you look for a symptom, check these three places in order.

  1. The [Contexa] mode= line in the startup log: CONTEXA writes this line once at INFO level when it turns on, for example [Contexa] mode=SANDBOX ownership=HOST_OWNED data=application enforcement=ENFORCE. mode is the security mode, ownership is the authentication ownership (which of two components of the same kind serves the application when it brings its own and CONTEXA has one too), data says which database holds the application's data (with contexa, the dedicated DB also serves as the application's database), and enforcement is the operating mode. If the line is missing, CONTEXA is not on; read The application started but CONTEXA does not work.
  2. The ERROR lines of the application's startup log: the lines CONTEXA writes and what they mean are in Check that it is on. Look especially for the ERROR-level [ContexaCapability] lines and for lines that contain the application starts without Contexa. Lines that start with [Contexa] are the results of CONTEXA's startup checks, and some of them are WARN.
  3. The CLI check: contexa doctor checks the Spring Boot and Java versions, the starter and @EnableAISecurity, that the CONTEXA settings are loaded, that the CONTEXA database answers, Ollama and its models, and the API key, and prints the fix next to each problem.
contexa doctor

This page separates the symptoms that depend on the security mode. In the default SANDBOX (@EnableAISecurity) the application keeps its own sign-in; in FULL (@EnableAISecurity(mode = SecurityMode.FULL)) CONTEXA provides the sign-in. The authentication ownership (HOST_OWNED, CONTEXA_OWNED) is a separate setting from the security mode: it settles which of two components of the same kind serves the application when the application brings its own (its UserDetailsService, JwtDecoder and the like) and CONTEXA has one too. Left unset, it follows the mode (SANDBOX → HOST_OWNED, FULL → CONTEXA_OWNED).

A decision is the conclusion the CONTEXA AI reaches about one user's request: ALLOW, step-up authentication (CHALLENGE), held for review (ESCALATE) or BLOCK. The operating mode decides whether decisions are made and whether they are applied to real requests. There are three: off (DISABLED), shadow mode (SHADOW) and enforcement mode (ENFORCE).

To find a section by symptom:

  • CLI install and init symptoms: the contexa command, Docker, Ollama, the starter download, undoing an installation.
  • The application does not start, or CONTEXA does not turn on: errors that stop the startup, an application that runs without CONTEXA, settings that have no effect.
  • Sign-in looks wrong: the default user, the admin console account, every request asking for sign-in, a form that answers 403.
  • No decisions come out, or the model or vector store is the problem: capability log lines, the chat model, the vector extension, decisions that never come, seal mismatches.
  • The dependency is not found.

CLI install and init symptoms

Every contexa init error says what to do, and nothing in the project is changed (or every change is rolled back). After fixing the cause, run contexa init again.

The contexa command is not found

The terminal cannot find contexa as an executable. The cause is that the export PATH=... line the installer printed at the end has not taken effect in the current terminal.

Fix: follow these steps.

  1. Run the export PATH=... line the installer printed, or open a new terminal. On Windows, reopen the terminals that were open before the installation.
  2. Run contexa --version and check that it prints a version.

Spring Boot 4 or 3.4 and older (SPRING_BOOT_UNSUPPORTED, SPRING_BOOT_TOO_OLD)

contexa init stops with one of these error codes. The Spring Boot version of the project is outside the range CONTEXA supports.

Cause: CONTEXA 0.1.x needs Spring Boot 3.5.x. Projects created on start.spring.io now use Spring Boot 4, and on 3.4 and older CONTEXA's task executor clashes with the one Spring Boot names taskExecutor, so the application does not start.

Fix: change the Spring Boot version in the build file to 3.5.x, or run contexa init in an empty folder to get a ready Spring Boot 3.5 sample application with CONTEXA. The message an application prints when it already runs on Spring Boot 4 is in Spring Boot 4.x.

Docker is missing or not running (DOCKER_MISSING, DOCKER_STOPPED)

Cause: contexa init runs the local PostgreSQL (and, without a running Ollama, Ollama) in Docker. If Docker is not installed or not running, it stops with one of these error codes.

Fix: start Docker for your operating system.

  1. On Windows and macOS start Docker Desktop and wait until it is ready; on Linux run sudo systemctl start docker.
  2. Interactive init offers to check again.
  3. To avoid Docker, use a PostgreSQL with pgvector that you already have. Choose it in the question or run contexa init --db-url jdbc:postgresql://host:5432/db with the password in CONTEXA_DB_PASSWORD.

A port is already in use

A port clash needs no action. The local services start on free ports: PostgreSQL from 55432, Ollama on 11434 or from 51434, and the local mail inbox from 51025 and 58025. Services that already run on the default ports are left alone, and an Ollama already running on 11434 is used as it is.

Ollama is not available or a model is missing (OLLAMA_MISSING)

Cause: Ollama, which runs the AI models, is not installed, or a model it needs has not been downloaded.

Fix: choose one of these.

  • Install Ollama from ollama.com/download (or start Docker so CONTEXA can start one), or choose OpenAI with --provider openai.
  • contexa init downloads only the models that are missing (qwen3:8b and mxbai-embed-large); when a download stops, running it again continues.
  • A lighter chat model for a small machine: set CONTEXA_OLLAMA_CHAT_MODEL (for example qwen2.5:3b) before contexa init; it downloads that model and writes it into the settings.

The CONTEXA starter cannot be downloaded (STARTER_UNAVAILABLE)

Cause: the project's build could not resolve ai.ctxa:spring-boot-starter-contexa through its repositories. contexa init rolled every change back.

Fix: check that the build reaches Maven Central (network, proxy, or a company repository that mirrors it), then run contexa init again (below).

What contexa reset reverts

reset restores exactly the files contexa init changed. It uses the installation record and the backups in the project's contexa/ folder (ignored by git). It reverts three things.

  • Files: files init created are removed and changed files are put back. Changes you made after init are kept; where they overlap with CONTEXA's changes the file is left as it is and listed.
  • Local services: they stay for your other projects. When no project uses them any more, reset offers to remove them with their data; contexa reset --services does that without asking.
  • Data: the project's CONTEXA data stays in its database until the local services are removed.

Installations made by CLI 0.1.x are reverted the same way; their old Docker stack is removed when its ownership can be verified, and left alone otherwise.

The application does not start, or CONTEXA does not turn on

An application that carries @EnableAISecurity ends its startup in one of three ways. Knowing which one tells you which section to read.

  • The startup stops. The settings do not match a configuration CONTEXA supports. In most cases Spring Boot's "APPLICATION FAILED TO START" report shows a Description (what is wrong) and an Action (what to change). The errors in the sections below belong here.
  • The application runs, but CONTEXA does not turn on. In the default SANDBOX, where the application keeps its sign-in, the dedicated DB or Redis cannot be reached. The application starts without CONTEXA and logs an ERROR (below).
  • The application and CONTEXA run, and a warning is logged. Either the warning is expected or it tells you to fix a setting (the standalone warning, old setting names).

The application started but CONTEXA does not work

The application started normally, but the startup log has no [Contexa] mode= line, protected methods get no decisions, and the admin console does not open.

Cause: in the default SANDBOX, where the application keeps its sign-in, a problem with CONTEXA does not stop the application. The application starts as it does without CONTEXA, and CONTEXA turns nothing on. It logs one ERROR line that names the cause. In FULL, where CONTEXA provides the sign-in, nobody could sign in without CONTEXA, so the same causes stop the application instead.

Check first: look for these lines in the startup log.

contexa.datasource.url must be configured for @EnableAISecurity

The application turned on @EnableAISecurity, but no dedicated CONTEXA database address is set, so the startup stops.

Message: Spring Boot's startup failure report shows contexa.datasource.url must be configured for @EnableAISecurity. as the Description and Use a dedicated Contexa database by default; sharing the application database requires explicit POC approval. as the Action. Version 0.1.1 joins the two sentences into one exception message. Full message: java.lang.IllegalStateException: contexa.datasource.url must be configured for @EnableAISecurity. Use a dedicated Contexa database by default; sharing the application database requires explicit POC approval.

Cause: once @EnableAISecurity is on, a dedicated CONTEXA database address is required. When the address is empty, CONTEXA stops the startup with this message before it tries to connect. This holds when the application keeps its own sign-in as well.

Check first: check that the settings files (profile-specific files included) contain contexa.datasource.url under exactly that name and that its value is not empty.

Fix: create the dedicated database (Create the dedicated database) and set its address. In an existing application do not set contexa.datasource.isolation.contexa-owned-application: true (Minimal settings).

contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}

contexa.datasource must not share ...

The dedicated CONTEXA database is the same as the application's database, so the startup stops.

Message: the Description is contexa.datasource must not share spring.datasource unless it is an approved POC: contexa.datasource.url and spring.datasource.url name the same database., or under a production profile contexa.datasource must not share the application datasource in production profiles: ...; the Action names the two settings that are needed. The messages of 0.1.1 are contexa.datasource must not share spring.datasource unless contexa.datasource.isolation.allow-shared-application-datasource=true and contexa.datasource.isolation.shared-application-datasource-risk-accepted=true are both set for an approved POC, or contexa.datasource must not share the application datasource in production profiles.

Cause: contexa.datasource.url equals your application's spring.datasource.url. The check compares the two values after trimming spaces and fires only when they are identical.

Fix: keep a separate dedicated database. If you must use the same database for a trial, set both settings above to true; it is still refused under the prod and production profiles. An application owned by CONTEXA (contexa-owned-application: true) skips this check.

Your application has no default database connection

The application fails to start with a database connection error. The error concerns the application's own default connection, not the dedicated CONTEXA database.

Message (Spring Boot): Failed to configure a DataSource: 'url' attribute is not specified and no embedded datasource could be configured.

Cause: the starter brings JPA, so when the application has no database address, Spring Boot cannot create a default connection. Version 0.1.1 raised this error whenever CONTEXA was on and the application had no database address, even if the application needs no database. Version 0.2.0 and later leave Spring Boot's database auto-configuration out when the application sets no database setting at all and has no embedded database, so the error remains for an application that sets database-related settings but no address. The typical case is an application with only spring.jpa.*, spring.flyway.*, spring.liquibase.* or spring.sql.init.* and no spring.datasource.url.

Check first: check whether the settings files still hold such database-related settings, and whether the application really uses a database.

Fix: if the application uses a database, set its address (spring.datasource.url). If it does not, remove the database-related settings. With @EnableAISecurity(mode = SecurityMode.FULL), where CONTEXA provides the sign-in, and no database address of the application's own, the CONTEXA database becomes the application's default connection and this error does not occur.

Contexa schema is partially installed ...

Only some CONTEXA tables exist in the CONTEXA database, so the startup stops.

Message: Contexa schema is partially installed without a complete ownership contract. No schema changes were applied. Restore a verified OSS backup or use a clean database.

Cause: only some CONTEXA tables exist in the CONTEXA database. CONTEXA does not repair such a database and stops the startup. If the tables are still incomplete after the first installation, it stops with Contexa schema is partially installed after canonical schema execution.; that message tells you to rebuild the database or to run META-INF/contexa/db/schema.sql by hand before starting the application.

Check first: check whether this database is used for something else, or whether an earlier installation failed halfway.

Fix: use a clean database or restore a verified backup. Also check that the database account can create the vector extension.

Spring Boot 4.x

The application runs on Spring Boot 4.x, so the startup stops. CONTEXA is built for Spring Boot 3.x.

Messages: the Description is Contexa runs on Spring Boot 3.x, and this application runs on Spring Boot 4.x.y. and the Action is Run this application on Spring Boot 3.x, or remove @EnableAISecurity. (the actual version appears in place of 4.x.y). The messages of 0.1.1 are Contexa does not support Spring Boot 4.x. Current version: ... (ERROR log) and Spring Boot 4.x is not supported by Contexa. Current version: ... (IllegalStateException).

Fix: use Spring Boot 3.5.x. CONTEXA is built and tested with 3.5.4.

@EnableAISecurity applies security through Spring Security

The application has no Spring Security, so the startup stops.

Message: @EnableAISecurity applies security through Spring Security, and it is not on the class path.

Cause: @EnableAISecurity declares that security is to be applied, and Spring Security is what applies it. The starter does not bring Spring Security, so the application has to declare it.

Fix: add org.springframework.boot:spring-boot-starter-security to your application (Add the dependencies). contexa init adds it for you.

SANDBOX keeps the application's sign-in, and this application has none

In the default SANDBOX the application keeps its own sign-in, but it has no sign-in configuration, so the startup stops.

Message: SANDBOX keeps the application's sign-in, and this application has none: no SecurityFilterChain and no users of its own, so every request would ask for a sign-in that nobody can complete.

Cause: in the default SANDBOX your application keeps its sign-in, it declares neither a SecurityFilterChain nor users, and only Spring Boot's default security chain is left. Every request would ask for a sign-in that nobody can complete, so CONTEXA refuses to start. For an application with neither a chain nor users, CONTEXA puts an isolation chain that lets every request through (contexaSandboxIsolationChain) in place of Spring Boot's default chain and keeps the access the application had before CONTEXA came, so this refusal does not normally occur (it is a safeguard).

Fix: choose one of two ways. Declare your application's SecurityFilterChain or users (Connect your existing sign-in), or use @EnableAISecurity(mode = SecurityMode.FULL) to let CONTEXA provide the sign-in. When the application declares its own SecurityFilterChain, this error does not occur. When it declares no chain but has a user who can sign in, you get only the warning described in Every request asks for sign-in instead of this error. An application that signs users in on its own, without Spring Security, declares neither a chain nor users. It gets the isolation chain, and it names the signed-in user with one ContexaSubjectResolver bean (Connect your existing sign-in).

The contexa.infrastructure.mode is standalone warning

The startup log shows one or two WARN lines with this text. They are not a configuration error; they are expected in the default infrastructure mode (standalone).

Cause: in standalone CONTEXA keeps its state in the memory of the application. There are two warnings.

  • The learned state (behavioral baselines and the like) is in memory, so a restart starts every user's learning again.
  • The decisions in force are in memory, so a restart ends a step-up authentication (CHALLENGE), a held-for-review (ESCALATE) and an ALLOW, and the next request is analyzed again. A BLOCK is applied again at startup from CONTEXA's blocked-user record (ctxa_blocked_user), so a block held in that record stays in force, and a block that was never recorded ends with the restart.

With off (DISABLED) nothing is learned and no decision is held, so these warnings are not written.

Fix: you can leave it during development. To keep learning and decisions in operation, switch to distributed.

Old setting names have no effect

Symptom: a setting written under an old name outside contexa.*, such as security.zerotrust.*, spring.auth.* or spring.ai.security.*, has no effect, and nothing is logged about it.

Cause: the aliases of the old names are gone. CONTEXA treats those names as your application's own settings and neither reads nor moves them, so the value is silently ignored (the exception is security.plane.kafka.group-id of the Kafka listener group). The vector store settings (spring.ai.vectorstore.pgvector.*) do not reach CONTEXA's store either; write them as contexa.vectorstore.pgvector.*.

Check first: look in the settings files for CONTEXA-related keys that do not start with contexa..

Fix: change to the new prefix. All moved names are in the configuration guide.

The starter is added but there are no CONTEXA tables

You added the dependency, but no CONTEXA tables appear in the CONTEXA database.

Cause: this is expected without @EnableAISecurity (the dependency only). The starter alone creates no CONTEXA filter, authentication provider or table. The tables are created and verified in the CONTEXA database when an application with CONTEXA turned on starts.

Check first: if you added @EnableAISecurity, look for the [Contexa] mode= line in the startup log. If it is missing, CONTEXA is not on; follow The application started but CONTEXA does not work.

Fix: if the tables are still missing after turning it on, check that contexa.iam.seed.enabled is not false and that contexa.datasource.* points at the CONTEXA database.

Sign-in looks wrong

The cause of a sign-in symptom depends on who handles sign-in. In SANDBOX, where the application keeps its sign-in, the application's sign-in stays as it was, and CONTEXA keeps a separate administrator account only for its admin console. In FULL, where CONTEXA provides the sign-in, the CONTEXA sign-in page is used, and the application's users are checked against CONTEXA's accounts (CONTEXA_OWNED, the default) or the application's UserDetailsService (HOST_OWNED), as the authentication ownership says.

Spring Boot's default user no longer signs in

In an application with Spring Security, Spring Boot creates a default user user and writes a new generated password at each start, in the log line Using generated security password. The symptom is that an application which signed in with that user no longer can.

Check first: look for the Using generated security password line in the startup log. If the line is there, the user exists: sign in with the password on that line. The password changes at every start. If the line is missing, one of the causes below applies.

Cause:

  • 0.1.1: the CONTEXA starter brings the OAuth2 classes. Spring Boot reads OAuth2 classes on the class path as the application's own sign-in and then creates no default user, so an application that signed in with that user has no user once CONTEXA is added. This version also exposes CONTEXA's delegating password encoder as the application's, which cannot check a password without a prefix such as {noop}, so naming the user alone is not enough.
  • 0.2.0 and later: where CONTEXA does not provide the sign-in, the starter names the user user for Spring Boot, so the default user and its log line stay as they were. CONTEXA's password encoder is kept apart from the application's authentication and has no effect on it. If the user is missing, one of these applies: CONTEXA provides the sign-in; the application has spring.security.oauth2.* or spring.security.saml2.* settings or SAML classes, in which case Spring Boot alone creates no such user either; or the application named the user differently with spring.security.user.name.

Fix: set spring.security.user.name: user and spring.security.user.password: "{noop}your-password". The {noop} in front of the password is Spring Security's notation for a password that is not encrypted, so use it in development only.

When the application keeps its own sign-in and has no users, OAuth2 or spring.security.user.* of its own, contexa init does this for you: it makes the password once, keeps it in ~/.contexa/credentials.properties outside the project and shows it at the end. Under FULL + CONTEXA_OWNED (a FULL that sets no ownership), where CONTEXA provides the sign-in, sign in with a CONTEXA account instead of the default user (The admin-console account and its password).

The admin-console account and its password

You cannot sign in to the admin console (/contexa/admin/login), or you do not know the account and password. The console account is separate from your application's users, so an application account cannot enter it.

Cause: the console account comes from these steps.

  1. In either mode (whatever the ownership), contexa init makes a password for the account admin, keeps it in ~/.contexa/credentials.properties and shows it at the end.
  2. CONTEXA creates the account from contexa.iam.seed.admin.password when the application starts.
  3. The example application created in an empty folder uses the sample accounts (admin / 1111) instead.
  4. In SANDBOX, where your application keeps its sign-in, this admin is still the account for the console. In the three combinations other than FULL + CONTEXA_OWNED, the console signs CONTEXA's administrator in at /contexa/admin/login with the password and then a passkey or a mailed code, and your application's users cannot enter it.
  5. Without the CLI, set contexa.iam.seed.admin.* yourself (example).

Check first: read the password on the last screen of contexa init or in the line contexa.iam.seed.admin.password of that file. If there is no account, look for these lines in the startup log.

  • [IamSeedData] Administrator 'admin' created (INFO): the account was created.
  • [IamSeedData] A user named ... exists; the administrator from ... is not created (INFO): a user with the same name or e-mail already exists, so nothing was created. The existing account is not changed.
  • [IamSeedData] Administrator ... created ..., but the administrators group ... is missing (WARN): the account exists, but the administrators group does not. Assign a group in the admin console.
  • No line at all: contexa.iam.seed.admin.password is empty so no account was requested, or CONTEXA is not on, or contexa.iam.seed.enabled is false.

Fix: a password changed in the admin console stays, because an existing account is never created again. If there is no account, start the application as the same user on the same computer, because contexa init keeps the password in a file in that user's home folder. When CONTEXA provides the sign-in, the one-time code of the second step arrives in the local inbox contexa init named.

Every request asks for sign-in · SANDBOX mode: the application declares users of its own and no SecurityFilterChain

After adding CONTEXA, even pages that should be open ask for a sign-in.

Cause: your application added spring-boot-starter-security but declares no SecurityFilterChain of its own, so Spring Boot's default security applies and every request requires authentication. The starter does not bring Spring Security, so the starter alone does not cause it.

In the default SANDBOX with @EnableAISecurity on, CONTEXA builds no chain for the application. When the application has users to sign in (UserDetailsService, AuthenticationProvider or AuthenticationManager), Spring Boot's default security stays the application's security, and CONTEXA logs [Contexa] SANDBOX mode: the application declares users of its own and no SecurityFilterChain, so Spring Boot's default security is active and every request requires authentication. ... as a WARN at startup. With no users either, CONTEXA puts an isolation chain that lets every request through in place of Spring Boot's default chain, so this symptom does not occur (above).

Check first: look for the WARN line above in the startup log. If it is there, the application declares no SecurityFilterChain of its own.

Fix: declare your application's SecurityFilterChain (Connect your existing sign-in). The anyRequest().permitAll() the log names as an example is safe for CONTEXA's paths: the admin console /contexa/admin/** is protected by CONTEXA's own chain and administrator sign-in, so your chain does not need to protect it. Keep your own pages protected as before. To leave sign-in to CONTEXA, use @EnableAISecurity(mode = SecurityMode.FULL) (with the CLI, contexa init --ownership contexa).

Saving a form answers 403 after Spring Security is turned on

After Spring Security is added, saving a Thymeleaf form answers 403.

Cause: turning Spring Security on turns CSRF protection on. A Thymeleaf form without th:action gets no CSRF token, so saving it answers 403. This is Spring Security's standard behavior, not CONTEXA's.

Fix: use th:action on the form, or send _csrf with the request.

No decisions come out, or the model or vector store is the problem

[ContexaCapability] ... · Contexa required capability check failed.

The startup log shows ERROR-level [ContexaCapability] lines, or the application stops with Contexa required capability check failed.

Log format: [ContexaCapability] <capability> status=<status> required=<true|false> followed by Reason, Missing beans and Recommended actions.

Cause: when the startup finishes, CONTEXA checks that the parts decisions need were created. One of them is missing. The kind of application decides how the result shows.

  • An application not owned by CONTEXA (WARN) logs ERRORs and keeps starting. The log appears only for parts that count as required (required=true); in STRICT mode parts that are not required are logged as well.
  • An application owned by CONTEXA (FAIL_FAST) stops with Contexa required capability check failed. An owned application is one with contexa-owned-application: true or a spring.application.name that starts with contexa-. No Spring AI ChatModel is configured for CONTEXA

CONTEXA cannot find a chat model to use, so the startup stops.

Message (start): No Spring AI ChatModel is configured for CONTEXA. Add at least one Spring AI chat provider starter to your application dependencies ... then configure the matching provider under spring.ai.*

Cause: a chat model bean exists, but CONTEXA could not build the chat client and model selection it uses. The message advises that, if the dependency is already present, you check that the provider's key or address is actually set. With no provider starter at all you get the llm-runtime capability result above instead of this message.

Check first: check that the application has a Spring AI chat provider starter and that the provider's key or address is set.

Fix: put provider keys in the Spring AI settings, not under contexa.llm: spring.ai.openai.api-key, spring.ai.anthropic.api-key, and for Ollama spring.ai.ollama.* or contexa.llm.chat.ollama.base-url. Set the provider order with contexa.llm.selection.chat.priority (Minimal settings).

The vector extension is missing (PostgreSQL)

The pgvector vector extension is missing in the CONTEXA database, or its account cannot create it, so the vector store is not created or CONTEXA does not turn on.

Cause: CONTEXA's vector table is created in the CONTEXA database, not in your application's default database, and that database needs the vector extension. When the vector store creates its table (contexa.vectorstore.pgvector.initialize-schema, default true), it also needs the hstore and uuid-ossp extensions. Early in the startup CONTEXA checks the account's privileges by creating these extensions and then undoing it. Without the privilege, an application that keeps its sign-in starts without CONTEXA, and otherwise the startup stops.

Check first: in the Contexa's database cannot be used (...) line of the startup log, look in the parentheses for a CREATE EXTENSION hint.

Fix: use an image with pgvector (for example pgvector/pgvector:pg16), or on an existing database run this once in the CONTEXA database with an account that has the privilege.

CREATE EXTENSION IF NOT EXISTS vector;

No decisions come out

The application starts and sign-in works, but calling a protected method creates no decision, or requests stay pending analysis. Check these items from the top.

  1. Operating mode: in the [Contexa] mode= startup line, read the enforcement value. With DISABLED or OBSERVE, @Protectable calls are not analyzed. A mode saved in the admin console wins over YAML, so check /contexa/admin/system-settings (startup log System runtime settings applied to AI decision mode: ...). What each mode means is in Start Safely in Shadow Mode.
  2. Parts: without a chat model and a vector store, requests stay pending analysis (above).
  3. What is protected: what gets analyzed is @Protectable method calls. A sign-in is not analyzed, and the first protected method a user calls after signing in gets that user's first decision. In the SHADOW and ENFORCE modes (ENFORCE is the default), calls without sign-in (anonymous) are refused before analysis; under DISABLED and OBSERVE they are not refused and go on as the application made them.
  4. Decisions apply from the next request: the default asynchronous methods are decided after the response, so the decision applies to the next call.
  5. A synchronous call takes long: when a call is analyzed synchronously with sync = true, the request waits for the decision for up to 40 seconds (contexa.security.zerotrust.agent.flight.wait). Past that time the request is refused and the analysis goes on. If your model is slower than that, raise this value.

You can read the decisions that were made in the admin console under Zero Trust, Decision records (Where to look at the results).

Old decision records mismatch after an upgrade

After an upgrade, the security event log and the dashboard's broken seals show decision records as MISMATCH. The seal of a decision record is the integrity seal that shows the record has not changed since it was saved.

Cause: when records saved before the upgrade show MISMATCH, the earlier release wrote the record's time again when it saved it. Records the new release saves are verified as they were sealed.

Fix: the old records are not sealed again (so that a mismatch keeps meaning a record was altered) and stay mismatched until the audit retention deletes them. A record made after the upgrade that shows MISMATCH was really changed: look into it (Decision records).

The ai.ctxa dependency is not found

Gradle or Maven cannot resolve ai.ctxa:spring-boot-starter-contexa. The official {{contexa.version}} needs only mavenCentral(). Do not add Spring milestone or snapshot repositories, or the Sonatype snapshot repository, to a regular application build. Check that the coordinates are ai.ctxa:spring-boot-starter-contexa:{{contexa.version}}; right after a release, try again once the Maven Central sync has finished.
