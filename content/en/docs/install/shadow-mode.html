Start Safely with Enforcement Modes

How to watch AI decisions in shadow mode (SHADOW) before applying them, check the results, and then move to enforcement (ENFORCE). It covers the four enforcement modes, the two ways to change the mode, where to look at the results, and how to roll back.

The four enforcement modes

The enforcement mode (contexa.security.zerotrust.mode) decides whether AI decisions are made and whether they are applied. The default is ENFORCE. When you first adopt Contexa, run it in the order observe (SHADOW) → check (Where to look at the results) → enforce (ENFORCE).

ModeAI analysisDecision and audit recordsEnforcement (store decision, block)Learning
DISABLEDNot for @Protectable calls and the decision APINot for those callsNoNo
OBSERVESame as DISABLED (only the monitoring label differs)SameNoNo
SHADOWYesYesNoNo
ENFORCE (default)YesYesYes: the decision is stored and applied from the next requestOnly ALLOW decisions that were applied

The sign-in success event (Contexa's MFA sign-in when Contexa owns sign-in; the application's interactive form or OAuth2 sign-in when the application owns it) is published without looking at the enforcement mode. The decision engine looks at the mode only at the enforcement step, so this event is analyzed and recorded under DISABLED and OBSERVE too, just not enforced. To stop all analysis, use contexa.security.zerotrust.enabled: false.

Two ways to change the mode, and which wins

WayWhen it appliesPrecedence
Save in the admin console at /contexa/admin/system-settingsAt once (no restart). The saved value stays in the Contexa database (system_settings) and is applied again each time the application finishes starting.1 (highest)
contexa.security.zerotrust.mode in application.ymlRead at startup, so a change needs a restart.2: only when no value was saved in the admin console
Nothing set—3: ENFORCE
 
contexa:
  security:
    zerotrust:
      mode: SHADOW   # DISABLED, OBSERVE, SHADOW, ENFORCE
  • When no value is stored, the system settings screen pre-fills the current mode. So saving once, even to change another field, makes the database value win over YAML from then on. Saving with the mode field empty stores SHADOW.
  • The CLI's contexa mode --shadow and --enforce change only YAML. With a value saved in the admin console they have no effect.
  • A decision analysis event carries the mode in force when it was created. An event created under SHADOW is not enforced even if the mode became ENFORCE by the time its decision arrives.

What actually happens in SHADOW

  • What is analyzed: not every request, but @Protectable method calls and sign-in successes: Contexa's MFA sign-in when Contexa owns sign-in, the application's interactive sign-in (form login, OAuth2 login) when the application owns it.
  • What is kept: the decision goes to the decision record table (ai_security_decision_observation) and the audit records (audit_log), not only to the log.
  • What is not done: storing the user's decision, the block signal that cuts responses in flight, the blocked-user record, sending risk signals, and learning. So no behavioral baseline is built during SHADOW.
  • @Protectable methods: even with a stored BLOCK, CHALLENGE or ESCALATE, the method runs and only a log line is written. A sync = true method is analyzed inside the request and runs even when the decision is BLOCK or the analysis fails.
  • Request-time filters (both ownership modes): nothing is stopped. A BLOCK, CHALLENGE or ESCALATE stored earlier (a decision from an ENFORCE period, or an administrator's block) is not enforced while SHADOW lasts, and applies again under ENFORCE if it has not expired.
  • Latency: the default asynchronous methods are analyzed after the response, so they do not slow down. sync = true methods and agent requests with no decision on record are analyzed inside the request, so they do.
  • Unchanged by the mode: refusing a @Protectable call without authentication, and refusals by policy (XACML) decisions. Re-evaluating a delegated agent's request as its delegator is only recorded while enforcement is off (any mode other than ENFORCE, or enabled: false).
  • Decision API (AuthZEN): under SHADOW it analyzes, but the answer's decision is always true. Under DISABLED and OBSERVE it answers true without analysis.
  • Agent request gate (both ownership modes): while enforcement is off (any mode other than ENFORCE) it records ended delegations, narrowed scopes and call limits and lets the request through (SHADOW in agent controls).

Contexa protects the admin console in both ownership modes. When your application owns sign-in, you sign in there with a Contexa administrator account, not an application account (installation guide).

Moving to ENFORCE

Check before you move:

  • The recommendation on the readiness screen is not DO_NOT_RECOMMEND, and decisions have built up (with no decisions at all it is INSUFFICIENT_DATA).
  • In the mix of decision types (ALLOW, BLOCK, CHALLENGE, ESCALATE), the share of normal requests that got BLOCK or CHALLENGE (the false positive rate) is below the bar your team set (for example under 1%). The code does not set this bar.
  • Decision latency does not affect throughput (latency in the decision monitor).
  • You get alerts when BLOCK or ESCALATE decisions come out.
  • The decision store fits your operation: standalone (default) is memory, distributed is Redis (Infrastructure mode).
contexa:
  security:
    zerotrust:
      mode: ENFORCE

If a mode was ever saved in the admin console, change it there instead of in YAML. After the switch, stored decisions apply like this.

Rolling back

WayResult
Save SHADOW in the admin consoleApplies at once (no restart). New decisions are not stored, applied or learned from.
YAML contexa.security.zerotrust.mode: SHADOWApplies after a restart, and only when no value was saved in the admin console.
contexa.security.zerotrust.enabled: falseNo AI analysis, and the decision event listener stops too (mode: DISABLED does not stop the listener).
contexa.enabled: falseTurns none of Contexa on. Without your own chain, Spring Boot's default security applies.

Decisions already stored stay, but are not enforced while you are rolled back. In both ownership modes the request-time filters and the check before @Protectable methods follow the enforcement mode and contexa.security.zerotrust.enabled. So after switching to SHADOW or turning it off nothing is stopped (the check before @Protectable methods only records). A BLOCK, CHALLENGE or ESCALATE stored before the switch, an administrator's block included, stays and applies again after you switch back to ENFORCE, until it expires or an administrator releases it.

Learned state is not erased by changing the mode. In standalone, though, it lives in memory and is lost on restart. Changing the mode in the admin console needs no restart.

For reference: steps after a decision

A decision event goes through the handlers below in order. Under SHADOW only the enforcement step (55) differs. Enforcement happens only when contexa.security.zerotrust.enabled is true and the mode is ENFORCE (isEnforcementEnabled()).

OrderWhat it doesUnder SHADOW
50Make the decision (ProcessingExecutionHandler)The same
55Enforcement (SecurityDecisionEnforcementHandler): writes the decision record; with ENFORCE stores the decision (writeFinalAction), on BLOCK sets the block flag (setBlockedFlag), sends the block signal (registerBlockAndAwait) and records the blocked user (recordBlock), and learns from applied ALLOW decisionsWrites the decision record only and skips the rest
56Seal evidence (SealedEvidenceCaptureHandler)The same
60Audit record (AuditingHandler)The same (written)
65Forward to Contexa SaaS (SaasForwardingHandler, only when turned on)The same
