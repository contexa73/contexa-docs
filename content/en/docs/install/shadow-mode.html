Start Safely in Shadow Mode

By default CONTEXA applies AI decisions to real requests, so a wrong decision can block a normal user. Shadow mode (SHADOW) makes decisions and records them, but blocks nobody. This page shows how to watch the results in shadow mode and then move to enforcement mode (ENFORCE). It covers the three operating modes, the two ways to change the mode, where to look at the results, and how to roll back.

The three operating modes

The operating mode (contexa.security.zerotrust.mode) decides two things: whether the AI makes decisions, and whether those decisions are applied to real requests. A decision is the AI's conclusion about one user's request: ALLOW, step-up authentication (CHALLENGE), held for review (ESCALATE) or BLOCK. If you set no mode, CONTEXA runs in ENFORCE.

When you first adopt CONTEXA, work in this order:

  1. Observe: Turn on SHADOW. The AI makes and records decisions, and no request is stopped.
  2. Check: Read the recorded decisions in the admin console (Where to look at the results). See how many decisions would have blocked or challenged normal users.
  3. Enforce: When the results are acceptable, switch to ENFORCE. From then on decisions apply to real requests.

The default is ENFORCE, so you must set SHADOW yourself to start by observing. The next section shows how.

The table shows what each mode does.

ModeIn shortAI analysisDecision and audit recordsEnforcement (store decision, block)Learning
Off (DISABLED)Turns AI decisions off.No (neither for @Protectable calls nor for the decision API)Not kept for those callsNoNo

OBSERVE is an old name that is still accepted. When you set it, the mode is read as DISABLED and a WARN is logged at start. The admin console does not offer it.

The terms in the table:

  • Decision and audit records: Two records in the CONTEXA database. The decision record (ctxa_ai_security_decision_observation) holds each decision and the reasons for it. The audit record (ctxa_audit_log) is the history of security events. They are database tables, not log files, so you can read them in the admin console.
  • Enforcement: Storing the decision and using it on the same user's next requests. On a BLOCK it also sends the signal that cuts responses in flight and writes a blocked-user record.
  • Shadow memory: The place where shadow mode keeps its decisions, apart from the store that enforcement uses. It exists so that the next request of the same user does not call the AI again. No request is stopped because of it.
  • Learning: Adding the usage pattern of a request that got an ALLOW (hours, network, browser and so on) to that user's behavioral baseline. The AI reads the baseline in later decisions. An ALLOW for a user who already has a stricter decision in place is not learned, in any mode.

CONTEXA analyzes calls to methods marked @Protectable, not every request (agent requests included). The decision API (AuthZEN) lets another system ask CONTEXA whether a user may do something. It is off by default (contexa.security.zerotrust.authzen.enabled); when you turn it on, the evaluation requests it receives are analyzed too. A sign-in is never analyzed, in any mode. The first protected method a user calls after signing in gets that user's first decision.

A stored decision is applied in two places. One is a filter CONTEXA puts in front of requests (called the request-time filters in this page). The other is the check right before a @Protectable method runs. Both are used whether your application owns sign-in (HOST_OWNED) or CONTEXA does (CONTEXA_OWNED). "Both ownership modes" in this page means these two cases (see Add to an existing Spring Security application).

Two ways to change the mode, and which wins

You set the mode by saving it in the admin console or by writing it in application.yml. When both exist, the value saved in the admin console wins. To change the mode on a running system, use the admin console: it needs no restart.

WayWhen it appliesPrecedence
Save in the admin console at /contexa/admin/system-settingsAt once (no restart). The saved value stays in the CONTEXA database (ctxa_system_settings) and is applied again each time the application finishes starting. When you run several instances with contexa.infrastructure.mode: distributed, the other instances receive the save signal and apply the same value.1 (highest)
contexa.security.zerotrust.mode in application.ymlRead at startup, so a change needs a restart.2: only when no value was saved in the admin console
Nothing set—3: ENFORCE
 
contexa:
  security:
    zerotrust:
      mode: SHADOW   # DISABLED, OBSERVE, SHADOW, ENFORCE
  • Choices in the admin console: The mode list offers only "Disabled", "Shadow" and "Enforce", which are DISABLED, SHADOW and ENFORCE. OBSERVE is not offered. When you change the mode you can fill in "Why the mode changes"; it is kept in the audit record and shown in the "Mode history" of the adoption screen.
  • The pre-filled value: When no mode is stored, the screen pre-fills the mode in effect. If you save only another setting, the mode is not stored, so YAML keeps winning. When you choose a mode different from the one in effect, the database value wins over YAML from then on. Choosing the same mode as YAML on purpose is not stored either, so YAML keeps deciding. If a mode is already stored and you save with the mode field empty, SHADOW is stored.
  • The CLI's contexa mode --shadow and --enforce change only YAML. With a value saved in the admin console they have no effect.
  • Analyses in flight when you change the mode: Each analysis request carries the mode it was created under. An analysis created under SHADOW is not enforced even if the mode became ENFORCE by the time its result arrives. Likewise an analysis created under ENFORCE is not enforced if you switch to SHADOW before its result arrives.

What actually happens in SHADOW

Shadow mode makes decisions and records them, but never uses a decision to stop a user. The behavior falls into three groups.

What it analyzes and remembers

  • What is analyzed: not every request, but calls to @Protectable methods (agent requests included). A sign-in is not analyzed; the first protected method a user calls after signing in gets that user's first decision.
  • What is kept: the decision goes to the decision record table (ctxa_ai_security_decision_observation) and the audit records (ctxa_audit_log), not only to the log.
  • What is remembered and learned: decisions are kept in the shadow memory. The next request of the same user is answered from it, so the AI is not called again, and the number of AI calls and the cost during shadow mode match those of ENFORCE. ALLOW decisions are learned into the behavioral baseline exactly as under ENFORCE.
  • Latency: the default (asynchronous) methods are analyzed after the response, so they do not slow down. sync = true methods and agent requests with no decision on record wait for the decision inside the request, so they do.

What it does not do

  • Not done: storing the decision in the enforcement store, sending the block signal that cuts responses in flight, writing the blocked-user record, sending the risk signal that tells your application's receivers a user's risk level changed, and narrowing an agent's allowed scope.
  • @Protectable methods: even with a stored BLOCK, CHALLENGE or ESCALATE, the method runs and only a log line is written. sync = true makes a method wait, before it runs, for the decision made inside the request; under shadow mode the method runs even when that decision is BLOCK or the analysis fails.
  • Request-time filters (both ownership modes): nothing is stopped. A BLOCK, CHALLENGE or ESCALATE stored during an ENFORCE period, or an administrator's block, is not enforced while SHADOW lasts, and applies again under ENFORCE if it has not expired.
  • Decision API (AuthZEN): under SHADOW it analyzes, but the decision in the answer is always true. Under DISABLED and OBSERVE it answers true without analysis.
  • Agent request gate (both ownership modes): it checks whether an agent's request meets an ended delegation, a narrowed scope or a call limit. While enforcement is off (any mode other than ENFORCE) it records what it finds and lets the request through (SHADOW in agent controls).
  • Re-evaluation as the delegator: when an agent calls on behalf of a user, CONTEXA evaluates the call again as that user (the delegator) to see whether the user could have made it. While enforcement is off (any mode other than ENFORCE, or enabled: false) the result is only recorded and the call is not stopped.

What shadow mode still stops

  • Calls without sign-in: when a caller who has not signed in, or is anonymous, calls a @Protectable method, CONTEXA refuses the call under SHADOW and ENFORCE. Under DISABLED and OBSERVE (and with enabled: false) CONTEXA does not refuse it: the call goes on as the application made it, and the method policies still decide on what the security context holds, a visitor or nobody. So moving from DISABLED to SHADOW can refuse such calls for the first time.
  • Refusals by access policies (XACML): a call that an access policy refuses is refused under every mode.

Where to look at the results

After you turn on shadow mode, look at the results in the admin console. The Zero Trust screens are easiest to follow in the order Overview, Adoption, Decision records, and all of them need ROLE_ADMIN.

WhereWhat you see
Zero Trust → Overview /contexa/admin/zero-trustProtection coverage, the number of decisions and of stopped requests per period (by day), and the console's warnings. Under shadow mode the stopped requests are not requests that were really stopped, but requests that enforcement would have stopped.
Zero Trust → Adoption /contexa/admin/zero-trust/adoptionWhether it is safe to move to ENFORCE. It weighs the SHADOW decisions made since shadow mode started, or the last 90 days of SHADOW decisions when the mode is not SHADOW now. It also shows the "Mode history" with the reason given for each change.
Zero Trust → Decision records /contexa/admin/zero-trust/decisionsEach decision and why. Nobody is blocked under SHADOW, so a decision that came out as BLOCK in shadow mode (on its first attempt, not a retry) waits for an administrator in the "Review queue" tab (?view=review) as "Would have blocked" (SHADOW_BLOCK). The tab also holds a "Daily sample" drawn at random each day and decisions marked "Rule broken" (the AI's answer broke a decision rule). An administrator opens each one and rates whether the decision was valid.

The adoption screen ends in one of three verdicts:

  • RECOMMENDED: "Every recommended criterion is met: moving to ENFORCE can be considered."
  • CONDITIONS_UNMET: "{count} criteria are not met: hold off applying."
  • DATA_INSUFFICIENT: "Not enough data to judge yet: the observation period or the decisions fall short of the recommended criteria."

CONTEXA protects the admin console in both ownership modes. When your application owns sign-in, you sign in there with a CONTEXA administrator account, not an application account (installation guide).

Moving to ENFORCE

First look at whether the verdict of the adoption screen is RECOMMENDED. With CONDITIONS_UNMET the table "Each criterion now" shows the criteria that are not met; with DATA_INSUFFICIENT the observation period or the number of decisions falls short. The screen weighs these criteria, with these recommended values by default:

Criterion on the screenWhat it measuresRecommended by default

Decided by the modelThe share of decisions the AI model answered itself.At least 95%

These are recommendations to start from, not a guarantee of the product; change them in the system settings (Zero Trust console) or with contexa.security.zerotrust.console.adoption.*. Your team checks the following itself.

  • Check that the decisions SHADOW would have blocked ("Would have blocked" in the review queue) have been reviewed. Under ENFORCE these users are really blocked.
  • Check that, in the mix of decision types (ALLOW, BLOCK, CHALLENGE, ESCALATE), the share of normal requests that got BLOCK or CHALLENGE (the false positive rate) is below the bar your team set (for example under 1%). The code does not set this bar.
  • Check that decision latency does not affect throughput (Zero Trust → Operations, "Latency by stage"; the adoption criterion "User wait p95 (synchronous)").
  • Check that you get alerts when BLOCK or ESCALATE decisions come out.
  • Check that the decision store fits your operation: standalone (default) is memory, distributed is Redis (Infrastructure mode).
contexa:
  security:
    zerotrust:
      mode: ENFORCE

If a mode was ever saved in the admin console, change it there instead of in YAML. After the switch:

  • If you ran under ENFORCE before, the BLOCK, CHALLENGE and ESCALATE decisions stored then, and administrators' blocks, apply again unless they have expired.
  • The decisions in the shadow memory do not carry over. Each user gets a new decision under ENFORCE.
  • The behavioral baseline learned during shadow mode stays in use.

Rolling back

If enforcement causes trouble, move the mode back to SHADOW. From then on new decisions are not applied. There are four ways, and the further down the table, the more they switch off.

WayResult
Save SHADOW in the admin consoleApplies at once (no restart). New decisions are not applied. Decision and audit records are still written, and ALLOW decisions are still learned.
YAML contexa.security.zerotrust.mode: SHADOWApplies after a restart, and only when no value was saved in the admin console.
contexa.security.zerotrust.enabled: falseNo AI analysis (the same as mode: DISABLED). In addition, where CONTEXA owns sign-in, it also stops changing authorities when the sign-in is read and stops session tracking. mode: DISABLED stops neither.
contexa.enabled: falseTurns none of CONTEXA on. Without a Spring Security filter chain of your own, Spring Boot's default security applies.

Decisions already stored stay, but are not enforced while you are rolled back. In both ownership modes the request-time filters and the check before @Protectable methods follow the operating mode and contexa.security.zerotrust.enabled. So after switching to SHADOW, or turning AI decisions off with contexa.security.zerotrust.enabled: false, these two stop nothing on the strength of a stored decision (the check before @Protectable methods only records). A BLOCK, CHALLENGE or ESCALATE stored before the switch, an administrator's block included, stays and applies again after you switch back to ENFORCE, until it expires or an administrator releases it. One step does not follow the mode: where CONTEXA owns sign-in, it narrows a user's authorities by the stored decision when the sign-in is read, and only enabled: false stops that.

The behavioral baseline is not erased by changing the mode. In standalone, though, it lives in memory and is lost when the application restarts. Changing the mode in the admin console needs no restart, so the baseline is kept.
