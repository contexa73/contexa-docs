Authorization Policies

Authorization is the step that decides, by policy, which URLs and methods a signed-in user may use. The settings on this page control which accounts can enter the admin console, what data CONTEXA writes to its database at first start, what decision applies when several policies match or none does, and how the admin console scans for resources. The policies themselves are created in the admin console. Several defaults suit development and testing, so the settings to change before a production deployment are collected in the first section.

Settings to check before a production deployment

Most settings on this page work with their defaults. The four settings below have defaults chosen for development and testing. Check their values before you deploy to production. The first one must be turned off.

Sample accounts must be off in production. There are five sample accounts and they share one password. That password is published with the code. The account admin holds the administrator role (ROLE_ADMIN), so anyone who knows the password can change policies, accounts, and system settings in the admin console. When contexa.iam.seed.accounts.enabled is not set, CONTEXA creates these accounts on the first start against a database that has no user accounts. An empty production database qualifies. Set contexa.iam.seed.accounts.enabled: false explicitly in the production configuration.

What this page sets

A policy is a rule that allows or denies a URL or a method. The effect of one policy is allow (ALLOW) or deny (DENY). The decision for when no policy matches is permit (PERMIT), deny (DENY) or only signed-in users (AUTHENTICATED). These values are separate from the decision the AI gives a request (allow, step-up authentication, held for review, block). Policy bodies are stored in CONTEXA's own database, not in application.yml. You create and edit them in the admin console (Policies). The settings on this page do not hold policy bodies. They control the behavior around policies.

Settings come from two places: the configuration file (YAML) and the admin console's system settings screen. The three policy decision settings exist in both places, and the stored system settings override the configuration file.

Admin console access

The admin console (/contexa/admin/**) is where you manage policies, accounts, and system settings. CONTEXA protects these addresses itself, so the application does not need to block them. To enter the console, a person needs a CONTEXA administrator account. An application user account does not work.

  • Turning it on and off: This page has no setting that turns the admin console on or off. The console runs with CONTEXA, and only accounts that hold the administrator role (ROLE_ADMIN) can enter. The way to turn off CONTEXA as a whole is in the rollback table of Start Safely in Shadow Mode.
  • Who protects it: Where the application keeps its sign-in (the default, HOST_OWNED), a chain made for the console signs CONTEXA administrators in at /contexa/admin/login. Where CONTEXA owns the sign-in (CONTEXA_OWNED), CONTEXA's security chain and method security protect the console. The difference between the two is described in Add to an Existing Spring Security Application.
  • First administrator: Create it with contexa.iam.seed.admin.* (below, example in Protecting it in HOST_OWNED mode). Create further administrators in the console and assign them the administrator role.
  • Default protection policies: The first start inserts two policies. ALLOW_CONTEXA_ADMIN_LOGIN opens the sign-in page /contexa/admin/login to everyone. ALLOW_CONTEXA_ADMIN_ADMINISTRATORS limits the rest of /contexa/admin/** to the administrator role. Neither policy can be deleted or disabled, and an edit that widens what it allows is refused.
  • Last administrator: When one active administrator is left, that account cannot be deleted, disabled, or stripped of the administrator role. If every administrator is locked out, set contexa.iam.seed.admin.* with a username and an e-mail that no account in the database uses, then restart. The start creates a new administrator.
  • Change record: When you change an item such as a policy decision or the scanner packages on the system settings screen, the old and new values are written to the audit record. A change of the operating mode is recorded separately, together with the reason you enter.

First start: schema and default data

On its first start, CONTEXA writes a schema and default data to its own database. This step is called seeding. It runs when CONTEXA is on through @EnableAISecurity and has its own database (contexa.datasource.url).

  1. CONTEXA inspects the state of the schema in its own database.
  2. When there is no schema, CONTEXA installs it (db/schema.sql). When the schema is complete, CONTEXA only maintains it by adding missing tables, indexes, and columns. When the schema is only partly there, CONTEXA changes nothing and stops the start. In that case, restore a verified backup or use a new database.
  3. CONTEXA inserts the default data: roles, groups, policies, condition templates, admin menus, and system settings.
  4. When the conditions are met, CONTEXA inserts the sample accounts (see the table below).
  5. After all beans exist, CONTEXA creates the first administrator if contexa.iam.seed.admin.password is set.

Most default data skips rows that already exist, so a restart is safe. The exception is the default policies that protect the admin console. Their name, effect, priority, and active flag are set back to the default values at every start.

Never turn the sample accounts on in production.
  • The sample accounts are admin, manager, developer, user, and finance. They share one password, which is published with the code.
  • Only admin holds the administrator role. The others belong to development, infrastructure, and finance role groups.
  • When CONTEXA creates the accounts, the start log carries one WARN line (Sample accounts were added ...). For a database that already has accounts, CONTEXA creates nothing and logs that fact at INFO.
  • Setting the property to false does not remove accounts that already exist. Create another administrator first, then delete or disable the sample accounts in the console. The last administrator cannot be deleted.
  • If you set contexa.iam.seed.accounts.enabled to true and also set contexa.iam.seed.admin.password, the sample account admin is inserted first, so the administrator you configured is not created.

When several policies match, and when none does

One request can match several policies, or none. The three settings below decide the policy decision (allow or deny) in these cases.

SettingDefaultMeaningWhen to change
contexa.policy.combining-algorithmFIRST_APPLICABLEHow several matching policies are combined into one decision (Combining algorithms).Change it to DENY_OVERRIDES when a deny must take precedence. On an installation where the default seed wrote a system settings row, this configuration file value is not used, so change it on the system settings screen.
contexa.policy.no-matching-url-policy-decisionAUTHENTICATEDThe decision when no URL policy matches. The values are listed below the table. On the system settings screen, this setting is named "Decision when no URL policy applies".Use DENY when every address has a policy. Do not use PERMIT in production.
contexa.policy.missing-method-policy-decisionPERMITThe decision when a @Protectable method has no policy (PERMIT or DENY). On the system settings screen, this setting is named "Decision when no method policy applies".Change it to DENY to block methods that have no policy. On an installation where the default seed wrote a system settings row, this configuration file value is not used, so change it on the system settings screen.

contexa.policy.no-matching-url-policy-decision takes one of three values.

  • AUTHENTICATED: a signed-in user passes. A request that is not signed in is sent to sign in. CONTEXA's own sign-in stays open.
  • PERMIT: everyone passes.
  • DENY: no one passes. This also refuses CONTEXA's sign-in pages that no policy names, so create a policy that allows the sign-in pages first.

When policies match but all of them are DENY policies whose conditions are not met, CONTEXA treats the request like one with no policy and uses the decision above. Only then does DENY_UNLESS_PERMIT deny. When no policy matches at all, every combining algorithm uses the decision above. Where your application keeps its sign-in (HOST_OWNED), your own chain decides your requests. The decision then applies only to requests you hand to CONTEXA's dynamic authorization component (CustomDynamicAuthorizationManager, .access(customDynamicAuthorizationManager)).

The stored system settings win over YAML. The settings are applied in this order.
  1. The default seed inserts one system settings row. The row holds combining algorithm FIRST_APPLICABLE, PERMIT for a method with no policy, and no value for a URL with no policy.
  2. When this row exists, CONTEXA overwrites the combining algorithm and the decision for methods with the row's values after all beans are created and before it takes requests. With the seed on, the YAML values contexa.policy.combining-algorithm and contexa.policy.missing-method-policy-decision are not used. These two YAML values apply only when there is no system settings row.
  3. The decision for URLs that no policy names is overwritten only after an operator saves one. Until then the YAML contexa.policy.no-matching-url-policy-decision applies, and AUTHENTICATED applies when YAML has none.
  4. Until a URL decision is saved, the system settings screen shows the decision in effect as selected.
  5. A save on the screen applies at once on this instance. With contexa.infrastructure.mode: distributed, CONTEXA also signals the other instances to read the settings again (First Start and Deployment).
  6. An installation made by an earlier version holds PERMIT for URLs in its row. An upgrade changes no stored decision, so those URLs stay open to everyone until an operator chooses another value. Where CONTEXA owns the sign-in (CONTEXA_OWNED), the start logs one line that says so.

Combining algorithms

A combining algorithm is the rule that merges the results of the individual policies into one decision when several policies match. The result of one policy depends on its effect. An ALLOW policy counts as permit when its condition holds and as deny when it does not. A DENY policy counts as deny when its condition holds and drops out of the calculation when it does not.

ValueWhen several policies matchName on the system settings screen
FIRST_APPLICABLE (default)The first applicable policy in priority order decides.First-match wins (simplest)
DENY_OVERRIDESAny deny makes the result deny. When permits and denies overlap, the deny wins.Deny wins (most secure)
PERMIT_OVERRIDESAny permit makes the result permit.Permit wins
DENY_UNLESS_PERMITThe result is deny unless there is an explicit permit.Deny unless explicitly permitted

Where they apply

  • URL policies: They apply in a chain that decides every request with CONTEXA's dynamic authorization (CustomDynamicAuthorizationManager). By default that is the default chain of @EnableAISecurity(mode = SecurityMode.FULL) (CONTEXA_OWNED).
  • Method policies: They apply when a @Protectable method is called, whatever the authentication ownership (@Protectable).

Resource scanning in the admin console

A resource is something a policy can target. The admin console finds the application's controller addresses and registers them as resources (Resource Scanner). You set the search range on the system settings screen, not in the configuration file.

  1. The scanner searches the packages listed in "Controller base packages" on the system settings screen (io.contexa.contexaiam. by default).
  2. It always adds the application's own package: the package of the main class, which Spring Boot's auto-configuration uses as its base.
  3. To register addresses outside the application's packages, add those packages to "Controller base packages". Enter one prefix per line or separate them with commas.

Real-time endpoint

The CONTEXA IAM module (the module for policies and the admin console) can register a STOMP endpoint for real-time messages. STOMP is a protocol for exchanging messages over WebSocket. The endpoint accepts connections from every origin. Nothing in CONTEXA sends messages to it, so turn it off with false when you do not use it.

SettingDefaultMeaningWhen to change
contexa.iam.websocket.enabledtrueIAM registers the STOMP endpoint /ws-soar (SockJS, broker /topic and /queue, application prefix /app). It registers the endpoint only in a servlet web application that has no bean named like one of Spring's message broker beans (21 names such as clientInboundChannel). An application that sets up its own STOMP configuration has beans with these names. With one such bean, CONTEXA logs a WARN and does not register the endpoint.Turn it off when you do not use the endpoint.
