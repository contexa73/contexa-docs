Authorization Policies

Sets how a decision is made when several policies match a URL or method or none does, what data goes in at first start, and how the admin console finds resources. The policies themselves are made in the admin console.

What this page sets

Policy bodies live in Contexa's database, not in application.yml; they are made and edited in the admin console (Policies). Settings are split between YAML and the admin console's system settings page. The three policy decision settings are in both, and the stored system settings win.

The admin console needs a Contexa administrator account in both ownerships. Contexa protects the admin console (/contexa/admin/**) itself: under CONTEXA_OWNED with its security chain and method security, under the default HOST_OWNED with a chain of its own that signs Contexa's administrators in at /contexa/admin/login. The application does not need to restrict these addresses, and its users cannot enter the console. Create the first administrator with contexa.iam.seed.admin.* (below, example in Protecting it in HOST_OWNED mode).

First start: schema and default data

When Contexa's own database is empty, startup installs the schema (db/schema.sql) and inserts the default data (roles, groups, policies, condition templates, admin menus, system settings). Every insert skips rows that already exist, so a restart is safe. When the schema is complete, startup only maintains it; when it is only partly there, startup changes nothing and stops. The seed runs when Contexa is on with @EnableAISecurity and has its own database (contexa.datasource.url).

SettingDefaultMeaning
contexa.iam.seed.enabledtrueInstalls the schema and default data at startup. Turn it off only for a database whose schema you manage yourself
contexa.iam.seed.accounts.enabledfalseAlso inserts five sample accounts and their group assignments (db/data-accounts.sql)
contexa.iam.seed.admin.password(none)When set, creates one administrator at the start (group of system administrators with ROLE_ADMIN; two-step sign-in when Contexa owns sign-in, the console's own sign-in at /contexa/admin/login under HOST_OWNED). A user with the same username or e-mail is never changed, so a password changed in the admin console stays. contexa init keeps this value in ~/.contexa/credentials.properties, outside the project
contexa.iam.seed.admin.usernameadminUsername of that administrator
contexa.iam.seed.admin.emailadmin@localhostE-mail of that administrator; the one-time code of the second sign-in step goes there (CONTEXA_OWNED)
Never turn the sample accounts on in a deployment. The five sample accounts (admin, manager, developer, user, finance) share one password published with the code. Turn them on only for a quick local start on your own database, and create the first administrator through your identity provider or the admin console.

When several policies match, and when none does

SettingDefaultMeaning
contexa.policy.combining-algorithmFIRST_APPLICABLEHow several matching policies are combined into one decision (table below)
contexa.policy.no-matching-url-policy-decisionPERMITDecision when no URL policy matches (PERMIT or DENY). Use DENY when every address has a policy
contexa.policy.missing-method-policy-decisionPERMITDecision when a @Protectable method has no policy (PERMIT or DENY)
The stored system settings win over YAML. The default seed inserts a system settings row (combining FIRST_APPLICABLE, no policy PERMIT and PERMIT). When that row exists, Contexa overwrites the three values with the row's values after all beans are created and before requests are taken, so with the seed on the YAML contexa.policy.* values are not used. Change them on the admin console's system settings page. A save applies at once on this instance and tells the other instances to read again. The YAML values are used only when there is no system settings row.

Combining algorithms

ValueWhen several policies match
FIRST_APPLICABLE (default)The first matching policy in priority order decides
DENY_OVERRIDESAny deny makes it deny. The safest
PERMIT_OVERRIDESAny permit makes it permit
DENY_UNLESS_PERMITDeny unless there is an explicit permit

Where they apply

  • URL policies apply in a chain that decides every request with Contexa's dynamic authorization (CustomDynamicAuthorizationManager). By default that is the default chain of @EnableAISecurity(mode = SecurityMode.FULL) (CONTEXA_OWNED).
  • Method policies apply when a @Protectable method is called, whatever the authentication ownership (@Protectable).

Resource scanning in the admin console

The admin console finds the application's controller addresses and registers them as resources that policies can target (Resource Scanner). The packages it searches are the resource scanner packages of the system settings page (io.contexa.contexaiam. by default, not set in YAML) plus the application's own packages (the ones Spring Boot knows); to register addresses outside the application's packages, add those packages there.

SettingDefaultMeaning
contexa.iam.admin.rest-docs-path/docs/index.htmlStart of the API documentation link the scanner makes for each URL resource (<path>#<controller>_<method>). Used in the resource details of the admin console and in AI resource naming. Contexa provides no such documentation page, so set your application's API documentation address
contexa.iam.admin.condition-templates.enabledfalsetrue: condition templates are made automatically when resources are refreshed in the admin console (policy center, resource management). Not at startup. Making condition templates by hand is not affected by this value

Real-time endpoint

SettingDefaultMeaning
contexa.iam.websocket.enabledtrueIAM registers the STOMP endpoint /ws-soar (SockJS, broker /topic and /queue, application prefix /app). Registered only in a servlet web application that has no STOMP configuration of its own (a clientInboundChannel bean)

The endpoint accepts connections from every origin. Nothing in Contexa sends messages to it, so turn it off with false when you do not use it.
