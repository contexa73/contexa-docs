Authentication and Sign-in

Which authentication settings you need depends on who handles sign-in, your application or CONTEXA. In the default mode, where your application handles sign-in (SANDBOX), CONTEXA only reads your application's sign-in result, so the settings to decide are limited to the step-up methods (passkey, one-time code by mail) and the proxy addresses. In the mode where CONTEXA itself handles sign-in, MFA and token issuance (FULL), you can set how the signed-in state is kept, the token lifetimes, the authorization server, the sign-in and MFA addresses, the MFA time limits and where MFA state is stored. Each section says in its first line which case it applies to.

What you set depends on who handles sign-in

Applies to: both cases. This section explains how to tell which case you are in.

The security mode decides who handles sign-in, that is, who verifies credentials and manages sessions and tokens: your application (SANDBOX) or CONTEXA (FULL). All of CONTEXA's features work in either mode. It determines which settings on this page apply to you. On this page, a decision is the conclusion CONTEXA reaches about a user's request: ALLOW, CHALLENGE, ESCALATE or BLOCK. Step-up authentication (MFA, multi-factor authentication) asks for a factor beyond the password, such as a passkey or a one-time code. A CHALLENGE decision requires it.

CONTEXA builds no security filter chain for your users' sign-in; it builds only the chain where CONTEXA administrators sign in to its admin console (/contexa/admin). The authentication ownership (contexa.bridge.ownership) is a separate setting from the security mode. It settles which of two components of the same kind serves your application when your application brings its own (its UserDetailsService, JwtDecoder and the like) and CONTEXA has one too: HOST_OWNED keeps your application's, CONTEXA_OWNED lets CONTEXA's serve where your application has none. It turns no feature off, and all four combinations are allowed. Left unset, it follows the mode (SANDBOX → HOST_OWNED, FULL → CONTEXA_OWNED). When your application keeps its sign-in, how its sign-in result reaches CONTEXA is described in Authentication Bridge.

Settings when your application keeps its sign-in (SANDBOX)

Applies to: SANDBOX only (your application keeps its sign-in).

In this mode your application's Spring Security configuration decides the sign-in method, the tokens and the sign-in addresses. So the sections Signed-in state, Token lifetimes, Authorization server and Sign-in and MFA addresses of this page do not apply. What CONTEXA sets itself is the verification-only step-up page (/contexa/step-up) that a user passes through when the decision is CHALLENGE. The page verifies the user with one of the methods available: a passkey, a one-time code by mail, or the application's own re-authentication. How the page works is described in Step-up when the application handles login.

Signed-in state: session or OAuth2 token

Applies to: FULL only (CONTEXA provides the sign-in).

Sets whether a signed-in user stays signed in through an HTTP session (SESSION) or through an OAuth2 access token (OAUTH2). Each flow (the configuration of one sign-in method) can set it in the DSL with .session() or .oauth2(), and that value takes precedence over the setting. contexa.auth.state-type applies when a flow sets none. Some shared handling, such as logout, reads this value whatever the flow sets. The default FULL chain sets .session() on its flows. An OAuth2 state flow is a flow that keeps the signed-in state in an OAuth2 token. The DSL is in Authentication DSL.

Token transport

How the access token and the refresh token travel with requests and responses, set by contexa.auth.token-transport-type.

ValueAccess tokenRefresh token
COOKIECookie accessTokenCookie refreshToken
HEADER (default)Authorization: Bearer … headerX-Refresh-Token header
HEADER_COOKIEAuthorization: Bearer … headerCookie refreshToken
  • Use COOKIE for an application with server-rendered pages. With a header transport and token-persistence: memory, a browser page navigation carries no token, so server pages stay unauthenticated after sign-in. With that combination an ERROR is logged once at startup. Header transports suit SPAs.
  • With COOKIE, CSRF protection is always on, since the browser sends the cookies with every request. COOKIE together with oauth2-csrf: false stops startup.

When CONTEXA issues tokens (authorization server)

Applies to: FULL only (CONTEXA provides the sign-in).

Under FULL, whatever the ownership, CONTEXA's authorization server is configured. It actually issues tokens when the server role includes AUTHORIZATION_SERVER (as COMBINED does) and some flow uses the OAuth2 state. The endpoint paths are fixed: /oauth2/authorize, /oauth2/token, /oauth2/jwks, /oauth2/revoke, /oauth2/introspect, /connect/register and /userinfo.

Passkey relying party (RP)

Applies to: both cases (SANDBOX and FULL).

A browser creates a passkey (a WebAuthn credential) bound to the site's domain. The relying party (RP) is the server-side identity that represents that domain. Passkeys of single-factor sign-in and of MFA both use the values below, and so does the passkey of the step-up in SANDBOX, where the application keeps its sign-in. In production, set rp-id to the site domain and allowed-origins to the real https addresses.

Passkeys work only when the webauthn4j library and the Jackson CBOR codec are on the class path. When the application excludes them, passkeys are off and only the other methods are offered.

Applies to: it differs by item. contexa.auth.mfa.max-retry-attempts and the three mail sending limits (contexa.auth.ott.email-max-concurrent-sends, contexa.auth.ott.email-send-wait-seconds and contexa.auth.ott.email-smtp-timeout-seconds) apply to both cases. Proxies and client IP

Applies to: both cases (SANDBOX and FULL).

When a load balancer or an API gateway sits in front of the application, the connecting address the application sees is the proxy's address. The real client IP arrives in the X-Forwarded-For header, but anyone can send that header. So by default CONTEXA does not trust it and uses the connecting address. When you list the proxies you trust, CONTEXA uses the IP in the header only for requests that come from those proxies.

The same kind of setting exists twice, for different uses, and the two are independent, so you set each one separately. Leave the proxy check (trusted-proxy-validation-enabled) of both at its default (true): turning it off lets anyone forge the header and spoof the client IP.
