When Contexa Owns Sign-in

Settings used when Contexa itself handles sign-in, MFA and token issuance (CONTEXA_OWNED). You choose whether the signed-in state is kept in a session or a token, the token lifetimes, Contexa's authorization server, the sign-in and MFA addresses, the MFA time limits and where MFA state is stored.

When these settings apply

Contexa handles sign-in when the authentication ownership is CONTEXA_OWNED. That is the default with @EnableAISecurity(mode = SecurityMode.FULL), and contexa.bridge.ownership can set it directly. Under the default HOST_OWNED, the application's Spring Security handles sign-in and Contexa builds no sign-in chain, so the settings on this page are not used, except the passkey relying party values, which the passkey factor of Contexa's step-up (/contexa/step-up, answering a CHALLENGE) uses too. How the application's sign-in is passed to Contexa then is in Authentication Bridge.

Signed-in state: session or OAuth2 token

Sets whether a signed-in user is remembered by an HTTP session (SESSION) or by an OAuth2 access token (OAUTH2). Each flow can set it in the DSL with .session() or .oauth2(), and that comes first. contexa.auth.state-type is used when a flow sets none, and some shared handling such as logout reads this value whatever the flow sets. The default FULL chain sets .session() on its flows. The DSL is in Authentication DSL.

SettingDefaultMeaning
contexa.auth.state-typeOAUTH2State type when a flow sets none (OAUTH2 or SESSION)
contexa.auth.oauth2-server-modeCOMBINEDThe server role Contexa takes in OAuth2 state flows (table below). This is the real switch for whether Contexa issues tokens
contexa.auth.token-transport-typeHEADERHow tokens are carried (table below)
contexa.auth.token-persistencememoryWhere the script of the MFA pages Contexa renders keeps the token: memory (lost on reload), localStorage or sessionStorage
contexa.auth.oauth2-csrffalseCSRF protection of the OAuth2 chain. With the COOKIE transport it is always on, whatever this value
contexa.auth.cookie-securetrueMarks the token cookies Secure. The Redis MFA session cookie is Secure only when this is true and the request is HTTPS
contexa.auth.cookie-same-siteLaxSameSite of the token cookies (Strict, Lax or None). None works only with cookie-secure: true (otherwise startup stops)

OAuth2 server roles

ValueWhat it does
RESOURCE_SERVEROnly checks the access token of a request. Contexa issues no tokens, so a login flow in the token state stops startup.
AUTHORIZATION_SERVERContexa issues tokens (the authorization server endpoints and logout).
COMBINED (default)Both.

Token transport

ValueAccess tokenRefresh token
COOKIECookie accessTokenCookie refreshToken
HEADER (default)Authorization: Bearer … headerX-Refresh-Token header
HEADER_COOKIEAuthorization: Bearer … headerCookie refreshToken
  • Use COOKIE for an application with server-rendered pages. With a header transport and token-persistence: memory, a browser page navigation carries no token, so server pages stay unauthenticated after sign-in. With that combination an ERROR is logged once at startup. Header transports suit SPAs.
  • With COOKIE, CSRF protection is always on, since the browser sends the cookies with every request. COOKIE together with oauth2-csrf: false stops startup.

Token lifetimes and concurrent sign-ins

The lifetimes of the tokens Contexa issues in OAuth2 state flows, and how many sign-ins one user may keep at once.

SettingDefaultMeaning
contexa.auth.access-token-validity3600000Access token lifetime (ms, 1 hour). 0 or less stops startup
contexa.auth.refresh-token-validity604800000Refresh token lifetime (ms, 7 days). 0 or less stops startup
contexa.auth.enable-refresh-tokentruefalse: no refresh token is created
contexa.auth.allow-multiple-loginsfalsefalse: a new sign-in invalidates all earlier sign-ins (valid refresh tokens) of the same user
contexa.auth.max-concurrent-logins3Most concurrent sign-ins with allow-multiple-logins: true. Beyond it the oldest sign-ins are invalidated first
  • Both lifetimes apply to the token settings of the internal client of Contexa's authorization server and to the token cookies. An internal client already stored in the database is brought to these lifetimes at startup.
  • Each refresh issues a new refresh token; the old one is not reused.

When Contexa issues tokens (authorization server)

Under CONTEXA_OWNED, Contexa's authorization server is configured. It actually issues tokens when the server role includes AUTHORIZATION_SERVER (as COMBINED does) and some flow uses the OAuth2 state. The endpoints are fixed: /oauth2/authorize, /oauth2/token, /oauth2/jwks, /oauth2/revoke, /oauth2/introspect, /connect/register and /userinfo.

# Added to your existing settings
contexa:
  auth:
    oauth2:
      client-secret: ${CONTEXA_OAUTH2_CLIENT_SECRET}
      issuer-uri: https://auth.example.com
      jwk-key-store-path: file:/etc/contexa/keys/jwk-keystore.p12
      jwk-key-store-password: ${CONTEXA_JWK_STORE_PASSWORD}
      jwk-key-alias: contexa
SettingDefaultMeaning
contexa.auth.oauth2.client-iddefault-clientID of Contexa's internal client. At first start a client with this ID is stored in the database
contexa.auth.oauth2.client-secretnoneSecret of the internal client. Required when issuing tokens (otherwise startup stops), and it must stay the same across restarts. The old default secret is refused
contexa.auth.oauth2.issuer-urihttp://localhost:9000The issuer (iss) of issued tokens, the issuer the resource server expects, and the start of the address Contexa gets its own tokens from. Set the real address in production
contexa.auth.oauth2.token-endpoint/oauth2/tokenPath added after issuer-uri when Contexa gets its own tokens
contexa.auth.oauth2.scopereadScopes of the internal client (several separated by commas or spaces). Empty: read
contexa.auth.oauth2.redirect-urihttp://localhost:8080Redirect URI registered when the internal client is first stored
contexa.auth.oauth2.authorized-urinoneAnother redirect URI registered with it
contexa.auth.oauth2.jwk-key-store-pathnonePKCS12 store with the token signing key. A plain path is read from the classpath; a file needs the file: prefix. Empty: a temporary RSA key on every start (ERROR log), so tokens from before a restart cannot be verified
contexa.auth.oauth2.jwk-key-store-passwordnoneKey store password
contexa.auth.oauth2.jwk-key-aliasnoneAlias of the key in the store. It is also the token's key ID
contexa.auth.oauth2.jwk-key-passwordnoneKey password. Empty: the store password
contexa.auth.internal.refresh-uri/api/refreshAddress where the browser gets a new access token. Registered when the authorization server runs in the same application (AUTHORIZATION_SERVER or COMBINED)
Startup stops when the stored internal client has another secret. The internal client is stored once, at first start; after that only its token lifetimes are updated. When the stored client does not accept the current client-secret, Contexa does not rewrite it silently but stops at startup. Change the stored client's secret, or remove that client so it is registered again. A signing key store written as a plain path such as /etc/… is looked up on the classpath and stops startup with KeyStore not found; for a file, add file:.

Sign-in and MFA addresses

The sign-in and MFA pages and processing addresses Contexa creates. An address written in a flow's DSL comes first; only addresses it leaves out use these settings. With several named MFA flows, each flow's addresses can carry a prefix. The logout processing address is fixed at /logout (with the flow prefix).

Passkey relying party (RP)

A browser creates a passkey bound to the site's domain. Passkeys of single-factor sign-in and of MFA both use the values below, and so does the passkey of the step-up under HOST_OWNED. In production, set rp-id to the site domain and allowed-origins to the real https addresses.

SettingDefaultMeaning
contexa.auth.urls.factors.passkey.rp-idlocalhostRelying party ID (usually the site domain)
contexa.auth.urls.factors.passkey.rp-namecontexa-identityName shown to the user
contexa.auth.urls.factors.passkey.allowed-originsnoneOrigins passkeys are accepted from (commas only, no spaces). Empty: http://localhost:{server.port} (8080 with no port)

contexa.auth.mfa.challenge-timeout-ms300000This long after a factor verification starts, verification requests get 403 (MFA session expired) (ms, 5 minutes)

contexa.auth.mfa.otp-token-validity-seconds300Validity written in the OTT mail (converted to minutes). The real code validity is Spring Security's default of 5 minutes and is not changed by this setting
contexa.auth.mfa.metrics-enabledtruefalse: the MFA state change listener (MfaStateChangeListener) is not created
contexa.auth.ott.fail-on-email-errortrueAn OTT request fails when no mail sender is configured or the mail cannot be sent. false: the code is created and only the mail is skipped (warning log)
contexa.auth.ott.code-to-console(unset)Whether a code is written to the log as well as mailed, so that a sign-in finishes without a mail server; a mail that fails is then no failed sign-in. contexa.auth.ott.email-max-concurrent-sends64The most sign-in mails sent at one time. A mail is sent on the thread of the request that asked for it, so this is the most request threads a slow mail server can hold
contexa.auth.ott.email-send-wait-seconds5Seconds a request waits for a place among the mails being sent. After that it fails as an undelivered mail does
contexa.auth.ott.email-smtp-timeout-seconds0Time limit (seconds) of the connect, read and write of the SMTP conversation. 0 sets none, and mail goes out with the application's own spring.mail.* settings. The MFA attempts a blocked user goes through to have a block released are set not here but in Enforcement Modes and Decision Tuning. MFA pages and factors are in MFA.

Turning auto-configurations off

All are on by default. Turning one off means its beans are not created, so turn it off only when the application registers beans doing the same work itself.

SettingDefaultWhat it turns off
contexa.identity.statemachine.enabledtrueThe MFA state machine (needed by MFA flows)
contexa.identity.mfa.enabledtrueMFA policy evaluators and providers, MFA page generation
contexa.identity.security-core.enabledtrueThe authentication security core (including the bootstrap that builds the security chain)
contexa.identity.service.enabledtrueThe address provider, the OTT mail service, the MFA configuration API
contexa.identity.handler.enabledtrueThe OTT issue success handler and the session sign-in success and failure handlers (created only under CONTEXA_OWNED)
