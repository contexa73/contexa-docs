First Start and Deployment (Standalone · Distributed)

The settings you need to add Contexa to an application and start it (the dedicated database · capability checks · turning features on and off), and the settings for moving from standalone mode on one machine to distributed mode where several machines share state (Redis · Kafka). Cache, scheduled-job locking and tracing are here too.

At a glance

Turning Contexa on goes in the order below. After steps 1–3 it starts; from step 4 on you do what you need.

Turning it on

The dependency is one starter, ai.ctxa:spring-boot-starter-contexa. What it brings and what it leaves to the application:

PartContents
The starter bringsThe five Contexa modules (common · core · identity · iam · autoconfigure), Spring Security, the OAuth2 resource server · client · authorization server, the Spring AI 1.1.8 BOM
The application addsA chat model starter (one or more of OpenAI · Anthropic · Ollama), the pgvector vector store starter (spring-ai-starter-vector-store-pgvector). For distributed mode, Redis · Redisson · Kafka (Distributed mode)
Spring Boot3.x. Contexa is built on 3.5.4 and refuses to start on 4.x.

Contexa turns on when you put @EnableAISecurity on the main class. Without it, all of Contexa's auto-configuration is left out and it does not touch the application. With it, contexa.enabled: false makes the annotation import nothing, so everything is off again.

@SpringBootApplication
@EnableAISecurity                       // default mode = SecurityMode.SANDBOX
public class MyApplication { }

The annotation's mode sets the default for who owns login. The default SANDBOX leaves login to the application (HOST_OWNED); FULL gives it to Contexa (CONTEXA_OWNED). FULL also turns on Contexa taking over the application's database below. The difference between the two is in Adding Contexa to a Spring Boot Application; the hint attributes for finding the login object are in Connecting Your Existing Login.

Dedicated Contexa database (required)

Contexa keeps its own data, such as policies, decision records and evidence, in a PostgreSQL database separate from the application's. If contexa.datasource.url is empty, start-up stops with an IllegalStateException ("contexa.datasource.url must be configured for @EnableAISecurity").

On the first start Contexa creates its tables and default data in this database (contexa.iam.seed.enabled, default true). If only some of the tables exist, start-up stops. Sample accounts are added only with contexa.iam.seed.accounts.enabled: true (Authorization Policies).

Using the same URL as the application database

The default is a separate database. When contexa.datasource.url equals spring.datasource.url, start-up succeeds only if both conditions below hold; if either is missing, start-up stops.

  • allow-shared-application-datasource and shared-application-datasource-risk-accepted are both true
  • No active profile is prod · production (sharing is not allowed in production profiles)

Contexa taking over the application's database

contexa-owned-application: true (or @EnableAISecurity(mode = SecurityMode.FULL)) is for the case where Contexa runs the whole application. With it on:

  • If the application did not create its own DataSource bean, the application's default DataSource becomes the Contexa database. The default JdbcTemplate · TransactionTemplate also use the Contexa database.
  • The sharing check above is skipped even when the URLs are the same.
  • The default behavior of capability checks becomes "stop start-up when a required part is missing" (FAIL_FAST).
Do not turn it on for an existing application with its own database. The Contexa database may become the application's default database instead of its spring.datasource.*.

Which database the vector store uses

The vector store that holds past decision records is created by Spring AI's pgvector auto-configuration. That auto-configuration uses the application's default JdbcTemplate. The dedicated database's contexaJdbcTemplate is not a default candidate, so it is not used there. Therefore:

  • With contexa-owned-application: true, the default JdbcTemplate is the Contexa database, so the vector table is created in the Contexa database too.
  • Otherwise the vector table is created in the application's default database, which must be able to use pgvector.
  • To leave the application database as it is and keep only the vector table in the Contexa database, declare your own VectorStore bean built on contexaDataSource. When a bean of that type exists, Spring AI's auto-configuration backs off.

The pgvector table name · dimensions · automatic table creation are in Connecting AI Models.

Capability checks

Capability checks are not switches that turn features on. When start-up finishes, they check that the parts a decision needs (chat model · embedding model · vector store · learning · decision engine · bridge) were all created, and report a missing one as an ERROR log starting with [ContexaCapability] … or stop start-up.

contexa.capability.modeWhat it does
AUTO (default)Behaves as FAIL_FAST when Contexa runs the application (contexa-owned-application: true, or spring.application.name starts with contexa-), and as WARN for any other application.
WARNReports missing required parts only as ERROR logs. Start-up continues.
FAIL_FASTStops start-up when a required part is missing.
STRICTAlso reports problems of parts that are not required, and stops start-up when a required part is missing.
OFFNo checks.
SettingDefaultMeaningWhen to change
contexa.capability.modeAUTOTable aboveFAIL_FAST to stop a production start with missing parts
contexa.capability.required.<capability>noneOverrides whether one capability is required. Capability names: llm-runtime · embedding-runtime · rag-vector · security-learning · autonomous-decision · bridgeTo silence a capability you do not use, or to make one you need required
contexa.capability.expose-diagnostics-endpointtrueWith Actuator, creates the diagnostics endpoint (contexacapabilities)false to leave the endpoint out

With Actuator, GET /actuator/contexacapabilities shows the same result. Whether it is exposed over the web is decided by Spring Boot's management.endpoints.web.exposure.include.

Choosing standalone or distributed

The infrastructure mode (contexa.infrastructure.mode) decides where decision and learning state is kept. Either mode needs the dedicated database.

WhatStandaloneDistributed
User decision storeMemory (with a user count limit)Redis
Behavioral baseline · decision context · threat score · re-entry records · distributed lockMemoryRedis (needs a Redis template bean)
Passing events to analyzeHanded over directly inside the same JVMKafka (when Spring Kafka and a KafkaTemplate bean are present)
Telling in-flight responses about a BLOCKInside the same JVMAcross nodes when Redisson is present
MFA sessionHTTP session (even if the application has Redis)Redis (when a string Redis template is present)
Contexa cacheLocal cache (contexa.cache.type is always LOCAL)Redis cache (Cache)
Login MFA state machine (when Contexa owns login)MemoryRedis (when a Redisson bean and spring-statemachine-data-redis are present)
Redis · Kafka auto-configurationContexa's are left out. The application's Redis · Kafka auto-configuration is also left out unless the application writes its connection address (spring.data.redis.host · spring.kafka.bootstrap-servers and so on) itselfAll kept

If the application declares store beans itself (ZeroTrustActionRepository, BaselineDataStore, SecurityContextDataStore and so on), those implementations are used instead of memory even in standalone mode. When the application provides both the baseline store and the context store (SecurityContextDataStore), the standalone WARN does not appear either.

Moving to distributed mode

The Contexa starter does not bring Redis · Redisson · Kafka, so the application adds them.

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-redis'   // Lettuce
    implementation 'org.redisson:redisson:3.48.0'                              // the version Contexa is built with
    implementation 'org.springframework.kafka:spring-kafka'
}
contexa:
  infrastructure:
    mode: distributed
  datasource:
    url: jdbc:postgresql://db.internal:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
  security:
    zerotrust:
      redis:
        timeout: 5000          # milliseconds

spring:
  data:
    redis:
      host: redis.internal
      port: 6379
  kafka:
    bootstrap-servers: kafka.internal:9092
  • Contexa creates the Redis connection. In distributed mode Contexa builds a single-server Redis connection itself from spring.data.redis.host · port · password, and this connection becomes the application's default Redis connection. It uses contexa.security.zerotrust.redis.timeout, in milliseconds, as the connect · command · pool-wait time limit.
  • Redisson. If the application declares no RedissonClient bean, Contexa builds a single-server client from spring.data.redis.host · port. That client uses no password and no database number (database 0). For a Redis with a password, declare your own RedissonClient bean.
  • The Kafka connection uses Spring's spring.kafka.*. Events to analyze go to the topic security.events.<category>.<type> (for example security.events.authorization.method), and events that could not be handled go to the DLQ topic. A failed event is retried 3 times, 1 second apart.
SettingDefaultMeaningWhen to change
contexa.infrastructure.modeSTANDALONEstandalone or distributed (case does not matter)To run several machines
contexa.security.zerotrust.redis.timeout5000Connect · command · pool-wait time limit of the Redis connection in distributed mode (milliseconds). Writing 5 means 5 millisecondsWhen Redis is far or slow
contexa.security.kafka.topic.dlqsecurity-events-dlqTopic for events that could not be handledWhen you have topic naming rules
security.plane.kafka.group-idsecurity-plane-consumerGroup of the Kafka listener that receives events. The name does not start with contexaWhen the same Kafka is shared with another Contexa group
Writing security.plane.kafka.group-id leaves one ERROR line in the start-up log. It is the log Contexa writes when it treats security.plane. as a legacy prefix and creates an alias. The value is used for the listener group as written. contexa.security.plane.kafka.group-id is read by nothing and has no effect.

Decision engine throughput, such as the analysis queue · thread counts · time limits, is in Enforcement Modes and Decision Tuning.

Scheduled jobs across instances

So that scheduled jobs, such as deleting records past their retention, run only once across instances, Contexa locks them with the shedlock table in the Contexa database (ShedLock). It does no harm with one instance. Contexa brings ShedLock itself; locking turns on when the Contexa database is present.

SettingDefaultMeaningWhen to change
contexa.scheduler.lock.enabledtrueTurn scheduled-job locking on. The longest a lock is held is fixed at 5 minutesTo turn it off briefly during a database migration
contexa.scheduler.lock.use-database-timetrueUse the database clock for lock times (false uses the JVM clock)Test environments where the database and JVM time zones differ

Tracing (OpenTelemetry)

Contexa creates an OpenTelemetry SDK that exports traces (spans) over OTLP gRPC and registers it globally. There is no metrics export. It is on by default, so it tries to send to localhost:4317 even when there is no collector. Turn it off if you run no collector.

contexa.opentelemetry.enabledtruefalse gives an empty SDK that exports nothingWhen there is no collector

contexa.opentelemetry.sampling-probability1.0Share of traces kept (0–1)To reduce it under heavy traffic
