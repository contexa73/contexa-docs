First Start and Deployment (Standalone · Distributed)

This page explains the infrastructure settings you make when you add CONTEXA to an application, start it and deploy it to production. One is required: the dedicated CONTEXA database (DB). What depends on your deployment is the infrastructure mode (standalone or distributed): use distributed mode (Redis, and optionally Kafka) when you run several instances or need learning state to survive a restart. The cache, scheduled-job locking and feature switches can start on their defaults.

Overview

CONTEXA is turned on and deployed in the order below. After steps 1–3 the application starts. From step 4 on, you do each step when you need it.

This page uses three terms. A decision is the conclusion CONTEXA reaches after analyzing a user's request: ALLOW, CHALLENGE (additional authentication), ESCALATE (held for review) or BLOCK. A behavioral baseline is the record of a user's normal behavior patterns, which CONTEXA consults in later decisions. An instance is one JVM process running the application.

The settings on this page fall into four groups.

  • Required. The address and account of the dedicated CONTEXA database (Dedicated database). Without the address, start-up stops.
  • Chosen by deployment. The infrastructure mode (Choosing standalone or distributed). The default standalone keeps state in JVM memory, so it suits development and a single instance. With two or more instances, use distributed and connect Redis (required) and Kafka (optional).
  • Turn off only what you do not use. The feature switches (Turning features on and off), the admin console WebSocket and tracing (OpenTelemetry). Do not turn off a feature you use.
  • Keep the defaults. The database connection pool, cache lifetimes and scheduled-job locking. Change them only when you observe a problem.

Turning it on

The application declares one CONTEXA dependency, the starter ai.ctxa:spring-boot-starter-contexa. The table shows what the starter brings and what the application adds itself.

PartContents
The starter bringsThe five CONTEXA modules (common · core · identity · iam · autoconfigure), the OAuth2 resource server · client · authorization server, the Spring AI 1.1.8 BOM
The application addsSpring Security (spring-boot-starter-security), a chat model starter (one or more of OpenAI · Anthropic · Ollama), the pgvector vector store starter (spring-ai-starter-vector-store-pgvector). For distributed mode, Redis · Redisson · Kafka (Distributed mode)
Spring Boot3.x. CONTEXA is built on 3.5.4 and refuses to start on 4.x.

CONTEXA turns on when you put @EnableAISecurity on the main class. Without it, none of CONTEXA's auto-configuration applies, so the application is not affected by CONTEXA. With the annotation, setting contexa.enabled: false makes the annotation import nothing, and CONTEXA is off again.

@SpringBootApplication
@EnableAISecurity                       // default mode = SecurityMode.SANDBOX
public class MyApplication { }

The annotation's mode sets the default for who owns login. The default SANDBOX leaves login to the application (HOST_OWNED). FULL gives login to CONTEXA (CONTEXA_OWNED). When the application does not set spring.datasource.url, FULL also turns on CONTEXA taking over the application's database below. The difference between the two is in Adding CONTEXA to a Spring Boot Application. The hint attributes for finding the login object are in Connecting Your Existing Login.

Dedicated CONTEXA database (required)

CONTEXA keeps its own data, such as policies, decision records, audit records and sealed evidence, in a PostgreSQL database separate from the application's. Sealed evidence is the audit trail that stores the basis of a decision as a sealed evidence package. If contexa.datasource.url is empty, start-up stops with an IllegalStateException ("contexa.datasource.url must be configured for @EnableAISecurity").

The database account must be able to create the PostgreSQL extension vector. Unless you turn off automatic vector table creation (contexa.vectorstore.pgvector.initialize-schema, default true), it must also create hstore and uuid-ossp. On most servers only a database administrator can create extensions, so the administrator must run CREATE EXTENSION before deployment.

At start-up CONTEXA connects to the dedicated database and checks this permission. If the database does not answer, CONTEXA retries once a second for 5 seconds. If it answers but the account lacks the permission, CONTEXA does not retry and treats it as a failure at once. The result of a failure depends on who owns login.

  • When the application owns login, the default (HOST_OWNED), the application starts without CONTEXA and logs an ERROR (Contexa's database cannot be used). CONTEXA turns on only after you fix the cause and restart the application.
  • When CONTEXA owns login (CONTEXA_OWNED), nobody could sign in without CONTEXA, so start-up fails.

On the first start CONTEXA creates its tables and default data in this database (contexa.iam.seed.enabled, default true). A database with only some of the tables is refused. Sample accounts are on even with no setting. In a database that has no user account at all, five sample accounts with a shared password are added. They are not added in either of these cases. In a database that already has user accounts they are not added even when you state contexa.iam.seed.accounts.enabled: true.

  • You set an administrator password with contexa.iam.seed.admin.password.
  • You set contexa.iam.seed.accounts.enabled: false.

In production, set an administrator password or turn the sample accounts off with contexa.iam.seed.accounts.enabled: false, so that accounts with a shared password are never created. When the sample accounts are created, the start-up log shows a WARN. Details are in Authorization Policies.

Using the same URL as the application database

The default is a CONTEXA database separate from the application database. When contexa.datasource.url and spring.datasource.url are the same string, start-up succeeds only if both conditions below hold. If either fails, start-up stops. When the two URLs differ as strings, this check does not run, even if they point to the same database.

  • allow-shared-application-datasource and shared-application-datasource-risk-accepted are both true.
  • No active profile is prod · production. In production profiles sharing is refused whatever the two settings say.

CONTEXA taking over the application's database

contexa-owned-application: true (or @EnableAISecurity(mode = SecurityMode.FULL) for an application with no database URL of its own) is for the case where CONTEXA runs the whole application. With it on:

  • If the application did not create its own DataSource bean, the CONTEXA database becomes the application's default DataSource. The default JdbcTemplate · TransactionTemplate also use the CONTEXA database.
  • The sharing check above is skipped even when the URLs are the same.
  • The default behavior of capability checks becomes "stop start-up when a required part is missing" (FAIL_FAST).
  • If the application sets its own spring.datasource.url and you still state true, the application's spring.datasource is not used. The start-up log shows one WARN.
Do not turn it on for an existing application with its own database. Even when the application sets its own database URL, stating true makes the CONTEXA database the application's default database instead of its spring.datasource.*.

Which database the vector store uses

The vector store that holds past decision records is always created in the dedicated CONTEXA database. It is the VectorStore bean (contexaVectorStore) that CONTEXA builds itself on the contexaJdbcTemplate, which is made from the dedicated database connection (contexaDataSource). It does not use the application's default JdbcTemplate, which Spring AI's pgvector auto-configuration uses. Therefore:

  • With contexa-owned-application: true or with false, the vector table is created in the CONTEXA database. This holds even when the application's default JdbcTemplate is the CONTEXA database.
  • CONTEXA creates no vector table in the application database.
  • If the application uses its own VectorStore through a pgvector starter, that store belongs to the application. CONTEXA's decision records do not go to it.

The pgvector table name · dimensions · automatic table creation are in Connecting AI Models.

Capability checks

Capability checks are not switches that turn features on. When start-up finishes, they check that the parts a decision needs (chat model · embedding model · vector store · learning · decision engine · bridge) were all created. Choosing standalone or distributed

The infrastructure mode (contexa.infrastructure.mode) decides where decision and learning state is kept. Either mode needs the dedicated database.

If the application declares store beans itself (ZeroTrustActionRepository, BaselineDataStore, SecurityContextDataStore and so on), those implementations are used instead of memory even in standalone mode. When the application provides both the baseline store and the context store (SecurityContextDataStore), the standalone WARN does not appear either.

When you restart an application in standalone mode, the following happens. In the operating modes that analyze decisions (SHADOW · ENFORCE), two WARN lines at start-up announce this.

  • The behavioral baselines and decision context are lost, so each user's learning starts again from the beginning.
  • ALLOW · CHALLENGE · ESCALATE decisions held in memory are lost, and the next request is analyzed again.
  • A BLOCK survives only when the CONTEXA database's blocked-user record (ctxa_blocked_user) still holds it in force. The restart stores it again. A block that is not in that record ends with the server.

Memory limits in standalone mode

Standalone mode keeps decision and learning state in the JVM heap, so it has limits. Past a limit, the oldest entries are released first.

Moving to distributed mode

Distributed mode (contexa.infrastructure.mode: distributed) keeps decision and learning state in Redis and spreads events to analyze through Kafka. The move needs libraries, connection settings and an application name. The CONTEXA starter does not bring the libraries, so the application adds them.

Required libraries and what happens without them

LibraryWhere CONTEXA uses itIf it is missing
spring-boot-starter-data-redisThe Redis connection and templates. Decisions · behavioral baselines · decision context · distributed locks · cache are kept in RedisStart-up is refused
org.redisson:redissonCONTEXA's own Redisson client. It carries BLOCK signals, policy and admin console change notices, and the locks and clean-up of MFA flowsStart-up is refused
spring-statemachine-data-redisStores the MFA state machine in Redis when CONTEXA owns loginStart-up is refused
spring-kafkaSpreads events to analyze between instancesThe application starts. Events are handled inside the same JVM and are not spread between instances

If any of the first three libraries is missing, distributed is refused at start. The console names the missing libraries and what to do. Add the libraries, or set contexa.infrastructure.mode=standalone again.

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-redis'   // Lettuce
    implementation 'org.redisson:redisson:3.48.0'                              // the version Contexa is built with
    implementation 'org.springframework.statemachine:spring-statemachine-data-redis'  // the starter sets the version
    implementation 'org.springframework.kafka:spring-kafka'
}
contexa:
  infrastructure:
    mode: distributed
  datasource:
    url: jdbc:postgresql://db.internal:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
  security:
    zerotrust:
      redis:
        timeout: 5000          # milliseconds

spring:
  data:
    redis:
      host: redis.internal

Redisson brings a JCache provider with it. An application whose cache goes through JCache (javax.cache) may then fail to start. In that case, name the application's cache yourself, for example spring.cache.type=caffeine. If the application has a JCache provider of its own, name it with spring.cache.jcache.provider. CONTEXA does not change the application's cache settings. When the start fails, it prints the cause and what to set in the start-up log.

The Redis connection

  • CONTEXA uses the application's Redis connection as it is. CONTEXA's Redis templates attach to the connection that spring-boot-starter-data-redis builds from spring.data.redis.host · port and the rest of spring.data.redis.*. The address, user name, password, database number, TLS, Sentinel, pool and time limits all apply unchanged.
  • Access on a request has a time limit. When an application request reads Redis (a single server or Sentinel with Lettuce), a CONTEXA client of its own, made from the same connection settings, waits about one second. The application's own Redis client settings are not changed.
  • CONTEXA builds a connection only when the application has none. If there is no RedisConnectionFactory bean, CONTEXA builds a single-server connection from spring.data.redis.host · port · username · password · database. Only then does it use contexa.security.zerotrust.redis.timeout (default 5000), in milliseconds, as the connect · command · pool-wait time limit. When the application has set up its connection, this connection is not built.
  • Redisson uses a CONTEXA client of its own. Whether or not the application declares a RedissonClient bean, CONTEXA builds and uses its own client (contexaRedissonClient). If the application declares its own RedissonClient, CONTEXA does not use it, so you do not need to declare one for a Redis with a password. CONTEXA's client reads the user name, password, database number, TLS, single-server and Sentinel settings from spring.data.redis.*. It connects on first use, so a Redis that is down at start-up does not stop the application from starting. Its wait is the shorter of spring.data.redis.timeout and one second, and it does not retry.
  • Only a single server and Sentinel are supported. Redis Cluster is not supported in this release. With a cluster, the start-up log shows one ERROR (Redis Cluster is not supported in this release) and start-up goes on. Decisions are written by scripts over several keys, which a cluster can refuse, and a decision that is not stored is not applied.
  • Start-up checks that Redis answers. CONTEXA tries to connect to a single-server Redis once a second for 5 seconds. If there is still no answer and the application owns login (HOST_OWNED, the default), the application starts without CONTEXA and logs an ERROR (Contexa's Redis cannot be reached). CONTEXA turns on only after you restore Redis and restart the application. With Sentinel this check is not made.

The Kafka connection and topics

  • The connection settings are Spring's spring.kafka.*. CONTEXA builds its own producer, consumer and template (contexaKafkaTemplate) from them and does not change the application's Kafka beans. So the application does not need to declare a KafkaTemplate bean. The producer waits for all replicas to confirm (acks=all) and waits only a few seconds for a send.
  • Topic names. Events to analyze go to the topic ctxa.<application name>.security.events.<category>.<type> (for example ctxa.order-service.security.events.authorization.method), and events that could not be handled go to the DLQ topic. The application name is spring.application.name, lower-cased, with any character other than a-z, 0-9 and - written as _ and the hex of its bytes. Without a name the prefix is just ctxa. (ctxa.security.events.authorization.method).
  • Topic creation. At start CONTEXA makes only the topics it uses: the three event topics (authentication.mfa, authentication.success, authorization.method) and the DLQ topic. An event topic has 3 partitions and a 7-day retention, and its replica count follows the broker default. The DLQ topic has 1 partition, 1 replica and a 30-day retention. Topics an earlier version made are not deleted.
  • When a topic cannot be made. If spring.kafka.admin.auto-create: false is set, or the broker does not answer so that CONTEXA cannot make or check a topic, the start-up log shows one ERROR ([ContexaKafkaTopics] Kafka topics Contexa needs are missing) and start-up goes on. Until the topic exists, its events are not published and reach no analysis. In that case, create the topics beforehand.
  • Failed handling. When handling an event fails, CONTEXA retries 3 times, 1 second apart, and also sends the event to the DLQ topic. Each event carries the name of the application that sent it, so CONTEXA skips events of other applications and does not analyze them.

Sharing Redis and Kafka with other applications

CONTEXA tells its own data apart by spring.application.name. With a name, Redis keys start with ctxa:<name>:, Kafka topics follow the ctxa.<application name>. rule above, and the Kafka listener group carries the name. The instances of one application use the same name, so they see the same state.

Without a name, CONTEXA uses keys with no prefix and a shared listener group. Another application on the same Redis and Kafka then sees this application's blocks and events, and the reverse. The start-up log shows one INFO line about it. If you share Redis or Kafka with another application, you must set spring.application.name. With a Redis and Kafka of its own, nothing needs to change.

When Redis or the database does not answer

CONTEXA does not stop the application because a store is down. If Redis or the CONTEXA database does not answer while the application runs, this happens.

  1. The first request that meets the outage waits about one second. After that, requests go on without waiting for the store.
  2. CONTEXA logs one ERROR ([Contexa] Redis does not answer or [Contexa] Contexa's database does not answer), and while the outage lasts it logs an ERROR with the time without an answer every minute.
  3. Calls to protected methods (@Protectable) can go on without a decision. CONTEXA logs the number of calls that went on without a decision as an ERROR every minute, and writes it to the audit records when the database is back. A call to a sensitive resource whose policies could not be read is the exception: it is refused and requires additional authentication.
  4. When the store answers again, CONTEXA notices within a second and recovers by itself. You do not need to restart the application.

While a store is down, decision control is weaker. Put the ERROR logs above on an alert. In distributed mode, running Redis with Sentinel helps keep it available.

Scheduled jobs across instances

Scheduled jobs, such as deleting records past their retention, must run only once even when there are several instances. For this, CONTEXA locks them with the ctxa_shedlock table in the CONTEXA database (ShedLock). The lock does no harm with one instance. CONTEXA brings ShedLock itself, and locking turns on when the CONTEXA database is present.

Tracing (OpenTelemetry)

CONTEXA can create an OpenTelemetry SDK that exports traces (spans) over OTLP gRPC and register it for the whole JVM. There is no metrics export. It is off by default. It is off so that CONTEXA does not collide with an OpenTelemetry agent or SDK the application already has. Two things turn it on.

  1. The application adds io.opentelemetry:opentelemetry-sdk and io.opentelemetry:opentelemetry-exporter-otlp to its dependencies. The starter does not bring them, and without the classes this setting does not apply.
  2. Set contexa.opentelemetry.enabled: true and write the collector address. If you write no address, CONTEXA tries to send to localhost:4317, so a collector must be listening there.

The global OpenTelemetry can be registered only once per JVM. If one is already registered, CONTEXA logs one ERROR, leaves the global instance as it is, and uses only its own bean.

Checking the connection

When you meet one of these in the start-up log or on a screen, find its meaning and what to do in this table.

Start-up log · screenMeaning and what to do
contexa.datasource.url must be configured for @EnableAISecurityThe dedicated database URL is missing. Set the dedicated database.
contexa.datasource must not share …The URL equals the application database. See the conditions for sharing.
Contexa's database cannot be used (ERROR)The dedicated database cannot be reached, or its account cannot create the extensions. When the application owns login (the default), it has started without CONTEXA. Fix the cause the log names and restart the application.
[ContexaCapability] … (ERROR)A part a decision needs is missing. Add the part the log names (chat model · vector store and so on).
[Contexa] contexa.infrastructure.mode is standalone … (WARN)A notice that learning state (behavioral baselines · decision context) or the decisions in force are kept in memory in standalone mode. Two lines can appear. Fine to leave as it is during development.
contexa.infrastructure.mode is distributed, and the Redis client is not on the class pathDistributed mode was refused because a Redis library is missing. Add the library the log names, or go back to standalone. See Required libraries above.
Contexa's Redis cannot be reached (ERROR)The Redis of distributed mode cannot be reached. When the application owns login (the default), it has started without CONTEXA. Restore Redis and restart the application.
[Contexa] Redis Cluster is not supported in this release (ERROR)The application uses Redis Cluster. Switch to a single server or Sentinel.
[ContexaKafkaTopics] Kafka topics Contexa needs are missing (ERROR)A Kafka topic could not be made or checked. Create the topics beforehand, or fix the broker connection. See The Kafka connection and topics.
[Contexa] Redis does not answer · [Contexa] Contexa's database does not answer (ERROR)A store does not answer while the application runs. See When Redis or the database does not answer.
[Contexa] spring.application.name is not set … (INFO)The application has no name, so its Redis and Kafka names are shared. If you share the infrastructure with another application, set the name. See Sharing Redis and Kafka with other applications.
[Contexa] HOST_OWNED mode: no SecurityFilterChain is declared … (WARN)The application owns login but declares no SecurityFilterChain, so Spring Boot's default security is on. Declare one. The anyRequest().permitAll() the log suggests is safe for CONTEXA's paths, because CONTEXA protects its admin console itself (Adding CONTEXA to a Spring Boot Application). If the application has neither a chain nor login users, start-up is refused instead of showing this WARN.
