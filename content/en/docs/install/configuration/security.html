Operating Modes and Decision Tuning

These settings control how CONTEXA makes AI decisions and applies them to requests. Most applications only need to set the operating mode (contexa.security.zerotrust.mode). The other settings work with their defaults; adjust them in the matching section when a problem such as slow analysis or too little throughput appears. How a decision is made and applied is explained in Decision Engine and request-time enforcement.

What to set first, and what to tune later

Every setting on this page has a default, so no setting is required. The one thing to decide first is the operating mode for your stage of adoption. With no mode set, CONTEXA runs in enforcement mode (ENFORCE), so an application that adopts CONTEXA for the first time sets shadow mode (SHADOW) itself. Decisions also need a connected chat model and vector store (Prerequisites); the settings that connect models are in Connecting AI Models.

Tune the other settings only when a symptom appears in operation. The table points to the section to read for each situation.

The order in which a decision is made

One decision is made and applied in the order below. Request-time enforcement is the step in which a CONTEXA filter checks the decision stored for the user when a request arrives and turns it into a step-up, block or held-for-review response.

Choosing the operating mode

The operating mode (contexa.security.zerotrust.mode) decides whether CONTEXA makes decisions with the AI model, and whether it applies a decision to real requests. A decision is the AI's conclusion about one user's request: ALLOW, step-up authentication (CHALLENGE), held for review (ESCALATE) or BLOCK. When you first adopt CONTEXA, start in shadow mode (SHADOW), check the decisions, and then raise the mode to enforcement mode (ENFORCE). The differences between the three modes and the steps to raise the mode are in Start Safely in Shadow Mode; this section summarizes them in a table.

ModeAI analysisStore · apply decisionsLearningUse it when
DISABLEDNoNoNoYou do not use AI decisions
OBSERVEAn old name that is still accepted. The code reads it as DISABLED and logs a WARN at start.—
SHADOWYesKeeps decisions in the decision and audit records and in shadow memory (explained below the table). No request is blocked and no response is changedAllow decisions onlyThe first stage of adoption, to check the quality of decisions
ENFORCE (default)YesStores the decision and applies it from the same user's next requestOnly allow decisions that were actually appliedProduction

Precisely, AI analysis runs when enabled is on and the mode is SHADOW or ENFORCE. Storing and applying decisions runs only when enabled is on and the mode is ENFORCE.

  • Shadow memory is where shadow mode keeps its decisions, apart from the store that enforcement uses. The next request of the same user is answered from it, so the AI is not called again. No request is stopped because of it.
  • Some requests still wait for analysis inside the request in shadow mode. Immediate-decision methods (@Protectable(sync = true)) and AI agent requests with no decision on record wait for the analysis result inside the request. Even when the result is not allow, the request is not stopped.
  • Some calls are still rejected in shadow mode. When a user who is not signed in, or is anonymous, calls a @Protectable method, CONTEXA rejects the call in SHADOW and ENFORCE. It does not reject it in DISABLED, so changing the mode from DISABLED to SHADOW can reject such calls for the first time (What actually happens in SHADOW).
  • contexa.security.zerotrust.enabled: false turns off more than DISABLED. Besides not analyzing, it stops the receiver of analysis events and the step that applies decisions to the login context.
  • Where to read the results, what to check before moving to ENFORCE and how to roll back are in Where to look at the results, Moving to ENFORCE and Rolling back.

Changing it in the admin console

You can also change the operating mode in the admin console's system settings (/contexa/admin/system-settings). The change applies as soon as you save, without a restart, so use this way to change the mode on a running system. Two ways to change the mode, and which wins shows which of the saved value and YAML wins.

  • Once you save a mode, the saved value wins over YAML. At every start CONTEXA replaces contexa.security.zerotrust.mode with the saved value. Changing only YAML therefore does not change the mode; change it in the admin console.
  • Until you save a mode, the console shows the mode currently in effect, pre-filled. Saving only other settings, or saving with the mode field empty, stores no mode, so the YAML value keeps applying. When you choose a mode different from the one in effect, the saved value wins over YAML from then on.
  • When a mode is already stored and you save with the mode field empty, SHADOW is stored.
Lowering the mode pauses the restrictions already stored; it does not remove them. A restriction is a stored BLOCK, CHALLENGE or ESCALATE decision. @Protectable methods follow the operating mode: in shadow mode they only record a stored restriction, and in Disabled they do not check it. The two filters CONTEXA places in front of requests (step-up authentication and access control) also follow the mode. Both when the application owns sign-in (HOST_OWNED) and when CONTEXA owns it (CONTEXA_OWNED), they stop a request only when enabled is on and the mode is ENFORCE. A stored restriction stays and applies again when the mode returns to ENFORCE. It ends only when an administrator releases it or the decision's lifetime passes.

Decision time limits

These settings decide how long CONTEXA waits for a decision when the AI model is slow or does not answer. If analyses rarely end by timeout with the defaults, leave them. Analysis has two layers: when Layer 1 cannot decide (ESCALATE), Layer 2 decides again (Decision Engine). All time limits are in milliseconds.

With a slow model such as a local model, raise the Layer 1 and Layer 2 limits, the limit of one model call and the budget of the whole analysis event together, as in Examples by situation. If you raise only one value, a shorter limit elsewhere applies first.

Throughput and queues

CONTEXA puts each analysis request (decision event) in a queue, and a worker takes events from the queue and analyzes them with the AI model. These settings decide the size of the queue and how many analyses run at once. Tune them only when there are very many concurrent users or the queue repeatedly fills up.

The thread pool for AI model analysis starts at a base size of 32 threads and grows to at most 64. Only after it has reached its maximum do tasks wait in the 256 waiting places, and when those are all taken, new tasks are refused.

contexa.security.plane.agent.* is not an AI agent setting. It configures the analysis worker of CONTEXA's decision engine. The limits of an AI agent (an AI that calls on behalf of a user) are in Agent limits.

When a decision cannot be made

A request that Layer 1 cannot decide goes to Layer 2. When Layer 2 also picks held for review (ESCALATE) or fails, no further analysis follows and no person reviews the request, so CONTEXA ends the decision with a fallback action. The default fallback action is step-up authentication (CHALLENGE). The settings below set this fallback action.

SettingDefaultMeaningWhen to change
contexa.security.tiered.layer2.escalate-fallback-actionCHALLENGEThe final action used instead when the result of Layer 2 stays held for review (ESCALATE), because it picked held for review or the analysis failed. Writing ESCALATE or PENDING_ANALYSIS gives CHALLENGETo treat undecided requests more strictly (BLOCK)
contexa.security.tiered.layer2.allow-escalate-final-actionfalseWith true, the held for review of Layer 2 is stored as it is instead of being replaced by the fallback action. How later requests are handled is in request-time enforcementTo keep undecided requests held for review with no fallback action
contexa.security.coldpath.max-escalation-windows10000Most counting windows that overload protection keeps, one per scope and scenario. Past it, the windows idle the longest are removed firstWhen there are very many scopes

Overload protection skips Layer 2 in a scope and scenario where held for review comes out in large numbers. The scope is the organization named in the event (the user when there is none, and the connecting IP when there is no user either), and the scenario is the scenario value in the event (the request path when there is none). For each scope and scenario CONTEXA keeps one counting window that holds up to the last 100 analyses. Protection starts when both conditions below are met.

  1. 11 or more analyses of the same scope and scenario have been counted (the count starts again once it reaches 100).
  2. Over half of them are held for review.

A request that Layer 1 held for review then ends as step-up authentication (CHALLENGE) without Layer 2. The values 100, 11 and half are fixed in code.

Minimum-action rules

A minimum-action rule sets a floor under the action so that the model cannot give a weak action such as ALLOW in a risky situation. When the facts of a decision meet the condition of a rule below, the action the model gives must be the floor of that rule or a stronger one. Actions get stronger in this order: ALLOW, step-up authentication, held for review, BLOCK. The rules have two modes, OBSERVE and ENFORCE (these are modes of the minimum-action rules; they are not the legacy operating-mode name OBSERVE). In the table below, an unexplained difference is one that departs from the behavioral baseline and that no business record, such as an approval or a ticket, explains.

  • OBSERVE (default): a violation of a floor is only recorded.
  • ENFORCE: the system prompt states the floors to the model, and the model is asked once more when its answer is weaker than a floor. If the answer is still weaker, it becomes held for review.

Behavioral baseline learning

The behavioral baseline is the reference of normal behavior that CONTEXA learns for each user and organization: working hours, devices, networks and targets. CONTEXA gives the baseline to the model as facts in later decisions, and the model evaluates whether a request departs from it. Only allow decisions are learned: in enforcement mode the ones actually applied, in shadow mode the ones kept in shadow memory (What is learned). Until enough requests are learned, a baseline is not yet established. A personal baseline is established when three conditions are all met: the number of learned requests, the period they span, and the share of new values.

Tuning the decision prompt

The decision prompt is the input sent to the AI model: the instructions and the grounds of the decision (the request, the behavioral baseline and past decision records). These settings decide which prompt version is used, how much goes into the prompt and in what format the answer is received. If decisions come out normally with the defaults, leave them. What the prompt contains is in The Decision Prompt. The model per analysis layer · output token limits · provider options are in Connecting AI Models.

Choosing the prompt version

Decisions use the prompt version chosen in the admin console (Prompt Versions). The setting below names the version to use when the console has chosen none. If neither exists, CONTEXA uses the newest version it provides. The earlier bundles v19, v20 and v21 no longer exist: a setting that still names one (such as 2026.10.30-v21.19) is logged once as a warning and is not used.

Client IP and trusted proxies

These settings are used when decision events, session fingerprints and IP access restrictions decide the client IP of a request. When a load balancer or gateway sits in front of the application, the connecting address of a request is the address of that device, so you register the device as a trusted proxy to read the real client IP. With the defaults (check on, list empty), X-Forwarded-For is not trusted and the connecting address is used. The setting is separate from contexa.bridge.network.trusted-proxies of the existing-login connection.

Receiving outside risk signals (off by default)

CONTEXA receives revocation and risk signals that other systems, such as an IdP, send (Security Event Tokens, OpenID SSF · CAEP · RISC) at POST /contexa/api/risk-signals. It handles a received signal as follows.

  • A signal whose signature verifies is answered with 202, and the subject's ALLOW decision or pending-analysis decision is removed so the next request is decided again.
  • A restriction already in force (BLOCK · ESCALATE · CHALLENGE) is not removed and stays, because a signal never weakens a decision.
  • A signal that ends sessions (session revoked · credential compromised · account disabled and so on) logs the user out of every session.
  • A signal that fails verification is answered with 400.

The application's authorization policy must allow the sender to reach this path.

Tuning request-time enforcement

Request-time enforcement is the step in which a CONTEXA filter checks the decision stored for the user when a request arrives, and asks for step-up authentication or stops the request when needed. The settings in this section fix details of that step, such as the lock that starts MFA, session and logout tracking and the initial threat score. Most applications keep the defaults.

The request-time filters run in both ownerships (who owns sign-in). When CONTEXA owns sign-in (CONTEXA_OWNED) they run inside the security chain CONTEXA builds. By default (HOST_OWNED) they run as servlet filters right after the application's security chain, and a CHALLENGE leads to CONTEXA's step-up screen (/contexa/step-up) instead of CONTEXA's MFA. The settings below about starting CONTEXA's MFA (the challenge.* lock) and about CONTEXA's own login context therefore act only under CONTEXA_OWNED. Stored decisions are also enforced before @Protectable methods. Responses per decision and how to release them are in request-time enforcement. The difference between the two ownerships is in Add to an Existing Spring Security Application.

Session identifier names

CONTEXA recognizes the session of a request in the order below. With this identifier it filters invalidated sessions and tracks sessions (CONTEXA_OWNED). If you have not renamed the session cookie or header, leave the settings in this section as they are.

  2. If there is none, it looks at the HTTP session.
