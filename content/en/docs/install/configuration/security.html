Enforcement Modes and Decision Tuning

Choose whether Contexa makes and applies decisions (the enforcement mode), and tune request-time enforcement, decision time and throughput, the decision prompt, minimum-action rules and behavioral baseline learning with settings. How a decision is made and applied is explained in Decision Engine and request-time enforcement.

At a glance

The path of one decision, and the section of this page that controls each point on it.

Choosing the enforcement mode

The enforcement mode (contexa.security.zerotrust.mode) decides whether decisions are made with the AI model, and whether a decision is stored and applied from the next request.

ModeAI analysisStore · apply decisionsLearningUse it when
DISABLEDNoNoNoYou do not use decisions
OBSERVEIn the current code it behaves exactly like DISABLED. Only the admin console monitor label differs.—
SHADOWYesDecisions go to the observation and audit records only; nothing is stored, blocked or changed in responsesNoWatching decisions in the first stage of adoption
ENFORCE (default)YesStored and applied from the same user's next requestOnly allow decisions that were actually appliedOperation

Precisely, AI analysis happens when enabled is on and the mode is SHADOW · ENFORCE, and storing · applying decisions only when enabled is on and the mode is ENFORCE.

  • Some requests still wait in shadow mode. Immediate-decision methods (@Protectable(sync = true)) and agent requests with no decision on record are analyzed inside the request. Even when the result is not allow, they are not stopped.
  • contexa.security.zerotrust.enabled: false turns off more than DISABLED. Besides not analyzing, it stops the receiver of analysis events and the step that applies decisions to the login context.
  • The order of raising the mode step by step is in Starting safely with enforcement modes.
contexa:
  security:
    zerotrust:
      mode: SHADOW     # watch first, then ENFORCE
SettingDefaultMeaningWhen to change
contexa.security.zerotrust.enabledtrueTurns zero trust decisions on as a wholeTo stop Contexa decisions entirely
contexa.security.zerotrust.modeENFORCEDISABLED · OBSERVE · SHADOW · ENFORCETo match the adoption stage

Changing it in the admin console

You can also change the enforcement mode in the admin console's system settings (/contexa/admin/system-settings). It applies as soon as you save, without a restart.

  • Once saved, the saved value wins over YAML from then on. Every start-up replaces contexa.security.zerotrust.mode with the saved value. Changing only YAML does not change the mode; change it in the console.
  • Until you save for the first time, the console shows the current mode pre-filled. Saving with the mode field empty makes it SHADOW.
Lowering the mode pauses restrictions already stored; it does not remove them. @Protectable methods follow the mode (in shadow mode they only record a stored restriction; in Disabled · Observe they do not look), and so do the two request-time filters (step-up authentication · access control) in both ownerships: unless enabled is on and the mode is ENFORCE, they stop nothing. A BLOCK · CHALLENGE · ESCALATE already stored stays and applies again when the mode returns to ENFORCE, until an administrator releases it or the decision's lifetime passes.

Tuning request-time enforcement

The request-time filters run in both ownerships. When Contexa owns login (CONTEXA_OWNED) they run inside the security chain Contexa builds; by default (HOST_OWNED) they run as servlet filters right after the application's security chain, and a CHALLENGE goes to Contexa's step-up instead of Contexa's MFA, so the settings below about starting Contexa's MFA (the challenge.* lock) and about Contexa's own login context act only under CONTEXA_OWNED. Decisions are enforced before @Protectable methods as well. Responses per decision and how to release them are in request-time enforcement.

Tuning the decision prompt

Decide what and how much is sent to the AI model, and which prompt bundle is used. What the bundles contain is in Decision Prompts and Bundles. The model per layer · output token limits · provider options are in Connecting AI Models.

Receiving outside risk signals (off by default)

Receives revocation · risk signals other systems send (Security Event Tokens, OpenID SSF · CAEP · RISC) at POST /contexa/api/risk-signals. A signal whose signature verifies is answered with 202, and the subject's decision is removed so the next request is decided again. A restriction already in force (BLOCK · ESCALATE · CHALLENGE) stays. A signal that ends sessions (session revoked · credential compromised · account disabled and so on) logs the user out of every session. A signal that fails verification is answered with 400. The application's authorization policy must let the sender reach this path.
