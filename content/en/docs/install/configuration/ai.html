Connecting AI Models

CONTEXA makes a decision for each protected request by having an AI model analyze it. CONTEXA does not connect to a model provider itself: it uses the models that the Spring AI starters in your application create, so connecting a model means adding the provider's Spring AI starter and API key to your application. You must settle three things: the chat model provider (the model that makes decisions), the embedding model provider (the model that finds similar past decision records), and the dedicated CONTEXA database with its vector store. Every other setting works with its default. This page explains how to connect and choose the models, and the concurrency limits for model servers.

What this page sets

CONTEXA does not call a model provider by itself. It gathers the Spring AI chat and embedding model beans of the application, names them, and at startup picks one primary chat model and one embedding model. A decision call uses the model set for its layer, or the primary chat model when none is set. This page centres on the settings; how a model is resolved is described in detail in the Model Provider reference (how each request gets its model).

The terms used on this page:

  • Provider: the party that supplies a model. This page covers openai, anthropic and ollama.
  • Model bean: a chat model or embedding model object that Spring AI creates in the application.
  • Chat model: the AI model that reads the facts of a request and answers with a decision: ALLOW, step-up authentication (CHALLENGE), held for review (ESCALATE) or BLOCK.
  • Embedding model: the AI model that turns a document into an array of numbers (a vector). It is used to search for similar past decision records.
  • Layer 1 and Layer 2 (layers): the two stages that make a decision. Layer 1 decides the request. Only a request that gets ESCALATE (an answer meaning that the facts alone cannot settle the decision) goes to Layer 2, which decides it again. This page also calls the two stages layers.
The application starts without a chat model. With no chat model at all, CONTEXA starts but cannot make decisions, and protected requests stay in pending analysis (PENDING_ANALYSIS). The capability check in the startup log ([ContexaCapability] llm-runtime and embedding-runtime) names the model beans that were not created. In a CONTEXA-owned application (FAIL_FAST) this check stops startup (Capability check). How to read the log is in Startup log messages and what to do.

Connecting a provider

You connect a provider through the application's Spring AI settings. The CONTEXA starter brings no model provider, and CONTEXA has no provider keys such as contexa.llm.openai.*. CONTEXA is built with Spring AI 1.1.8. Connect a provider in this order:

  1. Add the Spring AI starter of the provider you use to the application's dependencies (table below).
  2. Put the API key and the model name in the Spring AI settings (spring.ai.*).
  3. Set the address of the dedicated CONTEXA database (contexa.datasource.url). It is always required, whatever the model.
  4. Start the application and read the log. Check that there is no capability ERROR ([ContexaCapability]) and that the INFO log shows Embedding vector dimension verified (how to read the log: Messages and what to do).

OpenAIorg.springframework.ai:spring-ai-starter-model-openaiChat spring.ai.openai.chat.options.model, embedding spring.ai.openai.embedding.options.model
Anthropicorg.springframework.ai:spring-ai-starter-model-anthropicChat spring.ai.anthropic.chat.options.model
Ollamaorg.springframework.ai:spring-ai-starter-model-ollama, or the CONTEXA connectionChat spring.ai.ollama.chat.options.model, embedding spring.ai.ollama.embedding.options.model

A start with OpenAI alone. OpenAI supplies both a chat model and an embedding model, so this one setting connects both. When you set no embedding model name, Spring AI's default embedding model is used (Embedding model and vector dimension). contexa.datasource.url is the address of CONTEXA's own database, always required whatever the model.

spring:
  ai:
    openai:

  datasource:
    url: jdbc:postgresql://localhost:5432/contexa

  • With several providers every model is listed, and one primary chat model is picked by the rules of the next section.
  • Choosing the Spring AI model auto-configuration. Spring AI turns on the chat auto-configuration of every starter. When contexa.llm.selection.chat.priority names one provider (openai, anthropic or ollama), CONTEXA sets the default of spring.ai.model.chat to that provider, so the Spring AI chat auto-configuration of the other providers stays off. It sets spring.ai.model.embedding to the first provider of contexa.llm.selection.embedding.priority as well. Values the application sets for spring.ai.model.* win. CONTEXA does not turn off the image, speech and moderation model auto-configurations; to turn them off, the application sets none on the matching keys.
  • The temperature and seed of a decision call do not come from the Spring AI settings. The temperature sets how random an answer is, and the seed is the starting number that makes the same input give the same answer. A decision call carries contexa.security.tiered.determinism.temperature (0.0 by default) and seed (1 by default) on every call. Change them in Operating Modes and Decision Tuning.
  • contexa.llm.enabled: false turns off the whole CONTEXA LLM auto-configuration.

Choosing the primary chat model

At startup CONTEXA makes one chat model the primary chat model (bean name primaryChatModel). Decisions with no layer model and the calls of CONTEXA's AI pipeline use it. contexa.llm.selection.chat.mode sets how it is picked. With one provider, keep the default (dynamic-priority). With more than one provider, choose one of the three methods below.

ValueHow it picksWhen startup stops
dynamic-priority (default)Goes through the providers of the priority list in order and picks the first model whose bean can be created. When no model of a listed provider can be used, it tries the models of providers not in the list in turn (selection order).Model beans exist but none can be created
fixedUses only the models of the one provider in priority. It never moves to another provider.priority names more than one provider, or that provider has no model
spring-primaryThe one model marked primary (primary: true in a binding, or a @Primary bean). With a single model, that model.More than one primary, or several models and no primary

Among models of the same provider, the one marked primary comes first, then name order.

How dynamic-priority picks the model

The default, dynamic-priority, picks the primary chat model in this order:

  1. It splits the priority value at commas, turns it to lower case and merges repeated providers. The default is openai,anthropic,ollama.
  2. Starting with the first provider in the list, it tries to create the model beans classified under that provider, one by one. The primary-marked bean comes first, then name order (the binding key or the bean name). The first model that can be created becomes the primary chat model.
  3. A bean that cannot be created is skipped with the WARN log LLM runtime provider '<provider>' binding '<bean>' is not ready: .... It continues with the next bean of the same provider, then the next provider. The end of the log line is the reason it was skipped (a missing API key, a wrong address and so on).
  4. When no model of a listed provider is obtained, it tries every model bean, including providers not in the list, the same way (primary first, then provider name, then binding key). The WARN log of this step is LLM runtime binding '<bean>' is not ready: ....
  5. When no bean can be created, startup stops with the error of the first bean that failed.
Write the mode value in lower case with hyphens. Write dynamic-priority, fixed or spring-primary. CONTEXA uses this value as a condition to create the primary chat model bean. A name with underscores such as DYNAMIC_PRIORITY matches no condition, so the primary chat model is not created, with no error. When model beans exist but the Missing beans line of the capability check names UnifiedLLMOrchestrator, check the spelling of the mode value first.
  • The choice is made once, at startup. When a provider call fails while running, CONTEXA does not call another model instead. Transient errors such as a dropped connection, 429 or 503 are retried on the same model up to 4 times. Each retry writes a WARN log (Retry #number - RequestId: ...), and when all fail an ERROR log (failed after 4 retries) is written. What happens to a decision that never gets an answer is in Decision Engine.
  • The old setting contexa.llm.chat-model-priority is used only when priority is set to an empty value.
# Anthropic models only (added to your existing settings)
contexa:
  llm:
    selection:
      chat:
        mode: fixed
        priority: anthropic

Layer 1 and Layer 2 models

Most decisions end at Layer 1; only requests where Layer 1 answers ESCALATE go to Layer 2 (Decision Engine). Each layer can use its own model, for example a fast, low-cost model for Layer 1 and a more careful one for Layer 2. When you set none, both layers use the primary chat model.

# When the primary chat model is OpenAI (added to your existing settings)
contexa:
  security:
    tiered:
      llm:
        layer1:
          model: gpt-4o-mini
        layer2:
          model: gpt-4o
          backup:
            model: gpt-4o-mini

A layer model name becomes a real model in this order:

  1. Look for a model with the same name. When the name equals a name of a listed model (bean name, binding key, model name or alias), that model is used.
  2. When no model has the name, copy the primary chat model. The copy differs only in the model name. The copy works for the OpenAI chat model (mutate()) and for the Anthropic chat model (CONTEXA builds the copy again with the same client and default options). The Ollama chat model cannot be copied. To use such models per layer, name them with a binding (for Ollama, see below).
  3. When both fail, the layer model cannot be used. Startup goes on and one ERROR line is written (below).

For each layer model that cannot be used, one ERROR line is written at startup. Its format:

[TieredLayerModel] contexa.security.tiered.llm.layer2.model '<the name you set>' cannot be used, so layer 2 runs on '<the model used instead>': no chat runtime binding has this model id and the primary chat model cannot be copied with it. Bind a chat model with contexa.llm.bindings.chat to run it.
  • The model used instead is the layer's backup model, or the model name of the primary chat model when the backup cannot be used either. With no chat model at all the line says no chat model.
  • When you see this line, give the name you set to a model as a binding alias or model name.
  • The check runs only when the operating mode is shadow mode (SHADOW) or enforcement mode (ENFORCE). In off (DISABLED) neither layer runs, so no line is written.
  • A backup model is used only when the layer model is set, and it is not checked at startup. When the backup cannot be made at call time either, the primary chat model is used.

contexa.security.tiered.llm.layer2.modelnoneLayer 2 model. Empty: the primary chat model
contexa.security.tiered.llm.layer1.backup.modelnoneModel used when the Layer 1 model cannot be used

Naming models (bindings)

CONTEXA lists every chat and embedding model bean of the application by itself. An entry of the list (a binding) consists of a bean name, a provider, a model name, aliases and a primary mark. With no setting, a model can be found by its bean name, its provider (inferred from the bean class and name) and its model name (the provider's spring.ai.…options.model, else the bean name). contexa.llm.bindings corrects an entry of this list or adds aliases (more names that a layer model setting can use). When the application has one model bean, or no name needs to change, set nothing.

SettingDefaultMeaning
contexa.llm.bindings.chat.<name>.bean-namenoneThe model bean it applies to. Empty: the bean whose name equals <name>
contexa.llm.bindings.chat.<name>.providernoneThe provider. Empty: inferred from the bean class and name (ollama, anthropic, openai, gemini, mistral, bedrock, huggingface, otherwise spring)
contexa.llm.bindings.chat.<name>.model-idnoneThe model name. Empty: the key in the provider table above, else the bean name
contexa.llm.bindings.chat.<name>.aliases[]More names. A layer model setting can use them
contexa.llm.bindings.chat.<name>.enabledtruefalse: this setting is not used. The bean stays in the list under its own name
contexa.llm.bindings.chat.<name>.primaryfalsePicked first among models of the same provider, and the choice of spring-primary mode

For embedding models, write the same fields under contexa.llm.bindings.embedding.<name>.…. The providers whose embedding model name is read from a key are OpenAI and Ollama only.

  • Overlapping names stop startup. No bean name, binding key or alias may belong to two different models. The log is Duplicate chat runtime selector '<name>' is mapped by multiple bindings: ... (embedding for embedding models). Give the models different names.
  • When only the model name overlaps. Two model beans of the same provider that both take their model name from the same key have the same model name. That alone does not stop startup. But when you name a layer model with that model name, CONTEXA cannot tell which bean is meant and raises an error (... is the model of several of the application's beans ...). Give the two beans different model-id values, and refer to a model by its bean name or binding key.
  • An alias is a name to pick by. An OpenAI or Anthropic model picked by an alias is still called with the model set on its bean. Only for Ollama does the alias become the model of the call (below).
  • When bean-name names a bean that does not exist, a WARN log (Configured LLM binding '<key>' references missing bean '<bean>') is written and the setting is skipped.

Example: keep OpenAI as the primary chat model and run only Layer 2 on an Anthropic model. anthropicChatModel is the bean name the Spring AI Anthropic starter creates.

# Added to your existing settings
spring:
  ai:
    anthropic:
      api-key: ${ANTHROPIC_API_KEY}

contexa:
  llm:
    bindings:
      chat:
        anthropicChatModel:
          aliases: [expert]
  security:
    tiered:
      llm:
        layer2:
          model: expert

Using a local Ollama

Ollama is a self-hosted provider: it runs models on a server that you operate. It can be connected to CONTEXA in two ways. Choose one.

The CONTEXA connection is on when contexa.llm.chat.ollama.base-url is set (with the Ollama library in the application). Chat and embedding use the same Ollama server, and with no model set chat uses qwen3:8b and embedding uses mxbai-embed-large. The example below sets both the chat and the embedding provider to ollama (the two priority keys). A start with Ollama alone:

contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
  llm:
    chat:
      ollama:
        base-url: http://localhost:11434
        model: qwen3:8b
        keep-alive: 30m
    selection:
      chat:
        priority: ollama
      embedding:
        priority: ollama

An Ollama chat model cannot be copied, so name the layer models as aliases of the Ollama chat bean. An Ollama call sends the picked name as its model, so another model of the same server is used. Download that model to the Ollama server first.

  security:

      llm:

          model: qwen3:8b
        layer2:
          model: qwen3:14b

How many calls a model server takes

A model server can process only a set number of requests at once. To stay within that limit, CONTEXA passes every call it makes to a model server through one concurrency limiter per server (the gate). A server is a provider and an address. The decisions of both layers, the AI pipelines and the embeddings of the vector store all pass the gate. A call over the limit waits at the gate instead of piling up at the server.

  • A self-hosted server (Ollama, or an address on this host or a private network) runs 2 calls at once and one model at a time, because CONTEXA assumes the server holds only one model in memory. A call for another model, such as an embedding while decisions run, goes in when the running calls are done. A remote provider runs 16 calls at once.
  • Embeddings go in before waiting decision calls. A call that is in is never cut.
  • The time limits of model calls and of vector store writes and searches count from the moment the call passes the gate. The wait at the gate is bounded by the event processing limit (contexa.security.plane.agent.event-timeout-ms); a call that gets no turn within it ends as MODEL_SERVER_BUSY. This is recorded as a defined outcome, not as a server failure. When it appears often, check whether the server can really run more requests in parallel, and if so set the concurrency in the table below to that number.
  • After a rate limit (429), an overload (529) or a server that is unavailable for a while (503), calls to that server pause for 2 s, then 4, 8 and 12 s while it keeps answering so, and the call is sent again when its turn comes.

Embedding model and vector dimension

The embedding model turns documents such as past decision records into vectors (arrays of numbers) to store and search. The length of a vector is its dimension, and each model has its own. The stored vectors must have the model's dimension, so embedding is fixed to one provider. The embedding provider is openai or ollama. The embedding model is picked in this order (fixed, the default):

  1. It reads contexa.llm.selection.embedding.priority. The default is openai. Startup stops when the value does not name exactly one provider.
  2. It uses the first embedding model bean of that provider that can be created. The primary-marked bean comes first, then name order.
  3. When that provider has no embedding model, it uses the first other embedding model bean that can be created.
SettingDefaultMeaning
contexa.llm.selection.embedding.modefixedfixed: the model of the priority provider first, else another embedding model. spring-primary: the model marked primary. dynamic-priority cannot be used (startup stops)
contexa.llm.selection.embedding.priorityopenaiThe one embedding provider. Startup stops when more than one is named
contexa.llm.embedding.dimensions1024Embedding dimension. Used to set the dimension only when you set it (step 2 below)
contexa.llm.embedding.ollama.dimensions1024Ollama embedding dimension. Used only when you set it (step 3 below)

How the dimension is decided

CONTEXA decides the vector dimension in the order below. The first item that has a value wins.

  1. The value of contexa.vectorstore.pgvector.dimensions, when you set it
  2. The value of contexa.llm.embedding.dimensions, when you set it
  3. The provider's dimension key: spring.ai.openai.embedding.options.dimensions for OpenAI, contexa.llm.embedding.ollama.dimensions (or spring.ai.ollama.embedding.options.dimensions) for Ollama
  4. The model's value when CONTEXA knows the model: 1536 for OpenAI text-embedding-ada-002 and text-embedding-3-small, 3072 for text-embedding-3-large, 1024 for Ollama mxbai-embed-large and bge-m3
  5. For an unknown model with none of the values above, startup stops. Set that model's dimension in both contexa.llm.embedding.dimensions and contexa.vectorstore.pgvector.dimensions.

The embedding model and dimension for OpenAI:

  • CONTEXA puts no default on spring.ai.openai.embedding.options.model or dimensions; it follows your application's embedding model.
  • OpenAI with no model named is Spring AI's default text-embedding-ada-002 (1536 dimensions), and a dimensions value you set is used as it is.
  • An OpenAI installation by contexa init writes text-embedding-3-small (1536) into the settings file.
  • With no provider named in contexa.llm.selection.embedding.priority or spring.ai.model.embedding, CONTEXA takes the provider for OpenAI only when your application has the OpenAI embedding model class.

Three cases change what startup does:

  • A new database: the vector column is created with the size of the model in use.
  • Above 2000 dimensions: a pgvector HNSW index holds up to 2000, so startup is refused (when initialize-schema is true and the index is HNSW). The log begins with The vector store cannot create its index: an HNSW index holds at most 2000 dimensions ... and says what to do. Configure a smaller output (for example spring.ai.openai.embedding.options.dimensions=1536 with text-embedding-3-large), or create the table yourself and set contexa.vectorstore.pgvector.initialize-schema=false.
  • An OpenAI installation from an earlier version: its table has 1024 dimensions, so startup is refused, and the dimension mismatch log ends with A store made by an earlier Contexa keeps its vectors with .... With the two lines below it stays as it is, with nothing embedded again.
spring.ai.openai.embedding.options.model=text-embedding-3-small
spring.ai.openai.embedding.options.dimensions=1024
A changed dimension no longer fits the stored vectors. At startup CONTEXA compares the dimension of the embedding model in use, the configured vector store dimension and the dimension of an existing vector table (ctxa_vector_store by default), and stops when any differs. To change the dimension, create the table again or embed the documents again. When they match, the startup log shows the INFO line Embedding vector dimension verified: provider=…, model=…, dimension=…. The real line ends with an extra source=… (what decided the dimension).

Vector store (pgvector)

The vector store holds embedding vectors with their documents and searches for similar documents by similarity. CONTEXA builds it on the pgvector extension of PostgreSQL. Vectors are stored in the vector store bean (contexaVectorStore) that CONTEXA builds itself on the dedicated CONTEXA database (contexaJdbcTemplate). It does not use your application's VectorStore bean, and CONTEXA creates nothing in your application's database (dependencies in Installation Guide).

Write its settings as contexa.vectorstore.pgvector.*. CONTEXA's store reads only these keys; spring.ai.vectorstore.pgvector.* belongs to your application's own Spring AI store and does not apply to CONTEXA's.

Retrying failed stores

A document whose vector store failed waits in an in-memory queue and is stored again in the background, so that an outage of a few minutes does not lose learning records. The queue is lost on restart; when the documents must outlive a restart, the application registers its own FailedDocumentSink bean.

SettingDefaultMeaning
contexa.vectorstore.retry.enabledtruefalse: a failed store is only returned to the caller as an error
contexa.vectorstore.retry.queue-size2000Most waiting documents. When full, the oldest waiting document is dropped
contexa.vectorstore.retry.max-attempts20Given up after this many tries
contexa.vectorstore.retry.max-age1hGiven up this long after the first failure
contexa.vectorstore.retry.initial-delay10sWait before the first retry; it doubles with each failure
contexa.vectorstore.retry.max-delay5mLongest wait between two retries
contexa.vectorstore.retry.batch-size20Documents one retry stores. Halved while retries fail, grows back after they succeed

Past records and context search (RAG)

RAG (Retrieval-Augmented Generation) searches for related documents before a question is sent to the model and sends them along with it. CONTEXA searches similar past decision records this way. contexa.rag.* sets the defaults the AI pipeline and the AI Lab services (behavior analysis, policy generation) use when they search the vector store, and how long past decision records are kept. How many past records Layer 1 and Layer 2 of the decision engine look up, and at what similarity, is set in Operating Modes and Decision Tuning. The defaults work as they are; check that the retention period (retention-days) matches your organization's retention policy.

The ChatClient CONTEXA calls models with carries advisors, and a streamed answer is searched for the marker where the final answer starts. The other way round, some cases start but produce no decisions: no chat model at all, or a mode value written with underscores so that no primary chat model was created. When models are not connected, check in this order:

  1. Find the ERROR [ContexaCapability] in the startup log and read Missing beans.
  2. When no chat model bean exists, check the provider starter and the spring.ai.* keys. When model beans exist but UnifiedLLMOrchestrator is missing, check the spelling of the mode value.
  3. When you set a layer model, check for the ERROR [TieredLayerModel].
  4. For a vector store error, read the dimension message and check the vector extension (Troubleshooting).
