Connecting AI Models

How to connect the chat and embedding models Contexa uses for decisions and for its AI pipeline. You connect the providers, choose the primary chat model and the Layer 1 and Layer 2 models, and set up the embedding model, the vector store and the search over past records.

At a glance

Contexa does not call a model provider by itself. It gathers the Spring AI chat and embedding model beans of the application, names them, and at startup picks one primary chat model and one embedding model. A decision call uses the model set for its layer, or the primary chat model when none is set. This page centres on the settings; how a model is resolved is described in detail in the Model Provider reference (how each request gets its model).

The application starts without any model. With no chat model Contexa starts but cannot make decisions, and users stay at pending analysis. The capability check in the startup log ([ContexaCapability] llm-runtime and embedding-runtime) names the missing model beans.

Connecting a provider

The Contexa starter brings no model provider. Add the Spring AI starter of each provider you use to the application's dependencies, and put the API key and model name in the Spring AI settings (spring.ai.*). Contexa has no provider keys such as contexa.llm.openai.*. Contexa is built with Spring AI 1.1.8.

ProviderDependency to addKey Contexa reads as the model name
OpenAIorg.springframework.ai:spring-ai-starter-model-openaiChat spring.ai.openai.chat.options.model, embedding spring.ai.openai.embedding.options.model
Anthropicorg.springframework.ai:spring-ai-starter-model-anthropicChat spring.ai.anthropic.chat.options.model
Ollamaorg.springframework.ai:spring-ai-starter-model-ollama, or the Contexa connectionChat spring.ai.ollama.chat.options.model, embedding spring.ai.ollama.embedding.options.model

A start with OpenAI alone. contexa.datasource.url is the address of Contexa's own database, always required whatever the model.

spring:
  ai:
    openai:
      api-key: ${OPENAI_API_KEY}
      chat:
        options:
          model: gpt-4o-mini

contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
  • With several providers every model is listed, and one primary chat model is picked by the rules of the next section.
  • Choosing the Spring AI model auto-configuration. When contexa.llm.selection.chat.priority names one provider (openai, anthropic or ollama), Contexa sets the default of spring.ai.model.chat to that provider, so the Spring AI chat auto-configuration of the other providers stays off. It sets spring.ai.model.embedding to the first provider of contexa.llm.selection.embedding.priority as well. When either is set, the image, speech and moderation model auto-configurations are turned off (none). Values the application sets for spring.ai.model.* win.
  • The temperature and seed of a decision call do not come from the Spring AI settings. A decision call carries contexa.security.tiered.determinism.temperature (0.0 by default) and seed (1 by default) on every call. Change them in Enforcement Modes and Decision Tuning.
  • contexa.llm.enabled: false turns off the whole Contexa LLM auto-configuration.

Choosing the primary chat model

At startup Contexa makes one chat model the primary chat model (bean name primaryChatModel). Decisions with no layer model and the calls of Contexa's AI pipeline use it. contexa.llm.selection.chat.mode sets how it is picked.

ValueHow it picksWhen startup stops
dynamic-priority (default)Goes through the providers of the priority list in order and picks the first model whose bean can be created. When no model of a listed provider exists, it tries the other providers' models in turn.Model beans exist but none can be created
fixedUses only the models of the one provider in priority. It never moves to another provider.priority names more than one provider, or that provider has no model
spring-primaryThe one model marked primary (primary: true in a binding, or a @Primary bean). With a single model, that model.More than one primary, or several models and no primary

Among models of the same provider, the one marked primary comes first, then name order.

Write the mode value in lower case with hyphens. Write dynamic-priority, fixed or spring-primary. Contexa compares this text as written to create the primary chat model bean, so a name with underscores such as DYNAMIC_PRIORITY leaves the primary chat model uncreated, with no error.
  • The choice is made once, at startup. When a provider call fails while running, Contexa does not call another model instead. Transient errors such as a dropped connection, 429 or 503 are retried on the same model up to 4 times. What happens to a decision that never gets an answer is in Decision Engine.
  • The old setting contexa.llm.chat-model-priority is used only when priority is set to an empty value.
# Anthropic models only (added to your existing settings)
contexa:
  llm:
    selection:
      chat:
        mode: fixed
        priority: anthropic
SettingDefaultMeaning
contexa.llm.enabledtrueThe whole Contexa LLM auto-configuration
contexa.llm.selection.chat.modedynamic-priorityHow the primary chat model is picked (table above)
contexa.llm.selection.chat.priorityopenai,anthropic,ollamaProvider order. With fixed, name one provider only

Layer 1 and Layer 2 models

Most decisions end at Layer 1; only requests where Layer 1 answers ESCALATE go to Layer 2 (Decision Engine). Each layer can use its own model, for example a fast and cheap model for Layer 1 and a more careful one for Layer 2.

# When the primary chat model is OpenAI (added to your existing settings)
contexa:
  security:
    tiered:
      llm:
        layer1:
          model: gpt-4o-mini
        layer2:
          model: gpt-4o
          backup:
            model: gpt-4o-mini
  • How a model name is resolved. When the name equals a name of a listed model (bean name, binding key, model name or alias), that model is used.
  • When no model has the name, the primary chat model is copied with only the model name changed. The copy works for the OpenAI chat model (mutate()) and for the Anthropic chat model (Contexa builds the copy again with the same client and default options). The Ollama chat model cannot be copied. To use such models per layer, name them with a binding (for Ollama, see below).
  • Startup goes on when a layer model cannot be made. At startup one ERROR line names the layer, the model that was set and the model that runs in its place (the backup model, else the primary chat model). When you see it, give that name to a model as a binding alias or model name. The check runs when there is a primary chat model.
  • A backup model is used only when the layer model is set, and it is not checked at startup. When the backup cannot be made at call time either, the primary chat model is used.
SettingDefaultMeaning
contexa.security.tiered.llm.layer1.modelnoneLayer 1 model. Empty: the primary chat model
contexa.security.tiered.llm.layer2.modelnoneLayer 2 model. Empty: the primary chat model
contexa.security.tiered.llm.layer1.backup.modelnoneModel used when the Layer 1 model cannot be used
contexa.security.tiered.llm.layer2.backup.modelnoneModel used when the Layer 2 model cannot be used
contexa.security.tiered.llm.tiered.layer1.timeout-msnoneTime limit (ms) of a Layer 1 streaming call. Empty: 30000; above 120000: 120000
contexa.security.tiered.llm.tiered.layer2.timeout-msnoneTime limit (ms) of a Layer 2 streaming call. Empty: 60000; above 120000: 120000

The last two settings apply to streaming calls only and do not change decision time. The time limits of Layer 1 and Layer 2 and of a single model call are set in Enforcement Modes and Decision Tuning.

Naming models (bindings)

Contexa lists every chat and embedding model bean of the application by itself. With no setting, a model can be found by its bean name, its provider (inferred from the bean class and name) and its model name (the provider's spring.ai.…options.model, else the bean name). contexa.llm.bindings corrects an entry of this list or adds aliases.

SettingDefaultMeaning
contexa.llm.bindings.chat.<name>.bean-namenoneThe model bean it applies to. Empty: the bean whose name equals <name>
contexa.llm.bindings.chat.<name>.providernoneThe provider. Empty: inferred from the bean class and name (ollama, anthropic, openai, gemini, mistral, bedrock, huggingface, otherwise spring)
contexa.llm.bindings.chat.<name>.model-idnoneThe model name. Empty: the key in the provider table above, else the bean name
contexa.llm.bindings.chat.<name>.aliases[]More names. A layer model setting can use them
contexa.llm.bindings.chat.<name>.enabledtruefalse: this setting is not used. The bean stays in the list under its own name
contexa.llm.bindings.chat.<name>.primaryfalsePicked first among models of the same provider, and the choice of spring-primary mode

For embedding models, write the same fields under contexa.llm.bindings.embedding.<name>.…. The providers whose embedding model name is read from a key are OpenAI and Ollama only.

  • Overlapping names stop startup. No bean name, binding key, model name or alias may belong to two different models. Two model beans of the same provider that both take their model name from the same key can overlap; give them different model-id values.
  • An alias is a name to pick by. An OpenAI or Anthropic model picked by an alias is still called with the model set on its bean. Only for Ollama does the alias become the model of the call (below).
  • When bean-name names a bean that does not exist, a warning is logged and the setting is skipped.

Example: keep OpenAI as the primary chat model and run only Layer 2 on an Anthropic model. anthropicChatModel is the bean name the Spring AI Anthropic starter creates.

# Added to your existing settings
spring:
  ai:
    anthropic:
      api-key: ${ANTHROPIC_API_KEY}

contexa:
  llm:
    bindings:
      chat:
        anthropicChatModel:
          aliases: [expert]
  security:
    tiered:
      llm:
        layer2:
          model: expert

Using a local Ollama

Ollama can be connected in two ways. Choose one.

The Contexa connection is on when contexa.llm.chat.ollama.base-url is set (with the Ollama library in the application). Chat and embedding use the same Ollama server. A start with Ollama alone:

contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
  llm:
    chat:
      ollama:
        base-url: http://localhost:11434
        model: qwen3:8b
        keep-alive: 30m
    selection:
      chat:
        priority: ollama
      embedding:
        priority: ollama
SettingDefaultMeaning
contexa.llm.chat.ollama.base-urlnoneOllama server address. When set, Contexa creates the Ollama connection and the two beans above
contexa.llm.chat.ollama.modelnoneChat model. Empty: qwen3:8b
contexa.llm.chat.ollama.keep-alivenoneHow long the model stays in memory after a call (Ollama keep_alive, for example 30m). Empty: the Ollama default
contexa.llm.embedding.ollama.modelnoneEmbedding model. Empty: mxbai-embed-large
contexa.llm.embedding.ollama.dedicated-runtime-enabledfalsetrue: embeddings go to another Ollama server (bean contexaDedicatedOllamaEmbeddingModel)
contexa.llm.embedding.ollama.base-urlnoneAddress of the embedding server. Startup stops when the dedicated server is on and this is empty
contexa.llm.model-capabilities.ollama.disable-thinking-patternsnonePatterns of Ollama model names whose thinking is turned off (regular expressions, comma separated). Calls to a matching model turn thinking off

With both the chat server address and the dedicated embedding server there are two embedding beans (shared and dedicated), and by name order the dedicated one is picked first.

Different models per layer on one Ollama server

An Ollama chat model cannot be copied, so name the layer models as aliases of the Ollama chat bean. An Ollama call sends the picked name as its model, so another model of the same server is used. Pull that model into the Ollama server first.

# Added to the Ollama example above
contexa:
  llm:
    bindings:
      chat:
        contexaOllamaChatModel:
          aliases: [qwen3:8b, qwen3:14b]
  security:
    tiered:
      llm:
        layer1:
          model: qwen3:8b
        layer2:
          model: qwen3:14b

How many calls a model server takes

Every call Contexa makes to a model server passes one gate per server (provider and address): the decisions of both layers, the AI pipelines and the embeddings of the vector store. A call waits in line at the gate instead of piling up at the server.

  • A self-hosted server (Ollama, or an address on this host or a private network) runs 2 calls at once and one model at a time: a call for another model, such as an embedding while decisions run, goes in when the running calls are done. A remote provider runs 16 calls at once.
  • Embeddings go in before waiting decision calls. A call that is in is never cut.
  • The time limits of model calls and of vector store writes and searches count from the moment the call goes in. The wait in line is bounded by the event's budget (contexa.security.plane.agent.event-timeout-ms); a call that gets no turn within it ends as MODEL_SERVER_BUSY.
  • After a rate limit (429), an overload (529) or a server that is unavailable for a while (503), the server is left alone for 2 s, then 4, 8 and 12 s while it keeps answering so, and the call is sent again when its turn comes.
SettingDefaultMeaning
contexa.llm.gate.enabledtrueWhether model calls pass a gate per server
contexa.llm.gate.self-hosted-max-concurrent2Calls at once on a self-hosted server. Match the requests the server runs in parallel (Ollama: OLLAMA_NUM_PARALLEL). 0: no limit
contexa.llm.gate.remote-max-concurrent16Calls at once on a remote provider. 0: no limit
contexa.llm.gate.first-back-off-ms2000The first pause of the server gate after a rate limit, an overload (429, 503, 529) or another failure worth retrying (502, 504, a connection error and so on). It doubles while the server keeps answering so, up to six times this
contexa.llm.gate.servers.<name>.base-urlnoneThe address of one server, as the provider is configured with it
contexa.llm.gate.servers.<name>.max-concurrentnoneCalls at once on that server
contexa.llm.gate.servers.<name>.one-model-at-a-timenonefalse for a server that keeps the chat and the embedding model loaded together. Empty: true for a self-hosted server

A GPU server with enough memory for both models and four parallel requests:

contexa:
  llm:
    gate:
      servers:
        gpu:
          base-url: http://gpu-box:11434
          max-concurrent: 4
          one-model-at-a-time: false

Embedding model and vector dimension

The embedding model turns documents such as past decision records into vectors to store and search. The stored vectors must have the model's dimension, so embedding is fixed to one provider.

SettingDefaultMeaning
contexa.llm.selection.embedding.modefixedfixed: the model of the priority provider first, else another embedding model. spring-primary: the model marked primary. dynamic-priority cannot be used (startup stops)
contexa.llm.selection.embedding.priorityopenaiThe one embedding provider. Startup stops when more than one is named
contexa.llm.embedding.dimensions1024Embedding dimension. Used to set the dimension only when you set it (step 2 below)
contexa.llm.embedding.ollama.dimensions1024Ollama embedding dimension. Used only when you set it (step 3 below)

How the dimension is decided

  1. The value of contexa.vectorstore.pgvector.dimensions, when you set it
  2. The value of contexa.llm.embedding.dimensions, when you set it
  3. The provider's dimension key: spring.ai.openai.embedding.options.dimensions for OpenAI, contexa.llm.embedding.ollama.dimensions (or spring.ai.ollama.embedding.options.dimensions) for Ollama
  4. The model's value when Contexa knows the model: 1024 for OpenAI text-embedding-3-small, text-embedding-3-large and the other text-embedding-3 models, 1536 for text-embedding-ada-002, 1024 for Ollama mxbai-embed-large and bge-m3
  5. For an unknown model with none of the values above, startup stops. Set that model's dimension in both contexa.llm.embedding.dimensions and contexa.vectorstore.pgvector.dimensions.

With OpenAI embeddings, Contexa sets the default of spring.ai.openai.embedding.options.model to text-embedding-3-small and of dimensions to the dimension decided above, so 1024-dimension vectors are requested by default.

A changed dimension no longer fits the stored vectors. At startup Contexa compares the dimension of the embedding model in use, the configured vector store dimension and the dimension of an existing vector table (ctxa_vector_store by default), and stops when any differs. To change the dimension, create the table again or embed the documents again. When they match, the startup log shows Embedding vector dimension verified: provider=…, model=…, dimension=….

Vector store (pgvector)

Vectors are stored in the vector store bean (contexaVectorStore) that Contexa builds itself on the dedicated Contexa database (contexaJdbcTemplate). It does not use your application's VectorStore bean, and Contexa creates nothing in your application's database (dependencies in Installation Guide). Write its settings as contexa.vectorstore.pgvector.*. Contexa's store reads only these keys; spring.ai.vectorstore.pgvector.* belongs to your application's own Spring AI store and does not reach Contexa's.

Creating the table at first start. Contexa sets the default of contexa.vectorstore.pgvector.initialize-schema to true (Spring AI's own default is false). So the first start creates, in the dedicated Contexa database, the vector extension, the ctxa_vector_store table, its HNSW index and the metadata index for per-user searches. For a database whose schema is managed by migrations, turn it off and create the table and both indexes yourself.

# Added to your existing settings
contexa:
  vectorstore:
    pgvector:
      initialize-schema: false

Retrying failed stores

A document whose vector store failed waits in an in-memory queue and is stored again in the background, so that an outage of a few minutes does not lose learning records. The queue is lost on restart; when the documents must outlive a restart, the application registers its own FailedDocumentSink bean.

SettingDefaultMeaning
contexa.vectorstore.retry.enabledtruefalse: a failed store is only returned to the caller as an error
contexa.vectorstore.retry.queue-size2000Most waiting documents. When full, the oldest waiting document is dropped
contexa.vectorstore.retry.max-attempts20Given up after this many tries
contexa.vectorstore.retry.max-age1hGiven up this long after the first failure
contexa.vectorstore.retry.initial-delay10sWait before the first retry; it doubles with each failure
contexa.vectorstore.retry.max-delay5mLongest wait between two retries
contexa.vectorstore.retry.batch-size20Documents one retry stores. Halved while retries fail, grows back after they succeed

When startup stops

When the model settings do not fit, Contexa stops at startup instead of quietly using another model in production. Match the log message to the table below.

SituationFix
Chat mode: fixed with more than one provider in priority, or no model of that providerName one provider and add its Spring AI starter
Embedding mode: dynamic-priorityChange it to fixed
More than one provider in the embedding priorityName one
A model name or alias belongs to two modelsMake the names different
spring-primary with more than one primary, or several models and no primaryMark one with primary: true
An unknown embedding model with no dimension setSet contexa.llm.embedding.dimensions and contexa.vectorstore.pgvector.dimensions to that model's dimension
Dimensions differ (model, settings, existing table)Make them equal, and create the table again or embed again
The dedicated Ollama embedding server is on with no addressSet contexa.llm.embedding.ollama.base-url
Anthropic thinking settings refusedFix the setting the message names (table above)

The other way round, some cases start but produce no decisions: no chat model at all, or a mode value written with underscores so that no primary chat model was created.
