Resource Scanner

This page shows how the application's controller URLs and @Protectable methods are collected into the admin console's list of protectable resources, and how permissions and policies are attached to them. A scan runs only when an administrator presses "Load Resources", and it looks only inside the packages set in the system settings and the application's own packages.

Your application's own packages are scanned without writing them. The default scan package is io.contexa.contexaiam. (Contexa's own admin screens), and both scanners always add the packages Spring Boot knows for the application (the package of the @SpringBootApplication). The setting only adds to them, so to find classes outside the application's packages, enter that package (for example com.example.shared) in the admin console under "IAM → System Settings → Resource Scan Settings → Controller base packages". There is no automatic scan at application startup.

At a glance

A resource is one place that can be protected: a URL resource is one controller path, a method resource is one service method with @Protectable. Once a resource has a permission and a policy, that policy decides its requests.

Choosing the packages to scan

Both scanners (URL and method) use the same package list. The application's own packages (the ones Spring Boot knows) are always added without writing them. To add other packages, enter them in the admin console under "IAM → System Settings (/contexa/admin/system-settings) → Resource Scan Settings → Controller base packages".

com.example.shop
com.example.billing
  • One package per line, or separated with commas. The trailing dot (.) is added automatically.
  • The package itself and every package below it are scanned; com.example.shop includes com.example.shop.api.
  • The value is stored in the ctxa_system_settings table of the Contexa database. The default seed puts io.contexa.contexaiam. there, and an empty value falls back to it. Keep that value in the list if you also want Contexa's admin controllers listed.
  • A changed value is used from the next "Load Resources".

Running a scan

Press "Load Resources" in the "Policy Creation" tab of Policy Center (/contexa/admin/policy-center), which calls POST /contexa/admin/policy-center/refresh-resources. Press it again after deploying or adding endpoints. The old path POST /contexa/admin/workbench/resources/refresh also scans, but in step 6 it only moves "Protected → Awaiting Policy", and it skips step 7.

  1. Every scanner collects resources.
  2. When an identifier appears more than once, only the first one is used.
  3. Only resources not yet in the list are registered. AI names and describes them 100 at a time, and they are saved as "Unset" (NEEDS_DEFINITION) (Naming). Names and descriptions of existing resources are not changed.
  4. Resources that disappeared from the code are not deleted; the error log shows how many and one example.
  5. With contexa.iam.admin.condition-templates.enabled: true, condition templates are generated by AI (Condition templates).
  6. Resource states are aligned with the policies: a "Protected" resource with no policy targeting it becomes "Awaiting Policy", and an "Awaiting Policy" resource that a policy targets becomes "Protected".
  7. Policies with an empty readable description get one.

URL resources

Every handler method registered in Spring MVC's RequestMappingHandlerMapping (bean name requestMappingHandlerMapping) is looked at. All mapping annotations count, such as @GetMapping and @PostMapping.

  • The handler class must be inside a scan package and carry @Controller or @RestController. No security annotation is needed.
  • With several paths in one mapping only the first is used; with several HTTP methods only the first. No method means ANY.
  • The identifier is the URL pattern only. So GET and POST on the same path become one resource that keeps the HTTP method found first. A policy created from that resource targets that one method, so the other methods on the path do not match it. To cover them, add a target with HTTP method ANY through "Configure Resource Permissions", or add targets in Manual Mode.

Method resources

Each bean in the application context is taken out and its real class (behind any proxy, AopUtils.getTargetClass()) is looked at.

  • The class must be inside a scan package; @Controller and @RestController classes are skipped (controllers are URL resources).
  • Each public method declared in that class with @Protectable becomes one resource. When @Protectable is placed on the class, every public non-static method of the class becomes a resource.

Method policies find their method by an identifier of the same shape, so a policy created from the resource applies to that method as it is (What a policy is made of).

Naming

An identifier alone rarely says what a feature does, so AI gives each newly registered resource a readable name and description. For example:

IdentifierName given by AI (example)
GET /api/usersList All Users
PUT /api/users/{id}Update User Profile
DELETE /admin/roles/{id}Delete Role
AccountService.updateAccount(Long,AccountDto)Update Account Details
  • Only new resources are named, 100 per request. The identifier, service owner, type, HTTP method, the scanner's name and description, parameters, return type, API docs link and source location are sent along.
  • The request is handled by the AI engine's ResourceNamingLab (template and diagnosis type name "ResourceNaming"); there is no separate naming service.
  • Resources the AI does not answer for are not asked again; they are saved with fallback values. A name or description the scanner set is kept (the handler method name for URL resources); an empty name becomes the end of the identifier followed by Feature, and an empty description becomes AI suggestion unavailable.
  • An AI model connection is needed. Without a model, or when it fails, the scan still finishes with fallback values.

Browsing and filtering

The resource list in the "Policy Creation" tab filters by service owner, status, and keyword (identifier, name, description). There is no filter by resource type (URL or METHOD). Without a status filter, "Excluded" resources are hidden.

Defining a permission

  1. Press "Create Permission & Policy" on the resource row.
  2. Contexa moves the resource to "Awaiting Policy" and creates its automatic permission (POST /contexa/admin/workbench/resources/{id}/define, with the name and description).
  3. In the "Select Policy Setup Method" window, choose Quick Mode or the AI Policy Wizard (Connecting a policy).

The automatic permission's name is built from the resource type and identifier: characters other than letters and digits become _, in upper case.

/api/v1/invoices/{id}                             → URL_API_V1_INVOICES_ID
com.example.docs.DocumentService.getDocument(Long) → METHOD_DOCUMENTSERVICE_GETDOCUMENT
  • The automatic permission is marked as auto-created; its action type is the HTTP method for URLs and EXECUTE for methods.
  • It only links the resource to policy targets and never goes into a policy condition (Quick Mode).
  • Check several resources to define them at once (POST /contexa/admin/workbench/resources/define-batch). Resources that already have a permission are skipped.

Connecting a policy

The "Select Policy Setup Method" window offers two choices. Manual Mode is not opened from this window; use its card in the "Policy Creation" tab.

  • Quick Mode: pick roles and permissions and create an ALLOW or DENY policy at once. With several resources selected, the policies are created in one batch.
  • AI Policy Wizard: takes one resource only. The AI draft is saved as pending and applies after approval.

Saving the policy moves the resource to "Protected", and the policies reload so the next request is decided by it. URL policies are evaluated only when the request passes CustomDynamicAuthorizationManager, so in the default HOST_OWNED mode it has to be connected in the application's chain (Preparation). Each mode is described in Policy Management.

Exclude, restore and reset

  • Exclude: only "Unset" resources can be excluded (POST /contexa/admin/workbench/resources/{id}/exclude). "Awaiting Policy" rows show the button too, but the server refuses.
  • What exclusion really does: it hides the resource from the resource list and the permission list; authorization decisions do not change. A URL without a policy follows the "decision when no policy applies" (default AUTHENTICATED: a signed-in user passes). Open public paths (such as /actuator/health) with a policy or with permitAll in the application's chain.
  • Restore: brings an excluded resource back to "Unset" (POST /contexa/admin/workbench/resources/{id}/restore).
  • Release Policy Link: for the chosen resources that are "Awaiting Policy" only, deletes the linked permission and goes back to "Unset" (POST /contexa/admin/policy-center/api/reset-policy-status).
  • Deleting a policy: resources it targeted that no other policy uses go back to "Unset", and their automatic permissions are deleted.

Extension points

A scanner is one ResourceScanner interface. A bean of that type is used together with the default scanners when resources are loaded. To replace a default scanner, declare a bean of type MvcResourceScanner or MethodResourceScanner yourself (the auto-configuration backs off). The package setting does not apply to your own scanner, so choose inside it.

import io.contexa.contexacommon.entity.ManagedResource;
import io.contexa.contexaiam.resource.scanner.ResourceScanner;
import org.springframework.stereotype.Component;

import java.util.List;

@Component
public class ReportEndpointScanner implements ResourceScanner {

    @Override
    public List<ManagedResource> scan() {
        return List.of(ManagedResource.builder()
                .resourceIdentifier("/reports/export")
                .resourceType(ManagedResource.ResourceType.URL)
                .httpMethod(ManagedResource.HttpMethod.GET)
                .friendlyName("exportReport")
                .serviceOwner("ReportRouter")
                .status(ManagedResource.Status.NEEDS_DEFINITION)
                .build());
    }
}

The resource entity ManagedResource lives in the contexa-common module (io.contexa.contexacommon.entity). Its fields are identifier, type, HTTP method, name, description, service owner, parameter types, return type, API docs link, source location, available context variables (availableContextVariables), status, linked permission, created and updated times. The name cannot be empty. ResourceRegistryService, which ties scanning, defining and excluding together, can also be replaced with a bean of the same type.

Old paths

/contexa/admin/workbench/resources is the old resource screen path. Its screen file is gone, so GET does not open, but Policy Center keeps using this controller's API: POST /refresh · /{id}/define · /define-batch · /{id}/exclude · /{id}/restore · /{id}/manage.
