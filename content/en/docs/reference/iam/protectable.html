@Protectable: Protecting Methods

Put @Protectable on a method and Contexa evaluates the method's policies and applies the stored Zero Trust decision right before the call, then sends an analysis event for the next decision when the call ends. This page covers where to put it, connecting policies, the order in which one call is handled, choosing sync, the owner check, and the nine attributes.

At a glance

import io.contexa.contexacommon.annotation.Protectable;
import org.springframework.stereotype.Service;

@Service
public class ReportService {

    // Applies the stored decision; analysed after it runs, effective from the next call
    @Protectable(category = "REPORT", actions = "READ")
    public Report findReport(Long reportId) {
        ...
    }

    // An export that cannot be undone: gets its decision within this call before it runs
    @Protectable(category = "REPORT", actions = "EXPORT", sensitivity = "CONFIDENTIAL",
            exportSensitive = true, sync = true)
    public ReportFile exportReport(Long reportId) {
        ...
    }
}

The annotation lives in contexa-common; the method interceptor in contexa-iam handles it. How it differs from the other ways to protect things:

WayWhat it guardsWhere the rule livesAI decision

@PreAuthorizeMethod callsCode (static)#ai usable in the expression only under CONTEXA_OWNED (Where they can be used)

Before you use it

  • Contexa must be on (@EnableAISecurity). It works under both authentication ownerships. Under HOST_OWNED (the default, your application owns sign-in), your application must put the sign-in result into the Spring SecurityContext.
  • Only signed-in calls pass. Without authentication, or with an anonymous one, the call is refused with AuthenticationCredentialsNotFoundException.
  • Only calls through the Spring proxy are intercepted. Calls from another bean are covered; a call through this inside the same class is not (Spring AOP behaviour).
  • Stored decisions are enforced here and at the request-time filters, in both ownerships. Under HOST_OWNED the request-time filters run right after your application's security chain, so most requests meet a stored BLOCK, CHALLENGE or ESCALATE before they reach the method. If your application sets the signed-in user later (in an MVC interceptor or a controller), the filters do not see the user and the @Protectable method is where those requests are stopped (What works under each ownership).

What happens depends on the Zero Trust enforcement mode (contexa.security.zerotrust.mode). Policies are evaluated in every mode.

Enforcement modeMethod policiesStored decision appliedAnalysis
DISABLED, OBSERVE (or enabled: false)EvaluatedNoNo. No re-entry check and no analysis event either
SHADOWEvaluatedRecorded onlyYes (sync within the call). Decisions are not stored
ENFORCE (default)EvaluatedYesYes

The delegator re-evaluation refuses only under ENFORCE; in the other modes it only records.

Where to put it

  • Put it on a method or a class (io.contexa.contexacommon.annotation.Protectable, retained at runtime). It is looked up on the called method, then on that method in the actual class, then on the actual class, then on the class that declares the method. On a class, every method call of that bean is covered.
  • ownerField, however, is read only from an annotation on the method, and the Resource Scanner registers only annotated methods as resources.
  • The policy target identifier is package.Class.method(simple parameter types), for example com.example.report.ReportService.exportReport(Long). Use this string as the target of a METHOD policy.
  • The resourceId of a refusal is SimpleClassName.method (for example ReportService.exportReport).
  • The interceptor sits at the very front of Spring method security (AuthorizationInterceptorsOrder.FIRST + 1), so it runs before @PreAuthorize.

Connecting policies

When no executable policy targets the method, the policy step follows the default decision contexa.policy.missing-method-policy-decision (default PERMIT), and the next step (checking the decision) still runs. To block protected methods without a policy, set it to DENY (When no policy matches).

Connecting in Policy Center

  1. Find the resource: the Resource Scanner registers @Protectable on public methods of beans (controllers excluded) under the scan packages as METHOD resources. The default scan package is io.contexa.contexaiam., so add your application's package in the admin screen IAM > System Settings to see your methods. The scan does not run by itself at startup; it runs when you press "Load Resources" in the Policy Center (Resource Scanner).
  2. Create the permission: in the Resources tab of Policy Center (/contexa/admin/policy-center), give the resource a name and description and choose "Create Permission & Policy". The permission name is set automatically to METHOD_{CLASS}_{METHOD} (upper case, for example METHOD_REPORTSERVICE_EXPORTREPORT), and its action type is EXECUTE.
  3. Create the policy: create a METHOD-target policy in the Policy Creation tab in Quick mode (roles, permissions, effect, target), Manual mode (target and conditions written yourself) or AI mode. It takes effect once saved.

Writing conditions yourself

hasRole('ADMIN') and #ai.isAllowed()
hasRole('ANALYST') and !#ai.isBlocked() and T(java.time.LocalTime).now().getHour() < 18
isDelegatedAgent() and delegationAllowsOperation('EXPORT') and #ai.isAllowed()
  • A method policy's conditions are evaluated as SpEL exactly as written. The shorthand of a bare authority name (ROLE_ADMIN) works only in URL policies.
  • Several conditions of one policy are joined with and. Policies are ordered by target order, then priority, then policy ID, and merged with the same combining algorithm as URL policies (Decision rules).
  • Variables available in conditions: method parameter names (#reportId), #ai, and #ownerField when ownerField is set. Contexa puts the method's policy plan into the #methodPolicyPlan variable and evaluates it.
  • Agent expressions (third line) see the delegation stamp under both ownerships (Agent expressions).

The order in which one call is handled

  • ③ Policy evaluation: evaluates the policy plan (#methodPolicyPlan, each policy's condition and effect) and combines it. With no policy at all it is the default decision. Stored conditions are evaluated in the sandbox (Safeguards). A policy denial is not analysed, but under SHADOW and ENFORCE it is recorded in the session and in the user's authorization scope as "refused", which later decisions see.
  • ④ Delegator re-evaluation: a delegated agent's call is evaluated against the same policies again as the delegator and refused when the delegator could not make it or is unknown (Evaluated again as the delegator).
  • ⑤ Certification gate: OSS has no gate implementation. With a ProtectableResourceCertificationGate bean, a call to an uncertified resource is refused under ENFORCE as held for review (423) (Extension points).
  • ⑥ Asynchronous methods: a stored BLOCK, CHALLENGE or ESCALATE refuses the call before it runs. A person's call runs even without a decision and is analysed afterwards, but an agent call with no decision on record is decided in place (protectable.unrecorded-agent-request: DECIDE_IN_PLACE, Requests without a decision and ALLOW reuse).
  • An exception thrown while running is recorded as a failed run, not a denial (outcome METHOD_FAILED in the event).

Choosing sync

sync = false (default)sync = true
When it is decidedAnalysed after it runs; the decision applies from the next callAnalysed within this call, which follows the result
What stops it before it runsA stored BLOCK, CHALLENGE or ESCALATE; the in-place decision of an agent call with no decisionA stored restriction if any, otherwise an analysis result other than ALLOW
LatencyAlmost none (an agent call with no decision waits for its analysis)The analysis time on every call. Analysed again even with a stored ALLOW
Where it fitsMost reads and routine workThings that cannot be undone: payments, bulk exports, permission changes, deletions

sync = true stops a call before any side effect. The annotation's documentation recommends it only for resources that can answer within 3 seconds. With sync = false a first call may run without a decision, and the risk is stopped from the next call on.

Owner check (ownerField)

ownerField works only when the policy condition calls hasPermission(...). Before the method runs, while the policy is being evaluated, it reads that field from the target of hasPermission (or from the entity loaded by its ID) and compares it with the signed-in user's name (Authentication.getName()). It does not look at the return value.

@Protectable(ownerField = "username")
public void updateProfile(UserProfile profile) {
    ...
}
// The condition of this method's METHOD policy
// hasPermission(#profile, 'USER_UPDATE')
  1. hasPermission itself must be true first (Permission Evaluators). When it is false, the owner check is never reached.
  2. Two arguments (hasPermission(#profile, 'USER_UPDATE')) check the field of that object; three arguments (hasPermission(#id, 'USER', 'UPDATE')) check the field of the entity read through findById from the repository bean of that domain's evaluator.
  3. The field is looked up through the class hierarchy, then through the getter (getUsername()). The value is compared as a string.
  4. Holding the ROLE_ADMIN authority skips the owner check.
  5. A missing field, value or entity denies. Nested dot paths (owner.id) are not supported. When the target is null, no owner check is made.
  6. A condition can read the field name as #ownerField.
Under HOST_OWNED, check the permission evaluators first. The authorities the built-in domain evaluators look at (PermissionAuthority) are put in by Contexa's user store when Contexa owns sign-in. Your application's sign-in usually carries none, so hasPermission is false and the owner check never passes (What hasPermission checks).

The nine attributes

AttributeDefaultWhat it does
ownerField""Field or getter name used by the owner check (above)
verificationRequiredtrueWhether to apply the prompt quality certification gate. OSS has no gate implementation, so it has an effect only with a ProtectableResourceCertificationGate bean
syncfalseWhether to get the decision within this call (Choosing sync)
category""The resource's business category (for example REPORT). Role scope and delegated scope are compared in this vocabulary. Sensitivity words alone are not a category
sensitivity""Sensitivity (PUBLIC, INTERNAL, CONFIDENTIAL, RESTRICTED, ...). A value your application states on the request wins
actions{}What the method does (READ, EXPORT, ...). With exactly one, it is the request's operation unless your application states another on the request
importanceUNSPECIFIEDThe resource importance your application states. SENSITIVE: a request cannot lower it, each resource is decided on its own, an ALLOW is not reused for other resources, and restrictions are checked again right before it runs. NON_SENSITIVE: a candidate for a few requests passing before the first decision (a sensitivity stated on the request can raise it). UNSPECIFIED: judged by the sensitivity words
privilegedfalseStates that the method is privileged. Only true means something; false leaves it unstated
exportSensitivefalseStates that the method exports sensitive data. Only true means something
  • These nine are the only attributes. The resourceId, resourceUrl, httpMethod and criticality attributes of older documents do not exist in the code.
  • When the application starts, every @Protectable method of every bean is put in the resource context registry (resource ID fully.qualified.Class#method). category, sensitivity, actions, privileged, exportSensitive and importance become resource facts the decision engine uses. A ResourceContextDescriptor bean with the same resource ID replaces them.

Re-entry within the same request

When the same protected method is entered again while one HTTP request is being handled (for example, one request calls the method twice), it is analysed only once. This is not a guard against the same user calling repeatedly within a few seconds: the key includes a request ID the server creates anew for each request, so different requests never block one another.

  • Key: tenant, request ID, HTTP method, address, fully.qualified.Class.method and enforcement mode, plus the user and the context fingerprint (session, client IP, User-Agent).
  • When caught: an asynchronous method runs without analysis (no event, only a suppression record); a sync method is refused under ENFORCE with 503 (PENDING_ANALYSIS). In other modes it runs.
  • Window: contexa.security.zerotrust.protectable.rapid-reentry-window-ms (default 5000). Zero or less turns it off. Without a sign-in, a request or a context fingerprint nothing is checked.
  • Store: memory in standalone mode (keys that vanish when the window ends), Redis in distributed mode (SET NX, key security:protectable:rapid-reentry: + MD5). A Redis error lets the call through. Replace it with a ProtectableRapidReentryRepository bean.

Analysis events and metrics

  • An asynchronous method publishes an authorization event when it finishes (normally or with an exception). The event carries the outcome (METHOD_COMPLETED, METHOD_FAILED), and the asynchronous decision analyses it and applies the result from the next call on (Decision engine).
  • No event when: the mode does not analyse (DISABLED, OBSERVE); a re-entry within the same request; a policy denial (recorded as a denial instead); a Zero Trust refusal; a call already decided through sync; requests let through early by decision merging, except the first. Without an event publisher bean nothing is published either.
  • Metrics: auto-configuration does not give the interceptor a metrics collector (AuthorizationMetrics). If you set one, it counts the time spent publishing the event and the number of decisions.
