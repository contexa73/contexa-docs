@Protectable: Protecting Methods

@Protectable is the annotation that protects a method with AI decisions. When you put it on a method, CONTEXA checks every call just before the method runs. It checks whether the access policies connected to the method allow the call, and whether a decision already made for this user (allow, step-up authentication, held for review, block) stops it. When the call ends, CONTEXA sends it to AI analysis (the step where an AI model rates the call's risk and makes a decision) so that the result feeds the next decision. On this page you can check where to put the annotation, the order in which one call is checked, how to choose sync, refusal responses, the owner check, and the nine attributes.

Overview

import io.contexa.contexacommon.annotation.Protectable;
import org.springframework.stereotype.Service;

@Service
public class ReportService {

    // Applies the stored decision; analysed after it runs, effective from the next call
    @Protectable(category = "REPORT", actions = "READ")
    public Report findReport(Long reportId) {
        ...
    }

    // An export that cannot be undone: gets its decision within this call before it runs
    @Protectable(category = "REPORT", actions = "EXPORT", sensitivity = "CONFIDENTIAL",
            exportSensitive = true, sync = true)
    public ReportFile exportReport(Long reportId) {
        ...
    }
}

The two methods in the example are handled differently. In the default operating mode (ENFORCE), a call to findReport goes through these steps.

  1. CONTEXA evaluates the access policies connected to the method. If a policy refuses, the method does not run.
  2. CONTEXA looks up the decision stored for this user. If a block, a step-up authentication or a review hold is in force, CONTEXA refuses the call and the method does not run.
  3. If both checks pass, the method runs. It also runs when no decision exists yet for the user, as long as a person makes the call. Calls from AI agents are an exception; see step ⑥ in the processing order below.
  4. When the method returns, CONTEXA sends the call to analysis. The result applies from this user's next call.

The stored decision is the last decision the AI analysis made for this user.

exportReport uses sync = true. It finishes the analysis on the spot before it runs, and it runs only when the result is ALLOW. This stops an export, which cannot be undone, on the very first call. The price is that every call waits for the analysis.

The annotation lives in contexa-common. The method interceptor in contexa-iam intercepts the call and runs the checks. Compared with the other ways to protect things:

Before you use it

  • CONTEXA must be on (@EnableAISecurity). It works whether CONTEXA owns sign-in (CONTEXA_OWNED) or your application does (HOST_OWNED, the default). Under HOST_OWNED, your application must put the sign-in result into Spring's SecurityContext.
  • In the default mode, only signed-in calls pass. In the SHADOW and ENFORCE modes (ENFORCE is the default), CONTEXA refuses a call that has no authentication or only an anonymous one.
    • It throws AccessDeniedException, and the cause of that exception is AuthenticationCredentialsNotFoundException. Your application's Spring Security setup treats it like a request that is not signed in (it sends the user to the sign-in page or answers 401).
    • In the DISABLED and OBSERVE modes (and with contexa.security.zerotrust.enabled: false), CONTEXA does not refuse the call. The call goes on as your application made it, and the method policies are evaluated for whoever the security context holds (a visitor or nobody).
    • A call on a thread with neither a user nor a request (@Scheduled, or @Async when the executor does not carry the security context) has no one to decide for and runs in every mode.
  • Only calls through the Spring proxy are checked. A call from another bean is checked. A call through this inside the same class is not (this is how Spring AOP works).
  • The stored decision is applied in two places. One is CONTEXA's request filter, which sees each request as it arrives. The other is the @Protectable method.
    • Under HOST_OWNED, the filter runs right after your application's security filter chain. A request from a user under a block, a step-up or a review hold is therefore usually stopped at the filter, before it reaches the method.
    • If your application sets the signed-in user late (in an MVC interceptor or a controller), the filter does not see that user. The @Protectable method is then the only place that stops such requests (What works under each ownership). The first time CONTEXA sees this, it writes one warning to the log.

The Zero Trust operating mode (contexa.security.zerotrust.mode) sets how far CONTEXA applies decisions. Policies are evaluated in every mode.

Operating modeMethod policiesStored decision appliedAnalysis
DISABLED (off) and OBSERVE (same as off). enabled: false is the sameEvaluatedNot appliedNo. No same-request repeat check and nothing sent to analysis either
SHADOW (observation mode)EvaluatedRecorded only, never refusedYes (sync within the call). The result does not affect the call and is not stored as a decision
ENFORCE (enforcement mode, default)EvaluatedApplied (refused)Yes

The delegator re-evaluation (step ④ of the processing order) refuses only under ENFORCE; in the other modes it only records.

Where to put it

  • Put it on a method or a class (io.contexa.contexacommon.annotation.Protectable, kept at runtime). On a class, every method call of that bean is checked. CONTEXA looks for the annotation on the called method, then on that method in the actual class behind the proxy, then on the actual class, then on the class that declares the method, and uses the first one it finds.
  • ownerField, however, is read only from an annotation placed directly on the method. An ownerField on a class-level annotation is not used.
  • The policy target identifier is package.Class.method(simple parameter types), for example com.example.report.ReportService.exportReport(Long). Several parameter types are joined with commas and no spaces. Use this string as the target of a METHOD policy.
  • The resourceId of a refusal is SimpleClassName.method (for example ReportService.exportReport).
  • The interceptor sits at the very front of Spring method security (AuthorizationInterceptorsOrder.FIRST + 1), so it runs before @PreAuthorize.
  • A final method of a bean that Spring wraps in a class proxy is not protected, because Spring cannot intercept a final method. When the application starts, CONTEXA names such methods in a warning in the log.

Connecting policies

An administrator connects access policies to each method separately. When no policy targets the method (or none is active and approved), the policy step follows the default decision contexa.policy.missing-method-policy-decision (default PERMIT) and passes, and the call moves on to the next step, the check of the stored decision. To block protected methods that have no policy, set it to DENY (When no policy matches).

Connecting in Policy Center

  1. Find the resource: the Resource Scanner collects the methods that carry @Protectable as METHOD resources. When the annotation is on a class, it collects every public non-static method declared in that class.
    • It looks at beans in the scan packages and skips controllers.
    • The scan packages are your application's own packages (the ones Spring Boot auto-configuration knows) plus the packages you list in the admin screen IAM > System Settings (default io.contexa.contexaiam.). You do not need to list your own package to see your methods.
    • The scan does not run by itself at startup. It runs when you press "Load Resources" in Policy Center (Resource Scanner).
  2. Create the permission: in the Resources tab of Policy Center (/contexa/admin/policy-center), give the resource a name and description and choose "Create Permission & Policy". CONTEXA names the permission automatically as METHOD_{CLASS}_{METHOD} in upper case (for example METHOD_REPORTSERVICE_EXPORTREPORT), and its action type is EXECUTE.
  3. Create the policy: create a METHOD-target policy in the Policy Creation tab. Quick mode picks roles, permissions, effect and target. Manual mode lets you write the target and conditions yourself. There is also an AI mode. The policy takes effect once saved.

Writing conditions yourself

In Manual mode you write a policy's conditions as expressions. For example:

hasRole('ADMIN') and #ai.isAllowed()
hasRole('ANALYST') and !#ai.isBlocked() and T(java.time.LocalTime).now().getHour() < 18
isDelegatedAgent() and delegationAllowsOperation('EXPORT') and #ai.isAllowed()
  • A method policy's conditions are evaluated exactly as written, as SpEL (the Spring Expression Language). The shorthand of a bare authority name (ROLE_ADMIN) works only in URL policies.
  • Several conditions in one policy are joined with and, so all of them must hold. With several policies, CONTEXA evaluates them by target order, then priority, then policy ID, and merges the results with the same combining algorithm as URL policies (Decision rules).
  • Variables available in conditions: method parameter names (#reportId), #ai (which reads the stored decision), and #ownerField when ownerField is set. CONTEXA puts the list of policies that apply to this method (the policy plan) into the #methodPolicyPlan variable and evaluates it.
  • Agent expressions such as the third line see the delegation stamp (the value that says on whose behalf an agent works, and which operations and resources it was given) under both ownerships (Agent expressions).

The order in which one call is handled

When the method is called, CONTEXA checks the call in the order below. A check that refuses ends the call there, and the method does not run.

  • ③ Policy evaluation: CONTEXA evaluates every policy connected to the method and merges the results into one. The list it evaluates is the policy plan (#methodPolicyPlan, each policy's condition and effect). With no policy at all, it uses the default decision.
    • Conditions stored in the database are evaluated in a sandbox that cannot use risky features such as reflection (Safeguards).
    • A call that a policy refuses is not sent to analysis. Under SHADOW and ENFORCE it is instead recorded in the session and in the user's authorization scope as "refused", and later decisions see that record.
  • ④ Delegator re-evaluation: when an AI agent acting on a person's delegation makes the call, CONTEXA evaluates the same policies again with that person's authority. It refuses when the delegator could not make the call or is unknown. This keeps an agent from doing more than the person who delegated to it (Evaluated again as the delegator).
  • ⑤ Certification gate: OSS has no gate implementation, so a default installation skips this step. With a ProtectableResourceCertificationGate bean, a call to a resource without a prompt quality certification is refused under ENFORCE as held for review (423) (Extension points).
  • ⑥ sync = false methods: a stored block, step-up or review hold refuses the call before the method runs.
    • A person's call runs even without a decision and is analysed afterwards.
    • An AI agent call with no decision on record is decided on the spot (protectable.unrecorded-agent-request: DECIDE_IN_PLACE, Requests without a decision and ALLOW reuse).
    • A person's call can also be stopped when the session, network address or browser differs from the last decision and the call goes to a sensitive resource (see the 429 below under refusal responses).
  • An exception thrown while the method runs counts as a business error, not as a security refusal. The analysis records it as a failed run (METHOD_FAILED), and the exception reaches the caller unchanged.

Choosing sync

One rule decides it. Use sync = true for work that cannot be undone once it runs (payments, bulk exports, permission changes, deletions), and leave everything else on the default sync = false.

sync = false (default)sync = true
When it is decidedAnalysed after the call ends. The decision applies from the next callAnalysed within this call, and the result decides whether the method runs
What stops it before it runsA stored block, step-up or review hold. An AI agent call with no decision is decided on the spot and can be stoppedA stored restriction if there is one; otherwise an analysis result on the spot that is not ALLOW
LatencyAlmost none (only an AI agent call with no decision waits for its analysis)Every call waits for the analysis. It analyses again even with a stored ALLOW
Where it fitsMost reads and routine workThings that cannot be undone: payments, bulk exports, permission changes, deletions

sync = true stops a call before any side effect. The annotation's documentation recommends it only for resources that can answer within 3 seconds. With sync = false, a user's first call may run without a decision, and the risk is stopped from the next call on.

When the analysis does not finish within the time limit (default 40 seconds, contexa.security.zerotrust.agent.flight.wait), CONTEXA does not let the call through under ENFORCE. A person's call is asked for step-up authentication (401), and an AI agent's call is refused with 429.

Refusal responses

A call that fails a check does not run the method, and the caller receives one of these responses.

The other is when a person whose session, network address or browser differs from the last decision calls a sensitive resource and no decision exists yet for that environment (ENFORCE)

  "status": 403,

  "message": "Access blocked by AI security analysis",
  "action": "BLOCK",
  "resourceId": "ReportService.exportReport",
  "riskScore": null,
  "analysisTimeout": false,
  "timestamp": "2026-11-02T06:15:00Z"

  • The method throws ZeroTrustAccessDeniedException. For a call made from an MVC controller, ZeroTrustExceptionHandler (@ControllerAdvice, ordered before your application's own advice) turns it into the JSON above.
    • The response also carries an error field that the example does not show. error has the same value as code, except that for a CHALLENGE whose step-up has started it is MFA_CHALLENGE_REQUIRED.
    • In that case the response also carries mfaUrl and the address of the notice page, challengeNoticeUrl.
    • riskScore is empty.
  • When a browser page request (Accept with text/html) meets a BLOCK, an ESCALATE or a CHALLENGE whose step-up has started, the browser is redirected to the same screen the request-time filters use instead of getting JSON (Responses).
  • A call made outside Spring MVC (a servlet filter, for example) must have its exception handled by your application.
  • Under CONTEXA_OWNED, when an AI agent's call meets a CHALLENGE, CONTEXA asks the accountable person for confirmation instead of returning JSON (Confirmation by the accountable person).

Owner check (ownerField)

Use ownerField to check that "only the owner of this data may call this". For example, a profile update method can be limited to the signed-in user's own profile.

The check works only when the policy condition calls hasPermission(...). Before the method runs, while the policy is being evaluated, CONTEXA reads the field named by ownerField from the target of hasPermission (or from the entity loaded by its ID) and compares it with the signed-in user's name (Authentication.getName()). It does not look at the method's return value.

@Protectable(ownerField = "username")
public void updateProfile(UserProfile profile) {
    ...
}
// The condition of this method's METHOD policy
// hasPermission(#profile, 'USER_UPDATE')
  1. hasPermission itself must be true first (Permission Evaluators). When it is false, the owner check is never reached and the call is refused.
  2. A call with two arguments (hasPermission(#profile, 'USER_UPDATE')) checks the field of that object. A call with three arguments (hasPermission(#id, 'USER', 'UPDATE')) checks the field of the entity read through findById from the repository bean of that domain's evaluator.
  3. CONTEXA looks the field up through the class hierarchy, and then through the getter (getUsername()). It compares the value as a string.
  4. Holding the ROLE_ADMIN authority skips the owner check.
  5. A missing field, value or entity refuses the call. Nested dot paths (owner.id) are not supported. When the target is null, no owner check is made.
  6. A condition can read the field name as #ownerField.
Under HOST_OWNED, check the permission evaluators first. The authorities the built-in domain evaluators look at (PermissionAuthority) are put in by CONTEXA's user store when CONTEXA owns sign-in. When your application owns sign-in, its login information usually carries none. Then hasPermission is false and the owner check never passes (What hasPermission checks).

The nine attributes

ownerField, verificationRequired and sync change how the call is checked. The other six tell CONTEXA what kind of resource the method is. The AI analysis reads these values when it decides, and importance also changes how requests that arrive in numbers are handled.

AttributeDefaultWhat it does
ownerField""Field or getter name used by the owner check. Left empty, no owner check is made (above)
verificationRequiredtrueWhether to apply the prompt quality certification gate (step ⑤ of the processing order). OSS has no gate implementation, so it has an effect only when you register a ProtectableResourceCertificationGate bean. With false, the method skips the gate. Use it for exceptional resources such as authentication features or health checks
syncfalseWhether to get the decision within this call. With true, the method runs only after the analysis finishes with an ALLOW (Choosing sync)
category""The business category the method belongs to (for example REPORT). The AI analysis compares it with the business categories the user's role covers and with the scope delegated to an AI agent. Sensitivity words such as CONFIDENTIAL alone are not taken as a category
sensitivity""The resource's sensitivity (PUBLIC, INTERNAL, CONFIDENTIAL, RESTRICTED, ...). A value your application states on the request wins. A high sensitivity such as CONFIDENTIAL or RESTRICTED makes the resource a sensitive one (see importance below)
actions{}What the method does (READ, EXPORT, ...). Each value must name one of READ, WRITE, EXPORT, DELETE, ADMIN and EXECUTE. With exactly one, it becomes the request's operation unless your application states another on the request. A value outside these six is reported in a warning at startup. The request's operation then comes from its HTTP method
importanceUNSPECIFIEDYour application states whether the method is a sensitive resource. The three values differ as listed below the table
privilegedfalseStates that the method is privileged. Only true means something; false leaves it unstated. The resource information sent to the AI analysis then carries a privileged mark
exportSensitivefalseStates that the method exports sensitive data. Only true means something. The resource information then carries a sensitive-export mark. When privileged or this attribute is true and you state no sensitivity, the analysis receives a high sensitivity (HIGH)
  • SENSITIVE: treats the resource as sensitive. A request cannot lower it. For AI agent requests, each resource is decided on its own (an ALLOW earned on this resource is not reused for others), and when decision merging is on, restrictions are checked again right before the method runs. A person's call cannot pass, right after the environment changes, until a decision exists for the new environment.
  • NON_SENSITIVE: states that the resource is not sensitive. When decision merging (Decision merging, off by default) is on, a few read requests from an AI agent (3 by default) can pass before the first decision arrives. A sensitivity stated on the request can raise it to SENSITIVE.
  • UNSPECIFIED (default): states nothing. If sensitivity holds a word such as CONFIDENTIAL or RESTRICTED, the resource is treated as sensitive. Otherwise it is treated as a resource whose sensitivity is unknown. Either way, decision merging does not let it pass early.
  • These nine are the only attributes. The resourceId, resourceUrl, httpMethod and criticality attributes of older documents do not exist in the code.
  • When the application starts, CONTEXA puts every @Protectable method of every bean into the resource information registry (where per-method resource information is kept).
    • The resource ID is fully.qualified.Class#method. Overloaded methods with the same name share one resource ID, and the values of the first one found are used.
    • category, sensitivity, actions, privileged, exportSensitive and importance become resource information the decision engine uses.
    • A ResourceContextDescriptor bean with the same resource ID replaces the annotation's values.

Re-entry within the same request

When the same protected method is called again while one HTTP request is being handled (for example, one request calls the method twice), CONTEXA analyses it only once. This is not a guard against the same user calling repeatedly within a few seconds: the check key includes a request ID the server creates anew for each request, so different requests never block one another.

  • Check key: tenant, request ID, HTTP method, address, fully.qualified.Class.method and operating mode, plus the user and the context fingerprint (session, client IP, User-Agent).
  • When caught: a sync = false method runs without analysis (no analysis event is sent, only a suppression record is kept). A sync = true method is refused under ENFORCE with 503 (PENDING_ANALYSIS) and runs in the other modes.
  • Window: contexa.security.zerotrust.protectable.rapid-reentry-window-ms (default 5000) is how long the check is kept after the first call. Zero or less turns it off. Without a sign-in, a request or a context fingerprint, nothing is checked.
  • Store: memory in standalone mode (keys that vanish when the window ends), Redis in distributed mode (SET NX, key security:protectable:rapid-reentry: + MD5). A Redis error lets the call through. Replace the store with a ProtectableRapidReentryRepository bean.

Analysis events and metrics

  • A sync = false method sends an analysis event when it finishes (normally or with an exception). The event is the record of this one call. It carries the outcome (METHOD_COMPLETED, METHOD_FAILED), and the analysis reads it to produce the decision that applies from the next call on (Decision engine).
  • No event is sent when: the mode does not analyse (DISABLED, OBSERVE); a re-entry within the same request; a policy denial (a record of the refusal is kept instead); a Zero Trust refusal; a call already decided through sync; requests that decision merging let through early, except the first. Without an event publisher bean nothing is sent either.
  • Metrics: auto-configuration does not give the interceptor a metrics collector (AuthorizationMetrics). If you set one, it counts the time spent sending the event and the number of decisions.
