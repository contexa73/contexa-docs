End-to-End Dynamic Authorization

This walkthrough moves hard-coded requestMatchers rules into database policies, so URL and method access can change without code changes. It covers preparation, four scenarios, the decision when no policy applies, checking and rolling back, and the order in which one request is processed.

What you gain

A typical Spring Security application writes its access rules in Java configuration. Each new endpoint or role change means editing code, building and deploying.

http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/api/admin/**").hasRole("ADMIN")
    .requestMatchers("/api/users/**").hasAuthority("READ_USERS")
    .requestMatchers("/api/reports/**").hasAnyRole("ADMIN", "ANALYST")
    .requestMatchers("/api/orders/**").hasAuthority("MANAGE_ORDERS")
    // ... dozens more rules
    .anyRequest().authenticated()
);

With Contexa only public paths stay in code, and everything else goes to one dynamic authorization manager. Rules are edited as policies in the admin console and stored in the Contexa database; saving reloads them at once, with no recompilation.

http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/css/**", "/js/**").permitAll()
    .anyRequest().access(customDynamicAuthorizationManager)
);

Preparation

URL policies are evaluated only when the request passes CustomDynamicAuthorizationManager. Who connects the manager to the chain depends on the setup. @Protectable method policies are evaluated whenever the method is called, in every setup.

SetupURL policiesMethod policies
HOST_OWNED (default)Evaluated only when the application's chain calls .access(customDynamicAuthorizationManager)Evaluated
@EnableAISecurity(mode = SecurityMode.FULL)The Contexa chain sends every request except static filesEvaluated
SANDBOX mode with CONTEXA_OWNED set explicitlyNot evaluated (that chain only restricts /contexa/admin/** to ADMIN and allows the rest)Evaluated

In the default HOST_OWNED mode, connect the manager in the application's security configuration. Keep static matchers only for paths that must really be public, such as static files and public APIs.

import io.contexa.contexaiam.security.xacml.pep.CustomDynamicAuthorizationManager;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class AppSecurityConfig {

    @Bean
    SecurityFilterChain securityFilterChain(HttpSecurity http,
            CustomDynamicAuthorizationManager customDynamicAuthorizationManager) throws Exception {
        http.authorizeHttpRequests(auth -> auth
                        .requestMatchers("/css/**", "/js/**", "/images/**").permitAll()
                        .requestMatchers("/api/public/**").permitAll()
                        .anyRequest().access(customDynamicAuthorizationManager))
                .formLogin(Customizer.withDefaults());
        return http.build();
    }
}
URLs without a policy are open by default. Once .anyRequest().authenticated() is replaced by the manager, a URL that no policy matches follows the "decision when no policy applies" (default PERMIT) and is allowed even without login. Decide on the decision when no policy applies before all policies are written.
  • In this chain the seed policies also protect the admin console: /contexa/admin/** is decided by ALLOW_CONTEXA_ADMIN_ADMINISTRATORS (hasRole('ADMIN')) (Protecting the admin console).
  • Make your packages the scan target: admin console "IAM → System Settings → Controller base packages" (Choosing the packages to scan). With the default io.contexa.contexaiam. none of your endpoints are registered.

Scenario 1: protecting URLs

1. Write the controller as usual. No security annotation is needed.

@RestController
@RequestMapping("/api/v1/invoices")
public class InvoiceController {

    private final InvoiceService invoiceService;

    public InvoiceController(InvoiceService invoiceService) {
        this.invoiceService = invoiceService;
    }

    @GetMapping
    public List<InvoiceDto> listInvoices() {
        return invoiceService.findAll();
    }

    @PostMapping
    public InvoiceDto createInvoice(@RequestBody CreateInvoiceRequest req) {
        return invoiceService.create(req);
    }

    @DeleteMapping("/{id}")
    public void deleteInvoice(@PathVariable Long id) {
        invoiceService.delete(id);
    }
}

2. Press "Load Resources" in Policy Center. If the package is a scan target, two resources are registered. The identifier is only the URL pattern, so GET and POST on the same path become one.

IdentifierHTTP methodType
/api/v1/invoicesGET or POST (whichever is found first)URL
/api/v1/invoices/{id}DELETEURL

A policy created from a resource matches only that resource's one HTTP method. To cover both methods of /api/v1/invoices, add a target with HTTP method ANY through "Configure Resource Permissions", or add targets in Manual Mode.

3. Review the resources and create permissions. Check the AI name and description (for example "List Invoices"); without an AI model the handler method name stays. "Create Permission & Policy" on a resource to protect creates its automatic permission (URL_…). Open public paths with permitAll in the application's chain or with a policy, not by excluding them (exclusion only hides them from the list).

4. Create a policy in Quick Mode. Choose the roles ROLE_ADMIN · ROLE_FINANCE, the CRUD permission READ and the effect ALLOW, then "Create Policy". This condition is stored; the automatic permission only sets the target and is not part of the condition.

(hasAuthority('ROLE_ADMIN') or hasAuthority('ROLE_FINANCE')) and (hasAuthority('READ'))

To use a business permission such as "read invoices" in the condition, create a permission with that name in "IAM → Permission Management", attach it to a role, and pick it in Quick Mode's permission list.

5. Write narrower rules in Manual Mode. For example, to allow deleting invoices only for administrators on weekdays from 9:00 to 18:00, from the internal network, with an AI decision of ALLOW or CHALLENGE, join everything in one condition with and. A URL policy joins several conditions with OR, so three separate conditions would allow the request when any one holds.

Name        INVOICE_DELETE_RESTRICTED
Effect      ALLOW        Priority 50
Target      URL /api/v1/invoices/{id}   HTTP method DELETE
Condition   hasAuthority('ROLE_ADMIN')
            and T(java.time.LocalDate).now().getDayOfWeek().getValue() <= 5
            and T(java.time.LocalTime).now().isAfter(T(java.time.LocalTime).of(9,0))
            and T(java.time.LocalTime).now().isBefore(T(java.time.LocalTime).of(18,0))
            and hasIpAddress('10.0.0.0/8')
            and #ai.hasActionIn('ALLOW','CHALLENGE')

Manual Mode stores the conditions as SpEL exactly as entered (through the policy service DefaultPolicyService). Quick and AI Mode build conditions through the business rule translation (BusinessPolicyServiceImpl).

6. When the request arrives, DELETE /api/v1/invoices/42 is handled like this. The chain hands it to CustomDynamicAuthorizationManager; the manager walks the URL policies in priority order, finds the one whose path and method match (the policy above) and evaluates its condition. With the default FIRST_APPLICABLE that first result (allow or deny) is final, and it is audited either way. No code change, no redeploy.

Scenario 2: protecting methods

Putting @Protectable on a service method protects it method by method. ownerField names the field that holds the owner in the returned or target object.

@Service
public class DocumentService {

    private final DocumentRepository documentRepository;

    public DocumentService(DocumentRepository documentRepository) {
        this.documentRepository = documentRepository;
    }

    @Protectable(ownerField = "createdBy")
    public Document getDocument(Long documentId) {
        return documentRepository.findById(documentId)
                .orElseThrow(() -> new NotFoundException("Document not found"));
    }

    @Protectable(ownerField = "createdBy")
    public void updateDocument(Long documentId, UpdateDocumentRequest req) {
        Document doc = documentRepository.findById(documentId)
                .orElseThrow(() -> new NotFoundException("Document not found"));
        doc.setTitle(req.getTitle());
        doc.setContent(req.getContent());
        documentRepository.save(doc);
    }
}

"Load Resources" registers two method resources in the same list as URL resources, with the same review, permission, policy and exclusion steps. The class must be inside a scan package, and only @Protectable placed directly on a method is listed.

IdentifierOwning classType
com.example.docs.DocumentService.getDocument(Long)DocumentServiceMETHOD
com.example.docs.DocumentService.updateDocument(Long,UpdateDocumentRequest)DocumentServiceMETHOD

A method policy joins all its conditions with AND, and rules cannot carry their own effect. So "owner or administrator" is written in one condition with or, and "deny on a BLOCK decision" is added as another condition.

Policy       DOCUMENT_UPDATE_OWNER     effect ALLOW   priority 100
Target       METHOD com.example.docs.DocumentService.updateDocument(Long,UpdateDocumentRequest)
Condition 1  !#ai.isBlocked()
Condition 2  hasAuthority('ROLE_ADMIN') or hasPermission(#documentId, 'DOCUMENT', 'UPDATE')
  • The two conditions are joined with AND, so the call is allowed only when "not BLOCK, and administrator or owner". A separate DENY policy on the same method would have the same target as an opposite-effect policy and fail the conflict check (CRITICAL) (Effect, priority and combining).
  • When updateDocument is called, Contexa's method interception (AOP) evaluates the policies before the method runs. hasPermission(...) needs a domain permission evaluator for the DOCUMENT type to allow it (Permission evaluators); then the document's createdBy value is compared with the login name (authentication.getName()). ROLE_ADMIN skips the owner comparison.
  • A method without a policy to run follows the "decision when no method policy applies" (default PERMIT).

Scenario 3: AI drafts and approval

AI Mode does not add a new threat language; it writes policy drafts that combine the roles, permissions, condition templates and SpEL you already have. The model receives:

  • The usable roles and permissions (with the resources the permissions protect)
  • The stored condition templates
  • A summary of existing policies (to avoid conflicts and duplicates) and the role hierarchy
  • Similar policies found in the vector store

The model returns a policy draft (name, effect, roles, permissions, CRUD, condition templates, #ai conditions, custom SpEL), ID → name tables and its reasoning, not a list of recommended conditions. Saving gives source AI_GENERATED and status pending (PENDING).

Approval statusEvaluatedWhen
PENDINGNoA policy written by AI was saved
APPROVEDYes (when active)An administrator approved it
REJECTEDNoAn administrator rejected it (inactive)
NOT_REQUIREDYes (when active)A policy written by a person

There is no separate draft (DRAFT) state. The approval steps and checks are in Approving AI drafts. Once approved, #ai conditions are evaluated against the AI decision stored for the user.

#ai.isAllowed()                          the AI decision is ALLOW
#ai.needsChallenge()                     step-up is required (CHALLENGE)
#ai.hasActionIn('ALLOW', 'CHALLENGE')    either of the two
hasRole('ADMIN') and !#ai.isBlocked()    together with a role check

Scenario 4: from static rules to dynamic policies

The order for moving a configuration with many rules, like the one below, to Contexa policies.

@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(auth -> auth
        .requestMatchers("/css/**", "/js/**", "/images/**").permitAll()
        .requestMatchers("/api/public/**").permitAll()
        .requestMatchers("/api/admin/users/**").hasRole("ADMIN")
        .requestMatchers("/api/admin/audit/**").hasAuthority("VIEW_AUDIT")
        .requestMatchers("/api/reports/financial/**").hasAnyRole("ADMIN", "FINANCE")
        .requestMatchers(HttpMethod.DELETE, "/api/**").hasRole("ADMIN")
        // ... more rules
        .anyRequest().authenticated()
    );
    return http.build();
}
  1. Starter and @EnableAISecurity: the resource scanners are auto-configured, but they do not run at application startup.
  2. Set the scan packages and "Load Resources": check the names of the resources found and define the ones to protect as permissions. The list becomes the inventory of everything the application exposes.
  3. Create a policy per rule: map them as in the table below. Afterwards you can add conditions that are hard in static configuration, such as time, IP or the AI decision.
  4. Change the chain: keep only the public paths and switch to .anyRequest().access(customDynamicAuthorizationManager) (the configuration in Preparation).
  5. Decide what happens without a policy: decide how the remaining URLs, which .anyRequest().authenticated() used to cover, are handled (next section).
Static rulePolicy to createStored condition
.hasRole("ADMIN")Quick Mode, role ROLE_ADMIN(hasAuthority('ROLE_ADMIN'))
.hasAuthority("VIEW_AUDIT")Pick the permission VIEW_AUDIT, created in "IAM → Permission Management", in Quick Mode(hasAuthority('VIEW_AUDIT'))
.hasAnyRole("ADMIN", "FINANCE")Quick Mode, roles ROLE_ADMIN · ROLE_FINANCE(hasAuthority('ROLE_ADMIN') or hasAuthority('ROLE_FINANCE'))
.requestMatchers(HttpMethod.DELETE, "/api/**").hasRole("ADMIN")Manual Mode, target URL /api/** with HTTP method DELETEhasRole('ADMIN')

The decision when no policy applies, and combining

When no URL policy matches the request, the manager uses the "decision when no policy applies". The default is PERMIT (allow). The same holds when every matching policy is a DENY policy whose condition is false (not applicable), except under DENY_UNLESS_PERMIT, which denies then. The last line of the manager hands this decision to the combining step.

return combiningEvaluator.evaluate(matchedDecisions, currentAlgorithm, currentNoPolicyDecision);

URLs without a policy are closed through the setting.

  • Switch to deny: save DENY in admin console "IAM → System Settings → Decision when no URL policy applies". The setting name is contexa.policy.no-matching-url-policy-decision, but the system settings row created by the default seed overwrites YAML at startup, so change it on screen (Decision settings). When no policy matches at all, this decision is used whatever the combining algorithm.
  • Not with a broad policy: a policy on a broad path such as /** overlaps the targets of other policies, so an opposite-effect policy fails the conflict check (HIGH), either this one or the ones you create later (Conflict check).

What the effect means: an ALLOW policy allows when its condition is true and denies when it is false. A DENY policy denies when its condition is true and is not applicable (on to the next policy) when it is false. The four combining algorithms are in Effect, priority and combining.

How to check

  • Simulator: enter a user and a request in Policy Center's "Simulator" tab to see the result. An unsaved candidate policy can be compared before and after (#ai counts as true, hasIpAddress as false).
  • Access matrix: a roles × resources table shows who reaches what.
  • Real-time Monitor: every URL policy decision is audited, both allow (AUTHORIZATION_GRANTED) and deny (AUTHORIZATION_DENIED). Filter by decision with DECISION_ALLOW · DECISION_DENY (Real-time Monitor).
  • When a signed-in user's request is denied by a URL policy, Contexa also keeps that as a fact of the user's session and of the user's scope (when an AuthorizationDenialRecorder is present).

Rolling back

WayWhenHow
Version rollbackBring a changed policy back to earlier contentPolicy detail screen "Version History" → "Rollback to this version" (with a change reason). Recorded as a new version and applied at once

There is no button that switches a policy off (inactive) for a while. Policies made through the policy service are always stored as active.

How one request is processed

PartWhat it does
CustomDynamicAuthorizationManagerTies matching, evaluation, combining, the delegator check and auditing together. The decision it returns is only allow or deny; reason and risk go into the audit record
