Admin Console

The admin console (/contexa/admin/**) is where you manage policies, access, users, security decisions, agents and prompt quality. This page shows how the console is protected and entered, what each menu does, and what to do first.

Contexa protects the admin console in both ownership modes, and it needs a Contexa administrator account. In the default HOST_OWNED mode a chain of Contexa's own takes only /contexa/admin/** and signs Contexa's administrators in at /contexa/admin/login. The application's users cannot enter it, and the application does not need to restrict these paths, even when its own chain leaves every request at permitAll (Protecting it in HOST_OWNED mode).

Entering and protecting the console

Who can open the console depends on the authentication ownership (contexa.bridge.ownership) and the security mode.

The unblock-request and pending-analysis paths are /contexa/admin/api/aiam/zero-trust/** and /contexa/admin/api/aiam/sse/zero-trust/**. In the Contexa chain (the first two rows) blocked users use them to ask for their own release, so they are open to any signed-in user, not only administrators. The admin controllers carry @PreAuthorize("hasRole('ADMIN')"), so with method security on they need the ROLE_ADMIN authority.

Protecting it in HOST_OWNED mode

Nothing is needed in the application's security configuration. Contexa registers a chain of its own (contexaAdminConsoleSecurityFilterChain, order Ordered.HIGHEST_PRECEDENCE + 10) that takes only /contexa/admin and /contexa/admin/**. It is registered after Spring Boot's security auto-configuration, so an application without a chain of its own still gets Spring Boot's default chain. It signs administrators in with Contexa's user store (users in the Contexa database with the ADMIN role) at /contexa/admin/login; the form posts to the same address. The console sign-in, its CSRF token and the saved request are kept under session keys apart from the application's, so an administrator and an application user in one browser do not overwrite each other.

The console needs a Contexa administrator account; the application's user accounts cannot enter it. Contexa creates the first administrator at the first start from the settings below. Without the password it creates none, and a user with the same username or e-mail is never changed (First start).

contexa:
  iam:
    seed:
      admin:
        username: admin                       # default admin
        email: admin@example.com              # default admin@localhost
        password: ${CONTEXA_ADMIN_PASSWORD}   # example: CONTEXA_ADMIN_PASSWORD=Change-Me-2026

The value Change-Me-2026 is only an example. Put the real password in an environment variable (or a secret store) and never in a file you commit.

The sign-out button in the console header posts to /contexa/admin/logout. It ends only the console sign-in and keeps the session, so the application's sign-in in the same browser stays.

Sign-ins to the console count against the administrator account as they do under CONTEXA_OWNED: failed attempts, the lock and the address throttle follow the password policy. The application's own sign-ins never count against Contexa's accounts.

Two groups of paths under /contexa/admin/api/aiam/ belong to the application's signed-in user, not to the administrator: the release request of a blocked user (zero-trust/initiate-block-mfa, zero-trust/unblock-request) and the updates of the pending-analysis screen (sse/zero-trust/**). The console chain leaves them out, and they answer only a signed-in user, like the other user pages.

Method security is optional: when the application turns it on (@EnableMethodSecurity), the @PreAuthorize("hasRole('ADMIN')") on the console's controllers adds a second check. Because the console's chain takes /contexa/admin/**, the application's chain, and URL policies connected to it, do not see these paths.

IP Management rules can add a second layer. They apply to /contexa/* paths only in HOST_OWNED mode and to every path in CONTEXA_OWNED mode (IP and sessions). They do not replace authentication.

Menus

  • Menus live in the admin_menu table of the Contexa database. At startup the seed file db/data-menu.sql inserts or updates the default menus and merges duplicate rows with the same data_page. The screen is drawn from the menuTree that AdminMenuService builds from this table; no menu is hard-coded in the templates.
  • Menu type CORE is always shown. ENTERPRISE is shown only with contexa.enterprise.enabled: true, and SAAS only when that and contexa.saas.enabled: true are both on.
  • A menu with roles (admin_menu_role) is shown only to people with one of those roles; a menu without roles is shown to everyone. Add menus in "Menu Management" or in the seed file.

Access Center

Path /contexa/admin/access-center. It manages the chain user → group → role → permission in four tabs (Users, Groups, Roles, Overview). A user's detail shows the groups, the roles granted directly, the roles inherited from groups, and the permissions the user actually has. The Overview tab shows the counts of users, groups, roles and permissions and a diagram of the user → group → role → permission structure.

Permissions named READ · WRITE · UPDATE · DELETE linked to a role count as CRUD permissions. When a role is given to a user or a group, you can choose a subset of them; READ is always included. The choice is stored per user and role (UserRolePermission) and per group and role (GroupRolePermission).

Users, groups, roles, permissions and role hierarchy

Users (/contexa/admin/users), groups (/contexa/admin/groups), roles (/contexa/admin/roles) and permissions (/contexa/admin/permissions) are created, changed and deleted here. Users get permissions through their groups and their directly granted roles.

The role hierarchy (/contexa/admin/role-hierarchies) lets a higher role inherit the permissions of lower roles. The default seed hierarchy is ROLE_ADMIN > ROLE_DEVELOPER > ROLE_INFRA > ROLE_USER. The active hierarchy is applied to the Spring Security RoleHierarchy at startup and on every change, and is used when URL and method policy expressions are evaluated.

Real-time Monitor

Path /contexa/admin/security-monitor. It reads the audit records (audit_log) from the database 20 at a time. The period is 1 hour, 6 hours, 24 hours (default) or 3 days, and you can filter by category, a user-name keyword and subject kind (HUMAN_USER · DELEGATED_AGENT · AUTONOMOUS_AGENT).

Blocked users and stopped agents

Path /contexa/admin/blacklist. Users blocked by an AI decision, by state.

StateMeaning
BLOCKEDBlocked
UNBLOCK_REQUESTEDThe user asked for release
RESOLVEDHandled by an administrator
TIMEOUT_RESPONDEDNo release request within 24 hours of the block; handed to the automatic response
MFA_FAILEDThe unblock MFA failed

On the detail screen (/{id}), entering an action and a reason resolves the block (POST /{id}/resolve): the state becomes RESOLVED and the decision is passed to the decision engine as an administrator override. Delete a record with POST /{id}/delete; the matching JSON API is /contexa/admin/api/blacklist.

Stopped agents and delegations are shown and released in the agent stops tab of the same menu (/contexa/admin/blacklist/agents), which also holds the kill switch. It is separate from the list of blocked people (console screens of Stop, Confirm and Limit).

IP and sessions

  • IP Management (/contexa/admin/ip-management): create ALLOW · DENY rules for IPv4, IPv6 or CIDR, with expiry, on/off toggle and CSV export. An IP hit by a DENY rule gets 403. As soon as one active ALLOW rule exists, the rules act as an allow list and every IP not on it gets 403 too. The filter covers /contexa/* paths only in HOST_OWNED mode and every path in CONTEXA_OWNED mode, and skips static files.
  • Session Management (/contexa/admin/session-management): search active sessions (session ID, user, IP, User Agent, login time, last activity) and end one session (POST /{sessionId}/invalidate) or all sessions of a user (POST /user/{userId}/invalidate-all). CSV export is available.

Menu management

Path /contexa/admin/menu-management. It edits the menus in the admin_menu and admin_menu_role tables. The database is the only source of menus, so add new menus here or in db/data-menu.sql, not in the sidebar HTML. The visibility rules (menu type, roles) are those under Menus.

AI policy generation

Method · pathWhat it does
POST /contexa/admin/api/ai/policies/generate/streamWrites a policy draft from a natural-language request, streamed with SSE
POST /contexa/admin/api/ai/policies/generateThe same, returned in one response. 409 when an identical request is already running
POST /contexa/admin/api/policies/build-from-business-ruleSaves the confirmed draft as a policy
  1. The administrator writes the request (for example "developers may reach /api/** during business hours").
  2. AdvancedPolicyGenerationLab adds the usable roles, permissions and condition templates, the existing policies and the role hierarchy, and PolicyGenerationContextRetriever finds similar policies in the vector store.
  3. The AI returns a PolicyResponse (the policy draft, ID → name tables for roles, permissions and conditions, and the reasoning).
  4. The screen checks it against the items that exist and shows a preview.
  5. On save, BusinessPolicyService creates the policy, targets, rules and conditions and reloads. Because the source is AI_GENERATED, the policy is saved as pending and is not evaluated until approved (Approving AI drafts).
