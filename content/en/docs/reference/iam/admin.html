Admin Console

The admin console (/contexa/admin/**) is where you manage policies, access, users, security decisions, agents and prompt quality. This page shows how the console is protected and entered, what each menu does, and what to do first.

Contexa protects the admin console in both ownership modes, and it needs a Contexa administrator account. In the default HOST_OWNED mode a chain of Contexa's own takes only /contexa/admin/** and signs Contexa's administrators in at /contexa/admin/login. The application's users cannot enter it, and the application does not need to restrict these paths, even when its own chain leaves every request at permitAll (Protecting it in HOST_OWNED mode).

Entering and protecting the console

Who can open the console depends on the authentication ownership (contexa.bridge.ownership) and the security mode.

Protecting it in HOST_OWNED mode

Nothing is needed in the application's security configuration. Contexa registers a chain of its own (contexaAdminConsoleSecurityFilterChain, order Ordered.HIGHEST_PRECEDENCE + 10) that takes only /contexa/admin and /contexa/admin/**. It is registered after Spring Boot's security auto-configuration, so an application without a chain of its own still gets Spring Boot's default chain. It signs administrators in with Contexa's user store (users in the Contexa database with the ADMIN role) at /contexa/admin/login; the form posts to the same address. The console sign-in, its CSRF token and the saved request are kept under session keys apart from the application's, so an administrator and an application user in one browser do not overwrite each other.

The console needs a Contexa administrator account; the application's user accounts cannot enter it. Contexa creates the first administrator at the first start from the settings below. Without the password it creates none, and a user with the same username or e-mail is never changed (First start).

contexa:
  iam:
    seed:
      admin:
        username: admin                       # default admin
        email: admin@example.com              # default admin@localhost
        password: ${CONTEXA_ADMIN_PASSWORD}   # example: CONTEXA_ADMIN_PASSWORD=Change-Me-2026

The value Change-Me-2026 is only an example. Put the real password in an environment variable (or a secret store) and never in a file you commit.

The sign-out button in the console header posts to /contexa/admin/logout. It ends only the console sign-in and keeps the session, so the application's sign-in in the same browser stays.

Sign-ins to the console count against the administrator account as they do under CONTEXA_OWNED: failed attempts, the lock and the address throttle follow the password policy. The application's own sign-ins never count against Contexa's accounts.

Two groups of paths under /contexa/admin/api/aiam/ belong to the application's signed-in user, not to the administrator: the release request of a blocked user (zero-trust/initiate-block-mfa, zero-trust/unblock-request) and the updates of the pending-analysis screen (sse/zero-trust/**). The console chain leaves them out, and they answer only a signed-in user, like the other user pages.

Method security is optional: when the application turns it on (@EnableMethodSecurity), the @PreAuthorize("hasRole('ADMIN')") on the console's controllers adds a second check. Because the console's chain takes /contexa/admin/**, the application's chain, and URL policies connected to it, do not see these paths.

IP Management rules can add a second layer. They apply to /contexa/* paths only in HOST_OWNED mode and to every path in CONTEXA_OWNED mode (IP and sessions). They do not replace authentication.

Menus

  • Menus live in the ctxa_admin_menu table of the Contexa database. At startup the seed file db/data-menu.sql inserts or updates the default menus and merges duplicate rows with the same data_page. The screen is drawn from the menuTree that AdminMenuService builds from this table; no menu is hard-coded in the templates.
  • Menu type CORE is always shown. ENTERPRISE is shown only with contexa.enterprise.enabled: true, and SAAS only when that and contexa.saas.enabled: true are both on.
  • A menu with roles (ctxa_admin_menu_role) is shown only to people with one of those roles; a menu without roles is shown to everyone. Add menus in "Menu Management" or in the seed file.

JSON API and hourly tables

GET /contexa/admin/api/dashboard?period=day|week|month|quarter (default week) answers the whole dashboard as one JSON document: period, zeroTrust (the console's overview of the period, the decisions waiting for review and, under SHADOW, the adoption's verdict), operations, policy, iam, security, blocked, agents, system, attention, changes and denials. Only administrators get it: ROLE_ADMIN is checked on every call, besides method security, and another user gets 403. A period other than the four gets 400. The screen works out the to-do rows and the area states from these numbers.

Two numbers would be too heavy to count from the records on every call, so a scheduled job counts them by hour, as the Zero Trust console keeps its own hourly tables.

Every contexa.security.zerotrust.console.aggregation-interval-ms (default 60000) the current and the previous hour are counted again, and so is any hour an audit record written late belongs to. The first pass after a start counts the last 48 hours again, and the passes after it fill, 48 hours at a time, the hours of the last 90 days that have no row yet. The retention runs at contexa.security.zerotrust.console.retention-cron (default 0 17 3 * * *). Both retention values can also be saved in the system settings (System settings).

Access Center

Path /contexa/admin/access-center. It manages the chain user → group → role → permission in four tabs (Users, Groups, Roles, Overview). A user's detail shows the groups, the roles granted directly, the roles inherited from groups, and the permissions the user actually has. The Overview tab shows the counts of users, groups, roles and permissions and a diagram of the user → group → role → permission structure.

Permissions named READ · WRITE · UPDATE · DELETE linked to a role count as CRUD permissions. When a role is given to a user or a group, you can choose a subset of them; READ is always included. The choice is stored per user and role (UserRolePermission) and per group and role (GroupRolePermission).

Users, groups, roles, permissions and role hierarchy

Users (/contexa/admin/users), groups (/contexa/admin/groups), roles (/contexa/admin/roles) and permissions (/contexa/admin/permissions) are created, changed and deleted here. Users get permissions through their groups and their directly granted roles. The lists of groups, roles, permissions and role hierarchies page as the policy list does: first, previous, the pages near the current one, next and last. They draw no link to every page, and the page links keep the search word.

The role hierarchy (/contexa/admin/role-hierarchies) lets a higher role inherit the permissions of lower roles. The default seed hierarchy is ROLE_ADMIN > ROLE_DEVELOPER > ROLE_INFRA > ROLE_USER. The active hierarchy is applied to the Spring Security RoleHierarchy at startup and on every change, and is used when URL and method policy expressions are evaluated.

A save of the password policy or the system settings that changes no value records nothing, nor does excluding a resource already excluded, saving a resource's status as it was, or saving a condition's classification as it was. The dashboard's recent admin changes count and name them (Dashboard).

Security event log

Path /contexa/admin/security-monitor (Security → Security event log): "The authentication, authorization and decision events of the audit log, in time order. A decision row opens its decision." It reads the audit records (ctxa_audit_log) from the database 20 at a time and shows how many the list holds ("{count} events"). The period is 1 hour, 6 hours, 24 hours (default), 3 days, 7 days, 30 days or 90 days (?hours=, which takes other numbers of hours too), and you can filter by category, a user-name keyword and subject kind (HUMAN_USER · DELEGATED_AGENT · AUTONOMOUS_AGENT). The "Seal mismatch" chip lists the filter SEAL_MISMATCH. A link can name the start instead (?from=, an ISO instant such as 2026-11-18T03:00:00Z). The cards, the category and filter links, the pages and the CSV keep it; a period chip drops it. A start that cannot be read or lies ahead is ignored, and the last hours are read. The pages, the CSV, clearing the search and the period chips keep every filter of the list (category, filter, user name, subject kind). The pages are those of the policy list: first, previous, the pages near the current one, next and last. A page number before the first or after the last reads as the first or the last. The list, the CSV and the table of addresses read with every filter applied at once. The user name and the subject kind narrow a category's list, the list of each filter below, and the table of addresses. A search keeps the subject chip.

Blocked users and stopped agents

Path /contexa/admin/blacklist. Users blocked by an AI decision, by state.

StateMeaning
BLOCKEDBlocked
UNBLOCK_REQUESTEDThe user asked for release
RESOLVEDHandled by an administrator
TIMEOUT_RESPONDEDNo release request within 24 hours of the block; handed to the automatic response

On the detail screen (/{id}), entering an action and a reason resolves the block (POST /{id}/resolve): the state becomes RESOLVED and the decision is passed to the decision engine as an administrator override. Delete a record with POST /{id}/delete, which is written to the audit log (Audit records of admin changes); the matching JSON API is /contexa/admin/api/blacklist.

Stopped agents and delegations are shown and released in the agent stops tab of the same menu (/contexa/admin/blacklist/agents), which also holds the kill switch. It is separate from the list of blocked people (console screens of Stop, Confirm and Limit).

IP and sessions

  • IP Management (/contexa/admin/ip-management): create ALLOW · DENY rules for IPv4, IPv6 or CIDR, with expiry, on/off toggle and CSV export. An IP hit by a DENY rule gets 403. As soon as one active ALLOW rule exists, the rules act as an allow list and every IP not on it gets 403 too. The filter covers /contexa/* paths only in HOST_OWNED mode and every path in CONTEXA_OWNED mode, and skips static files. The allow, deny and total counts above the list are the rules in force now: enabled and not expired, as the filter applies them. Creating, deleting, switching on and switching off a rule is written to the audit log (Audit records of admin changes). The pages are those of the policy list and keep the type and the search word.
  • Session Management (/contexa/admin/session-management): search active sessions (session ID, user, IP, User Agent, login time, last activity) and end one session (POST /{sessionId}/invalidate) or all sessions of a user (POST /user/{userId}/invalidate-all). A session ended here is written to the audit log (Audit records of admin changes). CSV export is available. The pages are those of the policy list and keep the search word. Sessions are tracked when Contexa owns sign-in (CONTEXA_OWNED). A tracked session is marked expired when its HTTP session ends (a logout, its idle limit, or the application invalidating it) or its ID changes; under a new ID it is tracked again at its next request. Every 5 minutes, on one node at a time, a scheduled job deletes the active sessions no request reached for longer than the HTTP session idle limit (server.servlet.session.timeout, default 30 minutes) plus 2 minutes of tracking lag, such as the sessions of a stopped server, and deletes the ended sessions after 7 days. Sessions that never time out are not deleted this way.

The password policy (/contexa/admin/password-policy) applies the same rules to user registration and password changes. The lockout, IP lockout and expiry items are used by login failure handling (LoginPolicyService).

Each account's credentials_expired column says what the policy reads: a login writes it when it differs, saving the policy sets it for every account by the new expiry days (with 0 days passwords do not expire and every account's is cleared), and a new password an administrator sets clears it.

The password change screen is /contexa/password-change. It takes the current password and the new one twice, checks the policy, changes it, and sends the user to the Contexa login screen (/contexa/admin/mfa/login).

Menu management

Path /contexa/admin/menu-management. It edits the menus in the ctxa_admin_menu and ctxa_admin_menu_role tables. The database is the only source of menus, so add new menus here or in db/data-menu.sql, not in the sidebar HTML. The visibility rules (menu type, roles) are those under Menus.

AI policy generation

Method · pathWhat it does
POST /contexa/admin/api/ai/policies/generate/streamWrites a policy draft from a natural-language request, streamed with SSE
POST /contexa/admin/api/ai/policies/generateThe same, returned in one response. 409 when an identical request is already running
POST /contexa/admin/api/policies/build-from-business-ruleSaves the confirmed draft as a policy
  1. The administrator writes the request (for example "developers may reach /api/** during business hours").
  2. AdvancedPolicyGenerationLab adds the usable roles, permissions and condition templates, the existing policies and the role hierarchy, and PolicyGenerationContextRetriever finds similar policies in the vector store.
  3. The AI returns a PolicyResponse (the policy draft, ID → name tables for roles, permissions and conditions, and the reasoning).
  4. The screen checks it against the items that exist and shows a preview.
  5. On save, BusinessPolicyService creates the policy, targets, rules and conditions and reloads. Because the source is AI_GENERATED, the policy is saved as pending and is not evaluated until approved (Approving AI drafts).
