URL Access Policies (Dynamic URL Authorization)

Decide whether a URL request is allowed or denied with policies stored in the database. This page covers how to connect URL policies to requests, how to create a first policy, the order in which one request is decided, how to write conditions, and how a changed policy takes effect.

What it does

Spring Security's static matchers (requestMatchers(...).hasRole(...)) are fixed in code. CustomDynamicAuthorizationManager is a Spring AuthorizationManager: when the application starts it reads the URL policies from the database, builds a list of address matchers, and decides every request with that list. When you change a policy in the Policy Center admin screen, the list is rebuilt without redeploying. A policy written by AI enters the list only after a person approves it.

Enabling: connecting to requests

URL policies apply to requests only while the manager is connected to the authorization step of the security filter chain. With contexa-iam present the manager bean always exists, but how it is connected depends on authentication ownership.

import io.contexa.contexaiam.security.xacml.pep.CustomDynamicAuthorizationManager;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class AppSecurityConfig {

    @Bean
    SecurityFilterChain appChain(HttpSecurity http,
                                 CustomDynamicAuthorizationManager contexaUrlPolicies) throws Exception {
        http.authorizeHttpRequests(auth -> auth
                        .requestMatchers("/css/**", "/js/**", "/images/**", "/favicon.ico").permitAll()
                        .anyRequest().access(contexaUrlPolicies))
                .formLogin(Customizer.withDefaults());
        return http.build();
    }
}
What URL policies cannot see under HOST_OWNED. The authentication bridge filter is a servlet filter ordered right after your security chain (the chain's order + 1), so it runs after your security chain has finished. URL policies connected to your chain therefore do not see the delegation stamp: agent expressions answer as for a person's request, and no delegator re-evaluation happens. Put agent conditions in @Protectable method policies.

Using static rules alongside

  • Spring Security reads matchers from the top and uses the first that matches. Put static requestMatchers before anyRequest().
  • A request caught by a static matcher never reaches the URL policy manager. A database policy aimed at an address opened with permitAll() is silently ignored, so do not cover the same address with both a static rule and a policy.
  • Requests allowed statically do not pass through URL policies, so they do not appear in the authorization audit log either.

Creating a first URL policy

  1. Open the admin screen Policy > Policy Center (/contexa/admin/policy-center).
  2. In the Resources tab, pick a URL resource and choose "Create Permission & Policy", or create one in the Policy Creation tab in Quick, Manual or AI mode. If the resource is missing, check the scan packages of the Resource Scanner.
  3. Set the name, effect (ALLOW or DENY), priority (lower numbers first), URL pattern (/api/reports/**), HTTP method (GET and so on; ANY for every method) and condition (hasRole('MANAGER')).
  4. Saving rebuilds the mappings at once; no restart is needed. A policy written by hand has source MANUAL and approval status NOT_REQUIRED, so it runs right away.
  5. Check it with the policy list, the simulator and the impact analysis. Writing, validation, impact and simulation all live in Policy Center (Policy Management).

The address pattern uses Spring PathPattern syntax. Write ** only at the end of a pattern, as in /api/reports/**; a path variable such as /api/users/{id} can be read in conditions as #id.

From server code, use PolicyService. A saved policy takes effect at once, exactly like one created on screen.

import io.contexa.contexaiam.domain.dto.ConditionDto;
import io.contexa.contexaiam.domain.dto.PolicyDto;
import io.contexa.contexaiam.domain.dto.RuleDto;
import io.contexa.contexaiam.domain.dto.TargetDto;
import io.contexa.contexaiam.domain.entity.policy.Policy;
import io.contexa.contexaiam.domain.entity.policy.PolicyCondition;
import io.contexa.contexaiam.security.xacml.pap.service.PolicyService;
import java.util.List;
import org.springframework.stereotype.Service;

@Service
public class ReportPolicySetup {

    private final PolicyService policyService;

    public ReportPolicySetup(PolicyService policyService) {
        this.policyService = policyService;
    }

    public void createReportPolicy() {
        PolicyDto policy = PolicyDto.builder()
                .name("REPORTS_FOR_MANAGERS")
                .description("Managers read reports while the AI decision allows them")
                .effect(Policy.Effect.ALLOW)
                .priority(100)
                .targets(List.of(TargetDto.builder()
                        .targetType("URL")
                        .targetIdentifier("/api/reports/**")
                        .httpMethod("GET")
                        .build()))
                .rules(List.of(RuleDto.builder()
                        .description("manager and AI allow")
                        .conditions(List.of(ConditionDto.builder()
                                .expression("hasRole('MANAGER') and #ai.isAllowed()")
                                .authorizationPhase(PolicyCondition.AuthorizationPhase.PRE_AUTHORIZE)
                                .build()))
                        .build()))
                .build();
        policyService.createPolicy(policy);
    }
}
Write "and" inside one condition. A URL policy joins several conditions with or. Putting hasRole('MANAGER') and #ai.isAllowed() in two separate conditions gives (hasRole('MANAGER')) or (#ai.isAllowed()), which allows the request when either one holds.

The order in which one request is decided

  • A matching ALLOW policy whose condition is false denies too. Explicit DENY policies are not the only way to block. The full effect and combining rules are in Authorization Overview > Decision rules.
  • An address without a policy needs a signed-in user by default. The default decision is AUTHENTICATED: a signed-in user passes and a request that is not signed in is turned away (Contexa's own sign-in stays open). To open such addresses to everyone, set contexa.policy.no-matching-url-policy-decision to PERMIT. To deny by default, set it to DENY. Either can also be saved in the system settings screen (Settings). A catch-all DENY policy such as /** is hard to use instead: saving a policy is refused as a conflict when an active policy with the opposite effect covers the same address or an address its pattern overlaps (different HTTP methods count as no overlap).
  • A policy that failed the check at load time denies all its targets. The error log carries the policy ID and the reason.
  • The audit record (AUTHORIZATION_GRANTED, AUTHORIZATION_DENIED) carries the source IAM, user, client IP, session ID, User-Agent, request address, HTTP method, decision (ALLOW, DENY) and outcome (GRANTED, DENIED).
  • URL policy decisions apply whatever the Zero Trust enforcement mode. The mode changes only whether the delegator re-evaluation refuses (below).

Writing conditions

How stored conditions become an expression

A URL policy tidies its stored conditions into one expression at load time (PolicyExpressionConverter). Method policies skip this tidying and join their conditions with and as written.

Stored conditionsResulting expression
NonepermitAll: always allow for ALLOW, always deny for DENY
OneAs written; permitAll, denyAll and isAuthenticated() also stay as they are
Only an authority name (ROLE_ADMIN)hasAuthority('ROLE_ADMIN')
Several, all authority nameshasAnyAuthority('ROLE_ADMIN','ROLE_AUDITOR')
Several, mixed(condition1) or (condition2)
Upper-case authority names inside an expressionOnly those names are wrapped: ROLE_ADMIN or hasRole('AUDITOR') → hasAuthority('ROLE_ADMIN') or hasRole('AUDITOR')
A condition with hasPermission(...)That part is removed (object permissions cannot be judged for a URL). If nothing remains, ALLOW always denies (denyAll) and DENY always applies (permitAll)

Condition examples

hasRole('MANAGER') and #ai.isAllowed()
ROLE_ADMIN or hasRole('AUDITOR')
hasIpAddress('10.0.0.0/8') and T(java.time.LocalTime).now().getHour() < 18
httpMethod == 'GET' and !#ai.isBlocked()
isDelegatedAgent() and delegationAllowsOperation('READ')
  • The full list of usable expressions is in Authorization Overview > What a condition can use. The meaning of the #ai decision expressions and the agent expressions is in AI Security Expressions.
  • Expressions can be called without #ai. (isAllowed() = #ai.isAllowed()). Agent expressions are usually written without the prefix.
  • An agent condition like the last line only means something under CONTEXA_OWNED, where the URL step sees the delegation stamp (Enabling).

Agents acting for a person

A delegated agent may never do more than its delegator may. A delegated agent's request that the URL policies allow is evaluated against the policies once more as the delegator, and refused before any Contexa decision when the delegator may not make it or is unknown. The result is recorded in the decision event as delegatorAuthority.

ResultMeaningRequest
CARRIEDThe request authenticated as the delegator (a delegator token from token exchange); its own evaluation was the delegator'sUnchanged
PERMITTEDThe delegator may make it tooUnchanged
DENIEDThe delegator may not make itDenied
UNKNOWNThe delegator is unknown (no account, disabled, locked, or the lookup failed)Denied
UNAVAILABLEThere is nowhere to read the delegator from, so nothing was checkedUnchanged
  • The delegator's authority is read from your UserDetailsService. A disabled or locked account delegates nothing. To read it from elsewhere (a directory, ...), declare a DelegatorAuthoritySource bean.
  • When the enforcement mode is not ENFORCE (SHADOW, OBSERVE, DISABLED), nothing is refused; it is only recorded.
  • A person's requests and an autonomous agent's requests are not re-evaluated.
  • URL policies are re-evaluated in the Contexa chain (CONTEXA_OWNED); method policies under both ownerships (Agent security).

Changing and checking it took effect

  • Startup: the mapping list is first built when the application context is ready (ContextRefreshedEvent).
  • Saving a policy: saving in Policy Center, the PolicyService create, update, delete, approve, reject and rollback operations, and the business rule path all clear the policy caches (URL and method) and rebuild the mapping list. There is no public REST API to call for this.
  • Saving system settings: changing the combining algorithm or the default decisions applies them to this instance at once and rebuilds the list.
  • Several instances: in distributed mode (contexa.infrastructure.mode: distributed) with Redisson present, PolicyReloadBroadcaster notifies the other instances on the Redis topic contexa:policy:reload-signal; each receiving instance re-reads the stored system settings and rebuilds its list. In standalone mode only that instance changes.
  • Preview: the Policy Center simulator uses the same policy selection, order and address matching as enforcement.

SettingDefaultMeaningWhen to change
contexa.policy.no-matching-url-policy-decisionAUTHENTICATEDDecision when no URL policy matches (PERMIT, DENY or AUTHENTICATED)DENY to run deny-by-default, blocking addresses without a policy; PERMIT to keep them open to everyone

When the system settings row created by the default seed exists, its values replace the combining algorithm and the decision for methods at startup (initially FIRST_APPLICABLE and PERMIT), and the decision for URLs once an operator has saved one. The seed row holds none, so until then contexa.policy.no-matching-url-policy-decision applies. An installation made by an earlier version holds PERMIT for URLs in its row and keeps it, because an upgrade changes no stored decision. In operation, change them in the admin screen IAM > System Settings (/contexa/admin/system-settings). The admin screen's own settings (contexa.iam.admin.*) are in Admin Console, and all authorization settings in Authorization settings.
