Policy Management

This page shows how to create URL and method access policies in the admin console's Policy Center, how to approve drafts written by AI, and how to check what a saved policy decides for a request. Policies are stored in the Contexa database and are reloaded the moment you save them, so they apply from the next request.

At a glance

A policy has four parts: where (targets), under which condition (conditions), allow or deny (effect), and which policy is looked at first (priority). For example, "for /api/v1/invoices/**, if the user has ROLE_FINANCE, allow, priority 100" is one policy.

URL policies are evaluated only when the request passes the dynamic authorization manager. With @EnableAISecurity(mode = SecurityMode.FULL), the security chain Contexa builds sends every request to CustomDynamicAuthorizationManager. In the default HOST_OWNED mode Contexa builds no security chain, so the application's own chain has to call it, for example .anyRequest().access(customDynamicAuthorizationManager) (Preparation). @Protectable method policies are evaluated in both modes, whenever the method is called.

URL targets are matched with Spring path patterns (/api/**, /api/v1/invoices/{id}). A target without an HTTP method, or with ANY or ALL, matches every method; choosing ALL on screen stores no method. Path variables can be used in conditions, for example #id.

A method target identifier looks like package.Class.method(SimpleParameterTypes), for example com.example.docs.DocumentService.getDocument(Long). It is the same identifier the Resource Scanner produces.

How conditions are combined

When a policy has several conditions, Contexa joins them into one expression. URL policies and method policies join them differently.

Condition 1: hasAuthority('ROLE_ADMIN')
Condition 2: #ai.isAllowed()

URL policy    → (hasAuthority('ROLE_ADMIN')) or (#ai.isAllowed())
Method policy → (hasAuthority('ROLE_ADMIN')) and (#ai.isAllowed())
The Manual Mode screen describes this differently from what the code does. The screen says "each rule combined with OR, AND within a rule". In fact, regardless of rules, all conditions of a URL policy are joined with OR and all conditions of a method policy with AND. If a URL policy needs several conditions to hold together, write them in one condition joined with and.

Effect, priority and combining

The policies whose targets match the request are evaluated in ascending priority. For method policies the targetOrder of the target bound to that method comes first, then priority, then policy ID. The effect turns the condition result into a decision:

EffectCondition trueCondition false
ALLOWAllowDeny
DENYDenyNot applicable (this policy gives no result)

The default combining algorithm FIRST_APPLICABLE takes the first result that is not "not applicable". So an ALLOW policy evaluated first decides even when its condition is false: it denies. When no policy matches, or every matching one is not applicable, the "decision when no policy applies" (default PERMIT) is used. See Decision settings to change it.

Example: to stop users with a BLOCK decision and decide everyone else by role, write both in one condition: hasAuthority('ROLE_FINANCE') and !#ai.isBlocked(). Putting a separate DENY policy and ALLOW policy on the same target fails the conflict check below and is not saved.

Policies with opposite effects are not saved when their targets overlap. On save, Contexa looks for active policies with the opposite effect whose targets overlap. URL targets with the same path and HTTP method are CRITICAL; a pattern that contains the other, or two wildcard patterns that share at least their first two segments, are HIGH; both block the save. The same path with ANY on one side only is MEDIUM and is saved. Different HTTP methods (GET and DELETE) do not overlap. Method targets with the same identifier are CRITICAL. So a broad DENY policy such as /** cannot be used to build a "default deny". Set default deny with the "decision when no policy applies" in Decision settings.

Three ways to create a policy

Open "Policy → Policy Center" (/contexa/admin/policy-center) in the admin console and go to the "Policy Creation" tab. It holds the resource list and the three authoring modes. The resource list is filled by the Resource Scanner.

Quick Mode

Choosing two roles and the CRUD permission READ produces this condition:

(hasAuthority('ROLE_ADMIN') or hasAuthority('ROLE_FINANCE')) and (hasAuthority('READ'))
  • Roles are joined with or, CRUD permissions with or, your own permissions with or, and the groups with and.
  • The permission created automatically when a resource is defined (URL_… · METHOD_…) only sets the policy target; it is not part of the condition.
  • The target is the chosen resource's path with that resource's single HTTP method. A target entered with "Configure Resource Permissions" is a MANUAL target and lets you pick the HTTP method (ANY when none is given).
  • Only roles can be chosen as subjects, not groups. Quick Mode creates no permissions and attaches no permissions to roles. Giving users and groups roles and CRUD permissions is done in the Access Center.
  • If an automatic policy of a chosen role already exists (AUTO_POLICY_FOR_<role name>, Automatic role sync), the policy is still created and a warning is returned with it.
  • Run the checks before creating with POST /contexa/admin/policy-center/api/validate-quick.

Manual Mode

  1. Basics: policy name (unique), description, effect, priority (lower is evaluated first)
  2. Targets: type (URL · METHOD), identifier (for example /api/v1/invoices/** or a method identifier), HTTP method. You can add several targets.
  3. Rules: a rule description
  4. Conditions: a SpEL expression and a phase ("Pre-Authorize" · "Post-Authorize")
  5. Save Policy: saved with POST /contexa/admin/policy-center/create-policy, then the Policy List tab opens.

Manual Mode has no condition-template picker and no recommendation step; you write the conditions (Writing conditions). Before saving, POST /contexa/admin/policy-center/api/validate shows the expression check and conflicts.

AI Mode

  1. Describe the policy in words (for example "the finance team can read the invoice list"). Coming from a resource through the "AI Policy Wizard" puts that resource in front of your text.
  2. Contexa sends the model the roles, permissions and condition templates you can use, a summary of existing policies, the role hierarchy, and 5 similar policies found in the vector store.
  3. The model returns a draft: policy name, effect, role IDs, permission IDs, CRUD permissions, condition templates with values, #ai decision conditions, custom SpEL, tables that map IDs to names, and its reasoning. The screen receives it through POST /contexa/admin/api/ai/policies/generate/stream (SSE); POST /contexa/admin/api/ai/policies/generate returns it in one response.
  4. The screen checks the draft against the items that exist and shows it as a card. After your edits, saving calls POST /contexa/admin/api/policies/build-from-business-rule and creates a policy with source AI_GENERATED.
  5. The policy is saved as pending (PENDING) and is not evaluated until approved (Approving AI drafts).
AI Mode writes policy drafts. It does not recommend conditions separately or apply them with one click. It needs an AI model connection (Connecting AI models).

Many resources at once

Selecting several resources in the list and choosing Quick Mode creates a permission for each resource (define-batch) and then all policies in one call (POST /contexa/admin/policy-center/api/batch-create).

  • At least one role is required. A resource without a CRUD permission is skipped.
  • Each resource gets the condition (role or …) and (CRUD permission or …), priority 100, and the name <EFFECT>_<ROLES>_<CRUD>_<PATH> (up to 200 characters).
  • Each resource is checked before saving; a blocked one is skipped on its own. The result lists CREATED · SKIPPED · ERROR per resource.
  • The AI Policy Wizard takes one resource only.

Creating from code (business rule API)

You can create a policy over HTTP without the screen. Quick Mode and AI Mode use the same translation.

POST /contexa/admin/api/policies/build-from-business-rule
Content-Type: application/json

{
  "policyName": "INVOICE_READ_FOR_FINANCE",
  "description": "Finance team reads invoices",
  "effect": "ALLOW",
  "roleIds": [4],
  "permissionIds": [15],
  "crudPermissions": ["READ"],
  "aiActionEnabled": true,
  "allowedActions": ["ALLOW"]
}

When a permission in permissionIds is linked to a resource, that resource becomes a target. One of roles, permissions or spelId is required. On success the created policy is returned; on failure a 400 without a body.

All of these are joined with and into one condition. The priority is fixed at 100. A source of AI_GENERATED or AI_EVOLVED makes the policy pending; anything else needs no approval. sourceType: "MANUAL" with manualTargetType · manualTargetIdentifier · manualHttpMethod · manualTargetOrder sets a target directly.

Writing conditions

Conditions are Spring Security expressions (SpEL). Expressions that start with #ai read the AI decision stored for the user (AI security expressions).

GoalConditionWhere it works
Business hours only (9:00 to 18:00)T(java.time.LocalTime).now().isAfter(T(java.time.LocalTime).of(9,0)) and T(java.time.LocalTime).now().isBefore(T(java.time.LocalTime).of(18,0))URL · method
Internal network onlyhasIpAddress('10.0.0.0/8')URL
One role onlyhasAuthority('ROLE_MANAGER')URL · method

In a method policy, hasPermission(target ID, 'target type', 'action') needs a domain permission evaluator for that target type (Permission evaluators). On a method with @Protectable(ownerField = "createdBy"), after the evaluator allows it, the object's createdBy value is compared with the login name as well. ROLE_ADMIN skips that owner comparison.

Expression safety rules

Conditions are expressions stored in the database. Contexa checks them when saving and again when loading, and evaluates them in a restricted environment (sandbox).

  • Not allowed: T(...) type references (only LocalTime · LocalDate · LocalDateTime · DayOfWeek from java.time), constructor calls (new), bean references (@name), assignment, and the methods and properties used for reflection, class loading or process execution (getClass · forName · exec · getRuntime, class · classLoader and others). Expressions only read values and cannot change them.
  • On save: every save path (screen, API, version rollback and others) checks the expression, and a rejected one is not saved. The condition entity is checked once more right before it is written.
  • On load: a stored expression that fails is not dropped; the policy is turned into a deny. A URL policy denies all its target paths, and a method policy is made to yield deny for its effect. Dropping the policy could open the target through the "decision when no policy applies" (allow by default). The error log names the policy ID and the reason.

Condition templates

A condition template is a reusable SpEL fragment with %s slots for values. AI Mode drafts pick a template ID and values to build a condition. The condition list in Policy Center (GET /contexa/admin/policy-center/api/conditions) filters by a keyword in the name or description only.

ClassAssigned whenApproval required
UNIVERSALComplexity score 3 or lessNo
CONTEXT_DEPENDENTComplexity score 4 to 6No
CUSTOM_COMPLEXComplexity score 7 or moreYes

The complexity score is set from 1 to 10 when a template is saved, by counting #, parentheses, and, or, comparison operators, hasPermission, hasRole and similar parts. A template that contains permitAll or denyAll, or only isAuthenticated() without a role or authority check, is marked as requiring approval whatever its score.

Templates are written by the AI model: common templates plus templates for each method resource that has parameters, 10 resources per batch. Nothing is generated when there is no method resource. To generate them while resources are loaded, set contexa.iam.admin.condition-templates.enabled: true (default false). You can also call the API below.

The compatibility check treats UNIVERSAL templates as always compatible. For other templates it checks, in order, whether ABAC conditions can be used on the resource (always for URLs, decided by the parameters for methods), whether the domain fits, and whether the variables the expression uses are available on that resource.

What saving does

The readable description of hasAuthority('ROLE_ADMIN') and isAuthenticated() is ((Has authority(ROLE_ADMIN) and Authenticated user)). Each rule is put in parentheses, and rules are joined with or.

  • Telling other instances goes through a Redis topic when contexa.infrastructure.mode: distributed is set and Redisson is present. In standalone mode only the local instance reloads.
  • Deleting resets to "Unset" every resource of the policy's targets that no other policy uses, deletes the automatically created permissions and the version records, and reloads. The audit record (POLICY_DELETED) is written before the deletion.
  • Editing on the policy detail screen first records the content before the change as a version (UPDATED), then saves through the same checks.
  • When the policy service saves a policy whose conditions name permissions with hasAuthority('…'), it publishes a policy change event (PolicyChangedEvent) with those permission IDs; on delete it publishes one without permission IDs.

Approving AI drafts

A policy written by AI must be approved before it is evaluated. Policies written by people (MANUAL · IMPORTED) need no approval (NOT_REQUIRED) and apply at once.

  1. In Policy Center's "Policy List" tab (/contexa/admin/policy-center?tab=list), filter by approval status. You can also filter by keyword and by active state.
  2. Open the policy (/contexa/admin/policies/{id}) to see its targets, conditions and the AI reasoning. Check the result in advance with the simulator and the impact analysis (Checking the effect).
  3. "Approve" in the list opens the AI validation window (GET /contexa/admin/policy-center/api/{policyId}/ai-validation). The policy can be approved only when no item fails.
  4. Approve with POST /contexa/admin/policies/{id}/approve, reject with POST /contexa/admin/policies/{id}/reject. The person and time are recorded and the policies reload. The list shows the reject button for pending policies only.

The simulator uses the same rules as enforcement: which policies take part, their order, how conditions are joined, the effect and the combining algorithm. Facts that exist only in a live request cannot be simulated, so #ai conditions count as true, and conditions that need the request or method arguments, such as hasIpAddress or an object-level hasPermission, count as false.

Versions and rollback

The policy detail screen (/contexa/admin/policies/{id}) has "Version History", "Compare", "Rollback to this version" and "Impact Analysis". A rollback takes a change reason, restores that version's content, runs the expression and conflict checks again, and records a new version (ROLLBACK).

Automatic role sync

When permissions are attached to a role or changed, Contexa creates or updates that role's automatic policy.

Deleting a role deletes its automatic policy too. The policy service also has a method that creates an automatic policy per permission (synchronizePolicyForPermission), but nothing calls it today.

Decision settings

These decide how several matching policies are combined, and what happens when no policy applies.

SettingDefaultMeaningWhen to change it
contexa.policy.combining-algorithmFIRST_APPLICABLECombining algorithm (table below)When results should be combined by a rule such as "any deny wins" instead of priority

AlgorithmResult
FIRST_APPLICABLEThe first result that is not "not applicable"
DENY_OVERRIDESDeny if any policy denies, otherwise allow if any allows
PERMIT_OVERRIDESAllow if any policy allows, otherwise deny if any denies
DENY_UNLESS_PERMITAllow only if a matching policy allows, otherwise deny (also when all are not applicable). With no matching policy at all, the "decision when no policy applies"
YAML values are overwritten by the system settings at startup. The default seed creates a system_settings row (algorithm FIRST_APPLICABLE, both decisions PERMIT), and Contexa applies that row's values at startup and every time the system settings are saved. So change these three values in the admin console under "IAM → System Settings". Saving applies them to the instance at once, reloads the URL policies, and in distributed mode tells the other instances. YAML values are used only when there is no system_settings row (for example with contexa.iam.seed.enabled: false before anyone saves the system settings). 
contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
  iam:
    seed:
      enabled: false          # the values below apply only when no system_settings row is created
  policy:
    combining-algorithm: DENY_OVERRIDES
    no-matching-url-policy-decision: DENY
    missing-method-policy-decision: PERMIT
