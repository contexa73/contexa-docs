Authorization Overview

Contexa keeps access rules as policies in the database instead of in code, and applies them to URL requests and to @Protectable method calls. This page shows in one place when the two enforcement points are active, how one policy decides allow or deny, and how a changed policy takes effect.

At a glance

A Spring Security rule such as @PreAuthorize("hasRole('ADMIN')") lives in code, so changing it means building and deploying again. Contexa stores rules as policies in the database. When you change a policy in the Policy Center admin screen or through the policy service, it applies right away, with no redeployment.

Attaching policies to requests is still code and configuration, though. URL policies apply only when they are connected to the security filter chain, and method policies apply only to methods that carry @Protectable (When it is active).

Policy conditions are Spring SpEL expressions, not an XML policy language. Besides roles and authorities, a condition can read the AI decision Contexa stored (#ai.isAllowed()) and an agent's delegation facts (What a condition can use).

When it is active: by authentication ownership

Where policies apply depends on whether Contexa owns sign-in (CONTEXA_OWNED) or your application does (HOST_OWNED, the default). @EnableAISecurity(mode = SecurityMode.FULL) defaults to CONTEXA_OWNED, the default SANDBOX to HOST_OWNED, and a value you set in contexa.bridge.ownership wins.

Either way, a method is protected by Contexa policies only when it carries @Protectable. @PreAuthorize is Spring's static rule.

Policies that run

Whatever its source, only a policy that is active and whose approval status is APPROVED or NOT_REQUIRED runs.

  • Policies written by hand (MANUAL, also when the source is left empty) and imported ones (IMPORTED) are stored as NOT_REQUIRED and run at once. The policy AUTO_POLICY_FOR_{role} (priority 500), created when a role's permissions change, is stored the same way.
  • Policies written by AI (AI_GENERATED, AI_EVOLVED) arrive as PENDING and run only after an administrator approves them. Rejecting one (REJECTED) deactivates it.

Decision rules

Each policy's condition is evaluated, and its effect turns the result into that policy's outcome. The condition of a DENY policy is not negated: a true condition is deny, a false one is "not applicable".

EffectCondition trueCondition false
ALLOWAllowDeny
DENYDenyNot applicable (left out of combining)

A policy without conditions always applies: always allow for ALLOW, always deny for DENY. The outcomes of several policies are merged by the combining algorithm. URL and method policies share the same setting.

Combining algorithmResult
FIRST_APPLICABLE (default)The outcome of the first policy, in priority order, that applies
DENY_OVERRIDESDeny if any applicable policy denies, else allow
PERMIT_OVERRIDESAllow if any applicable policy allows, else deny
DENY_UNLESS_PERMITAllow if a policy allowed, else deny

When no policy matches

When no policy matches the request, the default decision is used whatever the algorithm. When policies match but none applies (only DENY policies with a false condition), DENY_UNLESS_PERMIT denies and the other algorithms use the default decision.

SettingDefaultMeaning
contexa.policy.no-matching-url-policy-decisionPERMITDefault decision for URL requests. DENY blocks URLs that have no policy
contexa.policy.missing-method-policy-decisionPERMITDefault decision for @Protectable methods
contexa.policy.combining-algorithmFIRST_APPLICABLECombining algorithm
The default is "no policy, allowed". URLs and methods without a policy are open. To deny by default in production, save both default decisions as DENY in the admin screen IAM > System Settings (/contexa/admin/system-settings). When the system settings row created by the default seed exists, its values (combining algorithm and both default decisions) replace contexa.policy.* from YAML at startup. The seed row starts as FIRST_APPLICABLE, PERMIT, PERMIT.

  • The #ai expressions do not analyse each request anew; they read the latest stored decision of the user (for a delegated agent, of the agent itself). No numeric risk score appears in an expression.
  • A condition cannot read the user or resource attributes of the evaluation context directly. The evaluation context (AuthorizationContext) holds the subject, resource, action and environment and the attributes userRoles and userGroups, none of which is exposed to expressions. The database attribute bean (DatabaseAttributePIP) is registered but never called by the evaluation, so it has no effect on decisions.

Safeguards

  • Expression checks: conditions are checked when saved and when loaded. A condition that does not parse or uses a forbidden construct is refused on save. A stored policy that fails the check on load becomes an always-deny (a URL policy's targets map to deny; a method policy gets a constant that denies for its effect), because dropping the policy could open its target through the default decision (allow).
  • Sandbox: stored conditions are evaluated in a restricted environment. T(...) reaches only LocalTime, LocalDate, LocalDateTime and DayOfWeek of java.time; new and @bean references are not available; methods and properties of reflection, class loading, process and thread types are refused; and properties cannot be written. Expressions such as hasRole, hasPermission and #ai.* keep working.
  • Delegator re-evaluation: a delegated agent's request a policy allows is evaluated again as the delegator, and refused before any Contexa decision when the delegator could not make it (Evaluated again as the delegator).

Changing a policy and checking it took effect

  1. Change: in the admin screen Policy > Policy Center (/contexa/admin/policy-center), pick a resource and create a permission and a policy, or save one from server code through PolicyService (Policy Management). The endpoints and methods to protect are found by the Resource Scanner and shown in Policy Center.
  2. Apply: creating, updating, deleting, approving or rejecting a policy clears the policy cache and rebuilds the URL mappings. In distributed mode (contexa.infrastructure.mode: distributed) with Redisson present, a reload signal goes to the other instances too. Saving the combining algorithm or the default decisions in System Settings also applies at once and sends the same signal.
  3. Preview: the simulator in Policy Center uses the same policy selection, order and address matching as enforcement.
  4. Check: URL authorization results are written to the audit log both when granted (AUTHORIZATION_GRANTED) and when denied (AUTHORIZATION_DENIED). A signed-in user's denial is also kept as a fact of the session, which later decisions see. The admin dashboard is at /contexa/admin/dashboard (Admin Console).

The admin screens serve three jobs: review and define what to protect in the Resources tab of Policy Center, create policies with targets, conditions and effects in its Policy Creation tab, and watch the results in Security > Real-time Monitor and the audit log. The full walk-through is in End-to-End Workflow.

Appendix: component map (XACML terms)

Contexa authorization is split into the five XACML roles. Use this when reading or extending the code.

XACML roleWhat it doesContexa implementation
PEP (enforcement point)Stops the request or call, gets the decision and enforces itURL: CustomDynamicAuthorizationManager (a Spring AuthorizationManager that builds its matcher list from URL policies at startup and on each reload). Method: AuthorizationManagerMethodInterceptor + ProtectableMethodAuthorizationManager
PDP (decision point)Evaluates condition expressions and merges the outcomesPolicyExpressionConverter (tidies URL conditions into SpEL), ExpressionAuthorizationManagerResolver (turns isAuthenticated() and a single authority name into Spring's own managers, everything else into a manager evaluated by the Contexa expression handler), CustomWebSecurityExpressionHandler, CustomMethodSecurityExpressionHandler (their expression roots CustomWebSecurityExpressionRoot and CustomMethodSecurityExpressionRoot extend AbstractAISecurityExpressionRoot), PolicyCombiningEvaluator
PAP (administration point)Stores, approves, versions and analyses policiesPolicyService (create, update, delete, approve, reject, versions, rollback, conflicts, impact, simulation), PolicySynchronizationService (creates and updates policies when a role's permissions change, asynchronously), PolicyBuilderService (templates, visual model, conflicts), BusinessPolicyService (business rule → policy), PolicyEnrichmentService (adds readable descriptions)
PIP (information point)Supplies attributes for evaluationContextHandler builds an AuthorizationContext for each URL request and method call. AttributeInformationPoint and DatabaseAttributePIP (subject, resource, action and environment attribute keys) exist but are not used by the evaluation
PRP (retrieval point)Reads and caches policiesDatabasePolicyRetrievalPoint: keeps the keys policies:url:all (every policy with a URL target; the PEP filters what runs) and policies:method:{identifier} in the Contexa cache

PolicyTranslator takes no part in decisions; it turns a condition into a human-readable description and a list of entitlements. It spells out and, or, not and the comparisons (equals, not equals, greater than, greater than or equal to, less than, less than or equal to), writes permitAll and denyAll as "All access permitted / denied", and describes function calls through five built-in translators (authentication, authority, role, IP address and default).
