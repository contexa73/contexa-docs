Permission Evaluators: hasPermission

What hasPermission(...) in a method policy condition looks at to answer true or false. Covers creating permissions and attaching them to roles, the five built-in domains, the synonyms of action names, and building an evaluator for a new domain.

What hasPermission actually checks

hasPermission(...) is Spring Security's object permission expression. Contexa's CompositePermissionEvaluator (a Spring PermissionEvaluator) picks one domain evaluator and hands it over. The built-in evaluators do not look at the target object or ID; they only check whether one of the signed-in user's permission names contains both the domain word and an action word.

  1. Only the user's PermissionAuthority entries, which come from Contexa permission records, count. Other authorities such as roles (ROLE_...) are ignored.
  2. That permission's target type must be METHOD.
  3. It is true when the permission name (upper case) contains the domain word (for example USER) and one of the action's synonyms (below) as substrings.
  4. The target object or ID takes no part in the decision. The only per-object check is the owner check of @Protectable(ownerField) (With the owner check).
Permission the user holdsExpressionResult
METHOD_USERSERVICE_GETUSER (target type METHOD)hasPermission(#id, 'USER', 'READ')True: it contains USER and GET (a READ synonym)
METHOD_REPORTSERVICE_EXPORTREPORT (METHOD)SameFalse: no USER
USER_READ (target type URL)SameFalse: the target type is not METHOD
Under HOST_OWNED it is usually false. PermissionAuthority entries are put into the sign-in by Contexa's user store when Contexa owns sign-in (CONTEXA_OWNED). Under the default HOST_OWNED, where your application owns sign-in, your sign-in carries none, so the built-in evaluators answer false. To decide by your application's own authorities, change the decision rule in a custom evaluator.

Preparation: create permissions and attach them to roles

  1. Create permissions in the admin screen IAM > Permission Management (/contexa/admin/permissions). The fields are name, description, target type (URL, METHOD) and action type (READ, WRITE, EXECUTE, DELETE, ALL).
  2. The evaluators look at the name, not the action type field. Put the domain and action words in the name (by convention DOMAIN_ACTION, for example USER_READ) and set the target type to METHOD.
  3. Permissions created from resources in Policy Center get automatic names: METHOD_{CLASS}_{METHOD} for METHOD resources and URL_{address} for URL resources (characters other than letters and digits become _), all upper case. Automatic names can match through the substring rule too: METHOD_ORDERSERVICE_UPDATEORDER matches ORDER and UPDATE.
  4. Attach permissions to a role in IAM > Role Management (/contexa/admin/roles) and give the role to users or groups. At sign-in the role's permissions are carried as PermissionAuthority, whose value is the permission name in upper case.

Where it is used

WhereWorks?
Conditions of @Protectable method policiesYes (under both authentication ownerships)
@PreAuthorize and other Spring method securityOnly under CONTEXA_OWNED (Contexa registers the handler that uses this evaluator)
Conditions of URL policiesNo. It is removed at load time. An ALLOW policy that had only hasPermission always denies; a DENY policy always applies

A check over the whole role is hasRole(...), and protecting each method with database policies is @Protectable; hasPermission is for checking permission names inside such a policy's condition. A #name in a condition is a method parameter name. #targetId has a value only when a parameter has that name. Method policies join conditions with and, so it can sit alongside other conditions.

Target types ignore case. The five built-in evaluators differ only in domain and repository bean name; their decision rule is the same.

hasPermission(#id, 'USER', 'READ')
hasPermission(#id, 'ROLE', 'EDIT')
hasPermission(#groupId, 'GROUP', 'DELETE')
hasPermission(null, 'USER_READ')
hasPermission(#userId, 'USER', 'UPDATE') and T(java.time.LocalTime).now().getHour() < 18
  • Domains such as ORDER, DOCUMENT, REPORT or PAYMENT have no evaluator. To use them, build one; without it a three-argument expression ends in an exception.
  • Write time conditions with T(java.time.LocalTime) and the like. There is no #time variable.

Action names and synonyms

ActionWords treated as the same
ReadGET, FIND, READ, FETCH, VIEW, RETRIEVE, LIST, SEARCH
CreateCREATE, SAVE, ADD, INSERT, REGISTER, POST
UpdateUPDATE, EDIT, MODIFY, CHANGE, PATCH, PUT
DeleteDELETE, REMOVE, DESTROY, DROP, ERASE, PURGE, CLEAR, TRUNCATE
  • When the action in the expression belongs to a group, any word of that group in the permission name is enough. An action outside the groups (for example EXPORT) is looked for as that word alone.
  • With two arguments, the action is what remains after removing the domain prefix from the permission string. hasPermission(#user, 'USER_FETCH') is FETCH, in the read group, so it is true when a METHOD permission's name contains USER and GET, READ or another read word.

How the evaluator is chosen

  • The evaluators are collected at startup and checked longest domain name first. So ROLE_HIERARCHY_READ goes to the ROLE_HIERARCHY evaluator, not the ROLE one. USER and ROLE have the same length, but their prefixes never overlap, so their order does not matter.
  • Without sign-in it is always false.
  • DomainPermissionEvaluator is the evaluator interface; the decision rule above lives in the base class AbstractDomainPermissionEvaluator.

With the owner check

In a method policy, when hasPermission is true and the method carries @Protectable(ownerField = "..."), the target's owner is checked next. With two arguments the field is read from the object passed; with three, from the entity the chosen evaluator reads through findById on its repository bean. It is compared with the signed-in user's name. The rules are in @Protectable > Owner check.

Custom domain evaluators

To use a new domain (for example DOCUMENT), register a bean that extends AbstractDomainPermissionEvaluator. Implementing only the DomainPermissionEvaluator interface fails at startup with ClassCastException, because the collector casts every evaluator to the base class.

import io.contexa.contexaiam.security.xacml.pdp.evaluation.method.AbstractDomainPermissionEvaluator;
import org.springframework.context.ApplicationContext;
import org.springframework.stereotype.Component;

@Component
public class DocumentPermissionEvaluator extends AbstractDomainPermissionEvaluator {

    private final ApplicationContext applicationContext;

    public DocumentPermissionEvaluator(ApplicationContext applicationContext) {
        this.applicationContext = applicationContext;
    }

    @Override
    protected String domain() {
        return "DOCUMENT";
    }

    @Override
    protected String repositoryBeanName() {
        return "documentRepository";
    }

    @Override
    protected ApplicationContext getApplicationContext() {
        return applicationContext;
    }
}
  • Write domain() in upper case. The permission string is upper-cased before comparison, but the domain name is not.
  • repositoryBeanName() is the repository bean used to read the entity through findById for the three-argument owner check (a Spring Data repository works). Without the bean the owner check denies.
  • Once it is a bean, auto-configuration collects every evaluator and sorts them by length; nothing else is needed. If you declare your own CompositePermissionEvaluator bean, the auto-configured one backs off.
  • To change the decision rule, override checkPermission(Authentication, Object) (protected), for example to decide by your application's own authorities under HOST_OWNED.
  • You can now write hasPermission(#docId, 'DOCUMENT', 'READ') and hasPermission(#document, 'DOCUMENT_UPDATE').
