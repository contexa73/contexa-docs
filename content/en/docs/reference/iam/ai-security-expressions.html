AI Security Expressions: Decision and Agent Conditions

Expressions that read, in a policy condition, the latest Zero Trust decision Contexa stored (#ai.isAllowed() and others) and the facts of agents and delegation (isDelegatedAgent() and others). Where you can use them depends on authentication ownership.

#ai cannot be used in the application's @PreAuthorize. Contexa does not turn Spring method security on for the whole application and does not register the expression handler that carries #ai in it. Even under CONTEXA_OWNED, the application's @PreAuthorize and @PostAuthorize are evaluated by Spring Security's default handler (Contexa's handler is used only for Contexa's own classes). Use #ai in the conditions of Contexa policies: @Protectable method policies and URL policies (under HOST_OWNED, URL policies connected to your chain).

Ownership follows the mode of @EnableAISecurity (FULL for CONTEXA_OWNED, the default SANDBOX for HOST_OWNED); a value set in contexa.bridge.ownership wins. The agent request gate is described in Stop, Confirm, Limit.

When a decision is made and when it is read

An #ai expression does not run an AI analysis on the spot. It reads the latest decision of that user, made by analysing earlier requests after their responses and stored.

  • Decision key: the user ID. A delegated agent acting for a person reads the decision under its own key (<user>::agent::<agent>), and reads BLOCK when its delegator is blocked (Decisions under the agent's own key).
  • No decision: not analysed yet, past its lifetime, or no authentication: it reads as PENDING_ANALYSIS.
  • ALLOW is bound to its context: an ALLOW reads as ALLOW only in the session, client IP and User-Agent (the context fingerprint) it was made for, and as pending analysis elsewhere. BLOCK, CHALLENGE and ESCALATE apply to every request of the user.
  • Even for sync methods, a method policy's condition is evaluated before the call's own decision, so it reads the decision stored until then (The order in which one call is handled).
  • No numeric risk score is exposed to expressions; only the five decisions are read.

The five decisions

DecisionMeaningLifetimeExpression that is true
ALLOWAllowed15 minutesisAllowed()
CHALLENGEStep-up authentication (MFA) needed30 minutesneedsChallenge()
ESCALATEHeld for review (analysis not finished)5 minutes; while unresolved it keeps reading as ESCALATEneedsEscalation()
BLOCKBlockedUntil releasedisBlocked()
PENDING_ANALYSISNo decision (pending analysis)-isPendingAnalysis()
  • The request-time filters (both ownership modes) promote an unresolved ESCALATE to BLOCK (Request-time enforcement).
  • The step-up of CHALLENGE is MFA: Contexa's MFA under CONTEXA_OWNED, Contexa's verification-only step-up under HOST_OWNED (passkey, one-time code by mail, or the application's own re-authentication). There is no other check such as a CAPTCHA.
  • Expressions that take a decision name as text (hasAction and others) ignore case and also accept the shorthands A, B, C and E. Unknown text is read as ESCALATE, so watch for typos.

Agent expressions

Apart from the model's decision, URL and method policies can check a delegation deterministically. These expressions read the request's delegation stamp (made by the authentication bridge from the token, session, ...), not the delegation record.

ExpressionMeaning
isAgent() / isDelegatedAgent() / isAutonomousAgent()Whether an agent makes the request / a delegated agent / an autonomous agent
agentId / isAgentIn('a', 'b')The requesting agent's ID / whether it is one of these
delegatorIdThe delegator (for a delegated agent)
delegationChainDepth / delegationChainDepthAtMost(n)The delegation chain depth (0 for a person or an autonomous agent, 1 for a direct delegation) / whether it is at most n
delegationAllowsOperation('READ')Whether the delegation allows the operation (case ignored)
delegationAllowsResource('/api/reports/1')Whether the delegation allows the target (a listed item ending in * covers every target starting with what precedes it)
delegationRequiresApproval()Whether the delegation requires the delegator's approval
agentRequestConfirmed()Whether the accountable person confirmed this very request (true only for an agent's request). The confirmation mark is attached by the agent request gate, which runs in both ownership modes
agentCallsInLastMinuteAtMost(n)Whether this delegation made at most n requests in the last minute, this one included; true for a person and when nothing counted them
 
isDelegatedAgent() and delegationAllowsOperation('READ') and delegationChainDepthAtMost(1)
!delegationRequiresApproval() or agentRequestConfirmed()
  • A person's request has no delegation stamp, so agent expressions are false for it. delegationChainDepthAtMost(n) (n of 0 or more) and agentCallsInLastMinuteAtMost(n) are the exceptions: they are true for a person.
  • The second line is a confirmation-required policy: when the delegation requires approval, only the very request the accountable person confirmed passes. Make it an ALLOW policy ordered before the other allowing policies (lower priority number). A policy with the opposite effect on the same target is refused on save as a conflict. The flow is in Confirmation by the accountable person.
  • The same descriptions appear in Delegation and Objective Contracts and Stop, Confirm, Limit.

Where the decision is read from

Where the expression isRead order
URL policyReads the decision store directly on every evaluation
Method policy① The decision the Contexa chain left on the request when it loaded the sign-in (CONTEXA_OWNED; skipped for delegated agents) → ② a 5-second local cache (up to 10,000 entries, keyed by decision key + context fingerprint) → ③ the decision store
  • Because of the local cache, a method policy's expression can read the previous decision for up to 5 seconds after it changes. "No decision" is not cached.
  • The decision store is memory in standalone mode (contexa.infrastructure.mode: standalone, the default) and Redis in distributed mode (distributed). The in-memory store keeps up to contexa.security.zerotrust.standalone.max-decision-users users (0 derives it from the heap size); past that it drops the users decided longest ago, never a user in a restricted state.

hasActionIn('ALLOW', 'CHALLENGE') does not mean "allowed once the step-up is done". It is true while the decision is CHALLENGE, so a request that never did the step-up passes. To require the step-up, leave CHALLENGE out of the list.

With permissions and ownership

  • Contexa's hasPermission(...) evaluator is used in method policy conditions. The application's @PreAuthorize has no Contexa handler. URL policies remove it.
  • The built-in domains are USER, ROLE, ROLE_HIERARCHY, GROUP and PERMISSION. Other domains such as ORDER or DOCUMENT need a custom evaluator; without one, a three-argument hasPermission ends in an exception (Permission Evaluators).
  • hasIpAddress and httpMethod work only in URL policies; the ownerField owner check only in method policies (Owner check).
hasPermission(#userId, 'USER', 'READ') and #ai.isAllowed()
hasPermission(#groupId, 'GROUP', 'UPDATE') and !#ai.isBlocked()
// #ai cannot be used in the application's @PreAuthorize. Use it in the condition of a Contexa method policy on a @Protectable method.
// Policy condition (entered in the policy center): !#ai.isBlocked() and hasRole('ADMIN')
@Protectable
public void rotateSigningKeys() {
    ...
}

In the admin screens

  • Write expressions directly in conditions in the Policy Creation tab of Policy Center (/contexa/admin/policy-center) (Policy Management).
  • On the business rule path (POST /contexa/admin/api/policies/build-from-business-rule), choosing to use the AI decision (aiActionEnabled) and the decisions to allow (allowedActions) builds an expression such as #ai.isAllowed() for one decision or #ai.hasActionIn(...) for several, joined with and inside one condition together with roles, permissions and SpEL written by hand. There are no named AI condition templates.
  • A policy written by AI arrives as PENDING and runs only once approved. A policy written by hand is NOT_REQUIRED and runs at once.
  • Record-only operation (SHADOW) is not set per policy; it is the global enforcement mode (contexa.security.zerotrust.mode, or the AI decision mode in System Settings).
  • Check results with the approval status in the policy list, the simulator and the audit log.

Safeguards

Conditions stored in the database are checked when saved and loaded, and evaluated in a sandbox. T(...) reaches only LocalTime, LocalDate, LocalDateTime and DayOfWeek; new, @bean and reflection are not available. Decision and agent expressions keep working. The full rules are in Authorization Overview > Safeguards.
