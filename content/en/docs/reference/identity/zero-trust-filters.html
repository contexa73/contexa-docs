Request-Time Enforcement

How a stored decision (allow, step-up authentication, block, held for review, pending analysis) applies to the user's next request. On this one page you see, for each decision, the response the user gets, how authorities change, how it is released, where the filters run in the security chain, and how agent requests differ.

These filters work in both ownership modes, with the same answers. When Contexa owns login (CONTEXA_OWNED) their servlet registration stays off and they go into the security chains Contexa builds. With the default HOST_OWNED Contexa builds no chain; the same filters run as servlet filters right after the application's Spring Security chain (Under HOST_OWNED), so the application's chain sets the user and applies its own rules first, and every path is enforced. A CHALLENGE then goes to Contexa's step-up instead of Contexa's MFA (The step-up under HOST_OWNED). Stored BLOCK, CHALLENGE and ESCALATE are also refused in front of @Protectable methods (Protected methods). How to keep your application's existing login is in Connecting Your Existing Login.

At a glance

Decisions are made asynchronously after the response has left and written to the decision store (Decision Engine); they apply on that user's next request. The filters let requests without a login pass untouched.

DecisionStored forWhere it applies
ALLOW15 minutesOnly in the session, IP and browser it was decided for (context hash). Elsewhere it reads as PENDING_ANALYSIS
CHALLENGE1800 secondsEvery session of that user
ESCALATE300 secondsEvery session of that user
BLOCKUntil releasedEvery session of that user
PENDING_ANALYSISNo limitRead when no decision is stored or its time has run out

The context hash is made from the session ID, the client IP and the User-Agent. A less strict decision cannot override a restriction already in force (BLOCK, CHALLENGE, ESCALATE).

The step-up under HOST_OWNED

When the application owns login, Contexa starts no MFA flow of its own and changes nothing of the application's login, session or cookies. A CHALLENGE sends the user, through the challenge notice page, to a verification-only step-up at /contexa/step-up. The step-up is reached through the application's own chain, so the user is the one the application signed in, and the application's CSRF protection applies to its posts. When the user passes, the result is recorded the same way as a completed Contexa MFA: the CHALLENGE becomes ALLOW.

  • What the page hands out (passkey options) is kept under the user's decision key, not in the session: in memory, or in Redis with contexa.infrastructure.mode: distributed.

PENDING_ANALYSIS: watching the response

With an allow or no decision yet the request passes, but its response is wrapped and watched. If a BLOCK signal arrives for this user while the response is going out, the response is cut. If nothing has been sent yet, what was written is discarded and 403 is sent with the marker __CONTEXA_RESPONSE_BLOCKED__:BLOCK; if sending has started, the marker is written and the response ends. The JavaScript SDK moves to the blocked page when it sees this marker (Extra verification after login).

How authorities change

  • Session flows: Contexa's session login repository (AISessionSecurityContextRepository) applies the decision the first time the request reads the login. When the authorities change, the login object is replaced with a ZeroTrustAuthenticationToken holding the decision (trust score, threat score, decision). An invalidated session is ended and the request goes on as not logged in.
  • Token flows: AIOAuth2ZeroTrustFilter, right after token validation (BearerTokenAuthenticationFilter), applies the decision to JWT requests and puts in a new JwtAuthenticationToken with the adjusted authorities. An invalidated token gets 401.
  • The decision used to adjust authorities is cached for 5 seconds. The two filters read the store directly without a cache, so blocking the response on a new BLOCK is not delayed.
  • A decision never adds authorities. ALLOW keeps the original ones; CHALLENGE, BLOCK and ESCALATE leave only the decision's marker authority. So the restriction also applies to authority checks such as URL policies and @PreAuthorize.
  • Under HOST_OWNED authorities are not changed: Contexa does not touch the application's SecurityContext, and the two filters answer from the stored decision.

Where the filters run

Under CONTEXA_OWNED the three filters (MFA-in-progress access control, access control, challenge) have their servlet registration turned off with FilterRegistrationBean, and Contexa's configurers put them into the chain of each flow. Their positions are not fixed numbers but positions relative to Spring filters. The configurer order values 44, 45 and 50 are the turns in which the configurers are applied, not filter positions.

Under HOST_OWNED

Contexa builds no chain, so the filters are registered as servlet filters ordered after the Spring Security filter chain (spring.security.filter.order, -100 by default). The application's chain runs first; the MFA-in-progress filter and the authority adjustment are not used.

The filters see the user only when the application sets it in a Spring Security filter. If it sets the user later (in an MVC interceptor or a controller), those requests are enforced only at @Protectable methods, and Contexa logs once [Contexa] HOST_OWNED: the application sets the signed-in user after Spring Security's filters ... (WARN).

The two filters follow the enforcement mode. New decisions are stored and applied only while contexa.security.zerotrust.enabled is on and contexa.security.zerotrust.mode is ENFORCE, and the access control and challenge filters stop requests only then, in both ownership modes. Under SHADOW, OBSERVE, DISABLED or with enabled: false nothing is stopped; BLOCK, CHALLENGE and ESCALATE stored earlier stay and apply again when the mode returns to ENFORCE, unless they have expired or been released. In that time the agent request gate records and lets agents through. With enabled: false the authority adjustment when the login is read and the session tracking stop as well.

MFA-in-progress access control

A session that finished only the primary login and not MFA passes only the requests needed to go on with or leave MFA: login and logout, the pages and factor addresses of every MFA flow, the MFA configuration API, Contexa's static files, the Zero Trust notice pages and the error path. Any other request moves to the MFA page in progress (or the login page when the MFA session is gone) for a browser, and gets 401 MFA_REQUIRED for an API. Passkey registration requests are refused too, so a passkey cannot be registered with the primary login alone to skip the second factor (the API gets 401 PASSKEY_REGISTRATION_REQUIRES_MFA).

Releasing a block

A BLOCK is released only by an administrator's approval. From the blocked page the user can verify themselves (MFA) and ask for the release.

  • Attempt limit: the release MFA start API and the access control filter look at contexa.security.zerotrust.max-block-mfa-attempts (default 2). The handler that counts failed release MFAs, however, uses a constant 2 instead of this setting. One failed MFA session counts once; at two the pending mark is removed and only block responses follow. Each failure returns 403 BLOCK_MFA_FAILED with the blocked page address, and the failure count is kept for 24 hours.
  • The session stays. When blocking, the filter only writes the response; it does not invalidate the session or log the user out.
  • Under HOST_OWNED the release MFA runs on Contexa's step-up. For a BLOCK an administrator lets the user release by MFA, the access control filter sends a browser to /contexa/step-up?purpose=block and answers an API with 401 BLOCK_MFA_REQUIRED and mfaUrl; passing it sets the same verified mark as the release MFA above. An administrator's approval still lifts the BLOCK.
  • An agent's BLOCK is 403 AGENT_BLOCKED and is not released by MFA. For releasing it see Stopping and releasing.

When held for review becomes a block

The first time ESCALATE stops a request, a retry mark (5 minutes) is set once. On the next request after both the decision's lifetime (300 seconds) and the retry mark have passed, the access control filter stores BLOCK, leaves the block mark and answers with a block. For a person it records the block; for an agent it stops that agent. MFA success does not release ESCALATE.

Agent requests

A request is an agent request when the authentication bridge put a delegation stamp naming an agent on it. An agent cannot answer a person's MFA, so the challenge filter sends it to the agent request gate instead. The gate checks, in order, the call limit → an ended delegation → the accountable person's confirmation for CHALLENGE → a narrowed scope. Responses and handling are in Stop, Confirm, Limit.

  • Without the gate (no agent confirmation service bean), CHALLENGE is answered with 403 AGENT_CONFIRMATION_REQUIRED.
  • The decision of an agent working for a person is read under the key <user>::agent::<agent>, and the agent also receives the delegating person's BLOCK.
  • An agent's BLOCK is 403 AGENT_BLOCKED.
  • The gate runs in both ownership modes. Under HOST_OWNED the challenge filter runs after the authentication bridge (Under HOST_OWNED), so the gate sees the delegation stamp. The URL authorization step inside the application's chain runs before the bridge, so it has no delegation stamp yet.
