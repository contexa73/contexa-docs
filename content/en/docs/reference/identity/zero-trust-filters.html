Request-Time Enforcement

A decision CONTEXA has made takes effect on that user's next request. This page explains, for each decision (allow, step-up authentication, held for review, block, pending analysis), what the user sees, how the response differs for a browser and an API client, and how the user's authorities change and are released. It also covers what differs when your application owns login and when CONTEXA does, where the filters run, how AI agent requests are handled, and the settings.

The user gets the same responses whoever owns login. When your application's Spring Security owns login, the mode is HOST_OWNED, the default. When CONTEXA owns login, the mode is CONTEXA_OWNED. In both modes the same filters give the same responses. Two things differ. First, where the filters run. Under CONTEXA_OWNED they sit inside the security chains CONTEXA builds. Under HOST_OWNED CONTEXA builds no chain, and the filters run as servlet filters right after your application's Spring Security chain (Filter position when the application owns login). Your chain sets the user and applies your rules first, so the filters apply decisions to every path of your application (the skipped addresses are in Addresses the filters skip). Second, where a step-up authentication (CHALLENGE) is handled. Under HOST_OWNED it goes to CONTEXA's step-up page instead of CONTEXA's MFA. That page does not sign anyone in; it only asks the user to verify once more (Step-up when the application owns login). In both modes, a stored block, step-up or hold for review also refuses requests in front of @Protectable methods (Protected methods). How to keep your application's existing login is in Connecting Your Existing Login.
Terms on this page. A decision is what CONTEXA decides about one request: ALLOW, CHALLENGE (step-up authentication), ESCALATE (held for review), BLOCK or PENDING_ANALYSIS. The decision store is where the latest decision of each user is kept. Request-time enforcement applies a stored decision on that user's next request, and the filters that do it are the challenge filter (step-up), the access control filter (block and hold for review) and the MFA-pending access control filter. Step-up authentication checks a user who is already logged in once more, and MFA is a login that adds checks after the password. The authentication stamp is the record in which the authentication bridge keeps the result of your application's login. The agent request gate is the filter that applies to the requests of AI agents only. Terms such as flow, chain and state are in Login Methods.

Overview

A decision is usually made after the response has left and is written to the decision store (Decision Engine). It applies from that user's next request on. CONTEXA does not hold a request while it waits for a decision. The filters let requests without a login pass untouched.

The table shows how long each decision lasts and which requests it applies to.

DecisionStored forWhere it applies
ALLOW15 minutes (set with contexa.security.zerotrust.allow-validity)Only requests from the session, IP and browser it was decided for (the context hash). If any of the three differs, the request reads as PENDING_ANALYSIS

ESCALATE300 secondsEvery session of that user
BLOCKUntil releasedEvery session of that user
PENDING_ANALYSISNo limitRead when no decision is stored or its time has run out

The context hash is made from the session ID, the client IP and the User-Agent. An ALLOW holds only in that environment, so a request from a changed environment is analyzed again. A block, step-up or hold for review covers the whole user whatever the environment. While one of these restrictions is in force, a newer and less strict decision cannot override it.

Response, authorities and release per decision

A request stopped by a restriction gets a different response depending on whether a browser or an API client sent it. A browser is sent to a notice page. An API or AJAX request receives a JSON error. A request counts as API or AJAX when it carries an Accept: application/json header or an X-Requested-With: XMLHttpRequest header, or when its path starts with /api/. Every JSON error body has timestamp, status, error, message and path, plus the fields in the table below.

With the default settings, the held-for-review (ESCALATE) response does not occur. With the default contexa.security.tiered.layer2.allow-escalate-final-action: false, CONTEXA does not store an ESCALATE that Layer 2 analysis picks. It stores the action of contexa.security.tiered.layer2.escalate-fallback-action instead (default CHALLENGE). Only an installation that sets the option to true stores ESCALATE decisions, and the behavior in the table above happens only there (Settings).

The time to wait for the lock, the lease time of the lock and the retry seconds of the 503 are settings (Settings). Step-up when the application owns login (HOST_OWNED)

HOST_OWNED is the mode in which your application owns login, sessions and cookies. In this mode, when the decision is CHALLENGE (step-up authentication required), CONTEXA asks the person making the request to prove once more that they are the user your application signed in. CONTEXA does not sign anyone in. It only verifies, and it leaves your application's login, session and cookies untouched.

  1. A request from the user receives a CHALLENGE decision.
  2. A browser is sent to /contexa/step-up, through a notice page that says step-up authentication is required. An API client receives a 401 response whose body carries the same address in mfaUrl.
  3. The user verifies with one of the methods the page offers (see the table below).
  4. When verification succeeds, the CHALLENGE is lifted and the request is allowed (ALLOW). The result is recorded the same way as a completed CONTEXA MFA.

The page is served inside your application's own Spring Security filter chain. So the person who reaches it is the user your application already signed in, and your application's CSRF protection applies to the POST requests the page sends.

MethodWhen the page offers it
PasskeyA passkey is registered in CONTEXA for the user. Relying party settings are contexa.auth.urls.factors.passkey.*. A user with no passkey can register a first one on the same page (see "Registering a first passkey" below).
One-time code by mailCONTEXA's copy of the user has a real e-mail address (an address in contexa.bridge.sync.synthetic-email-domain is not a real one) and mail is configured (spring.mail.*).
The application's own re-authenticationYour application re-authenticates the user with its own MFA or identity provider. See "The application's own re-authentication" below.

Registering a first passkey. A passkey can lift a CHALLENGE, so it cannot be registered at any moment. No CHALLENGE, BLOCK or ESCALATE decision may be in force for the user, and the session must already have confirmed the user, either with a one-time code or with a sign-in to your application's own MFA within the last 5 minutes (only for an application that has set a re-authentication address). A user who has just lifted a CHALLENGE with a one-time code is offered passkey registration right away.

One-time code by mail. CONTEXA mails at most one code per user every 30 seconds. A request inside that time sends nothing and the answer tells the user to wait, so a session under a CHALLENGE cannot flood the user's mailbox. A code works once: if it is used again, or by several requests at the same time, only the first request passes. The number of wrong entries allowed is contexa.auth.mfa.max-retry-attempts (the same value CONTEXA MFA uses) and is counted per session environment (browser and network address). At the limit, every code requested from that environment is discarded and a new one is needed. Someone who has stolen a cookie can use up their own entries, but the real user keeps using their own code.

The application's own re-authentication. After a CHALLENGE, your application may re-authenticate the user with its own MFA or identity provider. If the authentication stamp (the value the authentication bridge fills with your application's sign-in result) shows a completed MFA with an authentication time later than the CHALLENGE, the challenge filter lifts the CHALLENGE on that request by itself. When you set contexa.bridge.step-up.reauthentication-url to the address where your application re-authenticates, the page shows a link to it. Without that setting, your application's re-authentication is not used as a method.

  • Who is verified: only the authentication bridge's copy of your application's user. An application user therefore never meets a CONTEXA account of the same name.
  • Releasing a block: when a blocked user starts the release MFA from the block screen, they come to this page too (?purpose=block). Passing the MFA does not lift the BLOCK; an administrator must approve the release request (Releasing a block).
  • Agent requests: an agent's request is not verified on this page. Its accountable person confirms it; see Agent requests.
  • Where passkey options are kept: the passkey options the page issues are stored under the user's decision key, not in the session: in memory, or in Redis with contexa.infrastructure.mode: distributed.
  • Page resources: decisions never block the scripts, styles and images of CONTEXA's screens (/contexa/js/, /contexa/css/, /contexa/img/), because a blocked user must still be able to load the block screen and send a release request.
  • Signed-in users only: the pages under /contexa/step-up, the decision screens under /contexa/zero-trust/ and the agent delegation and confirmation pages answer only a signed-in user. An anonymous request receives 401 AUTHENTICATION_REQUIRED, whatever your application's own access rules allow.

Watching the response (PENDING_ANALYSIS)

CONTEXA does not hold a request until a decision arrives. A request with no block or hold for review in force (allowed, or pending analysis) passes. Its response is wrapped and watched while it goes out, because an ALLOW says nothing about the response that follows it: a long streaming response that starts right after an ALLOW must still stop if a block arrives in the middle. If a BLOCK signal arrives for this user while the response is going out, CONTEXA cuts the response.

  • Nothing sent yet: what was written is discarded, and CONTEXA sends 403 with the marker __CONTEXA_RESPONSE_BLOCKED__:BLOCK.
  • Sending has started: the status code can no longer change, so CONTEXA writes the marker and ends the response.

The JavaScript SDK moves the user to the blocked page when it sees this marker (Extra verification after login). A wrapped response carries the header X-Contexa-Monitored: true, which the SDK reads, and the header X-Contexa-Blocked-Redirect, which holds the address of the blocked page. Turn these headers off with contexa.security.zerotrust.monitoring-headers: false.

How authorities change

CONTEXA changes the Spring Security authorities (GrantedAuthority) of the logged-in user to match the decision. So the restriction also applies to authority checks such as URL policies and @PreAuthorize. A decision never gives authorities; it only takes them away. ALLOW keeps the original authorities. CHALLENGE, BLOCK and ESCALATE remove all of them and leave only the decision's marker authority. PENDING_ANALYSIS keeps the original authorities and adds its marker. Where the change happens depends on the kind of login.

  • Session login: CONTEXA's session login repository (AISessionSecurityContextRepository) applies the decision the first time a request reads the login. When the authorities change, it replaces the login object with a ZeroTrustAuthenticationToken that holds the decision (trust score, threat score, decision). An invalidated session is ended, and the request goes on as not logged in.
  • Token login: AIOAuth2ZeroTrustFilter, right after token validation (BearerTokenAuthenticationFilter), applies the decision to JWT requests and puts in a new JwtAuthenticationToken with the adjusted authorities. An invalidated token gets 401.
  • Cache: the decision used to adjust authorities is cached for 5 seconds, and only when it is an ALLOW. A restriction may end or change at any moment, so it is never cached. The challenge filter and the access control filter read the store directly without a cache, so a new BLOCK stops responses without delay.
  • Under HOST_OWNED authorities are not changed. CONTEXA does not touch the application's SecurityContext, and the two filters read the stored decision and answer directly.

Where the filters run

Three filters take part. The challenge filter handles step-up authentication, and the access control filter handles block and hold for review. The MFA-in-progress access control filter restricts sessions that have not finished MFA. Where they run depends on who owns login.

Under CONTEXA_OWNED the three filters (MFA-in-progress access control, access control, challenge) have their servlet registration turned off with FilterRegistrationBean. CONTEXA's configurers put them into the chain of each authentication flow instead. Their positions are not fixed numbers but positions relative to Spring filters. The configurer order values 44, 45 and 50 are the turns in which the configurers are applied, not filter positions. In the table, a session chain keeps the login state in a session cookie, and a token chain authenticates with a bearer token (JWT). The authentication bridge is the filter that reads your application's sign-in result and leaves it as an authentication stamp.

Filter position when the application owns login (HOST_OWNED)

Under HOST_OWNED CONTEXA builds no security chain. It registers the filters as servlet filters instead and orders them right after the Spring Security filter chain (spring.security.filter.order, -100 by default). So your application's chain runs first, sets the user and applies your rules, and the CONTEXA filters run after it. The MFA-in-progress filter and the authority adjustment are not used in this mode.

OrderFilterWhat it does
Chain + 1Authentication bridge (BridgeResolutionFilter)Reads the user your application's chain signed in and makes the authentication stamp
Chain + 2Challenge (ZeroTrustChallengeFilter)Sends a CHALLENGE to CONTEXA's step-up. Sends agent requests to the agent request gate
Chain + 3Access control (ZeroTrustAccessControlFilter)Stops BLOCK and ESCALATE, and watches PENDING_ANALYSIS responses
Chain + 4User path guard (HostOwnedUserPathGuard)CONTEXA's user pages answer only a signed-in user

The filters see the user only when your application sets it in a Spring Security filter. If it sets the user later (in an MVC interceptor or a controller), the filters do not know the user of that request. Decisions then apply to those requests only at @Protectable methods, and CONTEXA logs [Contexa] HOST_OWNED: the application sets the signed-in user after Spring Security's filters ... (WARN) once.

The two filters stop requests only in the operating mode ENFORCE. New decisions are stored and applied only while contexa.security.zerotrust.enabled is on and contexa.security.zerotrust.mode is ENFORCE. The access control and challenge filters also stop requests only then, in both ownership modes. Under SHADOW (observe only), OBSERVE, DISABLED or with enabled: false the filters stop nothing. A BLOCK, CHALLENGE or ESCALATE stored earlier stays and applies again when the mode returns to ENFORCE, unless it has expired or been released. In that time the agent request gate only records an ended delegation or a narrowed scope and lets the agent's request through. With enabled: false the authority adjustment when the login is read and the session tracking stop as well.

MFA-in-progress access control

When a user has finished only the primary login and not MFA, the session passes only the requests needed to go on with MFA or to leave it. These are login and logout, the pages and factor addresses of every MFA flow, the MFA configuration API, CONTEXA's static files, the Zero Trust notice pages and the error path. Every other request is stopped. A browser moves to the MFA page in progress (or to the login page when the MFA session is gone), and an API gets 401 MFA_REQUIRED. Passkey registration requests are stopped too, so a user cannot register a passkey with the primary login alone to skip the second factor. For that request an API gets 401 PASSKEY_REGISTRATION_REQUIRES_MFA.

Releasing a block

A BLOCK is released only by an administrator's approval. From the blocked page the blocked user passes MFA and then asks for the release. Passing MFA does not lift the BLOCK. An administrator reviews the request and approves it.

  • Attempt limit: the API that starts the release MFA and the access control filter look at contexa.security.zerotrust.max-block-mfa-attempts (default 2). The handler that counts failed release MFAs, however, uses a constant 2 instead of this setting. One failed MFA session counts once. At two failures the pending mark is removed and only block responses follow. Each failure returns 403 BLOCK_MFA_FAILED with the blocked page address, and the failure count is kept for 24 hours.
  • The session stays. When blocking, the filter only writes the response. It does not invalidate the session or log the user out.
  • Under HOST_OWNED the release MFA runs on CONTEXA's step-up page. For a BLOCK whose user has started the release MFA, the access control filter sends a browser to /contexa/step-up?purpose=block and answers an API with 401 BLOCK_MFA_REQUIRED and mfaUrl. Passing it sets the same verified mark as the release MFA above. An administrator's approval still lifts the BLOCK.
  • An agent's BLOCK is 403 AGENT_BLOCKED and is not released by MFA. For releasing it see Stopping and releasing.

When held for review becomes a block

Held for review (ESCALATE) stops a request until an administrator reviews it and approves. If the review stays open too long, the access control filter raises the decision to BLOCK. The steps are:

  1. The first time ESCALATE stops a request, the access control filter sets a retry mark (5 minutes) once.
  2. The decision's lifetime (300 seconds) and the retry mark both pass.
  3. On the next request after that, the filter stores BLOCK, leaves the block mark and answers with a block.

For a person the filter records the block. For an agent it stops that agent. MFA success does not release ESCALATE. As explained above, ESCALATE is not stored with the default settings, so this promotion does not happen there either.

Agent requests

An AI agent's request cannot answer a person's MFA. So when a CHALLENGE applies to an agent request, the challenge filter sends it to the agent request gate instead of MFA. The gate asks the person accountable for the agent (the person who delegated to it, or the sponsor of an agent that works without a delegation) to confirm the request, and it holds the request until that person approves. The agent gets 403 AGENT_CONFIRMATION_REQUIRED and sends the same request again once the accountable person has approved. A request is an agent request when the authentication bridge put a delegation stamp naming an agent on it. Responses and handling in detail are in Stop, Confirm, Limit.

The gate checks a request in this order.

  1. Call limit: when the agent passes its allowed number of calls, the request is refused and the answer says how long to wait.
  2. Ended delegation: a revoked delegation is refused. A delegation that has expired or not started yet requires the accountable person's confirmation.
  3. The accountable person's confirmation for a CHALLENGE: when the decision is CHALLENGE, the request waits until that person approves it.
  4. Narrowed scope: when a decision has narrowed the agent's scope, a request outside it is refused unless the accountable person confirmed that very request.
  • Without the gate (no agent confirmation service bean), a CHALLENGE is answered with 403 AGENT_CONFIRMATION_REQUIRED. There is then no procedure that asks the accountable person.
  • The decision of an agent working for a person is read separately, under the key <user>::agent::<agent>. The agent also receives the delegating person's BLOCK, so when the delegator is blocked the agent stops too.
  • An agent's own BLOCK is answered with 403 AGENT_BLOCKED. The delegating person's account is not blocked; only that agent is stopped.
  • The gate runs in both ownership modes. Under HOST_OWNED the challenge filter runs after the authentication bridge (Filter position when the application owns login), so the gate can see the delegation stamp. The URL authorization step inside the application's chain runs before the bridge, so it has no delegation stamp yet.
