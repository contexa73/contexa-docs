Sessions and Tokens

How to choose whether the state after login lives in a server session (.session()) or travels as tokens (JWT, .oauth2()). It covers the settings required to turn it on and how to check it, how to give people sessions and agents tokens, token checks and delegated tokens.

This is a feature for when Contexa owns login (CONTEXA_OWNED). With the default HOST_OWNED, your application's Spring Security handles sessions and tokens, and Contexa's authorization server and resource server configuration are not built. To keep your application's existing login, see Connecting Your Existing Login.

Choosing between sessions and tokens

Each flow picks one state after its authentication method (Choosing methods and states). Each flow can pick differently.

registry
        .form(form -> form.defaultSuccessUrl("/home"))
        .session(Customizer.withDefaults())       // people: session
        .rest(rest -> rest.order(50))
        .oauth2(Customizer.withDefaults())        // API clients: tokens
        .build();

Session state

Turned on with .session(Customizer.withDefaults()).

  • Changes the session ID at login (changeSessionId), unless sessionManagement(...) in global or in the flow option sets another session fixation policy (such as sessionFixation(fixation -> fixation.none())), which is then used. This holds for every login that ends in a session: form, REST, one-time code, passkey, and MFA (when the factors are completed, or at the primary login when no factor is required). Login also replaces the CSRF token, so a page that logs in with REST and stays open reads the token again before its next request.
  • The logout address is /logout; for an MFA flow with a prefix it is <prefix>/logout. The address is fixed: a logoutUrl(...) written in global or in the flow option logout(...) is not used, because the request-time access control and the MFA-in-progress access control let a restricted session through to exactly this address.
  • Logout invalidates the session and clears the login, and Contexa's logout handler (compositeLogoutHandler) does Contexa's cleanup and clears token cookies.
  • After logout: an MFA flow with a prefix goes to <prefix>/mfa/login; every other session flow goes to /contexa/admin/login. These are defaults: a logoutSuccessUrl(...) or logoutSuccessHandler(...) written in global or in the flow option logout(...) is used instead.

The configurer passed to .session(...) has no options to change. Session settings such as the number of concurrent sessions go in the flow option sessionManagement(...).

registry
        .form(form -> form.sessionManagement(session -> session.maximumSessions(1)))
        .session(Customizer.withDefaults())
        .build();

The limit applies to every login that ends in a session, whichever method logged the user in. With maxSessionsPreventsLogin(true), a login over the limit is refused as a failed login (a REST login and the MFA primary login answer 401; a form login moves to its failure address) and is not counted as a wrong password.

Checking it

  • The session cookie value changes between before and after login.
  • After POST /logout the session ends and the browser moves to the address above.

Token state (OAuth2)

Turned on with .oauth2(Customizer.withDefaults()). Contexa configures Spring Authorization Server and a Spring resource server in that chain.

What it needs

  • Conditions: CONTEXA_OWNED, the Contexa database (the contexaJdbcTemplate and contexaTransactionTemplate beans), and Spring Authorization Server on the class path.
  • contexa.auth.oauth2.client-secret: required when there is at least one token flow and the server mode includes the authorization server (default COMBINED). When empty, startup fails. The old default value (173f8245-…) is refused, and startup also fails when a client already stored in the database has a secret that does not match this value. Keep the same value across restarts.
  • Signing key store: without contexa.auth.oauth2.jwk-key-store-path, tokens are signed with a temporary RSA key that changes at every start, so a restart invalidates every existing token (an error is logged at startup). The path is looked up on the class path; for a file, prefix file:. The key store format is PKCS12, and a missing file makes startup fail.
contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: contexa
  bridge:
    ownership: CONTEXA_OWNED
  auth:
    oauth2:
      client-secret: replace-with-a-long-random-secret
      jwk-key-store-path: file:/etc/contexa/jwk.p12
      jwk-key-store-password: change-me
      jwk-key-alias: contexa
      jwk-key-password: change-me

What is attached automatically

  • Resource server: JWT validation, Contexa's token converter, 401 and 403 handlers, stateless (STATELESS).
  • Authorization server: OAuth2AuthorizationService, RegisteredClientRepository, the token endpoint, OIDC, and a grant that gives tokens to a logged-in user (below).
  • Server mode contexa.auth.oauth2-server-mode: RESOURCE_SERVER (validate only), AUTHORIZATION_SERVER (issue only), COMBINED (both, default). A login flow in the token state needs the issuing side: with RESOURCE_SERVER such a flow stops startup. Use COMBINED (or AUTHORIZATION_SERVER) where the application logs people in, or give those flows the session state. With AUTHORIZATION_SERVER the login succeeds and the next requests are anonymous, since nothing validates the token.
  • When the application defines one OAuth2TokenGenerator bean or one BearerTokenResolver bean, Contexa uses it as it is.
  • Logout (in a mode that includes the authorization server): POST /logout. An API request is answered 200 with status LOGGED_OUT; a plain browser submission moves to the login page (an MFA flow's own; otherwise contexa.auth.urls.primary.form-login-page). A logoutSuccessUrl(...) or logoutSuccessHandler(...) written in global or in logout(...) is not used in the token state; to change the answer, define a LogoutSuccessHandler bean named contexaOauth2LogoutSuccessHandler.

Use the COOKIE transport for server-rendered pages. With the HEADER or HEADER_COOKIE transport and in-memory token storage (contexa.auth.token-persistence: memory, default), the browser's page navigations carry no access token, so pages after login look logged out. Contexa reports this combination with an error log at startup.

Tokens after login

There is a grant, urn:ietf:params:oauth:grant-type:authenticated-user, that gives tokens to a user who finished form, REST or MFA login. When a login succeeds, Contexa requests this grant with its internal client inside the same application, receives the tokens and puts them in the success response. It is configured when the contexaTransactionTemplate bean exists.

Checking it

POST /api/login
Content-Type: application/json

{"username": "alice", "password": "s3cret"}

Send the response's accessToken as Authorization: Bearer … and the protected API answers; without it you get 401. Refresh is POST /api/refresh (contexa.auth.internal.refresh-uri); for an MFA flow with a prefix it is <prefix>/api/refresh.

People on sessions, agents on tokens (request scope)

One application can let people use a session flow while agents and API clients call with tokens. By default a token flow's chain takes every request the flow covers (all requests, or those under its urlPrefix). With the request scope TOKEN_REQUESTS it takes only requests that belong to tokens and passes the rest to the next flow.

Requests a TOKEN_REQUESTS flow takes:

  • Requests carrying an access token the way the chain reads it: the Authorization: Bearer header, or with the COOKIE transport the access token cookie (or the application's BearerTokenResolver bean when it defines one). A malformed token also comes here and is refused with 401.
  • CORS preflight requests announcing an Authorization header.
  • The chain's authorization server endpoints (token, JWK set, introspection, revocation, metadata, OIDC) and the refresh address.
  • The flow's authentication addresses (login processing path, one-time code and passkey endpoints, an MFA flow's pages and endpoints) and its urlPrefix.
  • Requests added with tokenScopeRequests(...), for example a metadata path clients read before they hold a token.
registry
        .rest(rest -> rest
                .loginProcessingUrl("/api/agent/login")
                .order(50))
        .oauth2(oauth2 -> oauth2.requestScope(OAuth2RequestScope.TOKEN_REQUESTS))
        .form(form -> form.defaultSuccessUrl("/home"))
        .session(Customizer.withDefaults())
        .build();
  • Flows with the same order follow the order they are written in. A flow after a flow that takes every request receives none, and Contexa logs an error at startup.
  • Without urlPrefix all MFA flows share the same addresses, so give a token-scoped MFA flow its own prefix.
  • The request scope sets the chain's request matcher, so do not set a matcher with rawHttp; add paths with tokenScopeRequests(...).
  • Log out of a token-scoped flow with the access token attached. A logout without a token goes to the session flow.

Token checks and decisions

Contexa's resource server checks every access token with Spring validators before Contexa reads the request: signature, lifetime, issuer (contexa.auth.oauth2.issuer-validation-enabled, on by default), and the audience (aud) when contexa.auth.oauth2.audiences is set. Contexa's authorization server names the ID of the client a token was issued to as the audience, so list the clients whose tokens this application accepts. A token that fails these checks is refused with 401, and no Contexa filter or decision runs for that request.

A Contexa decision never adds authorities. ALLOW keeps the token's authorities; CHALLENGE, BLOCK and ESCALATE remove the original authorities and leave only the decision's marker authority (How authorities change). To tie an operation to a scope, use a Spring rule such as hasAuthority("SCOPE_reports.write"); a token without that scope is refused whatever the decision.

If the application validates tokens with its own resource server, put the same checks on its decoder.

@Bean
JwtDecoder jwtDecoder() {
    NimbusJwtDecoder decoder = NimbusJwtDecoder.withIssuerLocation("https://idp.example.com").build();
    decoder.setJwtValidator(JwtValidators.createDefaultWithValidators(
            new JwtIssuerValidator("https://idp.example.com"),
            new JwtAudienceValidator("https://api.example.com")));
    return decoder;
}

Delegated tokens (token exchange)

An agent working for a person gets a token that names both: the person as sub and the agent as the actor (act, RFC 8693). Turn this grant on with contexa.auth.oauth2.token-exchange-enabled: true. It is off by default, and while off the token endpoint refuses every client's exchange request with unsupported_grant_type.

Register the agent's client in Spring's RegisteredClientRepository bean with the client_credentials and urn:ietf:params:oauth:grant-type:token-exchange grants and the scopes the agent may receive, and register the agent with that client ID (Registering an agent). The agent then presents its own token as the actor token and exchanges the person's token.

POST /oauth2/token
Authorization: Basic (the agent client's credentials)
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&subject_token=(the person's access token)
&subject_token_type=urn:ietf:params:oauth:token-type:access_token
&actor_token=(the agent's own access token)
&actor_token_type=urn:ietf:params:oauth:token-type:access_token
&scope=reports.read
  • Both tokens must have been issued by this authorization server and still be valid. If the person's token has may_act, only the actor named there can exchange it.
  • The scope is the requested scope and must be within the scopes registered for the agent client.
  • The issued token has sub = the person, act.sub = the agent client and client_id = the agent client. The resource server authenticates the request as the person (the person's authorities and the token's scopes), and every decision records the registered agent acting for that person.
  • Every token Contexa issues is made by Spring Authorization Server's token generator, which adds the token exchange act and the cnf binding of DPoP and mTLS clients before Contexa's claims (client_id, login facts, roles). So a token request with a DPoP proof receives a sender-bound token (token_type DPoP). When you define your own OAuth2TokenGenerator bean it is used as it is, and that bean must add these claims itself.
