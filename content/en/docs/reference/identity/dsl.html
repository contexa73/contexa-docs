Identity DSL

When Contexa owns login, you write the login methods (form, REST, one-time code, passkey, MFA) and the login state (session, token) in one method, and Contexa builds a Spring Security chain for each flow. This page covers when it is on, building a first chain, splitting requests across chains, settings shared by every chain and settings for one chain, and moving from an existing Spring Security configuration.

This is a feature for when Contexa owns login (CONTEXA_OWNED). With the default HOST_OWNED, your application's Spring Security handles login and the flows written here do not become chains. To keep your application's existing login, see Connecting Your Existing Login.

At a glance

You write flows one after another in a single PlatformConfig bean. A flow is a pair of one authentication method and one login state. At startup Contexa registers one SecurityFilterChain bean per flow, and each request is compared with the chains from the lowest order; the first chain that matches handles it.

When it is on: who owns login

Contexa has an authentication ownership setting (contexa.bridge.ownership) that says who handles login. Flows written with the DSL become chains only with CONTEXA_OWNED.

How to turn it on

WayResult
contexa.bridge.ownership: CONTEXA_OWNEDGives only login to Contexa. When set, it wins over the annotation's mode.
@EnableAISecurity(mode = SecurityMode.FULL)Becomes CONTEXA_OWNED when the ownership is not set. This mode means Contexa owns the whole application, so when the application has no DataSource bean, the Contexa database becomes the application's default DataSource (contexa.datasource.isolation.contexa-owned-application).
 
contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: contexa
  bridge:
    ownership: CONTEXA_OWNED

The Identity DSL comes with spring-boot-starter-contexa. The starter brings the identity, iam, core, autoconfigure and common modules and Spring Authorization Server, so no other dependency is needed.

To turn off the DSL, the chains and the request-time filters altogether, set contexa.identity.security-core.enabled: false.

When you define no PlatformConfig

When the application defines no PlatformConfig bean, @EnableAISecurity uses the default configuration below. With your own bean, the default is not used.

Building a first chain

The smallest configuration: one form login with session state. Put @Configuration on the configuration class. In Spring Security 6, @EnableWebSecurity does not include @Configuration, so with that alone the PlatformConfig bean is not registered.

@Configuration
public class LoginFlowsConfig {

    @Bean
    public PlatformConfig platformDslConfig(IdentityDslRegistry<HttpSecurity> registry) throws Exception {
        return registry
                .global(http -> http.authorizeHttpRequests(auth -> auth
                        .requestMatchers("/css/**", "/js/**").permitAll()
                        .anyRequest().authenticated()))
                .form(form -> form.defaultSuccessUrl("/home"))
                .session(Customizer.withDefaults())
                .build();
    }
}

What this gives you:

  • One chain bean, form_flowSecurityFilterChain1. The flow sets no scope, so it takes every request.
  • The login page is Spring's default page at GET /login, and login is processed at POST /login (contexa.auth.urls.single.form-login-processing).
  • Logging in changes the session ID (session fixation protection), and /logout logs out.
  • CSRF stays on, as in Spring's default.

Checking it

  • Opening a protected address in a browser goes to /login, and after login to /home.
  • If the startup log shows Skipping Contexa-owned authentication chain bootstrap in HOST_OWNED mode, the ownership is HOST_OWNED and no chain was built.
  • If a flow can never receive a request, the startup log shows a Flow '…' is never reached error (Splitting requests across chains).

Choosing methods and states

After an authentication method you call a state method; the state method applies to the method written just before it.

Authentication methodWhere it fitsDefault orderFlow name
.form(...)Server-rendered login page (Form login)100form_flow
.rest(...)JSON login for SPAs, mobile apps and APIs (REST login)200rest_flow
.ott(...)A one-time code received by email (One-time code)300ott_flow
.passkey(...)Passkey (Passkey)400passkey_flow
.mfa(...)Primary login + second factors (Adaptive MFA)200mfa
StateWhat it does
.session(...)Keeps the login in the HTTP session, changes the session ID at login, configures logout (Session state)
.oauth2(...)Issues and validates tokens (JWT). By default it configures a resource server and an authorization server together, and contexa.auth.oauth2.client-secret is required (Token state)
  • Using the same method more than once names the flows form_flow, form_flow_2, form_flow_3 and so on.
  • The same .form() can take a different state in each flow. The five methods and two states combine freely.
  • The lambda passed to .session(...) or .oauth2(...) applies to that state's configurer. For the token state the request scope (requestScope, tokenScopeRequests) is set here.
  • A flow with no state gets only its success and failure handlers from contexa.auth.state-type (default OAUTH2); no session or token configuration is attached. Always give each flow a state.

Splitting requests across chains

Chains are compared from the lowest order. A chain without a scope takes every request, so a chain placed after it never receives one. Contexa then names both flows in a Flow '…' is never reached error at startup. Flows with the same order are compared in the order they are written.

How to set the scopeFlowsEffect
rawHttp(http -> http.securityMatcher("/admin/**"))Form, REST, one-time code, passkeyTakes only requests under that path
.mfa(mfa -> mfa.urlPrefix("/admin"))MFAEvery MFA address gets the prefix and the chain scope becomes /admin/** (Several MFA flows)
.oauth2(oauth2 -> oauth2.requestScope(OAuth2RequestScope.TOKEN_REQUESTS))Token stateTakes only requests carrying a token and the flow's authentication addresses, and passes the rest to the next flow (Request scope)
When you narrow a form flow's scope, change its login processing path too. A form flow's login processing path is not loginPage but contexa.auth.urls.single.form-login-processing (default /login). If a chain scoped to /admin/** only gets loginPage("/admin/login"), the login POST (/login) goes to another chain. Two flows sharing one processing path do not stop startup, so take care. 
registry
        .global(http -> http.authorizeHttpRequests(auth -> auth.anyRequest().authenticated()))
        // Administrators: only under /admin, with the application's own login page
        .form(form -> form.order(10)
                .loginPage("/admin/login")
                .loginProcessingUrl("/admin/login")
                .defaultSuccessUrl("/admin")
                .permitAll()
                .rawHttp(http -> http.securityMatcher("/admin/**")))
        .session(Customizer.withDefaults())
        // API clients: only requests that carry a token
        .rest(rest -> rest.order(50))
        .oauth2(oauth2 -> oauth2.requestScope(OAuth2RequestScope.TOKEN_REQUESTS))
        // Everyone else: every remaining request
        .form(form -> form.order(100).defaultSuccessUrl("/home"))
        .session(Customizer.withDefaults())
        .build();

A chain's actual order value is Ordered.HIGHEST_PRECEDENCE + the flow's order, so it comes before any SecurityFilterChain bean the application registers on its own.

Settings for every chain (global)

The global(http -> ...) lambda is applied first to every flow's HttpSecurity. Flow settings are applied after it, so for the same item the flow wins; for example the flow option disableCsrf() turns CSRF off for that chain only. If the global lambda throws, Contexa logs a warning for that flow and carries on.

CSRF

FlowCSRF
Session stateOn, as in Spring's default.
Token state, HEADER or HEADER_COOKIE transportIn a server mode that includes the authorization server (default COMBINED) it follows contexa.auth.oauth2-csrf (default false), so it is off by default.
Token state, COOKIE transportAlways on, because the browser sends the cookies by itself. Setting contexa.auth.oauth2-csrf: false makes startup fail.
Flow option disableCsrf()Turns it off for that chain only.

To exchange the CSRF token in a cookie, put the Spring setting in global.

registry
        .global(http -> http.csrf(csrf -> csrf
                .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())))
        // ... flows

Login repository

With @EnableAISecurity, Contexa puts its session login repository (AISessionSecurityContextRepository) into every flow right after global. So even if global sets securityContext(sc -> sc.securityContextRepository(...)), it is replaced by this repository. You do not need to connect it yourself.

This repository extends Spring's HttpSessionSecurityContextRepository. When the login is read, an invalidated session is ended and an empty login is returned; otherwise the authorities are adjusted to the stored decision (How authorities change). When saved, it records the session tracking used for forced logout.

CORS and your own filters

CORS settings and your own filters are written the Spring way in global (every chain) or in the flow option rawHttp (one chain). Add your filter with http.addFilterBefore(...) in the same lambda.

registry
        .global(http -> http.cors(cors -> cors.configurationSource(request -> {
            CorsConfiguration config = new CorsConfiguration();
            config.setAllowedOrigins(List.of("https://app.example.com"));
            config.setAllowedMethods(List.of("GET", "POST"));
            config.setAllowCredentials(true);
            return config;
        })))
        // ... flows

Changing one chain (flow options)

Options used in an authentication method's lambda. Method-specific options (login page, parameter names and so on) are in Login Methods.

OptionMethodsWhen to use
order(int)Form, REST, one-time code, passkeyTo change the order chains are compared in. For MFA, .mfa(mfa -> mfa.order(...))
loginProcessingUrl(String)Form, REST, one-time code, passkeyTo change the login POST path. It has no effect on a single passkey flow
defaultSuccessUrl(...) · failureUrl(String)Form, RESTWhere to go after login success or failure
successHandler(...) · failureHandler(...)Form, REST, one-time codeTo write the response yourself (Success and failure handling). Not used by passkey flows
securityContextRepository(...)Every methodTo change where the login is kept. In session state Contexa's session repository takes precedence
disableCsrf()Every methodTo turn CSRF off for that chain only
cors(...) · headers(...) · sessionManagement(...) · logout(...)Every methodTo change that chain's Spring settings
authorizeStaticPermitAll(...)Every methodTo open static paths without authentication
rawHttp(...)Every methodSpring settings not listed above, and the chain scope (securityMatcher). Called several times, all of them apply in order
asep(...)Every methodHas no effect in the current version (ASEP)
  • Options are applied after global. The rawHttp lambda is a SafeHttpCustomizer, so it may throw checked exceptions.
  • .mfa() has none of these options. An MFA flow's scope is set with urlPrefix, and rawHttp is used inside the primary login's or a factor's options.
  • Global takes an HttpSecurity lambda directly, without options.
registry
        .form(form -> form
                .rawHttp(http -> http.securityMatcher("/portal/**"))
                .rawHttp(http -> http.headers(headers -> headers.frameOptions(frame -> frame.sameOrigin()))))
        .session(Customizer.withDefaults())
        .build();

Complete example

API clients use tokens, administrators use MFA under /admin, and everyone else uses form login.

@Configuration
public class LoginFlowsConfig {

    @Bean
    public PlatformConfig platformDslConfig(IdentityDslRegistry<HttpSecurity> registry) throws Exception {
        return registry
                .global(http -> http.authorizeHttpRequests(auth -> auth
                        .requestMatchers("/css/**", "/js/**", "/favicon.ico").permitAll()
                        .anyRequest().authenticated()))
                // 1. API clients and agents: only requests that carry a token
                .rest(rest -> rest.order(50))
                .oauth2(oauth2 -> oauth2.requestScope(OAuth2RequestScope.TOKEN_REQUESTS))
                // 2. Administrators: MFA under /admin
                .mfa(mfa -> mfa.urlPrefix("/admin").order(80)
                        .primaryAuthentication(primary -> primary.formLogin(form -> form.defaultSuccessUrl("/admin")))
                        .passkey(Customizer.withDefaults())
                        .ott(Customizer.withDefaults()))
                .session(Customizer.withDefaults())
                // 3. Everyone else: form login
                .form(form -> form.order(100).defaultSuccessUrl("/home"))
                .session(Customizer.withDefaults())
                .build();
    }
}

How it works

The validators check duplicate login processing paths, the MFA flow structure, passkey options (rpId), the MFA passkey registration path, that each authentication method has an implementation, and duplicate flow names. Their result does not stop startup, and only some of them log errors (a duplicate login processing path is not even logged).

Configurer order

The order value is the turn in which a configurer is applied, not the position of a filter. Filter positions are in Where the filters run.

Order valueWhat the configurer does
HIGHEST_PRECEDENCE + 100Applies the global lambda
HIGHEST_PRECEDENCE + 105Connects Contexa's session login repository
HIGHEST_PRECEDENCE + 110Connects the authentication bridge filter
HIGHEST_PRECEDENCE + 150Generates the MFA pages (MFA flows)
44 · 45 · 50Connects the MFA-in-progress access control, the request-time access control and the challenge filter
300Applies the authentication method (including flow options)
400Applies the login state (session or token)
500Default for a SecurityConfigurer bean the application makes

Extension point: adding configuration to every chain

A bean implementing SecurityConfigurer is applied by Contexa to every flow's chain. getOrder() decides its turn in the table above (default 500).

@Bean
public SecurityConfigurer chainNameHeaderConfigurer() {
    return new SecurityConfigurer() {
        @Override
        public void init(PlatformContext ctx, PlatformConfig config) {
        }

        @Override
        public void configure(FlowContext fc) throws Exception {
            String flowName = fc.flow().getTypeName();
            fc.http().headers(headers -> headers.addHeaderWriter(
                    new StaticHeadersWriter("X-Login-Flow", flowName)));
        }
    };
}

Moving from an existing Spring Security configuration

  1. Set the ownership to CONTEXA_OWNED (How to turn it on).
  2. Move the SecurityFilterChain beans into one PlatformConfig. One chain is one flow. securityMatcher moves to rawHttp and @Order to order.
  3. To hand URL rules to Contexa's dynamic authorization, use anyRequest().access(customDynamicAuthorizationManager) in global (as the default FULL configuration does). URL decisions then come from the policies in the admin console. The resource scanner only registers endpoints as resources; it does not read hasRole rules to create policies, so create policies for the same rules first (Resource scanner, Policies).
  4. A URL that no policy matches is allowed by default (contexa.policy.no-matching-url-policy-decision, default PERMIT).
  5. The enforcement mode does not affect URL policies. With contexa.security.zerotrust.mode (default ENFORCE) set to SHADOW, only the AI decisions stop being stored and applied; URL policy decisions are still enforced. Check policies in a test environment (Enforcement modes).
// Before
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain appChain(HttpSecurity http) throws Exception {
        return http
                .authorizeHttpRequests(auth -> auth
                        .requestMatchers("/admin/**").hasRole("ADMIN")
                        .anyRequest().authenticated())
                .formLogin(Customizer.withDefaults())
                .build();
    }
}
// After: create the /admin/** rule as a policy in the admin console
@Configuration
public class SecurityConfig {

    @Bean
    public PlatformConfig platformDslConfig(IdentityDslRegistry<HttpSecurity> registry,
                                            CustomDynamicAuthorizationManager customDynamicAuthorizationManager) throws Exception {
        return registry
                .global(http -> http.authorizeHttpRequests(auth -> auth
                        .requestMatchers("/css/**", "/js/**").permitAll()
                        .anyRequest().access(customDynamicAuthorizationManager)))
                .form(Customizer.withDefaults())
                .session(Customizer.withDefaults())
                .build();
    }
}
