Adaptive MFA

How to turn on an MFA flow that asks for second factors (an emailed one-time code, a passkey) after the primary login (form or REST). It covers what decides whether MFA is needed, the pages and addresses, the response formats, extra verification after login, the JavaScript SDK and the settings.

This is a feature for when Contexa owns login (CONTEXA_OWNED). With the default HOST_OWNED, your application's Spring Security handles login and no Contexa MFA flow is built. To keep your application's own login and MFA and tell Contexa the result, see Connecting Your Existing Login. With @EnableAISecurity(mode = SecurityMode.FULL) and no PlatformConfig defined, one MFA flow (form + passkey + one-time code) is on by default.

At a glance

When the primary login succeeds, the MFA policy decides whether this user needs MFA. If so, Contexa opens the page of the first second factor right away, and the user can pick a remaining factor with "another method". The login finishes once the required number of factors is done.

There are two second factors: an emailed one-time code (.ott()) and a passkey (.passkey()). There is no authenticator app code (TOTP) or text message (SMS) factor.

The simplest MFA

registry
        .mfa(mfa -> mfa
                .primaryAuthentication(primary -> primary.formLogin(Customizer.withDefaults()))
                .passkey(Customizer.withDefaults())
                .ott(Customizer.withDefaults()))
        .session(Customizer.withDefaults())
        .build();
  • Contexa generates the login page GET /mfa/login and the factor pages. The primary login is processed at POST /mfa/login.
  • The flow is named mfa, its default order is 200, and the chain bean is named like mfaSecurityFilterChain1.
  • The primary login is one of formLogin and restLogin (.primaryAuthentication(...) is required).
  • Without any second factor, startup fails. Calling .form() or .rest() inside .mfa() throws UnsupportedOperationException. Writing the same factor twice makes the later one replace the earlier one.
The one-time code factor needs mail settings. The code is sent with Spring mail (spring.mail.*); without a mail sender, issuing a code fails as contexa.auth.ott.fail-on-email-error (default true) says (One-time code).

Checking it

  • Opening a protected address goes to the /mfa/login page.
  • After the primary login, if MFA is needed, the first factor's page opens (for example /mfa/challenge/passkey). A user logging in for the first time has no stored decision and goes through MFA.

Second factors and how many are required

The primary login is number 0 and second factors are 1, 2, … in the order written. requiredFactors(n) sets how many factors must be completed.

requiredFactorsBehavior
Not setEvery registered factor must be completed
1Any one factor. The first factor opens automatically, and the "another method" link lets the user pick a remaining one (completed factors drop out of the list)
NN factors must be completed. When one is done, the next follows automatically
More than the factorsCan never complete. It is not checked at startup, so take care
 
registry
        .mfa(mfa -> mfa
                .primaryAuthentication(primary -> primary.formLogin(Customizer.withDefaults()))
                .passkey(Customizer.withDefaults())
                .ott(Customizer.withDefaults())
                .requiredFactors(1))   // passkey first; devices without one use the one-time code
        .session(Customizer.withDefaults())
        .build();

registry

                .primaryAuthentication(primary -> primary.formLogin(Customizer.withDefaults()))
                .ott(Customizer.withDefaults())
                .mfaPage(page -> page
                        .selectFactorPage("/mfa/select")

        .session(Customizer.withDefaults())
        .build();

Your own primary login page

  • With loginPage, as in formLogin(form -> form.loginPage("/login")), Contexa does not generate a login page. The application makes that page, and the page posts to POST /mfa/login.
  • To keep Contexa's page and change only its address, use defaultLoginUrl("/signin"). The page address and the processing path change together.

The policy that decides whether MFA is needed

When the primary login succeeds, the MFA policy provider decides. The default provider is the AI adaptive provider (AIAdaptiveMfaPolicyProvider), and among the registered evaluators the one with the highest priority that covers this user decides.

EvaluatorPriorityUsers it coversDecision
AgentAccountMfaPolicyEvaluator1000Accounts of approved agentsNever sends them to factors made for people; follows only Contexa's decision
ZeroTrustPolicyEvaluator100Every other userStored decision ALLOW → MFA skipped. CHALLENGE → MFA. BLOCK → blocked. ESCALATE → held for review (blocked). No decision (PENDING_ANALYSIS) → skipped if the last verified decision was ALLOW, otherwise MFA. No decision record, or an old one (contexa.security.zerotrust.analysis.max-age-ms, 1 hour) → MFA
DefaultMfaPolicyEvaluator-100A fallback for when an earlier evaluator throwsAsks for MFA in an MFA flow. The built-in evaluators turn their own errors into "MFA needed", so it is rarely used

The policy has four decisions: NO_MFA_REQUIRED (not needed), CHALLENGED (needed), BLOCKED (blocked) and ESCALATED (held for review, access blocked). Blocked and held for review both answer the primary login with 403 AUTHENTICATION_BLOCKED.

The AI adaptive provider adjusts the evaluator's decision with the AI analysis results (block mark, decision type, risk score). Without the AI feature (AICoreOperations) it uses the evaluator's decision as it is, without this adjustment. The decision for an approved agent account is never adjusted.

Changing the policy

  • Add an evaluator: a MfaPolicyEvaluator bean is considered by priority together with the built-in evaluators. Narrow the users it covers with supports(...). An evaluator that covers every user with a priority above 100 takes over the decision based on the Zero Trust decision.
  • For one flow only: .mfa(mfa -> mfa.policyProvider(myProvider)) changes that flow's provider.
  • The whole provider: a MfaPolicyProvider bean named aiAdaptiveMfaPolicyProvider replaces the default provider. Adding a bean of the same type under another name leaves the @Primary default in use. A provider implements four methods: evaluateInitialMfaRequirement, evaluateNextFactor, isFactorAvailableForUser and getRequiredFactorCount.
@Bean
public MfaPolicyEvaluator adminFlowAlwaysMfa() {
    return new MfaPolicyEvaluator() {
        @Override
        public boolean supports(FactorContext context) {
            return context != null && "mfa_admin".equals(context.getFlowTypeName());
        }

        @Override
        public MfaDecision evaluatePolicy(FactorContext context) {
            return MfaDecision.challenged("The admin flow always asks for a second factor");
        }

        @Override
        public int getPriority() {
            return 500;
        }
    };
}

Inside an evaluator, request information comes from the FactorContext attributes. For example the IP of the primary login request is context.getAttribute(FactorContextAttributes.DeviceAndSession.CLIENT_IP).

Extra verification after login

When the next request of a logged-in user finds a stored CHALLENGE decision, the request-time challenge filter starts MFA again (step-up). A browser goes to the /contexa/zero-trust/challenge-required?mfaUrl=… notice page, and an API gets 401 MFA_CHALLENGE_REQUIRED (body mfaUrl, challengeNoticeUrl). When this MFA succeeds, the decision changes to ALLOW. The full responses are in Request-Time Enforcement.

On a page that loads the JavaScript SDK, the SDK looks at fetch responses and handles them as follows.

ResponseWhat the SDK does
401 MFA_CHALLENGE_REQUIRED · BLOCK_MFA_REQUIREDMoves to challengeNoticeUrl (or mfaUrl)
Any other 401 (expired access token)Refreshes the token once and sends the same request again
403 ACCOUNT_BLOCKED · BLOCK_MFA_FAILEDMoves to redirectUrl (blocked page)
423 SECURITY_REVIEW_IN_PROGRESSMoves to redirectUrl (analysis pending page)
403 with the response-cut markerMoves to the blocked page

After MFA the original request is not sent again automatically. A request is resent only after an expired token is refreshed.

Several MFA flows

Each MFA flow can have its own chain, factors and addresses. urlPrefix("/admin") puts the prefix in front of every MFA address of that flow and makes the chain scope /admin/** (securityMatcher set automatically). The prefix may contain only letters, digits, /, _ and -.

Default addressurlPrefix("/admin")
/mfa/login/admin/mfa/login
/mfa/select-factor/admin/mfa/select-factor
/login/mfa-ott/admin/login/mfa-ott
/login/mfa-webauthn/admin/login/mfa-webauthn
/mfa/cancel/admin/mfa/cancel
  • Flow names: name("admin") gives mfa_admin; without a name they are mfa, mfa_2, mfa_3 in order.
  • An MFA flow without a prefix takes every request, so put it last. Flows after it are never reached, and an error is logged at startup.
  • .mfa() has no rawHttp; the scope is set with urlPrefix.
registry
        .mfa(mfa -> mfa.name("admin").urlPrefix("/admin").order(50)
                .primaryAuthentication(primary -> primary.formLogin(Customizer.withDefaults()))
                .passkey(Customizer.withDefaults())
                .requiredFactors(1))
        .session(Customizer.withDefaults())
        .mfa(mfa -> mfa
                .primaryAuthentication(primary -> primary.formLogin(Customizer.withDefaults()))
                .ott(Customizer.withDefaults()))
        .session(Customizer.withDefaults())
        .build();

Together with single login

MFA flows and single login flows can sit side by side. Requests are split by order and scope, and each flow picks its own state.

registry
        .mfa(mfa -> mfa.urlPrefix("/admin").order(50)
                .primaryAuthentication(primary -> primary.formLogin(Customizer.withDefaults()))
                .passkey(Customizer.withDefaults()))
        .session(Customizer.withDefaults())
        .rest(rest -> rest.order(100))
        .oauth2(Customizer.withDefaults())
        .build();

JavaScript SDK

Loading /js/contexa-mfa-sdk.js creates window.ContexaMFA (version 2.2.0). The MFA pages Contexa generates use this SDK. In your own pages or an SPA, use new ContexaMFA.Client(options).

<script src="/js/contexa-mfa-sdk.js"></script>
<script>
  const mfa = new ContexaMFA.Client({ tokenPersistence: 'sessionStorage' });

  async function signIn(username, password) {
    // The primary login goes through apiClient. Then call selectFactor, verifyOtt or verifyPasskey depending on the response.
    const result = await mfa.apiClient.loginForm(username, password);
    console.log(result);
  }
</script>

Progress states

A state machine (MfaState) manages MFA progress. Its end states are:

StateMeaning
MFA_SUCCESSFULMFA succeeded
MFA_NOT_REQUIREDMFA not needed
MFA_FAILED_TERMINALFinal failure
MFA_CANCELLEDCancelled by the user
MFA_SESSION_EXPIREDMFA session expired
MFA_SESSION_INVALIDATEDMFA session invalidated
MFA_RETRY_LIMIT_EXCEEDEDAttempt limit (contexa.auth.mfa.max-retry-attempts) exceeded
MFA_SYSTEM_ERRORSystem error
No state change events are published. The state machine event classes (MfaStateMachineEvents) are in the code, but nothing publishes them in the current version, so @EventListener cannot receive them.

Changing result handling

  • .mfa()'s mfaSuccessHandler and mfaFailureHandler accept a value but are not used.
  • The handlers that write MFA responses (PrimaryAuthenticationSuccessHandler, MfaFactorProcessingSuccessHandler, UnifiedAuthenticationFailureHandler) are classes that cannot be extended (final).
  • So MFA results are handled in the page or the SDK, from the JSON and redirects in Response formats. For single login flows see Success and failure handling.
