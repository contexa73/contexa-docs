Login Methods

The setup, processing addresses and checks of the four single-factor authentication methods CONTEXA offers when it handles login: form, REST, one-time code and passkey. The page also covers the handlers that write the success and failure responses, and where the login is kept.

This page applies to FULL (its main flow), where CONTEXA handles login. With the default security mode SANDBOX, your application handles login (whatever the ownership), and the authentication flows on this page (CONTEXA's main flow) are not built. To keep your application's existing login, see Connecting Your Existing Login. How to hand login to CONTEXA is in Before you start below.
Terms on this page. Authentication confirms who sent a request, and a credential is the value that proves it (a password, a one-time code or a passkey). An authentication flow is one unit of setup that pairs one authentication method with one authentication state. Each flow becomes one security filter chain (a bundle of Spring Security filters that inspect requests), and the chain with the lower order value receives a request first. Single-factor authentication is a login that ends with one credential; multi-factor authentication (MFA) checks a second authentication factor (a one-time code or a passkey) after the password. The authentication state is how the signed-in user is kept: the session state (.session()) keeps it in the server's HTTP session, and the token state (.oauth2()) keeps it in the access token the client sends with every request. The security context (SecurityContext) is the object that holds the signed-in user, and a handler is the code that writes the response when a login succeeds or fails. The setup syntax is in Identity DSL, and the states are in State Management.

Before you start: three requirements

CONTEXA handles login only when all three of the following are in place.

1. Declare that CONTEXA handles login

@SpringBootApplication
@EnableAISecurity(mode = SecurityMode.FULL)
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}
  • With mode = SecurityMode.FULL CONTEXA's main flow signs your application's users in. Without a mode the default is SANDBOX, and your application then handles login. The authentication ownership (contexa.bridge.ownership) is a setting separate from the security mode; left unset, it follows the mode (SANDBOX → HOST_OWNED, FULL → CONTEXA_OWNED). All four combinations are allowed. Under FULL the main flow checks users against CONTEXA's accounts with CONTEXA_OWNED, and against the UserDetailsService your application declares with HOST_OWNED (CONTEXA's accounts when it declares none).
  • The setting contexa.ai.security.mode: FULL does the same. The setting takes precedence over the value in the code.

2. Write the authentication flows in one bean

Login methods are written in one PlatformConfig bean. The bean method takes an IdentityDslRegistry<HttpSecurity> and writes, in order, an authentication method (.form() and so on), an authentication state (.session() or .oauth2()) and build(). Every short example on this page (registry ...) is the body of this method.

@Configuration
public class LoginFlowsConfig {

    @Bean
    public PlatformConfig platformDslConfig(IdentityDslRegistry<HttpSecurity> registry) throws Exception {
        return registry
                .form(form -> form.defaultSuccessUrl("/home"))
                .session(Customizer.withDefaults())
                .build();
    }
}

The configuration class must carry @Configuration. The default setup used when there is no such bean, and the options shared by every flow, are in Identity DSL.

3. The accounts that sign in are in the CONTEXA account store

  • Every single-factor login and the first step of MFA look the account up in the user table ctxa_users of the CONTEXA database (bean contexaUnifiedUserDetailsService). Authorities are computed from the roles given to the account itself and to the groups it belongs to.
  • A UserDetailsService bean of your application is not used for CONTEXA's login. A user who exists only in your application is refused as an unknown name is.
  • A locked account, a disabled account and an account past its validity date cannot sign in with a password, a one-time code or a passkey. External accounts that the bridge brought over from your application's login (externalAuthOnly) cannot be used for CONTEXA's login either (Connecting Your Existing Login).
  • First account: when contexa.iam.seed.admin.password is set, one administrator account (default name admin) is created at startup. When it is not set, five sample accounts are created in a database that has no user account yet. The sample accounts share one password, so in production set contexa.iam.seed.accounts.enabled: false so that they are not created (First start: schema and default data).

How one login request is processed

With form login in the session state, a request the user submits from the login page is processed in this order.

  1. Request arrives: the browser sends username and password to POST /login.
  2. Chain selection: of the security filter chains built for the flows, the chain that accepts this address processes the request. When several chains could accept it, the one with the lower order value goes first.
  3. Account lookup: the account with the same name is looked up in the CONTEXA account store. Without such an account the login fails.
  4. Credential check: the account state (locked, disabled, validity date) is checked first, and only an account that passes has its password compared with the stored one. When the password matches, the password's validity period is checked last.
  5. Success: the security context that holds the login is stored in the HTTP session, and the session ID is replaced with a new one (protection against session fixation). The browser is then sent to the address it first asked for, or to defaultSuccessUrl.
  6. Next request: when the browser sends the session cookie, CONTEXA's repository takes the security context out of the session and applies the Zero Trust decision stored for that user (Where the login is kept).

On failure, Spring's default handler sends the browser to /login?error. What differs for the other methods and for the token state is in the sections below and in Success and failure handling.

Which method when

For a first choice, decide by the kind of client. A web application whose pages the server renders uses form login with the session state; an SPA, a mobile app or an API client uses REST login with the token state. To let users sign in without a password, add a one-time code (production needs a mail server) or a passkey (needs an HTTPS domain; localhost during development).

Each method becomes its own chain. Shared options such as order, rawHttp and disableCsrf are in Flow options.

registry
        .form(form -> form

        .build();

Here the application makes the /admin/login page. To write the response yourself, give successHandler(...) and failureHandler(...) (Success and failure handling).

Checking it

  • Opening a protected address goes to the login page.
  • A successful login goes to defaultSuccessUrl (or the originally requested address), a failure to /login?error.

REST login

Logs in with a JSON body. It is mostly used with the token state, and it can be used with the session state as well.

registry
        .rest(rest -> rest.defaultSuccessUrl("/app"))
        .oauth2(Customizer.withDefaults())
        .build();
POST /api/login
Content-Type: application/json

{"username": "alice", "password": "s3cret"}
StateSuccess response (200, JSON)
.oauth2(), HEADER transport (default)accessToken, tokenType (Bearer), expiresIn, refreshToken, refreshExpiresIn, tokenTransportMethod, authenticated, redirectUrl, message, username
.session()authenticated, redirectUrl, message, username, stateType (SESSION) + session cookie
  • The login processing path takes POST only. GET /api/login at the same path shows a default login page. When loginProcessingUrl changes the path, the page is at the new path.
  • With .session(), redirectUrl is the page the browser asked for before it was sent to log in (its path and query), when there is one. With defaultSuccessUrl(url, true) it is always url.
  • A failed login is answered with status 401 and a JSON body. The failure response leaves no sooner than contexa.auth.mfa.minimum-delay-ms (default 500 ms) after the request arrived. This slows down brute-force attacks that try one password after another.
  • .oauth2() already applies the policy that creates no session (STATELESS), so you do not set it again with rawHttp. With .oauth2(), contexa.auth.oauth2.client-secret is required (What the token state needs).

GET /api/orders
Authorization: Bearer <accessToken>

With the received accessToken the protected API answers; without it you get 401.

One-time code (OTT)

Takes a user name, sends a one-time code by email, and logs in with that code.

registry
        .ott(Customizer.withDefaults())
        .session(Customizer.withDefaults())
        .build();
  • Sending service: the default OneTimeTokenService bean is EmailOneTimeTokenService. It keeps the code in the ctxa_one_time_tokens table of the CONTEXA database and sends it with Spring mail (spring.mail.*).
  • Recipient: the email address in the user table (ctxa_users). Without one, the user name is used as the address. A request email that differs from the registered address is refused.
  • When no mail is sent: when there is no such account, or the account is locked, disabled or expired, no code is created and no mail is sent. The answer then looks the same as a normal issue, so asking for a code does not reveal whether an account exists. A code login does not use the password, so an account whose password has expired can still sign in with a code.
  • Resend interval: to one address only one mail goes out per contexa.auth.mfa.email-resend-interval-seconds (default 120 seconds). A request inside that time creates no new code, and the code received earlier stays valid. Addresses that differ only in capitals or blanks count as the same address.
  • When mail cannot be sent: with contexa.auth.ott.fail-on-email-error (default true) issuing fails. With false the code is still created and a warning is logged.
  • Sending limits: at most contexa.auth.ott.email-max-concurrent-sends (default 64) mails are sent at one time. A request waits up to contexa.auth.ott.email-send-wait-seconds (default 5) for a place, and then fails as an undelivered mail does. contexa.auth.ott.email-smtp-timeout-seconds (default 0, not set) limits the connect, read and write of the SMTP conversation; a value is written into the application's mail sender where spring.mail.properties.mail.smtp.*timeout sets none, so it also applies to the application's other mail sent with that sender.
  • Validity: the code of a single one-time code login is valid for 5 minutes after it is created (Spring's default). A one-time code inside MFA has 6 digits and is valid for contexa.auth.mfa.otp-token-validity-seconds (default 300 seconds). The number of minutes in the email text comes from this setting in both cases.
  • Seeing the code in development and tests: when a development profile (local, dev, development, test) is active, or no mail server is configured, the code is also written to the log (WARN) besides being mailed. This lets a login finish without a mail server, and a mail that cannot be sent then does not fail the login. In production the code is sent by mail only. contexa.auth.ott.code-to-console (true or false) sets it yourself.
OptionDefaultWhen to change
tokenGeneratingUrl(String)/ott/generateTo change the code issuing path
defaultSubmitPageUrl(String)/login/ott/verifyTo change the code entry page path
showDefaultSubmitPage(boolean)truefalse when the application makes the code entry page
loginProcessingUrl(String)/login/ottTo change the code check path
tokenGenerationSuccessHandler(...)contexaOneTimeTokenCreationSuccessHandler beanTo change the response after a code is created. Only when contexa.auth.urls.factors.ott.code-sent is set to an address other than its default (/mfa/ott/code-sent) does it move there, with email, type=code_sent, flow=ott_single and repository in the query
tokenService(...)OneTimeTokenService beanSee the warning below

The request parameter names are fixed: username and token.

To change the sending service, register a bean, not the option. The DSL's tokenService(...) is used only to issue codes; codes are checked with the OneTimeTokenService bean. Giving another service through the option makes the check fail. A registered bean is used for both issuing and checking. 
@Bean
public OneTimeTokenService oneTimeTokenService() {
    // For example, in-memory storage for tests. This service sends no email, so the application delivers the code.
    return new InMemoryOneTimeTokenService();
}

Passkey

Logs in without a password using a WebAuthn passkey. A passkey is created bound to the domain of the service (the relying party ID, rpId), and at login the browser checks this domain and the origin it connected to (protocol, host and port). Both values must therefore match the production address.

registry
        .passkey(Customizer.withDefaults())
        .session(Customizer.withDefaults())
        .build();
contexa:
  auth:
    urls:
      factors:
        passkey:
          rp-id: example.com
          rp-name: Example
          allowed-origins: https://app.example.com
OptionDefaultWhen to change
rpId(String)localhostChange it to the production domain. The default comes from the setting contexa.auth.urls.factors.passkey.rp-id
rpName(String)contexa-identityThe service name users see
allowedOrigins(...)http://localhost: + server.port (8080 when unset)The origins browsers connect from. The setting allowed-origins (comma-separated) wins when present
assertionOptionsEndpoint(String) · loginProcessingUrl(String)/webauthn/authenticate/options · /login/webauthnNo effect on a single passkey flow, which uses Spring's default paths
  • A passkey flow in the session state does not use the successHandler and failureHandler options. In the token state, and for a passkey factor of MFA, they are called as for the other methods (Success and failure handling).
  • A passkey login is the login of the CONTEXA account the passkey belongs to, the same as its password login: no further account is created for it.
  • With an empty rpId, a configuration validator logs an error at startup. It does not stop the start.
  • With the CONTEXA database (a contexaJdbcTemplate bean), Spring's JDBC repositories that keep passkey data (JdbcUserCredentialRepository, JdbcPublicKeyCredentialUserEntityRepository) are registered automatically.

Success and failure handling

Without successHandler and failureHandler, CONTEXA picks handlers for the flow type and state. In the table, single means a non-MFA flow, MFA primary the first login of MFA, and MFA second factor the one-time code or passkey after it.

FlowStateSuccessFailure
Single form, one-time codeSessionSpring's default (moves to defaultSuccessUrl)Spring's default (moves to failureUrl)
Single RESTSessionSessionSingleAuthSuccessHandlerSessionSingleAuthFailureHandler
Single passkeySessionSpring's default JSON response (with the login facts recorded)Spring's default
Single, every methodTokenOAuth2SingleAuthSuccessHandler (issues tokens)OAuth2SingleAuthFailureHandler
MFA primaryBothPrimaryAuthenticationSuccessHandlerUnifiedAuthenticationFailureHandler
MFA second factorBothMfaFactorProcessingSuccessHandlerUnifiedAuthenticationFailureHandler
  • CONTEXA's handlers answer with JSON when the request's Accept or Content-Type carries JSON or its path contains /api/, and with a redirect otherwise.
  • In the token state a page login of a single flow goes, as in the session state, to the page the browser asked for before it was sent to log in (with defaultSuccessUrl(url, true) always to url). A failed page login moves to the flow's failureUrl, by default its login page with ?error (/login?error), as in the session state.
  • When the password is right but past its validity period, a REST flow, a form flow in the token state and the first step of MFA lead the user to the password change page. A browser is sent to /contexa/password-change?expired=true, and a script request is answered with 401 CREDENTIALS_EXPIRED and that page's address in nextStepUrl. The account name is kept in the session for the change page. A form flow in the session state answers with an ordinary login failure. One-time code and passkey logins do not use the password (One-time code).
  • In a form or REST flow, a given successHandler is attached directly in place of the automatic one. Even in the token state CONTEXA then issues no token, so that handler owns the response.
  • In a one-time code flow the automatic handler, when there is one, comes first. In the token state the given handler is called first after the tokens are issued, and CONTEXA writes the response only if that handler did not.
  • In an MFA flow, a successHandler given to the primary login or to a factor is called when the login completes at that step: the primary login's when the policy asks for no factor, otherwise the one of the factor that completed it. A failureHandler is called for failures of its own step. Each is called for its own flow and step only. CONTEXA writes the response afterwards when the handler did not.
  • For MFA results see MFA result handling.
