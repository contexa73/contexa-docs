Connecting Human Approval (Implementing ApprovalService)

For when you add your own flow that gets a person's approval before a response tool runs. It covers the methods you must fill in, where the OSS calls this service, the approval data types, notification hooks and the storage tables.

The OSS has no ApprovalService implementation. Creating approval requests, notifying approvers, and waiting for approval before resuming a response all need your own implementation or the enterprise SOAR module. Several default methods of the interface throw UnsupportedOperationException.

The human approval that works in the OSS today: unblocking

The human approval that actually works in the OSS is not SOAR but an administrator unblocking a user. When an administrator releases a blocked user in the admin console, Contexa records and learns from that decision.

  • The user's behavioral baseline learns from the facts of the blocked request.
  • The administrator override is written to the audit log.
  • If the decision feedback and threat outcome channels of the Contexa SaaS connection are on, those results are sent (Contexa SaaS connection, off by default).

The block and unblock flows are in Request-time enforcement and Admin console.

Where the OSS calls this service

The bean is injected optionally (@Autowired(required = false)), so one ApprovalService bean in your application is what Layer 2 receives. In practice your service serves your own SOAR flow (SOAR extension points) rather than this call.

Approval data

ApprovalRequest

A serializable value object in io.contexa.contexacore.domain. Main fields:

FieldMeaning
requestIdRequest ID. Made by create(...): APR-<current millis> (for example APR-1709942400000)
sessionId, incidentId, organizationIdSession, incident, organization
toolName, actionType, parameters, reason, potentialImpactWhat is to be done and why
approvalType, statusApproval type and status (table below)
requestedAt, requestedBy, approvedAt, approvedBy, rejectionReasonRequest and handling record
requiredRolesRoles that may approve
requiredApproversNumber of approvers needed. No OSS code reads this value
approvalTimeoutApproval time limit (minutes). The same value as getTimeoutMinutes() and the builder's timeoutMinutes(...)
metadataOther values (the builder's toolDescription and riskAssessment go here)

The methods that change the status do not check the current status; they only set values.

  • approve(approver): APPROVED, records who and when. reject(approver, reason): REJECTED with the reason.
  • expire(), cancel(): EXPIRED, CANCELLED, even when the request is not pending.
  • addApproval(approver, name, role, comments): stores neither name, role nor comments and becomes APPROVED on the first call. It does not count several approvers' approvals; count multi-approval in your implementation.
  • isAutoApprovable(): true when the approval type is AUTO.
// Static factory: requestId = "APR-<millis>", status = PENDING, requestedAt = now
ApprovalRequest request = ApprovalRequest.create(
        "session-123", "session_termination", Map.of("userId", "alice"), "Repeated unblock MFA failures");

// Builder: build() sets requestedAt to now and requiredRoles to an empty set.
// The builder leaves status empty unless you set it, so set it yourself.
ApprovalRequest built = ApprovalRequest.builder()
        .requestId("APR-" + System.currentTimeMillis())
        .sessionId("session-123")
        .toolName("session_termination")
        .toolParameters(Map.of("userId", "alice"))
        .approvalType(ApprovalRequest.ApprovalType.MANUAL)
        .status(ApprovalRequest.ApprovalStatus.PENDING)
        .requestReason("Repeated unblock MFA failures")
        .timeoutMinutes(30)
        .build();

Approval type ApprovalType and status ApprovalStatus

EnumValues (descriptions in code)
ApprovalRequest.ApprovalTypeAUTO (Auto Approval), MANUAL (Manual Approval Required), SINGLE (Single Approval), MULTI (Multi Approval Required), UNANIMOUS (Unanimous), EMERGENCY (Emergency Approval)
ApprovalRequest.ApprovalStatusPENDING, APPROVED, REJECTED, EXPIRED, CANCELLED

The OSS has no code that handles each type differently (multi or unanimous counting, an emergency procedure). Use the type as a marker your implementation uses to choose how to handle a request. Which type an @SoarTool approval requirement becomes is in @SoarTool and Tool Approval Levels.

ApprovalRequestDetails

A serializable record (io.contexa.contexacore.soar.approval) passed to requestApproval(SoarContext, ApprovalRequestDetails). Fields: actionName, actionType, riskLevel, description, arguments (a string), parameters (a map).

ApprovalRequestDetails details = new ApprovalRequestDetails(
        "session_termination",            // actionName
        "CONTAINMENT",                    // actionType
        "HIGH",                           // riskLevel
        "Terminate every session of alice",
        "userId=alice",                   // arguments
        Map.of("userId", "alice"));       // parameters

String approvalId = approvalService.requestApproval(soarContext, details);   // the bean you implemented

Receiving notices: SoarApprovalNotifier

An interface in io.contexa.contexacore.autonomous.notification with two methods: receiveApprovalNotification(String message) and sendApprovalReminder(String approvalId). The OSS has no implementation.

  • In distributed mode (contexa.infrastructure.mode=distributed), when the Redis configuration is on (with the Redisson library and a Redis connection) and this bean exists, messages on the Redis channel soar:approval:requests go to receiveApprovalNotification.
  • No OSS code sends to this channel. The sender (publishing when an approval request is made) and mail or messenger notices are yours to write.
  • No OSS code calls sendApprovalReminder either.

Storage

The OSS schema creates 6 approval tables (soar_approval_policies, soar_approval_requests, soar_approval_steps, soar_approval_assignments, soar_approval_votes, approval_notifications) and includes entities (ApprovalPolicyEntity, SoarApprovalRequest, SoarApprovalStep, SoarApprovalAssignment, SoarApprovalVote, ApprovalNotification) and repositories. But no OSS code writes or reads these tables (the only repository registered as a bean is ApprovalPolicyRepository, and nothing uses it). To keep approval records in the database, wire the repositories in your implementation.

A minimal implementation

The smallest implementation, keeping approval requests in memory. A real one adds storage (database) and approver notices.

import io.contexa.contexacore.domain.ApprovalRequest;
import io.contexa.contexacore.domain.SoarContext;
import io.contexa.contexacore.soar.approval.ApprovalRequestDetails;
import io.contexa.contexacore.soar.approval.ApprovalService;
import org.springframework.stereotype.Service;

import java.util.Map;
import java.util.Set;
import java.util.UUID;
import java.util.concurrent.ConcurrentHashMap;
import java.util.stream.Collectors;

@Service
public class InMemoryApprovalService implements ApprovalService {

    private final Map<String, ApprovalRequest> requests = new ConcurrentHashMap<>();

    @Override
    public String requestApproval(SoarContext soarContext, ApprovalRequestDetails details) {
        String approvalId = "APR-" + UUID.randomUUID();
        ApprovalRequest request = ApprovalRequest.builder()
                .requestId(approvalId)
                .sessionId(soarContext.getSessionId())
                .toolName(details.actionName())
                .actionDescription(details.description())
                .toolParameters(details.parameters() != null ? details.parameters() : Map.of())
                .status(ApprovalRequest.ApprovalStatus.PENDING)
                .build();
        requests.put(approvalId, request);
        // Notify the approvers here (mail, messenger).
        return approvalId;
    }

    @Override
    public ApprovalRequest.ApprovalStatus getApprovalStatus(String approvalId) {
        ApprovalRequest request = requests.get(approvalId);
        return request != null ? request.getStatus() : null;
    }

    @Override
    public void handleApprovalResponse(String approvalId, boolean isApproved, String comment, String reviewer) {
        ApprovalRequest request = requests.get(approvalId);
        if (request == null || request.getStatus() != ApprovalRequest.ApprovalStatus.PENDING) {
            return;   // ApprovalRequest does not check the status, so stop here.
        }
        if (isApproved) {
            request.approve(reviewer);
        } else {
            request.reject(reviewer, comment);
        }
    }

    @Override
    public Set<String> getPendingApprovalIds() {
        return requests.values().stream()
                .filter(r -> r.getStatus() == ApprovalRequest.ApprovalStatus.PENDING)
                .map(ApprovalRequest::getRequestId)
                .collect(Collectors.toSet());
    }

    @Override
    public int getPendingCount() {
        return getPendingApprovalIds().size();
    }

    @Override
    public ApprovalRequest getApprovalRequest(String approvalId) {
        return requests.get(approvalId);
    }
}
