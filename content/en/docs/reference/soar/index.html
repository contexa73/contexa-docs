SOAR Extension Points: What the OSS Has and What You Build

The interfaces, data types and hooks the OSS contains for SOAR (security orchestration, automation and response). Learn what is already there, what you build yourself or fill with the enterprise module, and where the OSS calls these hooks.

The OSS has no SOAR execution or approval implementation. With the OSS modules alone, no automated response such as running a tool happens, and no flow pauses a response for human approval and resumes it. These features need the enterprise SOAR module. Contexa's startup diagnostics also treat them as an enterprise capability (ENTERPRISE_SOAR) and advise to "enable enterprise mode and include the enterprise SOAR module on the runtime classpath". What the OSS provides are interfaces, an annotation and data types (and empty database tables), which you can also implement and plug in yourself.

What is there and what is not

The startup diagnostics count enterprise SOAR as on when contexa.enterprise.enabled=true and the enterprise module has registered the SOAR context bean (soarContextRetriever). How the enterprise module works is outside this documentation.

Where the hooks are called

These are all the places where OSS code calls a SOAR hook. The "In the OSS today" column is what actually happens with the OSS modules alone.

HookWhere and when the OSS calls itIn the OSS today
Layer 2 playbook recordWith contexa.security.tiered.layer2.enable-soar=true, when the Layer 2 decision is BLOCKNo code fills the decision's playbook value (soarPlaybook), so it returns at once. Even with a value, all it does is leave a list of BLOCK_IP, INVESTIGATE_IOC and NOTIFY_SOC descriptions in the data store; nothing is actually blocked or notified.
ApprovalService beanIf the Layer 2 decision carries the "approval required" flag and the bean exists, it requests a SOAR_CRITICAL_RESPONSE approvalThe flag is set only on Layer 2's technical-failure fallback decision, which returns before this call, so it is never reached. Even when it requests, it does not wait for the result (details).
A PipelineStep bean named pipelineSoarToolExecutionStepIn the general AI pipeline, when the request context is a SoarContext, this step runs instead of the LLM execution stepThe OSS has neither this bean nor a SoarLab implementation, so it does not happen.
SoarApprovalNotifier beanWhen the distributed-mode Redis configuration is on, messages on the Redis channel soar:approval:requests go to this beanNo OSS code sends to this channel (details).
SecurityActionEvent receiverPublished when a blocked user fails the unblock MFAIt is published. The receiver is yours to write (example below).
RiskAssessment bean (tool approval level)Registered as a beanNothing injects it (@SoarTool and Tool Approval Levels).

Data types

Request and context

TypeWhat it holdsGood to know
SoarLab
(io.contexa.contexacore.soar)		One interface: Mono<?> processAsync(SoarRequest request). Analysis, tool choice, approval and execution are up to the implementer.Extends no other interface (separate from the general AI Lab interface). No OSS implementation.

Creating one without templateType or diagnosisType throws.
SoarContextExtends DomainContext. Incident (incidentId, threatType, severity, description, affectedAssets, currentStatus, organizationId), progress (sessionState, executionMode, threatLevel, riskScore, conversationHistory), approval (approvalRequests, approvedTools, humanApprovalNeeded)A value holder that changes no state by itself. riskScore is a Double (may be empty), executionMode defaults to AUTO, and nothing reads emergencyMode.
SoarResponseExtends AIResponse. Analysis result, session state, executed tools, recommendations, summary, incident ID, threat level—

The SoarContext methods only change values: transitionTo(state) sets sessionState (no checks), approveTool(name) adds the name to the approved tool set, and addToolExecutionResult(name, result) puts it into the context's extracted value map as tool_result_<name> (not an audit record). The threatLevel values are CRITICAL, HIGH, MEDIUM, LOW, INFO, UNKNOWN.

SoarContext context = new SoarContext();
context.setIncidentId("INC-2024-001");
context.setThreatLevel(SoarContext.ThreatLevel.HIGH);

SoarRequest request = SoarRequest.builder()
        .context(context)
        .templateType(new TemplateType("SOAR"))
        .diagnosisType(new DiagnosisType("SOAR"))
        .incidentId("INC-2024-001")
        .threatType("UNAUTHORIZED_ACCESS")
        .description("Unusual export from the finance report API")
        .metadata(new HashMap<>(Map.of("incidentId", "INC-2024-001")))   // where getIncidentId() reads
        .build();

The OSS schema creates 7 SOAR tables (ctxa_soar_incidents, ctxa_soar_approval_policies, ctxa_soar_approval_requests, ctxa_soar_approval_steps, ctxa_soar_approval_assignments, ctxa_soar_approval_votes, ctxa_approval_notifications), and entities and repositories exist, but no OSS code writes or reads these tables.

If you build it yourself

  1. Running responses: implement SoarLab; to run tools through the general AI pipeline, provide a PipelineStep bean named pipelineSoarToolExecutionStep.
  2. Tool approval levels: put @SoarTool on your tools and grade them with RiskAssessment (@SoarTool and Tool Approval Levels).
  3. Human approval: implement ApprovalService (Connecting Human Approval).
  4. Automated response for blocked users: receive the SecurityActionEvent the OSS already publishes and run your application's response.
import io.contexa.contexacommon.soar.event.SecurityActionEvent;
import org.springframework.context.event.EventListener;
import org.springframework.stereotype.Component;

@Component
public class SecurityActionListener {

    @EventListener
    public void onSecurityAction(SecurityActionEvent event) {
        if (event.getActionType() == SecurityActionEvent.ActionType.SOAR_AUTO_RESPONSE) {
            // Run your application's response here (end sessions, notify the owner, ...).
            // event.getUserId(), event.getSourceIp() and event.getMetadata() are available.
        }
    }
}
