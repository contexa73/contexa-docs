@SoarTool and Tool Approval Levels

@SoarTool is the annotation that attaches a name, an approval requirement and execution limits to a response tool the AI calls. This page covers what each attribute means, the rules that set the approval level, where it must go to be read, and how to apply the other attributes yourself.

The OSS reads one attribute: approval. It is read only on a class that implements Spring AI's ToolCallback, at class level, and no OSS code injects the evaluator that reads it (RiskAssessment). The OSS has no code that finds, registers or runs tools carrying @SoarTool either. The other attributes take effect only through your own implementation or the enterprise SOAR module (SOAR extension points).

The rules that set the approval level

ApprovalRequirement and ApprovalType

The annotation states an approval requirement (SoarTool.ApprovalRequirement, 5 values), and the evaluator turns it into an approval type (ApprovalRequest.ApprovalType, 6 values). Only MANUAL and MULTI count as needing approval (requiresApproval is true).

ApprovalRequirementBecomes ApprovalTypeApproval needed
NONEAUTONo
AUTO (default)AUTONo
NOTIFICATIONSINGLENo
REQUIREDMANUALYes
MULTI_APPROVALMULTIYes

This table only maps levels. The OSS has no code that sends a notice, waits and then proceeds, or counts the approvals of several approvers.

The evaluator RiskAssessment

EvaluationRule
AnnotationThe @SoarTool(approval) of the ToolCallback implementation class, mapped as above. AUTO when absent; MANUAL when reading fails (the safe side)
Tool nameA value set with setToolApprovalType(name, type) wins. Otherwise the lower-cased name is checked in order: one of system, kernel, root, admin, production, critical together with a risk word gives MULTI → a risk word (delete, remove, kill, terminate, shutdown, destroy, format, wipe, purge, quarantine, isolate) gives MANUAL → scan, analysis or detect gives SINGLE → read, list, get or view gives AUTO → anything else gives SINGLE
ContextMANUAL if productionEnvironment is true, target contains production or critical, or userId is admin. Otherwise (also with no context) AUTO
Time of daySINGLE after 22:00 or before 06:00 server local time, otherwise AUTO

RiskAssessment is registered as a bean and can be replaced with a bean of the same type (@ConditionalOnMissingBean), but no OSS code injects and uses it. In your own execution flow, inject it and call assess(...) or assessWithDetails(...) (level, whether approval is needed, evaluation factors).

Where it must go to be read

The evaluator reads only the class-level @SoarTool of the tool object's class. So put it on a class that implements ToolCallback, as below. A value on a method, or on a service bean class of your application, is not read (and no code merges class and method values).

import io.contexa.contexacommon.annotation.SoarTool;
import org.springframework.ai.tool.ToolCallback;
import org.springframework.ai.tool.definition.ToolDefinition;

@SoarTool(name = "session_termination",
          description = "Terminates every session of the given user",
          approval = SoarTool.ApprovalRequirement.REQUIRED)
public class SessionTerminationTool implements ToolCallback {

    private final ToolDefinition definition = ToolDefinition.builder()
            .name("session_termination")
            .description("Terminates every session of the given user")
            .inputSchema("{\"type\":\"object\",\"properties\":{\"userId\":{\"type\":\"string\"}}}")
            .build();

    @Override
    public ToolDefinition getToolDefinition() {
        return definition;
    }

    @Override
    public String call(String toolInput) {
        // Your application implements the actual session termination.
        return "{\"terminated\":true}";
    }
}
ApprovalRequest.ApprovalType type = riskAssessment.assess(
        new SessionTerminationTool(), Map.of("target", "production-db"));
// annotation REQUIRED → MANUAL, context target contains production → MANUAL
// result MANUAL, riskAssessment.requiresApproval(type) == true
