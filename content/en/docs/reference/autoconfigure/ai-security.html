Turning Contexa On and Choosing a Security Mode

How to turn Contexa on with @EnableAISecurity, choose whether your application keeps owning login (SANDBOX) or hands it to Contexa (FULL), and check that it is on.

At a glance

The security mode decides who owns login. Whether decisions are actually enforced is decided separately by the enforcement mode.

Before you start

  1. One starter: ai.ctxa:spring-boot-starter-contexa. It brings the OAuth2 resource server, client and authorization server libraries. It does not bring Spring Security or an AI model provider starter: your application declares org.springframework.boot:spring-boot-starter-security itself, and without it @EnableAISecurity refuses to start.
  2. A dedicated Contexa database: contexa.datasource.url is required. If it is empty, startup stops with an IllegalStateException. The same URL as the application database is refused by default.
  3. AI for the decision engine: your application adds a Spring AI chat model provider, an embedding model provider and a vector store (PgVector). If one is missing, the startup diagnostics tell you (Connecting AI models).
  4. Spring Boot 3.x: the build baseline is 3.5.4. Contexa does not start on 4.x.
contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: contexa

Turning it on

@SpringBootApplication
@EnableAISecurity                      // mode = SecurityMode.SANDBOX (default)
public class LegacyApplication {
    public static void main(String[] args) {
        SpringApplication.run(LegacyApplication.class, args);
    }
}

Three modes with similar names

The three modes decide different things. The security mode and the enforcement mode are both named SecurityMode in code, which makes them easy to confuse (telling the packages apart).

In the enforcement mode, DISABLED and OBSERVE do not analyze, SHADOW makes decisions but neither stores nor applies them, and ENFORCE stores them and applies them from the next request. The order for a first rollout is in Starting Safely with Enforcement Modes.

If you choose SANDBOX (your application owns login)

What your application does

  1. Declare your own SecurityFilterChain. In this mode Contexa builds neither an authentication chain nor a placeholder chain. Without an application chain Spring Boot's default security applies (every request needs authentication), and Contexa reports it with a WARN log at startup. With no users of the application either, the start is refused. An application that did not use Spring Security declares spring-boot-starter-security and a chain that keeps its existing rules (for example anyRequest().permitAll()).
  2. Put the signed-in user in the SecurityContext as an authenticated Authentication. The authentication bridge makes decision facts only when such an Authentication exists, and @Protectable refuses the call without one. An application with its own login puts it there from a filter in its chain (Connecting Your Existing Login).
  3. Nothing to do for the admin console. Contexa protects /contexa/admin/** with a chain of its own and Contexa's administrator sign-in (Admin console). Method security is optional: Contexa does not register @EnableMethodSecurity in this mode, and when your application turns it on, the @PreAuthorize rules on the admin controllers add a check.

If you choose FULL (Contexa owns login)

When your application declares no PlatformConfig bean, Contexa builds the security chain from this default configuration.

  • Access rules: /contexa/css/**, /contexa/js/**, /images/** and /favicon.ico are allowed; every other request is decided by the dynamic authorization manager (CustomDynamicAuthorizationManager, the policies in the admin console) (Dynamic authorization).
  • Login: an MFA flow with form login (then /) as the primary step and passkey or one-time token (OTT) as the second factor (one factor required), with session state.
  • Enforcing decisions: a decision is made after the request finishes and is stored when the enforcement mode is ENFORCE. The request-time filters in the chain apply the stored decision to the next request (Request-time enforcement).
  • Also turned on: @PreAuthorize handling for Contexa's own classes only (Contexa's expression handler; @EnableMethodSecurity is not turned on for the whole application), the Contexa OAuth2 authorization server, the authentication success and failure handlers. The agent request gate runs here inside Contexa's chain.
FULL can change your application's default DataSource. When your application has no database of its own (spring.datasource.url is not set, or names the same database as contexa.datasource.url), this mode puts contexa.datasource.isolation.contexa-owned-application=true; when it names a database of its own, the flag stays false and your connection is kept. A value you set yourself always stands. With the flag true, if your application does not create a DataSource bean itself, the application's default dataSource, JdbcTemplate and TransactionTemplate point at the Contexa database, and the startup diagnostics default (AUTO) becomes FAIL_FAST, which stops startup when a required capability is missing. Use SANDBOX when you add Contexa to an existing application.

To use your own authentication configuration instead of the default, declare a PlatformConfig bean (Identity DSL). It becomes a chain only under CONTEXA_OWNED.

No SANDBOX-shaped chain

Under SANDBOX the ownership is always HOST_OWNED: a contexa.bridge.ownership=CONTEXA_OWNED beside it stops the start. There Contexa builds no chain from a PlatformConfig, the default one or yours. Its only chain is the console chain for /contexa/admin/**, with Contexa's administrator sign-in and the ADMIN role (What works under each ownership).

Legacy authentication object hints

For applications that keep a user object in the session or a request attribute outside Spring Security. The authentication stamp is made first from the Authentication in the SecurityContext; then the three channels, session, request attributes and headers, are tried in turn. The three attributes below affect only these three channels (Reading order).

AttributeDefaultWhat it changes
authObjectLocationAUTOOnly the order in which the three channels are tried. It turns no channel off.
AUTO, SESSION: session → request attributes → headers
REQUEST_ATTRIBUTE: request attributes → session → headers
HEADER: headers → session → request attributes
authObjectAttribute""The name of the attribute holding the user object. Used as the session attribute name when the location is SESSION and as the request attribute name when it is REQUEST_ATTRIBUTE. Not used with AUTO or HEADER.
authObjectTypeObject.class (none)The class of the user object. Candidates whose class name matches get a higher score (others are not filtered out). Applies to both the session and request attribute channels.
 
@SpringBootApplication
@EnableAISecurity(
        authObjectLocation = AuthObjectLocation.SESSION,
        authObjectAttribute = "loginUser",
        authObjectType = LoginUser.class)     // LoginUser: the user class your application keeps in the session
public class LegacyApplication { }

The header channel reads X-Contexa-* headers and is off by default (contexa.bridge.authentication.headers.enabled=false). Even when on, it accepts a request only if it comes from a trusted proxy and the user in the header is the user your application authenticated (Passing users through gateway headers). The session, request attributes and headers are also where authorization (the authorization stamp) and delegation information are read; the three attributes above do not affect those reads.

Checking that it is on

  • Startup log
    • Skipping Contexa-owned authentication chain bootstrap in HOST_OWNED mode (INFO) under HOST_OWNED: Contexa built no sign-in chain.
    • [Contexa] HOST_OWNED mode: no SecurityFilterChain is declared by the application ... (WARN): there is no application chain, so Spring Boot's default security is on. Declare your chain; the anyRequest().permitAll() the log suggests is safe for Contexa's paths, because the admin console is protected by Contexa's own chain.
    • [Contexa] HOST_OWNED: the application sets the signed-in user after Spring Security's filters ... (WARN, once): requests whose user is set in an MVC interceptor or a controller are enforced only at @Protectable methods.
    • Contexa owns the sign-in of this application, but the application declares its own security chain(s) [...] ... (start refused): use SANDBOX to keep the application's sign-in, or remove those chains.
    • [Contexa] CONTEXA_OWNED: the application declares the user store(s) [...], which Contexa's sign-in does not read: ... (WARN): Contexa's sign-in does not read the application's user stores, however many there are; Contexa's own accounts, the seeded administrator among them, sign in from Contexa's own user store, and the application's users do not sign in to Contexa.
    • [Contexa] A one-time-code factor is offered but no mail sender is configured (spring.mail.*) ... (WARN): no code can be delivered; configure mail, or users verify with a passkey only.
    • [ContexaCapability] ... (ERROR): the startup diagnostics found a missing bean (Startup diagnostics).
  • Admin console system settings (/contexa/admin/system-settings, ADMIN role): see and change the current enforcement mode. A value saved here applies without a restart and takes precedence over the YAML value.
  • Actuator: if present, the endpoint contexacapabilities shows the startup diagnostics.

Set the first four keys with the annotation attributes. The annotation puts these keys as a property source with the highest precedence, but when you wrote the same key in your application settings (YAML and so on), it puts that value as it is. The annotation attributes are the defaults for what you did not write. So writing contexa.ai.security.mode: FULL makes Contexa run as FULL even when the annotation says SANDBOX. And writing contexa.ai.security.mode in YAML alone does not turn Contexa on without the annotation, because the "on" marker is the property source the annotation puts. These keys are not in the configuration metadata either.
