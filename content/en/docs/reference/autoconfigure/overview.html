Auto-configuration: What Turns On and How to Turn It Off

What Contexa turns on and leaves out when your application starts. Check whether Contexa is on, and find how to turn a feature off or replace a default bean with your own.

At a glance: startup order

The defaults outside contexa.* (the Spring AI model selection spring.ai.model.chat · spring.ai.model.embedding) are visible only while Contexa is on, and pick the provider when one chat or embedding provider is named. A value for the same key in your application settings wins. The vector table name, dimension and creating the table at first start (initialize-schema) default under contexa.vectorstore.pgvector.* and apply to Contexa's store only.

Is Contexa on or off

StateWhat happens
Starter only (no @EnableAISecurity)All 81 Contexa auto-configurations are left out. The one exception, the auto-configuration that makes the Contexa database the application's default DataSource, stays only when both contexa.datasource.url and contexa.datasource.isolation.contexa-owned-application=true are set. Spring Boot's DataSource and JPA auto-configurations stay only when spring.datasource.url is set or an embedded database is on the classpath. Other auto-configurations are untouched.
@EnableAISecurity presentOn. The auto-configurations below turn on by their own conditions.
contexa.enabled is falseEven with the annotation, nothing is imported and no "on" marker is put, so it is the same as the starter only.
contexa.autonomous.enabled is not trueThe decision engine is what all of Contexa reads, so all of Contexa goes off. When the application owns sign-in (HOST_OWNED), one ERROR line is logged and the application starts without Contexa; when Contexa owns sign-in (CONTEXA_OWNED), the start is refused with the reason. To turn off only the decisions, use contexa.security.zerotrust.mode: DISABLED.
Contexa's database cannot be reached, or the single Redis server of distributed mode cannot (HOST_OWNED)One ERROR line is logged and the application starts without Contexa. Restart it once the store is back. Under CONTEXA_OWNED this check is not made and the start fails as it always did.
Spring Security is not on the classpath · the application is set to be reactive · distributed mode without the Redis classes · Spring Boot 4.xThe start is refused, with the reason and what to do.
The starter does not bring Spring Security. Spring Boot secures an application when Spring Security's configuration module is on the classpath, so it is left out on purpose and the build checks it: adding the starter alone changes nothing. To use @EnableAISecurity, your application adds spring-boot-starter-security, and if it declares no SecurityFilterChain of its own, Spring Boot's default security (every request needs authentication) applies. Declare your chain (What your application does).

Auto-configurations by area (81)

Everything in the four registration files (contexa-autoconfigure 76, contexa-common 2, contexa-core 1, contexa-identity 2). All of them stay only while Contexa is on, and then the "Condition" below applies. "Condition" is the class-level condition; individual beans have more. Setting the "Turn-off key" to false leaves that auto-configuration out (unset means on). AiSecurityConfiguration, which @EnableAISecurity imports, is outside this list.

Checking the startup diagnostics

When startup finishes, Contexa checks for each capability that the beans it needs were created. It is not a switch that turns features on; it reports what is missing or stops startup.

contexa.capability.modeWhat it does
AUTO (default)FAIL_FAST for a Contexa-owned application, WARN otherwise. A Contexa-owned application has contexa.datasource.isolation.contexa-owned-application=true or a spring.application.name starting with contexa-.
WARNReports problems of required capabilities as ERROR logs and keeps starting.
FAIL_FASTStops startup with an IllegalStateException when a required capability is missing or failed.
STRICTStops like FAIL_FAST, and also logs problems of capabilities that are not required.
OFFNo checks.
  • Six capabilities are checked: LLM_RUNTIME (chat model), EMBEDDING_RUNTIME (embedding model), RAG_VECTOR (vector store), SECURITY_LEARNING (learning), AUTONOMOUS_DECISION (decision engine), BRIDGE (authentication bridge). Whether each is on and required depends on the environment; override it with contexa.capability.required.<capability> (for example rag-vector).
  • Four enterprise capabilities (PQA_ENGINE, ENTERPRISE_SOAR, ENTERPRISE_MCP, ENTERPRISE_DASHBOARD) have names and on-rules only; the OSS has no checker for them. SOAR, for example, is on only with contexa.enterprise.enabled=true and the enterprise SOAR module (SOAR extension points).
  • Log: a problem shows as an ERROR line [ContexaCapability] <capability> .... A CapabilityContributor bean in your application runs its checks as well.
  • Actuator: the endpoint contexacapabilities shows the effective mode and the problem list. Whether it is exposed on the web follows Spring Boot Actuator's exposure settings.
  • Ownership checks (OwnershipStartupDiagnostics, independent of contexa.capability.mode): under CONTEXA_OWNED the start is refused when the application's own chains are never reached because Contexa's chain takes every request first, and a WARN when the application's UserDetailsService answers Contexa's sign-in (the seeded administrator then signs in only if that store has the account); in both ownerships a WARN when a one-time-code factor is offered but no mail sender is configured (spring.mail.*).
SettingDefaultMeaningWhen to change it
contexa.capability.modeAUTOTable aboveFAIL_FAST to stop a deployment with missing beans, WARN for logs only
contexa.capability.requiredEmptyPer-capability override of "required" (keys: llm-runtime, embedding-runtime, rag-vector, security-learning, autonomous-decision, bridge, ...)To drop a capability you do not use from "required", or to require one that must be there
contexa.capability.expose-diagnostics-endpointtrueRegisters the Actuator endpoint beanfalse when you do not want the diagnostics endpoint

Other startup logs: standalone mode logs one WARN that learned state is in memory (not when you provide the learning store beans). An old setting name is not read and leaves no log (the new names are in the configuration guide).

Replacing beans

When the application declares a bean of the same type (or the same name), the Contexa default steps aside.

Bean the application declaresWhen to use it
PlatformConfigTo use your own authentication configuration instead of the security mode's default (it becomes a chain only under CONTEXA_OWNED, Identity DSL)
ZeroTrustActionRepository, BaselineDataStore, SecurityContextDataStore, ProtectableRapidReentryRepositoryTo keep decisions, baselines, context or re-entry records elsewhere. Standalone mode can then persist them, and providing the learning stores removes the standalone WARN.
SecurityEventCollector, SecurityEventPublisher, BlockingSignalBroadcasterTo carry events and block signals over another transport
