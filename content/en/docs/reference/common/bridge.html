Connecting Your Existing Login (Authentication Bridge)

How CONTEXA takes, on every request, the login information your application already has, and uses it as facts of a decision. Your application hands CONTEXA one value, the request's user ContexaSubject: a user ID and an email are required, everything else is optional. It covers what an application with Spring Security and one without it each do, the order in which CONTEXA reads, how to tell it about MFA, the optional API (ContexaBridge, ContexaUsers), the outcomes and the extension points.

Terms on this page. ContexaSubject is the user of a request as your application tells CONTEXA. A user ID and an email are required; a display name, organization, tenant, authorities, login method, session key and delegation are optional. The identity is what CONTEXA found when it checked the user of a request: that user, its source (where it was read) and the outcome. A resolver (ContexaSubjectResolver) is a bean with which an application that does not use Spring Security takes the user of a request from its own login state. A trusted proxy is a server, a load balancer or an API gateway for example, whose X-Forwarded-For header carrying the client IP may be believed. The user copy is a row, kept in the CONTEXA database's user table, of a user who logged in through your application. The security mode (SANDBOX, FULL) and the authentication ownership (HOST_OWNED, CONTEXA_OWNED) are explained in Common Contracts.

Overview

When CONTEXA is on in its default mode (@EnableAISecurity, SANDBOX: your application keeps its sign-in), your application keeps handling login the way it always did (Spring Security, or its own session or token). On every request CONTEXA takes the request's user as a ContexaSubject through the authentication bridge (BridgeResolutionFilter), makes the identity, and puts the login method, MFA, authorities and delegation in the decision prompt as facts.

What the application must do

Your application hands CONTEXA one value, the request's user ContexaSubject (The value you hand over). How it hands it over depends on whether it signs users in with Spring Security.

  1. Tell it who is logged in. An application that uses Spring Security has nothing more to do (An application that uses Spring Security). One that does not hands the user over through a resolver or a request attribute (Resolver, Request attribute). A protected method (@Protectable) called in a request whose user could not be found (no identity) is refused in the SHADOW and ENFORCE modes (ENFORCE is the default); under DISABLED (the old name OBSERVE included) it is not refused.
  2. Tell it the email. Step-up codes are mailed to this address. Without an email the identity still stands, but no step-up code can be mailed to that user.
  3. Tell it about MFA and the login method (optional). With OAuth2 or OIDC tokens the standard claims (amr, acr, auth_time) are enough. Without standard claims, as with form login, put a ContexaAuthentication in the Authentication's details or set the request attributes ctxa.context.authenticationType and ctxa.context.mfaVerified. An application that hands the user over through a resolver or a request attribute puts a ContexaAuthentication in the ContexaSubject (Telling it about MFA).
  4. Authorities and delegation are optional. For an application that uses Spring Security, the Authentication's authorities and the access token's delegation claims are read as they are. An application that hands the user over through a resolver or a request attribute puts them in the ContexaSubject's authorities and delegation. CONTEXA does not interpret what the authorities mean; it shows them to the decision as reference facts.
  5. The Spring Security chain. With users of your own (a UserDetailsService and the like) but no chain, Spring Boot's default security (every request authenticated) applies, and CONTEXA logs a warning at startup to tell you. With neither a chain nor users of your own, CONTEXA puts an isolation chain that lets every request through in place of Spring Boot's default security, so access stays as it was before CONTEXA came.
An application that does not sign users in with Spring Security. @EnableAISecurity needs the Spring Security library, so your application declares the dependency (spring-boot-starter-security) itself. Beyond that it needs to declare no chain and fill no SecurityContext: tell CONTEXA the user your existing login verified through a resolver, or put it into a request attribute from your existing authentication filter. Under SANDBOX, with neither a chain nor users of your own, CONTEXA puts an isolation chain without filters, so your access rules stay as they are. Spring Security's standard firewall (StrictHttpFirewall), however, applies to every request whatever the chains, so a request whose path holds ;jsessionid= or //, for example, is refused with 400. To change that, use the Spring standard way (an HttpFirewall bean).

What the bridge does not do

  • In SANDBOX it does not interfere with the application's authentication, authorization or session. It saves nothing to the session and writes no headers.
  • It never decides who the user is by guessing at the fields of your application's own objects (a user object in the session, a principal of no standard kind). The user is read only from the ContexaSubject your application hands over and from Spring Security's standard kinds.
  • In either mode the bridge filter is registered as a servlet filter that runs after your security chain and all of your servlet filters have finished. CONTEXA's one servlet filter registration contexaFilterSlot is mapped with the servlet standard's "after every other filter mapping", so your filters all run first whatever order you give them, and the bridge is the first inside it (before CONTEXA's enforcement filters). CONTEXA's enforcement filters, controllers and @Protectable methods can read the identity, but URL authorization inside your chain runs before it exists. In FULL the filter also sits in CONTEXA's chain (after SecurityContextHolderFilter for session flows, after BearerTokenAuthenticationFilter for token flows); it runs once per request.
  • The exception: the user copy writes user rows to the CONTEXA database in SANDBOX as well.

Where and in which order it reads

CONTEXA tries the sources of contexa.bridge.identity-sources in turn, and the first source that names a user gives the request its identity. A source with no user for the request is skipped.

The value you hand over: ContexaSubject

The user a legacy application tells CONTEXA about (package io.contexa.contexacommon.security.bridge.subject). Building it never throws; a value that breaks a rule is reported in getProblems(). Leading and trailing blanks are stripped, and the case of the user ID is kept as given.

ContexaSubject subject = ContexaSubject.of(userId, email)
        .displayName(name)
        .authentication(ContexaAuthentication.of("PASSWORD+OTP").mfa(true).authenticatedAt(loginAt))
        .build();

userIdRequiredNot blank, at most 255 characters, no control characterThe request goes on as your application has it, without a CONTEXA identity (INVALID).
emailRequiredAn address (one @, no blank or control character), at most 255 charactersThe identity stands, marked as missing an email (EMAIL_MISSING, EMAIL_MALFORMED, EMAIL_TOO_LONG). No step-up code can be mailed.

The user ID becomes the key of decisions, blocks and the user copy, so always use the same value for one person (the login ID, for example). Decisions, the user copy and the step-up compare user IDs by the same rule (Unicode NFKC normalization, case ignored; contexa.security.zerotrust.normalize-user-keys=false turns it off).

An application that uses Spring Security

Your Spring Security keeps handling login, and CONTEXA reads the authenticated Authentication in the SecurityContext. The user ID is always Authentication.getName(); the email is looked for in the order of contexa.bridge.email-sources (by default the email claim, then the email provider bean).

Kind of loginUser IDEmail
Form, Basic, remember-me and the like (a UserDetails or text principal)getName()A BridgeUserEmailProvider bean
A resource server's JWT or opaque tokengetName() (sub by default for a JWT)The token's email claim, otherwise the email provider
OAuth2 or OIDC logingetName()The user attribute email, otherwise the email provider

When the login information carries no email, as a form login's UserDetails does not, declare one email provider bean. It is called on requests of users without an email, so it should answer quickly. A user handed over through a resolver or a request attribute without an email is asked about through the same bean.

@Bean
BridgeUserEmailProvider contexaEmailProvider(EmployeeRepository employees) {
    return userId -> employees.findEmailByLoginId(userId);
}

When the principal is an object of your own and none of Spring Security's standard kinds (UserDetails, Principal, text, an OAuth2 token or login and the like), CONTEXA does not read its fields, and the request goes on without an identity (UNSUPPORTED_PRINCIPAL). This problem is logged as [Contexa] Bridge: the signed-in Spring Security principal is of none of the kinds Spring Security names a user by ... (ERROR) at most once a minute (diagnostics). Map it yourself with a ContexaSubjectMapper bean then. An empty answer leaves the authentication to CONTEXA's reading of the standard kinds.

@Bean
ContexaSubjectMapper contexaSubjectMapper() {
    return authentication -> authentication.getPrincipal() instanceof MyLoginUser user
            ? Optional.of(ContexaSubject.of(user.getEmpNo(), user.getMail()).build())
            : Optional.empty();
}
  • Two mapper beans stop the start. A mapper that throws is caught by CONTEXA, and the request goes on without an identity (FAILED).
  • Under SANDBOX, when an interceptor or a controller signs the user in after the bridge filter, the user is read again when a @Protectable method is called (the resolver is not called again).

An application that does not use Spring Security: resolver

Your application implements ContexaSubjectResolver as one bean. The implementation takes the user of the request from your application's login state (a session object, the verification of its own token, the servlet container's user) and returns it.

@Component
class SessionLoginResolver implements ContexaSubjectResolver {

    @Override
    public Optional<ContexaSubject> resolve(ContexaRequestView request) {
        return request.sessionAttribute("loginVO", LoginVO.class)
                .map(vo -> ContexaSubject.of(vo.getLoginId(), vo.getEmail())
                        .displayName(vo.getName())
                        .build());
    }
}
  • When it is called: once per request, after every servlet filter of your application has run; the forwards, includes, asynchronous and error dispatches of that request reuse the first answer.
  • The request view ContexaRequestView is read-only. Use method(), path(), header(name), headers(name), cookie(name), attribute(name[, type]), sessionAttribute(name[, type]), sessionId(), remoteUser() and userPrincipal(). It never creates a session, and offers neither the body nor the parameters (this protects an application that reads a multipart or streamed body itself).
  • An empty answer is a request nobody signed in to. After your application signs the user out, simply answer empty. CONTEXA writes nothing to your application's session, so the identity never outlives your application's sign-in.
  • Failures and slowness: a resolver that throws is caught by CONTEXA, and the request goes on as your application has it, without an identity (FAILED). The time each call takes is measured and reported when it exceeds contexa.bridge.resolver.slow-threshold (100 ms by default, RESOLVER_SLOW); the call is never cut short.
  • Other ways of signing in: an application using servlet container authentication uses request.remoteUser(). An application behind a gateway returns only values that passed its own code verifying the gateway. CONTEXA never trusts a header by itself.
  • Paths that need no resolver call, static resources for example, are left out with contexa.bridge.resolver.exclude-paths (Ant patterns on the servlet path). Two resolver beans stop the start.

Handing the user over through a request attribute from your own filter

An application whose authentication filter already runs on every request may put the user into a request attribute from that filter instead. CONTEXA reads after every servlet filter of your application has run, so the order against CONTEXA needs no care. The code that puts it there must run after your application has verified the user.

request.setAttribute(ContexaSubject.REQUEST_ATTRIBUTE,
        ContexaSubject.of(user.getLoginId(), user.getEmail()).build());
  • The value must be a ContexaSubject. Anything else is not read and is reported as a problem (NOT_A_SUBJECT), and the request goes on without an identity (INVALID).
  • A client cannot set request attributes, so only your application's code decides this value.
  • Together with a resolver, the resolver comes first in the default order, and two different users are reported as SOURCES_DISAGREE (Where and in which order it reads).

Telling it about MFA and the login method

The login method, MFA, the authentication time and the assurance level are all optional; only what is stated reaches the decision as a fact. An application that uses Spring Security is read in this order.

  1. A ContexaAuthentication in the Authentication's details is used when present. It is how your application states these itself when there are no standard claims, as with form login.
  2. Otherwise the token's standard claims are read. The login method and MFA are derived from amr (RFC 8176), with the source marked DERIVED_FROM_AMR; auth_time is the authentication time and acr the assurance level.
  3. Without either, request attributes are read: the values your filter put into ctxa.context.authenticationType (the login method) and ctxa.context.mfaVerified (true or false).

The login facts the decision prompt carries are looked for in the Authentication's details and principal under set key names. When your application keeps MFA completion or the login method under another name, add that name to the key name settings.

amr valueLogin method
pwdPASSWORD
otp, sms, telONE_TIME_CODE
pop, hwk, swkPASSKEY
face, fpt, iris, retina, vbmBIOMETRIC
  • MFA rule: MFA is complete when amr holds mfa or two or more different methods. Example: ["pwd","otp"] → MFA complete, method PASSWORD+ONE_TIME_CODE. ["otp","sms"] → one method, so not MFA.
  • Authentication time is read from the ContexaAuthentication's authenticatedAt or the token's auth_time. The token issue time (iat) is deliberately not used because it changes when a token is reissued. An authentication time read from a Spring Security login that lies more than 60 seconds ahead of this server's clock is left out of the decision's input.
  • Assurance level is read from the ContexaAuthentication's assurance or the token's acr; it is not derived from amr.
  • An application that hands the user over through a resolver or a request attribute puts a ContexaAuthentication in the ContexaSubject's authentication. amr is not interpreted there, so state MFA directly with mfa(true), and only when two or more different factors were verified.

Optional API: telling it about sign-ins, sign-outs and leavers

Every call is optional. CONTEXA works without them; with them, an application that does not use Spring Security adds to the decisions the moments only it knows (a successful sign-in, a failed one, a sign-out). An application that signs in with Spring Security has nothing to call: CONTEXA listens to Spring Security's sign-in and sign-out events.

ContexaBridge.signedIn(request, ContexaSubject.of(user.getLoginId(), user.getEmail()).build());
ContexaBridge.signInFailed(request, loginId);
ContexaBridge.signedOut(request, user.getLoginId());
ContexaUsers.delete(user.getLoginId());

ContexaBridge.signedIn(request, subject)Where the sign-in succeeded, after your application changed the session IDMakes the user the identity of the request and waits for the user copy (a second at most), which it creates or updates with the sign-in time. Sends the sign-in to the decisions once.
ContexaBridge.signInFailed(request, userId)Where a sign-in failedCounts it as a failed sign-in of the user (the decisions' failure count).
ContexaBridge.signedOut(request, userId)Where the user signed outEnds the tracking of the request's session and lets go of what was kept for the sign-in. A block, a step-up or a review restriction stays.
ContexaUsers.delete(userId)The user left or was deleted (also outside a request)Deletes the user copy and every state kept for the user's decisions. The same user ID coming again is a new user. An administrator can delete the user in the admin console too.
  • No call throws; each reports through the outcome of a ContexaBridgeResult, and your application's request goes on whatever it is.
  • DONE: done. NOT_APPLICABLE: nothing to do, in a mode such as FULL where CONTEXA signs the users in and out itself (the three ContexaBridge calls). NOT_INITIALIZED: CONTEXA has not started or is not on in this application. INVALID: no request or no user, or a user ID that breaks its rules. FAILED: CONTEXA could not do it.
  • The result's reason is meant for your application's log; it never holds a user ID or an email.

Outcomes and the User bridge status screen

Every time CONTEXA checks the user of a request, it records one of four outcomes. None of them fails your application's request.

OutcomeMeaningThe request
RESOLVEDThe identity stands, marked as missing an email when there is noneCONTEXA decides for that user.
ABSENTA request nobody signed in toGoes on as your application has it, without a CONTEXA identity. A @Protectable method called in it is refused as described in What the application must do.
INVALIDThe user your application handed over breaks the standard (a user ID that breaks its rules, a principal CONTEXA does not read, a request attribute value that is no ContexaSubject)
FAILEDYour resolver or mapper threw

CONTEXA counts the outcomes, sources and problems (SubjectProblem) by kind, and logs each problem as an error at most once a minute (without the user ID or email). In the admin console, the sidebar's Zero Trust → User bridge status (/contexa/admin/zero-trust/bridge) shows the outcomes, the sources, the problems met with the recommended action, and the users whose copies are not merged. The numbers are counted on that server (node) since it started.

User copy: keeping the logged-in user in the CONTEXA database

The bridge keeps a copy row of a user who logged in through your application in the CONTEXA database's user table, so the admin console and policies can refer to that user. It works like this.

  • Key and password: The key is brg_ + SHA-256 (SUBJECT | organization (GLOBAL when none) | user ID). The user ID is taken by the same rule as decisions (NFKC normalization, case ignored). The source of the identity (Spring Security, a resolver, a request attribute) is not part of the key. The row has a random password and cannot be used to log in directly.
  • When it is written: Only when a value the copy keeps changes (the user ID and its sign-in source, the display name, the login method, the authorities, the email, organization, department and the rest). The request's IP, a renewed token and the request's authorization never write it, and the last sign-in time and IP are written only at a sign-in and when the copy is created. A request of the same user with the same values is answered from memory, without reading the CONTEXA database, for contexa.bridge.sync.min-refresh-interval-seconds (60 seconds by default). With a value of 0 or less nothing is remembered. CONTEXA's own accounts (the accounts the main chain signs in under FULL + CONTEXA_OWNED, the administrator of a console request) get no copy.
  • Email: It is the ContexaSubject's email for a user handed over through a resolver or a request attribute, and the email found in the authentication object (key names) for an application that uses Spring Security; without one, the email provider bean is asked. When your application gives none, the copy keeps a real address it already has, and none otherwise; no address is made up. Step-up codes are mailed to this address, so it follows a rule. The first real address your application shows is stored at once. When your application later shows a different address, the copy does not change at once: the new address waits. It replaces the address on record only after the user proves the address on record and then the waiting address, or an administrator enters an address. Anyone who holds a session can change the application's profile, and this keeps codes from going to someone else's address. Several copies may share an email and are still stored, but no step-up code is mailed to a copy whose email another user also has (only CONTEXA's own accounts must have unique emails).
  • Long values: A value from your application that is longer than its column (a department that is a long directory name, a phone number with an extension, a long avatar URL) is cut to the column, so one long value never fails the copy. An email longer than 255 characters is treated as missing. A user ID longer than 255 characters breaks the user ID rule and gets no copy (one error is logged).
  • A copy an administrator turned off is not turned on again by synchronization.
  • Turning it off: contexa.bridge.sync.enabled=false.

A key for one value uses the first value found, from the front of the list; a key that gathers several values (amr, roles, authorities, scopes) gathers them from both the details and the principal.
