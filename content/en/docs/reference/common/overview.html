Common Contracts: CONTEXA Types in Your Code

The CONTEXA annotations, decision values, mode enums and extension interfaces that you write in application code, in one place. Find the type for what you want to do, when to use it, and what actually happens with the OSS modules.

Terms on this page. A decision is what CONTEXA decides about one request (allow, step-up authentication, hold for review, block). The decision engine is the CONTEXA component that analyzes a request with an AI model and creates and stores the decision. A protected method is a method with @Protectable. The security mode, the authentication ownership and the operating mode have similar names but are different settings; below tells them apart.

Overview

All the types below live in the contexa-common module (only the operating mode enum is in contexa-core). The single starter (spring-boot-starter-contexa) brings them in.

Turning CONTEXA on: @EnableAISecurity

The switch you put on the main class (package io.contexa.contexacommon.annotation). It imports a selector (AiSecurityImportSelector, through @Import), and when Spring reads the configuration classes the selector loads the CONTEXA configuration. Without attributes the security mode is SANDBOX (your application owns login).

@EnableAISecurity
@SpringBootApplication
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}
  • It is the "on" marker. The annotation puts a bundle of setting keys (a property source), contexaAiSecurityAnnotation, into the Spring settings (Environment). CONTEXA counts itself on only while that bundle exists. Writing the same keys in your application settings (YAML and so on) does not turn it on. Without the annotation every CONTEXA auto-configuration is left out, even with the starter on the classpath.
  • A dedicated database is required. Startup is refused when contexa.datasource.url is empty. When the address is set but the database does not answer, an application in SANDBOX (it keeps its own sign-in) logs an ERROR and starts without CONTEXA, and an application in FULL (CONTEXA provides the sign-in) fails to start.
  • The other startup requirements (Spring Boot 3.x, a servlet web stack, Spring Security declared by the application, no AOT processing) and what happens when one is missing are in Turning CONTEXA On and Choosing a Security Mode.
  • The attribute (mode) and what happens when you turn it on are in Turning CONTEXA On and Choosing a Security Mode.

Choosing the methods to analyze and enforce: @Protectable

When a method with this annotation is called, CONTEXA receives the call first (AuthorizationManagerMethodInterceptor), evaluates the method authorization policies (ProtectableMethodAuthorizationManager), and the decision engine analyzes the call. This protected method is the unit a decision is made about.

  • Where it goes: a method or a class of a Spring bean. On a class it covers every method of the class. It does not have to be a controller. When the application starts, CONTEXA reads these methods, and when an administrator refreshes the resources they appear in the console's resource list (the ctxa_managed_resource table). A controller's methods are listed by their URL instead, so they are left out of that list.
  • Login is required in SHADOW and ENFORCE (ENFORCE is the default): a call made inside a request is refused when CONTEXA has no user to decide for. That user is the authenticated Authentication your application's Spring Security put into the SecurityContext; when there is none, or only an anonymous one, it is the user the authentication bridge found (named by your application's ContexaSubjectResolver bean or by the request attribute ctxa.subject, authentication bridge). With neither, the call is refused, and the reason is logged at ERROR as [Contexa] A @Protectable call (...) was refused: ..., at most once a minute. A call on a thread that holds neither a request nor a user (a scheduled job, or an asynchronous method that does not receive the security context) has no one to decide for, so it is not refused: it runs, and only the fact that it ran without a user is recorded. A thread that received the user is decided as a request is. Under DISABLED (the old name OBSERVE included) the call is not refused and goes on as the application made it.
  • Analysis runs only in the SHADOW and ENFORCE modes: under DISABLED only the authorization policies are evaluated; nothing is analyzed and no event is published.

An agent request with no decision on record is decided on the spot even on a default method (Agent security). How a decision is made is described in Decision Engine.

import io.contexa.contexacommon.annotation.Protectable;

import org.springframework.stereotype.Service;

@Service
public class ReportService {

    @Protectable(category = "REPORT", actions = {"EXPORT"},
                 importance = ResourceImportance.SENSITIVE, sync = true)
    public String exportMonthlyReport(String month) {
        return "report-" + month;
    }
}

Decision values: ZeroTrustAction

The value the decision engine makes and stores. Code fixes the default HTTP status, lifetime (how long a stored decision stays in effect) and authority (the role name used when the stored decision is applied) of each value.

ValueIn plain wordsHTTP status valueLifetimeAuthority (role name)
ALLOWAllow20015 minutes (default; contexa.security.zerotrust.allow-validity changes it)None
CHALLENGEStep-up authentication4011,800 s (30 min)ROLE_MFA_REQUIRED
ESCALATEHeld for review (analysis not finished)423300 s (5 min)ROLE_REVIEW_REQUIRED
BLOCKBlock403No expiry (until released)ROLE_BLOCKED
PENDING_ANALYSISPending analysis (no decision stored)5030ROLE_PENDING_ANALYSIS

When a value is read from a string (ZeroTrustAction.fromString), surrounding blanks and case do not matter, and the one-letter forms (A, B, C, E) are accepted. null reads as pending analysis, and an unknown string (an empty string, or a value such as UNBLOCK) reads as held for review. How a stored decision applies to the next request is in Request-time enforcement; where it is stored is in Decision Engine.

Three modes: security mode, authentication ownership, operating mode

The three modes decide different things. Their names are similar, so the table below tells them apart. The enum of the security mode is named SecurityMode; the enum of the operating mode is named EnforcementMode.

The values of the operating mode mean this. DISABLED analyzes no request. SHADOW analyzes and records the decision but does not apply it. ENFORCE analyzes, stores the decision and applies it from the next request. A mode written as OBSERVE is read as DISABLED, and one warning is logged at startup.

The security mode says what CONTEXA's security configuration does to your application. SANDBOX (the default) keeps CONTEXA apart from it: your application's sign-in, authorization and security settings (CSRF, CORS, headers) stay as they are, CONTEXA builds no authentication chain for your application's users (only a chain for the admin console), and it applies its decisions from servlet filters behind your application's chain. With users of your own (a UserDetailsService, AuthenticationProvider or AuthenticationManager bean) but no Spring Security chain declared, Spring Boot's default security applies (every request needs authentication); with neither a chain nor users of your own, CONTEXA puts an isolation chain that lets every request through, so access stays as it was before CONTEXA came. FULL makes CONTEXA your application's main security configuration (sign-in, authorization, security settings). All of CONTEXA's features work in either mode. The authentication ownership settles which of two components of the same kind serves your application when your application brings its own (its UserDetailsService, JwtDecoder and the like) and CONTEXA has one too: HOST_OWNED keeps your application's, CONTEXA_OWNED lets CONTEXA's serve where your application has none, and neither turns a feature off. What each mode changes and how to choose is in Turning CONTEXA On and Choosing a Security Mode.

Extension interfaces

When the application declares a bean of one of these interfaces, it tells CONTEXA about your application's login (ContexaSubjectResolver, ContexaSubjectMapper, BridgeUserEmailProvider), replaces CONTEXA's default (ContexaCacheService) or is added to the defaults (CapabilityContributor). The optional API you only call through static methods (ContexaBridge, ContexaUsers) is listed here too.

InterfaceWhen you implement itWith your bean
ContexaSubjectResolverFor an application that does not use Spring Security to tell the user of a request from its own login stateCONTEXA calls it once per request, after every servlet filter of your application has run, and makes the identity from the ContexaSubject it returns. Declare one bean only (two stop the start; Resolver).
ContexaSubjectMapperWhen the Spring Security principal is an object of your ownIt maps that authentication to a ContexaSubject. An empty answer leaves it to CONTEXA's reading of the standard kinds. Declare one bean only (An application that uses Spring Security).
BridgeUserEmailProviderWhen the login information carries no email (form login and the like)It tells the email of a user ID. Step-up codes are mailed to that address (email sources).
ContexaBridge (static methods signedIn, signInFailed, signedOut), ContexaUsers (static method delete)For an application that does not use Spring Security to tell CONTEXA about a successful sign-in, a failed one, a sign-out or a user who left (optional)You call them rather than implement them. They throw nothing and report through the outcome of a ContexaBridgeResult (NOT_INITIALIZED when CONTEXA has not started or is not on; Optional API).
CapabilityContributorTo add your own check to the startup capability diagnosticsThe results of every contributor are gathered with the default checker (Startup diagnostics). Three methods to implement: contributorName() (the contributor's name), capabilities() (the capabilities it checks) and check() (the check results).
ContexaCacheServiceTo replace CONTEXA's internal cacheYour implementation is used instead of the default (in memory in standalone mode, Redis in distributed mode). Values are stored as JSON, in memory and in Redis alike, so a type you put in the cache keeps its secrets out of the JSON (@JsonIgnore).

How to replace the beans the auto-configuration makes, such as the decision store, event publishing and data beans, is in Auto-configuration: replacing beans.

Module boundaries

  • The default configuration that @EnableAISecurity imports (io.contexa.autoconfigure.ai.AiSecurityConfiguration) is named by a class-name string, so contexa-common does not know the implementation modules at compile time.
  • contexa-common also holds the SOAR contracts (@SoarTool, SecurityActionEvent, tool policy interfaces) and the MCP tool-call contracts. The OSS has no implementation that runs these contracts. For SOAR see SOAR extension points; for MCP see Agent security.
