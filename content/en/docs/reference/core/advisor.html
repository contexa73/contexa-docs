Advisors: Stepping In Before and After an LLM Call

Advisors run before and after the request every time Contexa calls an AI model. This page explains what the built-in security context advisor does, how to write and register your own advisor, the order and error handling, and how to turn advisors on and off.

At a glance

Advisors are Spring AI CallAdvisor · StreamAdvisor objects. They look at or change the request before it reaches the model, and look at the response that comes back. Contexa advisors extend the base class BaseAdvisor, carry a domain (a group name), a name and an order, and the registry (AdvisorRegistry) keeps the enabled ones in order. The orchestrator attaches this list to every model call (Calling an LLM).

  • Automatic registration: Spring beans that extend BaseAdvisor are registered once, when the registry is created.
  • Not attached automatically: Spring AI Advisor beans that are not a BaseAdvisor (for example the RAG retrieval advisors) do not enter the registry. To attach one, register it with advisorRegistry.register(…) or add it per call with ExecutionContext.addAdvisor(…).
  • The only registry advisor OSS provides is the security context advisor of the SECURITY domain.

Built-in advisor: security context (SecurityContextAdvisor)

It puts "whose call this is" into the request context of every LLM call and writes an audit log line when the response arrives. Its name is SECURITY.security-context; its order is contexa.advisor.security.order (default 50).

  1. The orchestrator passes the ExecutionContext's userId · sessionId as event.userId · event.sessionId (only on the execute() family, with advisors on).
  2. With an event.userId, it looks up that user's authentication in the asynchronous security context provider (AsyncSecurityContextProvider). The provider is Redis when a generalRedisTemplate bean exists (distributed mode), otherwise memory.
  3. It puts the keys below into the request context.
KeyValue
user.idThe user of the authentication found, otherwise event.userId, otherwise anonymous
session.idThe session of the authentication found, otherwise event.sessionId, otherwise async-<UUID>
authenticatedtrue when an authentication was found or an event.userId is present
authoritiesThe authorities of the authentication found (as text). Only when one was found
principal.typeThe principal type of the authentication found (otherwise AsyncPrincipal). Only when one was found
async.contextAlways true
timestampThe request time (milliseconds)

When the response arrives it writes the INFO line LLM audit - userId: …, sessionId: …, authenticated: …, executionTimeMs: …, hasResponse: ….

Requiring authentication only checks whether a user ID was passed. With contexa.advisor.security.require-authentication=true (default false), a call with neither a user ID nor an authentication is stopped with a blocking error and the model is not called. It does not check a real login. stream() passes no user ID and a stream skips blocking errors, so streams are not stopped; and a call with advisorEnabled(false) does not go through this advisor.

Writing your own advisor

Extend BaseAdvisor, fill in the two methods beforeCall · afterCall and make it a Spring bean. The example stops prompts that are too long.

@Component
public class PromptSizeAdvisor extends BaseAdvisor {

    private static final int MAX_CHARS = 20_000;

    public PromptSizeAdvisor() {
        super("APP", "prompt-size", 60);   // domain, name, order (above 50: after the security context advisor)
    }

    @Override
    protected ChatClientRequest beforeCall(ChatClientRequest request) {
        String text = request.prompt().getContents();
        if (text != null && text.length() > MAX_CHARS) {
            throw AdvisorException.blocking(getDomain(), getName(),
                    "Prompt too long for user " + request.context().get("user.id"));
        }
        return request;
    }

    @Override
    protected ChatClientResponse afterCall(ChatClientResponse response, ChatClientRequest request) {
        return response;
    }
}
  • Order: to read the user.id the security context advisor puts in, use an order above 50. Below that it is not there yet (read event.userId instead).
  • Name: the full name is domain.name (for example APP.prompt-size). An empty domain or name fails registration with IllegalArgumentException.
  • Streams: beforeStream calls beforeCall by default, and afterStream does nothing by default (it is called for each streamed piece). Override them to behave differently for streams.
  • Context keys: after beforeCall, advisor.domain · advisor.name · advisor.timestamp are put into the request context (enrichContext).
  • To switch an advisor from a setting, override isEnabled(). It decides only whether the advisor is in the registry's list; whether an attached advisor actually acts is the value setEnabled(…) changes.

Order and error handling

The registry lists advisors by the smallest getOrder() first. Requests pass in this order and responses in reverse. An error is handled by when it happened and how the model was called.

CaseBlocking call (execute() family)Stream (stream())
Blocking error (AdvisorException.blocking(…)) before the model call (beforeCall)The model is not called and the call ends with that error. advisor.error · advisor.error.message · advisor.error.domain · advisor.blocked.by are left in the request context.Only this advisor is skipped and the model is called (not stopped).
Non-blocking error (AdvisorException.nonBlocking(…)) before the model callOnly this advisor is skipped and the call goes on.The same
Any other exception before the model callThe message is left in the request context as <domain.name>.error and the call goes on.Skipped; the call goes on.
An error after the model call (afterCall) or further inWhatever its kind, the call ends with the error (a blocking error also leaves the context keys above).The stream ends with the error.

Turning advisors on and off

ScopeHowResult
One advisorsetEnabled(false) · setEnabled(true)When off, it does nothing and passes on
One domainadvisorRegistry.disableDomain("SECURITY") · enableDomain(…)Every advisor of that domain off or on
AlldisableAll() · enableAll()Every registered BaseAdvisor off or on
One callExecutionContext.builder().advisorEnabled(false)The global advisors are left out; ThinkingGenerationAdvisor and that call's advisors stay
Security context advisorcontexa.advisor.security.enabled=falseLeft out of the registry's list

A change to the registry applies from the orchestrator's next call (each call compares the enabled list and rebuilds the ChatClient when it changed). The primaryChatClient bean, however, is built from the list at start and does not change.

// During maintenance, turn off every advisor of the SECURITY domain
advisorRegistry.disableDomain("SECURITY");

// Turn them on again afterwards
advisorRegistry.enableDomain("SECURITY");

// See what is registered
AdvisorRegistry.RegistryStats stats = advisorRegistry.getStats();
// stats.totalAdvisors, stats.totalDomains, stats.advisorsPerDomain

Do not turn off contexa.advisor.enabled (default true). Without it there is no registry bean, and the orchestrator is created only when that bean exists.

Checking

  • The list attached now: advisorRegistry.getEnabled() (in order). One advisor with advisorRegistry.get("SECURITY.security-context"), domains with getDomains(), counts with getStats().
  • Logs: the security context advisor's INFO LLM audit - …, and an advisor error's ERROR [<name>] Advisor error after …ms: ….
  • Request context: later advisors and afterCall can read user.id and the advisor.* keys.
