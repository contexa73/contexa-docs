Pipeline and RAG

How the pipeline that a Lab or a controller calls handles a request, step by step. You will learn how to choose a configuration, add RAG retrieval, shape the result, change steps and handle failures.

This is a different use from the security decision. The decision engine also passes through the same orchestrator and steps internally, but it makes decisions with its own configuration and rules. This page covers only the general-purpose use that application features call. For decisions, see the decision engine.

What the pipeline does

The pipeline orchestrator (PipelineOrchestrator) takes a request and a configuration (PipelineConfiguration), picks an executor that can handle that configuration, and runs the steps in order. There are two executors: the standard executor (UniversalPipelineExecutor), which returns a result object, and the streaming executor (StreamingUniversalPipelineExecutor), which streams text chunks.

It is usually called inside a Lab (Building the Lab). For a feature that one prompt can answer without a Strategy or Lab, a controller can call it directly; then you only need a context, a response type and a template.

// Direct pipeline: run with the default standard configuration (six steps)
Mono<SummaryResponse> result = pipelineOrchestrator.execute(request, SummaryResponse.class);

// For SSE on the screen, pass the orchestrator to StandardStreamingService (default streaming configuration)
Flux<ServerSentEvent<String>> events = streamingService.stream(request, pipelineOrchestrator);

The factory methods and the builder code below produce the same configurations.

// Standard: steps 1–6
PipelineConfiguration standard = PipelineConfiguration.builder()
    .addStep(PipelineConfiguration.PipelineStep.CONTEXT_RETRIEVAL)
    .addStep(PipelineConfiguration.PipelineStep.PREPROCESSING)
    .addStep(PipelineConfiguration.PipelineStep.PROMPT_GENERATION)
    .addStep(PipelineConfiguration.PipelineStep.LLM_EXECUTION)
    .addStep(PipelineConfiguration.PipelineStep.RESPONSE_PARSING)
    .addStep(PipelineConfiguration.PipelineStep.POSTPROCESSING)
    .build();

// Streaming: steps 1–4
PipelineConfiguration streaming = PipelineConfiguration.builder()
    .addStep(PipelineConfiguration.PipelineStep.CONTEXT_RETRIEVAL)
    .addStep(PipelineConfiguration.PipelineStep.PREPROCESSING)
    .addStep(PipelineConfiguration.PipelineStep.PROMPT_GENERATION)
    .addStep(PipelineConfiguration.PipelineStep.LLM_EXECUTION)
    .enableStreaming(true)
    .build();
  • The step list of a configuration turns steps on and off. The order of execution is not the order you add them but the fixed number of each step (1–6).
  • If you leave out retrieval or preprocessing, an empty text takes its place and everything still runs.
  • If you leave out response parsing or postprocessing in a standard configuration, the result does not become the response type, the run is treated as a failure, and a fallback response follows the failure policy.
  • If you leave out the model call in a streaming configuration, no text is produced at all.
  • timeoutSeconds(…) and addParameter(…) have no effect. They only hold values; no code reads them. The steps read request parameters (AIRequest.withParameter), not configuration parameters (Request parameters).

What each step does

1. Retrieval (CONTEXT_RETRIEVAL)

The retriever registry (ContextRetrieverRegistry) finds the retriever registered for the class of the request's context (or one of its parent classes), or uses the default retriever if there is none. The retriever searches the vector store with the question and returns the found documents joined line by line (contextInfo), together with the document list and metadata. If nothing is found, the next steps run with an empty text. The time taken is kept in the metadata contextRetrievalMs. The retriever side is covered in Adding RAG below.

2. Preprocessing (PREPROCESSING)

Leaves one system metadata text. The default implementation leaves an empty text, so it does nothing (only the time goes into preprocessingMs). This text is passed to the template's generateDomainSystemPrompt(request, systemMetadata), and the standard template adds it to the system prompt as a <context> block when it is not empty. To put values in, replace the preprocessing step.

3. Prompt generation (PROMPT_GENERATION)

  1. Finds the template bean by the name of the request's template type. If there is none, it fails with Template matching failed.
  2. Calls the template's generateSystemPrompt(request, systemMetadata) and generateUserPrompt(request, contextInfo). A standard template adds JSON format instructions to the system prompt; a streaming template adds the streaming rules and the JSON example.
  3. The prompt composer (LLMViewComposer, by default SafePromptNormalizationLLMViewComposer) tidies line breaks and keeps only one copy of a section repeated character for character. It does not cut or summarize.
  4. Leaves a Spring AI Prompt made of a system message and a user message. If the template reports a response type (standard templates do), that type is passed to the next step too.

4. Model call (LLM_EXECUTION)

  • Where it goes: UnifiedLLMOrchestrator sends it to the Spring AI chat model and applies the registered advisors (BaseAdvisor beans) (LLM orchestrator, Advisors).
  • Model: the model in the request parameter preferredModel if given; otherwise, or if it is not found, the default chat model. A general request has no analysis layer, so Layer 1 and Layer 2 model settings are not used. The rules that turn a name into a real model are in Model providers.
  • How the answer is received: a standard run knows the response type, so it first tries structured output (giving the model a schema and receiving an object) and, if that fails, receives raw text instead (with the request parameter structuredOutputPolicy=RAW_FORBIDDEN it fails instead).
  • Time limit and retries: one call must finish within contexa.security.plane.llm-timeout.provider-call-timeout-ms (default 60000 ms). A temporary failure (408, 409, 429, 5xx, a dropped connection and so on) is sent again with backoff up to 4 times (starting at 2 seconds, at most 12 seconds apart) (Retries).
  • Streaming: the streaming step (StreamingLLMExecutionStep) sends the model's text out chunk by chunk. It does not use request parameters (model, temperature and so on), does not retry, and the call itself has no time limit (streaming time limit). Advisors are attached, but a blocking error raised by an advisor before the model call does not stop it; only that advisor is skipped (advisor error handling).

5. Response parsing (RESPONSE_PARSING)

  • If step 4 already received an object through structured output, it is passed on as is.
  • If text came back, the JSON is extracted: ```json code blocks and surrounding text are removed, trailing commas before a closing bracket are deleted, and truncated JSON is kept up to the last complete entry.
  • The extracted JSON is converted into the target type. The target type is decided in this order: the template's response type → the response type passed to the run → the request parameter responseType → outputConverter → Map.
  • If it cannot be converted into the target type, it is left as a Map (a chance for a response processor in postprocessing); if even a Map fails, the JSON text is left as is. With the request parameter structuredOutputPolicy=RAW_FORBIDDEN, it fails without these fallbacks.

6. Postprocessing (POSTPROCESSING)

  • If the parsed result already is the response type, it is used as is.
  • Otherwise, response processors are called by the rules in Shaping the result.
  • If the parsed result is empty, a response holding only a FALLBACK marker is created (it is not the response type, so the run ends up as a failure).
  • If the result is an AIResponse, the run record is attached as metadata: the model actually used selectedModelId, whether the default model stood in modelSelectionFallbackUsed, the call time llmExecutionLatencyMs, the retry count providerRetryCount, template and prompt information, and more.
  • Finally, the executor returns the result only if it is the requested response type; otherwise the run is treated as a failure.

Adding RAG

RAG (retrieval-augmented generation) improves answers by finding related documents and putting them into the prompt. The retrieval step does this; there is nothing to turn on.

  • The default retriever (AuthorizedContextRetriever) searches with the request parameter naturalLanguageQuery for contexa.rag.defaults.top-k documents at or above similarity-threshold, keeps only documents that fit the requesting user, organization, tenant and retrieval purpose, and removes documents that look like prompt injection. Each remaining document is tagged with [auth=…] on its line.
  • Without a vector store, the default retriever always returns an empty result and the remaining steps run as usual.
  • Spring AI RAG advisor (RetrievalAugmentationAdvisor) beans are not attached to model calls automatically. Only BaseAdvisor beans are attached to model calls; RAG in the general pipeline is done by this retrieval step.
  • Your own retriever is a bean extending ContextRetriever; it is called only after you register it with the registry's registerRetriever(context class, retriever). A registered context type skips the default retriever's authorization filtering. A full example is in Build a custom AI feature, step 5.

Documents must be in the vector store before they can be found. Add them with Spring AI's VectorStore.

Document doc = new Document(
        "Product A is a lightweight laptop ideal for travel",
        Map.of("category", "electronics", "productId", "PROD-001"));
vectorStore.add(List.of(doc));

A document whose metadata names no allowed purpose appears in searches for any purpose. Detailed rules such as user and organization scope, document types and retention are in RAG and vector store.

Shaping the result: response processors

A response processor (DomainResponseProcessor) is the last chance to turn the parsed result into the response type, in the postprocessing step. Processors you make as beans are collected automatically and are called like this:

  • It is not called when the parsed result already is the response type. If structured output or response parsing succeeded, no processor is involved.
  • Processors are looked at in ascending getOrder() (default 0), and only the first one whose supports(template key) or supportsType(result class) is true has its wrapResponse() called. The template key is the name of the request's template type.
  • If a processor throws, only a log line is written and the next processor is looked at. With the request parameter strictResponsePostprocessing=true it fails right there, and also when no processor matches or the result is not the response type.
@Component
@RequiredArgsConstructor
public class ProductResponseProcessor implements DomainResponseProcessor {

    private final ObjectMapper objectMapper;   // the one Spring Boot creates

    @Override
    public boolean supports(String templateKey) {
        return "PRODUCT_RECOMMENDATION".equals(templateKey);
    }

    @Override
    public boolean supportsType(Class<?> responseType) {
        return false;   // pick by template key only
    }

    @Override
    public Object wrapResponse(Object parsedData, PipelineExecutionContext context) {
        // Convert into the response type when the parsed result was left as a Map
        if (!(parsedData instanceof Map)) {
            return parsedData;
        }
        ProductRecommendationResponse response =
                objectMapper.convertValue(parsedData, ProductRecommendationResponse.class);
        response.withMetadata("pipelineExecutionMs", context.getExecutionTime());
        return response;
    }
}

If you open supportsType() widely (for example to every Map), this processor also takes the results of other features, so narrowing by template key is safer. The pipeline context's getMetadata(name, type) reads run records such as selectedModelId.

Changing steps and adding executors

A new bean implementing PipelineStep is not inserted into the pipeline. An executor runs only the built-in steps it received when it was created (six for standard, four for streaming). Change things in the following ways instead.

What you want to changeHow
Put in system metadataMake a bean extending PreprocessingStep and override buildSystemMetadata(request) (example below). It is used instead of the built-in preprocessing bean.
How prompts are tidiedProvide your own LLMViewComposer bean.
A whole retrieval, prompt, parsing or postprocessing stepProviding your own ContextRetrievalStep, PromptGenerationStep, ResponseParsingStep or PostprocessingStep bean replaces the built-in one. Response parsing and postprocessing also contain decision-specific handling, so extend them and change only a part.
The way of running itselfAdd a PipelineExecutor bean. The orchestrator looks at executors from the lowest getPriority() and uses the first one whose supportsConfiguration(config) is true and whose streaming support matches.
 
@Component
public class CatalogPreprocessingStep extends PreprocessingStep {

    @Override
    protected <T extends DomainContext> String buildSystemMetadata(AIRequest<T> request) {
        return "catalogVersion=2026-11, locale=ko-KR";
    }
}
These beans are single for the whole application. Requests of the decision engine pass through the same orchestrator and steps, so a replaced step or an added executor is also called for decision requests. Narrow an executor to the configurations it should handle with supportsConfiguration(). Decision prompts do not include the system metadata from preprocessing.

Failures and checks

What a failed standard run (execute) looks like is decided by the request parameter pipelineFailurePolicy (case-insensitive; an unknown value means the default).

pipelineFailurePolicyOn failure
SYNTHETIC_FALLBACK_RESPONSE (default)Returns an empty object of the response type instead of an error. errorMessage is Pipeline execution failed: cause, and the metadata holds errorType (the exception class name) and timestamp. If the response type has no no-argument constructor (or (String, ExecutionStatus) constructor), even this fails.
PROPAGATE_ERRORSends the error to the caller as is. On the Strategy path it arrives turned into AIOperationException("Pipeline returned unexpected response type").
  • When a streaming run (executeStream) fails, it emits one text chunk ERROR: cause instead of an error, and ends. How it looks in SSE is in Streaming troubleshooting.
  • Step logs: [PIPELINE] STEP 3 completed: PROMPT_GENERATION (4ms) - Request: …, or STEP 3 failed: … on failure (streaming logs [STREAMING-PIPELINE]).
  • Step times: the pipeline context metadata pipelineStep.<step name>.ms (readable in a response processor).
  • Metadata of the result: selectedModelId, modelSelectionFallbackUsed, llmExecutionLatencyMs, providerRetryCount and more (postprocessing).

The SOAR step (not implemented in OSS)

The step list of a configuration also has SOAR_TOOL_EXECUTION, but it does not insert one more step. When the request's context is a SoarContext and a bean named pipelineSoarToolExecutionStep exists, the model call step is replaced by that bean. The OSS modules have no such bean, so application features do not use it. A SoarContext request is also handled without streaming by the streaming executor. For SOAR extensions, see SOAR.
