Calling an LLM

Every call Contexa makes to an AI model (LLM) goes through one place, the orchestrator. This page explains how to call a model from application code, which model a request goes to, how time limits, retries and provider-specific options are applied, and how to check the result of a call.

At a glance

The orchestrator (UnifiedLLMOrchestrator) is Contexa's single door to LLMs. The pipeline's LLM step (LLM_EXECUTION), the security decision engine and application code all call models through this object. One call is handled in the order below.

What you want to doWhat to use
Build an AI feature with a fixed input and output shapeStrategy, Lab and pipeline (Building an AI feature). The pipeline's LLM step calls the orchestrator for you.
Generate one text, chatExecutionContext and execute()
Get the answer as a Java objectexecuteEntity()
Get the answer piece by piecestream() (Streaming)
Let the model call the application's toolscallTools() · callToolCallbacks() (Tool calling)
Call with a chosen model or temperaturepreferredModel, temperature and so on in ExecutionContext.builder()

Before you start

  • At least one chat model is needed. Add a Spring AI provider starter (for example spring-ai-starter-model-openai) and set spring.ai.<provider>.* (API key, address); Spring AI then creates a chat model (ChatModel) bean. Contexa's own Ollama connection (contexa.llm.chat.ollama.base-url) also counts as a chat model. How to connect is in Connecting and Choosing Models.
  • Without a chat model the orchestrator bean is not created. When model selection finds no model at all, the call ends with the error No LLM model configured. ….
  • Injection: take LLMOperations (the execute(), stream() and executeEntity() on this page), or LLMClient · ToolCapableLLMClient, whose methods take only a prompt. The beans named llmClient and toolCapableLLMClient are the same orchestrator.
  • The orchestrator is created only when the advisor registry (AdvisorRegistry) bean exists. Do not turn off contexa.advisor.enabled (default true); to leave advisors out, use the other ways in Turning advisors on and off.
  • With contexa.llm.enabled=false the whole LLM auto-configuration (orchestrator, model selection, primary chat model) is off.

Your first call

Describe the call in an ExecutionContext. Only the prompt is required; add the rest when you need it.

@Service
public class SummaryService {

    private final LLMOperations llm;

    public SummaryService(LLMOperations llm) {
        this.llm = llm;
    }

    public Mono<String> summarize(String text, String userId) {
        ExecutionContext context = ExecutionContext.builder()
                .prompt(new Prompt("Summarize the following text in three lines.\n\n" + text))
                .requestId(UUID.randomUUID().toString())
                .userId(userId)          // the user ID advisors receive
                .temperature(0.2)
                .build();
        return llm.execute(context);     // the answer text
    }
}

To get the answer as a Java object, give executeEntity() the type.

record Summary(String title, List<String> points) {}

Mono<Summary> summary = llm.executeEntity(context, Summary.class);
  • Shortcuts: ExecutionContext.from(prompt) (prompt only) and ExecutionContext.forTier(2, prompt) (a layer). Both are created with advisors on.
  • Adding later: addMetadata(key, value), addAdvisor(advisor), addToolCallback(callback) (which also turns tool execution on).
  • An empty answer fails with LLM response is null or empty. For a model that returns thinking blocks before the answer, such as Claude, the thinking is skipped and only the answer is read.

Which model a request goes to

The model is chosen for each call in the order below; once a step decides, the later ones are not looked at. The recorded values and the detailed rules are in Connecting and Choosing Models.

  1. Requested model: preferredModel, otherwise the metadata requestedModelId → preferredModel → modelId. If that model cannot be made, selection moves to the next step.
  2. Layer model: the layer comes from analysisLevel (QUICK → 1, NORMAL → 2, DEEP → 3) → securityTaskType (table below) → tier. 1 or less is layer 1, 2 or more is layer 2, and the layer's model (contexa.security.tiered.llm.layer1.model · layer2.model) is used. With no layer model set, this step is skipped.
  3. Backup model: the layer's backup.model, when the layer model cannot be made
  4. Primary chat model: always used when nothing above decided (primaryChatModel)

ExecutionContext.getEffectiveTier() returns the layer number decided in the same order (analysisLevel → securityTaskType → tier); 3 stays 3, and it is null when none is set.

The security decision engine's Layer 1 and Layer 2 use the same layer models. For the models used in decisions, see Decision Engine: a different model for each layer.

Task type (securityTaskType)Layer
THREAT_FILTERING · QUICK_DETECTION1
CONTEXTUAL_ANALYSIS · BEHAVIOR_ANALYSIS · CORRELATION2
EXPERT_INVESTIGATION · INCIDENT_RESPONSE · FORENSIC_ANALYSIS · SOAR_AUTOMATION · APPROVAL_WORKFLOW3 (goes to the layer 2 model)
Values in the code that nothing uses. The default time limits of AnalysisLevel (AnalysisLevel.getDefaultTimeoutMs(), 50 · 300 · 5000 ms), its default model names (AnalysisLevel.getDefaultModelName()) and the per-layer temperature (TieredLLMProperties.getTemperatureForTier(), 0.3 · 0.7) are applied to no call. If you need a temperature, put it into the ExecutionContext.

Tool calling

The model can call the application's tools (methods) while it answers. Both Spring AI styles are accepted. The examples assume ToolCapableLLMClient was injected as toolClient.

public class IpTools {

    @Tool(description = "Block an IP address")
    public String blockIp(String ip) {
        // the application's blocking logic
        return "blocked " + ip;
    }
}

Prompt prompt = new Prompt("Block suspicious IP 192.168.1.100");

// Style 1: objects with @Tool methods
Mono<String> answer = toolClient.callTools(prompt, List.of(new IpTools()));
// Style 2: an array of ToolCallback
ToolCallback[] callbacks = ToolCallbacks.from(new IpTools());
Mono<String> answer = toolClient.callToolCallbacks(prompt, callbacks);
  • Both methods take the same path as execute() (model selection, time limit, retries). To also get the tool calls, use callToolsResponse() · callToolCallbacksResponse() (they return the ChatResponse).
  • With an ExecutionContext, use addToolCallback(...) (which turns tool execution on) or toolProviders with toolExecutionEnabled(true). When both are present, toolCallbacks are used.
  • Streaming: streamTools() lets the model call tools while it answers. streamToolCallbacks() works differently: the model does not choose the tools. Contexa first runs each tool once (its input is the first JSON after the tool's name in the prompt, otherwise the whole prompt), adds the results under Tool Results: to the prompt and streams that. A failed tool adds a line [tool name] Error: ….

Working with advisors

Advisors look at the request and the response before and after the model call. They are explained in Advisors; this section covers only how the orchestrator attaches them.

  • Global advisors: the enabled ones in the registry (AdvisorRegistry), in order. A change to the registry applies from the next call.
  • ThinkingGenerationAdvisor is always attached. It skips the thinking blocks a provider returns before the answer so that the answer is read.
  • Advisors of this call: those added with addAdvisor(...) are attached only to execute(), executeEntity() and tool calls.
  • advisorEnabled(false): only the global advisors are left out. ThinkingGenerationAdvisor and this call's advisors are still attached, and event.userId · event.sessionId are not passed. Left empty (null), advisors count as on.
  • stream(): only the global advisors are attached. This call's advisors and the user ID are not passed.

  • Past the time limit the call fails with LLM provider call exceeded timeout …, and the metadata providerCallFailureCategory becomes PROVIDER_CALL_TIMEOUT.
  • When stream() has a layer (analysisLevel · securityTaskType · tier), that layer's time limit applies. When time runs out, layer 1 turns the timeout error into the text TIMEOUT; layer 2 keeps the timeout error. A value that makes layer 3, such as DEEP, finds no layer time limit and ends with the error Invalid tier value: 3. Without a layer there is no layer time limit.

When a call is sent again

  • Retry of transient errors (execute() family): up to 4 more tries, waiting from 2 seconds and longer each time (at most 12 seconds). Retried: errors Spring AI classifies as transient, I/O errors (IOException), HTTP 408 · 409 · 429, 502 · 503 · 504, dropped or refused connections, and rate-limit messages such as "rate limit" or "try again in". Any other 4xx (the request itself was refused) is not retried.
  • Turning it off: the metadata disableRetries=true. The number of retries is recorded in providerRetryCount.
  • Refused fields: when the provider refuses the request with a 4xx (other than 408 · 409 · 429) because of a thinking or sampling field it carried, the request is sent once more without that field, within the time left. The model's later requests leave that field out too.
  • The security decision engine handles a failed decision call on its own (When the model's answer is changed).

Provider call throttling (off by default)

Makes calls wait so that the provider's per-minute request and token limits (429) are not hit. Each application instance counts on its own.

Options fitted to each provider

Providers take different option names and rules. Contexa looks at the provider of the chosen model and fits the options to it. Which models follow which rule can be changed in Provider capability settings.

ProviderWhat Contexa does
OpenAIFor the gpt-5 and o series (default list), maxTokens is sent as max_completion_tokens, and for models that take only the default sampling temperature · topP are left out. These models also get seed and the metadata openAiReasoningEffort · openAiVerbosity. The metadata promptCacheKey, when present, is sent as the prompt cache key.
AnthropicThe model's default options (including the prompt cache setting) are copied and the request values put on top. For Claude models that take only the default sampling, temperature · topP · topK are left out.
OllamaOllamaChatOptions get the model name, temperature, topP, seed and numPredict (= maxTokens). For a model on the thinking-off list, or with the metadata disableOllamaThinking=true, thinking is turned off.
OthersSpring AI's common ChatOptions (model name, temperature, topP, maxTokens)
