AI Engine: Calling an LLM from Your Own Features

With Contexa's general-purpose AI engine, a feature of your application can call an AI model (LLM) and get back a typed result object, or stream text to the screen as it is written. This page shows at a glance what you build, which path you call, what must be in place, and where to tune it.

This is not the security decision engine. This group (AI Engine) is the general-purpose AI pipeline that your application calls directly. The security decision that allows, steps up or blocks a request (Layer 1 and Layer 2 analysis) is made separately by the decision engine; your application does not call it through the APIs on this page.

What you can do with this engine

You ask an AI model with your own prompt and your own data, and receive the answer in one of two ways. It works just as well for features that have nothing to do with security (product recommendations, document summaries, classification and so on).

Contexa uses this engine too. Policy generation, resource name suggestions and condition template generation in the IAM admin console run on it (Where Contexa uses this engine).

What must be in place

The AI engine has no switch of its own; it is created when the Contexa platform is turned on. Only when all of the following are present are the engine's beans (AICoreOperations, PipelineOrchestrator, StandardStreamingService) created.

Three ways to call it

There are three ways to call the engine. Whichever you choose, the same pipeline calls the AI model at the end.

PathWhat you callWhat you buildWhen to use it
Strategy path (recommended)AICoreOperations, directly or passed to StandardStreamingServiceContext, response type, template, Lab, StrategyWhen you need input checks, protection against the same request running twice, and routing by diagnosis type

What you build

Each part is a Spring bean or a plain class, and Contexa finds it by name. A complete example from start to finish is in Build a Custom AI Feature.

Choosing how to receive the result

In the controller, one method of StandardStreamingService picks the way. request is an AIRequest; aiProcessor is the injected AICoreOperations.

// Standard: receive one result object
Mono<ProductRecommendationResponse> result =
        streamingService.process(request, aiProcessor, ProductRecommendationResponse.class);

// Streaming: receive SSE events to send to the screen
Flux<ServerSentEvent<String>> events = streamingService.stream(request, aiProcessor);

Where to tune it: settings and request parameters

Most of the AI engine's behavior is decided per request, not in application.yml. The pipeline steps read the values you put in with AIRequest.withParameter(name, value).

What you want to changeWhereDetails
Which model, temperature and maximum tokens to call withRequest parameters preferredModel, temperature, topP, seed, maxTokens (standard only). Without them, the default chat modelModel and generation options
Whether to receive failures as errorsRequest parameter pipelineFailurePolicyFailures and checks
Number of retrieved documents and minimum similaritycontexa.rag.defaults.top-k (10), contexa.rag.defaults.similarity-threshold (0.7)Pipeline settings
Time limit of one model callcontexa.security.plane.llm-timeout.provider-call-timeout-ms (60000)Pipeline settings
Model connection (provider OpenAI, Anthropic or Ollama, key, model name)spring.ai.* and Contexa's model connection settingsAI model configuration, Model providers
  • Layer 1 and Layer 2 model settings do not apply here. contexa.security.tiered.llm.layer1.model and contexa.security.tiered.llm.layer2.model are used by the decision engine. A general request has no analysis layer, so it uses the default chat model (how the model is decided).
  • There is no setting for a time limit on the whole pipeline. timeoutSeconds on PipelineConfiguration only holds a value; no code reads it.
  • The streaming time limit is 5 minutes, fixed in code, so no setting changes it.

Checking that it works

  • Step logs: a standard run logs each step, for example [PIPELINE] STEP 4 completed: LLM_EXECUTION (1830ms) - Request: … (streaming logs [STREAMING-PIPELINE]).
  • The model actually used: it is in the metadata selectedModelId of the standard result object. If the requested model was not found and the default model was used, modelSelectionFallbackUsed is true.
  • Failure: by default, instead of an error you get a response object whose errorMessage starts with Pipeline execution failed: …. Check getErrorMessage() before using the result.
  • Lock conflict: on the Strategy path, if exactly the same request (same response type, template, diagnosis type, user, session, organization and parameters) is already running, the new one is refused with StrategicOperationConflictException (a subtype of AIOperationException, message Strategic operation conflict).
  • Audit log: the Strategy path writes one AUDIT_START line to the logger IAM_AUDIT when it starts. Completion and failure are not written separately.

The default retriever filters by authorization

If you do not register a retriever of your own, the default retriever (AuthorizedContextRetriever) is used. Of the documents found in the vector store, it keeps only those that fit the requesting user, organization, tenant and retrieval purpose, removes documents that look like prompt injection, and tags each line with [auth=…] before putting it into the prompt. When you register your own retriever, requests with that context type do not go through this filtering. The detailed rules are in RAG and vector store.
