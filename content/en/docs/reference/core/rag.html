RAG: Storing and Searching Documents

How to store documents in Contexa's vector store (pgvector), find documents similar in meaning and send them to the AI model with the prompt (RAG). You will learn what to prepare, how storing, searching and failures work, how to build a domain-specific service, and how the decision engine's past decision records use the same store.

At a glance

When a document is stored, the embedding model turns its text into a list of numbers (a vector) that goes into a pgvector table. A search turns the query text into a vector too and finds the nearest documents.

  • General service (UnifiedVectorService): stores, searches and deletes any document. It has a search cache, a busy retry and a retry of failed stores. The decision engine's past decision records use this service too.
  • Domain-specific service (Lab): extends AbstractVectorLabService for one kind of document and adds metadata enrichment, validation and metrics. Examples: BehaviorVectorService (core), PolicyGenerationVectorService (iam).
  • Both implement the same contract, VectorOperations.

Before you start

  • Vector store: a VectorStore bean is needed, from the Spring AI pgvector starter (spring-ai-starter-vector-store-pgvector). Without it the general and behavior services are not created, and the pipeline's context retrieval returns nothing.
  • Embedding model: one Spring AI embedding model (fixed to one provider). How it is chosen is in Choosing the embedding model. Contexa follows your application's model: OpenAI with no model named is Spring AI's default text-embedding-ada-002.
  • Table: Contexa turns on Spring AI's initialize-schema by default. The first start creates the vector extension, the table (public.vector_store), its HNSW index and the metadata index used by per-user searches.
  • If migrations manage your schema, turn initialize-schema off and create the table, the vector index and the metadata index yourself. Off, nothing is created or changed at start.
  • Keys under contexa.vectorstore.pgvector.* are handed to Spring AI as spring.ai.vectorstore.pgvector.* (unless that key is set itself). Keys written directly as spring.ai.vectorstore.pgvector.* are treated as an old prefix and log an ERROR line at start. The index type contexa.vectorstore.pgvector.index-type (default HNSW) and the distance contexa.vectorstore.pgvector.distance-type (default COSINE_DISTANCE) are not read by Contexa either; they are handed to Spring AI this way.
  • With contexa.rag.enabled=false the RAG auto-configuration is off.
# When migrations manage the production schema
contexa:
  vectorstore:
    pgvector:
      initialize-schema: false   # handed over as spring.ai.vectorstore.pgvector.initialize-schema

Matching the dimension

The dimension of the pgvector table must equal the length of the vectors the embedding model produces. Contexa decides the dimension in the order below and puts the result in as a default setting. A new database gets a vector column of that size.

  1. contexa.vectorstore.pgvector.dimensions (or spring.ai.vectorstore.pgvector.dimensions)
  2. contexa.llm.embedding.dimensions
  3. The provider setting: spring.ai.openai.embedding.options.dimensions for OpenAI; contexa.llm.embedding.ollama.dimensions · spring.ai.ollama.embedding.options.dimensions for Ollama
  4. The value of a model Contexa knows: 1536 for text-embedding-ada-002 and text-embedding-3-small, 3072 for text-embedding-3-large, 1024 for mxbai-embed-large and bge-m3
  5. For any other model, one of 1 to 3 must be set (otherwise the application does not start).
# A smaller output (OpenAI): text-embedding-3-large gives 3072 dimensions by itself
spring:
  ai:
    openai:
      embedding:
        options:
          model: text-embedding-3-large
          dimensions: 1536

The dimension is checked at start, and start stops in these cases:

  • An unknown embedding model without a dimension set (Unknown embedding model dimension)
  • The pgvector dimension setting differs from the embedding model's (Embedding dimension mismatch)
  • The embedding column of an existing table has another dimension than the setting. Recreate the table or embed the documents again. An OpenAI installation from an earlier version (a 1024 table) stays as it is with two lines, with nothing embedded again.
  • Above 2000 dimensions while Contexa creates the table: a pgvector HNSW index holds up to 2000. Configure a smaller output, or create the table yourself and set contexa.vectorstore.pgvector.initialize-schema=false.

When the check passes, INFO Embedding vector dimension verified: provider=…, model=…, dimension=…, source=… is logged.

Storing documents

// Assumes UnifiedVectorService was injected
Document policyDoc = new Document(
        "Users must use MFA for admin operations",
        Map.of("documentType", "policy", "category", "auth"));

unifiedVectorService.storeDocument(policyDoc);
  • Metadata filled in: id (the document's id), timestamp (now, when missing), documentType (standard, when missing), version (1.0, when missing). When the embedding model is known, embeddingModel (provider/model) is added too and kept out of the embedded text.
  • Same event, overwritten: when the metadata has both eventId and documentType, the id is made from the two (UnifiedVectorService.documentId()). Storing the same event again overwrites the row instead of adding one.
  • Several: storeDocuments(list) stores them in batches of contexa.vectorstore.pgvector.batch-size (default 100).
  • Later: storeLater(document) does not store now but leaves the document to the retry queue (with the retry off, it is stored at once).
  • An empty text fails with VectorStoreException. The store time limit is contexa.vectorstore.pgvector.store-timeout-ms (default 15000 ms).
  • A documentType of behavior, behavior_analysis, suspicious, threat or ambiguous is deleted with the decision records once their retention passes (below). Use other names for application documents.

Searching

// Filter by equality (==)
List<Document> docs = unifiedVectorService.searchSimilar(
        "multi-factor authentication requirements",
        Map.of("category", "auth"));

// Choose the count, relevance and filter expression yourself
List<Document> top5 = unifiedVectorService.searchSimilar(SearchRequest.builder()
        .query("MFA policy")
        .topK(5)
        .similarityThreshold(0.7)
        .filterExpression("category == 'auth' && version == '1.0'")
        .build());
  • Defaults: with only a query, the top contexa.vectorstore.pgvector.top-k (100) documents with relevance contexa.vectorstore.pgvector.similarity-threshold (0.5) or more. The search time limit is contexa.vectorstore.pgvector.search-timeout-ms (15000 ms) and the HNSW search width contexa.vectorstore.pgvector.hnsw.ef-search (100).
  • Search cache: results of the same search are kept for contexa.security.tiered.vector-cache.expire-minutes (5 minutes), at most max-size (10000). A write clears the searches it can change (the writer's, its organization's and unscoped ones; invalidate-on-write). Turn it off with contexa.security.tiered.vector-cache.enabled=false.
Filter valueGeneral service searchSimilar(query, filters)Lab service
Text, numberEquality (==)Equality
True, falseEqualityIgnored
List (List)Not supported (the value becomes text and is compared for equality)Membership (IN)

Filter keys of the general service may use only letters, digits, _, . and - (otherwise IllegalArgumentException). Several conditions must all match (AND).

Preparing for failures

  • Busy retry: when the store answers "busy" (maximum pending requests exceeded, server busy, please try again, HTTP 503, a Spring AI transient error), it is tried up to 5 times in all, waiting from 250 ms and doubling (at most 2 seconds). Change the count with the JVM system property contexa.vector.busy-retry-attempts.
  • Retry of failed stores (on by default): a document whose store failed goes into a queue while the error is returned to the caller, and is stored again in the background. It is set with contexa.vectorstore.retry.*: a queue of 2000 (when full, the oldest document is dropped), at most 20 tries per document and up to 1 hour from its first failure, a first wait of 10 seconds doubling up to 5 minutes, and 20 documents per retry (halved while retries fail, growing back after they succeed). With contexa.vectorstore.retry.enabled=false the failure is only returned.
  • To survive a restart: the queue is in memory by default and is lost on restart. If it must survive, provide your own FailedDocumentSink bean (for example an outbox table).
  • Deletion and account purge: deleteDocuments(ids) also removes the same documents waiting in the queue. When an account is deleted, that user's waiting documents are dropped (discardPendingStores(userId)).
  • To learn about documents stored late, register addRetriedStoreListener(listener).

Building a domain-specific service (Lab)

For a service that handles only one kind of document, extend AbstractVectorLabService. Fill in four methods and storing gets metadata enrichment and validation, and searching gets the service's own filters.

public class FaqVectorService extends AbstractVectorLabService {

    public FaqVectorService(VectorStore vectorStore, ContexaRagProperties ragProperties) {
        super(vectorStore, null, ragProperties);   // null without metrics (VectorStoreMetrics)
    }

    @Override
    protected String getLabName() { return "Faq"; }

    @Override
    protected String getDocumentType() { return "faq"; }

    @Override
    protected Document enrichLabSpecificMetadata(Document document) {
        Map<String, Object> metadata = new HashMap<>(document.getMetadata());
        metadata.put("language", "en");
        return new Document(document.getText(), metadata);
    }

    @Override
    protected void validateLabSpecificDocument(Document document) {
        if (!document.getMetadata().containsKey("category")) {
            throw new IllegalArgumentException("category is required");
        }
    }
}
  • On store: id (random when missing), timestamp, documentType (getDocumentType() when missing), labName and processingTimestamp are added; then validation (contexa.rag.lab.validation-enabled) and enrichment (contexa.rag.lab.enrichment-enabled) run in that order, and metadata with null values is removed. Several documents go in batches of contexa.rag.lab.batch-size.
  • On search: the filters returned by getLabSpecificFilters() are added. A topK entry in the filters sets the count, otherwise contexa.rag.lab.top-k. The relevance is contexa.rag.lab.similarity-threshold.
  • A Lab service uses the VectorStore directly; it has no search cache, busy retry or store retry.
  • Its store and delete methods run in a transaction of Contexa's transaction manager (contexaTransactionManager) when it is a Spring bean.
  • With a VectorStoreMetrics bean, counts, times and errors of stores, searches and deletes are recorded per service name. OSS has no implementation of this bean.
  • To act after a store or search, override postProcessDocument(document, operationType).
# Settings shared by Lab services (the defaults)
contexa:
  rag:
    lab:
      batch-size: 50
      top-k: 100
      similarity-threshold: 0.75
      validation-enabled: true
      enrichment-enabled: true

Behavior record service (BehaviorVectorService)

A Lab service that stores user behavior as documents and finds similar behavior (name BehavioralAnalysis, document type behavior). It is created when a VectorStore bean exists. No OSS code calls its methods; the decision engine stores and searches its past decision records through the general service, not this one (below).

MethodWhat it does
storeBehavior(context)Stores user, IP (remoteIp), session (a random ID when missing), browser, OS, new device and new location as metadata, with the text User: …, IP: …, Path: …, Activity: …. The path is the context metadata requestPath
storeThreatPattern(context, response)Stores a threat pattern as document type threat. A failure is only logged, not thrown
storeAnalysisResult(context, response)Stores an analysis result as document type behavior_analysis (analysisId)
findSimilarBehaviors(userId, ip, path, topK)Similar behavior among that user's documents of this service; an empty list on failure
 
BehavioralAnalysisContext context = new BehavioralAnalysisContext("user-123", "session-abc");
context.setRemoteIp("192.168.1.100");
context.setUserAgent("Mozilla/5.0");
context.setCurrentActivity("GET /api/reports");
context.addMetadata("requestPath", "/api/reports");

behaviorVectorService.storeBehavior(context);

List<Document> similar = behaviorVectorService
        .findSimilarBehaviors("user-123", "192.168.1.100", "/api/reports", 5);
  • Validation: the metadata must have one of userId, sessionId or ipAddress, and the text must be at least 10 characters.
  • Enrichment: adds hour, dayOfWeek and isWeekend of the storing time, and networkSegment, the part of remoteIp before its last dot.
  • The behavior, threat and behavior_analysis documents of this service are also deleted with the decision records once their retention passes.

The decision engine's past decision records

The security decision engine keeps no store of its own: it uses the same general service (UnifiedVectorService) and the same pgvector table. The engine's side is in Decision Engine: what is learned.

  • Storing: a decision document is stored only when enforcement actually applied that action (nothing is stored in shadow mode). The document type follows the decision: ALLOW → behavior, BLOCK → threat, CHALLENGE → suspicious, ESCALATE and pending analysis → ambiguous. The id comes from the event ID and the document type, and a failed store goes through the retry queue above.
  • Reading: the v20 and v21 prompt bundles look the records up directly in the pgvector table's metadata, without an embedding (exact lookup, PgVectorPastRecordQuery). The v19 bundle uses the same service's similarity search (searchSimilar) with a user condition. An event without a user ID looks up no past records.
  • Retention: behavior, behavior_analysis, suspicious, threat and ambiguous documents older than contexa.rag.etl.behavior.retention-days (90 days) are deleted every day at 03:45 (contexa.rag.etl.behavior.retention-cleanup-cron). Zero or less keeps them. The search cache is cleared after a deletion.
  • Because the table is shared, application documents and decision records live in one table. Keep the documentType of application documents different from the five names above.

The pipeline and the RAG advisors

  • The pipeline's context retrieval step (CONTEXT_RETRIEVAL): the default retriever (AuthorizedContextRetriever) searches through the general service. The query is the request parameter naturalLanguageQuery, otherwise the text of the domain context. It finds the top contexa.rag.defaults.top-k (10) documents with relevance contexa.rag.defaults.similarity-threshold (0.7) or more, and puts into the prompt only those that fit the request's user, organization, tenant and retrieval purpose (PromptContextAuthorizationService). The pipeline is in AI pipeline.
  • RAG retrieval advisor beans: with VectorStore and ChatClient.Builder beans, Spring AI RetrievalAugmentationAdvisor beans are created: riskAssessmentRagAdvisor (risk_assessment documents with riskScore 0.5 or more, contexa.rag.risk.top-k 50 · similarity-threshold 0.8) and policyGenerationRagAdvisor (policy_evolution documents, 20 · 0.7). Both first refine the query with the chat model.
  • behaviorAnalysisRagAdvisor is created only with contexa.rag.behavior.shared-advisor-enabled=true (off by default). It searches the behavior documents of every user from the last contexa.rag.behavior.lookback-days (30) days, so for per-user retrieval write your own advisor with a user condition.
  • No OSS code uses these advisor beans, and they do not enter the registry automatically. To use one, add it to a call with ExecutionContext.addAdvisor(…) (Advisors).
  • contexa.rag.vocabulary-reindex-on-start (default true): after start, in the background, past-record documents stored under an older classification vocabulary are moved to the current one.

Checking

  • Start log: INFO Embedding vector dimension verified: … means the dimension check passed.
  • Store failures: unifiedVectorService.storeFailureStats() returns a StoreFailureStats (failed, pending, retried, dropped, deferred). With Micrometer present, the same values are published as the meters contexa.vector.store.* (failed, pending, retried, dropped, deferred).
  • Search cache: VectorStoreCacheLayer.getStatistics() (hit and miss counts, when record-stats is on).
  • Busy retry: WARN [UnifiedVectorService] Retrying … after busy failure (attempt=…, backoff=…ms, …).
