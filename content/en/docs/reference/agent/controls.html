Stop, Confirm, Limit

How Contexa stops an agent, asks the accountable person to confirm its request, and limits its pace and scope, according to the decision and the settings. It also covers the answers an agent receives and how to handle them, how administrators release a stop, and the console screens.

At a glance

What works under each ownership

The gate (① to ④) runs in both ownership modes: inside the security chain Contexa builds under CONTEXA_OWNED, and as a servlet filter right after the application's Spring Security chain by default (HOST_OWNED), behind the authentication bridge that stamps the delegation. The @Protectable methods (⑤) and the handling after a decision work in both.

Confirmation by the accountable person

On a CHALLENGE decision a person is asked to step up (MFA), but an agent cannot do MFA. So Contexa asks the person accountable for that agent to confirm that request.

{
  "status": "PENDING",
  "error": "AGENT_CONFIRMATION_REQUIRED",
  "trigger": "DECISION_CHALLENGE",
  "confirmationId": "6f1c2a90-…",
  "statusUrl": "/contexa/api/agent-confirmations/6f1c2a90-…",
  "expiresAt": "2026-11-02T06:15:00Z",
  "confirmationHeader": "Contexa-Agent-Confirmation",
  "message": "The person accountable for this agent must confirm this request; …",
  "path": "/api/reports/export"
}
  • Who confirms: the delegator for a delegated agent, the sponsor for an autonomous agent. Without an accountable person no confirmation is made and the request is refused (the body has no confirmationId).
  • A confirmation is bound to its request: tenant, user, agent, method, path, query string and the body's SHA-256. It is used only by that same request and becomes USED once used. The agent may name the confirmation ID in the Contexa-Agent-Confirmation header when sending again.
  • Time: the person's answer is awaited for confirmation-timeout (15 minutes by default), and an approval must be used within the same time. Past it the confirmation is EXPIRED (refused); expired ones are swept every minute.
  • Report: when the person reports the request, it is refused and the agent is stopped at once (as in stopping, with a BLOCK stored right away).
  • An approval is kept as a verifiable record. With Contexa's authorization server it is an OAuth2 authorization, without it a signature with the evidence signing key, verified again when used. What was confirmed also goes into the decision context (the v21 Confirmation line).
  • On the confirmation page only the person the confirmation is for decides, in their own session. A request from an agent is refused there even with that person's token.
Confirmation statusMeaning
PENDINGWaiting for the person
APPROVEDApproved, not used yet
USEDApproved and used by its request
REJECTED, EXPIRED, REPORTEDRefused, timed out, reported (all final refusals; refused is true in the status)

An agent asking for confirmation first

With the policy !delegationRequiresApproval() or agentRequestConfirmed() on work whose delegation requires approval, the agent can ask for a confirmation itself before it runs (trigger REQUESTED).

POST /contexa/api/agent-confirmations
Content-Type: application/json

{ "method": "POST", "target": "/api/reports/export?month=2026-10",
  "bodySha256": "9f86d081…", "reason": "Monthly report export" }

It returns 202 with the confirmation's status (409 without an accountable person, 403 when the caller is not an agent). target is the path with the query, starting with /; bodySha256 is the SHA-256 (hexadecimal) of the body it will send. Poll the status at GET /contexa/api/agent-confirmations/{id}. This too needs the gate that consumes confirmations, so it works only under CONTEXA_OWNED.

The start of the confirmation link in notices is set with confirmation-link-base-url (for example https://app.example.com). Left empty, the link is relative, with the application's path only. The Host header the agent sent is never used in the link.

Stopping and releasing

When a BLOCK is decided on an agent's request, that agent only is stopped. It is not added to the people's block list, and the person's own work goes on.

A report by the accountable person and a call limit set to STOP stop the agent the same way. A stop is released through the admin API or console, or on the accountable person's confirmation page (a kill switch stop by administrators only).

actionFieldsWhat it does
RELEASE_DELEGATIONuserId, agentIdClears the agent's decisions for that person so its next request is decided again. The revoked delegation stays revoked; the person delegates again
RELEASE_AGENTagentId (tenantId optional)Puts the registration back in service and clears the agent's decisions
KILL_SWITCHagentType, tenantId (optional)Stops every agent in service of that type (all types when empty) at once
KILL_SWITCH_RELEASEThe samePuts back only the agents the kill switch stopped; agents stopped for other reasons stay stopped
 
POST /contexa/admin/api/agents/stops
Content-Type: application/json

{ "action": "KILL_SWITCH", "agentType": "AGENT", "reason": "Prompt injection incident" }

reason is required and the ADMIN role is needed. GET shows the stopped agents and delegations. Without the service that stops agents (AgentContainmentService) it answers 503 (the autonomous security plane is off). A scope a BLOCK narrowed stays narrowed after the release until its period ends.

Scope narrowing

After a risky decision on an agent's request, the agent's next requests may only read for a while.

  • When: after a CHALLENGE, ESCALATE or BLOCK, or an ALLOW whose risk reaches risk-threshold (0.7 by default).
  • How long: duration (1 hour by default). A scope is only narrowed, never widened.
  • The operation is read from the method and the words of the path (READ, WRITE, EXPORT, DELETE, ADMIN, EXECUTE). A GET /api/exports, for example, is an export (EXPORT).
  • A request outside the scope gets 403 AGENT_SCOPE_NARROWED; it passes once its accountable person confirms it. A person's request is never narrowed.

Call limits and the denial alarm

LimitDefaultCounted for
One delegation120 per minuteOne person's work (the agent's decision key)
The whole agent600 per minuteEveryone the agent acts for
  • Past a limit, on-exceed decides: THROTTLE (default, 429 with Retry-After) or STOP (the agent is stopped; the request's own answer is still 429).
  • Denial alarm: when at least 10 requests in 5 minutes were refused at a rate of 50% or more, an audit record is written and the accountable person is told (once per window).
  • When the enforcement mode is not ENFORCE (SHADOW and so on), a request past a limit goes on and is only recorded. The counts are per instance.

Requests with no decision, and ALLOW reuse

  • No decision yet: a person's request goes on and is analysed afterwards, but an agent's request is decided in the request, even at an asynchronous @Protectable method (protectable.unrecorded-agent-request: DECIDE_IN_PLACE, default). With PROCEED it goes on as a person's does.
  • An ALLOW in force: for a person it answers later requests for its validity, but for an agent only the same operation, 3 distinct resources and 10 requests; for a sensitive resource (SENSITIVE or CRITICAL) only 1 resource. Past that the request is decided again in place, so an agent that reads a customer list one record at a time cannot read it all on its first ALLOW.

Decision merging (off by default)

When one agent sends many requests at once, the model is not called for each: the same question is analysed once. While the first request is analysed, the others wait for its verdict and are answered by it.

  • A restriction (BLOCK, ESCALATE, CHALLENGE) stored for the agent while requests wait answers them at once.
  • A failure of decision merging itself is not a decision: each request is then analysed on its own. The state is kept in memory per instance.

In modes that do not enforce (SHADOW and so on)

When the enforcement mode is not ENFORCE (SHADOW, OBSERVE, DISABLED, or contexa.security.zerotrust.enabled=false), the gate records ended delegations, narrowed scopes and call limits and lets the request on. The re-evaluation as the delegator is only recorded too. A CHALLENGE in force still waits for its confirmation.

Decision records and tamper checks

Each decision leaves one decision record in the audit log (ctxa_audit_log, category SECURITY_DECISION). For a person's request the agent and delegation fields are empty.

FieldContent
SubjectThe subject kind, the agent, the delegator, the delegation id
Operation asked forThe request's action family
Risk factsThe reason codes the decision cited, with their fact IDs
EnforcementThe response enforced and why. The outcome is APPLIED, KEPT_STRICTER (a stricter response already in force was kept), OBSERVED_ONLY (recorded only, in a mode that does not enforce) or DISCARDED (the processing lost ownership and the result was dropped)
Request context hashThe SHA-256 of the time, tenant, user, agent, delegation, operation, method, path, target, requested items and argument summary

With a signer (the signing key of sealed evidence), decision records are chained in the order they are saved: each record's fields and the previous record's hash are hashed together with SHA-256 and signed. The admin console's real-time monitor shows the check result of each record.

ResultMeaning
VERIFIEDAs sealed
MISMATCHA field changed, the hash was computed again so the signature fails, or a record in the middle of the chain was removed
UNVERIFIABLEWritten before records were sealed, or signed with a key no longer held (for example a temporary key before a restart)

The oldest records removed by the audit log retention (default 90 days, System Settings) do not count as MISMATCH.

Operations notes

  • Several instances: call limit counts and decision merging state are in memory per instance. In-memory registries and stores are lost on restart, so use the Contexa database in production.
  • Without the stop service (AgentContainmentService) there is no stop after a BLOCK and no narrowing, and the stop API answers 503. contexa.autonomous.enabled: false does not produce this state; it turns all of Contexa off.
  • An agent's decision is the model's; the engine only computes facts (Decision Engine).
