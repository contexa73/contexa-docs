Stop, Confirm, Limit

Stop, confirm and limit are the controls with which CONTEXA blocks or slows the request of an AI agent, according to the decision and the settings. CONTEXA stops the agent (stop), asks the accountable person to confirm its request (confirm), and limits its call rate and the operations it may do (limit). This page covers the answers an agent receives and how to handle them, the actions of accountable people and administrators (console screens included), the settings, and how decision records are checked for tampering.

Terms on this page. The agent gate is a request filter that applies to an agent's requests only. The accountable person is the person who confirms an agent's requests and receives stop notices (the delegator for a delegated agent, the sponsor named at registration for an autonomous agent). The kill switch lets an administrator stop every agent of one type (or of all types) at once. Decision merging analyses the same question once when one agent sends it many times at once (off by default). The other terms, such as delegator and delegation stamp, are in Agents as Security Subjects.

Overview

What works in each security mode

The security mode sets who handles sign-in: your application (SANDBOX) or CONTEXA (FULL). The authentication ownership (HOST_OWNED, CONTEXA_OWNED) is a separate setting and turns none of the controls below on or off. The gate (① to ④) runs under both modes. Under FULL it runs inside the security chain CONTEXA builds. Under the default SANDBOX it runs as a servlet filter after the application's Spring Security chain and its other servlet filters have all run, behind the authentication bridge that stamps the delegation. The @Protectable methods (⑤) and the handling after a decision work under both.

Confirmation by the accountable person

On a CHALLENGE decision a person is asked to step up (MFA), but an agent cannot do MFA. So CONTEXA asks the person accountable for that agent to confirm that request.

{
  "status": "PENDING",
  "error": "AGENT_CONFIRMATION_REQUIRED",
  "trigger": "DECISION_CHALLENGE",
  "confirmationId": "6f1c2a90-…",
  "statusUrl": "/contexa/api/agent-confirmations/6f1c2a90-…",
  "expiresAt": "2026-11-02T06:15:00Z",
  "confirmationHeader": "Contexa-Agent-Confirmation",
  "message": "The person accountable for this agent must confirm this request; …",
  "path": "/api/reports/export"
}
  • Who confirms: the delegator for a delegated agent, the sponsor for an autonomous agent. Without an accountable person no confirmation is made and the request is refused (the body has no confirmationId).
  • Notices: the accountable person gets a mail (the console when there is no mail) with a link to the confirmation page. When a confirmation of the same agent is already waiting, a new request sends no mail and is shown in the console only, so an agent cannot fill the mailbox of the accountable person. When a wait ends unanswered, the accountable person gets a notice, in the same way, that the request was refused.
  • A reason written by the agent is marked as unverified. When an agent asks for a confirmation itself, the reason it wrote appears in the notice with a mark that the agent wrote it and CONTEXA did not check it. This keeps it apart from the reasons CONTEXA sets (the grounds of a decision, an ended delegation).
  • The path the person sees: the path exactly as the agent sent it. When the application serves that path as another path (for example a path with encoded characters), the path that is served is shown too.
  • A confirmation is bound to its request: tenant, user, agent, method, path, query string and the body's SHA-256. It is used only by that same request and becomes USED once used. The agent may name the confirmation ID in the Contexa-Agent-Confirmation header when sending again.
  • Time: the person's answer is awaited for confirmation-timeout (15 minutes by default), and an approval must be used within the same time. Past it the confirmation is EXPIRED (refused); expired ones are swept every minute.
  • Report: when the person reports the request, it is refused and the agent is stopped at once (as in stopping, with a BLOCK stored right away).
  • An approval is kept as a verifiable record. With CONTEXA's authorization server it is an OAuth2 authorization, without it a signature with the evidence signing key, verified again when used. What was confirmed also goes into the decision context (the Confirmation line).
  • On the confirmation page only the person the confirmation is for decides, in their own session. A request from an agent is refused there even with that person's token.

An agent asking for confirmation first

With the policy !delegationRequiresApproval() or agentRequestConfirmed() on work whose delegation requires approval, the agent can ask for a confirmation itself before it runs (trigger REQUESTED).

POST /contexa/api/agent-confirmations
Content-Type: application/json

{ "method": "POST", "target": "/api/reports/export?month=2026-10",
  "bodySha256": "9f86d081…", "reason": "Monthly report export" }

It returns 202 with the confirmation's status. The errors are:

  • 403: the caller is not an agent.
  • 409: there is no accountable person, so no confirmation can be made.
  • 400: method or target is missing, method is not an HTTP method, target does not start with /, contains invisible characters or blanks, or is over 2048 characters, or the agent ID is too long for a confirmation to hold.
  • 429: the agent is past its call limit. This request counts as a call too.

target is the path with the query, starting with /. bodySha256 is the SHA-256 (hexadecimal) of the body the agent will send. The body is announced by its hash only, and CONTEXA never sees the body on this route. reason is stored up to 1000 characters. Poll the status at GET /contexa/api/agent-confirmations/{id}; an agent can read only its own confirmations.

This API is open under both security modes. Where a policy reads an approved confirmation depends on the kind of policy. @Protectable method policies read approvals under both modes. URL policies read them in CONTEXA's chain (FULL) and in CONTEXA's filter slot behind the application's chain (both modes), where they are evaluated after the agent gate. Only URL policies evaluated inside the application's chain with .access(...) run before the agent gate and cannot read approvals.

The start of the confirmation link in notices is set with confirmation-link-base-url (for example https://app.example.com). Left empty, the link is relative, with the application's path only. The Host header the agent sent is never used in the link.

Stopping and releasing

When a BLOCK is decided on an agent's request, that agent only is stopped. It is not added to the people's block list, and the person's own work goes on.

A report by the accountable person and a call limit set to STOP stop the agent the same way. A stop is released through the admin API or console, or on the confirmation page of the accountable person (a stop by the kill switch only by administrators).

The kill switch only changes the registration status of the agent to SUSPENDED. Revoking delegations, revoking tokens and sending notices happen only when the agent is stopped by a BLOCK or by a report. A registration stopped by the kill switch gets KILL_SWITCH: in front of its stop reason, and KILL_SWITCH_RELEASE puts back in service only the agents stopped for that reason.

actionFieldsWhat it does
RELEASE_DELEGATIONuserId, agentIdClears the agent's decisions for that person so its next request is decided again. The revoked delegation stays revoked; the person delegates again
RELEASE_AGENTagentId (tenantId optional)Puts the registration back in service and clears the agent's decisions
KILL_SWITCHagentType, tenantId (optional)Stops every agent in service of that type (all types when empty) at once
KILL_SWITCH_RELEASEThe samePuts back only the agents the kill switch stopped; agents stopped for other reasons stay stopped
 
POST /contexa/admin/api/agents/stops
Content-Type: application/json

{ "action": "KILL_SWITCH", "agentType": "AGENT", "reason": "Prompt injection incident" }

reason is required and the ADMIN role is needed. GET shows the stopped agents and delegations. Without the service that stops agents (AgentContainmentService) it answers 503 (the autonomous security plane is off). A scope a BLOCK narrowed stays narrowed after the release until its period ends.

Scope narrowing

After a risky decision on an agent's request, the agent's next requests may only read for a while.

  • When: after a CHALLENGE, ESCALATE or BLOCK, or an ALLOW whose risk reaches risk-threshold (0.7 by default).
  • How long: duration (1 hour by default). A scope is only narrowed, never widened. When risky decisions repeat, the allowed operations become the intersection of all the scopes so far, the end moves to the later time, and the scope ends only when its period has ended.
  • The kind of operation is decided from the method and the words of the path (READ, WRITE, EXPORT, DELETE, ADMIN, EXECUTE). When a word in the path points to write, export, delete, admin or execute, that word wins even if the method reads (a DELETE method stays a delete even if the word means write). When the word means read or is unknown, the method decides. For example, GET /api/exports is an export (EXPORT). When the path cannot be read as a routing rule, the kind of operation is unknown, it does not fall within the read scope, and the request is refused.
  • A request outside the scope gets 403 AGENT_SCOPE_NARROWED; it passes once its accountable person confirms it. A person's request is never narrowed.

Call limits and the denial alarm

LimitDefaultCounted for
One delegation120 per minuteOne person's delegated work (one decision key of the agent)
The whole agent600 per minuteEveryone the agent acts for
  • Calls are counted over the last minute. Past a limit, on-exceed decides: THROTTLE (default, 429 with Retry-After) or STOP (the agent is stopped the same way as for a BLOCK; the answer to the request itself is still 429).
  • Denial alarm: when one decision key (one delegation, or one autonomous agent) sent at least 10 requests in 5 minutes and 50% or more of them were refused, an audit record is written and the accountable person is told, at most once every 5 minutes. A request that waits for a confirmation is not counted as a refusal.
  • When the operating mode is not ENFORCE (SHADOW and so on), a request past a limit goes on and is only recorded. Call counts are per instance.

Requests with no decision, and ALLOW reuse

  • No decision yet: a person's request goes on and is analysed afterwards, but an agent's request is decided in the request, even at an asynchronous @Protectable method (contexa.security.zerotrust.protectable.unrecorded-agent-request: DECIDE_IN_PLACE, default). With PROCEED it goes on as a person's does.
  • Reuse of a stored ALLOW: for a person, an ALLOW answers later requests from the same session, IP and browser for its whole validity. For an agent it is used far more narrowly. It answers only requests from the same session, IP and browser that do the same operation as the request that got the ALLOW (READ and so on), and only up to 3 distinct resources and 10 requests. Past that the request is decided again in place.
    • For a sensitive resource (SENSITIVE or CRITICAL) the limit is 1 resource. A sensitive resource is counted by its path and its query values together, so /api/customers?id=7 and ?id=8 are different resources.
    • An ALLOW given for an ordinary resource is never used for a request to a sensitive resource.
    This keeps an agent that reads a customer list one record at a time from reading it all on its first ALLOW.

Decision merging (off by default)

When one agent sends many requests at once, the model is not called for each: the same question is analysed once. While the first request is analysed, the others wait for its verdict and are answered by it.

  • A restriction (BLOCK, ESCALATE, CHALLENGE) stored for the agent while requests wait answers them at once.
  • A failure of decision merging itself is not a decision: each request is then analysed on its own. The state is kept in memory per instance.

In modes that do not enforce (SHADOW and so on)

When the operating mode is not ENFORCE (SHADOW or DISABLED, or contexa.security.zerotrust.enabled=false), the gate records ended delegations, narrowed scopes and call limits and lets the request on. The re-evaluation as the delegator is only recorded too. A CHALLENGE in force still waits for its confirmation. The old name OBSERVE is read as DISABLED.

Decision records and tamper checks

Each decision leaves one decision record in the audit log (ctxa_audit_log, category SECURITY_DECISION). For a person's request the agent and delegation fields are empty.

FieldContent
SubjectThe subject kind, the agent, the delegator, the delegation id
Operation asked forThe request's action family
Risk factsThe reason codes the decision cited, with their fact IDs
EnforcementThe response enforced and why. The outcome is APPLIED, KEPT_STRICTER (a stricter response already in force was kept), OBSERVED_ONLY (recorded only, in a mode that does not enforce) or DISCARDED (the processing lost ownership and the result was dropped)
Request context hashThe SHA-256 of the time, tenant, user, agent, delegation, operation, method, path, target, requested items and argument summary

With a signer (the signing key of sealed evidence), decision records are chained in the order they are saved: each record's fields and the previous record's hash are hashed together with SHA-256 and signed. The admin console's security event log shows the check result of each record.

ResultMeaning
VERIFIEDAs sealed
MISMATCHA field changed, the hash was computed again so the signature fails, or a record in the middle of the chain was removed
UNVERIFIABLEWritten before records were sealed, or signed with a key no longer held (for example a temporary key before a restart)

The oldest records removed by the audit log retention (default 90 days, System Settings) do not count as MISMATCH.

A decision record keeps the time of its event, and the save does not write it again, so the record is verified as it was sealed. A decision record saved before this was fixed had its time written again by the save and stays MISMATCH; it is not sealed again, so that a mismatch keeps meaning a record was altered (Old decision records mismatch after an upgrade).

Operations notes

  • Several instances: call limit counts and decision merging state are in memory per instance. In-memory registries and stores are lost on restart, so use the CONTEXA database in production.
  • Without the stop service (AgentContainmentService) there is no stop after a BLOCK and no narrowing, and the stop API answers 503. contexa.autonomous.enabled: false does not produce this state; it turns all of CONTEXA off.
  • An agent's decision is the model's; the engine only computes facts (Decision Engine).
