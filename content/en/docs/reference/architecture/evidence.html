Sealed Evidence

To review a decision the AI model made, you need the prompt and the facts it was made from, exactly as they were. CONTEXA keeps these for a share of the requests the AI model decides (sealing), checks that the kept record has not changed, and can ask the model again from the same inputs (replay). On this page you can check what is sealed and when, how to confirm that nothing changed, how replay behaves and its limits, and retention and settings.

Overview

When the AI model decides a request, CONTEXA gathers what the decision was made from into one package and stores it separately. The package holds the prompt exactly as sent to the model, the ingredients of that prompt (request facts, canonical context, the baselines the decision read, past decision records) and the decision result. The canonical context is the set of facts the decision used, written in one fixed format. CONTEXA computes a hash of the package (a fingerprint that changes if a single character changes), signs it and stores it. This step is sealing, and a sealed package (an evidence package) is sealed evidence.

Sealing does not change the decision. A separate thread builds and stores the package after the decision is done. Signing needs a signing key. In production, set your own key. Without one, CONTEXA signs with a temporary key made at startup, and those signatures cannot be checked after a restart (see Adding signing keys).

What is sealed

One package holds seven sections. Sections 1 to 5 are the ingredients of the prompt, section 6 is the prompt the model actually received, and section 7 is the decision result. The hash covers all seven sections, so a change to any of them shows up when the package is checked.

  • Run information in section 6 that is longer than 512 characters is not kept whole; only its length and hash are kept.
  • The baselines the decision read are stored in section 4 under one key (decisionBaselines), one entry for the person's baseline and one for the organization's. If the decision found no baseline, the package says so explicitly. These are the values the analysis fixed when it read the baselines, and they are not read again while sealing. A later replay therefore asks again with the baselines the decision read (Replay). A package without this key was sealed before baselines were stored.

When it is sealed

CONTEXA does not seal every request the AI model decides; it seals a share. This saves storage, and it seals first the decisions that stopped a request and the allowed decisions that may be misses.

  • What can be sealed: only decisions made by the AI model. A decision made without a model call has no prompt the model received, so nothing is sealed.
  • Requests that are never sealed: requests without a user ID, failed processing, and requests whose path is /actuator · /health · /.well-known/ · /sse/. A decision about a @Protectable method is sealed whatever its path.
  • Which decisions are sealed: four rules decide.
    1. The window after a start or a change, and a stable share. This rule applies whatever the daily limit says.
      • The window: the first 1,000 decisions after a server starts, and the first 1,000 after the prompt version that decisions run changes, are all sealed (contexa.pqa.oss.sealed-evidence.full-capture-after-change). The version changes when the label that picks it is moved, when it is rolled back, or when the setting changes.
      • The stable share: outside the window, 1% of requests are sealed, chosen by a stable hash of the request ID (sample-percent), so the same request always gets the same answer.
      • Telling versions apart: a version is told apart by its name and content hash. A version that a canary (Canary for some users) or a run alongside (Run alongside) uses has a window of its own. Each server (node) counts its windows on its own.
    2. A decision that stopped the request. A step-up authentication (CHALLENGE), a hold for review (ESCALATE) or a block (BLOCK) is sealed.
    3. An allowed decision that may be a miss. An allowed request is sealed when any sign below says it may have been a threat that got through. An allowed decision with no sign is left to the share in rule 1.
      • The explanation the model marked most likely is not legitimate work.
      • The second analysis made the decision.
      • The model was asked again.
      • At least unknown-fact-threshold (3) decision facts were unknown.
      • The personal baseline is not established yet.
    4. The daily limit. Rules 2 and 3 apply only while fewer than daily-limit (2,000) packages are stored for the UTC day. The count includes every package of the day in the store, so servers that share a database keep to one limit. Each server reads the count every 30 seconds, so it may pass the limit by what it seals in between. Past the limit, the day is sealed by rule 1 alone, and the number of decisions left out is logged at most every 10 minutes. 0 means rule 1 alone from the start.
  • Storage: a sealed package takes about 60 KB (measured on the sample decisions of the product). Up to the default daily limit, that adds about 120 MB a day. Packages that rule 1 seals after the limit are added on top.
  • Effect on decisions: in the order of the decision steps, sealing sits after enforcement (55) and before audit (60), at 56. A separate thread assembles and stores the package. If that thread falls behind, the overflowing packages are dropped and the decision is not affected.
  • How long a captured prompt waits: a captured prompt waits in memory at most 10 minutes (snapshot-ttl) for the decision to finish and be sealed.
  • Link to the review queue: the review queue of the Zero Trust console (a menu of the admin console, Admin Console) is the list of decisions a person should review. While the capture is on, it holds only sealed decisions. A reviewed decision can then be replayed and made a case (Prompt Quality Assurance).

Confirming nothing changed

Whether a sealed package changed after it was stored is checked with a hash and a signature.

  • The hash: SHA-256 over the content of the seven sections, the prompt hashes, the schema number and more. Read the stored package again and repeat the calculation: if even one character changed, the value is different.
  • The signature and the chain (schema 3): with a signer, a package is sealed as schema 3. The default setup always has a signer. In schema 3 the tenant, the user, the sealing time and the hash of the package stored just before are also hashed, and that hash is signed with HMAC-SHA256. Someone who edits the database and recomputes the hash still cannot produce a matching signature without the signing key. Each package holds the previous package's hash, so the packages form a chain. Without a signer, a package is schema 2 and holds a hash only.

Checking a stored package gives one of three results.

ResultMeaning
VERIFIEDThe recomputed hash matches the stored one and, for schema 3, so does the signature.
MISMATCHThe content is taken to have changed after it was stored: the recomputed hash differs, the signature does not match, a signature that should be there is missing, or (where signing keys are configured) the package names a key this installation never held. A previous package that is gone without the retention explaining it (LINK_BROKEN) also belongs here.
UNVERIFIABLEThe check cannot tell. The hash or a prompt hash is empty, no key on this server can check the signature (for example a signature made with a temporary key from before a restart), or the neighbouring packages could not be read from the store.

The SEAL_INTEGRITY check of the evidence audit performs this check. The sealed evidence screen runs it when it opens a package, and a replay runs it too.

Adding signing keys

In production, set your own signing key: for each key ID, a Base64 secret of at least 32 bytes. The signature uses a secret key, so keep the key apart from the database; otherwise the signature adds little.

contexa:
  security:
    evidence:
      signing:
        keys:
          k2026: ${CONTEXA_EVIDENCE_KEY}   # Base64, at least 32 bytes
        active-key-id: k2026               # required with two or more keys
  • Without a key, a temporary key is made at startup and a WARN is logged. The application starts and signs packages normally, but a temporary key is lost at each restart. Signatures made with it cannot be checked after a restart (UNVERIFIABLE), and each server has a temporary key of its own.
  • When you rotate keys, set the new key as active-key-id and keep the retired key in the list. Each package records the ID of the key that signed it, so old signatures are checked with the old key. With two or more keys and no active-key-id, or one that is not in the list, the application does not start.
  • The decision audit records (ctxa_audit_log) are chained and signed by the same signer, and the security event log of the admin console shows the result for each record. The result for sealed packages is shown on the sealed evidence screen, not on the security event log.
  • A sealed package holds the previous package's hash. When one package is checked, CONTEXA looks for its previous package in the store. If it is gone and the retention does not explain it, the result is MISMATCH (LINK_BROKEN). Nothing walks the whole chain from start to end (see Limits).

The evidence audit

The evidence audit is CONTEXA checking the stored packages again, automatically. The inspector (PromptInspector) runs three checks on each package and counts, for each check, what matched, what did not and what could not be checked. It only points at problems for a person to review. It never changes a prompt, a decision or a rule, and it does not run on a decision thread.

Check (on the screen)What it checks
SEAL_INTEGRITY (Integrity)Whether the package is unchanged since it was stored and consistent inside. The package hash is recomputed and compared with the stored one, and for schema 3 the signature is checked too. The system prompt and the user prompt must both be stored and match their hashes. The prompt the model got must equal the original before compression, or a compression must be recorded. The request ID (correlation ID) must exist and match the request ID in the request facts. The sealed prompt must be the one the last model call sent, and the output retries recorded in the decision must agree with its model call stages
BUNDLE_TRACE (Trace of origin)Whether the sealed prompt came from a version that was actually released. The prompt version named in the package must be a release in the prompt release registry (the record of released versions; a retired row counts), the contract version and content hash in the package must be the release's, and the release must have an approval. A later release never turns an earlier prompt into a mismatch. Without a registry, the trace cannot be checked
SOURCE_TRUTH (Source records)Whether the facts the decision used are the same as the application's own records of them. The source verifier (PromptFactSourceVerifier) reads its sources again for the sealed decision and gives, for each fact, the value the source holds. The check compares that value with what the sealed decision collected: the on-call record, the assignment, the approvals and the delegation in its canonical context. A fact the sealed decision names as unknown is not a mismatch. A fact the sealed context holds no structured value for cannot be compared, so it counts as not checked. The default verifier reads CONTEXA's company records and delegations again, and a bean of the same type that the application declares replaces it. Without a verifier, the check records that no source is integrated
  • Verdicts: each package gets one.
    • PASS: all three checks matched.
    • FAIL: one or more mismatches.
    • INCOMPLETE: no mismatch, but something could not be checked.
    • NOT_APPLICABLE: the user prompt does not follow the prompt dictionary (the fixed layout of block titles and line names), so only the checks that do not read its lines ran.
    • ERROR: the package could not be inspected.
    Findings are MISMATCH and UNVERIFIABLE; something that could not be checked never counts as passing. The screen groups the verdicts as "All whole" (PASS, NOT_APPLICABLE), "With a problem" (FAIL) and "Not all checked" (INCOMPLETE, ERROR, not inspected yet).
  • Runs: the automatic audit runs every 30 seconds (contexa.prompt-inspection.interval, the first after initial-delay) and takes the oldest packages not inspected yet, 50 at a time (batch-size). With several servers, one lock lets only one run at a time. Packages are chosen by a hash of the package ID within sample-percent (default 100).
  • Inspector versions: each result keeps the inspector version (prompt-inspector/N, now 30) and, for a dictionary prompt, the dictionary it was read with. When the inspector version changes, packages are inspected again, and a package keeps the results of its latest two inspector versions.
  • Earlier packages: a package made with an earlier prompt bundle (v19, v20, v21) keeps that bundle name until its retention ends, and the checks that apply to it audit it.
  • The audit does not decide how long a package is kept (Retention). The checks that read the prompt's lines now check the renderer in the build; see What was removed.
  • When it exists: the inspector, the automatic audit, inspecting again and the sealed evidence screen exist only when contexa.enterprise.enabled is not true and contexa.prompt-inspection.enabled is true (default). Turning the inspection off leaves the replay and the prompt version trials on.

The sealed evidence screen

In the menu "Prompt Quality Assurance → Sealed evidence" (/contexa/admin/prompt-quality/evidence), an administrator can find a sealed decision, see whether its record is still whole, replay it and add it as a case. The screen needs the administrator role (ROLE_ADMIN) and describes itself as "The prompt, the facts and the answer of a decision, sealed as they were."

The earlier "Sealed Prompts" screens joined this one. Their old addresses /contexa/admin/prompt-inspection, /prompt-inspection/packages and /prompt-inspection/packages/{packageId} redirect to the matching place here, with their period and filters, so old bookmarks keep working.

Replay: asking again from the sealed inputs

Replay builds the prompt again from the inputs of a sealed decision (request facts, authentication state, canonical context, past records, baselines) and asks the model the same decision once more, with a prompt version an administrator chooses. For example, you can see how a new version would decide a request that was blocked last week. A replay changes neither the sealed package nor any real decision. The measurement of prompt quality uses the same replay on labelled cases (Measuring a version); to compare two versions on recent sealed decisions, use the trial in Measure & compare (Trial decisions).

  • On the screen: "Replay" on a package asks for the version and, optionally, the models for the second analysis ("Optional, comma separated, at most 3"). The screen warns: "A replay calls the model (once more per second-pass model). Nothing is applied, learned or sealed; it is audited."
  • What is asked: the first analysis is asked once. If it answers ESCALATE (held for review), the second analysis is asked once for each model you chose. If the first analysis could not read past records, the second is not asked, because a replay does not run the second analysis's own search.
  • Baselines: the person's and organization's baselines come from, in this order: those given with the replay; else those the package sealed with its decision ("sealed with the decision (as the decision read them)"); and, for a package sealed before baselines were stored, those CONTEXA keeps now ("as kept now (they may have changed since the decision)"). The answer says which one in baselines (GIVEN, SEALED or CURRENT).
  • State of the package: the answer also states the integrity of the sealed package: "intact since its seal", "changed after its seal: replayed from altered inputs" or "cannot be verified: the inputs may differ from the sealed ones". A changed package can still be replayed, so read this note before you read the result.
  • API: send one of these two requests.
    • POST /contexa/admin/api/sealed-decisions/{requestId}/replay
    • POST /contexa/admin/api/sealed-decisions/packages/{packageId}/replay
    The body is {"bundleVersion", "secondPassModels", "userBaseline", "organizationBaseline"}. bundleVersion holds the name of the prompt version, and at most 3 second-analysis models are allowed. The {requestId} in the path is the request (correlation) ID of the sealed decision. The names a replay accepts are listed by GET /contexa/admin/api/sealed-decisions/replay-bundles (the versions of the security decision that are not hidden, newest first). A hidden version is accepted by name too, because a sealed decision names the version it ran.
  • The AI model is really called, so it costs money. The result is not applied to any decision, learned or sealed. Only the audit record SEALED_DECISION_REPLAYED is written. Each analysis step waits at most 3 minutes. If the chosen version or the model differs from the original, the action can differ from the original decision.
  • When it fails: no sealed decision for that request ID or package gives 404; a name the list does not hold, or a bad request, gives 400; no decision pipeline in the application gives 503.
  • When it exists: the replay is there wherever sealed packages are kept, whether contexa.prompt-inspection.enabled is on or off. It is not there while contexa.enterprise.enabled=true.
POST /contexa/admin/api/sealed-decisions/7f3c2a/replay
Content-Type: application/json

{"bundleVersion": "v2.0", "secondPassModels": ["gpt-4o"]}

Retention

Sealed packages are not kept forever. They are deleted after the retention period.

  • A package expires 90 days after sealing (contexa.pqa.oss.sealed-evidence.retention.period), whatever the audit found in it. The expiry time is written into the package when it is sealed, so a change of the retention setting applies to packages sealed after the change. Expired packages are deleted every day at 03:30 (retention.cleanup-cron, in the server's time zone).
  • Kept past its expiry: a package that a prompt version trial decided again, a package a labelled case was added from, and the package of a decision an administrator evaluated stay for as long as that trial, case or evaluation is kept.
  • retention.clean-period (30 days) no longer removes anything. Earlier versions deleted a package whose last inspection found nothing wrong after 30 days. When the previous package is not in the store, the integrity check reads it this way: if the latest package still kept before this one is older than the shorter of clean-period and period, the gap is read as a deletion; if it is newer, the result is a broken link (LINK_BROKEN).

Limits

What sealed evidence shows is that a stored record has not changed since it was sealed. Keep these limits in mind.

  • Not every decision is sealed. Decisions that stopped the request and allowed decisions that may be misses are sealed up to the daily limit, and the rest by sample (When it is sealed). A decision that was not sealed cannot be looked at again this way. The same holds for packages dropped when the thread that builds and stores them falls behind.
  • It is not proof that a decision was right. Sealing shows that what the model received and answered has not changed. It does not show that the answer was right. The source-records check also compares only the structured facts that were sealed (on-call, assignment, approvals, delegation and so on) with the application's records, and counts a fact as not checked when the application's records cannot be read or are gone.
  • A signature means something only with a signing key you set. Without one, CONTEXA signs with a temporary key, and after a restart those signatures cannot be checked. Even with a key set, the signature method (HMAC) uses one shared secret, so anyone who knows the key can make signatures. Keep the key apart from the database.
  • The chain check goes back one package. Nothing walks the whole chain. The seal alone cannot tell that the last stored package was deleted (no later package points at it), or that a package was deleted from an old stretch the retention may already have reached. To find out, you need a record kept outside the database.
  • Packages are kept for a limited time. After the default 90 days a package is deleted, and after that it can be neither checked nor replayed (Retention).
  • A replay does not promise the original answer. A replay asks the model again and gets a new answer. With a different prompt version or model, the action can differ. A package found changed after sealing can still be replayed; the answer only marks that fact.

When it is on, and extension points

  • Sealing is on by default when contexa-iam is on the classpath and the CONTEXA database (contexa.datasource.*) is connected. While contexa.enterprise.enabled=true, the OSS sealing capture, the retention deletion, the evidence audit and the replay beans are not created.
  • To sign another way (a key management service, an HSM and so on), declare an EvidenceSigner bean. Decision audit records and sealed packages both use that signer.
  • To keep packages elsewhere, declare a SealedEvidencePackageRepository bean; to choose yourself which packages to seal, declare a SealedEvidenceCaptureSampling bean (it replaces the rules of When it is sealed).
  • To compare the decision facts with your application's own records yourself, declare a PromptFactSourceVerifier bean.

How sealed decisions become labelled cases, and how the quality of the prompt is measured on them, is in Prompt Quality Assurance.
