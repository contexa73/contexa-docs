Sealed Evidence and Official Verification

How to look again, later, at exactly which prompt and facts a decision was made from. It covers what is sealed and when, how to confirm nothing changed, how to view evidence in the admin console and run official verification and replay, and retention and settings.

At a glance

When the AI model makes a decision, Contexa seals the prompt exactly as sent to the model, its ingredients (request facts, canonical context, behavioral baseline, past decision records) and the decision result into one package with a hash and a signature. This package is the sealed evidence. Sealing never changes the decision and is stored separately after the decision is done.

What is sealed

One package holds seven sections.

Run information longer than 512 characters is kept as its length and hash only.

When it is sealed

  • Only decisions made by the AI model are sealed. A decision made without a model call has no prompt the model received, so nothing is sealed.
  • Requests without a user ID, failed processing and the paths /actuator · /health · /.well-known/ · /sse/ are not sealed.
  • Sampling: the first 1,000 decisions after startup and after a prompt bundle change are all sealed, then 1% (contexa.pqa.oss.sealed-evidence.full-capture-after-change, sample-percent). Each server (node) counts on its own.
  • Sealing sits after enforcement (55) and before audit (60) in the decision steps (56), but the package is assembled and stored on a separate thread. If that thread falls behind, the overflowing packages are dropped and the decision is not affected.
  • A captured prompt waits at most 10 minutes (snapshot-ttl) for the decision to finish and be sealed.

Confirming nothing changed

The package hash is SHA-256 over the seven sections, the prompt hashes, the schema number and more. With a signing key the package is schema 3: the tenant, the user, the sealing time and the previous package's hash are also hashed, and the hash is signed with HMAC-SHA256.

ResultMeaning
VERIFIEDThe recomputed hash matches and, for schema 3, so does the signature.
MISMATCHThe recomputed hash differs: the content changed after it was stored. A previous package that is gone without the retention explaining it (LINK_BROKEN) also belongs here.
UNVERIFIABLEThe hash or a prompt hash is empty, or no key can check the signature.

The SEAL_INTEGRITY check of the automatic inspection and official verification perform this check.

Adding signing keys

contexa:
  security:
    evidence:
      signing:
        keys:
          k2026: ${CONTEXA_EVIDENCE_KEY}   # Base64, at least 32 bytes
        active-key-id: k2026               # required with two or more keys
  • Without a key, a temporary key is made at startup and a WARN is logged. Signatures made with it cannot be checked after a restart (UNVERIFIABLE).
  • When you rotate keys, keep the retired key in the list so old signatures can still be checked. With two or more keys and no active-key-id, or one not in the list, the application does not start.
  • The decision audit records (ctxa_audit_log) are chained and signed by the same signer, and the security monitor of the admin console shows the result for each record. The result for sealed packages is shown on the inspection and official verification screens, not on the security monitor.
  • A sealed package holds the previous package's hash, and when one package is checked its previous package is looked for: if it is gone and the retention does not explain it, the result is MISMATCH (LINK_BROKEN). Nothing walks the whole chain.

Official verification

Official verification takes one sealed package and evaluates, with 12 metrics, whether that decision's prompt carried what the judgment needed. The evaluation uses rules and does not call the AI model. It first checks the package's integrity, then redraws the context sections of the prompt from the sealed canonical context and compares them with the sealed original (deterministic replay).

MetricWhat it checks
EIRDo the user, authentication, authority, resource and action of the request link into one security event?
CCRCan the information the judgment needs be told apart from what is missing?
CCSRDo values with the same meaning in the input never conflict?
PFRDoes the input carry every material needed to detect an attack?
MTRCan the input record, hashes and contract version be traced?
CORDo RAG and outside context stay out of the instructions and out-of-scope grounds?
RAPIs RAG evidence used only within the authorized scope and placed safely?
RPIDoes reverification or earlier-round information never contaminate the current judgment?
BMACan the judgment know the baseline's trust level and limits?
USNSCan subtle signals that differ from the user's baseline be seen?
BSRCan the session flow and behavior change be judged as a normal exception or an attack sign?
PREIs the target an actual protected resource?

Replay: asking again with another prompt bundle

Replay asks the same decision again with another prompt bundle, from the sealed inputs (request facts, authentication state, baseline summary, past records, canonical context). Use it to see how decisions on the same events would change before you put a new bundle into use.

  • On the "Sealed Prompts" detail screen, choose a prompt bundle and Layer 2 models under "Replay with a bundle" and confirm.
  • API: POST /contexa/admin/api/sealed-decisions/{requestId}/replay or POST /contexa/admin/api/sealed-decisions/packages/{packageId}/replay, body {"bundleVersion", "secondPassModels", "userBaseline", "organizationBaseline"}, at most 3 Layer 2 models. The {requestId} in the path is the request (correlation) ID of the sealed decision. The prompt bundles that can run: GET /contexa/admin/api/sealed-decisions/replay-bundles.
  • Layer 1 is asked once; if it answers ESCALATE, Layer 2 is asked for each chosen model. If Layer 1 could not read past records, Layer 2 is not asked.
  • The AI model is really called, so it costs money. The result is not applied, learned or sealed; only the audit record SEALED_DECISION_REPLAYED is written. The time limit is 3 minutes.
  • No sealed decision for that request ID or package gives 404; a prompt bundle this build does not run, or a bad request, gives 400; no decision pipeline gives 503.

Retention

  • A package expires 90 days after sealing (contexa.pqa.oss.sealed-evidence.retention.period) and is deleted every day at 03:30.
  • A package whose last inspection result is PASS or NOT_APPLICABLE and that no official verification used is deleted after 30 days (retention.clean-period).

When it is on, and extension points

  • Sealing is on by default when contexa-iam is on the classpath and the Contexa database (contexa.datasource.*) is connected.
  • To sign another way (a key management service, an HSM and so on), declare an EvidenceSigner bean. Decision audit records and sealed packages both use that signer.
  • To keep packages elsewhere, declare a SealedEvidencePackageRepository bean; to choose yourself which packages to seal, declare a SealedEvidenceCaptureSampling bean.

The automatic inspection that compares sealed prompts with facts is described in Prompt Governance and Inspection.
