Sealed Evidence

How to look again, later, at exactly which prompt and facts a decision was made from. It covers what is sealed and when, how to confirm nothing changed, the evidence audit, the sealed evidence screen, replaying a sealed decision, and retention and settings.

At a glance

When the AI model makes a decision, Contexa seals the prompt exactly as sent to the model, its ingredients (request facts, canonical context, the baselines the decision read, past decision records) and the decision result into one package with a hash and a signature. This package is the sealed evidence. Sealing never changes the decision and is stored separately after the decision is done.

What is sealed

One package holds seven sections.

  • Run information longer than 512 characters is kept as its length and hash only.
  • The baselines the decision read are sealed under one key of section 4, which the package hash has always covered: with the key the package says what was read (a baseline, or none), without it, as in a package sealed before this was added, nothing was kept. They are the values the analysis fixed when it read them, never read again while sealing, so a replay later reads what the decision read.

When it is sealed

  • Only decisions made by the AI model are sealed. A decision made without a model call has no prompt the model received, so nothing is sealed.
  • Requests without a user ID, failed processing and the paths /actuator · /health · /.well-known/ · /sse/ are not sealed.
  • Which decisions:
    1. The window after a change and a stable share, whatever the daily limit says: the first 1,000 decisions after a server starts and after the version decisions run changes (the label moved, a rollback, the setting) are all sealed, and otherwise 1% of the requests, chosen by a stable hash of the request ID (contexa.pqa.oss.sealed-evidence.full-capture-after-change, sample-percent). A version is told by its name and content hash. A version a canary or a shadow runs has a window of its own. Each server (node) counts the window on its own.
    2. A decision that stopped the request (CHALLENGE, ESCALATE, BLOCK) is sealed.
    3. An allowed decision is sealed when something says it may be a miss: the explanation the model marked most likely is not legitimate work, the second analysis decided, the model was asked again, at least unknown-fact-threshold (3) decision facts were unknown, or the personal baseline is not established. Other allowed decisions are left to the share.
    4. Rules 2 and 3 seal only while fewer than daily-limit (2,000) packages were sealed in the UTC day, counting every package of the day in the store, so servers that share a database stay near one limit (each reads the count every 30 seconds and may pass it by what it seals in between). Past the limit the day seals by rule 1 alone; the decisions left out are counted in the log at most every 10 minutes. 0 seals by rule 1 alone.
  • A sealed package takes about 60 KB of storage (measured on the sample decisions of the product), so the default daily limit adds at most about 120 MB a day.
  • Sealing sits after enforcement (55) and before audit (60) in the decision steps (56), but the package is assembled and stored on a separate thread. If that thread falls behind, the overflowing packages are dropped and the decision is not affected.
  • A captured prompt waits at most 10 minutes (snapshot-ttl) for the decision to finish and be sealed.
  • The review queue of the Zero Trust console draws sealed decisions while the capture runs, so a reviewed decision can be replayed and made a case (Prompt Quality Assurance).

Confirming nothing changed

The package hash is SHA-256 over the seven sections, the prompt hashes, the schema number and more. With a signing key the package is schema 3: the tenant, the user, the sealing time and the previous package's hash are also hashed, and the hash is signed with HMAC-SHA256.

ResultMeaning
VERIFIEDThe recomputed hash matches and, for schema 3, so does the signature.
MISMATCHThe recomputed hash differs: the content changed after it was stored. A previous package that is gone without the retention explaining it (LINK_BROKEN) also belongs here.
UNVERIFIABLEThe hash or a prompt hash is empty, or no key can check the signature.

The SEAL_INTEGRITY check of the evidence audit performs this check.

Adding signing keys

contexa:
  security:
    evidence:
      signing:
        keys:
          k2026: ${CONTEXA_EVIDENCE_KEY}   # Base64, at least 32 bytes
        active-key-id: k2026               # required with two or more keys
  • Without a key, a temporary key is made at startup and a WARN is logged. Signatures made with it cannot be checked after a restart (UNVERIFIABLE).
  • When you rotate keys, keep the retired key in the list so old signatures can still be checked. With two or more keys and no active-key-id, or one not in the list, the application does not start.
  • The decision audit records (ctxa_audit_log) are chained and signed by the same signer, and the security event log of the admin console shows the result for each record. The result for sealed packages is shown on the sealed evidence screen, not on the security event log.
  • A sealed package holds the previous package's hash, and when one package is checked its previous package is looked for: if it is gone and the retention does not explain it, the result is MISMATCH (LINK_BROKEN). Nothing walks the whole chain.

The evidence audit

The inspector (PromptInspector) audits each sealed package with three checks and counts, for each, what matched, what did not and what could not be checked. It points at problems for a person to review; it never changes a prompt, decision or rule, and it does not run on a decision thread.

Check (on the screen)What it compares
SEAL_INTEGRITY (Integrity)Whether the package hash still covers every sealed field, the system and user texts were captured and match their hashes, the prompt the model got is the drawn one or the difference is recorded, the request and correlation IDs are there, and the decision's output retries agree with its model call stages. A signed package (schema 3) is checked up to its signature
BUNDLE_TRACE (Trace of origin)Whether the prompt version the seal names is a release of the prompt release registry (a retired row counts), with that release's contract version, content hash and approval. A later release never turns an earlier prompt into a mismatch. Without a registry, the trace cannot be checked
SOURCE_TRUTH (Source records)Whether the facts the sealed decision collected are the host's own records of them. The source verifier (PromptFactSourceVerifier) reads its sources again for the sealed decision and gives, per fact, what the record says; the check compares it with what the sealed decision collected: the on-call record, the assignment, the approvals and the delegation of its canonical context. A fact the sealed decision names unknown is not a mismatch; a fact the sealed context keeps no value of is not compared. The default verifier reads Contexa's company records and delegations; a bean the application declares replaces it. Without a verifier the check records that no source is integrated
  • Verdicts: PASS (all matched), FAIL (one or more mismatches), INCOMPLETE (no mismatch but something could not be checked), NOT_APPLICABLE (the user text is not a dictionary prompt, so only the checks that do not read it ran), ERROR (could not be inspected). Findings are MISMATCH · UNVERIFIABLE; what could not be checked never counts as passing. The screen shows them as "All whole" (PASS, NOT_APPLICABLE), "With a problem" (FAIL) and "Not all checked" (INCOMPLETE, ERROR, not inspected yet).
  • Runs: every 30 seconds (contexa.prompt-inspection.interval, first after initial-delay), the oldest packages not inspected yet, 50 at a time (batch-size), under one lock across all servers. Packages are chosen by package ID hash within sample-percent (default 100).
  • Versions: each result keeps the inspector version (prompt-inspector/N, now 30) and, for a dictionary prompt, the dictionary it was read with. When the inspector version changes, packages are inspected again, and a package keeps the results of its latest and previous inspector versions.
  • Earlier packages: a package drawn with an earlier bundle (v19, v20, v21) keeps its bundle name until its retention ends and is audited by the checks that apply to it.
  • The audit no longer decides how long a package is kept (Retention). The checks that read the prompt's lines now check the renderer in the build; see What was removed.
  • The inspector, the automatic audit, inspecting again and the sealed evidence screen exist only when contexa.enterprise.enabled is not true and contexa.prompt-inspection.enabled is true (default). Turning the inspection off leaves the replay and the prompt version trials on.

Replay: asking again from the sealed inputs

Replay asks the same decision again from the sealed inputs (request facts, authentication state, canonical context, past records, baselines) with a version you choose. The measurement of prompt quality uses the same replay on labelled cases (Measuring a version); to compare two versions on recent sealed decisions, use the trial in Measure & compare (Trial decisions).

  • On a package's page, "Replay" asks for the version and, optionally, the second-pass models ("Optional, comma separated, at most 3"): "A replay calls the model (once more per second-pass model). Nothing is applied, learned or sealed; it is audited."
  • Baselines: those given with the replay, else those the package sealed with its decision ("sealed with the decision (as the decision read them)"), and for a package sealed before the baselines were, the person's and organization's baselines as kept now ("as kept now (they may have changed since the decision)"). The answer says which in baselines (GIVEN, SEALED or CURRENT).
  • The answer also states the sealed package's integrity: "intact since its seal", "changed after its seal: replayed from altered inputs" or "cannot be verified: the inputs may differ from the sealed ones".
  • API: POST /contexa/admin/api/sealed-decisions/{requestId}/replay or POST /contexa/admin/api/sealed-decisions/packages/{packageId}/replay, body {"bundleVersion", "secondPassModels", "userBaseline", "organizationBaseline"}, at most 3 Layer 2 models. The {requestId} in the path is the request (correlation) ID of the sealed decision. The names a replay accepts: GET /contexa/admin/api/sealed-decisions/replay-bundles (the versions of the security decision that are not hidden, newest first); a hidden version is taken by its name too, as a sealed decision names the version it ran.
  • Layer 1 is asked once; if it answers ESCALATE, Layer 2 is asked for each chosen model. If Layer 1 could not read past records, Layer 2 is not asked.
  • The AI model is really called, so it costs money. The result is not applied, learned or sealed; only the audit record SEALED_DECISION_REPLAYED is written. The time limit is 3 minutes.
  • No sealed decision for that request ID or package gives 404; a name the list does not hold, or a bad request, gives 400; no decision pipeline gives 503.
  • The replay is there wherever sealed packages are kept, whether contexa.prompt-inspection.enabled is on or off; it is not there while contexa.enterprise.enabled=true.

Retention

  • A package expires 90 days after sealing (contexa.pqa.oss.sealed-evidence.retention.period), whatever the audit found in it, and expired packages are deleted every day at 03:30 (retention.cleanup-cron).
  • Kept past its expiry: a package that a prompt version trial decided again, a package a labelled case was added from, and the package of a decision an administrator evaluated stay for as long as that trial, case or evaluation is kept.
  • retention.clean-period (30 days) no longer removes anything. Earlier versions deleted a package whose last inspection found nothing wrong after 30 days; the integrity check still reads a package missing before one older than the shorter of clean-period and period as such a removal, not as a broken link.

When it is on, and extension points

  • Sealing is on by default when contexa-iam is on the classpath and the Contexa database (contexa.datasource.*) is connected. While contexa.enterprise.enabled=true, none of the OSS sealing beans are created.
  • To sign another way (a key management service, an HSM and so on), declare an EvidenceSigner bean. Decision audit records and sealed packages both use that signer.
  • To keep packages elsewhere, declare a SealedEvidencePackageRepository bean; to choose yourself which packages to seal, declare a SealedEvidenceCaptureSampling bean (it replaces the rules of When it is sealed).
  • To compare the facts with your own records, declare a PromptFactSourceVerifier bean.

How sealed decisions become labelled cases, and how the quality of the prompt is measured on them, is in Prompt Quality Assurance.
