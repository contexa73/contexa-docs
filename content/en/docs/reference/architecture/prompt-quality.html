Prompt Quality Assurance

How Contexa measures whether the security decision prompt decides right, and keeps a version that decides worse from deciding without a reason. It covers the labelled cases a version is graded against, the measurement and its metrics, the wrong cases and their causes, the quality gate, what operation adds to the cases, the quality report, and what a decision records about its prompt.

At a glance

Quality is measured on decisions, not on the wording of a prompt. A version of the security decision prompt is run on labelled cases, decision inputs with their right answer, and its answers are graded against them by rules. When a version is to be used for decisions, the quality gate compares its measurement with the one of the version in use. Operation closes the loop: a decision an administrator rated, or an allowed decision later found to be a breach, becomes a case.

  • Rules grade, a model does not: an answer is right when its action is one of the case's allowed actions. No model grades an answer.
  • Every rate has its sample: a rate comes with its 95% range, counted by distinct root cases. When the cases cannot tell two versions apart, the screens say "Undecided".
  • The security decision only: labelled cases, measurements and the quality gate exist for cortex.security-decision. The seven other prompts with versions (Prompt Versions) have none.
This replaces the prompt inspection and the official verification. The official verification (12 metrics, 66 checks, and the "Protected Candidates", "Official Inspection" and "Inspection Overview" screens), the scoring of the sealed structure and the deterministic replay are removed. The inspection of sealed packages keeps three checks as the evidence audit (Sealed Evidence). What an upgrade changes is in What was removed, and upgrading.

Labelled cases

A labelled case is a decision input with its right answer. The input is what the replay of a sealed decision reads (the canonical context, the request facts, the authentication state, the baselines and the past records), not the text of a prompt, so a case is drawn again in whatever form a version gives the prompt. Cases are kept apart from the sealed decisions of operation; a replay builds the sealed form in memory.

The right answer

On the screenWhat it holds
Right answer (allowed actions)The actions that are right, one or more (for a threat, for example BLOCK, CHALLENGE and ESCALATE). An answer is right when its action is one of them
Preferred actionOptional; one of the allowed actions
What it isThreat, Normal or Uncertain. An uncertain case counts as a case that must be stopped, as a threat does
KindOutsider (someone else with the account), Insider (the account's owner doing what the role or the records do not cover), Normal work, Automation
Case gradeOrdinary, Must catch (such as an account takeover the server itself confirmed), Must not block. The gate lets no answer of a "Must catch" case allow and no answer of a "Must not block" case block, not in a single run
Why it is rightRequired, in Korean, English or both
Facts that decide itOptional, one a line (for example intent.anomalySignal=CONFIRMED_ACCOUNT_TAKEOVER). The cause "Input missing" is computed only for cases that name them
  • Roots: a case made from another case names that case's root. Variants of one decision are not independent, so the 95% ranges and the numbers of cases the gate needs are counted by distinct roots: variants alone do not fill a target.
  • Where a case comes from: "Contexa default" (the default set), "From operation" (a sealed decision an administrator added, or a decision rated in the decision detail, Connected to operation) and "Made by us" (a copy of another case with values changed, such as a new device, an outside address or an approval record taken out). A case from operation that the second analysis decided is marked and counted apart.
  • Fixed environment: a case keeps the time zone and the context format it is read in, and is replayed in its own time zone and with the versions of its own scope, whatever the server's time zone.

The Contexa default set

The product ships a default set of 70 cases, read only. They are 25 sealed decisions, 35 controlled variants made from 10 of them, and 10 control cases (keys VER-…) that carry a malicious signal the server verified, graded "Must catch", with BLOCK as their only right action. The 60 ordinary cases are 15 of each kind (44 threats, 1 uncertain, 15 normal) and count as 25 distinct roots to stop and 10 to allow. Every case says why in Korean and English, the 45 variants name the facts that decide them, and every case is read in UTC. The default set has no "Must not block" case.

  • A case of the default set is changed by copying it ("Copy to a new case"); the copy is counted under the same root.
  • Upgrading the product changes the default set only; your cases stay as they are.

Confirmation by a second administrator, and publishing

  • Two people set an answer. A case, and each change of its answer, waits ("To confirm") until an administrator other than the one who set the answer confirms it: "The administrator who set the answer cannot confirm it." A case labelled wrongly on purpose (an attack marked normal) would let a version that allows the attack pass. An installation with one administrator turns this off with contexa.pqa.oss.quality.two-person-confirmation=false: cases are then confirmed as they are submitted, and every change of an answer is still kept with who made it.
  • Publishing ("Publish the bundle") fixes the default set of this build and the confirmed cases of the scope by their content hashes. "The gate reads the published bundle. Publishing fixes the list of cases, and only the added cases are measured again." A case waiting for confirmation is not in it, and the same cases published again are the bundle published before. With nothing published in a scope, the first automatic measurement publishes the default set alone.
  • Changing an answer keeps the answer it replaces. The case detail shows "Answers better by changing the answer": the answers right on the present answer that were wrong on the answer the case was added with, counted apart because no version made them better.
  • Each step is audited: PROMPT_QUALITY_CASE_SUBMITTED, PROMPT_QUALITY_CASE_ANSWER_CHANGED, PROMPT_QUALITY_CASE_CONFIRMED, PROMPT_QUALITY_CASE_SET_PUBLISHED.

Personal data

A case from operation "holds a real user, real addresses and that user's baseline, and outlives the seal retention (90 days)". It stays in the Contexa database. Deleting a case deletes its answer changes and the answers measured on it, and a published bundle that held it reads it as missing. Deleting the user deletes the user's cases. The sealed package a case was added from is kept for as long as the case is. The quality report never reads the input of a case or why it is right (The quality report).

The labelled cases screen

  • Head: "Published bundle {version} · {when} · {n} cases" and the cases added since, with the buttons "Add from a sealed decision" (a decision that is not sealed is refused, NOT_SEALED), "New case" and "Publish the bundle".
  • Numbers: "Cases to stop" and "Cases to pass" (distinct roots of the published bundle against the target the gate needs, 200 and 300 by default), "Chance to tell a better version" and "To confirm".
  • "Chance to tell a better version" is the chance that the distinct roots to stop tell apart a version that misses 10 points less, by the gate's paired comparison at its level. It is computed exactly, taking the miss rate of the version in use, the roots as independent and the two versions' results as correlated by 0.7. Until the targets are met, comparisons come out "Undecided".
  • "Cases by resource grade" (Critical, Sensitive, General, Public), from the resource class the decision records keep: the roots to stop and to pass of the published bundle beside the decisions of the last 7 days, marked "Covered", "Few cases" (a side has fewer than 5 roots, the fewest a paired comparison of the grade can be significant with), "No case" or "No decision". "A measurement measures a version, not a resource": where operation decides and few cases cover the grade, the average hides a worse result there.
  • The list (All, To confirm), with filters such as the resource grade and the case name: the case, class and kind, right answer, case grade, resource and grade, and its result in the latest measurement of the version in use ("Right", "Missed", "Off the answer", "Not measured", "To confirm"). Actions: Copy, Confirm, Delete, Change the answer.
  • A case's detail: the right answer, why, the facts that decide it, the decision input in words rather than codes (Request, Session, Unlike usual, Work records, Unknown; values such as "Yes", "No", "Allow", "Deny"), the results by version with the action of each run, and the answer changes.

Measuring a version

A measurement is one prompt version, under the model setting the server runs, on one published bundle, each case run a number of times: 3 by default, 1 to 10. Each answer is the case's input replayed through the engine's decision pipeline, as a sealed decision is replayed, in the case's own time zone and with the versions of the case's scope: the prompt drawn with the version, the response check, the corrective retry and the fallback action. After a first answer of ESCALATE the second pass is asked with the server's second-layer model.

BasisWhat it counts
First answer"The answer the model gave with the prompt. It tells the prompt's quality, and the gate reads it."
Final action"The action after the engine's closing rules. It tells what the user meets." The closing rules are computed from the server's settings: the second pass after an ESCALATE, an action of the second pass that is none of the four replaced by CHALLENGE, and an ESCALATE left after it ending in the terminal action the server is set to. The overload protection depends on the load of the moment, so it is not replayed, and the result says so
  • The model setting of a measurement is every server setting that changes an answer: the models each layer asks (its own model, else the primary chat model, which the screens name), the options of each layer's request (output limit, reasoning effort, verbosity, thinking, budget profile), the determinism of the call, the structured output, the prompt's truncation and argument excerpts, the minimum action rules and their mode, what an ESCALATE left after the second pass ends in, and the context format. Timeouts, caches and the model gate are not in it, nor is the server's time zone: a case is drawn in the time zone it fixes, so changing the server's time zone leaves the measurements current. Two measurements are compared only under the same setting; a measurement taken under a setting the server no longer runs is stale.
  • Behind the decisions: a measurement waits in the server's line with the trials of the version screens, and its model calls wait behind real decisions at the model server's gate, contexa.pqa.oss.quality.measurement.concurrency at a time (1 by default; the gate of a self-hosted server has 2 slots, a remote provider 16).
  • One server at a time runs measurements, under a lock of the database with a heartbeat (heartbeat, 30 s). A server that stops leaves the measurement to another within about two and a half minutes, which resumes it from the answers taken. "Cancel" is written to the database, so the server running it stops at its next answer.
  • A busy model server does not count against the prompt. A replay the model server gave no answer to (busy, unreachable, a time limit) is asked again 2 more times, after 15 s and then 30 s. An answer that still did not come, or a case that could not be read, enters no metric, and the measurement shows "Incomplete, {n} answers".
  • Calls are counted before it starts: "About {cases} cases × {runs} runs = {calls} calls · about {minutes} min · limit {limit}", and "{n} answers measured already under the same setting are used again"; measured anew, every answer counts as a call. An answer makes at least one call and at most four for each attempt (the first pass and its corrective retry, the second pass and its retry): the default set run 3 times makes at least 210 calls and at most 2,520 with the default retries. A measurement that would make more calls than contexa.pqa.oss.quality.measurement.call-limit (3,000) does not start; one that reaches it stops and ends failed. The screen reckons about 7 seconds an answer.
  • Answers are used again: an answer kept for the same case content, version, model setting and run is not measured again, so a bundle published with new cases is measured on the new cases only. "Measure again without the kept answers" (API anew) asks every answer of the model anew, at least one call each; the list marks such a measurement "measured anew". A measurement started without it, "Save and measure at once" and the automatic measurement of a version without one use the kept answers.

The 11 metrics

A value is the mean of the runs. Each rate's 95% range is a Wilson interval with the distinct roots as its sample: the variants and runs of a root do not narrow it.

MetricDefinition
Miss rateOf the answers to cases that must be stopped, those that allowed. A case classed uncertain counts as one to stop
False stop rateOf the answers to cases that must be allowed, those outside the allowed actions
Friction rateOf the answers to cases that must be allowed, those that did not allow: it finds a version that asks every request to step up
Over-blockingOf the answers to cases whose right answer has no BLOCK, those that blocked
Action hit rateOf all answers, those inside the allowed actions
Deferral rateOf all answers, those whose first answer is ESCALATE: it finds a version that only defers
ConsistencyOf the cases with two or more answers, those whose answers all took the same action. It needs 2 runs or more
Citation accuracyOf the facts the answers cite, those in the prompt that the response check did not name
Asked againOf all answers, those that broke the answer contract and were asked again
Set without the modelOf all answers, those the engine decided because the model's answer could not be used
Decision time and answer tokensThe median and the 95th value. Shown, not judged

Comparing two versions

  • Two measurements are compared only when taken the same way: the same bundle version, model setting and number of runs ("Same conditions: bundle {version} · {models} · {n} runs").
  • Case against the same case: for each rate, each root holds the cases both measurements scored, and is worse, better or unchanged by its own rate. The exact one-sided sign test over the roots that changed says whether so many could turn one way by chance (the exact McNemar test when a root is one answer), at contexa.pqa.oss.quality.gate.significance (0.05).
  • Verdicts: "Same" (no difference, or one within the noise of the rate), "Better" or "Worse" (beyond the noise, and the test rejects chance), "Undecided" (nothing is paired, the noise is not known, or too few roots changed to tell). Counting changed cases alone would stop the same prompt one time in four to one in two.
  • The noise is how far the newest two measurements of one version taken the same way differ, of the version in use first, else of the candidate, when each has answers of its own: taken anew, or finding no kept answer to use again. A measurement that used answers kept from another shows no noise and is not read for it. "The difference of two measurements of one version taken anew is the noise the quality gate reads": measure the version in use anew twice, or let the weekly measurement do it (Measured again on schedule). Without such a pair the screen says the noise is "not known yet, so a difference is "undecided"".
  • Our cases apart: "Default bundle and our cases" shows the misses of each apart: "The default bundle does not stand for your environment and was used to make the product version, so it favours it."
  • Cases added after the version: the cases that came in after the version was made, which its author could not see. "A worse result only here hints at a version fitted to the cases seen." The gate's eleventh condition reads them.

The quality gate

When a version of the security decision is used for decisions or started as a canary, the release gate reads the quality gate: the candidate's measurement against the measurement of the version in use, on the latest published bundle of the scope, on the first answer basis. The other seven prompts take no quality condition.

#Condition (as the confirmation names it)When it does not hold
1Both versions measured on the same case set version, model setting and runsBlocks. A missing measurement fails it too
2No "must catch" case was ever allowedBlocks
3No "must catch" case newly answered outside its allowed actions (such as a challenge or a deferral where a block is right)Blocks when the candidate answers such a case outside its allowed actions, other than by allowing it, in any run, and the version in use never did. A case the version in use also answers outside them only warns, as it is not the candidate's doing; without a comparable measurement of the version in use every such answer counts against the candidate
4No "must not block" case was ever blockedBlocks
5Misses did not rise significantlyBlocks
6False stops, over-blocking, friction and deferrals did not rise significantlyBlocks
7Friction did not rise by the limit or more, whatever the significanceBlocks when the candidate's friction rate is higher than that of the version in use, on the same cases, by friction-increase-limit (0.20, 20 points: three more of the fifteen such answers of the default set run once) or more. It stops a version that challenges every request even where too few roots are left for the exact test of condition 6
8Set without the model within its limit, citation accuracy not significantly lowerBlocks above model-less-limit (5%) or when citation accuracy is worse

  • "Significantly" is the paired comparison of Comparing two versions: only a difference beyond the noise of one version measured twice blocks. Conditions 2, 3 and 4 allow not a single answer, and condition 7 blocks on the size of the rise alone.
  • With the default set alone (25 roots to stop, 10 to pass) condition 10 always warns.
  • When every condition holds, the confirmation says "All {n} conditions passed."

Warning or blocking, and the reason that overrides

  • WARN (the default of contexa.pqa.oss.quality.gate.mode): a verdict that blocks is applied as a warning: "The gate is in the warning mode, so the blocking conditions ({n}) are applied as warnings." The verdict itself is kept as computed.
  • BLOCK: a blocking condition stops the version unless an administrator writes a reason ("Use with this reason", "Start with this reason"). "A reason lets it through; who let it through and why is kept in the audit records" (PROMPT_VERSION_QUALITY_GATE_OVERRIDDEN). A blank reason is refused. An urgent new version that fixes a failure goes this way too. The setting says to set BLOCK once the reproducibility and discrimination checks have passed on the installation.
  • A reason overrides only a quality block: "Something other than quality blocks it too, so a reason cannot let it through."

The confirmation

  • The confirmation of "Use for decisions" and of "Start the canary" shows the gate's state and a line, then under "Quality gate · case set {version} · {models} · {n} run(s)" the conditions that matter: when the verdict blocks, only the blocking conditions are open; otherwise the warnings are. The rest fold into "{n} passed", "{n} warnings" and "{n} not looked at".
  • The newly missed cases open in Measure & compare ("Show the {n} newly missed cases"). When there are such cases and the verdict does not block, "I have read the newly missed cases" is ticked before going on.
  • The confirmation shows the latest trial ("Tried", "Not tried") only when the quality gate could not be read.

Going back, and versions that decide outside the gate

  • Going back to a version the scope used for decisions before takes no quality condition ("Passed (going back)"). A rollback, an emergency rollback too, goes only to such a version; any other target is refused. A version counts as used for decisions when it decides now, was applied as ACTIVE, was the target of a rollback that was not refused, or is named in the rollback records; a version that only ran as a canary does not count.
  • Two ways reach the decisions without the gate: the version contexa.security.tiered.prompt-bundle.active names, and the newest Contexa version an upgrade brings when no version is chosen on the screen. The version list says so ("{version} decides as the setting names it, without passing the release gate.") with the state of its measurement in this environment, and Contexa measures such a version once on its own.
  • Right after an upgrade the version in use has no measurement. Contexa measures it once by itself on the latest published bundle, publishing the default set first when the scope has none (the default set run 3 times is 210 answers, and model calls are made); until then the gate only warns. A Contexa version whose measurement the product ships, taken the same way here, is not measured again. A version in use measured under other settings only is measured once again; this is looked for every 10 minutes.
  • The gate's answer is in GET /contexa/admin/api/prompt-quality/versions/{number}/use-check (?target=CANARY for a canary) under quality: mode, measurement, verdict (as computed), applied (PASSED, WARNING or BLOCKED), rollback, overridable, rows (the eleven conditions), changes and details. POST /{number}/use and /canary/start take overrideReason (Prompt Versions API).

Connected to operation

What is sealed

Decisions that stopped the request (CHALLENGE, ESCALATE, BLOCK) and allowed decisions with a sign of risk are sealed first, up to 2,000 packages a UTC day, besides the window after a change and the 1% share. A seal now keeps the baselines the decision read, so a replay later reads what the decision read (When it is sealed).

The review queue samples allowed decisions by risk

A random sample of allowed decisions hardly ever finds a miss: with one miss in 10,000 allowed decisions, 20 a day find one in 500 days on average. So the review queue (Zero Trust → Decision records, ?view=review) draws each UTC day:

  1. up to contexa.security.zerotrust.console.review-daily-sample (20) stopped decisions, at random;
  2. up to review-risk-sample (10) allowed decisions with a sign that they may be misses: the explanation the model marked most likely is not legitimate work, the second analysis decided, the model was asked again, at least contexa.pqa.oss.sealed-evidence.unknown-fact-threshold (3) decision facts were unknown, or the personal baseline is not established; and the allowed decisions of a user blocked that day, looking back review-blocked-lookback-days (7) from the block, unless an administrator released the block or judged it wrong. Those before a block come first, then those with more signs;
  3. up to review-allowed-sample (5) allowed decisions without a sign, at random, to fill the number of ordinary cases.

While the sealed evidence capture runs, only sealed decisions are drawn, so a reviewed decision can be replayed and made a case. Test runs are not drawn, and the allowed decisions of a day are drawn once. With the defaults the queue takes up to 35 decisions a day instead of 20.

Evaluate and add as a case, and breaches after an allow

  • "Evaluate and add as a case" in a decision's detail keeps the evaluation and a case with the right answer you set: "The evaluation and the case are kept together or not at all. The case uses the sealed input." A decision that is not sealed cannot become a case: "This decision is not sealed, so it cannot become a case; the evaluation alone is kept." The case belongs to the platform scope and waits for a second administrator like any case.
  • "Confirm a breach after the allow" on a decision that allowed records the outcome ALLOWED_BREACH_CONFIRMED ("Allowed, later confirmed a breach") with an optional note. It counts as a miss seen in operation; recording it again keeps the first record, and only a decision that allowed can be confirmed. The outcome filter of the decision records has the value.
  • The sealed evidence screen ("Add as a case"), the labelled cases screen ("Add from a sealed decision") and a trial's result (a decision the two versions decided differently) add a sealed decision as a case too.

Measured again on schedule

  • At contexa.pqa.oss.quality.remeasure.cron (0 0 2 * * SUN, UTC; - turns it off) the version in use of every scope is measured again on the bundle its measurements run on. One server runs it.
  • The scheduled measurement is taken anew, without the kept answers, so that a version that came out worse under the same settings is found and two such measurements give the noise: it calls the model every week, about 210 calls for the default set run 3 times (at most 2,520 with the retries of a busy model server). A measurement the schedule could not finish is tried again.
  • A measurement taken again is compared with the version's measurement before; one that came out worse or changed is logged as a warning and shown on the quality screen. The product has no other notification of administrators.

The quality screen

  • Head: the version in use and since when (the first hour it decided within the last 90 days), its latest measurement (bundle, models, runs), a sentence on its misses, the period of the operation numbers (day, week by default, month, quarter) and the "Quality report" button.
  • "Version in use": whether its measurement is current or stale, the bundle, the model setting, the runs and "Next scheduled".
  • "Measured on the cases": the 11 metrics with their 95% ranges.
  • "Seen in operation": six numbers counted from the real decisions of the version in use and of the version before it, over periods of the same length on each side of the change: Stopped, Step-ups passed, Blocks released, Reviewed as right, Asked again, Set without the model. They are not graded against right answers.

The quality report

"Quality report" on the head of the quality screen exports, for a scope and a period of whole UTC days ("First day (UTC)", "Last day (UTC)"; 90 days by default, at most 400), one zip: report.json for a machine and report-ko.md and report-en.md for people. It asks no model.

SectionWhat it holds
1. Accuracy of the version in useThe measurements of the version in use and of the versions before it. Declaration of the accuracy metrics (EU AI Act, Article 15)
2. Case set versionsThe bundles the measurements ran on
3. Monitoring in operationThe operation numbers of the period. Monitoring after the release (EU AI Act, Article 72)
4. Overturned decisionsThe blocks an administrator released, the decisions an administrator rated wrong and the allowed requests confirmed as breaches. Monitoring of the decisions people overturned (NIST AI RMF, MANAGE)
5. Changes and approvalsThe changes of the versions and who approved them
6. MaskingThe masking rules the report was made with
  • The people the decisions and cases are about get pseudonyms: a keyed hash under a key drawn for this report and never written, the same person the same pseudonym within the report and another one in the next.
  • Texts administrators wrote (a reason, a note, a title) are kept, with the identifiers of such people replaced by their pseudonyms and every e-mail address and IP address replaced by a mark.
  • Never read into the report: the input of a case, why it is right, a decision's request, path, address, session or summary, and the note an administrator wrote on an overturned decision (its reason code is in it).
  • The administrators who acted are named as they are: the report is the record of who approved what.
  • API: GET /contexa/admin/api/prompt-quality/report?scope=&from=YYYY-MM-DD&to=YYYY-MM-DD; a period that starts after it ends or is longer than 400 days answers 400.

What a decision says about its prompt

A decision's prompt execution information, and its sealed evidence, name the prompt it was drawn with in two ways.

  • The version: its name (v2.0), what chose it and its content hash, as fixed on the event when the decision started (promptBundleSelection.version, .source, .contentHash). The decision record keeps the version name and the content hash.
  • The governance descriptor of the template: prompt key cortex.security-decision, template key, release 2026.11.16-v1.0 (a bundle name, so the product default 2026.11.18-v1.0 and the versions on it carry it too), output contract CORTEX_PROMPT_CONTRACT_V5, the user text layout v1.0-dictionary-blocks, and the release's hash. The trace check of the evidence audit compares the sealed descriptor with its release in the registry. The manifests of the earlier bundles v19, v20 and v21 are gone.

The order is in How a decision's version is chosen. Labels are read through the registry, cached for up to 60 seconds with an invalidation check every 5 seconds.

The registry behind the versions

Each version has one row in the prompt governance registry, and the screen's actions move the row's state through the release gate, which reads the quality gate for the security decision. The states keep their vocabulary (PromptBundleState); the screen shows them in its own words.

Registry stateOn the screen
ACTIVEUsed for decisions
CANARYCanary
SHADOWRunning alongside
AVAILABLENot used (a new version starts here)
DEPRECATEDNot used (a row an earlier bundle left; read as AVAILABLE)
RETIREDHidden
  • A move the gate refuses changes nothing and is recorded with its reasons; an applied move changes the registry state and the approval and rollback records, and announces a runtime cache invalidation. Moving a version to ACTIVE turns the other ACTIVE version of the same tenant and prompt into AVAILABLE (a bundle's row into DEPRECATED). A version used for decisions, a canary or a version run alongside goes back to AVAILABLE when it stops; a hidden version takes no state.
  • At start every server registers the build's product defaults as versions (the first installation's v1.0, an upgrade's next numbers) and retires the registry rows that name an earlier bundle. Those rows are kept: the trace check of earlier sealed decisions reads them.
  • Rollback, emergency rollback with a second administrator's approval, canary and running alongside are done on the version screens (Use for decisions and rollback).

What was removed, and upgrading

  • Removed: the official verification of a sealed package (12 metrics, 66 checks, its runs, results and reverification) with its screens "Protected Candidates" (/contexa/admin/prompt-quality/resources) and "Official Inspection" (/contexa/admin/prompt-quality/runtime-evidence) and their APIs, the "Inspection Overview" screen and its API GET /contexa/admin/api/prompt-inspection/overview, the scoring of the sealed structure and the deterministic replay.
  • The inspection checks: three stay as the evidence audit of sealed packages (SEAL_INTEGRITY, BUNDLE_TRACE, SOURCE_TRUTH). The six that read the prompt's lines (DICTIONARY_CONTRACT, DECISION_FACT_MATCH, FACT_ACCURACY, UNKNOWN_DECLARED, PAST_RECORD_NOTATION, SAME_FACT) check the renderer in the build over the golden inputs instead, and the citation check of REASON_MATCH runs on the decision path for every decision, its result kept with the decision record. The inspector is version 30 (prompt-inspector/30), so the sealed packages are inspected again with the three checks.
  • Removed settings: contexa.pqa.official-verification.stale-execution-timeout, contexa.pqa.routes.official-api-root, contexa.pqa.routes.enterprise-api-root, contexa.pqa.routes.enterprise-verification-runtime-runs-path. They are no longer read.
  • The capability PQA_ENGINE is gone. A value left in contexa.capability.required that names no capability of this version, such as pqa-engine, decides nothing: the start logs one warning ("Ignoring contexa.capability.required.pqa-engine: this version has no such capability …") and goes on. Remove the key. The settings object now keeps required as a map from the key to its value (Map<String, Boolean>), so code of the application that calls ContexaCapabilityProperties.getRequired() must take that type.
  • The 58 tables of the official verification are not created on a new installation, and an existing installation keeps them: Contexa never drops them by itself. The script META-INF/contexa/db/drop-retired-official-verification.sql of contexa-iam drops them; run it by hand against the Contexa database (for example psql -f drop-retired-official-verification.sql), and only after the upgrade: an older version reads a database without these tables as a partial installation and refuses to start.
  • What an upgrade changes in operation: the new version screen of the security decision saves and measures instead of using a version for decisions at once (Prompt Versions); the first start measures the version in use (210 answers, with model calls); the version in use is measured again anew every week (about 210 model calls with the default set); the review queue takes up to 35 decisions a day; stopped decisions and risky allowed ones are sealed up to 2,000 a day; a sealed package is no longer deleted after 30 days because its inspection found nothing (Retention); and the trials of the version screens wait behind the measurements in one line.
