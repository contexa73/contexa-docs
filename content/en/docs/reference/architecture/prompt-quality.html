Prompt Quality Assurance

How CONTEXA checks that the security decision prompt makes good decisions, and stops a worse version from going live without a stated reason. This page covers the labelled cases a version is graded against, how a version is measured, the wrong answers and their causes, the quality gate, how real decisions feed back into the cases, the quality report, and what each decision records about the prompt it used.

At a glance

Prompt Quality Assurance tells you whether a version of the security decision prompt makes good decisions, before you let that version decide for real. It works in three steps.

  1. You keep a set of labelled cases. Each case is a decision input (the facts about one request) together with the answer that is right for it.
  2. CONTEXA measures a prompt version. It replays every case through the version and counts how often the answers are right. Rules do the grading, not an AI model.
  3. When you want to use a version for decisions, the quality gate compares its measurement with the measurement of the version in use. If the new version is worse, the gate warns or blocks.

Real operation feeds the cases. An administrator can rate a real decision and add it as a case. An administrator can also record that an allowed request later turned out to be a breach, which counts as a miss seen in operation.

  • Rules grade the answers. An answer is right when its action is one of the actions the case allows. No AI model grades an answer.
  • Every rate shows how much data it rests on. A rate comes with its 95% range, which is computed from the number of distinct root cases. When there are too few cases to tell two versions apart, the screens say "Undecided".
  • Only the security decision prompt has these. Labelled cases, measurements and the quality gate exist for cortex.security-decision. The seven other prompts that have versions (Prompt Versions) have none.

These words have a fixed meaning on this page.

  • Action: a decision ends in one of four actions. ALLOW lets the request through, CHALLENGE asks for step-up authentication, ESCALATE holds the request for review, and BLOCK refuses it.
  • Version: one complete, unchangeable text of the security decision prompt, numbered v1.0, v2.0 and so on (Prompt Versions).
  • Case and root case: a case is one labelled test situation. A case made from another case is a variant, and it counts under the root, which is the original case. Variants of one case are not independent evidence, so ranges and required numbers of cases count roots.
  • Bundle: a published, fixed list of cases. A measurement runs on one bundle, and the gate reads the latest published bundle.
  • Measurement: one version run over every case of a bundle, each case several times.
  • Sealed decision: a real decision whose prompt, facts and answer CONTEXA saved when it was made, so that it can be examined or replayed later (Sealed Evidence).
  • Scope: the tenant whose prompt versions, cases and measurements a screen shows. Without a scope, a screen shows the whole platform.
  • First analysis and second analysis: a decision has at most two steps (Decision Engine). The first analysis (Layer 1) asks the AI model for an action. Only when that action is ESCALATE, which means "these facts cannot decide it", the second analysis (Layer 2) decides the same request once more.
  • Canary: a version that decides for only a share of requests, while the version in use decides for the rest.
This replaces the earlier prompt inspection and official verification. The official verification (12 metrics, 66 checks, and the "Protected Candidates", "Official Inspection" and "Inspection Overview" screens), the scoring of the sealed structure and the deterministic replay are removed. Three of the inspection checks remain, as the evidence audit of sealed packages (Sealed Evidence). What was removed, and upgrading lists what an upgrade changes.

Labelled cases

A labelled case is a test situation for the prompt. It holds the facts of one request and the actions that are right for that request. A measurement grades a prompt version by how often its answers fall inside those right actions.

The facts are the input that a replay of a sealed decision reads: the canonical context (CONTEXA's standard record of the user, device, resource and session), the request facts, the authentication state, the baselines (the usual behavior of the user and of the organization) and the past records. A case holds no prompt text. Each prompt version draws its own prompt from the same facts, in whatever form that version uses. Cases are kept apart from the sealed decisions of operation, and a replay rebuilds the sealed form in memory.

The right answer

You set these fields when you add a case. The gate later holds every version to them.

  • Roots. A case made from another case records that case as its root. Variants of one decision are not independent evidence. The 95% ranges and the numbers of cases the gate needs therefore count distinct roots, and variants alone cannot fill a target.
  • Where a case comes from. The screen labels the origin of each case. "Contexa default" is the default set. "From operation" is a sealed decision that an administrator added, or a decision rated in the decision detail (Connected to operation). "Made by us" is a copy of another case with some values changed, for example a new device, an outside address or an approval record taken out. A case from operation that the second analysis decided is marked and counted apart. The reason is that the sealed package then holds the input of the second analysis, so the first analysis replayed from it may see a different input than the original first analysis did.
  • Fixed environment. A case records the time zone and the context format it is read in. A replay uses that time zone and the prompt versions of the case's own scope, whatever the server's time zone is.

The CONTEXA default set

The product ships a default set of 70 cases, so you can measure a version before you add any case of your own. The set is read only.

  • What it holds. 25 sealed decisions, 35 controlled variants made from 10 of them, and 10 control cases (keys VER-…). A control case carries a malicious signal that the server verified, is graded "Must catch", and has BLOCK as its only right action.
  • How the cases are spread. The 60 ordinary cases are 15 of each kind (44 threats, 1 uncertain, 15 normal). They count as 25 distinct roots to stop and 10 to allow. Every case says why in Korean and English, the 45 variants name the facts that decide them, and every case is read in UTC. The default set has no "Must not block" case.
  • Changing a case. You change a case of the default set by copying it ("Copy to a new case"). The copy counts under the same root.
  • Upgrading. A product upgrade changes the default set only. Your own cases stay as they are.

Confirmation by a second administrator, and publishing

A new case, or a change to a case's answer, does not count until a second administrator confirms it. A confirmed case reaches the gate only after an administrator publishes it in a bundle.

  • Two people set an answer. A case, and each change of its answer, waits ("To confirm") until an administrator other than the one who set the answer confirms it. The same administrator is refused with "The administrator who set the answer cannot confirm it." The rule is there because a case labelled wrongly on purpose (an attack marked normal) would let a version that allows the attack pass. An installation with one administrator can turn the rule off with contexa.pqa.oss.quality.two-person-confirmation=false. Cases are then confirmed as they are submitted, and every change of an answer is still kept with the name of who made it.
  • Publishing ("Publish the bundle") fixes the default set of this build and the confirmed cases of the scope as one bundle, identified by the content hash of each case. "The gate reads the published bundle. Publishing fixes the list of cases, and only the added cases are measured again." A case that is waiting for confirmation is not in the bundle. Publishing the same cases again gives the bundle published before. When nothing is published in a scope, the first automatic measurement publishes the default set alone.
  • Changing an answer keeps the answer it replaces. The case detail shows "Answers better by changing the answer". These are the answers that are right under the present answer but were wrong under the answer the case was added with. They are counted apart because no version made them better.
  • Audit. Each step is audited: PROMPT_QUALITY_CASE_SUBMITTED, PROMPT_QUALITY_CASE_ANSWER_CHANGED, PROMPT_QUALITY_CASE_CONFIRMED, PROMPT_QUALITY_CASE_SET_PUBLISHED.

Personal data

A case from operation is built from a real decision, so it contains a real user's data. The case detail says it "holds a real user, real addresses and that user's baseline, and outlives the seal retention (90 days)". It stays in the CONTEXA database.

  • Deleting a case deletes its answer changes and the answers measured on it. A published bundle that held it then reads the case as missing.
  • Deleting the user deletes the user's cases.
  • The sealed package that a case was added from is kept for as long as the case is.
  • The quality report never reads the input of a case or why it is right (The quality report).

The labelled cases screen

This screen lists the cases of a scope and shows how many more you need. Use it to add, confirm, change, delete and publish cases.

  • Head: "Published bundle {version} · {when} · {n} cases" and the number of cases added since, with the buttons "Add from a sealed decision", "New case" and "Publish the bundle". A decision that is not sealed is refused, with the reason code NOT_SEALED.
  • Numbers: "Cases to stop" and "Cases to pass" show the distinct roots of the published bundle against the target the gate needs (200 and 300 by default). "Chance to tell a better version" and "To confirm" are the other two numbers.
  • "Chance to tell a better version" is the chance that the distinct roots to stop can tell apart a version that misses 10 points less, using the gate's paired comparison at its level. CONTEXA computes it exactly. It takes the miss rate of the version in use, treats the roots as independent, and treats the results of the two versions as correlated by 0.7. Until the targets are met, comparisons come out "Undecided".
  • "Cases by resource grade" (Critical, Sensitive, General, Public) uses the resource class that the decision records keep. For each grade it shows the roots to stop and to pass of the published bundle beside the decisions of the last 7 days. Each grade is marked "Covered", "Few cases", "No case" or "No decision". "Few cases" means that a side has fewer than 5 roots. That is the fewest at which a paired comparison of the grade can be significant at the default significance level of 0.05. The block exists because "A measurement measures a version, not a resource". Where operation decides on a grade that few cases cover, the average can hide a worse result there.
  • The list has the tabs "All" and "To confirm", and filters such as the resource grade and the case name. Its columns are the case, class and kind, right answer, case grade, resource and grade, and the result in the latest measurement of the version in use. That result is "Right", "Missed" (a case to stop was allowed in some run), "Off the answer" (an action fell outside the allowed actions, but the case was not allowed through), "Not measured" or "To confirm". The row actions are Copy, Confirm, Delete and Change the answer.
  • A case's detail shows the right answer, why it is right, the facts that decide it, and the decision input in words rather than codes (the tabs Request, Session, Unlike usual, Work records and Unknown, with values such as "Yes", "No", "Allow" and "Deny"). It also shows the results by version with the action of each run, and the answer changes.

Measuring a version

A measurement shows how well one prompt version decides on the labelled cases. You start one on the Measure & compare screen, and CONTEXA also starts one by itself when a version in use has none (Going back, and versions that decide outside the gate).

One measurement is one prompt version, run under the model setting the server uses now (its models and the options of its model requests), on one published bundle, with each case run several times (3 by default, 1 to 10). Each answer comes from the decision pipeline of the engine. CONTEXA takes the input of the case and replays it, as it replays a sealed decision, in the case's own time zone and with the versions of the case's scope. The replay draws the prompt with the version, checks the model's reply, retries once with a correction when the reply breaks the answer contract, and sets the fallback action when the reply still cannot be used. When the first answer is ESCALATE, the replay asks again, this time with the model the server uses for the second analysis.

The metrics can be counted on one of two bases. The gate reads the first answer.

BasisWhat it counts
First answer"The answer the model gave with the prompt. It tells the prompt's quality, and the gate reads it."
Final action"The action after the engine's closing rules. It tells what the user meets." CONTEXA computes the closing rules from the server's settings. After a first answer of ESCALATE, the second analysis decides. If the action of the second analysis is none of the four actions, it is replaced by CHALLENGE. An ESCALATE that is still left after the second analysis ends in the terminal action the server is set to. The overload protection (it ends an ESCALATE when one person's recent decisions defer too often) is not replayed, because it depends on the load of the moment, and the result says so
  • The model setting of a measurement is every server setting that can change an answer. It includes the models each layer asks (the first analysis and the second analysis each use their own model, else the primary chat model, and the screens name the model), the request options of each layer (output limit, reasoning effort, verbosity, thinking, budget profile), the determinism of the call, the structured output, the prompt's truncation and argument excerpts, the minimum action rules and their mode, the action an ESCALATE left after the second analysis ends in, and the context format. It leaves out timeouts, caches and the model server's gate, which change whether an answer arrives and not what it says. It also leaves out the server's time zone, because a case is drawn in the time zone it fixes, so changing the server's time zone leaves measurements current. Two measurements are compared only under the same setting. A measurement taken under a setting the server no longer runs is stale.
  • A measurement gives way to real decisions. It waits in the server's queue together with the trials of the version screens, and its model calls wait behind real decisions at the model server's gate. contexa.pqa.oss.quality.measurement.concurrency sets how many replays run at once (1 by default). The gate of a self-hosted server has 2 slots and the gate of a remote provider has 16.
  • One server at a time runs measurements. It holds a lock in the database and renews it with a heartbeat (heartbeat, 30 s). When that server stops, another server takes over within about two and a half minutes and resumes from the answers already taken. "Cancel" is written to the database, so the server running the measurement stops at its next answer.
  • A busy model server does not count against the prompt. When the model server gives no answer to a replay (it is busy, unreachable, or past a time limit), CONTEXA asks again up to 2 more times, after 15 s and then 30 s. An answer that still does not arrive, or a case that cannot be read, enters no metric, and the measurement shows "Incomplete, {n} answers".
  • The number of calls is shown before you start. The screen says "About {cases} cases × {runs} runs = {calls} calls · about {minutes} min · limit {limit}", and "{n} answers measured already under the same setting are used again". A measurement taken anew counts every answer as a call. One answer makes at least one call, and at most four for each attempt (the first analysis and its corrective retry, the second analysis and its retry). The default set run 3 times makes at least 210 calls and at most 2,520 with the default retries. A measurement whose minimum number of calls is above contexa.pqa.oss.quality.measurement.call-limit (3,000) does not start, and one that reaches the limit stops and ends failed. The screen reckons about 7 seconds an answer, shared among the replays that run at once.
  • Answers are reused. An answer kept for the same case content, version, model setting and run is not measured again, so a bundle published with new cases is measured on the new cases only. "Measure again without the kept answers" (API anew) asks the model for every answer again, at least one call each, and the list marks such a measurement "measured anew". A measurement started without that option reuses the kept answers. So do "Save and measure at once" and the automatic first measurement of a version that has none.

The 11 metrics

A measurement reports 11 metrics. Ten are rates, such as how often a threat was allowed. The last one, decision time and answer tokens, is shown but not graded. Each value is the mean of the runs. The 95% range of a rate is a Wilson interval (a standard range for a proportion) whose sample is the number of distinct roots, so the variants and repeated runs of a root do not narrow it.

MetricDefinition
Miss rateOf the answers to cases that must be stopped, the share that allowed the request. A case classed uncertain counts as one to stop
False stop rateOf the answers to cases that must be allowed, the share whose action is outside the allowed actions
Friction rateOf the answers to cases that must be allowed, the share that did not allow. It finds a version that asks every request to step up
Over-blockingOf the answers to cases whose right answer has no BLOCK, the share that blocked
Action hit rateOf all answers, the share whose action is inside the allowed actions
Deferral rateOf all answers, the share whose first answer is ESCALATE. It finds a version that only defers
ConsistencyOf the cases with two or more answers, the share whose answers all took the same action. It needs 2 runs or more
Citation accuracyOf the facts the answers cite, the share that are in the prompt and that the citation check did not flag
Asked againOf all answers, the share that broke the answer contract and were asked again
Set without the modelOf all answers, the share the engine decided because the model's answer could not be used
Decision time and answer tokensThe median and the 95th value. Shown, not judged

Comparing two versions

A comparison tells you, for each metric, whether a candidate version is better than, worse than or the same as the version in use.

  • Same conditions. Two measurements are compared only when they were taken the same way: the same bundle version, model setting and number of runs. The screen says "Same conditions: bundle {version} · {models} · {n} runs".
  • Case against the same case. For each rate, CONTEXA takes each root and the cases that both measurements scored. It marks the root worse, better or unchanged by its own rate. An exact one-sided sign test over the roots that changed then asks whether so many could turn one way by chance. When a root is a single answer, the exact McNemar test does this. The level is contexa.pqa.oss.quality.gate.significance (0.05).
  • Verdicts. "Same" means no difference, or a difference within the noise of the rate. "Better" or "Worse" means a difference beyond the noise that the test says is not chance. "Undecided" means nothing is paired, the noise is not known, or too few roots changed to tell. The verdicts rest on a test because counting changed cases alone would stop the same prompt one time in four to one in two.
  • The noise is how far two measurements of one version, taken the same way, differ from each other. A difference smaller than the noise says nothing about the versions. CONTEXA reads the noise from the newest two such measurements of the version in use first, else of the candidate, when each has answers of its own: taken anew, or finding no kept answer to reuse. A measurement that reused answers kept from another one shows no noise and is not read for it. "The difference of two measurements of one version taken anew is the noise the quality gate reads": measure the version in use anew twice, or let the weekly measurement do it (Measured again on schedule). Without such a pair the screen says the noise is "not known yet, so a difference is "undecided"".
  • Default cases and your cases, apart. "Default bundle and our cases" shows the misses of each apart. The reason is that "The default bundle does not stand for your environment and was used to make the product version, so it favours it."
  • Cases added after the version. These are the cases that came in after the version was made, which its author could not see. "A worse result only here hints at a version fitted to the cases seen." The gate's eleventh condition reads them.

Wrong cases and their causes

A wrong answer can have many sources: the prompt, the model, a rule of the engine or the data the decision was given. The view "Wrong cases and causes" tells you which one it was, so that you fix the right place and do not rewrite a prompt for a problem that lies elsewhere.

The view puts each wrong answer of a measurement down to one cause. Fixed rules decide the cause and no AI model is asked, so the same record always gets the same cause. When several causes fit, the answer gets the first one in the table below. An administrator can change a cause ("Change cause"). A changed cause is kept, and the rules do not overwrite it. The option "With the decisions rated "not valid" in operation" adds the real decisions that an administrator rated "not valid" in the decision detail over the last 90 days, and classifies them too.

The quality gate

The quality gate is the check that runs when you use a version of the security decision prompt for decisions, or start it as a canary. It compares the measurement of the new version (the candidate) with the measurement of the version in use, and it lets the change through, warns, or blocks. Both measurements are on the latest published bundle of the scope, and the comparison reads the first answers. The release gate of the version screens calls the quality gate and shows its result in the confirmation (Prompt Versions). The other seven prompts take no quality condition. In this section, "blocks" means that the gate stops a version from going live. It does not mean the BLOCK action of a decision.

#Condition (as the confirmation names it)When it does not hold
1Both versions measured on the same case set version, model setting and runsBlocks. A version without a measurement fails this condition too
2No "must catch" case was ever allowedBlocks
3No "must catch" case newly answered outside its allowed actions (such as a challenge or a deferral where a block is right)Blocks when, in any run, the candidate answers a "must catch" case outside its allowed actions without allowing it, and the version in use never did. If the version in use also answers such a case outside its allowed actions, the condition only warns, because the candidate did not cause it. Without a comparable measurement of the version in use, every such answer counts against the candidate
4No "must not block" case was ever blockedBlocks
5Misses did not rise significantlyBlocks
6False stops, over-blocking, friction and deferrals did not rise significantlyBlocks
7Friction did not rise by the limit or more, whatever the significanceBlocks when the candidate's friction rate is higher than that of the version in use, on the same cases, by friction-increase-limit (0.20, which is 20 points) or more. On the default set run once, that is three more of the fifteen answers to cases that must be allowed. The condition stops a version that challenges every request, also where the version in use already challenges so many requests that too few roots are left for the exact test of condition 6 to tell that it is worse
8Set without the model within its limit, citation accuracy not significantly lowerBlocks when the share of answers set without the model is above model-less-limit (5%), or when citation accuracy is worse
9No case newly missed or newly stoppedWarns, with a link to the cases. It warns about a newly missed case unless condition 5 already blocks, and about a newly stopped case unless condition 6 or 7 already blocks
10Enough cases to tellWarns, and says how many roots are missing (minimum-stop-roots 200 to stop, minimum-allow-roots 300 to pass) or how many rates are undecided
11The same result on cases added after the versionWarns, because the version may be fitted to the cases it saw. For misses, false stops, over-blocking and friction, Fisher's exact test asks whether the roots added later fail more often than the earlier ones
  • The terms in the conditions (misses, false stops, over-blocking, friction, deferrals, citation accuracy, set without the model) are the metrics of The 11 metrics.
  • "Significantly" has the meaning given in Comparing two versions: only a difference beyond the noise of one version measured twice blocks. Conditions 2, 3 and 4 allow not a single wrong answer, and condition 7 blocks on the size of the rise alone.
  • With the default set alone (25 roots to stop, 10 to pass), condition 10 always warns.
  • When every condition holds, the confirmation says "All {n} conditions passed."

Warning or blocking, and the reason that overrides

The setting contexa.pqa.oss.quality.gate.mode decides what the gate does with a verdict that blocks.

  • WARN (the default of contexa.pqa.oss.quality.gate.mode): a verdict that blocks is applied as a warning. The screen says "The gate is in the warning mode, so the blocking conditions ({n}) are applied as warnings." The verdict itself is kept as it was computed.
  • BLOCK: a blocking condition stops the version unless an administrator writes a reason ("Use with this reason", "Start with this reason"). "A reason lets it through; who let it through and why is kept in the audit records" (PROMPT_VERSION_QUALITY_GATE_OVERRIDDEN). A blank reason is refused. An urgent new version that fixes a failure goes this way too. The setting says to set BLOCK once the reproducibility and discrimination checks have passed on the installation.
  • A reason overrides only a quality block. When something other than quality blocks the version too, the confirmation says "Something other than quality blocks it too, so a reason cannot let it through."

Before it reads the conditions, the gate looks at which measurements exist. That state decides what the gate does.

The confirmation

When you choose "Use for decisions" or "Start the canary" on a version, a confirmation shows the gate's result before you go on.

  • It shows the gate's state and one summary line. Under "Quality gate · case set {version} · {models} · {n} run(s)" it opens the conditions that matter: the blocking ones when the verdict blocks, otherwise the warnings. The other conditions are folded into "{n} passed", "{n} warnings" and "{n} not looked at".
  • The newly missed cases open in Measure & compare ("Show the {n} newly missed cases"). When there are such cases and the verdict does not block, you tick "I have read the newly missed cases" before you go on.
  • The confirmation shows the latest trial ("Tried", "Not tried") only when the quality gate could not be read.

Going back, and versions that decide outside the gate

Two kinds of change skip the quality conditions: going back to an earlier version, and two ways in which a version can decide without ever passing the gate.

  • Going back to a version that the scope has used for decisions before takes no quality condition. The confirmation says "Passed (going back)". A rollback, an emergency rollback too, can go only to such a version, and any other target is refused. A version counts as used for decisions when it decides now, was applied as ACTIVE, was the target of a rollback that was not refused, or is named in the rollback records. A version that only ran as a canary does not count.
  • Two ways reach the decisions without the gate: the version that contexa.security.tiered.prompt-bundle.active names, and the newest CONTEXA version that an upgrade brings when no version is chosen on the screen. The version list says so ("{version} decides as the setting names it, without passing the release gate.") and shows the state of the version's measurement in this environment. CONTEXA measures such a version once on its own.
  • Right after an upgrade the version in use has no measurement. CONTEXA measures it once by itself on the latest published bundle, and it publishes the default set first when the scope has none. The default set run 3 times is 210 answers, so model calls are made. Until the measurement is done, the gate only warns. A CONTEXA version whose measurement the product ships, taken the same way here, is not measured again. A version in use that was measured under other settings only is measured once more. CONTEXA looks for such versions every 10 minutes.
  • API. GET /contexa/admin/api/prompt-quality/versions/{number}/use-check (?target=CANARY for a canary) returns the gate's answer under quality. Its fields are mode, measurement, verdict (as computed), applied (PASSED, WARNING or BLOCKED), rollback, overridable (whether a reason would override the block), rows (the eleven conditions), changes and details. POST /{number}/use and /canary/start take overrideReason (Prompt Versions API).

Connected to operation

Real decisions tell you where a prompt goes wrong in practice, so CONTEXA connects them to the cases and the measurements. This part covers which decisions are sealed so that they can become cases, how reviewers are given decisions to rate, how a rated decision or a breach is recorded, how the version in use is measured again every week, and the quality screen that shows the result.

What is sealed

A decision can become a case only when it is sealed, because a case needs the exact input the decision read. CONTEXA seals decisions that stopped the request (CHALLENGE, ESCALATE, BLOCK) and allowed decisions with a sign of risk first, up to 2,000 packages a UTC day. Besides these it seals the window after a change (the first decisions after a server starts or the version used for decisions changes, 1,000 by default) and the 1% share of the other decisions. A seal now keeps the baselines the decision read, so a replay later reads what the decision read (When it is sealed).

The review queue samples allowed decisions by risk

The review queue is the list of decisions that an administrator is asked to rate in the decision detail. It is the one direct measure in operation of whether decisions are right. A random sample of allowed decisions hardly ever finds a miss: with one miss in 10,000 allowed decisions, 20 a day find one in 500 days on average. So the review queue (Zero Trust → Decision records, ?view=review) draws these decisions each UTC day:

  1. Up to contexa.security.zerotrust.console.review-daily-sample (20) stopped decisions, at random.
  2. Up to review-risk-sample (10) allowed decisions chosen by risk. A decision qualifies when it shows a sign that it may be a miss: the explanation the model marked most likely is not legitimate work, the second analysis decided, the model was asked again, at least contexa.pqa.oss.sealed-evidence.unknown-fact-threshold (3) decision facts were unknown, or the personal baseline is not established. The allowed decisions of a user who was blocked that day also qualify. They are looked for review-blocked-lookback-days (7) back from the block, unless an administrator released the block or rated it not valid. Decisions before a block come first, then those with more signs.
  3. Up to review-allowed-sample (5) allowed decisions without any sign, at random, so that ordinary cases (cases that should pass) come in as well.

While the sealed evidence capture runs, only sealed decisions are drawn, so a reviewed decision can be replayed and made a case. Test runs are not drawn, and the allowed decisions of a day are drawn once. With the defaults the queue takes up to 35 decisions a day instead of 20.

Evaluate and add as a case, and breaches after an allow

Two buttons in a decision's detail turn a real decision into data for the quality gate.

  • "Evaluate and add as a case" keeps your evaluation of the decision and also makes a case with the right answer you set. "The evaluation and the case are kept together or not at all. The case uses the sealed input." A decision that is not sealed cannot become a case: "This decision is not sealed, so it cannot become a case; the evaluation alone is kept." The case belongs to the platform scope, because the decision records show the decisions of every tenant. It waits for a second administrator like any case.
  • "Confirm a breach after the allow" on a decision that allowed the request records the outcome ALLOWED_BREACH_CONFIRMED ("Allowed, later confirmed a breach"), with an optional note. It counts as a miss seen in operation. Recording it again keeps the first record, and only a decision that allowed can be confirmed. The outcome filter of the decision records has this value.
  • A sealed decision can also be added as a case from the sealed evidence screen ("Add as a case"), from the labelled cases screen ("Add from a sealed decision") and from a trial's result, where it is a decision the two versions decided differently.

Measured again on schedule

A version can get worse without anyone changing it, for example when the model behind it starts to answer differently. So CONTEXA measures the version in use again every week and compares the new result with the one before.

  • At contexa.pqa.oss.quality.remeasure.cron (0 0 2 * * SUN, UTC; - turns it off) CONTEXA measures the version in use of every scope again, on the bundle that scope's measurements run on. One server runs it.
  • The scheduled measurement is taken anew, without the kept answers. That finds a version that came out worse under the same settings, and two such measurements give the noise. It therefore calls the model every week. For the default set run 3 times, the 210 answers take 210 to 840 calls (a first analysis and its re-ask, a second analysis and its re-ask), and at most 2,520 with the retries of a busy model server. This happens in each scope that has its own measurement (the platform and every scope with a decision label). A measurement the schedule could not finish is tried again.
  • CONTEXA compares a measurement taken again with the measurement of the same version before it. A measurement that came out worse or changed is logged as a warning and shown on the quality screen. The product has no other notification of administrators.
  • When the model setting changes, CONTEXA measures the version in use once under the new setting and compares that measurement in the same way.

The quality screen

The quality screen is the first screen of the group. It answers "How right the prompt in use is, and what there is to check." Open it to see how good the version in use is and what needs your attention.

  • Head: the version in use and since when (the first hour it decided within the last 90 days), its latest measurement (bundle, models, runs), a sentence on how many of the cases it should stop it missed, the period of the operation numbers (day, week by default, month, quarter) and the "Quality report" button.
  • "Version in use": whether its measurement is current or stale, the bundle, the model setting, the runs and "Next scheduled".
  • "Measured on the cases": the 11 metrics with their 95% ranges.
  • "Seen in operation": six numbers counted from the real decisions of the version in use and of the version before it, over periods of the same length on each side of the change. They are not graded against right answers. Stopped is the share of decisions stopped by a step-up, a hold or a block. Step-ups passed is the share of stepped-up decisions whose step-up was completed. Blocks released is the share of blocks an administrator released. Reviewed as right is the share of reviewed decisions an administrator rated valid. Asked again and Set without the model are the same rates as in the metrics, counted on real decisions.
  • The things to check: the list below shows what needs your attention, each with a button. When nothing applies, the screen says "Nothing to check."

The quality report

The quality report is a file bundle for auditors and compliance reviews. It shows how accurate the version in use is, how it was measured and approved, and which decisions people overturned. Use it when someone asks you for evidence of the prompt's quality.

The "Quality report" button on the head of the quality screen exports one zip for a scope and a period. You choose the period as whole UTC days ("First day (UTC)", "Last day (UTC)"; 90 days by default, at most 400). The zip holds report.json for programs and report-ko.md and report-en.md for people. No AI model is asked to write it.

SectionWhat it holds
1. Accuracy of the version in useThe measurements of the version in use and of the versions before it. It answers the declaration of the accuracy metrics (EU AI Act, Article 15)
2. Case set versionsThe bundles the measurements ran on
3. Monitoring in operationThe operation numbers of the period. It answers monitoring after the release (EU AI Act, Article 72)
4. Overturned decisionsThe blocks an administrator released, the decisions an administrator rated wrong and the allowed requests confirmed as breaches. It answers the monitoring of the decisions people overturned (NIST AI RMF, MANAGE)
5. Changes and approvalsThe changes of the versions and who approved them
6. MaskingThe masking rules the report was made with
  • The people that decisions and cases are about get pseudonyms. A pseudonym is a keyed hash made with a key that is drawn for this report and never written down. The same person gets the same pseudonym within one report and a different one in the next.
  • Texts that administrators wrote (a reason, a note, a title) are kept. The identifiers of such people in them are replaced by their pseudonyms, and every e-mail address and IP address is replaced by a mark.
  • Never read into the report: the input of a case, why it is right, a decision's request, path, address, session or summary, and the note an administrator wrote on an overturned decision. The reason code of the overturned decision, which says what was wrong, is in the report.
  • The administrators who acted are named as they are, because the report is the record of who approved what.
  • API: GET /contexa/admin/api/prompt-quality/report?scope=&from=YYYY-MM-DD&to=YYYY-MM-DD. A period that starts after it ends, or that is longer than 400 days, is answered with 400.

What a decision says about its prompt

Every decision records which prompt it was drawn with, so you can always tell afterwards which version decided. A decision's prompt execution information, and its sealed evidence, name the prompt in two ways.

  • The version: its name (v2.0), what chose it and its content hash. They are fixed on the event when the decision starts (promptBundleSelection.version, .source, .contentHash). The decision record keeps the version name and the content hash.
  • The governance descriptor of the template is the fixed description of the prompt the engine runs. It holds the prompt key cortex.security-decision, the template key, the release 2026.11.16-v1.0, the output contract CORTEX_PROMPT_CONTRACT_V5, the user text layout v1.0-dictionary-blocks, and the release's hash. The release name is the name of the bundle the engine runs, so the product default v1.1.0, the earlier product versions and the versions made on them all carry it. The trace check of the evidence audit compares the sealed descriptor with its release in the registry. The manifests of the earlier bundles v19, v20 and v21 are gone.

What chose the version

The selection source tells you how a decision got its version.

The registry behind the versions

Each version has one row in the prompt governance registry, the table that records the state of every version. The actions on the version screens move that row from one state to another. The release gate checks each move, and for the security decision it calls the quality gate. The states keep their code names (PromptBundleState), and the screen shows them in its own words.

Registry stateOn the screen
ACTIVEUsed for decisions
CANARYCanary
SHADOWRunning alongside
AVAILABLENot used (a new version starts here)
DEPRECATEDNot used (a row an earlier bundle left; read as AVAILABLE)
RETIREDHidden
  • A refused move changes nothing. The gate records it with its reasons. An applied move changes the registry state and the approval and rollback records, and it announces a runtime cache invalidation.
  • Only one version is used for decisions. Moving a version to ACTIVE turns the other ACTIVE version of the same tenant and prompt into AVAILABLE. A row that names an earlier product bundle, not a numbered version, becomes DEPRECATED instead.
  • Stopping. A version used for decisions, a canary or a version run alongside goes back to AVAILABLE when it stops. A hidden version takes no state.
  • At start every server registers the build's product defaults as versions (the first installation's v1.0, an upgrade's next numbers) and retires the registry rows that name an earlier bundle. Those rows are kept, because the trace check of earlier sealed decisions reads them.
  • Rollback, emergency rollback with a second administrator's approval, canary and running alongside are done on the version screens (Use for decisions and rollback).

What was removed, and upgrading

Read this section when you upgrade from a version that had the official verification. It lists what disappeared, what replaces it, and what you may need to do by hand.

  • Removed: the official verification of a sealed package (12 metrics, 66 checks, its runs, results and reverification) with its screens "Protected Candidates" (/contexa/admin/prompt-quality/resources) and "Official Inspection" (/contexa/admin/prompt-quality/runtime-evidence) and their APIs, the "Inspection Overview" screen and its API GET /contexa/admin/api/prompt-inspection/overview, the scoring of the sealed structure and the deterministic replay.
  • The inspection checks: three of them stay, as the evidence audit of sealed packages (SEAL_INTEGRITY, BUNDLE_TRACE, SOURCE_TRUTH). Six checks read the lines of the prompt (DICTIONARY_CONTRACT, DECISION_FACT_MATCH, FACT_ACCURACY, UNKNOWN_DECLARED, PAST_RECORD_NOTATION, SAME_FACT). They no longer run on your sealed packages. They check the renderer of the build over a fixed set of reference inputs (the golden inputs) when CONTEXA is built. The citation check of REASON_MATCH runs on the decision path for every decision, and its result is kept with the decision record. The inspector is version 30 (prompt-inspector/30), so the sealed packages are inspected again with the three checks.
  • Removed settings: contexa.pqa.official-verification.stale-execution-timeout, contexa.pqa.routes.official-api-root, contexa.pqa.routes.enterprise-api-root, contexa.pqa.routes.enterprise-verification-runtime-runs-path. They are no longer read.
  • The capability PQA_ENGINE is gone. A value left in contexa.capability.required that names no capability of this version, such as pqa-engine, decides nothing. The start logs one warning ("Ignoring contexa.capability.required.pqa-engine: this version has no such capability …") and goes on. Remove the key. The settings object now keeps required as a map from the key to its value (Map<String, Boolean>), so code of your application that calls ContexaCapabilityProperties.getRequired() must take that type.
  • The 58 tables of the official verification are not created on a new installation, and an existing installation keeps them. CONTEXA never drops them by itself. The script META-INF/contexa/db/drop-retired-official-verification.sql of contexa-iam drops them. Run it by hand against the CONTEXA database (for example psql -f drop-retired-official-verification.sql), and only after the upgrade. An older version reads a database without these tables as a partial installation and refuses to start.
  • What an upgrade changes in operation:
    • The new version screen of the security decision saves and measures instead of using a version for decisions at once (Prompt Versions).
    • The first start after the upgrade measures the version in use (210 answers, with model calls).
    • The version in use is measured again anew every week (210 to 840 model calls per scope with the default set, at most 2,520 with retries).
    • The review queue takes up to 35 decisions a day.
    • Stopped decisions and risky allowed ones are sealed up to 2,000 a day.
    • A sealed package is no longer deleted after 30 days because its inspection found nothing (Retention).
    • The trials of the version screens wait behind the measurements in one queue.
