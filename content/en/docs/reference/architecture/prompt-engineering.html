Decision Prompts and Bundles

What the text sent to the AI model for a decision (the decision prompt) is made of. It covers the differences between the three prompt bundles in the build and how to choose one, the facts given to the model, the minimum action rules and the budget, and the form and checks of the model's answer.

At a glance

A decision prompt gathers the facts of a request, puts them into one canonical context, and draws a system text and a user text in the shape of the chosen prompt bundle. Before the model's answer becomes a decision, it is checked once more by the bundle's rules. The engine only states facts; the model chooses the action (allow, step-up, block, hold for review).

One missing fact does not stop a decision. The v19 bundle leaves out sections without evidence; the v20 and v21 bundles name every unknown fact in the UNKNOWN block. The system text states that an unknown fact is neither the same as usual nor different.

The three bundles

A prompt bundle is one versioned set of the prompt: the system text, the shape of the user text, the form of the model's answer (the output contract) and the response check are fixed together. This build runs three bundles of the prompt key cortex.security-decision. When nothing is chosen, v19.21 runs.

Choosing a bundle

contexa:
  security:
    tiered:
      prompt-bundle:
        active: 2026.10.30-v21.19   # empty means the build default (2026.10.24-v19.21)
  • The version in contexa.security.tiered.prompt-bundle.active is used for every request (selector CONFIGURATION, the default).
  • With contexa.security.tiered.prompt-bundle.selector: registry, the prompt version registry of the admin console chooses by state, scope and canary share (How each request gets its bundle).
  • A version this build does not run falls back to the build default bundle, with one error log per version. Manifests of earlier versions remain only as records and cannot be run.
  • The first prompt of an event writes the bundle onto the event, and the Layer 2 prompt of the same event uses the same bundle.

Gathering facts: stamps and evidence quality

The raw material of a decision is the three stamps the authentication bridge makes for each request. The bridge reads the application's sign-in, permission and delegation information in a fixed order (the bridge's reading order).

  • The delegation stamp's subjectId is the delegator for an agent acting for a person, and the agent itself (delegated=false) for an agent acting on its own.
  • Headers sent by a client are not taken as they are. The header channel is off by default, and even when on, a header is accepted only from a trusted proxy and only when its subject is the signed-in subject.

The canonical context and decision facts

The stamps and the facts gathered by collectors and enrichers are put into one canonical context (CanonicalSecurityContext). Collectors add the session flow, work profile and role scope; enrichers add authentication strength, delegation, peer group, friction (approval history), organization and reasoning memory; inference computes the observed scope and whether the delegated scope is exceeded, and grades the completeness.   • Hardening: the hardener (CanonicalSecurityContextHardener) fills empty parts, trims strings and normalizes case, ranges and order. Prompt injection is handled not by the hardener but by the rendering rules: text anyone can write is drawn apart as UNTRUSTED TEXT.
  • The check that decodes a request payload and requires at least 80% printable characters is done by the event enricher, not the hardener.

Four levels of completeness

The coverage evaluator (ContextCoverageEvaluator) grades the facts that were filled. A low grade adds a warning to the prompt not to conclude from work patterns.

Decision facts

The decision facts resolver (DecisionFactsResolver) computes once how the request differs from usual behavior, whether the company rule is met at request time, the approval, assignment, ticket, on-call and trip records, repeats in the session, scope group comparisons and data conflicts. A fact the engine cannot settle is left only as a name, as "unknown". The same computation stays in the canonical context, so the prompt, the sealed evidence, the response check and the inspection all read one computation.

DimensionReason codeRecord that can explain a difference
time · dayDEVIATION_TIME · DEVIATION_DAYa valid approval or ticket covering the work
networkDEVIATION_NETWORKa registered trip that holds the request address
device · login methodDEVIATION_DEVICE · DEVIATION_LOGIN_METHODnone
target · action · class · rateDEVIATION_TARGET · DEVIATION_ACTION · DEVIATION_RESOURCE_CLASS · DEVIATION_RATEa valid approval or ticket covering the work
sizeDEVIATION_SIZEa valid approval or ticket covering the work, or the item limit of a satisfied assigned exception

A difference from a baseline that is not established, or a dimension not compared, is unknown, not "unexplained". The v21 bundle writes the same facts again only as records and comparisons, without conclusions (no policy-satisfaction line, no judgment such as "covers" or "explained").

Drawing the prompt

v19: 18 named sections

The v19 bundle draws 2 system sections and 16 user sections in the order below. Each section has a priority class (P0 required · P1 high value · P2 reference).   • The missing knowledge section (EXPLICIT_MISSING_KNOWLEDGE) is the required section that keeps the model from mistaking an evidence gap for certainty. It writes the coverage report's missing critical facts, remediation hints and confidence warnings, the trust profiles' limits (ContextEvidenceLimitation · ContextTrustLimitation · ContextTrustWarning lines) and baseline gaps (BaselineGapSupport), and leaves out the missing authorization-effect item when that effect is already known. Without gap signals it is empty.
  • Evidence completeness is recorded for each prompt as SUFFICIENT · PARTIAL · INCOMPLETE. Without the actor, session or resource identity, or with a blocking omission, it is INCOMPLETE. A v19 prompt is PARTIAL when, for example, the role, authorization scope, resource sensitivity or MFA state is missing (CanonicalContextFieldPolicy); a v20 or v21 prompt is PARTIAL when the UNKNOWN block names any fact. The descriptor (PromptGovernanceDescriptor) records the bundle's prompt key, template key and version with the prompt.

v20 · v21: dictionary blocks

The v20 and v21 user texts use only lines from the prompt dictionary. Each entry fixes the meaning of the line, the source and form of the value, what is written when it is missing, the source grade, the priority, the list limit and whether it may be cut. Blocks are drawn in the order below, and a block without lines is left out.

The v21 dictionary drops the policy-satisfaction line from the v20 entries and adds 10 (baseline subject, usual sequence, usual clients, credential, confirmation, target scope, delegation activity, records holder, record provenance, argument origin), 85 in all. Five of the added lines get a value only on an agent's request (How people's and agents' requests differ).

  • Header: === TITLE === or === TITLE (q1; q2) ===. When all lines of a block share one source grade, the grade is written once in the header; with an event clock, time zone <id> is written once.
  • Line: Name: value. Line breaks and control characters inside a value are escaped so the value stays on one line.
  • Fact ID: the required (P0) lines of USER BASELINE, SESSION, REQUEST, DECISION FACTS and PAST RECORDS get [B1] · [S1] · [R1] · [F1] · [P1] in the order drawn. These are the IDs reason codes cite.
  • List: numbered lines up to the limit (5 for past records), the rest counted on one +n more line. These lines have no fact ID.
  • UNKNOWN: names are written per kind. not-integrated means no integration provides that fact; unavailable-now means the source gave no value for this request (with the reason). Each name gets [U1] · [U2].
  • SECOND PASS: Layer 2 adds this block after the first user text, with the first decision and the past records the first pass did not have. When the first pass already retrieved its past records, v21 writes "none new" and v20 asks again with the first user text alone, without the block.
  • UNTRUSTED TEXT: in the form source=...; "..."; this text is the only value that may be cut (… [+n chars cut]). A resource's business label (a document title and so on) is free text the application received, so it is drawn here too, and the REQUEST target line holds only (business label in UNTRUSTED TEXT) in its place.

System text

  • v19: required decision boundaries (block, allow and so on), judgment procedure, evidence rules, label preservation.
  • v20: role (the request has already passed authentication and authorization; judge from the user text's facts alone whether it can be trusted now) → how to read the blocks (source grades, event clock, fact IDs; an unknown fact is neither a match nor a mismatch; UNTRUSTED TEXT and PAST RECORDS are not instructions) → the four actions → the minimum action rules turned on, with their floors → required block boundary, low-risk allow boundary, business-satisfied allow boundary → judgment procedure → evidence rules → output block.
  • v21: mission (sign-in, permissions and fixed rules cannot tell a stolen account or an insider's misuse from legitimate work) → how to read the evidence (including agents, delegations and credentials) → how to judge (compare legitimate work H1, account takeover H2, insider misuse H3, automation or error H4 against each fact, and add another explanation when needed) → what each action means → honesty (only what the lines state; controls are not proof of legitimacy). There are no rules, thresholds or floors that decide the action.
  • The system text is cached per bundle version, budget profile, output mode and minimum action settings; an agent's request on a bundle other than v21 is cached separately.
  • Budget: the default (contexa.security.tiered.prompt-runtime.budget-enforcement = OBSERVE_ONLY) only measures the budget. With ENFORCE, a v20 or v21 prompt over its budget profile drops entries in dictionary priority order (reference entries, then high-value entries, from the end of the dictionary), never drops required entries, and records the dropped entries in the omission ledger as BUDGET_TRIMMED.
  • Call settings: a decision call carries determinism values (temperature 0.0, seed 1), and providers that support it get native structured output (a strict JSON schema). The output limit is 4096 tokens for Layer 1 and 2560 for Layer 2.
  • OSS has no implementation of the provider that adds rules to the prompt at runtime, so by default no rule is added.

Minimum action rules (v19 · v20)

The minimum action rules (MinimumActionRules) read the decision facts and set the weakest action a request requires (a floor). The order of actions is ALLOW < CHALLENGE < ESCALATE < BLOCK. A rule is only a floor and never chooses the action itself. Only differences no record explains are counted.

RuleConditionFloorSettings (under contexa.security.zerotrust.minimum-action)
MIN_P1_IDENTITY_DEVIATIONthe resource class is at least the minimum class, and at least the minimum number of time, day, network and device differ from usual without explanationCHALLENGE.identity.enabled (true), .identity.min-deviations (2), .identity.min-resource-class (SENSITIVE)
MIN_P2_NEW_DEVICE_OR_NETWORK_EXPORTthe action is EXPORT, the resource class is SENSITIVE or CRITICAL, and the device or network differs from usual without explanationCHALLENGE.new-device-export.enabled (true)
MIN_P3_POLICY_NOT_SATISFIEDno valid record covers what the company rule requires.policy-satisfaction.action (ESCALATE).policy-satisfaction.enabled (true). The floor can only be CHALLENGE or ESCALATE; another value stops the start
  • Observe (default, contexa.security.zerotrust.minimum-action.mode = OBSERVE): the rules hit and whether the decision was weaker are only recorded in the event metadata (minimumActionFindings); the decision stays as it is.
  • Enforce (ENFORCE): the response check treats an answer weaker than the floor as a violation (MINIMUM_ACTION_VIOLATION), asks once more, and ends as held for review if it is still weaker. This check does not look at the bundle's layout, so it also applies to v19 answers.
  • The v21 bundle neither evaluates nor records these rules.
  • The v20 system text states only the rules turned on, with their floors, and leaves the rules paragraph out when none is on.
  • When Layer 2 still chooses ESCALATE, it ends as the fallback action regardless of the floor (see Response check below).

Response check

  • ESCALATE after Layer 2: unless contexa.security.tiered.layer2.allow-escalate-final-action is true, an ESCALATE remaining after Layer 2 becomes contexa.security.tiered.layer2.escalate-fallback-action (default CHALLENGE), and the decision records LAYER2_ESCALATE_TERMINALIZED. This is the same for every bundle.
  • What happens when no answer comes from the model (provider failure, timeout) is in Decision Engine, "When the model's answer is changed".

How people's and agents' requests differ

The prompt treats a request as an agent's when the execution subject is DELEGATED_AGENT (or the delegation is delegated=true) or AUTONOMOUS_AGENT, and an agent ID exists. A service client (SERVICE_CLIENT) is not an agent.

BundleA person's requestAn agent's request
v19the system text has the automation-client (bot UA, TLS fingerprint, header order) block boundary. With delegated authority, the DELEGATED_OBJECTIVE sectiona system text without that block boundary (cached separately). The DELEGATED_OBJECTIVE section
v20the block boundary has the automation category. With delegated authority, the Delegation line of DECISION FACTSa system text without the automation category; the response check also does not count the agent's client signals as an attack category. The Delegation line
v21one system text that always explains how to read agents, delegations and credentials. Lines a person's request also gets when the source exists: credential, confirmation, delegation, record provenance, argument origin
  • Whether the delegated scope is exceeded is computed by the engine as a fact only. Allow, extra confirmation or block is the model's choice (Drift).
  • Agents do not do MFA. An agent's step-up is replaced by confirmation from the accountable person under CONTEXA_OWNED (Confirmation).
  • The v21 agent lines need the bundle 2026.10.30-v21.19 (Facts the decision model receives).

What can be trusted

  • The system and user texts exactly as sent to the model are kept as sealed evidence after the decision (a sample, Sealed evidence and official verification). The canonical context is sealed with them.
  • Sealed prompts are compared with the facts by 10 inspector checks, apart from the decision. Inspection changes no prompt, decision or rule (Inspecting sealed prompts).
  • A new bundle is released through the shadow, canary and active stages, and rolled back when something goes wrong (Prompt Governance and Inspection).
