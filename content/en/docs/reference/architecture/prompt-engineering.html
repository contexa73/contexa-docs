The Decision Prompt

What the AI model receives when CONTEXA hands it a decision (the decision prompt). The page covers what the model gets, the order the text is built in, which fact goes into which block, the form of the model's answer and how CONTEXA checks it, and what an application can change.

Overview

For each decision it hands to the AI model, CONTEXA sends two texts. The system text is a set of instructions: the model's role, how to read the facts, and how to answer. The user text states the facts of that one request, split into blocks. The model answers with one JSON object that holds an action: allow (ALLOW), step-up authentication (CHALLENGE), hold for review (ESCALATE) or block (BLOCK). CONTEXA checks that the answer follows the format and the citation rules, and only then records it as the decision. When the first analysis (Layer 1) answers hold for review (ESCALATE), a second analysis (Layer 2) decides again from the same text plus the facts it newly found.

The work is split. The CONTEXA engine collects and computes the facts and writes them into the user text. It first puts the facts into one form, the canonical context, and builds the user text from it. The model reads the facts and chooses the action. The product default version has no rule or threshold that picks an action. A floor on the action is added to the system text only when the host turns it on (Minimum action rules).

One missing fact does not stop a decision. The user text names every unknown fact in the UNKNOWN block. The system text tells the model not to read an unknown fact as matching the baseline or as differing from it.

  4. Minimum action rules: a floor that keeps the model's action from being too weak.
  5. The form of the model's answer and its check: what the answer holds, why it has that form, and how it is checked.

  7. Settings you often change: what an application can change.

Prompts are managed as versions

The sentences of the decision prompt are not in the code. They live in a document called a prompt version. Each decision runs one version, and that version supplies the sentences of the system text. The prompt key is cortex.security-decision.

The version CONTEXA ships is the product default. This build's release is v1.1.0, in the document prompt-versions/cortex.security-decision/v1.1.0.yaml of contexa-core. The earlier releases 2026.11.16-v1.0 and 2026.11.18-v1.0 are shipped beside it. The three differ little.

  • 2026.11.16-v1.0: the first release.
  • 2026.11.18-v1.0: the same prompt as 2026.11.16-v1.0, except for the reason code VERIFIED_SIGNAL and the use stated for the VerifiedSignal line. The Precedence sentence and the "Blocks your organization added" sentence appear only in the system text of a version an organization changed or added to.
  • v1.1.0: the same prompt as 2026.11.18-v1.0, without the Precedence sentence and the "Blocks your organization added" sentence that 2026.11.18-v1.0 adds for organization versions. No version built on v1.1.0 includes these two sentences (A new product default).

An organization makes its own versions from the product version, on the admin console or in documents (Prompt Versions). Every version keeps what the engine fixes: the blocks, lines and order of the user text, the fact IDs, the form of the answer and the reason code names.

Which version a decision runs

The version is chosen in this order (How a decision's version is chosen).

  1. The version chosen on the admin screen: the one marked "Use for decisions", or the version of a canary the request falls inside (a version applied to some users first).
  2. If none, the version the setting contexa.security.tiered.prompt-bundle.active names (v2.0 form).
  3. If none, the newest version provided by CONTEXA.
  • When a decision starts, its first prompt fixes the chosen version on the event (promptBundleSelection.version, .source, .contentHash). The second-analysis prompt and every retry of the same event use the same version.
  • With no choice, the product default of the build runs. When the store cannot find the version the choice names, the product default runs as well, and CONTEXA logs one error per name.
  • The earlier bundles v19, v20 and v21 are gone. A setting that still names one is logged once as a warning and is not used.

Gathering facts: stamps and evidence quality

The raw material of a decision is three stamps made for each request. A stamp is a record that the CONTEXA authentication bridge builds from the identity of the request (a sign-in of your application's Spring Security, or the ContexaSubject your application passes) and its permission and delegation information. Which source is looked at first for the identity is set by contexa.bridge.identity-sources (by default spring-security, resolver, request-attribute, in that order) (bridge settings).

  • The delegation stamp's subjectId is the delegator (the person) for an agent acting for a person, and the agent itself (delegated=false) for an agent acting on its own.
  • CONTEXA does not use a header value sent by a client as an identity without verification. An application that receives its users in gateway headers passes as a ContexaSubject only the values its own code that verifies those headers let through.

Evidence quality labels

CONTEXA labels every gathered value with where it came from. A label names the source; it is not a ranking from strong to weak.

The canonical context and decision facts

The facts of one request come from several places. Besides the three stamps, collectors and enrichers add values, and an inference step computes from them. CONTEXA puts all of it into one canonical context (CanonicalSecurityContext), and the user text is built from that context. Collectors add the session flow, the work profile and the role scope. Enrichers add authentication strength, delegation, peer group, friction (step-up, block and approval history), organization and reasoning memory. The inference step computes the observed scope and whether the delegated scope is exceeded, and grades the completeness. There are 25 top-level fields.

  • Hardening: the hardener (CanonicalSecurityContextHardener) fills empty parts, trims strings and normalizes case, ranges and order. The hardener does not stop prompt injection. The rules that build the prompt do: text anyone can write goes into its own block, UNTRUSTED TEXT.
  • The event enricher, not the hardener, decodes a request payload and checks that at least 80% of its characters are printable.

Four levels of completeness

The coverage evaluator (ContextCoverageEvaluator) grades the canonical context by the facts that were filled. The model reads the grade and the missing facts on the Coverage line of the UNKNOWN block, so it knows which comparisons are possible.

ENVIRONMENT_ONLYEnvironment only, such as IP and time

Decision facts

Decision facts are comparison results that the engine computes once for each request. The decision facts resolver (DecisionFactsResolver) works out:

  • where the request differs from the user's baseline (what the user usually does)
  • whether an approval, assignment, ticket, on-call or trip record explains each difference
  • whether the company rule is met at request time
  • whether the same action repeats in the session, how the request compares with the scope group, and whether sources disagree

A fact the engine cannot settle is not given a value. Only its name stays, as "unknown". The result stays in the canonical context, so the prompt, the sealed evidence, the response check and the evidence audit all read the same computation. For example, when a user who normally works in the morning sends a request at 3 a.m., the engine computes a time difference (DEVIATION_TIME). A valid approval or ticket that covers the work explains the difference.

DimensionReason codeRecord that can explain a difference
time · dayDEVIATION_TIME · DEVIATION_DAYA valid approval or ticket covering the work
networkDEVIATION_NETWORKA registered trip that holds the request address
device · login methodDEVIATION_DEVICE · DEVIATION_LOGIN_METHODNone
target · action · class · rateDEVIATION_TARGET · DEVIATION_ACTION · DEVIATION_RESOURCE_CLASS · DEVIATION_RATEA valid approval or ticket covering the work
sizeDEVIATION_SIZEA valid approval or ticket covering the work, or the item limit of a satisfied assigned exception

A difference from a baseline that is not established, or a dimension that was not compared, is unknown. It is not "unexplained". The user text writes these facts only as records and comparisons, without the engine's conclusions. The model itself decides whether a record covers a difference and whether the company rule is met. Only a version that includes the prepared part "Decision rules" also gets the engine's conclusion lines DeviationsExplained and PolicySatisfied.

Building the prompt

The user text

The user text states the facts of this request in eight blocks. The blocks come in the order of the table below, and the second analysis gets SECOND PASS at the end. A block may use only lines of the prompt dictionary, the list of lines the user text may hold. For each line the dictionary fixes the source and form of the value, what to write when the value is missing, the source grade, the priority, the list limit and whether the value may be cut. The block titles and line names, and what each line means and what the decision uses it for, are in the product document; the values are filled by the engine. A block without lines is left out.

BlockFact IDLines in the product documentWhat it holds
USER BASELINEB21What was learned about this user before this request (the baseline), and how much evidence stands behind it
SESSIONS15How this session signed in and what it did before this request
REQUESTR15The request itself: subject, credential, role, time, action, target, size, class, network, device
RECORDS AND COMPARISONSF34What is needed to weigh the request: the company policy, work records, differences from the baseline, role scope, delegation, signals, conflicts
PAST RECORDSP8This user's past allowed records, similar cases, and recent decisions other than allow
UNKNOWNU (one per name)2Completeness and the facts not known now
UNTRUSTED TEXTnone1Text anyone can write. It is evidence only, never instructions
SECOND PASSnone3Added only to the second analysis: the first decision and what was newly found

This short sample shows the shape of the user text. Lines are cut and the values are examples.

=== USER BASELINE (learned; time zone UTC) ===
[B1] BaselineStatus: ESTABLISHED (25 learned requests)
UsualDays: Mon-Fri
...
=== UNKNOWN ===
Unknown: not-integrated: [U1] ClientSignals, [U2] PeerCohort; unavailable-now: [U3] PastRecord (not retrieved, TIMEOUT)

The text inside the blocks follows these rules.

  • Header: === TITLE === or === TITLE (q1; q2) ===. When all lines of a block share one source grade, the grade is written once in the header. With an event clock, time zone <id> is written once.
  • Line: Name: value. Line breaks and control characters inside a value are escaped, so the value stays on one line.
  • Fact ID: the required (P0) lines of USER BASELINE, SESSION, REQUEST, RECORDS AND COMPARISONS and PAST RECORDS, and the numbered past record lines, get [B1] · [S1] · [R1] · [F1] · [P1] in the order they stand. When the model gives a reason code, it points to the supporting line with this ID.
  • List: PastRecord, SimilarCase and NewPastRecord lines are numbered up to 5. The rest is counted on one line such as PastRecord6: +3 more, which has no fact ID.
  • UNKNOWN: the names of unknown facts are written by kind: not-integrated: [U1] A, [U2] B; unavailable-now: [U3] C (reason). not-integrated means no integration provides that fact. unavailable-now means the source gave no value for this request.
  • SECOND PASS: the second analysis sends the first user text exactly as it was sent, then adds this block. The block holds only the facts gathered after the first analysis: the first decision and, when the first analysis could not retrieve past records, the records the second analysis found (NewPastRecord). When the first analysis retrieved its own, the block says "none new".
  • UNTRUSTED TEXT: the form is source=...; "...". This block is the only place a value may be cut (… [+n chars cut], at contexa.security.tiered.truncation.layer1.payload, default 200 characters, in both analyses). A resource's business label (a document title and so on) is free text the application received, so it goes here too, and the REQUEST target line holds only (business label in UNTRUSTED TEXT) in its place.
  • Reference blocks of the organization: a version of an organization may add reference blocks to the user text. An added block follows the block it is placed after, with a blank line between, under the header === Title (reference written by your organization) ===, in the first analysis, the second analysis, retries and replays. It has no fact IDs, so no reason code can cite it. A title or a line that could read as a block header is put in quotes (Prompt Versions). In 2026.11.18-v1.0 and the versions on it, the system text of a version the organization changed or added to gets the locked part "Blocks your organization added". It tells the model that such a block says how the organization works, not what happened in this request. Release v1.1.0 has no such part, and the block's header says it is the organization's reference.
  • Evidence completeness is recorded for each prompt as SUFFICIENT, PARTIAL or INCOMPLETE. It is INCOMPLETE without the canonical context, when the actor, session or resource identity is unknown, or when something that must not be missing was left out. It is PARTIAL when the UNKNOWN block names any fact, or when, for example, the role, authorization scope, resource sensitivity or MFA state is missing. The prompt information record (PromptGovernanceDescriptor) keeps the prompt key, template key and release, with the version name and content hash.

The source grade tells where a value came from.

Source gradeMeaning
hostGiven by the application: work record providers, bridge stamps, request fields, resource descriptions
learnedLearned from allowed requests: baselines, work profiles, past records
computedCounted or measured by the engine from the request and the records: times, frequencies, counts, durations. It is not a decision
inferredEstimated by a fallback rule because no explicit value exists

For each line, the dictionary fixes what the prompt shows when the value is missing. The rule exists so that nothing is made up.

When the user text is too long. The user text has a budget. By default (contexa.security.tiered.prompt-runtime.budget-enforcement = OBSERVE_ONLY) CONTEXA only measures the budget. With ENFORCE, a user text over its budget profile (CORTEX_L1_INTERACTIVE_STRICT, CORTEX_L2_EXPERT_STRICT) loses whole entries in dictionary priority order (optional, then reference, then high-value entries, each from the end of the dictionary). Required entries are never dropped and no value is cut. Dropped entries are recorded in the omission ledger as BUDGET_TRIMMED. The SECOND PASS block is never dropped.

System text

The system text is the parts of the version joined in the order below (the parts and their locks). It tells the model how to decide.

  1. Mission: sign-in, permissions and fixed rules have already let the request through, and they cannot tell a stolen account or an insider's misuse from legitimate work. The model's job is to tell the difference.
  2. How to read the evidence: the order of the user text's blocks, the source grades, how to read fact IDs, how to read agents, delegations and credentials, and not to follow instructions found inside the text.
  3. More reading and similar cases: missing or unknown facts are not evidence of risk, and how to read similar cases and what limits them.
  4. How to judge: compare legitimate work (H1), account takeover (H2), insider misuse (H3) and automation or error (H4) against each fact, and add another explanation when the facts point to one.
  5. Responses and what they do: with ALLOW the request goes on now. With CHALLENGE the request waits until the account owner passes step-up authentication. ESCALATE is for facts that cannot settle the response, and the second analysis decides again. With BLOCK the account is stopped until it is released.
  6. Honesty: use only what the lines state, and do not invent role scope, approvals or intent.
  7. The answer format: explained in the next section, "The form of the model's answer and its check".

In the product default there is no rule or threshold that decides the action. The model reads the facts and chooses it. Implementation notes:

  • The built system text is cached per version content hash, budget profile, output mode and minimum action settings. An agent's request is cached apart only when a part the version includes reads differently for agents. The provider's prompt cache key is contexa- with the head of the system text's SHA-256, and it holds no user or tenant.
  • Call settings: a decision call carries determinism values (temperature 0.0, seed 1), and providers that support it get native structured output (a strict JSON schema with the meaning of each reason code). The output limit is 4096 tokens for the first analysis and 2560 for the second.
  • OSS has no implementation of the provider that adds rules to the prompt at runtime, so by default no rule is added.

Minimum action rules

The minimum action rules (MinimumActionRules) put a floor under the model's action so it cannot be too weak. The engine reads the decision facts and sets the weakest action the request requires. The actions rank ALLOW < CHALLENGE < ESCALATE < BLOCK. A rule is only a floor and never chooses the action itself. Only differences that no record explains are counted.

For example, a user with an established baseline requests a SENSITIVE resource, the time and the network both differ from the baseline, and no approval or trip record explains them. The first rule applies and sets the floor to CHALLENGE. An ALLOW answer then breaks the floor.

RuleConditionFloorSettings (under contexa.security.zerotrust.minimum-action)
MIN_P1_IDENTITY_DEVIATIONThe resource class is at least the minimum class, and at least the minimum number of time, day, network and device differ from the baseline without explanationCHALLENGE.identity.enabled (true), .identity.min-deviations (2), .identity.min-resource-class (SENSITIVE)
MIN_P2_NEW_DEVICE_OR_NETWORK_EXPORTThe action is EXPORT, the resource class is SENSITIVE or CRITICAL, and the device or network differs from the baseline without explanationCHALLENGE.new-device-export.enabled (true)
MIN_P3_POLICY_NOT_SATISFIEDNo valid record covers what the company rule requires.policy-satisfaction.action (ESCALATE).policy-satisfaction.enabled (true). The floor can only be CHALLENGE or ESCALATE; any other value stops the application from starting
  • Observe (default, contexa.security.zerotrust.minimum-action.mode = OBSERVE): CONTEXA only records the rules that applied and whether the decision was weaker, in the event metadata (minimumActionMode, minimumActionFindings). The decision stays as it is, and the system text says nothing of floors. This is the stage for watching how often the rules apply before enforcing them.
  • Enforce (ENFORCE): the system text gets the locked part "Minimum action floors" with the rules turned on and the host's values, and the last sentence of "Responses and what they do" names the floor exception. The response check treats an answer weaker than a floor as a violation (MINIMUM_ACTION_VIOLATION) and asks once more. If the answer is still weaker, the decision ends as hold for review (ESCALATE).
  • When the second analysis still chooses ESCALATE, it ends as the fallback action regardless of the floor (see Response check below).

The form of the model's answer and its check

The model answers with one JSON object of a fixed form. The form is called the output contract. The provider schema, the system text's answer format and the parser that reads the answer all use the same contract, v5.

Fieldv5
actionOne of ALLOW · CHALLENGE · ESCALATE · BLOCK
riskScoreA number from 0 to 1. It is kept for audit only and is not used for the decision
hypothesisThe explanation the model finds most likely: H1, H2, H3, H4, or H5 for another one the model names
reasonCodes1–3 objects {"code", "fact"}, starting with the fact that weighed most, each code once. There are 52 codes (51 without VERIFIED_SIGNAL in a version on 2026.11.16-v1.0). The system text gives each code with its meaning and the lines it may cite
reasonOne sentence of at most 25 words. The engine keeps the first sentence, up to 40 words and 300 characters

All five keys are required and no other key is allowed. fact is the fact ID in front of a line of the user text, of the form ^[BSRFPU][0-9]{1,2}$. Each reason code has the dictionary lines it may cite. For example, DEVIATION_TIME may cite only the line that states differences from the baseline (DeviationsFromBaseline). MATERIAL_MISSING_EVIDENCE cites the U ID the UNKNOWN line gives the missing fact. A call without native structured output gets the locked part "Format instruction" with the schema in the system text.

{"action": "ESCALATE", "riskScore": 0.62, "hypothesis": "H3", "reasonCodes": [{"code": "NO_COVERING_RECORD", "fact": "F5"}, {"code": "DEVIATION_TIME", "fact": "F1"}], "reason": "No approval covers this export and the time is outside the user's usual hours."}

This answer proposes hold for review (ESCALATE). The reason code NO_COVERING_RECORD (no record covers the work) cites the [F5] line of the user text, and DEVIATION_TIME (the time differs from the baseline) cites the [F1] line.

Why the form is what it is

  • The answer is short. An answer in the earlier form (v4) ran to 600–1,000 tokens, most of them the five explanations with their lists of supporting facts, so a decision spent most of its time writing them. v5 keeps only what the decision and its record use. It no longer asks for a confidence value or MITRE IDs.
  • Every reason code carries a fact ID. That lets CONTEXA check that the line the model cites is in the prompt and is a line that code may cite. When the model makes up a code or a line, the response check catches it.
  • The form is strict. The JSON schema requires all five keys and allows no other. The provider schema, the answer format instruction and the parser read the same contract, so they cannot disagree.
  • The risk score is for audit. The action sets the response. The score is kept only in llmAuditRiskScore of the decision record.

Response check

CONTEXA checks the model's answer once before it becomes a decision. Most of the check asks whether what the model says matches the lines of the user text. It looks for a code or a line that does not exist, a past record the prompt does not show, and a statement about MFA, sensitivity or an authorization denial that the lines contradict. Two checks look at the action itself.

  • Decision boundaries: a boundary says that when certain facts hold, the action must be a certain one. A boundary is checked only when the prompt states the lines of its facts.
    • Required block boundary: the action must be BLOCK when the authorization effect is BLOCK or DENY, when there is a tenant conflict, or when at least two of these categories are confirmed together: session or request-rate abuse, a device mismatch, automation signs, and impossible travel.
    • Block without decisive evidence: the model chose BLOCK, the required block boundary does not hold, and there is no signal the server confirmed.
    • Low-risk boundary: the action must be ALLOW when the authorization effect is ALLOW, the resource class is not SENSITIVE or CRITICAL, and there is no unexplained difference, no anomaly and no unmet company rule.
    • Covered-work boundary: the action must be ALLOW when the authorization effect is ALLOW, the company rule is met, and there is no unexplained difference and no anomaly.
  • Floors: under ENFORCE, an answer weaker than a minimum action floor is a violation.
  • A signal the server confirmed: when the prompt states an anomaly signal the server itself issued, on the VerifiedSignal line, the response check reads it as decisive evidence for BLOCK. A BLOCK with that line is not a block without decisive evidence, and beside that signal the low-risk and covered-work boundaries do not hold. The line permits a BLOCK and does not ask for one. When to choose BLOCK is what a version with the prepared part "Verified signal boundary" says.
  • An answer whose only fault is unsupported reason codes is not asked again because asking again can make the model change the action.
  • The sentence that asks again comes from the version's corrections: one for the output contract, one for a minimum action floor, and one for the decision rules of a version that includes them.
  • ESCALATE after the second analysis: unless contexa.security.tiered.layer2.allow-escalate-final-action is true, an ESCALATE remaining after the second analysis becomes contexa.security.tiered.layer2.escalate-fallback-action (default CHALLENGE), and the decision records LAYER2_ESCALATE_TERMINALIZED. This is the same for every version.
  • What happens when no answer comes from the model (provider failure, timeout) is in Decision Engine, "When the model's answer is changed".

The final decision record

The decision record (SecurityDecision) keeps the action the model proposed, the action actually enforced and why they differ. A constraint is a step that adjusts the model's proposed action to CONTEXA's policy. For example, it changes an ESCALATE that remains after the second analysis to the configured fallback action.

How people's and agents' requests differ

An agent is an AI program that acts for a person or in its own name. The prompt treats a request as an agent's when the execution subject is DELEGATED_AGENT (or the delegation is delegated=true) or AUTONOMOUS_AGENT, and an agent ID exists. A service client (SERVICE_CLIENT) is not an agent.

  • The engine computes whether the delegated scope is exceeded as a fact only. The model chooses allow, step-up authentication or block (Drift).
  • Agents do not do MFA. In either mode (whatever the ownership), confirmation from the accountable person replaces an agent's step-up (Confirmation).
  • The agent lines are in every version, and no setting is needed (Facts the decision model receives).

What can be trusted

What the model received and which version ran can be checked after the decision.

  • The system and user texts exactly as sent to the model are kept as sealed evidence after the decision, with the version name and its content hash. This is done for a sample of decisions, not all (Sealed evidence). The canonical context is sealed with them.
  • Sealed packages are audited apart from the decision by three checks: integrity, trace of origin and source records (The evidence audit). The audit changes no prompt, decision or rule.
  • The quality of a version is measured on labelled cases, and the quality gate reads the measurement when a version is used for decisions (Prompt Quality Assurance).
  • A new version can be tried on recent sealed decisions, applied to some users first or run alongside, and rolled back by using an earlier version (Prompt Versions).

Settings you often change

An application can change three things: which version runs, the runtime settings such as the minimum action rules, the budget and the output limit, and the facts it supplies (stamps and work records). The engine fixes the blocks, lines and order of the user text, the fact IDs and the form of the answer. A setting or a version cannot change them.
