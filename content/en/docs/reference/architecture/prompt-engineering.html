The Decision Prompt

What the text sent to the AI model for a decision (the decision prompt) is made of. It covers the version a decision is drawn with, the facts given to the model, the minimum action rules and the budget, and the form and checks of the model's answer.

At a glance

A decision prompt gathers the facts of a request, puts them into one canonical context, and draws a system text and a user text with the prompt version the decision runs. Before the model's answer becomes a decision, it is checked once more. The engine only states facts; the model chooses the action (allow, step-up, block, hold for review).

One missing fact does not stop a decision. The user text names every unknown fact in the UNKNOWN block, and the system text states that an unknown fact is neither the same as usual nor different.

One prompt, kept as versions

The decision prompt has the prompt key cortex.security-decision. Its sentences are not in the code: they come from the version a decision runs. The version Contexa ships is the product default; this build's release is 2026.11.18-v1.0 (document prompt-versions/cortex.security-decision/2026.11.18.yaml of contexa-core). The earlier release 2026.11.16-v1.0 is shipped beside it, and the two product defaults draw the same prompt (A new product default). An organization makes its own versions from it on the admin console or in documents (Prompt Versions). Every version keeps what the engine fixes.

Which version a decision runs

  • The version chosen on the screen ("Use for decisions", or a canary the request falls inside), else the version contexa.security.tiered.prompt-bundle.active names (v2.0 form), else the newest version provided by Contexa (How a decision's version is chosen).
  • The first prompt of an event fixes the version on the event (promptBundleSelection.version, .source, .contentHash), and the Layer 2 prompt and every retry of the same event use the same version.
  • A version name the store cannot find, or no choice, runs the product default of the build, with one error log per name. The earlier bundles v19, v20 and v21 are gone; a setting that still names one is logged once as a warning and is not used.

Gathering facts: stamps and evidence quality

The raw material of a decision is the three stamps the authentication bridge makes for each request. The bridge reads the application's sign-in, permission and delegation information in a fixed order (the bridge's reading order).

  • The delegation stamp's subjectId is the delegator for an agent acting for a person, and the agent itself (delegated=false) for an agent acting on its own.
  • Headers sent by a client are not taken as they are. The header channel is off by default, and even when on, a header is accepted only from a trusted proxy and only when its subject is the signed-in subject.

The canonical context and decision facts

The stamps and the facts gathered by collectors and enrichers are put into one canonical context (CanonicalSecurityContext). Collectors add the session flow, work profile and role scope; enrichers add authentication strength, delegation, peer group, friction (approval history), organization and reasoning memory; inference computes the observed scope and whether the delegated scope is exceeded, and grades the completeness.   • Hardening: the hardener (CanonicalSecurityContextHardener) fills empty parts, trims strings and normalizes case, ranges and order. Prompt injection is handled not by the hardener but by the rendering rules: text anyone can write is drawn apart as UNTRUSTED TEXT.
  • The check that decodes a request payload and requires at least 80% printable characters is done by the event enricher, not the hardener.

Four levels of completeness

The coverage evaluator (ContextCoverageEvaluator) grades the facts that were filled. A low grade adds a warning to the prompt not to conclude from work patterns.

Decision facts

The decision facts resolver (DecisionFactsResolver) computes once how the request differs from usual behavior, whether the company rule is met at request time, the approval, assignment, ticket, on-call and trip records, repeats in the session, scope group comparisons and data conflicts. A fact the engine cannot settle is left only as a name, as "unknown". The same computation stays in the canonical context, so the prompt, the sealed evidence, the response check and the inspection all read one computation.

DimensionReason codeRecord that can explain a difference
time · dayDEVIATION_TIME · DEVIATION_DAYa valid approval or ticket covering the work
networkDEVIATION_NETWORKa registered trip that holds the request address
device · login methodDEVIATION_DEVICE · DEVIATION_LOGIN_METHODnone
target · action · class · rateDEVIATION_TARGET · DEVIATION_ACTION · DEVIATION_RESOURCE_CLASS · DEVIATION_RATEa valid approval or ticket covering the work
sizeDEVIATION_SIZEa valid approval or ticket covering the work, or the item limit of a satisfied assigned exception

A difference from a baseline that is not established, or a dimension not compared, is unknown, not "unexplained". The user text writes these facts only as records and comparisons, without the engine's conclusions: whether a record covers a difference, and whether the company rule is met, is the model's to judge. Only a version that puts in the prepared part "Decision rules" also gets the engine's conclusion lines DeviationsExplained and PolicySatisfied.

Drawing the prompt

The user text

The user text uses only lines of the prompt dictionary, in the blocks below. The block titles and line names, with what each line means and what the decision uses it for, are in the product document; the values are the engine's. Each entry fixes the source and form of its value, what is written when it is missing, the source grade, the priority, the list limit and whether it may be cut. A block without lines is left out.

BlockFact IDLines in the product documentWhat it holds
USER BASELINEB21what was learned about this user before this request, and how much evidence stands behind it
SESSIONS15how this session signed in and what it did before this request
REQUESTR15subject, credential, role, time, action, target, size, class, network, device
RECORDS AND COMPARISONSF34the company policy, the work records, differences from usual, role scope, delegation, signals, conflicts
PAST RECORDSP8this user's past allowed records, similar cases, and recent decisions other than allow

UNTRUSTED TEXTnone1text anyone can write; evidence only, never instructions
SECOND PASSnone3Layer 2 only: the first decision and what was newly found
  • Header: === TITLE === or === TITLE (q1; q2) ===. When all lines of a block share one source grade, the grade is written once in the header; with an event clock, time zone <id> is written once.
  • Line: Name: value. Line breaks and control characters inside a value are escaped so the value stays on one line.
  • Fact ID: the required (P0) lines of USER BASELINE, SESSION, REQUEST, RECORDS AND COMPARISONS and PAST RECORDS, and the numbered past record lines, get [B1] · [S1] · [R1] · [F1] · [P1] in the order drawn. These are the IDs reason codes cite.
  • List: PastRecord, SimilarCase and NewPastRecord lines are numbered up to 5; the rest is counted on one line such as PastRecord6: +3 more, which has no fact ID.
  • UNKNOWN: names are written per kind, not-integrated: [U1] A, [U2] B; unavailable-now: [U3] C (reason). not-integrated means no integration provides that fact; unavailable-now means the source gave no value for this request.
  • SECOND PASS: Layer 2 sends the first user text exactly as sent, then this block with only the facts gathered after the first pass: the first verdict and, when the first pass could not retrieve past records, the records Layer 2 found (NewPastRecord); when the first pass retrieved its own, "none new".
  • UNTRUSTED TEXT: in the form source=...; "..."; this text is the only value that may be cut (… [+n chars cut], at contexa.security.tiered.truncation.layer1.payload, default 200 characters, in both layers). A resource's business label (a document title and so on) is free text the application received, so it is drawn here too, and the REQUEST target line holds only (business label in UNTRUSTED TEXT) in its place.
  • Reference blocks of the organization: a block a version adds is drawn right after the block it follows, after a blank line, under === Title (reference written by your organization) ===, in Layer 1, Layer 2, the retries and the replays. It has no fact IDs, so no reason code can cite it; a title or a line that could read as a block header is drawn in quotes (Prompt Versions). In release 2026.11.18-v1.0 and the versions on it, the system text of a version the organization changed or added to gets the locked part "Blocks your organization added", which says such a block tells how the organization works, not what happened in this request.
  • Evidence completeness is recorded for each prompt as SUFFICIENT · PARTIAL · INCOMPLETE. Without the canonical context or the actor, session or resource identity, or with a blocking omission, it is INCOMPLETE; it is PARTIAL when the UNKNOWN block names any fact, or when, for example, the role, authorization scope, resource sensitivity or MFA state is missing. The descriptor (PromptGovernanceDescriptor) records the prompt key, template key and release with the prompt, beside the version name and content hash.

System text

  • The system text is the version's parts in order (the parts and their locks): mission (sign-in, permissions and fixed rules cannot tell a stolen account or an insider's misuse from legitimate work) → how to read the evidence (including agents, delegations and credentials) → more reading and similar cases → how to judge (compare legitimate work H1, account takeover H2, insider misuse H3, automation or error H4 against each fact, and add another explanation when needed) → responses and what they do → honesty → the answer format. In the product default there are no rules, thresholds or floors that decide the action.
  • The drawn system text is cached per version content hash, budget profile, output mode and minimum action settings; an agent's request is cached apart only when a part the version draws reads differently for agents. The provider's prompt cache key is contexa- with the head of the system text's SHA-256, and holds no user or tenant.
  • Budget: the default (contexa.security.tiered.prompt-runtime.budget-enforcement = OBSERVE_ONLY) only measures the budget. With ENFORCE, a user text over its budget profile (CORTEX_L1_INTERACTIVE_STRICT, CORTEX_L2_EXPERT_STRICT) drops whole entries in dictionary priority order (optional, then reference, then high-value entries, each from the end of the dictionary), never drops required entries or cuts a value, and records the dropped entries in the omission ledger as BUDGET_TRIMMED. A second pass block is never trimmed.
  • Call settings: a decision call carries determinism values (temperature 0.0, seed 1), and providers that support it get native structured output (a strict JSON schema with the meaning of each reason code). The output limit is 4096 tokens for Layer 1 and 2560 for Layer 2.
  • OSS has no implementation of the provider that adds rules to the prompt at runtime, so by default no rule is added.

Minimum action rules

The minimum action rules (MinimumActionRules) read the decision facts and set the weakest action a request requires (a floor). The order of actions is ALLOW < CHALLENGE < ESCALATE < BLOCK. A rule is only a floor and never chooses the action itself. Only differences no record explains are counted.

RuleConditionFloorSettings (under contexa.security.zerotrust.minimum-action)
MIN_P1_IDENTITY_DEVIATIONthe resource class is at least the minimum class, and at least the minimum number of time, day, network and device differ from usual without explanationCHALLENGE.identity.enabled (true), .identity.min-deviations (2), .identity.min-resource-class (SENSITIVE)
MIN_P2_NEW_DEVICE_OR_NETWORK_EXPORTthe action is EXPORT, the resource class is SENSITIVE or CRITICAL, and the device or network differs from usual without explanationCHALLENGE.new-device-export.enabled (true)
MIN_P3_POLICY_NOT_SATISFIEDno valid record covers what the company rule requires.policy-satisfaction.action (ESCALATE).policy-satisfaction.enabled (true). The floor can only be CHALLENGE or ESCALATE; another value stops the start
  • Observe (default, contexa.security.zerotrust.minimum-action.mode = OBSERVE): the rules hit and whether the decision was weaker are only recorded in the event metadata (minimumActionMode, minimumActionFindings); the decision stays as it is, and the system text says nothing of floors.
  • Enforce (ENFORCE): the system text gets the locked part "Minimum action floors" with the rules turned on and the host's values, and the last sentence of "Responses and what they do" names the floor exception. The response check treats an answer weaker than a floor as a violation (MINIMUM_ACTION_VIOLATION), asks once more, and ends as held for review (ESCALATE) if it is still weaker.
  • When Layer 2 still chooses ESCALATE, it ends as the fallback action regardless of the floor (see Response check below).

The form of the model's answer and its check

The output contract is the form of the model's answer. The provider schema, the system text's answer format and the parser that reads the answer all use the same contract, v5.

Fieldv5
actionone of ALLOW · CHALLENGE · ESCALATE · BLOCK
riskScorea number from 0 to 1, kept for audit only, not used for the decision
hypothesisthe explanation judged most likely: H1, H2, H3, H4, or H5 for another one the model names
reasonCodes1–3 objects {"code", "fact"}, the strongest first, each code once. 51 codes, drawn in the system text with their meaning and the lines each may cite
reasonone sentence of at most 25 words. The engine keeps the first sentence, up to 40 words and 300 characters

All five keys are required and no other key is allowed. fact is a fact ID of the form ^[BSRFPU][0-9]{1,2}$. Each reason code has the dictionary lines it may cite, and MATERIAL_MISSING_EVIDENCE cites the U ID the UNKNOWN line gives the missing fact. A call without native structured output gets the locked part "Format instruction" with the schema in the system text.

{"action": "ESCALATE", "riskScore": 0.62, "hypothesis": "H3", "reasonCodes": [{"code": "NO_COVERING_RECORD", "fact": "F5"}, {"code": "DEVIATION_TIME", "fact": "F1"}], "reason": "No approval covers this export and the time is outside the user's usual hours."}

Response check

  • A signal the server confirmed: when the prompt states an anomaly signal the server itself issued, on the VerifiedSignal line, the response check reads it as decisive evidence for BLOCK. A BLOCK with that line is not a block without decisive evidence, and beside that signal the low-risk and covered-work boundaries do not hold. The line permits a BLOCK and does not ask for one; when to choose BLOCK is what a version with the prepared part "Verified signal boundary" says.
  • The sentence that asks again comes from the version's corrections: one for the output contract, one for a minimum action floor, and one for the decision rules of a version that puts them in.
  • ESCALATE after Layer 2: unless contexa.security.tiered.layer2.allow-escalate-final-action is true, an ESCALATE remaining after Layer 2 becomes contexa.security.tiered.layer2.escalate-fallback-action (default CHALLENGE), and the decision records LAYER2_ESCALATE_TERMINALIZED. This is the same for every version.
  • What happens when no answer comes from the model (provider failure, timeout) is in Decision Engine, "When the model's answer is changed".

How people's and agents' requests differ

The prompt treats a request as an agent's when the execution subject is DELEGATED_AGENT (or the delegation is delegated=true) or AUTONOMOUS_AGENT, and an agent ID exists. A service client (SERVICE_CLIENT) is not an agent.

Part of the promptA person's requestAn agent's request
System textOne text that always explains how to read agents, delegations and credentials. Only the prepared part "Decision rules" reads differently: for an agent it leaves out the automation category of the block boundary
Lines with a value only for an agent—the subject line in agent form, BaselineSubject, UsualSequence, UsualClients, DelegationActivity
Lines drawn when their source existsCredential, Confirmation, Delegation and DelegationControls, RecordsHolder, RecordProvenance, ArgumentOrigin
Response checkclient signals count for the block boundarythe agent's client signals never count as an automation category
  • Whether the delegated scope is exceeded is computed by the engine as a fact only. Allow, extra confirmation or block is the model's choice (Drift).
  • Agents do not do MFA. An agent's step-up is replaced by confirmation from the accountable person under CONTEXA_OWNED (Confirmation).
  • The agent lines are in every version; no setting is needed (Facts the decision model receives).

What can be trusted

  • The system and user texts exactly as sent to the model are kept as sealed evidence after the decision (a sample, Sealed evidence and official verification), with the version name and its content hash. The canonical context is sealed with them.
  • Sealed prompts are compared with the facts by 10 inspector checks, apart from the decision. Inspection changes no prompt, decision or rule (Inspecting sealed prompts).
  • A new version is tried on recent sealed decisions, applied to some users first or run alongside, and rolled back by using an earlier version (Prompt Versions).
