Decision Engine: How a Decision Is Made

The decision engine uses an AI model to make a decision for each request (allow, step-up authentication, hold for review or block), stores it, and applies it to the same user's next request. On this page you can check which requests are analyzed, which facts the model receives and how the two analysis layers decide, when CONTEXA changes the model's answer, how long a decision lasts, and what the engine learns.

Overview

When a request calls a protected method (@Protectable), CONTEXA sends the request's facts to an AI model and gets a decision back. A decision is one of four: allow (ALLOW), step-up authentication (CHALLENGE), hold for review (ESCALATE) or block (BLOCK).

By default the request does not wait for the decision. The method runs and the response leaves first. Then CONTEXA makes the decision in the background, stores it, and applies it from the same user's next request. For example, if the model chooses block, that user's next request gets a block response. A method that needs a decision inside the call is marked @Protectable(sync=true). That method runs after it receives its decision.

The AI model chooses the action. The CONTEXA engine only gathers the facts it sends and does not choose the action. The model receives:

  • This request: the user, resource, time, IP address, device and the result of the method
  • Session flow: the earlier requests of the same session
  • Differences from the behavioral baseline: the baseline is what CONTEXA has learned about each user's working hours, devices, networks and targets. What is learned explains how.
  • Business context: whether business records such as approvals, tickets and assignments (Company Records) explain those differences
  • Past decision records: the user's earlier decisions and past requests similar to this one

When the model cannot be called or its answer has the wrong form, CONTEXA chooses the action itself. When the model's answer is changed lists those cases. A user with no stored decision, or whose decision has expired, is in the state pending analysis (PENDING_ANALYSIS). Requests in that state go through and become candidates for analysis.

Which requests are analyzed

Not every request goes to the AI model. Only the cases marked "analyzed" below call the model and produce a new decision. The other cases do not call the model.

If the decision is allow, the method runs; otherwise the call is refused (enforce mode). A stored allow does not answer the call, so every call is decided. Only a block, step-up or hold already in force answers it without analysis. The wait is at most 40 seconds (contexa.security.zerotrust.agent.flight.wait). The order of a decision: Layer 1 and Layer 2

A request that is analyzed gets its decision in at most two steps. Layer 1 sends the facts to the model and gets an action. If that action is not hold for review (ESCALATE, the answer "these facts cannot decide it"), it is the final decision. Only a request that received hold for review goes to Layer 2, which decides the same request once more. Most requests end in Layer 1.

Layer 1 starts the search for past decision records in the background as soon as the analysis begins. The search runs while the session flow and the baseline are prepared. When the prompt needs the records, Layer 1 waits up to 0.6 seconds (contexa.security.tiered.layer1.timeout.interactive-rag-wait-ms). If the search has not finished by then, the decision is made without past records.

The records found go into the PAST RECORDS block of the prompt. There the model compares the current request with the user's earlier requests. CONTEXA looks for records in two ways at once.

SearchLayer 1Layer 2
Exact lookupReads the user's allowed records of the same kind of action by conditions. It uses no embedding (a vector calculation for comparing meaning). Records of the same target come first, newest first. They appear as PastRecord lines in the prompt.Reuses the records Layer 1 found, and looks up again only when there are none.
Similarity searchFinds up to 12 records similar in meaning (contexa.security.tiered.layer1.vector-search-limit), with relevance 0.5 or more (layer1.rag.similarity-threshold), and draws them as SimilarCase lines. It runs only when the prompt version contains the part "Similar case reading". A version without that part uses the exact lookup only.Reuses the records Layer 1 found, and searches again only when there are none (up to 5, layer2.rag-top-k, relevance 0.5 or more).
Overload protection. When the model answers "cannot decide" (ESCALATE) for many requests, Layer 2 calls would surge. To prevent that, CONTEXA counts Layer 1 results per organization (per user when there is no organization) and request path. Once at least 11 results are counted and more than half of them are ESCALATE, CONTEXA does not call Layer 2 and ends the request with step-up authentication. The count restarts after 100 results, and also after a day without records. The ratio and counts are fixed in the code.

A different model for each layer

Layer 1 and Layer 2 can use different models, for example a fast, inexpensive model for Layer 1 and a more careful one for Layer 2. If you set nothing, both layers use the primary chat model.

contexa:
  security:
    tiered:
      llm:
        layer1:
          model: gpt-4o-mini   # empty: the primary chat model
        layer2:
          model: gpt-4o        # empty: the primary chat model

The example works as is when the primary chat model is OpenAI (only the name changes within the same provider).

  • Model order: the layer's model → (if set) the layer's backup model (layerN.backup.model) → the primary chat model.
  • A model name with no connection setting (contexa.llm.bindings.chat) runs on a copy of the primary chat model with only the name changed. The copy works for OpenAI chat models (mutate()) and for Anthropic chat models (CONTEXA builds the copy again with the same client and default options). A model that cannot be copied, such as Ollama, needs its own connection setting.
  • If a layer model cannot be made, the application still starts. One ERROR line at start names the layer, the model that was set and the model that runs in its place (the backup model, else the primary chat model), so check the start log. A wrong model name of the same provider cannot be detected at start and fails at the first call of that layer.

After the decision: five steps

Numbered steps (handlers) process a decision from the moment it is made until it is stored and recorded. They run in number order. The first step (50) is the Layer 1 and Layer 2 analysis described above. The others apply the decision, keep it as evidence, record it and forward it.

How a decision is stored and applied

In enforce mode (ENFORCE), CONTEXA stores the decision in the user decision store: server memory in standalone mode, Redis in distributed mode. The user's next request reads its decision from this store and applies it. Each decision has a lifetime. When it ends, the decision disappears from the store and the user is pending analysis again.

DecisionLifetimeWhere it applies
Allow (ALLOW)15 minutes (set with contexa.security.zerotrust.allow-validity)Only in the same session, IP address and browser it was made for. A request from anywhere else is analyzed again.
Step-up authentication (CHALLENGE)1,800 seconds (30 minutes). A step-up that CONTEXA chose because the model did not decide lasts 60 secondsEvery session of the user
Held for review (ESCALATE)300 seconds (5 minutes). With the default settings it is not stored as a final decision (see below)Every session of the user
Block (BLOCK)No expiry (until an administrator releases it or the block-release MFA is passed)Every session of the user
Pending analysis (PENDING_ANALYSIS)No stored decisionThe request goes through and analysis starts
  • A stricter decision is never overwritten by a weaker one. From strictest to weakest the order is block, hold, step-up. A weaker new decision is not stored while a stricter one is in force.
  • Hold for review is not stored with the default settings. When Layer 2 chooses hold, CONTEXA replaces it with contexa.security.tiered.layer2.escalate-fallback-action (default CHALLENGE) and stores that. To store the hold as it is, set contexa.security.tiered.layer2.allow-escalate-final-action=true.
  • Shadow mode (SHADOW) makes decisions and applies none. The model decides as in enforce mode, and the decision is written to the decision observation record. CONTEXA remembers the decision under separate keys, only to know whether the user's next request needs a new analysis. The filters and method checks that refuse requests or change authorities never read this memory. Shadow mode also sends no block signal, writes no blocked-user record, does not restrict an agent's later requests to reading, and sends no risk signal. An allow in this memory is used for learning.
  • An event carries the operating mode it was made under (decisionBoundaryMode). An event made in shadow mode is not enforced even if the mode became ENFORCE by the time its decision is ready.
  • Without the decision observation record (database), nothing is enforced. CONTEXA only keeps the decision, and the user stays pending analysis. New analyses of the same context pause for 30 seconds (contexa.security.zerotrust.analysis.audit-failure-cooldown-ms). When the same event is processed again, the kept decision is used without a new analysis.

How a stored decision changes authorities on the next request is described in request-time enforcement.

When the model's answer is changed

The action the model chose is the final decision except in the cases below. When the model cannot be called or its answer cannot be used, CONTEXA picks the safer action (step-up or hold).

CaseFinal decision
No answer from the model (provider outage, call timeout, output or context limit)Step-up authentication. Even in Layer 1 it is not sent to Layer 2. Because the model did not decide, this step-up lasts only 60 seconds, and in that time CONTEXA asks the model again up to 3 times (10 seconds apart). When the model decides, its decision replaces this step-up.
No action value, or an unknown oneStep-up authentication; DENY-like values are read as block and REVIEW as hold.
The answer breaks the response contract and still does after one corrective retry by CONTEXAHeld for review (from Layer 1 it goes to Layer 2). In a prompt version with the prepared part "Decision rules", a boundary still broken turns it into the boundary's action (block or allow).
Layer 1 itself fails (no result, Layer 1 time limit exceeded)Turned into hold and sent to Layer 2.
Layer 2 chooses hold (ESCALATE)No analysis follows Layer 2 and no person reviews the request, so the hold is replaced with contexa.security.tiered.layer2.escalate-fallback-action (default CHALLENGE).
Layer 2 fails technically (exception, over 30 seconds)Ends as the same escalate-fallback-action. If the model had already chosen step-up or block before the failure, that decision stands. With allow-escalate-final-action=true, hold is stored as the final decision (5 minutes).
Overload protection (the box above)Step-up authentication
The minimum-action rule in enforce mode (contexa.security.zerotrust.minimum-action.mode=ENFORCE) and an answer weaker than the floorCONTEXA asks once more with a correction, then holds if the answer is still weaker. What is learned

The engine learns two things from decisions: each person's behavioral baseline (working hours, devices, networks, targets and so on) and past decision records. Both become facts the model receives in later analyses. The more allow decisions accumulate, the firmer the idea of "what is normal for this user" becomes, and the more clearly a request outside it stands out.

  • Only allow decisions that actually stand are learned into the baseline. In enforce mode that is the stored allow. In shadow mode it is the allow CONTEXA remembered. An allow not stored because a stricter decision was in force, and late results of deleted accounts, are not learned. Learning is an exponential moving average (factor 0.1). For a person's request the organization baseline is updated too.
  • When a baseline counts as established: a personal baseline needs 20 or more learned requests, on 5 or more different days, with no more than 20% unseen values in its last 10 learnings. An organization baseline must learn from 3 or more people. Items that keep several values, such as IP ranges, push out the least used value when full (older values count less, with a 14-day half-life).
  • An unexplained new value is held, not learned at once. In enforce mode, when a request for a resource of sensitive class or above has an hour, day, network or device that differs from the baseline and that no business record explains, CONTEXA holds the request. It learns the value when the same value is seen at least twice on at least two days, or when the user passes step-up authentication on a request with that value. This keeps a value seen once from becoming usual behavior right away. For agents a first-seen value is held whatever the resource class. Shadow mode learns without this hold.
  • Requests that were stopped and then passed step-up are learned too. In enforce mode, a request stopped by step-up, hold or block is kept. CONTEXA learns it with weight 0.5 (an allowed request has weight 1) once the user passes MFA or an administrator releases the block.
  • Past decision records are written to the vector store when a decision is stored (remembered, in shadow mode), whether it is allow, step-up, hold or block. Records older than 90 days (contexa.rag.etl.behavior.retention-days) are deleted every day at 03:45. Zero or less keeps them forever.
  • The behavioral baseline is deleted after 30 days (contexa.security.zerotrust.baseline.retention) without new learning.

Good to know in operation

  • Seeing decisions: decisions are kept in the decision observation table (ctxa_ai_security_decision_observation) and the audit log, and shown in the Zero Trust console's decision records (/contexa/admin/zero-trust/decisions) and the admin console's security event log (/contexa/admin/security-monitor).
  • If no decision appears and users stay pending, check first: the operating mode is not OBSERVE or DISABLED, chat model and vector store beans exist, and the decision observation database can be written.
  • The analysis queue (where events collect before they join an analysis line) holds up to 10,000 events (contexa.security.plane.monitor.queue-size).
  • One event has a 180-second budget. If an attempt waits more than 60 seconds in the analysis thread pool (default core 32, max 64, queue 256) or exceeds the budget, it ends without a decision, and the event is queued again at most 3 times.
  • In distributed mode (contexa.infrastructure.mode=distributed) events go to the Kafka topic ctxa.<application name>.security.events.<category>.<type> (for example ctxa.order-service.security.events.authorization.method; the application name is spring.application.name, and without one the prefix is just ctxa.), and events that could not be handled go to the DLQ topic (ctxa.<application name>.security-events-dlq, or the name set in contexa.security.kafka.topic.dlq).
  • contexa.security.tiered.layer2.enable-soar has no effect in the OSS today: no code fills the playbook a blocking decision would carry, so no SOAR runs (SOAR).
