Prompt Governance and Inspection

How to change decision prompt bundles safely and check the result. It covers what identifies a bundle, which bundle runs for each request, how to release a new bundle through shadow, canary and active and roll it back, and how to inspect sealed prompts and replay them with another bundle.

At a glance

Decision prompts run as versioned bundles (the differences between the three bundles are in Decision Prompts and Bundles). The principle for changing a bundle is observe first, check, then enforce. A new bundle is first run on sampled requests apart from the decision (shadow), then applied to part of the scope (canary), then made the default (active). A sealed decision can also be asked again with another bundle (replay).

What a bundle is

A bundle is a governance descriptor (prompt key, template key, version, output contract version, release status, rollback version and so on) together with the shape of the user text its code draws. The prompt version is the bundle version, and it names the classpath manifest prompt-bundles/manifests/<prompt key>/<version>.json.

  • Three bundles can run. The decision prompt (cortex.security-decision) has 71 manifests (22 of the v19 line, 29 of v20, 20 of v21), but this build runs only 2026.10.24-v19.21 · 2026.10.24-v20.26 · 2026.10.30-v21.19; the others are records of earlier bundles. The manifests of the IAM module's three prompts (ConditionTemplate · PolicyGeneration · PolicyGenerationStreaming) are in the same list.
  • Eleven elements make up a bundle. A PRESENT element hashes its content; an ABSENT · UNVERSIONED · INCLUDED element hashes a fixed marker, so the state itself is part of the identity, and the bundle hash covers every element.
  • Checked when read. A manifest whose bundle hash does not match its elements, or two manifests with the same name and different hashes, fail at once.
  • Manifest fields: elements, golden inputs, parent version, change summary, problem IDs, author, frozen date, vocabulary version and compatible vocabulary versions, rollback targets, declared model profiles, evaluation scenario families.

How each request gets its bundle

One selector chooses the bundle each request runs, set by contexa.security.tiered.prompt-bundle.selector. The first prompt of an event writes the bundle onto the event, and the Layer 2 prompt of the same event uses the same bundle. The prompt execution information records the source it was chosen from.

Selection sourceWhen
BUILD_DEFAULTnothing was chosen, the selector failed, or the chosen version is not one this build runs (one error log per version)
CONFIGURATIONselector CONFIGURATION (default): the version in contexa.security.tiered.prompt-bundle.active, for every request
REGISTRYselector registry: the latest ACTIVE release of the request's scope, or of PLATFORM_GLOBAL when the scope has none
CANARYselector registry: the scope's CANARY release, for a request inside the canary share and targets
SHADOWthe scope's SHADOW release, only on a sampled copy apart from the decision (Shadow runs)
REPLAYwhen a sealed decision is asked again with a chosen bundle (Replay)

The registry selector caches a scope's releases for up to 60 seconds and checks for invalidation every 5 seconds. State transitions and rollbacks announce the invalidation. While the registry cannot be read, the build default bundle runs.

Releasing a new bundle

The six states

The registry has one state vocabulary (PromptBundleState). Names stored earlier are read with the same meaning, and the transition API accepts both. Only ACTIVE and CANARY are actually enforced.

  • EVALUATION_NOT_FOR_BUNDLE_HASH means the recorded evaluation was not made with this bundle's hash. A bundle's evidence is only an evaluation made with that bundle.
  • TEVV_GATE_NOT_READY: the evaluation must cover the manifest's evaluation scenario families (evaluationScenarioFamilies; when none, PROMPT_INJECTION · TOOL_MISUSE · MEMORY_POISONING). v20.26 and v21.19 declare PROMPT_INJECTION · MEMORY_POISONING.
  • A blocked transition changes nothing and is recorded with its reasons. An applied transition changes the registry state and the approval and rollback records, and announces a runtime cache invalidation.
  • Moving to ACTIVE turns the other ACTIVE of the same scope, key and template into DEPRECATED, so only one active release remains.

  "targetReleaseStatus": "SHADOW",

}

The response is a transition receipt: 200 when applied, 422 with the reasons when blocked, 400 for a state name of no vocabulary. An empty registryScope means PLATFORM_GLOBAL.

Registration at start

When the application starts, the build's three bundles are registered in the PLATFORM_GLOBAL scope. A new row starts with its descriptor's status: v19.21 as ACTIVE (but AVAILABLE when an ACTIVE of another bundle this build runs already exists), v20.26 and v21.19 as AVAILABLE. Existing rows keep their operational fields (state and so on). An ACTIVE row of a bundle this build no longer runs does not hold back the new build default.

Shadow runs and canary

  • A shadow run tries a candidate bundle on real requests without deciding anything. It reads the registry's SHADOW release whichever selector chooses the decision bundle, so an application that uses the configuration selector can also try a candidate.
  • A request whose event ID hash is below contexa.security.tiered.prompt-bundle.shadow.sample-percent (0–100, default 0 = no run) is sampled. The shadow runner exists only when this setting is written.
  • Up to shadow.daily-call-cap (default 100) runs per UTC day, one model call at a time. The event is copied before the decision and analyzed on another thread after it, then sealed as the SHADOW stage. Nothing is enforced or learned. A SHADOW release of a version this build does not run is skipped.
  • Canary runs only with the registry selector. The registry row's canary_percent (0–100, the whole scope when absent) is applied to the requester's hash (the user, else the session, else the event), and canary_tenants · canary_resource_families narrow it to tenants and resource families. Other requests use the latest ACTIVE.
  • OSS has no API or page that stores the canary share and targets. These three columns must be written directly in the registry table of the database.

Rollback and emergency stop

A rollback immediately replaces the bundle running in a scope with a rollback target its manifest declares. The original bundle becomes DEPRECATED and the target ACTIVE (other ACTIVEs of the scope also become DEPRECATED); the runtime cache is told, and the execution is recorded with the conditions checked. A refused rollback is recorded with its reasons and changes nothing.

Refusal reasonCondition
SOURCE_NOT_EXECUTINGthe original version is not ACTIVE or CANARY in the scope
TARGET_NOT_IN_BUILDthe target's manifest is not in this build
TARGET_NOT_DECLAREDthe target is not in the original manifest's rollbackTargets
VOCABULARY_INCOMPATIBLEthe target's manifest cannot read the current vocabulary version
TARGET_NOT_REGISTEREDthe target has no registry row in the scope
POLICY_SET_MISSINGthe target's policy set is missing (recorded as NOT_APPLICABLE without a policy set lookup)
 
POST /contexa/admin/api/prompt-quality/releases/rollback
Content-Type: application/json

{
  "registryScope": "PLATFORM_GLOBAL",
  "promptKey": "cortex.security-decision",
  "fromVersion": "2026.10.24-v20.26",
  "toVersion": "2026.10.24-v19.21",
  "reason": "Decision quality dropped after the release",
  "emergency": false
}

The result holds the execution key (RBX-…), the status and the conditions checked. The status is EXECUTED, or REFUSED with HTTP 422. An emergency stop ("emergency": true) runs the same way and ends as AWAITING_APPROVAL; another administrator approves it with POST /contexa/admin/api/prompt-quality/releases/rollback/{executionKey}/approve. The administrator who ran it cannot approve it.

Check that the rollback target can actually run. TARGET_NOT_IN_BUILD looks at the 71 manifests, so a version this build does not run also passes as a rollback target. If such a version becomes ACTIVE, requests run the build default bundle (v19.21). For example, the v21.19 manifest's rollback targets are 2026.10.29-v21.18 · 2026.10.27-v21.17, and this build runs neither.

Inspecting sealed prompts

The inspector (PromptInspector) reads the user text the model got from the sealed evidence and counts, for each check, what matched, what did not and what could not be checked. It points at problems for a person to review; it never changes a prompt, decision or rule, and it does not run on a decision thread. OSS always runs 10 checks.

CheckApplies toWhat it compares
SEAL_INTEGRITYevery packagewhether the package hash covers every sealed field, the system and user texts were captured and match their hashes, differences from the drawn prompt were recorded, and the request and correlation IDs exist. A signed package (schema 3) is checked up to its signature
BUNDLE_TRACEevery packagewhether the sealed descriptor names a registry release, and the contract version, hash and approval are that release's. Without a registry, everything is unverifiable
DICTIONARY_CONTRACTdictionary promptsline breaks, block headers in dictionary order, only the block's entries in order, value forms and missing wording, numbered line limits, fact ID order
DECISION_FACT_MATCHdictionary promptswhether each sealed decision fact has its line, the same value and the same fact ID
FACT_ACCURACYdictionary promptsthe drawn facts compared field by field with the sealed canonical context (without drawing again). A line whose source was not sealed is unverifiable
UNKNOWN_DECLAREDdictionary promptswhether facts not settled are in UNKNOWN with their kind and not drawn as values elsewhere, and drawn as the missing notation says
PAST_RECORD_NOTATIONdictionary promptsthe count on the PAST RECORDS status line, 12 fields per record line, same target first and newest first
SOURCE_TRUTHdictionary promptsfacts compared with their source records. The source verifier (PromptFactSourceVerifier) reads the records again as of the request time. The default verifier reads Contexa's work records and delegations (on-call, assignment, approvals, a delegation's agent, person, purpose and author); a bean the application declares replaces it
SAME_FACTdictionary promptswhether a fact stated by two lines has one value
REASON_MATCHdictionary promptswhether the sealed decision's reason codes cite prompt line IDs, the lines are ones the code may cite, and the condition holds in the sealed context
  • Dictionary prompts are the v20 bundle (v20-dictionary-blocks) and the v21 bundle (v21-dictionary-blocks). A v21 package runs the v21 version of each check. A package drawn with another build's dictionary or render counts as unverifiable in the dictionary checks.
  • Verdicts: PASS (all matched), FAIL (one or more mismatches), INCOMPLETE (no mismatch but something unverifiable), NOT_APPLICABLE (not a dictionary prompt, so only the checks for every package ran; v19), ERROR (could not be inspected). Findings are MISMATCH · UNVERIFIABLE; unverifiable never counts as passing.
  • Versions: each result keeps the inspector version (prompt-inspector/N) and the dictionary version (v20@ or v21@ with the head of the dictionary digest). When the inspector version changes, packages are inspected again.
  • Runs: every 30 seconds, the oldest packages not inspected yet, 50 at a time, under one lock across all servers. Packages are chosen by package ID hash within contexa.prompt-inspection.sample-percent (default 100).
  • Inspection results change one thing. A package whose last inspection was PASS or NOT_APPLICABLE and that no official verification used is deleted after 30 days.
  • The inspector exists only when contexa.enterprise.enabled is not true and contexa.prompt-inspection.enabled is true (default).

Sealing samples and retention

Inspection reads sealed evidence. Only decisions an AI model made are sealed: all of the first 1,000 decisions after start and after a bundle change, then 1%, kept for 90 days (counted per server). What is sealed, signing keys, retention and settings are in Sealed evidence and official verification.

Replaying a sealed decision

A replay draws the prompt again from a sealed decision's inputs with a chosen bundle and asks the AI model once more. Use it to see how the decision changes on the same event before moving a new bundle to shadow or canary. The result is not applied, learned or sealed; the model is really called, so it costs money, and an audit record (SEALED_DECISION_REPLAYED) is written.

  • Only bundles this build runs can be chosen: 2026.10.24-v19.21 · 2026.10.24-v20.26 · 2026.10.30-v21.19. Any other version is refused with 400. The list is GET /contexa/admin/api/sealed-decisions/replay-bundles.
  • When the answer is ESCALATE, each chosen Layer 2 model (up to 3) is asked again. Without given baselines, the person's and organization's baselines stored now are used, and the answer says so in baselines (GIVEN or CURRENT).
POST /contexa/admin/api/sealed-decisions/7f3c2a/replay
Content-Type: application/json

{"bundleVersion": "2026.10.30-v21.19", "secondPassModels": ["gpt-4o"]}

7f3c2a in the path is the request (correlation) ID of the sealed decision. Details such as the time limit and error responses, and replaying from the page, are in Sealed evidence and official verification, Replay.
