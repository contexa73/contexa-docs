Prompt Inspection and Replay

How Contexa checks the prompts its decisions were drawn with. It covers what a sealed decision says about its prompt, how the registry follows the prompt versions, how sealed prompts are inspected against the facts, and how a sealed decision is replayed.

At a glance

Every decision is drawn with a prompt version (Prompt Versions). The principle for changing it is observe first, check, then enforce: a new version is tried on recent sealed decisions, applied to some users first or run alongside, and then used for decisions. After a decision, a sample is sealed with the prompt exactly as sent, and the inspector compares the sealed prompt's lines with the sealed facts.

What a decision says about its prompt

A decision's prompt execution information, and its sealed evidence, name the prompt it was drawn with in two ways.

  • The version: its name (v2.0), what chose it and its content hash, as fixed on the event when the decision started (promptBundleSelection.version, .source, .contentHash). The decision record keeps the version name and the content hash.
  • The governance descriptor of the template: prompt key cortex.security-decision, template key, release 2026.11.16-v1.0 (a bundle name, so the product default 2026.11.18-v1.0 and the versions on it carry it too), output contract CORTEX_PROMPT_CONTRACT_V5, the user text layout v1.0-dictionary-blocks, and the release's hash. The release has one manifest in the build (prompt-bundles/manifests/cortex.security-decision/2026.11.16-v1.0.json); its element hashes let the inspector tell whether a package was drawn in this build's form. The manifests of the earlier bundles v19, v20 and v21 are gone.

The registry behind the versions

Each version has one row in the prompt governance registry, and the screen's actions move the row's state through the release gate. The states keep their vocabulary (PromptBundleState); the screen shows them in its own words.

Registry stateOn the screen
ACTIVEUsed for decisions
CANARYCanary
SHADOWRunning alongside
AVAILABLENot used (a new version starts here)
DEPRECATEDNot used (a row an earlier bundle left; read as AVAILABLE)
RETIREDHidden
  • A move the gate refuses changes nothing and is recorded with its reasons; an applied move changes the registry state and the approval and rollback records, and announces a runtime cache invalidation. Moving a version to ACTIVE turns the other ACTIVE version of the same tenant and prompt into AVAILABLE (a bundle's row into DEPRECATED). A version used for decisions, a canary or a version run alongside goes back to AVAILABLE when it stops; a hidden version takes no state.
  • At start every server registers the build's product defaults as versions (the first installation's v1.0, an upgrade's next numbers) and retires the registry rows that name an earlier bundle. Those rows are kept: the trace check of earlier sealed decisions reads them.
  • Rollback, emergency rollback with a second administrator's approval, canary and running alongside are done on the version screens (Use for decisions and rollback).

Inspecting sealed prompts

The inspector (PromptInspector) reads the user text the model got from the sealed evidence and counts, for each check, what matched, what did not and what could not be checked. It points at problems for a person to review; it never changes a prompt, decision or rule, and it does not run on a decision thread. OSS always runs 10 checks.

CheckApplies toWhat it compares
SEAL_INTEGRITYevery packagewhether the package hash covers every sealed field, the system and user texts were captured and match their hashes, differences from the drawn prompt were recorded, and the request and correlation IDs exist. A signed package (schema 3) is checked up to its signature
BUNDLE_TRACEevery packagewhether the sealed descriptor names a release row of the registry (a retired row counts), and the contract version, hash and approval are that row's. Without a registry, everything is unverifiable

UNKNOWN_DECLAREDdictionary promptswhether facts not settled are in UNKNOWN with their kind and not drawn as values elsewhere, and drawn as the missing notation says

SOURCE_TRUTHdictionary promptsfacts compared with their source records. The source verifier (PromptFactSourceVerifier) reads the records again as of the request time. The default verifier reads Contexa's work records and delegations (on-call, assignment, approvals, a delegation's agent, person, purpose and author); a bean the application declares replaces it
SAME_FACTdictionary promptswhether a fact stated by two lines has one value

  • Dictionary prompts are prompts drawn with the user text layout v1.0-dictionary-blocks in this build's form. A version that puts in the prepared part "Decision rules" is read with its own dictionary (with the conclusion lines).
  • Earlier packages: a package drawn with an earlier bundle (v19, v20, v21) or with another build's dictionary or render is unverifiable in every dictionary check, and its detail page says "An earlier version: this package cannot be inspected again", while the two checks for every package still run. Such packages keep their bundle name until their retention ends.
  • Verdicts: PASS (all matched), FAIL (one or more mismatches), INCOMPLETE (no mismatch but something unverifiable), NOT_APPLICABLE (no dictionary check applied), ERROR (could not be inspected). Findings are MISMATCH · UNVERIFIABLE; unverifiable never counts as passing.
  • Versions: each result keeps the inspector version (prompt-inspector/N) and the dictionary version (v1.0@ or v1.0-rules@ with the head of the dictionary digest). When the inspector version changes, packages are inspected again.
  • Runs: every 30 seconds, the oldest packages not inspected yet, 50 at a time, under one lock across all servers. Packages are chosen by package ID hash within contexa.prompt-inspection.sample-percent (default 100).
  • Inspection results change one thing. A package whose last inspection was PASS or NOT_APPLICABLE and that no official verification used is deleted after 30 days.
  • The inspector exists only when contexa.enterprise.enabled is not true and contexa.prompt-inspection.enabled is true (default).

Sealing samples and retention

Inspection reads sealed evidence. Only decisions an AI model made are sealed: all of the first 1,000 decisions after a server starts and after the version decisions run changes, otherwise 1%, kept for 90 days (counted per server). Each package keeps the version name and content hash the decision ran. What is sealed, signing keys, retention and settings are in Sealed evidence and official verification.

Replaying a sealed decision

A replay draws the prompt again from a sealed decision's inputs and asks the AI model once more. The result is not applied, learned or sealed; the model is really called, so it costs money, and an audit record (SEALED_DECISION_REPLAYED) is written.

  • What can be chosen: the names GET /contexa/admin/api/sealed-decisions/replay-bundles lists: the versions of the security decision that are not hidden, newest first (without the version tables, the one bundle name of this build, 2026.11.16-v1.0, which draws the build's product default 2026.11.18-v1.0). A replay also takes a hidden version by its name, as a sealed decision names the version it ran; a name that is no version and no bundle of this build is refused with 400. To decide recent sealed decisions again with two versions and compare them, use the trial decisions of the version screens.
  • When the answer is ESCALATE, each chosen Layer 2 model (up to 3) is asked again. Without given baselines, the person's and organization's baselines stored now are used, and the answer says so in baselines (GIVEN or CURRENT).
POST /contexa/admin/api/sealed-decisions/7f3c2a/replay
Content-Type: application/json

{"bundleVersion": "v2.0", "secondPassModels": ["gpt-4o"]}

7f3c2a in the path is the request (correlation) ID of the sealed decision. Details such as the time limit and error responses, and replaying from the page ("Replay with a version"), are in Sealed evidence and official verification, Replay.
