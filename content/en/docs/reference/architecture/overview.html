How CONTEXA Works

This page follows a request from the moment it arrives to the moment its decision is made and applied. It explains what a decision is, how to turn CONTEXA on, the three settings to choose first, what changes depending on who owns sign-in, and how the modules fit together.

What CONTEXA does

A request can pass sign-in and the permission check and still come from someone who stole the account, or from a user spending their own permission on another purpose. CONTEXA is the security layer that catches such requests. When a method the developer marked as protected (@Protectable) is called, CONTEXA asks an AI model "is the owner of this account doing their own work right now?". The model's answer is called a decision. CONTEXA stores it per user and applies it to that user's later requests.

Take a first call to a protected method as an example. No decision is stored for this user yet. The account has so far read only a few customer records a day, and now it downloads 1,000 customer records at once. The request is handled in this order.

  1. When the request arrives, a CONTEXA filter reads the decision stored for this user. If the decision is a block (BLOCK), step-up authentication (CHALLENGE) or a hold for review (ESCALATE), the request stops here. If it is an allow (ALLOW), or nothing is stored yet, the request goes on.
  2. The request runs through the application's logic and the protected method, and the response goes out. CONTEXA does not wait for the AI model in this step, so the response is not slowed down.
  3. When the protected method finishes, CONTEXA records the facts of the request: who did what, from which session and IP address. This record is called an analysis event.
  4. In the background, separately from the request, an AI model reads the analysis event, makes a decision and stores it. In this example the model could choose step-up authentication or a block.
  5. On the same user's next request, the filter from step 1 reads this decision and applies it. A new decision therefore usually takes effect from the next request.

If a valid decision already exists for the user, steps 3 and 4 do not analyze again. An allow, for example, is reused for 15 minutes for requests from the same session, IP address and browser.

Only two kinds of calls are decided on the spot, inside the request, and wait for the result: a method marked @Protectable(sync=true), and an AI agent request with no stored decision (see The two paths a request takes). Requests from AI agents (programs that call the application on behalf of a person) are told apart from people's requests and decided separately (Agents as security subjects). There are five decisions.

Turning it on

With only the starter dependency (spring-boot-starter-contexa) added, CONTEXA stays off and the application runs exactly as before. Putting @EnableAISecurity on the main class turns it on. Internally, the annotation loads AiSecurityConfiguration through AiSecurityImportSelector, and the auto-configurations of each module follow. Even with the annotation, contexa.enabled=false loads nothing. Without mode the annotation starts in SANDBOX, where the application keeps sign-in (HOST_OWNED; see The three choices to make first).

import io.contexa.contexacommon.annotation.EnableAISecurity;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
@EnableAISecurity   // no mode means SANDBOX: the application keeps sign-in (HOST_OWNED)
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}

Turning it on also needs a dedicated CONTEXA database (PostgreSQL). If its address (contexa.datasource.url) is empty, the application does not start.

contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa   # a Contexa database, not the application's
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
  • Using the same address as the application's database stops the start. CONTEXA is meant to have a database of its own, so it refuses a contexa.datasource.url that equals the application's spring.datasource.url. Only for a trial (POC) can the two share a database, by setting both contexa.datasource.isolation.allow-shared-application-datasource and contexa.datasource.isolation.shared-application-datasource-risk-accepted to true. A production profile (prod · production) still refuses it.
  • When the CONTEXA database cannot be reached. Where the application keeps sign-in (the default HOST_OWNED), the application starts without CONTEXA and logs an ERROR if the database does not answer within 5 seconds at start. The same happens when the database answers but its account may not create the PostgreSQL extensions CONTEXA needs (such as vector), and when distributed infrastructure mode cannot reach Redis. Restart the application after fixing the cause to turn CONTEXA on. Where CONTEXA owns sign-in (CONTEXA_OWNED), nobody could sign in without the database, so the application does not start.
  • Decisions need an AI chat model and a vector store. Without Spring AI ChatModel and VectorStore beans (PgVector, with an embedding model for it), the Layer 1 and Layer 2 analyses are not created and protected requests stay in pending analysis. Both layers are explained in How a decision is made.
  • A decision is applied only after it is recorded in the CONTEXA database. CONTEXA first writes an observation record (table ctxa_ai_security_decision_observation) for each decision. That record is the audit record of the decision, and it is also what restores the decision when the same event is processed again, without calling the model. When the write fails, the decision is not applied.
  • At start, CONTEXA checks that the beans it needs exist (contexa.capability.mode: AUTO · OFF · WARN · FAIL_FAST · STRICT). When something is missing, the default AUTO only logs it for an ordinary application and stops the start for a CONTEXA-only application (FAIL_FAST). A CONTEXA-only application is a FULL-mode application whose own data also lives in the CONTEXA database, or one whose name (spring.application.name) starts with contexa-.

The steps from the dependency to the first decision are in Getting started.

The two paths a request takes

CONTEXA splits its work into two paths. On the request-time path, while the user waits, it reads the decision already stored and applies it. On the asynchronous decision path, in the background and apart from the request, it makes a new decision and stores it. The two paths meet only at the decision store: what the request-time path reads was written there by the asynchronous path for an earlier request.

  • Analysis events come from protected methods. With the default settings, the events that lead to an AI analysis come from @Protectable method calls. A sign-in is not analyzed: when the signed-in user first calls a protected method, the model decides with that resource in front of it. An ordinary URL request that is not a protected method is not analyzed either, and a request that an authorization policy denied is kept only as a session fact, without analysis.
  • The request-time path usually does not call the AI model. It only reads the store, so a new decision usually applies from the next request. Two kinds of calls are decided inside the request and wait for the result: methods marked @Protectable(sync=true) and, by default, AI agent requests with no stored decision. When a person first calls a resource the application marked as sensitive from a new session, IP address or browser, CONTEXA does not hold the request. It answers with a response that asks the client to retry in a few seconds (429 with Retry-After) and makes the decision in the background.
  • Until a decision is stored, the user is in pending analysis. The request goes on. Its response is wrapped on the way out, so that a block signal arriving for this user while the response is being sent can cut it. This is the same under both ownership modes, and the same for an allow.

Following one request from start to end is in The Life of a Request.

What runs under each ownership mode

The ownership mode says who owns the application's sign-in, sessions and cookies. The default (only @EnableAISecurity) is HOST_OWNED, where the application owns them. CONTEXA then builds no sign-in chain, but it still applies decisions on every path: the same request-time filters run as servlet filters right after the application's Spring Security chain, give the same responses as under CONTEXA_OWNED, and apply again in front of @Protectable methods. Under CONTEXA_OWNED, where CONTEXA owns sign-in, the same filters run inside the chain CONTEXA builds.

The five decisions and their lifetimes

Decisions are stored per user, and each decision has a fixed lifetime. A decision does not stay until a new analysis replaces it: when its lifetime ends, it disappears and the user is back in pending analysis (a block has no limit).

  • The stricter decision wins. In the order block > held for review > step-up, a weaker new decision is not stored while a stricter one is in force.
  • An allow does not exempt a synchronous method. An allow lets only the asynchronous requests from the same session, IP address and browser skip a new analysis. A method marked @Protectable(sync=true) is decided on every call, even while an allow is in force.
  • By default, a hold for review is not stored. When Layer 2 also cannot decide and chooses ESCALATE, CONTEXA replaces it with the action set in contexa.security.tiered.layer2.escalate-fallback-action (default CHALLENGE) and stores that. To store the hold for an administrator's review as it is, set contexa.security.tiered.layer2.allow-escalate-final-action to true.
  • The responses users get for each decision (HTTP status, the page they are sent to) are in The Life of a Request and Request-time enforcement.

How a decision is made

Asking the AI model happens in the background, apart from the request. Layer 1 analysis decides first, and only a request that Layer 1 cannot decide goes to Layer 2 analysis, which decides it again. When the model has decided, CONTEXA stores and records the result.

  • The AI model chooses the action (allow, step-up, block, hold). CONTEXA's engine only gathers and sends the facts and does not choose the action.
  • When no answer comes back from the model (provider failure, timeout), Layer 1 passes the same request to Layer 2. If Layer 2 gets no answer either, the decision ends as step-up. That step-up was not decided by the model, so it lasts only 60 seconds, and in that time CONTEXA asks the model again up to 3 times (10 seconds apart). If the model later chooses allow, this step-up is lifted. When more than half of the recent Layer 1 results for the same organization (or user) and path are holds (counted once more than 10 are in), overload protection skips Layer 2 and ends directly as step-up.
  • Shadow mode applies nothing. It blocks no request and changes no authority. It does not write the decision to the real decision store; it keeps it only in memory of its own, so the same user's next request is not analyzed again, and it writes the observation and audit records.
  • What is learned and when the model's answer is changed: Decision Engine.

Infrastructure modes

The infrastructure mode decides where CONTEXA keeps its state: the stored decisions, the analysis events and what it has learned. Both modes need the dedicated CONTEXA database (PostgreSQL).

Write standalone or distributed in contexa.infrastructure.mode. Connection settings are in First start and deployment.

  • Restarting a server in standalone mode loses the stored allow, step-up and hold decisions, and the user's next request is analyzed again. A block is restored at start from the record contexa-iam keeps in the ctxa_blocked_user table, so it stays in force; a block with no such record is lost. With several servers, each server keeps its own decisions. That is why standalone is meant for development.
  • distributed needs the Redis client libraries. If the application does not have spring-boot-starter-data-redis, org.redisson:redisson and spring-statemachine-data-redis, it does not start.
