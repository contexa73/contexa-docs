How Contexa Works

What Contexa asks about each request, and when it makes and applies the answer (the decision), on one page. It also covers how to turn Contexa on, the three choices to make first, what actually runs under each ownership mode, and how the modules fit together.

What Contexa does

A request that passed sign-in and the permission check can still come from someone who stole the account, or from an insider using their own permission for another purpose. For each request it protects, Contexa asks an AI model "is the owner of this account doing their own work right now?", stores the answer as a decision, and applies it to that user's requests.

A decision is not made while the request waits. It is made in the background after the request has been handled and the response has left, and it applies from the same user's next request. Only a method that needs a decision inside the request (@Protectable(sync=true)) and an agent request with no decision on record are decided on the spot.

Requests from AI agents are told apart from people's requests and decided separately (Agents as security subjects).

Turning it on

With only the starter dependency (spring-boot-starter-contexa), Contexa stays off and the application runs as before. It is turned on by putting @EnableAISecurity on the main class. The annotation loads AiSecurityConfiguration through AiSecurityImportSelector, and the auto-configurations of each module follow. Even with the annotation, contexa.enabled=false loads nothing.

import io.contexa.contexacommon.annotation.EnableAISecurity;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
@EnableAISecurity   // no mode means SANDBOX: the application keeps sign-in (HOST_OWNED)
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}

A dedicated Contexa database must also be set. If it is empty, the application does not start.

contexa:
  datasource:
    url: jdbc:postgresql://localhost:5432/contexa   # a Contexa database, not the application's
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
  • The same address as the application database stops the start. Only for a trial (POC), setting both contexa.datasource.isolation.allow-shared-application-datasource and contexa.datasource.isolation.shared-application-datasource-risk-accepted to true allows sharing, and a production profile (prod · production) still refuses it.
  • Decisions need an AI chat model and a vector store. Without Spring AI ChatModel and VectorStore beans (PgVector, with an embedding model for it), Layer 1 and Layer 2 are not created and protected requests stay pending analysis.
  • A decision applies only after it is recorded in the Contexa database. Each decision is first written as an observation (table ctxa_ai_security_decision_observation); when that write fails, the decision is not applied.
  • At start, Contexa checks that the beans it needs exist (contexa.capability.mode: AUTO · OFF · WARN · FAIL_FAST · STRICT). When something is missing, the default AUTO only logs it for an ordinary application and stops the start for a Contexa-only application (FULL mode and the like) (FAIL_FAST).

The two lanes a request goes through

Contexa works in two lanes. The request-time lane reads and applies the decision already stored while the user waits; the asynchronous decision lane makes a new decision and stores it after the response has left. The two lanes meet only at the decision store.

  • Analysis events come from protected methods. With the default settings, analysis events are published by @Protectable method calls and by MFA sign-in success. An ordinary URL request that is not a protected method is not analyzed, and a request an authorization policy denied is kept only as a session fact, without analysis.
  • The request-time step never calls the AI model. It only reads the store. That is why a new decision usually applies from the next request.
  • Before a decision is stored, the user is pending analysis. The request goes on, and the response in flight is wrapped so that a block signal can cut it (under both ownership modes, and the same for an allow).

Following one request from start to end is in The Life of a Request.

What runs under each ownership mode

The default (only @EnableAISecurity) is HOST_OWNED. Contexa then builds no sign-in chain, but it still enforces on every path: the same request-time filters run as servlet filters right after the application's Spring Security chain, with the same responses as under CONTEXA_OWNED, and again in @Protectable methods.

The five decisions and their lifetimes

Decisions are stored per user, and each decision has a fixed lifetime. A decision does not stay "until a new analysis replaces it".

DecisionLifetimeWhere it appliesHow it ends
Allow (ALLOW)15 minutes (set with contexa.security.zerotrust.allow-validity)only in the same session, IP and browser it was made forback to pending analysis when the time passes
Step-up authentication (CHALLENGE)1,800 s (30 min)every session of the userallowed after passing the MFA this decision started, or the time runs out
Held for review (ESCALATE)300 s (5 min)every session of the useran administrator's approval. If unresolved when the time ends, the next request turns it into a block (CONTEXA_OWNED)
Block (BLOCK)no limitevery session of the useran administrator's approval (the user asks for release after the unblock MFA)
Pending analysis (PENDING_ANALYSIS)—no stored decisionchanges when an analysis stores a decision
  • The stricter decision wins. In the order block > held for review > step-up, a weaker new decision is not stored while a stricter one is in force.
  • The responses users get for each decision (HTTP status, the page they are sent to) are in The Life of a Request and Request-time enforcement.

How a decision is made

  • The AI model chooses the action (allow, step-up, block, hold). The engine only gathers and sends facts. When no answer comes back from the model (provider failure, timeout), the decision ends as step-up and is not passed to Layer 2.
  • Shadow mode stores nothing. Only the observation and audit records are written.
  • What is learned and when the model's answer is changed: Decision Engine.
