Prompt Versions

An administrator can change the security decision prompt, the text the AI model reads whenever CONTEXA decides on a request, from the admin console without touching source code: save the change as a new version, test it, switch it on, and switch back if it does not work out. This page explains what a version is, how the default version CONTEXA ships differs from versions your organization creates, and which parts you can and cannot change. It then gives the order for testing a new version, applying it to some users first, passing the quality gate, using it for decisions and rolling it back, and how CONTEXA picks the version for each decision. Seven other AI prompts are kept as versions in the same way.

Overview

For each decision, CONTEXA sends the AI model a prompt. The system prompt holds the standing instructions: the model's mission, how to read the evidence and the answer format. The user prompt holds the facts of this one request, which the engine fills in. CONTEXA keeps each prompt as versions: v1.0, v2.0 and so on, with numbers counted separately for each tenant (or the whole platform) and prompt.

A version is a whole prompt, and it never changes once it is saved. A change is always saved as the next number. A version is one of two kinds:

  • "Provided by Contexa" is the product default, the prompt CONTEXA ships. It comes from a YAML file called the product document and holds every part of the prompt.
  • "Our organization" is a version your administrators make. It names a base, the version it starts from, and holds only what it changes, deletes or adds. Everything else comes from the base.

The version that is switched on is called "Used for decisions" on the screens. This page also calls it the version in use.

  • Where: the menu "Prompt Quality Assurance → Prompt versions" (/contexa/admin/prompt-quality/versions). The bar of the group's five menus sits on top (Prompt Quality Assurance). Every screen and API needs the administrator role.
  • Which version decides: CONTEXA takes the version an administrator chose on the screen, else the one the configuration names, else the newest version CONTEXA provides (How a decision's version is chosen). CONTEXA fixes that choice when the decision starts. Layer 1 (the first analysis), Layer 2 (the second analysis, which runs only when Layer 1 answers ESCALATE, meaning its facts cannot decide the request) and every retry of the decision then use the same version. The other seven prompts take the version chosen on the screen, else the newest CONTEXA version (The seven prompts other than the security decision).
  • What stays CONTEXA's: a version cannot change the standard blocks of facts in the user prompt, the values the engine fills in, the answer format, the reason codes or the rules marked with a lock. The other sentences of the prompt live in versions, not in the code.
  • Which prompt: the list screen has a "Prompt" choice with eight prompts: "Security decision" (cortex.security-decision) first, then the seven prompts other than the security decision (below). This page describes the security decision unless it names another prompt.
  • Where to read what: changing and saving a version is in The three-click flow. What you may and may not change is in Locked parts and parts you may change. Testing is in Trial decisions and Measuring a version. Switching a version on and going back is in Use for decisions, rollback and hiding. Which version a decision gets is in How a decision's version is chosen.

The three-click flow

Changing the prompt takes three steps: start a new version, save it, then switch it on. Unless you choose to use a version at once, saving it does not change which version decides, so you can save, check and test a version before anything depends on it.

  1. "New version" on the list screen opens the new version screen. Its base, the version it starts from, is the version in use now (/versions/new?base={number}). "New version" on a table row, or on a version's own screen, starts from that version instead.
  2. Change the parts and choose "Save". Only the parts you may change are open for editing. Parts with a lock are folded under "Contexa rules". The "Checks before saving" box runs again each time you change something, and "Save" works only when every check passes. Saving creates the next number and leaves the base as it is.
  3. "Use for decisions" on the new version's row switches it on. The confirmation shows "Now" (the version in use) and "Next" (the new version), and "Takes effect" ("Every server follows within about 5 seconds; a decision already started ends with its version."). It also shows what the release gate found. The release gate is the set of checks every switch passes through (Use for decisions, rollback and hiding). For the security decision it includes the quality gate (The confirmation). A field "Reason (optional)" is kept in the history. When the quality gate is in its blocking mode, a quality block stops the switch unless you write a reason, and "Use with this reason" overrides it.
  • Security decision, measure first: tick "Save and measure at once" and choose "Save". CONTEXA saves the version and starts measuring it. A measurement replays the labelled cases (Labelled cases) with the new version and checks its answers against the right ones (Measuring a version). The version is not switched on. "Save and open Measure & compare" saves the version and opens the measurement, or its start screen with the new version chosen. The version's own screen then says "{version} is saved and being measured." with "Open the measurement", or "{version} is saved, but its measurement could not start." with the reason. A measurement asks for no reason.
  • The seven other prompts have no measurement. Tick "Save and use at once", write a reason if you want one, and choose "Save": the version is saved and switched on in one step (steps 2 and 3 together).

Locked parts and parts you may change

A version's system prompt is a list of parts that the model reads from top to bottom. Each part covers one topic, such as the mission or the answer format. A part is either locked or open to change.

  • A locked part is a CONTEXA rule. No version can change or delete it, and the new version screen keeps it folded.
  • A part you may change is open as a text box. Change the text, set it back with "Back to the product default", or take the part out with "Delete this part" ("Restore" brings it back).
  • A part of your own is added with "Add a part".

Four parts of the system prompt are open to change: "More reading", "Similar case reading", "Similar case limits" and "How to judge". Every other part is locked. In the table below they are marked "may change". What the four say:

  • "More reading" (more-reading) adds reading rules for the evidence. For example, several missing or unknown facts do not add up to a risk without a fact that states one.
  • "Similar case reading" (similar-case-reading) says how to read the past records that the similarity search found. A version that deletes this part also turns that search off.
  • "Similar case limits" (similar-case-limits) says what a similar case cannot show. For example, another person's similar work does not explain a difference in this account's own device, network, time or login method.
  • "How to judge" (how-to-judge) lists the steps the model follows. The model builds one story of the request and weighs four explanations against the facts: legitimate work, account takeover, insider misuse, and automation or error.

Parts 15 to 18 always stay at the end, because a model follows an answer format best near the end. An added part never lands in the middle of a list: when later parts continue the list of the part you name, the new part goes after them.

  • Precedence and "Blocks your organization added": these are two locked sentences that earlier releases add to a version your organization changed. The first says that a fixed CONTEXA rule wins over an instruction your organization wrote. The second says that a block your organization added to the user prompt is the organization's own reference, not a fact about this request.

    Release v1.1.0 and the versions based on it include neither sentence, so a version whose changes say the same as the product default produces exactly the product default's system prompt. The quality gate and the header of each block your organization adds guard the organization's versions instead.

    On an earlier release, a version that changes or adds a part gets the Precedence sentence after the Mission and, on 2026.11.18-v1.0, the "Blocks your organization added" sentence right after How to read the evidence. A version that only deletes parts or puts prepared parts in gets neither.

  • User prompt: the eight standard blocks (User baseline, Session, Request, Records and comparisons, Past records (RAG), Unknown, Untrusted text, Second pass) are all locked. Their titles, line names, order, fact IDs and values belong to the engine, which fills them in for every decision. "Add a reference block" puts a block of your organization (a title and a text) after the standard block you name. A later version can change or delete an added block. A changed block stays a block your organization added: every later version includes it at the place it was added, under the same header, and counts it in the length, size and decision time estimates. A deleted block is left out. A version's content hash stays as it is.
  • How an added block appears: in the security decision prompt (Layer 1, Layer 2, the retries and the replays), right after the standard block it follows, after a blank line, under the header === Title (reference written by your organization) ===. An added block has no fact IDs, so the model cannot cite it as a fact. A title or a line that could be read as the header of a standard block appears in quotes.
  • Marks on a version's screen: each part carries a mark that says how it relates to the base: "Locked", "As the default", "As the base", "Changed" (shown beside the base's text), "Deleted", "Added", "Prepared part put in" or "Conditional".

Optional parts CONTEXA prepared

CONTEXA ships two optional parts. They are in the product document, but every version leaves them out until a version puts them in. On the new version screen they appear under "{n} parts Contexa prepared", each with its measurement and a "Put in" button. Once a prepared part is in, it is locked: its text cannot be changed. A version made on that base shows it as "A prepared part the base version put in. The next version can take it out." with "Take out in this version" ("Put back" undoes it). CONTEXA measured both parts, and neither gets a plain recommendation: the table shows the verdicts, and the measurement below shows the numbers.

Checks before saving

Every version passes the same checks before it is saved, whether it comes from the screen, an uploaded document or a document of the folder. If any check fails, nothing is saved and every problem is named.

  • A version that came from a document (an upload or the folder) cannot be the base of a version made on the screen: "{version} came from a document, so the screen cannot build on it. Change the document instead: it is registered again as the next version." This keeps the two ways of editing from colliding.
  • The check on standard block titles only stops a new save. A version saved before the check is assembled as it was, and such a title appears in quotes in its prompt.
  • Besides the checks, the screen shows without refusing: the tokens of the system prompt and the added blocks against the base, about how much longer or shorter decisions take, and, for the security decision, "After saving, measure it in Measure & compare before it decides."

How length affects decision time and the context

A longer prompt takes longer to decide and uses more of the model's context, the amount of text the model can read at once. The checks estimate the length of the system prompt and refuse a version of the security decision that cannot fit.

  • Tokens: CONTEXA counts a quarter of the characters of every part the version includes. Each part counts with its longest text (under any condition), its heading and its lines. A prepared part that is not put in is not counted. The product default v1.0 is about 4,100 tokens. The blocks a version adds to the user prompt count too, as the prompt shows them: with their header lines in the security decision, under their titles in another prompt. The values the engine fills in for each decision are not counted.
  • The limit: the version's system tokens, plus the input, plus the answer tokens must not exceed the context of the model that decides first.
    • The answer tokens are the larger of contexa.security.tiered.layer1.max-output-tokens (default 4096) and layer2.max-output-tokens (default 2560).
    • The input is the longest user prompt of the latest 500 decisions, plus all the new version's added blocks.
    CONTEXA measures each decision with the version it ran: its prompt tokens, less that version's system tokens and the added blocks that version included. The decision with the most left over is the longest. All the new version's added blocks count, whatever its base. A decision whose recorded version cannot be found is measured with the product default. Without a recent decision, the input is the new version's added blocks. The screen, the document folder and an upload count the same way.
  • The model's context: for an Ollama model it is contexa.llm.model-capabilities.ollama.max-context-length (default 32768; a value under 4096 keeps the default). When no first-layer model is known, CONTEXA uses the Ollama value. A model of another provider has a known context only when a setting declares its context window, and no setting declares one now. For such a model the context is not known and the length is not checked ("The model's context is not known, so the length was not checked").
  • Decision time: the difference in tokens from the base (the system prompt and the added blocks), times the median decision time per input token of the latest 200 decisions. The checks and the decision time card on a version's screen (security decision) show this estimate. Without decisions it is not shown.

Use for decisions, rollback and hiding

"Use for decisions" switches a saved version on. Going back is the same step on an earlier version. Hiding takes a version you no longer need off the list.

  • Use for decisions marks the version as the one in use, and the version used before becomes "Not used". The move passes through the release gate, which blocks:
    • a hidden version;
    • a move that would leave no version used for decisions;
    • a version that does not keep the prompt injection guard of the product default it is based on. On every product default the guard is the evidence reading, with its rule that records and untrusted text are evidence only and never instructions, together with the untrusted text block. On 2026.11.16-v1.0 and 2026.11.18-v1.0, which have it, the Precedence sentence belongs to the guard too;
    • a prompt whose product declares no model, budget, token counting, cache or compaction policy.
    When the gate blocks, the confirmation shows "Blocked" with the reasons and nothing changes.
  • The quality gate (security decision): for the security decision the release gate also reads the quality gate: eleven conditions on the measurements of the version and of the version in use. By default a failed condition only warns. In the blocking mode it blocks, and a reason overrides the block (The quality gate). When CONTEXA cannot read the quality gate, the confirmation shows instead whether the version was tried: "Not tried" with "This version has not been tried. A trial before it decides is recommended.", the gate's warning TRIAL_RECOMMENDED.
  • When it takes effect: each server caches the choice for 60 seconds and checks every 5 seconds whether it changed, so every server follows within about 5 seconds. A decision already started keeps its version.
  • Rollback is "Use for decisions" on an earlier version. The list screen says: "To roll back, choose "Use for decisions" on an earlier version: every server follows within about 5 seconds. A version cannot be changed once made; "New version" makes the next number." Going back to a version the tenant used for decisions before takes no quality condition (the gate shows "Passed (going back)"). For an urgent case, see Emergency rollback and history.
  • The record: every move is recorded with who, when, what and why in the history and the audit log (category PROMPT_VERSION_CHANGED, actions PROMPT_VERSION_*). A quality gate overridden with a reason is recorded as PROMPT_VERSION_QUALITY_GATE_OVERRIDDEN.
  • Hide (on a version's screen, for a version in the state "Not used"): "Only takes it off the list. Its content stays; decision records and sealed evidence keep pointing at it." A version used for decisions, a canary or running alongside cannot be hidden. The version that decisions use without a choice on the screen, the one the setting names or the newest CONTEXA version, counts as in use and cannot be hidden either. A hidden version cannot be used, measured, tried or rolled back to. "Show hidden versions" lists hidden versions again.

How a decision's version is chosen

When a decision starts, CONTEXA chooses its version in this order and fixes the choice on the event, the security event the decision is made for.

  1. The choice made on the screen: a canary the request falls inside, else the version used for decisions for the request's tenant, else the one for the whole platform (PLATFORM_GLOBAL). The list shows it as "Chosen on the screen" (or "Canary").
  2. The setting contexa.security.tiered.prompt-bundle.active, when it names a version (v2.0; 2 and v2 read the same) that exists and is not hidden. CONTEXA reads it for every decision, so a version that appears later is used from then on. The list shows it as "Chosen by the configuration". The setting is for the security decision only.
  3. The newest version provided by CONTEXA, shown as "Contexa default".
  • When the setting names a version that does not exist or is hidden, CONTEXA logs a warning once and passes over the setting until that version exists. When it names an earlier bundle, which no longer exists (such as 2026.10.24-v19.21), CONTEXA logs a warning once ("earlier bundles are gone"), and the order above runs as if the setting were empty.
  • Outside the gate: a version chosen by the setting or as the newest CONTEXA version decides without passing the release gate. The list says so ("{version} decides as the setting names it, without passing the release gate.", or "{version} decides as the newest Contexa version, taken on the upgrade without passing the release gate.") and shows the state of its measurement in this environment. CONTEXA also measures such a version once on its own (Prompt Quality Assurance).
  • Registering a product default never marks it as used for decisions. A version carries that mark only after an administrator chooses "Use for decisions", so the setting and the newest-version rule work as described above.
  • CONTEXA checks whether a named version exists, and which CONTEXA version is the newest, at most once a minute. When the database cannot be read, it uses the last values it read. Without them it uses the product document of the build, the newest release the build ships (v1.1.0, which sends the same prompts as 2026.11.18-v1.0).
  • The event metadata keeps promptBundleSelection.version, .source and .contentHash. Layer 1, Layer 2, every retry and the decision side of a run alongside read the version from there, so switching the version in use never changes a decision already started.

A new product default

A new CONTEXA release can ship a new product default. This section covers what happens to the versions you already have.

  • On the first start of an installation, CONTEXA registers the newest product default of the build as v1.0. An upgrade registers each newer product default as the next number, in order. The version used for decisions does not change by itself.
  • When the version in use is your organization's and is based on an older product default, the list shows "New product default": "Contexa released a new product default, {new}. The {in use} in use keeps running. To use the new rules, carry your changes onto the new base."
  • When the version in use is an older version provided by CONTEXA, there is nothing to carry. The notice reads "Contexa released the newer product version {new}. The {in use} in use keeps running; use {new} for decisions to run its rules." with a "Use for decisions" button beside "See what changed".
  • The release this build ships: the security decision's product default of this build is v1.1.0. It is 2026.11.18-v1.0 without the Precedence sentence and the "Blocks your organization added" sentence (Locked parts and parts you may change). Nothing else changed, so its own prompt is that of 2026.11.18-v1.0. CONTEXA took the two sentences out for two reasons:
    • Included only in a version the organization changed or added to, they made a version that changed a part without changing its meaning send a different system prompt than the version it was based on, and borderline cases were decided differently.
    • Included in every version, they raised the misses of the product default itself (15 to 17 of 55 threats in the measurement).
  • The earlier releases: 2026.11.18-v1.0 is 2026.11.16-v1.0 with the locked part "Blocks your organization added" (included only in a version the organization changed or added to) and the reason code VERIFIED_SIGNAL (Signal the server confirmed) after THREAT_MATCH. Both earlier releases still ship, and an installation that registered one registers the newer ones as the next numbers on upgrade.
  • Names of product defaults: from v1.1.0 on, a product default is named vX.Y.Z, and its date is written in the head of its document. The three numbers mean:
    • X goes up when the make-up of the prompt changes: the order of the blocks, the answer format, the response check, or several parts written anew.
    • Y goes up when the text the model is given changes: a sentence is added, changed or taken out, or the condition a part is included under changes.
    • Z goes up when the prompts the model is given stay the same to the letter and only comments, titles or descriptions change. A change of one character of what the model is given is never a Z, because a small change of wording can change the decisions of borderline cases.
    CONTEXA measures a new X or Y before it ships and checks that a new Z produces the same prompts. The two dated product defaults 2026.11.16-v1.0 and 2026.11.18-v1.0 keep their names, because installations registered them by name.
  • "Carry onto the new base" opens the new version screen on the new product default with your changes on it: "{n} carried, {m} could not be". The carried changes are all those that the version, and the organization versions down its chain of bases, made to the product default: changed parts (their latest title and text), added parts and blocks (changed since or not, with their place), prepared parts put in, and deleted parts. A change the new base cannot take is listed as "Could not be carried: {part} ({change}) — the new base does not have that part or no longer lets it change." Nothing is a version until you save it, and drafts are not kept.

Trial decisions

A trial compares two versions on recent real decisions before one of them decides. CONTEXA decides the latest sealed decisions again with both versions, up to the number you choose, and shows where their actions differ. The decisions made again are only recorded and are never applied to anyone. A trial has no right answer to grade against: it compares the actions of two versions. To grade a version against right answers, measure it on the labelled cases (Measuring a version).

  1. In Measure & compare (/contexa/admin/prompt-quality/measure), choose the input "Latest sealed decisions". Then choose "Version to try", "Compared with" (the version in use is marked "(now)") and "Decisions to replay": latest 20, 50 or 100.
  2. Choose "Start the trial". CONTEXA decides each of the latest sealed decisions again with both versions (those of the tenant, when one is chosen). The screen warns: "Calls the model twice per decision, behind any real decision waiting. Seals are a sample: with fewer, it uses what there is."
  3. The result opens at /contexa/admin/prompt-quality/measure/trials/{id} and shows four cards and the details.
Card · sectionMeaning
Same actionDecisions both versions answered with the same action
Format errors"Decisions whose first answer broke the answer format, or with no usable answer. A retry for a decision rule is not counted."
Decision time (mean)The mean time of a replay, for each version
Answer length (mean)The mean answer tokens, for each version
ActionsALLOW · CHALLENGE · ESCALATE · BLOCK and "No answer", for each version

Each row opens the decision's detail, and "Add as a case" turns the sealed decision into a labelled case with the right answer you set
  • Nothing is applied, learned or sealed: CONTEXA keeps each answer only in the trial's own records. A trial calls the model, so it costs as much as twice the number of decisions replayed.
  • Only one trial runs at a time per prompt. It shares one queue with the measurements, so it waits behind a measurement that is running, and its model calls wait behind the decisions at the model gate. You can cancel it ("Cancel"). A trial left unfinished by a server stop is marked failed when the server starts again.
  • From the result you can start "Canary for some users" or choose "Use {version} for decisions". Both go through the quality gate.
  • Trials are for the security decision only: its sealed decisions are the inputs a trial decides again.

Canary for some users

A canary switches a new version on for a share of users while everyone else keeps the version in use, so you can watch the new version on real traffic before everyone depends on it. On the advanced screen, choose the version, the "Share of users" (10, 25 or 50%), "Tenants" (empty for all, commas for several) and "Address starts or resource IDs" (for example /api/payments, empty for all), then "Start the canary".

  • "A user always falls on the same side. The other users are decided with the version in use." CONTEXA assigns the side from a hash of the user (else the session, else the event).
  • A request uses the canary version when its tenant is one of the tenants given, its resource address starts with one of the values given (or its resource ID equals one), and its user falls inside the share. An empty field covers all. The decision of such a request records the source CANARY.
  • The confirmation of "Start the canary" shows the quality gate as "Use for decisions" does (use-check?target=CANARY). In the blocking mode a quality block needs a reason ("Start with this reason").
  • One version is a canary at a time, and "Stop" ends it. The start and the stop are in the history.

Run alongside

Running a version alongside tests it on real requests without affecting anyone. After a real decision is made, CONTEXA runs a copy of the request through the version you chose and records the result. On the advanced screen, choose the version, the "Sample" (5 or 10%) and the "Daily limit" (1 to 10,000), then "Start". The screen warns: "Calls the model once more. The results are only recorded, never applied. The version that decides is not run again."

  • CONTEXA copies a sampled request before its decision and analyses the copy apart, with the version run alongside, after the decision. It seals the copy as the SHADOW stage. Nothing is enforced or learned.
  • The component that runs the copies is present wherever decisions are sealed, and it does nothing until a version runs alongside. The sample and daily limit you choose on the screen are saved with the version and shown on the screen's "Now:" line. A version with none saved uses contexa.security.tiered.prompt-bundle.shadow.sample-percent and .daily-call-cap (Settings). The daily limit counts the runs of the version per UTC day on each server. A request whose decision already runs that same version is not run again.
  • "Results of running alongside", on the Measurements view of Measure & compare, pairs each run with the decision of its request. Choose a "Period" of 1, 7, 30 or 90 days (7 by default). The results show "Requests run alongside", "Paired with their decision", "Answered otherwise" and the actions that changed. "Inspection of the sealed decisions (by version, stage and action)" counts Sealed, Failed, Passed and Not inspected. Below, up to 50 paired requests are listed, those answered otherwise first, each with its "Decision seal" and "Alongside seal" opening the sealed evidence. The runs of a version that stopped keep their results for the period.
  • One version runs alongside at a time, and "Stop" ends it.

Emergency rollback and history

When the version in use must be replaced quickly, an administrator can roll back to an earlier version at once, and a second administrator approves the rollback afterwards. The history records every action on versions.

  • Emergency rollback (advanced screen): choose "Roll back to" and give a reason. "An emergency rollback applies at once and is finished when another administrator approves it." The administrator who rolled back cannot approve it. A rollback, an emergency one too, goes only to a version the tenant used for decisions before. Any other target is refused.
  • The rollback table shows When, Versions, Who, State ("Applied", "Awaiting approval", "Approved", "Refused", "Incomplete") and Approval. A rollback awaiting approval has an "Approve" button.
  • History lists what was done to the versions of the prompt, newest first (up to 50): made, hidden, uploaded, registered from the folder, used for decisions, canary started and stopped, alongside started and stopped, rolled back in an emergency, rollback approved, trial started and cancelled, quality gate overridden, each with who did it and the reason. "The audit log keeps the same".

Import and download

A version document is a file that holds one version. Use documents to move a version between servers or to keep versions in version control.

  • Download ("Download as a document" on a version's screen, or the advanced screen) offers two forms. "Changes only (can be uploaded again)" writes your organization's document, with its base named by number and content hash (basedOn, basedOnHash). "Whole version (to read)" writes every part as the model receives it, marked kind: rendered, and cannot be uploaded. The file is named cortex.security-decision-v2.0.yaml (-full.yaml for the whole version).
  • Upload ("Upload a version document"): the document passes the checks before saving and becomes the next number. "The base is found by its content, so the numbers may differ between servers." The base is the version whose content hash is given in basedOnHash, else the version numbered basedOn. A document uploaded again under the same file name with the same content makes no new version: it is the version it already is.
  • The document format is in the appendix.

Document folder

Set contexa.prompt.versions.directory to a folder, and every server reads it at start and every minute after. This lets you keep versions as files.

  • Every .yaml or .yml file directly in the folder (1,000,000 bytes at most) is a version document of the whole platform. A document not registered yet, or one whose text changed, is saved as the next version. The same document read again, or read by another server, is the version it already is.
  • A document that cannot be saved is not registered. The reason is kept with the reading and logged as a warning.
  • The advanced screen shows the Folder, the Setting, "Last read" (when and how many documents), "Last registered", the documents not registered with their reasons, and "Read it now". Without the setting, it says: "Set contexa.prompt.versions.directory to a folder to turn it on."
  • To change a version that came from the folder, change its file: it is registered again as the next number.

How a call gets its version

  • Every call uses the version an administrator chose with "Use" on the screen, else the newest version provided by CONTEXA (PromptVersionInUse). The setting contexa.security.tiered.prompt-bundle.active applies to the security decision only.
  • One request uses a single version for its system prompt, its user prompt and its execution record (PromptVersionPin). When an administrator switches the version in the middle of a call, the call does not mix two versions. The record names the version and its content hash.
  • Without the console's database, or when it cannot be read, a call uses the product document of the build.

What the screens show for them

  • These prompts say "Use" where the security decision says "Use for decisions", "In use" instead of "Used for decisions", and "In use now" on the list card. The list screen's footer reads: "To roll back, choose "Use" on an earlier version: every server follows within about 5 seconds. A version cannot be changed once made; "New version" makes the next number."
  • "Measure" and the trials are for the security decision only, because their inputs are its labelled cases and sealed decisions. On the advanced screen the other prompts have Document folder, Import and download, and History. Canary for some users, Run alongside and Emergency rollback are for the security decision only.
  • The finished prompt of a version's screen is built with a fixed example input: "This prompt keeps no record of its calls, so this is the version drawn with a fixed example input."
  • The checks before saving have no length check for these prompts. The length limit is built from the decision model's context and the longest recent decision input, so it applies to the security decision only.
  • "Use" goes through the same release gate as "Use for decisions", without the quality gate. At start, CONTEXA checks that the product documents of all eight prompts declare their model, budget, token counting, cache and compaction policies, and the gate does not start when one is missing. A version of these prompts inherits those policies, so it meets none of those blockers. The prompt injection guard is checked for the security decision only. A prompt whose product the build does not ship is still blocked.

Appendix: the version document

A version document is one YAML file, and one document is one version. An organization's document holds only what it changes. CONTEXA reads it with SnakeYAML's safe constructor, so a document can build nothing but maps, lists and plain values. Duplicate keys and aliases are refused, and a document holds at most 1,000,000 characters. The example below adds a part, changes a part, deletes a part, puts a prepared part in, and adds a reference block to the user prompt; the comments mark each change.

prompt: cortex.security-decision
kind: organization
basedOn: v1.0
basedOnHash: sha256:9c1f…              # written by a download; another server finds the base by it
title: Our decision guidelines
description: Our organization's context, and no similar case limits
system:
  - key: org-context                   # add a part
    add-after: honesty-more
    title: Our organization
    text: |
      Finance staff export the ledger in the last three working days of each month.
  - key: how-to-judge                  # change a part
    text: |
      1. Build one story of this request: ...
  - key: similar-case-limits           # delete a part
    delete: true
  - key: verified-signal-boundary      # put a prepared part in
    include: true
user:
  - key: org-reference                 # add a reference block
    add-after: REQUEST
    title: Organization reference
    text: |
      Month-end closing runs from the 26th to the last day of the month.
FieldMeaning
promptRequired. The prompt the document is for (cortex.security-decision)
kindproduct, organization or rendered. Without it, a document with release is a product document, else an organization's
basedOn · basedOnHashThe base by number and by content hash (sha256: and the hex). The hash is looked for first; one of the two is required
title · descriptionWhat the version is called and what it is for; without a title the version is called by its number
system · userThe parts of the system prompt and the blocks of the user prompt
A part: keyRequired. A key of the base changes the part; a new key with add-after adds one
A part: title · textThe title (required for an added part; a change keeps the base's title without one) and the text (required for a change or an addition)
A part: add-after · delete: true · include: trueAdd after the named part or block, delete the part, put a prepared part in. At most one of them; a deleted or included part has no title or text
  • The product document has the same form but holds every part. For the security decision it is contexa-core's prompt-versions/cortex.security-decision/v1.1.0.yaml (release v1.1.0). The earlier 2026.11.16.yaml (2026.11.16-v1.0) and 2026.11.18.yaml (2026.11.18-v1.0) ship beside it, unchanged. Each part has key, title, locked and its text, and may have join, heading, group, when (a condition such as minimum-action-enforce), prepared, whenText, items (the reason codes, or a block's lines and their use) and effects. The document also holds the corrections, the sentences that ask again for an answer that broke the format or a rule. An organization's document cannot set these fields.
  • The start of the application fails when the reason codes of the product document differ from the engine's. It fails too when another release the build ships names a reason code the engine lacks, or names them in another order. A rollback refuses a version whose reason codes are neither the engine's nor those of a release the build ships.
  • Content hash: the SHA-256 of the parts of the assembled version in their order. Two versions that produce the same prompt have the same hash.
