Prompt Versions

How to change the security decision prompt without touching source code. A version is a complete prompt that never changes once made: Contexa's rules stay locked, and the rest can be changed, deleted or added to on the screen or in a document. This page covers the three-click flow, the locked and changeable parts, using a version for decisions through the quality gate and rolling back, measuring and trials, canaries, running alongside, documents, the length check the order in which a decision's version is chosen, and the seven AI prompts other than the security decision kept the same way.

At a glance

The prompt decisions use is kept as versions: v1.0, v2.0 and so on, one number per tenant and prompt. Every version is a whole prompt. The version Contexa ships (Provided by Contexa) holds every part; a version of Our organization holds its base and only what it changes, deletes or adds. A version cannot be changed once made: a change is always the next number.

  • Where: menu "Prompt Quality Assurance → Prompt versions" (/contexa/admin/prompt-quality/versions), with the bar of the five menus of the group on top (Prompt Quality Assurance). Every screen and API needs the administrator role.
  • What runs: a decision takes the version chosen on the screen, else the one the configuration names, else the newest Contexa version (How a decision's version is chosen). The version is fixed on the event when the decision starts, so Layer 1, Layer 2 and every retry of one decision use the same version. The other seven prompts take their label, else the newest Contexa version (The seven prompts other than the security decision).
  • What stays Contexa's: the standard blocks of the user prompt and the values the engine fills in, the answer format, the reason codes and the rules marked with a lock. The prompt's sentences come from the version; the code holds no sentence of the prompt.
  • Prompt choice: the list screen has a "Prompt" choice with eight prompts: "Security decision" (cortex.security-decision) first, then the seven prompts other than the security decision (below). This page speaks of the security decision unless it names another prompt.

The three-click flow

  1. "New version" on the list screen opens the new version screen with the version used for decisions now as its base (/versions/new?base={number}). "New version" on a row, or on a version's screen, starts from that version instead.
  2. Change the parts and choose "Save". Only the parts you may change are open; parts with a lock are folded under "Contexa rules". The "Checks before saving" box is checked again as you change it, and "Save" works only when it passes. Saving makes the next number and leaves the base as it is.
  3. "Use for decisions" on the new version's row. The confirmation shows "Now", "Next" and "Takes effect" ("Every server follows within about 5 seconds; a decision already started ends with its version."), for the security decision the quality gate (The confirmation), and a reason you may write ("Reason (optional)", kept in the history). In the blocking mode a quality block needs the reason, and "Use with this reason" overrides it.
  • The security decision: "Save and measure at once" on the new version screen saves the version and starts its measurement on the labelled cases; it no longer uses the version for decisions. "Save and open Measure & compare" saves and opens the measurement, or its start with the new version chosen. The version's screen then says "{version} is saved and being measured." with "Open the measurement", or "{version} is saved, but its measurement could not start." with the reason. A measurement takes no reason.
  • The seven other prompts have no measurement: "Save and use at once" with its reason does steps 2 and 3 together.

Locked parts and parts you may change

A version's system prompt is made of parts drawn from top to bottom. A part with a lock is a Contexa rule: no version can change or delete it, and the new version screen keeps it folded. The parts you may change are open as text boxes: change the text, set it back with "Back to the product default", or take the part out with "Delete this part" ("Restore" brings it back). You may also add parts of your own.

  • Where an added part goes: after a part you name, from Mission to More honesty ("An added part goes no later than after More honesty; the answer format always comes last."). Parts 15–18 always stay at the end, as a model follows a format best near the end. An added part does not split a list: it follows the parts that continue the one it names.
  • Precedence: a version with a changed or added part of the organization gets the Precedence sentence after the Mission. A version that only deletes parts or puts prepared parts in does not, so the product default's prompt stays as it is. In release 2026.11.18-v1.0 and the versions on it, the same version also gets the "Blocks your organization added" sentence right after How to read the evidence.
  • User prompt: the eight standard blocks (User baseline, Session, Request, Records and comparisons, Past records (RAG), Unknown, Untrusted text, Second pass) are all locked: their titles, line names, order, fact IDs and values are the engine's, and the engine fills them for every decision. "Add a reference block" puts a block of the organization (a title and a text) after a standard block you name; an added block can be changed or deleted in a later version. A changed block stays a block the organization added: every version after draws it at the place it was added, under the same header, and counts it in the length, size and decision time estimates. A deleted block is left out. A version's content hash stays as it is.
  • How an added block is drawn: in the security decision's prompt (Layer 1, Layer 2, the retries and the replays) right after the standard block it follows, after a blank line, under the header === Title (reference written by your organization) ===. It has no fact IDs, so the model cannot cite it as a fact. A title or a line that could read as the header of a standard block is drawn in quotes.
  • Marks on a version's screen: "Locked", "As the default", "As the base", "Changed" (shown beside the base's text), "Deleted", "Added", "Prepared part put in", "Conditional".

Parts Contexa prepared

Two parts are in the product document but left out of every version until a version puts them in. On the new version screen they are under "{n} parts Contexa prepared", each with its measurement and a "Put in" button. Once in, a prepared part is locked: its text cannot be changed. A version made on that base shows it as "A prepared part the base version put in. The next version can take it out." with "Take out in this version" ("Put back" undoes it).

Checks before saving

The same checks apply to a version saved on the screen, an uploaded document and a document of the folder. If any fails, nothing is saved and every problem is named.

  • A document is also refused when it cannot be read as YAML, has a field the form does not have, misses a required field, is for another prompt, is a whole-version document (kind: rendered), or names a base this server does not have ("The base version is not on this server").
  • A version that came from a document (an upload or the folder) cannot be the base of a version made on the screen: "{version} came from a document, so the screen cannot build on it. Change the document instead: it is registered again as the next version." This keeps the two ways of editing from colliding.
  • The check that refuses a standard block's title only stops a save. A version saved before the check is assembled as it was, and such a title is drawn in quotes.
  • Beside the checks the screen shows, without refusing: the tokens of the system prompt and the added blocks against the base, about how much longer or shorter decisions take, and "After saving, a trial on recent decisions is recommended before it decides."

How length affects decision time and the context

A longer prompt takes longer to decide and uses more of the model's context. The checks estimate the system prompt and refuse a version of the security decision that cannot fit.

  • Tokens: a quarter of the characters of every part the version draws, each part counted with its longest text (any condition), its heading and its lines. A prepared part not put in is not counted. The product default v1.0 is about 4,100 tokens. The blocks a version adds to the user prompt count too, as the prompt draws them: with their header lines in the security decision, under their titles in another prompt. The values the engine fills in for each decision are not counted.
  • The limit: the version's system tokens + the input + the answer tokens (the larger of contexa.security.tiered.layer1.max-output-tokens, default 4096, and layer2.max-output-tokens, default 2560) must not exceed the context of the model that decides first. The input is the longest user prompt of the latest 500 decisions with all the new version's added blocks. Each decision is measured with the version it ran: its prompt tokens less that version's system tokens and the added blocks that version drew, and the decision with the most left is the longest. The new version's added blocks all count, whatever its base. A decision whose recorded version is not found is measured with the product default. Without a recent decision, the input is the new version's added blocks. The screen, the document folder and an upload count the same way.
  • The model's context: for an Ollama model, contexa.llm.model-capabilities.ollama.max-context-length (default 32768; a value under 4096 keeps the default). When no first-layer model is known, the Ollama value is used. A model of another provider has a context only when a setting declares its context window, and no setting declares one now: its context is not known and the length is not checked ("The model's context is not known, so the length was not checked").
  • Decision time: the difference in tokens from the base, the system prompt and the added blocks, times the median decision time per input token of the latest 200 decisions, in the checks and on the version screen's decision time card (security decision). Without decisions it is not shown.

Use for decisions, rollback and hiding

  • Use for decisions moves the screen's label to the version through the release gate, and the version used before becomes "Not used". The gate blocks a hidden version, a move that leaves no version used for decisions, a version that does not keep the prompt injection guard of its product, and a prompt whose product declares no model, budget, token counting, cache or compaction policy; the confirmation then shows "Blocked" with the reasons and nothing changes. For the security decision the release gate also reads the quality gate: nine conditions on the measurements of the version and of the version in use, a warning by default and a block in the blocking mode, which a reason overrides (The quality gate). When the quality gate cannot be read, the confirmation shows instead whether the version was tried ("Not tried" with "This version has not been tried. A trial before it decides is recommended.", the gate's warning TRIAL_RECOMMENDED). The label is cached for 60 seconds and the invalidation is checked every 5 seconds, so every server follows within about 5 seconds. A decision already started keeps its version.
  • Rollback is "Use for decisions" on an earlier version: "To roll back, choose "Use for decisions" on an earlier version: every server follows within about 5 seconds. A version cannot be changed once made; "New version" makes the next number." Going back to a version the scope used for decisions before takes no quality condition ("Passed (going back)").
  • Every move is recorded with who, when, what and why in the history and the audit log (category PROMPT_VERSION_CHANGED, actions PROMPT_VERSION_*); a quality gate overridden with a reason is PROMPT_VERSION_QUALITY_GATE_OVERRIDDEN.
  • Hide (on a version's screen, for a version in the state "Not used"): "Only takes it off the list. Its content stays; decision records and sealed evidence keep pointing at it." A version used for decisions, a canary or running alongside cannot be hidden; a hidden version cannot be used, measured, tried or rolled back to. Hidden versions are listed with "Show hidden versions".

How a decision's version is chosen

When a decision starts, its version is chosen in this order and fixed on the event.

  1. The label of the screen: a canary the request falls inside, else the version used for decisions, of the request's tenant, else of the whole platform (PLATFORM_GLOBAL). The list shows it as "Chosen on the screen" (or "Canary").
  2. The setting contexa.security.tiered.prompt-bundle.active, when it names a version (v2.0; 2 and v2 read the same) that exists and is not hidden. It is read for every decision: a version that appears later is used from then on. Shown as "Chosen by the configuration". The setting is for the security decision only.
  3. The newest version provided by Contexa, shown as "Contexa default".
  • A setting that names a version that does not exist or is hidden is logged once as a warning and passed over until it exists. A setting that names an earlier bundle (such as 2026.10.24-v19.21) is logged once as a warning ("earlier bundles are gone"); the order above then runs as if the setting were empty.
  • Outside the gate: the setting and the newest Contexa version decide without passing the release gate. The list says so ("{version} decides as the setting names it, without passing the release gate.", or "{version} decides as the newest Contexa version, taken on the upgrade without passing the release gate.") with the state of its measurement in this environment, and Contexa measures such a version once on its own (Prompt Quality Assurance).
  • Registering a product default never puts a label on it: a label exists only after an administrator chooses "Use for decisions", so the setting and the default work as they say.
  • The existence of a version and the newest Contexa version are read at most once a minute. When the database cannot be read, the last values read are used, and without them the product document of the build (2026.11.18-v1.0).
  • The event metadata keeps promptBundleSelection.version, .source and .contentHash. Layer 1, Layer 2, every retry and the decision side of a run alongside read the version from there, so moving the label never changes a decision already started.

A new product default

  • On the first start of an installation the newest product default of the build is registered as v1.0. An upgrade registers each newer product default as the next number, in order. The version used for decisions does not change by itself.
  • When the version in use is our organization's and stands on an older product default, the list shows "New product default": "Contexa released a new product default, {new}. The {in use} in use keeps running. To use the new rules, carry your changes onto the new base."
  • When the version in use is an older version provided by Contexa, there is nothing to carry: the notice reads "Contexa released the newer product version {new}. The {in use} in use keeps running; use {new} for decisions to run its rules." with a "Use for decisions" button beside "See what changed".
  • The security decision's product default of this build is 2026.11.18-v1.0: 2026.11.16-v1.0 with the locked part "Blocks your organization added" (Locked parts and parts you may change). The part is drawn only in a version the organization changed or added to. It also adds the reason code VERIFIED_SIGNAL (Signal the server confirmed) after THREAT_MATCH, so the product default's own prompt differs only by that code line and the use stated for the VerifiedSignal line. 2026.11.16-v1.0 is still shipped, and an installation that registered it registers 2026.11.18-v1.0 as the next number on upgrade.
  • "Carry onto the new base" opens the new version screen on the new product default with your changes on it: "{n} carried, {m} could not be". The changes carried are all those the version and the organization versions down its chain of bases made to the product default: changed parts (their latest title and text), added parts and blocks (changed since or not, with their place), prepared parts put in, and deleted parts. A change the new base cannot take is listed as "Could not be carried: {part} ({change}) — the new base does not have that part or no longer lets it change." Nothing is a version until you save it; drafts are not kept.

Trial decisions

"Before a new version decides, compare it on recent real decisions. The decisions made again are only recorded, never applied to anyone." A trial has no right answer to grade against: it compares the actions of two versions. To grade a version against right answers, measure it on the labelled cases (Measuring a version).

  1. In Measure & compare (/contexa/admin/prompt-quality/measure), choose the input "Latest sealed decisions", then "Version to try", "Compared with" (the version in use is marked "(now)") and "Decisions to replay": latest 20, 50 or 100.
  2. "Start the trial". The latest sealed decisions (of the tenant, when one is chosen) are each decided again with both versions: "Calls the model twice per decision, behind any real decision waiting. Seals are a sample: with fewer, it uses what there is."
  3. The result opens at /contexa/admin/prompt-quality/measure/trials/{id} and shows four cards and the details.
Card · sectionMeaning
Same actionDecisions both versions answered with the same action
Format errors"Decisions whose first answer broke the answer format, or with no usable answer. A retry for a decision rule is not counted."
Decision time (mean)The mean time of a replay, for each version
Answer length (mean)The mean answer tokens, for each version
ActionsALLOW · CHALLENGE · ESCALATE · BLOCK and "No answer", for each version

  • Nothing is applied, learned or sealed: each answer is kept in the trial's tables. A trial calls the model, so it costs as much as twice the decisions.
  • One trial runs at a time per prompt, in the same line as the measurements, so it waits behind a measurement that runs; its model calls wait behind the decisions at the model gate. It can be cancelled ("Cancel"); a trial left unfinished by a server stop is marked failed when the server starts again.
  • From the result: "Canary for some users" and "Use {version} for decisions", both through the quality gate.
  • Trials are for the security decision only: its sealed decisions are the inputs a trial decides again.

Canary for some users

On the advanced screen: choose the version, the "Share of users" (10, 25 or 50%), "Tenants" (empty for all, commas for several) and "Address starts or resource IDs" (for example /api/payments, empty for all), then "Start the canary".

  • "A user always falls on the same side. The other users are decided with the version in use." The side is drawn from a hash of the user (else the session, else the event).
  • A request is inside the canary when its tenant is one of the tenants given and its resource address starts with one of the values given or its resource ID equals one; an empty field covers all. Its decision records the source CANARY.
  • The confirmation of "Start the canary" shows the quality gate as "Use for decisions" does (use-check?target=CANARY); in the blocking mode a quality block needs a reason ("Start with this reason").
  • One version is a canary at a time; "Stop" ends it. The start and stop are in the history.

Run alongside

On the advanced screen: choose the version, the "Sample" (5 or 10%) and the "Daily limit" (1 to 10,000), then "Start". "Calls the model once more. The results are only recorded, never applied. The version that decides is not run again."

  • A sampled request is copied before its decision and analysed apart with the version run alongside after the decision. The copy is sealed as the SHADOW stage; nothing is enforced or learned.
  • The shadow runner is there wherever decisions are sealed, and runs nothing until a version runs alongside. The sample and daily limit chosen on the screen are kept on the version's registry row and shown on the screen's "Now:" line; a row without them runs contexa.security.tiered.prompt-bundle.shadow.sample-percent and .daily-call-cap (Settings). The daily limit counts the runs of the version per UTC day on each server. A request whose decision runs that same version is not run again.
  • "Results of running alongside", on the Measurements view of Measure & compare, pairs each run with its request's decision over a "Period" of 1, 7, 30 or 90 days (7 by default): "Requests run alongside", "Paired with their decision", "Answered otherwise", the actions that changed, "Inspection of the sealed decisions (by version, stage and action)" with Sealed, Failed, Passed and Not inspected, and up to 50 paired requests, those answered otherwise first, each with its "Decision seal" and "Alongside seal" opening the sealed evidence. Runs of a version that stopped keep their results for the period.
  • One version runs alongside at a time; "Stop" ends it.

Emergency rollback and history

  • Emergency rollback (advanced screen): choose "Roll back to" and give a reason. "An emergency rollback applies at once and is finished when another administrator approves it." The administrator who rolled back cannot approve it. A rollback, an emergency one too, goes only to a version the scope used for decisions before; any other target is refused.
  • The rollback table shows When, Versions, Who, State ("Applied", "Awaiting approval", "Approved", "Refused", "Incomplete") and Approval; a rollback awaiting approval has an "Approve" button.
  • History lists what was done to the versions of the prompt, newest first (up to 50): made, hidden, uploaded, registered from the folder, used for decisions, canary started and stopped, alongside started and stopped, rolled back in an emergency, rollback approved, trial started and cancelled, with who and the reason. "The audit log keeps the same".

Import and download

Use documents to move a version between servers or to keep it in version control.

  • Download ("Download as a document" on a version's screen, or the advanced screen): "Changes only (can be uploaded again)" writes the organization's document with its base named by number and content hash (basedOn, basedOnHash); "Whole version (to read)" writes every part as the version draws it, marked kind: rendered, and cannot be uploaded. The file is named cortex.security-decision-v2.0.yaml (-full.yaml for the whole version).
  • Upload ("Upload a version document"): the document passes the checks before saving and becomes the next number. "The base is found by its content, so the numbers may differ between servers." The base is the version with the content hash basedOnHash names, else the version numbered basedOn. A document uploaded again under the same file name with the same content is the version it already is.
  • The document format is in the appendix.

Document folder

Set contexa.prompt.versions.directory to a folder, and every server reads it at start and every minute after.

  • Every .yaml or .yml file directly in the folder (1,000,000 bytes at most) is a version document of the whole platform. A document not registered yet, or one whose text changed, is saved as the next version; the same document read again, or by another server, is the version it already is.
  • A document that cannot be saved is not registered: why is kept with the reading and logged as a warning.
  • The advanced screen shows the Folder, the Setting, "Last read" (when and how many documents), "Last registered", the documents not registered with their reasons, and "Read it now". Without the setting: "Set contexa.prompt.versions.directory to a folder to turn it on."
  • To change a version that came from the folder, change its file: it is registered again as the next number.

How a call gets its version

  • Every call draws the version the prompt's label points at ("Use" on the screen), else the newest version provided by Contexa (PromptVersionInUse). The setting contexa.security.tiered.prompt-bundle.active applies to the security decision only.
  • The system prompt, the user prompt and the execution record of one request are drawn with the same version (PromptVersionPin): a label moved in between does not mix two versions in one call. The record names the version and its content hash.
  • Without the console's database, or when it cannot be read, a call draws the product document of the build.

What the screens show for them

  • "Use" instead of "Use for decisions", "In use" instead of "Used for decisions", and "In use now" on the list card: "To roll back, choose "Use" on an earlier version: every server follows within about 5 seconds. A version cannot be changed once made; "New version" makes the next number."
  • "Measure" and the trials are for the security decision only: its labelled cases and sealed decisions are their inputs. On the advanced screen the other prompts have Document folder, Import and download and History; Canary for some users, Run alongside and Emergency rollback are for the security decision only.
  • The finished prompt of a version's screen is drawn with a fixed example input: "This prompt keeps no record of its calls, so this is the version drawn with a fixed example input."
  • The checks before saving have no length check for these prompts: the length limit is the decision model's context with the longest recent decision input.
  • "Use" goes through the same release gate as "Use for decisions", without the quality gate. The start checks that the product documents of all eight prompts declare their model, budget, token counting, cache and compaction policies, and the gate does not start when one is missing; a version of these prompts inherits them, so it meets none of those blockers. The prompt injection guard is checked for the security decision only. A prompt whose product the build does not ship is still blocked.

Policy generation

Policy generation has two releases: 2026.11.17-v1.0 and 2026.11.18-v1.0 (contexa-iam: prompt-versions/PolicyGeneration/2026.11.18.yaml). For a request without data, the new release draws "No IAM data or similar query patterns were provided." in the Data part instead of the word null. 2026.11.17-v1.0 and the versions made on it still draw null. An installation that registered 2026.11.17-v1.0 registers the new release as the next number on upgrade; the version in use does not change by itself. For the seven prompts other than the security decision, such as policy generation, every release the build ships is found by its own release name without the version tables, so a request that names the earlier release draws that release. Appendix: the version document

A version document is one YAML file; one document is one version. An organization's document holds only what it changes. It is read with SnakeYAML's safe constructor: a document builds nothing but maps, lists and plain values, duplicate keys and aliases are refused, and a document holds at most 1,000,000 characters.

prompt: cortex.security-decision
kind: organization
basedOn: v1.0
basedOnHash: sha256:9c1f…              # written by a download; another server finds the base by it
title: Our decision guidelines
description: Our organization's context, and no similar case limits
system:
  - key: org-context                   # add a part
    add-after: honesty-more
    title: Our organization
    text: |
      Finance staff export the ledger in the last three working days of each month.
  - key: how-to-judge                  # change a part
    text: |
      1. Build one story of this request: ...
  - key: similar-case-limits           # delete a part
    delete: true
  - key: verified-signal-boundary      # put a prepared part in
    include: true
user:
  - key: org-reference                 # add a reference block
    add-after: REQUEST
    title: Organization reference
    text: |
      Month-end closing runs from the 26th to the last day of the month.
FieldMeaning
promptRequired. The prompt the document is for (cortex.security-decision)
kindproduct, organization or rendered. Without it, a document with release is a product document, else an organization's
basedOn · basedOnHashThe base by number and by content hash (sha256: and the hex). The hash is looked for first; one of the two is required
title · descriptionWhat the version is called and what it is for; without a title the version is called by its number
system · userThe parts of the system prompt and the blocks of the user prompt
A part: keyRequired. A key of the base changes the part; a new key with add-after adds one
A part: title · textThe title (required for an added part; a change keeps the base's title without one) and the text (required for a change or an addition)
A part: add-after · delete: true · include: trueAdd after the named part or block, delete the part, put a prepared part in. At most one of them; a deleted or included part has no title or text
  • The product document is the same form with every part: contexa-core's prompt-versions/cortex.security-decision/2026.11.18.yaml (release 2026.11.18-v1.0). The earlier 2026.11.16.yaml (2026.11.16-v1.0) is shipped beside it, unchanged. Each part has key, title, locked and its text, and may have join, heading, group, when (a condition such as minimum-action-enforce), prepared, whenText, items (the reason codes, a block's lines and their use) and effects. It also holds the corrections that ask again for an answer that broke the format or a rule. An organization's document cannot set these fields.
  • The start fails when the reason codes of the product document differ from the engine's. It fails too when another release the build ships names a reason code the engine lacks, or names them in another order. A rollback refuses a version whose reason codes are neither the engine's nor those of a release the build ships.
  • Content hash: the SHA-256 of the parts of the assembled version in their order. Two versions that draw the same prompt have the same hash.
