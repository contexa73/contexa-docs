The Life of a Request

Follows one request in order: it arrives, the stored decision is applied, it runs, it is analyzed, and that decision applies to the next request. It also covers the responses users get for each decision, how a block spreads and is released, and how application code reads the decision.

At a glance

At request time only the decision already stored is applied. The new decision about this request is made after the response has left and applies from the same user's next request. One per-user decision store links the two.

Example. A user exports a report through a protected method. The response leaves at once and analysis starts in the background. If the AI model chooses block, the decision is stored and the user's next request gets the block response. If the model chooses allow, that allow is used only for 15 seconds in the same session, IP and browser; after that, requests are pending analysis again and are analyzed.

The full comparison of the ownership modes is in How Contexa Works.

Request time ①: reading the decision and changing authorities

This step exists only under CONTEXA_OWNED. When the Contexa chain reads the security context, it applies the stored decision so that the application's authority checks such as hasRole() follow the decision.

  • Where: in the session chain, the security context repository (AISessionSecurityContextRepository) applies it when it first reads the context; in the token chain, the filter right after JWT validation (AIOAuth2ZeroTrustFilter) does.
  • Whose decision: it is read by user ID. An agent acting for a person reads its own key (<user>::agent::<agent>), and a block of the delegator counts as its block too.
  • Allow is bound to its context: an allow reads as allow only in the session, IP and browser it was made for (the context hash), and as pending analysis anywhere else.
  • 5-second cache: the decision of the same user and context is kept in server memory for 5 seconds. Changing authorities right after a new block can be up to 5 seconds late, but the two filters read the store directly without the cache, so the block response is not late.
  • Invalidated sessions and tokens: a session on the invalidation list is ended and the request goes on as not signed in. A JWT is refused with 401.
  • With contexa.security.zerotrust.enabled=false, this step (applying the decision, changing authorities, session tracking) does not run.
  • Implementation order: AISessionSecurityContextRepository's loadDeferredContext → AbstractZeroTrustSecurityService's applyZeroTrustToContext → adjustAuthoritiesByAction. Session tracking and invalidation records are kept in memory in standalone mode (InMemoryZeroTrustSecurityService) and in Redis in distributed mode (RedisZeroTrustSecurityService).

Request time ②: what users get for each decision

Under CONTEXA_OWNED, two filters (the challenge filter for step-up, the access control filter for block and hold) read the decision from the store, not from the authorities, and answer. A browser request is sent to a notice page; an API or AJAX request gets a JSON error.

The method step: @Protectable

The interception in front of a protected method (AuthorizationManagerMethodInterceptor) runs under both ownership modes. It runs before Spring's method security (@PreAuthorize and the like).

  • In shadow mode, the stored decision and the immediate decision of step 6 are recorded only, not refused.
  • If the application declares a resource certification gate (ProtectableResourceCertificationGate) bean, a method with @Protectable(verificationRequired) (default true) on an uncertified resource is refused with 423. OSS has no implementation of this bean.
  • Whether an agent request with no decision on record is decided on the spot is set by contexa.security.zerotrust.protectable.unrecorded-agent-request (default DECIDE_IN_PLACE; PROCEED lets it through like a person).

A refusal becomes one of the responses below. The body has status · code (ZERO_TRUST_<decision>) · message · action · resourceId · riskScore · analysisTimeout · timestamp.

How the decision is made

This is what happens after the analysis event has been published. The request thread does not wait.

  • Filter: if the decision of this user (an agent's own key for an agent) and context is not pending analysis, nothing new is analyzed; the request is recorded only as "not analyzed". With contexa.security.zerotrust.enabled=false, received events do nothing.
  • Delivery: standalone mode passes events inside one server; distributed mode passes them through Kafka.
  • Queue: events go into a queue of 10,000 and are taken 8 at a time, then lined up per user and session and handled one at a time. Each event has an analysis budget of 180 seconds, and a temporary failure goes back to the line up to 3 times.
  • Decision: Layer 1 decides, and only when Layer 1 chooses ESCALATE does Layer 2 decide again. The Layer 1 and Layer 2 prompts of one event are drawn with the same prompt bundle.
  • Processing steps: make the decision (50) → enforce (55) → seal evidence (56) → audit (60) → SaaS forwarding (65, only when turned on).

How a block spreads and is released

How a block spreads

A server that missed the signal also checks the store every 0.5 seconds. Contexa's own refusal responses are not cut.

How a block is released

  • A block record has five states: BLOCKED · UNBLOCK_REQUESTED · RESOLVED · TIMEOUT_RESPONDED · MFA_FAILED.
  • The unblock MFA cannot be started again once the attempt limit (contexa.security.zerotrust.max-block-mfa-attempts, default 2) is reached. Failures are counted for 24 hours.
  • A delegated agent's block cannot be released by MFA; it gets 403 AGENT_BLOCKED.
  • When an unresolved hold turns into a block, the same block storage, flag and block record (person) or agent stop take place.

  • The request-time filters do not read the enforcement mode. Even after switching to SHADOW or turning off contexa.security.zerotrust.enabled, the filters keep enforcing the block (no expiry), step-up and hold already stored (CONTEXA_OWNED).
  • An event carries the mode it was published under. The decision of an event published under SHADOW is not stored or applied, even if the mode has meanwhile become ENFORCE.
  • Decision results go to the observation and audit records. The observation table is ai_security_decision_observation; the decision records are shown in the admin console's "Real-time Monitor" (/contexa/admin/security-monitor).

Reading the decision in application code

  • Request attribute contexa.zeroTrustAction: a request the decision was applied to keeps the decision (CONTEXA_OWNED).
  • Authentication object ZeroTrustAuthenticationToken: getAction() · getTrustScore() · getThreatScore(). It becomes this object only when the session chain changed the authorities; the token chain keeps a JwtAuthenticationToken.
  • Policy expressions #ai: used in Contexa's policy (XACML) expressions. To use them in the application's @PreAuthorize, the mode must be CONTEXA_OWNED.
  • Decision classes: on ZeroTrustAction, isBlocking() is true for block and hold, and isAccessRestricted() for block, step-up and hold.
ExpressionTrue when
#ai.isAllowed()the current decision is allow
#ai.isBlocked()the current decision is block
#ai.needsChallenge()the current decision is step-up
#ai.needsEscalation()the current decision is held for review

#ai.hasAction('ALLOW')the current decision is the one given
#ai.hasActionIn('ALLOW', 'PENDING_ANALYSIS')the current decision is one of those given
The usual state is pending analysis. An allow is used only for 15 seconds in the same context, so requiring only #ai.isAllowed() refuses most requests. To filter out only restricting decisions, accept allow and pending analysis together, as below. 
// #ai is registered only under CONTEXA_OWNED (@EnableAISecurity(mode = SecurityMode.FULL) or contexa.bridge.ownership=CONTEXA_OWNED).
import org.springframework.security.access.prepost.PreAuthorize;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class ReportController {

    @GetMapping("/reports")
    @PreAuthorize("#ai.hasActionIn('ALLOW', 'PENDING_ANALYSIS') and hasRole('ADMIN')")
    public String reports() {
        return "ok";
    }
}

Agent expressions (isAgent() and others) are in Stop, Confirm, Limit; all policy expressions are in AI security expressions.

Learning and live notifications

  • Learning: only allow decisions actually applied are learned into the behavioral baseline. Decisions in shadow mode are not learned. The learning service (SecurityLearningService) hands them to baseline learning (BaselineLearningService, an exponential moving average), and frequently used IP ranges are kept up to a fixed number, pushing out the least used first. The conditions are in Decision Engine, "What is learned".
  • Live notifications (SSE): subscribing to GET /contexa/admin/api/aiam/sse/zero-trust/subscribe gives the signed-in user their own decision, analysis progress and error notifications (ZeroTrustSsePublisher). It is not a channel that sends every decision to administrators.
  • Notice pages: /contexa/zero-trust/blocked · /contexa/zero-trust/challenge-required · /contexa/zero-trust/analysis-pending are the pages a user who got a decision sees.
