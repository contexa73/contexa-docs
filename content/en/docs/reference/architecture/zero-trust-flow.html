The Life of a Request

This page follows one request from its arrival to the moment its decision is made and applied. CONTEXA splits the work into a path that handles the request and a path that analyzes it. At request time it applies only the decision already stored. The new decision is made after the response has left, and it applies to the next request. The page also covers the response a user gets for each decision, how a block spreads and is released, and how application code reads the decision.

At a glance: the request path and the analysis path

CONTEXA does two kinds of work on separate paths. The request path runs from the arrival of a request to the end of its response, and it applies only the decision already stored. The analysis path starts after the response has left: an AI model analyzes the request, makes a new decision and stores it. The new decision applies from the same user's next request.

A decision is the result that says how to treat one user's requests. It is one of allow (ALLOW), step-up authentication (CHALLENGE, one more verification is required), hold for review (ESCALATE, requests stop until an administrator has reviewed them) or block (BLOCK). A user with no stored decision, or whose decision's lifetime is over, is in the state pending analysis (PENDING_ANALYSIS). Requests in that state pass, and analysis starts.

One per-user decision store links the two paths. The analysis path writes the decision to the store, and the request path reads it on the same user's next request. In standalone mode (standalone, the default) the store is server memory. In distributed mode (distributed) it is Redis. The mode is set with contexa.infrastructure.mode.

Example. A user exports a report through a protected method. The response leaves at once, and analysis starts in the background. If the AI model chooses block, the decision is stored and the user's next request gets the block response. If the model chooses allow, that allow is used only for 15 minutes, in the same session, IP and browser (contexa.security.zerotrust.allow-validity). A request after those 15 minutes is pending analysis again and is analyzed. Only a method that needs its decision inside the call itself is an exception; the method step below describes it.

How step 3 is done depends on who owns login, sessions and cookies. When your application owns them, the mode is HOST_OWNED. When CONTEXA owns them, it is CONTEXA_OWNED. This setting is called the ownership mode and is set with contexa.bridge.ownership.

Under either ownership mode, filters and protected methods apply the stored decision. What differs is whether authorities are changed and where a step-up is sent. The full comparison of the ownership modes is in How CONTEXA Works.

Request time ①: applying the stored decision to authorities (CONTEXA_OWNED)

This step exists only when CONTEXA owns sign-in (CONTEXA_OWNED). The moment the chain CONTEXA built reads the security context (Spring Security's sign-in information) from the request, it reads the stored decision and changes the user's authorities to match it. The application's authority checks such as hasRole() then follow the decision without any extra code. For example, a blocked user holds only ROLE_BLOCKED instead of the original authorities, so a hasRole('ADMIN') check fails.

  • Where: in the chain that signs in with sessions (the session chain), the security context repository (AISessionSecurityContextRepository) applies it when it first reads the context. In the chain that authenticates with JWTs (the token chain), the filter right after JWT validation (AIOAuth2ZeroTrustFilter) applies it.
  • Whose decision: it reads the decision stored under the user ID. An AI agent acting for a person reads the decision stored under its own key (<user>::agent::<agent>). When the user who delegated the work to the agent (the delegator) is blocked, the agent counts as blocked too.
  • An allow is tied to where it was made: an allow reads as allow only for a request with the same value (the context hash) built from the session ID, client IP and browser (User-Agent) the decision was made for. If any of the three differs, it reads as pending analysis. Step-up, block and hold are not tied this way; they apply to all of the user's sessions.
  • 5-second cache: a result read as allow is kept in server memory for 5 seconds for the same user and context. Restricting decisions such as a block are not cached. So changing authorities right after a new block is stored can be up to 5 seconds late. The two filters described in the next section read the store directly without the cache, so the block response is not late.
  • Invalidated sessions and tokens: a session on the invalidation list is ended, and the request is handled as not signed in. An invalidated JWT is refused with 401.
  • With contexa.security.zerotrust.enabled=false, this step (applying the decision, changing authorities, session tracking) does not run. Session tracking records each user's session IDs so that a forced logout reaches every session of that user.
  • Following it in code: the order is AISessionSecurityContextRepository's loadDeferredContext → AbstractZeroTrustSecurityService's applyZeroTrustToContext → adjustAuthoritiesByAction. Session tracking and invalidation records are kept in memory in standalone mode (InMemoryZeroTrustSecurityService) and in Redis in distributed mode (RedisZeroTrustSecurityService).
DecisionAuthorities after the change

The authentication object is replaced only when the authorities actually change. The session chain replaces it with a ZeroTrustAuthenticationToken that carries the decision and the scores. The token chain replaces it with a new JwtAuthenticationToken with only the authorities changed. Opaque tokens get no authority change, so for them only the two filters' reads of the decision apply.

Request time ②: what users get for each decision

When the stored decision is step-up, block or hold, CONTEXA does not pass the request to your application. It answers the request itself, through two filters: the challenge filter handles step-up, and the access control filter handles block and hold. Both filters read the decision from the decision store directly, not from the authorities. So both ownership modes give the same responses. Under HOST_OWNED the filters run right after the application's chain and send a step-up to CONTEXA's step-up page (The step-up under HOST_OWNED). A browser request is sent to a notice page; an API or AJAX request gets a JSON error.

The method step: protected methods (@Protectable)

Filters apply the stored decision to each HTTP request. The interception in front of a protected method (AuthorizationManagerMethodInterceptor) applies it once more at each method call. A protected method is also where analysis events are published. The interception runs under both ownership modes, and it runs before Spring's method security (@PreAuthorize and the like).

Protected methods come in two kinds. An ordinary method runs without waiting for a decision and is analyzed afterwards. An immediate-decision method (@Protectable(sync=true)) gets its decision inside the call and runs only if the result is allow.

  • In shadow mode (SHADOW), the stored decision and the immediate decision of step 6 are only recorded; they do not refuse the call.
  • If the application declares a resource certification gate (ProtectableResourceCertificationGate) bean, a method with @Protectable(verificationRequired) (default true) that handles an uncertified resource is refused with 423. OSS has no implementation of this bean.
  • Whether an AI agent request with no stored decision is decided on the spot is set by contexa.security.zerotrust.protectable.unrecorded-agent-request. The default is DECIDE_IN_PLACE; PROCEED lets the request through like a person's.

When the method step refuses a call, CONTEXA answers with one of the HTTP responses below. The body has status · code (ZERO_TRUST_<decision>) · message · action · resourceId · riskScore · analysisTimeout · timestamp. For a block, a started step-up or a hold, a browser page request (Accept with text/html) is sent to the same notice page as in Request time ② instead of getting JSON.

The analysis path: how the decision is made

This is what happens after the analysis event has been published. The thread that handled the request does not wait for it. The analysis runs in the background, separately from the response, and its result is used by the next request.

  • Filter: if the decision of this user (an AI agent's own key for an agent) and context is not pending analysis, nothing new is analyzed. The request is recorded only as "not analyzed". With contexa.security.zerotrust.enabled=false, received events do nothing.
  • Delivery: in standalone mode events are passed inside one server. In distributed mode they are passed through Kafka.
  • Queue: events go into a queue of 10,000 and are taken 8 at a time. The events taken are lined up per user and session and handled one at a time. Each event gets up to 180 seconds of analysis time. After a temporary failure it goes back into the line, up to 3 times.
  • Decision: Layer 1 decides first. Only when Layer 1 chooses hold (ESCALATE) does Layer 2 decide again. The Layer 1 and Layer 2 prompts of one event are drawn with the same prompt version.
  • Processing steps: once the decision exists, the steps run in this order: make the decision (50) → apply (55) → seal evidence (56) → audit (60) → SaaS forwarding (65, only when turned on). The numbers are the run order. The apply step stores the decision and, for a block, sends the signal that cuts responses in flight. Evidence sealing seals the prompt exactly as it was sent to the model, together with the decision. Auditing writes the decision to the audit record.

How a block spreads and is released

A block is the strictest decision. This section explains how a stored block stops responses in flight and later requests, and how a block is released.

How a block spreads

A server that missed the signal also checks the store every 0.5 seconds. CONTEXA's own refusal responses are not cut.

How a block is released

  • A block record has five states: BLOCKED · UNBLOCK_REQUESTED · RESOLVED · TIMEOUT_RESPONDED · MFA_FAILED.
  • The unblock MFA cannot be started again once the attempt limit (contexa.security.zerotrust.max-block-mfa-attempts, default 2) is reached. Failures are counted for 24 hours.
  • When your application owns login (HOST_OWNED), CONTEXA starts no MFA flow of its own. The unblock MFA goes through the verification-only step-up page (/contexa/step-up?purpose=block); see The step-up under HOST_OWNED.
  • The block of an AI agent working on a delegation cannot be released by MFA; its requests get 403 AGENT_BLOCKED.
  • When an unresolved hold turns into a block, the same things happen: the block is stored, the block flag is set, and a block record (person) is written or the agent is stopped.

How agent requests differ

Operating modes and operation

The operating mode decides whether CONTEXA analyzes requests and whether it stores and applies decisions. At the start of adoption you can run shadow mode (SHADOW), which analyzes requests and keeps the decisions in its own memory without applying them to requests.

Off (DISABLED, including the old name OBSERVE)nononenonenone
Shadow mode (SHADOW)yesnot applied. The decision stays in shadow mode's own memory. A protected method's stored decision is recorded onlywrittenallows only
Enforce mode (ENFORCE, default)yesstored and applied from the next requestwrittenonly allows actually applied
  • The request-time filters follow the operating mode. After switching to SHADOW or turning off contexa.security.zerotrust.enabled, nothing is stopped in either ownership mode. The block (no expiry), step-up and hold already stored stay in the store and apply again under ENFORCE.
  • An analysis event carries the operating mode it was published under. The decision of an event published under SHADOW is not stored or applied, even if the mode has meanwhile become ENFORCE.
  • Decision results go to the observation and audit records. The observation table is ctxa_ai_security_decision_observation. The decision records are shown in the admin console's "Security event log" (/contexa/admin/security-monitor) and in the Zero Trust console's decision records (/contexa/admin/zero-trust/decisions).

Reading the decision in application code

These are the ways application code learns the current user's decision.

  • Request attribute contexa.zeroTrustAction: a request the decision was applied to keeps the decision under this name (CONTEXA_OWNED).
  • Authentication object ZeroTrustAuthenticationToken: use getAction() · getTrustScore() · getThreatScore(). It becomes this object only when the session chain changed the authorities; the token chain keeps its JwtAuthenticationToken.
  • Policy expressions #ai: used in CONTEXA's policy (XACML) expressions. They cannot be used in the application's @PreAuthorize.
  • Decision classes: on ZeroTrustAction, isBlocking() is true for block and hold, and isAccessRestricted() is true for block, step-up and hold.
ExpressionTrue when
#ai.isAllowed()the current decision is allow
#ai.isBlocked()the current decision is block
#ai.needsChallenge()the current decision is step-up
#ai.needsEscalation()the current decision is held for review
#ai.isPendingAnalysis()the current decision is pending analysis
#ai.hasAction('ALLOW')the current decision is the one given
#ai.hasActionIn('ALLOW', 'PENDING_ANALYSIS')the current decision is one of those given
With no stored decision the state is pending analysis. An allow is used only for 15 minutes, in the session, IP and browser it was made for. So a user's first request, a request after those 15 minutes and a request from another environment all read as pending analysis. Requiring only #ai.isAllowed() refuses those requests. To filter out only step-up, block and hold, accept allow and pending analysis together, as below. 
// #ai cannot be used in the application's @PreAuthorize. Use it in the condition of a Contexa method policy on a @Protectable method.
// Policy condition (entered in the policy center): #ai.hasActionIn('ALLOW', 'PENDING_ANALYSIS') and hasRole('ADMIN')
import io.contexa.contexacommon.annotation.Protectable;
import org.springframework.stereotype.Service;

@Service
public class ReportService {

    @Protectable
    public String reports() {
        return "ok";
    }
}

Agent expressions (isAgent() and others) are in Stop, Confirm, Limit; all policy expressions are in AI security expressions.

Learning and live notifications

This covers how decisions feed learning, and how a user receives their own decisions live.

  • Learning: the behavioral baseline (the pattern of working hours, devices and networks learned for each user) learns only from allow decisions: in enforce mode the ones actually applied, in shadow mode the ones kept in shadow mode's own memory. The learning service (SecurityLearningService) hands them to baseline learning (BaselineLearningService, an exponential moving average). Frequently used IP ranges are kept up to a fixed number, and when the number is exceeded the least used are pushed out first. The conditions are in Decision Engine, "What is learned".
  • Live notifications (SSE): subscribing to GET /contexa/admin/api/aiam/sse/zero-trust/subscribe gives the signed-in user their own decision, analysis progress and error notifications (ZeroTrustSsePublisher). It is not a channel that sends every decision to administrators.
  • Notice pages: /contexa/zero-trust/blocked · /contexa/zero-trust/challenge-required · /contexa/zero-trust/analysis-pending are the pages a user who got a decision sees.
