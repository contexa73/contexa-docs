Quick Start

Get Started

The shortest way to turn Contexa on in a Spring Boot application: add the dependencies, enable AI security, configure the dedicated database and the AI models, then run and check that it is on. Each step is explained in detail in the installation guide.

Fastest: let the CLI do all of this. In your Spring Boot 3 project folder (or an empty folder, which gets a sample application):

curl -fsSL https://install.ctxa.ai | sh      # Windows: irm https://install.ctxa.ai/install.ps1 | iex
contexa init

It prepares a local PostgreSQL with pgvector and an AI model, changes the project, checks the dependencies and starts the application. What it does is in Install with the CLI. The steps below do the same by hand.

Prerequisites

Before you start, make sure the following are installed and running.

Requirement Version Notes
Java 17+ Contexa is built with the Java 17 toolchain.
Spring Boot 3.x Built and tested with 3.5.4. The startup is refused on 4.x.
PostgreSQL pgvector A dedicated Contexa database with the vector extension (the code does not check the PostgreSQL version)
AI models Chat + embedding This page uses a local Ollama. OpenAI and Anthropic work too.

Database Setup

Create the dedicated Contexa database and turn on the vector extension. Contexa creates its tables in this database when the application first starts.

SQL 
CREATE USER contexa WITH PASSWORD 'change-me';
CREATE DATABASE contexa OWNER contexa;
\c contexa
CREATE EXTENSION IF NOT EXISTS vector;

Ollama Models

Pull the models for chat and embeddings. The names must match the model values in the step 3 settings.

Shell 
ollama pull qwen3:8b
ollama pull mxbai-embed-large

Add Dependency

The single Contexa starter brings all five Contexa modules (common, core, identity, iam, autoconfigure). It does not bring an AI provider starter or the PgVector starter, so add them alongside.

Gradle (Kotlin DSL) 
dependencies {
    implementation("ai.ctxa:spring-boot-starter-contexa:0.1.1")
    implementation(platform("org.springframework.ai:spring-ai-bom:1.1.8"))
    implementation("org.springframework.ai:spring-ai-starter-model-ollama")
    implementation("org.springframework.ai:spring-ai-starter-vector-store-pgvector")
}
Gradle (Groovy) 
dependencies {
    implementation 'ai.ctxa:spring-boot-starter-contexa:0.1.1'
    implementation platform('org.springframework.ai:spring-ai-bom:1.1.8')
    implementation 'org.springframework.ai:spring-ai-starter-model-ollama'
    implementation 'org.springframework.ai:spring-ai-starter-vector-store-pgvector'
}
Maven 
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.ai</groupId>
            <artifactId>spring-ai-bom</artifactId>
            <version>1.1.8</version>
            <type>pom</type>

</dependencyManagement>

    <dependency>
        <groupId>ai.ctxa</groupId>

Choosing a provider — add only the chat provider starters you use: spring-ai-starter-model-openai for OpenAI, spring-ai-starter-model-anthropic for Anthropic. Anthropic has no embedding model, so add OpenAI or Ollama for embeddings. Spring AI BOM 1.1.8 is the version Contexa is built and tested with.

2

Enable AI Security

Putting @EnableAISecurity on the main class turns Contexa on. Without it every Contexa auto-configuration is left out, even with the starter on the classpath. Without attributes it is the SANDBOX mode with the authentication ownership HOST_OWNED: Contexa builds no sign-in chain, and your application's Spring Security keeps owning sign-in, sessions and access rules. Contexa still decides and enforces on every path, with filters that run right after your chain, and protects its own admin console. To leave sign-in to Contexa, use @EnableAISecurity(mode = SecurityMode.FULL) (what changes, annotation reference).

Java 
@SpringBootApplication
@EnableAISecurity
public class MyApplication {

    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}

Under the hood — @EnableAISecurity imports AiSecurityConfiguration through AiSecurityImportSelector. When your application has no PlatformConfig bean, this configuration creates a default PlatformConfig; security chains are built from it only when Contexa owns sign-in (CONTEXA_OWNED).

What your application must do when it owns sign-in (default) — ① Declare your own SecurityFilterChain (without it Spring Boot's default security asks every request for sign-in, and Contexa reports it with an ERROR log). ② Put the signed-in user into the SecurityContext as an authenticated Authentication, in a filter of that chain. The admin console /contexa/admin/** is protected by Contexa's own chain and administrator sign-in, so your chain does not need to protect it. Example code is in Connect your existing sign-in in the installation guide.

3

Configure

Write your application's database, the dedicated Contexa database (required) and the AI models in application.yml.

YAML 
spring:
  application:
    name: my-app                     # do not start it with contexa-
  datasource:                        # your application's default database
    url: jdbc:postgresql://localhost:5432/myapp
    username: myapp
    password: ${MYAPP_DB_PASSWORD}

contexa:
  datasource:                        # dedicated Contexa database (required)
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
  llm:
    selection:
      chat:
        mode: dynamic-priority       # the default, written exactly like this
        priority: ollama
      embedding:
        mode: fixed                  # the default
        priority: ollama
    chat:
      ollama:
        base-url: http://127.0.0.1:11434
        model: qwen3:8b
        keep-alive: 30m
    embedding:
      ollama:
        dedicated-runtime-enabled: false
        model: mxbai-embed-large
        dimensions: 1024

The dedicated Contexa database is required — without contexa.datasource.url the startup stops with contexa.datasource.url must be configured for @EnableAISecurity. The same address as your application database is refused by default too. Do not set contexa.datasource.isolation.contexa-owned-application: true in an existing application: with it your application's default database connection can become the Contexa database, and the capability check gets strict.

Application name — when spring.application.name starts with contexa-, Contexa treats the application as owned by Contexa and runs the capability check as FAIL_FAST, so the startup stops when a required part such as the chat model or the vector store is missing. Use another name.

Ollama settings — when you set contexa.llm.chat.ollama.base-url, Contexa creates the chat model and (on the same server) the embedding model on that Ollama server itself, so you do not need to set Spring AI's spring.ai.ollama.*. With an empty model, chat uses qwen3:8b and embeddings use mxbai-embed-large. keep-alive is how long the model stays in memory, dedicated-runtime-enabled: true runs only the embeddings on another Ollama server (contexa.llm.embedding.ollama.base-url), and dimensions is the embedding dimension (default 1024).

OpenAI and Anthropic — put provider keys in the Spring AI settings, not under contexa.llm: spring.ai.openai.api-key, spring.ai.anthropic.api-key. Then set contexa.llm.selection.chat.priority to that provider, and contexa.llm.selection.embedding.priority to openai or ollama for embeddings (Minimal settings).

Model priority — contexa.llm.selection.chat.priority takes a comma-separated provider list (ollama, anthropic, openai); the default is openai,anthropic,ollama. Contexa looks for each provider's model in order, moves to the next provider when one cannot be used, and finally uses any available model even if it is not listed. contexa.llm.selection.chat.mode is dynamic-priority (default, list order), fixed (a single provider) or spring-primary (the Spring @Primary bean), and the value must be written exactly in this lower-case, hyphenated form. Embeddings use a single provider with fixed, because the vector dimension is fixed.

4

Run & Verify

Start the application and check that Contexa is on.

Shell 
# Gradle
./gradlew bootRun

# Maven
mvn spring-boot:run

Verify: Startup Log

  • [IamSeedData] OSS schema provenance verified. — the tables in the Contexa database are ready.
  • Skipping Contexa-owned authentication chain bootstrap in HOST_OWNED mode — Contexa is on in the way where your application owns sign-in.
  • An ERROR-level [ContexaCapability] ... — a part such as the chat model or the vector store is missing. As it is, no decision will be made (Troubleshooting).

Verify: Auto-Configuration Report

Start with the --debug flag to see which Contexa auto-configurations were applied.

Shell 
./gradlew bootRun --args='--debug'

In the positive matches, look for io.contexa auto-configurations such as CoreInfrastructureAutoConfiguration, CoreDataAutoConfiguration and CoreLLMAutoConfiguration. Without @EnableAISecurity they are all left out.

Verify: Actuator Endpoints

With spring-boot-starter-actuator you can use the health endpoint and the contexacapabilities endpoint, which shows Contexa's capability check (to open it over the web, add it to Spring Boot's management.endpoints.web.exposure.include).

Shell 
curl http://localhost:8080/actuator/health
curl http://localhost:8080/actuator/contexacapabilities

Database required — Contexa does not start when it cannot connect to the dedicated Contexa database, or when only some Contexa tables exist in it. Before running, check that contexa.datasource.* is right and that the database and the vector extension exist.

Method-Level Security

Protect Your First Method

Put @Protectable on the methods to protect with AI decisions. Before the call, the policy and the user's stored decision are checked (on BLOCK, CHALLENGE or ESCALATE the method does not run); after it runs, the call is handed over for analysis. By default the decision is made after the response and applies from the next call; with sync = true it is made inside the call. A Spring Authentication is needed at call time; without one, or with an anonymous one, the call is refused.

Java 
@Service
public class OrderService {

    @Protectable
    public Order getOrder(Long orderId) {
        return orderRepository.findById(orderId)
                .orElseThrow(() -> new OrderNotFoundException(orderId));
    }
}

Common @Protectable Attributes

Attribute Type Default Description
ownerField String "" The field (or getter) name on the target object used for row-level owner checks. Its value is compared with the signed-in user's name (administrators skip it). Empty means no check.
sync boolean false With true the decision is made inside the call before the method returns (the response takes longer). With false only an analysis event is published and the decision is made asynchronously after the response.

There are nine attributes in all (including verificationRequired, category, sensitivity, actions, importance, privileged and exportSensitive). All of them are in the @Protectable reference.

AI Decisions

What Happens Next — The Five Decisions

A request Contexa analyzed gets a decision (ZeroTrustAction) stored, which applies to the user's next request. This is with the ENFORCE enforcement mode (default).

Decision Status code Valid for Behavior
ALLOW 200 15 s The request is processed as usual.
BLOCK 403 No expiry Refused. The decision authority is ROLE_BLOCKED, kept until an administrator releases it or block-release MFA is passed.
CHALLENGE 401 1,800 s Step-up authentication (MFA) is required. The decision authority is ROLE_MFA_REQUIRED.
ESCALATE 423 300 s Held for review for a while. The decision authority is ROLE_REVIEW_REQUIRED.
PENDING_ANALYSIS Passes (503) — No decision is stored. The request goes on and analysis starts (decision authority ROLE_PENDING_ANALYSIS). Agent requests and sync = true methods are decided in place, and are refused with 503 when no decision can be obtained.

An AI model makes the decision — the decision engine gathers the facts of the request (sign-in information, behavioral baseline, past decision records and more) and asks an AI model, so decisions come out without writing policy rules. By default the decision is made asynchronously after the response. In the default way where your application owns sign-in, decisions are enforced at @Protectable methods; enforcement at the URL works when Contexa owns sign-in. Details are in Decision engine.
