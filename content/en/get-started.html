Quick Start

Get Started

CONTEXA is a security library that you add to a Spring Boot application. When a user calls a method you have protected, an AI model analyzes the request and decides one of four outcomes: allow (ALLOW), require step-up authentication (CHALLENGE), hold for review (ESCALATE), or block (BLOCK). CONTEXA stores the decision and, by default, applies it from the same user's next request on. This page is the shortest way to turn CONTEXA on: add the dependencies, enable AI security with one annotation, configure the dedicated database and the AI models, run the application and check that CONTEXA is on, then protect one method. Each step is explained in detail in the installation guide.

Fastest: let the CLI do all of this. In your Spring Boot 3 project folder (or an empty folder, which gets a sample application):

curl -fsSL https://install.ctxa.ai | sh      # Windows: irm https://install.ctxa.ai/install.ps1 | iex
contexa init

The CLI asks which AI model you want, prepares a local PostgreSQL with pgvector and that model, adds the dependencies, @EnableAISecurity and the settings to your project, checks that the dependencies resolve, and then asks whether to start the application. contexa reset undoes it. What it does is in Install with the CLI. The steps below do the same by hand.

Prerequisites

Before you start, make sure the following are installed and running.

Requirement Version Notes
Java 17+ CONTEXA is built with the Java 17 toolchain.
Spring Boot 3.x CONTEXA is built and tested with 3.5.4. The startup is refused on 4.x. Only servlet (Spring MVC) applications are supported, so a reactive (WebFlux) setup, Spring AOT processing and native images are refused at startup too.
PostgreSQL pgvector A database used by CONTEXA alone, where it keeps its own tables and its vector store. Create it apart from your application's database. It needs the vector extension (the code does not check the PostgreSQL version).
AI models Chat + embedding The chat model makes the decisions; the embedding model finds past records that are close in meaning. This page uses a local Ollama. OpenAI and Anthropic work too.

Database Setup

Create a database for CONTEXA alone, apart from your application's database, and turn on the vector extension. Run the SQL below as a PostgreSQL administrator. You do not create CONTEXA's tables yourself: CONTEXA creates them in this database when the application first starts.

SQL 
CREATE USER contexa WITH PASSWORD 'change-me';
CREATE DATABASE contexa OWNER contexa;
\c contexa
CREATE EXTENSION IF NOT EXISTS vector;

Ollama Models

If you use Ollama, pull a chat model and an embedding model now. The names must match the model values in the step 3 settings. If you use OpenAI for both chat and embeddings, skip this.

Shell 
ollama pull qwen3:8b
ollama pull mxbai-embed-large

Add Dependency

The single CONTEXA starter brings all five CONTEXA modules (common, core, identity, iam, autoconfigure). It does not bring Spring Security, an AI provider starter (the connection to the models) or the PgVector starter, so add them alongside, as in the examples below. The starter alone changes nothing in your application. The decision to apply security is made in step 2, when you add the annotation.

Gradle (Kotlin DSL) 
dependencies {
    implementation("ai.ctxa:spring-boot-starter-contexa:0.1.1")
    implementation("org.springframework.boot:spring-boot-starter-security")
    implementation(platform("org.springframework.ai:spring-ai-bom:1.1.8"))
    implementation("org.springframework.ai:spring-ai-starter-model-ollama")
    implementation("org.springframework.ai:spring-ai-starter-vector-store-pgvector")
}
Gradle (Groovy) 
dependencies {
    implementation 'ai.ctxa:spring-boot-starter-contexa:0.1.1'

    implementation 'org.springframework.ai:spring-ai-starter-model-ollama'

}

Choosing a provider — the examples above use Ollama. Add only the starters of the providers you use: spring-ai-starter-model-openai for OpenAI, spring-ai-starter-model-anthropic for Anthropic. Anthropic has no embedding model, so add OpenAI or Ollama for embeddings. Spring AI BOM 1.1.8 is the version CONTEXA is built and tested with.

2

Enable AI Security

Putting @EnableAISecurity on the main class turns CONTEXA on. Without it, none of CONTEXA's auto-configuration is applied, even with the starter on the classpath, so your application stays as it was.

Without attributes the annotation uses the default way, SANDBOX. It adds CONTEXA to an application that already has its own sign-in, so your application's Spring Security keeps owning sign-in, sessions and access rules. In the code this is called HOST_OWNED, meaning that the application owns sign-in. SANDBOX is the name of this way, not a test environment. CONTEXA builds no sign-in chain in this way. Instead, CONTEXA filters run right after your application's Spring Security filter chain has identified the user, and apply the stored decision on every path. CONTEXA protects its own admin console /contexa/admin/** with a chain of its own.

To leave sign-in to CONTEXA as well (CONTEXA_OWNED), use @EnableAISecurity(mode = SecurityMode.FULL). CONTEXA's chain then handles sign-in, MFA and sessions, and some of your application's responses change (what changes, annotation reference). The rest of this page assumes the default way.

Java 
@SpringBootApplication
@EnableAISecurity
public class MyApplication {

    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}

What your application must do when it owns sign-in (default) — CONTEXA can recognize your users only if your application does two things.

① Declare your own SecurityFilterChain. Without one, Spring Boot's default security asks every request for sign-in. CONTEXA reports this with a WARN log, and if the application has no way to sign users in either (no UserDetailsService, AuthenticationProvider or AuthenticationManager bean of its own), the start is refused.

② In a filter of that chain, put the signed-in user into the SecurityContext as an authenticated Authentication. CONTEXA's filters read it to learn whose request it is. Without it, CONTEXA sees an anonymous request and applies no decision.

The admin console /contexa/admin/** is protected by CONTEXA's own chain and administrator sign-in, so your chain does not need to protect it. Example code is in Connect your existing sign-in in the installation guide.

Under the hood — @EnableAISecurity imports the configuration class AiSecurityConfiguration through AiSecurityImportSelector. When your application has no PlatformConfig bean, it creates a default PlatformConfig, but a sign-in chain is built from it only when CONTEXA owns sign-in (CONTEXA_OWNED).

3

Configure

Write three things in application.yml: the database your application already uses (leave it as it is), the dedicated CONTEXA database (required) and the AI models.

YAML 
spring:
  application:
    name: my-app                     # do not start it with contexa-
  datasource:                        # your application's default database
    url: jdbc:postgresql://localhost:5432/myapp
    username: myapp
    password: ${MYAPP_DB_PASSWORD}

contexa:
  datasource:                        # dedicated Contexa database (required)
    url: jdbc:postgresql://localhost:5432/contexa
    username: contexa
    password: ${CONTEXA_DB_PASSWORD}
  llm:
    selection:
      chat:
        mode: dynamic-priority       # the default, written exactly like this
        priority: ollama
      embedding:
        mode: fixed                  # the default
        priority: ollama
    chat:
      ollama:
        base-url: http://127.0.0.1:11434
        model: qwen3:8b
        keep-alive: 30m
    embedding:
      ollama:
        dedicated-runtime-enabled: false
        model: mxbai-embed-large
        dimensions: 1024

The dedicated CONTEXA database is required — without contexa.datasource.url the startup stops with the message contexa.datasource.url must be configured for @EnableAISecurity. The same address as your application database (spring.datasource.url) is refused by default too. Do not set contexa.datasource.isolation.contexa-owned-application: true in an existing application. It declares that the CONTEXA database also serves as your application's database, so your application's default database connection can become the CONTEXA database, and the capability check (the startup check that the required parts are present) gets stricter.

Application name — when spring.application.name starts with contexa-, CONTEXA treats the application as part of CONTEXA itself and runs the capability check as FAIL_FAST. The startup then stops when a required part such as the chat model or the vector store is missing. In an ordinary application the same problem is only reported in an ERROR log and the application keeps starting. Use a name that does not start with contexa-.

Ollama settings — when you set contexa.llm.chat.ollama.base-url, CONTEXA builds the chat model that talks to that Ollama server itself, and the embedding model on the same server, so you do not need to set Spring AI's spring.ai.ollama.*. With an empty model, chat uses qwen3:8b and embeddings use mxbai-embed-large. keep-alive is how long the chat model stays in memory. dimensions is the size of the embedding vectors (default 1024). dedicated-runtime-enabled: true runs only the embeddings on another Ollama server, whose address goes in contexa.llm.embedding.ollama.base-url.

OpenAI and Anthropic — to use one of these instead of Ollama, change two things. First, put the provider key in the Spring AI settings, not under contexa.llm: spring.ai.openai.api-key, spring.ai.anthropic.api-key. Second, set contexa.llm.selection.chat.priority to that provider for chat, and contexa.llm.selection.embedding.priority to openai or ollama for embeddings (Minimal settings).

Model priority — contexa.llm.selection.chat.priority takes a comma-separated provider list (ollama, anthropic, openai); the default is openai,anthropic,ollama. CONTEXA looks for each provider's model in that order. When a provider cannot be used, it moves to the next one, and when none of the listed providers works, it uses any available model, even one that is not listed. contexa.llm.selection.chat.mode chooses how the model is picked: dynamic-priority (default) follows the list order, fixed uses a single provider, and spring-primary uses the Spring @Primary bean. Write the value exactly in this lower-case, hyphenated form. Embeddings use a single provider with fixed, because the vector dimension is fixed.

4

Run & Verify

Start the application, then check that CONTEXA is on in three ways: the startup log, the auto-configuration report and the Actuator endpoints.

Shell 
# Gradle
./gradlew bootRun

# Maven
mvn spring-boot:run

Verify: Startup Log

When startup finishes, look for these lines in the log. The first two together show that CONTEXA is on.

  • [IamSeedData] OSS schema provenance verified. — the tables in the dedicated CONTEXA database are ready. On the first start, CONTEXA creates them just before this line.
  • Skipping Contexa-owned authentication chain bootstrap in HOST_OWNED mode — CONTEXA is on in the default way, where your application owns sign-in. CONTEXA skipped building a sign-in chain.
  • An ERROR-level [ContexaCapability] ... — a required part such as the chat model or the vector store is missing. The application keeps starting (it stops only when its name starts with contexa-), but as it is no decision will be made (Troubleshooting).

Verify: Auto-Configuration Report

When you start Spring Boot with the --debug flag, it prints a report of the auto-configurations it applied. Use that report to see which CONTEXA auto-configurations were applied.

Shell 
./gradlew bootRun --args='--debug'

In the report's positive matches, look for io.contexa auto-configurations such as CoreInfrastructureAutoConfiguration, CoreDataAutoConfiguration and CoreLLMAutoConfiguration. Without @EnableAISecurity they are all left out.

Verify: Actuator Endpoints

With spring-boot-starter-actuator in your application you can use the health endpoint and the contexacapabilities endpoint, which shows the result of CONTEXA's capability check (the check that its required parts are present). The contexacapabilities endpoint is not open over the web by default, so add it to Spring Boot's management.endpoints.web.exposure.include.

Shell 
curl http://localhost:8080/actuator/health
curl http://localhost:8080/actuator/contexacapabilities

Database required — CONTEXA stays off when it cannot use its dedicated database. What you see depends on the problem.

When CONTEXA cannot connect (it retries for about 5 seconds), or the database account is not allowed to create the extensions CONTEXA needs (such as vector): in the default way the application starts without CONTEXA, and the log has one ERROR line that begins Contexa's database cannot be used. When CONTEXA owns sign-in, the application does not start.

When only some CONTEXA tables exist in the database: the startup stops with Contexa schema is partially installed. Use an empty database, or restore a verified backup.

Before running, check that contexa.datasource.* is right and that the database and the vector extension exist.

Method-Level Security

Protect Your First Method

Put @Protectable on the methods you want to protect with AI decisions. When a protected method is called, CONTEXA treats the user's request as something to analyze, and first applies any decision already stored for that user.

Java 
@Service
public class OrderService {

    @Protectable
    public Order getOrder(Long orderId) {
        return orderRepository.findById(orderId)
                .orElseThrow(() -> new OrderNotFoundException(orderId));
    }
}

When a protected method is called, CONTEXA checks in this order. If a check fails, the method does not run.

  1. Sign-in. The caller must be signed in: a Spring Authentication must exist at call time. A call without one, or with an anonymous one, is refused. This check applies only when the operating mode is shadow mode (SHADOW) or enforce mode (ENFORCE); the default is ENFORCE. A call on a thread that holds neither a web request nor a user (a scheduled job, for example) has no one to decide for, so it runs and only the fact that it ran is recorded.
  2. Policies. The policies written for this method are evaluated. If a policy denies the call, the method does not run. When no policy targets the method, the default decision applies, which is permit (PERMIT).
  3. Stored decision. If a block (BLOCK), step-up (CHALLENGE) or review (ESCALATE) decision is stored for the user, the call is refused. In shadow mode the call is not refused: it passes and a log line is written.
  4. Run and analysis request. When every check passes, the method runs, and when it ends CONTEXA sends a request to analyze the call. The response does not wait for the decision. The decision is made in the background and applies from the same user's next call (see sync = true below).

With sync = true, the decision is made inside the call, after the policy check and before the method runs. In enforce mode the call is refused unless the decision is ALLOW, and the response takes that much longer.

Common @Protectable Attributes

Attribute Type Default Description
ownerField String "" The name of the field (or getter) used for row-level owner checks. When a method policy condition calls hasPermission(...), CONTEXA reads this value from the target object and compares it with the signed-in user's name (a user with the ROLE_ADMIN authority skips the check). Empty means no owner check.
sync boolean false With true the decision is made inside the call, before the method runs (the response takes longer). With false only an analysis request is sent after the method ends, and the decision is made in the background and applies from the next call.

There are nine attributes in all. Besides the two in the table, they are verificationRequired, category, sensitivity, actions, importance, privileged and exportSensitive. All of them are in the @Protectable reference.

AI Decisions

What Happens Next — The Five Decisions

When CONTEXA analyzes a request, it creates a decision (ZeroTrustAction), stores it per user, and applies it from that user's next request. There are five decisions, listed below. A decision is applied only when the operating mode is enforce mode (ENFORCE, the default).

Decision Status code Valid for Behavior
ALLOW 200 15 minutes The request is processed as usual. The 15 minutes is the default; contexa.security.zerotrust.allow-validity changes it.
BLOCK 403 No expiry The request is refused. The decision stays in force until an administrator releases it, or, when the administrator has allowed it, until the user passes block-release MFA. When CONTEXA owns sign-in, the user's authorities become just ROLE_BLOCKED.
CHALLENGE 401 1,800 s Step-up authentication (MFA) is required. An API request receives 401, and a browser is sent to the step-up page. When CONTEXA owns sign-in, the user's authorities become just ROLE_MFA_REQUIRED.
ESCALATE 423 300 s Held for review. The caller is told to wait until the review ends (an API request gets 423, a browser a waiting page). When CONTEXA owns sign-in, the user's authorities become just ROLE_REVIEW_REQUIRED.
PENDING_ANALYSIS Passes (503) — No decision is stored yet. The request goes on and analysis starts. An AI agent request or a sync = true method cannot go on without a decision, so it is decided in place and refused with 503 when no decision can be obtained. When CONTEXA owns sign-in, ROLE_PENDING_ANALYSIS is added to the user's original authorities.

The ROLE_... authorities in the table are decision markers. CONTEXA puts them in the user's authority list only when CONTEXA owns sign-in, and ALLOW keeps the original authorities. When your application owns sign-in (the default), CONTEXA does not change your application's authorities. Its filters and @Protectable read the stored decision and give the same responses.

The operating mode is set with contexa.security.zerotrust.mode. When you first adopt CONTEXA, you can use shadow mode (SHADOW): requests are analyzed and decisions are recorded, but no request is stopped (Start Safely in Shadow Mode).

An AI model makes the decision — the decision engine gathers the facts of the request (sign-in information, behavioral baseline, past decision records and more) and asks an AI model, so you get decisions without writing policy rules. Analysis happens when a protected method (@Protectable) is called. A plain URL request that is not a protected method is not analyzed; it only has the stored decision applied. By default the decision is made in the background after the method ends. A stored decision is applied on every path even when your application owns sign-in (the default): CONTEXA's filters, which run right after your application's security chain has identified the user, check the stored decision, and CONTEXA checks it once more before a @Protectable method runs. When CONTEXA owns sign-in, the same filters run inside CONTEXA's chain. Details are in Decision engine.
